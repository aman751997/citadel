<h2 id="prologue">Prologue · Four questions, four tools</h2>

Every problem here is a **graph**: things (courses, letters, accounts, points) joined by **edges** (rules, shared emails, cables). Edges may be **directed** (one-way: "b before a") or **undirected** (two-way), and may carry a **weight** (a cost, a time, a price). In code you almost always store a graph as an **adjacency list**: for every node, the list of edges leaving it. Building it is O(V + E), and every algorithm below starts there.

Plain breadth-first and depth-first search, flood fills and island counting live in the <a href={`${BASE}dsa/lessons/graphs/`}>Graphs</a> lesson. This one is about four tools for the questions plain search answers badly:

1. **Topological sort**: an order that respects every "before" rule, or proof that none exists.
2. **Union-find**: which group each node belongs to, as edges keep arriving.
3. **Dijkstra's algorithm**: the cheapest route from one source when no weight is negative.
4. **Minimum spanning tree** (Prim's or Kruskal's): the cheapest set of edges that connects everything.

And one more for the awkward cases: **Bellman-Ford**, which relaxes every edge in rounds and survives negative weights and limits on the number of edges.

Ask three questions about every tool. The answers *are* the tool:

| Tool | What is settled? | Why is the move safe? | When do I stop? |
|---|---|---|---|
| Topological sort | Every node already popped | A node is popped only once nothing it waits for is left | The queue is empty |
| Union-find | Every group's root | Linking two roots merges whole groups and splits nothing | The edges run out |
| Dijkstra | Every node popped with its current distance | Weights are never negative, so no later route can undercut it | The heap is empty |
| MST (Prim's) | Every point inside the tree | The cheapest edge leaving the tree is always safe to add | Every point is inside |
| Bellman-Ford | Every distance that uses at most r edges, after round r | Each round adds exactly one more edge to every route | After the allowed number of rounds |

### When this pattern fires

- **"Prerequisites", "dependencies", "must happen before", "is there a valid order?"** Checking every ordering is n! work; following every path from every node to hunt for a cycle is O(V · (V + E)). Kahn's algorithm does it in **O(V + E)**.
- **"Groups", "merge", "connected", "same set?", "the extra edge".** Re-running a search after every new edge costs O(V + E) each time. Union-find makes each edge **near-constant amortised**.
- **"Cheapest", "fastest", "minimum total time" with weights that are never negative.** Enumerating routes is exponential. Dijkstra is **O((V + E) log V)**.
- **"Connect all", "minimum cost to link every ...".** Trying edge subsets is exponential. Prim's and Kruskal's are **O(E log E)**, or **O(V²)** for a dense graph.
- **"At most k stops", or negative weights.** Bellman-Ford with k + 1 rounds: **O(k · (V + E))**.

<h2 id="playground">Playground · You make every move</h2>

Three drills. **Kahn's queue:** seed the queue with every node that waits on nothing, pop one, cut its outgoing edges, and know when an empty queue means a cycle. **Union-find:** find both roots, then either merge the groups or flag the edge as the one that closes a loop. **The Dijkstra heap:** pop the cheapest entry, skip it if the table already knows better, relax its edges. Say the reason **before** pulling the lever.

<h2 id="course-schedule">Chapter 1 · Course Schedule</h2>

### Problem

There are `numCourses` courses, `0` to `numCourses − 1`. Each pair `[a, b]` means **you must take `b` before `a`**. Can you finish every course?

`numCourses = 4`, `[[1,0],[2,0],[3,1],[3,2]]` gives `true` (take 0, then 1 and 2, then 3). `numCourses = 3`, `[[1,0],[1,2],[2,1]]` gives `false`: 1 and 2 wait on each other.

### How to recognise it

- "Prerequisites", "dependencies", "must happen before".
- The question is whether a valid order **exists**, which is the same as asking whether the rules contain a **cycle**.
- The graph is **directed**: "a before b" is not "b before a".

### Brute force

Try every ordering of the courses and test each against every rule: O(n! · E). A smarter brute force starts a DFS from every course and checks whether it can walk back to itself: O(V · (V + E)). Both redo work. The graph already tells you which courses can go first.

### Intuition

Some courses wait on nothing. Take those. Once they are taken, some other courses have nothing left to wait for. Repeat. If you can keep going until every course is taken, the rules are consistent. If you get stuck with courses left over, every leftover course is still waiting on another leftover course: they wait on each other in a loop.

To track "what is each course still waiting for", count the edges running into it. Draw each rule as a directed edge **`b → a`** (prerequisite first). The count of edges into a node is its **in-degree**.

### Algorithm

1. Build `next[b]` (the courses that need `b`) and `indegree[a]` (how many prerequisites `a` has).
2. Put every course with `indegree 0` in a queue.
3. While the queue is not empty: pop a course, count it as taken, and for each course it points to, decrement its in-degree. If that reaches 0, push it.
4. Return `taken == numCourses`.

### Java solution

<HintLadder hints={hints.canFinish}>

```java id=canFinish
public boolean canFinish(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    int[] indegree = new int[numCourses];
    for (int[] p : prerequisites) {                  // [a, b]: b must come before a
        next.get(p[1]).add(p[0]);                    // track b -> a
        indegree[p[0]]++;
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int c = 0; c < numCourses; c++) if (indegree[c] == 0) ready.add(c);
    int taken = 0;
    while (!ready.isEmpty()) {
        int c = ready.poll();
        taken++;
        for (int d : next.get(c))
            if (--indegree[d] == 0) ready.add(d);    // its last prerequisite just finished
    }
    return taken == numCourses;                      // leftovers sit on, or behind, a cycle
}
```

</HintLadder>

### Why it works

- **Settled:** a course's in-degree equals the number of its prerequisites not yet popped. A course enters the queue exactly when that number is 0, so every pop respects every rule.
- **Why leftovers mean a cycle:** suppose course `x` is never popped. Then its in-degree never reached 0, so some prerequisite `y` of `x` was also never popped. The same argument applies to `y`, giving a `z`, and so on. There are finitely many courses, so walking backwards along never-popped prerequisites must revisit one: a cycle. Conversely, every course on a cycle waits for the one before it, so none can reach 0.
- **When we stop:** when the queue is empty.

</Figure>

### Complexity

**O(V + E) time, O(V + E) space** for the adjacency list, the in-degrees and the queue. Every course is enqueued at most once and every edge is cut exactly once.

### The second tool: three colours

Depth-first search finds the same cycle. Walk forward along edges and colour every course:

- **white**: not visited yet;
- **grey**: on the path you are walking right now;
- **black**: finished. Everything reachable from it has been explored, and it leads to no cycle.

An edge into a **grey** course points back onto your own path: **a cycle**. An edge into a **black** course is harmless.

<DryRun title="Three colours on the diamond: black is not a cycle" frames={colourFrames(4, [[0, 1], [0, 2], [1, 3], [2, 3]], { 0: [40, 110], 1: [150, 40], 2: [150, 180], 3: [270, 110] })} predict />

<DryRun title="Three colours finds a real cycle" frames={colourFrames(3, [[0, 1], [1, 2], [2, 0]], { 0: [160, 40], 1: [260, 170], 2: [60, 170] })} predict />

```java id=canFinishDfs
private static final int WHITE = 0, GREY = 1, BLACK = 2;

public boolean canFinish(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    for (int[] p : prerequisites) next.get(p[1]).add(p[0]);
    int[] colour = new int[numCourses];              // all WHITE
    for (int c = 0; c < numCourses; c++)
        if (colour[c] == WHITE && hasCycle(c, next, colour)) return false;
    return true;
}

private boolean hasCycle(int u, List<List<Integer>> next, int[] colour) {
    colour[u] = GREY;                                // u is on the path we are walking
    for (int v : next.get(u)) {
        if (colour[v] == GREY) return true;          // a track back onto our own path
        if (colour[v] == WHITE && hasCycle(v, next, colour)) return true;
    }
    colour[u] = BLACK;                               // everything after u is cycle-free
    return false;
}
```

**O(V + E) time.** The recursion can go as deep as the longest path (up to V). At LeetCode's 2,000 courses that is fine; for much deeper graphs prefer Kahn's, which uses no recursion.

<Reveal q="Why three colours? Wouldn't a single visited flag do?">

"Visited" mixes up two different things: *on my current path* (a cycle if I reach it again) and *finished earlier* (completely safe). The diamond shows the difference. Walk 0 → 1 → 3, finish, back up, then 0 → 2 → 3: course 3 is visited, but it is **not** on the current path. A one-flag DFS reports a cycle there and returns `false` for a schedule that is perfectly possible.

</Reveal>

### Edge cases and mistakes

- No prerequisites at all: every in-degree is 0, so the answer is `true`.
- A self-loop `[a, a]` is a cycle: the course waits on itself.
- Duplicate pairs are harmless as long as the list and the count agree.
- Reversed edges still pass the cycle check (see the next question), which is why the direction bug only shows up in Course Schedule II.

The classic bug is the one-flag DFS:

```java fragment
if (visited[v]) return true;      // BUG: "seen before" is not "on my path"; the diamond looks like a cycle
```

On `numCourses = 4`, `[[1,0],[2,0],[3,1],[3,2]]` it returns `false`; the answer is `true`.

### Practice

<Reveal q="Why does the direction of the edge matter so much, when a reversed cycle is still a cycle?">

For **this** question it doesn't: reversing every edge turns a cycle into a cycle and an acyclic graph into an acyclic graph, so `canFinish` gives the same answer either way. That is exactly why the direction bug survives Course Schedule I and only shows up in Course Schedule II, where the order comes out backwards. Build `b → a` from the start and you never have to think about it.

</Reveal>

**Variations to try:** return the number of courses that can be taken; detect a cycle in an undirected graph (that is union-find, Chapter 6).

<h2 id="course-schedule-ii">Chapter 2 · Course Schedule II</h2>

### Problem

Same input as Chapter 1. Return **any** order in which all courses can be taken, or an **empty array** if none exists.

`numCourses = 4`, `[[1,0],[2,0],[3,1],[3,2]]` gives `[0,1,2,3]` (`[0,2,1,3]` is also accepted). `numCourses = 2`, `[[1,0],[0,1]]` gives `[]`.

### How to recognise it

- "Return an order", "a valid schedule", "build order".
- The same dependency graph as Chapter 1, but now you need the order itself, not just yes or no.

### Brute force

Try all n! permutations and test each against every rule. A less wasteful brute force repeatedly scans all courses for one whose prerequisites are all taken: O(V · (V + E)) because each pick costs a scan. Kahn's queue makes "which course is ready?" free.

### Intuition

You already built the order in Chapter 1 without writing it down. Each course stepped off the queue at the moment its last prerequisite was taken. **The pop order is the answer.** Write each pop into the next slot of the result, and check the count at the end.

### Algorithm

1. Build the edges `b → a` and the in-degrees exactly as before.
2. Queue every course with in-degree 0.
3. Pop a course, write it into `order[placed++]`, cut its edges, and queue any course that reaches 0.
4. If `placed == numCourses`, return `order`. Otherwise return an empty array.

### Java solution

<HintLadder hints={hints.findOrder}>

```java id=findOrder
public int[] findOrder(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    int[] indegree = new int[numCourses];
    for (int[] p : prerequisites) {
        next.get(p[1]).add(p[0]);                    // b -> a: the prerequisite comes first
        indegree[p[0]]++;
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int c = 0; c < numCourses; c++) if (indegree[c] == 0) ready.add(c);
    int[] order = new int[numCourses];
    int placed = 0;
    while (!ready.isEmpty()) {
        int c = ready.poll();
        order[placed++] = c;                         // the pop order IS the timetable
        for (int d : next.get(c))
            if (--indegree[d] == 0) ready.add(d);
    }
    return placed == numCourses ? order : new int[0];
}
```

</HintLadder>

Using a min-heap instead of the queue gives the smallest order in dictionary order, at O(V log V + E).

### Why it works

When course `c` is popped, its in-degree is 0, so every prerequisite of `c` was popped, and written, earlier. Every edge therefore points from an earlier slot to a later one, which is exactly what a valid order means.

- **Settled:** the filled prefix of `order` is a valid order of the courses taken so far.
- **Why the move is safe:** a course is only popped when nothing it waits for is left.
- **When we stop:** the queue is empty; the count tells you whether all courses were placed.

### Complexity

**O(V + E) time and space.**

### Edge cases and mistakes

- Cycle: fewer than `numCourses` placed, so return `new int[0]`, not a partial list.
- `numCourses = 1` with no pairs: `[0]`.
- Several valid orders exist; the judge accepts any, so do not rely on a specific one.

The classic bug is building the edge as `a → b` (`next.get(p[0]).add(p[1])`). The graph is still acyclic, so nothing crashes, but on `numCourses = 2`, `[[1, 0]]` the answer comes out as `[1, 0]`: course 1 before its own prerequisite.

### Practice

<Reveal q="Can depth-first search produce the order too?">

Yes: **reverse post-order**. A course "finishes" in the DFS only after everything that must come after it has finished, so listing courses as they finish gives a valid order backwards. Reverse it at the end. A grey-to-grey edge still means a cycle.

```java id=findOrderDfs
public int[] findOrder(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    for (int[] p : prerequisites) next.get(p[1]).add(p[0]);
    int[] colour = new int[numCourses];              // 0 white, 1 grey, 2 black
    List<Integer> finished = new ArrayList<>();
    for (int c = 0; c < numCourses; c++)
        if (colour[c] == 0 && !visit(c, next, colour, finished)) return new int[0];
    Collections.reverse(finished);                   // last to finish goes first
    return finished.stream().mapToInt(Integer::intValue).toArray();
}

private boolean visit(int u, List<List<Integer>> next, int[] colour, List<Integer> finished) {
    colour[u] = 1;
    for (int v : next.get(u)) {
        if (colour[v] == 1) return false;            // cycle
        if (colour[v] == 0 && !visit(v, next, colour, finished)) return false;
    }
    colour[u] = 2;
    finished.add(u);                                 // everything that must follow u is listed already
    return true;
}
```

<h2 id="alien-dictionary">Chapter 3 · Alien Dictionary</h2>

### Problem

An alien language uses lowercase English letters in an unknown order. You get a list of `words` that is **already sorted** lexicographically by that order. Return a string containing **every letter that appears in the words, each exactly once**, in an order consistent with the list. If several orders work, LeetCode accepts any of them. If no order could produce the list, return `""`. (LeetCode Premium · LintCode 892.)

`["wrt","wrf","er","ett","rftt"]` gives `"wertf"`. `["abc","ab"]` gives `""`.

"Sorted lexicographically" means: compare two words at their **first differing position**; the word with the earlier letter there comes first. If one word runs out before any difference, it is a **prefix** of the other, and the shorter word comes first. So `["abc", "ab"]` is impossible under every alphabet.

### How to recognise it

- Sorted data with a hidden ordering, and you must recover the ordering.
- Each pair of neighbours gives a "this before that" rule: dependencies again.
- "Any valid order" or "return empty if contradictory": topological sort.

### Brute force

Try every permutation of the letters (up to 26!) and check whether the word list is sorted under it. Exponential. The list itself tells you the rules directly.

### Intuition

Compare two **neighbouring** words. They agree for a while, then differ at one position. That single difference is the only thing the dictionary decided: the letter in the first word comes before the letter in the second. Everything after that position carries no information. Collect those rules, and you have prerequisites again: **letters are nodes, rules are edges, and the answer is a topological order**.

### Dry run

Watch each pair produce at most one rule, then Kahn's algorithm run over the letters. When several letters are ready at once, the smallest goes first, so the answer is one fixed string.

</Figure>

### Algorithm

1. **Nodes:** every letter that appears anywhere, even letters that end up with no rule. They still belong in the answer.
2. **Edges:** for each **adjacent** pair of words, find the first position where they differ; that gives one edge, `first word's letter → second word's letter`, and **nothing else**. If they never differ and the first word is longer, return `""` at once.
3. Store each rule once (a `Set`), and count in-degrees only for new rules.
4. Run Kahn's algorithm over the letters. If fewer letters come out than went in, the rules contradict each other (a cycle): return `""`.

### Java solution

<HintLadder hints={hints.alienOrder}>

```java id=alienOrder
public String alienOrder(String[] words) {
    Map<Character, Set<Character>> next = new HashMap<>();
    Map<Character, Integer> indegree = new HashMap<>();
    for (String w : words)
        for (char c : w.toCharArray()) { next.putIfAbsent(c, new HashSet<>()); indegree.putIfAbsent(c, 0); }
    for (int i = 0; i + 1 < words.length; i++) {
        String a = words[i], b = words[i + 1];
        int len = Math.min(a.length(), b.length()), j = 0;
        while (j < len && a.charAt(j) == b.charAt(j)) j++;
        if (j == len) {
            if (a.length() > b.length()) return "";   // "abc" before "ab": no alphabet does that
            continue;                                 // a prefix before the longer word: no rule
        }
        if (next.get(a.charAt(j)).add(b.charAt(j)))   // first difference only; count each rule once
            indegree.merge(b.charAt(j), 1, Integer::sum);
    }
    PriorityQueue<Character> ready = new PriorityQueue<>();   // smallest letter first: one fixed answer
    for (Map.Entry<Character, Integer> e : indegree.entrySet()) if (e.getValue() == 0) ready.add(e.getKey());
    StringBuilder order = new StringBuilder();
    while (!ready.isEmpty()) {
        char c = ready.poll();
        order.append(c);
        for (char d : next.get(c))
            if (indegree.merge(d, -1, Integer::sum) == 0) ready.add(d);
    }
    return order.length() == indegree.size() ? order.toString() : "";   // short = a cycle of rules
}
```

</HintLadder>

The min-heap makes the answer the **smallest valid order in normal alphabetical order**. LeetCode accepts any valid order, so a plain queue also passes there; LintCode's version asks for that smallest order when several exist (check its statement for its exact tie rule), and the heap gives it.

### Why it works

- **Why adjacent pairs are enough:** an alphabet is consistent with the list exactly when the list is sorted under it, and a list is sorted exactly when **every adjacent pair** is in order (lexicographic order is transitive). So the adjacent pairs carry every rule there is.
- **Why only the first difference:** the dictionary decided the order of two words at their first difference and never looked further. `"ab"` before `"ba"` says `a` comes before `b`; it says nothing about `b` and `a` in the second position.
- **Settled and stopping:** every edge you add is a rule the list proves, and every rule the list proves is implied by your edges. A letter order is valid exactly when it is a topological order of the letter graph.

### Complexity

**O(C) time**, where C is the total number of characters in all words: comparing neighbours touches each character at most twice, and the letter graph has at most 26 nodes and 26 × 25 rules, so sorting it is constant-size work. **O(1) extra space** beyond that, since everything is bounded by the alphabet.

### Edge cases and mistakes

- A prefix listed after the longer word (`["abc","ab"]`): return `""`.
- A letter that appears in no rule still goes in the answer.
- Identical neighbouring words, or a prefix before its longer word: no rule, no error.
- Adding a rule for **every** differing position instead of only the first.

The classic bug is skipping the prefix check. `["abc", "ab"]` then yields no rules at all, and the code happily returns an order of `a`, `b`, `c` instead of `""`.

### Practice

<Reveal q="Two neighbour pairs can produce the same rule twice. Does that break the in-degree count?">

Only if you count it twice in one place and once in another. The code above stores each letter's successors in a `Set` and increments the in-degree **only when the set actually changes**, so a repeated rule is a no-op. (Keeping duplicates in both the list and the count is also consistent; mixing the two is the bug.)

</Reveal>

**Variations to try:** return whether the order is **unique** (the queue must never hold two letters at once); validate that a given alphabet sorts the list.

<h2 id="connected-components">Chapter 4 · Number of Connected Components</h2>

### Problem

`n` nodes, `0` to `n − 1`, and a list of undirected `edges`. Return how many connected pieces (components) the graph has. (LeetCode Premium · LintCode search.)

`n = 5`, `[[0,1],[1,2],[3,4]]` gives `2`. `n = 4`, no edges, gives `4`.

### How to recognise it

- "Groups", "connected", "merge", "same set?".
- Edges **arrive one at a time**, or you only care about who ends up together, not the routes.
- No direction, no weights.

### Brute force

Keep a label per node. For each edge, relabel every node that carries one endpoint's label with the other's: O(n) per edge, O(n · E) overall. For a fixed edge list, DFS or BFS from each unvisited node counts components in O(V + E), which is already fine. The trouble starts when you need answers **between** edges, or when you need the edge that closes a loop (Chapter 6).

### Intuition

Make every group a little tree and name the group by the tree's **root**. Each node stores one number, `parent[x]`: the node it points to. A root points to itself. To ask "are `a` and `b` in the same group?", follow parents from each until you reach a root. Same root, same group.

To merge two groups, don't touch members: point **one root at the other**. That moves a whole tree in one write and splits nothing.

Two refinements keep the trees short:

- **Path compression.** While `find` walks up, re-point every node it passes straight at the root. The next `find` from any of them is one hop.
- **Union by size.** Always hang the **smaller** group's root under the larger one's. A node only gets one level deeper when its group at least doubles, so no tree is taller than log₂ n.

With both, any sequence of m operations on n nodes costs **O(m · α(n))**, where α is the **inverse Ackermann function**. It grows so slowly that α(n) is at most 4 for any n you could ever store. In an interview say: **near-constant amortised time per operation**. (With only one refinement you get O(log n) amortised; with neither, a single find can cost O(n).)

### Dry run

### Algorithm

1. `parent[i] = i`, `size[i] = 1`, `sets = n`.
2. `find(x)`: if `parent[x] != x`, set `parent[x] = find(parent[x])`. Return `parent[x]`.
3. `union(a, b)`: find both roots. If equal, return `false` (this edge closes a loop). Otherwise hang the smaller root under the larger, add the sizes, decrement `sets`, return `true`.
4. For every edge call `union`; return `sets`.

### Java solution

The union-find class below is written once and reused for the rest of Part Two, for Kruskal's algorithm and for two side quests.

```java id=dsu group=uf
static class DSU {
    final int[] parent, size;
    int sets;                                        // how many separate clans remain
    DSU(int n) {
        parent = new int[n];
        size = new int[n];
        sets = n;
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }   // everyone heads their own clan
    }
    int find(int x) {
        if (parent[x] != x) parent[x] = find(parent[x]);   // path compression: point straight at the root
        return parent[x];
    }
    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;                  // already one clan: this edge closes a cycle
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;                             // smaller clan's head joins the larger clan's head
        size[ra] += size[rb];
        sets--;
        return true;
    }
}
```

The recursive `find` is safe here: union by size keeps every tree at most log₂ n tall, so the recursion is at most about 17 deep for 100,000 nodes.

<HintLadder hints={hints.countComponents}>

```java id=countComponents group=uf
public int countComponents(int n, int[][] edges) {
    DSU dsu = new DSU(n);
    for (int[] e : edges) dsu.union(e[0], e[1]);     // each real merge removes one clan
    return dsu.sets;
}
```

</HintLadder>

### Why it works

Every group is a tree hanging from its root, and union only ever re-points a **root**, so it moves a whole tree and splits nothing.

- **Settled:** after each edge, the groups are exactly the connected components of the edges processed so far, and `sets` equals their number.
- **Why the move is safe:** two nodes are connected by the edges seen so far exactly when their roots match.
- **When we stop:** when the edges run out.

### Complexity

**O(n + E · α(n)) time, O(n) space.** No adjacency list is ever built.

### Edge cases and mistakes

- No edges: the answer is `n`.
- A duplicate edge or an edge inside one group: `union` returns `false`, the count does not change.
- A self-loop `[a, a]`: same root, no change.

The classic bug is "union" without finding the roots, `parent[e[1]] = e[0]`, then counting roots. On `n = 3`, edges `[[0, 1], [2, 1]]`, the second edge re-points 1 from 0 to 2 and tears 0 off its group: you count 2 roots (0 and 2), but everything is connected. The answer is 1.

### Practice

<Reveal q="Depth-first search also counts components in O(V + E). Why bother with union-find?">

For a fixed list of edges, DFS or BFS is just as good: start a search from every unvisited node and count the starts. Union-find wins when **edges arrive one at a time** and you need answers in between ("are these two connected yet?"), when you need **the edge that closes a cycle** (Chapter 6), and when you want Kruskal's algorithm (Chapter 8). It also needs no adjacency list. Name both in an interview, and say which property of the problem decided it.

</Reveal>

**Variations to try:** return the size of the largest component; answer "are x and y connected?" after each edge.

<h2 id="graph-valid-tree">Chapter 5 · Graph Valid Tree</h2>

### Problem

`n` nodes, `0` to `n − 1`, and undirected `edges`. Return `true` if the edges form a **tree**: connected, with no cycle. (LeetCode Premium · LintCode 178.)

`n = 5`, `[[0,1],[0,2],[0,3],[1,4]]` gives `true`. `n = 5`, `[[0,1],[1,2],[2,3],[1,3],[1,4]]` gives `false`: there is a loop.

### How to recognise it

- "Is this a tree?", "exactly one path between any two nodes", "connected and acyclic".
- The two properties (connected, no cycle) suggest a count plus a union-find pass.

### Brute force

For every edge, remove it and search to see whether the graph stays connected, or search for a cycle from every node: O(E · (V + E)). A single DFS with parent tracking is O(V + E) and also fine. The union-find version is shorter and reuses Chapter 4.

### Intuition

A tree on `n` nodes has **exactly `n − 1` edges**. That alone is not enough, but it is half the proof. A forest (no cycle) with `c` pieces has exactly `n − c` edges, because each piece is a tree with one fewer edge than nodes. So **no cycle + `n − 1` edges forces `c = 1`**: connected. That is a tree.

So: if `edges.length != n − 1`, return `false`. Otherwise union every edge; if any union finds both ends already in one group, there is a cycle: return `false`. Otherwise return `true`.

### Algorithm

1. If `edges.length != n − 1`, return `false`.
2. Create union-find with `n` nodes.
3. For each edge, call `union`. If it returns `false`, return `false`.
4. Return `true`.

### Java solution

<HintLadder hints={hints.validTree}>

```java id=validTree group=uf
public boolean validTree(int n, int[][] edges) {
    if (edges.length != n - 1) return false;         // too few to connect, or too many to avoid a loop
    DSU dsu = new DSU(n);
    for (int[] e : edges)
        if (!dsu.union(e[0], e[1])) return false;    // both ends already connected: a loop
    return true;                                     // n - 1 edges and no loop: one piece
}
```

</HintLadder>

### Why it works

The edge count rules out "too few edges to connect everything"; the cycle check rules out "an edge wasted on a loop". Together they leave only trees.

- **Settled:** while no union has failed, the edges processed so far form a forest, and the group count is `n` minus the number of edges processed.
- **When we stop:** after all `n − 1` edges, or at the first failed union.

### Complexity

**O(n + E · α(n)) time, O(n) space.**

### Edge cases and mistakes

- `n = 1`, no edges: a tree. The code returns `true` without running a single union.
- Two pieces, no loop: the count check catches it.
- A loop plus an isolated node: the right count, but the union check catches it.

The classic bug is checking only one half. "No union failed" alone says `true` for `n = 4`, `[[0, 1], [2, 3]]` (two pieces). "Exactly `n − 1` edges" alone says `true` for `n = 4`, `[[0, 1], [1, 2], [2, 0]]` (a loop, and node 3 alone). Both are `false`.

<Reveal q="n = 1 and no edges. Tree?">

Yes. One node is a tree with zero edges, and `0 == n − 1`. The code returns `true` without running a single union. (Edge cases like this are free when the rule is a formula rather than a special case.)

</Reveal>

<h2 id="redundant-connection">Chapter 6 · Redundant Connection</h2>

### Problem

A tree on `n` nodes, labelled **`1` to `n`**, had one extra edge added. You get all `n` edges in order. Return an edge whose removal leaves a tree; if several qualify, return **the one that occurs last** in the input.

`[[1,2],[1,3],[2,3]]` gives `[2,3]`. `[[1,2],[2,3],[3,4],[1,4],[1,5]]` gives `[1,4]`.

### How to recognise it

- "The extra edge", "the edge that creates a cycle", "return the last such edge".
- Edges arrive in order, and you are asked about the first moment the structure stops being a tree.

### Brute force

Before adding each edge, search the graph built so far to see whether its ends are already connected: O(E · (V + E)). Another way: remove each edge from last to first and test whether what remains is a tree. Union-find answers "already connected?" in near-constant time.

### Intuition

Replay the edges in order through union-find. The first edge whose union **fails**, because both ends already share a root, is the answer. Why the last edge of the cycle? A tree plus one edge has **exactly one cycle**, and the removable edges are exactly the edges on it. The edges before the failing one form a forest, so the failing edge's ends were joined by a path of **earlier** edges: the rest of the cycle. Every other cycle edge therefore comes earlier in the input, which is the "last one" tie-break.

  <Rail fig={figures.surplus} name="surplus" />
</Figure>

### Dry run

The array has an unused slot 0, because nodes are numbered from 1. That is the same trick the Java uses (size `n + 1`).

### Algorithm

1. Create union-find with `edges.length + 1` slots (nodes are `1` to `n`; ignore slot 0).
2. For each edge in order, call `union`.
3. The first edge for which `union` returns `false` is the answer. Return it.

### Java solution

<HintLadder hints={hints.redundant}>

```java id=findRedundantConnection group=uf
public int[] findRedundantConnection(int[][] edges) {
    DSU dsu = new DSU(edges.length + 1);             // junctions are 1..n, and there are n edges
    for (int[] e : edges)
        if (!dsu.union(e[0], e[1])) return e;        // already connected: this track closes the loop
    return new int[0];                               // unreachable for valid input
}
```

</HintLadder>

### Why it works

- **Settled:** before each edge, the processed edges form a forest, and the groups are its pieces.
- **Why the move is safe:** a failing union means a path of earlier edges already joins the ends, so this edge completes the one and only cycle.
- **When we stop:** at the first failure. No later union can fail, because there is only one cycle.

### Complexity

**O(n · α(n)) time, O(n) space.**

### Edge cases and mistakes

- The extra edge may be the very last edge, or the very first cycle edge to appear (then it is the last edge of the cycle in input order).
- A duplicate of an earlier edge (`[1,2]` twice) is the extra edge: the second copy fails.

The classic bug is `new DSU(edges.length)`. The nodes are numbered `1` to `n`, so node `n` is out of bounds: on `[[1, 2], [1, 3], [2, 3]]` the structure has slots 0 to 2, so the second edge's `find(3)` throws `ArrayIndexOutOfBoundsException`. Size it `n + 1` and ignore slot 0.

### Practice

<Reveal q="What changes if the graph is directed (Redundant Connection II)?">

A lot. In a rooted tree with one extra directed edge, the extra edge either gives some node **two parents**, or creates a **cycle**, or both. You must find a node with in-degree 2, try removing each of its two parent edges, and use union-find on the rest to see which removal leaves a valid rooted tree. Same structure, more case analysis: a good transfer test once this chapter feels easy.

<h2 id="network-delay">Chapter 7 · Network Delay Time</h2>

### Problem

`n` nodes, `1` to `n`. `times[i] = [u, v, w]` is a **one-way** edge from `u` to `v` taking `w` time (`w` is never negative). A signal starts at node `k`. Return the time for **every** node to receive it (the largest shortest-path distance), or `−1` if some node never does.

`times = [[2,1,1],[2,3,1],[3,4,1]]`, `n = 4`, `k = 2` gives `2`. `times = [[1,2,1]]`, `n = 2`, `k = 2` gives `−1`.

### How to recognise it

- "Shortest", "cheapest", "minimum time" from one source on a **weighted** graph.
- Weights are non-negative.
- Plain BFS is the wrong tool: it counts edges, not total weight.

### Brute force

Enumerate every route from `k` to every node and keep the cheapest: exponential. Bellman-Ford relaxes all E edges V − 1 times, O(V · E): correct, but slower than needed when weights are non-negative. BFS fails because a two-edge route can be cheaper than a one-edge route.

### Intuition

Keep `dist[]`, the cheapest route found so far to each node (∞ at the start, 0 for the source). Always expand the node with the **smallest** known distance next. Why is that one safe to finish? Any other route to it must leave the settled nodes through some entry that is still waiting, and that entry already costs at least as much. From there the route only **adds** non-negative weights, so nothing can undercut it. A min-heap of `(distance, node)` entries finds the cheapest unsettled node quickly.

An entry can become **stale**: the node was reached again later by a cheaper route, and the old entry is still in the heap. Skip it when it pops.

Node 1's first offer is 4, but 0→2→1 costs 1 + 2 = 3; node 3's first offer is 6, but 0→2→1→3 costs 4. Final distances 0, 3, 1, 4; the last node hears at time 4. Green edges form the tree of cheapest routes.">

</Figure>

Watch the heap, the distance array and which edge is being relaxed. Stale entries get skipped when they pop.

### Algorithm

1. `dist[k] = 0`, every other `dist` is ∞. The min-heap holds `(dist, node)` entries, starting with `(0, k)`.
2. Pop the **cheapest** entry `(d, u)`. If `d > dist[u]`, it is **stale**: skip it.
3. Otherwise `d` is final for `u`. For every edge `u → v` with weight `w`: if `d + w < dist[v]`, set `dist[v] = d + w` and push `(dist[v], v)`.
4. When the heap is empty, if any `dist` is ∞ return `−1`; otherwise return the largest `dist`.

### Java solution

<HintLadder hints={hints.networkDelay}>

```java id=networkDelayTime
public int networkDelayTime(int[][] times, int n, int k) {
    List<List<int[]>> out = new ArrayList<>();
    for (int i = 0; i <= n; i++) out.add(new ArrayList<>());          // nodes are 1..n
    for (int[] t : times) out.get(t[0]).add(new int[]{t[1], t[2]});
    int[] dist = new int[n + 1];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[k] = 0;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));   // [dist, node]
    heap.add(new int[]{0, k});
    while (!heap.isEmpty()) {
        int[] top = heap.poll();
        int d = top[0], u = top[1];
        if (d > dist[u]) continue;                   // stale ticket: u was settled cheaper
        for (int[] e : out.get(u)) {
            int v = e[0], nd = d + e[1];
            if (nd < dist[v]) { dist[v] = nd; heap.add(new int[]{nd, v}); }
        }
    }
    int last = 0;
    for (int v = 1; v <= n; v++) {
        if (dist[v] == Integer.MAX_VALUE) return -1; // never reached
        last = Math.max(last, dist[v]);
    }
    return last;
}
```

</HintLadder>

### Why it works

- **Settled:** every popped, non-stale node has its final distance; every other node's `dist` is the cheapest route found so far whose last step leaves a settled node.
- **Why the move is safe:** when `(d, u)` is popped and not stale, every other route to `u` must leave the settled nodes through an entry still in the heap. That entry costs **at least `d`** (the heap popped `d` first), and the rest of the route only adds non-negative weights.
- **When we stop:** the heap is empty.

**Why it fails with negative edges.** The argument rests on "the rest of the route only adds". A negative weight breaks it. With three nodes A, B, C: A→B costs 2, A→C costs 3, C→B costs **−2**. Dijkstra pops A, then pops B at 2 and declares it final. Only afterwards does it pop C at 3 and discover A→C→B costs 3 − 2 = 1.

<Figure caption="A three-node counterexample. B is popped and settled at 2 before C is explored; the true cheapest distance to B is 3 + (−2) = 1. With negative weights, 'cheapest entry in the heap' is no longer 'final'.">
  <Rail fig={figures.negative} name="negative" />
</Figure>

Step through the textbook version that never revisits a settled node. It settles B at 2 and never fixes it.

### Complexity

**O((V + E) log V) time, O(V + E) space.** The heap can hold up to one entry per successful relaxation (at most E), and log E ≤ 2 log V. `d + e[1]` never overflows: we only relax from popped nodes, whose `dist` is finite and at most 100 × (n − 1).

### Edge cases and mistakes

- Some node unreachable: its `dist` stays ∞, so return `−1`.
- `n = 1`: the answer is `0`.
- Zero-weight edges are fine; negative ones are not (use Bellman-Ford).
- Nodes are numbered from 1: size the arrays `n + 1`.

The classic bug is locking a node the first time it is **offered** instead of when it is **popped**.

```java fragment
if (!seen[v]) { seen[v] = true; dist[v] = d + w; heap.add(new int[]{dist[v], v}); }   // BUG: first offer wins
```

On `times = [[1,2,5],[1,3,1],[3,2,1]]`, `n = 3`, `k = 1`, node 2 is locked at 5 before 1→3→2 (cost 2) is found: the answer comes out 5 instead of 2.

### Practice

<Reveal q="Our lazy version pushes a new entry whenever dist improves. Doesn't that repair the negative case?">

On that tiny example, by luck: C relaxes C→B, writes `dist[B] = 1` and pushes `(1, B)`, which is popped and processed again. But B was already *treated as final* once, and anything computed from B's old distance has to be redone. On larger graphs with negative edges this re-processing can happen exponentially many times in the worst case, and a **negative cycle** makes it loop forever. The guarantee ("popped means final") is gone. With negative weights, use **Bellman-Ford** (Chapter 9).

</Reveal>

<Reveal q="What if you delete the stale check, `if (d > dist[u]) continue`?">

The answers stay correct: relaxing from a stale distance `d > dist[u]` offers `d + w`, which can never beat the `dist[u] + w` already offered. But every stale entry rescans its node's edges, so the work grows. The check is one line; keep it.

</Reveal>

**Variations to try:** print the actual route (store a `parent` array); find the cheapest route to one target and stop as soon as it is popped.

<h2 id="min-cost-points">Chapter 8 · Min Cost to Connect All Points</h2>

### Problem

`points[i] = [x, y]`. Connecting two points costs their **Manhattan distance** `|x1 − x2| + |y1 − y2|`. Return the minimum total cost so that every point is connected to every other (directly or through others).

`[[0,0],[2,2],[3,10],[5,2],[7,0]]` gives `20`. `[[3,12],[-2,5],[-4,1]]` gives `18`.

### How to recognise it

- "Connect everything", "minimum total cost to link all", "cheapest network".
- You do not care about the route between any particular pair, only the **total** cost.
- The answer is a **tree**: a loop would contain an edge you could remove.

### Brute force

Try every subset of `n − 1` edges and keep the cheapest one that connects everything: C(E, n − 1), exponential. Building every edge and sorting is better (Kruskal's), but with `n(n − 1)/2` edges (about 500,000 at n = 1,000) it is heavier than it needs to be.

### Intuition

The **cut property** is the whole proof. Split the points into any two groups. The **cheapest edge crossing between the groups** belongs to some minimum spanning tree (MST). Why: take an MST that doesn't use it. Adding it creates a loop, and that loop must cross the split a second time through some other edge that costs at least as much. Swap them: still connected, still a tree, no more expensive.

- **Prim's algorithm** grows one tree. The split is "inside the tree" versus "outside"; each round adds the cheapest edge leaving the tree.
- **Kruskal's algorithm** sorts every edge by cost and keeps one exactly when it joins two different groups (union-find). The edge it keeps is the cheapest crossing between its own group and everyone else.

**Which for this problem?** Every pair of points is a candidate edge, so the graph is **dense**. Prim's **without a heap** is the clean choice: keep `best[v]`, the cheapest edge from the tree to each outside point; each round scan for the smallest, add it, and update `best` using the newcomer. That is **O(n²) time, O(n) space**, and no edge list is ever built. Kruskal's must build and sort all the edges: **O(n² log n) time, O(n²) space**.

  <Rail fig={figures.cable} name="cable" />
</Figure>

### Algorithm

1. `best[v] = ∞` for every point, `best[0] = 0`, `inTree` empty, `total = 0`.
2. Repeat `n` times: pick the point `u` outside the tree with the smallest `best[u]`; mark it inside; add `best[u]` to `total`.
3. For every point `v` still outside, compute the distance from `u` to `v`; if it is smaller than `best[v]`, update `best[v]`.
4. Return `total`.

### Java solution

<HintLadder hints={hints.minCostPoints}>

```java id=minCostConnectPoints
public int minCostConnectPoints(int[][] points) {
    int n = points.length;
    int[] best = new int[n];                         // cheapest known cable from the tree to each point
    Arrays.fill(best, Integer.MAX_VALUE);
    boolean[] inTree = new boolean[n];
    best[0] = 0;                                     // start anywhere: point 0 joins for free
    int total = 0;
    for (int round = 0; round < n; round++) {
        int u = -1;
        for (int v = 0; v < n; v++)                  // the closest point outside the tree
            if (!inTree[v] && (u == -1 || best[v] < best[u])) u = v;
        inTree[u] = true;
        total += best[u];
        for (int v = 0; v < n; v++) {                // the newcomer may offer cheaper cables
            if (inTree[v]) continue;
            int d = Math.abs(points[u][0] - points[v][0]) + Math.abs(points[u][1] - points[v][1]);
            if (d < best[v]) best[v] = d;
        }
    }
    return total;
}
```

</HintLadder>

```java id=minCostConnectPointsKruskal group=uf
public int minCostConnectPointsKruskal(int[][] points) {
    int n = points.length;
    List<int[]> cables = new ArrayList<>();          // [cost, i, j]
    for (int i = 0; i < n; i++)
        for (int j = i + 1; j < n; j++)
            cables.add(new int[]{Math.abs(points[i][0] - points[j][0]) + Math.abs(points[i][1] - points[j][1]), i, j});
    cables.sort((a, b) -> Integer.compare(a[0], b[0]));
    DSU dsu = new DSU(n);
    int total = 0;
    for (int[] c : cables) {
        if (dsu.sets == 1) break;                    // n - 1 cables laid: everyone is connected
        if (dsu.union(c[1], c[2])) total += c[0];    // joins two clans: the cheapest such cable is safe
    }
    return total;
}
```

Kruskal's shines when the edges are **given** and sparse (E much smaller than V²): **O(E log E)** for the sort, near-constant per union. For a complete graph of points, the O(n²) Prim's above uses less time and far less memory.

</Reveal>

### Why it works

- **Settled:** the edges chosen so far are part of some MST, and `best[v]` is the cheapest edge from the current tree to `v`.
- **Why the move is safe:** the cut property. The cheapest edge crossing from the tree to the outside is never regretted.
- **When we stop:** every point is inside the tree, after `n` rounds.

### Complexity

**O(n²) time, O(n) space.** Each single distance is at most 4 × 10⁶, and LeetCode's answer fits in an `int`. A heap-based Prim's (`(cost, point)` entries, skip points already inside) is O(E log V) = O(n² log n) here: correct, but slower on a complete graph.

### Edge cases and mistakes

- One point: the answer is `0`.
- Duplicate points: distance 0 between them, they join for free.
- Ties between equal edges: any choice leads to the same minimum total.

The classic bug is taking the `n − 1` cheapest edges without checking that each joins two different groups. On `[[0,0],[1,0],[0,1],[10,10]]` the three cheapest edges (1, 1, 2) form a triangle among the first three points and leave (10,10) unconnected: total 4. The right answer is 1 + 1 + 19 = 21.

### Practice

<Reveal q="Is the minimum spanning tree also the tree of cheapest routes from one point?">

No. An MST minimises the **total** edge cost, not any particular trip. Take A–B 2, A–C 2, B–C 1: the cheapest routes from A use A–B and A–C, total 4. The cheapest network uses B–C plus one of the others, total 3. If the question is "fastest from the depot to each city", use Dijkstra.

</Reveal>

**Variations to try:** return the edges chosen, not just the total; find the second-cheapest spanning tree; connect points but some pairs are not allowed.

<h2 id="cheapest-flights">Chapter 9 · Cheapest Flights Within K Stops</h2>

### Problem

`n` cities, `flights[i] = [from, to, price]` (one-way, prices positive). Return the cheapest price from `src` to `dst` using **at most `k` stops** (at most **`k + 1` flights**), or `−1` if impossible.

`n = 3`, `[[0,1,100],[1,2,100],[0,2,500]]`, `src = 0`, `dst = 2`, `k = 1` gives `200`. With `k = 0` it gives `500`.

### How to recognise it

- Shortest or cheapest route **with a limit on the number of edges**.
- A plain shortest path (Dijkstra) might use too many stops.
- Or: negative weights, where Dijkstra is not allowed.

### Brute force

Explore every route of at most `k + 1` flights with DFS: about out-degree^(k + 1) routes. BFS level by level is the same idea with pruning. Dijkstra with a visited set is tempting but wrong: it settles each city once at its cheapest price, and that cheapest price may already have used up the stops.

### Intuition

Think in **rounds**. Round `r` finds the cheapest price to every city using at most `r` flights. Keep `cost[]`, ∞ everywhere except `cost[src] = 0`. In each round, try every flight once: `prev[from] + price < cost[to]` lowers `cost[to]`.

There is one rule that matters: **read from a copy of last round's board, write to the new one.** Without the copy, a price written earlier in the same round can be read later in that round, and one round chains **two** flights. Whether it happens depends on the order of the flights in the input, the worst kind of bug.

<Figure caption="Flights 0→1 (100), 1→2 (100), 0→2 (500), from 0 to 2. With k = 0 the answer is 500, the direct flight. In place, round 1 processes 0→1 (cost[1] = 100) and then 1→2 reads that fresh 100: cost[2] = 200, a two-flight trip in a round that allows one. With k = 1 the answer really is 200.">
  <Rail fig={figures.tickets} name="tickets" />
</Figure>

### Dry run

Two arrays: `prev` (read only) and `cost` (being written). With `k = 1` there are two rounds.

<DryRun title="Bellman-Ford with k = 1: read only last round's table" frames={bellmanFrames(3, [[0, 1, 100], [1, 2, 100], [0, 2, 500]], 0, 2, 1, { 0: [40, 110], 1: [160, 40], 2: [280, 110] })} predict />

<Trace title="Read only last round's table" steps={flightSteps} takeaway="Remember: k stops = k + 1 rounds. Copy the table at the start of each round and read only from the copy." />

### Algorithm

1. `cost[src] = 0`, everything else ∞.
2. Repeat `k + 1` times: `prev = cost.clone()`.
3. For every flight `[from, to, price]`: if `prev[from]` is not ∞ and `prev[from] + price < cost[to]`, set `cost[to] = prev[from] + price`.
4. Return `cost[dst]`, or `−1` if it is still ∞.

### Java solution

<HintLadder hints={hints.cheapestFlights}>

```java id=findCheapestPrice
public int findCheapestPrice(int n, int[][] flights, int src, int dst, int k) {
    final int INF = Integer.MAX_VALUE;
    int[] cost = new int[n];
    Arrays.fill(cost, INF);
    cost[src] = 0;
    for (int round = 1; round <= k + 1; round++) {   // round r allows r flights
        int[] prev = cost.clone();                   // Snapshot: last round's board, read-only
        for (int[] f : flights) {
            int from = f[0], to = f[1], price = f[2];
            if (prev[from] != INF && prev[from] + price < cost[to]) cost[to] = prev[from] + price;
        }
    }
    return cost[dst] == INF ? -1 : cost[dst];
}
```

</HintLadder>

### Why it works

- **Settled:** after round `r` (counting from 1), `cost[v]` is the cheapest price from `src` to `v` using **at most `r` flights**.
- **Why the move is safe:** `prev` holds the best with at most `r − 1` flights; every new price is one of those plus exactly one flight; and `cost` started as a copy of `prev`, so routes with fewer flights are kept.
- **When we stop:** after exactly `k + 1` rounds.

### Complexity

**O(k · (n + E)) time, O(n) space.** Prices are at most 10⁴ and a route has at most n ≤ 100 flights, so prices stay far inside `int`.

### Edge cases and mistakes

- `k = 0`: one round, only direct flights.
- `src == dst`: the answer is `0`.
- `dst` unreachable within the limit: `−1`.
- `prev[from]` still ∞: skip, or the addition overflows.

The classic bug is relaxing in place, without the copy. On flights `[[0,1,100],[1,2,100],[0,2,500]]`, `src = 0`, `dst = 2`, `k = 0`, the first round chains 0→1→2 and returns **200** instead of **500**.

### Practice

<Reveal q="Plain Bellman-Ford updates in place and still works. Why is this different?">

Plain Bellman-Ford wants the cheapest route with **any** number of edges. Reading a fresh value only finds good routes sooner, and after V − 1 rounds every shortest path (at most V − 1 edges) has been found, so in-place is fine, even faster. Here the **number of edges is the constraint**, so each round must add exactly one. Plain Bellman-Ford also handles **negative** weights, and if a V-th round still improves something, a negative cycle is reachable.

</Reveal>

<Reveal q="Can BFS do it, one level of flights at a time?">

Yes: each BFS level is one more flight. Carry `(city, price)` pairs; push a city again only when the new price beats the best price seen for it so far. A pruned pair is dominated by an earlier one with no more flights and no higher price, so nothing is lost. Stop after `k + 1` levels.

```java id=findCheapestPriceBfs
public int findCheapestPrice(int n, int[][] flights, int src, int dst, int k) {
    List<List<int[]>> out = new ArrayList<>();
    for (int i = 0; i < n; i++) out.add(new ArrayList<>());
    for (int[] f : flights) out.get(f[0]).add(new int[]{f[1], f[2]});
    int[] best = new int[n];
    Arrays.fill(best, Integer.MAX_VALUE);
    best[src] = 0;
    Deque<int[]> level = new ArrayDeque<>();         // [city, price paid to get here]
    level.add(new int[]{src, 0});
    for (int taken = 0; taken <= k && !level.isEmpty(); taken++) {   // this level adds flight taken + 1
        for (int size = level.size(); size > 0; size--) {
            int[] cur = level.poll();
            for (int[] e : out.get(cur[0])) {
                int price = cur[1] + e[1];
                if (price < best[e[0]]) { best[e[0]] = price; level.add(new int[]{e[0], price}); }
            }
        }
    }
    return best[dst] == Integer.MAX_VALUE ? -1 : best[dst];
}
```

</Reveal>

<Reveal q="Why not just run Dijkstra and stop when the stop count runs out?">

Because Dijkstra settles each city **once**, at its cheapest price, and the cheapest price to a middle city may already have used up the changes. Take edges 0→1 (1), 1→2 (1), 0→2 (5), 2→3 (1) with k = 1. Dijkstra reaches city 2 first via 0→1→2 for 2 (two flights), marks it done, and then cannot extend it to 3 without a third flight. The legal route 0→2→3 for 6 needed city 2 at the **pricier** price 5 with **fewer** flights, and that entry is thrown away as "already settled": the answer comes out −1.

```java fragment
if (visited[city]) continue;   // BUG: a pricier entry with fewer flights can be the only one that fits
```

A correct Dijkstra must make the state **(city, flights used)** and keep an entry unless another one for the same city is no worse in **both** price and flights. That works, but it is easy to get wrong. Bellman-Ford's k + 1 rounds are simpler and fast enough here.

</Reveal>

**Variations to try:** allow negative prices (the same rounds still work); return the route; return the cheapest price for every possible `k`.

<h2 id="safe-states">Side quest 1 · Find Eventual Safe States</h2>

### Problem

`graph[i]` lists the nodes you can move to from `i`. A **terminal** node (no outgoing edges) is safe. A node is **safe** if **every** possible walk from it ends at a terminal node. Return all safe nodes in increasing order.

`[[1,2],[2,3],[5],[0],[5],[],[]]` gives `[2,4,5,6]`.

### How to recognise it

- Directed graph, "every path from here ends at...", "cannot reach a cycle".
- It looks like cycle detection, but you want the nodes that are **not** upstream of a cycle.

### Brute force

From every node, DFS over everything reachable and check whether a cycle is reachable: O(V · (V + E)). The three-colour DFS of Chapter 1 does it in one pass (a node is safe exactly when its DFS finishes black).

### Intuition

A node is unsafe exactly when some walk from it can loop forever, that is, when it can reach a cycle. Run Kahn's algorithm **backwards**. Reverse every edge, and for each node count its exits that are not yet proven safe. Terminals start at 0. When a node is proven safe, every node that leads into it loses one unproven exit; reaching 0 proves that node safe too. Nodes never popped can reach a loop.

<Figure caption="LeetCode's example, graph = [[1,2],[2,3],[5],[0],[5],[],[]]. 5 and 6 are terminal; 2 and 4 lead only to 5. Nodes 0, 1 and 3 can circle 0 → 1 → 3 → 0 forever. Safe: [2, 4, 5, 6].">
  <Rail fig={figures.safe} name="safe" />
</Figure>

### Dry run

The picture keeps the original arrows. The map counts **unproven exits** for each node. When a node is popped it is safe, and the nodes pointing at it lose one.

<DryRun title="Kahn's algorithm run backwards" frames={safeFrames([[1, 2], [2, 3], [5], [0], [5], [], []], { 0: [36, 50], 1: [122, 50], 2: [209, 50], 3: [79, 150], 4: [209, 150], 5: [288, 100], 6: [288, 180] })} predict />

### Algorithm

1. Build `into[v]`, the nodes that have `v` as an exit, and `unproven[u] = graph[u].length`.
2. Queue every node with `unproven == 0` (terminals).
3. Pop `v`, mark it safe, and for each `u` in `into[v]` decrement `unproven[u]`; at 0, queue `u`.
4. Return the safe nodes in increasing order.

### Java solution

<HintLadder hints={hints.safeStates}>

```java id=eventualSafeNodes
public List<Integer> eventualSafeNodes(int[][] graph) {
    int n = graph.length;
    List<List<Integer>> into = new ArrayList<>();    // reversed tracks: who leads into me
    for (int i = 0; i < n; i++) into.add(new ArrayList<>());
    int[] unproven = new int[n];                     // exits not yet proven safe
    for (int u = 0; u < n; u++) {
        unproven[u] = graph[u].length;
        for (int v : graph[u]) into.get(v).add(u);
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int u = 0; u < n; u++) if (unproven[u] == 0) ready.add(u);   // dead ends
    boolean[] safe = new boolean[n];
    while (!ready.isEmpty()) {
        int v = ready.poll();
        safe[v] = true;
        for (int u : into.get(v))
            if (--unproven[u] == 0) ready.add(u);    // every exit of u is now proven safe
    }
    List<Integer> answer = new ArrayList<>();
    for (int u = 0; u < n; u++) if (safe[u]) answer.add(u);
    return answer;
}
```

</HintLadder>

### Why it works

- **Settled:** a popped node has every exit proven safe, so every walk from it ends at a terminal.
- **Why the move is safe:** a node reaches 0 only when all its exits were popped.
- **When we stop:** the queue is empty. Nodes never popped have an exit that can never be proven safe: they can reach a cycle.

### Complexity

**O(V + E) time and space.**

### Edge cases and mistakes

- A self-loop counts as an exit that never becomes safe, so its node is correctly unsafe.
- A node with no edges at all is terminal, so it is safe.
- Running Kahn's forwards answers a different question (which nodes are not stuck behind a cycle).

### Practice

<Reveal q="Why reverse the edges? Couldn't you run Kahn's algorithm forwards?">

Forwards, Kahn's algorithm proves things about **what comes before** a node ("nothing upstream is stuck"). Safety is about **what comes after** ("nothing downstream can loop"). Reversing every edge swaps the two, so the same in-degree argument, now an *out*-degree argument, proves safety from the terminals backwards. The three-colour DFS also works: a node is safe exactly when its DFS finishes black.

</Reveal>

<h2 id="parallel-courses">Side quest 2 · Parallel Courses III</h2>

### Problem

You are no longer limited to one course at a time. Course `i` takes `time[i]` months, any number of courses may run at once, and a course may start the moment all its prerequisites are finished. How many months until everything is done? Relations are `[prev, next]`, courses `1` to `n`, and there is no cycle.

`n = 3`, `relations = [[1,3],[2,3]]`, `time = [3,2,5]` gives `8`.

### How to recognise it

- Dependencies with durations, "unlimited parallel work", "earliest completion".
- That is a **longest path in a DAG**, not a shortest one.

### Brute force

Recursively compute `finish(v) = time[v] + max(finish(p))` over its prerequisites, without remembering results. On a diamond-heavy graph the same finish times are recomputed exponentially often. Memoising fixes it: that is dynamic programming over the graph.

### Intuition

A course **starts** when its slowest prerequisite finishes, and finishes `time` months later. Topological order is exactly the order in which those `max`es can be computed: when a course is popped, all its prerequisites have already reported their finish times. So run Kahn's algorithm, and push each finish time forward along the edges with `start[v] = max(start[v], finish)`.

### Dry run

Courses 0 and 1 (times 3 and 2) both run at once. Course 2 (5 months) starts at 3, when the slower prerequisite finishes. Total 8.

<DryRun title="Longest path over a topological order" frames={parallelFrames(3, [[0, 2], [1, 2]], [3, 2, 5], { 0: [50, 50], 1: [50, 170], 2: [220, 110] })} predict />

### Algorithm

1. Build edges and in-degrees (relations are 1-indexed; subtract 1).
2. Queue every course with in-degree 0 and `start = 0`.
3. Pop `u`: `finish = start[u] + time[u]`; update `answer = max(answer, finish)`.
4. For each `v` after `u`: `start[v] = max(start[v], finish)`; decrement its in-degree; queue at 0.
5. Return `answer`.

### Java solution

The block also contains **Parallel Courses (unit time)**: the fewest semesters, or `−1` if there is a cycle. It is the same idea with every `time` equal to 1, peeled one level of the queue at a time.

<HintLadder hints={hints.parallelCourses}>

```java id=parallelCourses
// Parallel Courses III: relations[i] = [prev, next], courses 1..n, time[i] months for course i + 1.
public int minimumTime(int n, int[][] relations, int[] time) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] indegree = new int[n];
    for (int[] r : relations) { next.get(r[0] - 1).add(r[1] - 1); indegree[r[1] - 1]++; }
    int[] start = new int[n];                        // latest finish among prerequisites seen so far
    Deque<Integer> ready = new ArrayDeque<>();
    for (int i = 0; i < n; i++) if (indegree[i] == 0) ready.add(i);
    int answer = 0;
    while (!ready.isEmpty()) {
        int u = ready.poll();
        int finish = start[u] + time[u];             // every prerequisite of u has already reported
        answer = Math.max(answer, finish);
        for (int v : next.get(u)) {
            start[v] = Math.max(start[v], finish);
            if (--indegree[v] == 0) ready.add(v);
        }
    }
    return answer;
}

// Parallel Courses (unit time, may contain a cycle): fewest semesters, or -1.
public int minimumSemesters(int n, int[][] relations) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] indegree = new int[n];
    for (int[] r : relations) { next.get(r[0] - 1).add(r[1] - 1); indegree[r[1] - 1]++; }
    List<Integer> semester = new ArrayList<>();
    for (int i = 0; i < n; i++) if (indegree[i] == 0) semester.add(i);
    int semesters = 0, taken = 0;
    while (!semester.isEmpty()) {                    // one level of the queue = one semester
        semesters++;
        taken += semester.size();
        List<Integer> following = new ArrayList<>();
        for (int u : semester)
            for (int v : next.get(u)) if (--indegree[v] == 0) following.add(v);
        semester = following;
    }
    return taken == n ? semesters : -1;
}
```

</HintLadder>

### Why it works

- **Settled:** when a course is popped, every prerequisite has reported, so `start[u]` is its true earliest start.
- **Why the move is safe:** taking the maximum over prerequisites is exactly the "wait for the slowest one" rule.
- **When we stop:** the queue is empty. The answer is the largest finish time.

### Complexity

**O(n + relations) time and space** for both versions.

### Edge cases and mistakes

- No relations: everything runs at once, so the answer is the largest single `time`.
- Remember the 1-indexed relations and the 0-indexed `time` array.
- Adding the times along a path instead of taking the maximum over prerequisites.

### Practice

<Reveal q="Isn't the longest path supposed to be hard?">

In a general graph, yes (it is NP-hard: it contains the Hamiltonian path problem). In a **DAG** it is easy, because there are no cycles to go round: process nodes in topological order and take a `max` over incoming edges. That is dynamic programming over a topological order, the same reason Bellman-Ford's rounds work: each answer depends only on answers that are already final.

</Reveal>

<h2 id="accounts-merge">Side quest 3 · Accounts Merge</h2>

### Problem

Each record is a name followed by email addresses, and **two records belong to the same person if they share any address**. Return one record per person: the name, then all their addresses in sorted order.

`[["John","a@x","b@x"],["John","b@x","c@x"],["Mary","m@x"]]` gives `[["John","a@x","b@x","c@x"],["Mary","m@x"]]`.

### How to recognise it

- "Share any key", "belong together", transitive grouping over records.
- The things to group are not numbered; you must invent the numbering.

### Brute force

Compare every pair of records for a shared email, merge them, and repeat until nothing changes. Merging changes which pairs share emails, so you loop again: roughly O(A²) per pass over A records. Union-find makes the transitive closure automatic.

### Intuition

The nodes are **emails**, not records. Each record says "all these emails belong together". Give every distinct email a number, union every email in a record with that record's first email, then group the emails by root. Names are only labels: two different people can share a name, so **never union by name**.

### Dry run

Five emails `e0` to `e4`. Record 1 holds `e0, e1`; record 2 holds `e1, e2`; record 3 holds `e3, e4`. Each record becomes edges from its first email to the others: `e0–e1`, `e1–e2`, `e3–e4`. Two groups remain: two people.

<DryRun title="Union every email with its record's first email" frames={dsuFrames(5, [[0, 1], [1, 2], [3, 4]], { labels: ['e0', 'e1', 'e2', 'e3', 'e4'] })} predict />

### Algorithm

1. Assign each distinct email a number; remember the owner name for each email.
2. For every record, union the first email with every other email in that record.
3. Group emails by `find(email)`.
4. Sort each group, put the owner's name in front, and return all rows.

### Java solution

<HintLadder hints={hints.accountsMerge}>

```java id=accountsMerge group=uf
public List<List<String>> accountsMerge(List<List<String>> accounts) {
    Map<String, Integer> id = new HashMap<>();       // email -> its number in the register
    Map<String, String> owner = new HashMap<>();     // email -> the name on its record
    for (List<String> acc : accounts)
        for (int i = 1; i < acc.size(); i++)
            if (!id.containsKey(acc.get(i))) { id.put(acc.get(i), id.size()); owner.put(acc.get(i), acc.get(0)); }
    DSU dsu = new DSU(id.size());
    for (List<String> acc : accounts)
        for (int i = 2; i < acc.size(); i++) dsu.union(id.get(acc.get(1)), id.get(acc.get(i)));
    Map<Integer, List<String>> clans = new HashMap<>();
    for (String email : id.keySet())
        clans.computeIfAbsent(dsu.find(id.get(email)), r -> new ArrayList<>()).add(email);
    List<List<String>> merged = new ArrayList<>();
    for (List<String> emails : clans.values()) {
        Collections.sort(emails);
        List<String> row = new ArrayList<>();
        row.add(owner.get(emails.get(0)));
        row.addAll(emails);
        merged.add(row);
    }
    return merged;
}
```

</HintLadder>

### Why it works

- **Settled:** after all unions, two emails share a root exactly when a chain of records connects them.
- **Why the move is safe:** union only ever merges whole groups; belonging is transitive.
- **When we stop:** after every record has been processed.

### Complexity

**O(A log A) time, O(A) space**, where A is the total number of email entries: the sort dominates; the unions are near-constant each.

### Edge cases and mistakes

- Two people with the same name and no shared email stay separate.
- A record with a single email: no unions, still its own group.
- Union by position in the record list, not by names.

### Practice

<Reveal q="Record A has emails x and y; record B has y and z; record C has z and w. Are A and C the same person?">

Yes. A and B share y, B and C share z, so all three are one person with x, y, z, w, even though A and C share nothing directly. Belonging is **transitive**, which is exactly what union-find maintains and what a pairwise comparison of records would miss.

</Reveal>

<h2 id="evaluate-division">Side quest 4 · Evaluate Division</h2>

### Problem

You learn equations `a / b = 2.0` and `b / c = 3.0`. Answer queries such as `a / c` (6.0), or `−1.0` if the ratio cannot be determined.

`equations = [["a","b"],["b","c"]]`, `values = [2.0, 3.0]`, queries `[["a","c"],["c","a"],["a","e"],["a","a"],["x","x"]]` gives `[6.0, 0.16667, -1.0, 1.0, -1.0]`.

### How to recognise it

- Relationships with multiplicative (or additive) values between pairs; "can this be derived?".
- A chain a → b → c multiplies along the path.

### Brute force

Build a graph where `a → b` has weight `a / b` and `b → a` has weight `1 / (a / b)`. Answer each query with a DFS that multiplies weights along a path: O(V + E) per query. It is correct and fine for LeetCode's limits. Weighted union-find answers each query in near-constant time after the build.

### Intuition

A **weighted** union-find. Every variable keeps `parent[x]` **and** `ratio[x] = x / parent[x]`. During `find`, multiply ratios along the path, so after compression `ratio[x] = x / root`. Then any two variables in the same group compare through their common root: `c / d = (c / root) ÷ (d / root)`.

<Figure caption="a / b = 2 and b / c = 3 stored as weighted parent pointers a → b → c. find(a) multiplies along the walk and compresses: a now points straight at the root c with ratio 2 × 3 = 6, so a / c = 6.">
  <Rail fig={figures.ratios} name="ratios" />
</Figure>

### Dry run

Each arrow is labelled with `x / parent`. The first query triggers the compression: `ratio[a]` becomes 6.

<DryRun title="Weighted union-find" frames={ratioFrames([['a', 'b', 2], ['b', 'c', 3]], [['a', 'c'], ['c', 'a'], ['a', 'e']])} predict />

### Algorithm

1. For each equation `a / b = v`, create `a` and `b` as roots with ratio 1 if they are new.
2. Find both roots. If different, set `parent[ra] = rb` and `ratio[ra] = v · ratio[b] / ratio[a]`.
3. For a query `c / d`: if either variable was never seen, or the roots differ, answer `−1.0`. Otherwise answer `ratio[c] / ratio[d]`.

### Java solution

<HintLadder hints={hints.calcEquation}>

```java id=calcEquation
public double[] calcEquation(List<List<String>> equations, double[] values, List<List<String>> queries) {
    Map<String, String> parent = new HashMap<>();
    Map<String, Double> ratio = new HashMap<>();     // ratio(x) = x / parent(x)
    for (int i = 0; i < equations.size(); i++) {
        String a = equations.get(i).get(0), b = equations.get(i).get(1);
        for (String x : new String[]{a, b})
            if (!parent.containsKey(x)) { parent.put(x, x); ratio.put(x, 1.0); }
        String ra = find(parent, ratio, a), rb = find(parent, ratio, b);
        if (!ra.equals(rb)) {
            parent.put(ra, rb);
            ratio.put(ra, values[i] * ratio.get(b) / ratio.get(a));   // ra / rb, from a / b = v
        }
    }
    double[] answer = new double[queries.size()];
    for (int q = 0; q < queries.size(); q++) {
        String c = queries.get(q).get(0), d = queries.get(q).get(1);
        if (!parent.containsKey(c) || !parent.containsKey(d)
                || !find(parent, ratio, c).equals(find(parent, ratio, d))) answer[q] = -1.0;
        else answer[q] = ratio.get(c) / ratio.get(d);     // (c / root) / (d / root)
    }
    return answer;
}

private String find(Map<String, String> parent, Map<String, Double> ratio, String x) {
    String p = parent.get(x);
    if (p.equals(x)) return x;
    String root = find(parent, ratio, p);            // afterwards ratio(p) = p / root
    ratio.put(x, ratio.get(x) * ratio.get(p));       // x / root = (x / p) * (p / root)
    parent.put(x, root);
    return root;
}
```

</HintLadder>

### Why it works

Joining two groups needs one formula, `ra / rb = v · ratio[b] / ratio[a]`, derived in the question below.

- **Settled:** after `find(x)`, `ratio[x] = x / root`.
- **When we stop:** after every equation has been joined; queries only read.

### Complexity

**Near-linear time**: path compression alone gives O(log V) amortised per find, and LeetCode allows at most 20 equations (40 variables). A variable never seen in any equation gives `−1.0`, even for `x / x`.

### Edge cases and mistakes

- Variable not in any equation: `−1.0`, including `x / x`.
- Variables in different groups: `−1.0`.
- Remember to multiply ratios during compression, not just re-point the parent.

### Practice

<Reveal q="Union of a / b = v with roots ra and rb: what ratio does ra get?">

You want `ra / rb`. You know `a = ratio[a] · ra`, `b = ratio[b] · rb`, and `a = v · b`. So `ratio[a] · ra = v · ratio[b] · rb`, which gives **`ra / rb = v · ratio[b] / ratio[a]`**. Set `parent[ra] = rb` with that ratio, and the whole group of `ra` inherits the right rates through compression.

</Reveal>

<h2 id="min-effort">Side quest 5 · Path With Minimum Effort</h2>

### Problem

A height map `heights[r][c]`. Walk from the top-left to the bottom-right, stepping up, down, left or right. A route's **effort** is not the sum of its climbs but its **single steepest step**. Find the route with the least effort.

`[[1,2,2],[3,8,2],[5,3,5]]` gives `2`. `[[1,2,3],[3,8,4],[5,3,5]]` gives `1`.

### How to recognise it

- Shortest-path shape, but the route cost is a **max**, not a sum.
- Weighted grid, "minimise the worst step", "bottleneck".

### Brute force

Try every route and keep the one with the smallest maximum step: exponential. A simpler correct idea is binary search on the answer: for a threshold `t`, flood-fill only through steps of at most `t`.

### Intuition

Dijkstra never needed **sums**. It needed one thing: **extending a route never makes it cheaper**. `max(effort so far, next step)` has that property, since a longer route's worst step is at least as bad. So the cheapest entry in the heap is still final when popped. Replace `d + w` with `max(d, w)` and nothing else changes.

<Figure caption="LeetCode's example [[1,2,2],[3,8,2],[5,3,5]]. The route 1 → 3 → 5 → 3 → 5 down the left and along the bottom never changes height by more than 2 (gold). Any route through the 8 needs a step of at least 5.">
  <ArrayStrip name="row 0" values={[1, 2, 2]} indices={false} tones={{ 0: 'hot' }} />
  <ArrayStrip name="row 1" values={[3, 8, 2]} indices={false} tones={{ 0: 'hot', 1: 'out' }} />
  <ArrayStrip name="row 2" values={[5, 3, 5]} indices={false} tones={{ 0: 'hot', 1: 'hot', 2: 'hot' }} />
</Figure>

### Dry run

The second grid holds the best effort found so far for each square. The corner is final the moment it pops.

<DryRun title="Dijkstra with max instead of plus" frames={effortFrames([[1, 2, 2], [3, 8, 2], [5, 3, 5]])} predict />

### Algorithm

1. `effort[0][0] = 0`, all others ∞. Heap of `(effort, r, c)` starts with `(0, 0, 0)`.
2. Pop the smallest entry; skip it if stale (`e > effort[r][c]`).
3. If this is the bottom-right square, return `e`.
4. For each neighbour: `ne = max(e, |height difference|)`. If `ne < effort[nr][nc]`, update and push.

### Java solution

<HintLadder hints={hints.minEffort}>

```java id=minimumEffortPath
public int minimumEffortPath(int[][] heights) {
    int rows = heights.length, cols = heights[0].length;
    int[][] effort = new int[rows][cols];
    for (int[] r : effort) Arrays.fill(r, Integer.MAX_VALUE);
    effort[0][0] = 0;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));   // [effort, r, c]
    heap.add(new int[]{0, 0, 0});
    int[][] steps = {{1, 0}, {-1, 0}, {0, 1}, {0, -1}};
    while (!heap.isEmpty()) {
        int[] top = heap.poll();
        int e = top[0], r = top[1], c = top[2];
        if (e > effort[r][c]) continue;              // stale
        if (r == rows - 1 && c == cols - 1) return e;   // popped means final
        for (int[] s : steps) {
            int nr = r + s[0], nc = c + s[1];
            if (nr < 0 || nc < 0 || nr >= rows || nc >= cols) continue;
            int ne = Math.max(e, Math.abs(heights[nr][nc] - heights[r][c]));   // the worst step so far
            if (ne < effort[nr][nc]) { effort[nr][nc] = ne; heap.add(new int[]{ne, nr, nc}); }
        }
    }
    return effort[rows - 1][cols - 1];               // not reached: the corner is always popped above
}
```

</HintLadder>

### Why it works

- **Settled:** a popped square has the least possible worst step among all routes to it.
- **Why the move is safe:** `max` never decreases when you extend a route, the same property that made sums work.
- **When we stop:** the corner is popped, so returning then is safe.

### Complexity

**O(R · C · log(R · C)) time, O(R · C) space.**

### Edge cases and mistakes

- A single square: the answer is `0`.
- A flat map: every step is `0`, so the answer is `0`.
- Using `effort + step` instead of `max(effort, step)` answers a different problem (total climb).

### Practice

<Reveal q="Is there a second way, without a heap?">

Yes: **binary search on the answer**. For a threshold `t`, a flood fill that only takes steps of height change at most `t` tells you whether the corner is reachable. Reachability only gets easier as `t` grows, so binary search finds the smallest `t` that works: O(R · C · log H) for heights up to H. Union-find works too: sort the steps by height change and union until the two corners share a root. Three tools, one problem. Say which you would pick and why.

</Reveal>

<h2 id="choose-the-tool">When a tool breaks</h2>

Each tool here carries a condition. A wrong answer usually means the condition failed, not the code:

- **Dijkstra needs non-negative weights.** One negative edge breaks "popped means final" (Chapter 7's three nodes). Use **Bellman-Ford**, O(V · E). If every weight is the same, Dijkstra is overkill: **plain BFS** gives the same distances in O(V + E). If weights are only 0 or 1, a **0-1 BFS** with a deque does it in O(V + E).
- **Union-find cannot delete.** Once two groups merge, nothing records which edge joined them. If edges are removed over time, either reverse time offline (deletions become unions) or use heavier dynamic-connectivity structures.
- **Union-find ignores direction.** "a before b" and "b before a" look the same to it, so it can never detect a **directed** cycle. Prerequisites need a topological sort.
- **Topological sort needs a DAG.** On a graph with cycles there is no order to find; the right question becomes "which nodes are stuck?" (Kahn's leftovers) or "what are the cycles?" (strongly connected components).
- **An MST is not a set of shortest paths.** It minimises the **total** edge cost, not any particular trip. If the question is "fastest from the depot to each city", you want Dijkstra's tree of cheapest routes, which can be a different tree.
- **All pairs, small n.** When n is a few hundred and you need every pair's distance, **Floyd–Warshall**'s three nested loops (O(V³)) are simpler than running Dijkstra from every node.

<Reveal q="All weights are positive, but the question is the cheapest route with at most k edges. Dijkstra or Bellman-Ford?">

Bellman-Ford with k + 1 rounds and a copy (Chapter 9), O(k · (V + E)). Dijkstra can be adapted with (node, edges used) states, but a plain visited-set Dijkstra is wrong: it throws away pricier entries that used fewer edges. Name the constraint that decides it: **a limit on edges, not on price**.

</Reveal>

<h2 id="wider-family">Related patterns · How the other roadmap patterns connect</h2>

The shared idea: **process things in an order that makes each decision final.**

| Shared idea | Where it shows up | Where it belongs |

**Kahn's algorithm is BFS with a gate.** A node enters the queue not when it is first reached, but when its **last** incoming edge is cut. Remove the gate and you get ordinary BFS.

**Dijkstra is BFS with a heap.** When every edge weighs 1, the queue already pops in distance order; the heap is what lets unequal weights keep that promise.

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Keep the tutorial code closed. Before you write a line, write down the nodes, the edges, which tool, what is settled, why the next move is safe, and when you stop.

1. **The only possible ranking.** `n` players and a list of results "x beat y". Is the ranking of all players **uniquely** determined? Test: no results with 2 players, a straight chain, a chain plus a shortcut, and a contradiction.
2. **Wells and pipes.** `n` houses. House `i` can dig its own well for `well[i]`, or be piped to house `j` for `pipe(i, j)`. Minimum total cost so every house has water. Test: wells cheaper than every pipe, one cheap well and cheap pipes, a single house.
3. **The safest route.** Each road has a probability `p` (between 0 and 1) of getting through without a breakdown; probabilities along a route multiply. Find the most reliable route between two cities. Test: no route, a direct road worse than a two-road detour, a road with `p = 0`.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**Unique ranking:** Kahn's algorithm, plus one check: the ranking is unique exactly when **the queue never holds more than one player**. Two ready players at once means neither result decides between them. Also check that every player was popped (no contradiction). This is LeetCode's Sequence Reconstruction in disguise.

**Wells and pipes:** add a **virtual source** node, with an edge of cost `well[i]` to each house. Now "dig a well" is just another pipe, and the answer is the MST of the n + 1 nodes (Kruskal's with union-find, or Prim's from the source). The trick, turning a per-node cost into an edge from a new node, is worth remembering on its own.

**Safest route:** Dijkstra with a **max**-heap of probabilities, multiplying instead of adding. It is safe because every `p` is at most 1, so extending a route can never make it *more* reliable, the same property that made sums and maxima work. (Taking `−log p` turns it into ordinary non-negative Dijkstra, which is the proof.)

Now explain why a slightly wrong version fails one of your tests: checking only "every player popped" for uniqueness, forgetting the virtual source, a heap that pops the least reliable first. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

Graph tools do **not** automatically mean O(V + E). Count the heap (log factors), the sort (Kruskal's), the rounds (Bellman-Ford's k), and the adjacency list you build. Say the time **and** space before you code.

## Five bugs to check for

1. **The edge points the wrong way.** `[a, b]` in Course Schedule means **b → a**. Reversed edges still pass cycle checks and produce a perfectly backwards order.
2. **One colour where three are needed.** A plain visited flag in a directed DFS reports a cycle on every diamond. Grey (on the path) is not black (finished).
3. **Linking members instead of roots.** `parent[b] = a` without `find` tears `b` out of its group. Always `parent[find(b)] = find(a)`, smaller under larger, and size the array `n + 1` for 1-indexed nodes.
4. **Settling on the first offer.** In Dijkstra a node is final when its entry is **popped**, not when it is first **pushed**. And never with negative weights.
5. **Reading this round's values.** In the k-stops problem, relax from a **copy** of last round's table, or one round can chain several flights.

<h2 id="revision">Revision</h2>

**How to recognise it.** Prerequisites or "must happen before": topological sort. Groups, merging, "the extra edge", connectivity as edges arrive: union-find. Cheapest route with non-negative weights: Dijkstra. Connect everything cheaply: MST. A limit on edges, or negative weights: Bellman-Ford.

**Core algorithms.**

- **Kahn's:** count in-degrees, queue the zeros, pop and cut edges, queue what reaches zero. Fewer than n popped means a cycle.
- **Union-find:** `find` with path compression; `union` links root to root, smaller under larger; a failed union means a cycle.
- **Dijkstra:** min-heap of `(distance, node)`; skip stale entries; a popped entry is final; relax its edges.
- **Prim's / Kruskal's:** the cheapest edge crossing a cut is safe. Prim's grows one tree (O(n²) with an array on dense graphs); Kruskal's sorts edges and keeps those that join two groups.
- **Bellman-Ford:** k + 1 rounds, reading a copy of last round's table.

**Common mistakes.**

- Building the edge `a → b` for `[a, b]` in Course Schedule.
- One visited flag in a directed DFS.
- `parent[b] = a` without finding roots; array of size `n` for 1-indexed nodes.
- Settling a node when it is pushed, or using Dijkstra with negative weights.
- Relaxing in place in the k-stops problem.
- Taking the `n − 1` cheapest edges without checking for loops.

**Complexity.**

| Tool | Time | Space |
|---|---|---|
| Kahn's | O(V + E) | O(V + E) |
| Union-find | O(m · α(n)) for m operations | O(n) |
| Dijkstra (heap) | O((V + E) log V) | O(V + E) |
| Prim's (array) / Kruskal's | O(V²) / O(E log E) | O(V) / O(E) |
| Bellman-Ford, k rounds | O(k · (V + E)) | O(V) |

**Three representative problems.**

1. [Course Schedule](https://leetcode.com/problems/course-schedule/): in-degrees, a queue of zeros, leftovers mean a cycle.
2. [Redundant Connection](https://leetcode.com/problems/redundant-connection/): union-find; the first failed union is the answer.
3. [Network Delay Time](https://leetcode.com/problems/network-delay-time/): Dijkstra; popped and not stale means final.
