<h2 id="prologue">Prologue · Four ledgers on one desk</h2>

<Scene chapter="Prologue" title="The drafting office" mood="dawn">

Crossmere Junction smells of coal smoke and wet ink. On your first morning at the Crossmere & Northern Railway, the Keeper leads you past the clatter of the yard to a long desk with four ledgers on it.

The first lists which stations must be built before which. The second is a register of rival railway clans, crossed out and rewritten as families merge. The third is a toll book for the post roads. The fourth is a stack of tickets, each stamped with how many changes it allows.

*"Every clerk here can trace a line with a finger,"* she says. *"That's not the job. The job is knowing, at every moment, what is already settled — and proving that the next move can't unsettle it."*

She taps each ledger in turn. *"Four ledgers. Four promises. Which one is a question asking for?"*

</Scene>

Every problem in this book is a **graph**: things (stations, courses, letters, accounts, points) joined by **edges** (tracks, rules, shared emails, cables). Edges may be **directed** (one-way: “b before a”) or **undirected** (two-way), and may carry a **weight** (a toll, a time, a price). In code you almost always store a graph as an **adjacency list**: for every node, the list of edges leaving it. Building it is O(V + E) and every algorithm below starts there.

The plain tools — breadth-first and depth-first search, flood fills, counting islands — live in the previous town. This book is about four tools for the questions plain search answers badly:

1. **Topological sort** — an order that respects every “before” rule, or proof that none exists.
2. **Union-find** — which group each node belongs to, as edges keep arriving.
3. **Dijkstra’s algorithm** — the cheapest route from one source when weights are never negative.
4. **Minimum spanning tree** (Prim’s or Kruskal’s) — the cheapest set of edges that connects everything.

And one more for the awkward cases: **Bellman-Ford**, which relaxes every edge in rounds and survives negative weights and limits on the number of edges.

The Keeper asks her three questions here, as everywhere in the realm. Each tool answers them differently, and that answer *is* the tool:

| Tool | What is settled? | Why is the move safe? | When do I stop? |
|---|---|---|---|
| Topological sort | Every station already popped | It was popped only once nothing waited before it | The platform is empty |
| Union-find | Every clan head (root) | Linking two roots merges whole clans and splits nothing | The tracks run out |
| Dijkstra | Every town popped with its current fare | Tolls are never negative, so no later route can undercut it | The ticket rack is empty |
| MST (Prim’s) | Every point inside the network | The cheapest cable leaving the network is always safe to lay | Every point is inside |
| Bellman-Ford | Every fare that uses at most r edges, after round r | Each round adds exactly one more edge to every route | After the allowed number of rounds |

### When this pattern fires

- **“Prerequisites”, “dependencies”, “must happen before”, “is there a valid order?”** Checking every ordering is n! work; following every path from every node to hunt for a cycle is O(V · (V + E)). Kahn’s algorithm does it in **O(V + E)**.
- **“Groups”, “merge”, “connected”, “same set?”, “the extra edge”.** Re-running a search after every new edge costs O(V + E) each time. Union-find makes each edge **near-constant amortised**.
- **“Cheapest”, “fastest”, “minimum total time” with weights that are never negative.** Enumerating routes is exponential. Dijkstra is **O((V + E) log V)**.
- **“Connect all”, “minimum cost to link every …”.** Trying edge subsets is exponential. Prim’s and Kruskal’s are **O(E log E)**, or **O(V²)** for a dense graph.
- **“At most k stops”, or negative weights.** Bellman-Ford with k + 1 rounds: **O(k · (V + E))**.

<Scene chapter="Chapter 1" title="The surveyor’s prerequisites" mood="dawn">

**Problem: Course Schedule · Topological sort (Kahn’s algorithm)**

There are `numCourses` courses, `0` to `numCourses − 1`. Each pair `[a, b]` means **you must take `b` before `a`**. Can you finish every course?

Draw each rule as a directed track **`b → a`** (prerequisite first). Then:

1. **In-degree** of a course = how many tracks run into it = how many prerequisites it still waits for.
2. Every course with in-degree 0 goes on the **Ready** queue.
3. Pop a course, count it as taken, and **cut its outgoing tracks**: decrement the in-degree of every course it points to. Any course that drops to 0 joins Ready.
4. When Ready is empty, you have taken some number of courses. If it is all of them, return `true`.

<Figure caption="The diamond: [[1,0],[2,0],[3,1],[3,2]] drawn as tracks 0 → 1, 0 → 2, 1 → 3, 2 → 3. Only course 0 starts at in-degree 0. Popping 0 drops 1 and 2 to zero; popping both drops 3 from 2 to 0. All four are taken: true.">
  <Rail fig={figures.diamond} name="diamond" />
</Figure>

<Trace title="Count what each course waits for" steps={kahnSteps} takeaway="Remember: [a, b] is the track b → a. Pop only zeros; cut the popped course’s tracks; leftovers mean a cycle." />

**Why leftover courses mean a cycle.** Suppose course `x` is never popped. Then its in-degree never reached 0, so some prerequisite `y` of `x` was also never popped. The same argument applies to `y`, giving a `z`, and so on. There are only finitely many courses, so walking backwards along never-popped prerequisites must eventually revisit one: **a cycle**. Conversely, every course on a cycle waits for the one before it, so none of them can ever reach 0. Leftovers are exactly the courses that sit on a cycle or depend on one.

<Figure caption="[[1,0],[1,2],[2,1]]. Course 0 is popped, and course 1 drops from in-degree 2 to 1 — but its other prerequisite is 2, and 2 waits on 1. Ready is empty with 1 of 3 courses taken: false.">
  <Rail fig={figures.stuck} name="stuck" />
</Figure>

**What stays true:** at every moment, a course’s in-degree equals the number of its prerequisites that have **not** been popped yet. A course enters Ready exactly when all of its prerequisites have been taken, so every pop respects every rule.

<Reveal q="Why does the direction of the track matter so much, when a reversed cycle is still a cycle?">

For **this** question it doesn’t: reversing every track turns a cycle into a cycle and an acyclic graph into an acyclic graph, so `canFinish` gives the same answer either way. That is exactly why the direction bug survives Course Schedule I and only shows up in Course Schedule II, where the order comes out backwards. Build `b → a` from the start and you never have to think about it.

</Reveal>

<HintLadder hints={hints.canFinish}>

```java id=canFinish
public boolean canFinish(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    int[] indegree = new int[numCourses];
    for (int[] p : prerequisites) {                  // [a, b]: b must come before a
        next.get(p[1]).add(p[0]);                    // track b -> a
        indegree[p[0]]++;
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int c = 0; c < numCourses; c++) if (indegree[c] == 0) ready.add(c);
    int taken = 0;
    while (!ready.isEmpty()) {
        int c = ready.poll();
        taken++;
        for (int d : next.get(c))
            if (--indegree[d] == 0) ready.add(d);    // its last prerequisite just finished
    }
    return taken == numCourses;                      // leftovers sit on, or behind, a cycle
}
```

**O(V + E) time, O(V + E) space** for the adjacency list, the in-degrees and the queue. Every course is enqueued at most once and every track is cut exactly once.

</HintLadder>

### The second tool: three colours

Depth-first search can find the same cycle. Walk forward along tracks, and colour every course:

- **white** — not visited yet;
- **grey** — on the path you are walking right now;
- **black** — finished: everything reachable from it has been explored, and it leads to no cycle.

A track into a **grey** course is a track back onto your own path: **a cycle**. A track into a **black** course is harmless — that course was fully explored and is cycle-free.

```java id=canFinishDfs
private static final int WHITE = 0, GREY = 1, BLACK = 2;

public boolean canFinish(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    for (int[] p : prerequisites) next.get(p[1]).add(p[0]);
    int[] colour = new int[numCourses];              // all WHITE
    for (int c = 0; c < numCourses; c++)
        if (colour[c] == WHITE && hasCycle(c, next, colour)) return false;
    return true;
}

private boolean hasCycle(int u, List<List<Integer>> next, int[] colour) {
    colour[u] = GREY;                                // u is on the path we are walking
    for (int v : next.get(u)) {
        if (colour[v] == GREY) return true;          // a track back onto our own path
        if (colour[v] == WHITE && hasCycle(v, next, colour)) return true;
    }
    colour[u] = BLACK;                               // everything after u is cycle-free
    return false;
}
```

**O(V + E) time.** The recursion can go as deep as the longest path (up to V). At LeetCode’s 2,000 courses that is fine; for much deeper graphs prefer Kahn’s, which uses no recursion.

<Reveal q="Why three colours? Wouldn’t a single visited flag do?">

“Visited” mixes up two different things: *on my current path* (a cycle if I reach it again) and *finished earlier* (completely safe). The diamond above shows the difference. Walk 0 → 1 → 3, finish, back up, then 0 → 2 → 3: course 3 is visited, but it is **not** on the current path. A one-flag DFS reports a cycle there and returns `false` for a schedule that is perfectly possible.

</Reveal>

**Catch the bug:** the one-flag DFS.

```java fragment
if (visited[v]) return true;      // BUG: "seen before" is not "on my path"; the diamond looks like a cycle
```

On `numCourses = 4`, `[[1,0],[2,0],[3,1],[3,2]]` it returns `false`; the answer is `true`. [Solve Course Schedule](https://leetcode.com/problems/course-schedule/).

**Problem: Course Schedule II · Topological sort, returning the order**

Same input; return **any** order in which all courses can be taken, or an **empty array** if none exists.

The order in which Kahn’s algorithm pops courses **is** a valid order: a course is popped only after every course pointing into it has been popped. So write each pop into the next slot of the answer, and check the count at the end.

**Why it works:** when course `c` is popped, its in-degree is 0, so every prerequisite of `c` was popped — and written — earlier. Every track therefore points from an earlier slot to a later one, which is exactly what a valid order means.

**What stays true:** the answer’s filled prefix is a valid order of the courses taken so far, and the courses not yet written are exactly those with a prerequisite still unwritten.

<Reveal q="Can depth-first search produce the order too?">

Yes: **reverse post-order**. A course “finishes” in the DFS only after everything that must come after it has finished, so listing courses as they finish gives a valid order backwards. Reverse it at the end. A grey-to-grey track still means a cycle.

```java id=findOrderDfs
public int[] findOrder(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    for (int[] p : prerequisites) next.get(p[1]).add(p[0]);
    int[] colour = new int[numCourses];              // 0 white, 1 grey, 2 black
    List<Integer> finished = new ArrayList<>();
    for (int c = 0; c < numCourses; c++)
        if (colour[c] == 0 && !visit(c, next, colour, finished)) return new int[0];
    Collections.reverse(finished);                   // last to finish goes first
    return finished.stream().mapToInt(Integer::intValue).toArray();
}

private boolean visit(int u, List<List<Integer>> next, int[] colour, List<Integer> finished) {
    colour[u] = 1;
    for (int v : next.get(u)) {
        if (colour[v] == 1) return false;            // cycle
        if (colour[v] == 0 && !visit(v, next, colour, finished)) return false;
    }
    colour[u] = 2;
    finished.add(u);                                 // everything that must follow u is listed already
    return true;
}
```

</Reveal>

```java id=findOrder
public int[] findOrder(int numCourses, int[][] prerequisites) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < numCourses; i++) next.add(new ArrayList<>());
    int[] indegree = new int[numCourses];
    for (int[] p : prerequisites) {
        next.get(p[1]).add(p[0]);                    // b -> a: the prerequisite comes first
        indegree[p[0]]++;
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int c = 0; c < numCourses; c++) if (indegree[c] == 0) ready.add(c);
    int[] order = new int[numCourses];
    int placed = 0;
    while (!ready.isEmpty()) {
        int c = ready.poll();
        order[placed++] = c;                         // the pop order IS the timetable
        for (int d : next.get(c))
            if (--indegree[d] == 0) ready.add(d);
    }
    return placed == numCourses ? order : new int[0];
}
```

**O(V + E) time and space.** Using a min-heap instead of the queue gives the smallest order in dictionary order, at O(V log V + E).

</HintLadder>

**Catch the bug:** building the track as `a → b` (`next.get(p[0]).add(p[1])`). The graph is still acyclic, so nothing crashes — but on `numCourses = 2`, `[[1, 0]]` the answer comes out as `[1, 0]`, course 1 before its own prerequisite. **Problem: Alien Dictionary · Topological sort over letters** (LeetCode Premium · LintCode 892)

An alien language uses lowercase English letters in an unknown order. You get a list of `words` that is **already sorted** lexicographically by that order. Return a string containing **every letter that appears in the words, each exactly once**, in an order consistent with the list. If several orders work, LeetCode accepts any of them. If no order could produce the list, return `""`.

“Sorted lexicographically” means: compare two words at their **first differing position**; the word with the earlier letter there comes first. If one word runs out before any difference — it is a **prefix** of the other — the shorter word comes first. So `["abc", "ab"]` is impossible under every alphabet, and the answer is `""`.

Three steps:

1. **Nodes:** every letter that appears anywhere, even letters that end up with no rule (they still belong in the answer).
2. **Tracks:** for each **adjacent** pair of words, find the first position where they differ; that gives one track, `first word’s letter → second word’s letter`, and **nothing else**. If they never differ and the first word is longer, return `""` at once.
3. **Kahn’s algorithm** over the letters. If fewer letters come out than went in, the rules contradict each other (a cycle): return `""`.

<Figure caption="LeetCode’s example. The four neighbour pairs give four rules: wrt | wrf ⇒ t → f; wrf | er ⇒ w → e; er | ett ⇒ r → t; ett | rftt ⇒ e → r. Only w starts at in-degree 0, and each pop frees exactly one letter: wertf.">
  <Rail fig={figures.alien} name="alien" />
</Figure>

<Trace title="One rule per neighbour" steps={alienSteps} takeaway="Remember: adjacent words only, first difference only, and a longer word before its own prefix means return an empty string." />

**Why adjacent pairs are enough:** an alphabet is consistent with the list exactly when the list is sorted under it, and a list is sorted exactly when **every adjacent pair** is in order (lexicographic order is transitive). So the adjacent pairs carry every rule there is; comparing non-adjacent words could only repeat them.

**Why only the first difference:** the dictionary decided the order of two words at their first difference and never looked further. `"ab"` before `"ba"` says `a` comes before `b` — it says nothing at all about `b` and `a` in the second position.

**What stays true:** every track you add is a rule the list proves, and every rule the list proves is implied by your tracks. A letter order is valid exactly when it is a topological order of the letter graph.

<Reveal q="Two neighbour pairs can produce the same rule twice. Does that break the in-degree count?">

Only if you count it twice in one place and once in another. The code below stores each letter’s successors in a `Set` and increments the in-degree **only when the set actually changes**, so a repeated rule is a no-op. (Keeping duplicates in both the list and the count is also consistent; mixing the two is the bug.)

</Reveal>

```java id=alienOrder
public String alienOrder(String[] words) {
    Map<Character, Set<Character>> next = new HashMap<>();
    Map<Character, Integer> indegree = new HashMap<>();
    for (String w : words)
        for (char c : w.toCharArray()) { next.putIfAbsent(c, new HashSet<>()); indegree.putIfAbsent(c, 0); }
    for (int i = 0; i + 1 < words.length; i++) {
        String a = words[i], b = words[i + 1];
        int len = Math.min(a.length(), b.length()), j = 0;
        while (j < len && a.charAt(j) == b.charAt(j)) j++;
        if (j == len) {
            if (a.length() > b.length()) return "";   // "abc" before "ab": no alphabet does that
            continue;                                 // a prefix before the longer word: no rule
        }
        if (next.get(a.charAt(j)).add(b.charAt(j)))   // first difference only; count each rule once
            indegree.merge(b.charAt(j), 1, Integer::sum);
    }
    PriorityQueue<Character> ready = new PriorityQueue<>();   // smallest letter first: one fixed answer
    for (Map.Entry<Character, Integer> e : indegree.entrySet()) if (e.getValue() == 0) ready.add(e.getKey());
    StringBuilder order = new StringBuilder();
    while (!ready.isEmpty()) {
        char c = ready.poll();
        order.append(c);
        for (char d : next.get(c))
            if (indegree.merge(d, -1, Integer::sum) == 0) ready.add(d);
    }
    return order.length() == indegree.size() ? order.toString() : "";   // short = a cycle of rules
}
```

**O(C) time**, where C is the total number of characters in all words: comparing neighbours touches each character at most twice, and the letter graph has at most 26 nodes and 26 × 25 rules, so sorting it is constant-size work. **O(1) extra space** beyond that, since everything is bounded by the alphabet.

The min-heap makes the answer the **smallest valid order in normal alphabetical order**. LeetCode accepts any valid order, so a plain queue also passes there; LintCode’s version asks for that smallest order when several exist (check its statement for its exact tie rule), and the heap gives it.

</HintLadder>

**Catch the bug:** skipping the prefix check. `["abc", "ab"]` then yields no rules at all, and the code happily returns an order of `a`, `b`, `c` instead of `""`. The other classic slips: forgetting letters that appear in no rule (they must still be in the answer), and adding a rule for **every** differing position instead of only the first. [Solve Alien Dictionary](https://leetcode.com/problems/alien-dictionary/) · [LintCode 892](https://www.lintcode.com/problem/892/).

<Scene chapter="Chapter 4" title="The clan register" mood="dusk">

**Problem: Number of Connected Components in an Undirected Graph · Union-find**

`n` nodes, `0` to `n − 1`, and a list of undirected `edges`. Return how many connected pieces (components) the graph has.

**Union-find** (a disjoint-set union, or DSU) keeps one number per node:

- `parent[x]` — the node `x` points to. A node with `parent[x] == x` is a **root**: the head of its clan. Following parents from any node always ends at its root.
- **`find(x)`** follows parents up to the root. Two nodes are in the same clan exactly when they have the same root.
- **`union(a, b)`** finds both roots. Same root: nothing to do — and this edge **closes a cycle**, because `a` and `b` were already connected. Different roots: point one root at the other, merging the two whole clans.

Count components by starting at `n` and subtracting one for **every union that merges two different clans**.

Two refinements make it fast:

- **Path compression.** While `find` walks up, re-point every node it passes straight at the root. The next `find` from any of them is one hop.
- **Union by size (or rank).** Always hang the **smaller** clan’s root under the larger’s. A node only gets one level deeper when its clan at least doubles, so no tree is ever taller than log₂ n.

With both, any sequence of m operations on n nodes costs **O(m · α(n))**, where α is the **inverse Ackermann function**. It grows so slowly that α(n) is at most 4 for any n you could ever store. Say it plainly in an interview: **near-constant amortised time per operation**. (With only one of the two refinements you get O(log n) amortised; with neither, a single find can cost O(n).)

<Figure caption="Path compression. Before: find(4) walks 4 → 3 → 1 → 0 (a register merged carelessly, with no size rule). After: every node on that walk points straight at root 0, so the next find from 4 or 3 is one hop. Node 2 was not on the walk and is untouched.">
  <Rail fig={figures.forestBefore} name="forest-before" />
  <Rail fig={figures.forestAfter} name="forest-after" />
</Figure>

<Trace title="Merge heads, never members" steps={componentSteps} takeaway="Remember: union links root to root, smaller under larger. Each successful union removes exactly one clan." />

**Why it works:** every clan is a tree hanging from its root, and union only ever re-points a **root**, so it moves a whole tree and splits nothing. Two nodes are connected by the edges seen so far exactly when their roots match.

**What stays true:** after each edge, the clans are exactly the connected components of the edges processed so far, and `sets` equals their number.

The register below is written once and reused for the rest of Part Two, and again for Kruskal’s algorithm and two side quests:

```java id=dsu group=uf
static class DSU {
    final int[] parent, size;
    int sets;                                        // how many separate clans remain
    DSU(int n) {
        parent = new int[n];
        size = new int[n];
        sets = n;
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }   // everyone heads their own clan
    }
    int find(int x) {
        if (parent[x] != x) parent[x] = find(parent[x]);   // path compression: point straight at the root
        return parent[x];
    }
    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;                  // already one clan: this edge closes a cycle
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;                             // smaller clan's head joins the larger clan's head
        size[ra] += size[rb];
        sets--;
        return true;
    }
}
```

The recursive `find` is safe here: union by size keeps every tree at most log₂ n tall, so the recursion is at most about 17 deep for 100,000 nodes.

<Reveal q="Depth-first search also counts components in O(V + E). Why bother with union-find?">

For a fixed list of edges, DFS or BFS is just as good: start a search from every unvisited node and count the starts. Union-find wins when **edges arrive one at a time** and you need answers in between (“are these two connected yet?”), when you need **the edge that closes a cycle** (Chapter 6), and when you want Kruskal’s algorithm (Chapter 8). It also needs no adjacency list. Name both in an interview, and say which property of the problem decided it.

</Reveal>

**Problem: Graph Valid Tree · Union-find + edge count** (LeetCode Premium · LintCode 178)

`n` nodes, `0` to `n − 1`, and undirected `edges`. Return `true` if the edges form a **tree**: connected, with no cycle.

A tree on `n` nodes has **exactly `n − 1` edges**. That alone is not enough, but it is half the proof:

- A graph with no cycle is a forest. A forest with `c` pieces has exactly **`n − c`** edges (each piece is a tree, with one fewer edge than nodes).
- So **no cycle + `n − 1` edges ⇒ `c = 1`**: connected. That is a tree.

So: if `edges.length != n − 1`, return `false`. Otherwise union every edge; if any union finds both ends already in one clan, there is a cycle: return `false`. Otherwise return `true`.

</Figure>

<Trace title="Both halves of the charter" steps={treeSteps} takeaway="Remember: a tree is exactly n − 1 edges AND no cycle. Either one alone can be fooled." />

**Why it works:** the edge count rules out “too few edges to connect everything”; the cycle check rules out “an edge wasted on a loop”. Together they leave only trees.

**What stays true:** while no union has failed, the edges processed so far form a forest, and the clan count is `n` minus the number of edges processed.

```java id=validTree group=uf
public boolean validTree(int n, int[][] edges) {
    if (edges.length != n - 1) return false;         // too few to connect, or too many to avoid a loop
    DSU dsu = new DSU(n);
    for (int[] e : edges)
        if (!dsu.union(e[0], e[1])) return false;    // both ends already connected: a loop
    return true;                                     // n - 1 edges and no loop: one piece
}
```

**O(n + E · α(n)) time, O(n) space.**

**Problem: Redundant Connection · Union-find, the edge that closes a cycle**

A tree on `n` nodes, labelled **`1` to `n`**, had one extra edge added. You get all `n` edges in order. Return an edge whose removal leaves a tree; if several qualify, return **the one that occurs last** in the input.

Replay the edges through union-find. The first edge whose union **fails** — both ends already share a root — is the answer.

<Figure caption="LeetCode’s second example: [1,2], [2,3], [3,4], [1,4], [1,5]. After the first three, junctions 1–4 share one root. Track #4, [1,4], finds both ends already connected: it closes the loop 1–2–3–4–1, and it is the answer. Track #5 joins junction 5 normally.">
  <Rail fig={figures.surplus} name="surplus" />

<Trace title="The first track you didn’t need" steps={redundantSteps} takeaway="Remember: replay in order; the first failed union is the loop’s last track, which is exactly the tie-break the problem asks for." />

**Why it works:** a tree plus one edge has **exactly one cycle**, and the removable edges are exactly the edges on it. Replaying in order, the edges before the failing one form a forest, so the failing edge’s ends were joined by a path of **earlier** edges — the rest of the cycle. Every other cycle edge therefore comes before it: it is the cycle’s **last** edge in the input, which is precisely the tie-break. No later union can fail, because there is only one cycle.

**What stays true:** before each edge, the processed edges form a forest, and the clans are its pieces.

A lot. In a rooted tree with one extra directed edge, the extra edge either gives some node **two parents**, or creates a **cycle**, or both. You must find a node with in-degree 2, try removing each of its two parent edges, and use union-find on the rest to see which removal leaves a valid rooted tree. Same register, more case analysis — a good transfer test once this chapter feels easy.

</Reveal>

<h2 id="network-delay">Chapter 7 · The mail must arrive</h2>

<Scene chapter="Chapter 7" title="The mail must arrive" mood="dawn">

The Royal Mail leaves Crossmere at dawn and fans out along one-way post roads, each with a fixed travel time. The Postmaster wants one number: how long until the very last town has its letters?

**Problem: Network Delay Time · Dijkstra’s algorithm**

`n` nodes, `1` to `n`. `times[i] = [u, v, w]` is a **one-way** edge from `u` to `v` taking `w` time (`w` is never negative). A signal starts at node `k`. Return the time for **every** node to receive it — the largest shortest-path distance — or `−1` if some node never does.

**Dijkstra’s algorithm:**

1. `dist[k] = 0`, every other `dist` is ∞. A min-heap holds `(dist, node)` tickets, starting with `(0, k)`.
2. Pop the **cheapest** ticket `(d, u)`. If `d > dist[u]`, it is **stale** — a cheaper ticket for `u` was already popped — so skip it.
3. Otherwise `d` is final for `u`. **Relax** every edge `u → v` with weight `w`: if `d + w < dist[v]`, write `dist[v] = d + w` and push `(dist[v], v)`.
4. When the heap is empty, `dist` holds every shortest distance.

<Figure caption="The ticket rack’s favourite example: roads 0→1 (4), 0→2 (1), 2→1 (2), 1→3 (1), 2→3 (5), source 0. Town 1’s first offer is 4, but 0→2→1 costs 1 + 2 = 3; town 3’s first offer is 6, but 0→2→1→3 costs 4. Final fares 0, 3, 1, 4; the last town hears at time 4. Green roads form the tree of cheapest routes.">
  <Rail fig={figures.mail} name="mail" />
</Figure>

<Trace title="Which ticket is certain?" steps={dijkstraSteps} takeaway="Remember: pop the cheapest; skip it if the board already knows better; otherwise it is final — relax its roads." />

**Why it works:** when `(d, u)` is popped and not stale, every other route to `u` must leave the settled towns somewhere, through a ticket that is still in the heap. That ticket costs **at least `d`** (the heap popped `d` first), and the rest of that route only **adds** non-negative tolls. So nothing can undercut `d`.

**What stays true:** every popped, non-stale town has its final distance; every other town’s `dist` is the cheapest route found so far whose last step leaves a settled town.

**Why it fails with negative edges.** The whole argument rests on “the rest of the route only adds”. A negative toll breaks it. With three towns — A→B costs 2, A→C costs 3, C→B costs **−2** — Dijkstra pops A, then pops B at 2 and declares it final. Only afterwards does it pop C at 3 and discover A→C→B costs 3 − 2 = 1.

<Figure caption="A three-town counterexample. B is popped and settled at 2 before C is explored; the true cheapest fare to B is 3 + (−2) = 1. With negative tolls, “cheapest ticket in the rack” is no longer “final”.">
  <Rail fig={figures.negative} name="negative" />
</Figure>

<Reveal q="Our lazy version pushes a new ticket whenever dist improves. Doesn’t that repair the negative case?">

On that tiny example, by luck: C relaxes C→B, writes `dist[B] = 1` and pushes `(1, B)`, which is popped and processed again. But B was already *treated as final* once, and anything computed from B’s old fare has to be redone. On larger graphs with negative edges this re-processing can happen exponentially many times in the worst case, and a **negative cycle** makes it loop forever. The guarantee — popped means final — is gone. With negative weights, use **Bellman-Ford** (Chapter 9).

</Reveal>

<Reveal q="What if you delete the stale check, `if (d > dist[u]) continue`?">

The answers stay correct: relaxing from a stale fare `d > dist[u]` offers `d + w`, which can never beat the `dist[u] + w` already offered. But every stale ticket rescans its town’s roads, so the work grows. The check is one line; keep it.

</Reveal>

```java id=networkDelayTime
public int networkDelayTime(int[][] times, int n, int k) {
    List<List<int[]>> out = new ArrayList<>();
    for (int i = 0; i <= n; i++) out.add(new ArrayList<>());          // nodes are 1..n
    for (int[] t : times) out.get(t[0]).add(new int[]{t[1], t[2]});
    int[] dist = new int[n + 1];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[k] = 0;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));   // [dist, node]
    heap.add(new int[]{0, k});
    while (!heap.isEmpty()) {
        int[] top = heap.poll();
        int d = top[0], u = top[1];
        if (d > dist[u]) continue;                   // stale ticket: u was settled cheaper
        for (int[] e : out.get(u)) {
            int v = e[0], nd = d + e[1];
            if (nd < dist[v]) { dist[v] = nd; heap.add(new int[]{nd, v}); }
        }
    }
    int last = 0;
    for (int v = 1; v <= n; v++) {
        if (dist[v] == Integer.MAX_VALUE) return -1; // never reached
        last = Math.max(last, dist[v]);
    }
    return last;
}
```

**O((V + E) log V) time, O(V + E) space.** The heap can hold up to one ticket per successful relaxation (at most E), and log E ≤ 2 log V. `d + e[1]` never overflows: we only relax from popped towns, whose `dist` is finite and at most 100 × (n − 1).

</HintLadder>

**Catch the bug:** locking a town the first time it is **offered** instead of when it is **popped**.

<h2 id="min-cost-points">Chapter 8 · Wire for the telegraph</h2>

<Scene chapter="Chapter 8" title="Wire for the telegraph" mood="dusk">

The Company is stringing telegraph wire between its depots. Wire runs along the town grid — east-west, then north-south — so a cable between two depots costs the blocks between them, one direction plus the other. Any depot can be wired to any other.

The wire doesn’t have to make any particular trip short. It only has to connect everyone, and the Board pays by the yard.

You start listing every possible cable. There are thousands.

*"Begin with one depot,"* the Keeper says. *"Of all the cables that leave your little network, which one could you never regret?"*

</Scene>

**Problem: Min Cost to Connect All Points · Minimum spanning tree**

`points[i] = [x, y]`. Connecting two points costs their **Manhattan distance** `|x1 − x2| + |y1 − y2|`. Return the minimum total cost so that every point is connected to every other (directly or through others).

The cheapest connected set of cables is a **tree** (a loop would contain a cable you could remove), spanning all points: a **minimum spanning tree (MST)**.

**The cut property** is the whole proof. Split the points into any two groups. The **cheapest cable crossing between the groups** belongs to some MST. Why: take an MST that doesn’t use it. Adding it creates a loop, and that loop must cross the split a second time, through some other cable that costs at least as much. Swap them: still connected, still a tree, no more expensive.

- **Prim’s algorithm** grows one tree. The split is “inside the tree” versus “outside”; each round adds the cheapest cable leaving the tree.
- **Kruskal’s algorithm** sorts every cable by cost and keeps one exactly when it joins two different clans (union-find). The cable it keeps is the cheapest crossing between its own clan and everyone else.

**Which for this problem?** Every pair of points is a candidate cable, so there are `n(n − 1)/2` of them — about 500,000 at n = 1,000. The graph is **dense**. Prim’s **without a heap** is the clean choice: keep `best[v]`, the cheapest cable from the tree to each outside point; each round scan for the smallest, add it, and update `best` using the newcomer. That is **O(n²) time, O(n) space**, and no cable list is ever built. Kruskal’s must build and sort all the cables: **O(n² log n) time, O(n²) space**.

<Figure caption="LeetCode’s first example: p0 (0,0), p1 (2,2), p2 (3,10), p3 (5,2), p4 (7,0). Prim’s from p0 adds p1 for 4, p3 for 3, p4 for 4 (through p3), and p2 for 9 (through p1). Total 20.">
  <Rail fig={figures.cable} name="cable" />
</Figure>

<Trace title="The cable you can’t regret" steps={primSteps} takeaway="Remember: the cheapest cable leaving the tree is always safe. After each join, let the newcomer lower everyone’s best offer." />

**What stays true:** the cables chosen so far are part of some MST, and `best[v]` is the cheapest cable from the current tree to `v`.

```java id=minCostConnectPointsKruskal group=uf
public int minCostConnectPointsKruskal(int[][] points) {
    int n = points.length;
    List<int[]> cables = new ArrayList<>();          // [cost, i, j]
    for (int i = 0; i < n; i++)
        for (int j = i + 1; j < n; j++)
            cables.add(new int[]{Math.abs(points[i][0] - points[j][0]) + Math.abs(points[i][1] - points[j][1]), i, j});
    cables.sort((a, b) -> Integer.compare(a[0], b[0]));
    DSU dsu = new DSU(n);
    int total = 0;
    for (int[] c : cables) {
        if (dsu.sets == 1) break;                    // n - 1 cables laid: everyone is connected
        if (dsu.union(c[1], c[2])) total += c[0];    // joins two clans: the cheapest such cable is safe
    }
    return total;
}
```

Kruskal’s shines when the edges are **given** and sparse (E much smaller than V²): **O(E log E)** for the sort, near-constant per union. For a complete graph of points, the O(n²) Prim’s above uses less time and far less memory.

</Reveal>

**Problem: Cheapest Flights Within K Stops · Bellman-Ford with a round limit**

`n` cities, `flights[i] = [from, to, price]` (one-way, prices positive). Return the cheapest price from `src` to `dst` using **at most `k` stops** — that is, at most **`k + 1` flights** — or `−1` if impossible.

**Bellman-Ford in rounds.** Keep `cost[]`, ∞ everywhere except `cost[src] = 0`. Run exactly **`k + 1` rounds**. In each round, first copy the board: `prev = cost.clone()`. Then for every flight, **read from `prev`, write to `cost`**: if `prev[from] + price < cost[to]`, lower `cost[to]`.

**What stays true:** after round `r` (counting from 1), `cost[v]` is the cheapest price from `src` to `v` using **at most `r` flights**. Proof: `prev` holds the best with at most `r − 1` flights; every new fare is one of those plus exactly one flight; and `cost` started as a copy of `prev`, so routes with fewer flights are kept.

**Why the copy matters.** Without it, a fare written earlier in the same round can be read later in that round, and one round chains **two** flights. Whether it happens depends on the order of the flights in the input — the worst kind of bug.

<Reveal q="Plain Bellman-Ford updates in place and still works. Why is this different?">

Plain Bellman-Ford wants the cheapest route with **any** number of edges. Reading a fresh value only finds good routes sooner, and after V − 1 rounds every shortest path (at most V − 1 edges) has been found — so in-place is fine, even faster. Here the **number of edges is the constraint**, so each round must add exactly one. Plain Bellman-Ford also handles **negative** weights, and if a V-th round still improves something, a negative cycle is reachable.

</Reveal>

```java id=findCheapestPrice
public int findCheapestPrice(int n, int[][] flights, int src, int dst, int k) {
    final int INF = Integer.MAX_VALUE;
    int[] cost = new int[n];
    Arrays.fill(cost, INF);
    cost[src] = 0;
    for (int round = 1; round <= k + 1; round++) {   // round r allows r flights
        int[] prev = cost.clone();                   // Snapshot: last round's board, read-only
        for (int[] f : flights) {
            int from = f[0], to = f[1], price = f[2];
            if (prev[from] != INF && prev[from] + price < cost[to]) cost[to] = prev[from] + price;
        }
    }
    return cost[dst] == INF ? -1 : cost[dst];
}
```

**O(k · (n + E)) time, O(n) space.** Prices are at most 10⁴ and a route has at most n ≤ 100 flights, so fares stay far inside `int`.

</HintLadder>

<Reveal q="Can BFS do it, one level of flights at a time?">

Yes: each BFS level is one more flight. Carry `(city, price)` pairs; push a city again only when the new price beats the best price seen for it so far. A pruned pair is dominated by an earlier one with no more flights and no higher price, so nothing is lost. Stop after `k + 1` levels.

```java id=findCheapestPriceBfs
public int findCheapestPrice(int n, int[][] flights, int src, int dst, int k) {
    List<List<int[]>> out = new ArrayList<>();
    for (int i = 0; i < n; i++) out.add(new ArrayList<>());
    for (int[] f : flights) out.get(f[0]).add(new int[]{f[1], f[2]});
    int[] best = new int[n];
    Arrays.fill(best, Integer.MAX_VALUE);
    best[src] = 0;
    Deque<int[]> level = new ArrayDeque<>();         // [city, price paid to get here]
    level.add(new int[]{src, 0});
    for (int taken = 0; taken <= k && !level.isEmpty(); taken++) {   // this level adds flight taken + 1
        for (int size = level.size(); size > 0; size--) {
            int[] cur = level.poll();
            for (int[] e : out.get(cur[0])) {
                int price = cur[1] + e[1];
                if (price < best[e[0]]) { best[e[0]] = price; level.add(new int[]{e[0], price}); }
            }
        }
    }
    return best[dst] == Integer.MAX_VALUE ? -1 : best[dst];
}
```

</Reveal>

<Reveal q="Why not just run Dijkstra and stop when the stop count runs out?">

Because Dijkstra settles each city **once**, at its cheapest fare — and the cheapest fare to a middle city may already have used up the changes. Take roads 0→1 (1), 1→2 (1), 0→2 (5), 2→3 (1) with k = 1. Dijkstra reaches city 2 first via 0→1→2 for 2 (two flights), marks it done, and then cannot extend it to 3 without a third flight. The legal route 0→2→3 for 6 needed city 2 at the **pricier** fare 5 with **fewer** flights, and that ticket is thrown away as “already settled”: the answer comes out −1.

```java fragment
if (visited[city]) continue;   // BUG: a pricier ticket with fewer flights can be the only one that fits
```

A correct Dijkstra must make the state **(city, flights used)** and keep a ticket unless another one for the same city is no worse in **both** price and flights. That works, but it is easy to get wrong. Bellman-Ford’s k + 1 rounds are simpler and fast enough here.

</Reveal>

**Catch the bug:** relaxing in place, without the copy. On flights `[[0,1,100],[1,2,100],[0,2,500]]`, `src = 0`, `dst = 2`, `k = 0`, the first round chains 0→1→2 and returns **200** instead of **500**. <h2 id="safe-states">Side quest 1 · Stations with no way back</h2>

**The page says:** forget prerequisites. Each station lists where you may go next. A **dead end** (no exits) is safe. A station is **safe** if **every** possible journey from it ends at a dead end. Which stations are safe?

**The reasoning:** a station is unsafe exactly when some journey from it can loop forever — when it can reach a cycle. Run Kahn’s algorithm **backwards**: reverse every track, and count each station’s exits that are not yet proven safe. Dead ends start at 0. When a station is proven safe, every station leading into it loses one unproven exit; reaching 0 proves that station safe too. Stations never popped can reach a loop.

<Figure caption="LeetCode’s example, graph = [[1,2],[2,3],[5],[0],[5],[],[]]. 5 and 6 are dead ends; 2 and 4 lead only to 5. Stations 0, 1 and 3 can circle 0 → 1 → 3 → 0 forever. Safe: [2, 4, 5, 6].">
  <Rail fig={figures.safe} name="safe" />
</Figure>

<Reveal q="Why reverse the tracks? Couldn’t you run Kahn’s algorithm forwards?">

Forwards, Kahn’s algorithm proves things about **what comes before** a station (“nothing upstream is stuck”). Safety is about **what comes after** (“nothing downstream can loop”). Reversing every track swaps the two, so the same in-degree argument — now an *out*-degree argument — proves safety from the dead ends backwards. The three-colour DFS also works: a station is safe exactly when its DFS finishes black.

</Reveal>

<HintLadder hints={hints.safeStates}>

```java id=eventualSafeNodes
public List<Integer> eventualSafeNodes(int[][] graph) {
    int n = graph.length;
    List<List<Integer>> into = new ArrayList<>();    // reversed tracks: who leads into me
    for (int i = 0; i < n; i++) into.add(new ArrayList<>());
    int[] unproven = new int[n];                     // exits not yet proven safe
    for (int u = 0; u < n; u++) {
        unproven[u] = graph[u].length;
        for (int v : graph[u]) into.get(v).add(u);
    }
    Deque<Integer> ready = new ArrayDeque<>();
    for (int u = 0; u < n; u++) if (unproven[u] == 0) ready.add(u);   // dead ends
    boolean[] safe = new boolean[n];
    while (!ready.isEmpty()) {
        int v = ready.poll();
        safe[v] = true;
        for (int u : into.get(v))
            if (--unproven[u] == 0) ready.add(u);    // every exit of u is now proven safe
    }
    List<Integer> answer = new ArrayList<>();
    for (int u = 0; u < n; u++) if (safe[u]) answer.add(u);
    return answer;
}
```

**O(V + E) time and space.** A self-loop counts as an exit that never becomes safe, so its station is correctly unsafe.

</HintLadder>

<h2 id="parallel-courses">Side quest 2 · Building in parallel</h2>

**The page says:** you are no longer limited to one course at a time. Course `i` takes `time[i]` months, any number of courses may run at once, and a course may start the moment all its prerequisites are finished. How many months until everything is done? (Relations are `[prev, next]`, courses `1` to `n`, and there is no cycle.)

**The reasoning:** a course **starts** when its slowest prerequisite finishes, and finishes `time` months later. That is a **longest path in a DAG**, and topological order is exactly the order in which those `max`es can be computed: when a course is popped, all its prerequisites have already reported their finish times. Push each finish time forward along its tracks.

<Reveal q="Isn’t “longest path” supposed to be hard?">

In a general graph, yes (it is NP-hard: it contains the Hamiltonian path problem). In a **DAG** it is easy, because there are no cycles to go round: process nodes in topological order and take a `max` over incoming edges. That is dynamic programming over a topological order — the same reason Bellman-Ford’s rounds work: each answer depends only on answers that are already final.

</Reveal>

<HintLadder hints={hints.parallelCourses}>

```java id=parallelCourses
// Parallel Courses III: relations[i] = [prev, next], courses 1..n, time[i] months for course i + 1.
public int minimumTime(int n, int[][] relations, int[] time) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] indegree = new int[n];
    for (int[] r : relations) { next.get(r[0] - 1).add(r[1] - 1); indegree[r[1] - 1]++; }
    int[] start = new int[n];                        // latest finish among prerequisites seen so far
    Deque<Integer> ready = new ArrayDeque<>();
    for (int i = 0; i < n; i++) if (indegree[i] == 0) ready.add(i);
    int answer = 0;
    while (!ready.isEmpty()) {
        int u = ready.poll();
        int finish = start[u] + time[u];             // every prerequisite of u has already reported
        answer = Math.max(answer, finish);
        for (int v : next.get(u)) {
            start[v] = Math.max(start[v], finish);
            if (--indegree[v] == 0) ready.add(v);
        }
    }
    return answer;
}

// Parallel Courses (unit time, may contain a cycle): fewest semesters, or -1.
public int minimumSemesters(int n, int[][] relations) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] indegree = new int[n];
    for (int[] r : relations) { next.get(r[0] - 1).add(r[1] - 1); indegree[r[1] - 1]++; }
    List<Integer> semester = new ArrayList<>();
    for (int i = 0; i < n; i++) if (indegree[i] == 0) semester.add(i);
    int semesters = 0, taken = 0;
    while (!semester.isEmpty()) {                    // one level of the queue = one semester
        semesters++;
        taken += semester.size();
        List<Integer> following = new ArrayList<>();
        for (int u : semester)
            for (int v : next.get(u)) if (--indegree[v] == 0) following.add(v);
        semester = following;
    }
    return taken == n ? semesters : -1;
}
```

**O(n + relations) time and space** for both. The semester count is the same idea with every `time` equal to 1, peeled one level of the queue at a time.

<h2 id="accounts-merge">Side quest 3 · The merged ledgers</h2>

**The page says:** the clans are no longer numbered. Each record is a name followed by email addresses, and **two records belong to the same person if they share any address**. Return one record per person: the name, then all their addresses in sorted order.

**The reasoning:** the nodes are **emails**, and each record says “all these emails belong together”. <Reveal q="Record A has emails x and y; record B has y and z; record C has z and w. Are A and C the same person?">

Yes. A and B share y, B and C share z, so all three are one person with x, y, z, w — even though A and C share nothing directly. Belonging is **transitive**, which is exactly what union-find maintains and what a pairwise comparison of records would miss.

</Reveal>

public List<List<String>> accountsMerge(List<List<String>> accounts) {
    Map<String, Integer> id = new HashMap<>();       // email -> its number in the register
    Map<String, String> owner = new HashMap<>();     // email -> the name on its record
    for (List<String> acc : accounts)
        for (int i = 1; i < acc.size(); i++)
            if (!id.containsKey(acc.get(i))) { id.put(acc.get(i), id.size()); owner.put(acc.get(i), acc.get(0)); }
    DSU dsu = new DSU(id.size());
    for (List<String> acc : accounts)
        for (int i = 2; i < acc.size(); i++) dsu.union(id.get(acc.get(1)), id.get(acc.get(i)));
    Map<Integer, List<String>> clans = new HashMap<>();
    for (String email : id.keySet())
        clans.computeIfAbsent(dsu.find(id.get(email)), r -> new ArrayList<>()).add(email);
    List<List<String>> merged = new ArrayList<>();
    for (List<String> emails : clans.values()) {
        Collections.sort(emails);
        List<String> row = new ArrayList<>();
        row.add(owner.get(emails.get(0)));
        row.addAll(emails);
        merged.add(row);
    }
    return merged;
}

<h2 id="evaluate-division">Side quest 4 · Exchange rates</h2>

**The page says:** the clans now carry **exchange rates**. You learn `a / b = 2.0` and `b / c = 3.0`; answer questions like `a / c` (6.0), or `−1.0` if the ratio cannot be determined.

**The reasoning:** a **weighted** union-find. Every variable keeps `parent[x]` **and** `ratio[x] = x / parent[x]`. During `find`, multiply ratios along the path, so after compression `ratio[x] = x / root`. Then any two variables in the same clan compare through their common root: `c / d = (c / root) / (d / root)`.

<Figure caption="a / b = 2 and b / c = 3 stored as weighted parent pointers a → b → c. find(a) multiplies along the walk and compresses: a now points straight at the root c with ratio 2 × 3 = 6, so a / c = 6.">
  <Rail fig={figures.ratios} name="ratios" />
</Figure>

<Reveal q="Union of a / b = v with roots ra and rb: what ratio does ra get?">

You want `ra / rb`. You know `a = ratio[a] · ra`, `b = ratio[b] · rb`, and `a = v · b`. So `ratio[a] · ra = v · ratio[b] · rb`, which gives **`ra / rb = v · ratio[b] / ratio[a]`**. Set `parent[ra] = rb` with that ratio, and the whole clan of `ra` inherits the right rates through compression.

</Reveal>

<HintLadder hints={hints.calcEquation}>

```java id=calcEquation
public double[] calcEquation(List<List<String>> equations, double[] values, List<List<String>> queries) {
    Map<String, String> parent = new HashMap<>();
    Map<String, Double> ratio = new HashMap<>();     // ratio(x) = x / parent(x)
    for (int i = 0; i < equations.size(); i++) {
        String a = equations.get(i).get(0), b = equations.get(i).get(1);
        for (String x : new String[]{a, b})
            if (!parent.containsKey(x)) { parent.put(x, x); ratio.put(x, 1.0); }
        String ra = find(parent, ratio, a), rb = find(parent, ratio, b);
        if (!ra.equals(rb)) {
            parent.put(ra, rb);
            ratio.put(ra, values[i] * ratio.get(b) / ratio.get(a));   // ra / rb, from a / b = v
        }
    }
    double[] answer = new double[queries.size()];
    for (int q = 0; q < queries.size(); q++) {
        String c = queries.get(q).get(0), d = queries.get(q).get(1);
        if (!parent.containsKey(c) || !parent.containsKey(d)
                || !find(parent, ratio, c).equals(find(parent, ratio, d))) answer[q] = -1.0;
        else answer[q] = ratio.get(c) / ratio.get(d);     // (c / root) / (d / root)
    }
    return answer;
}

private String find(Map<String, String> parent, Map<String, Double> ratio, String x) {
    String p = parent.get(x);
    if (p.equals(x)) return x;
    String root = find(parent, ratio, p);            // afterwards ratio(p) = p / root
    ratio.put(x, ratio.get(x) * ratio.get(p));       // x / root = (x / p) * (p / root)
    parent.put(x, root);
    return root;
}
```

**Near-linear time**: path compression alone gives O(log V) amortised per find, and LeetCode allows at most 20 equations (40 variables). A variable never seen in any equation gives `−1.0` — even for `x / x`.

<h2 id="min-effort">Side quest 5 · The gentlest gradient</h2>

**The page says:** a surveyor must walk a height map from the top-left square to the bottom-right, stepping up, down, left or right. A route’s **effort** is not the sum of its climbs but its **single steepest step**. Find the route with the least effort.

**The reasoning:** Dijkstra never needed **sums**. It needed one thing: **extending a route never makes it cheaper**. `max(effort so far, next step)` has that property — a longer route’s worst step is at least as bad — so the cheapest ticket in the rack is still final when popped. Replace `d + w` with `max(d, w)` and nothing else changes.

<Reveal q="Is there a second way, without a heap?">

Yes: **binary search on the answer**. For a threshold `t`, a flood fill that only takes steps of height change at most `t` tells you whether the corner is reachable. Reachability only gets easier as `t` grows, so binary search finds the smallest `t` that works: O(R · C · log H) for heights up to H. Union-find works too: sort the steps by height change and union until the two corners share a root. Three tools, one problem — say which you’d pick and why.

```java id=minimumEffortPath
public int minimumEffortPath(int[][] heights) {
    int rows = heights.length, cols = heights[0].length;
    int[][] effort = new int[rows][cols];
    for (int[] r : effort) Arrays.fill(r, Integer.MAX_VALUE);
    effort[0][0] = 0;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));   // [effort, r, c]
    heap.add(new int[]{0, 0, 0});
    int[][] steps = {{1, 0}, {-1, 0}, {0, 1}, {0, -1}};
    while (!heap.isEmpty()) {
        int[] top = heap.poll();
        int e = top[0], r = top[1], c = top[2];
        if (e > effort[r][c]) continue;              // stale
        if (r == rows - 1 && c == cols - 1) return e;   // popped means final
        for (int[] s : steps) {
            int nr = r + s[0], nc = c + s[1];
            if (nr < 0 || nc < 0 || nr >= rows || nc >= cols) continue;
            int ne = Math.max(e, Math.abs(heights[nr][nc] - heights[r][c]));   // the worst step so far
            if (ne < effort[nr][nc]) { effort[nr][nc] = ne; heap.add(new int[]{ne, nr, nc}); }
        }
    }
    return effort[rows - 1][cols - 1];               // not reached: the corner is always popped above
}
```

**O(R · C · log(R · C)) time, O(R · C) space.** Returning as soon as the corner is popped is safe for the same reason as everywhere in Dijkstra: popped means final.

</HintLadder>

**Transfer test:** in Swim in Rising Water, a route costs the **highest square** it ever stands on. What do you put in the heap first, and what replaces `max(e, |difference|)`? (The start square’s own height; `max(e, grid[nr][nc])`.) <h2 id="choose-the-tool">When the railway lies</h2>

<Scene title="The refund road" mood="storm">

One spring the Company, desperate to win passengers from a rival, starts paying people to ride a certain branch line. The toll on that road becomes a refund: minus two shillings.

Heap pops the town at the end of it before the refund road is ever looked at, and Dist writes its fare as final. A passenger arrives with a ticket one shilling cheaper than the board says is possible.

The Keeper looks at the board for a long time. *"Heap didn’t lie,"* she says at last. *"His promise did. It assumed every road costs something. Nobody checked."*

</Scene>

Each tool here carries a condition, and a wrong answer usually means the condition failed, not the code:

- **Dijkstra needs non-negative weights.** One negative edge breaks “popped means final” (Chapter 7’s three towns). Use **Bellman-Ford**, O(V · E). If every weight is the same, Dijkstra is overkill: **plain BFS** gives the same distances in O(V + E). If weights are only 0 or 1, a **0-1 BFS** with a deque does it in O(V + E).
- **Union-find cannot delete.** Once two clans merge, nothing records which edge joined them. If edges are removed over time, either reverse time offline (deletions become unions) or use heavier dynamic-connectivity structures.
- **Union-find ignores direction.** “a before b” and “b before a” look the same to it, so it can never detect a **directed** cycle. Prerequisites need a topological sort.
- **Topological sort needs a DAG.** On a graph with cycles there is no order to find; the right question becomes “which nodes are stuck?” (Kahn’s leftovers) or “what are the cycles?” (strongly connected components).
- **An MST is not a set of shortest paths.** It minimises the **total** cable, not any particular trip. If the question is “fastest from the depot to each town”, you want Dijkstra’s tree of cheapest routes, which can be a different tree.
- **All pairs, small n.** When n is a few hundred and you need every pair’s distance, **Floyd–Warshall**’s three nested loops (O(V³)) are simpler than running Dijkstra from every node.

<Reveal q="All tolls are positive, but the question is the cheapest route with at most k edges. Dijkstra or Bellman-Ford?">

Bellman-Ford with k + 1 rounds and a copy (Chapter 9), O(k · (V + E)). Dijkstra can be adapted with (node, edges used) states, but a plain visited-set Dijkstra is wrong: it throws away pricier tickets that used fewer edges. Name the constraint that decides it: **a limit on edges, not on price**.

</Reveal>

<h2 id="wider-family">The neighbouring lines · How the other roadmap patterns connect</h2>

The Railway isn’t the only company in the realm that keeps a ledger of what is settled. The shared idea: **process things in an order that makes each decision final.**

| Shared idea | Where it shows up | Where it belongs |
|---|---|---|
| Plain BFS/DFS, flood fill, visited sets | Number of Islands, Clone Graph, shortest path when every edge counts as one | <a href={`${BASE}dsa/lessons/graphs/`}>Graphs</a> |
| A min-heap that always yields the best remaining item | Dijkstra’s ticket rack and Prim’s heap version are the same heap that merges k sorted lists | <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> |
| Binary search on the answer | Path With Minimum Effort: “is the corner reachable with steps of at most t?” is monotone in t | <a href={`${BASE}dsa/lessons/binary-search/`}>Binary Search</a> |
| Fill a table in an order where every dependency is already final | Longest path in a DAG over topological order; Bellman-Ford’s round r from round r − 1 | <a href={`${BASE}dsa/lessons/dp-1d/`}>Dynamic Programming</a> |
| A greedy choice with an exchange-argument proof | Prim’s and Kruskal’s: the cut property says the cheapest crossing cable is never regretted | <a href={`${BASE}dsa/lessons/greedy/`}>Greedy</a> |
| A tree is a connected graph with no cycle | Graph Valid Tree’s n − 1 edges; every rooted tree is a DAG with in-degree at most 1 | <a href={`${BASE}dsa/lessons/trees-dfs/`}>Trees</a> |

**Kahn’s algorithm is BFS with a gate.** A node enters the queue not when it is first reached, but when its **last** incoming edge is cut. Remove the gate and you get ordinary BFS.

**Dijkstra is BFS with a heap.** When every edge weighs 1, the queue already pops in distance order; the heap is what lets unequal weights keep that promise.

<h2 id="exit-ticket">The dispatcher’s exam · Build a solution with the labels removed</h2>

<Scene title="No chapter titles" mood="dawn">

On the morning of the exam the Keeper hands you a sheet with no chapter names and no hints — three problems, a pen, and the three questions carved over the door of the drafting office.

*"Pick one,"* she says. *"Before you write a line, tell me what is settled, why your next move can’t unsettle it, and when you stop."*

</Scene>

Choose one. Keep the tutorial code closed. Write down the nodes, the edges, which tool, and the invariant before coding.

1. **The only possible ranking.** `n` players and a list of results “x beat y”. Is the ranking of all players **uniquely** determined? Test: no results with 2 players, a straight chain, a chain plus a shortcut, and a contradiction.
2. **Wells and pipes.** `n` houses. House `i` can dig its own well for `well[i]`, or be piped to house `j` for `pipe(i, j)`. Minimum total cost so every house has water. Test: wells cheaper than every pipe, one cheap well and cheap pipes, a single house.
3. **The safest route.** Each road has a probability `p` (between 0 and 1) of getting through without a breakdown; probabilities along a route multiply. Find the most reliable route between two towns. Test: no route, a direct road worse than a two-road detour, a road with `p = 0`.

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**Unique ranking:** Kahn’s algorithm, plus one check: the ranking is unique exactly when **Ready never holds more than one player** — two ready players at once means neither result decides between them. Also check that every player was popped (no contradiction). This is LeetCode’s Sequence Reconstruction in disguise.

**Wells and pipes:** add a **virtual source** node, with an edge of cost `well[i]` to each house. Now “dig a well” is just another pipe, and the answer is the MST of the n + 1 nodes (Kruskal’s with union-find, or Prim’s from the source). The trick — turn a per-node cost into an edge from a new node — is worth remembering on its own.

**Safest route:** Dijkstra with a **max**-heap of probabilities, multiplying instead of adding. It is safe because every `p` is at most 1, so extending a route can never make it *more* reliable — the same property that made sums and maxima work. (Taking `−log p` turns it into ordinary non-negative Dijkstra, which is the proof.)

Now explain why a slightly wrong version fails one of your tests — checking only “every player popped” for uniqueness, forgetting the virtual source, a heap that pops the least reliable first. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

Passing this once is a useful checkpoint. Rebuild one of these on another day, with a changed input and without the headings choosing the tool for you.

Graph tools do **not** automatically mean O(V + E). Count the heap (log factors), the sort (Kruskal’s), the rounds (Bellman-Ford’s k), and the adjacency list you build. Say the time **and** space before you code.

## Five bugs the Keeper keeps in her pocket

1. **The track points the wrong way.** `[a, b]` in Course Schedule means **b → a**. Reversed tracks still pass cycle checks and produce a perfectly backwards order.
2. **One colour where three are needed.** A plain visited flag in a directed DFS reports a cycle on every diamond. Grey (on the path) is not black (finished).
3. **Linking members instead of heads.** `parent[b] = a` without `find` tears `b` out of its clan. Always `parent[find(b)] = find(a)`, smaller under larger — and size the register `n + 1` for 1-indexed nodes.
4. **Settling on the first offer.** In Dijkstra a town is final when its ticket is **popped**, not when it is first **pushed**. And never with negative weights.
5. **Reading this round’s fares.** In the k-stops problem, relax from a **copy** of last round’s board, or one round can chain several flights.

**Look these up yourself** — real ideas this book didn’t have room for:

- **Strongly connected components** (Tarjan’s or Kosaraju’s algorithm) — what to do with a directed graph that *has* cycles: collapse each cycle-cluster to one node and get a DAG.
- **Bridges and articulation points** — the tracks and stations whose loss disconnects the network, found in one DFS.
- **0-1 BFS** — shortest paths when every weight is 0 or 1, in O(V + E) with a deque.
- **A\* search** — Dijkstra plus a heuristic that never overestimates; how route planners focus the search toward the goal.
- **Floyd–Warshall** — all-pairs shortest paths in O(V³), and why it also handles negative edges.
- **Johnson’s algorithm** — reweight edges with one Bellman-Ford run so Dijkstra works on graphs with negative edges.
- **Union-find with rollback** — undo the last union (no path compression), the basis of offline dynamic connectivity.
- **Eulerian paths (Hierholzer’s algorithm)** — use every edge exactly once; the idea behind Reconstruct Itinerary.
