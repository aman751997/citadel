<h2 id="prologue">Prologue · One thread, every corridor</h2>

<Scene chapter="Prologue" title="The ball of red thread" mood="dawn">

Threadmoor is built on top of its labyrinth. The town hall cellar has a stair that goes down into the dark, and the Guild of Threadwalkers has one job: write every way through into the Book of Ways.

On your first morning the Keeper gives you a ball of red thread and ties its end to a ring by the stair. *"You will never see the whole labyrinth,"* she says. *"You see one junction at a time, and you hold one thread. Tie it, walk a corridor to its end, then wind it back to the junction and try the next door."*

A junior threadwalker went down last week without thread. He came back with a book of guesses, some written twice and some never.

*"Every corridor exactly once,"* the Keeper says, *"and back to this stair with the thread in your hand. How?"*

</Scene>

Backtracking is the **one template** for problems that ask you to **build every answer** (or find one answer) out of a sequence of choices. The search walks a tree that is never stored: each node is a partial answer, and each edge is one choice. Three moves, always in this order:

1. **Choose** — add one option to the current partial answer (tie the thread to a door).
2. **Explore** — recurse to make every remaining choice (walk everything behind that door).
3. **Un-choose** — remove exactly what you added (wind the thread back to the junction).

```java fragment
void backtrack(int start, List<Integer> path) {
    if (/* the thread is a complete answer */) {
        result.add(new ArrayList<>(path));      // record a COPY, never the thread itself
        return;                                 // (some problems record at every node instead)
    }
    for (int i = start; i < n; i++) {           // every door at this junction
        if (/* nothing behind door i can work */) continue;   // prune (or break, if sorted)
        path.add(option(i));                    // CHOOSE: tie the thread to door i
        backtrack(nextStart(i), path);          // EXPLORE: walk everything behind it
        path.remove(path.size() - 1);           // UN-CHOOSE: wind the thread back
    }
}
```

The Keeper asks her three questions here, as everywhere in the realm:

1. **What is settled?** The thread. At every moment `path` holds exactly the choices on the way from the entrance to this junction — no more, no fewer.
2. **Why is this move safe?** Every choice is undone before its sibling is tried, so each door at a junction starts from the **same** thread. And the doorwarden (`start`) or the bells (`used[]`) make sure no answer is walked twice.
3. **When do I stop?** When the thread is a complete answer (record a copy), when the junction has no doors left, or when the Shears prove nothing behind a door can work.

> “The thread holds exactly the choices between the entrance and here.” That is the promise. Every chapter in this book keeps it, then changes what counts as a door.

The tree is not a data structure you build. It is the **shape of the recursion**: the call stack is the path from the root to the node you are visiting, and the thread is that same path written as a list.

### When this pattern fires

- **“Return all …”, “list every …”, “generate all …”** — subsets, combinations, permutations, partitions, arrangements. The output itself is a list of lists.
- **Place things under rules** — queens that can’t attack, digits that can’t repeat in a row, a word traced through a grid without reusing a cell.
- **The constraints are tiny.** n ≤ 10, n ≤ 16, a 9 × 9 board, a word of at most 15 letters. Small limits are the problem setter admitting that exponential time is expected.
- **Loops whose depth depends on the input.** Choosing k items needs k nested loops, and you can’t write k loops when k is a variable. Recursion is a loop nest of any depth.

**Exponential is expected, and that is honest.** Subsets of 20 items number 2²⁰ = 1,048,576; just writing them down takes that many steps. What backtracking saves is not the exponent of the *answer*; it is the waste around it. Generate-everything-then-filter places 8 queens one per row in 8⁸ = 16,777,216 ways and checks each. Backtracking abandons a partial board the moment two queens attack, and makes only **2,057** calls to find all 92 solutions.

<h2 id="subsets">Chapter 1 · The lantern room</h2>

<Scene chapter="Chapter 1" title="The lantern room" mood="dawn">

The first chamber holds three hooks and three lanterns, marked 1, 2 and 3. The Guild’s customer, a lamp-maker, wants a page in the Book of Ways for every way the room can be lit — any lanterns at all, including none.

A junior threadwalker has already tried. His method was efficient: whenever the thread held a lighting, he pinned **the thread itself** into the book, to save copying. This morning every one of his eight pages shows the same thing — a bare stub of thread, tied to nothing.

*"Two questions,"* she says. *"How does the walk make sure every lighting gets visited once? And what, exactly, goes onto the page?"*

</Scene>

**Problem: Subsets · include/exclude, or choose from a start index**

There are two shapes of the same search, and you should be able to draw both.

**Shape 1 — in or out.** Walk the items in order. At item `i` the junction has exactly two doors: **take it** or **leave it**. After n decisions the thread is complete. The leaves of this binary tree are the 2ⁿ subsets.

<Figure caption="Shape 1 for [1, 2]: each level decides one item. Take-or-leave at two levels gives 2 × 2 = 4 leaves, and the leaves are the subsets [1, 2], [1], [2], [ ]. Only leaves are recorded.">
  <Mermaid code={`flowchart TD
  R["decide 1"] -->|"take 1"| A["[1] · decide 2"]
  R -->|"leave 1"| B["[ ] · decide 2"]
  A -->|"take 2"| A1["[1,2] ✓"]
  A -->|"leave 2"| A2["[1] ✓"]
  B -->|"take 2"| B1["[2] ✓"]
  B -->|"leave 2"| B2["[ ] ✓"]`} />
</Figure>

```java id=subsetsInOut
public List<List<Integer>> subsets(int[] nums) {
    List<List<Integer>> result = new ArrayList<>();
    decide(nums, 0, new ArrayList<>(), result);
    return result;
}

private void decide(int[] nums, int i, List<Integer> path, List<List<Integer>> result) {
    if (i == nums.length) {                       // every item decided: a leaf
        result.add(new ArrayList<>(path));        // record a COPY
        return;
    }
    path.add(nums[i]);                            // choose: take nums[i]
    decide(nums, i + 1, path, result);            // explore
    path.remove(path.size() - 1);                 // un-choose
    decide(nums, i + 1, path, result);            // explore the other door: leave nums[i]
}
```

**Shape 2 — for each choice from `start`.** At a junction, the doors are “add item `i`” for every `i ≥ start`, and the child junction starts at `i + 1`. **Every node is a subset**, so the Scribe records on arrival, before the loop. This is the tree in the prologue figure, and it is the shape the rest of this book uses, because it bends to every later rule: duplicates, a fixed size, a target sum.

**Why `start` matters:** it is the doorwarden’s whole job. Items are only ever added **in index order**, so the subset `{1, 2}` can be built as `[1, 2]` and never as `[2, 1]`. Every subset has exactly one increasing order, so it has exactly one node in the tree.

<Trace title="Wind the thread, copy the page" steps={subsets} takeaway="Remember: record new ArrayList<>(path) — a copy. Every add has a matching remove right after the recursive call. In shape 2 every node is a subset; in shape 1 only the leaves are." />

**Why it works:** shape 2 visits one node per increasing index sequence `i₁ < i₂ < … < iₖ`, and those sequences are in one-to-one correspondence with subsets. Un-choose restores the thread, so each sibling starts from the parent’s exact thread.

**What stays true:** when `backtrack(start, path)` is called, `path` holds the chosen items in increasing index order, all with index below `start`. When it returns, `path` is exactly what it was when it was called.

<Reveal q="The Scribe writes result.add(path). Why does every page end up empty?">

`path` is one list object, shared by the whole search. `result.add(path)` stores a **reference** to it, not its contents. Every later add and remove changes that one list, and when the search finishes the thread has been wound all the way back, so it is empty. On `[1, 2, 3]` the book has 8 entries, and all 8 are the same empty list. `new ArrayList<>(path)` takes a snapshot that later moves cannot touch. (For strings built in a `StringBuilder`, `toString()` is the copy.)

</Reveal>

<Reveal q="2ⁿ subsets — but the usual bound is O(n · 2ⁿ). Where does the extra n come from?">

From copying. There are 2ⁿ nodes and each record copies up to n items. Summed exactly, the subsets of n items contain n · 2ⁿ⁻¹ items in total, which is Θ(n · 2ⁿ). The output is that big, so no algorithm can do better. The recursion itself uses O(n) extra space (the thread and the call stack), not counting the output.

</Reveal>

```java id=subsets
public List<List<Integer>> subsets(int[] nums) {
    List<List<Integer>> result = new ArrayList<>();
    backtrack(nums, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] nums, int start, List<Integer> path, List<List<Integer>> result) {
    result.add(new ArrayList<>(path));            // every node is a subset: record a copy
    for (int i = start; i < nums.length; i++) {
        path.add(nums[i]);                        // choose
        backtrack(nums, i + 1, path, result);     // explore: only items after i
        path.remove(path.size() - 1);             // un-choose
    }
}
```

**O(n · 2ⁿ) time, O(n) extra space** besides the output (the thread and up to n + 1 stack frames).

</HintLadder>

**Catch the bug:** forget the un-choose and the thread only ever grows.

```java fragment
for (int i = start; i < nums.length; i++) {
    path.add(nums[i]);
    backtrack(nums, i + 1, path, result);
    // BUG: no path.remove(...) — on [1, 2, 3] the fifth page reads [1, 2, 3, 3] where [1, 3] belongs
}
```

A second, Java-only trap: `path.remove(nums[i])` with an `int` argument calls `remove(int index)`, not `remove(Object)`. It removes **by position**, so on `[1, 2, 3]` it throws `IndexOutOfBoundsException` while winding back from `[1, 2, 3]`: it tries to remove index 3 from a three-item thread. Always write `path.remove(path.size() - 1)`. [Solve Subsets](https://leetcode.com/problems/subsets/).

<Scene chapter="Chapter 2" title="The twin keys">

The Keeper lines the keys up on the bench, iron first, then the two brass keys side by side.

</Scene>

**Problem: Subsets II · sort, then skip twins at the same depth**

Duplicates create duplicate **corridors**. If two equal values are both offered as doors at the same junction, the subtrees behind them are identical, so every subset in the second one is written twice.

The fix has two parts:

1. **Sort**, so equal values sit side by side.
2. At a junction, **skip `nums[i]` if `i > start` and `nums[i] == nums[i - 1]`**. The twin just to the left already opened this exact corridor at this exact depth.

<Figure caption="Sorted [1, 2, 2]. At the entrance, the second 2 (index 2) would open a corridor identical to the first 2’s: [2], then [2, 2]. The dashed edge is skipped. One level down, under [1, 2] (start = 2), the same 2 is the FIRST door at its junction, so it is taken: [1, 2, 2]. Six pages: [ ], [1], [1, 2], [1, 2, 2], [2], [2, 2].">
  <Mermaid code={`flowchart TD
  R["[ ]"] -->|"+1"| A["[1]"]
  R -->|"+2 (idx 1)"| B["[2]"]
  R -.->|"2 (idx 2): twin, skip"| X["[2] again ✗"]
  A -->|"+2 (idx 1)"| AB["[1,2]"]
  A -.->|"2 (idx 2): twin, skip"| Y["[1,2] again ✗"]
  AB -->|"+2 (idx 2): i = start, take"| ABB["[1,2,2]"]
  B -->|"+2 (idx 2): i = start, take"| BB["[2,2]"]`} />
</Figure>

<Trace title="Twin or first door?" steps={subsetsDup} takeaway="Remember: sort, then skip when i > start && nums[i] == nums[i - 1]. The first door at every junction is always walked, twin or not." />

**Why `i > start`, not `i > 0`:** the rule says “a twin **at the same junction** has already been tried”. At `i == start`, `nums[i]` is the **first** door at this junction — nothing at this depth has been tried yet. Its twin to the left is not a sibling; it is already **on the thread** (or was deliberately left out higher up). `i > 0` skips it anyway, and every subset containing two equal values vanishes.

**Why it works:** in a sorted array, a multiset subset with c copies of a value is built canonically by taking the **leftmost** c copies. The skip rule allows exactly that: a later copy can only be taken when every earlier copy at this junction was taken first.

**What stays true:** at every junction, the doors walked carry **distinct values**, so no two sibling subtrees are identical.

<Reveal q="Why not just generate everything and put the results in a HashSet?">

It works if you sort each subset first (so `[1, 2]` and `[2, 1]` hash the same), but it does the duplicate work and then throws it away. With 10 copies of the same value the tree has 2¹⁰ = 1,024 nodes but only 11 distinct subsets. The skip rule walks 11 nodes, not 1,024. Interviewers ask for the skip rule precisely because it shows you understand which corridors are identical.

</Reveal>

<HintLadder hints={hints.subsetsDup}>

```java id=subsetsWithDup
public List<List<Integer>> subsetsWithDup(int[] nums) {
    Arrays.sort(nums);                                       // twins must sit side by side
    List<List<Integer>> result = new ArrayList<>();
    backtrack(nums, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] nums, int start, List<Integer> path, List<List<Integer>> result) {
    result.add(new ArrayList<>(path));
    for (int i = start; i < nums.length; i++) {
        if (i > start && nums[i] == nums[i - 1]) continue;   // same value, same junction: already walked
        path.add(nums[i]);
        backtrack(nums, i + 1, path, result);
        path.remove(path.size() - 1);
    }
}
```

**O(n · 2ⁿ) time** in the worst case (all values distinct), plus O(n log n) to sort; **O(n) extra space** besides the output.

</HintLadder>

**Catch the bug:** `if (i > 0 && nums[i] == nums[i - 1]) continue;` On `[1, 2, 2]` it returns 4 subsets — `[ ]`, `[1]`, `[1, 2]`, `[2]` — and loses `[1, 2, 2]` and `[2, 2]`. Forgetting to sort is the other half: on `[2, 1, 2]` the twins aren’t adjacent, the rule never fires, and `[2]` is written twice (while `[2, 1]` and `[1, 2]` both appear). [Solve Subsets II](https://leetcode.com/problems/subsets-ii/).

<Scene chapter="Chapter 3" title="The expedition of k" mood="dusk">

**Problem: Combinations · fixed size k, prune by room left**

Same doorwarden as Subsets, two changes:

- **Record only full hands.** The thread is complete when it holds `k` items; record a copy and return — going deeper can only make hands of k + 1.
- **The Shears: leave room for the rest.** If the thread still needs `need = k − path.size()` items, the first of them can be at most `n − need + 1`, because the remaining `need − 1` items must all be bigger. A door beyond that bound leads only to dead ends.

<Figure caption="n = 4, k = 2. At the entrance need = 2, so the loop stops at 4 − 2 + 1 = 3: the door ‘4’ (dashed) is cut, because nothing bigger than 4 is left to pair with it. Six pages: [1, 2], [1, 3], [1, 4], [2, 3], [2, 4], [3, 4] — C(4, 2) = 6.">
  <Mermaid code={`flowchart TD
  R["[ ] · need 2"] -->|"+1"| A["[1]"]
  R -->|"+2"| B["[2]"]
  R -->|"+3"| C["[3]"]
  R -.->|"4: no room, cut"| D["[4] ✗"]
  A --> A2["[1,2] ✓"]
  A --> A3["[1,3] ✓"]
  A --> A4["[1,4] ✓"]
  B --> B3["[2,3] ✓"]
  B --> B4["[2,4] ✓"]

<Trace title="Room for the rest" steps={combinations} takeaway="Remember: record when path.size() == k, then return. The loop runs i up to n − (k − path.size()) + 1." />

**Why it works:** the doorwarden makes the thread strictly increasing, so each k-set is built once, in its sorted order. The room-left bound only removes doors whose subtrees contain no complete hand.

**What stays true:** the thread is strictly increasing and every item on it is below `start`. With the Shears in place, **every node visited lies on the way to at least one full hand**, so no work is wasted on dead ends.

<Reveal q="Is the room-left prune just a speed-up, or can it change the answer?">

Only speed. Without it, the loop walks doors like ‘4’ at the entrance, finds nobody left, and returns without recording. The answer is the same. With it, the search never visits a dead end, which is what makes the bound O(k · C(n, k)) honest: each of the C(n, k) hands is copied for k steps, and every internal node lies on the way to some hand.

</Reveal>

<HintLadder hints={hints.combine}>

```java id=combine
public List<List<Integer>> combine(int n, int k) {
    List<List<Integer>> result = new ArrayList<>();
    backtrack(n, k, 1, new ArrayList<>(), result);
    return result;
}

private void backtrack(int n, int k, int start, List<Integer> path, List<List<Integer>> result) {
    if (path.size() == k) {                          // a full hand: record it, go no deeper
        result.add(new ArrayList<>(path));
        return;
    }
    int need = k - path.size();
    for (int i = start; i <= n - need + 1; i++) {    // the Shears: leave room for the rest
        path.add(i);
        backtrack(n, k, i + 1, path, result);
        path.remove(path.size() - 1);
    }
}
```

**O(k · C(n, k)) time, O(k) extra space** besides the output.

</HintLadder>

**Catch the bug:** cutting one door too early, `i <= n - need`. The bound is wrong at every depth, not just the entrance: on n = 4, k = 2 the book gets only `[1, 2]`, `[1, 3]`, `[2, 3]` — every hand containing 4 is lost, 3 pages instead of 6. When you write a prune, test it on an input where the last door matters. [Solve Combinations](https://leetcode.com/problems/combinations/).

<h2 id="combination-sum">Chapter 4 · The toll purse</h2>

<Scene chapter="Chapter 4" title="The toll purse" mood="night">

Deeper down, a toll gate wants exactly 7 copper. The purse holds coins of 2, 3, 6 and 7 — as many of each as you like. The gatekeeper wants a page for every **different** handful that pays exactly 7.

The first corridor goes 2, 2, 2 — six copper — and the next 2 would make 8. You hesitate with the coin over the slot.

The Shears hang on a hook by the gate. *"The coins are sorted,"* the Keeper says. *"If a 2 is already too much, what do you know about the 3, the 6 and the 7?"*

Then she taps the 2 still in your hand. *"And after you pay with a 2 — may the next coin be a 2 again?"*

</Scene>

**Problem: Combination Sum · reuse allowed: pass `i`, not `i + 1`**

Three changes from Subsets:

- **The thread is complete when the remaining amount is 0.** Carry `remain = target − (sum of the thread)` down the recursion.
- **Reuse: the child starts at `i`**, not `i + 1`. The same coin may be chosen again, but no coin to its *left* may come back — that is what still prevents `[2, 2, 3]` from also appearing as `[3, 2, 2]`.
- **The Shears: sort, then break.** If `candidates[i] > remain`, this coin overshoots, and since the array is sorted, so does every coin after it. `break`, not `continue`.

<Figure caption="Sorted [2, 3, 6, 7], target 7. Each node shows the thread and what is still owed. Dashed edges are cut by the Shears: the coin is bigger than what is owed, and so is every coin after it. ‘Dead end’ nodes are walked, but their very first coin overshoots. Two pages: [2, 2, 3] and [7].">
  <Mermaid code={`flowchart TD

**Why it works:** each handful is a multiset of coins, and the doorwarden builds it in **non-decreasing** order — exactly one order per multiset. Passing `i` allows equal neighbours; never going left forbids every other order.

**What stays true:** `remain ≥ 0` at every node, the thread is non-decreasing, and every coin on it is at most `candidates[start]`.

<Reveal q="What changes if the child starts at 0 instead of i?">

Every handful is written once **per order**. On `[2, 3, 6, 7]` with target 7 the book gets `[2, 2, 3]`, `[2, 3, 2]`, `[3, 2, 2]` and `[7]`. That is the tree of **ordered sequences** — the right tree for a different question (Combination Sum IV counts those, and counts them with DP, not by walking).

</Reveal>

<Reveal q="How big can this tree get?">

The thread holds at most `target / min` coins, and each junction has at most N doors, so the tree has at most about N^(target/min + 1) nodes. That bound is loose but honest: the work is **exponential in target / min**, not in N alone. LeetCode keeps target ≤ 40 and guarantees fewer than 150 answers, which is why the search is fast there.

</Reveal>

```java id=combinationSum
public List<List<Integer>> combinationSum(int[] candidates, int target) {
    Arrays.sort(candidates);                            // sorted, so one overshoot ends the loop
    List<List<Integer>> result = new ArrayList<>();
    backtrack(candidates, target, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] c, int remain, int start, List<Integer> path, List<List<Integer>> result) {
    if (remain == 0) {                                  // paid exactly: record a copy
        result.add(new ArrayList<>(path));
        return;
    }
    for (int i = start; i < c.length; i++) {
        if (c[i] > remain) break;                       // the Shears: this and every later coin overshoot
        path.add(c[i]);
        backtrack(c, remain - c[i], i, path, result);   // i, not i + 1: the same coin may come again
        path.remove(path.size() - 1);
    }
}
```

**Exponential in target / min(candidates)** (roughly O(N^(T/M + 1)) nodes, plus copying each answer); **O(T/M) extra space** for the thread and the stack. Candidates are positive, so `remain` only goes down and the recursion always ends.

</HintLadder>

**Catch the bug:** `backtrack(c, remain - c[i], i + 1, path, result)` forbids reuse. On `[2, 3, 6, 7]` with target 7 it returns only `[7]` and loses `[2, 2, 3]`. The opposite slip, `break` without sorting first, cuts real answers: on unsorted `[2, 7, 3]` with target 7, the 7 doesn’t fit after `[2, 2]`, the loop breaks, and the 3 behind it is never tried: `[2, 2, 3]` is lost. [Solve Combination Sum](https://leetcode.com/problems/combination-sum/).

```java id=letterCombinations

public List<String> letterCombinations(String digits) {

private void backtrack(String digits, int pos, StringBuilder path, List<String> result) {
    if (pos == digits.length()) {                          // one letter per digit: record
```

<h2 id="permutations">Chapter 6 · The procession</h2>

<Scene chapter="Chapter 6" title="The procession" mood="dawn">

On festival day three banner-bearers — 1, 2 and 3 — must walk the labyrinth in single file, and the festival master wants a page for every **order** they could walk in.

**Problem: Permutations · a `used[]` array instead of `start`**

In a subset, `{2, 1}` and `{1, 2}` are the same group, so the doorwarden forbids looking left. In an ordering, `[2, 1, 3]` and `[1, 2, 3]` are **different answers**, so every item must be offered at every depth — **every item not already on the thread**. That is `used[]`:

- The loop always runs `i` from 0.
- Skip `i` if `used[i]`.
- Choose = `used[i] = true` and add; un-choose = remove and `used[i] = false`. Both pieces of state are undone, in reverse order.
- Record when the thread holds all n items.

**Why it works:** at depth d the thread holds d distinct items, and every unused item is offered, so each ordering corresponds to exactly one root-to-leaf path.

**What stays true:** `used[i]` is true **exactly** for the items on the thread. Every line that changes one changes the other.

<Reveal q="Why is the time O(n · n!) and not just O(n!)?">

There are n! leaves, and each copy costs n. The internal nodes add little: depth d has n!/(n − d)! nodes, and summing over d gives fewer than e · n! ≈ 2.72 · n! nodes in total, each scanning n bells. So the whole walk is O(n · n!). For n = 10 that is 3,628,800 orderings — about the limit of what is reasonable to list.

</Reveal>

```java id=permute
public List<List<Integer>> permute(int[] nums) {
    List<List<Integer>> result = new ArrayList<>();
    backtrack(nums, new boolean[nums.length], new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] nums, boolean[] used, List<Integer> path, List<List<Integer>> result) {
    if (path.size() == nums.length) {                    // everyone is in line: record
        result.add(new ArrayList<>(path));
        return;
    }
    for (int i = 0; i < nums.length; i++) {              // every item, from the beginning
        if (used[i]) continue;                           // already on the thread
        used[i] = true;                                  // choose: ring the bell...
        path.add(nums[i]);                               // ...and tie the thread
        backtrack(nums, used, path, result);             // explore
        path.remove(path.size() - 1);                    // un-choose, in reverse order
        used[i] = false;
    }
}
```

**O(n · n!) time, O(n) extra space** besides the output (the bells, the thread, and n + 1 stack frames).

</HintLadder>

**Catch the bug:** forgetting `used[i] = false`. On `[1, 2, 3]` the first walk rings every bell and nothing ever silences them, so the book has one page, `[1, 2, 3]`. Using `start` instead of `used[]` gives the same single page, for a different reason. [Solve Permutations](https://leetcode.com/problems/permutations/).

<h2 id="word-search">Chapter 7 · The lettered floor</h2>

<Scene chapter="Chapter 7" title="The lettered floor" mood="night">

The floor of the next hall is laid with lettered tiles. A message is hidden in it: a word spelled by stepping from tile to tile — up, down, left or right — and no tile may be stood on twice.

You chalk a cross on every tile you stand on, so you don’t step on it again. Your first walk fails, and you climb out, leaving the crosses where they are. Your second walk needs one of those tiles. It is crossed. You tell the Keeper the word isn’t there.

She looks at the chalk for a long moment.

*"You marked the tiles of a walk that is over,"* she says. *"Whose path are those crosses still protecting?"*

</Scene>

**Problem: Word Search · grid backtracking with in-place marking**

The thread is a path of cells. At step k, standing on a cell that matches `word[k]`, the doors are the four neighbours. Two rules:

- **No cell twice on the same path.** Mark the cell before exploring — overwrite it with `'#'`, a character no word contains — so a neighbour lookup fails on it.
- **Un-choose restores the cell.** A cell used by a failed walk is free again for the next walk. Marking is the *choose*, restoring is the *un-choose*.

<Figure caption="board [[A, B], [A, A]], word AAB. A walk from (0, 0) goes down to (1, 0) and fails: its right neighbour holds A, not B. Restore both cells, and a later walk from (1, 0) goes up to (0, 0), then right to the B at (0, 1). Leave the crosses in place and that walk finds (1, 0) and (0, 0) still crossed: the answer flips to false.">
  <ArrayStrip name="row 0" values={['A', 'B']} indices={false} tones={{ 0: 'hot', 1: 'hot' }} pointers={[{ at: 0, label: 'step 2' }, { at: 1, label: 'step 3', tone: 'green' }]} />
  <ArrayStrip name="row 1" values={['A', 'A']} indices={false} tones={{ 0: 'hot' }} pointers={[{ at: 0, label: 'step 1', tone: 'blue' }]} />
</Figure>

<Trace title="Chalk on the tiles" steps={wordSearch} takeaway="Remember: mark before exploring, restore after — on success and on failure. A visited mark in backtracking belongs to one path, not to the whole search." />

**Why it works:** the marks on the board are exactly the cells of the current path (the thread, drawn on the floor). A step onto a marked cell would reuse a cell; a step onto an unmarked cell can’t.

**What stays true:** when `dfs(r, c, k)` is called, exactly k cells are marked, and they spell `word[0..k − 1]` along a path ending next to `(r, c)`. When it returns, the board is exactly as it was.

<Reveal q="Graph DFS marks visited and never unmarks. Why must this one unmark?">

In graph traversal the question is “**can** I reach this node?” — once reached, it never needs visiting again. Here the question is about **paths**: a cell that was useless as step 3 of one walk can be exactly step 1 of another. The mark means “on the current path”, so it must be lifted when the path leaves.

</Reveal>

<HintLadder hints={hints.wordSearch}>

```java id=exist
public boolean exist(char[][] board, String word) {
    for (int r = 0; r < board.length; r++)
        for (int c = 0; c < board[0].length; c++)
            if (dfs(board, word, r, c, 0)) return true;
    return false;
}

private boolean dfs(char[][] board, String word, int r, int c, int k) {
    if (k == word.length()) return true;                      // every letter matched
    if (r < 0 || c < 0 || r >= board.length || c >= board[0].length) return false;
    if (board[r][c] != word.charAt(k)) return false;          // wrong letter, or '#' (on the path)
    char saved = board[r][c];
    board[r][c] = '#';                                        // choose: this cell is on the path
    boolean found = dfs(board, word, r + 1, c, k + 1) || dfs(board, word, r - 1, c, k + 1)
                 || dfs(board, word, r, c + 1, k + 1) || dfs(board, word, r, c - 1, k + 1);
    board[r][c] = saved;                                      // un-choose: restore, success or not
    return found;
}
```

**O(R · C · 3ᴸ) time** for an R × C board and a word of length L (four doors at the first step, at most three after it, because the cell you came from is marked), **O(L) extra space** for the stack. Restoring even on success leaves the caller’s board untouched.

</HintLadder>

**Catch the bug:** two opposite slips. Never restoring the cell: on `[[A, B], [A, A]]` with `AAB`, the answer becomes false. Never marking at all: on `[[A, B]]` with `ABA`, the walk goes A → B → back to the same A and returns true, though the word needs two different A tiles. [Solve Word Search](https://leetcode.com/problems/word-search/).

<Scene chapter="Chapter 8" title="The mirror ribbon" mood="dusk">

**Problem: Palindrome Partitioning · choose where the next piece ends**

The thread is the list of pieces cut so far, and `start` is where the next piece begins. The doors at a junction are the possible **end positions** `end = start .. n − 1`. A door is open only if `s[start..end]` is a palindrome — the Shears cut every other door before it is walked. Record when `start == n`: the whole ribbon is cut.

<Figure caption='s = "aab". From position 0, the pieces ‘a’ and ‘aa’ are palindromes; ‘aab’ is cut. Following ‘a’, the next piece is ‘a’ (then ‘b’) — ‘ab’ is cut. Two pages: [a, a, b] and [aa, b].'>
  <Mermaid code={`flowchart TD

**Why it works:** a partition is a sequence of pieces whose lengths sum to n; choosing each piece’s end in turn reaches every sequence exactly once, and the palindrome check removes exactly the invalid ones.

**What stays true:** the pieces on the thread are palindromes and, joined, spell exactly `s[0..start − 1]`.

<Reveal q="Checking each piece costs O(n). Can you avoid re-checking the same piece?">

Yes: precompute `isPal[i][j]` for every piece in O(n²) with `isPal[i][j] = s[i] == s[j] && (j − i < 2 || isPal[i + 1][j − 1])`. Then each check is O(1). It doesn’t change the worst case — a string of n equal letters has 2ⁿ⁻¹ partitions, and copying them costs O(n · 2ⁿ) — but it is a good thing to mention.

</Reveal>

```java id=partition
public List<List<String>> partition(String s) {
    List<List<String>> result = new ArrayList<>();
    backtrack(s, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(String s, int start, List<String> path, List<List<String>> result) {
    if (start == s.length()) {                                 // the whole ribbon is cut
        result.add(new ArrayList<>(path));
        return;
    }
    for (int end = start; end < s.length(); end++) {           // where does the next piece end?
        if (!isPalindrome(s, start, end)) continue;            // the Shears: nobody buys this piece
        path.add(s.substring(start, end + 1));                 // choose
        backtrack(s, end + 1, path, result);                   // explore the rest of the ribbon
        path.remove(path.size() - 1);                          // un-choose
    }
}

private boolean isPalindrome(String s, int lo, int hi) {
    while (lo < hi) if (s.charAt(lo++) != s.charAt(hi--)) return false;
    return true;
}
```

**O(n · 2ⁿ) time, O(n) extra space** besides the output. There are at most 2ⁿ⁻¹ ways to cut a string of n letters (cut or don’t cut at each of the n − 1 gaps), and each costs O(n) to check and copy.

</HintLadder>

**Catch the bug:** recursing with `start + 1` instead of `end + 1` re-cuts letters that are already in the piece: on `"aab"` it writes pages like `[aa, a, b]` whose letters don’t even spell the input. [Solve Palindrome Partitioning](https://leetcode.com/problems/palindrome-partitioning/).

**Problem: N-Queens · one queen per row; column and diagonal sets**

Two queens can’t share a row, so put **exactly one queen per row** and make the row the depth. The doors at row `r` are the columns `c = 0 .. n − 1`. A door is open only if the square is not attacked, and that is three O(1) lookups:

- **Column:** `cols[c]`.
- **Diagonal (top-left to bottom-right):** every square on it has the same `r − c`. It ranges from −(n − 1) to n − 1, so store it at index `r − c + n − 1`.
- **Anti-diagonal (top-right to bottom-left):** every square on it has the same `r + c`, from 0 to 2n − 2.

Choose = place the queen and mark all three; un-choose = clear all three.

**What stays true:** at row `r`, rows `0 .. r − 1` each hold one queen, no two of them attack each other, and the three sets hold exactly their columns and diagonal labels.

<Reveal q="How much work is this really?">

Row r has at most n − r free columns (each earlier queen holds one), so depth r has at most n!/(n − r)! nodes, fewer than e · n! in all, each scanning n columns: **O(n · n!)** as an upper bound, plus O(n²) to draw each solution. The diagonals prune far harder than that bound admits. For n = 8 the search makes **2,057** calls in total, against 8! = 40,320 column orders and 8⁸ = 16,777,216 one-per-row placements.

</Reveal>

```java id=solveNQueens
public List<List<String>> solveNQueens(int n) {
    List<List<String>> result = new ArrayList<>();
    int[] queenCol = new int[n];                             // queenCol[r] = column of row r's queen
    boolean[] cols = new boolean[n], diag = new boolean[2 * n - 1], anti = new boolean[2 * n - 1];
    place(0, n, queenCol, cols, diag, anti, result);
    return result;
}

private void place(int r, int n, int[] queenCol, boolean[] cols, boolean[] diag, boolean[] anti,
                   List<List<String>> result) {
    if (r == n) {                                            // a queen in every row: record
        result.add(draw(queenCol));
        return;
    }
    for (int c = 0; c < n; c++) {
        if (cols[c] || diag[r - c + n - 1] || anti[r + c]) continue;   // watched: the Shears
        queenCol[r] = c;
        cols[c] = diag[r - c + n - 1] = anti[r + c] = true;           // choose
        place(r + 1, n, queenCol, cols, diag, anti, result);           // explore the next row
        cols[c] = diag[r - c + n - 1] = anti[r + c] = false;          // un-choose
    }
}

private List<String> draw(int[] queenCol) {
    List<String> board = new ArrayList<>();
    for (int c : queenCol) {
        char[] row = new char[queenCol.length];
        Arrays.fill(row, '.');
        row[c] = 'Q';
        board.add(new String(row));
    }
    return board;
}
```

**O(n · n!) time** as an upper bound (far less in practice), **O(n) extra space** for the sets and the stack, besides the output. `queenCol[r]` needs no un-choose: it is overwritten the next time row r is filled, and only read when every row is set.

</HintLadder>

**Catch the bug:** indexing the diagonal as `diag[r - c]` throws `ArrayIndexOutOfBoundsException` on the first square with c > r — the offset `+ n − 1` is not optional. And clearing only `cols[c]` on the way back leaves stale diagonals that block real solutions. [Solve N-Queens](https://leetcode.com/problems/n-queens/).

<h2 id="combination-sum-ii">Side quest 1 · Each coin once, twins in the purse</h2>

**The map says:** the purse now holds coins that may repeat — `[10, 1, 2, 7, 6, 1, 5]` — and **each coin may be spent at most once**. Every different handful paying exactly 8, written once.

**The reasoning:** two rules you already own, combined. **No reuse** is Chapter 1’s `i + 1`. **Duplicates** are Chapter 2’s sort plus `i > start` twin skip. The sorted break from Chapter 4 still holds.

<Reveal q="Which order should the twin skip and the overshoot break go in — and does it matter?">

Either order gives the right answer: if `c[i]` is a twin of `c[i − 1]`, skipping it is correct; if `c[i] > remain`, breaking is correct, and a twin of an overshooting coin overshoots too. The habit worth keeping is to write the skip first, because it is the rule about **which doors exist**, and the break is a rule about **which doors are worth walking**.

</Reveal>

<HintLadder hints={hints.comboSum2}>

```java id=combinationSum2
public List<List<Integer>> combinationSum2(int[] candidates, int target) {
    Arrays.sort(candidates);
    List<List<Integer>> result = new ArrayList<>();
    backtrack(candidates, target, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] c, int remain, int start, List<Integer> path, List<List<Integer>> result) {
    if (remain == 0) {
        result.add(new ArrayList<>(path));
        return;
    }
    for (int i = start; i < c.length; i++) {
        if (i > start && c[i] == c[i - 1]) continue;       // twin at this junction: already walked
        if (c[i] > remain) break;                          // sorted: every later coin overshoots too
        path.add(c[i]);
        backtrack(c, remain - c[i], i + 1, path, result);  // i + 1: each coin spent once
        path.remove(path.size() - 1);
    }
}
```

**O(n · 2ⁿ) time** in the worst case (every subset of coins is a node), **O(n) extra space**. On `[10, 1, 2, 7, 6, 1, 5]` with target 8: `[1, 1, 6]`, `[1, 2, 5]`, `[1, 7]`, `[2, 6]`.

</HintLadder>

**Transfer test:** what does the output become if you keep `i + 1` but drop the twin skip? (Six pages for four handfuls: the sorted coins `[1, 1, 2, 5, 6, 7, 10]` hold two 1s, so `[1, 2, 5]` and `[1, 7]` are each written once per 1. `[1, 1, 6]` uses both 1s, so it still appears once.) [Solve Combination Sum II](https://leetcode.com/problems/combination-sum-ii/).

<h2 id="permutations-ii">Side quest 2 · Processions with twins</h2>

**The map says:** the banner-bearers include twins — `[1, 1, 2]` — and two orders that look the same are the same order. Every **distinct** ordering, once.

**The reasoning:** sort, keep `used[]`, and add one rule:

```text
skip i  if  i > 0  &&  nums[i] == nums[i - 1]  &&  !used[i - 1]
```

Read it as: **a twin may only step onto the thread after the twin to its left is already on it.** Equal values are then always placed in index order — copy 0, then copy 1, then copy 2 — and each distinct ordering of values has exactly **one** way to assign copies in index order. So it is built exactly once.

Why does `!used[i − 1]` mean “out of order”? At the moment you consider copy `i`, the left twin `i − 1` is either on the thread (`used[i − 1]` is true — fine, the copies are going in order) or not. If it is **not** on the thread, then placing copy `i` now means copy `i − 1` would come later, behind it: the out-of-order assignment of a sequence that the in-order branch already builds. That includes the case where copy `i − 1` was tried **at this same position** a moment ago and un-chosen — which is exactly the duplicate subtree you want to avoid.

<Trace title="Which twin may walk?" steps={permDup} takeaway="Remember: sort, then skip a twin whose left twin is NOT on the thread. That forces equal values into index order, so each distinct ordering has exactly one branch." />

<Reveal q="Some solutions write used[i − 1] without the !. Is that wrong?">

Not wrong — **slower**. `used[i − 1]` forces the copies into **reverse** index order instead (the right twin first). Every distinct ordering still has exactly one branch, so the answer is the same. But branches that start with the wrong copy are only discovered dead deeper down. On `[1, 1, 1, 1]` the `!used` version makes 5 calls to find the single ordering; the `used` version makes 23. Dropping the `used` check entirely (`nums[i] == nums[i − 1]` alone) is wrong: no copy after the first can ever be placed, and on `[1, 1, 2]` the book stays empty. Dropping the skip altogether writes `[1, 1, 2]`, `[1, 2, 1]` and `[2, 1, 1]` twice each: 6 pages for 3 orderings.

</Reveal>

<HintLadder hints={hints.permDup}>

```java id=permuteUnique
public List<List<Integer>> permuteUnique(int[] nums) {
    Arrays.sort(nums);                                      // twins side by side
    List<List<Integer>> result = new ArrayList<>();
    backtrack(nums, new boolean[nums.length], new ArrayList<>(), result);
    return result;
}

private void backtrack(int[] nums, boolean[] used, List<Integer> path, List<List<Integer>> result) {
    if (path.size() == nums.length) {
        result.add(new ArrayList<>(path));
        return;
    }
    for (int i = 0; i < nums.length; i++) {
        if (used[i]) continue;
        if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;   // left twin must already walk
        used[i] = true;
        path.add(nums[i]);
        backtrack(nums, used, path, result);
        path.remove(path.size() - 1);
        used[i] = false;
    }
}
```

**O(n · n!) time** in the worst case (all distinct), **O(n) extra space** besides the output.

</HintLadder>

**Transfer test:** how many pages for `[1, 1, 2, 2]`? (4! / (2! · 2!) = 6.) Then explain, without running anything, why the twin rule needs `used[]` here but Subsets II needed `start`. [Solve Permutations II](https://leetcode.com/problems/permutations-ii/).

<h2 id="generate-parentheses">Side quest 3 · Balanced lanterns</h2>

**The map says:** the Guild hangs n red lanterns that open a passage and n blue lanterns that close one. Every **balanced** row of 2n lanterns — every way to write n pairs of well-formed parentheses.

**The reasoning:** each position has two doors, `(` and `)`. Generating all 2²ⁿ rows and filtering is wasteful. Two counters let the Shears cut every bad door **before** it is walked:

- `(` is open while `open < n` — you still have an opener to spend.
- `)` is open while `close < open` — a closer needs an unmatched opener before it.

With both rules, **every corridor you walk can still be completed**, so no dead ends are visited at all. Record when the row has length 2n.

<Figure caption="n = 2. ‘)’ at the start is cut (close would exceed open); ‘(((’ never happens (open would exceed n). Two rows: (()) and ()().">
  <Mermaid code={`flowchart TD
  R["'' · 0 open, 0 closed"] -->|"("| A["( · 1,0"]
  R -.->|") cut: close would pass open"| X["✗"]
  A -->|"("| AA["(( · 2,0"]
  A -->|")"| AB["() · 1,1"]
  AA -->|")"| AAB["(() · 2,1"] -->|")"| AABB["(()) ✓"]
  AB -->|"("| ABA["()( · 2,1"] -->|")"| ABAB["()() ✓"]`} />
</Figure>

<HintLadder hints={hints.parens}>

```java id=generateParenthesis
public List<String> generateParenthesis(int n) {
    List<String> result = new ArrayList<>();
    backtrack(n, 0, 0, new StringBuilder(), result);
    return result;
}

private void backtrack(int n, int open, int close, StringBuilder path, List<String> result) {
    if (path.length() == 2 * n) {
        result.add(path.toString());
        return;
    }
    if (open < n) {                                   // an opener is still available
        path.append('(');
        backtrack(n, open + 1, close, path, result);
        path.deleteCharAt(path.length() - 1);
    }
    if (close < open) {                               // a closer needs an unmatched opener
        path.append(')');
        backtrack(n, open, close + 1, path, result);
        path.deleteCharAt(path.length() - 1);
    }
}
```

**O(n · Cₙ) time**, where Cₙ is the nth Catalan number (1, 2, 5, 14, 42 for n = 1 … 5; it grows like 4ⁿ / n^1.5): no corridor is wasted and each row costs 2n to copy. **O(n) extra space.**

</HintLadder>

**Transfer test:** add the rule “no lantern may be more than d deep” (at most d unmatched openers at any moment). Which single condition changes? (`open < n` becomes `open < n && open - close < d`.) For n = 3 and d = 2, how many rows survive? (4: everything except `((()))`.) [Solve Generate Parentheses](https://leetcode.com/problems/generate-parentheses/).

<h2 id="combination-sum-iii">Side quest 4 · Nine numbered stones</h2>

**The map says:** nine stones numbered 1 to 9, each usable once. Choose **exactly k** of them that add up to **exactly n**.

**The reasoning:** Chapter 3 (fixed size k) meets Chapter 4 (a purse). Stones are already sorted, so a stone bigger than what is left ends the loop. Record only when the thread holds k stones **and** owes 0; at k stones, return either way.

<HintLadder hints={hints.comboSum3}>

```java id=combinationSum3
public List<List<Integer>> combinationSum3(int k, int n) {
    List<List<Integer>> result = new ArrayList<>();
    backtrack(k, n, 1, new ArrayList<>(), result);
    return result;
}

private void backtrack(int k, int remain, int start, List<Integer> path, List<List<Integer>> result) {
    if (path.size() == k) {                          // k stones: record only if paid exactly
        if (remain == 0) result.add(new ArrayList<>(path));
        return;
    }
    for (int d = start; d <= 9; d++) {
        if (d > remain) break;                       // stones only get bigger from here
        path.add(d);
        backtrack(k, remain - d, d + 1, path, result);   // d + 1: each stone once
        path.remove(path.size() - 1);
    }
}
```

At most C(9, k) ≤ 126 hands, so the work is tiny: **O(k · C(9, k))** time, **O(k)** space. k = 3, n = 9 gives `[1, 2, 6]`, `[1, 3, 5]`, `[2, 3, 4]`.

</HintLadder>

**Transfer test:** add a remaining-sum bound that cuts even earlier: with `need` stones still to pick, the smallest possible total is `d + (d + 1) + … + (d + need − 1)`. Why is it safe to `break` (not `continue`) when that exceeds `remain`? (The smallest total only grows with d.) [Solve Combination Sum III](https://leetcode.com/problems/combination-sum-iii/).

<h2 id="restore-ip">Side quest 5 · The four-part address</h2>

**The map says:** a string of digits like `"25525511135"` is an address with its dots rubbed off. Put back exactly three dots so that it splits into **four parts**, each a number from 0 to 255 with **no leading zero** (`"0"` is fine, `"01"` is not). Every valid address.

**The reasoning:** Palindrome Partitioning with a fixed number of pieces and a different rule for a valid piece. Each junction offers piece lengths 1, 2 or 3. Two kinds of Shears:

- **Piece rules:** a piece longer than one digit can’t start with `0`; a piece can’t exceed 255. Both only get worse as the piece grows, so `break`.
- **Remaining-length bound:** with `left` pieces still to cut, the remaining digits must number between `left` and `3 · left`. Outside that window, no corridor can finish.

<Reveal q='"0000" and "101023": how many addresses each?'>

`"0000"` has exactly one, `0.0.0.0`: every piece must be a lone `0`. `"101023"` has five: `1.0.10.23`, `1.0.102.3`, `10.1.0.23`, `10.10.2.3`, `101.0.2.3`. Note what isn’t there: `1.01.0.23` (leading zero) and anything with a piece above 255.

</Reveal>

<HintLadder hints={hints.ip}>

```java id=restoreIpAddresses
public List<String> restoreIpAddresses(String s) {
    List<String> result = new ArrayList<>();
    backtrack(s, 0, new ArrayList<>(), result);
    return result;
}

private void backtrack(String s, int start, List<String> parts, List<String> result) {
    int left = 4 - parts.size();                       // pieces still to cut
    int rest = s.length() - start;                     // digits still unused
    if (left == 0) {
        if (rest == 0) result.add(String.join(".", parts));
        return;
    }
    if (rest < left || rest > 3 * left) return;        // the Shears: too few or too many digits left
    for (int len = 1; len <= 3 && start + len <= s.length(); len++) {
        String part = s.substring(start, start + len);
        if (len > 1 && part.charAt(0) == '0') break;   // "0" is fine; "01", "012" never are
        if (Integer.parseInt(part) > 255) break;       // a longer piece would only be bigger
        parts.add(part);
        backtrack(s, start + len, parts, result);
        parts.remove(parts.size() - 1);
    }
}
```

At most 3⁴ = 81 corridors whatever the input, so **O(1) time and space** for practical purposes (strings longer than 12 digits are cut at the first junction).

</HintLadder>

**Transfer test:** IPv6-style, eight parts of one to four hex digits each, no leading-zero rule. Which three numbers in the code change? (4 → 8 pieces, 3 → 4 digits per piece, 255 → 0xFFFF — and the zero rule goes away.) [Solve Restore IP Addresses](https://leetcode.com/problems/restore-ip-addresses/).

<h2 id="k-partition">Side quest 6 · Equal shares for k heirs</h2>

**The map says:** an old guild master leaves a chest of coins with values `nums`, to be split among **k heirs** so that every heir’s share has exactly the same total. Is it possible?

**The reasoning:** each coin must go to one of k buckets. The doors at coin `i` are the buckets; a door is open if the coin fits (`bucket[b] + nums[i] ≤ side`, where `side = total / k`). If every coin is placed without overflow, every bucket is exactly `side`, because the buckets add up to `k · side`.

This is the side quest where **pruning decides whether you finish at all**:

1. **Quick exits.** `total % k != 0`, or a coin bigger than `side`: impossible.
2. **Biggest coins first.** Large coins hit the limit early, so bad corridors die near the root instead of near the leaves.
3. **Empty-bucket symmetry.** If a coin failed in an empty bucket, it will fail in every other empty bucket too — they are interchangeable. `break`.

<Reveal q="How much do those prunes buy? Try [2, 2, 2, 2, 3, 4, 5] with k = 4.">

The total is 20, so each heir needs 5; but the 4 can only pair with nothing (no 1s), so the answer is false. With biggest-first **and** the empty-bucket break, the search makes **12** calls. Biggest-first alone: **233**. Smallest-first without the break: **1,245**. And pruning is not a guarantee: the problem is NP-hard in general, and on fifteen 2s and one 3 with k = 3 the fully pruned search still makes **405,870** calls before it can say no. The guaranteed alternative is a bitmask DP over subsets, O(n · 2ⁿ).

</Reveal>

<HintLadder hints={hints.kPartition}>

```java id=canPartitionKSubsets
public boolean canPartitionKSubsets(int[] nums, int k) {
    int total = 0;
    for (int x : nums) total += x;
    if (total % k != 0) return false;
    int side = total / k;
    Arrays.sort(nums);                                       // place the biggest coins first
    if (nums[nums.length - 1] > side) return false;
    return fill(nums, nums.length - 1, new int[k], side);
}

private boolean fill(int[] nums, int i, int[] bucket, int side) {
    if (i < 0) return true;                                  // every coin placed: every bucket is exactly side
    for (int b = 0; b < bucket.length; b++) {
        if (bucket[b] + nums[i] > side) continue;            // the Shears: overflow
        bucket[b] += nums[i];                                // choose
        if (fill(nums, i - 1, bucket, side)) return true;    // explore
        bucket[b] -= nums[i];                                // un-choose
        if (bucket[b] == 0) break;                           // failed in an empty bucket: every empty bucket fails
    }
    return false;
}
```

**O(kⁿ) time** in the worst case, **O(n + k) extra space**. LeetCode’s limits (n ≤ 16, values from 1 to 10⁴) are what make it feasible.

</HintLadder>

**Transfer test:** Matchsticks to Square is this problem with k = 4. And if the question were “**how many** ways to split?”, would you still walk the tree? (Not if n grows — counting is a job for DP over bitmasks; see the next page.) [Solve Partition to K Equal Sum Subsets](https://leetcode.com/problems/partition-to-k-equal-sum-subsets/).

<h2 id="choose-the-tool">When the thread is the wrong tool</h2>

<Scene title="The counting clerk" mood="storm">

A clerk from the Counting House arrives with a question for the Guild. *“The stair below the hall has 40 steps, and you may climb one or two at a time. How many different ways are there to the top?”*

A junior threadwalker brightens and goes down with a ball of thread to walk every way and count the pages. He is still down there at supper, and at breakfast.

The Keeper writes a number on a slip of paper — 165,580,141 — and hands it to the clerk.

*"The thread is for when you must see every way,"* she says. *"When all you want is how many, stop walking. The ways to step 40 are the ways to step 39 plus the ways to step 38."*

</Scene>

Backtracking is the right tool when you must **produce** every answer, or when you must find one answer and there is no structure to exploit. It is the wrong tool when:

- **Only a count is wanted.** The number of answers can be astronomical while the count is easy. Climbing 40 stairs one or two at a time has 165,580,141 ways; a DP over steps computes it in about 40 additions. Same for “how many combinations pay this amount” (Coin Change II) and “how many ordered ways” (Combination Sum IV): **DP**, O(N · target).
- **The best answer is wanted, and subproblems repeat.** Fewest coins, fewest palindrome cuts, longest anything — the same suffix or remaining amount is reached by many different threads. **DP / memoisation** solves each once.
- **The shortest path or fewest moves is wanted.** A thread finds *a* path, not the shortest, unless it walks every path. **BFS** finds the shortest in an unweighted maze or word ladder in one sweep.
- **One valid answer is wanted and the problem has structure.** “Can you jump to the end?” is a **greedy** scan. One N-Queens board for n = 1,000,000 has an explicit construction (see *Look these up yourself*) — no search at all.
- **A yes/no subset question with small numbers.** “Can some subset sum to T?” with n = 200 and values ≤ 100 is a **DP over sums** (T ≤ 20,000), not 2²⁰⁰ threads.

<Reveal q="Word Break asks “can s be split into dictionary words?” — threads or a table?">

A table. The plain thread walk tries every split and is exponential on inputs like `"aaaa…ab"` with dictionary `["a", "aa", "aaa"]`: the same suffix is re-explored down countless threads. Note that `canBreak(i)` depends only on `i`, so memoise it (or fill `dp[i]` left to right) for O(n²) checks. Word Break **II**, which asks for every sentence, is a backtracking problem again — the output itself can be exponential — but memoising the suffixes still helps.

</Reveal>

<h2 id="wider-family">The neighbouring guilds · How the other roadmap patterns connect</h2>

The Guild of Threadwalkers isn’t the only one in the realm that walks a tree and comes back. The shared idea: **a depth-first walk that undoes its own changes on the way back up.**

| Shared idea | Where it shows up | Where it belongs |
|---|---|---|
| The thread is a stack: choose = push, un-choose = pop | The path list and the call stack move together | <a href={`${BASE}dsa/lessons/stacks/`}>Stacks</a> |
| Root-to-leaf path with remove-on-return | Path Sum II records every root-to-leaf path with a target sum, removing the node on the way back up | <a href={`${BASE}dsa/lessons/trees-dfs/`}>Trees (DFS)</a> |
| Visited marks that stay vs. marks that are lifted | Number of Islands marks for good (reachability); Word Search lifts the mark (paths) | <a href={`${BASE}dsa/lessons/graphs/`}>Graphs</a> |
| A subtree whose answer depends only on where you are | Word Break, Coin Change, Palindrome Partitioning II: memoise the thread’s suffix | <a href={`${BASE}dsa/lessons/dp-1d/`}>1-D Dynamic Programming</a> |
| A subset is a row of on/off bits | Iterate masks 0 … 2ⁿ − 1 instead of recursing; bitmask DP for k-partition | <a href={`${BASE}dsa/lessons/bit-manipulation/`}>Bit Manipulation</a> |
| Running totals removed on the way back | Path Sum III keeps a vault of prefix totals for the current path only | <a href={`${BASE}dsa/lessons/prefix-sum/`}>Prefix Sum</a> |

**Backtracking is DFS on a tree you never build.** Trees DFS walks a tree that exists in memory; backtracking walks the tree of partial answers, generated one door at a time. The recursion looks the same, and the habit that matters is the same: **every change you make on the way down, undo on the way up.**

**Visited means different things.** In graph traversal, a visited mark is permanent, because the question is reachability. In backtracking, a mark means “on the current thread”, so it must be lifted when the thread leaves. Mixing them up is the Word Search bug from Chapter 7.

<h2 id="exit-ticket">The threadwalker’s exam · Build a solution with the labels removed</h2>

<Scene title="No chapter titles" mood="dawn">

On the morning of the exam the Keeper hands you three maps with no chamber names, a fresh ball of thread, and the three questions carved over the stair behind her.

*"Pick one,"* she says. *"Before you write a line of code, tell me what the thread holds, what the doors are at each junction, and what makes you wind back."*

</Scene>

Choose one. Keep the tutorial code closed. Draw the tree for a tiny input first, then code it.

1. **The changing case.** Given a string of letters and digits, return every string you can make by switching each letter between lower and upper case (digits stay as they are). Test: `""`, `"1"`, `"a1b2"`, a string of only digits.
2. **The kind arrangement.** Numbers 1 … n are put in a row, positions 1 … n. An arrangement is *kind* if, at every position i, the number there divides i or i divides it. Count the kind arrangements for n up to 15. Test: n = 1, 2, 3 (answers 1, 2, 3).
3. **The dictionary sentences.** Given a string and a dictionary, return every way to insert spaces so each piece is a dictionary word. Test: no split possible, one word, a word that is a prefix of another.

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**The changing case:** the include/exclude shape — at each letter, two doors (lower, upper); at each digit, one. Depth = position; record at the end. At most 2ⁿ strings, O(n · 2ⁿ).

**The kind arrangement:** permutations with `used[]`, filling position `pos` (1-indexed) and pruning a number the moment it fails the divisibility test at that position, so the tree never grows a bad prefix. Count leaves instead of recording them. The pruning is what makes n = 15 fast; walking all 15! orders would not be.

**The dictionary sentences:** Palindrome Partitioning with “is a dictionary word” in place of “is a palindrome”. Doors = end positions of the next word. For heavy inputs, memoise the sentences of each suffix.

Now break your own solution on purpose — drop an un-choose, record without copying, use `i > 0` for a twin skip — and name the test that catches it. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

Passing this once is a useful checkpoint. Rebuild one of these on another day, with a changed input and without the headings choosing the pattern for you.

<h2 id="cheat-sheet">The Keeper’s map notes</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Every subset | Loop from `start`, child at `i + 1`, record at every node | The thread is increasing; each subset has one node |
| Every subset, values repeat | Sort; skip `i > start && nums[i] == nums[i − 1]` | Siblings at a junction carry distinct values |
| Exactly k of 1..n | Record at size k; loop to `n − need + 1` | Every node can still reach a full hand |
| Reusable coins to a target | Sort; child at `i`; `break` when the coin exceeds `remain` | `remain ≥ 0`; the thread is non-decreasing |
| Each position has its own menu | Depth = position; doors = that position’s options | One option per position so far |
| Every ordering | `used[]`, loop from 0, record at size n | `used[i]` is true exactly for items on the thread |
| A path in a grid, no cell twice | Mark the cell, explore 4 ways, restore it | Marked cells are exactly the current path |
| Cut a string into valid pieces | Doors = end positions; walk only valid pieces | Pieces on the thread spell `s[0..start − 1]` |
| Place pieces that can’t attack | One per row; column, `r − c + n − 1`, `r + c` sets | The sets hold exactly the placed queens’ lines |
| Coins once, purse has twins | Sort; twin skip; child at `i + 1`; sorted break | Sibling coins carry distinct values |
| Orderings with twins | Sort; skip twin if `!used[i − 1]` | Equal values are placed in index order |
| Balanced brackets | `(` while `open < n`; `)` while `close < open` | Every walked prefix can still be completed |
| Exactly k numbers from 1..9 summing to n | Size k + purse; `break` on overshoot | `remain ≥ 0`, the thread is increasing |
| Split a string into a fixed number of valid parts | Piece rules + remaining-length window | Remaining digits fit the remaining parts |
| Split items into k equal buckets | Biggest first; overflow skip; empty-bucket break | No bucket exceeds `total / k` |

**Exponential is not a bug here.** Every row of this table produces (or searches) an exponential family. Say the honest bound — O(n · 2ⁿ), O(n · n!), O(k · C(n, k)) — and say what the pruning buys on top of it.

## Five bugs the Keeper keeps in her pocket

1. **Pinning the thread.** `result.add(path)` stores the one shared list; every page ends empty. Record `new ArrayList<>(path)` (or `sb.toString()`).
2. **The forgotten un-choose.** Every add, mark, bell or counter changed before the recursive call must be undone right after it — including `used[i] = false` and restoring a grid cell.
3. **The wrong twin rule.** `i > 0` instead of `i > start` loses subsets with repeated values; no sort means the rule never sees the twins.
4. **Reuse confusion.** Child at `i + 1` when reuse is allowed loses `[2, 2, 3]`; child at `i` when it isn’t uses a coin twice; child at `0` writes every handful once per order.
5. **Java’s `remove(int)`.** `path.remove(nums[i])` removes by position, not by value. Write `path.remove(path.size() - 1)`.
