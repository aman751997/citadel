<h2 id="prologue">Prologue · What a DP problem looks like</h2>

Dynamic programming is one idea: **answer every smaller version of the question once, write it down, and build each bigger answer only from answers already written.** A written answer is never recomputed.

Example: in how many ways can you climb 30 stairs, one or two steps at a time? The ways to reach step 30 are the ways to reach step 29 plus the ways to reach step 28. A plain recursion asks "how many ways to reach step 3?" over 300,000 times on the way. A table asks it once.

It works when a problem has two properties:

- **Optimal substructure.** The answer to the big question can be assembled from answers to smaller questions of the same kind.
- **Overlapping subproblems.** The same smaller questions come up again and again.

Without the first, no table helps: the pieces don't combine. Without the second, there is nothing to save: merge sort splits into halves that never repeat, so it is plain divide and conquer. **Both together is the signal.**

### Three ways to write the same thing

Every problem here is solved in this order:

1. **Brute-force recursion.** Define a function for the smaller question and call it on every possible last decision. Correct, usually exponential.
2. **Memoisation (top-down).** The same recursion plus a cache. Before computing, look in the cache; after computing, store. Same code shape, polynomial time.
3. **Tabulation (bottom-up).** Fill the cache in an order where everything a cell needs is already written. No recursion. Then, if each cell reads only a few recent cells, keep only those (space optimisation).

The cache and the table are the same array: memoisation discovers the order by recursing, tabulation chooses it in advance.

### The five answers

Before you code any DP problem, say these five things, in this order. They replace memorising problems:

1. **State.** Finish the sentence "`dp[i]` is the number of ways / the cheapest cost / whether it is possible … for the first `i` …". If you cannot say it in one sentence, you cannot build it.
2. **Recurrence, from the last decision.** Look at the final move of any solution and list what it could have been. Each possibility leaves a smaller problem whose answer is a cell you already have.
3. **Base cases.** The smallest cells the recurrence cannot build. Usually the empty prefix, `dp[0]`.
4. **Order of transitions.** Every cell the recurrence reads must be written before the cell that reads it. In one dimension that is usually left to right.
5. **Where the answer lives, and the space.** Which cell answers the original question: `dp[n]`, or the largest `dp[i]`? Then ask how far back the recurrence reads. If it reads a fixed number of recent cells, keep only those.

Three questions to ask at every cell: **what is settled** (every cell already written is final), **why is this transition safe** (the cases split every solution and each case is a settled cell), and **when do I stop** (when the answer cell is written).

### Three kinds of question, three ways to combine

| The question asks… | Combine the cases with | An impossible case counts as | The empty base is usually |
|---|---|---|---|
| **How many ways?** (counting) | **sum** | 0 | 1: one way to do nothing |
| **Cheapest or best?** (optimisation) | **min** or **max** | a sentinel such as "∞", or skip it | 0 |
| **Is it possible?** (feasibility) | **OR** | false | true |

One rule hides in that table. **Counting needs cases that do not overlap**: if one solution fits two cases, a sum counts it twice. Min, max and OR do not care; seeing the same candidate twice changes nothing.

### How to recognise it

- The question asks **how many ways**, **the minimum or maximum**, or **whether it is possible**, over a sequence, string or amount.
- Each answer is built from a **choice at each position** (take or skip, one step or two, which coin, where the word ends), and the choices interact only through a small summary: the index reached, the amount left. **That summary is your state.**
- Brute force tries every sequence of choices (2ⁿ). The table visits each state once, so the cost drops to **(number of states) × (choices per state)**: O(n), O(n²) or O(n × amount).
- It does **not** fire when you must list every solution (the output itself is exponential: that is backtracking), or when one greedy choice is provably always safe (that is greedy, and cheaper). See <a href="#choose-the-tool">When a table is overkill</a>.

<h2 id="climbing-stairs">Chapter 1 · Climbing Stairs</h2>

### Problem

You climb `n` steps, taking one or two at a time. How many distinct ways reach the top?

`n = 3` gives 3: 1+1+1, 1+2, 2+1. `n = 5` gives 8.

This chapter walks the whole journey once, **brute force → memoisation → table → rolling variables**, so every later chapter can start from the table.

### How to recognise it

- "How many ways", with a fixed set of moves.
- The last move is one of a few options, and what came before is the same problem, smaller.

### Brute force

Look at the **last move** of any climb to step `n`. It was a single step from `n − 1` or a double step from `n − 2`. Those two groups never overlap (the last move differs) and miss nothing (there is no third kind of move). So:

```java id=climbBrute
public int climbStairs(int n) {
    if (n <= 1) return 1;                            // step 0 or step 1: exactly one way
    return climbStairs(n - 1) + climbStairs(n - 2);  // last move was one step, or two
}
```

It is correct. It is also hopeless for large `n`, and the call tree shows why.

Count the calls: `calls(n) = 1 + calls(n − 1) + calls(n − 2)`, with one call each for `n = 0` and `n = 1`. That gives 1, 1, 3, 5, 9, 15, … which is exactly `2 × ways(n) − 1`. For `n = 30` that is **2,692,537 calls** to produce the answer 1,346,269. The call count grows by about ×1.618 per step: **exponential time**, O(φⁿ), where φ is the golden ratio.

### Memoisation

Same recursion, one change: **before computing, check the cache; after computing, write the answer.**

```java id=climbMemo
public int climbStairs(int n) {
    int[] memo = new int[n + 1];                     // 0 = not computed yet (every real answer is ≥ 1)
    return climb(n, memo);
}

private int climb(int i, int[] memo) {
    if (i <= 1) return 1;
    if (memo[i] != 0) return memo[i];                // already computed: read it, don't recurse
    memo[i] = climb(i - 1, memo) + climb(i - 2, memo);
    return memo[i];
}
```

Now each step from 2 to `n` is solved once and makes two calls; every later visit is a lookup. That is **2n − 1 calls**: 9 for `n = 5` instead of 15, and 59 for `n = 30` instead of 2.7 million. **O(n) time, O(n) space** for the cache, plus O(n) depth of recursion on the call stack.

The sentinel matters: "0 means not computed" is safe only because no real answer is 0. When 0 *can* be an answer, fill the cache with −1 or use `Integer[]` with `null`.

### Intuition

The recursion only ever asks about `n − 1`, `n − 2`, …, `0`: that is `n + 1` different questions. So write the answers to those questions down in order, smallest first, and nothing needs to recurse.

**The five answers.**

- **State:** `ways[i]` = the number of distinct ways to stand on step `i`, starting from the ground (step 0).
- **Recurrence:** the last move was one step (from `i − 1`) or two (from `i − 2`): `ways[i] = ways[i − 1] + ways[i − 2]`.
- **Base cases:** `ways[0] = 1` (the empty climb) and `ways[1] = 1`.
- **Order:** `i` from 2 up to `n`. Both cells it reads are smaller, so both are written.
- **Space:** each cell reads only the last two. Keep two variables, O(1).

### Algorithm

1. Set `ways[0] = 1` and `ways[1] = 1`.
2. For `i` from 2 to `n`, set `ways[i] = ways[i − 1] + ways[i − 2]`.
3. Return `ways[n]`.
4. To save space, keep only `prev = ways[i − 2]` and `curr = ways[i − 1]`, and slide them up one step each iteration.

### Java solution

First the table, so the recurrence is visible:

```java id=climbTable
public int climbStairs(int n) {
    int[] ways = new int[n + 1];
    ways[0] = 1;                                     // the empty climb: one way to stay put
    if (n >= 1) ways[1] = 1;
    for (int i = 2; i <= n; i++)
        ways[i] = ways[i - 1] + ways[i - 2];         // both cells are already written
    return ways[n];
}
```

The loop reads only the last two cells. Everything below them is never touched again, so two variables carry them up the stair.

```java id=climbStairs
public int climbStairs(int n) {
    int prev = 1, curr = 1;                          // ways[0], ways[1]
    for (int i = 2; i <= n; i++) {
        int next = curr + prev;                      // ways[i] = ways[i-1] + ways[i-2]
        prev = curr;                                 // slide both variables up one step
        curr = next;
    }
    return curr;                                     // loop exit: curr = ways[n], prev = ways[n-1]
}
```

**O(n) time, O(1) extra space.** The four versions in this chapter all return the same numbers; the checker runs each against an independent count of every climb.

</HintLadder>

### Why it works

Every climb to step `i` ends with exactly one last move, a 1 or a 2. Removing it leaves a climb to `i − 1` or `i − 2`, and every such climb extends in exactly one way. So the two groups are disjoint, complete, and counted by cells already written.

**What stays true:** at the top of iteration `i`, `curr = ways[i − 1]` and `prev = ways[i − 2]`. When the loop ends, `curr = ways[n]` and `prev = ways[n − 1]`, so `curr` is the answer. Narrating the loop exit like this is a habit worth building.

<Reveal q="Why is ways[0] = 1? Nobody climbed anything.">

Because the recurrence needs it to be. `ways[2]` must be 2 (1+1, or 2). The recurrence says `ways[2] = ways[1] + ways[0] = 1 + ways[0]`, so `ways[0]` must be 1. In words: **there is exactly one way to do nothing**, and the double step from the ground extends it. Counting problems almost always start with "empty = 1". Setting it to 0 makes every answer wrong from step 2 on.

</Reveal>

<Reveal q="Isn’t this just Fibonacci?">

Yes, shifted by one: `ways(n) = F(n + 1)` with `F(1) = F(2) = 1`. Knowing that is a bonus, not a method: the next chapter changes one word of the question and the formula is gone, while the five answers still work. It does tell you about overflow: `ways(45) = 1,836,311,903` just fits in an `int` (LeetCode caps `n` at 45), and `ways(46) = 2,971,215,073` would not.

</Reveal>

### Complexity

- **Time O(n):** one addition per step.
- **Space O(1)** with two variables, O(n) with the table or the memo.

### Edge cases and mistakes

- **Sliding in the wrong order.** `prev = curr; curr = curr + prev;` overwrites `prev` before it is used, so each step just doubles `curr`. For `n = 5` it returns 16 instead of 8. Keep the new value in `next` until both old ones have been read.

### Practice

Allow moves of 1, 2 or 3 steps (see <a href="#k-steps">Up to k steps</a>), then break some steps.

<h2 id="min-cost-stairs">Chapter 2 · Min Cost Climbing Stairs</h2>

### Problem

`cost[i]` is the toll for **standing** on step `i`. You may start on step 0 or step 1 for free, climb one or two steps at a time, and the top is the position just past the last step, where nobody collects a toll. Find the cheapest total.

`cost = [10, 15, 20]` gives 15: start on step 1, pay 15, step two to the top.

### How to recognise it

- Climbing Stairs, but "cheapest" instead of "how many". Cost is paid per step stood on, so the best path may skip a cheap step to avoid an expensive one beyond it.

### Brute force

Define `arrive(i)` = the cheapest toll total to arrive at position `i`, and recurse on both last moves. Memoisation is the same cache as Chapter 1.

```java fragment
int arrive(int[] cost, int i) {                      // cheapest way to arrive at position i
    if (i <= 1) return 0;                            // start on step 0 or 1 for free
    return Math.min(arrive(cost, i - 1) + cost[i - 1],    // one step up, paying for step i-1
                    arrive(cost, i - 2) + cost[i - 2]);   // two steps up, paying for step i-2
}
// brute force: O(2^n) calls. Memoised with int[] memo (-1 = empty): one call per i, O(n).
```

Positions repeat exactly as in Chapter 1; only the combine step changes, `min` instead of `+`.

### Intuition

The cheapest climb to `i` must use the cheapest climb to wherever it came from: swapping in a cheaper prefix could only lower the total. That is optimal substructure in one sentence.

**The five answers.**

- **State:** `dp[i]` = the cheapest total toll to **arrive at** position `i`, where positions run from 0 to `n` and position `n` is the top.
- **Recurrence:** you arrived by one step from `i − 1` (paying `cost[i − 1]`, the step you stood on) or two from `i − 2` (paying `cost[i − 2]`): `dp[i] = min(dp[i − 1] + cost[i − 1], dp[i − 2] + cost[i − 2])`.
- **Base cases:** `dp[0] = dp[1] = 0`. Starting on either is free.
- **Order:** `i` from 2 to `n`.
- **Answer and space:** `dp[n]`, the top, **not** `dp[n − 1]`, the last step. Only the last two cells are read, so O(1) extra space works.

### Algorithm

1. Create `dp` with `n + 1` cells. Set `dp[0] = dp[1] = 0`.
2. For `i` from 2 to `n`, set `dp[i]` to the smaller of the two arrivals.
3. Return `dp[n]`.

### Java solution

<HintLadder hints={hints.minCost}>

```java id=minCostClimbingStairs
public int minCostClimbingStairs(int[] cost) {
    int n = cost.length;
    int[] dp = new int[n + 1];                       // dp[i] = cheapest way to arrive at position i
    dp[0] = 0;                                       // you may start on step 0...
    dp[1] = 0;                                       // ...or on step 1, for free
    for (int i = 2; i <= n; i++)
        dp[i] = Math.min(dp[i - 1] + cost[i - 1],    // one step up from i-1, paying for i-1
                         dp[i - 2] + cost[i - 2]);   // two steps up from i-2, paying for i-2
    return dp[n];                                    // the top is position n, past the last step
}
```

**O(n) time, O(n) space** as written; the loop reads only the last two cells, so two variables give **O(1)** exactly as in Chapter 1. Tolls are at most 999 and there are at most 1000 steps, so totals stay far inside `int`.

</HintLadder>

<Trace title="Pay for the step you stand on" steps={minCost} takeaway="Remember: dp[i] = min(dp[i − 1] + cost[i − 1], dp[i − 2] + cost[i − 2]); the top is position n, past the last step." />

### Why it works

Any climb to `i` ends with a single or a double step, and what it paid before that last move is the cost of a climb to `i − 1` or `i − 2`. The cheapest climb to `i` must use the cheapest climb to wherever it came from. **What stays true:** before iteration `i`, every `dp[0..i − 1]` is the true minimum for its position.

<Reveal q="Counting needed disjoint cases. Does min?">

No. If two last moves led to the same climb, `min` would see the same cost twice and still pick correctly. **Optimisation and feasibility forgive overlap; counting does not.** That is why Chapter 1 had to argue "the last move differs, so the groups are disjoint", and this chapter only needs "the cases cover every climb".

</Reveal>

### Complexity

- **Time O(n):** one `min` per position.
- **Space O(n)** as written, O(1) with two rolling variables.

### Edge cases and mistakes

- **Returning `dp[n − 1]`.** That treats the last step as the top. On `[10, 15, 20]` it returns 10, the price of arriving on the last step before paying its toll, instead of 15.
- Paying `cost[i]` for the step you **arrive** on instead of the one you leave: the state says "arrive at `i`", so tolls belong to the steps you left from.

### Practice

Redefine the state as "cheapest cost of a climb that stands on step `i` and pays for it": `dp[i] = cost[i] + min(dp[i − 1], dp[i − 2])`, and the answer moves to `min(dp[n − 1], dp[n − 2])`.

<h2 id="house-robber">Chapter 3 · House Robber</h2>

### Problem

Houses in a line hold `nums[i]` each. You cannot take from two neighbouring houses. Find the most you can collect.

`[2, 7, 9, 3, 1]` gives 12 (houses 0, 2 and 4). `[2, 1, 1, 2]` gives 4 (houses 0 and 3).

### How to recognise it

- "Maximum sum with no two adjacent picks": a take-or-skip choice at every position, where taking blocks the neighbour.
- Brute force is every subset, 2ⁿ of them.

### Brute force

Decide only the **last house**. If you knock, the previous house is off-limits; if you skip, the rest is the same problem one house shorter.

```java fragment
int best(int[] nums, int i) {                        // most from houses 0..i-1
    if (i == 0) return 0;
    if (i == 1) return nums[0];
    return Math.max(nums[i - 1] + best(nums, i - 2), // knock the last house, skip the one before
                    best(nums, i - 1));              // skip the last house
}
// brute force: two calls per level, O(2^n). With int[] memo (-1 = empty): O(n) time and space.
```

The calls overlap exactly as in Chapter 1, so the same cache fixes it.

### Intuition

The last house is either in the plan or not. Whichever it is, what remains is a smaller street whose best answer you already know.

**The five answers.**

- **State:** `dp[i]` = the most from **the first `i` houses** (houses `0..i − 1`).
- **Recurrence:** **knock** house `i − 1`: `nums[i − 1] + dp[i − 2]`, because house `i − 2` is off-limits. **Skip** it: `dp[i − 1]`. Take the larger.
- **Base cases:** `dp[0] = 0` (no houses), `dp[1] = nums[0]`.
- **Order:** left to right.
- **Answer and space:** `dp[n]`. Only the last two cells are read: O(1) with `prev` and `curr`.

Notice the convention: **`dp` has n + 1 cells and `dp[i]` covers a prefix of length `i`**, so `dp[0]` is the empty street and no index ever goes negative. It is the same trick as the zero on top of a prefix-sum array.

### Algorithm

1. Set `prev = 0` (`dp[0]`) and `curr = 0`.
2. For each purse `x`, compute `next = max(curr, prev + x)`: skip it, or knock on top of `dp[i − 2]`.
3. Slide: `prev = curr`, `curr = next`.
4. Return `curr`.

### Java solution

<HintLadder hints={hints.robber}>

```java id=rob
public int rob(int[] nums) {
    int prev = 0, curr = 0;                          // dp[i-2], dp[i-1]: before the street, both 0
    for (int x : nums) {                             // x = nums[i-1], the house being decided
        int next = Math.max(curr, prev + x);         // skip it, or knock on top of dp[i-2]
        prev = curr;
        curr = next;
    }
    return curr;                                     // dp[n]
}
```

**O(n) time, O(1) extra space.** At most 100 houses of at most 400 each: no overflow risk.

</HintLadder>

<Trace title="Knock or skip?" steps={robber} takeaway="Remember: dp[i] = max(nums[i − 1] + dp[i − 2], dp[i − 1]). The cell says what the best prefix earns, not whether its last house was used." />

### Why it works

The best plan for the first `i` houses either uses house `i − 1` or it does not. If it does, it cannot use house `i − 2`, and the rest of it must be a best plan for the first `i − 2` houses (otherwise swap in a better one). If it does not, it is a best plan for the first `i − 1`. Both are settled cells.

**What stays true:** before handling house `i − 1`, `curr = dp[i − 1]` and `prev = dp[i − 2]`, the best totals for the two shorter streets.

<Reveal q="Two greedy habits: ‘every other door’ and ‘biggest purse first’. Do either work?">

Neither. **Every other door** on `[2, 1, 1, 2]` collects 2 + 1 = 3 either way, but houses 0 and 3 give 4. **Biggest first** on `[3, 4, 3]` grabs the 4, which blocks both 3s: total 4, when 3 + 3 = 6. One locally attractive door can cost you two good neighbours. The table tries both options at every door and keeps the better one, which is exactly what greedy cannot afford to do.

</Reveal>

<Reveal q="Does dp[i] mean house i − 1 was robbed?">

No, and this is the most common confusion in state design. `dp[i]` is the best **for the prefix**, whichever way it was achieved. Some people define `rob[i]` = the best plan that *does* use house `i`; that works too, but then the answer is the max over all `rob[i]`, and the recurrence must look back two **or three** houses. Pick the state that makes the last decision simplest, and say it in words before you code.

</Reveal>

### Complexity

- **Time O(n):** one comparison per house.
- **Space O(1):** two variables instead of the whole `dp` array.

### Edge cases and mistakes

- **The every-other-door habit, written as code.**

```java fragment
int even = 0, odd = 0;                       // BUG: assumes the best plan alternates perfectly
for (int i = 0; i < nums.length; i++) if (i % 2 == 0) even += nums[i]; else odd += nums[i];
return Math.max(even, odd);                  // [2, 1, 1, 2] → 3, but houses 0 and 3 give 4
```

The best plan may skip **two** doors in a row.

<h2 id="house-robber-circle">Chapter 4 · House Robber II</h2>

### Problem

Same rule, but the houses stand in a circle: house `0` and house `n − 1` are neighbours too.

`[2, 7, 9, 3, 1]` on a ring gives 11 (2 + 9), not 12: houses 0 and 4 are now neighbours.

### How to recognise it

- A known linear problem made circular: the new constraint touches exactly one pair, the two ends.

### Brute force

Try every subset and reject any with two neighbours, counting the end pair as neighbours: O(2ⁿ · n). A recursion with one extra flag, "did we take house 0?", does the same job.

```java fragment
int go(int[] a, int i, boolean tookFirst) {          // best from houses i..n-1
    if (i >= a.length) return 0;
    int skip = go(a, i + 1, tookFirst);
    boolean blocked = i == a.length - 1 && tookFirst;     // the last house touches house 0
    int take = blocked ? 0 : a[i] + go(a, i + 2, tookFirst || i == 0);
    return Math.max(skip, take);
}
// brute force: O(2^n). Memo on (i, tookFirst): 2n states, O(n).
```


### Intuition

**In every valid plan, at least one of the two ends is skipped.** So every valid plan lives entirely inside one of two straight streets:

- houses `0..n − 2` (the last one skipped), or
- houses `1..n − 1` (the first one skipped).

Each is Chapter 3 exactly, and neither can contain the forbidden pair. Run both and take the larger. One special case: a single house has no neighbour at all, and both streets would be empty, so return `nums[0]` directly.

**The five answers.**

- **State:** per street, the same as Chapter 3: `dp[i]` = the most from the first `i` houses *of that street*.
- **Recurrence:** `dp[i] = max(nums[i − 1] + dp[i − 2], dp[i − 1])` on each street.
- **Base cases:** `dp[0] = 0`, `dp[1]` = the street's first purse. For the whole ring with `n = 1`, return `nums[0]`.
- **Order:** left to right, once per street.
- **Answer and space:** `max(street one, street two)`. Two passes of two variables: O(1).

### Algorithm

1. If `n == 1`, return `nums[0]`.
2. Run House Robber on houses `0..n − 2`.
3. Run House Robber on houses `1..n − 1`.
4. Return the larger of the two.

### Java solution

<HintLadder hints={hints.circle}>

```java id=robCircle
public int rob(int[] nums) {
    int n = nums.length;
    if (n == 1) return nums[0];                      // one house: no neighbour to worry about
    return Math.max(robLine(nums, 0, n - 2),         // leave the last house alone
                    robLine(nums, 1, n - 1));        // or leave the first house alone
}

private int robLine(int[] nums, int lo, int hi) {   // Chapter 3 on nums[lo..hi]
    int prev = 0, curr = 0;
    for (int i = lo; i <= hi; i++) {
        int next = Math.max(curr, prev + nums[i]);
        prev = curr;
        curr = next;
    }
    return curr;
}
```

**O(n) time, O(1) extra space**: two passes of Chapter 3.

</HintLadder>

<Trace title="Break the ring" steps={circle} takeaway="Remember: some end of the ring is always skipped, so solve houses 0..n − 2 and houses 1..n − 1 with Chapter 3, and take the max. One house is a special case." />

### Why it works

Every valid plan on the ring skips house 0 or house `n − 1` (or both), so it is a valid plan on one of the two streets. Conversely, every valid plan on either street is valid on the ring, because the street leaves out one end of the forbidden pair. So the best on the ring is the best of the two streets.

**What stays true:** each call to `robLine` sees a straight street, where Chapter 3's invariant holds unchanged.

<Reveal q="Why not run Chapter 3 once on the whole ring and fix it up if it used both ends?">

Because "fixing up" is a new optimisation problem. If the straight answer used both ends, you would need the best plan without one of them, which is the two-street computation anyway. Splitting first means each sub-problem has the clean structure the five answers need.

</Reveal>

### Complexity

- **Time O(n):** two linear passes.
- **Space O(1):** two variables per pass.

### Edge cases and mistakes

- **Dropping the `n == 1` check.** With one house both streets are empty (`0..−1` and `1..0`), so `[7]` returns 0 instead of 7.
- `n == 2`: each street is a single house, and the answer is the larger of the two. `[1, 2]` gives 2.

<h2 id="decode-ways">Chapter 5 · Decode Ways</h2>

### Problem

A digit string encodes letters: `A = 1`, `B = 2`, …, `Z = 26`. Count the ways to cut the string into valid letters.

`"226"` gives 3 (2-2-6, 22-6, 2-26). `"06"` gives 0.

### How to recognise it

- "Count the ways to split or decode a string", where each piece is one of a few allowed sizes.
- Some pieces are valid only under a condition (here the value range 1..26), so the transition has `if`s.

### Brute force

Recurse on the last letter: it used one digit or two. Try both, when allowed.

```java fragment
int ways(String s, int i) {                          // decodings of the first i digits
    if (i == 0) return 1;                            // the empty prefix: one way
    int total = 0;
    if (s.charAt(i - 1) != '0') total += ways(s, i - 1);        // last letter = one digit
    if (i >= 2) {
        int two = (s.charAt(i - 2) - '0') * 10 + (s.charAt(i - 1) - '0');
        if (two >= 10 && two <= 26) total += ways(s, i - 2);    // last letter = two digits
    }
    return total;
}
// brute force: up to two calls per level, O(2^n) on a string of ones. Memo: n + 1 states, O(n).
```

This is Chapter 1's tree again, with some branches switched off by conditions.

### Intuition

Cover all but the last digit with your hand. The last letter used either the last digit or the last two. When is each one allowed?

**The zero is the whole problem.** A `'0'` can never be a letter on its own, and can only finish a two-digit letter as **10** or **20**. Learn these by heart; interviewers love them:

| Input | Answer | Why |
|---|---|---|
| `"0"` | 0 | 0 alone is no letter |
| `"06"` | 0 | 0 alone fails; "06" has a leading zero, so it is not 6 |
| `"10"` | 1 | only J (10); "1, 0" fails on the 0 |
| `"27"` | 1 | 27 > 26, so only B, G |
| `"100"` | 0 | J leaves a lone 0; "00" is no letter |
| `"226"` | 3 | 2-2-6, 22-6, 2-26 |
| `"11106"` | 2 | 1-1-10-6 and 11-10-6 |

**The five answers.**

- **State:** `dp[i]` = the number of ways to decode **the first `i` digits**.
- **Recurrence:** **one digit**, `s[i − 1]`, allowed when it is `'1'..'9'`: adds `dp[i − 1]`. **Two digits**, `s[i − 2..i − 1]`, allowed when they form **10 to 26** (which rules out a leading zero): adds `dp[i − 2]`.
- **Base cases:** `dp[0] = 1`. The empty prefix decodes one way (to nothing), so a valid first letter extends it.
- **Order:** `i` from 1 to `n`; the two-digit case needs `i ≥ 2`.
- **Answer and space:** `dp[n]`. Only the last two cells are read: O(1) with two variables, O(n) as written.

### Algorithm

1. Create `dp` with `n + 1` cells and set `dp[0] = 1`.
2. For `i` from 1 to `n`: if `s[i − 1]` is not `'0'`, add `dp[i − 1]`.
3. If `i ≥ 2` and the last two digits are between 10 and 26, add `dp[i − 2]`.
4. Return `dp[n]`.

### Java solution

<HintLadder hints={hints.decode}>

```java id=numDecodings
public int numDecodings(String s) {
    int n = s.length();
    int[] dp = new int[n + 1];                       // dp[i] = decodings of the first i digits
    dp[0] = 1;                                       // the empty prefix: one way (decode nothing)
    for (int i = 1; i <= n; i++) {
        char one = s.charAt(i - 1);
        if (one != '0') dp[i] += dp[i - 1];          // last letter used one digit: '1'..'9'
        if (i >= 2) {
            int two = (s.charAt(i - 2) - '0') * 10 + (one - '0');
            if (two >= 10 && two <= 26) dp[i] += dp[i - 2];   // last letter used two digits
        }
    }
    return dp[n];
}
```

**O(n) time, O(n) space**, or O(1) with two rolling variables (the loop reads only `dp[i − 1]` and `dp[i − 2]`). LeetCode guarantees the answer fits in a 32-bit integer.

</HintLadder>

<Trace title="One digit, two digits, both or neither?" steps={decode} takeaway="Remember: one digit needs 1..9; two digits need 10..26. dp[0] = 1, and a zero can only end a 10 or a 20." />

### Why it works

Every decoding of the first `i` digits ends with a one-digit or a two-digit letter, never both, so the two groups are **disjoint** and counting by sum is safe. Removing the last letter leaves a decoding of the first `i − 1` or `i − 2` digits, already counted.

**What stays true:** `dp[i]` counts decodings of exactly the first `i` digits, using every one of them. A zero that cannot be absorbed makes `dp[i] = 0`, and that 0 then poisons everything that reads it, correctly.

<Reveal q="dp[0] = 1 for an empty message seems like cheating. What breaks if it is 0?">

`dp[2]` for `"12"` must be 2 (A-B or L). The two-digit case adds `dp[0]`. If `dp[0] = 0`, the reading "L" is never counted and you get 1. **The empty prefix is the one way to have decoded nothing yet**, the same 1 as Chapter 1's empty climb.

</Reveal>

### Complexity

- **Time O(n):** two constant-time checks per digit.
- **Space O(n)** for `dp`, O(1) with rolling variables.

### Edge cases and mistakes

- **Testing the two-digit letter with `Integer.parseInt(s.substring(i - 2, i)) <= 26`.** On `"06"` the parse gives 6, so the code counts "F" and returns 1 instead of 0. The check is `10 ≤ two ≤ 26`, and the 10 is what forbids the leading zero.
- `"100"` is 0: the final `"00"` is no letter, and `"10"` then leaves a lone `"0"`.

<h2 id="coin-change">Chapter 6 · Coin Change</h2>

### Problem

Fewest coins that sum to exactly `amount`, each denomination usable any number of times; return −1 if impossible.

`coins = [1, 3, 4]`, `amount = 6` gives 2 (3 + 3). Greedy would pick 4 + 1 + 1.

### How to recognise it

- "Fewest items to reach a target", with unlimited reuse.
- Greedy looks tempting but is wrong for arbitrary denominations.

### Brute force

Try every coin as the **last** coin, then solve the smaller amount.

```java fragment
int fewest(int[] coins, int a) {                     // fewest coins summing to a, or INF
    if (a == 0) return 0;
    int best = INF;                                  // INF = amount + 1: "impossible"
    for (int c : coins)
        if (c <= a) best = Math.min(best, fewest(coins, a - c) + 1);
    return best;
}
// brute force: branches into every coin at every level, up to O(coins^amount).
// Memo: amount + 1 states, each tries every coin: O(amount × coins).
```

The same amount is reached by many coin orders (1+3 and 3+1), so the cache pays off hugely.

### Intuition

You do not know the best first coin. But do you know the best way to make every **smaller** amount? The last coin leaves exactly one smaller amount, and that amount should itself use the fewest coins.

**The five answers.**

- **State:** `dp[a]` = the fewest coins that sum to exactly `a`.
- **Recurrence:** `dp[a] = 1 + min over coins c ≤ a of dp[a − c]`.
- **Base cases:** `dp[0] = 0`. Every other cell starts as **"unreachable"**.
- **Order:** `a` from 1 to `amount`; every `a − c` is smaller.
- **Answer and space:** `dp[amount]`, or **−1** if it is still unreachable. The recurrence can look back as far as the largest coin, so keep the whole row.

**The sentinel for "unreachable" needs care.** Use `amount + 1`: no real answer can need more than `amount` coins (the smallest coin is at least 1), so `amount + 1` behaves like infinity, and adding 1 to it cannot overflow. Using `Integer.MAX_VALUE` looks natural and is a trap; see the mistakes below.

<Figure caption="Coins [1, 3, 4], amount 6. dp[6] = 1 + min(dp[5], dp[3], dp[2]) = 1 + min(2, 1, 2) = 2: the last coin is a 3, after the best way to make 3 (one 3). Greedy’s 4 + 1 + 1 uses three.">
  <ArrayStrip name="dp" values={[0, 1, 2, 1, 1, 2, 2]} pointers={[{ at: 2, label: '6 − 4', tone: 'blue' }, { at: 3, label: '6 − 3', tone: 'green' }, { at: 5, label: '6 − 1', tone: 'blue' }, { at: 6, label: 'amount' }]} tones={{ 0: 'done', 3: 'done', 6: 'hot' }} />
</Figure>

### Dry run

Each frame tries every coin as the last one and keeps the cheapest.

<DryRun title="Coin Change: coins 1, 3, 4; amount 6" frames={coinFrames([1, 3, 4], 6)} predict />

<DryRun title="Coin Change: an unreachable amount" frames={coinFrames([2], 5)} />

### Algorithm

1. Create `dp` of size `amount + 1`, fill with `amount + 1`, and set `dp[0] = 0`.
2. For `a` from 1 to `amount`, for each coin `c ≤ a`: if `dp[a − c] + 1 < dp[a]`, update `dp[a]`.
3. If `dp[amount]` is still `amount + 1`, return −1; otherwise return it.

### Java solution

<HintLadder hints={hints.coins}>

```java id=coinChange
public int coinChange(int[] coins, int amount) {
    int INF = amount + 1;                            // more coins than any real answer needs
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, INF);
    dp[0] = 0;                                       // zero coins make zero
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a && dp[a - c] + 1 < dp[a])     // c is the LAST coin; dp[a - c] is final
                dp[a] = dp[a - c] + 1;
    return dp[amount] == INF ? -1 : dp[amount];
}
```

**O(amount × coins) time, O(amount) space.** With LeetCode's `amount ≤ 10⁴`, `INF + 1` is tiny. If a cell `a − c` is unreachable, `dp[a − c] + 1 = INF + 1` never wins the comparison, so unreachable amounts stay at `INF`.

</HintLadder>

<Trace title="Which coin went last?" steps={coins} takeaway="Remember: dp[a] = 1 + min dp[a − c] over coins c ≤ a, with unreachable cells as amount + 1. Unreachable at the end means −1." />

### Why it works

Any best collection for `a` has some last coin `c`; the rest is a collection for `a − c`, and it must be a best one, or swapping it in would beat the best. Trying every `c` covers every possible last coin.

**What stays true:** before computing `dp[a]`, every `dp[0..a − 1]` holds the true minimum, or the sentinel `amount + 1` if that amount cannot be made.

<Reveal q="Greedy works for real currencies. Why not here?">

Systems like 1, 2, 5, 10, 20, 50 are *canonical*: greedy happens to be optimal for them. Arbitrary coin sets are not. `[1, 3, 4]` with 6 is the smallest kind of counterexample: greedy takes the 4 and is left with two 1s. The table never commits to a coin; it compares every possible last coin against amounts it has already solved.

</Reveal>

<Reveal q="Does it matter whether the coin loop is outside or inside the amount loop?">

**Not for the minimum**: either order fills every `dp[a]` from final values of smaller amounts. **It matters a lot for counting.** If you count the *number of ways* to make an amount, coins-outside counts each combination once (1+2 and 2+1 are the same), while amounts-outside counts ordered sequences (1+2 and 2+1 differ). That is Coin Change II versus Combination Sum IV, and the <a href={`${BASE}dsa/lessons/dp-2d/`}>2-D DP lesson</a> builds it properly.

</Reveal>

### Complexity

- **Time O(amount × coins):** each of the `amount` cells tries every coin once.
- **Space O(amount):** the `dp` row.

### Edge cases and mistakes

- **`Integer.MAX_VALUE` as the sentinel**, combined with `Math.min(dp[a], dp[a - c] + 1)`:

```java fragment
Arrays.fill(dp, Integer.MAX_VALUE);          // BUG: MAX_VALUE + 1 wraps to MIN_VALUE
for (int a = 1; a <= amount; a++)
    for (int c : coins) if (c <= a) dp[a] = Math.min(dp[a], dp[a - c] + 1);
// coins [2], amount 3: dp[1] stays MAX_VALUE, so dp[3] = MAX_VALUE + 1 = -2147483648
```

The overflowed value is the smallest `int` there is, so it *wins* every `min` and the method returns −2147483648 instead of −1.

- `amount = 0` returns 0 (no coins needed).

<h2 id="word-break">Chapter 7 · Word Break</h2>

### Problem

Can the string `s` be cut into dictionary words, each usable any number of times?

`s = "leetcode"`, dictionary `["leet", "code"]` gives `true`.

### How to recognise it

- A yes/no question about splitting a string into allowed pieces.
- Greedy cuts (longest word first) fail, because an early word can strand the rest.

### Brute force

Try every position where the last word could start.

```java fragment
boolean can(String s, int i, Set<String> words) {    // can the first i characters be split?
    if (i == 0) return true;                         // the empty prefix needs no words
    for (int j = 0; j < i; j++)                      // the last word is s[j..i)
        if (can(s, j, words) && words.contains(s.substring(j, i))) return true;
    return false;
}
// brute force: each prefix re-asks every shorter prefix, exponential in the worst case
// (try "aaaaaaaaab" with words "a", "aa", "aaa"). Memo: n + 1 states × n starts, O(n^3) with substring cost.
```

### Intuition

Do not guess the first word. For every point in the string, ask: **could everything before it be read?** Then ask where the last word began.

**The five answers.**

- **State:** `dp[i]` = **true** if the first `i` characters can be split into dictionary words.
- **Recurrence:** if the last word is `s[j..i)`, the rest is the first `j` characters: `dp[i] = OR over j of (dp[j] AND s[j..i) is a word)`.
- **Base cases:** `dp[0] = true`: the empty prefix needs no words.
- **Order:** `i` from 1 to `n`; every `j` is smaller.
- **Answer and space:** `dp[n]`. `j` can reach back only as far as the longest word, but the simple version keeps the whole row.

Put the words in a `HashSet` for O(1)-expected lookups, and limit `j` to the last `maxLen` positions: a last word cannot be longer than the longest word in the dictionary.

### Algorithm

1. Put the words in a set and find `maxLen`.
2. Create `dp` of `n + 1` booleans with `dp[0] = true`.
3. For `i` from 1 to `n`, try `j` from `i − 1` down to `max(0, i − maxLen)`: if `dp[j]` is true and `s[j..i)` is in the set, set `dp[i] = true` and stop.
4. Return `dp[n]`.

### Java solution

<HintLadder hints={hints.words}>

```java id=wordBreak
public boolean wordBreak(String s, List<String> wordDict) {
    Set<String> words = new HashSet<>(wordDict);
    int maxLen = 0;
    for (String w : wordDict) maxLen = Math.max(maxLen, w.length());
    int n = s.length();
    boolean[] dp = new boolean[n + 1];               // dp[i]: the first i characters split cleanly
    dp[0] = true;                                    // the empty prefix needs no words
    for (int i = 1; i <= n; i++)
        for (int j = i - 1; j >= Math.max(0, i - maxLen) && !dp[i]; j--)
            dp[i] = dp[j] && words.contains(s.substring(j, i));   // last word is s[j..i)
    return dp[n];
}
```

**O(n × L²) time** with `L` the longest word: up to `L` start positions per `i`, each making an O(L) substring and hash. Without the `maxLen` limit it is O(n³). **O(n + total dictionary size) space.**

</HintLadder>

### Why it works

A split of the first `i` characters ends with some word `s[j..i)`, and what precedes it is a split of the first `j` characters. Trying every `j` covers every possible last word. OR is forgiving: if two splits both work, true is still just true.

**What stays true:** before computing `dp[i]`, `dp[0..i − 1]` say exactly which prefixes are splittable.

<Reveal q="Greedy longest fails on praysong. Does greedy SHORTEST work?">

No. With words `a`, `abc` and `b`, the string `abc` is one word. Shortest-first takes `a`, then `b`, then is stuck on `c`. **Any greedy cut commits too early.** The table keeps every reachable cut point alive at once, so a bad early word cannot hide a good one.

</Reveal>

<Reveal q="What if the question asked for every possible sentence, not just yes or no?">

That is Word Break II, and the output itself can be exponential: a string of 20 `a`s with words `a` and `aa` has 10,946 sentences. A table cannot print them faster than they exist. Use backtracking, pruned by this chapter's `dp` (never start a word at a position from which the rest cannot be finished).

</Reveal>

### Complexity

- **Time O(n × L²):** `n` prefixes, at most `L` starts each, an O(L) substring and hash per start.
- **Space O(n + dictionary size):** the `dp` array and the set.

### Edge cases and mistakes

- **Greedy longest-match**, which feels like reading. On `"praysong"` it takes *prays* and strands *ong*, returning false.
- Forgetting `dp[0] = true`: nothing could ever become true.

<h2 id="lis">Chapter 8 · Longest Increasing Subsequence</h2>

### Problem

A subsequence keeps the original order but may skip elements. Find the length of the longest **strictly** increasing one.

`[10, 9, 2, 5, 3, 7, 101, 18]` gives 4 (for example 2, 3, 7, 18).

### How to recognise it

- "Longest ... subsequence" with an ordering rule between chosen elements (not contiguous).
- The next choice depends on the **last value chosen**, which a plain prefix state would not remember.

### Brute force

Try every subset of positions and check it is increasing: **O(2ⁿ · n)**. A smarter recursion asks, for each index `i`, "what is the longest run that **ends at** `i`?"

```java fragment
int endingAt(int[] nums, int i) {                    // longest increasing run ENDING at index i
    int best = 1;                                    // nums[i] on its own
    for (int j = 0; j < i; j++)
        if (nums[j] < nums[i]) best = Math.max(best, endingAt(nums, j) + 1);
    return best;
}
// answer = max over i of endingAt(nums, i).
// Without a cache an increasing array re-asks every smaller j: exponential.
// With int[] memo: n states, each scans up to n earlier j: O(n^2).
```

### Intuition

You start to write `dp[i]` = the longest run among the first `i` elements. Then you stop: to decide whether element `i` can extend a run, you need to know the value the run **ended on**, and that definition does not say. So change the state: make the **last element part of the state**.

**The five answers (the O(n²) table).**

- **State:** `dp[i]` = the length of the longest increasing subsequence **that ends at index `i`**.
- **Recurrence:** what came just before `nums[i]`? Either nothing (`dp[i] = 1`), or some earlier `j` with `nums[j] < nums[i]`, extending the best run that ends there: `dp[i] = 1 + max dp[j]` over those `j`.
- **Base cases:** every `dp[i]` starts at 1: the element alone.
- **Order:** `i` left to right; every `j` is smaller.
- **Answer and space:** **the maximum over all `dp[i]`**, not `dp[n − 1]`. The longest run can end anywhere. Each cell reads every earlier cell, so keep the whole row: O(n).

<Figure caption="[10, 9, 2, 5, 3, 7, 101, 18]. dp[5] = 3: the 7 extends a length-2 run ending at 5 or at 3. The best is 4, reached at both 101 and 18, for example 2, 3, 7, 18.">

### The O(n log n) tails array

The table does O(n) work per element. A different state does it in O(log n). Keep one shelf per run length: **`tails[k]` = the smallest value that ends any increasing subsequence of length `k + 1` seen so far.** A small ending is valuable: it is easier to extend later.

For each new value `x`, find the **first** `k` with `tails[k] ≥ x`:

- if there is none, `x` extends the longest run: append it;
- otherwise `x` can extend the length-`k` run that ends at `tails[k − 1] < x`, so it ends a run of length `k + 1` with a tail no bigger than the old one: overwrite `tails[k]` with `x`.

The answer is the number of shelves used.

**Why the shelves stay sorted:** any run of length `k + 2` that ends in `t` contains a run of length `k + 1` that ends below `t` (drop its last element). So the smallest length-`(k + 2)` ending is bigger than the smallest length-`(k + 1)` ending: `tails` is **strictly increasing**, always, which is what lets you binary search it.

**And the warning that trips everyone: `tails` is not the subsequence.** On `[3, 4, 1]` the shelves end as `[1, 4]`, but 1 comes after 4 in the input, so `[1, 4]` is no subsequence at all. Only its **length** is the answer. (Recovering an actual LIS needs a parent pointer per element.)

### Algorithm

**Table.**

1. Set every `dp[i] = 1`.
2. For each `i`, for each `j < i` with `nums[j] < nums[i]`, set `dp[i] = max(dp[i], dp[j] + 1)`.
3. Return the maximum of all `dp[i]`.

**Tails.**

1. Keep an empty `tails` array and a `size`.
2. For each `x`, binary search the first position `lo` in `tails[0..size)` with `tails[lo] ≥ x`.
3. Set `tails[lo] = x`. If `lo == size`, increment `size`.
4. Return `size`.

### Java solution

<HintLadder hints={hints.lis}>

```java id=lisQuadratic
public int lengthOfLIS(int[] nums) {
    int n = nums.length, best = 0;
    int[] dp = new int[n];                           // dp[i] = longest increasing run ENDING at i
    for (int i = 0; i < n; i++) {
        dp[i] = 1;                                   // nums[i] on its own
        for (int j = 0; j < i; j++)
            if (nums[j] < nums[i]) dp[i] = Math.max(dp[i], dp[j] + 1);   // extend a run ending at j
        best = Math.max(best, dp[i]);                // the answer can end anywhere
    }
    return best;
}
```

**O(n²) time, O(n) space.** Fine for LeetCode's 2500 elements; the follow-up asks for better.

</HintLadder>

<HintLadder hints={hints.tails}>

```java id=lisTails
public int lengthOfLIS(int[] nums) {
    int[] tails = new int[nums.length];              // tails[k] = smallest tail of any length-(k+1) run
    int size = 0;
    for (int x : nums) {
        int lo = 0, hi = size;                       // find the first k with tails[k] >= x
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (tails[mid] < x) lo = mid + 1; else hi = mid;
        }
        tails[lo] = x;                               // replace a bigger tail, or open a new shelf
        if (lo == size) size++;
    }
    return size;                                     // tails[0..size) is NOT itself a subsequence
}
```

**O(n log n) time, O(n) space.** The binary search is the "first position where the condition flips" search from the <a href={`${BASE}dsa/lessons/binary-search/`}>Binary Search</a> lesson.

</HintLadder>

<Trace title="Shelve the values" steps={lis} takeaway="Remember: dp[i] ends AT i and the answer is the max; tails[k] is the smallest ending of a length-(k + 1) run, stays strictly increasing, and is not itself the subsequence." />

### Why it works

**Table:** every increasing subsequence ending at `i` is either `nums[i]` alone or a run ending at some `j < i` with a smaller value, plus `nums[i]`; the best such run is `dp[j]`, settled.

**Tails:** after reading a prefix, `tails[k]` is the smallest ending of any length-`(k + 1)` run inside that prefix, `tails` is strictly increasing, and its size is the LIS of the prefix.

<Reveal q="Non-decreasing instead of strictly increasing (7, 7, 7 counts as length 3). What changes?">

In the table: `nums[j] ≤ nums[i]`. On the shelves: search for the first tail **strictly greater** than `x` (an upper bound) instead of the first tail `≥ x`. Then an equal value opens a new shelf rather than overwriting. On `[7, 7, 7, 7]` the strict version answers 1 and the non-decreasing version answers 4.

</Reveal>

### Complexity

- **Table: time O(n²), space O(n).** Each of `n` cells scans up to `n` earlier cells.
- **Tails: time O(n log n), space O(n).** One binary search per element on an array of at most `n` shelves.

### Edge cases and mistakes

- **Returning `dp[n − 1]`.** That assumes the longest run ends at the last element. On `[1, 3, 2, 0]`, `dp = [1, 2, 2, 1]`: it returns 1 instead of 2. Step 5 of the five answers exists for exactly this.
- **Reading `tails` as the answer sequence.** Only its length is meaningful.
- Equal values: strictly increasing means `[2, 2, 2]` has LIS 1.

<h2 id="longest-palindrome">Chapter 9 · Longest Palindromic Substring</h2>

### Problem

Return the longest substring that reads the same forwards and backwards.

`"babad"` gives `"bab"` (or `"aba"`). `"cbbd"` gives `"bb"`.

### How to recognise it

- "Longest palindromic ..." or "all palindromes" in a string, contiguous.
- A palindrome is a smaller palindrome with one matching pair around it, so it can be grown outward.

### Brute force

Check every substring: `n²` substrings, each checked in O(n): **O(n³)**. The check itself is a recurrence:

```java fragment
boolean isPal(String s, int l, int r) {              // is s[l..r] a palindrome?
    if (l >= r) return true;                         // empty or a single letter
    return s.charAt(l) == s.charAt(r) && isPal(s, l + 1, r - 1);
}
```

Memoising `isPal(l, r)` gives `n²` states, a 2-D table (see the <a href={`${BASE}dsa/lessons/dp-2d/`}>2-D DP lesson</a>).

### Intuition

**`s[i..j]` is a palindrome exactly when `s[i] == s[j]` and `s[i + 1..j − 1]` is one.** Instead of storing every window, walk that recurrence **outward from one centre**: start at the middle, and widen while the ends match. Each centre is a one-dimensional chain, and only the previous window matters, so there is nothing to store.

A palindrome's centre is **either a letter** (odd length, like `aba`) **or the gap between two letters** (even length, like `abba`). A string of length `n` has `n` letter-centres and `n − 1` gap-centres: **2n − 1 centres**. Forget the gaps and you miss every even palindrome.

**The five answers.**

- **State:** the window `s[l..r]` around a fixed centre: is it a palindrome?
- **Recurrence:** `pal(l, r) = s[l] == s[r] && pal(l + 1, r − 1)`, read from the inside out: if the inner window is a palindrome and the new ends match, the outer one is too.
- **Base cases:** the empty window (gap centre) and a single letter (letter centre).
- **Order:** from the centre outward: `l` goes down, `r` goes up.
- **Answer and space:** the longest window found over all `2n − 1` centres. O(1) extra space, because each chain keeps only its current window.

<Figure caption="“babad”. From the letter-centre at index 1, the centre widens once (b = b) to “bab”, then stops (index −1 does not exist). The centre at index 2 gives “aba”, equally long; either is a correct answer. Every gap-centre fails at once: no two neighbours match.">
  <ArrayStrip name="s" values={['b', 'a', 'b', 'a', 'd']} pointers={[{ at: 1, label: 'centre', tone: 'purple' }]} tones={{ 0: 'blue', 1: 'purple', 2: 'blue' }} regions={[{ from: 0, to: 2, label: 'bab', tone: 'gold' }]} />
</Figure>

### Dry run

### Algorithm

1. For every index `c`, widen from `(c, c)` for odd lengths and from `(c, c + 1)` for even lengths.
2. Widen while `l ≥ 0`, `r < n` and `s[l] == s[r]`.
3. When the loop stops, the last matching window is `s[l + 1..r − 1]`. Keep it if it is longer than the best.
4. Return the best window.

### Java solution

<HintLadder hints={hints.longestPal}>

```java id=longestPalindrome
public String longestPalindrome(String s) {
    int bestL = 0, bestR = 0;                        // best window s[bestL..bestR], inclusive
    for (int c = 0; c < s.length(); c++) {
        int[] odd = expand(s, c, c);                 // centre on a letter: "aba"
        int[] even = expand(s, c, c + 1);            // centre in the gap after it: "abba"
        if (odd[1] - odd[0] > bestR - bestL) { bestL = odd[0]; bestR = odd[1]; }
        if (even[1] - even[0] > bestR - bestL) { bestL = even[0]; bestR = even[1]; }
    }
    return s.substring(bestL, bestR + 1);
}

private int[] expand(String s, int l, int r) {
    while (l >= 0 && r < s.length() && s.charAt(l) == s.charAt(r)) { l--; r++; }
    return new int[]{l + 1, r - 1};                  // the last window that still matched
}
```

**O(n²) time, O(1) extra space.** LeetCode guarantees at least one character. (Manacher's algorithm does it in O(n); see Beyond this page.)

</HintLadder>

<Trace title="Grow the palindrome" steps={palindromes} takeaway="Remember: 2n − 1 centres: every letter and every gap. Widen while both ends match; the last matching window is the palindrome." />

### Why it works

Every palindrome has exactly one centre, and widening from that centre finds it (and every shorter palindrome around the same centre) before the first mismatch stops the loop. Trying every centre therefore sees every palindrome's maximal extent.

**What stays true:** while widening, `s[l + 1..r − 1]` is a palindrome; the loop stops at the first pair that does not match or falls off the string.

**The table alternative** `pal[i][j] = s[i] == s[j] && (j − i < 2 || pal[i + 1][j − 1])` is a genuine DP over **two indexes**: O(n²) space as well as time (see Chapter 10). In the interview, lead with centres.

### Complexity

- **Time O(n²):** `2n − 1` centres, each widening at most `n / 2` steps (a string of one repeated letter is the worst case).
- **Space O(1):** two indexes and the best window.

### Edge cases and mistakes

- **Expanding only from letters.** On `"cbbd"` the only palindromes are single letters and `bb`, whose centre is the gap between the two b's; the letter-only version returns `"c"` instead of `"bb"`.
- `"aaaa"` is the slowest case and returns the whole string.

<h2 id="palindromic-substrings">Chapter 10 · Palindromic Substrings</h2>

### Problem

Count how many substrings of `s` are palindromes. Substrings at different positions count separately.

`"aaa"` gives 6: `a`, `a`, `a`, `aa`, `aa`, `aaa`.

### How to recognise it

- Chapter 9's structure, but the question is "how many". You must argue each palindrome is counted exactly once.

### Brute force

Check every substring with `isPal`: **O(n³)**. Memoising `isPal(l, r)` gives the O(n²) table, the same state as Chapter 9's alternative.

### Intuition

Same 2n − 1 centres. **Every successful widening is one more palindrome**: the window at that moment is a different substring. So count widenings instead of remembering the widest.

**The five answers.**

- **State:** the window `s[l..r]` around a centre, as in Chapter 9.
- **Recurrence:** the window is a palindrome if `s[l] == s[r]` and the inner window is. Each time it succeeds, add 1 to the total.
- **Base cases:** empty and single-letter windows (the first widening from a letter centre always succeeds).
- **Order:** outward from each centre. For the table version, `i` runs **downward** from `n − 1` to 0, because `pal[i][j]` reads `pal[i + 1][j − 1]`, a row below.
- **Answer and space:** the total count. O(1) space with centres, O(n²) with the table.

### Algorithm

1. For every `c`, count widenings from `(c, c)` and from `(c, c + 1)`.
2. A widening succeeds when both indexes are in range and `s[l] == s[r]`; then add 1 and step outward.
3. Return the total.

### Java solution

<HintLadder hints={hints.countPal}>

```java id=countSubstrings
public int countSubstrings(String s) {
    int count = 0;
    for (int c = 0; c < s.length(); c++) {
        count += expandCount(s, c, c);               // odd lengths, centred on letter c
        count += expandCount(s, c, c + 1);           // even lengths, centred after letter c
    }
    return count;
}

private int expandCount(String s, int l, int r) {
    int found = 0;
    while (l >= 0 && r < s.length() && s.charAt(l) == s.charAt(r)) { found++; l--; r++; }
    return found;                                    // every successful widening is one palindrome
}
```

The 2-D table, for comparison (O(n²) time **and** space):

```java id=countSubstringsTable
public int countSubstrings(String s) {
    int n = s.length(), count = 0;
    boolean[][] pal = new boolean[n][n];             // pal[i][j]: is s[i..j] a palindrome?
    for (int i = n - 1; i >= 0; i--)                 // i DOWNWARD: row i + 1 is ready first
        for (int j = i; j < n; j++) {
            pal[i][j] = s.charAt(i) == s.charAt(j) && (j - i < 2 || pal[i + 1][j - 1]);
            if (pal[i][j]) count++;
        }
    return count;
}
```

**Centres: O(n²) time, O(1) space. Table: O(n²) time, O(n²) space.** The answer is at most n(n + 1)/2 ≈ 500,000 for LeetCode's 1000 letters: an `int` is plenty.

</HintLadder>

### Why it works

Each palindromic substring has exactly one centre, and is found exactly once, at the widening step that reaches its ends. So the count is exact, with no double counting, which, for a counting problem, is the thing you must argue.

**The table version's evaluation order.** `pal[i][j]` reads `pal[i + 1][j − 1]`, a row **below** `i`, so rows are filled from `i = n − 1` down to 0. Fill upward and that cell is still `false` when read, so every palindrome longer than 2 is missed.

### Complexity

- **Centres: time O(n²), space O(1).** The count itself can be Θ(n²) (`"aaaa…"`), but it is a single integer.
- **Table: time O(n²), space O(n²).**

### Edge cases and mistakes

- **Filling the table with `i` going up.** On `"abba"` the cell for the whole word reads `pal[1][2]` (the inner `bb`) before it has been written, so it counts 5 instead of 6.
- Counting distinct texts instead of positions: `"aaa"` has three `a` palindromes, not one.

<h2 id="delete-and-earn">Variation 1 · Delete and Earn</h2>

### Problem

Pick any number `x` from the list and earn `x` points, but every copy of `x − 1` and `x + 1` is then destroyed. Repeat while numbers remain. Maximise the points.

`[3, 4, 2]` gives 6 (take 4, which destroys 3, then take 2). `[2, 2, 3, 3, 3, 4]` gives 9.

### How to recognise it

- A choice that removes its neighbours by **value**, and the input order does not matter.

### Brute force

Try every possible first pick, delete the neighbours, recurse on what remains.

```java fragment
int play(List<Integer> bag) {                        // try every possible first pick
    int best = 0;
    for (int x : new HashSet<>(bag)) {
        List<Integer> rest = new ArrayList<>(bag);
        rest.remove(Integer.valueOf(x));
        rest.removeIf(y -> y == x - 1 || y == x + 1);
        best = Math.max(best, x + play(rest));
    }
    return best;
}
// brute force: exponential in the list size. The reduction below collapses it to n states.
```

### Intuition

If you take one `x`, you may as well take **every** copy of `x`: its neighbours are already destroyed, and the other copies harm nothing. So collapse each value into one "house" worth `x × count(x)`, line the houses up by value, and the rule "taking `x` destroys `x − 1` and `x + 1`" becomes **"no two adjacent houses"**. That is Chapter 3, over values `0..max`.

**The five answers.**

- **State:** `best[v]` = the most points using only values up to `v`.
- **Recurrence:** `best[v] = max(best[v − 1], best[v − 2] + earn[v])` where `earn[v] = v × count(v)`: skip `v`, or take all of `v` and fall back two values.
- **Base cases:** nothing below value 0, so `best` of negative values is 0.
- **Order:** `v` from 0 up to `max`.
- **Answer and space:** `best[max]`. Two rolling variables for the recurrence, plus the bucket array `earn`.

<Figure caption="[2, 2, 3, 3, 3, 4] becomes houses by value: earn[2] = 4, earn[3] = 9, earn[4] = 4. House Robber on [0, 0, 4, 9, 4] picks the 9 (all three 3s) for 9; the alternative, 2s and 4s, gives 8.">
  <ArrayStrip name="earn[v]" values={[0, 0, 4, 9, 4]} tones={{ 3: 'hot', 2: 'out', 4: 'out' }} />
</Figure>

### Dry run

<DryRun title="Delete and Earn" frames={earnFrames([2, 2, 3, 3, 3, 4])} predict />

### Algorithm

1. Build `earn[v] = v × count(v)` for `v` in `0..max`.
2. Run House Robber on `earn` with `prev` and `curr`.
3. Return `curr`.

### Java solution

<HintLadder hints={hints.earn}>

```java id=deleteAndEarn
public int deleteAndEarn(int[] nums) {
    int max = 0;
    for (int x : nums) max = Math.max(max, x);
    int[] earn = new int[max + 1];                   // earn[v] = v × (copies of v): one "house" per value
    for (int x : nums) earn[x] += x;
    int prev = 0, curr = 0;                          // House Robber over values 0..max
    for (int v = 0; v <= max; v++) {
        int next = Math.max(curr, prev + earn[v]);   // take every v (so no v − 1), or skip v
        prev = curr;
        curr = next;
    }
    return curr;
}
```

**O(n + max) time, O(max) space.** Values are at most 10⁴, so the bucket array is small; with huge sparse values, sort the distinct values and treat a gap of more than 1 as "not adjacent".

</HintLadder>

<Reveal q="Why is it safe to take all copies of x at once?">

Taking one `x` destroys every `x − 1` and `x + 1`, and the remaining copies of `x` are not destroyed by anything except picking `x ± 1`, which no longer exist. So taking them all only adds points and changes no other option. Once that is clear, the order of moves does not matter, only the **set of values** taken, which must contain no two consecutive values.

</Reveal>

### Why it works

A set of taken values with no two consecutive is exactly a legal game, scoring the sum of `earn` over that set. House Robber maximises that sum.

### Complexity

- **Time O(n + max):** one pass to bucket, one pass over values.
- **Space O(max):** the `earn` array.

### Edge cases and mistakes

- Scoring `x` once per pick instead of taking all copies breaks the reduction.
- If values were up to `10⁹`, sort the distinct values instead of bucketing.

### Practice

What if taking `x` destroyed `x ± 2` instead? Odd and even values no longer interact at all: split the values into the two parity chains and run House Robber on each, stepping by 2.

<h2 id="perfect-squares">Variation 2 · Perfect Squares</h2>

### Problem

What is the fewest perfect squares (1, 4, 9, 16, …) that sum to `n`?

`n = 12` gives 3 (4 + 4 + 4). `n = 13` gives 2 (4 + 9).

### How to recognise it

- Coin Change, with every perfect square up to `n` as a coin.

### Brute force

Try every square as the last one, then solve the remainder:

```java fragment
int fewest(int a) {                                  // fewest squares summing to a
    if (a == 0) return 0;
    int best = a;                                    // a ones always works
    for (int r = 1; r * r <= a; r++) best = Math.min(best, fewest(a - r * r) + 1);
    return best;
}
// brute force: exponential, the same amounts re-asked in many orders. Memo: n states × √n squares.
```

### Intuition

Chapter 6 with the coin list generated on the fly. And because 1 is a square, **every amount is reachable**: instead of a sentinel, start each cell at `a` (all ones), a true upper bound.

**The five answers.**

- **State:** `dp[a]` = the fewest squares that sum to `a`.
- **Recurrence:** `dp[a] = 1 + min dp[a − r²]` over `r² ≤ a`.
- **Base cases:** `dp[0] = 0`.
- **Order:** `a` from 1 to `n`.
- **Answer and space:** `dp[n]`. Reads back up to `a − 1`, so the full row: O(n).

### Dry run

<DryRun title="Perfect Squares: n = 12" frames={squaresFrames(12)} predict />

### Algorithm

1. Set `dp[0] = 0`.
2. For `a` from 1 to `n`, start `dp[a] = a`, then for each `r` with `r² ≤ a` set `dp[a] = min(dp[a], dp[a − r²] + 1)`.
3. Return `dp[n]`.

### Java solution

<HintLadder hints={hints.squares}>

```java id=numSquares
public int numSquares(int n) {
    int[] dp = new int[n + 1];                       // dp[a] = fewest squares summing to a
    for (int a = 1; a <= n; a++) {
        dp[a] = a;                                   // worst case: 1 + 1 + ... + 1, always possible
        for (int r = 1; r * r <= a; r++)
            dp[a] = Math.min(dp[a], dp[a - r * r] + 1);   // r² is the last square
    }
    return dp[n];
}
```

**O(n √n) time, O(n) space.** (Lagrange's four-square theorem says the answer is never more than 4, which is a fact, not a method.)

</HintLadder>

<Reveal q="Greedy: take the biggest square that fits. Does it work for 12?">

Greedy takes 9 and is left with 3 = 1 + 1 + 1: **four** squares. The table finds 4 + 4 + 4: **three**. Same lesson as Coin Change: no coin system is safe for greedy unless it is proven so.

</Reveal>

### Why it works

Any best decomposition of `a` has a last square `r²`, and the rest is a best decomposition of `a − r²`. Every square that fits is tried.

### Complexity

- **Time O(n √n):** `n` cells, up to `√n` squares each.
- **Space O(n):** the `dp` row.

### Edge cases and mistakes

- `n` itself a perfect square gives 1.

### Practice

Count the **number of ways** to write `n` as a sum of squares, where order does not matter. Which loop goes outside? Squares outside, amounts inside: combinations, as in Coin Change II.

<h2 id="partition-preview">Variation 3 · Partition Equal Subset Sum</h2>

### Problem

Can the numbers be split into two groups with equal sums? Each number goes in exactly one group.

`[1, 5, 11, 5]` gives `true` (11 and 1 + 5 + 5). `[1, 2, 5]` gives `false`.

### How to recognise it

- Subset sum with each item used **at most once** (the 0/1 knapsack family).

### Brute force

Take or skip each number: 2ⁿ subsets.

```java fragment
boolean can(int[] a, int i, int left) {              // can numbers i.. make exactly `left`?
    if (left == 0) return true;
    if (i == a.length || left < 0) return false;
    return can(a, i + 1, left - a[i]) || can(a, i + 1, left);   // take a[i], or skip it
}
// brute force: O(2^n). Memo on (i, left): n × target states, a 2-D table.
```

### Intuition

The two groups have equal sums exactly when one of them sums to `total / 2` (so an odd total is an instant no). That is Chapter 6's amount table with booleans, `can[s]` = "some subset of the numbers seen so far sums to `s`", with one new rule: **each number may be used at most once.** The memo above has two parameters, numbers considered and sum left; the one-row table is that 2-D table compressed (the <a href={`${BASE}dsa/lessons/dp-2d/`}>2-D DP lesson</a> builds the full version).

The compression has one trap: **the inner loop must run backwards**, from `target` down to `x`. Reading `can[s − x]` must mean "reachable **without** this `x`". Going backwards, `can[s − x]` has not been touched yet this round, so it still holds last round's value. Going forwards, it may already have been set **by this same `x`**, which silently uses `x` twice.

**The five answers.**

- **State:** `can[s]` = true when some subset of the numbers seen so far sums to `s`.
- **Recurrence:** `can[s] = can[s] OR can[s − x]` for each new number `x`.
- **Base cases:** `can[0] = true`: the empty subset.
- **Order:** numbers in input order; for each number, `s` from `target` **down** to `x`.
- **Answer and space:** `can[target]`. One row of `target + 1` cells: O(total).

<Figure caption="[1, 2, 5], target 4. No subset sums to 4, so the answer is false. Forwards, the very first number already breaks it: with x = 1, can[1] becomes true, then can[2] reads the fresh can[1], can[3] reads can[2], can[4] reads can[3], so a single 1 is used four times.">
  <ArrayStrip name="forwards, x = 1" values={['T', 'T', 'T', 'T', 'T']} tones={{ 2: 'out', 3: 'out', 4: 'out' }} />
  <ArrayStrip name="backwards, x = 1" values={['T', 'T', 'F', 'F', 'F']} tones={{ 1: 'done' }} />
</Figure>

### Dry run

The correct, backward loop on a splittable input:

<DryRun title="Partition: backward loop" frames={partitionFrames([3, 1, 2, 2])} predict />

The same loop run forwards on `[1, 2, 5]` (the true answer is false). Watch for the frame where the cell being read was already written earlier in the same round.

### Algorithm

1. Sum the numbers. If the total is odd, return `false`.
2. Set `target = total / 2`, `can[0] = true`, everything else `false`.
3. For each number `x`, for `s` from `target` down to `x`: `can[s] = can[s] OR can[s − x]`.
4. Return `can[target]`.

### Java solution

<HintLadder hints={hints.partition}>

```java id=canPartition
public boolean canPartition(int[] nums) {
    int total = 0;
    for (int x : nums) total += x;
    if (total % 2 != 0) return false;                // an odd total can't split evenly
    int target = total / 2;
    boolean[] can = new boolean[target + 1];         // can[s]: some subset of the numbers so far sums to s
    can[0] = true;                                   // the empty subset
    for (int x : nums)
        for (int s = target; s >= x; s--)            // BACKWARDS: can[s - x] is still last round's value
            can[s] = can[s] || can[s - x];
    return can[target];
}
```

**O(n × total) time, O(total) space.** This is *pseudo-polynomial*: fast because LeetCode keeps the total at most 200 × 100 = 20,000.

</HintLadder>

### Why it works

Going backwards, `can[s − x]` still holds the answer for the earlier numbers alone, so `can[s] OR can[s − x]` means "reachable without `x`, or by adding this one `x`".

### Complexity

- **Time O(n × total):** each of `n` numbers sweeps up to `target` cells.
- **Space O(total):** one boolean row.

### Edge cases and mistakes

- **Looping forwards** reads cells already updated by the same number; it turns `[1, 2, 5]` into `true`.
- An odd total is an immediate `false`.

### Practice

Flip the loop to run forwards. Which problem have you just solved instead? Unlimited copies of each number: Coin Change's unbounded choice, as a yes/no question.

<h2 id="count-lis">Variation 4 · Number of Longest Increasing Subsequences</h2>

### Problem

Not the length of the longest increasing subsequence: the **number** of different longest ones (different sets of positions).

`[1, 3, 5, 4, 7]` gives 2 (1-3-5-7 and 1-3-4-7). `[2, 2, 2, 2, 2]` gives 5.

### How to recognise it

- Chapter 8, but counting the longest runs: keep a **count** next to the length.

### Brute force

Enumerate every subset, keep the increasing ones, track the longest and how many reach it: **O(2ⁿ · n)**. Chapter 8's `endingAt(i)` recursion is the better start; here it simply returns two numbers (length, count) instead of one, and memoising it gives O(n²).

### Intuition

Keep Chapter 8's `len[i]` (longest run ending at `i`) and add `cnt[i]` = how many runs ending at `i` reach that length. When an earlier `j` (with `nums[j] < nums[i]`) gives a **longer** run, it replaces: `cnt[i] = cnt[j]`. When it gives an **equal** run, it adds: `cnt[i] += cnt[j]`. At the end, sum `cnt[i]` over every `i` whose `len[i]` is the overall maximum.

**The five answers.**

- **State:** `len[i]` = the longest increasing run ending at `i`; `cnt[i]` = the number of runs of that length ending at `i`.
- **Recurrence:** for each `j < i` with `nums[j] < nums[i]`: if `len[j] + 1 > len[i]` then `len[i] = len[j] + 1` and `cnt[i] = cnt[j]`; if equal, `cnt[i] += cnt[j]`.
- **Base cases:** `len[i] = cnt[i] = 1`.
- **Order:** `i` left to right.
- **Answer and space:** the sum of `cnt[i]` where `len[i]` equals the maximum. Two arrays of `n`: O(n).

<Reveal q="[1, 3, 5, 4, 7]: what are len, cnt and the answer?">

`len = [1, 2, 3, 3, 4]` and `cnt = [1, 1, 1, 1, 2]`. The 7 can extend a length-3 run ending at 5 **or** at 4: two ways of equal length, so `cnt = 1 + 1 = 2`. The answer is **2**: 1-3-5-7 and 1-3-4-7. The tails array of Chapter 8 cannot do this: it keeps one tail per length and throws away how many runs reached it.

</Reveal>

### Dry run

<DryRun title="Number of LIS: [1, 3, 5, 4, 7]" frames={countLisFrames([1, 3, 5, 4, 7])} predict />

### Algorithm

1. Set `len[i] = cnt[i] = 1` for each `i`.
2. For each `j < i` with `nums[j] < nums[i]`: longer run replaces, equal run adds.
3. Track the best length overall and the total count of runs reaching it.

### Java solution

<HintLadder hints={hints.countLis}>

```java id=findNumberOfLIS
public int findNumberOfLIS(int[] nums) {
    int n = nums.length, bestLen = 0, total = 0;
    int[] len = new int[n], cnt = new int[n];        // longest run ending at i, and how many reach it
    for (int i = 0; i < n; i++) {
        len[i] = 1; cnt[i] = 1;
        for (int j = 0; j < i; j++) {
            if (nums[j] >= nums[i]) continue;
            if (len[j] + 1 > len[i]) { len[i] = len[j] + 1; cnt[i] = cnt[j]; }   // longer: replace
            else if (len[j] + 1 == len[i]) cnt[i] += cnt[j];                    // tie: add
        }
        if (len[i] > bestLen) { bestLen = len[i]; total = cnt[i]; }
        else if (len[i] == bestLen) total += cnt[i];
    }
    return total;
}
```

**O(n²) time, O(n) space.** LeetCode promises the answer fits in a 32-bit integer.

</HintLadder>

### Why it works

Every longest run ending at `i` has a previous element `j` and a run of length `len[i] − 1` ending there. Different `j` give different runs (disjoint), and `cnt[j]` counts them.

### Complexity

- **Time O(n²):** the double loop.
- **Space O(n):** `len` and `cnt`.

### Edge cases and mistakes

- Treating a **shorter** run like a tie: only `len[j] + 1 == len[i]` adds.
- Reading `cnt` at the last index only: sum over every `i` that reaches the best length.
- On `[2, 2, 2, 2, 2]` every element is its own longest run, so the answer is 5.

### Practice

Predict `[1, 2, 4, 3, 5, 4, 7, 2]` (answer 3) before running it.

<h2 id="k-steps">Variation 5 · Up to k steps at a time</h2>

### Problem

Climbing Stairs with longer legs: moves of 1, 2, …, up to `k` steps are allowed. Count the ways to reach step `n`. (For `k = 3` with Tribonacci's own base cases, this is LeetCode's N-th Tribonacci Number.)

`n = 3, k = 3` gives 4: 1+1+1, 1+2, 2+1, 3.

### How to recognise it

- Each cell reads `k` cells instead of 2; a sliding range turns O(n × k) into O(n).

### Brute force

```java fragment
long ways(int i, int k) {                            // ways to stand on step i with moves 1..k
    if (i == 0) return 1;
    long total = 0;
    for (int m = 1; m <= k && m <= i; m++) total += ways(i - m, k);
    return total;
}
// brute force: O(k^n)-ish. Memo: n + 1 states × k terms, O(n × k).
```

### Intuition

The last move is now one of `k` sizes, so `ways[i] = ways[i − 1] + … + ways[i − k]` (skipping negative indexes), with `ways[0] = 1`. Summing `k` cells per step is O(n × k). But the sum is a **window** sliding up the table: add the newest cell, drop the one that fell out of reach, O(n) total.

**The five answers.**

- **State:** `ways[i]` = the number of ways to reach step `i`.
- **Recurrence:** `ways[i] = ways[i − 1] + … + ways[i − k]`, computed as `window += ways[i − 1]` then `window −= ways[i − k − 1]` when that index exists.
- **Base cases:** `ways[0] = 1`.
- **Order:** `i` from 1 to `n`.
- **Answer and space:** `ways[n]`. The window needs the cell `k + 1` below, so keep the last `k + 1` cells; as written, the full row.

<Reveal q="Tribonacci is T(0) = 0, T(1) = T(2) = 1, then the sum of the last three. The k = 3 stairs are 1, 1, 2, 4, 7, 13… Same recurrence, same sequence?">

Same recurrence, **different base cases**, so a shifted sequence: `ways(n) = T(n + 1)`. Tribonacci runs 0, 1, 1, 2, 4, 7, 13, so `ways(0) = T(1) = 1` and `ways(3) = T(4) = 4`. The recurrence says how cells relate; **the base cases decide which sequence you get.** Copying a recurrence without its base cases is how two correct-looking solutions disagree.

</Reveal>

### Dry run

Blue cells are the current window; the "newest" cell is the one just added.

<DryRun title="Up to k steps: n = 7, k = 3" frames={kStepsFrames(7, 3)} predict />

### Algorithm

1. Set `ways[0] = 1` and `window = 0`.
2. For `i` from 1 to `n`: add `ways[i − 1]` to `window`.
3. If `i − k − 1 ≥ 0`, subtract `ways[i − k − 1]`.
4. Set `ways[i] = window`. Return `ways[n]`.

### Java solution

<HintLadder hints={hints.kSteps}>

```java id=climbK
public long climbK(int n, int k) {                   // ways to reach step n with moves of 1..k
    long[] ways = new long[n + 1];
    ways[0] = 1;                                     // the empty climb
    long window = 0;                                 // ways[i-1] + ... + ways[i-k]
    for (int i = 1; i <= n; i++) {
        window += ways[i - 1];                       // the newest cell comes into reach
        if (i - k - 1 >= 0) window -= ways[i - k - 1];   // the one k + 1 below falls out of reach
        ways[i] = window;
    }
    return ways[n];
}
```

```java id=tribonacci
public int tribonacci(int n) {
    if (n == 0) return 0;
    int a = 0, b = 1, c = 1;                         // T(i-3), T(i-2), T(i-1) for i = 3
    for (int i = 3; i <= n; i++) {
        int next = a + b + c;
        a = b; b = c; c = next;
    }
    return c;                                        // n = 1 or 2 never enter the loop: T = 1
}
```

**O(n) time each; O(n) space for `climbK`, O(1) for Tribonacci.** `T(37) = 2,082,876,103` is the largest LeetCode asks for, and it fits in an `int`.

</HintLadder>

### Why it works

`window` always equals `ways[i − 1] + … + ways[i − k]`: moving up one step adds one cell and loses one.

### Complexity

- **Time O(n):** one add and one subtract per step.
- **Space O(n)** with the table, O(k) with a circular buffer, O(1) for fixed `k = 3`.

### Edge cases and mistakes

- Subtracting the wrong index: the cell that leaves is `ways[i − k − 1]`, not `ways[i − k]`.
- The counts overflow `int` quickly, which is why `climbK` uses `long`.

### Practice

Some steps are cracked and cannot be stood on. What changes? Their cells are written as 0, and they still have to leave the window correctly.

<h2 id="tickets">Variation 6 · Minimum Cost for Tickets</h2>

### Problem

You travel on certain days of the year (sorted, between 1 and 365). Passes cost `costs[0]` for 1 day, `costs[1]` for 7 consecutive days, `costs[2]` for 30. What is the cheapest way to cover every travel day?

`days = [1, 4, 6, 7, 8, 20]`, `costs = [2, 7, 15]` gives 11.

### How to recognise it

- "Cheapest way to cover" with a few fixed-size options; the state can run over **calendar days**.

### Brute force

At each uncovered visit, try each of the three passes, then jump to the first visit it does not cover.

```java fragment
int cost(int[] days, int[] costs, int idx) {         // cheapest cover for visits idx.. onward
    if (idx == days.length) return 0;
    int best = Integer.MAX_VALUE, span[] = {1, 7, 30};
    for (int p = 0; p < 3; p++) {
        int j = idx;
        while (j < days.length && days[j] < days[idx] + span[p]) j++;   // first visit not covered
        best = Math.min(best, costs[p] + cost(days, costs, j));
    }
    return best;
}
// brute force: 3 choices per pass, exponential in the number of passes. Memo on idx: at most 365 states.
```

### Intuition

Let the state run over **calendar days**: `dp[d]` = the cheapest cover for every visit on days `1..d`. On a day with no visit, nothing new is needed: `dp[d] = dp[d − 1]`. On a visit day, look at the **last pass bought**, the one covering day `d`. A 1-day pass covers `d` alone: `dp[d − 1] + costs[0]`. A 7-day pass ending on `d` covers `d − 6..d`: `dp[d − 7] + costs[1]`. A 30-day pass: `dp[d − 30] + costs[2]`. Clamp negative days to 0.

**The five answers.**

- **State:** `dp[d]` = the cheapest cover for every visit on days `1..d`.
- **Recurrence:** quiet day: `dp[d] = dp[d − 1]`. Visit day: the minimum of the three last-pass options above.
- **Base cases:** `dp[0] = 0`.
- **Order:** `d` from 1 to the last visit day.
- **Answer and space:** `dp[last]`. Reads back up to 30 days: keep the row (at most 366 cells).

<Reveal q="Isn’t it wrong to assume a 7-day pass ends exactly on day d? Travellers buy passes that start on a visit day.">

Shifting a pass later never helps and never hurts once it covers the same visits, so you may picture the last pass as **ending** on `d`. Every visit in `d − 6..d` is covered by it, and everything before `d − 6` must be covered by earlier passes, at cost `dp[d − 7]`. Any real purchase plan maps to one of the three cases, so the minimum over them is exact.

</Reveal>

### Dry run

<DryRun title="Minimum Cost for Tickets" frames={ticketsFrames([1, 4, 6, 7, 8, 20], [2, 7, 15])} predict />

### Algorithm

1. Mark the visit days. Create `dp` with `last + 1` cells, `dp[0] = 0`.
2. For each day `d` from 1 to `last`: if it is not a visit day, copy `dp[d − 1]`.
3. Otherwise take the minimum of `dp[d − 1] + costs[0]`, `dp[max(0, d − 7)] + costs[1]` and `dp[max(0, d − 30)] + costs[2]`.
4. Return `dp[last]`.

### Java solution

<HintLadder hints={hints.tickets}>

```java id=mincostTickets
public int mincostTickets(int[] days, int[] costs) {
    int last = days[days.length - 1];
    boolean[] visit = new boolean[last + 1];
    for (int d : days) visit[d] = true;
    int[] dp = new int[last + 1];                    // dp[d] = cheapest cover for every visit on days 1..d
    for (int d = 1; d <= last; d++) {
        if (!visit[d]) { dp[d] = dp[d - 1]; continue; }      // a quiet day costs nothing
        dp[d] = Math.min(dp[d - 1] + costs[0],               // last pass: 1 day, covering d
                Math.min(dp[Math.max(0, d - 7)] + costs[1],  // 7 days, covering d-6..d
                         dp[Math.max(0, d - 30)] + costs[2]));   // 30 days, covering d-29..d
    }
    return dp[last];
}
```

**O(last day) time and space**, at most 365. On `[1, 4, 6, 7, 8, 20]` with costs `[2, 7, 15]` the answer is 11: a 1-day pass for day 1, a 7-day pass for days 4..8 (bought on day 2, 3 or 4), and a 1-day pass for day 20.

</HintLadder>

### Why it works

On a visit day `d`, some pass covers `d`; assume it ends on `d`. What is left is the earlier cover `dp[d − span]`. Trying all three spans covers every plan.

### Complexity

- **Time O(last day):** three lookups per day.
- **Space O(last day):** the `dp` array.

### Edge cases and mistakes

- `d − 7` and `d − 30` must be clamped to 0.
- Not copying `dp[d − 1]` on quiet days, or returning `dp[days.length]` (the table is indexed by calendar day).

### Practice

The state here is the **day**, not the index of the visit. What would `dp[i]` over visits look like, and why does it need a pointer that skips forward past every visit a pass covers? (That is exactly the brute-force `j` loop above.)

<h2 id="choose-the-tool">When a table is overkill</h2>

A table is the right tool when **choices interact** and the same sub-questions repeat. It is the wrong tool when:

- **One choice is provably always safe.** Jump Game asks only "can I reach the end?" The farthest reachable index, carried forward, already contains everything a table would store, so greedy does it in O(n) where the table is O(n²). Greedy needs a proof; when you cannot find one, the table is the safe fallback.
- **You must list every solution.** Word Break II, all decodings, all subsets: the output is exponential, so use backtracking (pruned by a feasibility table if you like).
- **The sub-questions never repeat.** Merge sort, binary search, tree traversals: plain recursion or divide and conquer, no memo needed.
- **The state is too big.** If the honest state is "which items have I used" over 40 items, that is 2⁴⁰ cells. Look for structure (sorting, greedy, meet in the middle) before you write the table.

<Reveal q="Show me both Jump Game solutions, and why the greedy one is safe.">

**Greedy invariant:** before index `i`, `reach` is the farthest index reachable from index 0 using only indexes before `i`. If `i > reach`, nothing can ever cross the gap. Otherwise `i` is reachable, and `i + nums[i]` may extend the reach. The table stores "reachable or not" per index, but every reachable index is ≤ `reach` and every index ≤ `reach` is reachable, so one number holds the whole table.

```java id=canJump
public boolean canJump(int[] nums) {
    int reach = 0;                                   // farthest index reachable so far
    for (int i = 0; i < nums.length; i++) {
        if (i > reach) return false;                 // a gap nobody can cross
        reach = Math.max(reach, i + nums[i]);
    }
    return true;
}

public boolean canJumpTable(int[] nums) {           // the DP version: correct, but O(n²)
    int n = nums.length;
    boolean[] ok = new boolean[n];                   // ok[i]: index i can be reached
    ok[0] = true;
    for (int i = 1; i < n; i++)
        for (int j = 0; j < i && !ok[i]; j++)
            ok[i] = ok[j] && j + nums[j] >= i;       // the last jump came from j
    return ok[n - 1];
}
```

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**The tiled walkway:** `dp[i]` = tilings of length `i`. Last decision at the right end: one vertical 2 × 1 slab (`dp[i − 1]`), two horizontal slabs stacked (`dp[i − 2]`), or one 2 × 2 slab (`dp[i − 2]`). So `dp[i] = dp[i − 1] + 2 × dp[i − 2]`, `dp[0] = dp[1] = 1`: 1, 1, 3, 5, 11. The three last-pieces are disjoint, so the sum is safe.

**The divisible chain:** sort first; then in a valid subset each element divides the next, so it is Chapter 8 with "divides" in place of "less than": `dp[i]` = the largest chain **ending** at `nums[i]`, extend from any `j < i` with `nums[i] % nums[j] == 0`, answer = max. Answers: 2, 4, 1.

**Ordered coin sequences:** `dp[a]` = ordered sequences summing to `a`, `dp[0] = 1`. Last coin `c`: `dp[a] = sum of dp[a − c]`. Amounts in the **outer** loop, so every order is counted. For `[1, 2, 3]` and 4: 1, 1, 2, 4, **7**.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Ways to climb with 1 or 2 steps | `ways[i] = ways[i − 1] + ways[i − 2]`, `ways[0] = ways[1] = 1` | Last move splits climbs into disjoint groups |
| Cheapest climb, pay per step stood on | `dp[i] = min(dp[i − 1] + cost[i − 1], dp[i − 2] + cost[i − 2])` | The top is position n; answer `dp[n]` |
| Max sum, no two adjacent | `dp[i] = max(nums[i − 1] + dp[i − 2], dp[i − 1])` | `dp[i]` is the best for the first i, used or not |
| …in a circle | Max of houses `0..n − 2` and `1..n − 1`; one house alone | Some end is always skipped |
| Count decodings of digits | One digit if 1..9 adds `dp[i − 1]`; two if 10..26 adds `dp[i − 2]`; `dp[0] = 1` | A zero only ends a 10 or a 20 |
| Fewest coins for an amount | `dp[a] = 1 + min dp[a − c]`, sentinel `amount + 1`, −1 if unreached | `dp[a − c]` is final before `dp[a]` |
| Split a string into dictionary words | `dp[i] = OR (dp[j] && word(s[j..i)))`, `dp[0] = true` | Every reachable cut point stays alive |
| Longest increasing subsequence | `dp[i]` ends at i, answer the max; or tails + binary search | Tails stays strictly increasing; it is not the LIS |
| Longest palindromic substring | Expand around 2n − 1 centres | Letters and gaps; widen while ends match |
| Count palindromic substrings | Count every successful widening | Each palindrome has exactly one centre |
| Take x, lose x ± 1 | Bucket `x × count(x)` by value, then House Robber | Taking one x means taking them all |
| Fewest squares summing to n | Coin change with squares; start at `dp[a] = a` | 1 is a square: always reachable |
| Two equal-sum groups, each item once | Boolean `can[s]`, inner loop **backwards** | `can[s − x]` is still last round's value |
| Number of longest increasing runs | `len[i]`, `cnt[i]`: longer replaces, equal adds | Sum `cnt` where `len` is max |
| Up to k steps per move | Running window of the last k cells | Same recurrence, base cases pick the sequence |
| Cheapest passes covering travel days | `dp[d]` over calendar days; the last pass ends on d | Quiet days copy `dp[d − 1]` |

Space is not automatic. The rolling variables work only when the recurrence reads a **fixed** number of recent cells (Chapters 1 to 5, Delete and Earn, fixed k steps). Coin Change, Word Break, LIS and Tickets read back arbitrarily far, so they keep the whole row.

## Five common bugs

1. **The wrong empty base.** Counting starts at `dp[0] = 1` (one way to do nothing); feasibility at `true`; costs at 0. `dp[0] = 0` in a counting problem zeroes everything above it.
2. **Overflowing the sentinel.** `Integer.MAX_VALUE + 1` wraps negative and wins every `min`. Use `amount + 1`, or skip unreachable cells.
3. **The answer in the wrong cell.** Min Cost's top is `dp[n]`, not `dp[n − 1]`; LIS's answer is the max over all `dp[i]`. Say step 5 aloud before coding.
4. **Overwrite before use.** Rolling variables need a `next` temporary; a 0/1 knapsack row needs its inner loop backwards. Both bugs read a value that has already been replaced.
5. **Zero and the two-digit letter.** `"06"` is not F. The two-digit check is `10 ≤ value ≤ 26`, not just `≤ 26`.

<h2 id="revision">Revision</h2>

**How to recognise it.** The question asks how many ways, the best value, or whether something is possible, over a sequence, string or amount. Each answer is built from a choice at each position, and a small summary of the choices so far (an index, an amount, "ends at i") is enough. Brute force would be exponential because the same sub-questions repeat. If one greedy choice is provably safe, use greedy; if you must list every solution, use backtracking.

**Core algorithm.** Say the five answers: (1) the state, in one sentence; (2) the recurrence from the last decision; (3) the base cases, usually the empty prefix; (4) an order in which every cell it reads is already written; (5) the answer cell and how far back the recurrence reads. Write the brute-force recursion, add a memo, then fill the table bottom-up. If only the last few cells are read, keep only those. Combine cases with **sum** (counting, disjoint), **min/max** (optimising) or **OR** (feasibility).

**Common mistakes.**

- The wrong empty base (`dp[0] = 0` when counting needs 1).
- Overflowing a sentinel (`Integer.MAX_VALUE + 1`); use `amount + 1`.
- The answer in the wrong cell (`dp[n − 1]` instead of `dp[n]`, or not the max over `dp[i]` for "ends at i").
- Overwriting a value before reading it (rolling variables, 0/1 knapsack loop direction).
- Leading zeros in Decode Ways; missing gap centres in palindromes.

**Complexity.** Time is (number of states) × (transitions per state): O(n) for fixed look-back, O(n × amount) for Coin Change, O(n²) for LIS with a table, O(n log n) with tails, O(n²) for palindromes by centres. Space is the table size, or O(1) when only a fixed number of recent cells are read.

**Three representative problems.**

1. [House Robber](https://leetcode.com/problems/house-robber/): take or skip, `dp[i] = max(nums[i − 1] + dp[i − 2], dp[i − 1])`.
2. [Coin Change](https://leetcode.com/problems/coin-change/): the last piece, `dp[a] = 1 + min dp[a − c]`, with a safe sentinel.
3. [Longest Increasing Subsequence](https://leetcode.com/problems/longest-increasing-subsequence/): "ends at i" state, answer is the max, tails for O(n log n).

**Look these up yourself.** Real ideas this lesson did not have room for:

- **Reconstructing the solution.** Store which choice won in each cell (a parent pointer), then walk back from the answer cell to print the actual plan, not just its value.
- **Matrix exponentiation.** Any fixed linear recurrence (Climbing Stairs, Tribonacci) can be computed in O(log n) by raising a small matrix to a power.
- **State-machine DP.** Best Time to Buy and Sell Stock with cooldown: several cells per day, one per state (holding, sold, resting).
- **Pseudo-polynomial time.** Why the knapsack table is "fast" only when the numbers are small, and why the general problem is NP-hard.
- **Patience sorting and Dilworth's theorem.** The card game behind tails, and why the number of piles equals the LIS.
- **Bitmask DP.** When the state is a set of up to about 20 items (travelling salesman on small inputs).
- **Digit DP.** Counting numbers up to N with a property, one digit at a time; Decode Ways' grown-up relative.
