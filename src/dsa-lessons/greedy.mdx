<h2 id="prologue">Prologue · Why a greedy choice can be trusted</h2>

A **greedy algorithm** builds its answer one choice at a time. Each choice follows a simple local rule (the farthest reach, the smallest card, the biggest gain) and is **never taken back**. That makes it fast: no backtracking, no table of alternatives.

It also makes it dangerous. A greedy rule that sounds sensible is wrong surprisingly often, and wrong silently: it returns a plausible number. So you do not write a greedy rule until you can say **why it is safe**. A rule is correct when two things hold:

1. **The greedy-choice property.** Some best answer agrees with the greedy's first choice, so you never need to regret it.
2. **Optimal substructure.** After that choice, what remains is the same kind of problem, only smaller, so the same rule applies again.

### Three ways to prove it

Every chapter names the proof it uses.

- **Stays ahead.** After every step, the greedy is at least as far along as any other solution after the same number of steps. If it is never behind, it cannot finish behind.
- **Exchange argument.** Take any best answer that disagrees with the greedy at its first difference. Swap that choice for the greedy's and show the answer gets no worse. Repeat until it *is* the greedy's answer.
- **Forced move.** Sometimes only one choice could possibly be right (the smallest card can only start a group). A forced choice needs no exchange: there is nothing to swap it with.

### Three questions before every move

1. **What is settled?** Every choice already made. Greedy never revisits one.
2. **Why is this move safe?** Name the proof: stays ahead, exchange, or forced. "It looks best" is not an answer.
3. **When do I stop?** When the input is used up, or as soon as the summary you carry already decides the answer.

The dry runs below show a `settled` row for exactly this reason: watch what each choice makes final.

### Hunt for the counterexample first

Before writing code, try to break the rule on **three tiny inputs**, each chosen to hurt:

1. **The degenerate input.** One element, all values equal, all negative, zeros.
2. **The trap.** A big, tempting early choice that blocks something better later.
3. **The tie.** Two choices look equally good. Does the tie-break matter?

If any of them breaks the rule, drop it. The fix is usually to try every choice and remember the results (dynamic programming). If none does, write the one-sentence proof. Two minutes of hunting either saves you from a wrong answer or tells you what the proof must say.

### How to recognise it

- **An optimisation (max, min, fewest, "can you?") where each step has a natural best-looking choice**: farthest reach, smallest remaining card, biggest gain, earliest end.
- **One pass that carries one or two summary values** (a running total, a farthest reach, a tank) instead of a table of possibilities.
- **Sorting by one key makes every decision obvious** (smallest cookie to the least hungry child; heaviest person first).
- **The brute force tries all subsets, all orders or all subarrays** (2ⁿ, n! or n²) and the greedy runs in **O(n) or O(n log n)**.

Warning signs that greedy will fail: **arbitrary coin values**, **whole (0/1) items with weights**, **weighted** choices where one big item is worth many small ones. Hunt hardest there.

One honest note. Some of these chapters are filed under dynamic programming in other books; Kadane's algorithm is the textbook example. That is not a contradiction. **A greedy algorithm is a DP whose proof lets it keep a single candidate per step** instead of a whole table.

<h2 id="max-subarray">Chapter 1 · Maximum Subarray</h2>

### Problem

Find the largest total of a contiguous, non-empty stretch of the array.

`[-2, 1, -3, 4, -1, 2, 1, -5, 4]` gives `6`, from the stretch `[4, -1, 2, 1]`.

### How to recognise it

- "Largest sum of a contiguous subarray", the stretch must be non-empty.
- Negative numbers are allowed, so "take everything" is not the answer.
- The question about a stretch can be asked at each end index: what is the best stretch ending *here*?

### Brute force

Try every start and end and add up the stretch. That is O(n²) with a running sum, O(n³) if you re-add each time. For 10⁵ values it is 5 × 10⁹ steps.

### Intuition

Carry one number, `run`: **the best total of a stretch that ends exactly here**. At each new value `x` there are only two kinds of stretch ending here: `x` alone, or `x` added to a stretch that ended one step earlier. So:

```text
run  = max(x, run + x)        restart here, or extend
best = max(best, run)
```

And `run + x` loses to `x` alone **exactly when `run` is negative**. A negative run only lowers whatever it is attached to, so put it down.

- **Greedy choice:** at each value, keep the old run only if it is not negative.
- **Tempting rule that fails:** "restart whenever the *next value* is negative". On `[5, -2, 5]` it restarts at -2, never sees 5 - 2 + 5 = **8**, and answers 5. A stretch often crosses a negative value and is still worth keeping. The test is on the *run*, not on the next value.

### Dry run

<DryRun title="Maximum Subarray" frames={kadaneFrames([-2, 1, -3, 4, -1, 2, 1, -5, 4])} predict />

### Algorithm

1. Set `run = best = nums[0]`. Never start from 0: that would allow the empty stretch.
2. For each later value `x`: set `run = max(x, run + x)`.
3. Set `best = max(best, run)`.
4. Return `best`.

### Java solution

<HintLadder hints={hints.kadane}>

```java id=maxSubArray
public int maxSubArray(int[] nums) {
    int run = nums[0], best = nums[0];             // non-empty: start from the first value, never from 0
    for (int i = 1; i < nums.length; i++) {
        run = Math.max(nums[i], run + nums[i]);    // restart when the old run is a burden (negative)
        best = Math.max(best, run);
    }
    return best;
}
```

</HintLadder>

### Why it works

**Proof: exchange.** Take any stretch that ends at index `i` and starts before it. Split it into "everything before `i`" and `x`. If the part before `i` has a negative total, **exchange** the stretch for `x` alone: strictly better. If it has a non-negative total, the best such part is the best stretch ending at `i - 1`, which is `run`. So `max(x, run + x)` really is the best stretch ending at `i`. Every stretch ends somewhere, so the largest `run` ever seen is the answer.

- **Settled:** after index `i`, `run` is the best total of a non-empty stretch ending exactly at `i`, and `best` is the best total of any non-empty stretch inside `0..i`.
- **When we stop:** at the end of the array. `run` is then only the best stretch ending at the **last** index, so the answer is `best`, not `run`.

<Reveal q="Isn't this dynamic programming?">

Yes, and that is fine. Write `dp[i]` for the best stretch ending at `i`: `dp[i] = max(nums[i], dp[i - 1] + nums[i])`. Kadane keeps only the latest `dp` value. The greedy reading is the reset rule: the proof that a negative prefix is never worth keeping. The <a href={`${BASE}dsa/lessons/prefix-sum/`}>Prefix Sum</a> lesson has a third view: the best stretch ending at `j` is the prefix total at `j` minus the smallest earlier prefix total.

</Reveal>

### Complexity

- **Time O(n):** one pass.
- **Space O(1):** two integers. LeetCode's bounds (at most 10⁵ values within ±10⁴) keep every total within ±10⁹, inside `int`.

### Edge cases and mistakes

- `[-3, -1, -2]`: every value negative. The answer is **-1**, the largest single value. The stretch must be non-empty, so 0 is not allowed.
- `[0, 0]`: with `run = 0`, extending and restarting give the same total, so either is fine.
- A single element.

**The classic bug:** the empty-stretch version.

```java fragment
int run = 0, best = 0;                             // BUG: 0 is the empty stretch
for (int x : nums) { run = Math.max(0, run + x); best = Math.max(best, run); }
return best;                                       // [-3, -1, -2] -> 0 instead of -1
```

<Reveal q="Why not start run and best at 0, the way a sum usually starts?">

Because 0 is the total of the **empty** stretch, and the problem forbids it. On `[-3, -1, -2]` a version that starts at 0 and resets the run to 0 never sees anything above 0 and returns **0**, while the right answer is -1. Starting both at `nums[0]` and restarting at the value itself (not at 0) keeps every candidate non-empty.

</Reveal>

<h2 id="max-product">Chapter 2 · Maximum Product Subarray</h2>

### Problem

Find the largest product of a contiguous, non-empty stretch.

`[2, 3, -2, 4]` gives `6`, from `[2, 3]`. `[-2, 3, -4]` gives `24`, the whole array.

### How to recognise it

- Same shape as Maximum Subarray, but the operation is multiplication.
- Negative values flip the sign, and zeros wipe everything out.
- A stretch ending here is `x` times a stretch ending one step earlier, or `x` alone.

### Brute force

Try every start and end and multiply. O(n²) with a running product, one pass per start.

### Intuition

Which earlier product makes `x × earlier` largest?

- If `x > 0`, the **largest** earlier product.
- If `x < 0`, the **smallest** (most negative) earlier product, because a negative times a negative is a large positive.
- If `x = 0`, it does not matter: everything through the zero becomes 0, and the next value starts fresh.

So carry two numbers: `hi`, the largest product of a stretch ending here, and `lo`, the smallest.

- **Greedy choice:** keep only the two extremes of the earlier products, not all of them.
- **Tempting rule that fails:** track only the maximum, as in Kadane. On `[-2, 3, -4]` it answers **3**, but the whole array gives **24**. The most negative product, -6, is exactly what the last -4 needs.

### Dry run

<DryRun title="Maximum Product Subarray" frames={maxProductFrames([-2, 3, -4])} predict />

### Algorithm

1. Set `hi = lo = best = nums[0]`.
2. For each later value `x`, compute `a = hi * x` and `b = lo * x` **from the old `hi` and `lo`**.
3. New `hi = max(x, a, b)`; new `lo = min(x, a, b)`.
4. Set `best = max(best, hi)`. Return `best`.

### Java solution

<HintLadder hints={hints.product}>

```java id=maxProduct
public int maxProduct(int[] nums) {
    int hi = nums[0], lo = nums[0], best = nums[0];   // largest / smallest product of a stretch ending here
    for (int i = 1; i < nums.length; i++) {
        int x = nums[i];
        int a = hi * x, b = lo * x;                   // both from the OLD hi and lo
        hi = Math.max(x, Math.max(a, b));
        lo = Math.min(x, Math.min(a, b));
        best = Math.max(best, hi);
    }
    return best;
}
```

</HintLadder>

### Why it works

**Proof: stays ahead, with two runners.** For a fixed `x`, the map "earlier product `P` becomes `x × P`" is increasing when `x > 0` and decreasing when `x < 0`. Either way its maximum and minimum over all earlier products are reached at the **extremes**, `hi` and `lo`. So the only candidates that can ever win are `x`, `hi × x` and `lo × x`, and throwing every other earlier product away loses nothing. No stretch ending at `i` has a product above `hi` or below `lo`.

- **Settled:** after index `i`, `hi` and `lo` are the largest and smallest products of non-empty stretches ending exactly at `i`; `best` is the largest product of any stretch in `0..i`.
- **When we stop:** at the end of the array; the answer is `best`.

<Reveal q="Some solutions swap hi and lo when x is negative. Is that the same thing?">

Yes. Multiplying by a negative turns the largest product into the smallest and vice versa, so `if (x < 0) swap(hi, lo)` followed by `hi = max(x, hi × x)` and `lo = min(x, lo × x)` gives exactly the same values. Use whichever you can explain.

</Reveal>

### Complexity

- **Time O(n):** one pass.
- **Space O(1):** three integers. LeetCode states that every subarray's product fits in a 32-bit integer; `hi × x` and `lo × x` are products of real subarrays, so they fit too. (If a judge's tests break that promise, carry `hi` and `lo` as `long`.)

### Edge cases and mistakes

- `[2, 3, 0, 4]`: a zero resets everything; the answer is **6**, from `[2, 3]`.
- `[-2]`: a single negative value; the answer is **-2**.
- Two negatives separated by positives, like `[-2, 3, -4]`.

**The classic bug:** overwriting `hi` before `lo` reads it.

```java fragment
hi = Math.max(x, Math.max(hi * x, lo * x));
lo = Math.min(x, Math.min(hi * x, lo * x));    // BUG: uses the NEW hi
// [-2, 3, -4, -1] -> 96, a product no stretch has (the answer is 24)
```

The other classic: dropping `lo` entirely answers 3 on `[-2, 3, -4]`.

<h2 id="gas-station">Chapter 3 · Gas Station</h2>

### Problem

`gas[i]` is the fuel you collect at station `i`; `cost[i]` is the fuel burned driving to station `i + 1` (wrapping around). Return the station to start from, with an empty tank, to complete the ring, or -1 if none works.

`gas = [1,2,3,4,5]`, `cost = [3,4,5,1,2]` gives `3`.

### How to recognise it

- A circular route with a gain or loss at each step.
- "Which start works?" where trying each start looks like n separate simulations.
- Each station's net effect is `gas[i] - cost[i]`, its **gain**.

### Brute force

Simulate the lap from every start. Each simulation is O(n), and there are n starts: O(n²).

### Intuition

Two questions hide in one. Each needs its own proof.

- **Whether any start works.** A full lap changes the tank by the total gain. If total gas is less than total cost, no start can work. If it is at least the total cost, some start does.
- **Where it is.** Carry `tank`, the fuel since the current start. **If `tank` goes negative after station `i`, none of the stations from `start` to `i` can be a start**, so jump to `i + 1`.

- **Greedy choice:** after a failure, discard every station you have already tried and restart right after the failure.
- **Tempting rule that fails:** "start at the richest station". With `gas = [0, 1, 3]` and `cost = [3, 0, 1]` the richest is station 2 (gas 3). Starting there you have 2 after leaving, then 2 + 0 - 3 = -1 at the wrap: dry. The only working start is **station 1**. A big pile of fuel says nothing about what comes after it.

### Dry run

Grey cells are stations ruled out as starts. Watch `settled` grow each time the tank goes negative.

<DryRun title="Gas Station" frames={gasFrames([1, 2, 3, 4, 5], [3, 4, 5, 1, 2])} predict />

### Algorithm

1. Set `total = 0`, `tank = 0`, `start = 0`.
2. For each station `i`, let `gain = gas[i] - cost[i]` and add it to both `total` and `tank`.
3. If `tank < 0`: set `start = i + 1` and `tank = 0`.
4. After the loop, return `start` if `total >= 0`, else -1.

### Java solution

<HintLadder hints={hints.gas}>

```java id=canCompleteCircuit
public int canCompleteCircuit(int[] gas, int[] cost) {
    int total = 0, tank = 0, start = 0;
    for (int i = 0; i < gas.length; i++) {
        int gain = gas[i] - cost[i];
        total += gain;                     // decides WHETHER: the whole lap
        tank += gain;                      // decides WHERE: oil since the current start
        if (tank < 0) {                    // can't reach i + 1: no station in start..i can start
            start = i + 1;
            tank = 0;
        }
    }
    return total >= 0 ? start : -1;
}
```

</HintLadder>

### Why it works

**Claim 1, whether. Proof: the lowest point.** Drive from station 0 without ever resetting, and write down the running total of gains, allowing it to go negative. Let station `m` be where that running total is **lowest** (just before `m`'s own gain is added). Start at `m`. On the way to any later station, your tank equals the running total there minus the lowest value: never negative. After you wrap past the end, your tank is that same difference plus the whole lap's total, which is at least 0. You never run dry.

**Claim 2, where. Proof: stays ahead.** You reached every station `k` between `start` and `i` with a tank of at least 0, and still ran dry after `i`. Starting at `k` with an *empty* tank is never better than arriving there with something, so you would run dry by `i` too. A restart happens exactly when the running total sets a new low, which is why the final `start` sits right after the lowest point of Claim 1.

- **Settled:** at the top of iteration `i`, `tank` is the oil gained from `start` to `i - 1`, it is at least 0, and no station before `start` can be a valid start. `total` is the gain of stations `0..i - 1`.
- **When we stop:** after the last station. `total` answers *whether*, `start` answers *where*. Neither alone is enough.

<Reveal q="The scan never drives the wrap-around from start back to start. Why trust it?">

Because Claim 1 already did. The final `start` sits right after the lowest point of the running total, and the lowest-point proof covers the whole lap, wrap-around included, whenever the total is at least 0. The loop does not need to simulate what the proof guarantees.

</Reveal>

### Complexity

- **Time O(n):** one pass.
- **Space O(1):** three integers. With at most 10⁵ stations and amounts up to 10⁴, totals stay within ±10⁹, inside `int`. LeetCode promises the answer is unique when it exists; in general several starts may work, and this returns the one just after the first lowest point.

### Edge cases and mistakes

- One station (`[5]`, `[4]`: start 0).
- A ring that cannot be finished (LeetCode's second example: total gas 9, total cost 10).
- Every gain 0: every start works; this code returns 0, the first.

**The classic bug:** returning `start` without the total check. On `gas = [2, 3, 4]`, `cost = [3, 4, 3]` it returns **2**, but the lap loses 1 unit of fuel and the answer is -1.

<h2 id="jump-game">Chapter 4 · Jump Game</h2>

### Problem

`nums[i]` is the longest jump you may take from stone `i`; you may always jump shorter. Starting at index 0, can you reach the last index?

`[2, 3, 1, 1, 4]` is `true`. `[3, 2, 1, 0, 4]` is `false`.

### How to recognise it

- "Can you reach the end?" with a maximum jump (or step, or fuel) at each position.
- You do not need the path, only whether one exists.
- If you can land on position `j`, any shorter jump from the same take-off lands in between.

### Brute force

Try every jump length from every reachable stone, recursively (or with a DP table of reachable stones). Without memory that is exponential; with memory it is O(n × maxJump), up to O(n²).

### Intuition

**The reachable stones always form one unbroken block, `0..far`.** If you can land on stone `j`, every stone between the take-off stone and `j` is reachable by a shorter leap from the same take-off. So walk left to right, carrying `far`: the farthest stone reachable from any stone seen so far. If you ever stand at an index beyond `far`, there is a gap nobody can cross.

- **Greedy choice:** do not pick a path. Only remember how far *anyone* could get.
- **Tempting rule that fails:** "any zero before the end means stuck". On `[2, 0, 1, 0]` that says false, but stone 0 leaps over the zero to stone 2, and stone 2 reaches the end. A zero only matters when `far` stops on it. (`[3, 2, 1, 0, 4]` is the real trap: every stone reaches stone 3 at most.)

### Algorithm

1. Set `far = 0`.
2. For each index `i` from 0: if `i > far`, return false (a gap).
3. Otherwise set `far = max(far, i + nums[i])`.
4. If the loop finishes, return true.

### Java solution

<HintLadder hints={hints.jump}>

```java id=canJump
public boolean canJump(int[] nums) {
    int far = 0;                                   // every stone 0..far is reachable
    for (int i = 0; i < nums.length; i++) {
        if (i > far) return false;                 // a gap: no reachable stone lands on i
        far = Math.max(far, i + nums[i]);
    }
    return true;
}
```

</HintLadder>

### Why it works

**Proof: stays ahead.** Claim: when the loop reaches stone `i` without failing, every stone `0..far` is reachable and no reachable stone lies beyond `far`. It holds at the start (`far = 0`). Stone `i` is inside the block, so it is reachable, and it extends the block to `i + nums[i]`. If `i > far`, no reachable stone reaches `i`, so `i` and everything after it is unreachable.

- **Settled:** at the top of iteration `i`, `far` is the farthest stone reachable using take-off stones `0..i - 1`.
- **When we stop:** either at a gap (return false), or when the loop ends without one (the last stone is reachable). You may also stop early once `far >= nums.length - 1`.

<Reveal q="Some solutions walk backwards with a ‘goal’ stone. Same thing?">

Yes, mirrored. Start with `goal = n - 1`. Walking from the right, if `i + nums[i] >= goal`, stone `i` can reach the goal, so it becomes the new goal. The answer is `goal == 0`. Both are O(n); pick the one whose invariant you can say out loud.

</Reveal>

### Complexity

- **Time O(n):** one pass.
- **Space O(1):** one integer.

### Edge cases and mistakes

- `[0]`: you are already on the last stone: **true**.
- `[3, 2, 1, 0, 4]`: **false**.
- `[2, 0, 1, 0]`: a zero you leap over: **true**.

**The classic bug:** "any zero before the end means stuck" (see above), or checking `i > far` *after* using `nums[i]`, which lets an unreachable stone extend `far`.

<h2 id="jump-game-ii">Chapter 5 · Jump Game II</h2>

### Problem

Same stones, new question: the fewest jumps to reach the last index. The last index is always reachable.

`[2, 3, 1, 1, 4]` gives `2` (0 to 1 to 4). `[0]` gives `0`.

### How to recognise it

- "Minimum number of jumps / steps / hops" with a reach at each position.
- Unweighted shortest path where the graph is implicit: stone `i` connects to `i + 1 .. i + nums[i]`.
- Reachable positions after `k` jumps form a contiguous block.

### Brute force

A real breadth-first search from stone 0: put each stone in a queue with its distance, and push every stone it can jump to. Correct, but it examines every jump edge: O(n × maxJump), up to O(n²).

### Intuition

Think in rounds. The stones you can stand on with **at most k jumps** form one block `0..end`, by Chapter 4's argument. While you scan the stones of that block, track `far`, the farthest any of them reaches: **that is where the block for k + 1 jumps ends.** So:

- Scan stones left to right, updating `far`.
- When the scan reaches `end`, the edge of the current block, one more jump is forced: `jumps++`, `end = far`.
- Stop before the last stone: you never jump *from* it.

You never decide which stone to land on. You only count how many times you cross an edge.

- **Greedy choice:** extend to the farthest *next reach*, not the farthest *landing spot*.
- **Tempting rule that fails:** "always jump as far as you can". On `[2, 3, 1, 1, 4]` it goes 0, 2, 3, 4: **three** jumps, while 0, 1, 4 takes **two**. The long jump lands on a stone with a short reach. The landing spot is the wrong thing to be greedy about.

<Figure caption="[2, 3, 1, 1, 4] in levels. Level 0 is stone 0; it reaches 2, so level 1 is stones 1..2. Scanning them, stone 1 reaches 1 + 3 = 4, so level 2 is stones 3..4 and contains the last stone: 2 jumps.">

</Figure>

### Dry run

The green region is everything reachable with `jumps` jumps. A jump is counted only when `i` reaches `end`.

<DryRun title="Jump Game II" frames={jumpIIFrames([2, 3, 1, 1, 4])} predict />

### Algorithm

1. Set `jumps = 0`, `end = 0`, `far = 0`.
2. For `i` from 0 to `n - 2`: set `far = max(far, i + nums[i])`.
3. If `i == end`: set `jumps++` and `end = far`.
4. Return `jumps`.

### Java solution

<HintLadder hints={hints.jump2}>

```java id=jump
public int jump(int[] nums) {
    int jumps = 0, end = 0, far = 0;               // end: last stone reachable with `jumps` jumps
    for (int i = 0; i < nums.length - 1; i++) {    // never jump FROM the last stone
        far = Math.max(far, i + nums[i]);          // the next block ends at the best reach so far
        if (i == end) {                            // edge of this block: one more jump is forced
            jumps++;
            end = far;
        }
    }
    return jumps;
}
```

</HintLadder>

### Why it works

**Proof: stays ahead.** Let `E(k)` be the end of the block after `k` jumps. Claim: for any path at all, the stone it stands on after `k` jumps is at most `E(k)`. True for `k = 0`. If a path stands on `p <= E(k)` after `k` jumps, its next landing is at most `p + nums[p]`, and `p` was scanned before the edge `E(k)`, so `p + nums[p] <= far = E(k + 1)`. **The greedy's block is never behind any path.** And every stone inside the block really is reachable in that many jumps. So the first `k` whose block contains the last stone is the minimum.

- **Settled:** whenever `i == end`, `far` is the farthest stone reachable from any stone in `0..end`, exactly the end of the next block.
- **When we stop:** after `i = n - 2`. `jumps` is the number of edges crossed, and `end >= n - 1`.

<Reveal q="Why is this breadth-first search, and why is it O(n) instead of O(n × maxJump)?">

A real BFS from stone 0 would put each stone in a queue with its distance. But the stones at distance `k` are always one contiguous run, `E(k - 1) + 1 .. E(k)`, so the queue is just a window, and two integers can hold it. Each stone is scanned once: O(n) time, O(1) space. A plain BFS that examines every jump edge costs O(n × maxJump).

</Reveal>

<Reveal q="What if the last stone might be unreachable?">

Then a block can stop growing: at `i == end`, `far` is still `end`. Add `if (far <= i) return -1;` inside the `i == end` branch, before `end = far`. LeetCode guarantees reachability here; Chapter 4 is the check if it doesn't.

</Reveal>

### Complexity

- **Time O(n):** each stone is scanned once.
- **Space O(1):** three integers.

### Edge cases and mistakes

- `[0]`: the loop never runs and the answer is 0.
- Two stones, `[1, 0]`: one jump.
- A long first jump that covers everything: answer 1.

**The classic bug:** looping to `i < nums.length`. When the last stone is the edge of a block, the loop counts a jump *from* it: `[2, 3, 1, 1, 4]` returns 3, and `[0]` returns 1.

<h2 id="partition-labels">Chapter 6 · Partition Labels</h2>

### Problem

Cut a string into as many pieces as possible so that **each letter appears in at most one piece**. Return the piece sizes.

`"ababcbacadefegdehijhklij"` gives `[9, 7, 8]`.

### How to recognise it

- Cut a sequence into the most pieces under a "no value may span two pieces" rule.
- Each letter has a first and a last position, and a piece that holds the letter must stretch across it.
- Cutting early is always better, as long as the cut is legal.

### Brute force

Try every set of cut positions: 2ⁿ⁻¹ ways, and check each piece. Or grow a piece and, for each new letter, rescan the rest of the string to see if it appears later: O(n²).

### Intuition

A piece that contains letter `c` must reach `last[c]`, the last index of `c`. So walk the string carrying `end`: **the farthest last appearance of any letter seen in the current piece**. When `i == end`, no letter in the piece appears again: cut, record the size, and start a new piece.

- **Greedy choice:** cut at the earliest legal point, the first `i` where `i == end`.
- **Tempting rule that fails:** "cut where the current letter makes its last appearance". On `"abba"` that cuts after the second b (index 2) and returns `[3, 1]`, which splits `a` across two pieces. The right answer is `[4]`. The `max` in `end = max(end, last[c])` is what protects letters seen earlier.

<Figure caption="LeetCode's example. The first piece must reach the last a (8); c's last copy at 7 is already inside. The second piece starts with d (last at 14) and stretches to the last e at 15. The third runs to the end. Sizes 9, 7, 8.">

</Figure>

### Algorithm

1. First pass: record `last[c]`, the last index of each letter.
2. Set `start = 0`, `end = 0`.
3. For each `i`: set `end = max(end, last[s[i]])`.
4. If `i == end`: record the piece size `end - start + 1` and set `start = i + 1`.

### Java solution

<HintLadder hints={hints.partition}>

```java id=partitionLabels
public List<Integer> partitionLabels(String s) {
    int[] last = new int[26];
    for (int i = 0; i < s.length(); i++) last[s.charAt(i) - 'a'] = i;
    List<Integer> sizes = new ArrayList<>();
    int start = 0, end = 0;
    for (int i = 0; i < s.length(); i++) {
        end = Math.max(end, last[s.charAt(i) - 'a']);   // the piece must reach this letter's last copy
        if (i == end) {                                  // nothing inside goes further: a safe cut
            sizes.add(end - start + 1);
            start = i + 1;
        }
    }
    return sizes;
}
```

</HintLadder>

### Why it works

**Proof: stays ahead, with forced cuts.** A cut after index `i` is **legal** exactly when no letter appears on both sides of it. Every valid split cuts only at legal points, and cutting at *every* legal point is itself a valid split. So the most pieces you can get is "cut at every legal point". The scan's test `i == end` is exactly "`i` is legal": `end` is the farthest last appearance of any letter in the current piece, and letters of earlier pieces all ended before it began. The greedy takes each legal cut the moment it appears, so its k-th cut is never later than anyone else's.

- **Settled:** `end` is the farthest last appearance of every letter in `s[start..i]`, and every piece already recorded contains all copies of its letters.
- **When we stop:** at the end of the string, where `i == end` always holds.

### Complexity

- **Time O(n):** two passes.
- **Space O(1) beyond the output:** 26 integers.

### Edge cases and mistakes

- `"abba"`: the shortcut cuts too early; the answer is `[4]`.
- `"abc"`: every letter once: `[1, 1, 1]`.
- `"aaaa"`: one piece: `[4]`.

**The classic bug:** cutting when the *current* letter makes its last appearance (`last[c] == i`) instead of when `i == end`. On `"abba"` it returns `[3, 1]`, an illegal split.

<h2 id="hand-of-straights">Chapter 7 · Hand of Straights</h2>

### Problem

Split the cards into groups of `groupSize` consecutive values, using every card. Return whether it can be done.

`hand = [1,2,3,6,2,3,4,7,8]`, `groupSize = 3` is `true` (1 2 3, 2 3 4, 6 7 8).

### How to recognise it

- "Divide into groups of k consecutive numbers", every element used.
- Duplicates are allowed, so you need counts.
- One end of the sorted values has no choice about where it goes.

### Brute force

Try every way to place each card into a group: exponential. A smarter brute force tries every group a chosen card could belong to, with backtracking.

### Intuition

**The smallest remaining card must start a group.** No smaller card exists, so its group cannot begin below it, and a group of consecutive values that begins at `x` is exactly `x, x + 1, ..., x + groupSize - 1`. Remove one of each; if any value is missing, answer false. Repeat until the cards run out.

- **Greedy choice:** always start from the smallest card left (a `TreeMap` of counts gives it in O(log n)).
- **Tempting rule that fails:** "start a group from whatever card you see first" (or the most common value). On `[2, 1, 3, 4, 5, 6]` with groups of 3, starting at 2 makes 2, 3, 4 and strands the 1; the correct answer is true (1 2 3, 4 5 6). Those cards still have a choice, and a wrong choice strands someone.

### Algorithm

1. If `hand.length % groupSize != 0`, return false.
2. Count the cards in a `TreeMap`.
3. While the map is not empty: let `first` be the smallest key.
4. For `v` from `first` to `first + groupSize - 1`: if `v` is missing, return false; otherwise remove one copy of `v`.
5. Return true.

### Java solution

<HintLadder hints={hints.straights}>

```java id=isNStraightHand
public boolean isNStraightHand(int[] hand, int groupSize) {
    if (hand.length % groupSize != 0) return false;
    TreeMap<Integer, Integer> count = new TreeMap<>();
    for (int card : hand) count.merge(card, 1, Integer::sum);
    while (!count.isEmpty()) {
        int first = count.firstKey();                  // the smallest card MUST start a group
        for (int v = first; v < first + groupSize; v++) {
            Integer have = count.get(v);
            if (have == null) return false;            // a hole in the forced group: no arrangement exists
            if (have == 1) count.remove(v); else count.put(v, have - 1);
        }
    }
    return true;
}
```

</HintLadder>

### Why it works

**Proof: forced move.** Every valid arrangement puts the smallest card `x` in some group, and that group can only be `x .. x + groupSize - 1`. So every valid arrangement contains this group; removing it leaves a smaller hand that must be arrangeable on its own (optimal substructure). There is no exchange to make, because there was never a choice. And if a value in the forced group is missing, **no arrangement exists**, not merely "this attempt failed". That is why the code can return false at once with no backtracking.

- **Settled:** the map holds exactly the cards not yet grouped, and every group formed so far is part of every valid arrangement.
- **When we stop:** when the map is empty (true), or at the first hole (false).

<Reveal q="Would starting from the LARGEST card work too?">

Yes, by the mirror argument: nothing is larger, so the largest card must **end** its group. Use `lastKey()` and count downward. What fails is starting anywhere else, because those cards still have a choice.

</Reveal>

### Complexity

- **Time O(n log n):** every card is removed exactly once, each with an O(log n) map operation.
- **Space O(n):** the count map. Values reach 10⁹ and `groupSize` 10⁴, so `first + groupSize` stays inside `int`. Divide Array in Sets of K Consecutive Numbers is the same problem.

### Edge cases and mistakes

- `[1, 2, 3, 4, 5]` with groups of 4: false before you start, since 5 cards do not split into 4s.
- `groupSize = 1`: always true.
- `[2, 1, 3, 4, 5, 6]` with groups of 3: true; the trap for "start from the first card you see".

**The classic bug:** walking the cards in input order with a `HashMap` and starting a group from each card that is still there. On `[2, 1, 3, 4, 5, 6]` with groups of 3 it starts 2, 3, 4, strands the 1, and returns false.

<h2 id="stock-ii">Side quest 1 · Best Time to Buy and Sell Stock II</h2>

### Problem

A share's price is known for every day. You may hold at most one share, and buy and sell as often as you like (selling and buying again on the same day is allowed). Maximise the total profit.

`[7, 1, 5, 3, 6, 4]` gives `7` (buy at 1, sell at 5; buy at 3, sell at 6).

### How to recognise it

- Unlimited transactions, one share at a time, no fee.
- Profit is a sum of price differences.

### Brute force

Try every set of buy and sell days: exponential. A DP over (day, holding or not) is O(n) and also correct; the greedy is simpler because there is no fee.

### Intuition

A trade that buys on day `a` and sells on day `b` earns `p[b] - p[a]`, which equals the sum of the day-to-day changes from `a` to `b`. **Every rising step can be earned on its own** (buy yesterday, sell today), and **no falling step ever has to be taken**.

- **Greedy choice:** take every positive day-to-day change.
- **Tempting rule that fails:** "buy at the lowest price, sell at the highest" (a single trade). On `[1, 5, 3, 6]` it earns 6 - 1 = 5, but 1 to 5 and 3 to 6 earns 4 + 3 = **7**.

<Figure caption="[7, 1, 5, 3, 6, 4]. Daily changes -6, +4, -2, +3, -2. Take the +4 (buy at 1, sell at 5) and the +3 (buy at 3, sell at 6): profit 7.">
  <ArrayStrip name="price" values={[7, 1, 5, 3, 6, 4]} />
  <ArrayStrip name="change" values={['·', -6, 4, -2, 3, -2]} tones={{ 2: 'done', 4: 'done', 1: 'out', 3: 'out', 5: 'out', 0: 'ghost' }} />
</Figure>

### Dry run

<DryRun title="Stock II" frames={stockFrames([7, 1, 5, 3, 6, 4])} predict />

### Algorithm

1. Set `profit = 0`.
2. For each day `i` from 1: add `max(0, prices[i] - prices[i - 1])` to `profit`.
3. Return `profit`.

### Java solution

<HintLadder hints={hints.stock}>

```java id=maxProfit
public int maxProfit(int[] prices) {
    int profit = 0;
    for (int i = 1; i < prices.length; i++)
        profit += Math.max(0, prices[i] - prices[i - 1]);   // take every rising step, skip every fall
    return profit;
}
```

</HintLadder>

### Why it works

**Proof: exchange.** Replace any trade with the rising steps inside it; the profit never goes down. And no plan can beat the sum of all rising steps, because each plan's profit is a sum of daily changes over days it holds, and dropping the falling ones only helps.

- **Settled:** after day `i`, `profit` is the best profit for days `0..i`.
- **When we stop:** after the last day.

### Complexity

- **Time O(n)**, **space O(1)**.

### Edge cases and mistakes

- One price, or prices that only fall: 0.
- Flat days add nothing.
- The classic slip is the single-trade rule above.

### Practice

**Transfer test:** now every sale costs a fee. Why does the step-by-step trick break? (Each separate step would pay the fee; merging steps into one long trade pays it once. The choice now depends on the future, so carry two states, holding and not holding, which is a small DP.)

<h2 id="assign-cookies">Side quest 2 · Assign Cookies</h2>

### Problem

Child `i` needs a cookie of size at least `g[i]`; the cookies have sizes `s[j]`. Each child gets at most one cookie. Satisfy as many children as possible.

`g = [1, 2, 3]`, `s = [1, 1]` gives `1`.

### How to recognise it

- Match items to needs, each used once, maximise matches.
- A match works when the item is at least the need.

### Brute force

Try every assignment of cookies to children: n! orderings (or a bipartite-matching search). Far too slow for large inputs.

### Intuition

Sort both lists. Give the **least hungry** child the **smallest cookie that satisfies them**. A cookie too small for the least hungry child is too small for everyone left: throw it away.

- **Greedy choice:** smallest cookie that fits the least hungry waiting child.
- **Tempting rule that fails:** "give the biggest cookie to the least hungry child". With `g = [1, 2]` and `s = [1, 2]` it gives cookie 2 to the child needing 1, and cookie 1 cannot satisfy the child needing 2: **1** child fed instead of 2.

<Reveal q="Hunger [1, 2, 3], rolls [1, 1]. And hunger [1, 2], rolls [1, 2, 3]?">

First: the roll of 1 satisfies the child who needs 1; the second roll of 1 is too small for the child who needs 2, and therefore for everyone left. **1.** Second: roll 1 to the child needing 1, roll 2 to the child needing 2, and the roll of 3 is spare. **2.**

</Reveal>

### Dry run

<DryRun title="Assign Cookies" frames={cookiesFrames([2, 1, 3], [1, 3, 1, 2])} predict />

### Algorithm

1. Sort both arrays.
2. Set `child = 0`.
3. For each cookie in increasing size: if it is at least `g[child]`, set `child++`.
4. Stop when cookies or children run out. Return `child`.

### Java solution

<HintLadder hints={hints.cookies}>

```java id=findContentChildren
public int findContentChildren(int[] g, int[] s) {
    Arrays.sort(g);
    Arrays.sort(s);
    int child = 0;                                     // least hungry child still waiting
    for (int roll = 0; roll < s.length && child < g.length; roll++)
        if (s[roll] >= g[child]) child++;              // smallest roll that fits: never a waste
    return child;                                      // a roll too small here is too small for everyone
}
```

</HintLadder>

### Why it works

**Proof: exchange.** Suppose a best plan gives that child a roll `y` instead of the smallest fitting roll `x`. Then `y >= x`. If `x` is unused, swap `y` for `x`. If another child has `x`, swap their rolls: that child needed at most `x`, and `y >= x`, so both are still satisfied. Either way the count is unchanged.

- **Settled:** every child before `child` is fed, each with the smallest roll that could feed them.
- **When we stop:** when either list runs out.

### Complexity

- **Time O(n log n + m log m)** for the two sorts, then one linear walk.
- **Space O(1)** beyond the sort.

### Edge cases and mistakes

- No cookies, or no children: 0.
- All cookies too small: 0.
- Spare cookies at the end are fine.

### Practice

**Transfer test:** what if a child may take several rolls whose sizes add up to their need? (The swap argument breaks, since two small rolls might serve one child or two, and the problem becomes a much harder packing problem.)

<h2 id="boats">Side quest 3 · Boats to Save People</h2>

### Problem

Each boat carries at most two people and at most `limit` in total weight; nobody is heavier than `limit`. Carry everyone in the fewest boats.

`people = [3, 2, 2, 1]`, `limit = 3` gives `3`.

### How to recognise it

- Pair items under a capacity, at most two per container.
- Sorting turns "which pair?" into "which two ends?".

### Brute force

Try every way to pair people up: exponential, or O(n²) with a greedy search over pairs. Sorting avoids both.

### Intuition

Look at the **heaviest** person. They must leave in some boat. If even the lightest person cannot ride with them, nobody can: they go alone. Otherwise, pair them with the lightest.

- **Greedy choice:** heaviest with lightest if they fit, else heaviest alone.
- **Tempting rule that fails:** "pair the two lightest people". With `[1, 1, 3, 3]` and `limit = 4` it pairs 1 + 1, then sends each 3 alone: **3** boats. Pairing each 3 with a 1 needs **2**.

<Reveal q="Weights [3, 2, 2, 1], limit 3. How many boats?">

Sorted: 1, 2, 2, 3. The 3 cannot ride with the 1 (4 > 3): alone. The 2 rides with the 1 (3 &lt;= 3). The last 2 rides alone. **3 boats.**

</Reveal>

### Dry run

<DryRun title="Boats to Save People" frames={boatsFrames([3, 2, 2, 1], 3)} predict />

### Algorithm

1. Sort the weights.
2. Set `light = 0`, `heavy = n - 1`, `boats = 0`.
3. While `light <= heavy`: if `people[light] + people[heavy] <= limit`, advance `light`.
4. Always do `heavy--` and `boats++`. Return `boats`.

### Java solution

<HintLadder hints={hints.boats}>

```java id=numRescueBoats
public int numRescueBoats(int[] people, int limit) {
    Arrays.sort(people);
    int boats = 0, light = 0, heavy = people.length - 1;
    while (light <= heavy) {
        if (people[light] + people[heavy] <= limit) light++;   // the lightest rides along if anyone can
        heavy--;                                               // the heaviest leaves in this boat regardless
        boats++;
    }
    return boats;
}
```

</HintLadder>

### Why it works

**Proof: exchange.** In a best plan, say the heaviest `h` rides with `p` (or alone) and the lightest `l` rides with `q` (or alone). Swap `p` and `l`: `h + l` fits by assumption, and `p + q <= h + p` (since `q <= h`) also fits. No extra boat.

- **Settled:** everyone outside `light..heavy` has boarded, in the fewest boats possible for them.
- **When we stop:** when the pointers cross. When `light == heavy`, one person is left and takes a boat alone.

### Complexity

- **Time O(n log n)** for the sort; the loop is O(n).
- **Space O(1)** beyond the sort.

### Edge cases and mistakes

- One person: 1 boat.
- Everyone exactly at `limit`: each rides alone.
- The slip is `light < heavy` in the loop, which skips the last person.

### Practice

**Transfer test:** boats that hold three people. Does pairing the heaviest with the two lightest still have a proof? (No. The swap argument relied on exactly two seats. Try weights [1, 1, 2, 2, 2, 2] with limit 5.)

<h2 id="candy">Side quest 4 · Candy</h2>

### Problem

Children stand in a line with ratings. Each gets at least one sweet, and a child rated higher than an **immediate neighbour** must get more than that neighbour. Use the fewest sweets.

`[1, 0, 2]` gives `5` (2, 1, 2).

### How to recognise it

- A local rule between neighbours on **both** sides.
- A single pass cannot see the other side.

### Brute force

Search every assignment of sweets and check the rules, or repeat "fix any violated pair" until nothing changes (up to O(n²) passes).

### Intuition

Every child has two rules, one per side. Satisfy them **one direction at a time**. A left-to-right pass gives `L[i]`: 1, or `L[i - 1] + 1` when rated above the left neighbour. A right-to-left pass does the same for the right neighbour. The answer for child `i` is `max(L[i], R[i])`.

- **Greedy choice:** give each child the smallest count that satisfies one side, then raise it only as needed for the other.
- **Tempting rule that fails:** a single left-to-right pass. On `[5, 4, 3, 2, 1]` every child is not above the left neighbour, so everyone gets 1: total 5, which breaks every right-hand rule. The answer is **15**.

<Figure caption="[1, 2, 87, 87, 87, 2, 1]. Left pass 1, 2, 3, 1, 1, 1, 1; right pass 1, 1, 1, 1, 3, 2, 1; take the larger: 1, 2, 3, 1, 3, 2, 1 = 13. Equal neighbours (the 87s) impose nothing on each other.">
  <ArrayStrip name="rating" values={[1, 2, 87, 87, 87, 2, 1]} />
  <ArrayStrip name="left pass" values={[1, 2, 3, 1, 1, 1, 1]} tones={{ 2: 'hot' }} />
  <ArrayStrip name="right pass" values={[1, 1, 1, 1, 3, 2, 1]} tones={{ 4: 'hot' }} />
  <ArrayStrip name="sweets" values={[1, 2, 3, 1, 3, 2, 1]} tones={{ 0: 'done', 1: 'done', 2: 'done', 3: 'done', 4: 'done', 5: 'done', 6: 'done' }} />
</Figure>

### Dry run

<DryRun title="Candy" frames={candyFrames([1, 2, 87, 87, 87, 2, 1])} predict />

### Algorithm

1. Give everyone 1 sweet.
2. Left to right: if `ratings[i] > ratings[i - 1]`, set `c[i] = c[i - 1] + 1`.
3. Right to left: if `ratings[i] > ratings[i + 1]`, set `c[i] = max(c[i], c[i + 1] + 1)`.
4. Return the sum of `c`.

### Java solution

<HintLadder hints={hints.candy}>

```java id=candy
public int candy(int[] ratings) {
    int n = ratings.length;
    int[] c = new int[n];
    Arrays.fill(c, 1);
    for (int i = 1; i < n; i++)                        // left neighbours
        if (ratings[i] > ratings[i - 1]) c[i] = c[i - 1] + 1;
    for (int i = n - 2; i >= 0; i--)                   // right neighbours, keeping the stricter need
        if (ratings[i] > ratings[i + 1]) c[i] = Math.max(c[i], c[i + 1] + 1);
    int total = 0;
    for (int x : c) total += x;
    return total;
}
```

</HintLadder>

### Why it works

**Proof: stays ahead, in both directions.** By induction along each rising run, any valid assignment gives child `i` at least `L[i]` and at least `R[i]`. And `max(L[i], R[i])` satisfies every rule, so it is the minimum. The second pass computes that max in place.

- **Settled:** after the left pass, every left-neighbour rule holds; after the right pass, both do, and no count was ever lowered.
- **When we stop:** after the second pass.

### Complexity

- **Time O(n)**, **space O(n)** for the counts.

### Edge cases and mistakes

- One child: 1 sweet.
- Equal ratings impose nothing on each other.
- A valley, like `[3, 1, 3]`: the low child gets 1 and both neighbours get 2.

**The classic bug:** writing `c[i] = c[i + 1] + 1` in the second pass, without the max. On `[1, 3, 4, 5, 2]` it overwrites the 5's left-pass 4 with 2, so the 5 gets fewer sweets than the 4 beside it: total 9, invalid. The answer is 11.

### Practice

**Transfer test:** why does a single left-to-right pass fail on `[5, 4, 3, 2, 1]`? (It gives everyone 1 sweet, total 5. Every rule here compares a child with the neighbour on their right, and only the right-to-left pass looks that way: the answer is 15.)

<h2 id="wildcard-parens">Side quest 5 · Valid Parenthesis String</h2>

### Problem

A string of `(`, `)` and `*`, where each `*` may be read as `(`, as `)`, or as nothing. Can it be read as correctly matched brackets?

`"(*))"` is `true`. `"(*"` is `true`. `")("` is `false`.

### How to recognise it

- Bracket matching, but some characters are wildcards.
- Choosing each wildcard greedily (always `(`, always `)`) will fail on some input.

### Brute force

Try all three readings of every `*`: 3ᵏ combinations for `k` stars, each checked in O(n).

### Intuition

Do not guess what each `*` is. Track **every possible count of open brackets at once**. Those counts always form a range `lo..hi`: `(` moves both ends up, `)` moves both down, and `*` lowers `lo` and raises `hi` (it could be either, or nothing). Two rules keep the range honest:

- If `hi < 0`, there are too many `)` even with every `*` read as `(`: **false**.
- If `lo < 0`, clamp it to 0. A negative count is not a real option; it means some `*` must be read differently.

At the end, a count of 0 must be possible: `lo == 0`.

- **Greedy choice:** postpone every decision; keep only the lowest and highest possible open counts.
- **Tempting rule that fails:** "read every `*` as nothing". On `"(*"` that gives `(`, which is invalid, but reading the `*` as `)` gives `()`: the answer is **true**. (Always reading it as `(` fails on the same string; always reading it as `)` fails on `"*)"`.)

<Figure caption="“(*))”. After each character the possible open counts are 1..1, 0..2, 0..1 (clamped from -1), 0..0 (clamped). hi never drops below 0 and lo ends at 0: valid, reading the * as (.">
  <ArrayStrip name="s" values={['(', '*', ')', ')']} />
  <ArrayStrip name="lo" values={[1, 0, 0, 0]} tones={{ 3: 'done' }} />
  <ArrayStrip name="hi" values={[1, 2, 1, 0]} />
</Figure>

### Dry run

<DryRun title="Valid Parenthesis String" frames={wildcardFrames('(*))')} predict />

### Algorithm

1. Set `lo = hi = 0`.
2. For each character: `(` does `lo++, hi++`; `)` does `lo--, hi--`; `*` does `lo--, hi++`.
3. If `hi < 0`, return false.
4. If `lo < 0`, set `lo = 0`.
5. After the loop, return `lo == 0`.

### Java solution

<HintLadder hints={hints.wildcard}>

```java id=checkValidString
public boolean checkValidString(String s) {
    int lo = 0, hi = 0;                    // fewest and most '(' that could be open right now
    for (char ch : s.toCharArray()) {
        if (ch == '(') { lo++; hi++; }
        else if (ch == ')') { lo--; hi--; }
        else { lo--; hi++; }               // '*' as ')' lowers, as '(' raises, as nothing stays
        if (hi < 0) return false;          // too many ')' even if every '*' opens
        if (lo < 0) lo = 0;                // a count below zero is not a real option
    }
    return lo == 0;
}
```

</HintLadder>

### Why it works

**Proof: invariant.** After each character, `lo..hi` is exactly the set of open counts some reading of the prefix can reach. Every step changes a count by -1, 0 or +1, so the set can never develop a gap, and two numbers describe it fully. A count of 0 at the end means some reading balances.

- **Settled:** the whole prefix is summarised by `lo..hi`; no reading has been lost.
- **When we stop:** at the end of the string, or as soon as `hi < 0`.

### Complexity

- **Time O(n)**, **space O(1)**.

### Edge cases and mistakes

- Empty string: true.
- Only stars: true.
- `")("`: `hi` goes negative at the first character: false.

**The classic bug:** forgetting the clamp. On `"(*)"`, `lo` goes 1, 0, -1 and the function returns false, but reading the `*` as nothing gives `"()"`.

### Practice

**Transfer test:** a two-stack solution pushes the indices of `(` and `*`, matches each `)` against an open `(` first (else a `*`), then pairs leftover `(` with leftover `*`. Why must each leftover `(` be paired with a `*` **to its right**? (A `*` before an opener cannot close it.)

<h2 id="merge-triplets">Side quest 6 · Merge Triplets to Form Target Triplet</h2>

### Problem

You have triples. Merging two triples replaces one with their position-by-position maximum. Can some triple become exactly the target?

`triplets = [[2,5,3],[1,8,4],[1,7,5]]`, `target = [2,7,5]` gives `true`.

### How to recognise it

- Combine with max (or min), and the target must be hit exactly.
- Operations only move values one way.

### Brute force

Try every subset of triples, merge it, and compare with the target: 2ⁿ subsets.

### Intuition

Maxima never go down. So **a triple with any value above the target in the same position can never be used**: it would overshoot forever. Every other triple is **safe**: merging it never pushes anything past the target. So merge all the safe ones, and check that each of the three positions is matched exactly by at least one of them. Order does not matter, because max does not care about order.

- **Greedy choice:** filter out triples that overshoot; merge everything that remains.
- **Tempting rule that fails:** "merge everything". With triples `(2, 9, 5)`, `(1, 7, 1)` and target `(2, 7, 5)`, merging both gives `(2, 9, 5)`: the 9 overshoots. The only safe triple is `(1, 7, 1)`, which matches the middle but not 2 or 5: **false**.

<Reveal q="Triples (2, 9, 5) and (1, 7, 1), target (2, 7, 5). Yes or no?">

(2, 9, 5) has 9 > 7 in the middle: unsafe, never used. The only safe triple is (1, 7, 1), which matches the middle but not 2 or 5. **No.** A version that skips the filter sees a 2, a 7 and a 5 somewhere and wrongly says yes.

</Reveal>

### Dry run

<DryRun title="Merge Triplets" frames={tripletsFrames([[2, 5, 3], [1, 8, 4], [1, 7, 5]], [2, 7, 5])} predict />

### Algorithm

1. Set `hit = [false, false, false]`.
2. For each triple: skip it if any value exceeds the target in the same position.
3. Otherwise, for each position where it equals the target, set `hit[k] = true`.
4. Return true if all three flags are set.

### Java solution

<HintLadder hints={hints.triplets}>

```java id=mergeTriplets
public boolean mergeTriplets(int[][] triplets, int[] target) {
    boolean[] hit = new boolean[3];
    for (int[] t : triplets) {
        if (t[0] > target[0] || t[1] > target[1] || t[2] > target[2]) continue;   // overshoots forever
        for (int k = 0; k < 3; k++) if (t[k] == target[k]) hit[k] = true;      // safe: merge it in
    }
    return hit[0] && hit[1] && hit[2];
}
```

</HintLadder>

### Why it works

**Proof: invariant.** The merge of all safe triples is at most the target in every position (each safe triple is), and at position `k` it equals the target exactly when some safe triple does. Any usable merge uses only safe triples, so it is at most the merge of all of them; if even that misses a position, nothing can reach it.

- **Settled:** each triple is judged once, safe or not, and a safe triple never needs reconsidering.
- **When we stop:** after the last triple.

### Complexity

- **Time O(n)**, **space O(1)**.

### Edge cases and mistakes

- A triple equal to the target: true by itself.
- A triple that matches in two positions but overshoots in the third: unusable.
- The slip is skipping the filter.

### Practice

**Transfer test:** if merging took the position-by-position **minimum**, what changes? (Mirror everything: discard triples with any value below the target, then look for exact matches.)

<h2 id="choose-the-tool">When greedy fails</h2>

Greedy is the wrong tool whenever the **greedy-choice property fails**: no best answer agrees with the local rule. The hunt usually finds out in one tiny input.

- **Coin change with arbitrary coins.** For coins {1, 3, 4} and amount 6, largest-first uses 3 coins (4 + 1 + 1); the best is 2 (3 + 3). No best answer for 6 even uses a 4, so there is no exchange to make. Real currencies like {1, 5, 10, 25} are designed so largest-first works; arbitrary coin sets are not.
- **0/1 knapsack.** Capacity 50, items (weight 10, value 60), (20, 100), (30, 120). Best value per kilo first takes 60 and 100, then 120 no longer fits: **160**. Taking the 20 and the 30 gives **220**. Whole items leave empty space the ratio argument cannot account for. (With fractions allowed, fractional knapsack, the ratio rule *is* optimal: there is never empty space.)
- **Weighted interval scheduling.** Earliest-end-first is optimal when every booking is worth the same; give them weights and it fails. See <a href={`${BASE}dsa/lessons/intervals/#choose-the-tool`}>the Intervals lesson</a>.

The fix in all three is the same: **try every choice, and remember the answer for each smaller problem.** That is dynamic programming; <a href={`${BASE}dsa/lessons/dp-1d/`}>1-D Dynamic Programming</a> is where it lives.

<HintLadder hints={hints.coins} labels={['Hunt first', 'What to remember', 'The recurrence', 'Compare with the Java solution']}>

```java id=coinChange
public int coinChange(int[] coins, int amount) {
    int[] best = new int[amount + 1];                  // best[a] = fewest coins for amount a
    Arrays.fill(best, Integer.MAX_VALUE);
    best[0] = 0;
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a && best[a - c] != Integer.MAX_VALUE)
                best[a] = Math.min(best[a], best[a - c] + 1);   // try EVERY last coin
    return best[amount] == Integer.MAX_VALUE ? -1 : best[amount];
}
```

**O(amount × coins) time, O(amount) space.** On {1, 3, 4} and 6, `best` is 0, 1, 2, 1, 1, 2, 2: the last coin is a 3, after `best[3] = 1`.

</HintLadder>

<Reveal q="How would I know, in an interview, whether largest-first is safe for a given coin set?">

You usually cannot prove it on the spot, and the interviewer rarely wants you to. If the coins are part of the input, assume they are arbitrary and use DP. If they are fixed and familiar (1, 5, 10, 25), say that this particular set is "canonical": largest-first is known to be optimal for it, and arbitrary sets are not. The term to look up is *canonical coin systems*.

</Reveal>

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Keep the lesson closed. Write down the rule, three counterexample attempts, the proof's name, the invariant, and the complexity **before** coding.

1. **Cover a recording.** Clips `[start, end]` of a match recording are given, possibly overlapping. Use the fewest clips to cover `[0, T]`, or return -1. Test: a gap in the middle, one clip that covers everything, clips that only touch at their ends.
2. **Change at the lemonade stand.** Customers pay in order with a 5, 10 or 20; a lemonade costs 5 and you start with no change. Can you give everyone correct change? Test: the first customer pays 10; a 20 when you hold one 10 and one 5; a 20 when you hold three 5s.
3. **Flip k signs.** An array of integers and a number `k`: flip the sign of exactly `k` elements (the same element may be flipped more than once) to make the sum as large as possible. Test: no negatives and odd `k`; more negatives than `k`; a zero in the array.

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**Cover a recording** is Chapter 5 in disguise. Sort the clips by start. The clips that start at or before your current covered point are "the current window"; scanning them, track the farthest end: that is where the next window ends. Count a clip each time you must move past the current end; return -1 if the farthest end does not grow. Proof: stays ahead, exactly as in Jump Game II. O(n log n).

**Lemonade change** is an exchange argument. For a 20, give a 10 + 5 when you can, rather than 5 + 5 + 5: a 10 can only ever help with a 20, while a 5 helps with both 10s and 20s, so keeping 5s never hurts. Two counters, O(n).

**Flip k signs** is a forced move, then a cleanup. Flipping the most negative value gains the most, so sort and flip negatives from smallest upward while `k` lasts. If `k` is still odd afterwards, flip the element with the smallest absolute value once (a zero absorbs any leftover for free). O(n log n).

Now explain why a slightly wrong version fails one of your tests: forgetting the gap check, paying a 20 with three 5s first, flipping the wrong element at the end. That counterexample is stronger evidence of understanding than a memorised rule.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The proof that makes it safe |
|---|---|---|
| Largest sum of a contiguous stretch | `run = max(x, run + x)`, `best = max(best, run)`, both from `nums[0]` | Exchange: a negative prefix only lowers what follows |
| Largest product of a contiguous stretch | Carry `hi` and `lo`; candidates `x`, `hi·x`, `lo·x` from the old values | Keep every survivor: extremes stay extreme under multiplication |
| Start a circular trip with an empty tank | `total` decides whether; restart after each deficit decides where | Lowest point of the running total; failed stretches can't contain a start |
| Can you reach the end? | `far = max(far, i + nums[i])`; fail when `i > far` | Stays ahead: reachable stones form one block `0..far` |
| Fewest jumps to the end | Windows: scan, update `far`, jump when `i == end`; loop to n - 2 | Stays ahead: no k-jump path passes the k-th window's end |
| Most pieces, each letter in one piece | `last[c]`; `end = max(end, last[c])`; cut when `i == end` | Every legal cut is taken the moment it appears |
| Groups of consecutive cards | Sorted counts; the smallest card starts a group | Forced move: the smallest card has one possible group |
| Unlimited trades, one share at a time | Sum of positive day-to-day changes | Exchange: any trade splits into its rising steps |
| Match items to needs, maximise matches | Sort both; smallest item that fits the smallest need | Exchange: swap rolls, nobody loses |
| Pairs under a weight limit | Sort; heaviest leaves, with the lightest if they fit | Exchange: swap partners, both boats still fit |
| Neighbour rules in a line | Left pass, right pass, keep the max | Each pass is a lower bound; the max meets both |
| Wildcards that may be (, ) or nothing | Range `lo..hi` of open counts; clamp `lo`; fail on `hi < 0` | The range is exactly the set of possible counts |
| Build a target from position-wise maxima | Discard triples that overshoot; check each position is hit | Maxima never go down; safe triples never hurt |
| Arbitrary coins, 0/1 items, weights | **Not greedy:** DP over amounts or capacities | The hunt finds a counterexample |

**Greedy does not mean O(1) space or no sorting.** Kadane, the jump games and Gas Station run in O(n) with O(1) extra space; the sorting side quests cost O(n log n); Hand of Straights needs an O(n) map; Candy needs an O(n) array. Count what you build.

## Five common bugs

1. **The empty stretch.** Starting Kadane's `run` and `best` at 0 returns 0 on an all-negative array. Start at `nums[0]`.
2. **Overwriting before reading.** In Maximum Product, `lo` must use the *old* `hi`. Compute `hi × x` and `lo × x` first.
3. **Half a proof.** Gas Station without the total check returns a start for a ring that cannot be finished.
4. **Jumping from the last stone.** Jump Game II's loop runs to `n - 2`; looping to `n - 1` counts an extra jump.
5. **Trusting a rule nobody tried to break.** Largest-coin-first, best-ratio-first, longest-leap-first. Three tiny inputs before any code.

<h2 id="revision">Revision</h2>

**How to recognise it.** An optimisation or "can you?" question where each step has a natural best-looking choice, and the brute force is exponential or quadratic. Before committing, hunt for a counterexample on three tiny inputs (degenerate, trap, tie). Arbitrary coins, 0/1 items and weights are the usual traps.

**Core algorithm.** Name the greedy choice. Name the proof: stays ahead, exchange, or forced move. Make one pass (after one sort if the proof needs it), carrying one or two summary values: a running total, a farthest reach, a tank, a range of possible counts. Say what is settled and what each variable means when the loop ends.

**Common mistakes.**

- Starting a running value at 0 when the empty answer is not allowed.
- Updating one summary from another that is already overwritten (`hi` and `lo`).
- Using the answer-so-far where the final summary is needed (`run` instead of `best`; `start` without `total`).
- Looping one step too far (Jump Game II counts a jump from the last stone).
- A tempting rule never tested on a trap input.

**Complexity.** One pass with a few variables is O(n) time and O(1) space. Sorting-based greedies are O(n log n). Counting variants (Hand of Straights) add an O(n) map; Candy adds an O(n) array.

**Three representative problems.**

1. [Maximum Subarray](https://leetcode.com/problems/maximum-subarray/): exchange argument; restart when the run is negative.
2. [Jump Game II](https://leetcode.com/problems/jump-game-ii/): stays ahead; count the edges of levels.
3. [Partition Labels](https://leetcode.com/problems/partition-labels/): forced cuts; end = max(end, last[c]).
