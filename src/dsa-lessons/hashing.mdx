<h2 id="prologue">Prologue · Look it up, don't search for it</h2>

Suppose you must answer one question about 10,000 values: does any value appear twice?

The obvious way compares every value with every other value. That is `n(n − 1) / 2` comparisons, almost 50 million for 10,000 values.

A **hash set** answers "have I seen this value?" in **O(1) expected time**. Read each value once, ask the set, then add it. That is 10,000 steps instead of 50 million.

This whole lesson is that one move, used in different ways.

### The two rules that make it work

A hash table turns a key into a number, its **hash code**, and uses that number to pick one **bucket** out of a fixed number of buckets. Two rules matter:

1. **Equal keys get equal hash codes.** If `a.equals(b)`, then `a.hashCode() == b.hashCode()`. So a twin of `x` can only ever be in `x`'s bucket.
2. **Different keys may share a bucket.** That is a *collision*, and it is legal. `equals` then compares the few keys inside that one bucket.

So "have I seen `x`?" means: compute `x`'s bucket, open that one bucket, compare with the handful of keys there. When keys spread evenly and the table grows with the data, a bucket holds about one key on average. That is why the cost is **O(1) expected**.

### Three questions before every move

1. **What is settled?** Everything already stored. A stored key can always be found again, as long as nobody changes it after storing it (Chapter 3).
2. **Why is this move safe?** Equal keys share a bucket, so looking in one bucket is as good as looking everywhere. And you ask before you store, so a value never finds itself.
3. **When do I stop?** When the question is answered (the first repeat, the partner found) or when the last item has been stored.

### How Java's HashMap really works

Interviewers rarely ask you to build a hash table. They often ask *why* a lookup is O(1) and when it is not. Here is Java's `HashMap` (a `HashSet` is a `HashMap` with dummy values), at interview depth:

1. **The hash code.** `hashCode()` turns the key into an `int`. For an `Integer` it is the value itself. For a `String` it is `s[0]·31^(n−1) + s[1]·31^(n−2) + … + s[n−1]`, computed with `int` overflow.
2. **The bucket.** `HashMap` mixes the high bits into the low ones (`h ^ (h >>> 16)`) and keeps the low bits: `hash & (capacity − 1)`. Capacity is always a power of two, so this is a fast remainder. For an `Integer` key from 0 to 65,535 the bucket is exactly `value % capacity`, so the toy table above is the real thing.
3. **Collisions, by chaining.** Different keys can share a bucket (`"Aa"` and `"BB"` both hash to 2112). Each bucket holds a short linked list of entries. A lookup walks it, comparing the stored hash first and then calling `equals`.
4. **Load factor and resizing.** The load factor is entries ÷ buckets. Java starts with 16 buckets and a limit of 0.75, so the 13th entry (past 16 × 0.75 = 12) **doubles the table to 32 buckets and re-files every entry**. Each entry either stays in bucket `i` or moves to `i + 16`. One resize is O(n), but because the table doubles, all the re-filing over a map's life adds up to roughly 2n moves: **amortised O(1) per insert**.
5. **Expected versus worst.** With well-spread hash codes the average chain has at most about 0.75 entries, so `add`, `contains` and `remove` are **O(1) expected**. If every key lands in one bucket, each lookup walks a chain of n: **O(n) each, O(n²) to build the set**. Since Java 8, a bucket whose chain grows past 8 entries is converted into a small red-black tree (when the table has at least 64 buckets; a smaller table just resizes instead). For keys that implement `Comparable`, such as `String` and `Integer`, that worst case becomes **O(log n)**.

Say it in the room as: **"O(1) expected per operation, O(n) worst case, O(log n) in Java 8+ when a crowded bucket is treeified and the keys are comparable."**

### When this pattern fires

The giveaway is almost always the same: **an O(n²) solution whose inner loop is searching for one specific thing.** If you can say what the inner loop is looking for, a hash table can usually look it up instead:

- **"Have I seen this before?"** Duplicates, repeated states, cycles, visited corners. Comparing each item with every earlier one is O(n²); a set makes it **O(n) expected**.
- **"Is its partner here?"** A pair with a target sum, a complement, a mirror image. The inner loop of a pair search becomes one lookup.
- **"How many of each?"** Frequencies, anagrams, the most common values.
- **"Which ones belong together?"** Grouping by a key computed from each item.
- **"Is `x` present?", asked many times** while you build something else: consecutive runs, valid boards, word lists.

Recognition is the hard part. Before coding, say one sentence out loud: *"My inner loop is searching for ___; I can look that up."*

The price, every time: **O(n) extra memory, no ordering, and a worst case the average hides.** The "When hashing is the wrong tool" section near the end covers when that price is too high.

<h2 id="contains-duplicate">Chapter 1 · Contains Duplicate</h2>

### Problem

Given an integer array `nums`, return `true` if any value appears at least twice, `false` if every value is distinct.

`[1, 2, 3, 1]` returns `true`. `[1, 2, 3, 4]` returns `false`.

### How to recognise it

- The question is "has anything repeated?" or "have I seen this before?".
- The brute force compares every item with every earlier item.
- You only need a yes or no, not positions.

### Brute force

For each index `i`, scan every earlier index `j` for an equal value. That is `n(n − 1) / 2` comparisons: 49,995,000 for 10,000 values. **O(n²) time, O(1) space.** Slow because every item is compared with items it can never match, and the same question ("is `x` among the earlier values?") is answered by scanning instead of looking up.

### Intuition

Read the values once. Keep a set of the values read so far. For each new value, ask the set whether it is already there. If yes, you found a repeat and can stop. If no, add it.

Java's `Set.add` does both jobs in one call: it **returns `false` when an equal element is already present**, and leaves the set unchanged.

### Dry run

<DryRun title="Contains Duplicate" frames={containsDuplicateFrames([4, 1, 7, 3, 1, 9])} predict />

### Algorithm

1. Create an empty set `seen`.
2. For each value `x` in `nums`: if `seen.add(x)` returns `false`, return `true`.
3. If the loop ends, return `false`.

### Java solution

<HintLadder hints={hints.containsDuplicate}>

```java id=containsDuplicate
public boolean containsDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int x : nums)
        if (!seen.add(x)) return true;               // add says false: x was already on file
    return false;
}

// Low-memory alternative: sort in place, then any repeat sits beside its twin. Reorders nums.
public boolean containsDuplicateSorted(int[] nums) {
    Arrays.sort(nums);
    for (int i = 1; i < nums.length; i++)
        if (nums[i] == nums[i - 1]) return true;
    return false;
}
```

**Set: O(n) expected time, O(n) extra space. Sorted: O(n log n) time, no hash table.**

</HintLadder>

### Why it works

- **Settled:** before handling index `i`, the set holds exactly the distinct values among `nums[0..i − 1]`, and none of them has repeated. Otherwise you would already have returned.
- **Why the move is safe:** equal values have equal hash codes, so a repeat of `x` can only be in `x`'s bucket. Searching that one bucket is the same as searching everything stored so far.
- **When we stop:** at the first `add` that returns `false`, or when the array ends.

### Complexity

- **Time:** O(n) expected. One expected-O(1) `add` per value.
- **Space:** O(n). In the worst case every value is distinct and all are stored.
- Sorting version: O(n log n) time, no hash table.

### Edge cases and mistakes

- Empty array and one-element array: no repeat, return `false`.
- All values equal: `true` at index 1.
- The classic bug is the size-comparison one-liner on an `int[]`.

```java fragment
return nums.length != new HashSet<>(Arrays.asList(nums)).size();   // BUG: a set holding ONE int[]
```

`Arrays.asList` on an `int[]` cannot box the ints. It makes a list with one element, the array itself. The set always has size 1, so `[1, 2]` "contains a duplicate". Box first: `Arrays.stream(nums).boxed().collect(Collectors.toSet())`.

The size-comparison idea itself is fine (set size versus array length). It always reads the whole array, though, while the `add` check stops at the first repeat.

### Practice

<Reveal q="The set costs O(n) extra memory. Can you answer without it?">

Yes: **sort, then compare neighbours.** After sorting, any repeat sits right beside its twin. That is O(n log n) time with little or no extra memory, but it reorders the caller's array. Interviewers like hearing both: the set for speed, sorting when memory is tight or the data is already sorted. Both versions are in the solution above.

</Reveal>

<Reveal q="Why not compare the set's size with the array's length at the end?">

That works, but it always reads the whole array, while the `add` check stops at the first repeat. And in Java there is a trap in the one-liner: see the bug above.

</Reveal>

<h2 id="two-sum">Chapter 2 · Two Sum</h2>

### Problem

Given an array `nums` and an integer `target`, return the **indices** of the two numbers that add up to `target`. Exactly one solution exists, and you may not use the same element twice.

`nums = [2, 7, 11, 15]`, `target = 9` returns `[0, 1]`.

### How to recognise it

- A pair of items must satisfy a condition (sum, difference, mirror).
- The array is **unsorted**, and you must report the **original positions**, so sorting would lose them.
- The inner loop of the pair search is looking for one exact value.

### Brute force

Try every pair `(i, j)` and check `nums[i] + nums[j] == target`. **O(n²) time, O(1) space.** For each `x` the inner loop is really asking one question: "is `target − x` somewhere else in the array?". Scanning to answer it is the waste.

### Intuition

Holding `x`, you do not need *any* other number. You need exactly `target − x`. So keep a map from each value you have read to its index, and at each position:

1. **Ask:** is `target − x` in the map? If yes, at index `j`, the answer is `[j, i]`.
2. **Store:** otherwise record `x → i`, so later values can find it.

**Ask always goes first.** The map then holds only *earlier* positions, so a match can never be the current value pairing with itself.

### Algorithm

1. Create an empty map `indexOf` (value to index).
2. For each index `i`, with `x = nums[i]`: look up `target − x`.
3. If it is present at index `j`, return `[j, i]`.
4. Otherwise store `x → i`.
5. If the loop ends, return an empty array (LeetCode guarantees this never happens).

### Java solution

<HintLadder hints={hints.twoSum}>

```java id=twoSum
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> indexOf = new HashMap<>();     // value -> an index where it was filed
    for (int i = 0; i < nums.length; i++) {
        Integer j = indexOf.get(target - nums[i]);       // Ask first: has the partner passed by?
        if (j != null) return new int[]{j, i};
        indexOf.put(nums[i], i);                         // ...then File
    }
    return new int[0];                                   // LeetCode guarantees a pair, so never reached there
}
```

**O(n) expected time, O(n) extra space.** LeetCode bounds values and target to ±10⁹, so `target − nums[i]` stays within ±2 × 10⁹, inside `int`.

</HintLadder>

### Why it works

- **Settled:** before handling index `i`, the map holds every value among `nums[0..i − 1]`, each with an index where it occurs, and no valid pair lies entirely inside `nums[0..i − 1]`.
- **Why the move is safe:** take any valid pair `j < i`. When the scan reaches `i`, the value at `j` is already stored (perhaps under a later index with the same value, which is just as good), so the lookup finds a partner.
- **When we stop:** at the first position that completes any pair.

### Complexity

- **Time:** O(n) expected: one lookup and at most one insert per element.
- **Space:** O(n) for the map.

### Edge cases and mistakes

- Duplicate values: `[3, 3]`, target 6. The map keeps one index per value, but the second 3 asks before storing, so it finds the first.
- `target − x == x`, as in `[3, 2, 4]` with target 6. Ask-before-store keeps this correct.
- Negative numbers and zero work unchanged.

The classic bug: storing before asking.

```java fragment
indexOf.put(nums[i], i);                             // BUG: stored first...
Integer j = indexOf.get(target - nums[i]);           // ...so x can find itself
if (j != null) return new int[]{j, i};               // [3, 2, 4], target 6 -> [0, 0]
```

On `[3, 2, 4]` with target 6, index 0 stores `3 → 0`, asks for `6 − 3 = 3`, and returns `[0, 0]`: one element used twice.

### Practice

<Trace title="Ask, then store" steps={twoSum} takeaway="Remember: look up target − x first, then store x → i. The map holds only earlier positions, so nothing pairs with itself, duplicates included." />

<Reveal q="Two passes (store everything first, then look up): would that work?">

Yes, with one extra check: the partner's index must differ from `i`. With `[3, 2, 4]` and target 6, the first pass stores `3 → 0`, and at `i = 0` the lookup for 3 finds index 0, itself, so you must skip it. Duplicates still work, because the later `3` overwrites the earlier index. One pass is shorter, needs no special case, and can stop early.

</Reveal>

<Reveal q="What if the numbers were sorted, and memory was scarce?">

Then it is Two Sum II, and <a href={`${BASE}dsa/lessons/two-pointers/`}>two pointers</a> win: one marker at each end, move the left one when the sum is too small and the right one when it is too big. O(n) time, **O(1)** space. The map spends O(n) memory to buy freedom from sorted order. Do not pay for what the input already gives you.

</Reveal>

<h2 id="custom-keys">Chapter 3 · Path Crossing, and keys that break</h2>

### Problem

A path is a string of moves `N`, `S`, `E`, `W`, each moving one unit. You start at `(0, 0)`. Return `true` if the path ever visits the same point twice (the start counts as visited).

`"NES"` returns `false`. `"NESW"` returns `true` (it ends back at the start).

### How to recognise it

- "Visited before" again, but the thing being remembered is a **pair** `(x, y)`.
- You must build a key for the set yourself. Plain `int` sets cannot hold two numbers.

### Brute force

Keep a list of all corners visited. After each move, scan the whole list for the new corner. **O(n²) time, O(n) space.** The scan is the "seen before?" question again.

### Intuition

The algorithm is Chapter 1 again: store the start, then store every corner, and stop at the first `add` that returns `false`. Everything interesting is in the **key**.

**The contract.** Java's `Object.hashCode` documentation says: **if two objects are equal according to `equals`, they must have the same hash code.** Unequal objects may share a hash code. That is only a collision and costs a comparison. And `hashCode` must not change while the fields that `equals` uses do not change.

Here is a class that looks right and is not:

```java fragment
class Point {                                        // BROKEN as a key
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
    // no hashCode(): the one inherited from Object comes from identity,
    // so two equal Points almost always get different hash codes
}
```

Two `new Point(0, 0)` objects are equal, but their inherited hash codes come from object identity. They land in different buckets, `equals` is never called, and the set holds both. Worse, now and then two identity hashes *do* share a bucket and the set finds the twin, so the bug comes and goes. (The mirror-image mistake, `hashCode` without `equals`, fails every time: equal keys share a bucket, and the inherited `equals` still compares identity.)

### Two more ways a key lies

**A key that changes after it is stored.** Put an `ArrayList` `[1, 2]` into a `HashSet`, then call `list.add(3)` on that same list. The set stored it under the hash of `[1, 2]`, which is 994 (bucket 2 of 16). The list now hashes to 30817 (bucket 1). `set.contains(list)` looks in bucket 1 and finds nothing. `set.contains(List.of(1, 2))` looks in bucket 2, finds the entry, and `equals` says no. The entry is stranded. **Never mutate a key while it is stored.** Remove it, change it, add it back, or use keys that cannot change.

```java fragment
Set<List<Integer>> set = new HashSet<>();
List<Integer> list = new ArrayList<>(List.of(1, 2));
set.add(list);
list.add(3);                                         // the key's hash changes from 994 to 30817
set.contains(list);                                  // false: wrong bucket
set.contains(List.of(1, 2));                         // false: right bucket, but equals says no
```

**`==` on boxed numbers.** A `Map<Integer, Integer>` hands back `Integer` objects, and `==` on two objects compares references. Java must reuse cached objects for values from −128 to 127, so `Integer a = 127, b = 127; a == b` is `true`. With default JVM settings, `Integer c = 1000, d = 1000; c == d` is `false`. Code that compares `map.get(x) == map.get(y)` passes every small test and fails in production. **Compare boxed values with `.equals`, or unbox to `int` first.** (Side quest 1 has a famous one-liner that falls into exactly this.)

### Building a key that tells the truth

- **A `record`.** `record Point(int x, int y)` generates `equals` and `hashCode` from both components. This is the cleanest answer in Java 16+.
- **By hand.** Override both, from the same final fields. `31 * x + y` is a fine hash: collisions such as (0, 31) and (1, 0) are legal and cost only a comparison.
- **A string with a separator.** `x + "," + y` works, because no digit or minus sign is a comma. Without the separator, (1, 23) and (12, 3) both become `"123"`.
- **One `long`.** `((long) x << 32) | (y & 0xffffffffL)` packs both coordinates into 64 bits with no collisions at all.

### Algorithm

1. Define a key type with matching `equals` and `hashCode` (a record is enough).
2. Create a set and add the start `(0, 0)`.
3. For each move, update `x` or `y`.
4. If `add(new Point(x, y))` returns `false`, return `true`.
5. After the last move, return `false`.

### Java solution

<HintLadder hints={hints.pathCrossing}>

```java id=pathCrossing
record Point(int x, int y) {}                        // a record writes equals AND hashCode from x and y

public boolean isPathCrossing(String path) {
    Set<Point> visited = new HashSet<>();
    int x = 0, y = 0;
    visited.add(new Point(0, 0));                    // the start counts as visited
    for (char move : path.toCharArray()) {
        if (move == 'N') y++;
        else if (move == 'S') y--;
        else if (move == 'E') x++;
        else x--;                                    // 'W'
        if (!visited.add(new Point(x, y))) return true;   // this corner was already on file
    }
    return false;
}
```

**O(n) expected time, O(n) extra space** for n moves.

</HintLadder>

<Reveal q="No records allowed (an older Java). Write the key by hand.">

Both methods, from the same final fields, plus the packed-`long` key, which needs no class at all:

```java id=pathCrossingManual
static final class Corner {
    private final int x, y;                          // final: a filed key must never change
    Corner(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Corner)) return false;
        Corner c = (Corner) o;
        return x == c.x && y == c.y;
    }
    @Override public int hashCode() { return 31 * x + y; }   // the same fields as equals
}

public boolean isPathCrossing(String path) {
    Set<Corner> visited = new HashSet<>();
    int x = 0, y = 0;
    visited.add(new Corner(0, 0));
    for (char move : path.toCharArray()) {
        if (move == 'N') y++; else if (move == 'S') y--; else if (move == 'E') x++; else x--;
        if (!visited.add(new Corner(x, y))) return true;
    }
    return false;
}

static long pack(int x, int y) {                     // a collision-free key for any two ints
    return ((long) x << 32) | (y & 0xffffffffL);
}
```

The mask matters: without `& 0xffffffffL`, a negative `y` is sign-extended to 64 bits and wipes out `x`'s half.

</Reveal>

### Why it works

- **Settled:** the set holds every corner visited so far, each exactly once, and no stored key ever changes.
- **Why the move is safe:** a record's `equals` and `hashCode` are both computed from `x` and `y`, so equal corners always get equal hash codes and land in the same bucket, where `equals` recognises them.
- **When we stop:** at the first corner that is already in the set, or after the last move.

### Complexity

- **Time:** O(n) expected for n moves.
- **Space:** O(n) for up to n + 1 corners.

### Edge cases and mistakes

- Empty path: only the start exists, so `false`.
- The start must be stored first, or `"NESW"` is missed.
- A string key with no separator.

```java fragment
if (!visited.add(x + "" + y)) return true;           // BUG: (1, 11) and (11, 1) are both "111"
```

On the 32-move route E, then N eleven times, then E ten times, then S ten times, the path never repeats a corner, but (1, 11) and (11, 1) both become `"111"`, and the method reports a crossing.

<h2 id="valid-anagram">Chapter 4 · Valid Anagram</h2>

### Problem

Given two strings `s` and `t`, return `true` if `t` is an anagram of `s`: the same letters, each used the same number of times, in any order.

`s = "anagram"`, `t = "nagaram"` returns `true`. `s = "rat"`, `t = "car"` returns `false`.

### How to recognise it

- "Same letters in any order", "rearrangement", "permutation of".
- Order is irrelevant, only **how many of each** matters.
- The alphabet is small and fixed (26 lowercase letters), so a plain array can be the map.

### Brute force

Two ways. Take each letter of `s` and search for an unused match in `t`, crossing it off: **O(n²)**. Or sort both strings and compare them: **O(n log n)**, which is fine but not optimal. Both ignore that the only thing that matters is a count per letter.

### Intuition

Two strings are anagrams exactly when every letter appears the same number of times in both. So **count**.

With only lowercase `a` to `z`, the counter does not need a hash table at all. An `int[26]` indexed by `c − 'a'` is a map with 26 fixed keys: no hashing, no boxing, one array access per letter.

Add 1 for each letter of `s`, subtract 1 for each letter of `t`, and check that all 26 counts end at zero. **Check the lengths first.** Unequal lengths can never be anagrams, and equal lengths are what let one loop walk both strings.

### Algorithm

1. If `s.length() != t.length()`, return `false`.
2. Create `count = new int[26]`.
3. For each index `i`: `count[s[i] − 'a']++` and `count[t[i] − 'a']--`.
4. If any count is not zero, return `false`. Otherwise return `true`.

### Java solution

<HintLadder hints={hints.anagram}>

```java id=isAnagram
public boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;      // also what lets one loop cover both strings
    int[] count = new int[26];                       // count[c - 'a']: a map with 26 fixed keys
    for (int i = 0; i < s.length(); i++) {
        count[s.charAt(i) - 'a']++;
        count[t.charAt(i) - 'a']--;
    }
    for (int c : count) if (c != 0) return false;
    return true;
}

// Follow-up: any Unicode text. Count code points in a map instead.
public boolean isAnagramUnicode(String s, String t) {
    Map<Integer, Integer> count = new HashMap<>();
    s.codePoints().forEach(cp -> count.merge(cp, 1, Integer::sum));
    t.codePoints().forEach(cp -> count.merge(cp, -1, Integer::sum));
    for (int c : count.values()) if (c != 0) return false;
    return true;
}
```

**O(n) time, O(1) extra space** for the 26 counts; the Unicode version is O(n) expected time and O(k) space for k distinct characters. Sorting both strings and comparing also works, in O(n log n).

</HintLadder>

### Why it works

- **Settled:** after processing index `i`, `count[c]` equals (copies of `c` in `s[0..i]`) minus (copies of `c` in `t[0..i]`).
- **Why the move is safe:** a count array is the multiset of letters with positions thrown away. Two strings are anagrams exactly when their multisets are equal, and `+s − t` is zero everywhere exactly then.
- **When we stop:** after the loop, when all 26 counts are checked.

### Complexity

- **Time:** O(n): one pass over both strings, plus 26 checks.
- **Space:** O(1): the array has 26 slots whatever the input size. The Unicode version is O(k) for k distinct characters.

### Edge cases and mistakes

- Different lengths: return `false` immediately.
- Empty strings are anagrams of each other.
- Repeated letters: `"aab"` versus `"abb"` differ even though they share the same set of letters. Counts catch it; a set would not.

The classic bug: dropping the length check while keeping the single loop over `s`. With `s = "ab"` and `t = "abx"`, the loop never reaches the `x`, every count is 0, and the method returns `true`.

### Map idioms worth knowing cold

When the keys are not 26 letters, the counter is a `HashMap`. These calls keep the code short and the intent obvious:

| You want | Write | What it does |
|---|---|---|
| Count `x` | `count.merge(x, 1, Integer::sum)` | Puts 1 if `x` is absent, else adds 1 |
| Read with a default | `count.getOrDefault(x, 0)` | Never inserts anything |
| A list per key | `groups.computeIfAbsent(k, key -> new ArrayList<>()).add(v)` | Creates the list once, returns it every time |
| Remember only the first | `first.putIfAbsent(x, i)` | Returns the previous value, or `null` if `x` was new |
| Decrement, drop at zero | `count.computeIfPresent(x, (key, c) -> c == 1 ? null : c - 1)` | Returning `null` removes the entry |

One trap: `merge` removes an entry only when the function returns `null`. `count.merge(x, -1, Integer::sum)` leaves a count of 0 in the map, so `count.size()` no longer means "letters still owed".

### Practice

<Trace title="Counts up, counts down" steps={anagram} takeaway="Remember: lengths first, then +1 for s and −1 for t; anagrams exactly when every count is 0. A big or unknown alphabet swaps the array for a map." />

</Reveal>

<h2 id="group-anagrams">Chapter 5 · Group Anagrams</h2>

### Problem

Given an array of strings, group the anagrams together. The groups and the order inside each group can be returned in any order.

`["eat","tea","tan","ate","nat","bat"]` returns `[["eat","tea","ate"],["tan","nat"],["bat"]]`.

### How to recognise it

- "Group", "bucket", "which items are equivalent?".
- Two items belong together when they have the same **canonical form** (something computable from each item alone).
- Comparing every pair to decide "same group?" is the O(n²) you want to avoid.

### Brute force

For each word, compare it with every word already placed in a group (an anagram check each time). With n words of length k, that is O(n² · k) at best. The real problem: you are comparing words with words, when each word could compute a **label** by itself and let the labels do the matching.

### Intuition

This is the idea that makes hashing a *pattern* rather than a data structure: **map every item to a canonical key, and let the map do the grouping.** The key must satisfy one rule:

> `key(a).equals(key(b))` **exactly when** `a` and `b` belong in the same group.

Too fine, and twins never meet (keying by the spelling: `"eat"` and `"tea"` stay apart). Too coarse, and strangers share a group (the sum of character codes: `"ad"` and `"bc"` both total 197). For anagrams there are two exact keys:

- **Sorted letters.** `"tea"` becomes `"aet"`. Every rearrangement sorts to the same string; different letter multisets sort to different strings. O(k log k) per word of length k.
- **The 26 counts, with a separator after each.** `"tea"` becomes `"1#0#0#0#1#…"`. O(k + 26) per word. **The separator is not decoration.** Counts can have two digits: a word with a = 1 and b = 12 and a word with a = 11 and b = 2 would both write `"112000…"` without it. With it, `"1#12#…"` and `"11#2#…"` stay apart. (`Arrays.toString(count)` also works; its `", "` is a separator.)

### Algorithm

1. Create a map from key to list of words.
2. For each word, compute its key (sort its letters).
3. `computeIfAbsent(key, new list)` and add the word.
4. Return the map's values.

### Java solution

<HintLadder hints={hints.group}>

```java id=groupAnagrams
public List<List<String>> groupAnagrams(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        char[] letters = s.toCharArray();
        Arrays.sort(letters);
        String key = new String(letters);            // "eat", "tea", "ate" -> "aet"
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}

// Count key: O(k + 26) per word instead of O(k log k).
public List<List<String>> groupAnagramsByCount(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        int[] count = new int[26];
        for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
        StringBuilder key = new StringBuilder();
        for (int c : count) key.append(c).append('#');   // '#' ends each count: 1#12# vs 11#2#
        groups.computeIfAbsent(key.toString(), k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}
```

**Sorted key: O(n · k log k) time. Count key: O(n · (k + 26)) time.** Both use O(n · k) space for the groups and keys. LeetCode allows the empty string; it sorts to `""` (or counts to 26 zeros), and all empty strings share one group.

</HintLadder>

### Why it works

- **Settled:** after handling the first `i` words, every one of them sits in exactly one list, under its own key, and each list holds every word so far with that key.
- **Why the move is safe:** the map gathers items whose keys are equal, and the keys are equal exactly when the items are anagrams. So each list is one complete group, no more, no less.
- **When we stop:** when the last word is filed.

### Complexity

- **Sorted key:** O(n · k log k) time. **Count key:** O(n · (k + 26)) time.
- **Space:** O(n · k) for the stored words and keys.

### Edge cases and mistakes

- The empty string is allowed. It sorts to `""` (or counts to 26 zeros), and all empty strings share one group.
- A single word is its own group.
- The classic bug is a count key with no separators.

```java fragment
for (int c : count) key.append(c);                   // BUG: a=1,b=12 and a=11,b=2 both give "112000..."
```

`"a"` followed by twelve `"b"`s and eleven `"a"`s followed by `"bb"` are not anagrams, yet they land in the same group.

<h2 id="longest-consecutive">Chapter 6 · Longest Consecutive Sequence</h2>

### Problem

Given an unsorted array of integers, return the length of the longest run of consecutive values (each one more than the last). It must run in O(n).

`[100, 4, 200, 1, 3, 2]` returns `4`, from the run `1, 2, 3, 4`.

### How to recognise it

- "Consecutive" values in an **unsorted** array, with an O(n) requirement.
- You keep asking "is `x + 1` (or `x − 1`) present?".
- Sorting gives O(n log n), which the problem statement rules out.

### Brute force

For every number `x`, walk `x + 1, x + 2, …` using lookups until the run breaks. Correct, but a number in the middle of a run is walked once from its own position and again from every smaller number in the run. On the numbers 1 to n that is about n²/2 steps: **O(n²)**. Sorting first is O(n log n) and works, but is not O(n).

### Intuition

The waste is walking the same street from every house on it. A run has exactly **one honest starting point**: its smallest number, the one whose predecessor `x − 1` is **not** in the set.

File every number in a set. Then, for each number `x` in the set:

- **If `x − 1` is in the set, skip `x`.** It is in the middle of a run, and the run's real start will walk past it.
- **If `x − 1` is absent, `x` starts a run.** Walk `x + 1, x + 2, …` while they are present. When the walk stops at `cur`, the run is `x..cur`, of length `cur − x + 1`.

Say the state at loop exit out loud: **when the inner `while` stops, `cur` is the last number of the run, `cur + 1` is absent, and the length is `cur − x + 1`.** That sentence is the difference between a correct answer and an off-by-one.

<Figure caption="The same numbers drawn in order (the set itself has no order). Only 1, 100 and 200 lack a predecessor, so only they start walks. The walk from 1 steps on 2, 3 and 4 exactly once; the 4 is never a start, because 3 is present.">
  <ArrayStrip values={[1, 2, 3, 4, 100, 200]} indices={false} tones={{ 0: 'hot', 1: 'done', 2: 'done', 3: 'done', 4: 'hot', 5: 'hot' }} pointers={[{ at: 0, label: 'start (0 absent)' }, { at: 4, label: 'start', tone: 'blue' }, { at: 5, label: 'start', tone: 'blue' }]} regions={[{ from: 0, to: 3, label: 'run of 4', tone: 'gold' }]} />
</Figure>

### Dry run

The set is walked in the order the numbers arrived, because a Java `HashSet` has no useful order. Notice that the answer does not depend on it.

<DryRun title="Longest Consecutive Sequence" frames={longestConsecutiveFrames([100, 4, 200, 1, 3, 2])} predict />

### Algorithm

1. Put every number in a `HashSet`.
2. For each `x` in the set: if `x − 1` is in the set, skip it.
3. Otherwise set `cur = x` and, while `cur + 1` is in the set, increase `cur`.
4. Update `best = max(best, cur − x + 1)`.
5. Return `best`.

### Java solution

<HintLadder hints={hints.streak}>

```java id=longestConsecutive
public int longestConsecutive(int[] nums) {
    Set<Integer> set = new HashSet<>();
    for (int x : nums) set.add(x);
    int best = 0;
    for (int x : set) {                              // the set, not nums: each value once
        if (set.contains(x - 1)) continue;           // x is mid-run; its start will walk past it
        int cur = x;
        while (set.contains(cur + 1)) cur++;         // walk the run from its start
        best = Math.max(best, cur - x + 1);          // here cur is the run's last number
    }
    return best;
}
```

**O(n) expected time, O(n) extra space.** LeetCode bounds values to ±10⁹, so `x − 1` and `cur + 1` never overflow; with the full `int` range, `Integer.MAX_VALUE + 1` wraps to `Integer.MIN_VALUE` and could fake a successor, so walk in `long` there.

</HintLadder>

### Why it works

- **Settled:** after the outer loop handles some numbers, `best` is the length of the longest run that starts among them, and no run has been walked twice.
- **Why the move is safe:** every number belongs to exactly one maximal run, and every run has exactly one start, its smallest number. Only starts walk, so every number is stepped on by exactly one walk.
- **When we stop:** when every number in the set has been either skipped or walked from.

**Why it is O(n), not O(n²):** count the lookups. There is one "is `x − 1` here?" per distinct number. Summed over all walks, there is one "is `cur + 1` here?" per distinct number (each successful step lands on a new number; each walk ends with one failed lookup, charged to its last number). That is **exactly 2m lookups for m distinct numbers**, plus n insertions: O(n) expected time.

### Complexity

- **Time:** O(n) expected: n insertions plus at most 2m lookups.
- **Space:** O(n) for the set.

### Edge cases and mistakes

- Empty array: `0`.
- Duplicates: `[1, 2, 2, 3]` has run length 3. Loop over the **set**, not over `nums`.
- Negative numbers and zero work unchanged.
- The classic bug: no start check.

```java fragment
for (int x : set) {                                  // BUG: every number walks
    int cur = x;
    while (set.contains(cur + 1)) cur++;
    best = Math.max(best, cur - x + 1);
}
```

The answers are right, and the time is not: on the numbers 1 to 100,000 the walks take 100,000 + 99,999 + … + 1 ≈ 5 × 10⁹ steps.

### Practice

<Trace title="Who is allowed to start walking?" steps={streak} takeaway="Remember: skip x when x − 1 is present; otherwise walk up from x. Each number is walked exactly once, so the whole pass is O(n)." />

<Reveal q="Isn't sorting simpler? O(n log n) is barely worse.">

Sorting is a fine first answer: sort, then scan, extending the current run when `a[i] == a[i − 1] + 1`, **ignoring duplicates** (`a[i] == a[i − 1]` neither extends nor breaks the run), and resetting otherwise. It uses little memory. But the problem demands O(n), and the set gets there. Say both in the interview: the sort for a quick correct baseline, the set for the requirement. A `TreeSet` also works, at O(n log n), because it iterates in order.

</Reveal>

<Reveal q="Why loop over the set, not over nums?">

Duplicates. Looping over `nums` judges each copy separately, and every copy of a run's start walks the whole run again. With n/2 copies of 1 followed by 2, 3, …, n/2, that is about n/2 walks of length n/2: O(n²) all over again. The set holds each value once.

</Reveal>

<h2 id="encode-decode">Chapter 7 · Encode and Decode Strings</h2>

### Problem

Design two methods: `encode(List<String> strs)` returns one `String`, and `decode(String str)` returns a `List<String>`, so that `decode(encode(strs))` equals `strs` for **every** list. The strings may contain any characters at all (LeetCode's version allows all 256 ASCII characters, so commas, `#`, digits and newlines included) and may be empty. The list itself may be empty. No built-in serialization. (LeetCode Premium; free on LintCode.)

`["lint", "code", "love", "you"]` can be sent as one string and decoded back to the same four strings.

### How to recognise it

- Several pieces of data must travel as **one string** and be recovered exactly.
- The pieces can contain any character, so no delimiter is safe.
- This is the same job as building a safe key: two different inputs must never produce the same string.

### Brute force

Join the strings with a delimiter such as `,` and split on it when decoding. It is O(n) and wrong: `["a,b"]` and `["a", "b"]` both become `"a,b"`. Any single delimiter can appear inside the data. Picking a rarer delimiter only makes the failure rarer, never impossible.

### Intuition

There are two real fixes:

1. **Escaping.** Mark the special characters inside the data (say `/` becomes `//` and `;` becomes `/;`) and end each string with an unescaped `;`. Correct, but every character must be scanned and rewritten on both sides.
2. **Length prefix (framing).** Write each string as **its length, a `#`, then the string itself**. The decoder reads digits up to the first `#`. A length's digits never contain `#`, so the first `#` really is the end of the header. Then it takes **exactly that many characters, without looking at what they are.** A `#` or a digit inside a string is just data.

<Figure caption="[“a#b”, “”, “c”] encodes to 3#a#b0#1#c. The decoder reads 3, takes a#b (whose # is data), reads 0 and takes nothing, reads 1 and takes c. An empty list encodes to the empty string, and a list holding one empty string to 0#, so the two stay apart.">

</Figure>

This chapter belongs in the hashing lesson for a reason. **A key, a frame and a serialised message do the same job: two different things must never produce the same string.** Chapter 3's `x + "," + y` and Chapter 5's `"1#12#…"` were frames too.

### Dry run

### Algorithm

**Encode:** for each string, append its length, then `#`, then the string.

**Decode:**

1. Set `i = 0`. `i` always points at the start of a header.
2. Find the first `#` at or after `i`. The digits between are the length `len`.
3. Take the next `len` characters after that `#` as the next string.
4. Move `i` to just after those characters. Repeat until `i` reaches the end.

### Java solution

<HintLadder hints={hints.codec}>

```java id=codec
public String encode(List<String> strs) {
    StringBuilder out = new StringBuilder();
    for (String s : strs) out.append(s.length()).append('#').append(s);   // header, then body
    return out.toString();
}

public List<String> decode(String str) {
    List<String> strs = new ArrayList<>();
    int i = 0;                                       // i always points at the start of a header
    while (i < str.length()) {
        int hash = str.indexOf('#', i);              // a length's digits never contain '#'
        int len = Integer.parseInt(str.substring(i, hash));
        strs.add(str.substring(hash + 1, hash + 1 + len));   // take len characters, whatever they are
        i = hash + 1 + len;
    }
    return strs;
}
```

**O(total characters) time for both, O(1) extra space beyond the output.** Java’s `length()` and `substring` both count UTF-16 units, so they agree with each other for any Java string, emoji included.

</HintLadder>

<Reveal q="Show me the escaping version. Why does it end each string with ; instead of putting ; between strings?">

A terminator per string keeps `[]` (encoded as the empty string) apart from `[""]` (encoded as `;`). A separator between strings would turn both into the empty string.

```java id=codecEscaped
// Escaping: '/' becomes "//", ';' becomes "/;", and an unescaped ';' ends each string.
public String encodeEscaped(List<String> strs) {
    StringBuilder out = new StringBuilder();
    for (String s : strs) {
        for (char c : s.toCharArray()) {
            if (c == '/' || c == ';') out.append('/');   // escape the two special characters
            out.append(c);
        }
        out.append(';');                             // a terminator per string
    }
    return out.toString();
}

public List<String> decodeEscaped(String str) {
    List<String> strs = new ArrayList<>();
    StringBuilder cur = new StringBuilder();
    for (int i = 0; i < str.length(); i++) {
        char c = str.charAt(i);
        if (c == '/') cur.append(str.charAt(++i));   // whatever follows an escape is data
        else if (c == ';') { strs.add(cur.toString()); cur.setLength(0); }
        else cur.append(c);
    }
    return strs;
}
```

Both are O(total length). Framing never touches the bodies, so it is simpler to get right and lets a reader skip a string it does not need. Escaping keeps the text readable. Real protocols use both: HTTP's `Content-Length` is a length prefix; CSV quoting is escaping.

</Reveal>

### Why it works

- **Settled:** after each iteration, the decoded list equals a prefix of the original list, and `i` sits exactly where the next encoded string begins.
- **Why the move is safe:** decoding keeps one promise: **at the top of the loop, `i` points at the start of a header.** That is true at `i = 0`. The header's digits end at the first `#` after `i`; the body is exactly the next `len` characters; so `i = hash + 1 + len` is the start of the next header. By induction every string is recovered exactly, whatever it contains.
- **When we stop:** when `i` reaches the end of the encoded string.

### Complexity

- **Time:** O(total characters) for both methods.
- **Space:** O(1) extra beyond the output. Java's `length()` and `substring` both count UTF-16 units, so they agree with each other for any Java string, emoji included.

### Edge cases and mistakes

- Empty list, a list holding one empty string, and strings containing `#` or digits.
- Strings of length 10 or more: the header has more than one digit.
- The classic bug: a one-digit header.

```java fragment
int len = str.charAt(i) - '0';                       // BUG: assumes every length is below 10
strs.add(str.substring(i + 2, i + 2 + len));
i += 2 + len;
```

`["hello world!"]` encodes to `"12#hello world!"`. This decoder reads a length of 1, takes `"#"`, then reads `'h' − '0'` = 56 as the next length and throws `StringIndexOutOfBoundsException`. Write the whole number, or a fixed-width header (say, always 4 characters).

<h2 id="isomorphic">Side quest 1 · Isomorphic Strings</h2>

### Problem

Can `s` be turned into `t` by replacing letters, where every occurrence of a letter becomes the same letter, and **no two different letters become the same letter**? A letter may map to itself.

`"egg"` and `"add"` returns `true`. `"foo"` and `"bar"` returns `false`.

### How to recognise it

- A **one-to-one** mapping between two sequences (letters to letters, pattern to words).
- "Each X always maps to the same Y" **and** "no two X map to the same Y".

### Brute force

For each pair of positions `(i, j)`, check that `s[i] == s[j]` exactly when `t[i] == t[j]`. That is O(n²). It is correct, because that condition is the definition, but every pair is compared.

### Intuition

One map from `s`-letters to `t`-letters checks the first rule: each letter keeps its promise. It cannot see the second. On `"badc"` and `"baba"`, the forward map is perfectly consistent (b→b, a→a, d→b, c→a), yet b and d both become b. **Keep a second map, from `t` back to `s`.** A conflict in either direction means `false`.

### Dry run

<DryRun title="Isomorphic Strings: the second map matters" frames={isomorphicFrames('badc', 'baba')} predict />

### Algorithm

1. Create `forward` (s-letter to t-letter) and `backward` (t-letter to s-letter).
2. For each index `i`, let `a = s[i]` and `b = t[i]`.
3. If `forward` already maps `a` to something other than `b`, return `false`.
4. If `backward` already maps `b` to something other than `a`, return `false`.
5. Record `a → b` and `b → a`. After the loop return `true`.

### Java solution

<HintLadder hints={hints.isomorphic}>

```java id=isIsomorphic
public boolean isIsomorphic(String s, String t) {
    Map<Character, Character> forward = new HashMap<>();    // letter of s -> letter of t
    Map<Character, Character> backward = new HashMap<>();   // letter of t -> letter of s
    for (int i = 0; i < s.length(); i++) {
        char a = s.charAt(i), b = t.charAt(i);
        Character toB = forward.putIfAbsent(a, b);          // null if a had no partner yet
        Character toA = backward.putIfAbsent(b, a);
        if (toB != null && !toB.equals(b)) return false;    // a already promised to another letter
        if (toA != null && !toA.equals(a)) return false;    // b already claimed by another letter
    }
    return true;
}

// Word Pattern: letters on one side, whole words on the other. Same two promises.
public boolean wordPattern(String pattern, String s) {
    String[] words = s.split(" ");
    if (words.length != pattern.length()) return false;
    Map<Character, String> forward = new HashMap<>();
    Map<String, Character> backward = new HashMap<>();
    for (int i = 0; i < words.length; i++) {
        char p = pattern.charAt(i);
        String w = words[i];
        String toW = forward.putIfAbsent(p, w);
        Character toP = backward.putIfAbsent(w, p);
        if (toW != null && !toW.equals(w)) return false;
        if (toP != null && !toP.equals(p)) return false;
    }
    return true;
}
```

**O(n) time; O(k) space for k distinct letters (or words).** LeetCode guarantees `s` and `t` have equal length.

</HintLadder>

### Why it works

- **Settled:** after index `i`, both maps agree with every pair seen so far, and neither has a letter with two partners.
- **Why the move is safe:** the two rules are exactly "forward is a function" and "backward is a function". Checking both on every new pair catches every violation at the first position where it appears.
- **When we stop:** at the first conflict, or after the last index.

### Complexity

- **Time:** O(n).
- **Space:** O(k) for k distinct letters (or words). LeetCode guarantees `s` and `t` have equal length.

### Edge cases and mistakes

- A letter mapping to itself is allowed.
- Only checking one direction (`"badc"` and `"baba"`).
- A famous one-liner compares `put` return values with `!=`, which breaks on boxed `Integer`s.

<Reveal q="The one-liner lastS.put(s[i], i) != lastT.put(t[i], i) passes every short test and fails on long strings. Why?">

The logic is right: two strings are isomorphic exactly when each position's previous occurrence matches in both. But `put` returns `Integer` objects, and `!=` compares references. Previous indices up to 127 come from the Integer cache and compare equal; from 128 on, each boxing makes a new object. On `"ab"` repeated 100 times against `"cd"` repeated 100 times, clearly isomorphic, the check at index 130 compares two different `Integer(128)` objects and returns `false`.

```java fragment
if (lastS.put(s.charAt(i), i) != lastT.put(t.charAt(i), i)) return false;   // BUG: Integer != Integer
```

Fix: `!Objects.equals(lastS.put(...), lastT.put(...))`.

</Reveal>

You could run the two maps per word, or give every word a **signature**: the index of each letter's first occurrence, so `"mee"` becomes `[0, 1, 1]` and `"abb"` becomes `[0, 1, 1]`. <h2 id="nearby-duplicate">Side quest 2 · Contains Duplicate II</h2>

### Problem

Given `nums` and `k`, return `true` if there are two different indices `i` and `j` with `nums[i] == nums[j]` and `|i − j| ≤ k`.

`[1, 2, 3, 1]` with `k = 3` returns `true`. With `k = 2` it returns `false`.

### How to recognise it

- "Seen before", but only **recently**: within the last `k` positions.
- A set that must **forget** old entries: a sliding window holding a set.

### Brute force

For each `i`, check the next `k` positions for an equal value. That is O(n · k), up to O(n²). The waste: each check rescans values that the previous step already looked at.

### Intuition

A twin of `nums[i]` that counts can only be among the last `k` values, `nums[i − k..i − 1]`. So the set must forget anything older: keep exactly those `k` values. Add `nums[i]` (if `add` fails, a twin is within `k`). Then, if the set holds more than `k` values, remove `nums[i − k]`, which would be too far back for the next position.

The set is a sliding window: the <a href={`${BASE}dsa/lessons/sliding-window/`}>Sliding Window</a> lesson's fixed-size window, holding a set instead of a sum. The window **grows** while it holds at most `k` values and **shrinks by one from the left** the moment it would hold `k + 1`.

<Figure caption="[1, 2, 3, 1] with k = 3. Before reading index 3, the set holds the last three values {1, 2, 3}. add(1) fails: the other 1 is at index 0, exactly 3 positions back. With k = 2, the 1 at index 0 would already have been removed, and the answer would be false.">
  <ArrayStrip values={[1, 2, 3, 1]} tones={{ 0: 'blue', 3: 'hot' }} regions={[{ from: 0, to: 2, label: 'the set: last k = 3 values', tone: 'blue' }]} pointers={[{ at: 3, label: 'add(1) fails' }]} />
</Figure>

### Dry run

<DryRun title="Contains Duplicate II" frames={nearbyDuplicateFrames([1, 0, 1, 1], 1)} predict />

### Algorithm

1. Create an empty set `window`.
2. For each index `i`: if `window.add(nums[i])` returns `false`, return `true`.
3. If `window.size() > k`, remove `nums[i − k]`.
4. After the loop return `false`.

### Java solution

<HintLadder hints={hints.nearby}>

```java id=containsNearbyDuplicate
public boolean containsNearbyDuplicate(int[] nums, int k) {
    Set<Integer> window = new HashSet<>();           // the values at the last k positions
    for (int i = 0; i < nums.length; i++) {
        if (!window.add(nums[i])) return true;       // a twin at most k positions back
        if (window.size() > k) window.remove(nums[i - k]);   // too far back for position i + 1
    }
    return false;
}
```

**O(n) expected time, O(min(n, k)) space.** All values in the window are distinct (a repeat would have returned), so the set’s size is the number of positions it covers. With `k = 0`, every value is removed as soon as it is added, and the answer is always false — correct, since `i ≠ j` is required.

</HintLadder>

### Why it works

- **Settled:** before handling index `i`, the set holds exactly `nums[i − k..i − 1]`.
- **Why the move is safe:** a twin farther back than `k` cannot count, so forgetting it never loses an answer. A twin within `k` is still in the set.
- **When we stop:** at the first failed `add`, or at the end.

### Complexity

- **Time:** O(n) expected.
- **Space:** O(min(n, k)).

### Edge cases and mistakes

- `k = 0`: always `false`, because `i ≠ j` is required and every value is removed as soon as it is added.
- Removing the wrong element (`nums[i − k + 1]` or `nums[i − k − 1]`) shifts the window by one and gives a wrong answer at exactly distance `k`.

### Practice

<Reveal q="Can you do it without the window, with a map instead?">

Yes: map each value to the **last** index where it appeared. At index `i`, if `nums[i]` was last seen at `j` and `i − j ≤ k`, return true; then overwrite with `i`. Keeping the latest index is right here, because the closest earlier twin is the one most likely to be within `k`. Same O(n) time; O(n) space instead of O(k).

</Reveal>

<h2 id="top-k">Side quest 3 · Top K Frequent Elements</h2>

### Problem

Return the `k` values that appear most often in `nums` (LeetCode guarantees the answer is unique), and do better than sorting the counts.

`[1, 1, 1, 2, 2, 3]` with `k = 2` returns `[1, 2]`.

### How to recognise it

- "Most frequent", "top k by count", "k most common".
- Counting is step one; selecting the largest counts is step two.

### Brute force

Count with a map, then sort all distinct values by count and take the first `k`. That is O(n log n) for up to n distinct values. It is correct and a fine baseline, but the problem asks for better.

### Intuition

Count with `merge`, as in Chapter 4. Now you need the `k` largest counts. A heap does it in O(n log k) (see the <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> lesson). But **no count can exceed n**, so the counts can index an array: bucket `f` holds every value that appeared exactly `f` times. Walk the buckets from `n` down and take values until you have `k`. That is a bucket sort, and it is O(n).

<Figure caption="[1, 1, 1, 2, 2, 3], k = 2. Counts: 1 appears 3 times, 2 twice, 3 once. Buckets by count: bucket 3 holds 1, bucket 2 holds 2, bucket 1 holds 3. Walking down from bucket 6 takes 1, then 2.">
  <ArrayStrip name="bucket f" values={['·', '3', '2', '1', '·', '·', '·']} tones={{ 3: 'hot', 2: 'hot', 1: 'done' }} pointers={[{ at: 3, label: 'take 1' }, { at: 2, label: 'take 2', tone: 'blue' }]} />
</Figure>

### Dry run

<DryRun title="Top K Frequent Elements" frames={topKFrames([4, 1, 4, 2, 4, 1], 2)} predict />

### Algorithm

1. Count every value in a map `freq`.
2. Create `byFreq`, an array of lists of size `n + 1`. Put each value in `byFreq[its count]`.
3. For `f` from `n` down to 1, take values from `byFreq[f]` until `k` are chosen.

### Java solution

<HintLadder hints={hints.topK}>

```java id=topKFrequent
public int[] topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int x : nums) freq.merge(x, 1, Integer::sum);
    List<Integer>[] byFreq = new List[nums.length + 1];  // byFreq[f] = values seen exactly f times
    for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
        int f = e.getValue();
        if (byFreq[f] == null) byFreq[f] = new ArrayList<>();
        byFreq[f].add(e.getKey());
    }
    int[] answer = new int[k];
    int filled = 0;
    for (int f = nums.length; f >= 1 && filled < k; f--)  // most frequent first
        if (byFreq[f] != null)
            for (int x : byFreq[f])
                if (filled < k) answer[filled++] = x;
    return answer;
}
```

**O(n) expected time, O(n) space.** (`new List[n + 1]` is a raw array, because Java can’t create generic arrays; the compiler warns, and the code is safe.)

</HintLadder>

### Why it works

- **Settled:** all buckets above `f` have been fully taken, so the chosen values have counts at least as large as anything left.
- **Why the move is safe:** counts are bounded by `n`, so an array index can stand for a count. Walking from the highest index down visits values in order of decreasing frequency, with no comparison sort.
- **When we stop:** as soon as `k` values are chosen.

### Complexity

- **Time:** O(n) expected: counting is O(n), bucketing is O(distinct), the walk is O(n + k).
- **Space:** O(n) for the map and buckets. (`new List[n + 1]` is a raw array, because Java cannot create generic arrays; the compiler warns, and the code is safe.)

### Edge cases and mistakes

- All values the same: one bucket at index `n`.
- `k` equal to the number of distinct values: take everything.
- Allocating buckets of size `n` instead of `n + 1` crashes when one value fills the whole array.

### Practice

<Reveal q="When would you still choose the heap?">

When n is huge or streaming and k is small. The buckets need O(n) memory up front, sized by the input length; a heap of size `k` needs only O(k) beyond the counts, and it keeps working as new values arrive. Interviewers often ask for both.

</Reveal>

<h2 id="sudoku">Side quest 4 · Valid Sudoku</h2>

### Problem

A 9 × 9 Sudoku board is partly filled (`'.'` is empty). Is it **valid**: no digit repeated in any row, any column or any 3 × 3 box? The board need not be solvable.

### How to recognise it

- "No repeats within each group", with several overlapping groups (rows, columns, boxes).
- It is "seen before?" asked 27 times over.

### Brute force

For each filled cell, scan its row, its column and its box for the same digit. That is up to 27 comparisons per cell. For a fixed 9 × 9 board that is a constant, but it does not scale and it is easy to scan the wrong cells.

### Intuition

Give every row, every column and every box its own small set of digits. For each filled cell, check its digit against the three sets it belongs to, then add it to all three. Digits are 1 to 9, so each set can be a `boolean[9]`: a set with nine fixed keys, like Chapter 4's `int[26]`.

The only real decision is **numbering the boxes 0 to 8**: `box = (r / 3) * 3 + c / 3`, left to right, top to bottom.

### Dry run

### Algorithm

1. Create three `boolean[9][9]` tables: `row`, `col`, `box`.
2. For each filled cell `(r, c)` with digit `d`, compute `b = (r / 3) * 3 + c / 3`.
3. If `row[r][d]`, `col[c][d]` or `box[b][d]` is already true, return `false`.
4. Otherwise set all three to true. After all cells, return `true`.

### Java solution

<HintLadder hints={hints.sudoku}>

```java id=isValidSudoku
public boolean isValidSudoku(char[][] board) {
    boolean[][] row = new boolean[9][9], col = new boolean[9][9], box = new boolean[9][9];
    for (int r = 0; r < 9; r++)
        for (int c = 0; c < 9; c++) {
            if (board[r][c] == '.') continue;
            int d = board[r][c] - '1';               // digits 1..9 -> 0..8
            int b = (r / 3) * 3 + c / 3;             // boxes 0..8, left to right, top to bottom
            if (row[r][d] || col[c][d] || box[b][d]) return false;   // seen before?
            row[r][d] = col[c][d] = box[b][d] = true;
        }
    return true;
}
```

**O(81) = O(1) time and space** for a fixed 9 × 9 board; O(N²) for an N × N board. An equally good version files strings like `"5 in row 0"`, `"5 in col 3"`, `"5 in box 1"` in one `HashSet<String>` — a composite key with its separators spelled out.

</HintLadder>

### Why it works

- **Settled:** every filled cell read so far is recorded in exactly one row set, one column set and one box set, and no set contains a repeated digit.
- **Why the move is safe:** a repeat anywhere on the board shares a row, a column or a box with its twin, so the second one meets the first in one of the three sets.
- **When we stop:** at the first clash, or after all 81 cells.

### Complexity

- **Time and space:** O(81) = O(1) for a fixed 9 × 9 board; O(N²) for an N × N board.
- An equally good version stores strings like `"5 in row 0"`, `"5 in col 3"`, `"5 in box 1"` in one `HashSet<String>`: a composite key with its separators spelled out.

### Edge cases and mistakes

- The empty board is valid.
- Forgetting the digit-to-index shift (`'1'` is index 0).
- The box formula: `r / 3 + c / 3` gives cell (0, 3) and cell (3, 0) both box 1, though they sit in boxes 1 and 3. A board with a 5 in each of those cells is valid, and this version rejects it.

### Practice

<h2 id="happy-number">Side quest 5 · Happy Number</h2>

### Problem

Start from `n` and repeatedly replace it by the **sum of the squares of its digits**. Return `true` if it reaches 1.

`19` returns `true` (19 → 1 + 81 = 82 → 64 + 4 = 68 → 36 + 64 = 100 → 1). `2` returns `false`.

### How to recognise it

- A process that repeats, and the question is whether it ends or loops forever.
- Any "does this ever come back to a state it has been in?" question is "seen before?" on states.

### Brute force

Keep applying the step until you reach 1 or give up after a large fixed number of steps. That works only because the sequence is small, and "give up after N steps" is a guess, not a proof.

### Intuition

If it never reaches 1, the sequence must repeat, and a repeat is "seen before?". Why must it repeat? A number with d ≥ 4 digits is at least 10^(d−1), but its digit-square sum is at most 81d, which is smaller. So the numbers fall below 1000, and from there they never exceed 3 × 81 = 243. Trapped among finitely many values, the sequence either reaches 1 (which maps to itself) or cycles. Check every value against a set; stop at 1 or at the first repeat.

### Algorithm

1. Create an empty set `seen`.
2. While `n != 1` and `seen.add(n)` succeeds, set `n` to the sum of the squares of its digits.
3. Return `n == 1`.

### Java solution

<HintLadder hints={hints.happy}>

```java id=isHappy
public boolean isHappy(int n) {
    Set<Integer> seen = new HashSet<>();
    while (n != 1 && seen.add(n)) n = next(n);       // stop at 1, or at the first repeat
    return n == 1;
}

// Floyd's version: O(1) memory. On a cycle, the fast walker laps the slow one.
public boolean isHappyFloyd(int n) {
    int slow = n, fast = next(n);
    while (fast != 1 && slow != fast) {
        slow = next(slow);
        fast = next(next(fast));
    }
    return fast == 1;
}

private int next(int n) {                            // the sum of the squares of the digits
    int sum = 0;
    while (n > 0) { int d = n % 10; sum += d * d; n /= 10; }
    return sum;
}
```

**O(log n) per step**, and after the first step the values are at most 810 (`Integer.MAX_VALUE` has ten digits), so the number of steps is bounded by a small constant. Set: O(1) extra space in practice (a few hundred values at most); Floyd: O(1) strictly.

</HintLadder>

### Why it works

- **Settled:** `seen` holds every value of the sequence so far, each once.
- **Why the move is safe:** the sequence is deterministic, so once a value repeats, everything after it repeats too. It can never reach 1 without having reached it already.
- **When we stop:** at 1 (happy) or at the first repeated value (unhappy).

### Complexity

- **Time:** O(log n) per step, and after the first step the values are at most 810 (`Integer.MAX_VALUE` has ten digits), so the number of steps is bounded by a small constant.
- **Space:** the set is O(1) extra space in practice (a few hundred values at most); Floyd's version is O(1) strictly.

### Edge cases and mistakes

- `n = 1` is happy immediately.
- Looping "until it reaches 1" without cycle detection never ends on unhappy numbers.
- Digit extraction with `n % 10` and `n /= 10` must stop at `n > 0`, or the loop never ends.

### Practice

<Reveal q="The set costs memory. Can you detect the cycle without remembering anything?">

Yes: **Floyd's tortoise and hare**, from the <a href={`${BASE}dsa/lessons/linked-lists/`}>Linked Lists</a> lesson. Treat "next number" as a pointer. A slow walker takes one step, a fast walker two; on a cycle the fast one laps the slow one and they meet. If the sequence reaches 1, the fast walker gets there first and stays. O(1) space. Both versions are in the solution above.

</Reveal>

<h2 id="first-unique">Side quest 6 · First Unique Character</h2>

### Problem

Return the index of the **first** character in `s` that appears exactly once, or −1 if there is none. Order matters now.

`"leetcode"` returns `0`. `"loveleetcode"` returns `2`. `"aabb"` returns `-1`.

### How to recognise it

- "First", "earliest" combined with a **frequency** condition (exactly once).
- Counting finds which characters qualify, but not which one is first.

### Brute force

For each index, scan the whole string for another copy of that character. That is O(n²). The inner scan is really asking "how many times does this character appear?", which a count answers in O(1).

### Intuition

Counting (Chapter 4) tells you which characters are unique, but the counts have forgotten the order. The string has not. So count in one pass, then walk **the string** a second time and return the first index whose character has count 1.

</Figure>

### Algorithm

1. Count every character in `int[26]`.
2. Walk the string from index 0.
3. Return the first index whose character has count 1.
4. If none, return −1.

### Java solution

<HintLadder hints={hints.firstUnique}>

```java id=firstUniqChar
public int firstUniqChar(String s) {
    int[] count = new int[26];
    for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
    for (int i = 0; i < s.length(); i++)             // walk the string: it remembers the order
        if (count[s.charAt(i) - 'a'] == 1) return i;
    return -1;
}
```

**O(n) time, O(1) extra space.** For a stream where you can’t make a second pass, keep the candidates in insertion order — a `LinkedHashMap`, or a queue whose front you pop while its character has repeated.

</HintLadder>

### Why it works

- **Settled:** after pass 1 the counts are final. In pass 2, every index before `i` was a repeat.
- **Why the move is safe:** the string order is the order the question cares about, and the counts answer "unique?" for any character in O(1).
- **When we stop:** at the first count of 1, or at the end of the string.

### Complexity

- **Time:** O(n): two passes.
- **Space:** O(1): 26 counts. For a stream where you cannot make a second pass, keep the candidates in insertion order: a `LinkedHashMap`, or a queue whose front you pop while its character has repeated.

### Edge cases and mistakes

- Empty string, or every character repeated: `-1`.
- The classic slip: scanning the 26 counts for the first count of 1 (see below).

### Practice

<Reveal q="Why not scan the 26 counts for the first count of 1?">

Because the count array is in alphabetical order, not string order. On `"loveleetcode"` the unique letters are v, t, c and d; scanning the counts finds c first and returns its index, 8. The first unique character in the string is v, at index 2.

</Reveal>

<h2 id="choose-the-tool">When hashing is the wrong tool</h2>

Say two hundred million registration numbers sit in one array that barely fits in memory, and you must find out whether any number appears twice. A `HashSet` needs its own entry for every number: many times more memory than the array itself. There is no room for it. The better move is to put the array itself in order, so twins sit side by side.

A hash table is the right tool when you need **fast membership, counting or grouping, and you can afford the memory**. It is the wrong tool when:

- **Memory is the binding constraint.** An `int[]` stores a value in 4 bytes. A `HashSet<Integer>` on a 64-bit JVM typically spends around 50 bytes or more per entry (the entry node, the boxed `Integer`, the slot in the table). For 200 million values that is the difference between under 1 GB and roughly 10 GB. **Sort in place and compare neighbours**: O(n log n) time, almost no extra memory.
- **The question is about order.** The next value above `x`, the smallest, a range of keys, sorted output: a `HashSet` keeps no order. Use a **`TreeSet` / `TreeMap`** (a red-black tree): O(log n) per add, remove and lookup, plus `floor`, `ceiling`, `higher`, `first`, `last` and in-order iteration.
- **The input is already sorted.** Pairs, duplicates and merges on sorted data need no memory: <a href={`${BASE}dsa/lessons/two-pointers/`}>two pointers</a>, O(1) space.
- **The alphabet is tiny and fixed.** 26 letters, 10 digits, 128 ASCII codes: a plain array is a faster, smaller map.
- **You need a guarantee, not an average.** Expected O(1) can degrade under adversarial keys (hash flooding). A tree gives O(log n) every time.
- **You need insertion order.** `LinkedHashMap` / `LinkedHashSet` keep it, for a few bytes more per entry.

<Reveal q="Contains Duplicate: HashSet or TreeSet?">

Both are correct. `HashSet` is O(n) expected; `TreeSet` is O(n log n) guaranteed and keeps the values sorted. Choose `HashSet` unless you also need order, or guarantees against adversarial input. Say why: the reason is the recognition practice, not the answer.

</Reveal>

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Keep the tutorial code closed. Before coding, write down what you will store, what you will look up, and which comes first.

1. **The brick wall.** A wall is given as rows of brick widths; every row has the same total width. Draw one vertical line from top to bottom crossing as few bricks as possible (running along an edge between two bricks does not cross either; the wall's two outer sides are not allowed). Return the number of bricks crossed. Test: one row, identical rows, rows of a single brick.
2. **Shifted twins.** Group strings where one becomes another by shifting every letter by the same amount around the alphabet: `"abc"`, `"bcd"` and `"xyz"` belong together, and so do `"az"` and `"ba"`. Test single letters, the empty string, and wrap-around.
3. **Pairs at distance k.** Count the distinct pairs of values `(a, b)` in an array with `b − a = k`, for a given `k ≥ 0`. Test `k = 0` with duplicates, negative values, and no pairs.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**The brick wall:** a line crosses the fewest bricks where the most rows have an edge. Walk each row, keeping a running width, and count each inner edge position (every running width except the row's last) in a map. The answer is rows minus the largest count, or rows if no row has an inner edge. Chapter 4's counting, keyed by position.

**Shifted twins:** a signature that ignores the shift: the differences between neighbouring letters, mod 26, **with separators**, or shift each string so its first letter becomes `a`. `"az"` and `"ba"` both have difference 25. Chapter 5, with a different key.

**Pairs at distance k:** count values in a map. For `k > 0`, count the distinct `x` with `x + k` present; for `k = 0`, count the values that appear at least twice. The `k = 0` case is the trap: a plain set lets every value pair with itself, the very bug Chapter 2's ask-before-store avoids.

Now explain why a slightly wrong version fails one of your tests: a key without separators, a value pairing with itself, the outer edge counted as an edge. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Start with... | The invariant to keep |
|---|---|---|
| Has anything repeated? | `HashSet`; `if (!seen.add(x)) return true` | The set holds exactly the distinct values before `i` |
| A pair summing to a target, unsorted, original positions | Map value → index; ask for `target − x`, then store `x` | The map holds only earlier positions |
| Your own class, or a pair, as a key | A `record`, or `equals` + `hashCode` from the same final fields | Equal keys get equal hash codes; stored keys never change |
| Same letters, any order (lowercase) | `int[26]`: +1 for s, −1 for t, all zero | Equal lengths; every count ends at 0 |
| Group items that are "the same" up to order | Map from canonical key → list, with `computeIfAbsent` | `key(a)` equals `key(b)` exactly when they belong together |
| Longest consecutive run, unsorted, O(n) | Set; walk only from `x` with `x − 1` absent | Every number is walked exactly once |
| Many strings through one string | `length#string`; decode by counting | `i` always points at a header |
| A one-to-one letter replacement | Two maps, forward and backward | No letter has two partners in either direction |
| A twin within k positions | A set of the last k values | The set holds exactly `nums[i − k..i − 1]` |
| The k most frequent values | Count map, then buckets indexed by frequency | No frequency exceeds n |
| A grid with no-repeat rules | 27 small sets; box `(r / 3) * 3 + c / 3` | Each digit at most once per row, column and box |
| Does a sequence loop forever? | A set of seen states, or Floyd | A repeat means a cycle |
| The first item that appears exactly once | Count, then a second pass in the original order | The input remembers order; the counts do not |
| Order questions: next above x, sorted output | `TreeSet` / `TreeMap`, O(log n) | Hashing gives membership, never order |

Hashing does **not** come free: every map and set here costs O(n) extra memory (or O(k), O(26)). Only the `int[26]` and `boolean[9]` versions and Floyd's cycle check run in O(1) extra space. Count every structure you build.

## Five bugs to check for

1. **Storing before asking.** The current value finds itself: Two Sum on `[3, 2, 4]` with target 6 returns `[0, 0]`.
2. **A key that breaks the contract.** `equals` without `hashCode` (equal keys in different buckets), or a key mutated after storing (stranded in the wrong bucket). Use records or immutable fields.
3. **`==` on boxed numbers.** It works up to 127 and fails at 128. Compare `Integer`s with `.equals`, or unbox.
4. **Keys that collide by construction.** Concatenation without separators (`"1" + "12"` and `"11" + "2"`), `int[]` used as a key (identity, not contents), a delimiter where a length was needed.
5. **Walking from every number.** Longest Consecutive without the `x − 1` check, or looping over `nums` instead of the set, quietly turns O(n) back into O(n²).

<h2 id="revision">Revision</h2>

**How to recognise it.** An O(n²) solution whose inner loop searches for one specific thing: "seen before?", "is the partner here?", "how many of each?", "which items belong together?". Ask whether a lookup by key can replace the scan.

**Core algorithm.** Pick what to remember (a set for membership, a map for counts or indices, a map to lists for groups) and the key that makes equal things equal. Walk the input once. **Ask the structure first, then store the current item.** Use a canonical key for grouping (sorted letters, counts with separators, a record) and a length prefix when packing strings.

**Common mistakes.**

- Storing before asking, so a value matches itself.
- Keys that break the contract: `equals` without `hashCode`, mutated keys, arrays as keys, concatenation without separators.
- `==` on boxed `Integer`s.
- Walking a run from every number instead of only from its start.
- Forgetting length checks (anagrams) or the backward map (isomorphic).

**Complexity.** O(n) expected time and O(n) extra space. A fixed alphabet (`int[26]`, `boolean[9]`) makes the space O(1). The worst case is O(n) per operation if every key collides (O(log n) in Java 8+ for comparable keys). Sorting trades the table for O(n log n) time and little memory.

**Three representative problems.**

1. [Two Sum](https://leetcode.com/problems/two-sum/): ask for `target − x`, then store.
2. [Group Anagrams](https://leetcode.com/problems/group-anagrams/): canonical key, then `computeIfAbsent`.
3. [Longest Consecutive Sequence](https://leetcode.com/problems/longest-consecutive-sequence/): a set, walking only from run starts.

**Look these up yourself:** real ideas this page did not have room for:

- **Open addressing and linear probing:** store entries in the array itself instead of in chains; Python's `dict` and Java's `IdentityHashMap` work this way.
- **Hash flooding and seeded hashing (SipHash):** why many languages randomise their string hash per process, after attacks that forced every key into one bucket.
- **Robin Hood and cuckoo hashing:** schemes that cut the variance of probe lengths, or guarantee O(1) worst-case lookups.
- **Bloom filters:** "definitely not seen / probably seen" in a few bits per item, when even a set is too big.
- **Rolling hashes (Rabin–Karp):** hash every window of a string in O(1) per slide.
- **Consistent hashing:** the system-design cousin: adding a server moves only a small fraction of keys.
- **LinkedHashMap in access order:** an LRU cache in a dozen lines with `removeEldestEntry`.
- **Universal and perfect hashing:** choosing the hash function at random to turn "expected" into a provable guarantee.
