<h2 id="prologue">Prologue · Ten thousand letters</h2>

<Scene chapter="Prologue" title="Ten thousand letters" mood="dawn">

Letterby is a town that writes. Every morning the mail coach tips a fresh mountain of letters onto the floor of the Sorting Office, and every one of them must be in its place by noon.

On your first morning the postmaster brings a question with the sacks. *"Has anyone written to us twice?"* A junior sorter lays the first letter beside every other letter, then the second beside every other. Ten thousand letters make almost fifty million comparisons. At dusk he is still on the first sack.

The Keeper says nothing. She leads you to the back wall — rows of numbered wooden pigeonholes — where a broad-shouldered clerk called Hash is inking a brass stamp.

*"Hash gives every letter a number,"* she says. *"The same letter always gets the same number. So when a letter arrives, how many holes do you need to look in?"*

</Scene>

**Hash** reads a key and stamps it with a number, its *hash code*. The wall has a fixed number of holes, and the stamp picks one. Two rules make the whole office work:

1. **Equal letters get equal stamps.** If `a.equals(b)`, then `a.hashCode() == b.hashCode()`. So a twin of `x` can only ever be filed in `x`’s hole.
2. **Different letters may share a stamp.** That is a *collision*, and it is legal. **Equals** opens the hole and compares the few letters inside.

So “have I seen `x`?” means: stamp `x`, open one hole, compare with the handful of letters there. When the stamps spread letters evenly and the wall grows with the mail, a hole holds about one letter on average, and the whole question costs **O(1) expected time**.

The Keeper asks her three questions here, as everywhere in the realm:

1. **What is settled?** Everything on file. A filed letter can always be found again — as long as nobody alters it after filing (Chapter 3).
2. **Why is this move safe?** Equal things get equal stamps, so looking in one hole is as good as looking everywhere. And you ask before you file, so nothing ever finds itself.
3. **When do I stop?** When the question is answered — the first repeat, the partner found — or when the last letter is filed.

> “Equal things get equal stamps, so one hole is enough.” That is the promise. Every chapter in this book keeps it, then asks the wall a different question.

### When this pattern fires

The giveaway is almost always the same: **an O(n²) solution whose inner loop is searching for one specific thing.** If you can say what the inner loop is looking for, a hash table can usually look it up instead:

- **“Have I seen this before?”** Duplicates, repeated states, cycles, visited corners. Comparing each item with every earlier one is O(n²); a set makes it **O(n) expected**.
- **“Is its partner here?”** A pair with a target sum, a complement, a mirror image. The inner loop of a pair search becomes one lookup.
- **“How many of each?”** Frequencies, anagrams, the most common values.
- **“Which ones belong together?”** Grouping by a key computed from each item.
- **“Is `x` present?”, asked many times** while you build something else: consecutive runs, valid boards, word lists.

You’ve named the fear before: **Recognition Fear**, freezing when a problem doesn’t announce its pattern. In this town, the cure is one sentence you say out loud before coding: *“My inner loop is searching for ___; I can look that up.”*

The price, every time: **O(n) extra memory, no ordering, and a worst case the average hides.** The last chapter of this book is about when that price is too high.

<h2 id="contains-duplicate">Chapter 1 · The second letter</h2>

<Scene chapter="Chapter 1" title="The second letter" mood="dawn">

The postmaster’s question is still on the counter: in this sack, has anyone written twice? Each letter carries a sender number.

You pick up the first letter. Hash stamps it — hole 214 — and you slide it in. The second letter, hole 37. The third, hole 214 again. Your stomach drops; then Equals opens hole 214, looks at both letters, and shakes his head. Different senders, same stamp.

*"And an empty one proves everything,"* says the Keeper. *"When does a letter tell you it has been here before?"*

</Scene>

**Problem: Contains Duplicate · “seen before?” with a set**

Read the values once. For each one, ask the set whether it is already on file; if it is, you have found a repeat and can stop. Otherwise file it. Java’s `Set.add` does both in one call: it **returns `false` when an equal element is already present**, and leaves the set unchanged.

Comparing every pair costs `n(n − 1) / 2` comparisons — 49,995,000 for 10,000 letters. The set costs one expected-O(1) step per letter.

### How the wall really works

Interviewers rarely ask you to build a hash table, but they often ask *why* a lookup is O(1) and when it isn’t. Here is Java’s `HashMap` (a `HashSet` is a `HashMap` with dummy values), at interview depth:

1. **The stamp.** `hashCode()` turns the key into an `int`. For an `Integer` it is the value itself. For a `String` it is `s[0]·31^(n−1) + s[1]·31^(n−2) + … + s[n−1]`, computed with `int` overflow.
2. **The hole.** `HashMap` mixes the high bits into the low ones (`h ^ (h >>> 16)`) and keeps the low bits: `hash & (capacity − 1)`. Capacity is always a power of two, so this is a fast remainder. For an `Integer` key from 0 to 65,535 the hole is exactly `value % capacity` — the toy wall in the prologue is the real thing.
3. **Collisions, by chaining.** Different keys can share a hole (`"Aa"` and `"BB"` both hash to 2112). Each hole holds a short linked list of entries. A lookup walks it, comparing the stored hash first and then calling `equals`.
4. **Load factor and resizing.** The load factor is entries ÷ holes. Java starts with 16 holes and a limit of 0.75, so the 13th entry (past 16 × 0.75 = 12) **doubles the wall to 32 holes and re-files every entry**. Each entry either stays in hole `i` or moves to `i + 16`. One resize is O(n), but because the wall doubles, all the re-filing over a map’s life adds up to roughly 2n moves: **amortised O(1) per insert**.
5. **Expected versus worst.** With well-spread stamps the average chain has at most about 0.75 entries, so `add`, `contains` and `remove` are **O(1) expected**. If every key lands in one hole, each lookup walks a chain of n: **O(n) each, O(n²) to build the set**. Since Java 8, a hole whose chain grows past 8 entries is converted into a small red-black tree (when the table has at least 64 holes; a smaller table just resizes instead), so for keys that implement `Comparable`, such as `String` and `Integer`, that worst case becomes **O(log n)**.

Say it in the room as: **“O(1) expected per operation, O(n) worst case — O(log n) in Java 8+ when a crowded bucket is treeified and the keys are comparable.”**

**Why it works:** equal values have equal stamps, so a repeat of `x` can only be filed in `x`’s hole. Searching that one hole is the same as searching everything filed so far.

**What stays true:** before handling index `i`, the set holds exactly the distinct values among `nums[0..i − 1]`, and none of them has repeated — otherwise you would already have returned.

<Reveal q="The set costs O(n) extra memory. Can you answer without it?">

Yes: **sort, then compare neighbours.** After sorting, any repeat sits right beside its twin. That is O(n log n) time with little or no extra memory — but it reorders the caller’s array. Interviewers like hearing both: the set for speed, sorting when memory is tight or the data is already sorted. Both versions are in the solution below.

</Reveal>

<Reveal q="Why not compare the set’s size with the array’s length at the end?">

That works (it is the roadmap’s one-line trigger: *set size vs array size*), but it always reads the whole array, while the `add` check stops at the first repeat. And in Java there is a trap waiting in the one-liner — see the bug below.

</Reveal>

<HintLadder hints={hints.containsDuplicate}>

```java id=containsDuplicate
public boolean containsDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int x : nums)
        if (!seen.add(x)) return true;               // add says false: x was already on file
    return false;
}

// Low-memory alternative: sort in place, then any repeat sits beside its twin. Reorders nums.
public boolean containsDuplicateSorted(int[] nums) {
    Arrays.sort(nums);
    for (int i = 1; i < nums.length; i++)
        if (nums[i] == nums[i - 1]) return true;
    return false;
}
```

**Set: O(n) expected time, O(n) extra space. Sorted: O(n log n) time, no hash table.**

</HintLadder>

**Catch the bug:** the size comparison, written in a hurry on an `int[]`.

```java fragment
return nums.length != new HashSet<>(Arrays.asList(nums)).size();   // BUG: a set holding ONE int[]
```

`Arrays.asList` on an `int[]` cannot box the ints; it makes a list with one element, the array itself. The set always has size 1, so `[1, 2]` “contains a duplicate”. Box first: `Arrays.stream(nums).boxed().collect(Collectors.toSet())`. [Solve Contains Duplicate](https://leetcode.com/problems/contains-duplicate/).

<Scene chapter="Chapter 2" title="Exact postage">

A parcel for the coast needs exactly 9 pence in stamps — two stamps, no more, no change given. The stamp drawer holds single stamps in a row, in no order at all: 2, 7, 11, 15. The postmaster wants the two drawer positions.

The junior sorter tries the first stamp with every other, then the second with every other. You remember the twins of Arraytown, walking inward from both ends — but this drawer isn’t sorted, and sorting it would scramble the positions you have to report.

Ask leans over the counter with the register open. *"You’re holding a 7,"* says the Keeper. *"Which stamp would finish the job? Has it already passed through your hands?"*

</Scene>

**Problem: Two Sum · the register of values already seen**

Holding `x`, you don’t need *any* stamp — you need exactly `target − x`. So keep a register: a map from each value you have read to its index. At each position:

1. **Ask:** is `target − x` on file? If yes, at index `j`, the answer is `[j, i]`.
2. **File:** otherwise record `x → i`, so later values can find it.

**Ask always goes first.** The register then holds only *earlier* positions, so a match can never be the current value pairing with itself.

<Trace title="Ask, then file" steps={twoSum} takeaway="Remember: look up target − x first, then file x → i. The register holds only earlier positions, so nothing pairs with itself — duplicates included." />

**Why it works:** take any valid pair `j < i`. When the scan reaches `i`, the value at `j` is already on file (perhaps under a later index with the same value, which is just as good), so the lookup finds a partner. The scan returns at the **first** position that completes any pair.

**What stays true:** before handling index `i`, the register holds every value among `nums[0..i − 1]`, each with an index where it occurs, and no pair lies entirely inside `nums[0..i − 1]`.

<Reveal q="Two passes — file everything first, then look up — would that work?">

Yes, with one extra check: the partner’s index must differ from `i`. With `[3, 2, 4]` and target 6, the first pass files `3 → 0`, and at `i = 0` the lookup for 3 finds index 0 — itself — so you must skip it. Duplicates still work, because the later `3` overwrites the earlier index. One pass is shorter, needs no special case, and can stop early.

</Reveal>

<Reveal q="What if the stamps WERE sorted, and memory was scarce?">

Then it is Two Sum II, and the twins from <a href={`${BASE}dsa/lessons/two-pointers/`}>Arraytown</a> win: one marker at each end, move the left one when the sum is too small and the right one when it is too big. O(n) time, **O(1)** space. The map spends O(n) memory to buy freedom from sorted order; don’t pay for what the input already gives you.

</Reveal>

```java id=twoSum
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> indexOf = new HashMap<>();     // value -> an index where it was filed
    for (int i = 0; i < nums.length; i++) {
        Integer j = indexOf.get(target - nums[i]);       // Ask first: has the partner passed by?
        if (j != null) return new int[]{j, i};
        indexOf.put(nums[i], i);                         // ...then File
    }
    return new int[0];                                   // LeetCode guarantees a pair, so never reached there
}
```

**O(n) expected time, O(n) extra space.** LeetCode bounds values and target to ±10⁹, so `target − nums[i]` stays within ±2 × 10⁹, inside `int`.

</HintLadder>

**Catch the bug:** filing before asking.

```java fragment
indexOf.put(nums[i], i);                             // BUG: filed first...
Integer j = indexOf.get(target - nums[i]);           // ...so x can find itself

```

<h2 id="custom-keys">Chapter 3 · The forged stamp</h2>

<Scene chapter="Chapter 3" title="The forged stamp" mood="night">

A courier walks the town one block at a time — north, south, east or west — and the postmaster wants to know whether she ever stands on the same corner twice. A corner is a pair of numbers, so you write a little `Point` class, give it an `equals`, and file every corner she reaches.

Her route tonight is north, east, south, west: straight back to where she started. Your set says she never crossed.

The Keeper reads your class and hands it to Hash without a word. Hash stamps two identical corners. The stamps come out different.

*"Equals never even got a look,"* she says. *"Who taught your Point to stamp itself?"*

</Scene>

**Problem: Path Crossing · keys you build yourself**

The algorithm is Chapter 1 again: file the start, then file every corner, and stop at the first `add` that returns `false`. Everything interesting is in the key.

**The contract.** Java’s `Object.hashCode` documentation says: **if two objects are equal according to `equals`, they must have the same hash code.** Unequal objects may share a hash code — that is only a collision, and costs a comparison. And `hashCode` must not change while the fields that `equals` uses don’t change.

Here is your class from the scene:

```java fragment
class Point {                                        // BROKEN as a key
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
    // no hashCode(): the one inherited from Object comes from identity,
    // so two equal Points almost always get different stamps
}
```

Two `new Point(0, 0)` objects are equal, but their inherited stamps come from object identity. They land in different holes, `equals` is never called, and the set holds both. Worse, now and then two identity hashes *do* share a hole and the set finds the twin — so the bug comes and goes. (The mirror-image mistake, `hashCode` without `equals`, fails every time: equal keys share a hole, and the inherited `equals` still compares identity.)

### Two more ways a key lies

**A key that changes after filing.** Put an `ArrayList` `[1, 2]` into a `HashSet`, then call `list.add(3)` on that same list. The set filed it under the hash of `[1, 2]`, which is 994 (hole 2 of 16). The list now hashes to 30817 (hole 1). `set.contains(list)` looks in hole 1 and finds nothing; `set.contains(List.of(1, 2))` looks in hole 2, finds the entry, and `equals` says no. The entry is stranded. **Never mutate a key while it is filed** — remove it, change it, add it back, or use keys that can’t change.

```java fragment
Set<List<Integer>> set = new HashSet<>();
List<Integer> list = new ArrayList<>(List.of(1, 2));
set.add(list);
list.add(3);                                         // the key's hash changes from 994 to 30817
set.contains(list);                                  // false: wrong hole
set.contains(List.of(1, 2));                         // false: right hole, but equals says no
```

**`==` on boxed numbers.** A `Map<Integer, Integer>` hands back `Integer` objects, and `==` on two objects compares references. Java must reuse cached objects for values from −128 to 127, so `Integer a = 127, b = 127; a == b` is `true` — and with default JVM settings, `Integer c = 1000, d = 1000; c == d` is `false`. Code that compares `map.get(x) == map.get(y)` passes every small test and fails in production. **Compare boxed values with `.equals`, or unbox to `int` first.** (Side quest 1 has a famous one-liner that falls into exactly this.)

<Trace title="Stamps that lie" steps={keys} takeaway="Remember: equals and hashCode come from the same fields; keys never change while filed; boxed numbers compare with equals; string keys need separators." />

### Building a key that tells the truth

- **A `record`.** `record Point(int x, int y)` generates `equals` and `hashCode` from both components. This is the cleanest answer in Java 16+.
- **By hand.** Override both, from the same final fields. `31 * x + y` is a fine stamp: collisions such as (0, 31) and (1, 0) are legal and cost only a comparison.
- **A string with a separator.** `x + "," + y` works, because no digit or minus sign is a comma. Without the separator, (1, 23) and (12, 3) both become `"123"`.
- **One `long`.** `((long) x << 32) | (y & 0xffffffffL)` packs both coordinates into 64 bits with no collisions at all.

**Why it works:** a record’s `equals` and `hashCode` are both computed from `x` and `y`, so equal corners always get equal stamps and land in the same hole, where `equals` recognises them.

**What stays true:** the set holds every corner visited so far, each exactly once, and no filed key ever changes.

<HintLadder hints={hints.pathCrossing}>

```java id=pathCrossing
record Point(int x, int y) {}                        // a record writes equals AND hashCode from x and y

public boolean isPathCrossing(String path) {
    Set<Point> visited = new HashSet<>();
    int x = 0, y = 0;
    visited.add(new Point(0, 0));                    // the start counts as visited
    for (char move : path.toCharArray()) {
        if (move == 'N') y++;
        else if (move == 'S') y--;
        else if (move == 'E') x++;
        else x--;                                    // 'W'
        if (!visited.add(new Point(x, y))) return true;   // this corner was already on file
    }
    return false;
}
```

**O(n) expected time, O(n) extra space** for n moves.

</HintLadder>

<Reveal q="No records allowed (an older Java). Write the key by hand.">

Both methods, from the same final fields — plus the packed-`long` key, which needs no class at all:

```java id=pathCrossingManual
static final class Corner {
    private final int x, y;                          // final: a filed key must never change
    Corner(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Corner)) return false;
        Corner c = (Corner) o;
        return x == c.x && y == c.y;
    }
    @Override public int hashCode() { return 31 * x + y; }   // the same fields as equals
}

public boolean isPathCrossing(String path) {
    Set<Corner> visited = new HashSet<>();
    int x = 0, y = 0;
    visited.add(new Corner(0, 0));
    for (char move : path.toCharArray()) {
        if (move == 'N') y++; else if (move == 'S') y--; else if (move == 'E') x++; else x--;
        if (!visited.add(new Corner(x, y))) return true;
    }
    return false;
}

static long pack(int x, int y) {                     // a collision-free key for any two ints
    return ((long) x << 32) | (y & 0xffffffffL);
}
```

The mask matters: without `& 0xffffffffL`, a negative `y` is sign-extended to 64 bits and wipes out `x`’s half.

</Reveal>

**Catch the bug:** a string key without a separator.

```java fragment
if (!visited.add(x + "" + y)) return true;           // BUG: (1, 11) and (11, 1) are both "111"
```

On the 32-move route E, then N eleven times, then E ten times, then S ten times, the courier never repeats a corner — but (1, 11) and (11, 1) both become `"111"`, and the method reports a crossing. [Solve Path Crossing](https://leetcode.com/problems/path-crossing/).

<h2 id="valid-anagram">Chapter 4 · Same letters, new order</h2>

<Scene chapter="Chapter 4" title="Same letters, new order" mood="dusk">

Two telegrams arrive from the same ship, minutes apart. One reads ANAGRAM; the other, NAGARAM. The wireless operator swears the second is the first, scrambled by a storm.

**Problem: Valid Anagram · counting with an int[26]**

Two strings are anagrams exactly when every letter appears the same number of times in both. Order is irrelevant, so **count**. With only lowercase `a`–`z`, the counter doesn’t need a hash table at all: an `int[26]` indexed by `c − 'a'` is a map with 26 fixed keys — no hashing, no boxing, one array access per letter.

Add 1 for each letter of `s`, subtract 1 for each letter of `t`, and check that all 26 cups end at zero. **Check the lengths first**: unequal lengths can never be anagrams, and equal lengths are what let one loop walk both strings.

### Map idioms worth knowing cold

When the keys aren’t 26 letters, the counter is a `HashMap`. These calls keep the code short and the intent obvious:

| You want | Write | What it does |
|---|---|---|
| Count `x` | `count.merge(x, 1, Integer::sum)` | Puts 1 if `x` is absent, else adds 1 |
| Read with a default | `count.getOrDefault(x, 0)` | Never inserts anything |
| A list per key | `groups.computeIfAbsent(k, key -> new ArrayList<>()).add(v)` | Creates the list once, returns it every time |
| Remember only the first | `first.putIfAbsent(x, i)` | Returns the previous value, or `null` if `x` was new |
| Decrement, drop at zero | `count.computeIfPresent(x, (key, c) -> c == 1 ? null : c - 1)` | Returning `null` removes the entry |

One trap: `merge` removes an entry only when the function returns `null`. `count.merge(x, -1, Integer::sum)` leaves a count of 0 in the map, so `count.size()` no longer means “letters still owed”.

**Why it works:** a count array is the multiset of letters with positions thrown away. Two strings are anagrams exactly when their multisets are equal, and `+s − t` is zero everywhere exactly then.

**What stays true:** after processing index `i`, `count[c]` equals (copies of `c` in `s[0..i]`) minus (copies of `c` in `t[0..i]`).

The same tray, one-sided. Count the magazine’s letters; then for each letter of the note, take one bead out, and fail the moment a cup would go below zero. The magazine may have extra letters, so there is no length equality — only “enough of each”. O(m + n) time, O(1) space for 26 letters.

```java id=isAnagram
public boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;      // also what lets one loop cover both strings
    int[] count = new int[26];                       // count[c - 'a']: a map with 26 fixed keys
    for (int i = 0; i < s.length(); i++) {
        count[s.charAt(i) - 'a']++;
        count[t.charAt(i) - 'a']--;
    }
    for (int c : count) if (c != 0) return false;
    return true;
}

// Follow-up: any Unicode text. Count code points in a map instead.
public boolean isAnagramUnicode(String s, String t) {
    Map<Integer, Integer> count = new HashMap<>();
    s.codePoints().forEach(cp -> count.merge(cp, 1, Integer::sum));
    t.codePoints().forEach(cp -> count.merge(cp, -1, Integer::sum));
    for (int c : count.values()) if (c != 0) return false;
    return true;
}
```

**O(n) time, O(1) extra space** for the 26 counts; the Unicode version is O(n) expected time and O(k) space for k distinct characters. Sorting both strings and comparing also works, in O(n log n).

</HintLadder>

**Problem: Group Anagrams · hash by signature**

This is the idea that makes hashing a *pattern* rather than a data structure: **map every item to a canonical key, and let the map do the grouping.** The key must satisfy one rule:

> `key(a).equals(key(b))` **exactly when** a and b belong in the same group.

Too fine, and twins never meet (keying by the spelling: `"eat"` and `"tea"` stay apart). Too coarse, and strangers share a drawer (the sum of character codes: `"ad"` and `"bc"` both total 197). For anagrams there are two exact keys:

- **Sorted letters.** `"tea"` → `"aet"`. Every rearrangement sorts to the same string; different letter multisets sort to different strings. O(k log k) per word of length k.
- **The 26 counts, with a separator after each.** `"tea"` → `"1#0#0#0#1#…"`. O(k + 26) per word. **The separator is not decoration.** Counts can have two digits: a word with a = 1 and b = 12 and a word with a = 11 and b = 2 would both write `"112000…"` without it. With it, `"1#12#…"` and `"11#2#…"` stay apart. (`Arrays.toString(count)` also works; its `", "` is a separator.)

**Why it works:** the map gathers items whose keys are equal, and the keys are equal exactly when the items are anagrams. So each list in the map is one complete group — no more, no less.

**What stays true:** after handling the first `i` words, every one of them sits in exactly one list, under its own key, and each list holds every word so far with that key.

Because Java arrays don’t override `equals` or `hashCode`: two arrays with identical counts are different keys, stamped by identity. Every word would get a drawer of its own.
```java id=groupAnagrams
public List<List<String>> groupAnagrams(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        char[] letters = s.toCharArray();
        Arrays.sort(letters);
        String key = new String(letters);            // "eat", "tea", "ate" -> "aet"
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}

// Count key: O(k + 26) per word instead of O(k log k).
public List<List<String>> groupAnagramsByCount(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        int[] count = new int[26];
        for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
        StringBuilder key = new StringBuilder();
        for (int c : count) key.append(c).append('#');   // '#' ends each count: 1#12# vs 11#2#
        groups.computeIfAbsent(key.toString(), k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}
```

**Sorted key: O(n · k log k) time. Count key: O(n · (k + 26)) time.** Both use O(n · k) space for the groups and keys. LeetCode allows the empty string; it sorts to `""` (or counts to 26 zeros), and all empty strings share one group.

</HintLadder>

<Scene chapter="Chapter 6" title="The house numbers">

**Problem: Longest Consecutive Sequence · start only where x − 1 is absent**

File every number in a set. Then, for each number `x` in the set:

- **If `x − 1` is in the set, skip `x`.** It is in the middle of a run, and the run’s real start will walk past it.
- **If `x − 1` is absent, `x` starts a run.** Walk `x + 1, x + 2, …` while they are present. When the walk stops at `cur`, the run is `x..cur`, of length `cur − x + 1`.

Narrate the state at loop exit, out loud: **when the inner `while` stops, `cur` is the last number of the run, `cur + 1` is absent, and the length is `cur − x + 1`.** That sentence is the difference between a correct answer and an off-by-one.

<Figure caption="The same numbers drawn in order (the set itself has no order). Only 1, 100 and 200 lack a predecessor, so only they start walks. The walk from 1 steps on 2, 3 and 4 exactly once; the 4 is never a start, because 3 is present.">
  <ArrayStrip values={[1, 2, 3, 4, 100, 200]} indices={false} tones={{ 0: 'hot', 1: 'done', 2: 'done', 3: 'done', 4: 'hot', 5: 'hot' }} pointers={[{ at: 0, label: 'start (0 absent)' }, { at: 4, label: 'start', tone: 'blue' }, { at: 5, label: 'start', tone: 'blue' }]} regions={[{ from: 0, to: 3, label: 'run of 4', tone: 'gold' }]} />
</Figure>

<Trace title="Who is allowed to start walking?" steps={streak} takeaway="Remember: skip x when x − 1 is present; otherwise walk up from x. Each number is walked exactly once, so the whole pass is O(n)." />

**Why it is O(n), not O(n²):** every number belongs to exactly one maximal run, and every run has exactly one start — its smallest number. Only starts walk, so every number is stepped on by exactly one walk. Count the lookups: one “is `x − 1` here?” per distinct number, and, summed over all walks, one “is `cur + 1` here?” per distinct number (each successful step lands on a new number; each walk ends with one failed lookup, charged to its last number). That is **exactly 2m lookups for m distinct numbers**, plus n insertions: O(n) expected time.

**What stays true:** after the outer loop handles a set of numbers, `best` is the length of the longest run that starts among them — and no run has been walked twice.

<Reveal q="Isn’t sorting simpler? O(n log n) is barely worse.">

Sorting is a fine first answer: sort, then scan, extending the current run when `a[i] == a[i − 1] + 1`, **ignoring duplicates** (`a[i] == a[i − 1]` neither extends nor breaks the run), and resetting otherwise. It uses little memory. But the problem demands O(n), and the set gets there. Say both in the interview: the sort for a quick correct baseline, the set for the requirement. A `TreeSet` also works, at O(n log n), because it iterates in order.

</Reveal>

<Reveal q="Why loop over the set, not over nums?">

Duplicates. Looping over `nums` judges each copy separately, and every copy of a run’s start walks the whole run again. With n/2 copies of 1 followed by 2, 3, …, n/2, that is about n/2 walks of length n/2: O(n²) all over again. The set holds each value once.

</Reveal>

<HintLadder hints={hints.streak}>

```java id=longestConsecutive
public int longestConsecutive(int[] nums) {
    Set<Integer> set = new HashSet<>();
    for (int x : nums) set.add(x);
    int best = 0;
    for (int x : set) {                              // the set, not nums: each value once
        if (set.contains(x - 1)) continue;           // x is mid-run; its start will walk past it
        int cur = x;
        while (set.contains(cur + 1)) cur++;         // walk the run from its start
        best = Math.max(best, cur - x + 1);          // here cur is the run's last number
    }
    return best;
}
```

**O(n) expected time, O(n) extra space.** LeetCode bounds values to ±10⁹, so `x − 1` and `cur + 1` never overflow; with the full `int` range, `Integer.MAX_VALUE + 1` wraps to `Integer.MIN_VALUE` and could fake a successor, so walk in `long` there.

</HintLadder>

**Problem: Encode and Decode Strings · length-prefix framing**

Design two methods: `encode(List<String> strs)` returns one `String`, and `decode(String str)` returns a `List<String>`, so that `decode(encode(strs))` equals `strs` for **every** list. The strings may contain any characters at all — LeetCode’s version allows all 256 ASCII characters, so commas, `#`, digits and newlines included — and may be empty; the list itself may be empty. No built-in serialization. (LeetCode Premium; free on LintCode.)

**Why delimiters alone fail:** join with commas, and `["a,b"]` and `["a", "b"]` both become `"a,b"`. Any single delimiter can appear inside the data; a rarer one only makes the failure rarer. There are two real fixes:

1. **Escaping.** Mark the special characters inside the data — say `/` becomes `//` and `;` becomes `/;` — and end each string with an unescaped `;`. Correct, but every character must be scanned and rewritten on both sides.
2. **Length prefix (framing).** Write each string as **its length, a `#`, then the string itself**. The decoder reads digits up to the first `#` — a length’s digits never contain `#`, so the first `#` really is the end of the header — then takes **exactly that many characters, without looking at what they are.** A `#` or a digit inside a string is just data.

This chapter belongs in the hashing book for a reason. **A key, a frame and a serialised message do the same job: two different things must never produce the same string.** Chapter 3’s `x + "," + y` and Chapter 5’s `"1#12#…"` were frames too.

<Trace title="Where does each parcel end?" steps={codec} takeaway="Remember: write length#string; decode by reading the digits up to the first #, then counting exactly that many characters. Never search the data for structure." />

**Why it works:** decoding keeps one promise — **at the top of the loop, `i` points at the start of a header.** That is true at `i = 0`. The header’s digits end at the first `#` after `i`; the body is exactly the next `len` characters; so `i = hash + 1 + len` is the start of the next header. By induction every string is recovered exactly, whatever it contains.

**What stays true:** after each iteration, the decoded list equals a prefix of the original list, and `i` sits exactly where the next encoded string begins.

<Reveal q="Show me the escaping version. Why does it end each string with ; instead of putting ; between strings?">

A terminator per string keeps `[]` (encoded as the empty string) apart from `[""]` (encoded as `;`). A separator between strings would turn both into the empty string.

```java id=codecEscaped
// Escaping: '/' becomes "//", ';' becomes "/;", and an unescaped ';' ends each string.
public String encodeEscaped(List<String> strs) {
    StringBuilder out = new StringBuilder();
    for (String s : strs) {
        for (char c : s.toCharArray()) {
            if (c == '/' || c == ';') out.append('/');   // escape the two special characters
            out.append(c);
        }
        out.append(';');                             // a terminator per string
    }
    return out.toString();
}

public List<String> decodeEscaped(String str) {
    List<String> strs = new ArrayList<>();
    StringBuilder cur = new StringBuilder();
    for (int i = 0; i < str.length(); i++) {
        char c = str.charAt(i);
        if (c == '/') cur.append(str.charAt(++i));   // whatever follows an escape is data
        else if (c == ';') { strs.add(cur.toString()); cur.setLength(0); }
        else cur.append(c);
    }
    return strs;
}
```

Both are O(total length). Framing never touches the bodies, so it is simpler to get right and lets a reader skip a string it doesn’t need. Escaping keeps the text readable. Real protocols use both: HTTP’s `Content-Length` is a length prefix; CSV quoting is escaping.

</Reveal>

```java id=codec
public String encode(List<String> strs) {

public List<String> decode(String str) {
    List<String> strs = new ArrayList<>();
    int i = 0;                                       // i always points at the start of a header
    while (i < str.length()) {
        int hash = str.indexOf('#', i);              // a length's digits never contain '#'
        int len = Integer.parseInt(str.substring(i, hash));
        strs.add(str.substring(hash + 1, hash + 1 + len));   // take len characters, whatever they are
        i = hash + 1 + len;
    }
    return strs;
}
```

**O(total characters) time for both, O(1) extra space beyond the output.** Java’s `length()` and `substring` both count UTF-16 units, so they agree with each other for any Java string, emoji included.

<h2 id="isomorphic">Side quest 1 · Two-way promises</h2>

**The envelope says:** can `s` be turned into `t` by replacing letters, where every occurrence of a letter becomes the same letter, and **no two different letters become the same letter**? (`"egg"` → `"add"` yes; `"foo"` → `"bar"` no.)

**The reasoning:** one map from `s`-letters to `t`-letters checks the first rule — each letter keeps its promise. It cannot see the second: on `"badc"` → `"baba"`, the forward map is perfectly consistent (b→b, a→a, d→b, c→a), yet b and d both become b. **Keep a second map, from `t` back to `s`.** A conflict in either direction means no.

<Reveal q="A famous one-liner compares put’s return values: lastS.put(s[i], i) != lastT.put(t[i], i). Why does it pass every short test and fail on long strings?">

The logic is right: two strings are isomorphic exactly when each position’s previous occurrence matches in both. But `put` returns `Integer` objects, and `!=` compares references. Previous indices up to 127 come from the Integer cache and compare equal; from 128 on, each boxing makes a new object. On `"ab"` repeated 100 times against `"cd"` repeated 100 times — clearly isomorphic — the check at index 130 compares two different `Integer(128)` objects and returns `false`.

```java fragment
if (lastS.put(s.charAt(i), i) != lastT.put(t.charAt(i), i)) return false;   // BUG: Integer != Integer
```

Fix: `!Objects.equals(lastS.put(...), lastT.put(...))`.

</Reveal>

```java id=isIsomorphic
public boolean isIsomorphic(String s, String t) {
    Map<Character, Character> forward = new HashMap<>();    // letter of s -> letter of t
    Map<Character, Character> backward = new HashMap<>();   // letter of t -> letter of s
    for (int i = 0; i < s.length(); i++) {
        char a = s.charAt(i), b = t.charAt(i);
        Character toB = forward.putIfAbsent(a, b);          // null if a had no partner yet
        Character toA = backward.putIfAbsent(b, a);
        if (toB != null && !toB.equals(b)) return false;    // a already promised to another letter
        if (toA != null && !toA.equals(a)) return false;    // b already claimed by another letter
    }
    return true;
}

// Word Pattern: letters on one side, whole words on the other. Same two promises.
public boolean wordPattern(String pattern, String s) {
    String[] words = s.split(" ");
    if (words.length != pattern.length()) return false;
    Map<Character, String> forward = new HashMap<>();
    Map<String, Character> backward = new HashMap<>();
    for (int i = 0; i < words.length; i++) {
        char p = pattern.charAt(i);
        String w = words[i];
        String toW = forward.putIfAbsent(p, w);
        Character toP = backward.putIfAbsent(w, p);
        if (toW != null && !toW.equals(w)) return false;
        if (toP != null && !toP.equals(p)) return false;
    }
    return true;
}
```

**O(n) time; O(k) space for k distinct letters (or words).** LeetCode guarantees `s` and `t` have equal length.

(Chapter 5: words match exactly when their signatures are equal.) [Solve Isomorphic Strings](https://leetcode.com/problems/isomorphic-strings/) · [Word Pattern](https://leetcode.com/problems/word-pattern/) · [Find and Replace Pattern](https://leetcode.com/problems/find-and-replace-pattern/).

<h2 id="nearby-duplicate">Side quest 2 · Only the last k letters</h2>

**The envelope says:** a repeat only counts if the two positions are **at most k apart**: `nums[i] == nums[j]` with `|i − j| ≤ k`.

**The reasoning:** a twin of `nums[i]` that counts can only be among the last k values, `nums[i − k..i − 1]`. So the set must forget anything older: keep exactly those k values. Add `nums[i]` (if `add` fails, a twin is within k); then, if the set holds more than k values, remove `nums[i − k]`, which would be too far back for the next position. The set is a sliding window — the <a href={`${BASE}dsa/lessons/sliding-window/`}>Sliding Window</a> book’s fixed pane, holding a set instead of a sum.

<Figure caption="[1, 2, 3, 1] with k = 3. Before reading index 3, the set holds the last three values {1, 2, 3}. add(1) fails: the other 1 is at index 0, exactly 3 positions back. With k = 2, the 1 at index 0 would already have been removed, and the answer would be false.">
  <ArrayStrip values={[1, 2, 3, 1]} tones={{ 0: 'blue', 3: 'hot' }} regions={[{ from: 0, to: 2, label: 'the set: last k = 3 values', tone: 'blue' }]} pointers={[{ at: 3, label: 'add(1) fails' }]} />
</Figure>

<HintLadder hints={hints.nearby}>

```java id=containsNearbyDuplicate
public boolean containsNearbyDuplicate(int[] nums, int k) {
    Set<Integer> window = new HashSet<>();           // the values at the last k positions
    for (int i = 0; i < nums.length; i++) {
        if (!window.add(nums[i])) return true;       // a twin at most k positions back
        if (window.size() > k) window.remove(nums[i - k]);   // too far back for position i + 1
    }
    return false;
}
```

**O(n) expected time, O(min(n, k)) space.** All values in the window are distinct (a repeat would have returned), so the set’s size is the number of positions it covers. With `k = 0`, every value is removed as soon as it is added, and the answer is always false — correct, since `i ≠ j` is required.

</HintLadder>

<Reveal q="Can you do it without the window, with a map instead?">

Yes: map each value to the **last** index where it appeared. At index `i`, if `nums[i]` was last seen at `j` and `i − j ≤ k`, return true; then overwrite with `i`. Keeping the latest index is right here, because the closest earlier twin is the one most likely to be within k. Same O(n) time; O(n) space instead of O(k).

</Reveal>

**Transfer test:** Contains Duplicate III relaxes “equal” to “within `valueDiff` of each other”. A set can no longer answer with one lookup. Which structure answers “is any value in `[x − d, x + d]`?” — and what trick with buckets of width `d + 1` restores O(1)? [Solve Contains Duplicate II](https://leetcode.com/problems/contains-duplicate-ii/).

<h2 id="top-k">Side quest 3 · The busiest addresses</h2>

**The envelope says:** return the **k values that appear most often** (LeetCode guarantees the answer is unique), and do better than sorting the counts.

**The reasoning:** count with `merge`, as in Chapter 4. Now you need the k largest counts. The heap in the <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> book does it in O(n log k). But **no count can exceed n**, so the counts can index an array: bucket `f` holds every value that appeared exactly `f` times. Walk the buckets from `n` down and take values until you have k. That is a bucket sort, and it is O(n).

<Figure caption="[1, 1, 1, 2, 2, 3], k = 2. Counts: 1 appears 3 times, 2 twice, 3 once. Buckets by count: bucket 3 holds 1, bucket 2 holds 2, bucket 1 holds 3. Walking down from bucket 6 takes 1, then 2.">
  <ArrayStrip name="bucket f" values={['·', '3', '2', '1', '·', '·', '·']} tones={{ 3: 'hot', 2: 'hot', 1: 'done' }} pointers={[{ at: 3, label: 'take 1' }, { at: 2, label: 'take 2', tone: 'blue' }]} />
</Figure>

<HintLadder hints={hints.topK}>

```java id=topKFrequent
public int[] topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int x : nums) freq.merge(x, 1, Integer::sum);
    List<Integer>[] byFreq = new List[nums.length + 1];  // byFreq[f] = values seen exactly f times
    for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
        int f = e.getValue();
        if (byFreq[f] == null) byFreq[f] = new ArrayList<>();
        byFreq[f].add(e.getKey());
    }
    int[] answer = new int[k];
    int filled = 0;
    for (int f = nums.length; f >= 1 && filled < k; f--)  // most frequent first
        if (byFreq[f] != null)
            for (int x : byFreq[f])
                if (filled < k) answer[filled++] = x;
    return answer;
}
```

**O(n) expected time, O(n) space.** (`new List[n + 1]` is a raw array, because Java can’t create generic arrays; the compiler warns, and the code is safe.)

</HintLadder>

<Reveal q="When would you still choose the heap?">

When n is huge or streaming and k is small. The buckets need O(n) memory up front, sized by the input length; a heap of size k needs only O(k) beyond the counts, and it keeps working as new values arrive. Interviewers often ask for both.

</Reveal>

**Transfer test:** Sort Characters By Frequency wants the whole string rearranged, most frequent characters first. Which part of this solution stays, and what replaces “take k”? [Solve Top K Frequent Elements](https://leetcode.com/problems/top-k-frequent-elements/) · [Sort Characters By Frequency](https://leetcode.com/problems/sort-characters-by-frequency/).

<h2 id="sudoku">Side quest 4 · Twenty-seven small registers</h2>

**The envelope says:** a 9 × 9 Sudoku board, partly filled. Is it **valid** — no digit repeated in any row, any column or any 3 × 3 box? (It need not be solvable.)

**The reasoning:** “seen before?” 27 times over. Give every row, every column and every box its own small set of digits. For each filled cell, check its digit against the three sets it belongs to, then add it to all three. Digits are 1 to 9, so each set can be a `boolean[9]`: a set with nine fixed keys, like Chapter 4’s `int[26]`. The only real decision is **numbering the boxes 0..8**: `box = (r / 3) * 3 + c / 3`, left to right, top to bottom.

<Figure caption="Box numbers for every cell: (r / 3) * 3 + c / 3. Rows 0–2 are boxes 0, 1, 2; rows 3–5 are 3, 4, 5; rows 6–8 are 6, 7, 8.">
  <ArrayStrip name="rows 0–2" values={[0, 0, 0, 1, 1, 1, 2, 2, 2]} />
  <ArrayStrip name="rows 3–5" values={[3, 3, 3, 4, 4, 4, 5, 5, 5]} tones={{ 0: 'hot' }} />
  <ArrayStrip name="rows 6–8" values={[6, 6, 6, 7, 7, 7, 8, 8, 8]} />
</Figure>

<HintLadder hints={hints.sudoku}>

```java id=isValidSudoku
public boolean isValidSudoku(char[][] board) {
    boolean[][] row = new boolean[9][9], col = new boolean[9][9], box = new boolean[9][9];
    for (int r = 0; r < 9; r++)
        for (int c = 0; c < 9; c++) {
            if (board[r][c] == '.') continue;
            int d = board[r][c] - '1';               // digits 1..9 -> 0..8
            int b = (r / 3) * 3 + c / 3;             // boxes 0..8, left to right, top to bottom
            if (row[r][d] || col[c][d] || box[b][d]) return false;   // seen before?
            row[r][d] = col[c][d] = box[b][d] = true;
        }
    return true;
}
```

**O(81) = O(1) time and space** for a fixed 9 × 9 board; O(N²) for an N × N board. An equally good version files strings like `"5 in row 0"`, `"5 in col 3"`, `"5 in box 1"` in one `HashSet<String>` — a composite key with its separators spelled out.

</HintLadder>

**Catch the bug:** `r / 3 + c / 3` for the box. Cell (0, 3) and cell (3, 0) both get box 1, though they sit in boxes 1 and 3. A board with a 5 in each of those cells is valid, and this version rejects it.

**Transfer test:** Sudoku Solver fills the board by backtracking. Which three structures from this quest make each “can I place d here?” check O(1), and what must you undo when you take a digit back out? [Solve Valid Sudoku](https://leetcode.com/problems/valid-sudoku/).

<h2 id="happy-number">Side quest 5 · The letter that keeps coming back</h2>

**The envelope says:** start from `n` and repeatedly replace it by the **sum of the squares of its digits**. Return true if it reaches 1. (19 → 1 + 81 = 82 → 64 + 4 = 68 → 36 + 64 = 100 → 1: happy.)

**The reasoning:** if it never reaches 1, the sequence must repeat — and a repeat is “seen before?”. Why must it repeat? A number with d ≥ 4 digits is at least 10^(d−1), but its digit-square sum is at most 81d, which is smaller. So the numbers fall below 1000, and from there they never exceed 3 × 81 = 243. Trapped among finitely many values, the sequence either reaches 1 (which maps to itself) or cycles. Check every value against a set; stop at 1 or at the first repeat.

<Figure caption="Every unhappy number falls into the same eight-number cycle. Checked by brute force for every start below 1000; larger starts drop below 1000 in a step or two.">
  <Mermaid code={`flowchart LR
  A["19"] --> B["82"] --> C["68"] --> D["100"] --> E(["1"])
  E --> E
  F["2"] --> G["4"]
  G --> H["16"] --> I["37"] --> J["58"] --> K["89"] --> L["145"] --> M["42"] --> N["20"] --> G`} />
</Figure>

<Reveal q="The set costs memory. Can you detect the cycle without remembering anything?">

Yes: **Floyd’s tortoise and hare**, from the <a href={`${BASE}dsa/lessons/linked-lists/`}>Linked Lists</a> book. Treat “next number” as a pointer. A slow walker takes one step, a fast walker two; on a cycle the fast one laps the slow one and they meet. If the sequence reaches 1, the fast walker gets there first and stays. O(1) space. Both versions are below.

</Reveal>

<HintLadder hints={hints.happy}>

```java id=isHappy
public boolean isHappy(int n) {
    Set<Integer> seen = new HashSet<>();
    while (n != 1 && seen.add(n)) n = next(n);       // stop at 1, or at the first repeat
    return n == 1;
}

// Floyd's version: O(1) memory. On a cycle, the fast walker laps the slow one.
public boolean isHappyFloyd(int n) {
    int slow = n, fast = next(n);
    while (fast != 1 && slow != fast) {
        slow = next(slow);
        fast = next(next(fast));
    }
    return fast == 1;
}

private int next(int n) {                            // the sum of the squares of the digits
    int sum = 0;
    while (n > 0) { int d = n % 10; sum += d * d; n /= 10; }
    return sum;
}
```

**O(log n) per step**, and after the first step the values are at most 810 (`Integer.MAX_VALUE` has ten digits), so the number of steps is bounded by a small constant. Set: O(1) extra space in practice (a few hundred values at most); Floyd: O(1) strictly.

</HintLadder>

**Transfer test:** for an unhappy number, return the **length of the cycle** it falls into. A set can’t tell you; which structure from Chapter 2 can? (A map from each value to the step where it first appeared: at the first repeat, the cycle length is the current step minus the stored one.) <h2 id="first-unique">Side quest 6 · The first letter nobody else sent</h2>

**The envelope says:** return the index of the **first** character in `s` that appears exactly once, or −1. Order matters now.

**The reasoning:** counting (Chapter 4) tells you which characters are unique, but the counts have forgotten the order. The string hasn’t. So count in one pass, then walk **the string** a second time and return the first index whose character has count 1.

<Reveal q="Why not scan the 26 counts for the first count of 1?">

Because the count array is in alphabetical order, not string order. On `"loveleetcode"` the unique letters are v, t, c and d; scanning the counts finds c first and returns its index, 8. The first unique character in the string is v, at index 2.

</Reveal>

<HintLadder hints={hints.firstUnique}>

```java id=firstUniqChar
public int firstUniqChar(String s) {
    int[] count = new int[26];
    for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
    for (int i = 0; i < s.length(); i++)             // walk the string: it remembers the order
        if (count[s.charAt(i) - 'a'] == 1) return i;
    return -1;
}
```

**O(n) time, O(1) extra space.** For a stream where you can’t make a second pass, keep the candidates in insertion order — a `LinkedHashMap`, or a queue whose front you pop while its character has repeated.

</HintLadder>

<h2 id="choose-the-tool">When the wall is the wrong tool</h2>

<Scene title="The archive with one shelf" mood="storm">

The regional archive sends for help. Two hundred million registration numbers sit in one long ledger that fills their only shelf, and they want to know whether any number was issued twice.

You reach for the wall. The Keeper stops your hand and does the arithmetic on the back of an envelope: every filed letter needs its own envelope, its own tag, its own slot — many times the paper of the ledger itself. There is no room for a second shelf, let alone a wall.

*"The wall buys speed with space,"* she says. *"When there is no space to spend, put the ledger itself in order. Twins sit side by side."*

</Scene>

A hash table is the right tool when you need **fast membership, counting or grouping, and you can afford the memory**. It is the wrong tool when:

- **Memory is the binding constraint.** An `int[]` stores a value in 4 bytes. A `HashSet<Integer>` on a 64-bit JVM typically spends around 50 bytes or more per entry (the entry node, the boxed `Integer`, the slot in the table). For 200 million values that is the difference between under 1 GB and roughly 10 GB. **Sort in place and compare neighbours**: O(n log n) time, almost no extra memory.
- **The question is about order.** The next value above `x`, the smallest, a range of keys, sorted output: a `HashSet` keeps no order. Use a **`TreeSet` / `TreeMap`** (a red-black tree): O(log n) per add, remove and lookup, plus `floor`, `ceiling`, `higher`, `first`, `last` and in-order iteration.
- **The input is already sorted.** Pairs, duplicates and merges on sorted data need no memory: <a href={`${BASE}dsa/lessons/two-pointers/`}>two pointers</a>, O(1) space.
- **The alphabet is tiny and fixed.** 26 letters, 10 digits, 128 ASCII codes: a plain array is a faster, smaller map.
- **You need a guarantee, not an average.** Expected O(1) can degrade under adversarial keys (hash flooding). A tree gives O(log n) every time.
- **You need insertion order.** `LinkedHashMap` / `LinkedHashSet` keep it, for a few bytes more per entry.

<Reveal q="Contains Duplicate: HashSet or TreeSet?">

Both are correct. `HashSet` is O(n) expected; `TreeSet` is O(n log n) guaranteed and keeps the values sorted. Choose `HashSet` unless you also need order, or guarantees against adversarial input. Say why — the reason is the recognition rep, not the answer.

</Reveal>

<h2 id="exit-ticket">The sorter’s exam · Build a solution with the labels removed</h2>

<Scene title="No chapter titles" mood="dawn">

On the morning of the exam the Keeper hands you three envelopes with no chapter names and no hints, and points at the three questions carved over the wall of pigeonholes.

*"Pick one,"* she says. *"Before you write a line, tell me what you will file, what you will ask the wall, and which comes first."*

Choose one. Keep the tutorial code closed. Write down the key, the lookup and the order of operations before coding.

1. **The brick wall.** A wall is given as rows of brick widths; every row has the same total width. Draw one vertical line from top to bottom crossing as few bricks as possible (running along an edge between two bricks doesn’t cross either; the wall’s two outer sides are not allowed). Return the number of bricks crossed. Test: one row, identical rows, rows of a single brick.
2. **Shifted twins.** Group strings where one becomes another by shifting every letter by the same amount around the alphabet: `"abc"`, `"bcd"` and `"xyz"` belong together, and so do `"az"` and `"ba"`. Test single letters, the empty string, and wrap-around.
3. **Pairs at distance k.** Count the distinct pairs of values `(a, b)` in an array with `b − a = k`, for a given `k ≥ 0`. Test `k = 0` with duplicates, negative values, and no pairs.

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**The brick wall:** a line crosses the fewest bricks where the most rows have an edge. Walk each row, keeping a running width, and count each inner edge position (every running width except the row’s last) in a map. The answer is rows minus the largest count — or rows, if no row has an inner edge. Chapter 4’s counting, keyed by position.

**Shifted twins:** a signature that ignores the shift: the differences between neighbouring letters, mod 26, **with separators** — or shift each string so its first letter becomes `a`. `"az"` and `"ba"` both have difference 25. Chapter 5, with a different key.

**Pairs at distance k:** count values in a map. For `k > 0`, count the distinct `x` with `x + k` present; for `k = 0`, count the values that appear at least twice. The `k = 0` case is the trap — a plain set lets every value pair with itself, the very bug Chapter 2’s ask-before-file avoids.

Now explain why a slightly wrong version fails one of your tests — a key without separators, a value pairing with itself, the outer edge counted as an edge. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

<h2 id="cheat-sheet">The Keeper’s sorting notes</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Has anything repeated? | `HashSet`; `if (!seen.add(x)) return true` | The set holds exactly the distinct values before `i` |
| A pair summing to a target, unsorted, original positions | Map value → index; ask for `target − x`, then file `x` | The register holds only earlier positions |
| Your own class, or a pair, as a key | A `record`, or `equals` + `hashCode` from the same final fields | Equal keys get equal stamps; filed keys never change |
| Same letters, any order (lowercase) | `int[26]`: +1 for s, −1 for t, all zero | Equal lengths; every count ends at 0 |
| Group items that are “the same” up to order | Map from canonical key → list, with `computeIfAbsent` | `key(a)` equals `key(b)` exactly when they belong together |
| Longest consecutive run, unsorted, O(n) | Set; walk only from `x` with `x − 1` absent | Every number is walked exactly once |
| Many strings through one string | `length#string`; decode by counting | `i` always points at a header |
| A one-to-one letter replacement | Two maps, forward and backward | No letter has two partners in either direction |
| A twin within k positions | A set of the last k values | The set holds exactly `nums[i − k..i − 1]` |
| The k most frequent values | Count map, then buckets indexed by frequency | No frequency exceeds n |
| A grid with no-repeat rules | 27 small sets; box `(r / 3) * 3 + c / 3` | Each digit at most once per row, column and box |
| Does a sequence loop forever? | A set of seen states, or Floyd | A repeat means a cycle |
| The first item that appears exactly once | Count, then a second pass in the original order | The input remembers order; the counts don’t |
| Order questions: next above x, sorted output | `TreeSet` / `TreeMap`, O(log n) | Hashing gives membership, never order |

The wall does **not** come free: every map and set here costs O(n) extra memory (or O(k), O(26)). Only the `int[26]` and `boolean[9]` versions and Floyd’s cycle check run in O(1) extra space. Count every structure you build.

## Five bugs the Keeper keeps in her pocket

1. **Filing before asking.** The current value finds itself: Two Sum on `[3, 2, 4]` with target 6 returns `[0, 0]`.
2. **A key that breaks the contract.** `equals` without `hashCode` (equal keys in different holes), or a key mutated after filing (stranded in the wrong hole). Use records or immutable fields.
3. **`==` on boxed numbers.** It works up to 127 and fails at 128. Compare `Integer`s with `.equals`, or unbox.
4. **Keys that collide by construction.** Concatenation without separators (`"1" + "12"` and `"11" + "2"`), `int[]` used as a key (identity, not contents), a delimiter where a length was needed.
5. **Walking from every number.** Longest Consecutive without the `x − 1` check, or looping over `nums` instead of the set, quietly turns O(n) back into O(n²).

**Look these up yourself** — real ideas this book didn’t have room for:

- **Open addressing and linear probing** — store entries in the array itself instead of in chains; Python’s `dict` and Java’s `IdentityHashMap` work this way.
- **Hash flooding and seeded hashing (SipHash)** — why many languages randomise their string hash per process, after attacks that forced every key into one bucket.
- **Robin Hood and cuckoo hashing** — schemes that cut the variance of probe lengths, or guarantee O(1) worst-case lookups.
- **Bloom filters** — “definitely not seen / probably seen” in a few bits per item, when even a set is too big.
- **Rolling hashes (Rabin–Karp)** — hash every window of a string in O(1) per slide; on your deferred list for now.
- **Consistent hashing** — the system-design cousin: adding a server moves only a small fraction of keys.
- **LinkedHashMap in access order** — an LRU cache in a dozen lines with `removeEldestEntry`.
- **Universal and perfect hashing** — choosing the hash function at random to turn “expected” into a provable guarantee.
