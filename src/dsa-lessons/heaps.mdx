<h2 id="prologue">Prologue · What a heap problem looks like</h2>

A **heap** keeps one value within reach at all times: the smallest (a **min-heap**) or the largest (a **max-heap**). Values come and go; the best one is always on top. Java calls it a `PriorityQueue`.

| Operation | Cost | Meaning |
|---|---|---|
| `peek()` | O(1) | Look at the top |
| `offer(x)` | O(log n) | Add a value; it climbs to its place |
| `poll()` | O(log n) | Remove the top; another value sinks into its place |

### How to recognise the pattern

You need the min or max of a collection **again and again while it changes**:

- "kth largest", "top k", "k closest": the best k of many.
- "from a stream", "too much data to hold": keep only k values, O(k) memory.
- "running median": two heaps that meet in the middle.
- "merge k sorted ...": a heap of the k current fronts.
- "always do the most urgent / most frequent / cheapest thing next": a heap inside a simulation loop.

### The brute force it replaces

Re-scanning for the best (O(n) per question) or re-sorting (O(n log n) per question). With 100,000 changes and a question after each, scanning costs about 10¹⁰ steps. A heap costs about 100,000 × log₂ 100,000 ≈ 1.7 million.

### Three questions before every move

1. **What is settled?** Who is on top, and why nothing below can beat it.
2. **Why is this move safe?** Which value may leave, or which swap restores order without breaking anything above it.
3. **When do I stop?** When the moving value fits, when the input is empty, or when only the answer remains.

<h2 id="build-the-pyramid">Chapter 1 · Build a min-heap</h2>

### Problem

Implement a min-heap from scratch with `push`, `pop` and `peek`, stored in a plain array. Then know the Java tool, `PriorityQueue`, that you will actually use.

Example: push 0 into `[1, 3, 2, 7, 4, 5, 8]` and the array becomes `[0, 1, 2, 3, 4, 5, 8, 7]`.

### How to recognise it

- "Implement a priority queue / heap", or "why is `poll()` O(log n)?"
- Any time you say "best item first" and the interviewer asks what is underneath.

### Brute force

Keep a plain list. If it stays **unsorted**, `peek` and `poll` scan for the minimum: O(n). If it stays **sorted**, `peek` is O(1) but every insert shifts elements: O(n). Either way one operation costs O(n).

### Intuition

A heap does not sort everything. It keeps a weaker promise that is cheaper to maintain: **every parent is at most its children**. Siblings and cousins are in no order. That is enough to put the minimum at the root, and a repair after one change only has to walk a single path from a leaf to the root (or back), about log₂ n steps.

A heap is a **complete binary tree**: every row is full except perhaps the last, which fills from the left. With no gaps you need no pointers. Number the seats row by row and store them in an array:

- The **parent** of index i is `(i - 1) / 2` (integer division).
- The **children** of index i are `2i + 1` and `2i + 2`, when they are less than the size.
- Indexes from `n / 2` to `n - 1` are leaves. The height is ⌊log₂ n⌋.

The array is **not** sorted: `[1, 3, 2, 7, 4, 5, 8]` is a perfectly good heap.

**Push (sift-up).** Put the value in the next free seat, index `size`, so the tree stays complete. Then, while it is smaller than its parent, swap them.

### Algorithm

1. **push(x):** write x at index `size`, increase `size`, then sift up from that index.
2. **Sift up from i:** while `i > 0` and the parent is bigger than `a[i]`, swap with the parent and move to it. Otherwise stop.
3. **pop():** save `a[0]`, move the last value to index 0, decrease `size`, then sift down from index 0.
4. **Sift down from i:** pick the smaller child (the left one if there is no right). If it is smaller than `a[i]`, swap and move to it. Otherwise, or if there are no children, stop.
5. **peek():** return `a[0]`.
6. **Build from n values in O(n):** sift down every parent, from index `n / 2 − 1` back to 0.

### Java solution

<HintLadder hints={hints.minHeap}>

```java id=minHeap
class MinHeap {
    private int[] a = new int[8];
    private int size = 0;

    public int size() { return size; }

    public int peek() {
        if (size == 0) throw new NoSuchElementException();
        return a[0];                                  // the root: smallest of all
    }

    public void push(int x) {
        if (size == a.length) a = Arrays.copyOf(a, size * 2);
        a[size] = x;                                  // take the next free seat...
        siftUp(size++);                               // ...then climb while smaller than the parent
    }

    public int pop() {
        int top = peek();
        a[0] = a[--size];                             // the last seat's occupant moves to the root...
        siftDown(0);                                  // ...then sinks below any smaller child
        return top;
    }

    // Build from n values in O(n): sink every parent, starting from the last parent.
    public void buildFrom(int[] values) {
        a = Arrays.copyOf(values, Math.max(8, values.length));
        size = values.length;
        for (int i = size / 2 - 1; i >= 0; i--) siftDown(i);
    }

    private void siftUp(int i) {
        while (i > 0) {
            int parent = (i - 1) / 2;
            if (a[parent] <= a[i]) return;            // order holds: stop climbing
            swap(i, parent);
            i = parent;
        }
    }

    private void siftDown(int i) {
        while (true) {
            int left = 2 * i + 1, right = left + 1, smallest = i;
            if (left < size && a[left] < a[smallest]) smallest = left;
            if (right < size && a[right] < a[smallest]) smallest = right;
            if (smallest == i) return;                // no child is smaller: stop sinking
            swap(i, smallest);
            i = smallest;
        }
    }

    private void swap(int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }
}
```

**push and pop: O(log n). peek: O(1). buildFrom: O(n). Space: O(n).** This `pop` throws on an empty heap, like `PriorityQueue.remove()`; `PriorityQueue.poll()` returns `null` instead.

</HintLadder>

### Why it works

- **Settled:** the rule "parent ≤ children" holds everywhere except at the one value that is moving, and only between it and its neighbours on its path.
- **Sift-up is safe:** the parent that steps down was already at most everything below it, so it is fine in its new seat. The climber is smaller than that parent, so it is also smaller than its new sibling.
- **Sift-down is safe:** the child that rises was the smaller child, so it is at most its sibling, and it was smaller than the sinking value, so it is at most that too.
- **When we stop:** sift-up stops at the root or when the parent is at most the value. Sift-down stops when no child is smaller, or there are no children.

### Complexity

- **push, pop: O(log n).** Each step moves one row and there are ⌊log₂ n⌋ rows.
- **peek: O(1).** It reads index 0.
- **buildFrom: O(n).** Most values are near the bottom and sink almost nowhere (see the Reveal below).
- **Space: O(n)** for the array.

### Edge cases and mistakes

- Pop from a heap with one value: the "last value" is the root itself. This `pop` throws on an empty heap, like `PriorityQueue.remove()`; `PriorityQueue.poll()` returns `null`.
- **The classic bug:** a sift-down that only ever looks at the **left** child. Pop from `[1, 4, 2, 5, 6, 3]`: 3 moves to the root, sees its left child 4, and stops, so `peek()` says 3 while 2 is still inside. Compare with both children, every time, and swap with the smaller.
- Growing the array: double it, never grow by one.

**The tool you will actually use.** `java.util.PriorityQueue` is a **min-heap by default**. A max-heap is the same class with a reversed comparator. Know the three spellings cold:

```java id=spellings
PriorityQueue<Integer> minHeap = new PriorityQueue<>();                          // smallest on top
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder()); // largest on top
PriorityQueue<int[]> bySecond = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1])); // any key you like
```

| PriorityQueue method | Cost (from the Javadoc) |
|---|---|
| `offer`, `add`, `poll`, `remove()` | O(log n) |
| `peek`, `element`, `size` | O(1) |
| `remove(Object)`, `contains(Object)` | O(n): it scans the array |

Two Java facts interviewers love:

- **Write comparators with `Integer.compare`, never subtraction.** `(a, b) -> a[1] - b[1]` looks fine until the difference overflows. With 2,000,000,000 and −2,000,000,000, the subtraction wraps to a negative number, and the bigger value lands on top of your min-heap.

```java fragment
PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> a[1] - b[1]); // BUG near ±2^31
```

- **Iterating a PriorityQueue is not sorted order.** Offer 3, 1, 2 and print it: you get `[1, 3, 2]`, the array layout. Only repeated `poll()` drains in order. Printing a heap while debugging will lie to you.

<h2 id="the-door-guard">Chapter 2 · Kth Largest Element in an Array</h2>

### Problem

Given an integer array and `k`, return the kth largest element (the kth in sorted order, counting duplicates separately).

`[3, 2, 1, 5, 6, 4]`, k = 2 gives `5`.

### How to recognise it

- "kth largest", "top k", "k best", "k smallest".
- The data may be a **stream**, or too big to sort or store: the follow-up asks for O(k) memory.
- You only need one value (the kth), or a small group (the k best), not a full ordering.

### Brute force

Sort, then index from the end: O(n log n) time. It is correct, but it sorts all n values to learn about one position, and it cannot work on a stream because it needs every value in memory.

### Intuition

You only need the k best values seen so far. When a newcomer arrives, ask one question: **who does it have to beat?** Not the champion, only the weakest of the current k, because that is the one who would lose their seat. So keep the k best in a structure that shows the weakest at a glance: a **min-heap of size k**. Its root, the smallest of the k largest, is the **guard** (our name for that root).

That feels backwards, so say it out loud: to find the kth **largest**, keep a **min**-heap. A newcomer either beats the guard (the guard is evicted and the newcomer joins) or is turned away. When the input ends, the guard is the weakest of the k largest, which is exactly the kth largest.

### Dry run

### Algorithm

1. Create an empty min-heap.
2. For each value x: `offer(x)`.
3. If the heap now holds more than k values, `poll()` (the smallest leaves).
4. After the last value, `peek()` is the answer.

"Offer, then poll if too big" gives the same verdict as comparing x with the guard first.

### Java solution

<HintLadder hints={hints.kthLargest}>

```java id=findKthLargest
public int findKthLargest(int[] nums, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>();  // MIN-heap: the guard stands on top
    for (int x : nums) {
        heap.offer(x);
        if (heap.size() > k) heap.poll();                 // k + 1 inside: the weakest leaves
    }
    return heap.peek();                                   // weakest of the k largest = kth largest
}
```

**O(n log k) time, O(k) space.** Duplicates count separately: in `[3, 2, 3, 1, 2, 4, 5, 5, 6]`, the 4th largest is 4.

</HintLadder>

### Why it works

- **Settled:** after each value, the heap holds exactly the k largest values seen so far (or all of them, before k have arrived).
- **Why the move is safe:** a newcomer x that beats the guard g makes g the (k + 1)th largest, so g can leave. A newcomer with x ≤ g has at least k seen values ahead of it, so it can never be among the k largest. (If x equals g, swapping one for the other changes nothing.)
- **When we stop:** when the input ends. The guard is then the kth largest.

### Complexity

- **Time O(n log k):** n values, each costing one offer and at most one poll on a heap of size k + 1.
- **Space O(k):** the heap never grows past k + 1. That bound is why this beats sorting and why it works on a **stream** you could never store. Say that word in the interview.

| Approach | Time | Extra space | Works on a stream? |
|---|---|---|---|
| Sort, then index | O(n log n) | depends on the sort | no |
| Max-heap of everything, poll k times | O(n + k log n) with heapify | O(n) | no |
| **Size-k min-heap** | **O(n log k)** | **O(k)** | **yes** |
| Quickselect ([when not to use a heap](#choose-the-tool)) | O(n) expected, O(n²) worst | O(1), reorders input | no |

### Edge cases and mistakes

- Duplicates count separately: in `[3, 2, 3, 1, 2, 4, 5, 5, 6]`, the 4th largest is 4.
- k = 1 (a running maximum) and k = n (the minimum).
- **The classic bug:** `new PriorityQueue<>(Comparator.reverseOrder())` here returns 2 on `[3, 2, 1, 5, 6, 4]`, k = 2. A max-heap trimmed to k throws away the largest value every time and keeps the k **smallest**. The guard must be the weakest of the best, so the heap must be a **min**-heap.

### Practice

<Trace title="Beat the guard or bounce" steps={kthLargest} takeaway="Remember: a min-heap of size k. The root is the weakest of the best k: beat it to enter. At the end, the root is the answer." />

<Reveal q="Why not a max-heap? And what if k is huge, say k = n − 2?">

A max-heap trimmed to size k evicts its **largest** value every time, so it keeps the k **smallest**. On `[3, 2, 1, 5, 6, 4]` with k = 2 it returns 2, not 5. An untrimmed max-heap of everything is correct, but needs O(n) space and fails the “it’s a stream” follow-up.

When k is close to n, flip the question: the kth largest is the (n − k + 1)th **smallest**. With k = n − 2 that is the 3rd smallest, so keep a max-heap of size 3 instead of a min-heap of size n − 2.

</Reveal>

**Variations to try:** return all k values, not just the kth; the kth **smallest** (flip the heap); the kth largest after every new number (Side quest 1).

<h2 id="top-k-frequent">Chapter 3 · Top K Frequent Elements</h2>

### Problem

Given an integer array and `k`, return the k most frequent values, in any order. The answer is guaranteed to be unique.

`[1, 1, 1, 2, 2, 3]`, k = 2 gives `[1, 2]`.

### How to recognise it

- "Most frequent", "top k by count".
- The ranking key is not the value itself but something you compute first (a count).

### Brute force

Count with a map, sort the distinct values by count, take the first k: O(n + u log u) for u distinct values. When u is close to n that is a full sort to keep k values.

### Intuition

It is Chapter 2 with a different key. Count first, then run the same size-k min-heap over the distinct values, but **compare counts, not values**. The guard is the least frequent of the chosen k, and any more frequent value can evict it.

  <ArrayStrip name="count" values={[3, 2, 1]} indices={false} tones={{ 0: 'done', 1: 'done', 2: 'out' }} />

### Dry run

<DryRun title="Top K Frequent: heap ordered by count" frames={topKFrequentFrames([1, 1, 1, 2, 2, 3], 2)} predict />

### Algorithm

1. Count each value with a `HashMap`.
2. Create a min-heap ordered by `count.get(value)`.
3. For each distinct value: `offer` it, and `poll` if the size passes k.
4. Poll the heap into the result array, filling from the back so the most frequent ends up first.

### Java solution

<HintLadder hints={hints.topK}>

```java id=topKFrequent
public int[] topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> count = new HashMap<>();
    for (int x : nums) count.merge(x, 1, Integer::sum);
    // MIN-heap by frequency: the least frequent of the chosen k guards the door.
    PriorityQueue<Integer> heap = new PriorityQueue<>(
        (a, b) -> Integer.compare(count.get(a), count.get(b)));
    for (int value : count.keySet()) {
        heap.offer(value);
        if (heap.size() > k) heap.poll();
    }
    int[] result = new int[k];
    for (int i = k - 1; i >= 0; i--) result[i] = heap.poll();  // most frequent ends up first
    return result;
}
```

With u distinct values: **O(n + u log k) time, O(u + k) space.** The lambda reads `count`, which is never reassigned, so Java accepts it.

</HintLadder>

### Why it works

- **Settled:** after each distinct value is offered, the heap holds the k most frequent values offered so far, and never more than k entries.
- **Why the move is safe:** a value counted more often than the guard makes the guard the (k + 1)th most frequent, so it leaves. A value counted no more often than the guard has k values at least as frequent ahead of it.
- **When we stop:** when every distinct value has been offered.

### Complexity

- **Time O(n + u log k):** one pass to count, then u heap operations on a heap of size k.
- **Space O(u + k):** the count map plus the heap.

### Edge cases and mistakes

- k equal to the number of distinct values; a single distinct value; negative values.
- **The classic bug:** a heap ordered by **value** keeps the k biggest values. On `[1, 1, 1, 2, 2, 3]`, k = 2, it returns 2 and 3, but 1 is the most frequent. Order by `count.get(...)`.

### Practice

<Trace title="What does the guard measure?" steps={topK} takeaway="Remember: count with a map, then keep k values in a min-heap ordered by count. The least frequent of the chosen k guards the door." />

<Reveal q="Counts can never exceed n. Can you avoid the heap entirely?">

Yes: **bucket sort by frequency.** Make buckets 0 to n, put each value into the bucket of its count, then walk from bucket n downward collecting values until you have k. That is O(n) time and O(n) space. Mention it when asked for better than O(n log k), then use the heap anyway unless pushed: the heap version is the one that generalises (a stream, a custom tie-break).

```java id=topKFrequentBuckets
public int[] topKFrequentBuckets(int[] nums, int k) {
    Map<Integer, Integer> count = new HashMap<>();
    for (int x : nums) count.merge(x, 1, Integer::sum);
    List<List<Integer>> bucket = new ArrayList<>();     // bucket[f] = values seen exactly f times
    for (int f = 0; f <= nums.length; f++) bucket.add(new ArrayList<>());
    for (Map.Entry<Integer, Integer> e : count.entrySet()) bucket.get(e.getValue()).add(e.getKey());
    int[] result = new int[k];
    int filled = 0;
    for (int f = nums.length; f >= 1 && filled < k; f--)
        for (int value : bucket.get(f))
            if (filled < k) result[filled++] = value;
    return result;
}
```

</Reveal>

### Problem

Given points `[x, y]` and `k`, return the k points closest to the origin, in any order.

`[[3, 3], [5, -1], [-2, 4]]`, k = 2 gives `[[3, 3], [-2, 4]]`.

### How to recognise it

- Chapter 2's "k best", but **smaller is better**: closest, cheapest, earliest.

### Brute force

Compute every distance, sort, take the first k: O(n log n). It works, but it sorts everything to keep k.

### Intuition

Flip everything. To keep the k **smallest** distances, the one in danger is the **largest** of them: the farthest point still inside. So the heap is a **max-heap** by distance, trimmed to size k. Do not memorise "max-heap for smallest". Ask: **who among the chosen is in danger?**

Compare **squared** distances, x² + y². The square root grows whenever its input grows, so the order is identical and you avoid floating point.

### Algorithm

1. Create a max-heap ordered by squared distance.
2. For each point: `offer` it, and `poll` if the size passes k (the farthest leaves).
3. Return the heap's contents (any order is accepted).

### Java solution

<HintLadder hints={hints.kClosest}>

```java id=kClosest
public int[][] kClosest(int[][] points, int k) {
    // MAX-heap by squared distance: the FARTHEST of the chosen k guards the door.
    PriorityQueue<int[]> heap = new PriorityQueue<>(
        (a, b) -> Long.compare(dist(b), dist(a)));
    for (int[] p : points) {
        heap.offer(p);
        if (heap.size() > k) heap.poll();                 // evict the farthest of k + 1
    }
    return heap.toArray(new int[0][]);                    // any order is accepted
}

private long dist(int[] p) {
    return (long) p[0] * p[0] + (long) p[1] * p[1];       // squared: no sqrt, no rounding
}
```

**O(n log k) time, O(k) space.** The answer may be in any order, so returning the heap’s array is fine. The squares are computed in `long`: the problem’s coordinates (|x| ≤ 10⁴) fit in `int`, but 50,000² + 50,000² does not.

</HintLadder>

### Why it works

- **Settled:** after each point, the heap holds the k closest points seen so far, with the farthest of them on top.
- **Why the move is safe:** a closer newcomer evicts the farthest chosen point, which is now the (k + 1)th closest. A farther newcomer has k closer points ahead of it, so it can never be among the k closest.
- **When we stop:** when the points run out.

### Complexity

- **Time O(n log k)**, **space O(k)**.

### Edge cases and mistakes

- k equal to n; points at the origin; several points at the same distance.
- **The classic bug:** a **min**-heap trimmed to k throws away the closest point at every overflow. On `[[1, 3], [-2, 2]]`, k = 1, it keeps (1, 3), but (−2, 2) is closer (8 versus 10).

<h2 id="running-median">Chapter 5 · Find Median from Data Stream</h2>

### Problem

Design a structure with `addNum(num)` and `findMedian()`. The median is the middle value of the numbers added so far, or the average of the two middle values when the count is even.

Add 5, 2, 8: the median is 5. Add 1: the median is (2 + 5) / 2 = 3.5.

### How to recognise it

- "Median", "middle value", "percentile", after **every** insertion.
- Numbers arrive over time and you cannot sort once at the end.

### Brute force

Keep a list. Sort it on every `findMedian`: O(n log n) per query. Or insert each number into its sorted place: O(n) per add. Both are far too slow for a long stream.

### Intuition

You never need the whole order, only the **border** between the smaller half and the larger half. At that border you need the biggest of the small values and the smallest of the large values. Each is exactly what a heap shows on top:

- **low**: a **max-heap** of the smaller half. Its top is the largest small value.
- **high**: a **min-heap** of the larger half. Its top is the smallest large value.

Keep two promises: **every value in low ≤ every value in high**, and **low has the same size as high, or exactly one more**. Then the median is low's top (odd count) or the average of both tops (even count).

The routine that keeps both promises with no case analysis:

1. Offer the newcomer to **low**.
2. Move low's top up to **high**. (Order restored.)
3. If high is now bigger than low, move high's top back to **low**. (Sizes restored.)

<DryRun title="Find Median: two heaps" frames={medianFrames([5, 2, 8, 1, 9, 4])} predict />

### Algorithm

1. `addNum(x)`: `low.offer(x)`.
2. `high.offer(low.poll())`.
3. If `high.size() > low.size()`: `low.offer(high.poll())`.
4. `findMedian()`: if low is bigger, return `low.peek()`; else return the average of both peeks (widen to `double` before adding).

### Java solution

<HintLadder hints={hints.median}>

```java id=medianFinder
class MedianFinder {
    // low: the smaller half, largest on top. high: the larger half, smallest on top.
    private final PriorityQueue<Integer> low = new PriorityQueue<>(Comparator.reverseOrder());
    private final PriorityQueue<Integer> high = new PriorityQueue<>();

    public void addNum(int num) {
        low.offer(num);                     // 1. always enter through low
        high.offer(low.poll());             // 2. low's largest steps up: order restored
        if (high.size() > low.size())       // 3. sizes: low keeps the extra one, never high
            low.offer(high.poll());
    }

    public double findMedian() {
        if (low.size() > high.size()) return low.peek();
        return ((double) low.peek() + high.peek()) / 2.0;   // widen BEFORE adding
    }
}
```

**addNum: O(log n)** (one offer and up to two moves). **findMedian: O(1). Space: O(n).** The `(double)` cast comes **before** the addition.

</HintLadder>

### Why it works

- **Settled:** low ≤ high, and low's size minus high's size is 0 or 1.
- **Order stays true:** step 2 moves the largest of low-plus-newcomer into high. Everything left in low is at most that value, and was already at most everything in high. Step 3 moves high's smallest down, which keeps the order too.
- **Sizes stay true:** before the add, low = high or low = high + 1. After step 2, high gained one. If they were equal, high is now bigger and step 3 moves one back; if low had the extra, they are now equal and step 3 does nothing.
- **When we stop:** there is no stopping rule: the structure is always ready, and `findMedian` is a peek or two.

### Complexity

- **addNum: O(log n)** (one offer and up to two moves between heaps).
- **findMedian: O(1).**
- **Space: O(n)**, every number is stored once.

### Edge cases and mistakes

- The very first number (high is empty), two equal numbers, very large values.
- **Bug 1:** rebalancing with `high.size() >= low.size()`. On `[1, 2]` the 2 is pulled back into low, low ends two bigger, and the median comes out 2.0 instead of 1.5. The threshold is strictly greater.
- **Bug 2:** `(low.peek() + high.peek()) / 2.0` adds two `Integer`s as `int` first. With two copies of 2,147,483,647 it returns −1.0. Widen before adding.

### Practice

<Trace title="Through low, every time" steps={median} takeaway="Remember: offer to low, move low's top to high, and move high's top back if high got bigger. The median is at the tops." />

<Reveal q="Why go THROUGH low every time, instead of placing the number on the correct side directly?">

Both can be correct. Direct placement means comparing with both tops, handling an empty heap on either side, and then a size fix in either direction. That is the classic place to fumble under interview pressure. The routine handles every case mechanically, including the very first number.

A common slip is deriving this live and losing a case. Practise it until your hands know it, then explain the two promises it keeps.

</Reveal>

<Reveal q="Follow-up: what if every number is an integer from 0 to 100? And what if 99% of them are?">

All in 0–100: skip the heaps. Keep a count array of size 101 and a total. To find the median, walk the counts until you pass the middle position: O(101) per query, O(1) per add.

99% in range: keep the same count array plus counts of how many values fell below 0 and above 100. The median almost always lands inside the array; only if the outliers are numerous enough to contain it do you need them in sorted form (for example, in a small heap or sorted list on each side).

</Reveal>

<h2 id="window-median">Chapter 6 · Sliding Window Median</h2>

### Problem

Given an array and a window size `k`, report the median of every window of k consecutive numbers.

`[1, 3, -1, -3, 5, 3, 6, 7]`, k = 3 gives `[1, -1, -1, 3, 5, 6]`.

### How to recognise it

- Chapter 5's median, but values also **leave** (the oldest one slides out of the window).
- The tricky word is "remove": a heap can only remove its top cheaply.

### Brute force

Sort each window: O(n · k log k). Or use two heaps and call `PriorityQueue.remove(Object)` for the leaving value. That call scans the array: O(k) per slide, O(n · k) overall. With n = 100,000 and k = 50,000 that is billions of steps.

### Intuition

**Lazy deletion.** When a value leaves the window, do not remove its entry. Mark it **dead** by fixing the bookkeeping now, and pop it later, only when it reaches a top (the only place a heap can remove cheaply).

Three design choices make this clean:

- **Store indexes, not values,** ordered by value and then by index. Every entry is distinct, so "which entry is this?" is never ambiguous. And "dead" needs no extra map: an index is dead exactly when it is below the window's `start`. (The classic version stores values plus a map of pending deletions. It works, but equal values can sit in both heaps and the bookkeeping gets delicate.)
- **Keep live counts,** `lowLive` and `highLive`. Physical heap sizes include dead entries, so they cannot be used for balancing.
- **Keep both tops live:** after anything that can change a top, pop dead entries off it.

### Dry run

Faded entries are dead: they left the window but are still inside the heap. Watch the live counts, not the heap sizes.

<DryRun title="Sliding Window Median: lazy deletion" frames={windowMedianFrames([3, 5, 6, 1, 4], 3)} predict />

### Algorithm

For each new index i:

1. **Admit** i: into low if it comes before low's top in the (value, index) order, else into high. Count it as live there.
2. **Retire** `i - k`: compare it with low's top. Low's top is live and is the largest live entry in low, and every live high entry is larger, so "at most low's top" means "it is in low". Decrement that side's live count. Leave the entry where it is.
3. **Prune** dead tops, then **rebalance by live counts**: low may hold the same number as high, or one more. One move is always enough (see below). Prune the heap you moved from.
4. **Read** the median from the live tops once the window is full, averaging in `double`.

### Java solution

<HintLadder hints={hints.windowMedian}>

```java id=medianSlidingWindow
public double[] medianSlidingWindow(int[] nums, int k) {
    // Heaps hold INDEXES, ordered by value and then by index, so no two entries tie.
    Comparator<Integer> order = (a, b) -> nums[a] != nums[b]
        ? Integer.compare(nums[a], nums[b]) : Integer.compare(a, b);
    PriorityQueue<Integer> low = new PriorityQueue<>(order.reversed()); // smaller half
    PriorityQueue<Integer> high = new PriorityQueue<>(order);           // larger half
    int lowLive = 0, highLive = 0;          // entries still inside the window
    double[] result = new double[nums.length - k + 1];
    for (int i = 0; i < nums.length; i++) {
        // 1. Admit index i on the side where it belongs.
        if (low.isEmpty() || order.compare(i, low.peek()) < 0) { low.offer(i); lowLive++; }
        else { high.offer(i); highLive++; }
        // 2. Retire index i - k: change the live count now, remove the entry later.
        int out = i - k;
        if (out >= 0) {
            if (order.compare(out, low.peek()) <= 0) lowLive--;
            else highLive--;
        }
        int start = i - k + 1;              // indexes below start are dead
        prune(low, start);
        prune(high, start);
        // 3. Rebalance by LIVE counts. One move is always enough.
        if (lowLive > highLive + 1) {
            high.offer(low.poll()); lowLive--; highLive++; prune(low, start);
        } else if (highLive > lowLive) {
            low.offer(high.poll()); highLive--; lowLive++; prune(high, start);
        }
        // 4. Once the window is full, read the median from the live tops.
        if (start >= 0) {
            result[start] = k % 2 == 1 ? nums[low.peek()]
                : ((double) nums[low.peek()] + nums[high.peek()]) / 2.0;
        }
    }
    return result;
}

// Lazy deletion: dead entries leave only when they reach the top.
private void prune(PriorityQueue<Integer> heap, int start) {
    while (!heap.isEmpty() && heap.peek() < start) heap.poll();
}
```

**O(n log n) time, O(n) space in the worst case.** Dead entries only leave when they surface, and some never do: on a steadily rising input, old small values stay buried at the bottom of low, which ends up holding nearly all n entries. The TreeSet version is **O(n log k) time, O(k) space.** Both average in `double`: the window `[2147483647, 2147483647]` must give 2147483647.0, not −1.0.

</HintLadder>

### Why it works

- **Settled** after every step: (1) every live entry in low comes before every live entry in high; (2) `lowLive − highLive` is 0 or 1; (3) both tops are live. Promise 3 is what makes steps 2 and 4 safe: you only ever compare against, or read, a live top.
- **One move is enough:** before the step the live difference was 0 or 1; admitting and retiring each change it by one, so it lands between −2 and 3. One move shifts it by 2: −2 → 0, −1 → 1, 2 → 0, 3 → 1.
- **When we stop:** after the last index.

### Complexity

- **Time O(n log n)**, **space O(n)** in the worst case. Dead entries leave only when they surface, and some never do: on a steadily rising input, old small values stay buried at the bottom of low, which ends up holding nearly all n entries.
- The TreeSet alternative below is **O(n log k) time, O(k) space.**

### Edge cases and mistakes

- k = 1 and k = n; even and odd k; equal values (the index tie-break matters); values near ±2³¹.
- **The classic bug:** balancing with `low.size()` and `high.size()` counts the dead. On `[3, 5, 6, 1]`, k = 3, the buried 3 makes low look two bigger, the 5 is pushed up to high, and the second median comes out **1** instead of **5**.

### Practice

<Trace title="Stop counting, don't stop running" steps={windowMedian} takeaway="Remember: a leaving value only changes the live count. Pop dead entries when they reach a top, and balance by live counts, never by heap.size()." />

<Reveal q="Isn't there a structure that can just delete from the middle?">

Yes. Two `TreeSet`s of indexes, ordered by (value, index), delete any entry in O(log k). Then Chapter 5’s dance works unchanged: remove the leaving index from whichever set holds it, then offer through low. It is shorter and uses O(k) space. Know both; the heap version teaches lazy deletion, which comes back in Dijkstra’s shortest paths.

```java id=medianSlidingWindowTree
public double[] medianSlidingWindowTree(int[] nums, int k) {
    Comparator<Integer> order = (a, b) -> nums[a] != nums[b]
        ? Integer.compare(nums[a], nums[b]) : Integer.compare(a, b);
    TreeSet<Integer> low = new TreeSet<>(order), high = new TreeSet<>(order);
    double[] result = new double[nums.length - k + 1];
    for (int i = 0; i < nums.length; i++) {
        if (i >= k && !low.remove(i - k)) high.remove(i - k);  // a real O(log k) delete
        low.add(i);                                            // Chapter 5's dance, unchanged
        high.add(low.pollLast());
        if (high.size() > low.size()) low.add(high.pollFirst());
        if (i >= k - 1) {
            result[i - k + 1] = k % 2 == 1 ? nums[low.last()]
                : ((double) nums[low.last()] + nums[high.first()]) / 2.0;
        }
    }
    return result;
}
```

<h2 id="merge-k">Chapter 7 · Merge K Sorted Lists</h2>

### Problem

Merge k sorted linked lists into one sorted linked list.

`[1→4→5, 1→3→4, 2→6]` becomes `1→1→2→3→4→4→5→6`.

### How to recognise it

- "Merge k sorted ...": lists, arrays, files, shards, streams.
- Each source is already sorted, so you only ever need the next item from each one.

### Brute force

Collect all N nodes and sort them: O(N log N). Or merge the lists one after another: the running result grows, so the total work is O(N · k). The first ignores that the lists are sorted; the second re-walks the long result again and again.

### Intuition

The next node of the answer is always one of the k **current heads**, because everything behind a head is at least as large as it. So keep a min-heap holding exactly one head per list. Poll the smallest, append it to the answer, and push **its** successor from the same list.

### Dry run

Each list shows its current head. The heap holds exactly one head per non-empty list.

<DryRun title="Merge K Sorted Lists: heap of heads" frames={mergeKFrames([[1, 4, 5], [1, 3, 4], [2, 6]])} predict />

### Algorithm

1. Push the head of every non-empty list into a min-heap ordered by value.
2. Create a dummy node and a `tail` pointer.
3. While the heap is not empty: poll the smallest node, link it after `tail`, and move `tail` to it.
4. If that node has a `next`, push the `next`.
5. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.mergeK}>

```java id=mergeKLists
public ListNode mergeKLists(ListNode[] lists) {
    PriorityQueue<ListNode> heap = new PriorityQueue<>((a, b) -> Integer.compare(a.val, b.val));
    for (ListNode head : lists) if (head != null) heap.offer(head);   // one head per list
    ListNode dummy = new ListNode(0), tail = dummy;
    while (!heap.isEmpty()) {
        ListNode node = heap.poll();          // the smallest head of all
        tail.next = node;
        tail = node;
        if (node.next != null) heap.offer(node.next);   // its list sends the next in line
    }
    return dummy.next;
}
```

**O(N log k) time, O(k) extra space** for the heap. Nodes are relinked, not copied.

</HintLadder>

### Why it works

- **Settled:** the output is the sorted merge of everything announced so far, and the heap holds the current head of every non-empty list.
- **Why the move is safe:** each list is sorted, so the smallest unannounced node of a list is its head, and the smallest unannounced node overall is the smallest head.
- **When we stop:** when the heap is empty, because every list is exhausted.

### Complexity

- **Time O(N log k):** each of N nodes enters and leaves a heap of at most k entries. The bound comes from the heap's **size**, not the total data, exactly like the size-k heap in Part Two.
- **Space O(k)** extra for the heap. Nodes are relinked, not copied.

### Edge cases and mistakes

- No lists, an empty list among the lists, a single list, lists of different lengths.
- **The classic bug:** pushing `node.next` without checking for `null`. `PriorityQueue` throws a `NullPointerException` on `offer(null)`, and an empty input list has a `null` head too. Guard both places. And compare with `Integer.compare(a.val, b.val)`, not `a.val - b.val`.

<h2 id="task-scheduler">Chapter 8 · Task Scheduler</h2>

### Problem

Tasks are letters. Each task takes one time unit, and two runs of the same letter must be at least `n` units apart. You may idle. Return the fewest time units to finish everything.

`AAABBB`, n = 2 gives `8`: `A B _ A B _ A B`.

### How to recognise it

- "Cooldown", "at least n apart", "most urgent first", "fewest time units".
- Each step you pick the best **available** item, and an item becomes unavailable for a while after you use it.

### Brute force

Try every order of the tasks, idling where needed, and keep the shortest. That is exponential. A tempting shortcut is to run tasks in alphabetical order, which ignores which letter has the longest chain of cooldowns ahead.

### Intuition

At every time unit, run the **ready** task with the **most copies left**. It has the longest chain of rests ahead of it, so starting it early lets other tasks fill those rests. Tasks that just ran wait on a **cooldown queue** (FIFO) of `{copies left, last time unit of the rest}`, and return to the heap when their rest ends. If the heap is empty, the unit is idle.

The letters do not matter, only the counts. That is why the heap holds plain integers.

<Figure caption="AAABBB with n = 2: A B · A B · A B. Each A is followed by 2 units that are not A. The two idle units (dashed) are forced: 8 units in all.">
  <ArrayStrip name="time 1 to 8" values={['A', 'B', '·', 'A', 'B', '·', 'A', 'B']} indices={false} tones={{ 2: 'ghost', 5: 'ghost', 0: 'hot', 3: 'hot', 6: 'hot' }} regions={[{ from: 0, to: 2, label: 'frame 1', tone: 'blue' }, { from: 3, to: 5, label: 'frame 2', tone: 'blue' }, { from: 6, to: 7, label: 'last row', tone: 'green' }]} />
</Figure>

### Dry run

The ready heap is a max-heap of copies left. The cooldown queue shows when each resting task returns. The schedule grows one unit per frame, idle units included.

<DryRun title="Task Scheduler: ready heap and cooldown queue" frames={taskSchedulerFrames('AAABBB', 2)} predict />

### Algorithm

1. Count each letter. Put every count into a max-heap (`ready`).
2. Keep a FIFO queue `cooling` of `{copies left, time its rest ends}`.
3. Loop while `ready` or `cooling` is non-empty. Add 1 to `time`.
4. If `ready` is non-empty, poll it and subtract 1. If copies remain, add `{left, time + n}` to `cooling`. (An empty heap means this unit is idle.)
5. If the front of `cooling` ends at this `time`, move it back into `ready`.
6. Return `time`.

### Java solution

<HintLadder hints={hints.scheduler}>

```java id=leastInterval
public int leastInterval(char[] tasks, int n) {
    int[] count = new int[26];
    for (char t : tasks) count[t - 'A']++;
    PriorityQueue<Integer> ready = new PriorityQueue<>(Comparator.reverseOrder()); // remaining counts
    for (int c : count) if (c > 0) ready.offer(c);
    Deque<int[]> cooling = new ArrayDeque<>();   // {remaining count, last time unit of its rest}
    int time = 0;
    while (!ready.isEmpty() || !cooling.isEmpty()) {
        time++;
        if (!ready.isEmpty()) {
            int left = ready.poll() - 1;         // run the task with the most copies left
            if (left > 0) cooling.offer(new int[]{left, time + n});
        }                                        // (an empty ready heap means: idle)
        if (!cooling.isEmpty() && cooling.peek()[1] == time) ready.offer(cooling.poll()[0]);
    }
    return time;
}
```

The heap holds at most 26 entries, so each unit costs O(1): **O(total time units) time, O(1) extra space.** The total is at most max(tasks, (f − 1)(n + 1) + 26). This is **greedy + heap**: the heap is just “give me the best current choice” machinery. The Greedy pattern on your roadmap builds on exactly this.

</HintLadder>

### Why it works

- **Settled:** the ready heap holds exactly the tasks allowed to run now, with their copies left; the cooldown queue holds every other unfinished task, in the order their rests end.
- **Why the greedy is safe** (a lower bound, plus a check): say the largest count is f, and t tasks share it. Each of those t tasks runs f times with n units between runs, so its last run comes at least (f − 1)(n + 1) units after its first. The t tasks start at t different units, so the one that starts last starts at unit t or later. **No schedule can finish before (f − 1)(n + 1) + t**, and none can finish before the number of tasks. Running the ready task with the most copies left always reaches the larger of those two bounds. The full argument is longer, so the lesson's checker compares this simulation with an exhaustive search over every possible schedule on thousands of small inputs.
- **When we stop:** when both the heap and the queue are empty.

### Complexity

- The heap holds at most 26 entries, so each unit costs O(1): **O(total time units) time, O(1) extra space.**
- The total is at most max(tasks, (f − 1)(n + 1) + 26).
- This is **greedy + heap**: the heap is just "give me the best current choice" machinery.

### Edge cases and mistakes

- n = 0 (no cooldown), a single task type, every unit idle at the start.
- **The classic bug:** off-by-one rests. Storing `time + n + 1` and returning the task when `peek()[1] == time` makes every task rest one unit too long: AA with n = 1 then takes 4 units (A · · A) instead of 3 (A · A). A task that ran at time t may run again at t + n + 1, so its rest ends at the end of t + n.

### Practice

<Trace title="Who runs, who rests" steps={scheduler} takeaway="Remember: run the ready task with the most copies left; tasks that just ran wait n units in the cooldown queue. Idle units count." />

<Reveal q="Is there a formula? Derive it from the frames in the figure.">

Yes. Let f be the largest count and t the number of tasks that have it. The most frequent task forces f − 1 full **frames** of n + 1 units, plus a **last row** holding each of the t tied tasks once: (f − 1) × (n + 1) + t. Other tasks slot into the frames’ gaps. If there are more tasks than gaps, there are no idle units at all and the answer is simply the number of tasks. So the answer is max(tasks, (f − 1)(n + 1) + t). For AAABBB, n = 2: max(6, 2 × 3 + 2) = 8.

```java id=leastIntervalFormula
public int leastIntervalFormula(char[] tasks, int n) {
    int[] count = new int[26];
    for (char t : tasks) count[t - 'A']++;
    int maxFreq = 0, tiedAtMax = 0;
    for (int c : count) {
        if (c > maxFreq) { maxFreq = c; tiedAtMax = 1; }
        else if (c == maxFreq && c > 0) tiedAtMax++;
    }
    return Math.max(tasks.length, (maxFreq - 1) * (n + 1) + tiedAtMax);
}
```

The formula is O(number of tasks). The heap version generalises (it can return the actual schedule, not just its length) and is easier to defend step by step. Know both.

</Reveal>

<h2 id="kth-in-a-stream">Side quest 1 · Kth Largest in a Stream</h2>

### Problem

Design a class that is built with `k` and a starting array, and has `add(val)` returning the kth largest value so far, after every add. Example: k = 3, start `[4, 5, 8, 2]`, adds 3, 5, 10, 9, 4 return 4, 5, 5, 8, 8.

### How to recognise it

- Chapter 2, but the queue never ends and someone asks after **every** arrival.

### Brute force

Keep every number and sort after each add: O(n log n) per add and O(n) memory, growing forever.

### Intuition

Chapter 2's heap already holds the answer after every arrival; you just never asked it before the end. Keep the heap as a field, trimmed to k. Anything evicted can never be the kth largest again, because the heap only gets stronger.

### Dry run

<DryRun title="Kth Largest in a Stream" frames={kthStreamFrames(3, [4, 5, 8, 2], [3, 5, 10, 9, 4])} predict />

### Algorithm

1. Store `k` and an empty min-heap.
2. `add(val)`: offer, and poll if the size passed k. Return `peek()`.
3. The constructor feeds the starting numbers through `add`.

### Java solution

<HintLadder hints={hints.streamKth}>

```java id=kthLargestStream
class KthLargest {
    private final PriorityQueue<Integer> heap = new PriorityQueue<>(); // never more than k inside
    private final int k;

    public KthLargest(int k, int[] nums) {
        this.k = k;
        for (int x : nums) add(x);
    }

    public int add(int val) {
        heap.offer(val);
        if (heap.size() > k) heap.poll();
        return heap.peek();
    }
}
```

**O(n log k) to build, O(log k) per add, O(k) space.** The problem guarantees at least k numbers exist whenever you are asked, so the root is never missing. Example: k = 3, start `[4, 5, 8, 2]`, adds 3, 5, 10, 9, 4 → 4, 5, 5, 8, 8.

</HintLadder>

### Why it works

The heap is always the k largest values seen so far, so its root is the kth largest. The problem guarantees at least k numbers exist whenever you are asked, so the root is never missing.

### Complexity

**O(n log k)** to build, **O(log k)** per add, **O(k)** space.

### Edge cases and mistakes

- Fewer than k starting numbers (the heap fills over later adds); duplicates; k = 1.
- Returning `heap.peek()` before the heap holds k values.

### Practice

<Reveal q="Why not keep every number and sort after each add?">

That is O(n log n) per add and O(n) memory, and it grows forever. The gate is O(log k) per add and O(k) memory, forever. Anything evicted from the gate can never be the kth largest again, because the gate only ever gets stronger.

</Reveal>

<h2 id="last-stone">Side quest 2 · Last Stone Weight</h2>

### Problem

Each turn, smash the two heaviest stones. Equal stones both vanish; otherwise the lighter vanishes and the heavier loses that much weight. Return the last stone's weight (0 if none).

`[2, 7, 4, 1, 8, 1]` gives `1`.

### How to recognise it

- "Repeatedly take the two largest (or smallest)", and the result goes back into the pool.

### Brute force

Sort the array every turn: O(n² log n) in total.

### Intuition

Each turn needs the two largest of a collection that keeps changing: a **max-heap** simulation. The leftover goes **back** into the heap, because it may be lighter than stones still waiting.

### Dry run

<DryRun title="Last Stone Weight" frames={lastStoneFrames([2, 7, 4, 1, 8, 1])} predict />

### Algorithm

1. Put every stone in a max-heap.
2. While more than one stone remains: poll y, poll x (y ≥ x). If y > x, offer `y − x`.
3. Return the remaining stone, or 0.

### Java solution

<HintLadder hints={hints.stones}>

```java id=lastStoneWeight
public int lastStoneWeight(int[] stones) {
    PriorityQueue<Integer> heap = new PriorityQueue<>(Comparator.reverseOrder());
    for (int s : stones) heap.offer(s);
    while (heap.size() > 1) {
        int y = heap.poll(), x = heap.poll();   // the two heaviest, y >= x
        if (y > x) heap.offer(y - x);           // equal stones both vanish
    }
    return heap.isEmpty() ? 0 : heap.peek();
}
```

Each turn removes at least one stone: **O(n log n) time, O(n) space.**

</HintLadder>

### Why it works

The heap always holds the current stones, so each poll returns the heaviest. Each turn removes at least one stone, so the loop ends.

### Complexity

**O(n log n) time, O(n) space.**

### Edge cases and mistakes

- One stone; all equal stones (result 0); forgetting to offer the leftover back.

### Practice

<Reveal q="[2, 7, 4, 1, 8, 1]: trace it. What is left?">

8 and 7 → 1 remains: `[2, 4, 1, 1, 1]`. 4 and 2 → 2: `[2, 1, 1, 1]`. 2 and 1 → 1: `[1, 1, 1]`. 1 and 1 → both gone: `[1]`. The last stone weighs **1**. Notice how the 1 left by the first smash had to wait behind heavier stones.

</Reveal>

**Transfer test:** now you may choose **any** two stones each turn and want the **smallest possible** final stone. Does the heap still work? (It does not: that version is a subset-sum partition, a dynamic-programming problem. See Last Stone Weight II in Beyond this page.)

<h2 id="reorganize-string">Side quest 3 · Reorganize String</h2>

### Problem

Rearrange the letters of a string so that **no two neighbours are equal**, or return an empty string if that is impossible.

`aab` gives `aba`. `aaab` is impossible.

### How to recognise it

- "No two adjacent equal", "at least k apart": a cooldown again.

### Brute force

Try every permutation: O(n!). Even sorting by frequency and interleaving needs care at the edges.

### Intuition

The most common letter is the dangerous one; leave it for the end and it piles up. So, greedily, place the letter with the **most copies left**, but never the letter you just placed. That letter sits out for one turn, then goes back into the max-heap: Chapter 8 with n = 1. If the heap runs dry while a letter is still waiting, there is nowhere to put it.

### Dry run

<DryRun title="Reorganize String" frames={reorganizeFrames('aaabbc')} predict />

### Algorithm

1. Count letters; put `{letter, count}` in a max-heap by count.
2. Keep one `benched` entry (empty at first).
3. Poll the top, append its letter, decrement it. Put the previous benched entry back in the heap. Bench the current one if copies remain.
4. When the heap is empty: if something is still benched, return `""`; else return the string.

### Java solution

<HintLadder hints={hints.reorganize}>

```java id=reorganizeString
public String reorganizeString(String s) {
    int[] count = new int[26];
    for (char c : s.toCharArray()) count[c - 'a']++;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(b[1], a[1])); // {letter, left}
    for (int c = 0; c < 26; c++) if (count[c] > 0) heap.offer(new int[]{c, count[c]});
    StringBuilder out = new StringBuilder();
    int[] benched = null;                        // the letter just placed sits out one turn
    while (!heap.isEmpty()) {
        int[] top = heap.poll();                 // most copies left, and not the last letter
        out.append((char) ('a' + top[0]));
        top[1]--;
        if (benched != null) heap.offer(benched);
        benched = top[1] > 0 ? top : null;
    }
    return benched == null ? out.toString() : "";   // someone still waiting: impossible
}
```

With an alphabet of 26 letters the heap stays tiny: **O(n log 26) = O(n) time, O(n) space** for the output. The heap holds `{letter, copies}` pairs, and a pair is changed only after it has been polled. Changing a value while it sits inside a heap breaks the heap silently.

</HintLadder>

### Why it works

The letter with the most copies left is the hardest to place, so it goes first whenever it is allowed. Benching the last placed letter guarantees no two neighbours match.

### Complexity

With an alphabet of 26 letters the heap stays tiny: **O(n log 26) = O(n) time, O(n) space** for the output.

### Edge cases and mistakes

- It is possible exactly when the most common letter appears at most ⌈n / 2⌉ times. A single letter is fine; `aaab` is not.
- Changing a value while it sits inside the heap breaks the heap silently. The heap holds `{letter, copies}` pairs, and a pair is changed only after it has been polled.

### Practice

<Reveal q="When is it impossible? Check 'aab' and 'aaab'.">

It is possible exactly when the most common letter appears at most ⌈n / 2⌉ times. `aab`: 2 of 3, limit 2, so `aba`. `aaab`: 3 of 4, limit 2, impossible. Each copy of the top letter needs a different letter between it and the next one.

</Reveal>

**Transfer test:** now equal letters must be at least **k** apart. Which chapter's cooldown queue do you need, and how long is it?

<h2 id="ipo">Side quest 4 · IPO</h2>

### Problem

You start with w coins and may finish at most k projects, one after another. Each project needs at least its required capital to start (the coins are not spent), and its profit is added when it is done. End with as many coins as possible.

w = 0, k = 2, profits `[1, 2, 3]`, capital `[0, 1, 1]` gives `4`.

### How to recognise it

- "Unlock, then choose": a budget decides what is available, and among the available you take the best.

### Brute force

Try every order of up to k projects: O(n^k). Greedy needs two orderings at once, which a sort cannot give you while the set of affordable projects keeps growing.

### Intuition

Every round asks two questions. *What can I afford?* A **min-heap by capital** holds the locked projects, cheapest first; unlock from its top while affordable. *What pays most?* A **max-heap by profit** holds the unlocked ones. Take its top. Coins only grow, so an unlocked project stays unlocked: nothing ever moves back.

### Dry run

<DryRun title="IPO: unlock, then choose" frames={ipoFrames(2, 0, [1, 2, 3], [0, 1, 1])} predict />

### Algorithm

1. Put every project in `locked`, ordered by capital.
2. Repeat k times: move every project with capital ≤ w from `locked` to `open` (ordered by profit).
3. If `open` is empty, stop. Otherwise add its top profit to w.
4. Return w.

### Java solution

<HintLadder hints={hints.ipo}>

```java id=findMaximizedCapital
public int findMaximizedCapital(int k, int w, int[] profits, int[] capital) {
    // locked: projects you cannot afford yet, cheapest first.
    PriorityQueue<Integer> locked = new PriorityQueue<>((a, b) -> Integer.compare(capital[a], capital[b]));
    // open: profits of projects you can afford, best first.
    PriorityQueue<Integer> open = new PriorityQueue<>(Comparator.reverseOrder());
    for (int i = 0; i < profits.length; i++) locked.offer(i);
    for (int round = 0; round < k; round++) {
        while (!locked.isEmpty() && capital[locked.peek()] <= w) open.offer(profits[locked.poll()]);
        if (open.isEmpty()) break;               // nothing affordable, now or ever
        w += open.poll();                        // take the best profit on offer
    }
    return w;
}
```

Each project enters and leaves each heap at most once: **O(n log n) time, O(n) space.**

</HintLadder>

### Why it works

Take any best plan and compare it with the greedy first move, the top profit p you can afford now. If the plan uses p later, doing it first only raises your coins sooner, so everything after it stays affordable. If the plan never uses p, swap p in for the plan's first project: that project was affordable now too and paid no more than p, so every later step is still affordable and you finish with at least as many coins. Either way a best plan can start with p; repeat the argument for the next round. It needs profits ≥ 0.

### Complexity

Each project enters and leaves each heap at most once: **O(n log n) time, O(n) space.**

### Edge cases and mistakes

- Nothing affordable at the start; k larger than the number of projects; zero-profit projects.

### Practice

<Reveal q="Why is taking the biggest affordable profit never a mistake?">

Take any best plan and compare it with the greedy first move, the top profit p you can afford now. If the plan uses p later, doing it first only raises your coins sooner, so everything after it stays affordable. If the plan never uses p, swap p in for the plan’s first project: that project was affordable now too and paid no more than p, so every later step is still affordable and you finish with at least as many coins. Either way a best plan can start with p; repeat the argument for the next round. It needs profits ≥ 0. Example: w = 0, k = 2, profits `[1, 2, 3]`, capital `[0, 1, 1]`. Only project 0 is affordable: w = 1. Now projects 1 and 2 unlock; take profit 3: **w = 4**.

</Reveal>

<h2 id="smallest-range">Side quest 5 · Smallest Range Covering Elements from K Lists</h2>

### Problem

Given k sorted lists, find the **narrowest** range that contains at least one number from each list (ties go to the smaller start).

`[[4, 10, 15, 24, 26], [0, 9, 12, 20], [5, 18, 22, 30]]` gives `[20, 24]`.

### How to recognise it

- A range or window must "touch" every one of k sorted sources.

### Brute force

Try every pair of values as the range ends and check each list: O(N² · k) for N values.

### Intuition

Hold one candidate from each list, as in Chapter 7. Those k candidates span `[their minimum, their maximum]`, and that range covers every list. To try for a narrower one, the only useful move is to **advance the list holding the minimum**: advancing anything else only raises the maximum. Track the maximum yourself; the heap gives the minimum. Stop when the minimum's list runs out, because no later range can cover that list.

<Figure caption="The classic input. The heap holds one value per list; the best range found is [20, 24], using 24 from the first list, 20 from the second and 22 from the third.">
  <ArrayStrip name="list 1" values={[4, 10, 15, 24, 26]} indices={false} tones={{ 3: 'hot' }} />
  <ArrayStrip name="list 2" values={[0, 9, 12, 20]} indices={false} tones={{ 3: 'hot' }} />
  <ArrayStrip name="list 3" values={[5, 18, 22, 30]} indices={false} tones={{ 2: 'hot' }} />
</Figure>

### Dry run

<DryRun title="Smallest Range from K Lists" frames={smallestRangeFrames([[4, 10, 15, 24, 26], [0, 9, 12, 20], [5, 18, 22, 30]])} predict />

### Algorithm

1. Push the first value of every list into a min-heap; track the maximum of them.
2. Record `[heap min, max]` as the best range so far.
3. Poll the minimum. If this range is narrower, record it.
4. If that list has no next value, stop. Else push its next value and update the maximum.
5. Repeat from step 3.

### Java solution

<HintLadder hints={hints.smallestRange}>

```java id=smallestRange
public int[] smallestRange(List<List<Integer>> nums) {
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0])); // {value, list, position}
    int max = Integer.MIN_VALUE;
    for (int i = 0; i < nums.size(); i++) {
        int v = nums.get(i).get(0);
        heap.offer(new int[]{v, i, 0});
        max = Math.max(max, v);
    }
    int bestLo = heap.peek()[0], bestHi = max;
    while (true) {
        int[] min = heap.poll();                 // [min, max] covers one value from every list
        if ((long) max - min[0] < (long) bestHi - bestLo) { bestLo = min[0]; bestHi = max; }
        int next = min[2] + 1;
        if (next == nums.get(min[1]).size()) break;   // that list is spent: no later range covers it
        int v = nums.get(min[1]).get(next);
        heap.offer(new int[]{v, min[1], next});
        max = Math.max(max, v);
    }
    return new int[]{bestLo, bestHi};
}
```

With N numbers in total: **O(N log k) time, O(k) space.** Widths are compared in `long`, so even a range from −2³¹ to 2³¹ − 1 is measured correctly. Because minimums are processed in increasing order, the strict `<` keeps the earlier, smaller start on ties.

</HintLadder>

### Why it works

- **Settled:** every range with its minimum below the current heap minimum has already been considered.
- **Safe move:** advancing a non-minimum list can only keep or raise the maximum while the minimum stays the same, so it cannot improve the range.

### Complexity

With N numbers in total: **O(N log k) time, O(k) space.** Widths are compared in `long`, and because minimums are processed in increasing order, the strict `<` keeps the earlier, smaller start on ties.

### Edge cases and mistakes

- Lists of different lengths; a single list (the answer is one value); extreme values (the width needs `long`).

### Practice

**Transfer test:** why is it safe to stop the moment one list runs out, even if other lists still have values?

<h2 id="sorted-matrix">Side quest 6 · Kth Smallest Element in a Sorted Matrix</h2>

### Problem

An n × n grid where every row and every column is sorted. Find the kth smallest value (duplicates count separately).

`[[1, 5, 9], [10, 11, 13], [12, 13, 15]]`, k = 8 gives `13`.

### How to recognise it

- "kth smallest" over data that is already sorted in several directions.

### Brute force

Flatten and sort: O(n² log n). It ignores the sorting that the grid already has.

### Intuition

Each **row is a sorted list**. So this is Chapter 7 in disguise: a heap of row fronts, popping the smallest k − 1 times and pushing the next cell in the same row. Seed it with the first column, but only the first min(n, k) rows can matter.

### Dry run

<DryRun title="Kth Smallest in a Sorted Matrix" frames={sortedMatrixFrames([[1, 5, 9], [10, 11, 13], [12, 13, 15]], 8)} predict />

### Algorithm

1. Push the first cell of each of the first min(n, k) rows.
2. Repeat k − 1 times: poll the smallest; if its row has a next cell, push it.
3. The top of the heap is the answer.

### Java solution

<HintLadder hints={hints.matrixKth}>

```java id=kthSmallest
public int kthSmallest(int[][] matrix, int k) {
    int n = matrix.length;
    PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0])); // {value, row, col}
    for (int r = 0; r < Math.min(n, k); r++) heap.offer(new int[]{matrix[r][0], r, 0});
    for (int taken = 1; taken < k; taken++) {
        int[] cur = heap.poll();                 // the next smallest overall
        if (cur[2] + 1 < n) heap.offer(new int[]{matrix[cur[1]][cur[2] + 1], cur[1], cur[2] + 1});
    }
    return heap.peek()[0];
}
```

**O(k log min(n, k)) time, O(min(n, k)) space.** A classic alternative ignores the heap: binary search on the **value**, counting how many cells are ≤ a guess with a staircase walk, in O(n log(max − min)).

</HintLadder>

### Why it works

Each row is sorted, so a row's smallest unseen cell is its front. The smallest unseen cell overall is the smallest front, so pops come out in sorted order, and the (k − 1) pops discard exactly the k − 1 smallest values.

### Complexity

**O(k log min(n, k)) time, O(min(n, k)) space.** A classic alternative ignores the heap: binary search on the **value**, counting how many cells are at most a guess with a staircase walk, in O(n log(max − min)).

### Edge cases and mistakes

- n = 1; k = 1; k = n²; the same value in several rows (duplicates count separately).

### Practice

<Reveal q="[[1, 5, 9], [10, 11, 13], [12, 13, 15]], k = 8. What comes out?">

Pops in order: 1, 5, 9, 10, 11, 12, 13 (that is k − 1 = 7 pops), and the root is then the other **13**. The answer is 13: duplicates count separately. Reading the grid row by row would give 13 too here, but only by luck; rows overlap in value in general.

</Reveal>

<h2 id="choose-the-tool">When not to use a heap</h2>

A heap pays off when you ask "what is best?" **again and again while the collection changes**. Suppose instead you are given a fixed list of a thousand scores and asked for the third best, once. You could offer all of them to a size-3 heap and read the root, and it would be correct. But nothing was arriving and nothing was leaving, so the heap protected you from nothing. When the data does not change, cheaper tools exist:

<Mermaid code={`flowchart TD
  Q["Need the best item, or the kth best?"] --> C{"Does the collection change<br/>between questions?"}
  C -- "no, and it is sorted" --> I["Index into it: O(1)"]
  C -- "no, unsorted" --> S["Scan for one extreme: O(n)<br/>kth: quickselect, expected O(n)"]
  C -- "yes" --> W{"Do items leave in arrival order?<br/>(sliding window max or min)"}
  W -- "yes" --> D["Monotonic deque: O(n) total"]
  W -- "no" --> H["Heap: O(log n) per change"]`} />

**Quickselect** answers "kth largest of a fixed array" in **expected O(n)**. Pick a random pivot, partition into less than / equal to / greater than the pivot (the same three-zone partition as Sort Colors in <a href={`${BASE}dsa/lessons/two-pointers/`}>Two Pointers</a>), and keep only the side that contains the target index n − k. Each round discards a constant fraction of the array on average.

<HintLadder hints={hints.quickselect}>

```java id=quickselect
public int findKthLargestQuick(int[] nums, int k) {
    int target = nums.length - k;                // kth largest sits at index n - k once sorted
    int lo = 0, hi = nums.length - 1;
    Random random = new Random();
    while (true) {
        int pivot = nums[lo + random.nextInt(hi - lo + 1)];
        int lt = lo, i = lo, gt = hi;            // [lo, lt) < pivot, [lt, i) == pivot, (gt, hi] > pivot
        while (i <= gt) {
            if (nums[i] < pivot) swap(nums, lt++, i++);
            else if (nums[i] > pivot) swap(nums, i, gt--);
            else i++;
        }
        if (target < lt) hi = lt - 1;
        else if (target > gt) lo = gt + 1;
        else return pivot;                       // target landed in the == pivot block
    }
}

private void swap(int[] a, int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }
```

**Expected O(n) time, O(1) extra space**; the worst case is O(n²) with persistently unlucky pivots (random pivots make that vanishingly unlikely). It **reorders the input**, and it needs the whole array in memory, so it cannot handle a stream. Say both trade-offs out loud; the heap answer is often the safer one to offer first.

</HintLadder>

<Reveal q="Sliding window maximum: why is a heap the wrong tool, even though it works?">

A max-heap of the window with lazy deletion (Chapter 6’s trick) works in O(n log n). But in a window, values leave in **arrival order**, and a value that has a bigger value after it can never be the maximum again. A monotonic deque throws such values away immediately and gets O(n) total. When removals follow arrival order, reach for the deque.

</Reveal>

**The k = 2 case needs no heap.** Comparing two fronts is one `if`. The heap earns its O(log k) only when k grows.

**A deque is not a heap.** It keeps candidates in arrival order and throws away the dominated ones; a heap keeps everyone and only knows the best.

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Keep the lesson closed. Before you code, write down what your heap holds, what its top means, why each eviction is safe, and your stopping rule.

1. **Ties decide.** Given a list of words, return the k most frequent; equal counts are ordered alphabetically. Test ties at the k-th place, k equal to the number of distinct words, and a single word.
2. **Rooms for everyone.** Given meeting intervals, find the fewest rooms so no two overlapping meetings share one. A meeting ending at 5 and one starting at 5 may share. Test nested meetings, touching meetings, and one meeting.
3. **Glue the sticks.** Joining two sticks costs the sum of their lengths, and the result is one stick. Join all sticks into one for the least total cost. Test one stick (cost 0), equal sticks, and lengths that make the total exceed 2³¹.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**Ties decide:** count words; keep a size-k min-heap whose top is the **worst** candidate: lower count first, and for equal counts the alphabetically **later** word (it is the one to evict). Poll into the result from the back. The tie-break flips inside the heap, and that is the whole trap.

**Rooms:** sort meetings by start; keep a min-heap of end times of meetings in progress. For each meeting, if the earliest end is ≤ its start, that room frees up (poll); then push this meeting's end. The largest heap size is the answer. `≤`, not `<`, is the touching-meetings test.

**Sticks:** a min-heap of lengths. Repeatedly poll the two shortest, add their sum to the cost, push the sum back. Joining the two shortest first is safe because the shortest sticks are counted in the most later joins (this is Huffman coding's argument). Use `long` for the cost.

Now explain why a slightly wrong version fails on one of your tests. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Start with... | The promise to keep |
|---|---|---|
| Build or explain a heap | Array; parent `(i − 1) / 2`, children `2i + 1`, `2i + 2`; sift up and down | Every parent ≤ its children |
| Kth largest | Size-k **min**-heap | Heap = the k largest so far; root = kth largest |
| Top k frequent | Count map + size-k min-heap **by count** | Heap = the k most frequent so far |
| K closest / k smallest by a key | Size-k **max**-heap by the key | Root = the worst of the chosen k |
| Running median | Two heaps + the through-low routine | low ≤ high; low has the same size or one more |
| Window median | Two heaps of indexes + lazy deletion + live counts | Live counts balanced; both tops live |
| Merge k sorted | Min-heap of heads | One front per non-empty list; at most k entries |
| Cooldowns between repeats | Max-heap of counts + FIFO cooldown queue | The heap holds only tasks allowed to run now |
| Kth largest after every add | Size-k min-heap kept between calls | The root answers in O(1) |
| Repeatedly combine the two biggest | Max-heap simulation | Leftovers go back to compete |
| No equal neighbours | Max-heap + a one-turn bench | The letter just placed sits out a turn |
| Unlock by budget, take the best | Min-heap by cost + max-heap by profit | Everything affordable is in the profit heap |
| Narrowest range over k lists | Heap of fronts + running max | `[heap min, max]` covers every list |
| Kth smallest in a sorted grid | Heap of row fronts | Pops come out in sorted order |
| Kth of a fixed array | Quickselect (or sort and index) | The target index stays inside `[lo, hi]` |

A heap does **not** make everything O(log n). Count what it holds: size k gives log k; lazy deletion can let it grow to n; and `remove(Object)` is a linear scan.

### Five bugs to check for

1. **The wrong heap kind for top-k.** A max-heap trimmed to k keeps the k smallest. An untrimmed one is correct but O(n) space, and dies on "it's a stream". Ask who among the chosen is in danger.
2. **The subtraction comparator.** `a - b` overflows near ±2³¹ and silently flips the order. Reach for `Integer.compare` (or `Long.compare`) by reflex.
3. **Believing the printout.** Iterating or printing a `PriorityQueue` shows the array layout, `[1, 3, 2]`, not sorted order. Only `poll()` drains in order.
4. **Two-heap bookkeeping.** Placing directly on the "right" side (case-analysis bugs), rebalancing with `>=` instead of `>`, adding two `int`s before averaging, and, with lazy deletion, balancing by `size()` instead of live counts.
5. **Feeding the heap bad entries.** Offering `null` successors in k-way merge, or changing a value while it sits inside the heap. The heap never re-sifts on its own; take the entry out, change it, put it back.

<h2 id="revision">Revision</h2>

**How to recognise it.** You need the best item (smallest, largest, most urgent, cheapest) of a collection that keeps changing, or the best k of a lot of data, or the middle value of a stream, or the next item from k sorted sources.

**Core algorithm.** Choose what the heap holds and what its top means, then keep that true:

- Top k of the largest: a min-heap of size k, top = weakest of the chosen. Flip it (max-heap) for the k smallest.
- Median: a max-heap for the smaller half and a min-heap for the larger half, sizes within one.
- Merge k sources: a min-heap holding one front per source.
- Simulation: a max-heap of what is ready, plus a queue for what is waiting.
- Removal from the middle: lazy deletion, balanced by live counts.

**Common mistakes.**

- Wrong heap kind for top-k; subtraction comparators that overflow.
- Trusting a printed `PriorityQueue`; offering `null`; mutating an entry inside the heap.
- Two heaps: `>=` instead of `>`, adding ints before widening, balancing by `size()` after lazy deletion.

**Complexity.** `offer` and `poll` are O(log n), `peek` is O(1), building from n values is O(n). Top-k is O(n log k) time and O(k) space; merging k sources is O(N log k); the median stream is O(log n) per add and O(1) per read.

**Three representative problems.**

1. [Kth Largest Element in an Array](https://leetcode.com/problems/kth-largest-element-in-an-array/): a size-k min-heap, root = answer.
2. [Find Median from Data Stream](https://leetcode.com/problems/find-median-from-data-stream/): two heaps, enter through low.
3. [Merge K Sorted Lists](https://leetcode.com/problems/merge-k-sorted-lists/): a min-heap of heads.

**Look these up yourself:** real ideas this page did not have room for:

- **Heapsort:** build a max-heap in place, then repeatedly swap the root to the end: O(n log n), O(1) space, not stable.
- **Indexed priority queue (decrease-key):** the alternative to lazy deletion when entries must change priority, as in textbook Dijkstra.

- **Median of medians:** a deterministic O(n) selection algorithm that removes quickselect's O(n²) worst case.
- **External merge sort:** sorting data bigger than memory: sort chunks, then a k-way merge from disk.
- **Huffman coding:** the stick-gluing greedy, used to build optimal prefix codes.
- **Order-statistic trees:** balanced trees that answer "kth smallest" and delete in O(log n); the heavy-duty version of the TreeSet trick.
- **Pairing and Fibonacci heaps:** heaps with cheaper merge and decrease-key, behind some theoretical graph-algorithm bounds.
