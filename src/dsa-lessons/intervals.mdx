<h2 id="prologue">Prologue · What an interval problem looks like</h2>

An **interval** is a pair `[start, end]`: a meeting, a booking, a shift, a balloon on a wall. The questions are always about how intervals relate. Do they **overlap**? How many overlap at once? What is their union? Which ones should be dropped?

### The overlap test

Two closed intervals `a` and `b` overlap exactly when **each one starts no later than the other ends**:

```text
a and b overlap  <=>  a.start <= b.end  &&  b.start <= a.end
                 <=>  max(a.start, b.start) <= min(a.end, b.end)
```

<Figure caption="Two bookings share time exactly when the later start (5) comes no later than the earlier end (7). The shared stretch runs from max(2, 5) = 5 to min(7, 10) = 7.">
  <Timeline {...figures.overlap} />
</Figure>

### The brute force, and the sort that removes it

Unsorted, any range could clash with any other. Checking all pairs is O(n²): for 40 bookings that is 780 comparisons, and for 100,000 it is five billion.

Now **sort by start**. If `cur` comes before `next` in start order, then `cur.start <= next.start <= next.end`. The first half of the overlap test is already true. Only one comparison is left:

```text
after sorting by start:   next overlaps cur  <=>  next.start <= cur.end
```

That is the whole pattern: **sort, then sweep**. A single left-to-right walk compares each range with one running "current" thing. The cost drops from O(n²) to **O(n log n)** for the sort plus O(n) for the walk.

### Three questions before every move

1. **What is settled?** Everything behind the sweep: ranges already emitted, kept, cancelled, or counted.
2. **Why is this move safe?** Usually because of the sort: nothing later can start earlier.
3. **When do I stop?** When the last range is read. Anything still open must be emitted.

### How to recognise the pattern

The input is ranges (times, bookings, segments, `[start, end]` pairs) and the question is about overlap: merge them, insert one, count how many run at once, remove the fewest to de-conflict, find common free time. Calendar and booking questions in system-design rounds hide the same tools.

### The one rule to read from every problem: does touching count?

Does `[1, 2]` clash with `[2, 3]`? There is no universal answer. **Read the problem's definition of overlap and say your assumption out loud.** In this chapter:

| Problem | Do `[1,2]` and `[2,3]` overlap? | So the test is |
|---|---|---|
| Merge Intervals, Insert Interval | Yes: they merge into `[1,3]` | `next.start <= cur.end` |
| Meeting Rooms I and II | No: back-to-back is fine | clash when `start < previous end`; reuse a room when `freeAt <= start` |
| Non-overlapping Intervals | No: LeetCode says so | keep when `start >= lastEnd` |
| Burst Balloons (side quest) | Yes: one arrow at 2 pops both | new arrow only when `start > arrowAt` |
| Interval List Intersections | Yes: the answer includes `[2,2]` | keep when `lo <= hi` |
| My Calendar, Car Pooling | No: `[start, end)` | dropoffs before pickups |

<h2 id="merge-intervals">Chapter 1 · Merge Intervals</h2>

### Problem

Given a list of ranges, merge every group that overlaps and return the merged ranges. Touching counts as overlapping.

`[[1,3],[2,6],[8,10],[15,18]]` becomes `[[1,6],[8,10],[15,18]]`.

### How to recognise it

- The input is ranges and the answer is their **union**.
- Words like "merge", "combine", "busy periods", "covered time".
- The order of the input is arbitrary, so sorting is allowed.

### Brute force

Repeat until nothing changes: find any two ranges that overlap and replace them with their union. Each pass checks every pair, and there can be up to n passes. That is O(n²) to O(n³) and the code is fiddly.

### Intuition

Once the ranges are sorted by start, a gap can only appear **between neighbours in the sweep**. So hold one **open card** `cur` and compare only the next range with it:

- `next.start <= cur.end`: `next` shares time with the card. **Extend** the card's end to `max(cur.end, next.end)`.
- `next.start > cur.end`: there is a gap. Every later range starts even later, so nothing can reach back across it. The card is final: **emit** it and open a new card.

At the end, the last card is still open. Emit it.

</Figure>

### Algorithm

1. If the list is empty, return an empty list.
2. Sort by start.
3. Open a card with a copy of the first range.
4. For each next range: if `next.start <= cur.end`, set `cur.end = max(cur.end, next.end)`. Otherwise add `cur` to the output and open a new card from `next`.
5. After the loop, add the open card to the output.

### Java solution

Work through the hints first, then reveal the code.

<HintLadder hints={hints.merge}>

```java id=merge
public int[][] merge(int[][] intervals) {
    if (intervals.length == 0) return new int[0][];
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
    List<int[]> out = new ArrayList<>();
    int[] cur = intervals[0].clone();
    for (int i = 1; i < intervals.length; i++) {
        int[] next = intervals[i];
        if (next[0] <= cur[1]) {
            cur[1] = Math.max(cur[1], next[1]);   // extend: MAX, never replace
        } else {
            out.add(cur);                         // a gap: cur is finished
            cur = next.clone();
        }
    }
    out.add(cur);                                 // the last open card
    return out.toArray(new int[0][]);
}
```

The `clone()` calls keep the caller's inner arrays untouched. The outer array is reordered by the sort.

</HintLadder>

### Why it works

- **Settled:** every range in `out` is final, sorted, and separated from the next by a real gap. The card covers exactly the union of the ranges read since it was opened.
- **Why the move is safe:** the card's start is the smallest start of everything it holds, and every unread range starts at or after `next.start`. When `next.start > cur.end`, no unread range can touch the card, so closing it is never premature.
- **When we stop:** when the ranges run out. The card left open is emitted after the loop.

### Complexity

- **Time O(n log n):** the sort dominates. The sweep is one O(n) pass.
- **Space O(n):** the output. Java's object sort may use up to O(n) more workspace.

### Edge cases and mistakes

- Empty input, one range, all ranges identical.
- A range nested inside another: `[1,10],[2,3]`.
- Touching ranges `[1,2],[2,3]` merge to `[1,3]`.

Two lines are where nearly everyone slips.

```java fragment
cur[1] = next[1];        // BUG 1: replaces instead of extending
...
return out.toArray(...); // BUG 2: forgot out.add(cur) after the loop
```

Bug 1 breaks on `[[1,10],[2,3],[4,5]]`. The swallowed `[2,3]` shrinks the card to `[1,3]`, and `[4,5]` is wrongly split off. The answer comes out `[[1,3],[4,5]]` instead of `[[1,10]]`. Bug 2 drops the final range on every non-empty input.

### Practice

<Trace title="Extend, close, or finish?" steps={mergeSweep} takeaway="Remember: overlap is decided by next.start against cur.end; the new end is a max; and the last card is emitted after the loop." />

<Reveal q="Why do you never need Math.min for the card's start?">

Because you sorted by start. The card was opened by the earliest range of its group, and everything that joins it starts at the same time or later. A min would always return `cur.start`. It is harmless, but it signals you have not trusted the sort.

Ties in start order don't matter either. If two ranges start together, whichever comes first opens the card and the other extends it with a max.

</Reveal>

**Variations to try:** return the total length covered; merge with a tolerance (`next.start <= cur.end + k`); merge but keep a count of how many ranges each result absorbed.

<h2 id="insert-interval">Chapter 2 · Insert Interval</h2>

### Problem

You get a sorted list of non-overlapping ranges and one new range. Insert the new range and merge anything it overlaps. Touching counts as overlapping.

Ledger `[[1,2],[3,5],[6,7],[8,10],[12,16]]`, new `[4,8]` gives `[[1,2],[3,10],[12,16]]`.

### How to recognise it

- The list is **already sorted and clash-free**. That is a gift: use it.
- One new item is added, not a whole second list.
- The interviewer asks for O(n).

### Brute force

Append the new range, sort everything, and run Merge Intervals. It is correct and a fine fallback. It costs O(n log n) because it re-sorts a list that was already sorted.

### Intuition

Because the ledger is sorted and clash-free, its **ends are sorted too**. So the new range splits the ledger into **three contiguous runs**:

1. **Entirely before** the newcomer: `entry.end < new.start`. Copy them.
2. **Overlapping** the newcomer: `entry.start <= new.end`. Absorb each one into the newcomer.
3. **Entirely after**: everything left. Copy them.

<Figure caption="Phase 1 (grey): 1–2 ends before 4. Phase 2 (gold): 3–5, 6–7 and 8–10 all reach the newcomer, which grows to 3–10. Phase 3 (blue): 12–16 starts after 10 and is copied as it is.">
  <Timeline {...figures.insert} />
</Figure>

### Dry run

<DryRun title="Insert Interval" frames={insertFrames([[1,2],[3,5],[6,7],[8,10],[12,16]], [4,8])} predict />

### Algorithm

1. Walk with one index `i`. Let `start, end` describe the newcomer.
2. While `entry.end < start`: copy the entry.
3. While `entry.start <= end`: set `start = min(start, entry.start)` and `end = max(end, entry.end)`.
4. Add `[start, end]` to the output, once.
5. Copy every remaining entry.

### Java solution

<HintLadder hints={hints.insert}>

```java id=insert
public int[][] insert(int[][] intervals, int[] newInterval) {
    List<int[]> out = new ArrayList<>();
    int i = 0, n = intervals.length;
    int start = newInterval[0], end = newInterval[1];
    while (i < n && intervals[i][1] < start) {       // phase 1: ends before the newcomer
        out.add(intervals[i++]);
    }
    while (i < n && intervals[i][0] <= end) {        // phase 2: overlaps (touching counts)
        start = Math.min(start, intervals[i][0]);
        end = Math.max(end, intervals[i][1]);
        i++;
    }
    out.add(new int[]{start, end});                  // the newcomer, exactly once
    while (i < n) {                                  // phase 3: starts after it
        out.add(intervals[i++]);
    }
    return out.toArray(new int[0][]);
}
```

</HintLadder>

### Why it works

- **Settled:** the output so far is sorted and clash-free. The newcomer covers itself plus every entry it has absorbed.
- **Why the move is safe:** once an entry fails "ends before the newcomer", every later entry fails it too, because ends are sorted. Once an entry starts after the grown newcomer ends, every later one does too. So the three phases really are three contiguous runs.
- **When we stop:** after phase 3 reads the last entry.

### Complexity

- **Time O(n):** each entry is visited once, with no sort.
- **Space O(n):** the output.

### Edge cases and mistakes

- An empty ledger returns just the newcomer.
- A newcomer that lands in a gap absorbs nothing and is still added once.
- A newcomer before everything, or after everything.

The classic bug: writing phase 1 as `intervals[i][1] <= start`. It copies `[1,4]` straight past a newcomer `[4,6]`, leaving `[[1,4],[4,6]]`. Those touch, and this problem says they must be one range, `[[1,6]]`.

Only the **first** absorbed entry can lower the start and only the **last** can raise the end. Using `min` and `max` on every step is simpler and still correct.

### Practice

<Reveal q="Why not just append the newcomer and run Merge Intervals?">

It gives the right answer and is a fine fallback under pressure. But it re-sorts a sorted ledger: O(n log n) instead of O(n). The interviewer handed you sorted input on purpose, so say so and then use it.

You could also binary search for where phase 2 begins. It doesn't change the bound, because building the output is O(n) anyway.

</Reveal>

<h2 id="meeting-rooms">Chapter 3 · Meeting Rooms</h2>

### Problem

LeetCode premium. Given meetings `[start, end]` with `start < end`, return `true` if one person can attend all of them, meaning no two overlap. A meeting ending at 10 and another starting at 10 do **not** clash, so meetings are effectively `[start, end)`.

`[[0,30],[5,10],[15,20]]` gives `false`. `[[7,10],[2,4]]` gives `true`.

### How to recognise it

- A yes/no question: does **any** clash exist?
- You don't need to know which ranges clash or how many.
- Back-to-back is allowed, so the test is strict.

### Brute force

Compare every meeting with every other: O(n²) pairs. It works, but it does far more checking than needed.

### Intuition

After sorting by start, you only need to compare **neighbours**. Suppose some pair clashes, and take the clashing pair `(j, i)` closest together in start order. If they are not neighbours, the meeting `j + 1` between them starts no earlier than `j` and no later than `i`. Since `i` starts before `j` ends, so does `j + 1`. Then `j` and `j + 1` clash too, which is a closer pair. That contradicts our choice. So the closest clashing pair is always two neighbours.

<Figure caption="The diary in start order. 5–10 starts before 0–30 ends, so the answer is false the moment you compare the first neighbours.">
  <Timeline {...figures.attend} />
</Figure>

### Dry run

First an input where touching is fine, then one with a clash.

<DryRun title="Meeting Rooms: all fit" frames={attendFrames([[7,10],[2,4],[4,6]])} predict />

<DryRun title="Meeting Rooms: a clash" frames={attendFrames([[0,30],[5,10],[15,20]])} predict />

### Algorithm

1. Sort by start.
2. For each meeting from the second on, compare its start with the previous meeting's end.
3. If `start < previous.end`, return `false`.
4. If the loop finishes, return `true`.

### Java solution

<HintLadder hints={hints.attend}>

```java id=canAttendMeetings
public boolean canAttendMeetings(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] < intervals[i - 1][1]) return false;   // starts before the previous ends
    }
    return true;
}
```

</HintLadder>

### Why it works

- **Settled:** every meeting before `i` has been checked against its predecessor and none clash.
- **Why the move is safe:** the neighbour argument above. If any clash existed, a neighbouring pair would show it.
- **When we stop:** at the first clash (return false) or after the last meeting (return true).

### Complexity

- **Time O(n log n):** the sort. The scan is O(n).
- **Space O(1)** extra, beyond what the sort uses.

### Edge cases and mistakes

- Zero or one meeting is trivially `true`.
- `<=` instead of `<` rejects back-to-back meetings like `[[1,5],[5,8]]`.
- Skipping the sort makes `[[7,10],[2,4]]` look like a clash.

### Practice

<Trace title="Can she attend them all?" steps={attendAll} takeaway="Remember: sort first, compare each meeting with its predecessor, and use start < previous end. Back-to-back is not a clash." />

<Reveal q="Why is comparing neighbours enough? Couldn't meeting 4 clash with meeting 1 while 2 and 3 look fine?">

Suppose some pair clashes, and pick the clashing pair `(j, i)` that is closest together in start order. If they are not neighbours, look at meeting `j + 1`, which sits between them. It starts no earlier than `j` and no later than `i`, so it starts before `j` ends (since `i` does). It also ends after it starts. So `j` and `j + 1` clash: a closer pair, contradicting our choice. The closest clashing pair is always a pair of neighbours.

</Reveal>

**Variation:** return the first pair that clashes. The same loop works: return `[intervals[i-1], intervals[i]]` at the clash.

<h2 id="meeting-rooms-ii">Chapter 4 · Meeting Rooms II</h2>

### Problem

LeetCode premium. Given meetings `[start, end]` with `start < end`, return the minimum number of rooms so every meeting has a room for its whole duration. A room freed at time `t` can host a meeting that starts at `t`.

`[[0,30],[5,10],[15,20]]` gives `2`. `[[7,10],[2,4]]` gives `1`.

### How to recognise it

- "Minimum number of rooms / platforms / servers / resources."
- The real question is **the largest number of meetings running at the same moment**.
- Fewer rooms than that peak is impossible: at the busiest moment each running meeting needs its own room. The peak is also always enough, as Method 2 shows by actually handing out that many rooms.

### Brute force

For every start time, count how many meetings are running at that moment. That is O(n) per time, O(n²) in total. It is correct because the peak always happens at some meeting's start.

### Intuition

You don't need to look at meetings at all. Only **changes** matter: +1 when a meeting starts and −1 when one ends. Sort those changes by time and keep a running total. The largest running total is the answer.

**The tie rule: at the same time, process checkouts before check-ins.** A room freed at 10 is free for a meeting starting at 10. If the check-in went first, the count would briefly include both and show a phantom room. In code, sort `(time, delta)` pairs by time, then by delta, so `−1` sorts before `+1`.

<Figure caption="The running count. At 10 the checkout is processed before the check-in, so the count goes 2 → 1 → 2 and never reads 3. The peak is 2 rooms.">
  <Timeline {...figures.roomsSweep} />
</Figure>

### Dry run

Method 1: the event sweep. Watch the tie at time 10.

<DryRun title="Meeting Rooms II: event sweep" frames={roomsSweepFrames([[0,30],[5,10],[10,20]])} predict />

### Algorithm

1. Make two events per meeting: `(start, +1)` and `(end, −1)`.
2. Sort by time; at equal times, `−1` before `+1`.
3. Walk the events, adding each delta to `inUse`.
4. After each event, update `rooms = max(rooms, inUse)`.
5. Return `rooms`.

### Java solution

<HintLadder hints={hints.roomsSweep}>

```java id=minMeetingRooms
public int minMeetingRooms(int[][] intervals) {
    int[][] events = new int[intervals.length * 2][];
    int k = 0;
    for (int[] m : intervals) {
        events[k++] = new int[]{m[0], +1};   // check-in
        events[k++] = new int[]{m[1], -1};   // checkout
    }
    // Earlier time first; at the same time, -1 (checkout) before +1 (check-in).
    Arrays.sort(events, (a, b) -> a[0] != b[0] ? Integer.compare(a[0], b[0]) : Integer.compare(a[1], b[1]));
    int inUse = 0, rooms = 0;
    for (int[] e : events) {
        inUse += e[1];
        rooms = Math.max(rooms, inUse);
    }
    return rooms;
}
```

</HintLadder>

### Why it works

- **Settled:** `inUse` is the number of meetings running after all events processed so far.
- **Why the tie rule is exactly right:** with checkouts first, the count right after all events at time `t` equals the number of meetings running from `t` until the next event. The counts in between are never higher. So the largest count seen is exactly the busiest moment. With check-ins first, the in-between counts can overshoot.
- **When we stop:** after the last event.

### Complexity

- **Time O(n log n):** sorting 2n events.
- **Space O(n):** the event array.

### Edge cases and mistakes

- Back-to-back meetings `[[10,20],[0,10]]` need only one room.
- Sorting events by time alone, with check-ins and checkouts in input order, can report a phantom room: on `[[10,20],[0,10]]` it answers 2. Encode the tie in the comparator.
- A single meeting needs 1 room; no meetings need 0.

### Method 2: min-heap of end times

Take meetings **in start order** and keep a **min-heap** with one entry per room opened: the time that room's latest meeting ends. For each new meeting:

- If the room that frees earliest (`heap.peek()`) is free by the meeting's start (`<= start`), **reuse it**: `poll()` its old end time.
- Either way, `offer()` the meeting's end. That room is busy until then.

The answer is the heap's size at the end. Why:

- **The heap is not the set of rooms in use right now.** A room that has emptied stays in the heap until a later meeting reuses it. Each meeting pops **at most one** entry and always pushes one, so the size goes up by one (a new room) or stays the same (a reused room). **It never shrinks.** So the final size is the number of rooms ever opened.
- **A new room opens only when it must.** That happens only when even the earliest-freeing room ends after this meeting's start. Then every room in the heap holds a meeting that started at or before this one (start order) and is still running now. All of them plus the newcomer run at the same moment. So the rooms opened never exceed the peak overlap, and cannot be less.

<Figure caption="The heap method on 0–5, 1–2, 6–7. 1–2 arrives while room A is busy until 5, so room B opens. At 6, room B (free since 2) is reused. The heap ends holding 5 and 7: size 2 = rooms opened = the answer, even though at 6 only one meeting is running.">
  <Timeline {...figures.roomsHeap} />
</Figure>

<DryRun title="Meeting Rooms II: min-heap" frames={roomsHeapFrames([[0,5],[1,2],[6,7]])} predict />

**Algorithm:** sort by start; for each meeting, poll if `peek <= start`; offer the meeting's end; return the heap size.

<HintLadder hints={hints.roomsHeap}>

```java id=minMeetingRoomsHeap
public int minMeetingRoomsHeap(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
    PriorityQueue<Integer> roomFreeAt = new PriorityQueue<>();   // one entry per room ever opened
    for (int[] m : intervals) {
        if (!roomFreeAt.isEmpty() && roomFreeAt.peek() <= m[0]) {
            roomFreeAt.poll();          // reuse the room that frees earliest
        }
        roomFreeAt.offer(m[1]);         // that room is busy until m[1]
    }
    return roomFreeAt.size();           // never shrank, so this is the number of rooms opened
}
```

</HintLadder>

**Complexity:** O(n log n) time: the sort, plus at most one poll and one offer per meeting. O(n) space for the heap in the worst case (every meeting overlapping). This version previews the <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> pattern.

### Practice

<Trace title="Click up, click down" steps={roomsSweep} takeaway="Remember: the answer is the peak of the running count; checkouts before check-ins at equal times; and the heap's size counts rooms ever opened, not rooms busy right now." />

<Reveal q="Could you add up all the changes at each time instead of ordering them?">

Yes. Put every `+1` and `−1` into a `TreeMap<Integer, Integer>` keyed by time, summing the changes that share a time, then walk the map in key order. At 10 the net change is `−1 + 1 = 0`, so no phantom ever appears. This "difference map" is a valid alternative. It is the same idea as the difference array in the Car Pooling side quest, and the usual solution to My Calendar III.

The other classic variant keeps two sorted arrays, `starts` and `ends`, and walks them like two pointers: whenever the next end is `<=` the next start, free a room first. The playground's room-counting mode works this way.

</Reveal>

<Reveal q="What if you popped every free room with while instead of if?">

Then the heap would hold exactly the rooms busy right now, and its **final** size would no longer be the answer. On `[[0,5],[1,2],[6,7]]`, at 6 the loop pops both 2 and 5, pushes 7, and ends with size 1. The answer is 2. With `while`, you must record the largest size seen after each push. Either way is correct if you are consistent. Mixing `while` with `return size()` is the bug.

</Reveal>

<h2 id="non-overlapping">Chapter 5 · Non-overlapping Intervals</h2>

### Problem

Given ranges, return the **minimum number to remove** so the rest do not overlap. Touching is allowed: LeetCode states that `[1,2]` and `[2,3]` do not overlap.

`[[1,2],[2,3],[3,4],[1,3]]` gives `1` (remove `[1,3]`).

### How to recognise it

- "Fewest removals", "most you can keep", "maximum number of non-conflicting tasks".
- Every kept item is worth the same (1), however long it is.
- This is classic **activity selection**.

### Brute force

Try every subset of ranges, keep the valid ones, and take the biggest: O(2ⁿ · n). Hopeless beyond about 20 ranges.

### Intuition

Fewest cancellations is the same as **most bookings kept**. Each one is worth 1, so what matters is how much room a kept booking leaves for the rest. The booking that **ends earliest** leaves the most room.

So: **sort by end time. Keep a booking whenever it starts at or after `lastEnd`; otherwise cancel it.** Start order fails: one long booking such as `[1,100]` would be kept first and block everything.

<Figure caption="End order: 2–4, 5–7, 8–11 are kept (green); 1–12 starts before 11 and is cancelled. One cancellation. Start order would have kept 1–12 first and cancelled the other three.">
  <Timeline {...figures.keepByEnd} />
</Figure>

### Dry run

<DryRun title="Non-overlapping Intervals" frames={keepFrames([[1,12],[2,4],[5,7],[8,11]])} predict />

### Algorithm

1. Sort by end.
2. Set `lastEnd` to negative infinity and `kept = 0`.
3. For each range: if `start >= lastEnd`, keep it (`kept++`, `lastEnd = end`). Otherwise cancel it.
4. Return `n − kept`.

### Java solution

<HintLadder hints={hints.eraseOverlap}>

```java id=eraseOverlapIntervals
public int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));
    int kept = 0;
    long lastEnd = Long.MIN_VALUE;           // nothing kept yet
    for (int[] iv : intervals) {
        if (iv[0] >= lastEnd) {              // touching is not a clash here
            kept++;
            lastEnd = iv[1];
        }
    }
    return intervals.length - kept;
}
```

</HintLadder>

### Why it works

The exchange argument.

- Let `g` be the booking that ends earliest. Take any best plan, and let `f` be its earliest-ending booking. Swap `f` for `g`. Every other booking in the plan starts at or after `f.end`, and `g.end <= f.end`, so they all still fit. The plan is still valid and just as large. So **some best plan always starts with `g`**.
- **Settled:** the kept bookings never overlap, and some best plan contains all of them.
- **Why the move is safe:** keep `g`, discard everything that starts before `g.end`, and repeat the same argument on what is left.
- **When we stop:** after the last booking.

### Complexity

- **Time O(n log n):** the sort. The scan is O(n).
- **Space O(1)** extra beyond the sort. The `long` sentinel handles an empty input and the first booking without a special case.

### Edge cases and mistakes

- `iv[0] > lastEnd` cancels touching bookings: `[[1,2],[2,3]]` would report 1 instead of 0.
- Sorting by start with the same rule fails `[[1,100],[2,3],[4,5]]`. Start order keeps `[1,100]` and cancels 2; end order keeps `[2,3]` and `[4,5]` and cancels 1.
- This is activity selection. The same greedy shows up again in the <a href={`${BASE}dsa/lessons/greedy/`}>Greedy</a> part of the roadmap.

### Practice

<Trace title="Keep or cancel?" steps={keepByEnd} takeaway="Remember: sort by END; keep when start >= lastEnd; count cancellations as n − kept. The longest booking is not the most valuable." />

<Reveal q="Can start order ever work?">

Yes, with a different rule. Sort by start, and on a clash cancel **whichever of the two ends later** (keep `lastEnd = min(lastEnd, end)`). That is the earliest-end idea in disguise, and it gives the same answer. What fails is start order with the same keep-if-it-fits rule.

</Reveal>

<h2 id="burst-balloons">Side quest 1 · Minimum Arrows to Burst Balloons</h2>

### Problem

Balloons span `[start, end]` along a wall. An arrow shot at position `x` pops every balloon with `start <= x <= end`. Pop them all with the **fewest arrows**.

`[[10,16],[2,8],[1,6],[7,12]]` gives `2`.

### How to recognise it

- "Fewest points that hit every range."
- This is Chapter 5 with one rule changed: **touching now counts.** `[1,2]` and `[2,3]` share the point 2, so one arrow pops both.

### Brute force

Try every set of arrow positions: exponential. A smaller version tries every endpoint as an arrow and picks greedily by "which pops the most", which is O(n²) and not even correct in general.

### Intuition

Look at the balloon that ends first. Some arrow must hit it at or before its end. Slide that arrow right, all the way to the end, and it never pops fewer: no balloon ends earlier, so everything it popped is still under it. So **fire at the earliest end**, sweep away every balloon that has started by then, and repeat.

<Figure caption="The example sorted by end. The arrow at 6 pops 1–6 and 2–8; 7–12 starts after 6, so a second arrow goes at 12 and also pops 10–16. Two arrows.">
  <Timeline {...figures.arrows} />
</Figure>

### Dry run

<DryRun title="Burst Balloons" frames={arrowsFrames([[10,16],[2,8],[1,6],[7,12]])} predict />

### Algorithm

1. Sort by end (with `Integer.compare`).
2. Fire the first arrow at the first balloon's end.
3. For each next balloon: if `start > arrowAt`, fire a new arrow at its end.
4. Return the arrow count.

### Java solution

<HintLadder hints={hints.arrows}>

```java id=findMinArrowShots
public int findMinArrowShots(int[][] points) {
    if (points.length == 0) return 0;
    Arrays.sort(points, (a, b) -> Integer.compare(a[1], b[1]));   // never a[1] - b[1]: it can overflow
    int arrows = 1;
    int arrowAt = points[0][1];
    for (int i = 1; i < points.length; i++) {
        if (points[i][0] > arrowAt) {        // strictly after: touching balloons share the arrow
            arrows++;
            arrowAt = points[i][1];
        }
    }
    return arrows;
}
```

</HintLadder>

### Why it works

- **Settled:** every balloon before `i` is popped by some fired arrow, and the last arrow sits as far right as it can.
- **Why the move is safe:** the earliest-ending unpopped balloon needs an arrow at or before its end; moving that arrow to the end only widens what it can reach.
- **When we stop:** after the last balloon.

### Complexity

**O(n log n)** time for the sort, **O(1)** extra space beyond it.

### Edge cases and mistakes

Coordinates span the whole `int` range, and the comparator `(a, b) -> a[1] - b[1]` overflows. On `[[-2147483646,-2147483645],[2147483646,2147483647]]` the subtraction wraps around, the sort puts the balloons in the wrong order, and the answer becomes 1 instead of 2. Always use `Integer.compare`.

Also: an empty array needs 0 arrows, and `>=` instead of `>` would give touching balloons separate arrows.

### Practice

**Transfer test:** the answer here equals the most balloons you can choose with no two touching. Why are "fewest stabbing points" and "most disjoint intervals" the same number?

<h2 id="interval-intersections">Side quest 2 · Interval List Intersections</h2>

### Problem

Two lists of ranges, each sorted and free of internal overlaps. Ends are included. Return every range where **both** lists are present.

A: `[0,2],[5,10],[13,23],[24,25]`, B: `[1,5],[8,12],[15,24],[25,26]` gives `[1,2],[5,5],[8,10],[15,23],[24,24],[25,25]`.

### How to recognise it

- Two sorted lists of ranges and a question about where **both** apply.
- Nothing needs sorting. The input already is.

### Brute force

Compare every slot of A with every slot of B: O(m · n). It ignores that both lists are sorted.

### Intuition

Give each list a reader, `i` and `j`. The current slots overlap from `lo = max(starts)` to `hi = min(ends)`. Record it if `lo <= hi`.

Then **advance whichever slot ends first.** Its business is finished: the other list's later slots all start after that list's current slot ends, which is no earlier than this one's end. So nothing left can reach it.

<Figure caption="Each A∩B piece runs from the later start to the earlier end. Single-point overlaps such as 5–5 and 24–24 count, because ends are included.">
  <Timeline {...figures.intersections} />
</Figure>

### Dry run

<DryRun title="Interval List Intersections" frames={intersectFrames([[0,2],[5,10],[13,23],[24,25]], [[1,5],[8,12],[15,24],[25,26]])} predict />

### Algorithm

1. Start `i = 0`, `j = 0`.
2. While both are in range: `lo = max` of the starts, `hi = min` of the ends.
3. If `lo <= hi`, record `[lo, hi]`.
4. Advance the reader whose slot ends first.

### Java solution

<HintLadder hints={hints.intersections}>

```java id=intervalIntersection
public int[][] intervalIntersection(int[][] firstList, int[][] secondList) {
    List<int[]> out = new ArrayList<>();
    int i = 0, j = 0;
    while (i < firstList.length && j < secondList.length) {
        int lo = Math.max(firstList[i][0], secondList[j][0]);
        int hi = Math.min(firstList[i][1], secondList[j][1]);
        if (lo <= hi) out.add(new int[]{lo, hi});
        if (firstList[i][1] < secondList[j][1]) i++;   // the one that ends first is finished
        else j++;
    }
    return out.toArray(new int[0][]);
}
```

</HintLadder>

### Why it works

- **Settled:** every overlap involving a slot before `i` or before `j` has been recorded.
- **Why the move is safe:** the slot that ends first can't meet anything later in the other list.
- **When we stop:** when either list runs out.

### Complexity

**O(m + n)** time, since every step advances one reader. Output is at most m + n slots. This is the merge step from <a href={`${BASE}dsa/lessons/two-pointers/`}>Two Pointers</a>, applied to ranges.

### Edge cases and mistakes

- An empty list gives an empty result.
- Single-point overlaps `[5,5]` count when ends are included, so use `lo <= hi`, not `lo < hi`.
- Advancing the slot that starts first can lose an overlap (see below).

### Practice

<Reveal q="Why advance the slot that ends first, and not the one that starts first?">

The slot that ends first, say `A[i]`, is done: every later slot in B starts after `B[j]` ends, and `B[j]` ends no earlier than `A[i]`. So nothing left in B can reach `A[i]`. The slot that *starts* first might be long and still overlap `B[j + 1]`, so advancing it would lose that overlap. On ties, advancing either one is safe.

</Reveal>

**Transfer test:** change the output to the **union** of both lists. Which chapter's code do you reach for, and do you still need to sort?

<h2 id="free-time">Side quest 3 · Employee Free Time</h2>

### Problem

LeetCode premium, hard. Each employee has a sorted list of non-overlapping shifts `[start, end]`. Return every stretch of **positive length** when **nobody** is working, between the first shift's start and the last shift's end. (LeetCode uses an `Interval` class; here `int[][][]`.)

`[[[1,2],[5,6]],[[1,3]],[[4,10]]]` gives `[[3,4]]`.

### How to recognise it

- "Common free time", "when is everyone available".
- Free for everyone means **outside the union of everyone's busy time**.

### Brute force

Check every unit of time against every employee: O(T · employees). It breaks when times are large.

### Intuition

It looks hard and is not. Pool every shift, sort by start, and run Chapter 1's sweep. Instead of emitting the merged blocks, emit the **gaps between them**.

<Figure caption="Pooled and merged, the busy time is 1–3 and 4–10. The only gap is 3–4: the one stretch when all three employees are off.">
  <Timeline {...figures.freeTime} />
</Figure>

### Dry run

<DryRun title="Employee Free Time" frames={freeTimeFrames([[[1,2],[5,6]],[[1,3]],[[4,10]]])} predict />

### Algorithm

1. Pool all shifts into one list and sort by start.
2. Set `busyUntil` to the first shift's end.
3. For each shift: if `start > busyUntil`, record the gap `[busyUntil, start]`.
4. Set `busyUntil = max(busyUntil, end)`.

### Java solution

<HintLadder hints={hints.freeTime}>

```java id=employeeFreeTime
public int[][] employeeFreeTime(int[][][] schedule) {
    List<int[]> all = new ArrayList<>();
    for (int[][] person : schedule) for (int[] shift : person) all.add(shift);
    if (all.isEmpty()) return new int[0][];
    all.sort((a, b) -> Integer.compare(a[0], b[0]));
    List<int[]> free = new ArrayList<>();
    int busyUntil = all.get(0)[1];
    for (int[] shift : all) {
        if (shift[0] > busyUntil) free.add(new int[]{busyUntil, shift[0]});   // a real gap
        busyUntil = Math.max(busyUntil, shift[1]);
    }
    return free.toArray(new int[0][]);
}
```

</HintLadder>

### Why it works

- **Settled:** `busyUntil` is the end of the merged busy block so far, and every gap before it is recorded.
- **Why the move is safe:** the same argument as Merge Intervals. A shift starting after `busyUntil` proves nothing earlier or later covers that gap.
- **When we stop:** after the last shift. There is no trailing gap, since we only report time between the first start and last end.

### Complexity

**O(N log N)** time for N shifts in total, **O(N)** space for the pooled list.

### Edge cases and mistakes

`shift[0] >= busyUntil` reports zero-length "gaps" like `[3,3]` when one shift ends as another starts. The problem wants positive length only. Also handle no shifts at all.

### Practice

**Transfer test:** each employee's list is already sorted. How could a heap that holds one shift per employee avoid sorting everything, and what would the time become for k employees?

<h2 id="my-calendar">Side quest 4 · My Calendar I</h2>

### Problem

Requests arrive **one at a time** and each must be accepted or refused on the spot. A request `[start, end)` is accepted only if it does not clash with anything already accepted.

`book(10,20)` true, `book(15,25)` false, `book(20,30)` true.

### How to recognise it

- An **online** problem: you cannot sort requests you haven't seen.
- "Design a calendar / booking system."

### Brute force

Keep a list and check every accepted booking for each request. That is O(n) per request and O(n²) over n requests.

### Intuition

The accepted bookings never overlap each other, so in start order their ends are in order too. A new request can only clash with **its two neighbours**: the accepted booking that starts at or just before `start`, and the one that starts at or just after. Anything further away is blocked by those two. A `TreeMap` from start to end finds both in O(log n): `floorEntry(start)` and `ceilingEntry(start)`.

<Figure caption="book(10, 20) is accepted; book(15, 25) is refused because 10–20 runs past 15; book(20, 30) is accepted. Touching is fine for [start, end) bookings.">
  <Timeline {...figures.calendar} />
</Figure>

### Dry run

<DryRun title="My Calendar I" frames={calendarFrames([[10,20],[15,25],[20,30],[5,10],[12,14]])} predict />

### Algorithm

1. Look up the booking that starts at or before `start` (the floor).
2. Look up the booking that starts at or after `start` (the ceiling).
3. Refuse if the floor ends after `start`, or the ceiling starts before `end`.
4. Otherwise store `start → end` and accept.

### Java solution

<HintLadder hints={hints.calendar}>

```java id=myCalendar
class MyCalendar {
    private final TreeMap<Integer, Integer> booked = new TreeMap<>();   // start -> end, never overlapping

    public boolean book(int start, int end) {                            // [start, end)
        Map.Entry<Integer, Integer> before = booked.floorEntry(start);   // starts at or before start
        Map.Entry<Integer, Integer> after = booked.ceilingEntry(start);  // starts at or after start
        if (before != null && before.getValue() > start) return false;   // runs past our start
        if (after != null && after.getKey() < end) return false;         // begins before our end
        booked.put(start, end);
        return true;
    }
}
```

</HintLadder>

### Why it works

- **Settled:** `booked` holds only non-overlapping bookings, so its ends are sorted along with its starts.
- **Why the move is safe:** if any accepted booking clashed with the request, one of the two neighbours would too.
- **When we stop:** each call finishes after at most two lookups and one insert.

### Complexity

**O(log n)** per request, **O(n)** space.

### Edge cases and mistakes

- Touching bookings are accepted: use `>` and `<`, not `>=` and `<=`.
- A request with the same start as an accepted one: the floor entry has `start`, and its end is greater than `start`, so it is refused.
- A request that fully contains an accepted booking is caught by the ceiling check.

<h2 id="car-pooling">Side quest 5 · Car Pooling</h2>

### Problem

A vehicle drives one way with `capacity` seats. Each trip is `[riders, pickup, dropoff]`. Riders leave at their dropoff **before** anyone boards there. Can the vehicle serve every trip?

`[[2,1,5],[3,3,7]]` with capacity 4 gives `false`; with capacity 5 it gives `true`.

### How to recognise it

- "Can capacity ever be exceeded along a route or timeline?"
- It is Meeting Rooms II with weights.

### Brute force

For every location, add up the riders of every trip covering it: O(L · n). Fine only for tiny inputs.

### Intuition

Each trip is an event `(pickup, +riders)` and `(dropoff, −riders)`. Sort by location, with **dropoffs before pickups** at the same place (Chapter 4's tie rule), and watch the running load. If it ever exceeds `capacity`, the answer is `false`.

<Figure caption="Between 3 and 5 both trips are aboard: 2 + 3 = 5 riders. With 4 seats the answer is false; with 5 it is true.">
  <Timeline {...figures.carPool} />
</Figure>

### Dry run

<DryRun title="Car Pooling, 4 seats" frames={carPoolFrames([[2,1,5],[3,3,7]], 4)} predict />

### Algorithm

1. Make events `(pickup, +riders)` and `(dropoff, −riders)`.
2. Sort by place; at the same place, the negative change first.
3. Add each change to `load`; if `load > capacity`, return `false`.
4. Return `true` after the last event.

### Java solution

<HintLadder hints={hints.carPool}>

```java id=carPooling
public boolean carPooling(int[][] trips, int capacity) {
    int[][] events = new int[trips.length * 2][];
    int k = 0;
    for (int[] t : trips) {
        events[k++] = new int[]{t[1], t[0]};     // board t[0] riders at t[1]
        events[k++] = new int[]{t[2], -t[0]};    // they leave at t[2]
    }
    // By place; at the same place, negative (dropoff) before positive (pickup).
    Arrays.sort(events, (a, b) -> a[0] != b[0] ? Integer.compare(a[0], b[0]) : Integer.compare(a[1], b[1]));
    int load = 0;
    for (int[] e : events) {
        load += e[1];
        if (load > capacity) return false;
    }
    return true;
}
```

</HintLadder>

### Why it works

- **Settled:** `load` is the number of riders aboard after all events so far, and it never exceeded `capacity`.
- **Why the move is safe:** with dropoffs first, the load after each place equals the true load on the road just after it.
- **When we stop:** at the first overflow, or after the last event.

### Complexity

**O(n log n)** time, **O(n)** space.

### Edge cases and mistakes

- `[[2,1,5],[3,5,7]]` with 3 seats must be `true`: riders leave at 5 before others board at 5. Pickups first would count 5 riders.
- A single trip larger than capacity fails immediately.

### Practice

<Reveal q="LeetCode bounds the locations by 1000. Can you skip the sort?">

Yes: a **difference array**. Make `int[] change = new int[1001]`, add `riders` at `pickup` and subtract at `dropoff`, then take running sums from left to right. The load at location `x` is the running sum at `x`, and the dropoff-first rule happens automatically because both changes land in the same cell. That is O(n + L) for L locations. It is the <a href={`${BASE}dsa/lessons/prefix-sum/`}>Prefix Sum</a> lesson's trick, run on a timeline.

</Reveal>

<h2 id="covered-intervals">Side quest 6 · Remove Covered Intervals</h2>

### Problem

Some ranges lie entirely inside another (`c <= a` and `b <= d` means `[a,b)` is covered by `[c,d)`). Remove every covered one and return how many remain. All intervals are distinct.

`[[1,4],[3,6],[2,8]]` gives `2` (`[3,6]` is inside `[2,8]`).

### How to recognise it

- "Remove ranges contained in others."
- It needs a sort with a **two-key comparator**.

### Brute force

For each range, check whether any other range covers it: O(n²).

### Intuition

Sort by start. Everything before a range starts no later, so the range is covered **exactly when something before it reaches at least as far**. Track `furthestEnd`; a range survives only if its end goes beyond it.

The trap is the **tie**. When two ranges start together, the longer one must come first, or the shorter one is counted before its cover arrives. Sort by start ascending, then **end descending**.

### Dry run

<DryRun title="Remove Covered Intervals" frames={coveredFrames([[1,4],[3,6],[2,8],[1,2]])} predict />

### Algorithm

1. Sort by start ascending; on equal starts, larger end first.
2. Set `furthestEnd` to negative infinity and `remaining = 0`.
3. For each range: if `end > furthestEnd`, it survives (`remaining++`, `furthestEnd = end`).
4. Otherwise it is covered.

### Java solution

<HintLadder hints={hints.covered}>

```java id=removeCoveredIntervals
public int removeCoveredIntervals(int[][] intervals) {
    // Start ascending; on equal starts the LONGER interval first, so it can cover the shorter one.
    Arrays.sort(intervals, (a, b) -> a[0] != b[0] ? Integer.compare(a[0], b[0]) : Integer.compare(b[1], a[1]));
    int remaining = 0;
    long furthestEnd = Long.MIN_VALUE;
    for (int[] iv : intervals) {
        if (iv[1] > furthestEnd) {     // reaches past everything before it: not covered
            remaining++;
            furthestEnd = iv[1];
        }
    }
    return remaining;
}
```

</HintLadder>

### Why it works

- **Settled:** `furthestEnd` is the largest end among ranges seen so far; those ranges all start no later than the current one.
- **Why the move is safe:** the current range is covered exactly when some earlier range ends at or beyond its end. Surviving ranges have strictly increasing ends.
- **When we stop:** after the last range.

### Complexity

**O(n log n)** time, **O(1)** extra space beyond the sort.

### Edge cases and mistakes

With ends sorted ascending on ties, `[[1,2],[1,4]]` goes wrong. `[1,2]` comes first and survives, then `[1,4]` survives too: answer 2, but `[1,2]` lies inside `[1,4]` and the right answer is 1. With the longer one first, `[1,4]` sets `furthestEnd = 4` and `[1,2]` is correctly found covered.

### Practice

<Reveal q="With ends sorted ascending on ties, what goes wrong on [[1,2],[1,4]]?">

`[1,2]` comes first: its end 2 beats the starting `furthestEnd`, so it survives. Then `[1,4]` reaches 4, so it survives too. Answer 2, but `[1,2]` lies inside `[1,4]`, and the right answer is 1. With the longer one first, `[1,4]` sets `furthestEnd = 4` and `[1,2]` is correctly found covered.

</Reveal>

<h2 id="choose-the-tool">When greedy fails · Weighted jobs</h2>

### Problem

Jobs have a fee: `1–4` pays 10, `2–3` pays 1, `3–5` pays 1. Choose non-clashing jobs for the most total pay. This is Maximum Profit in Job Scheduling.

### How to recognise it

It looks like Chapter 5, but every job now has a **weight**. The end-order greedy keeps `2–3` and `3–5` and earns 2. The best is `1–4` alone: 10.

### Brute force

Try every subset of jobs: O(2ⁿ).

### Intuition

The exchange argument in Chapter 5 swapped one booking for another of **equal value**. With weights, swapping a 10-coin job for a 1-coin job that ends earlier is not "just as good". The greedy has no proof.

**Weighted interval scheduling needs dynamic programming.** Sort jobs by end. For each job, either skip it (best so far stays) or take it plus the best plan that **finishes by its start**, found with a binary search over the sorted ends.

### Dry run

State: `best[k]` = most pay using the first `k` jobs in end order. Recurrence: `best[k+1] = max(best[k], best[lo] + pay)`, where `lo` counts earlier jobs ending by this job's start. Base: `best[0] = 0`.

<DryRun title="Weighted job scheduling (DP table)" frames={jobsFrames([1,2,3], [4,3,5], [10,1,1])} predict />

### Algorithm

1. Sort job indices by end time; copy the sorted ends into `ends[]`.
2. `best[0] = 0`.
3. For each job in order, binary search `lo` = number of earlier jobs with `end <= start`.
4. `best[k+1] = max(best[k], best[lo] + profit)`.
5. Return `best[n]`.

### Java solution

<HintLadder hints={hints.jobs}>

```java id=jobScheduling
public int jobScheduling(int[] startTime, int[] endTime, int[] profit) {
    int n = startTime.length;
    Integer[] order = new Integer[n];
    for (int i = 0; i < n; i++) order[i] = i;
    Arrays.sort(order, (a, b) -> Integer.compare(endTime[a], endTime[b]));
    int[] ends = new int[n];
    for (int k = 0; k < n; k++) ends[k] = endTime[order[k]];
    int[] best = new int[n + 1];               // best[k] = most pay using the first k jobs by end
    for (int k = 0; k < n; k++) {
        int job = order[k];
        int lo = 0, hi = k;                    // how many earlier jobs end by this job's start?
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (ends[mid] <= startTime[job]) lo = mid + 1;
            else hi = mid;
        }
        best[k + 1] = Math.max(best[k], best[lo] + profit[job]);
    }
    return best[n];
}
```

</HintLadder>

### Why it works

Any plan either excludes the job (so it is a plan over the first `k` jobs) or includes it, in which case the rest must finish by its start: a plan over the first `lo` jobs. Taking the better of the two covers every plan.

### Complexity

**O(n log n)** time (sort plus a binary search per job), **O(n)** space.

### Edge cases and mistakes

Touching jobs are compatible (`<=`). LeetCode's limits keep the total within `int`; use `long` if pay can be larger. Using the end-order greedy here is the classic mistake.

### Practice

Two other places where a single sweep is the wrong tool:

- **Many questions about one fixed set.** "How many bookings cover time `t`?" asked 100,000 times: sort the starts and the ends separately, and answer each query with two <a href={`${BASE}dsa/lessons/binary-search/`}>binary searches</a>. The count is the number of starts `<= t` minus the number of ends `<= t` (for `[start, end)` bookings).
- **Requests that arrive over time.** Sorting needs the whole input. Online accept/refuse belongs in an ordered map (Side quest 4).

<Reveal q="Does every interval problem start by sorting by start?">

No. Non-overlapping Intervals and Burst Balloons sort by **end**; Remove Covered Intervals needs a two-key sort; Insert Interval and Interval List Intersections get sorted input and must not re-sort; My Calendar can't sort at all. The real first question is: **what order makes the next decision safe?**

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see | Start with | The promise to keep |
|---|---|---|
| Merge / combine overlapping ranges | Sort by start; extend with max or close at a gap | Emitted ranges are final; the card is the union of what it absorbed |
| Insert into sorted, clash-free ranges | Three phases: before / absorb / after | O(n), no re-sort; the newcomer is added once |
| Can one person attend everything? | Sort by start; compare neighbours with `<` | The closest clashing pair is always a pair of neighbours |
| Fewest rooms / most at once | Events +1/−1, ends before starts on ties; or a min-heap of end times | Answer = peak count = rooms ever opened |
| Fewest removals / most non-overlapping | Sort by END; keep if `start >= lastEnd` | Some best plan contains every kept booking |
| Fewest points that stab every range | Sort by end; new point only if `start > point` | Each point sits at the earliest unstabbed end |
| Overlaps of two sorted lists | Two readers; record `[max start, min end]`; advance the one ending first | A slot that ends first cannot meet anything later |
| Common free time | Pool, sort, merge; report the gaps | Gaps are outside everyone's busy time |
| Accept/refuse bookings online | `TreeMap`: check floor and ceiling only | Accepted bookings never overlap |
| Capacity over a route or timeline | Weighted events, removals first; or a difference array | The peak load decides |
| Remove ranges inside others | Sort by start, end descending; track the furthest end | Covered if and only if something earlier reaches as far |
| Weighted non-overlapping jobs | DP over end order + binary search, not greedy | best[k] covers the first k jobs |

Sorting by start or end is O(n log n) before the sweep begins. Count the sort, the output, and any heap or event array before you state a complexity.

### Five common bugs

1. **Extending with `next.end` instead of `Math.max(cur.end, next.end)`.** A swallowed booking shrinks the merge: `[1,10],[2,3]`.
2. **Forgetting to emit the last card** after the sweep.
3. **The wrong tie-break in an event sweep.** Check-ins before checkouts at the same time count a phantom extra room.
4. **Sorting by start for the removal greedy.** It is the END sort that makes the keep-if-it-fits rule correct: `[1,100],[2,3],[4,5]`.
5. **`<` versus `<=` on touching ranges** (`[1,2],[2,3]`). Read the problem's definition of overlap; say your assumption out loud.

<h2 id="revision">Revision</h2>

**How to recognise it.** The input is ranges `[start, end]`. The question is about overlap: merge, insert, any clash, peak overlap, fewest removals, common free time. Decide first whether touching counts.

**Core algorithm.** Pick the order that makes the next decision safe (usually sort by start; sort by end for "keep the most"). Sweep once, holding one running thing: an open card, a `lastEnd`, a running count, or a heap of end times. Emit the open thing after the loop.

**Common mistakes.**

- `max` forgotten when extending, last card not emitted.
- Wrong tie-break: checkouts must come before check-ins at equal times.
- Start sort for the keep-most greedy; `<` versus `<=` on touching ranges.
- `a[1] - b[1]` comparator overflow with large values.

**Complexity.** Sort O(n log n) plus a sweep O(n): O(n log n) time, O(n) space for output or events. Sorted input (Insert Interval, Intersections) gives O(n) or O(m + n). Online bookings with a `TreeMap` are O(log n) per request.

**Three representative problems.**

1. [Merge Intervals](https://leetcode.com/problems/merge-intervals/): sort by start, extend or close.
2. [Meeting Rooms II](https://leetcode.com/problems/meeting-rooms-ii/) (premium; [LintCode 919](https://www.lintcode.com/problem/919/)): events with a tie rule, or a min-heap.
3. [Non-overlapping Intervals](https://leetcode.com/problems/non-overlapping-intervals/): sort by end, keep greedily.
