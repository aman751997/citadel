<h2 id="prologue">Prologue · The rope you must never drop</h2>

A **linked list** is a chain of nodes. Each node holds a value and one reference, `next`, to another node, or `null` when the chain ends. You never see the whole chain. You hold references, usually just `head`, and reach everything else by following `next`.

```java fragment
// The LeetCode shape used throughout. One value, one next pointer.
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
    ListNode(int val, ListNode next) { this.val = val; this.next = next; }
}
```

### The one rule: never drop the rope

This lesson calls a `next` pointer **a rope**. A node is only reachable if some variable, or some other node's `next`, still holds it. In Java, a node nothing refers to is garbage-collected.

So **overwriting a `next` pointer is the only dangerous move in this whole lesson.** It can cut off everything that rope used to lead to. Before you touch any `next`, name the variable that already holds what it points to now. If you cannot, save it first.

### Three questions before every move

1. **What is settled?** The reversed prefix, the merged output so far, the nodes the slow pointer has passed.
2. **Why is this move safe?** Which variable still holds the node whose `next` I am about to change?
3. **When do I stop?** At `null`, at a meeting, or when a gap reaches the end.

### How to recognise the pattern

The input is a linked list and the question involves **cycles, middles, ends, reversals, splicing or reordering**. It also fires when an array secretly behaves like a list (values that are valid indexes, as in Find the Duplicate Number) and when you need O(1) lookups *plus* an order (a cache). Arrays index; lists *point*, so every technique here moves pointers cleverly instead of counting.

### The brute force it replaces

Copy every node into an `ArrayList`, index into it, rebuild the list. That costs O(n) extra memory and usually a second pass. The techniques here do the same jobs in **one pass with O(1) extra memory**, and that is what interviewers ask for.

### Two tools used in almost every problem

- **The dummy head.** `ListNode dummy = new ListNode(0, head);` Deleting or inserting before the head stops being a special case: the head becomes an ordinary node that some pointer points at. Return `dummy.next`, never `dummy`. When in doubt, use a dummy.
- **Draw it.** Four boxes and arrows on paper before you code. Pointer bugs are invisible in code and obvious in a picture. One picture, then one line of code per arrow you change.

<h2 id="find-the-middle">Chapter 1 · Middle of the Linked List</h2>

### Problem

Given the head of a singly linked list, return the middle node. If there are two middle nodes, return the second one.

`1 → 2 → 3 → 4 → 5` returns the node 3. `1 → 2 → 3 → 4 → 5 → 6` returns the node 4.

### How to recognise it

- A singly linked list and a question about its **middle** (or a fraction of it).
- You do not know the length, and a second pass is unwelcome.
- You can only move forward.

### Brute force

Walk once to count the length n, then walk again n / 2 steps. Or copy the nodes into an array and index `n / 2`. Both are O(n) time. The two-pass walk is fine; the array costs O(n) space.

### Intuition

Use two pointers that start together. `slow` moves 1 node per turn and `fast` moves 2. **Fast always covers twice the distance of slow**, so when fast has covered the whole list, slow has covered half of it. No counting, no second trip, two variables of memory.

<Figure caption="Where the pointers stand when the loop stops. Five nodes: fast rests on 5 after 4 hops and slow on 3 after 2, the exact middle. Six nodes: fast falls off to null after 6 hops and slow stands on 4 after 3, the second of the two middles.">
  <ArrayStrip name="odd" values={[1, 2, 3, 4, 5, 'null']} join="→" indices={false} pointers={[{ at: 2, label: 'SLOW', tone: 'green' }, { at: 4, label: 'FAST' }]} tones={{ 2: 'done', 5: 'ghost' }} />
  <ArrayStrip name="even" values={[1, 2, 3, 4, 5, 6, 'null']} join="→" indices={false} pointers={[{ at: 3, label: 'SLOW', tone: 'green' }, { at: 6, label: 'FAST' }]} tones={{ 3: 'done', 6: 'ghost' }} />
</Figure>

### Dry run

Odd length first, then even. Turn on Predict mode and guess where fast lands.

<DryRun title="Middle of 1 → 2 → 3 → 4 → 5" frames={middleFrames([1, 2, 3, 4, 5])} predict />

<DryRun title="Middle of 1 → … → 6" frames={middleFrames([1, 2, 3, 4, 5, 6])} />

### Algorithm

1. Start `slow` and `fast` on `head`.
2. While `fast != null` and `fast.next != null`: move `slow` one node, `fast` two nodes.
3. Return `slow`.

### Java solution

Work through the hints first, then reveal the code.

<HintLadder hints={hints.middle}>

```java id=middleNode
public ListNode middleNode(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow; // even length: the SECOND middle
}

public ListNode firstMiddle(ListNode head) {
    if (head == null) return null;
    ListNode slow = head, fast = head.next; // one-node head start
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow; // even length: the FIRST middle
}
```

</HintLadder>

### Why it works

- **Settled:** after t turns, slow has made t hops and fast has made 2t. Every node slow has passed lies in the first half.
- **Why the move is safe:** the guard `fast != null && fast.next != null` proves that `fast.next.next` exists before you read it.
- **When we stop:** on an odd list of 2m + 1 nodes, fast lands on the last node after m turns, so slow is on node m (counting from 0): the centre. On an even list of 2m nodes, fast reaches `null` after m turns and slow is on node m: the second of the two centre nodes.

<Reveal q="What if the problem wants the FIRST of two middle nodes?">

Give fast a one-node head start: `fast = head.next`. On even lists it runs out one turn earlier and slow stops on the first middle (3 in 1 → … → 6). On odd lists nothing changes.

An equivalent spelling keeps both on `head` and tightens the guard to `fast.next != null && fast.next.next != null`. You will meet that guard again in Reorder List, where it marks the end of the first half.

</Reveal>

### Complexity

- **Time O(n):** fast visits about n nodes and slow about n / 2.
- **Space O(1):** two pointers.

### Edge cases and mistakes

- Empty list: the guard fails at once and `slow` is `null`. A single node returns itself.
- The guard's order matters. `while (fast.next != null && fast != null)` reads `fast.next` before checking `fast`, so it throws a NullPointerException as soon as fast falls off an even list. Check `fast != null` first; Java's `&&` stops at the first false.

<h2 id="detect-a-cycle">Chapter 2 · Linked List Cycle</h2>

### Problem

Given `head`, return `true` if some node can be reached again by following `next`. In other words: does the list loop?

`3 → 2 → 0 → −4` where the last `next` points back at the node 2: true. `1 → 2 → null`: false.

### How to recognise it

- "Does it ever end?", "is there a cycle?", "have we seen this state before?"
- You must use O(1) memory, so a visited set is not allowed (or is the follow-up).
- The structure is a list, or something that behaves like one (a function applied again and again).

### Brute force

Keep a `HashSet<ListNode>` of nodes seen. Walk the list; if you reach a node already in the set, there is a cycle; if you reach `null`, there is none. That is O(n) time and **O(n) space**. Say it first in an interview, then offer the two-pointer version.

### Intuition

If the list ends, `fast` reaches `null` first: it is always ahead. If the list loops, fast never reaches `null`; it circles, and eventually slow enters the loop too. From then on, **fast gains exactly one node on slow every turn**, so it cannot jump over slow. It must land on slow's node.

<Figure caption="3 → 2 → 0 → −4, and the last next points back at 2. Slow visits 2, 0, −4; fast visits 0, 2, −4. After three turns both stand on −4: the same node, so there is a loop.">
  <Mermaid code={`flowchart LR
    A(("3")) --> B(("2")) --> C(("0")) --> D(("-4"))
    D -->|"loops back"| B`} />
</Figure>

### Dry run

<DryRun title="A list with a cycle" frames={cycleFrames([3, 2, 0, -4], 1)} predict />

A list with repeated values but no cycle. This is why you compare nodes, not values.

<DryRun title="Equal values, no cycle" frames={cycleFrames([1, 2, 2, 3], null)} />

### Algorithm

1. Start `slow` and `fast` on `head`.
2. While `fast != null` and `fast.next != null`: move `slow` one node and `fast` two nodes.
3. **After moving**, if `slow == fast` (the same node), return `true`.
4. If the loop ends, `fast` found the end: return `false`.

### Java solution

<HintLadder hints={hints.cycle}>

```java id=hasCycle
public boolean hasCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true; // compare NODES (==), never values
    }
    return false; // fast found the end
}
```

</HintLadder>

### Why it works

With no loop, fast hits `null` and you return false. With a loop of length L, look at the moment slow enters it. Measure how many nodes fast is *behind* slow along the loop: some d with 0 ≤ d &lt; L. Each turn slow moves one and fast two, so d drops by exactly 1 (counting round the loop). It cannot skip from 1 to −1, so it reaches 0 within at most L turns: slow never needs more than one lap.

- **Settled:** fast has made twice slow's hops. If fast found `null`, the list has an end.
- **Why the move is safe:** a gap that shrinks by exactly 1 per turn must hit 0.
- **When we stop:** on a meeting (true) or on `null` (false).

<Reveal q="Why compare slow == fast instead of slow.val == fast.val?">

Because two nodes can hold the same value. In `1 → 2 → 2 → 3 → null`, after one turn slow is on the first 2 and fast on the second 2. Equal values, different nodes, and no loop at all. `==` on references asks "is this the same node?", which is the only question that proves anything.

</Reveal>

### Complexity

Slow needs a hops to reach the loop (a = the tail before it), then at most L more turns until fast catches it. a + L is at most n, so the whole race is **O(n) time** with **O(1) extra space**. The `HashSet` version is O(n) time and O(n) space.

### Edge cases and mistakes

- The empty list and a single node are both handled by the guard.
- A single node pointing at itself is a cycle: after one turn both pointers are on it.
- The classic bug is comparing *before* moving. Both pointers start on the head, so this reports a loop on every list:

```java fragment
ListNode slow = head, fast = head;
while (fast != null && fast.next != null) {
    if (slow == fast) return true; // true on the very first check, for every list
    slow = slow.next;
    fast = fast.next.next;
}
```

Move first, then compare.

### Practice

<Trace title="Same node, or same value?" steps={cycle} takeaway="Remember: move first, then compare the nodes themselves. A meeting proves a loop; fast reaching null proves an end." />

<Reveal q="Could fast move 3 nodes per turn instead of 2?">

It can work, but not always. With speed 3 the gap shrinks by 2 per turn, and it can jump from 1 straight past 0. On an even-length loop with an odd gap, they never meet. Speed 2 shrinks the gap by exactly 1, which is why it is the standard.

</Reveal>

<h2 id="nth-from-end">Chapter 3 · Remove Nth Node From End of List</h2>

### Problem

Remove the nth node from the end of the list and return the head. `1 → 2 → 3 → 4 → 5` with n = 2 becomes `1 → 2 → 3 → 5`.

### How to recognise it

- A position counted **from the end** of a singly linked list.
- You cannot walk backwards, and you want one pass.
- A deletion, which means you need the node *before* the target.

### Brute force

Walk once to get the length `len`, then walk again to the node at position `len − n` (the one before the target) and cut. That is two passes, O(n) time, O(1) space. It is a correct first answer.

### Intuition

"The nth from the end" is a distance from `null`. If `lead` is k hops ahead of `trail`, then when lead reaches `null`, trail is k hops from `null`. A fixed gap stands in for counting.

You do not want to stand *on* the target: **a rope is cut from the node before it**. So choose a gap of **n + 1**. Start both on a dummy so deleting the head is not special.

<Figure caption="Remove the 2nd from the end of 1 → 2 → 3 → 4 → 5. Lead opened a gap of n + 1 = 3 hops, then both moved in step. Lead is on null, so trail is on 3, right before the target 4: trail.next = trail.next.next cuts it out.">
  <ArrayStrip values={['D', 1, 2, 3, 4, 5, 'null']} join="→" indices={false} pointers={[{ at: 3, label: 'TRAIL', tone: 'blue' }, { at: 6, label: 'LEAD' }]} tones={{ 0: 'ghost', 4: 'hot', 6: 'ghost' }} regions={[{ from: 3, to: 6, label: 'gap: n + 1 = 3 hops', tone: 'gold' }]} />
</Figure>

### Dry run

<DryRun title="Remove the 2nd from the end" frames={nthFrames([1, 2, 3, 4, 5], 2)} predict />

Removing the head itself: the dummy makes it work with no special case.

<DryRun title="Remove the only node" frames={nthFrames([1], 1)} />

### Algorithm

1. Create `dummy` pointing at `head`; start `lead` and `trail` on `dummy`.
2. Move `lead` forward n + 1 times (the gap).
3. While `lead != null`: move both `lead` and `trail` one node.
4. `trail` now stands just before the target: `trail.next = trail.next.next`.
5. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.nth}>

```java id=removeNthFromEnd
public ListNode removeNthFromEnd(ListNode head, int n) {
    ListNode dummy = new ListNode(0, head);
    ListNode lead = dummy, trail = dummy;
    for (int i = 0; i <= n; i++) lead = lead.next; // open a gap of n + 1
    while (lead != null) {
        lead = lead.next;
        trail = trail.next;
    }
    trail.next = trail.next.next; // trail stands just before the target
    return dummy.next;
}
```

</HintLadder>

### Why it works

Number the dummy 0, the nodes 1 to len, and `null` len + 1. Lead ends at len + 1, so trail ends at len + 1 − (n + 1) = len − n. The nth node from the end is at position len − n + 1: the one right after trail.

- **Settled:** once the gap is open, lead is exactly n + 1 hops ahead of trail.
- **Why the move is safe:** the cut `trail.next = trail.next.next` re-points one rope to the node after the target, so nothing past the target is lost.
- **When we stop:** when lead is `null`.

**Why the dummy:** when n equals the length, the target is the head itself and the node "before" it is the dummy. Trail never leaves it, the cut re-points `dummy.next`, and returning `dummy.next` gives the right answer, possibly the empty list.

<Reveal q="Why not count the length first, then walk to position len − n?">

That is correct, also O(n) time, and a fine first answer. It takes two passes. The gap does the same job in one, which is the follow-up the problem itself asks for. Both use O(1) extra space.

</Reveal>

### Complexity

- **Time O(n):** lead walks the list once; trail follows it.
- **Space O(1):** three pointers. LeetCode guarantees 1 ≤ n ≤ length, so lead never steps past `null` while opening the gap.

### Edge cases and mistakes

- n equals the length (remove the head); a one-node list.
- A gap of n instead of n + 1 lands trail *on* the target. On `1 → 2` with n = 1, trail finishes on 2, the last node, and `trail.next.next` throws a NullPointerException, on every list when n = 1. With a larger n it is quieter and worse: on `1 → 2 → 3 → 4 → 5` with n = 2, trail stands on 4 and the cut removes 5, the node after the target.

<h2 id="find-the-duplicate">Chapter 4 · Find the Duplicate Number</h2>

### Problem

An array `nums` has n + 1 integers, each between 1 and n. Exactly one value is repeated (it may appear more than twice). Return it without modifying the array and using O(1) extra space.

`[1, 3, 4, 2, 2]` returns 2.

### How to recognise it

- Values are valid **indexes** into the same array (range 1..n in n + 1 slots).
- Read-only input and O(1) space. That rules out sorting and hashing.
- A repeated value must exist (pigeonhole). That hints at a structure that is forced to revisit something: a cycle.

The constraints do the recognising. A common failure is freezing because the problem does not look like a list. Ask what shape "value = next index" makes.

### Brute force

Compare every pair: O(n²) time, O(1) space. Or sort a copy (O(n log n), but O(n) space and it copies the input), or use a `HashSet` (O(n) time, O(n) space). The constraints forbid the last two.

### Intuition

Make index i a node whose pointer goes to index `nums[i]`. Every index has exactly one pointer out, and every value 1..n is a real index, so **no pointer leads off the array**. Start at index 0 and keep following pointers: with only n + 1 indexes you must eventually revisit one. The walk ends in a loop.

Two facts make that loop useful. **No value is 0**, so nothing points at index 0: it sits on a tail before the loop. And the loop's **entrance** has two pointers arriving: one from the tail, one from the node before it inside the loop. Two slots holding the same value means two pointers to the same index. That index is the duplicate.

<Figure caption="nums = [1, 3, 4, 2, 2] as pointers: 0 → 1 → 3 → 2 → 4 → 2 → … Index 2 is the loop's entrance, with pointers arriving from 3 (nums[3] = 2) and from 4 (nums[4] = 2). The entrance is the duplicate.">
  <ArrayStrip name="nums" values={[1, 3, 4, 2, 2]} tones={{ 3: 'hot', 4: 'hot' }} />
  <Mermaid code={`flowchart LR
    I0(("0")) --> I1(("1")) --> I3(("3")) --> I2(("2")) --> I4(("4"))

**Phase 1 is Chapter 2's race**: `slow = nums[slow]`, `fast = nums[nums[fast]]`, until they stand on the same index. That meeting is *somewhere* in the loop, not necessarily at the entrance. **Phase 2** sends one pointer back to index 0, and both take one step per turn. They meet exactly at the entrance. The next section shows why.

### Dry run

<DryRun title="Find the duplicate in [1, 3, 4, 2, 2]" frames={duplicateFrames([1, 3, 4, 2, 2])} predict />

### Algorithm

1. Start `slow` and `fast` at index 0.
2. **Phase 1:** repeat `slow = nums[slow]`, `fast = nums[nums[fast]]` until `slow == fast`. Use `do … while`, so they move before they are compared.
3. **Phase 2:** set `slow = 0`. Leave `fast` where it is.
4. Repeat `slow = nums[slow]`, `fast = nums[fast]` (one step each) until `slow == fast`.
5. Return `slow`: the loop's entrance, which is the duplicate.

### Java solution

<HintLadder hints={hints.duplicate}>

```java id=findDuplicate
public int findDuplicate(int[] nums) {
    int slow = 0, fast = 0;
    do {                                  // phase 1: race to a meeting
        slow = nums[slow];
        fast = nums[nums[fast]];
    } while (slow != fast);
    slow = 0;                             // phase 2: restart one pointer
    while (slow != fast) {
        slow = nums[slow];
        fast = nums[fast];
    }
    return slow;                          // the loop's entrance = the duplicate
}
```

</HintLadder>

### Why it works

**The distance argument, one line at a time:**

1. At the meeting, slow has made some number of steps, s, and fast has made **2s**. They stand on the same index, so fast's extra s steps were whole laps: **s is a multiple of L**.
2. Slow's s steps were the a steps of the tail, then b steps past E, plus possibly some whole laps: s = a + b + (whole laps). Since s is a whole number of laps, **so is a + b: a + b = kL** for some whole number k.
3. Rearrange: **a = kL − b = (k − 1)·L + (L − b)**.
4. Read it aloud. A pointer at M that takes a steps goes round (k − 1) whole laps and then L − b more, which is exactly the way from M back to E. A pointer at the start that takes a steps also reaches E. **Same number of steps, same index.**
5. They cannot meet earlier: until step a, the restarted pointer is still on the tail, and no tail index is part of the loop.

Check it on the figure's numbers, `[1, 3, 4, 2, 2]`: the tail 0 → 1 → 3 → 2 gives a = 3; the loop 2 → 4 → 2 gives L = 2; the pointers met on 4 after slow made s = 4 steps, so b = 1. Then a + b = 4 = 2 · L, so k = 2, and (k − 1)·L + (L − b) = 2 + 1 = 3 = a.

<Reveal q="Why must the walk start at index 0, not at index 1 or n?">

Because 0 is the one index nothing points at, so it is guaranteed to be on the tail (a ≥ 1), and the entrance then has two distinct pointers in. Start on an index already inside the loop and a = 0: phase 2 returns your starting index, duplicate or not. On `[1, 3, 4, 2, 2]`, starting at index 4 returns 4, which appears only once.

</Reveal>

### Complexity

- **Time O(n):** phase 1 is at most a + L steps, phase 2 is a steps.
- **Space O(1):** two integers. The array is never modified. The duplicate may appear more than twice; the entrance still has at least two pointers in.

### Edge cases and mistakes

- All values equal, `[2, 2, 2, 2, 2]`: the loop is the single index 2 pointing at itself.
- Restarting phase 2 at `nums[0]` instead of 0. On `[1, 3, 4, 2, 2]` the two pointers then chase each other round the 2–4 loop forever, one step apart.
- Returning the phase 1 meeting point (4 here) instead of running phase 2.

<h2 id="reverse-the-chain">Chapter 5 · Reverse Linked List</h2>

### Problem

Reverse a singly linked list in place and return the new head. `1 → 2 → 3 → 4 → 5` becomes `5 → 4 → 3 → 2 → 1`.

### How to recognise it

- "Reverse", "read from the back", "compare front and back", "last becomes first".
- Singly linked, so you cannot walk backwards, and the follow-up asks for O(1) space.
- It is also a sub-step of Reverse II, k-Group, Reorder List and Palindrome List. This is the fundamental of the lesson.

### Brute force

Push every value on a stack (or copy to an array) and write the values back in reverse order. That is O(n) time and **O(n) extra space**, and it rewrites values rather than re-pointing nodes. A recursive version also costs O(n) stack.

### Intuition

Walk the list once. At each node, re-point its `next` at the node *behind* it. The trouble: the `next` you are about to overwrite is your only way to reach the nodes ahead. So **save the rope before you cut it**.

Keep three pointers. `prev` is the head of the reversed part (starts `null`). `cur` is the node being flipped. `next` is the saved rope to everything not yet flipped.

### Dry run

Every turn is four frames, one per line, so you can see what each assignment does. The three rows show the list as seen from `prev`, from `cur` and from `next`.

### Algorithm

1. `prev = null`, `cur = head`.
2. While `cur != null`, run four lines **in this order**:
   1. `next = cur.next` (save the rope).
   2. `cur.next = prev` (flip the pointer).
   3. `prev = cur` (advance prev).
   4. `cur = next` (advance cur).
3. Return `prev`, not `cur`: cur has walked off the end.

### Java solution

<HintLadder hints={hints.reverse}>

```java id=reverseList
public ListNode reverseList(ListNode head) {
    ListNode prev = null, cur = head;
    while (cur != null) {
        ListNode next = cur.next;   // 1. save the rope before cutting it
        cur.next = prev;            // 2. flip the pointer
        prev = cur;                 // 3. advance prev
        cur = next;                 // 4. advance cur
    }
    return prev;                    // prev is the new head (cur is null!)
}
```

</HintLadder>

### Why it works

**Why this order:** line 1 grabs the other end of the rope, then line 2 cuts it. Line 3 must come before line 4 because `cur` is what lets you reach the node that `prev` is about to hold; move `cur` first and the reversed part loses its only holder.

- **Settled:** at the top of every loop, `prev` is the head of the reversed part (nodes already turned, in reverse order), `cur` is the head of the untouched part, and together they hold every node.
- **Why the move is safe:** `next` holds the untouched part while `cur.next` is overwritten.
- **When we stop:** each turn moves one node from the front of the untouched part to the front of the reversed part. When `cur` is `null` the untouched part is empty and `prev` is the whole reversed list. An empty list needs no special case.

<Reveal q="Can you reverse it recursively? What does that cost?">

Yes. Reverse everything after the head, then hang the head on the end.

```java id=reverseRecursive
public ListNode reverseRecursive(ListNode head) {
    if (head == null || head.next == null) return head;
    ListNode newHead = reverseRecursive(head.next);
    head.next.next = head; // the node after me now points back at me
    head.next = null;      // and I point at nothing, for now
    return newHead;
}
```

The trick line is `head.next.next = head`: after the recursive call, `head.next` is the *last* node of the reversed rest, and you tie it back to `head`. It is still O(n) time, but the call stack holds n frames: **O(n) space**. On a very long list, Java can throw a StackOverflowError. Interviewers often ask for both versions; lead with the loop.

</Reveal>

### Complexity

- **Time O(n):** each node is re-pointed exactly once.
- **Space O(1):** three pointers (the recursive version is O(n) stack).

### Edge cases and mistakes

- Empty list returns `null`; a one-node list returns itself.
- **Flip before save:** the rest of the list is gone.

```java fragment
while (cur != null) {
    cur.next = prev;          // the rope to the rest is gone...
    ListNode next = cur.next; // ...so this "saves" prev instead
    prev = cur;
    cur = next;               // cur walks backwards
}
```

- Returning `cur` returns `null`. Returning `head` returns the old first node, which is now the last: a one-node list.

<h2 id="reverse-a-stretch">Chapter 6 · Reverse Linked List II</h2>

### Problem

Reverse only the nodes from position `left` to position `right` (1-based) and leave the rest alone. `1 → 2 → 3 → 4 → 5` with left = 2, right = 4 becomes `1 → 4 → 3 → 2 → 5`.

### How to recognise it

- "Reverse a sublist" or "between positions".
- The reversed part has **two seams** with the rest of the list. Seams are where the bugs live.
- It is the four-line dance on a window.

### Brute force

Copy the values of positions left..right into an array, reverse the array, and write the values back. O(n) time, O(right − left) space, and it rewrites values rather than moving nodes (not allowed if nodes carry other data). Or reverse the whole list and fix both ends, which is the same seam problem in disguise.

### Intuition

The turning is the easy part (Chapter 5). The hard part is the **seams**: who re-points the pointer coming *into* the stretch, and who re-points the pointer going *out*?

- Put a dummy in front. Walk to `before`, the node just before position `left`.
- Remember `first = before.next`. After the flips it is the stretch's *last* node.
- Run the four-line dance exactly `right − left + 1` times.
- Re-tie both seams: `before.next = prev` (into the new front of the stretch) and `first.next = cur` (out to the node after position `right`).

### Algorithm

1. Create `dummy` pointing at `head`. Walk `before` from `dummy` for `left − 1` steps.
2. `first = before.next`; `prev = null`; `cur = first`.
3. Run the four lines `right − left + 1` times.
4. Seam 1: `before.next = prev`.
5. Seam 2: `first.next = cur`.
6. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.reverseII}>

```java id=reverseBetween
public ListNode reverseBetween(ListNode head, int left, int right) {
    ListNode dummy = new ListNode(0, head);
    ListNode before = dummy;
    for (int i = 1; i < left; i++) before = before.next; // stand at left − 1
    ListNode first = before.next;          // becomes the stretch's last node
    ListNode prev = null, cur = first;
    for (int i = left; i <= right; i++) {  // the four-line dance, right − left + 1 times
        ListNode next = cur.next;
        cur.next = prev;
        prev = cur;
        cur = next;
    }
    before.next = prev;  // seam 1: into the new front of the stretch
    first.next = cur;    // seam 2: out to the node after right
    return dummy.next;
}
```

</HintLadder>

### Why it works

- **Settled:** during the flips, `before` still points at `first`, the flipped part is held by `prev`, and everything after the stretch is held by `cur`. Nothing is lost; it is only disconnected until the seams are re-tied.
- **Why the move is safe:** after exactly right − left + 1 flips, `prev` is the node at position `right` and `cur` is the node after it (possibly `null`), which are exactly the two nodes the seams need.
- **When we stop:** after the counted flips, not when `cur` is null (the stretch may end mid-list).

<Reveal q="Why does first end up as the stretch's last node, and what does it point at before seam 2?">

The dance turns the stretch around, so its old front ends up at the back. On the first flip, `prev` was `null`, so `first.next` was set to `null`. Until seam 2 re-points it to `cur`, the stretch ends in `null` and the rest of the list is held only by `cur`.

</Reveal>

### Complexity

- **Time O(n):** one walk to `left`, one pass over the stretch.
- **Space O(1).** Positions are 1-based, with 1 ≤ left ≤ right ≤ n.

### Edge cases and mistakes

- `left = 1`: `before` stays on the dummy, and the new head is `dummy.next`. `left == right`: one flip, nothing changes.
- **Seam amnesia.** Forget `first.next = cur` and you get `1 → 4 → 3 → 2 → null`: node 5 is dropped.
- Return `head` instead of `dummy.next` when `left = 1` and you return the old first node, now in the middle.

<h2 id="reverse-in-groups">Chapter 7 · Reverse Nodes in k-Group</h2>

### Problem

Reverse the list k nodes at a time. If fewer than k nodes remain at the end, leave them as they are. `1 → 2 → 3 → 4 → 5` with k = 2 becomes `2 → 1 → 4 → 3 → 5`. (Hard.)

### How to recognise it

- "Every k nodes", "in blocks", "groups".
- A short tail that must **not** be reversed.
- Reverse II, repeated.

### Brute force

Copy values into an array, reverse each complete block of k, write them back: O(n) time, O(n) space, and it rewrites values. The pointer version does the same thing in O(1) space.

### Intuition

This is Chapter 6 over and over. The new discipline: **count before you cut**, and **know where to stand for the next group**.

Keep `before`, the node in front of the next group; it starts on a dummy. Repeat:

1. Send a `probe` k nodes ahead of `before`. If it falls off the list first, fewer than k remain: stop.
2. Otherwise reverse the group as in Chapter 6 (`first = before.next`, `after = probe.next`, flip until `cur == after`) and re-tie both seams.
3. **Move `before` to `first`**: the group's old front is now its last node, right in front of the next group.

  <ArrayStrip name="after" values={[2, 1, 4, 3, 5, 'null']} join="→" indices={false} tones={{ 0: 'done', 1: 'done', 2: 'done', 3: 'done', 5: 'ghost' }} regions={[{ from: 0, to: 1, label: 'flipped', tone: 'green' }, { from: 2, to: 3, label: 'flipped', tone: 'green' }, { from: 4, to: 4, label: 'as is', tone: 'dim' }]} />
</Figure>

### Dry run

<DryRun title="Reverse in groups of 2" frames={kGroupFrames([1, 2, 3, 4, 5], 2)} predict />

### Algorithm

1. `dummy` before `head`; `before = dummy`.
2. Loop: set `probe = before` and move it k times. If it becomes `null`, break.
3. `first = before.next`, `after = probe.next`.
4. Flip with the four lines until `cur == after`.
5. `before.next = prev` (seam 1) and `first.next = after` (seam 2).
6. `before = first`. Go to step 2.
7. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.kGroup}>

```java id=reverseKGroup
public ListNode reverseKGroup(ListNode head, int k) {
    ListNode dummy = new ListNode(0, head);
    ListNode before = dummy;
    while (true) {
        ListNode probe = before;
        for (int i = 0; i < k && probe != null; i++) probe = probe.next;
        if (probe == null) break;              // fewer than k remain: leave them
        ListNode first = before.next, after = probe.next;
        ListNode prev = null, cur = first;
        while (cur != after) {                 // the four-line dance on this group
            ListNode next = cur.next;
            cur.next = prev;
            prev = cur;
            cur = next;
        }
        before.next = prev;   // seam 1 (prev is the old probe)
        first.next = after;   // seam 2
        before = first;       // stand in front of the next group
    }
    return dummy.next;
}
```

</HintLadder>

### Why it works

- **Settled:** everything up to and including `before` is finished (groups reversed and correctly linked), and `before.next` is the first node not yet processed.
- **Why the move is safe:** the probe proves a full group exists before any pointer changes, so a short tail is never touched.
- **When we stop:** when the probe hits `null`: fewer than k nodes remain.

<Reveal q="Recursion or iteration?">

A recursive version reverses the first group and ties its old front to `reverseKGroup(after, k)`. It reads nicely, but it holds one stack frame per group: O(n / k) space. The loop above is O(1). Either is accepted on LeetCode; know which one you wrote and say its space cost.

</Reveal>

### Complexity

- **Time O(n):** every node is probed once and flipped at most once.
- **Space O(1).** With k = 1 every group is a single node and nothing changes.

### Edge cases and mistakes

- k = 1, k equal to the length, k larger than the length (nothing changes), an empty list.
- Setting `before = prev` (the group's *new* front) instead of `first`. The next probe then counts from the wrong node, and the old first node is dragged into every later group: on `1 → 2 → 3 → 4` with k = 2 you get `2 → 3 → 4 → 1` instead of `2 → 1 → 4 → 3`.
- Flipping before counting reverses the short tail.

<h2 id="merge-two">Chapter 8 · Merge Two Sorted Lists</h2>

### Problem

Merge two sorted linked lists into one sorted list made of the existing nodes (no new nodes). `1 → 2 → 4` and `1 → 3 → 4` give `1 → 1 → 2 → 3 → 4 → 4`.

### How to recognise it

- Two sorted sequences and one sorted output.
- "Splice", "re-use the nodes", O(1) extra space.
- It is also the merge step of Sort List and the k = 2 case of Merge k Sorted Lists.

### Brute force

Copy all values into an array, sort it, and build a new list: O((m + n) log(m + n)) time and O(m + n) space. It ignores that both inputs are already sorted.

### Intuition

Only the two **front** nodes can be the next smallest, so compare just those. Build the output with a `dummy` and a `tail` that always stands on the last node of the output. Each turn **splice the smaller front node after `tail`**, advance that list, and advance `tail`. When one list runs out, **attach the other in one re-tie**: it is already linked and already sorted, so no leftover loop is needed.

  <ArrayStrip name="merged" values={['D', 1, 1, 2, 3, 4, 4, 'null']} join="→" indices={false} pointers={[{ at: 6, label: 'TAIL', tone: 'green' }]} tones={{ 0: 'ghost', 2: 'blue', 4: 'blue', 6: 'blue', 7: 'ghost' }} />

### Dry run

<DryRun title="Merge 1 → 2 → 4 and 1 → 3 → 4" frames={mergeListsFrames([1, 2, 4], [1, 3, 4])} predict />

### Algorithm

1. `dummy = new ListNode(0)`; `tail = dummy`.
2. While both lists are non-empty: if `list1.val <= list2.val`, `tail.next = list1` and advance `list1`; otherwise do the same with `list2`. Then `tail = tail.next`.
3. `tail.next = list1 != null ? list1 : list2`.
4. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.merge}>

```java id=mergeTwoLists
public ListNode mergeTwoLists(ListNode list1, ListNode list2) {
    ListNode dummy = new ListNode(0), tail = dummy;
    while (list1 != null && list2 != null) {
        if (list1.val <= list2.val) { tail.next = list1; list1 = list1.next; }
        else { tail.next = list2; list2 = list2.next; }
        tail = tail.next;
    }
    tail.next = (list1 != null) ? list1 : list2; // the leftover is already linked
    return dummy.next;
}
```

</HintLadder>

### Why it works

- **Settled:** `dummy.next … tail` is sorted and contains exactly the nodes taken so far.
- **Why the move is safe:** every node still waiting in either list is at least `tail.val`, because both lists are sorted and we always took the smaller front. Re-pointing `tail.next` loses nothing: the taken node is still held by its list pointer until that pointer advances.
- **When we stop:** when one list is empty; the other is already sorted and linked, so one assignment finishes.

<Reveal q="Why <= rather than <?">

Both produce a sorted result. With `<=`, a tie takes list1's node first, so equal values keep their original relative order: the merge is **stable**. That matters when nodes carry more than a value, and it is what makes merge sort stable (see Sort List).

</Reveal>

### Complexity

- **Time O(m + n):** every node is re-pointed once; none is created.
- **Space O(1).** Either list may be empty.

### Edge cases and mistakes

- Both empty returns `null`; one empty returns the other.
- Forgetting `tail = tail.next`. Tail stays on the dummy, every splice overwrites `dummy.next`, and the final re-tie leaves only the leftover: merging `1 → 2 → 4` with `1 → 3 → 4` returns just `4`.
- Returning `dummy` instead of `dummy.next` puts a fake 0 at the front.

<h2 id="reorder">Chapter 9 · Reorder List</h2>

### Problem

Reorder `L0 → L1 → … → Ln` into `L0 → Ln → L1 → Ln−1 → L2 → …`, in place, without changing node values. `1 → 2 → 3 → 4 → 5 → 6` becomes `1 → 6 → 2 → 5 → 3 → 4`.

### How to recognise it

- The target order alternates between the front and the back.
- You cannot walk backwards, and you cannot see the last node from the first.
- It is a composite: the answer is three earlier moves chained.

### Brute force

Copy the nodes into an `ArrayList`, then re-link with two indexes from both ends. O(n) time, O(n) space. It is correct, so say it first, then offer the O(1)-space version.

### Intuition

You need the back half readable forwards. So: **find the middle** (Chapter 1) → **reverse the second half** (Chapter 5) → **weave** the two halves together, one node from each. If you can narrate this cold, you own the pattern.

<Figure caption="Reorder 1 → … → 6. Slow stops on 3, the end of the first half. Cut there and reverse the second half into 6 → 5 → 4. Weave one from each: 1 → 6 → 2 → 5 → 3 → 4.">
  <ArrayStrip name="first half" values={[1, 2, 3, 'null']} join="→" indices={false} pointers={[{ at: 2, label: 'SLOW', tone: 'green' }]} tones={{ 3: 'ghost' }} />
  <ArrayStrip name="second, reversed" values={[6, 5, 4, 'null']} join="→" indices={false} tones={{ 0: 'blue', 1: 'blue', 2: 'blue', 3: 'ghost' }} />
  <ArrayStrip name="woven" values={[1, 6, 2, 5, 3, 4, 'null']} join="→" indices={false} tones={{ 1: 'blue', 3: 'blue', 5: 'blue', 6: 'ghost' }} />
</Figure>

### Dry run

The weave is where ropes get dropped: look at the two frames per pair. First both ropes are saved (`n1`, `n2`), then they are re-tied.

<DryRun title="Reorder 1 → 2 → 3 → 4 → 5" frames={reorderFrames([1, 2, 3, 4, 5])} predict />

### Algorithm

1. If the list has 0 or 1 nodes, return.
2. `slow = fast = head`; while `fast.next != null && fast.next.next != null`, move `slow` one node and `fast` two.
3. `second = slow.next`; **cut** with `slow.next = null`.
4. Reverse `second` with the four lines.
5. Weave: while `second != null`, save `n1 = first.next` and `n2 = second.next`, then `first.next = second`, `second.next = n1`, `first = n1`, `second = n2`.

### Java solution

<HintLadder hints={hints.reorder}>

```java id=reorderList
public void reorderList(ListNode head) {
    if (head == null || head.next == null) return;
    // 1. find the end of the first half
    ListNode slow = head, fast = head;
    while (fast.next != null && fast.next.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    // 2. cut, then reverse the second half
    ListNode second = slow.next, prev = null;
    slow.next = null;
    while (second != null) {
        ListNode next = second.next;
        second.next = prev;
        prev = second;
        second = next;
    }
    // 3. weave: save both ropes, then re-tie
    ListNode first = head;
    second = prev;
    while (second != null) {
        ListNode n1 = first.next, n2 = second.next;
        first.next = second;
        second.next = n1;
        first = n1;
        second = n2;
    }
}
```

The method returns nothing; it re-ties the list in place.

</HintLadder>

### Why it works

With the guard `fast.next != null && fast.next.next != null`, slow stops on the last node of the first half, which has ⌈n / 2⌉ nodes; the second half has ⌊n / 2⌋. After reversing, the second half's front is the original last node.

- **Settled:** the weave alternates one node from each half; everything already woven is final.
- **Why the move is safe:** both ropes (`n1`, `n2`) are saved before either is overwritten.
- **When we stop:** when the second half runs out. With odd n the first half is longer by one: its last node is the true middle, which should come last, and after the cut it already points at `null`.

<Reveal q="Would Chapter 1's guard (fast != null && fast.next != null) work here too?">

Surprisingly, yes. On even lengths slow then stops on the second middle, so the first half keeps two more nodes than the second. Those two nodes are consecutive in the answer anyway (try 1 → 2 → 3 → 4: either guard gives 1 → 4 → 2 → 3). This lesson uses the balanced guard because it is the habit that keeps working when the halves really must be balanced, as in Sort List.

</Reveal>

### Complexity

- **Time O(n):** three linear passes.
- **Space O(1):** pointers only.

### Edge cases and mistakes

- 0, 1 and 2 nodes; odd and even lengths.
- Forgetting the cut, `slow.next = null`. The first half still points into the second, and the weave ties a node to itself: on `1 → 2 → 3 → 4`, node 3 ends up pointing at 3, a one-node loop that hangs whoever prints the list.
- Re-tying `first.next = second` before saving `n1`: the rest of the first half is dropped.

<h2 id="copy-random">Chapter 10 · Copy List with Random Pointer</h2>

### Problem

Each node has a `next` and a `random` pointer (to any node in the list, or `null`). Build a deep copy: new nodes, with every pointer, `next` and `random`, leading only to new nodes.

### How to recognise it

- A structure with a second pointer that can lead anywhere, including *forward* to a node you have not copied yet.
- "Deep copy", "clone". It is Clone Graph on a list.

### Brute force

Create the clones in order, tying `next` as you go. But a `random` can point forward to a clone that does not exist yet. The brute-force fix is to find each target by walking from the head for every node: O(n²) time. The standard fix is a map.

### Intuition

Two answers, and you should be able to give both.

- **The map.** Map each original node to its clone. Pass 1 creates every clone, so every target exists. Pass 2 wires both pointers through the map. O(n) extra space; say it first.
- **The weave.** Put each clone right after its original (`A → A′ → B → B′`), so the clone of any node X is simply `X.next`. Then `clone.random = orig.random.next`, then unweave. O(1) extra space beyond the clones themselves.

<Figure caption="Woven. Every clone sits right after its original, so the clone of X is X.next. A's random points at C, so A′'s must point at C.next, which is C′, never at C itself.">
  <Mermaid code={`flowchart LR
    A["A"] --> A2["A′"] --> B["B"] --> B2["B′"] --> C["C"] --> C2["C′"]
    A -.->|"random"| C
    A2 -.->|"random = A.random.next"| C2`} />
</Figure>

### Dry run

This dry run is the weave. Three passes: insert the clones, set their `random` pointers, unweave. The last frame also checks that the original list is restored.

<DryRun title="Copy a list: A.random = C, B.random = A" frames={copyRandomFrames([2, 0, null])} predict />

### Algorithm

The map version:

1. Pass 1: for every original node, `clone.put(node, new Node(node.val))`.
2. Pass 2: for every node, `clone.get(node).next = clone.get(node.next)` and `clone.get(node).random = clone.get(node.random)`.
3. Return `clone.get(head)`.

The weave version:

1. For every original `cur`, insert `copy` after it.
2. For every original `cur`, if `cur.random != null` set `cur.next.random = cur.random.next`.
3. Unweave: re-point every original to the original after it and every clone to the clone after it. Return the first clone.

### Java solution

On LeetCode the `Node` class (with `val`, `next`, `random`) is given to you. It is written out here as a nested class so the code is complete and tested.

<HintLadder hints={hints.copyRandom}>

```java group=copy
static class Node {
    int val;
    Node next, random;
    Node(int val) { this.val = val; }
}

// Answer 1 — the map. O(n) time, O(n) extra space.
public Node copyRandomList(Node head) {
    Map<Node, Node> clone = new HashMap<>();
    for (Node cur = head; cur != null; cur = cur.next) clone.put(cur, new Node(cur.val));
    for (Node cur = head; cur != null; cur = cur.next) {
        clone.get(cur).next = clone.get(cur.next);     // get(null) is null
        clone.get(cur).random = clone.get(cur.random);
    }
    return clone.get(head);
}
```

```java group=copy
// Answer 2 — the weave. O(n) time, O(1) extra space beyond the clones.
public Node copyRandomListWoven(Node head) {
    if (head == null) return null;
    for (Node cur = head; cur != null; cur = cur.next.next) {   // 1. weave A → A' → B → B'
        Node copy = new Node(cur.val);
        copy.next = cur.next;
        cur.next = copy;
    }
    for (Node cur = head; cur != null; cur = cur.next.next)     // 2. clone of X is X.next
        if (cur.random != null) cur.next.random = cur.random.next;
    Node copyHead = head.next;
    for (Node cur = head; cur != null; cur = cur.next) {        // 3. unweave, restoring the original
        Node copy = cur.next;
        cur.next = copy.next;
        copy.next = (copy.next != null) ? copy.next.next : null;
    }
    return copyHead;
}
```

</HintLadder>

### Why it works

**The map:** pass 1 creates a clone for every original, so every target exists before any pointer is wired. Pass 2 wires both pointers through the map. `map.get(null)` is `null`, which handles the list's end and missing random pointers for free. The map compares nodes by identity (`Node` does not override `equals`), so two nodes with the same value stay separate.

**The weave:** while woven, the list itself *is* the map: clone(X) = X.next. Unweaving re-points every original to the original after it and every clone to the clone after it, restoring the input exactly.

- **Settled:** a clone's pointers may only land on clones.
- **When we stop:** after each pass reaches the end.

<Reveal q="Why must the weave restore the original list?">

Because the caller still owns it. A deep copy that leaves the original tangled with clones is a broken original. LeetCode checks the input list too, and an interviewer will ask. Step 3 restores every original `next` as it peels the clones off.

</Reveal>

### Complexity

Both are **O(n) time**. The map costs O(n) extra space; the weave costs O(1) beyond the n clones the answer needs anyway.

### Edge cases and mistakes

- Empty list; a node whose `random` is itself; a `random` pointing forward.
- `copy.random = orig.random`: a shallow copy whose random pointers lead home into the old chain. Its values print correctly, but LeetCode's checker rejects it, and any later change to the original leaks into the copy.
- In the weave, reading `cur.next.next` after the unweave has started, or skipping the restore.

<h2 id="lru-cache">Chapter 11 · LRU Cache</h2>

### Problem

Design a cache with a fixed capacity. `get(key)` returns the value or −1. `put(key, value)` inserts or updates. When full, inserting evicts the **least recently used** key. Both operations must run in O(1).

### How to recognise it

- "O(1) lookup **and** know which entry is oldest."
- "Evict the least recently used." Recency order plus fast access by key.
- It is a small system design, not a trick.

### Brute force

Keep a list ordered by recency and scan it on every call: O(n) per `get` and `put`. Or keep a map of key → last-used timestamp and scan for the smallest timestamp on eviction: O(n) per eviction. Neither meets O(1).

### Intuition

You need two things at once: find any entry by key instantly, and know instantly which one has waited longest. No single structure does both, so combine two.

- A **HashMap** gives O(1) lookup from key to node.
- A **doubly linked list** keeps the nodes in recency order: most recent at the front, least recent at the back.

`get` moves a node to the front. `put` either updates and moves it, or adds a new node at the front and, if over capacity, evicts the back. **Every operation updates the map and the list together.**

<Figure caption="Two sentinels, head and tail, mean every real node always has two real neighbours, so unlinking never needs a null check. The map points straight at nodes. Eviction removes tail.prev, from the list and, using the key stored in the node, from the map.">
  <Mermaid code={`flowchart LR
    H["head sentinel"] <--> N3["key 3 · most recent"] <--> N1["key 1"] <--> T["tail sentinel"]
    M[("HashMap: key → node")] -.-> N3
    M -.-> N1`} />
</Figure>

### Dry run

This is LeetCode's example with capacity 2. Watch the list and the map change together.

<DryRun title="LRU cache, capacity 2" frames={lruFrames(2, [['put', 1, 1], ['put', 2, 2], ['get', 1], ['put', 3, 3], ['get', 2], ['put', 4, 4], ['get', 1], ['get', 3], ['get', 4]])} predict />

### Algorithm

1. Keep `map: key → node` and a doubly linked list between `head` and `tail` sentinels.
2. `get(key)`: if absent return −1. Otherwise unlink the node, add it after `head`, return its value.
3. `put(key, value)`: if present, update the value, unlink and add it at the front.
4. Otherwise, if the map is at capacity, take `oldest = tail.prev`, unlink it and `map.remove(oldest.key)`.
5. Create the node, put it in the map, add it at the front.

### Java solution

<HintLadder hints={hints.lru}>

```java id=lru
class LRUCache {
    private class Node {
        int key, val;
        Node prev, next;
        Node(int key, int val) { this.key = key; this.val = val; }
    }
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0); // sentinels

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        unlink(node);
        addFront(node);          // used: now the most recent
        return node.val;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {      // update: never evicts
            node.val = value;
            unlink(node);
            addFront(node);
            return;
        }
        if (map.size() == capacity) {
            Node oldest = tail.prev;
            unlink(oldest);
            map.remove(oldest.key);  // why each node stores its key
        }
        node = new Node(key, value);
        map.put(key, node);
        addFront(node);
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addFront(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }
}
```

</HintLadder>

### Why it works

- **Settled:** the list order is exactly the recency order, and the map holds exactly the nodes in the list.
- **Why the move is safe:** `unlink` re-points two ropes that are both held by `node`; `addFront` re-points four, and the order shown (set the new node's two pointers first) never drops a neighbour. The sentinels remove every null check.
- **When we stop:** each operation is a fixed number of pointer changes plus one map operation.

<Reveal q="Why a doubly linked list, not a singly linked one?">

`get` must move an arbitrary node from the middle to the front in O(1). Unlinking a node means re-pointing its **predecessor's** `next`, and only a `prev` pointer gives you the predecessor instantly. With a singly linked list you would walk from the head to find it: O(n), and the whole contract breaks. This "why doubly" follow-up is asked nearly every time.

</Reveal>

<Reveal q="Doesn't Java already have this?">

It does. A `LinkedHashMap` built with `accessOrder = true` keeps entries in access order, and overriding `removeEldestEntry` turns it into an LRU cache. Mention it, then build the manual version anyway, because that is the actual test.

```java id=lruLinked
class LRUCache extends LinkedHashMap<Integer, Integer> {
    private final int capacity;
    LRUCache(int capacity) {
        super(16, 0.75f, true);              // true = order by access, not insertion
        this.capacity = capacity;
    }
    public int get(int key) { return getOrDefault(key, -1); }   // a hit counts as access
    public void put(int key, int value) { super.put(key, value); }
    @Override protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        return size() > capacity;            // evict after inserting past capacity
    }
}
```

</Reveal>

### Complexity

- **Time O(1)** per `get` and `put` (expected, for the hash map).
- **Space O(capacity).** LeetCode guarantees capacity ≥ 1.

### Edge cases and mistakes

- Capacity 1; `put` on an existing key (update, no eviction); `get` of a missing key.
- Map updated and list not, or the other way round. The two structures drift, and a later `get` finds a node that was evicted, or eviction removes a key that is still in the list. Every operation touches both.
- The quietest version: forgetting `map.remove(oldest.key)`, so the map grows forever and `get` returns evicted values.

LRU Cache deserves its own practice session.

<h2 id="cycle-entrance">Variation 1 · Linked List Cycle II</h2>

### Problem

Do not just say there is a loop. Return the node where it begins, or `null` if there is none. `3 → 2 → 0 → −4` with the last `next` pointing back at the node 2 returns the node 2.

### How to recognise it

- "Where does the cycle start?" after you already know how to detect one.
- Constant memory, so no visited set.

### Brute force

Walk the list, store every node in a `HashSet`, and return the first node you meet twice. O(n) time, O(n) space.

### Intuition

This is Chapter 4's phase 2 on a real list. Race the pointers (Chapter 2). If fast finds `null`, there is no loop. If they meet, start a new walker at the head and step it and slow one node at a time. By the distance argument (a = (k − 1)·L + (L − b)) they meet exactly at the entrance.

### Dry run

<DryRun title="Find where the loop starts" frames={cycleEntranceFrames([3, 2, 0, -4], 1)} predict />

### Algorithm

1. Race `slow` and `fast` from the head; return `null` if `fast` finds the end.
2. On a meeting, put `walker` on `head`.
3. Step `walker` and `slow` one node at a time until they are equal.
4. Return `walker`.

### Java solution

<HintLadder hints={hints.cycleEntrance}>

```java id=detectCycle
public ListNode detectCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {                 // phase 1 done: we are in the loop
            ListNode walker = head;
            while (walker != slow) {        // phase 2: equal steps
                walker = walker.next;
                slow = slow.next;
            }
            return walker;                  // the entrance
        }
    }
    return null;                            // fast found the end: no loop
}
```

</HintLadder>

### Why it works

Same argument as Chapter 4: at the meeting a + b is a whole number of laps, so a pointer starting at the head and one starting at the meeting point reach the entrance after the same number of steps.

<Reveal q="What if the last node loops all the way back to the head?">

Then the tail is empty: a = 0. The pointers start on the entrance but must move before comparing, so slow makes exactly one lap and they meet back on the head (b = 0). Phase 2's walker starts on the head, already equal to slow, so the loop body never runs and the head is returned. Correct, with no special case.

</Reveal>

### Complexity

**O(n) time, O(1) extra space.**

### Edge cases and mistakes

- No cycle, a one-node self-loop, a loop through the head (above).
- Returning the phase 1 meeting node instead of running phase 2.

### Practice

<h2 id="palindrome-list">Variation 2 · Palindrome Linked List</h2>

### Problem

Does the list read the same forwards and backwards? Use O(1) extra memory: no copying values into an array. `1 → 2 → 2 → 1` is a palindrome; `1 → 2` is not.

### How to recognise it

- A property of "front vs back" on a singly linked list.
- The follow-up forbids the array copy.

### Brute force

Copy the values into an array and compare from both ends: O(n) time, O(n) space. Or recurse with a front pointer: also O(n) stack.

### Intuition

You cannot walk backwards, so make the back half walk forwards. Find the middle (Chapter 1), reverse the second half (Chapter 5), then walk both halves together comparing values. Then **reverse it back**: the caller's list should look the way they gave it to you.

### Dry run

<DryRun title="Is 1 → 2 → 3 → 2 → 1 a palindrome?" frames={palindromeFrames([1, 2, 3, 2, 1])} predict />

### Algorithm

1. Find the middle with slow and fast (Chapter 1's guard).
2. Reverse the list starting at `slow`.
3. Walk `l` from `head` and `r` from the reversed half; compare values until `r` is `null`.
4. Reverse the back half again to restore the list.
5. Return the verdict.

### Java solution

<HintLadder hints={hints.palindrome}>

```java id=isPalindrome
public boolean isPalindrome(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    ListNode tail = reverse(slow);               // the back half, readable forwards
    boolean same = true;
    for (ListNode l = head, r = tail; r != null; l = l.next, r = r.next) {
        if (l.val != r.val) { same = false; break; }
    }
    reverse(tail);                               // put the nodes back as you found them
    return same;
}

private ListNode reverse(ListNode cur) {
    ListNode prev = null;
    while (cur != null) {
        ListNode next = cur.next;
        cur.next = prev;
        prev = cur;
        cur = next;
    }
    return prev;
}
```

</HintLadder>

### Why it works

The restore works because the node before the middle never stopped pointing at the middle.

<Reveal q="With an odd length, the middle node ends up in both halves. Is that a problem?">

No. With Chapter 1's guard, slow stops on the true middle and the reversed half starts there. The node before the middle still points at it, so the front walker also reaches it and compares the middle with itself. The comparison stops when the reversed half runs out.

</Reveal>

### Complexity

**O(n) time, O(1) extra space.**

### Edge cases and mistakes

- Empty or one node (a palindrome); two equal nodes; odd and even lengths.
- Forgetting to restore the list when the caller still needs it, or returning early on a mismatch *before* restoring.

### Practice

**Transfer test:** a recursive solution can compare front and back without reversing anything. What does it cost, and which constraint does it break? (O(n) stack space: it breaks the O(1) memory rule.)

<h2 id="intersection">Variation 3 · Intersection of Two Linked Lists</h2>

### Problem

Two lists may merge into one shared tail. Return the first node they share, or `null`. O(m + n) time, O(1) space. Compare nodes, not values.

### How to recognise it

- Two lists, "where do they join", "common node".
- The lists have different lengths before the join.

### Brute force

For every node in A, scan all of B: O(m · n) time. Or put A's nodes in a `HashSet` and look up B's: O(m + n) time, O(m) space.

### Intuition

Call the first list's own part a, the second's own part b, and the shared tail c. Walking side by side from the two heads, the walkers reach the join at different times whenever a ≠ b. So **let each walker, when it runs off its list, restart on the other list's head**. Walker A covers a + c, then b. Walker B covers b + c, then a. **a + c + b = b + c + a**: they step onto the join on the same turn. With no shared tail, both reach `null` on the same turn instead, and the loop ends with `null`.

<Figure caption="A: 4 → 1 → [8 → 4 → 5]. B: 5 → 6 → 1 → [8 → 4 → 5]. The purple nodes are the same nodes. The two 1s are different nodes with equal values, so the answer is the 8, not the 1. Here a = 2, b = 3, c = 3: both walkers pass 2 + 3 + 3 = 8 nodes, then step onto the 8 together.">
  <ArrayStrip name="A" values={[4, 1, 8, 4, 5, 'null']} join="→" indices={false} tones={{ 2: 'purple', 3: 'purple', 4: 'purple', 5: 'ghost' }} />
  <ArrayStrip name="B" values={[5, 6, 1, 8, 4, 5, 'null']} join="→" indices={false} tones={{ 3: 'purple', 4: 'purple', 5: 'purple', 6: 'ghost' }} />
</Figure>

### Dry run

The shared nodes are highlighted. Note that `a` and `b` both appear on the shared tail in each row, because it is the same memory.

<DryRun title="Walkers swap lists" frames={intersectionFrames([4, 1], [5, 6, 1], [8, 4, 5])} predict />

### Algorithm

1. `a = headA`, `b = headB`.
2. While `a != b`: `a = (a == null) ? headB : a.next`; `b = (b == null) ? headA : b.next`.
3. Return `a`.

### Java solution

<HintLadder hints={hints.intersection}>

```java id=getIntersectionNode
public ListNode getIntersectionNode(ListNode headA, ListNode headB) {
    ListNode a = headA, b = headB;
    while (a != b) {
        a = (a == null) ? headB : a.next;   // ran off A? continue on B
        b = (b == null) ? headA : b.next;   // ran off B? continue on A
    }
    return a;                               // the shared node, or null
}
```

</HintLadder>

### Why it works

Each walker visits at most a + c + b nodes, plus one `null` step when it switches. If the lists share no tail (c = 0), walker A is on `null` after a + b + 1 steps (a, then null, then b) and so is walker B (b, null, a). `null == null`, the loop ends, and the method returns `null`. If a = b, they meet on their first pass, at the join or at `null`.

<Reveal q="Why does the loop always end, even when the lists never meet?">

Because after both walkers have switched once, they have walked the same total distance, a + b (+ c if shared). Either they are on the same shared node, or both are on `null`, and `null == null` ends the loop.

</Reveal>

### Complexity

**O(m + n) time, O(1) extra space.** The equivalent "measure both lengths, advance the longer one by the difference" also works; this version needs no arithmetic.

### Edge cases and mistakes

- No intersection; one list empty; the lists share everything (a = b = 0).
- Comparing values, which can stop one node early. Build two lists whose values make a value comparison stop on the first 1 above.

### Practice

**Transfer test:** why must the comparison be `a != b` on nodes? (Equal values do not mean the same node.)

<h2 id="add-two-numbers">Variation 4 · Add Two Numbers</h2>

### Problem

Each list is a non-negative number, one digit per node, **least significant digit first**. Return their sum in the same form. `2 → 4 → 3` plus `5 → 6 → 4` is 342 + 465 = 807, so return `7 → 0 → 8`.

### How to recognise it

- Numbers too long for `int` or `long` (up to 100 digits), stored digit by digit.
- Least significant first: exactly the order you add by hand.

### Brute force

Convert each list to a number, add, convert back. It overflows `int`/`long` on long inputs. (`BigInteger` works but is not the point.)

### Intuition

Add column by column, like on paper. Chapter 8's tools build the answer: a dummy and a tail, plus a **carry** that survives between columns. Keep going **while either list or the carry remains**.

### Dry run

<DryRun title="342 + 465" frames={addTwoFrames([2, 4, 3], [5, 6, 4])} />

A carry that outlives both lists needs its own node.

<DryRun title="5 + 5" frames={addTwoFrames([5], [5])} predict />

### Algorithm

1. `dummy`, `tail`, `carry = 0`.
2. While `l1 != null || l2 != null || carry != 0`: `sum = carry`, add each non-null digit and advance.
3. Append a node with `sum % 10`; `carry = sum / 10`.
4. Return `dummy.next`.

### Java solution

<HintLadder hints={hints.addTwo}>

```java id=addTwoNumbers
public ListNode addTwoNumbers(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0), tail = dummy;
    int carry = 0;
    while (l1 != null || l2 != null || carry != 0) {
        int sum = carry;
        if (l1 != null) { sum += l1.val; l1 = l1.next; }
        if (l2 != null) { sum += l2.val; l2 = l2.next; }
        tail.next = new ListNode(sum % 10);
        tail = tail.next;
        carry = sum / 10;
    }
    return dummy.next;
}
```

</HintLadder>

### Why it works

The invariant is the carry: after each column, `carry` is exactly what the higher columns still owe. The loop stops only when both lists are used up and nothing is owed.

<Reveal q="Why does the loop condition include carry != 0?">

Because the sum can be one digit longer than both inputs. `5` plus `5` is 10: after the only column, both lists are used up but the carry is 1, and it needs its own node. Stop on the lists alone and you return `0` instead of `0 → 1`.

</Reveal>

### Complexity

**O(max(m, n)) time**, and the output has at most max(m, n) + 1 nodes. Never convert to `int` or `long`: the lists can be 100 digits long.

### Edge cases and mistakes

- Different lengths; a final carry; both lists `0`.
- Dropping the `carry != 0` condition, or forgetting to advance only the non-null list.

### Practice

**Transfer test:** Add Two Numbers II stores the **most** significant digit first. Which chapter turns it back into this problem, and what does that cost the inputs? (Reverse both lists, Chapter 5, or use stacks; reversing mutates the inputs unless you restore them.)

<h2 id="rotate-list">Variation 5 · Rotate List</h2>

### Problem

Rotate the list to the right by k places: each place moves the last node to the front. `1 → 2 → 3 → 4 → 5` rotated by 2 is `4 → 5 → 1 → 2 → 3`. k can be far larger than the list.

### How to recognise it

- "Rotate", "shift cyclically", k possibly huge.
- Constant memory.

### Brute force

Do the single rotation (find the last node, move it to the front) k times: O(n · k), far too slow when k is 2,000,000,000.

### Intuition

Rotating by the length changes nothing, so first **measure the length n** (the same walk finds the last node) and reduce `k %= n`. The last k nodes move to the front, so the new tail is node n − k. Then **close the ring and cut it**: cut after the new tail, and tie the old last node to the old head.

### Dry run

<DryRun title="Rotate 1 → … → 5 right by 2" frames={rotateFrames([1, 2, 3, 4, 5], 2)} predict />

### Algorithm

1. If the list has fewer than 2 nodes, return `head`.
2. Walk to the last node, counting `n`.
3. `k %= n`; if `k == 0`, return `head`.
4. Walk to `newTail` (node number n − k); `newHead = newTail.next`.
5. `newTail.next = null`; `last.next = head`; return `newHead`.

### Java solution

<HintLadder hints={hints.rotate}>

```java id=rotateRight
public ListNode rotateRight(ListNode head, int k) {
    if (head == null || head.next == null) return head;
    int n = 1;
    ListNode last = head;
    while (last.next != null) { last = last.next; n++; }  // length and last node
    k %= n;
    if (k == 0) return head;
    ListNode newTail = head;
    for (int i = 1; i < n - k; i++) newTail = newTail.next; // node n − k
    ListNode newHead = newTail.next;
    newTail.next = null;   // cut
    last.next = head;      // close the old ends together
    return newHead;
}
```

</HintLadder>

### Why it works

After the cut, the list is two pieces: the first n − k nodes and the last k nodes. Tying the old last node to the old head puts the last k in front. Cutting *before* joining means no moment has a loop.

<Reveal q="k = 2,000,000,000 on a three-node list?">

2,000,000,000 mod 3 = 2, so you rotate by 2. Never walk k steps; walk at most 2n. And if k mod n is 0, return the head untouched.

</Reveal>

### Complexity

**O(n) time, O(1) extra space.**

### Edge cases and mistakes

- Empty list, one node, k = 0, k a multiple of n.
- Forgetting `k %= n` (a long walk or a NullPointerException).
- Forgetting the cut: the list becomes a ring.

### Practice

**Transfer test:** the new head is the kth node from the end, which Chapter 3's gap could find in one pass. Why does this problem still need the length? (To reduce k mod n when k exceeds the length.)

<h2 id="sort-list">Variation 6 · Sort List</h2>

### Problem

Sort the list in O(n log n) time. No copying values into an array. `4 → 2 → 1 → 3` becomes `1 → 2 → 3 → 4`.

### How to recognise it

- "Sort a linked list" with an O(n log n) bound.
- No random access, so quicksort and heapsort (index-based) are out.

### Brute force

Copy to an array, sort, write back: O(n log n) time but O(n) space and rewritten values. Or insertion sort on the list: O(n²).

### Intuition

Merge sort only needs two things a list does well: **split** it at the middle (Chapter 1, then cut the pointer between the halves) and **merge** two sorted lists (Chapter 8). Sort each half recursively, then merge.

### Dry run

Each line of the call tree shows a split, then later its merge. Predict the length of the left half.

<DryRun title="Sort 4 → 2 → 1 → 3" frames={sortListFrames([4, 2, 1, 3])} predict />

### Algorithm

1. If the list has 0 or 1 nodes, return it.
2. `slow = head`, `fast = head.next`; move until `fast` or `fast.next` is `null` (the **first** middle).
3. `right = slow.next`; `slow.next = null` (cut).
4. Return `merge(sortList(head), sortList(right))`.

### Java solution

<HintLadder hints={hints.sortList}>

```java id=sortList
public ListNode sortList(ListNode head) {
    if (head == null || head.next == null) return head;
    ListNode slow = head, fast = head.next;        // first middle: 2 nodes split 1 + 1
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    ListNode right = slow.next;
    slow.next = null;                              // cut the rope between the halves
    return merge(sortList(head), sortList(right));
}

private ListNode merge(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(0), tail = dummy;
    while (a != null && b != null) {
        if (a.val <= b.val) { tail.next = a; a = a.next; }
        else { tail.next = b; b = b.next; }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;
    return dummy.next;
}
```

</HintLadder>

### Why it works

Each call splits into strictly smaller lists (the first-middle split never leaves a half empty when n ≥ 2) and merges two sorted lists into one, so by induction every call returns a sorted list. The `<=` keeps it stable.

<Reveal q="Which middle do you split at, and does it matter?">

It matters. Split at the **first** middle: start `fast = head.next`. On a two-node list, slow stays on the first node and the halves are 1 + 1. With Chapter 1's second-middle start, a two-node list splits into 2 + 0, the left half is the whole list again, and the recursion never ends.

</Reveal>

### Complexity

- **Time O(n log n):** log n levels of splitting, O(n) merging per level.
- **Space O(log n)** for the recursion stack. LeetCode's follow-up asks for O(1), which needs the bottom-up version (see Beyond this page).

### Edge cases and mistakes

- Empty list, one node, two nodes (the infinite-recursion trap above), duplicates.
- Forgetting the cut `slow.next = null`: the left half still contains the right half.

### Practice

**Transfer test:** Merge k Sorted Lists can be done by merging pairs, level by level, exactly like this merge sort's upward half. What is its running time with N total nodes and k lists? (O(N log k).)

<h2 id="choose-the-tool">When not to use pointers</h2>

A tempting plan: "Middles are cheap now, so binary search a sorted list: find the middle, go left or right, find the middle again. Log n steps!" It fails because finding a middle costs O(length), not O(1). Each round walks the remaining range: n/2 + n/4 + … ≈ n hops per query. That is **O(n) per search**, no better than a scan.

When a list will face many random-access questions, **copy it into an array once** (O(n) time and space), then binary search or index freely. For membership questions, a `HashSet` is simpler still.

The list techniques shine for **one pass with O(1) memory**. Reach for something else when:

- You need **random access** (by index, by binary search) many times: copy to an array.
- Memory is allowed and clarity matters: an `ArrayList<ListNode>` makes Reorder List a two-pointer problem. It is correct, so say it first, then offer the O(1) version.
- The input is an array to begin with: do not build a list. (Find the Duplicate *imagines* one; it never allocates a node.)
- You need ordering by key with fast inserts and lookups: a `TreeMap` or a heap, not a hand-kept sorted list.

<Reveal q="Is copying into an ArrayList ever the right interview answer?">

Yes, as a first answer, when you name its cost. "Copy to a list, two pointers from the ends, O(n) space" is a working Reorder List. Then: "the follow-up is O(1) space: middle, reverse, weave." Interviewers reward the path from correct to optimal. They do not reward freezing while you search for the clever version.

</Reveal>

<h2 id="wider-family">Related patterns</h2>

The shared idea is always the same: **a reference is a position, and you choose how positions move**.

| Idea here | What it shares | Where it lives |
|---|---|---|
| Lead and trail with a fixed gap | Two positions with a preserved relationship | <a href={`${BASE}dsa/lessons/two-pointers/`}>Arrays & Two Pointers</a> |
| Reverse a list, or compare front to back | A stack reverses order too, at O(n) space | <a href={`${BASE}dsa/lessons/stacks/`}>Stacks</a> |
| Merge two sorted lists → merge k | A heap picks the smallest of k heads in O(log k) | <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> |

| Find the middle | Halving, but only arrays halve in O(1) | <a href={`${BASE}dsa/lessons/binary-search/`}>Binary Search</a> |
| A node with two pointers instead of one | A binary tree is a list whose nodes branch | <a href={`${BASE}dsa/lessons/trees-dfs/`}>Trees</a> |
| LRU: a map pointing into a structure | Hashing for O(1) lookup | <a href={`${BASE}dsa/lessons/hashing/`}>Hashing</a> |

**Fast/slow is not read/write.** In array problems, a read and a write pointer build a kept prefix. Here, both pointers only follow the structure; neither writes. Their *speed difference* is the information.

**A gap is a distance, not a value.** Chapter 3's gap counts hops. Two Pointers' target-difference search compares values and lets the gap change. Do not mix their movement rules.

Choose one. Use your editor, keep the lesson's code closed, and draw the before/after picture first. Before you code, say which pointer you will re-point, who holds each node while you do it, and when you stop.

1. **Keep only the loners.** A sorted list: delete every node whose value appears more than once, keeping only values that appear exactly once. `1 → 2 → 3 → 3 → 4 → 4 → 5` becomes `1 → 2 → 5`. Test a list where the head's value repeats, and one where every value repeats.
2. **Swap neighbours.** Swap every two adjacent nodes by re-pointing, not by swapping values. `1 → 2 → 3 → 4` becomes `2 → 1 → 4 → 3`. Test an odd length and a single node.
3. **Split by a threshold.** Given x, re-tie the list so every node with a value below x comes before every other node, keeping the original order **within** both groups. Test x below every value, above every value, and a list that alternates.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**Loners:** a dummy (the head itself may be deleted) and `prev`, the last node known to be kept. At each step, if the node after `prev` starts a run of equal values, skip the whole run: `prev.next = first node after the run`. Otherwise advance `prev`. Return `dummy.next`.

**Swap neighbours:** Chapter 7 with k = 2 works. The direct version: a dummy, `before`, and per pair `a = before.next`, `b = a.next`; re-tie `a.next = b.next`, `b.next = a`, `before.next = b`, then `before = a`. Three re-ties, and every node stays held.

**Split by a threshold:** two dummies and two tails, one list for "below x" and one for the rest. Splice each node onto the right tail, tie the first list's tail to the second list's head, and **set the second tail's `next` to `null`**. Forget that last line and the old pointer can tie the end back into the middle: a loop.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Middle of a list, one pass | slow + fast from head (`fast = head.next` for the first middle) | fast has made twice slow's hops |
| Does it loop? O(1) memory | slow + fast; move, then compare nodes | Inside a loop the gap shrinks by exactly 1 |
| Remove the nth from the end | Dummy; lead hops n + 1; walk until lead is null | trail stops just before the target |
| Array, values 1..n, one duplicate, read-only, O(1) | Hidden list i → nums[i]; Floyd's two phases from 0 | a = (k − 1)·L + (L − b): equal steps meet at the entrance |
| Reverse a list | prev / cur / next: save, flip, advance, advance | prev heads the reversed part; nothing is unheld |
| Reverse positions left..right | Dummy, before, first; the dance; two seams | before.next = prev, first.next = cur |
| Reverse every k | Probe k ahead; Reverse II in a loop; before = first | Everything up to before is finished |
| Merge two sorted lists | Dummy + tail; splice smaller; attach leftover | dummy.next … tail is sorted and complete |
| First, last, second, second-to-last | Middle → cut → reverse → weave | Save both ropes before each weave re-tie |
| Deep copy with extra pointers | Map old → clone, or weave clones in | A clone's pointers land only on clones |
| O(1) get / put with eviction by recency | HashMap + doubly linked list with sentinels | Map and list change together, every time |
| Where does the loop start? | Race, then restart a walker at head | Equal steps meet at the entrance |
| Palindrome list, O(1) memory | Middle → reverse back half → compare → restore | The front half is untouched |
| Two lists share a tail | Each walker restarts on the other's head | Both walk a + c + b |
| Add numbers stored as digit lists | Dummy + tail + carry | Loop while a list or the carry remains |
| Rotate right by k | Length + last; k %= n; cut after n − k; join ends | Never walk k steps |
| Sort a list in O(n log n) | Merge sort: split at the first middle, merge | A two-node list splits 1 + 1 |
| Many random-access queries | Copy to an array once | Pointer tricks are for one pass |

Linked-list techniques do not automatically mean O(1) space. Recursion costs stack (recursive reversal, merge sort), and maps cost memory (Copy Random, LRU). Count every structure you build.

### Six bugs to check for

1. **Losing the rope.** Writing `cur.next = prev` before saving `next`: the rest of the list is gone.
2. **Returning `cur`** (which is `null`) instead of `prev` from a reversal.
3. **The `fast.next.next` NullPointerException.** The guard is `fast != null && fast.next != null`, in that order.
4. **Seam amnesia** in stretch reversals. The reversed chunk floats disconnected; always re-tie both ends.
5. **Comparing values, not nodes** in cycle detection. Duplicate values give false positives.
6. **LRU: map updated, list not** (or the other way round). The two structures drift; every operation touches both.

<h2 id="revision">Revision</h2>

**How to recognise it.** The input is a linked list (or an array that acts like one) and the question is about a middle, an end, a cycle, a reversal, a splice, a reordering, or a cache with recency. The constraint is usually one pass and O(1) extra memory.

**Core algorithm.** Three reusable moves. *Two walkers:* fast and slow (speed 2 vs 1) find middles and cycles; a fixed gap of n + 1 finds the nth from the end. *The four-line dance:* `next = cur.next; cur.next = prev; prev = cur; cur = next`, then re-tie both seams for partial reversals. *Dummy plus tail:* build or edit a list without a special case for the head. Before overwriting any `next`, name the variable that holds what it points to now.

**Common mistakes.**

- Flipping before saving `next` (dropping the rope); returning `cur` instead of `prev`.
- `fast.next.next` without checking `fast` and `fast.next`; comparing values instead of nodes; comparing before moving.
- Forgetting seam 2, the cut (`slow.next = null`), or `tail = tail.next`.
- Map and list drifting apart in LRU; returning `dummy` instead of `dummy.next`.

**Complexity.** Almost everything is **O(n) time and O(1) space**. Recursive reversal and merge sort cost O(n) and O(log n) stack. Copy with a map and LRU cost O(n) space. LRU operations are O(1). Sort List is O(n log n).

**Three representative problems.**

1. [Reverse Linked List](https://leetcode.com/problems/reverse-linked-list/): the four-line dance, the base of half the chapter.
2. [Linked List Cycle](https://leetcode.com/problems/linked-list-cycle/): fast and slow, compare nodes after moving.
3. [Reorder List](https://leetcode.com/problems/reorder-list/): middle, reverse, weave, chained.
