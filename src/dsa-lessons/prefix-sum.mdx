<h2 id="prologue">The idea</h2>

Say you have a list of numbers and someone asks for the sum of positions 1 to 3. You add three numbers. Then they ask for positions 2 to 4, and you add three more, mostly the same ones. After forty questions you have added the same values hundreds of times.

The fix: do the adding once, in advance, and store it.

Define a `prefix` array:

- `prefix[0] = 0`
- `prefix[i + 1] = prefix[i] + nums[i]`

So `prefix[i]` is the sum of the first `i` values, `nums[0]` through `nums[i - 1]`. It has **n + 1** entries.

Now any range is one subtraction:

```text
sum(l..r) = prefix[r + 1] - prefix[l]
```

`prefix[r + 1]` is everything up to and including `r`. `prefix[l]` is everything before `l`. Both start at index 0, so the shared beginning cancels, and what is left is exactly `nums[l]` through `nums[r]`.

<Figure caption="nums = [3, 1, 4, 1, 5]. The range 1..3 is prefix[4] - prefix[1] = 9 - 3 = 6, which is 1 + 4 + 1.">

</Figure>

Three questions to ask of every problem in this chapter:

1. **What is settled?** Every `prefix` entry already written. It never changes.
2. **Why is the move safe?** Two prefixes share their whole beginning. Subtracting cancels it exactly, whatever the signs.
3. **When do we stop?** When the last value has been absorbed. One pass, no looking back.

**Always use length n + 1 with `prefix[0] = 0`.** Then a range starting at index 0 needs no special case.

### When this pattern applies

The same values would be added again and again. That repeated work is the signal.

- **Many range questions on data that does not change.** Re-adding costs O(n) per question. A prefix array costs O(n) once, then O(1) per question.
- **"How many subarrays sum to exactly K"**, especially with negative values. Checking every subarray is O(n²). A running total plus a hash map of earlier totals does it in one pass.
- **"Left of i versus right of i"**: a pivot, a balance point, a product of everything except i.
- **Many range updates, read once at the end**: the same idea run backwards (variation 6).

<h2 id="range-sum">Chapter 1 · Range Sum Query</h2>

### Problem

Range Sum Query, Immutable. Build a class from an array. Then answer many `sumRange(left, right)` calls, each returning the sum of `nums[left..right]` inclusive.

Example: `nums = [-2, 0, 3, -5, 2, -1]`. `sumRange(0, 2)` is 1, `sumRange(2, 5)` is -1, `sumRange(0, 5)` is -3.

### How to recognise it

- The array never changes.
- There are many range-sum questions, not one.
- Asking for the sum of a contiguous range, nothing fancier.

### Brute force

For every query, loop from `left` to `right` and add. That is O(n) per query, so O(n · q) for q queries. With 10⁴ values and 10⁴ queries that is 10⁸ additions, all re-doing the same work.

### Intuition

Two ranges that start at index 0 share everything before the point where they differ. If you know the sum of "everything up to here" for every position, the sum of the range between two positions is the difference of those two numbers. The beginning cancels.

A picture that avoids off-by-ones: write `prefix[i]` on the fence post just **before** value `i`. There are n values and n + 1 posts. The range `left..right` sits between post `left` and post `right + 1`.

### Algorithm

1. In the constructor, create `prefix` with `n + 1` entries and `prefix[0] = 0`.
2. For each `i` from 0 to n - 1, set `prefix[i + 1] = prefix[i] + nums[i]`.
3. For `sumRange(left, right)`, return `prefix[right + 1] - prefix[left]`.

### Java solution

Hints first, then the code.

<HintLadder hints={hints.rangeSum}>

```java id=NumArray
class NumArray {
    private final int[] prefix;

    public NumArray(int[] nums) {
        prefix = new int[nums.length + 1];          // prefix[0] = 0: the line above everything
        for (int i = 0; i < nums.length; i++)
            prefix[i + 1] = prefix[i] + nums[i];
    }

    public int sumRange(int left, int right) {
        return prefix[right + 1] - prefix[left];    // through right, minus before left
    }
}
```

</HintLadder>

### Why it works

`prefix[right + 1] = nums[0] + … + nums[right]` and `prefix[left] = nums[0] + … + nums[left - 1]`. Subtract, and the first `left` values cancel one by one. Nothing in that argument cares whether values are positive.

**Settled:** after the build loop handles index `i`, entries `prefix[0..i + 1]` are exact and never rewritten. **Safe move:** subtracting two exact prefixes. **Stop:** after the last value.

### Complexity

- **Time:** O(n) to build, O(1) per query (one subtraction).
- **Space:** O(n) for the `prefix` array.

LeetCode's bounds (at most 10⁴ values, each within ±10⁵) keep every total within ±10⁹, inside `int`. With larger inputs make `prefix` a `long[]`.

### Edge cases and mistakes

The classic bug is `prefix[right] - prefix[left]`. It stops one entry short and drops `nums[right]`. On the example above, `sumRange(0, 2)` would return `prefix[2] - prefix[0] = -2` instead of 1.

Other cases: a single-element range (`left == right`), a range starting at 0, and negative values (nothing special happens).

<Reveal q="Why n + 1 entries? Couldn't prefix[i] simply include nums[i] itself?">

It can. That is an *inclusive* prefix. Then the sum of `0..r` is `p[r]`, but a range starting at 0 has no entry "before 0" to subtract, so every query needs `left == 0 ? p[right] : p[right] - p[left - 1]`. The leading zero is that "before 0" entry, written once so no query needs an `if`. A length-n array is where most prefix off-by-ones are born.

</Reveal>

<Reveal q="The array is built once. What if a value is changed after it is built?">

Every total after the changed position is now wrong. Rewriting them is O(n) per change, which ruins the deal when changes and questions interleave. That problem is **Range Sum Query, Mutable**, and the tool is a Fenwick tree or a segment tree (O(log n) per update and per query). See [When prefix sums are the wrong tool](#choose-the-tool).

</Reveal>

<h2 id="pivot-index">Chapter 2 · Find Pivot Index</h2>

### Problem

Find Pivot Index. Return the **leftmost** index where the sum of everything strictly to its left equals the sum of everything strictly to its right. An empty side counts as 0. Return -1 if there is none.

Example: `[1, 7, 3, 6, 5, 6]` returns 3, because 1 + 7 + 3 = 11 and 5 + 6 = 11.

### How to recognise it

- "Left of i" compared with "right of i".
- You need one index, not a count.
- Only left and right sums matter, not arbitrary ranges.

### Brute force

For each index, sum the left side and sum the right side with two loops. That is O(n) per index, O(n²) overall.

### Intuition

You do not need the whole prefix array. Left, pivot and right always add up to the grand total:

```text
total = leftSum + nums[i] + rightSum      so      rightSum = total - leftSum - nums[i]
```

If you carry `leftSum` as you walk and know `total`, the right side is free.

<Figure caption="[1, 7, 3, 6, 5, 6], total 28. At index 3 the left is 1 + 7 + 3 = 11 and the right is 28 - 11 - 6 = 11. Indexes 0, 1 and 2 do not balance, so 3 is the answer.">
  <ArrayStrip values={[1, 7, 3, 6, 5, 6]} pointers={[{ at: 3, label: 'PIVOT', tone: 'purple' }]} tones={{ 3: 'purple' }} regions={[{ from: 0, to: 2, label: 'left = 11', tone: 'blue' }, { from: 4, to: 5, label: 'right = 11', tone: 'green' }]} />
</Figure>

### Dry run

<DryRun title="Find Pivot Index" frames={pivotFrames([1, 7, 3, 6, 5, 6])} predict />

<Trace title="Weigh both sides" steps={pivot} takeaway="Remember: right = total - left - nums[i]. Compare first, then add nums[i] to the left side." />

### Algorithm

1. Compute `total`, the sum of all values.
2. Set `leftSum = 0` (nothing is left of index 0).
3. For each `i` from left to right: if `leftSum == total - leftSum - nums[i]`, return `i`.
4. Otherwise add `nums[i]` to `leftSum` and continue.
5. If the loop ends, return -1.

### Java solution

<HintLadder hints={hints.pivot}>

```java id=pivotIndex
public int pivotIndex(int[] nums) {
    int total = 0;
    for (int x : nums) total += x;
    int leftSum = 0;                                 // nothing to the left of index 0
    for (int i = 0; i < nums.length; i++) {
        if (leftSum == total - leftSum - nums[i]) return i;
        leftSum += nums[i];                          // only now does nums[i] join the left side
    }
    return -1;
}
```

</HintLadder>

(Find the Middle Index in Array is the same problem.)

### Why it works

The three parts always add up to `total`, so `rightSum` is exact without ever being summed. Scanning from the left makes the first match the leftmost pivot.

**Settled:** at the top of iteration `i`, `leftSum` is exactly `nums[0] + … + nums[i - 1]`. **Safe move:** comparing against `total - leftSum - nums[i]`. **Stop:** at the first match, or after the last index. That is why `leftSum` grows **after** the comparison.

### Complexity

- **Time:** O(n), two passes.
- **Space:** O(1). No prefix array is needed.

Values within ±1000 and at most 10⁴ of them keep totals far inside `int`.

### Edge cases and mistakes

- Comparing `leftSum` with `total - leftSum` forgets that the pivot belongs to neither side. On `[2, 1, -1]` it misses index 0 (left 0, right 1 + (-1) = 0) and returns -1.
- An empty side is allowed, so index 0 and the last index can be pivots.
- Adding `nums[i]` to `leftSum` before comparing breaks the invariant (see below).

<Reveal q="What goes wrong if you add nums[i] to leftSum before comparing?">

Then `leftSum` includes the pivot itself, and you compare the wrong two sides. On `[1, 7, 3, 6, 5, 6]` the comparison at index 3 becomes 17 against 28 - 17 - 6 = 5, and no index ever matches: the function returns -1 instead of 3.

</Reveal>

### Practice

Variation: return *every* pivot index instead of the first. (Same loop, collect instead of return.) Variation: the first index where left sum equals right sum with the pivot counted on the left side. (Change the comparison, not the idea.)

<h2 id="product-except-self">Chapter 3 · Product of Array Except Self</h2>

### Problem

Return an array where `answer[i]` is the product of every value except `nums[i]`. No division. O(n) time.

Example: `[1, 2, 3, 4]` returns `[24, 12, 8, 6]`.

### How to recognise it

- "Everything except i."
- Division is banned (or a value can be zero).
- The answer is per position, so sorting cannot help.

### Brute force

For each `i`, multiply all the other values: O(n²). The tempting shortcut, multiply everything and divide by `nums[i]`, is banned and also breaks on zeros.

### Intuition

"Everything except `i`" is "everything left of `i`" times "everything right of `i`". Both are running products: one from the front, one from the back. The empty product is 1, the same way the empty sum is 0.

Pass 1 writes the left products straight into `answer`. Pass 2 walks backwards carrying a single number, `suffix`, and multiplies it in. No second array is needed.

  <ArrayStrip name="answer" values={[24, 12, 8, 6]} tones={{ 0: 'done', 1: 'done', 2: 'done', 3: 'done' }} />
</Figure>

### Dry run

<DryRun title="Product of Array Except Self" frames={productFrames([1, 2, 3, 4])} predict />

<Trace title="Multiply the two sides" steps={product} takeaway="Remember: answer[i] = left product × right product. In pass 2, use suffix first, then fold nums[i] into it." />

### Algorithm

1. Create `answer` and set `answer[0] = 1` (nothing is left of index 0).
2. For `i` from 1 to n - 1: `answer[i] = answer[i - 1] * nums[i - 1]`.
3. Set `suffix = 1` (nothing is right of the last index).
4. For `i` from n - 1 down to 0: first `answer[i] *= suffix`, then `suffix *= nums[i]`.
5. Return `answer`.

### Java solution

<HintLadder hints={hints.product}>

```java id=productExceptSelf
public int[] productExceptSelf(int[] nums) {
    int n = nums.length;
    int[] answer = new int[n];
    answer[0] = 1;                                   // nothing lies left of index 0
    for (int i = 1; i < n; i++)
        answer[i] = answer[i - 1] * nums[i - 1];     // product of nums[0..i-1]
    int suffix = 1;                                  // product of everything right of i
    for (int i = n - 1; i >= 0; i--) {
        answer[i] *= suffix;                         // use it first...
        suffix *= nums[i];                           // ...then let nums[i] join it
    }
    return answer;
}
```

</HintLadder>

### Why it works

After pass 1, `answer[i]` is the product of `nums[0..i - 1]`. In pass 2, at the moment the loop reaches `i`, `suffix` is the product of `nums[i + 1..n - 1]`. Multiplying gives everything except `nums[i]`. There is no division, so zeros need no special case.

**Settled:** during pass 2, every position after `i` already holds its final answer, and `suffix` is the product of exactly those positions' values.

### Complexity

- **Time:** O(n), two passes.
- **Space:** O(1) beyond the output array (the problem's follow-up says the output does not count).

The problem guarantees every prefix and suffix product fits in a 32-bit `int`.

### Edge cases and mistakes

- Swapping the two lines in pass 2 (`suffix *= nums[i]` first) folds each value into its own product. On `[1, 2, 3, 4]` every slot becomes 24.
- Zeros: `[-1, 1, 0, -3, 3]` gives `[0, 0, 9, 0, 0]`. The two-sided product handles it with no extra code.
- Initialising `answer[0]` to `nums[0]` instead of 1.

<Reveal q="Why not compute the total product once and divide by nums[i]?">

The problem forbids division, and it would fail anyway. With one zero, the total is 0, yet the zero's own position should get the product of everything else. With `[-1, 1, 0, -3, 3]` the answer is `[0, 0, 9, 0, 0]`, and 0 ÷ 0 cannot produce that 9. Division needs a zero count and special cases; the two-sided product needs neither.

</Reveal>

### Practice

Variation: do the same with sums ("sum of everything except i"). With sums you may subtract, so `total - nums[i]` works. Say why the same shortcut fails for products.

<h2 id="count-k">Chapter 4 · Subarray Sum Equals K</h2>

### Problem

Subarray Sum Equals K. Count the contiguous subarrays whose sum is exactly `k`. Values can be negative.

Example: `[3, 4, 7, -2, 2]` with `k = 7` returns 3. The subarrays are `[3, 4]`, `[7]` and `[7, -2, 2]`.

### How to recognise it

- "Count" (or "does one exist") contiguous subarrays with an exact sum.
- Negative values or zeros are allowed.
- You cannot sort, because order matters.

### Brute force

Try every start and every end, keeping a running sum for each start: O(n²) time. It is correct, but with 2 × 10⁴ values that is 2 × 10⁸ steps, and interviewers expect better.

### Intuition

Do not hunt for the subarray. **Stand at where it ends** and ask where it began.

A subarray `i..j` sums to `k` exactly when

```text
prefix[j + 1] - prefix[i] = k      ⟺      prefix[i] = prefix[j + 1] - k
```

So walk left to right with a running total. At each position ask: **how many earlier totals equal `running - k`?** Each one is the start of a different subarray ending right here. Then record the current total so later positions can use it.

The hash map goes from total to **how many times** it has appeared. Counts, not just presence: equal totals at different positions are different starting points.

<Figure caption="[3, 4, 7, -2, 2] with k = 7. prefix = [0, 3, 7, 14, 12, 14]. Three pairs of entries differ by exactly 7: 0 to 7 is [3, 4]; 7 to 14 (entry 3) is [7]; 7 to 14 (entry 5) is [7, -2, 2]. Answer: 3.">

  <ArrayStrip name="prefix" values={[0, 3, 7, 14, 12, 14]} pointers={[{ at: 2, label: 'a start: 7', tone: 'blue' }, { at: 5, label: 'here: 14' }]} tones={{ 0: 'blue', 3: 'hot' }} />

<Mermaid code={`flowchart LR
  S["seed: seen[0] = 1"] --> A["running += nums[j]"]
  A --> C["count += seen[running − k]"]
  C --> R["seen[running] += 1"]
  R -->|next j| A`} />

**Why not a sliding window?** A window needs monotonicity: grow it and the sum goes up, shrink it and the sum goes down. **Negative values break that**, so a window has no safe direction to move. The hash map does not care about direction. Say that sentence out loud in an interview; this boundary is the question half the time.

### Dry run

Watch the map fill up and the count grow.

<DryRun title="Subarray Sum Equals K" frames={countKFrames([3, 4, 7, -2, 2], 7)} predict />

<Trace title="Ask the map about the start" steps={countK} takeaway="Remember: seed total 0 once, then for each value add, count running - k, record. The seed catches runs from the start; the order stops a total matching itself." />

### Algorithm

1. Create a map `seen` from total to count. Put `0 → 1` (the empty prefix).
2. Set `running = 0` and `count = 0`.
3. For each value: add it to `running`.
4. Add `seen[running - k]` (0 if absent) to `count`.
5. Then add 1 to `seen[running]`.
6. Return `count`.

### Java solution

<HintLadder hints={hints.countK}>

```java id=subarraySum
public int subarraySum(int[] nums, int k) {
    Map<Integer, Integer> seen = new HashMap<>();
    seen.put(0, 1);                                  // the empty prefix: runs that start at index 0
    int prefix = 0, count = 0;
    for (int x : nums) {
        prefix += x;
        count += seen.getOrDefault(prefix - k, 0);   // every earlier start of a run ending here
        seen.merge(prefix, 1, Integer::sum);         // record AFTER counting (no self-match)
    }
    return count;
}
```

</HintLadder>

### Why it works

Every subarray ending at `j` has exactly one start `i`, and so exactly one earlier prefix `prefix[i]`. At the moment you count, the map holds `prefix[0]` through `prefix[j]`, exactly the possible starts of a non-empty subarray ending at `j`, each with its multiplicity.

**Settled:** before handling index `j`, the map holds every prefix `prefix[0..j]` with its count, and `count` is the number of qualifying subarrays that end before `j`. **Safe move:** matching on `running - k`. **Stop:** after the last value.

### Complexity

- **Time:** O(n) expected, one pass with O(1) average map operations.
- **Space:** O(n) for the map (up to n + 1 distinct totals).

LeetCode's bounds (at most 2 × 10⁴ values within ±1000, `k` within ±10⁷) keep `running` and `running - k` well inside `int`. For larger values use `long` keys.

### Edge cases and mistakes

Two details interviewers watch for:

1. **The seed, `seen.put(0, 1)`.** It is the empty prefix, the entry before everything. Without it, subarrays that start at index 0 are never counted: on `[1, 2, 3]` with `k = 3` you find `[3]` but lose `[1, 2]`, returning 1 instead of 2. This is **the** classic bug of the pattern.
2. **Count before you record.** If the current total goes into the map first, then with `k = 0` it matches itself, a subarray of length zero. On `[1]` with `k = 0` that returns 1 instead of 0.

The two failures side by side:

```java fragment
seen.merge(prefix, 1, Integer::sum);         // BUG: recorded first, so k = 0 matches itself: [1], k = 0 → 1
count += seen.getOrDefault(prefix - k, 0);
// ... and with seen.put(0, 1) missing: [1, 2, 3], k = 3 → 1 instead of 2
```

<Reveal q="Why does the map keep a count, not just 'seen or not seen'?">

Equal totals at different positions are different starts. In `[1, -1, 1, -1]` with `k = 0`, the prefix array is `[0, 1, 0, 1, 0]`. Total 0 appears three times (3 pairs) and total 1 twice (1 pair): **4 subarrays**. A presence-only set would undercount.

</Reveal>

<h2 id="multiple-of-k">Chapter 5 · Continuous Subarray Sum</h2>

### Problem

Continuous Subarray Sum. Return true if some subarray of **length at least 2** has a sum that is a multiple of `k` (zero counts as a multiple).

Example: `[23, 2, 4, 6, 7]` with `k = 6` returns true, because `2 + 4 = 6`.

### How to recognise it

- "Multiple of k" or "divisible by k" for a contiguous run.
- A length rule (here, at least 2).
- You need existence, not a count.

### Brute force

Try every start and end with a running sum and check `sum % k == 0`: O(n²).

### Intuition

If two running totals leave the **same remainder** mod `k`, their difference is a multiple of `k`, and their difference is exactly the subarray between them. So store **remainders** instead of totals.

Two changes from Chapter 4:

- **Remainders, not totals.** The subarray `i + 1..j` works when `prefix[j + 1] % k == prefix[i + 1] % k`.
- **Store the first index, never overwrite it.** The question has a length rule, and the earliest index gives the longest stretch. Seed remainder 0 at index **-1**: the empty prefix sits just before index 0, so a subarray `0..j` has length `j - (-1) = j + 1`.

<Figure caption="[23, 2, 4, 6, 7] with k = 6. Running totals 23, 25, 29, 35, 42 leave remainders 5, 1, 5, 5, 0. Remainder 5 first appears after index 0 and again after index 2: the stretch between, positions 1..2 = 2 + 4 = 6, has length 2. Return true.">

  <ArrayStrip name="remainder" values={[5, 1, 5, 5, 0]} pointers={[{ at: 0, label: 'first 5', tone: 'blue' }, { at: 2, label: '5 again' }]} />
</Figure>

### Dry run

<DryRun title="Continuous Subarray Sum" frames={multipleKFrames([23, 2, 4, 6, 7], 6)} predict />

### Algorithm

1. Create a map `firstSeen` from remainder to index. Put `0 → -1`.
2. Keep a running remainder `rem = 0`.
3. For each index `i`: `rem = (rem + nums[i]) % k`.
4. If `rem` is not in the map, store `rem → i` and continue.
5. If it is, and `i - firstSeen[rem] >= 2`, return true.
6. Never overwrite an existing entry. After the loop, return false.

### Java solution

<HintLadder hints={hints.multipleK}>

```java id=checkSubarraySum
public boolean checkSubarraySum(int[] nums, int k) {
    Map<Integer, Integer> firstSeen = new HashMap<>();
    firstSeen.put(0, -1);                            // empty prefix sits just before index 0
    long rem = 0;                                    // long: rem + nums[i] can exceed int
    for (int i = 0; i < nums.length; i++) {
        rem = (rem + nums[i]) % k;
        Integer first = firstSeen.get((int) rem);
        if (first == null) firstSeen.put((int) rem, i);   // remember only the first time
        else if (i - first >= 2) return true;
    }
    return false;
}
```

</HintLadder>

### Why it works

If `P1 % k == P2 % k`, then `P2 - P1` is divisible by `k`. Every qualifying subarray ends at some `j`. If any start works, the earliest index with the same remainder gives the longest subarray, so checking only the first index is enough to answer "does one of length at least 2 exist?"

**Settled:** before handling index `j`, the map holds, for every remainder seen so far, the **earliest** index where it appeared (-1 for the empty prefix). **Safe move:** comparing against the earliest index. **Stop:** when a long-enough match appears, or at the end.

### Complexity

- **Time:** O(n).
- **Space:** O(min(n, k)), since there are at most `min(n + 1, k)` distinct remainders.

Values here are non-negative, so remainders are too. Values reach 10⁹ and `k` reaches 2³¹ - 1; keeping `rem` in a `long` makes `rem + nums[i]` safe without relying on any promise about the grand total.

### Edge cases and mistakes

- `firstSeen.put(rem, i)` on every step stores the **latest** index; `[5, 0, 0]` with `k = 3` then returns false.
- Two adjacent zeros `[0, 0]` qualify for any `k`.
- A length-1 match (`i - first == 1`) must be ignored, not returned.
- Forgetting the `0 → -1` seed loses subarrays that start at index 0: `[6, 6]` with `k = 6` returns false instead of true.

<Reveal q="Why keep the first index? Try [5, 0, 0] with k = 3.">

Remainders: 2 after index 0, still 2 after index 1 (length 1, too short), still 2 after index 2. With the first index kept (0), index 2 gives length 2 - 0 = 2: positions 1..2 are `[0, 0]`, total 0, a multiple of 3. **True.** Overwrite with the latest index (1) and index 2 gives length 1 again: you return **false**.

</Reveal>

<h2 id="equal-zeros-ones">Variation 1 · Equal 0s and 1s</h2>

### Problem

Contiguous Array. Given a 0/1 array, return the length of the **longest** contiguous subarray with equally many 0s and 1s.

Example: `[0, 1, 1, 1, 1, 1, 0, 0, 0]` returns 6 (the subarray `[1, 1, 1, 0, 0, 0]`).

### How to recognise it

- Only two kinds of value, and "equal counts".
- "Longest", so positions matter, not just counts.
- No `k` anywhere. The target is hidden: the balance must be 0.

### Brute force

Count 0s and 1s for every start and end: O(n²), or O(n³) if you recount each time.

### Intuition

Turn every 0 into -1. A subarray has equal 0s and 1s exactly when its ±1 values sum to 0. That is Chapter 4 with `k = 0`. Two equal running balances bracket a balanced subarray, and since you want the **longest**, keep the **first** index of each balance, seeded with balance 0 at index -1 (Chapter 5's trick).

<Figure caption="[0, 1, 1, 1, 1, 1, 0, 0, 0]. Balance after each index (0 → -1, 1 → +1): -1, 0, 1, 2, 3, 4, 3, 2, 1. Balance 1 first appears after index 2 and again after index 8, so positions 3..8 are balanced: length 8 - 2 = 6.">
  <ArrayStrip name="nums" values={[0, 1, 1, 1, 1, 1, 0, 0, 0]} tones={{ 3: 'hot', 4: 'hot', 5: 'hot', 6: 'hot', 7: 'hot', 8: 'hot' }} regions={[{ from: 3, to: 8, label: 'longest balanced: 6', tone: 'gold' }]} />
  <ArrayStrip name="balance" values={[-1, 0, 1, 2, 3, 4, 3, 2, 1]} pointers={[{ at: 2, label: 'first 1', tone: 'blue' }, { at: 8, label: '1 again' }]} />
</Figure>

### Dry run

<DryRun title="Contiguous Array" frames={equalZerosOnesFrames([0, 1, 1, 1, 1, 1, 0, 0, 0])} predict />

### Algorithm

1. Map `firstSeen`: balance to index. Put `0 → -1`.
2. For each index `i`: add +1 for a 1 and -1 for a 0 to `balance`.
3. If `balance` is in the map, `best = max(best, i - firstSeen[balance])`.
4. Otherwise store `balance → i`. Never overwrite.
5. Return `best`.

### Java solution

<HintLadder hints={hints.contiguous}>

```java id=findMaxLength
public int findMaxLength(int[] nums) {
    Map<Integer, Integer> firstSeen = new HashMap<>();
    firstSeen.put(0, -1);                            // balance 0 before index 0
    int balance = 0, best = 0;
    for (int i = 0; i < nums.length; i++) {
        balance += nums[i] == 1 ? 1 : -1;
        if (firstSeen.containsKey(balance)) best = Math.max(best, i - firstSeen.get(balance));
        else firstSeen.put(balance, i);              // first time only: earliest = longest
    }
    return best;
}
```

</HintLadder>

### Why it works

`ones - zeros` over any subarray equals the difference of two balances. Equal balances mean a difference of 0, so the subarray between them is balanced. The earliest index for a balance gives the longest subarray ending at the current index.

### Complexity

- **Time:** O(n).
- **Space:** O(n). The balance stays within ±n, so an `int[2n + 1]` offset by n can replace the map.

### Edge cases and mistakes

- Forgetting the `-1` seed: `[0, 1]` returns 0 instead of 2.
- Overwriting the first index: you measure shorter stretches.
- Counting 0s as 0 instead of -1: the balance never goes down.

<Reveal q="Why does turning 0 into -1 work, when counting 0s and 1s separately feels more natural?">

Equal counts means `ones - zeros = 0`. With 0 → -1 and 1 → +1, the sum of any subarray is exactly `ones - zeros`. So "equal counts" becomes "sum is 0", and a sum question is a prefix question. Disguises like this are the whole game: **find the transform that makes the property a sum**.

</Reveal>

<h2 id="divisible-by-k">Variation 2 · Divisible by K, with negatives</h2>

### Problem

Subarray Sums Divisible by K. Count the subarrays whose sum is divisible by `k`. Values can be negative.

Example: `[4, 5, 0, -2, -3, 1]` with `k = 5` returns 7.

### How to recognise it

- Count (not just detect) subarrays divisible by `k`.
- Negative values are allowed.
- No length rule, so no first index is needed.

### Brute force

Check every subarray's sum with `% k`: O(n²).

### Intuition

Counting brings back Chapter 4's tally; divisibility brings back Chapter 5's remainders. Equal remainders mean a divisible subarray between them, and every pair counts. Remainders live in `0..k - 1`, so an `int[k]` replaces the map.

The trap is Java. **Java's `%` keeps the sign of the left operand**: `-1 % 5` is `-1`, not 4. Mathematically -1 and 4 are the same remainder class, but the buckets would treat them as strangers. Fold every remainder into `0..k - 1` with `((x % k) + k) % k` or `Math.floorMod(x, k)`.

### Dry run

Watch the raw Java remainder next to the folded one.

<DryRun title="Subarray Sums Divisible by K" frames={divisibleFrames([4, 5, 0, -2, -3, 1], 5)} predict />

### Algorithm

1. Create `seen = new int[k]` and set `seen[0] = 1` (the empty prefix).
2. For each value: `rem = ((rem + x) % k + k) % k`.
3. Add `seen[rem]` to `count`.
4. Then increment `seen[rem]`.
5. Return `count`.

### Java solution

<HintLadder hints={hints.divisible}>

```java id=subarraysDivByK
public int subarraysDivByK(int[] nums, int k) {
    int[] seen = new int[k];                         // seen[r] = earlier totals with remainder r
    seen[0] = 1;                                     // the empty prefix
    int rem = 0, count = 0;
    for (int x : nums) {
        rem = ((rem + x) % k + k) % k;               // fold Java's negative % into 0..k-1
        count += seen[rem];                          // count first...
        seen[rem]++;                                 // ...then record
    }
    return count;
}
```

</HintLadder>

### Why it works

Two prefixes with the same remainder differ by a multiple of `k`. Each earlier prefix with the same remainder is a different start, and the array stores how many there are. Folding keeps equal remainder classes in the same bucket.

### Complexity

- **Time:** O(n + k).
- **Space:** O(k).

On the example, the remainders (with the seed) are 0, 4, 4, 4, 2, 4, 0: one pair of 0s plus six pairs of 4s gives **7**.

### Edge cases and mistakes

`[-1, 5]` with `k = 5`: the totals are -1 and 4, and `[5]` is divisible, so the answer is **1**. With plain `%`, a `HashMap` version silently returns 0, and an `int[k]` version throws `ArrayIndexOutOfBoundsException` on index -1.

```java fragment
rem = (rem + x) % k;          // BUG in Java: can be negative, so -1 and 4 never meet
```

<Reveal q="[-1, 5] with k = 5. What does the naive % version return?">

Running totals are -1 and 4. The subarray `[5]` is divisible by 5, so the answer is **1**. Naively, -1 % 5 = -1 and 4 % 5 = 4 land in different buckets: a `HashMap` version returns **0**, and an `int[k]` version throws on index -1. With `floorMod`, -1 becomes 4, which matches the later 4.

</Reveal>

### Problem

Count Number of Nice Subarrays. Count the subarrays that contain **exactly `k` odd numbers**.

Example: `[2, 2, 2, 1, 2, 2, 1, 2, 2, 2]` with `k = 2` returns 16.

### How to recognise it

- "Exactly k" of some property of the values.
- The values themselves do not matter, only whether each has the property.
- Count, not longest.

### Brute force

For every start and end count the odd values: O(n²).

### Intuition

Write 1 for an odd value and 0 for an even one. A subarray's count of odd numbers is now its *sum*, and the problem is Chapter 4 on a 0/1 array. The running count never exceeds n, so an `int[n + 1]` of tallies replaces the map.

### Algorithm

1. `seen = new int[n + 1]`, with `seen[0] = 1`.
2. For each value: `odd += x & 1`.
3. If `odd >= k`, add `seen[odd - k]` to `count`.
4. Then increment `seen[odd]`.
5. Return `count`.

### Java solution

<HintLadder hints={hints.nice}>

```java id=numberOfSubarrays
public int numberOfSubarrays(int[] nums, int k) {
    int[] seen = new int[nums.length + 1];           // seen[c] = earlier lines with c odd numbers
    seen[0] = 1;                                     // the empty prefix has 0 odd numbers
    int odd = 0, count = 0;
    for (int x : nums) {
        odd += x & 1;                                // 1 for odd (works for negatives too)
        if (odd >= k) count += seen[odd - k];
        seen[odd]++;
    }
    return count;
}
```

</HintLadder>

### Why it works

This is Chapter 4 on a transformed array. A subarray has exactly `k` odd numbers when the odd-count prefix at its end minus the one before its start equals `k`.

### Complexity

- **Time:** O(n).
- **Space:** O(n).

### Edge cases and mistakes

- Skipping the `odd >= k` check indexes `seen[-1]` for small totals.
- Using `x % 2 == 1` fails for negative odd values (`-3 % 2 == -1`). `x & 1` works for both.
- `k = 0` is safe: counting before recording means an entry never matches itself.

Both are O(n). The window version needs O(1) extra space but relies on a trick (exactly = at most k minus at most k - 1) that only works because the 0/1 counts are non-negative. The prefix version needs O(n) space, reads more directly, and is the same code you already trust from Chapter 4. Name both in an interview; pick the one you can defend.

</Reveal>

<h2 id="prefix-xor">Variation 4 · A different operation (XOR)</h2>

### Problem

XOR Queries of a Subarray. Given an array and many queries `[l, r]`, return the bitwise XOR of `arr[l..r]` for each query.

Example: `arr = [1, 3, 4, 8]`, query `[1, 2]` returns 7 (that is 3 ^ 4), and `[3, 3]` returns 8.

### How to recognise it

- Many range questions on fixed data, but the operation is XOR, not sum.
- There is no minus sign for XOR. Ask whether the operation can undo itself.

### Brute force

XOR every value in each query: O(n) per query, O(n · q) overall.

### Intuition

Subtraction was never the point. The point is that the shared beginning **cancels**. XOR cancels itself: `x ^ x = 0`. So running XORs work exactly like running sums:

```text
xor(l..r) = px[r + 1] ^ px[l]
```

<Figure caption="arr = [1, 3, 4, 8], px = [0, 1, 2, 6, 14]. xor(1..2) = px[3] ^ px[1] = 6 ^ 1 = 7 = 3 ^ 4. xor(3..3) = 14 ^ 6 = 8.">
  <ArrayStrip name="arr" values={[1, 3, 4, 8]} tones={{ 1: 'hot', 2: 'hot' }} regions={[{ from: 1, to: 2, label: '3 ^ 4 = 7', tone: 'gold' }]} />
  <ArrayStrip name="px" values={[0, 1, 2, 6, 14]} pointers={[{ at: 1, label: 'px[1]', tone: 'blue' }, { at: 3, label: 'px[3]' }]} tones={{ 0: 'ghost' }} />
</Figure>

**What makes a prefix trick legal:** the operation must have an **inverse** that removes the shared beginning. Sums have subtraction; XOR is its own inverse. Products have division only when there are no zeros, which is why Chapter 3 multiplied two sides instead of dividing. **Max and min have no inverse**, so a prefix-max array answers only ranges that start at 0.

### Dry run

<DryRun title="XOR Queries of a Subarray" frames={xorFrames([1, 3, 4, 8], [[1, 2], [3, 3]])} predict />

### Algorithm

1. Build `px` with `px[0] = 0` and `px[i + 1] = px[i] ^ arr[i]`.
2. For each query `[l, r]`, answer `px[r + 1] ^ px[l]`.
3. To **count** subarrays with XOR exactly `k`, use Chapter 4's map seeded `0 → 1` and look up `px ^ k` before recording `px`.

### Java solution

<HintLadder hints={hints.xor}>

```java id=xorQueries
public int[] xorQueries(int[] arr, int[][] queries) {
    int[] px = new int[arr.length + 1];              // px[0] = 0, the XOR of nothing
    for (int i = 0; i < arr.length; i++) px[i + 1] = px[i] ^ arr[i];
    int[] answer = new int[queries.length];
    for (int q = 0; q < queries.length; q++)
        answer[q] = px[queries[q][1] + 1] ^ px[queries[q][0]];
    return answer;
}

// The vault works with XOR too: count stretches whose XOR is exactly k.
public long countXorK(int[] nums, int k) {
    Map<Integer, Integer> seen = new HashMap<>();
    seen.put(0, 1);
    int px = 0;
    long count = 0;
    for (int x : nums) {
        px ^= x;
        count += seen.getOrDefault(px ^ k, 0);       // start total s with s ^ px == k, so s = px ^ k
        seen.merge(px, 1, Integer::sum);
    }
    return count;
}
```

</HintLadder>

### Why it works

`px[r + 1] = arr[0] ^ … ^ arr[r]` and `px[l] = arr[0] ^ … ^ arr[l - 1]`. XOR them: the first `l` values appear twice and cancel to 0, leaving `arr[l] ^ … ^ arr[r]`. For counting, `s ^ px == k` means `s = px ^ k`.

### Complexity

- **Time:** O(n + q) for the queries. The counting version is O(n) expected.
- **Space:** O(n).

XOR never carries, so there is no overflow to worry about.

### Edge cases and mistakes

- Using `-` instead of `^` between prefixes.
- Forgetting `px[0] = 0`, which breaks every query starting at index 0.
- For the counting version, looking up `px - k` instead of `px ^ k`.

<Reveal q="Then how do you answer 'maximum on l..r' many times?">

Not with a prefix array. A sparse table answers range-minimum or range-maximum in O(1) after O(n log n) preprocessing, because max is *idempotent* (overlapping two ranges does not double-count). A segment tree handles it in O(log n) and also survives updates. A monotonic deque handles fixed-size sliding windows.

</Reveal>

<h2 id="grid-sums">Variation 5 · Two dimensions (grid sums)</h2>

### Problem

Range Sum Query 2D, Immutable. Given a matrix, answer many `sumRegion(row1, col1, row2, col2)` calls: the sum of the rectangle with those corners (inclusive).

Example: for `[[1, 2, 3], [4, 5, 6], [7, 8, 9]]`, the rectangle rows 1..2, columns 1..2 is 5 + 6 + 8 + 9 = 28.

### How to recognise it

- A fixed table and many rectangle-sum questions.
- Same idea as Chapter 1, now in two directions.

### Brute force

Loop over the rectangle for each query: O(rows × cols) per query.

### Intuition

Let `P[r + 1][c + 1]` be the total of the block from the top-left corner down to `(r, c)`. Same n + 1 convention in both directions: row 0 and column 0 of `P` are zeros. Any rectangle is then four lookups:

```text
sum = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]
```

Take the big block, cut off the strip above, cut off the strip to the left, and **add back the corner block**, which you cut off twice. That is inclusion-exclusion, and it builds the table too: `P[r+1][c+1] = m[r][c] + P[r][c+1] + P[r+1][c] - P[r][c]`.

### Algorithm

1. Create `P` with `(rows + 1) × (cols + 1)` zeros.
2. For each cell: `P[r+1][c+1] = m[r][c] + P[r][c+1] + P[r+1][c] - P[r][c]`.
3. For a query, return `P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]`.

### Java solution

<HintLadder hints={hints.grid}>

```java id=NumMatrix
class NumMatrix {
    private final int[][] P;                         // P[r+1][c+1] = block (0,0)..(r,c)

    public NumMatrix(int[][] matrix) {
        int rows = matrix.length, cols = matrix[0].length;   // LeetCode guarantees at least 1 x 1
        P = new int[rows + 1][cols + 1];
        for (int r = 0; r < rows; r++)
            for (int c = 0; c < cols; c++)
                P[r + 1][c + 1] = matrix[r][c] + P[r][c + 1] + P[r + 1][c] - P[r][c];
    }

    public int sumRegion(int row1, int col1, int row2, int col2) {
        return P[row2 + 1][col2 + 1] - P[row1][col2 + 1] - P[row2 + 1][col1] + P[row1][col1];
    }
}
```

</HintLadder>

### Why it works

`P[r+1][c+1]` is the exact sum of the block `(0,0)..(r,c)`. The block above and the block to the left of a rectangle both contain the top-left corner block, so removing both removes it twice. Adding it back once leaves exactly the rectangle.

### Complexity

- **Time:** O(rows × cols) to build, O(1) per query.
- **Space:** O(rows × cols).

LeetCode's bounds (at most 200 × 200 cells within ±10⁴) keep every block total within ±4 × 10⁸, inside `int`.

### Edge cases and mistakes

- Forgetting the zero border in either direction.
- Using `r2` instead of `r2 + 1` (and the same for columns).
- Forgetting to add the corner back: you get 27 instead of 28 on the example.

<Reveal q="Why add P[r1][c1] back instead of subtracting it a third time?">

The block above the rectangle and the block to its left **overlap** in the top-left corner. Subtracting both removes that corner twice, so it must be added back once. In the figure: 45 - 6 - 12 would remove the 1 in the corner twice and give 27; adding it back gives 28.

</Reveal>

<h2 id="range-updates">Variation 6 · Range updates (difference array)</h2>

### Problem

Corporate Flight Bookings. There are `n` flights numbered 1 to n. Each booking `[first, last, seats]` adds `seats` to every flight from `first` to `last`. Return every flight's total after all bookings.

Example: `n = 5`, bookings `[1,2,10]`, `[2,3,20]`, `[2,5,25]` returns `[10, 55, 45, 25, 25]`.

### How to recognise it

- Many range **writes**, read once at the end (the reverse of the earlier chapters).
- "Add v to every element in l..r."

### Brute force

Loop over each booking's range and add: O(n × bookings). At 2 × 10⁴ by 2 × 10⁴ that is 400 million writes.

### Intuition

Run the prefix array backwards. Keep a `diff` array with one slot per flight plus one spare. A booking pins **+v where it starts** and **-v just after it ends**. One sweep of running totals across `diff` then rebuilds every flight's count: the +v switches the booking on, and the -v switches it off. Two writes per booking instead of touching every flight in its range.

### Algorithm

1. Create `diff` with `n + 1` slots.
2. For each booking `[first, last, seats]`: `diff[first - 1] += seats` and `diff[last] -= seats`.
3. Sweep `i` from 0 to n - 1, keeping `running += diff[i]`.
4. Set `answer[i] = running`.

### Java solution

<HintLadder hints={hints.flights}>

```java id=corpFlightBookings
public int[] corpFlightBookings(int[][] bookings, int n) {
    int[] diff = new int[n + 1];                     // one spare slot past the last flight
    for (int[] b : bookings) {
        diff[b[0] - 1] += b[2];                      // flights are 1-indexed: first flight -> slot first-1
        diff[b[1]] -= b[2];                          // switch off just AFTER flight last (slot last)
    }
    int[] answer = new int[n];
    int running = 0;
    for (int i = 0; i < n; i++) {
        running += diff[i];
        answer[i] = running;
    }
    return answer;
}
```

</HintLadder>

### Why it works

The running total at slot `i` is the sum of every `+v` at or before `i` minus every `-v` at or before `i`. A booking contributes `+v` exactly from its first slot until the slot after its last, which is its range.

### Complexity

- **Time:** O(n + bookings).
- **Space:** O(n) for `diff`.

Painting every booking's range directly is O(n × bookings). Totals stay under 2 × 10⁸, inside `int`.

### Edge cases and mistakes

- Flights are 1-indexed: the start goes to slot `first - 1`, the minus to slot `last`.
- Putting the minus at `last - 1` switches the booking off one slot early.
- Without the spare slot, a booking ending at the last flight indexes out of bounds.

<Reveal q="Why does the diff array need n + 1 slots?">

A booking that ends at the last flight writes its -v at slot n, one past the end. Nobody ever reads that slot; it only exists so the code needs no `if (last < n)` check. It is the mirror image of the prefix array's extra zero.

</Reveal>

<h2 id="choose-the-tool">When prefix sums are the wrong tool</h2>

A prefix array is the right tool when **the data is fixed and the questions are many**, or when a single pass can count matches against earlier totals. It is the wrong tool when:

- **Values change between questions.** A point update invalidates O(n) entries. Use a **Fenwick tree** or **segment tree**: O(log n) per update and per query.
- **All values are positive and you want the shortest or longest subarray meeting a threshold.** A sliding window does it in O(n) time with O(1) space, because positives make the window sum monotone. **The boundary sentence:** all-positive plus shortest/longest subarray meeting a threshold means window. Negatives present, or "count exactly K", means prefix + hash map. Say which, and why.
- **The operation has no inverse** (max, min, GCD). A prefix array answers only ranges that start at 0; use a sparse table, a segment tree, or a monotonic deque.
- **There is only one question.** Building a prefix array to answer it once is just a loop with extra memory.

<Reveal q="All values are strictly positive and you must COUNT the subarrays summing to exactly k. Window or hash map?">

Both are correct. With **strictly positive** values each end has at most one matching start, and the window finds it in O(n) time and O(1) space. The map also works in O(n) expected time but costs O(n) space. The moment zeros or negatives appear, the window's shrink rule loses its proof and only the map remains. Name the constraint that decides it.

</Reveal>

**Longest exact subarray:** a map from running total to its **first** index, seeded `0 → -1`. At index `j`, if `running - k` is in the map, the subarray has length `j - first`. Record a total only if it is absent. Chapter 4's lookup plus Chapter 5's first-index rule.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Start with... | The invariant |
|---|---|---|
| Many range-sum questions, fixed data | `prefix` of n + 1 entries; `prefix[r + 1] - prefix[l]` | `prefix[i]` is the total of everything before i |
| Left side equals right side | Total once; `right = total - left - nums[i]` | `leftSum` covers exactly `0..i - 1` when you compare |
| Product of everything except i, no division | Left products in the answer, then a running suffix | `suffix` holds the product of everything after i |
| Count subarrays summing to exactly K (negatives possible) | Running total + count map seeded `0 → 1`; count, then record | The map holds every earlier prefix, with multiplicity |
| A subarray of length ≥ 2 summing to a multiple of K | Remainder → first index, seeded `0 → -1`; never overwrite | Each remainder maps to its earliest index |
| Longest subarray with equal 0s and 1s | 0 → -1, balance → first index | Equal balances bracket a balanced subarray |
| Count subarrays divisible by K, negatives present | `int[k]` counts of `floorMod` remainders, seeded at 0 | Every remainder lies in `0..k - 1` |
| Count subarrays with exactly K odd numbers | 1 for odd, 0 for even; Chapter 4 on the counts | The map holds earlier odd-counts |
| Range XOR questions | XOR prefix; `px[r + 1] ^ px[l]` | XOR is its own inverse |
| Rectangle sums in a fixed table | (rows + 1) × (cols + 1) table; add back the corner | `P[r][c]` is the block above and left of `(r, c)` |
| Many range updates, one read | Difference array: +v at start, -v just after the end; one sweep | The sweep's running total is the true value |

A prefix array does **not** automatically mean O(1) space. The map costs O(n); the 2-D table costs O(rows × cols); only Find Pivot Index and Product Except Self (beyond its output) run in O(1) extra space. Count every structure you build.

### Five bugs to watch for

1. **The missing seed.** Without `seen.put(0, 1)`, or `0 → -1` when you measure lengths, subarrays that start at index 0 vanish silently.
2. **Recording before counting.** The current total matches itself, and with `k = 0` every position counts a phantom empty subarray.
3. **A prefix array of length n.** Ranges from index 0 need special cases and off-by-ones creep in everywhere. Always n + 1, with a zero first; `prefix[r] - prefix[l]` drops the last value.
4. **Int overflow.** Long arrays of big values overflow a running `int` total. When the bounds do not promise otherwise, use `long`.
5. **Java's negative remainder.** `-1 % 5 == -1`. Fold with `Math.floorMod` or `((x % k) + k) % k` before using a remainder as a key or an index.

**How to recognise it.** Many questions about sums (or XOR, counts) over contiguous ranges of fixed data; "count subarrays with sum exactly K"; "left of i versus right of i"; many range updates read once.

**Core algorithm.**

1. Build `prefix` of n + 1 entries with `prefix[0] = 0`.
2. A range is `prefix[r + 1] - prefix[l]`.
3. To count subarrays with sum k: keep a running total and a map of earlier totals seeded `0 → 1`. For each value, add, count `map[running - k]`, then record.
4. For "longest", store the **first** index of each total or remainder, seeded `0 → -1`.

**Common mistakes.** Missing seed; recording before counting; prefix length n instead of n + 1; Java's negative `%`; `int` overflow; using a window when negatives are present.

**Complexity.** Build O(n) time and O(n) space. Range query O(1). The one-pass hash map count is O(n) expected time and O(n) space.
