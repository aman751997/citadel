<h2 id="prologue">Prologue · What a stack problem looks like</h2>

A **stack** is a pile you touch only at the top. `push` adds an item on top, `pop` removes the top item, and `peek` looks at it without removing it. All three are O(1). Nothing below the top can be reached until everything above it is gone. That is **last in, first out**.

It sounds like a restriction. It is the whole point. When the answer always involves **the most recent unfinished thing**, a stack hands you exactly that thing and keeps everything else out of the way.

### Two triggers

1. **Nesting, matching, undo.** Brackets, expressions, "the most recently opened thing must close first", undo history. Last-in-first-out is the problem statement. This is Part One.
2. **The nearest greater or smaller element.** For each item, find the nearest item on one side that beats it. In disguise this is the next warmer day, the first taller bar, a car catching the car ahead, the widest rectangle under some bars, or a stock price's span. This is Part Two, the **monotonic stack**, and it is what interviews test most.

### The brute force, and why a stack beats it

For "next greater element", the obvious approach scans forward from every item. On a list that only gets smaller, that is n(n − 1)/2 comparisons: **O(n²)**.

The stack version is **O(n)**. Every item is pushed once and popped at most once, so the total work is at most 2n operations, however the loops are nested.

### Three questions before every push or pop

1. **What is still waiting?** An open bracket with no closer yet. A day with no warmer day yet. And what shape do the waiting items form on the stack?
2. **Why is this pop safe?** Which waiting item was just answered, and why will it never be needed again?
3. **When do I stop popping, and what happens to the leftovers?** Stop at the first item the arrival cannot answer. Leftovers get a default answer, or a sentinel flushes them out.

### Why stopping early is safe

Picture the stack just before a value of 170 arrives. Reading from the bottom to the top, the waiting values never increase: 185, 150, 140. The arrival pops 140, then 150, then stops at 185. Everything deeper than 185 is at least as large as 185, so if 170 cannot beat 185 it cannot beat them either.

### Java: use ArrayDeque

Use `ArrayDeque` as your stack, not the legacy `Stack` class. `Stack` extends `Vector`, synchronizes every call, and its own Javadoc recommends `Deque` instead. Saying so in an interview costs nothing.

```java fragment
Deque<Integer> stack = new ArrayDeque<>();
stack.push(4);        // top is 4
stack.push(9);        // top is 9
stack.peek();         // 9, still there
stack.pop();          // 9, removed
stack.isEmpty();      // false: 4 is left
```

Two behaviours to know by heart. `pop()` on an empty `ArrayDeque` throws `NoSuchElementException`. `peek()` returns `null`, which throws a `NullPointerException` if you unbox it into an `int`. Printing an `ArrayDeque` lists the **top first**.

<h2 id="valid-parentheses">Chapter 1 · Valid Parentheses</h2>

### Problem

A string contains only `(`, `)`, `[`, `]`, `{`, `}`. Return `true` if every bracket is closed by the same kind of bracket, in the correct order.

`"([]){}"` is valid. `"([)]"` is not. `"(("` is not.

### How to recognise it

- Pairs of symbols that must nest properly.
- "The most recently opened thing must close first."
- Any input where a closer has to be checked against **the latest unmatched opener**.

### Brute force

Repeatedly delete adjacent pairs `()`, `[]`, `{}` from the string until nothing changes. The string is valid if it ends up empty. Each pass is O(n) and there can be n/2 passes: **O(n²)**.

### Intuition

At any moment, the only bracket you may close is **the one opened most recently that is still open**. That is the top of a stack. Push on open. On close, the top must be its partner.

A small trick makes the check shorter: **push the closer you expect**, not the opener you saw. Then checking a closer is one comparison against `pop()`.

<Figure caption="Reading ( [ ) ]. Two cases are open, and the top expects ]. The arriving ) would close the outer bracket while the inner one is still open, so the pairs cross. Reject.">

  <ArrayStrip name="expected closers · bottom → top" values={[')', ']']} indices={false} pointers={[{ at: 1, label: 'TOP', tone: 'blue' }]} tones={{ 1: 'blue' }} />
</Figure>

### Dry run

Turn on Predict and guess each closer's outcome before it is shown.

<DryRun title="Valid Parentheses" frames={parenFrames('{[()]}(]')} predict />

<DryRun title="Valid Parentheses: crossed pairs" frames={parenFrames('([)]')} />

### Algorithm

1. Create an empty stack.
2. For each character: if it is an opener, push the closer it expects.
3. If it is a closer: if the stack is empty, or the popped value is not this character, return `false`.
4. After the loop, return `true` only if the stack is empty.

### Java solution

Work through the hints first, then reveal the code.

<HintLadder hints={hints.parentheses}>

```java id=isValid
public boolean isValid(String s) {
    Deque<Character> st = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        switch (c) {
            case '(' -> st.push(')');
            case '[' -> st.push(']');
            case '{' -> st.push('}');
            default -> { if (st.isEmpty() || st.pop() != c) return false; }
        }
    }
    return st.isEmpty();          // leftovers = unclosed opens
}
```

`st.pop() != c` compares a `Character` with a `char`, so Java unboxes and compares the characters themselves. An odd-length string can return `false` at once; that is a cheap early exit, not a fix.

</HintLadder>

### Why it works

- **What is settled:** the stack lists every opener still waiting for its closer, oldest at the bottom, innermost on top.
- **Why each move is safe:** a correct closer must close the innermost open bracket. If it closes anything else, two pairs cross. So each closer is compared with the one bracket it is allowed to close.
- **When we stop:** at the end of the string. Anything left on the stack is an opener that never closed.

### Complexity

- **Time O(n):** each character is pushed or popped once.
- **Space O(n):** the stack holds every opener in the worst case, such as `"(((((("`.

### Edge cases and mistakes

- **Closing on an empty stack:** `")("` must return `false` before `pop()` throws.
- **Forgetting the end check:** `"(("` never fails during the loop. Returning `true` there is wrong, because leftovers are unclosed openers.
- The empty string is valid.

<Reveal q="With only one kind of bracket, ( and ), do you still need a stack?">

No. A counter is enough: add 1 on `(`, subtract 1 on `)`, fail if the counter ever goes below 0, and require 0 at the end. With one kind, all openers are the same, so you only need to know *how many* are open, not *which*.

With three kinds, you need to know which kind is innermost. Three separate counters cannot do that: `([)]` brings every counter back to 0 and would be accepted.

</Reveal>

**Variations to try:** return the index of the first bad character; return the minimum number of insertions to make the string valid; allow `*` as a wildcard.

<h2 id="min-stack">Chapter 2 · Min Stack</h2>

### Problem

Design a stack with `push`, `pop`, `top` and `getMin`, **all in O(1)**.

`push 5, push 3, push 7, push 2, getMin` gives 2. After `pop`, `getMin` gives 3.

### How to recognise it

- "Design a data structure" with a stack and one extra query (min, max, sum) in O(1).
- The extra answer has to survive `pop`.

### Brute force

Store the values and scan the whole stack on every `getMin`. That is **O(n) per query**.

A single `min` variable is O(1) but breaks on pop: after `push 5, push 3, pop` it still says 3, and nothing tells you the minimum went back to 5.

### Intuition

The minimum from *before* the last push has to be remembered somewhere, and it has to come back exactly when that push is undone.

So keep a second stack, `mins`, the same height as `values`. Each level of `mins` records **the minimum of everything at or below that level**. Push both together, pop both together.

<Figure caption="After push 5, 3, 7, 2, each mins level is the minimum at or below it. Pop the 2 and the new top of mins says 3, which was written when 7 was the top and is still true.">
  <ArrayStrip name="values" values={[5, 3, 7, 2]} pointers={[{ at: 3, label: 'TOP' }]} tones={{ 3: 'hot' }} />
  <ArrayStrip name="mins" values={[5, 3, 3, 2]} pointers={[{ at: 3, label: 'getMin()', tone: 'green' }]} tones={{ 3: 'done' }} />
</Figure>

### Dry run

<DryRun title="Min Stack" frames={minStackFrames([['push', 5], ['push', 3], ['push', 7], ['push', 2], ['getMin'], ['pop'], ['pop'], ['getMin'], ['pop'], ['getMin']])} predict />

### Algorithm

1. Keep two stacks: `values` and `mins`.
2. `push(x)`: push `x` to `values`. Push `min(x, mins.peek())` to `mins` (just `x` if `mins` is empty).
3. `pop()`: pop both stacks.
4. `top()`: peek `values`. `getMin()`: peek `mins`.

### Java solution

<HintLadder hints={hints.minStack}>

```java id=minStack
class MinStack {
    private final Deque<Integer> values = new ArrayDeque<>();
    private final Deque<Integer> mins = new ArrayDeque<>();   // mins.peek() = minimum at or below the top

    public void push(int val) {
        values.push(val);
        mins.push(mins.isEmpty() ? val : Math.min(val, mins.peek()));
    }
    public void pop() {
        values.pop();
        mins.pop();
    }
    public int top() { return values.peek(); }
    public int getMin() { return mins.peek(); }
}
```

The problem promises that `pop`, `top` and `getMin` are only called on a non-empty stack.

</HintLadder>

### Why it works

- **What is settled:** for every level k, `mins[k]` is the minimum of `values[0..k]`.
- **Why it stays true:** a level's value is computed from the items at or below it, and those never change while that level exists. Only the top can change. So when a level becomes the top again, its stored minimum is still exactly right.
- **When we stop:** there is no loop. Every operation touches only the tops.

The general lesson: **give each stack level its own extra information** instead of recomputing it. The same idea gives you a max stack, a stack that knows its sum, or Stock Span's (price, span) pairs later in this chapter.

### Complexity

- **Time O(1)** per operation: only the tops are touched.
- **Space O(n):** `mins` is as tall as `values`.

### Edge cases and mistakes

- Duplicates of the minimum: `push 2, push 2, pop, getMin` must still say 2.
- Reading `getMin` on an empty stack is outside the problem's promise; do not add code for it.
- The lean variant below has a Java trap that small tests never catch.

<Reveal q="Can you save space by pushing onto mins only when a new record arrives?">

Yes, and it is a favourite follow-up. Push onto `mins` only when the new value is **less than or equal to** the current minimum. Pop from `mins` only when the value leaving `values` equals the current minimum.

```java id=minStackLean
class MinStackLean {
    private final Deque<Integer> values = new ArrayDeque<>();
    private final Deque<Integer> mins = new ArrayDeque<>();   // only record-setting values

    public void push(int val) {
        values.push(val);
        if (mins.isEmpty() || val <= mins.peek()) mins.push(val);   // <=, not <
    }
    public void pop() {
        int removed = values.pop();             // unbox first: compare ints, not Integer objects
        if (removed == mins.peek()) mins.pop();
    }
    public int top() { return values.peek(); }
    public int getMin() { return mins.peek(); }
}
```

Why `<=`: after `push 2, push 2`, a strict `<` records only one 2. The first `pop` removes that record while another 2 is still on the stack, and `getMin()` finds `mins` empty. The worst case is still O(n) extra space (a stack that only ever gets smaller), but typical inputs use much less.

</Reveal>

**The classic bug.** In the lean version, this line compares two `Integer` objects.

```java fragment
if (values.pop() == mins.peek()) mins.pop();   // compares two Integer objects
```

`==` on two `Integer` objects compares references. Java caches the boxes for -128 to 127, so `push 10, push 9, pop` works by luck. With `push 1000, push 999, pop`, the two 999s are different objects, the record is never popped, and `getMin()` answers 999 though only 1000 remains. Unbox to `int` first, as above, or use `equals`.

<h2 id="reverse-polish">Chapter 3 · Evaluate Reverse Polish Notation</h2>

### Problem

Evaluate an expression in postfix form. Tokens are integers and the operators `+ - * /`. Division truncates toward zero. The expression is valid.

`["4","13","5","/","+"]` is 4 + 13 / 5, which is 6.

### How to recognise it

- Expressions with the operator **after** its operands, and no brackets.
- "Evaluate", "calculate", where each operation consumes the latest results.

### Brute force

Repeatedly scan for the first operator that has two numbers directly before it, replace those three tokens with the result, and rescan. Each replacement shifts the list and each scan is O(n): **O(n²)**.

### Intuition

In postfix, every operator comes **after** its operands: `3 + 4` is written `3 4 +`. No brackets are needed, because the order of the tokens already is the order of the work.

An operator's operands are **the two most recent results**. Push numbers. When an operator arrives, pop two, combine, and push the answer back. One value is left at the end.

<Figure caption="The tree for 4 + 13 / 5. Read it in post-order (left subtree, right subtree, then the operator) and you get exactly the tokens: 4 13 5 / +. The right subtree finishes last, so its value is on top when the operator arrives.">
  <Mermaid code={`flowchart TD\n  P["+"] --> A["4"]\n  P --> D["/"]\n  D --> B["13"]\n  D --> C["5"]`} />
</Figure>

The one trap is **operand order**. The first pop is the value written *last*, which is the **right-hand operand**. For `5 3 -`, the first pop is 3 and the second is 5, so compute 5 − 3.

### Dry run

<DryRun title="Evaluate Reverse Polish Notation" frames={rpnFrames(['4', '13', '5', '/', '+'])} predict />

<DryRun title="A longer expression with a negative number" frames={rpnFrames(['10', '6', '9', '3', '+', '-11', '*', '/', '*', '17', '+', '5', '+'])} />

### Algorithm

1. Create an empty stack of ints.
2. For each token: if it is one of `+ - * /`, pop `right`, then pop `left`, and push `left op right`.
3. Otherwise parse the token as an integer and push it.
4. After the loop, the single value on the stack is the answer.

### Java solution

<HintLadder hints={hints.rpn}>

```java id=evalRPN
public int evalRPN(String[] tokens) {
    Deque<Integer> stack = new ArrayDeque<>();
    for (String token : tokens) {
        switch (token) {
            case "+", "-", "*", "/" -> {
                int right = stack.pop();   // popped first = written second
                int left = stack.pop();
                stack.push(switch (token) {
                    case "+" -> left + right;
                    case "-" -> left - right;
                    case "*" -> left * right;
                    default -> left / right;   // Java truncates toward zero, as required
                });
            }
            default -> stack.push(Integer.parseInt(token));
        }
    }
    return stack.pop();
}
```

The problem guarantees a valid expression, no division by zero, and results that fit in 32 bits.

</HintLadder>

### Why it works

- **What is settled:** the stack holds the values of the complete sub-expressions read so far, in order, none of them used yet.
- **Why each move is safe:** an operator's right operand is the expression that finished most recently, so its value is on top. The left operand finished just before it, so its value is directly underneath. Replacing two values with one keeps that true for whatever comes next.
- **When we stop:** when the tokens run out. A valid expression leaves exactly one value.

### Complexity

- **Time O(n):** each token is handled once, with O(1) stack work.
- **Space O(n):** a run of numbers before the first operator all sit on the stack.

### Edge cases and mistakes

- **Operand order.** This one-liner is the classic bug.

```java fragment
case "-" -> stack.push(stack.pop() - stack.pop());   // first pop is the RIGHT operand
```

It computes right − left, so `5 3 -` gives −2. It passes every test that uses only `+` and `*`, which is why it survives until the interview.

- **Negative numbers.** `-11` is a number that starts with `-`. Compare the **whole token** with the four operators and treat anything else as a number.
- **Division.** Java's `int` division already truncates toward zero.

<Reveal q="Why not test token.charAt(0) to tell numbers from operators?">

Because `-11` is a number that starts with `-`. Compare the **whole token** with `"+"`, `"-"`, `"*"` and `"/"`, and treat anything else as a number.

</Reveal>

<h2 id="daily-temperatures">Chapter 4 · Daily Temperatures</h2>

### Problem

For each day, return how many days you must wait for a warmer temperature. If there is none, return 0.

`[73, 74, 75, 71, 69, 72, 76, 73]` gives `[1, 1, 4, 2, 1, 1, 0, 0]`.

### How to recognise it

- "Next greater (or warmer, taller, larger) element to the right", answered as a value or a **distance**.
- Each item wants the **nearest** item that beats it, not the best one overall.
- The brute force has a nested loop that scans forward from each position.

### Brute force

For each day, read forward until something warmer appears. On a month that only gets colder, every day reads every later day: n(n − 1)/2 steps, **O(n²)**. The same nights are read again and again.

### Intuition

Turn the question around. Treat each day as a visitor that arrives and waits.

> A day sits on the stack because it is **still waiting for its answer**. When today arrives, it answers every waiting day it beats. Pop them and record `today - day`. Then today waits too.

Today can only answer days that are **colder** than it. Which waiting days are those? Here is the part worth understanding rather than memorising.

**The invariant.** Read the stack from bottom to top: temperatures **never increase**. Each waiting day is at most as warm as the day beneath it. Equal temperatures can sit together, because 70° does not answer 70°.

It holds because today pops every waiting day colder than itself before it is pushed. Whatever is left directly underneath it is at least as warm as today.

**Why stopping early is safe.** If today cannot beat the top, it cannot beat anyone below the top, because they are all at least as warm.

**Which way does the stack slope?** Do not memorise "decreasing stack for next greater". Work it out from who gets answered. A warmer arrival pops colder days, so the days left underneath are warmer: temperatures fall (never rise) as you go up. For the next *smaller* element, a colder arrival pops warmer values, so the values rise as you go up.

**Push indexes, not temperatures.** The answer is a distance, `today - day`. You can always read a temperature from an index (`temperatures[day]`), but never the index from a temperature.

### Dry run

Watch the stack: days pop only when today is strictly warmer, and the loop stops at the first day it cannot beat.

<DryRun title="Daily Temperatures" frames={tempsFrames([73, 74, 75, 71, 69, 72, 76, 73])} predict />

### Algorithm

1. Create `answer` filled with 0, and an empty stack of indexes.
2. For each day `today` from left to right:
3. While the stack is not empty and `temperatures[today]` is strictly greater than the temperature at the top: pop it as `answered` and set `answer[answered] = today - answered`.
4. Push `today`.
5. Days still on the stack keep 0.

### Java solution

<HintLadder hints={hints.temps}>

```java id=dailyTemperatures
public int[] dailyTemperatures(int[] temperatures) {
    int n = temperatures.length;
    int[] answer = new int[n];                    // days nobody answers stay 0
    Deque<Integer> waiting = new ArrayDeque<>();  // indexes; temperatures never increase bottom to top
    for (int today = 0; today < n; today++) {
        while (!waiting.isEmpty() && temperatures[today] > temperatures[waiting.peek()]) {
            int answered = waiting.pop();         // today answers this day
            answer[answered] = today - answered;
        }
        waiting.push(today);                      // today now waits
    }
    return answer;
}
```

</HintLadder>

### Why it works

- **What is settled:** a popped day has its final answer. A day still on the stack has not met a warmer day yet.
- **Why each pop is safe:** today is warmer than that day, and no earlier arrival was warmer (otherwise it would already have been popped). So today is the *first* warmer day.
- **When we stop:** when the top is at least as warm as today. Everything under it is at least as warm too, so nobody else can be answered. At the end, the leftovers keep 0.

### Complexity

- **Time O(n).** The interviewer will point at the `while` inside the `for` and ask, "Isn't that O(n²)?" Every index is pushed exactly once and popped at most once, so all the `while` loops *together* pop at most n times. A single day can pop many, but not every day can.
- **Space O(n):** a month that only cools keeps every day waiting.

### Edge cases and mistakes

- **`>=` instead of `>`.** Equal days then answer each other. On `[70, 70, 71]`, day 1 would "answer" day 0 with 1, though 70° is not warmer than 70°. The correct answer is `[2, 1, 0]`.
- **Pushing temperatures instead of indexes.** That leaves no way to compute the distance.
- A strictly decreasing input leaves every day on the stack: all zeros.

<Reveal q="Now you want the PREVIOUS warmer day for each day instead. What changes?">

You look left instead of right, and the answer appears at push time instead of pop time. When today arrives, pop every waiting day that is **no warmer** than today (`temperatures[top] <= temperatures[today]`). Whatever is left on top is the nearest earlier day that is strictly warmer, or nothing. Then push today.

Popping those days is safe because today is at least as warm and closer, so no later day will ever need them. Stock Span (a side quest below) is this exact shape.

</Reveal>

<h2 id="circular-next-greater">Chapter 5 · Next Greater Element II</h2>

### Problem

The array is **circular**: after the last element comes the first. For each element, return the first strictly greater value you meet going forward, wrapping around. Return −1 if there is none.

`[1, 2, 1]` gives `[2, -1, 2]`.

### How to recognise it

- Next greater element, plus a ring: "circular array", "wraps around".
- The last elements need to look at the front.

### Brute force

For each index, scan the next n − 1 positions with `(i + k) % n`. That is n × (n − 1): **O(n²)**.

### Intuition

In a circular array, the elements after index `i` are `i+1, …, n-1`, and then `0, …, i-1`. A single pass leaves the last elements without a look at the front.

So sweep **twice**: `i` runs from 0 to 2n − 1, and you read `nums[i % n]`. Every waiting index gets to see all of its circular successors.

Push only during the first lap (`i < n`). In the second lap, **answer but do not push**: every index has already waited once, and nobody new needs to.

<Figure caption="The doubled sweep over [1, 2, 1]. In lap one, 2 answers index 0. Index 1 (value 2) and index 2 (value 1) are left waiting. In lap two, i = 4 reads nums[1] = 2, which answers index 2. Nothing is strictly greater than 2, so index 1 keeps −1. Final: [2, −1, 2].">
  <ArrayStrip name="i % n reads" values={[1, 2, 1, 1, 2, 1]} pointers={[{ at: 4, label: 'answers index 2' }]} tones={{ 3: 'ghost', 4: 'ghost', 5: 'ghost' }} regions={[{ from: 0, to: 2, label: 'lap one: answer and push', tone: 'gold' }, { from: 3, to: 5, label: 'lap two: answer only', tone: 'blue' }]} />
</Figure>

### Dry run

<DryRun title="Next Greater Element II" frames={circularFrames([1, 2, 1])} predict />

<DryRun title="A longer ring" frames={circularFrames([3, 1, 2, 4, 2])} />

### Algorithm

1. Fill `answer` with −1. Create an empty stack of indexes.
2. For `i` from 0 to 2n − 1, let `value = nums[i % n]`.
3. While the stack is not empty and `value` is strictly greater than the value at the top: pop it and set its answer to `value`.
4. If `i < n`, push `i`. In the second lap, push nothing.

### Java solution

<HintLadder hints={hints.circular}>

```java id=nextGreaterElements
public int[] nextGreaterElements(int[] nums) {
    int n = nums.length;
    int[] answer = new int[n];
    Arrays.fill(answer, -1);                       // leftovers: nothing greater anywhere
    Deque<Integer> waiting = new ArrayDeque<>();   // indexes still waiting
    for (int i = 0; i < 2 * n; i++) {
        int value = nums[i % n];
        while (!waiting.isEmpty() && value > nums[waiting.peek()]) {
            answer[waiting.pop()] = value;
        }
        if (i < n) waiting.push(i);                // the second lap only answers
    }
    return answer;
}
```

No copy of the array is needed; `i % n` does the wrapping.

</HintLadder>

### Why it works

- **What is settled:** the waiting values never increase from bottom to top, and every index on the stack has not yet met a strictly greater value going clockwise.
- **Why two laps are enough:** an element's circular next greater, if it exists, is within the next n − 1 positions after it. Index `i` is pushed at step `i`, and the sweep keeps reading until step 2n − 1, which is at least `i + n - 1`. The pop logic is the same as in Chapter 4, so the first greater value it meets is the one that answers it.
- **When we stop:** after 2n reads. Indexes still waiting hold a maximum value, so −1 is correct.

### Complexity

- **Time O(n):** 2n reads, n pushes, at most n pops.
- **Space O(n):** the stack and the answer.

### Edge cases and mistakes

- **Stopping after one lap.** `[1, 2, 1]` would give `[2, -1, -1]`. The correct answer is `[2, -1, 2]`.
- **`>=` instead of `>`.** Equal values answer each other: `[7, 7]` must stay `[-1, -1]`.
- A single element is its own only candidate, so the answer is `[-1]`.

<Reveal q="Many solutions push in both laps. Is that wrong?">

It is wasted work, not a wrong answer. A second-lap copy of index `j` can only be answered by a value from `j + 1` to `n - 1`, and if such a value exists, the first lap already found that same first greater value. If it does not exist there, the copy is never popped and changes nothing. Pushing only in the first lap keeps each index waiting once, which makes the "pushed once, popped at most once" argument easy to say.

</Reveal>

<h2 id="car-fleet">Chapter 6 · Car Fleet</h2>

### Problem

Cars drive on a one-lane road toward `target`. Car `i` starts at `position[i]` with `speed[i]`. A car cannot pass: a faster car that catches a slower one drives behind it at the slower speed. Cars that reach the target together form a fleet. Count the fleets.

`target = 12`, `position = [10, 8, 0, 5, 3]`, `speed = [2, 4, 1, 1, 3]` gives 3.

### How to recognise it

- Objects move toward one end, cannot overtake, and merge when one catches another.
- The answer counts groups, not individuals.
- Sorting by position makes "who is directly ahead" well defined.

### Brute force

Simulate the road hour by hour (or event by event), merging cars as they catch up. Each event needs a scan to find the next catch: **O(n²)** at best, and fiddly with fractional times.

### Intuition

The car closest to the target cannot be slowed: nobody is in front of it. That is the first thing that is settled. So **process cars from the front to the back**, and give each one its **solo arrival time**, `(target - position) / speed`: when it would arrive if the road were empty.

A car can never arrive before the car directly in front of it. So its real arrival time is **the larger of its own solo time and the arrival time of the fleet directly ahead**:

- **Solo time ≤ fleet ahead:** it catches up at or before the target and joins that fleet. Arriving together exactly at the target counts as joining.
- **Solo time > fleet ahead:** it never catches them. It leads a **new fleet**, and that fleet is now "the fleet directly ahead" for every car behind it.

That is stack thinking: a stack of fleet arrival times, with the fleet directly ahead on top. A slower car pushes a new fleet. A faster car is absorbed and pushes nothing. The answer is the stack's size.

<Figure caption="Front to back, with each car's solo time. 8 (1 h) catches 10 (1 h) exactly at the target. 3 (3 h) catches 5 (7 h). 0 (12 h) is slower than everything ahead and arrives alone. That makes three fleets.">
  <ArrayStrip name="front → back" values={['p10 · 1h', 'p8 · 1h', 'p5 · 7h', 'p3 · 3h', 'p0 · 12h']} indices={false} tones={{ 0: 'hot', 2: 'hot', 4: 'hot' }} regions={[{ from: 0, to: 1, label: 'fleet 1 · 1h', tone: 'green' }, { from: 2, to: 3, label: 'fleet 2 · 7h', tone: 'blue' }, { from: 4, to: 4, label: 'fleet 3 · 12h', tone: 'purple' }]} />
</Figure>

### Dry run

<DryRun title="Car Fleet" frames={fleetFrames(12, [10, 8, 0, 5, 3], [2, 4, 1, 1, 3])} predict />

### Algorithm

1. Sort the car indexes by position, closest to the target first.
2. For each car, compute `time = (target - position) / speed`.
3. If the stack is empty or `time` is strictly greater than the top, push it: a new fleet.
4. Otherwise the car joins the fleet ahead: push nothing.
5. Return the stack's size.

### Java solution

<HintLadder hints={hints.fleet}>

```java id=carFleet
public int carFleet(int target, int[] position, int[] speed) {
    int n = position.length;
    Integer[] order = new Integer[n];
    for (int i = 0; i < n; i++) order[i] = i;
    Arrays.sort(order, (a, b) -> Integer.compare(position[b], position[a]));   // closest to target first
    Deque<Double> fleets = new ArrayDeque<>();     // arrival times; the fleet directly ahead is on top
    for (int car : order) {
        double time = (double) (target - position[car]) / speed[car];
        if (fleets.isEmpty() || time > fleets.peek()) {
            fleets.push(time);                     // can't catch the fleet ahead: a new fleet
        }                                          // otherwise it catches up and joins
    }
    return fleets.size();
}
```

Positions are distinct in this problem, so the sort order is unambiguous. At this problem's bounds (up to 10⁶), `double` times are precise enough: equal fractions always give exactly the same `double`. If you would rather remove all doubt, compare `(long) (target - p1) * s2` with `(long) (target - p2) * s1` instead of dividing.

</HintLadder>

### Why it works

- **What is settled:** after each car, the stack holds the arrival time of every fleet formed so far, front fleet at the bottom. Times **strictly increase** from bottom to top, and the top is the fleet directly ahead of the next car.
- **Why each move is safe:** a car is only ever held up by cars in front of it, and those were all processed first. The fleet directly ahead sets the earliest this car can arrive.
- **When we stop:** after the last (rearmost) car.

### Complexity

- **Time O(n log n)** for the sort; the sweep itself is O(n).
- **Space O(n):** the sorted order and the stack.

### Edge cases and mistakes

- **`>=` instead of `>`.** Cars that arrive together would be split. With target 10, positions `[0, 5]` and speeds `[2, 1]`, both cars arrive at hour 5, which is one fleet, but the `>=` version counts two.
- **Sorting back to front.** From the back you do not yet know whether the car ahead will itself be held up.
- One car is always one fleet.

<Reveal q="You only ever read the top of that stack. Do you need the stack at all?">

No. Keep one variable: the arrival time of the fleet directly ahead.

```java id=carFleetCount
public int carFleet(int target, int[] position, int[] speed) {
    Integer[] order = new Integer[position.length];
    for (int i = 0; i < order.length; i++) order[i] = i;
    Arrays.sort(order, (a, b) -> Integer.compare(position[b], position[a]));
    int fleets = 0;
    double ahead = 0;                              // arrival time of the fleet directly ahead
    for (int car : order) {
        double time = (double) (target - position[car]) / speed[car];
        if (time > ahead) { fleets++; ahead = time; }
    }
    return fleets;
}
```

Every solo time is positive, so the first car always starts a fleet. Explaining it with the stack first and then collapsing it shows the interviewer that you know *why* one variable is enough.

</Reveal>

<h2 id="largest-rectangle">Chapter 7 · Largest Rectangle in Histogram</h2>

### Problem

Bars of width 1 stand side by side, with the given heights. Find the area of the largest rectangle that fits inside the histogram.

`[2, 1, 5, 6, 2, 3]` gives 10 (bars 5 and 6, height 5, width 2).

### How to recognise it

- A rectangle whose height is limited by its **shortest** bar.
- "Largest", "widest" or "most" over contiguous ranges, with a min inside.
- Needing the nearest smaller bar on **both** sides.

### Brute force

Try every left edge and every right edge, tracking the minimum height in between. That is n(n + 1)/2 pairs: **O(n²)**. For 10⁵ bars, that is five billion steps.

### Intuition

This is the hardest chapter of the lesson because of its **two seams**, not its idea. Take it slowly.

**The idea.** Every rectangle has a shortest bar, and that bar sets its height. So for each bar, imagine the widest rectangle in which *it* is the shortest bar. That rectangle stretches until the **nearest strictly shorter bar on each side**. The answer is the best of those n rectangles.

That is a "nearest smaller element" question in both directions at once, and one monotonic stack answers both:

- Keep bar indexes with **heights strictly increasing from bottom to top**.
- When a bar arrives that is **no taller** than the top (`heights[top] >= current`), the top's rectangle cannot stretch past it. **Finalize** the top: pop it.
- After the pop, the **new top** is the nearest strictly shorter bar on its left, and `i` is where it stops on the right. Width = `i - newTop - 1`.

<Figure caption="The best rectangle: bars 2 and 3, height 5, width 2, area 10. It is finalized when the height-2 bar arrives at i = 4: popping bar 3 (height 6), then bar 2 (height 5) leaves bar 1 (height 1) on top, so the width is 4 − 1 − 1 = 2.">
  <Bars heights={[2, 1, 5, 6, 2, 3]} rect={{ from: 2, to: 3, height: 5 }} pointers={[{ at: 1, label: 'new top' }, { at: 4, label: 'i', tone: 'blue' }]} />
</Figure>

**The two seams:**

1. **The sentinel flush.** Bars still on the stack when the input ends were never finalized. So run `i` one step past the end and treat that position as a bar of **height 0**. It is shorter than everything, so it finalizes everyone still waiting.
2. **The empty-stack width.** If the stack is empty after a pop, nothing shorter exists on the left, and the rectangle reaches all the way back to index 0. Width = `i`.

### Dry run

Each pop shows the popped bar, the new top, the width and the area. Predict the width before it is revealed.

<DryRun title="Largest Rectangle in Histogram" frames={histFrames([2, 1, 5, 6, 2, 3])} predict />

<DryRun title="Equal heights: [3, 3, 3]" frames={histFrames([3, 3, 3])} />

### Algorithm

1. Create an empty stack of indexes.
2. For `i` from 0 to `n` inclusive. At `i = n`, use height 0 (the sentinel).
3. While the stack is not empty and the top's height is `>=` the current height: pop it as `m`.
4. Its left edge is the new top, or −1 if the stack is empty. Width = `i - left - 1`. Area = `heights[m] * width`. Update the best.
5. Push `i`.

### Java solution

<HintLadder hints={hints.histogram}>

```java id=largestRectangleArea
public int largestRectangleArea(int[] heights) {
    int n = heights.length, best = 0;
    Deque<Integer> stack = new ArrayDeque<>();     // indexes; heights strictly increase bottom to top
    for (int i = 0; i <= n; i++) {
        int current = (i == n) ? 0 : heights[i];   // the sentinel: height 0 flushes the stack
        while (!stack.isEmpty() && heights[stack.peek()] >= current) {
            int height = heights[stack.pop()];
            int left = stack.isEmpty() ? -1 : stack.peek();   // nearest strictly shorter bar on the left
            int width = i - left - 1;              // left == -1 gives width i
            best = Math.max(best, height * width);
        }
        stack.push(i);                             // pushing the sentinel index is harmless
    }
    return best;
}
```

With heights up to 10⁴ and up to 10⁵ bars, the largest area is 10⁹, which fits in an `int`.

</HintLadder>

### Why it works

- **What is settled:** heights on the stack strictly increase from bottom to top, and every bar between two neighbouring stack entries is at least as tall as the upper one.
- **Why each pop is safe:** every popped rectangle is real. The bars between the new top and `i` are all at least as tall as the popped bar: the ones that once stood between them were popped by something no taller than themselves.
- **Why the best is found:** take the best rectangle, and let `b` be the *rightmost* of its shortest bars. When `b` is popped, the new top is the nearest strictly shorter bar on its left, and `i` is the nearest bar to its right that is no taller. Because `b` is the rightmost shortest bar, that is exactly the first strictly shorter one. So the pop measures the best rectangle at full width.
- **When we stop:** at the sentinel, which pops everything left.

### Complexity

- **Time O(n):** each index is pushed once and popped at most once.
- **Space O(n):** a strictly increasing histogram keeps every bar on the stack.

### Edge cases and mistakes

- **No sentinel.** `[2, 4]` returns 0, because both bars are pushed and never finalized. The answer is 4.
- **Width from the popped bar's own index.** `i - popped` forgets taller bars already popped on its left: at the sentinel, bar 4 (height 2) would get width 2 instead of 4.
- **Empty-stack width.** `i`, not `i - 1`.
- A single bar, all equal bars, and an increasing run are good tests.

<Reveal q="What do equal heights do here? Try [3, 3, 3].">

With `>=`, an equal arrival finalizes the earlier equal bar *too early*. Bar 0 is popped at i = 1 with width 1 (area 3), and bar 1 at i = 2 with width 2 (area 6). That is harmless, because the last bar of the run is finalized by the sentinel with the full width: bar 2 at i = 3, width 3, area 9.

Popping on strict `>` is also correct, the other way round. Equal bars stay stacked, and the *earliest* one of the run gets the full width when it is finally popped. Either works. Know which one you wrote, and why.

</Reveal>

<Reveal q="Is there a version that is easier to reason about, at the cost of a second pass?">

Yes. Compute `left[i]`, the nearest strictly shorter bar to the left, with one stack pass left to right (or −1). Compute `right[i]`, the nearest strictly shorter bar to the right, with a second pass right to left (or n). The answer is the maximum of `heights[i] × (right[i] - left[i] - 1)`. It is still O(n), with more code. Some people find it easier to prove under pressure; the one-pass version is what most interviewers expect to see.

</Reveal>

<h2 id="next-greater-map">Side quest 1 · Next Greater Element I</h2>

### Problem

You get two lists of distinct values. `nums1` is a subset of `nums2`. For each value in `nums1`, find the first larger value to its **right in nums2**, or −1.

`nums1 = [4, 1, 2]`, `nums2 = [1, 3, 4, 2]` gives `[-1, 3, -1]`.

### How to recognise it

- Next greater element, but only a **subset of values** is asked about.
- The reference list does not change between queries.

### Brute force

For each query, find the value in `nums2` and scan right. That is O(n · m).

### Intuition

The answers depend only on `nums2`. So compute the next greater value for *every* element of `nums2` in one waiting-stack pass, store it in a `HashMap` from value to answer, and answer each query with one lookup. Because the values are distinct, they can be both the stack entries and the map keys.

### Dry run

<DryRun title="Next Greater Element I" frames={nextGreaterMapFrames([4, 1, 2], [1, 3, 4, 2])} predict />

### Algorithm

1. Walk `nums2` left to right with a stack of values.
2. While the current value is greater than the top: pop it and store `top → current` in the map.
3. Push the current value.
4. For each value of `nums1`, answer `map.getOrDefault(value, -1)`.

### Java solution

<HintLadder hints={hints.nextGreaterMap}>

```java id=nextGreaterElement
public int[] nextGreaterElement(int[] nums1, int[] nums2) {
    Map<Integer, Integer> nextGreater = new HashMap<>();
    Deque<Integer> waiting = new ArrayDeque<>();   // values from nums2 (all distinct)
    for (int value : nums2) {
        while (!waiting.isEmpty() && value > waiting.peek()) {
            nextGreater.put(waiting.pop(), value);
        }
        waiting.push(value);
    }
    int[] answer = new int[nums1.length];
    for (int i = 0; i < nums1.length; i++) answer[i] = nextGreater.getOrDefault(nums1[i], -1);
    return answer;
}
```

</HintLadder>

### Why it works

The waiting-stack pass from Chapter 4 gives the first greater value to the right for every element of `nums2`. The map just remembers those answers by value, and `nums1` values are all in `nums2`. Anyone left on the stack has no greater value to the right, which is what the default −1 means.

### Complexity

**O(n + m) time, O(n) space**, compared with O(n · m) for scanning `nums2` once per query.

### Edge cases and mistakes

<Reveal q="Why does the word 'distinct' matter so much here?">

The map is keyed by value. If `nums2` had two 4s, they could have different next greater values, and one would overwrite the other. With duplicates, you would have to key by index, and the query would have to say *which* 4 it means.

</Reveal>

Also check a value with no greater element (−1) and a one-element `nums2`.

### Practice

**Transfer test:** the queries arrive one at a time, forever, and `nums2` never changes. Which part of the work do you do once, and what does each query cost?

<h2 id="stock-span">Side quest 2 · Online Stock Span</h2>

### Problem

Prices arrive one per day, and you cannot see the future. When a price arrives, report its **span**: the number of consecutive days, ending today and including today, whose price was **less than or equal to** today's.

Prices `100, 80, 60, 70, 60, 75, 85` give spans `1, 1, 1, 2, 1, 4, 6`.

### How to recognise it

- "Previous greater element" in a **stream**, where each answer is needed immediately.
- A count of consecutive earlier days that are no larger.

### Brute force

On each call, walk backwards while the price is at most today's. A list that only rises makes every call O(n), so n calls cost **O(n²)**.

### Intuition

This is the "previous greater" question from Chapter 4's reveal, live. A day that today beats (or ties) can never block anyone after today, because today is at least as high *and* closer. So pop it, and **absorb its span**, since its span already counted the days it had absorbed. The stack holds (price, span) pairs with prices **strictly decreasing** from bottom to top.

<Figure caption="Prices 100, 80, 60, 70, 60, 75, 85. When 75 arrives, it pops 60 (span 1) and 70 (span 2, which already covers the 60 before it). 1 + 1 + 2 = 4. It stops at 80.">
  <ArrayStrip name="price" values={[100, 80, 60, 70, 60, 75, 85]} pointers={[{ at: 5, label: 'TODAY' }]} tones={{ 2: 'out', 3: 'done', 4: 'done', 5: 'hot' }} regions={[{ from: 2, to: 5, label: 'span 4', tone: 'green' }]} />
  <ArrayStrip name="span" values={[1, 1, 1, 2, 1, 4, 6]} indices={false} tones={{ 5: 'hot' }} />
</Figure>

### Dry run

<DryRun title="Online Stock Span" frames={spanFrames([100, 80, 60, 70, 60, 75, 85])} predict />

### Algorithm

1. Keep a stack of `{price, span}` pairs.
2. On `next(price)`, start with `span = 1`.
3. While the top's price is `<= price`: pop it and add its span.
4. Push `{price, span}` and return `span`.

### Java solution

<HintLadder hints={hints.span}>

```java id=stockSpanner
class StockSpanner {
    private final Deque<int[]> stack = new ArrayDeque<>();   // {price, span}; prices strictly decrease bottom to top

    public int next(int price) {
        int span = 1;                                         // today counts
        while (!stack.isEmpty() && stack.peek()[0] <= price) {
            span += stack.pop()[1];                           // absorb everything that day had absorbed
        }
        stack.push(new int[]{price, span});
        return span;
    }
}
```

</HintLadder>

### Why it works

A popped day is at most today's price, so for any later day, today is a closer blocker that is at least as high. The popped day will never be the answer to anything again. Its span already covers the days it absorbed, so adding it counts them all exactly once. The first price strictly greater than today ends the span.

### Complexity

**Amortized O(1) per call**: each day is pushed once and popped at most once. A single call can take O(n), but only after n calls that each took O(1). **O(n) space.**

### Edge cases and mistakes

- Equal prices count (`<=`): `[70, 70]` gives spans `1, 2`.
- Forgetting to add the popped span (adding 1 per pop) is wrong: absorbed days would be dropped.
- A strictly falling list keeps every day on the stack, with all spans equal to 1.

### Practice

**Transfer test:** change the rule to "strictly less than today's price". What changes in the pop condition, and what does `[70, 70]` return now?

<h2 id="asteroids">Side quest 3 · Asteroid Collision</h2>

### Problem

Rocks sit on a line. The sign is the direction (positive moves right, negative moves left) and the absolute value is the size. All move at the same speed. When two meet, the smaller explodes; equal sizes both explode. Return what is left.

`[5, 10, -5]` gives `[5, 10]`. `[8, -8]` gives `[]`. `[10, 2, -5]` gives `[10]`.

### How to recognise it

- Neighbours interact, and the result of one interaction changes who meets next.
- Only some pairs can ever collide, and the survivors keep their order.

### Brute force

Repeatedly find the leftmost right-mover followed directly by a left-mover, resolve it, and rescan. Each scan is O(n) and there can be O(n) collisions: **O(n²)**.

### Intuition

The only rocks that can ever meet are a right-mover followed, somewhere later, by a left-mover. Keep a stack of **survivors so far**. A left-mover that arrives fights the top survivor, as long as the top moves right: the newest right-mover is the one it reaches first. If it wins, it keeps fighting the next survivor down. Here the arrival does not answer the waiting items. It **fights** them.

### Dry run

<DryRun title="Asteroid Collision" frames={asteroidFrames([5, 10, -5, -12, 3])} predict />

### Algorithm

1. For each rock, set `alive = true`.
2. While `alive`, the rock moves left, and the top survivor moves right: compare sizes.
3. Top smaller: pop it and keep fighting. Equal: pop it and the rock dies. Top bigger: the rock dies.
4. If the rock is still alive, push it.
5. The stack, bottom to top, is the answer (rightmost on top).

### Java solution

<HintLadder hints={hints.asteroids}>

```java id=asteroidCollision
public int[] asteroidCollision(int[] asteroids) {
    Deque<Integer> survivors = new ArrayDeque<>();
    for (int rock : asteroids) {
        boolean alive = true;
        while (alive && rock < 0 && !survivors.isEmpty() && survivors.peek() > 0) {
            int top = survivors.peek();
            if (top < -rock) survivors.pop();          // the right-mover explodes; keep fighting
            else {
                if (top == -rock) survivors.pop();     // equal sizes: both explode
                alive = false;                         // the incoming rock is gone
            }
        }
        if (alive) survivors.push(rock);
    }
    int[] result = new int[survivors.size()];
    for (int i = result.length - 1; i >= 0; i--) result[i] = survivors.pop();   // top is the rightmost
    return result;
}
```

</HintLadder>

### Why it works

Survivors on the stack never collide with each other: a left-mover is only ever pushed when nothing right-moving is on top. The newest right-mover is the only one a new left-mover can reach, so comparing with the top is enough, and a win means it meets the next one down.

### Complexity

**O(n) time, O(n) space.** Each rock is pushed at most once and popped at most once. The answer comes out of the stack top-first, so fill the result from the back.

### Edge cases and mistakes

<Reveal q="[−2, −1, 1, 2]: what collides?">

Nothing. The left-movers are already to the left of every right-mover, and they all move apart. A left-mover only fights when the top survivor moves **right**. The `peek() > 0` check is what keeps this input untouched.

</Reveal>

Also check equal sizes (`[8, -8]` leaves nothing) and a big left-mover that clears the whole stack and is then pushed.

### Practice

**Transfer test:** the rule changes so that on a tie, the left-mover survives and only the right-mover explodes. Which single line changes?

<h2 id="remove-k-digits">Side quest 4 · Remove K Digits</h2>

### Problem

You get a number as a string and must remove exactly `k` digits. The rest keep their order. Make the result as small as possible: no leading zeros, and `"0"` if nothing is left.

`"1432219"`, `k = 3` gives `"1219"`. `"10200"`, `k = 1` gives `"200"`. `"10"`, `k = 2` gives `"0"`.

### How to recognise it

- Delete exactly k items to make a sequence smallest (or largest).
- The leftmost positions matter most, and the order of what is kept is fixed.

### Brute force

Try every way to choose which k digits to delete: C(n, k) subsets, up to 2ⁿ. Far too slow for 10⁵ digits. A smaller greedy brute force deletes the first digit that is bigger than its right neighbour, k times: O(n · k).

### Intuition

The leftmost digits matter most. If a digit is followed by a **smaller** digit, deleting the bigger one makes the number smaller, so do that as early as possible. Keep a stack of kept digits that is **non-decreasing** from bottom to top. While removals remain and the arrival is smaller than the top, pop. If removals are left over at the end, take them off the tail: the kept digits never decrease, so the largest ones are at the end.

<Figure caption="1432219 with k = 3. 3 removes 4, 2 removes 3, and the second 1 removes a 2. Kept: 1 2 1 9, so the answer is 1219.">
  <ArrayStrip name="digits" values={[1, 4, 3, 2, 2, 1, 9]} tones={{ 1: 'out', 2: 'out', 4: 'out', 0: 'done', 3: 'done', 5: 'done', 6: 'done' }} />
</Figure>

### Dry run

<DryRun title="Remove K Digits" frames={removeKFrames('1432219', 3)} predict />

<DryRun title="Leading zeros: 10200, k = 1" frames={removeKFrames('10200', 1)} />

### Algorithm

1. Use a `StringBuilder` as the stack of kept digits.
2. For each digit: while `k > 0` and the top is greater than the digit, pop and decrement `k`.
3. Append the digit.
4. If `k` is still positive, remove `k` digits from the end.
5. Strip leading zeros, keeping at least one digit. If nothing is left, return `"0"`.

### Java solution

<HintLadder hints={hints.removeDigits}>

```java id=removeKdigits
public String removeKdigits(String num, int k) {
    StringBuilder kept = new StringBuilder();      // used as a stack: digits never decrease
    for (char digit : num.toCharArray()) {
        while (k > 0 && kept.length() > 0 && kept.charAt(kept.length() - 1) > digit) {
            kept.deleteCharAt(kept.length() - 1);  // a bigger digit before a smaller one: remove it
            k--;
        }
        kept.append(digit);
    }
    kept.setLength(kept.length() - k);             // removals still owed come off the tail
    int start = 0;
    while (start < kept.length() - 1 && kept.charAt(start) == '0') start++;   // keep at least one digit
    return kept.length() == 0 ? "0" : kept.substring(start);
}
```

</HintLadder>

### Why it works

At the first position where a digit is larger than the next one, deleting it gives a smaller number than any deletion further right, because the digit that replaces it is smaller and sits in a more significant place. The stack applies that rule repeatedly. If no such position remains the digits are non-decreasing, so the best removal is the last digit.

### Complexity

**O(n) time, O(n) space.** Each digit is pushed once and popped at most once. A `StringBuilder` works as a stack of characters and makes the final string cheap to build.

### Edge cases and mistakes

- `"12345"` with k = 2 never pops, so the tail trim is what gives `"123"`.
- `"10200"` with k = 1 gives `"0200"` before stripping, so the answer is `"200"`.
- `"10"` with k = 2 leaves nothing: return `"0"`.

### Practice

**Transfer test:** make the **largest** number instead. Which comparison flips, and where do leftover removals come from now?

<h2 id="rain-in-layers">Side quest 5 · Rain water, layer by layer</h2>

### Problem

Bars of width 1 arrive one at a time from the left, and you never know how many are still coming. Rain fills every dip. How much water is trapped once the last bar has arrived? (This is Trapping Rain Water, solved with a stack.)

`[0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]` gives 6.

### How to recognise it

- Water between walls, with bars arriving one at a time and no known right end.
- You met this in <a href={`${BASE}dsa/lessons/two-pointers/#catch-the-rain`}>the Two Pointers lesson</a>, with two pointers walking in from both ends. A stack is the answer when you must process left to right.

### Brute force

For each bar, scan left for the tallest wall and right for the tallest wall. Water above the bar is `min(left, right) - height`. That is **O(n²)**.

### Intuition

Fill the water in **horizontal layers** instead of columns. Keep bar indexes whose heights **never increase** from bottom to top. When a taller bar arrives, pop the top: it is a **floor**. The new top is the left wall, and the arriving bar is the right wall. That fills a layer `width = i - left - 1` wide and `min(left wall, right wall) - floor` deep. If the stack is empty after popping a floor, there is no left wall, and the water runs off.

<Figure caption="Heights 2, 0, 1, 0, 3: five units, filled in three layers. When 1 arrives it fills 1 unit above index 1. When 3 arrives it fills 1 unit above index 3, then a 3-wide layer from height 1 to 2 across indices 1 to 3. Per column, that is 2 + 1 + 2 = 5.">
  <Bars heights={[2, 0, 1, 0, 3]} water={[0, 2, 1, 2, 0]} />
</Figure>

### Dry run

<DryRun title="Trapping Rain Water with a stack" frames={rainFrames([2, 0, 1, 0, 3])} predict />

### Algorithm

1. Keep a stack of indexes whose heights never increase from bottom to top.
2. For each bar `i`: while it is taller than the top, pop the top as `floor`.
3. If the stack is empty, stop popping: no left wall.
4. Otherwise `left` is the new top. Add `(i - left - 1) * (min(height[left], height[i]) - height[floor])`.
5. Push `i`.

### Java solution

<HintLadder hints={hints.rainStack}>

```java id=trapStack
public int trap(int[] height) {
    Deque<Integer> stack = new ArrayDeque<>();      // indexes; heights never increase bottom to top
    int water = 0;
    for (int i = 0; i < height.length; i++) {
        while (!stack.isEmpty() && height[i] > height[stack.peek()]) {
            int floor = stack.pop();
            if (stack.isEmpty()) break;             // no left wall: water runs off
            int left = stack.peek();
            int width = i - left - 1;
            int depth = Math.min(height[left], height[i]) - height[floor];
            water += width * depth;                 // one horizontal layer
        }
        stack.push(i);
    }
    return water;
}
```

</HintLadder>

### Why it works

A popped floor is lower than the arriving bar and, by the stack's order, no higher than the bar beneath it. So the region between the new top and `i`, above the floor, is bounded by both walls and is filled up to the lower wall. Each layer is counted once, when its floor is popped.

### Complexity

**O(n) time, O(n) space.** The two-pointer version is O(1) space but needs both ends up front. This one works on a stream.

### Edge cases and mistakes

- Equal heights are safe: a floor next to an equal wall adds a layer of depth 0.
- An empty stack after popping the floor means there is no left wall: break, add nothing.
- A strictly increasing or decreasing input traps nothing.

### Practice

**Transfer test:** both versions get 6 on `[0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]`. Explain why one adds water **column by column** and the other **layer by layer**, yet they must agree.

<h2 id="subarray-minimums">Side quest 6 · Sum of Subarray Minimums</h2>

### Problem

Add up the minimum of **every** contiguous subarray, modulo 10⁹ + 7.

`[3, 1, 2, 4]` gives 17.

### How to recognise it

- A sum or count over **all** subarrays of a min or max.
- n(n + 1)/2 subarrays are too many to list, so you count by contribution instead.

### Brute force

For every start, extend the end while tracking the minimum: O(n²). Recomputing each minimum from scratch is O(n³).

### Intuition

Turn it around. For each element, ask **in how many subarrays is it the minimum?** An element at `m` is the minimum of every subarray that starts after its nearest smaller element on the left and ends before its nearest smaller element on the right. Its contribution is `arr[m] × (m - left) × (right - m)`.

**The duplicates trap.** With `[2, 2]`, the subarrays are `[2]`, `[2]` and `[2, 2]`, and the sum is 6. If both sides stop only at strictly smaller elements, both 2s claim `[2, 2]`, and you get 8. If both sides stop at smaller-or-equal elements, neither claims it, and you get 4. Fix: **strict on one side, non-strict on the other**, so every subarray is credited to exactly one of its minimums.

That is the histogram loop exactly: pop while `arr[top] >= current`. The new top is the nearest **strictly** smaller element on the left. `i` is the nearest smaller-**or-equal** element on the right. Each subarray is credited to its *rightmost* minimum.

<Figure caption="[3, 1, 2, 4]. The 1 can start at index 0 or 1 (2 choices) and end at index 1, 2 or 3 (3 choices), so it is the minimum of 2 × 3 = 6 subarrays. All four contributions: 3 + 6 + 4 + 4 = 17.">
  <ArrayStrip values={[3, 1, 2, 4]} pointers={[{ at: 1, label: 'MIN' }]} tones={{ 1: 'hot' }} regions={[{ from: 0, to: 3, label: '1 is the minimum of 6 subarrays', tone: 'gold' }]} />
</Figure>

### Dry run

<DryRun title="Sum of Subarray Minimums" frames={subMinsFrames([3, 1, 2, 4])} predict />

<DryRun title="Duplicates: [2, 2]" frames={subMinsFrames([2, 2])} />

### Algorithm

1. Keep a stack of indexes with strictly increasing values. Loop `i` from 0 to `n`, where `i == n` flushes everything.
2. While the top's value is `>=` the current (or `i == n`): pop it as `m`.
3. `left` is the new top, or −1. The right stop is `i`.
4. Add `arr[m] * (m - left) * (i - m)` to the total, modulo 10⁹ + 7.
5. Push `i`.

### Java solution

<HintLadder hints={hints.subarrayMins}>

```java id=sumSubarrayMins
public int sumSubarrayMins(int[] arr) {
    final long MOD = 1_000_000_007L;
    int n = arr.length;
    long total = 0;
    Deque<Integer> stack = new ArrayDeque<>();      // indexes; values strictly increase bottom to top
    for (int i = 0; i <= n; i++) {
        while (!stack.isEmpty() && (i == n || arr[stack.peek()] >= arr[i])) {
            int m = stack.pop();
            int left = stack.isEmpty() ? -1 : stack.peek();   // nearest strictly smaller on the left
            // i is the nearest smaller-or-equal on the right (or n)
            total = (total + (long) arr[m] * (m - left) * (i - m)) % MOD;
        }
        stack.push(i);
    }
    return (int) total;
}
```

</HintLadder>

### Why it works

A subarray's minimum is credited to its rightmost minimum element. For element `m`, a subarray qualifies when it starts after `left` (the nearest strictly smaller on the left, so no smaller element is inside and equal ones to the left are allowed) and ends before `i` (the nearest smaller-or-equal on the right, so no equal element to the right is inside). Each subarray is counted exactly once.

### Complexity

**O(n) time, O(n) space.** Here the sentinel is `i == n` itself, which flushes everything without inventing a height. The product of three factors can exceed `int`, so it is computed in `long`, with the modulus taken at every step.

### Edge cases and mistakes

- Strict on both sides double counts; non-strict on both sides loses subarrays (see `[2, 2]` above).
- `arr[m] * (m - left) * (i - m)` overflows `int`: cast the first factor to `long`.
- A single element contributes itself.

<h2 id="choose-the-tool">When a stack is not enough</h2>

Suppose the request is: "for each day, the warmest day within the next three". You reach for the stack. Then you notice the problem. On a stack, an item waits as long as it takes. Now a day that has fallen three days behind must *leave*, and it leaves from the **old end**, which a stack cannot reach.

A stack only removes from one end. When items must **expire from the old end** as well, as in a sliding window of size k, you need a **deque**. A monotonic deque pops beaten values from the back, exactly as you have been doing, and also drops expired indexes from the front. That is Sliding Window Maximum, and it belongs to the <a href={`${BASE}dsa/lessons/sliding-window/`}>Sliding Window lesson</a>.

Three more ways to tell a stack is not the right tool:

- **"The warmest day anywhere after this one"** asks for a maximum, not the *nearest* warmer day. One backward pass with a running maximum does it in O(n) with O(1) extra space.
- **"The k-th largest so far"** or **"the best k"** wants a ranking, not a nearest neighbour. Use a heap (the <a href={`${BASE}dsa/lessons/heaps/`}>Heaps lesson</a>).
- **Pairs anywhere in the array** that satisfy a sum or difference do not care about who is nearest. Use sorting with two pointers, or hashing.

<Reveal q="Isn't ArrayDeque already a deque? Why does the tool matter?">

The class can do both jobs. What matters is the **promise** your algorithm keeps. A stack algorithm only ever touches the newest end, and its correctness argument says nothing about expiring old items. Once old items must leave, you need a new invariant, such as "every index in the deque is inside the window and values decrease from front to back". You cannot borrow the stack proof for that.

</Reveal>

| Reversing or checking a list from the back | The visited nodes, popped in reverse | <a href={`${BASE}dsa/lessons/linked-lists/`}>Linked Lists</a> |
| Best k, running median | Not a stack: a heap ranks instead of remembering recency | <a href={`${BASE}dsa/lessons/heaps/`}>Heaps</a> |

**Recursion is a stack you did not write.** Every recursive DFS can be turned into a loop with an explicit `Deque`. Do that when the recursion depth could overflow the call stack (say, a path of 10⁵ nodes).

**A monotonic stack is not a heap.** Both give you a "best" item at the top, but a stack's top is the *most recent survivor*, not the global best. The top of a waiting stack is the *smallest* waiting value, which is exactly what the next arrival needs to compare against.

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Use your editor, keep this page closed, and write down what is waiting, the pop condition, and the stopping rule before you code.

1. **Look left for something smaller.** For each value, return the nearest value to its **left** that is strictly smaller, or −1. Test an increasing input, a decreasing input, and repeated values.
2. **Decode a string.** Decode strings like `3[a2[c]]` into `accaccacc`. Counts can have several digits, and brackets nest. Test `2[ab]3[c]` and `10[a]`.
3. **Largest rectangle of ones.** Given a grid of 0s and 1s, find the area of the largest rectangle containing only 1s. Test an all-zero grid, a single row, and a single column.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**Look left:** go left to right. Pop while the top is **greater than or equal to** the current value; whatever remains on top is strictly smaller and nearest, or −1 if the stack is empty. Then push the current value. The stack's values strictly increase from bottom to top. Each value is pushed and popped once: O(n).

**Decode:** keep two stacks, one of counts and one of the strings built so far. On `[`, push the current count and the current string, then start fresh. On `]`, pop them and set the current string to the saved string plus the current one repeated count times. Digits accumulate as `count = count * 10 + d`. This is a stack of *saved state*, the same shape as the postfix evaluator.

**Rectangle of ones:** turn each row into a histogram. `heights[j]` counts the consecutive 1s ending at this row in column j, and resets to 0 on a 0. Run Chapter 7 on every row and keep the best: O(rows × cols).

Then explain why a slightly wrong version fails on one of your tests. A counterexample you found yourself is stronger evidence of understanding than a memorised template.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Brackets, nesting, "valid sequence" | Push the expected closer; a closer must match the top | The stack lists every unclosed opener, innermost on top |
| O(1) minimum with undo | A parallel stack of "minimum at or below this level" | Each level's extra information stays true while that level exists |
| Postfix expression | Push numbers; an operator pops right, then left | The stack holds finished sub-expression values in order |
| Next warmer / greater, to the right | Waiting stack of indexes; pop while strictly beaten | Values never increase bottom to top; everyone on it is unanswered |
| Next greater in a circular array | Sweep 2n with `i % n`; push only in lap one | Every index waits once and sees all its successors |
| Cars catching up, no passing | Sort front first; compare solo time with the fleet ahead | Fleet arrival times strictly increase bottom to top |
| Largest rectangle under heights | Pop while top ≥ arrival; width i − newTop − 1; height-0 sentinel | Heights strictly increase; a popped rectangle is complete |
| Next greater for a subset of queries | One pass over the reference list into a value → answer map | Each answer is computed once; lookups are O(1) |
| Span looking back, streaming | (price, span) pairs; pop on ≤ and absorb spans | A popped day can never block anyone after today |
| Collisions between neighbours | Stack of survivors; a left-mover fights right-moving tops | Survivors so far never collide with each other |
| Smallest number after k deletions | Non-decreasing stack of digits; pop larger digits while k remains | Kept digits never decrease; trim leftovers from the tail |
| Trapped water, bars arriving live | Stack of non-increasing heights; pop a floor, fill a layer | Each pop fills one horizontal layer, exactly once |
| Sum over every subarray's minimum | Contribution counting with histogram boundaries | Strict on one side, non-strict on the other: each subarray counted once |

A stack solution is **not** automatically O(n). Count pushes and pops: if every item is pushed once and popped at most once, the total work is linear. If items can be pushed more than once, as with a careless second lap, recount.

### Five common bugs

1. **Popping or peeking an empty stack.** `")("`, the histogram's empty-stack width, and RPN on bad input. Check `isEmpty()` first, and remember that `peek()` returns `null`.
2. **Forgetting the leftovers.** Return `stack.isEmpty()` for brackets. Use the sentinel for the histogram. Make sure the default answer (0, −1) is already in place for anyone still waiting.
3. **Operand order.** The first pop is the right-hand operand. `5 3 -` is 2.
4. **Values where you needed indexes.** Distances and widths need positions. Push indexes and read values through them.
5. **`>` versus `>=` without a reason.** Decide what equal values do. Warmer means strictly warmer. A span counts equal prices. The histogram and the subarray minimums need one strict side and one non-strict side.

<h2 id="revision">Revision</h2>

**How to recognise it.** Two triggers. (1) Nesting, matching or undo: the most recently opened thing must be handled first. (2) The nearest greater or smaller element on one or both sides: next warmer day, next greater value, widest rectangle, stock span. Decide whether equal values count as "beating" before you write the pop condition.

**Core algorithm.** Keep a stack of indexes (or expected closers, or saved state). For each arrival, pop while it answers the top, record the answer at pop time, then push the arrival. Items left at the end get a default answer, or a sentinel (height 0, `i == n`) flushes them. For next greater, values never increase bottom to top. For the histogram, heights strictly increase and a pop measures `height × (i − newTop − 1)`.

**Common mistakes.**

- Popping or reading an empty stack; forgetting the end check or sentinel.
- Pushing values when you needed indexes.
- `>` versus `>=`: equal values answering each other, or double counting with duplicates.
- Operand order in postfix; comparing `Integer` objects with `==`.

**Complexity.** O(n) time, because every item is pushed once and popped at most once. O(n) space for the stack. Sorting first (Car Fleet) makes it O(n log n).

**Three representative problems.**

1. [Valid Parentheses](https://leetcode.com/problems/valid-parentheses/): push the expected closer, match on close.
2. [Daily Temperatures](https://leetcode.com/problems/daily-temperatures/): the waiting stack, next greater in O(n).
3. [Largest Rectangle in Histogram](https://leetcode.com/problems/largest-rectangle-in-histogram/): pop to finalize, with a sentinel and the empty-stack width.
