<h2 id="prologue">Prologue · Walking a tree level by level</h2>

A **binary tree** is drawn with the root at the top. Each node has at most two children, a left one and a right one.

- The root is on **level 0**. A node's level is its **depth**: the number of edges between it and the root.
- A node with no children is a **leaf**.
- The number of nodes on a level is that level's **width**.

**Depth-first search** goes as deep as it can, then backs up. It visits the tree in the order of the path it walks. **Breadth-first search (BFS)** visits all of level 0, then all of level 1, then level 2. The tool is a **queue**: first in, first out.

Take the front node, process it, and add its children to the **back**. Children always join behind everyone already waiting. So **no node on level d + 1 can be processed before the last node on level d**.

### Three questions before every move

1. **What is settled?** Every node already processed, and every level whose row is closed. Nobody is processed twice.
2. **Why is this move safe?** The queue is first-in, first-out. Children join behind their whole level, so levels leave the queue in order, and within a level, left to right.
3. **When do we stop?** When the queue is empty. Each node joined once and left once.

> The invariant: **at the start of each level, the queue holds exactly that level and nothing else.** Every chapter keeps this promise and asks a different question of each level.

**Reading LeetCode's array form.** `[3, 9, 20, null, null, 15, 7]` lists the root, then each level left to right. Every real node takes the next two entries as its left and right child. `null` means "no child here", and trailing nulls are dropped. Node 9 takes `null, null` (a leaf). Node 20 takes `15, 7`. Every tree in this lesson and its practice prompts uses this form.

### How to recognise the pattern

The answer is **organised by depth**, or you want **the nearest of something**:

- **"Row by row", "level by level", "top to bottom"**: return the levels as lists (Chapter 1), alternate their direction (Chapter 2), or keep one node per level (Chapter 3).
- **One answer per level**: the average, sum, maximum, first or last node of each level (side quest 1).
- **Nearest, shallowest, fewest steps**: in a tree or any unweighted graph, the first time BFS reaches something it got there with the fewest edges (side quests 2 and 6).
- **Neighbours on the same level**: link them, measure their spread, compare their parents (side quests 3 to 5).

### The brute force this replaces

To get level d naively, walk the whole tree once per level and keep the nodes at depth d. That is O(n · h), which is **O(n²)** on a chain. BFS is **one pass, O(n)**.

A depth-first walk that carries a `depth` argument and appends to `rows[depth]` is also O(n). The tests for this lesson use exactly that as the oracle. BFS wins when you want to **stop early** at the nearest thing, or when the problem is about **rings of distance** rather than rows.

<h2 id="level-order">Chapter 1 · Level Order Traversal</h2>

### Problem

Return the values of a binary tree level by level, left to right.

`[3, 9, 20, null, null, 15, 7]` gives `[[3], [9, 20], [15, 7]]`.

### How to recognise it

- The word "level", "row" or "depth" is in the question.
- The output is a list of lists, one per level.
- You need to know **where one level ends** and the next begins.

### Brute force

For each depth d from 0 up, run a full DFS and collect the nodes whose depth is d. Stop when a pass finds nothing. Each pass touches every node, and there can be h passes: O(n · h), up to O(n²) on a chain.

### Intuition

A plain queue already produces the right **order**: process the front, append its children. The only open problem is **where one level ends**, because nothing in the queue says which level a node belongs to.

Here is the observation. **When the previous level has just been finished, the queue holds exactly the next level and nobody else.** Everyone from the earlier level is gone. Nobody from the level after has been added yet, because only this level's nodes add them. So count the queue **right then**, once:

```text
size = queue.size()          // exactly one level is waiting
process exactly size nodes   // their children join behind, but are not counted
close the row                // now the queue is exactly the next level
```

Children that join during the level stand **behind** the counted ones, and the count stops before them. That frozen number is the **size snapshot**. It is why the code has two loops: the outer `while` runs once per level, the inner `for` runs exactly `size` times.

### Algorithm

1. If the root is null, return an empty list.
2. Put the root in a queue.
3. While the queue is not empty:
   1. Read `size = queue.size()` once.
   2. Make an empty row.
   3. Repeat `size` times: poll the front, add its value to the row, and offer its non-null left then right child.
   4. Add the row to the answer.
4. Return the answer.

### Java solution

<HintLadder hints={hints.levelOrder}>

```java id=levelOrder
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> levels = new ArrayList<>();
    if (root == null) return levels;                 // ArrayDeque refuses null: guard first
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();                     // snapshot: exactly one level is waiting
        List<Integer> level = new ArrayList<>(size);
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            level.add(node.val);
            if (node.left != null) queue.offer(node.left);    // the next level joins the BACK
            if (node.right != null) queue.offer(node.right);
        }
        levels.add(level);                           // the level is done: close the row
    }
    return levels;
}
```

**O(n) time, O(w) extra space** for the queue (plus the O(n) answer). The queue holds the rest of one level plus the start of the next, so it never exceeds two levels' worth. On a complete tree it peaks at the bottom level.

</HintLadder>

### Why it works

- **Settled:** every level above the current one is closed in the answer. No node is processed twice.
- **Why the move is safe:** by induction on levels. Level 0 is the only thing in the queue at the start. If the queue holds exactly level d when the outer loop begins, the inner loop processes exactly those `size` nodes, left to right. The only nodes that join are their children. That is all of level d + 1, left to right, because each parent adds left before right and parents are processed left to right. So the next outer iteration starts with exactly level d + 1.
- **When we stop:** the queue is empty. Every node was offered once and polled once, and the number of rows equals the height of the tree (counted in nodes). Say this out loud in an interview.

### Complexity

- **Time O(n):** each node joins and leaves the queue once.
- **Space O(w):** w is the widest level. A chain has w = 1. A complete tree has about n / 2 nodes on its bottom level (a full tree with h levels has 2^h - 1 nodes and 2^(h-1) on the last level), so BFS space is O(1) on a chain but **O(n) on a bushy tree**. A depth-first walk is the opposite: O(h) stack, which is O(n) on a chain and O(log n) on a bushy tree.

### Edge cases and mistakes

- Empty tree: return an empty list, and guard before `offer(root)` because `ArrayDeque` rejects null.
- A single node: `[[1]]`.
- A chain: one node per level, queue size 1.

**The classic bug: the live bound.**

```java fragment
for (int i = 0; i < queue.size(); i++) {      // BUG: re-reads a size that changes inside the loop
    TreeNode node = queue.poll();             // [3, 9, 20, null, null, 15, 7] -> [[3, 9], [20, 15], [7]]
```

It looks identical to the right answer and passes on a one-node tree. Freeze `size` in a variable first.

<Reveal q="Why not just loop while i < queue.size()?">

Because `queue.size()` changes inside the loop. It grows when children join and shrinks when you poll. On `[3, 9, 20, null, null, 15, 7]` a live bound processes 3 (the queue becomes `[9, 20]`, size 2), then 9 (queue `[20]`, size 1), then stops at `i = 2`. The rows come out `[[3, 9], [20, 15], [7]]`. The snapshot is the only value that still means "how many were on this level".

</Reveal>

<Reveal q="I have seen a version that pushes a null marker after each level. Is that wrong?">

It works, but it is more fragile. After each level you put a marker in the queue; when you poll the marker, the level is over. Two traps. You must **re-add the marker only if the queue is not empty**, or the loop spins forever. And a `null` marker forces a `LinkedList`, because **`ArrayDeque` refuses null**. A dedicated marker object avoids the second trap:

```java id=levelOrderMarker
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> levels = new ArrayList<>();
    if (root == null) return levels;
    final TreeNode END = new TreeNode();             // a marker object: ArrayDeque refuses null itself
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    queue.offer(END);
    List<Integer> level = new ArrayList<>();
    while (!queue.isEmpty()) {
        TreeNode node = queue.poll();
        if (node == END) {                           // this level is over
            levels.add(level);
            level = new ArrayList<>();
            if (!queue.isEmpty()) queue.offer(END);  // re-arm only if another level waits
        } else {
            level.add(node.val);
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
    }
    return levels;
}
```

The snapshot version needs no marker, no special case and no extra check. Prefer it; recognise this one.

</Reveal>

<Reveal q="Why ArrayDeque and not LinkedList? Both implement Queue.">

Three reasons. **It refuses nulls**, so `offer(null)` throws a `NullPointerException` at the exact line of the bug instead of letting a null wander through the queue and fail later. **It is faster**: one growable array, no node object per element. And **it does both jobs**: `offer`/`poll` as a queue, `push`/`pop` as a stack, `offerFirst`/`pollLast` as a deque.

A common habit with `LinkedList` is to offer both children unconditionally and skip nulls when polling. With the size snapshot, the nulls are counted as part of a level. On the single-node tree `[1]` that produces a phantom last level: `[[1], []]`. `ArrayDeque` would have thrown at the first `offer(null)`.

</Reveal>

<h2 id="zigzag">Chapter 2 · Zigzag Level Order</h2>

### Problem

Return the levels with alternating direction: level 0 left to right, level 1 right to left, level 2 left to right, and so on.

For the tree 1..7 (`[1, 2, 3, 4, 5, 6, 7]`) the answer is `[[1], [3, 2], [4, 5, 6, 7]]`.

### How to recognise it

- It is Level Order with one extra rule about direction.
- The words "zigzag", "spiral" or "alternate direction".

### Brute force

Run level order, then reverse every odd row. That is already O(n) and perfectly correct. The "optimisation" here is doing it in the same pass, and, more importantly, **not breaking the queue** while trying to change direction. Many people try to change the order children are added, and that is the trap.

### Intuition

**The queue never changes. Only where you write does.**

Run Chapter 1 exactly. The inner loop still processes level d from left to right. On a left-to-right level, the i-th node processed goes into slot `i`. On a right-to-left level, it goes into slot `size - 1 - i`.

The snapshot does double duty. It ends the level, **and** it tells you where the far end of the row is before you have seen the whole level.

### Algorithm

1. Run level order with a size snapshot per level, and a boolean `leftToRight = true`.
2. Make a row with `size` slots.
3. For the i-th node processed, store its value in slot `i` if `leftToRight`, otherwise in slot `size - 1 - i`. Offer its children left then right, as always.
4. Add the row to the answer, then flip `leftToRight`.

### Java solution

<HintLadder hints={hints.zigzag}>

```java id=zigzagLevelOrder
public List<List<Integer>> zigzagLevelOrder(TreeNode root) {
    List<List<Integer>> levels = new ArrayList<>();
    if (root == null) return levels;
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    boolean leftToRight = true;
    while (!queue.isEmpty()) {
        int size = queue.size();
        Integer[] row = new Integer[size];            // the snapshot also sizes the row
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            row[leftToRight ? i : size - 1 - i] = node.val;   // only the pen changes direction
            if (node.left != null) queue.offer(node.left);     // the queue never does
            if (node.right != null) queue.offer(node.right);
        }
        levels.add(Arrays.asList(row));
        leftToRight = !leftToRight;
    }
    return levels;
}
```

**O(n) time, O(w) extra space.** Each value is written once, straight into its final slot.

</HintLadder>

### Why it works

- **Settled:** Chapter 1's invariant is untouched. The queue still holds exactly one level, left to right, because nothing about the queue changed.
- **Why the move is safe:** the slot formula reverses a sequence of known length `size` in place. The first processed goes last, the last processed goes first.
- **When we stop:** the queue is empty, as before.

### Complexity

- **Time O(n)**, each node once.
- **Space O(w)** for the queue. The row array is part of the output.

### Edge cases and mistakes

- Empty tree and a single node behave as in Chapter 1.
- Level 1 is the first reversed one. With only two levels you cannot see a scrambled bug, so test three or more.

**The classic bug: flipping the queue instead of the write position.**

```java fragment
// BUG: before a right-to-left level, offer children right-first
if (nextIsReversed) { offer(node.right); offer(node.left); } else { offer(node.left); offer(node.right); }
// tree 1..7: level 1 comes out [3, 2] (correct), level 2 comes out [6, 7, 4, 5] (scrambled)
```

Level 1 is right, which is what makes this bug convincing. But level 1 was *processed* as 3, then 2, so 3's children joined the queue before 2's.

<Reveal q="Are there other correct ways?">

Yes, and they are worth recognising. **Reverse alternate rows:** build each row left to right, then `Collections.reverse` it on odd levels; still O(n) in total. **Add to the front:** collect the row in a `LinkedList<Integer>` (or `ArrayDeque`) with `addFirst` on odd levels. **Two stacks:** pop level d from one stack while pushing children into another, left-then-right on even levels and right-then-left on odd ones. That flip is correct only because a **stack** reverses the next level on its own. With a queue, the same flip scrambles it (the bug above).

</Reveal>

<h2 id="right-side-view">Chapter 3 · Right Side View</h2>

### Problem

Imagine standing to the right of the tree. Return the values you can see, from top to bottom: one per level.

`[1, 2, 3, null, 5, null, 4]` gives `[1, 3, 4]`.

### How to recognise it

- "Visible from the right (or left)", "rightmost node of each level".
- The answer has exactly one value per level.

The view is **the last node on each level**, wherever it hangs. "Right side" does not mean "right children".

<Figure caption="Top: LeetCode's example [1, 2, 3, null, 5, null, 4]; the view is 1, 3, 4. Bottom: [1, 2, 3, 4]; the view is 1, 3 and then 4, a left child, because nothing on level 2 is to its right.">
  <Tree {...figures.rightView} />
  <Tree {...figures.leftHidden} />
</Figure>

### Brute force

Collect all levels (Chapter 1) and take the last value of each. It is O(n) time and O(n) space for the full answer. It works, but it stores every value just to keep one per level. Walking only right children is a tempting shortcut, and it is wrong (see the mistakes below).

### Intuition

There are two good ways.

**Way 1, BFS:** run Chapter 1 and record the node when `i == size - 1`. The snapshot is what makes "last on this level" knowable at the moment you process it.

**Way 2, DFS, right first:** walk depth-first, **right child before left**, carrying the depth. The first node you reach on each new level is the rightmost one, because everything to its right was explored first. You know a level is new when `depth == view.size()`: the view has one entry per level seen so far.

### Dry run

<DryRun title="Right side view on [1, 2, 3, null, 5, null, 4]" frames={rightViewFrames([1, 2, 3, null, 5, null, 4])} predict />

The second example, where the visible node on the last level is a **left** child:

<DryRun title="Right side view on [1, 2, 3, 4]" frames={rightViewFrames([1, 2, 3, 4])} />

<Trace title="Which node is visible?" steps={rightView} takeaway="Remember: the view is the LAST node of each level (i == size - 1), or the FIRST node reached at each new depth when you go right-first." />

### Algorithm

BFS version:

1. Run level order with a size snapshot per level.
2. For the i-th node processed on a level, if `i == size - 1`, add its value to the view.
3. Offer children left then right as usual.

DFS version:

1. Call `climb(node, depth)`. If the node is null, return.
2. If `depth == view.size()`, this is the first node seen on a new level: add it.
3. Recurse on the **right** child, then the left child, with `depth + 1`.

### Java solution

<HintLadder hints={hints.rightView}>

```java id=rightSideView
public List<Integer> rightSideView(TreeNode root) {
    List<Integer> view = new ArrayList<>();
    if (root == null) return view;
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            if (i == size - 1) view.add(node.val);    // last on this level: nothing is to its right
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
    }
    return view;
}
```

```java id=rightSideViewDfs
public List<Integer> rightSideView(TreeNode root) {
    List<Integer> view = new ArrayList<>();
    climb(root, 0, view);
    return view;
}

private void climb(TreeNode node, int depth, List<Integer> view) {
    if (node == null) return;
    if (depth == view.size()) view.add(node.val);     // first node reached on a new level
    climb(node.right, depth + 1, view);               // right child first
    climb(node.left, depth + 1, view);
}
```

**Both are O(n) time.** BFS uses **O(w)** extra space; DFS uses **O(h)** stack.

</HintLadder>

### Why it works

- **BFS, settled:** `view` holds the last node of every closed level. **Safe:** the level is processed left to right, so the last one has nothing to its right.
- **DFS, settled:** `view.size()` is the number of levels already seen, and `view[d]` is the rightmost node on level d. **Safe:** the walk reaches level d for the first time along the path that turns right at every chance, so any node on level d to the right of it would have been reached earlier.
- **When we stop:** BFS ends when the queue is empty; DFS ends when the recursion returns from the root.

### Which walk? The trade, in one table

| | BFS (queue) | DFS (recursion or stack) |
|---|---|---|
| Visits nodes | level by level, left to right | one path at a time, as deep as possible |
| Extra space | O(w): up to about n / 2 on a complete tree | O(h): up to n on a chain, about log₂ n when balanced |
| Natural for | rows, per-level answers, **nearest / fewest edges**, stopping early | answers that come **up from subtrees**: height, balance, diameter, path sums, LCA |
| Right side view | `i == size - 1` | right first, `depth == view.size()` |

When the level order is the point (rows, "nearest", "fewest steps", per-level aggregates), reach for BFS. When the answer is built from subtrees, use DFS. When both work, as here, **pick by shape**: a wide, shallow tree favours DFS's O(h). A long chain favours BFS's O(w), and a very deep recursion risks a `StackOverflowError` in Java. Say that sentence in the interview.

### Complexity

- **Time O(n)** for both: every node is looked at once.
- **Space:** O(w) for BFS (the queue), O(h) for DFS (the call stack).

### Edge cases and mistakes

- Empty tree gives an empty view.
- A visible node can be a left child (`[1, 2, 3, 4]` gives `[1, 3, 4]`).
- A chain going left gives every node.

**The classic bug: walking right children only.**

```java fragment
for (TreeNode n = root; n != null; n = n.right) view.add(n.val);   // BUG: [1, 2, 3, 4] -> [1, 3], loses level 2
```

It passes LeetCode's first example, `[1, 2, 3, null, 5, null, 4]`, by luck: there the right children happen to reach every level.

<Reveal q="And the LEFT side view?">

Record `i == 0` in the BFS, or climb **left first** with the same `depth == view.size()` rule. The left view of `[1, 2, 3, 4]` is `[1, 2, 4]`.

</Reveal>

<h2 id="average-levels">Side quest 1 · Average of Levels</h2>

### Problem

Return the average value of the nodes on each level.

`[3, 9, 20, null, null, 15, 7]` gives `[3.0, 14.5, 11.0]`.

### How to recognise it

"Average, sum, maximum, minimum or count **per level**." The answer is one number per level, not a list of values.

### Brute force

Run Chapter 1 to get every row as a list, then average each list. Correct and O(n), but it stores all the values when you only need a running total per level.

### Intuition

Same loop, but the row becomes **two numbers**: a running sum and the snapshot `size`. When the inner loop ends, the level's average is `sum / size`. This is the template for every **per-level aggregate**: replace the list with whatever the level needs (sum, max, min, count, first, last).

### Dry run

<DryRun title="Average of levels on [3, 9, 20, null, null, 15, 7]" frames={averageLevelsFrames([3, 9, 20, null, null, 15, 7])} />

### Algorithm

1. Run level order with a size snapshot.
2. Per level, set `long sum = 0`.
3. For each of the `size` nodes, add its value to `sum` and offer its children.
4. Add `(double) sum / size` to the answer.

### Java solution

<HintLadder hints={hints.average}>

```java id=averageOfLevels
public List<Double> averageOfLevels(TreeNode root) {
    List<Double> averages = new ArrayList<>();
    if (root == null) return averages;
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        long sum = 0;                                // two values of 2^31 - 1 already overflow an int
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            sum += node.val;
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
        averages.add((double) sum / size);           // divide as a double, not as a long
    }
    return averages;
}
```

**O(n) time, O(w) extra space.** LeetCode's example `[3, 9, 20, null, null, 15, 7]` gives `[3.0, 14.5, 11.0]`.

</HintLadder>

### Why it works

The inner loop touches exactly the nodes of one level (the snapshot), so `sum` covers exactly that level and `size` is its count.

### Complexity

**Time O(n)**, **space O(w)** for the queue.

### Edge cases and mistakes

<Reveal q="LeetCode allows values up to 2^31 - 1. What goes wrong with an int sum and sum / size?">

Two separate bugs. **Overflow:** on `[2147483647, 2147483647, 2147483647]`, level 1's two values add to 4,294,967,294, which wraps to -2 in an `int`, and the "average" comes out -1.0 instead of 2147483647.0. Use a `long` sum: a level holds at most 10^4 values here, so a `long` can't overflow. **Integer division:** with `long sum`, `sum / size` truncates before it becomes a double. On `[3, 9, 20, null, null, 15, 7]` level 1 gives 14.0 instead of 14.5. Cast first: `(double) sum / size`.

</Reveal>

<h2 id="min-depth">Side quest 2 · Minimum Depth</h2>

### Problem

Find the fewest nodes on a path from the root down to a **leaf** (a node with no children). Count nodes, including both ends.

`[3, 9, 20, null, null, 15, 7]` gives `2`. `[1, 2]` gives `2`.

### How to recognise it

"Nearest", "shallowest", "fewest steps to a leaf". It is a shortest-path question on an unweighted structure.

### Brute force

Recursion over the whole tree: the minimum of the two subtrees' answers. It must visit **every** node, because it cannot know the right subtree is deeper without exploring it. Always O(n), with O(h) recursion depth.

### Intuition

Levels leave the queue in order of depth, so **the first leaf you process is on the shallowest level that has one**. Stop right there. Nothing deeper is ever touched.

<Figure caption="[1, 2, 3, null, null, null, 4, null, 5, null, 6]. BFS processes 1, then 2, a leaf on level 1, and returns. Node 3 is still waiting in the queue and is never processed. 4, 5 and 6 are never even added. A recursion that takes the smaller of both sides has to walk the whole chain first.">
  <Tree {...figures.minDepth} />
</Figure>

On a tree with a leaf near the top and a 100,000-node chain below, BFS makes a few calls and recursion makes 100,000 (and risks a `StackOverflowError`). In the worst case both are O(n): a perfectly balanced tree has its leaves at the bottom.

### Dry run

<DryRun title="Minimum depth on [1, 2, 3, null, null, null, 4, null, 5, null, 6]" frames={minDepthFrames([1, 2, 3, null, null, null, 4, null, 5, null, 6])} predict />

### Algorithm

1. If the root is null, return 0.
2. Start with `depth = 1` and the root in the queue.
3. For each level, process `size` nodes. If a node has no left and no right child, return `depth`.
4. Otherwise offer its children. After the level, `depth++`.

### Java solution

<HintLadder hints={hints.minDepth}>

```java id=minDepth
public int minDepth(TreeNode root) {
    if (root == null) return 0;
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    int depth = 1;                                   // level 0 holds paths of 1 node
    while (!queue.isEmpty()) {
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            if (node.left == null && node.right == null) return depth;   // first leaf = nearest
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
        depth++;
    }
    return depth;                                    // unreachable: every non-empty tree has a leaf
}
```

**O(n) time in the worst case, O(w) extra space**, and it stops at the first leaf.

</HintLadder>

### Why it works

- **Settled:** every level above `depth` has been fully processed and had no leaf.
- **Why the move is safe:** the queue releases levels in order of depth, so nothing shallower can still be waiting. The same sentence proves BFS finds shortest paths in any unweighted graph.
- **When we stop:** at the first leaf, or never early if the tree is balanced.

### Complexity

**Time O(n)** worst case, but often much less. **Space O(w).**

### Edge cases and mistakes

- Empty tree: 0. A single node: 1.
- A chain: the answer is its length, not 1.

**The classic bug: a null child is not a way out.**

<Reveal q="The one-line recursion 1 + min(minDepth(left), minDepth(right)): what does it return on [1, 2]?">

**1**, but the answer is **2**. The root has a left child, so it is not a leaf. Its missing right child returns 0, and `min` picks that 0. **A null child is not a way out.** The correct recursion only takes the minimum when both children exist:

```java id=minDepthDfs
public int minDepth(TreeNode root) {
    if (root == null) return 0;
    if (root.left == null) return 1 + minDepth(root.right);   // one child only: follow it
    if (root.right == null) return 1 + minDepth(root.left);
    return 1 + Math.min(minDepth(root.left), minDepth(root.right));
}
```

Correct, but it visits every node every time.

</Reveal>

<h2 id="max-width">Side quest 3 · Maximum Width</h2>

### Problem

The width of a level is the distance from its leftmost to its rightmost node, **counting the empty positions between them** (the ones a complete tree would have filled). Return the widest level.

`[1, 3, 2, 5, 3, null, 9]` gives `4`.

### How to recognise it

The width counts gaps, so the number of nodes on a level is **not** its width. You need positions.

### Brute force

Fill the tree out to a complete tree with explicit null nodes and count level by level. That is O(2^h) nodes, which explodes on a skinny deep tree.

### Intuition

Number positions as if the tree were complete: the root is position 0, and a node at position p has children at **2p + 1** (left) and **2p + 2** (right). The width of a level is **last position - first position + 1**, and BFS hands you the first and last node of every level.

<Figure caption="LeetCode's example [1, 3, 2, 5, 3, null, 9], with positions renumbered from 0 on each level. Level 2 has nodes at positions 0, 1 and 3; position 2 is empty. Width 3 - 0 + 1 = 4, although only 3 nodes live there.">
  <Tree {...figures.width} />
</Figure>

**Renumber every level.** Positions double on every level: by level 31 they no longer fit in an `int`, by level 63 not in a `long`, and a chain of 3,000 nodes would need 3,000-bit numbers. Subtract the level's first position from every position on that level before computing children. Every number you hold is then a real distance from the level's left end, which is never more than the answer, and LeetCode promises the answer fits in an `int`. Keep positions in a `long` anyway, because the children of a position near 2^31 are near 2^32.

### Dry run

Queue entries are shown as `value@position`. Positions are renumbered so the first node of every level is position 0.

<DryRun title="Maximum width on [1, 3, 2, 5, 3, null, 9]" frames={maxWidthFrames([1, 3, 2, 5, 3, null, 9])} />

### Algorithm

1. Put `(root, 0)` in the queue.
2. For each level, remember `first = queue.peek().pos`.
3. For each of the `size` entries: `pos = entry.pos - first`; remember it as `last`; offer the children at `2 * pos + 1` and `2 * pos + 2`.
4. Width is `last + 1`. Keep the maximum.

### Java solution

<HintLadder hints={hints.width}>

```java id=widthOfBinaryTree
static class Seat {                                  // a node and its position on this level
    final TreeNode node;
    final long pos;
    Seat(TreeNode node, long pos) { this.node = node; this.pos = pos; }
}

public int widthOfBinaryTree(TreeNode root) {
    if (root == null) return 0;
    Queue<Seat> queue = new ArrayDeque<>();
    queue.offer(new Seat(root, 0));
    long best = 0;
    while (!queue.isEmpty()) {
        int size = queue.size();
        long first = queue.peek().pos;               // leftmost position on this level
        long last = 0;
        for (int i = 0; i < size; i++) {
            Seat s = queue.poll();
            long pos = s.pos - first;                // renumber: the level starts at position 0
            last = pos;
            if (s.node.left != null) queue.offer(new Seat(s.node.left, 2 * pos + 1));
            if (s.node.right != null) queue.offer(new Seat(s.node.right, 2 * pos + 2));
        }
        best = Math.max(best, last + 1);             // first is 0 after renumbering
    }
    return (int) best;
}
```

**O(n) time, O(w) extra space.** LeetCode's second example, `[1, 3, 2, 5, null, null, 9, 6, null, 7]`, has width 7 on its bottom level.

</HintLadder>

### Why it works

A node's position is its index in the complete-tree numbering. Two nodes on the same level are `last - first` positions apart, and that is exactly the count of frames between them plus one. Renumbering subtracts the same constant from every node on the level, so differences are unchanged.

### Complexity

**Time O(n), space O(w).** Positions stay small because of the renumbering.

### Edge cases and mistakes

- A single node has width 1. A chain has width 1 on every level.
- Deep skinny trees overflow naive positions.

<Reveal q="Plenty of Java solutions skip the renumbering and still pass. Why?">

Luck in the arithmetic. Java's `int` and `long` wrap around on overflow, and wrapped numbers still **subtract** correctly as long as the true difference fits: last - first + 1 comes out right even when both positions are garbage. Compare two wrapped positions with `<`, or port the code to a language where overflow is an error or numbers grow without bound, and it fails or crawls. Renumbering makes the code correct by construction instead of by accident.

</Reveal>

<h2 id="next-pointers">Side quest 4 · Next Right Pointers</h2>

### Problem

Every node has a `next` pointer. Set each one to the node immediately to its right on the same level; the rightmost node's `next` stays `null`. The tree is **perfect** (every level full). Use **O(1) extra space**: no queue.

For the tree 1..7: `2 → 3`, `4 → 5 → 6 → 7`, and `1`, `3`, `7` point to null.

### How to recognise it

"Connect each node to its right neighbour", with a space limit that rules out a queue.

### Brute force

Run level order with a queue and link each node to the one processed after it, unless it is the last on its level. It works on **any** tree, and costs O(w) for the queue:

```java id=connectQueue
static class Node {
    int val;
    Node left, right, next;
    Node(int val) { this.val = val; }
}

public Node connect(Node root) {
    if (root == null) return null;
    Queue<Node> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            Node node = queue.poll();
            if (i < size - 1) node.next = queue.peek();   // the next one processed is its right neighbour
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
    }
    return root;
}
```

### Intuition

To drop the queue, notice what the pointers are: **a finished level is a linked list**. Stand on level d, already linked, and walk it left to right along its own `next` pointers. From each node you can reach both its children, and through `next`, the children of its right neighbour. That is every pair of neighbours on level d + 1:

- **siblings:** `head.left.next = head.right`;
- **across the gap between two parents:** `head.right.next = head.next.left`.

Then step down to the level's leftmost node, `leftmost.left`, and repeat.

<Figure caption="The tree 1..7 with its next pointers (dashed). Walking level 1 along 2 → 3: node 2 links 4 → 5 (siblings) and, through its own pointer to 3, links 5 → 6 (different parents). Node 3 links 6 → 7. The right end of every level stays null.">
  <Tree {...figures.next} />
</Figure>

### Dry run

The array is the current level, walked by its own `next` pointers. The `links` variable grows as each head creates links.

<DryRun title="Next right pointers on a perfect tree of 7" frames={nextPointersFrames([1, 2, 3, 4, 5, 6, 7])} predict />

### Algorithm

1. Let `leftmost = root`.
2. While `leftmost` has a left child (a level exists below):
   1. For each `head` on this level, following `next`: set `head.left.next = head.right`; if `head.next != null`, set `head.right.next = head.next.left`.
   2. Move down: `leftmost = leftmost.left`.
3. Return the root.

### Java solution

<HintLadder hints={hints.connect}>

```java id=connect
static class Node {
    int val;
    Node left, right, next;
    Node(int val) { this.val = val; }
}

public Node connect(Node root) {
    Node leftmost = root;
    while (leftmost != null && leftmost.left != null) {          // a level exists below this one
        for (Node head = leftmost; head != null; head = head.next) {   // walk this level by its next pointers
            head.left.next = head.right;                          // siblings
            if (head.next != null) head.right.next = head.next.left;   // across the gap between parents
        }
        leftmost = leftmost.left;                                 // step down to the next level
    }
    return root;
}
```

**O(n) time, O(1) extra space**: three pointers, no queue, no recursion.

</HintLadder>

### Why it works

- **Settled:** when we stand on level d, every level up to and including d is fully linked.
- **Why the move is safe:** a perfect tree has two children for every node on the level above the bottom, so `head.left` and `head.right` always exist, and a head's right neighbour is the only node that can be next to `head.right`.
- **When we stop:** `leftmost` has no left child: it is a leaf level.

### Complexity

**Time O(n)**: every node is a head once. **Space O(1)**: no queue, no recursion.

### Edge cases and mistakes

- Empty tree and a single node need no links.
- **The classic bug:** forgetting the link across the gap. With only `head.left.next = head.right`, node 5 in the tree 1..7 is left pointing at null instead of 6.

<Reveal q="Transfer test: the tree is no longer perfect (Populating Next Right Pointers II). What breaks, and what fixes it?">

`head.left` may be missing, the gap between children can span several parents, and the next level need not start at `leftmost.left`. Fix: while walking level d by its pointers, **build level d + 1 as a linked list** with a dummy head and a tail pointer, appending each child that exists. The dummy's `next` is then the next level's leftmost node. Still O(1) extra space:

```java id=connectAny
static class Node {
    int val;
    Node left, right, next;
    Node(int val) { this.val = val; }
}

public Node connect(Node root) {
    Node leftmost = root;
    while (leftmost != null) {
        Node dummy = new Node(0), tail = dummy;      // the level below, built as a linked list
        for (Node head = leftmost; head != null; head = head.next) {
            if (head.left != null) { tail.next = head.left; tail = tail.next; }
            if (head.right != null) { tail.next = head.right; tail = tail.next; }
        }
        leftmost = dummy.next;                       // leftmost node of the level below
    }
    return root;
}
```

The dummy-head trick is straight out of the linked-list toolbox: it removes the "is this the first one?" special case.

</Reveal>

<h2 id="cousins">Side quest 5 · Cousins in a Binary Tree</h2>

### Problem

Two nodes with values x and y (all values unique) are **cousins** if they are on the same level but have different parents. Return whether they are.

`[1, 2, 3, null, 4, null, 5]` with x = 4, y = 5 gives `true`. `[1, 2, 3]` with x = 2, y = 3 gives `false` (siblings).

### How to recognise it

"Same depth" plus a relationship about parents. You need depth **and** parent for two nodes.

### Brute force

Walk the tree twice: once to find the depth and parent of x, once for y, then compare. O(n) time and fine. The BFS version does it in one walk and can stop early.

### Intuition

Two facts, both visible in the BFS. **Same level:** when a level closes, check whether both were found on it. If only one was, they are on different levels, so answer no right away. **Different parents:** siblings are caught **at the parent**, while it is processed, because that is the one moment both children are in view at once.

<Figure caption="[1, 2, 3, null, 4, null, 5]: x = 4 and y = 5 are both on level 2, with parents 2 and 3 (blue). Cousins. In [1, 2, 3], the pair 2 and 3 share level 1 but also share parent 1: siblings, not cousins.">
  <Tree {...figures.cousins} />
</Figure>

### Dry run

<DryRun title="Cousins on [1, 2, 3, null, 4, null, 5], x = 4, y = 5" frames={cousinsFrames([1, 2, 3, null, 4, null, 5], 4, 5)} />

The same walk on siblings, which must return false:

<DryRun title="Cousins on [1, 2, 3], x = 2, y = 3" frames={cousinsFrames([1, 2, 3], 2, 3)} />

### Algorithm

1. Run level order with a size snapshot. Per level, set `foundX = foundY = false`.
2. For each node processed: set `foundX` or `foundY` if its value matches. If its two children are exactly x and y, return false.
3. Offer the children.
4. After the level: both found, return true; exactly one found, return false.
5. If the queue empties without either, return false.

### Java solution

<HintLadder hints={hints.cousins}>

```java id=isCousins
public boolean isCousins(TreeNode root, int x, int y) {
    if (root == null) return false;
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        boolean foundX = false, foundY = false;
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            if (node.val == x) foundX = true;
            if (node.val == y) foundY = true;
            if (node.left != null && node.right != null
                    && ((node.left.val == x && node.right.val == y) || (node.left.val == y && node.right.val == x)))
                return false;                        // same parent: siblings, not cousins
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
        if (foundX && foundY) return true;           // same level, and the sibling check never fired
        if (foundX || foundY) return false;          // one was here, the other wasn't
    }
    return false;
}
```

**O(n) time, O(w) extra space.** It can stop at the first level holding either node.

</HintLadder>

### Why it works

The queue keeps levels apart, so "found on this level" means "has this depth". The sibling check is the only place where the parent relationship is cheap to see: the parent is the node whose two children you are looking at.

### Complexity

**Time O(n), space O(w).**

### Edge cases and mistakes

- x or y is the root: the root is alone on level 0, so false.
- **The classic bug:** checking only the level. Compare depths alone and the siblings 2 and 3 in `[1, 2, 3]` pass as cousins.

### Practice

**Transfer test:** Cousins in Binary Tree II replaces every value with the sum of its cousins' values. Which two per-level numbers do you need? (The level's total, and for each parent the sum of its own children: cousins' sum = level total - siblings' total.)

<h2 id="distance-k">Side quest 6 · Nodes at Distance K</h2>

### Problem

Given a tree, a `target` node and an integer `k`, return the values of all nodes exactly `k` edges from the target, in any order. Distance counts up as well as down.

`[3, 5, 1, 6, 2, 0, 8, null, null, 7, 4]`, target 5, k = 2 gives `[7, 4, 1]`.

### How to recognise it

"Distance from a node" in a tree, where the answer can include ancestors and other branches. It is shortest path in an unweighted graph, and it is the bridge from trees to graphs.

### Brute force

For each node, compute its distance to the target through the lowest common ancestor. That is O(n) per node and O(n²) overall, and fiddly.

### Intuition

Child links only lead down; the answer may need to go **up**, and then down into a different branch. So first give every node a way up: walk the tree once and record each node's **parent**. Now every node has up to three neighbours (left, right, parent) and the tree is an **undirected graph**.

Then run BFS **from the target**, one ring per step. Because the walk can come straight back the way it came, keep a **visited set**: a node is reached once, on its first ring.

<Figure caption="LeetCode's example [3, 5, 1, 6, 2, 0, 8, null, null, 7, 4], target 5 (purple), k = 2. Ring 1 reaches 6, 2 and, up the dashed link, 3. Ring 2 reaches 7, 4 and 1. Answer [7, 4, 1], in any order.">
  <Tree {...figures.distanceK} />
</Figure>

### Dry run

The map view is the parent table, the queue is the current ring, and the visited set grows as nodes are reached. Tree nodes in the visited set are shaded.

<DryRun title="Nodes at distance 2 from 5" frames={distanceKFrames([3, 5, 1, 6, 2, 0, 8, null, null, 7, 4], 5, 2)} predict />

### Algorithm

1. Pass 1: walk the tree (any traversal) and record `parent[child] = node`.
2. Put the target in the queue and in a visited set.
3. Repeat `k` times, while the queue is not empty: take a size snapshot; for each node of the ring, look at left, right and parent; for each neighbour not yet visited, mark it and offer it.
4. The queue now holds exactly the nodes at distance `k`. Return their values.

### Java solution

<HintLadder hints={hints.distanceK}>

```java id=distanceK
public List<Integer> distanceK(TreeNode root, TreeNode target, int k) {
    Map<TreeNode, TreeNode> parent = new HashMap<>();
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {                       // pass 1: record every node's parent
        TreeNode node = queue.poll();
        if (node.left != null) { parent.put(node.left, node); queue.offer(node.left); }
        if (node.right != null) { parent.put(node.right, node); queue.offer(node.right); }
    }
    Set<TreeNode> heard = new HashSet<>();
    heard.add(target);
    queue.offer(target);
    for (int beat = 0; beat < k && !queue.isEmpty(); beat++) {   // pass 2: one ring per step
        int size = queue.size();
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            for (TreeNode next : new TreeNode[]{node.left, node.right, parent.get(node)})
                if (next != null && heard.add(next)) queue.offer(next);   // first time only
        }
    }
    List<Integer> ring = new ArrayList<>();
    for (TreeNode node : queue) ring.add(node.val);  // the queue is exactly ring k
    return ring;
}
```

**O(n) time, O(n) extra space** for the parent map, the visited set and the queue.

</HintLadder>

### Why it works

- **Settled:** every node closer than the current ring is in the visited set.
- **Why the move is safe:** BFS reaches nodes in order of distance, and the visited set stops the walk going back to a closer node. A node's first visit is its shortest distance.
- **When we stop:** after `k` rings the queue holds exactly the nodes at distance k. If the queue empties first, nobody is that far away and the answer is empty.

### Complexity

**Time O(n)**: each node is added once. **Space O(n)** for the parent map, the visited set and the queue.

### Edge cases and mistakes

- k = 0 returns just the target.
- k larger than the tree's reach returns an empty list.
- **The classic bug:** no visited set. The walk bounces back. In the example, ring 2 would also reach 5 three times (from 6, from 2 and from 3) and return `[5, 7, 4, 5, 5, 1]`. This is the bridge to graphs: once a walk can return the way it came, it needs a visited set.

<h2 id="choose-the-tool">When BFS is the wrong tool</h2>

Suppose you are asked whether a tree is balanced: at every node, do the left and right subtrees differ in height by at most one? BFS tells you how many nodes are on each level, but not which subtree they came from, and the question is about every single node. Some questions are answered **from below**: each node needs its subtrees' answers first.

BFS is the right tool when **the answer is organised by level, or by distance from a start**. It is the wrong tool when:

- **The answer at a node is built from its subtrees.** Height, balance, diameter, maximum path sum, lowest common ancestor, subtree sums: each needs answers to come **up** from the children. A post-order DFS does it in one O(n) pass; levels give you nothing to combine.
- **The question is about root-to-leaf paths.** Path Sum, "all root-to-leaf paths": carry the path down one branch at a time with DFS. A level mixes many unrelated paths.
- **The tree is a binary search tree and order matters.** An in-order DFS visits values in sorted order; BFS does not.
- **The tree is very wide and shallow, and order does not matter.** Both walks are O(n) time, but BFS holds a whole level (up to about n / 2 nodes) while DFS holds one path.

<Reveal q="Maximum Depth of Binary Tree. BFS or DFS?">

Both are correct and O(n). DFS is one line, `1 + max(depth(left), depth(right))`, with O(h) stack. BFS counts levels with the snapshot loop and O(w) memory. Interviewers accept either; name the space trade, and pick BFS if the tree may be a 100,000-node chain (no deep recursion).

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Start with... | The invariant to keep |
|---|---|---|
| Return the tree row by row | `ArrayDeque`; `size = queue.size()` before the inner loop | The queue holds exactly one level at the top of each iteration |
| Rows alternate direction | Same loop; write into slot `i` or `size - 1 - i` | The queue stays left to right; only the write position flips |
| What you see from the right (or left) | `i == size - 1` (or `i == 0`); or DFS right-first with `depth == view.size()` | One entry per level: the last (or first) on it |
| An average, sum, max per row | Replace the row list with an accumulator (`long` sums, `double` division) | The aggregate covers exactly the snapshot's nodes |
| Nearest leaf, fewest steps, shallowest anything | Level by level; return at the first match | Levels leave the queue in order of depth |
| Width counting gaps | Carry positions; children at 2p + 1, 2p + 2; renumber each level | Width = last position - first position + 1 |
| Link each node to its right neighbour, O(1) space | Walk level d by its `next` links; link level d + 1 (dummy head if not perfect) | A finished level is a linked list |
| Same depth, different parents | Catch siblings at the parent; then "both on this level?" | A level with only one of them ends the search |
| Everything K steps from a node | Parent map, then rings from the target with a visited set | After k rings the queue is exactly the answer |
| Height, balance, diameter, path sums | A DFS that returns answers upward | The wrong tool for BFS |

Memory: BFS is O(w), which is about n / 2 on a complete tree; DFS is O(h), which is n on a chain. The parent map and visited set of side quest 6 are O(n). Only the pointer walk of side quest 4 is O(1).

### Five bugs to remember

1. **The live bound.** `for (int i = 0; i < queue.size(); i++)` re-reads a size that changes inside the loop, and levels bleed into each other. Snapshot `size` first.
2. **Nulls in the queue.** `ArrayDeque.offer(null)` throws; a `LinkedList` accepts it and produces phantom levels or a later crash. Guard the root, and offer only non-null children.
3. **Flipping the queue instead of the write position.** Reordering how children join scrambles every later level. Choose the direction only when writing.
4. **A null child is not a leaf.** In minimum depth, a node with one child is not a way out; `min(left, right)` with a 0 from the missing side returns too early.
5. **Walking back the way you came.** Once a tree has parent links it is a graph: without a visited set, the walk bounces between a node and its parent.

<h2 id="revision">Revision</h2>

**How to recognise it.** The answer is organised by depth ("row by row", "per level"), or you need the nearest or fewest-steps answer in a tree or an unweighted graph. A queue plus a size snapshot is the first thing to try.

**The core algorithm.**

1. Put the root in a queue (guard a null root).
2. While the queue is not empty, read `size = queue.size()` once.
3. Process exactly `size` nodes: poll, use the node, offer its non-null children.
4. Close the level (row, sum, view, depth) and repeat.

For graph-like problems, add a visited set and start from the target instead of the root.

**Common mistakes.**

- Using `queue.size()` as a live loop bound.
- Offering null children (phantom levels, or an NPE on `ArrayDeque`).
- Changing the order children join to get a zigzag.
- Treating a null child as a leaf in minimum depth.
- Forgetting the visited set once parent links exist.
- Overflowing `int` sums or positions, and integer division in averages.

**Complexity.** Time O(n): each node joins and leaves the queue once. Space O(w) for the queue, where w is the widest level. That is about n / 2 on a complete tree, and 1 on a chain. Distance K is O(n) for the parent map and visited set. The pointer walk in Next Right Pointers is O(1).

**Three representative problems.**

- [Binary Tree Level Order Traversal](https://leetcode.com/problems/binary-tree-level-order-traversal/): the template.
- [Binary Tree Right Side View](https://leetcode.com/problems/binary-tree-right-side-view/): one node per level, BFS or DFS.
- [Minimum Depth of Binary Tree](https://leetcode.com/problems/minimum-depth-of-binary-tree/): stop at the first match.

- **Multi-source BFS** — start the queue with many nodes at once (Rotting Oranges, Walls and Gates); distances to the nearest source in one pass.

- **0-1 BFS** — a deque that handles edges of weight 0 or 1, the step between BFS and Dijkstra.
- **Iterative deepening DFS** — level-order discovery with only O(h) memory, by re-running DFS with a growing depth limit.

- **Morris traversal** — a depth-first walk in O(1) extra space by temporarily threading the tree.
- **Binary Tree Vertical Order Traversal vs Vertical Order Traversal** — two LeetCode problems whose only difference is the tie rule, and why one needs a sort.
