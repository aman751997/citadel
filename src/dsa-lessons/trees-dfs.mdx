<h2 id="prologue">Prologue · Nobody sees the whole tree</h2>

<Scene chapter="Prologue" title="The orchard that hangs" mood="dawn">

Rootholm is built on the lip of a cliff, and its orchard grows the wrong way. Each great tree is anchored at the top by a single trunk; every branch hangs lower than the fork it came from, and the fruit swings over the sea.

On your first morning the harvest-master wants a number: how many forks does the old tree have? You lean over the edge. Leaves, ropes, fog. You can see the trunk and the two branches just below it. Nothing else.

The Keeper sits beside you on the stone. *"Nobody here has ever seen a whole tree,"* she says. *"So nobody tries. You ask the left branch how many forks hang from it. You ask the right branch the same. Then you add one for yourself."*

"And who answers the branch?"

*"The branch below it. Same question, smaller tree."* She drops a pebble into the fog. *"Two things I want before you touch a rope. What does a branch promise to tell you? And what do you say when there is nothing below you at all?"*

</Scene>

A **binary tree** is a node with two slots below it, `left` and `right`. Each slot holds another binary tree, or nothing. Read that sentence twice, because it is the whole pattern: **a tree is made of smaller trees**. So a function on a tree can be made of the same function on its smaller trees.

### The contract: trust the call

Before any code, write one sentence: **what does `f(node)` promise to return for the subtree hanging from `node`?** Then build the function in three moves:

1. **Base case first.** What is `f(null)`? Usually `0`, `null`, `true` or an empty list. It needs no work.
2. **Trust the call.** Assume `f(node.left)` and `f(node.right)` already keep the promise. Do not trace inside them.
3. **Combine.** Build this node’s answer from the two answers and `node.val`.

Why is trusting safe? The two children are **strictly smaller trees**, and the smallest tree of all, the empty one, is handled by the base case. If the combine step is right whenever the children’s answers are right, then the answer is right for trees of size 0, so for size 1, so for size 2, and so on. That is induction, and you never have to say the word in an interview: “each call handles its own subtree; I only need to check one level.”

<Mermaid code={`flowchart TD
  A["f(node)"] --> B{"node == null?"}
  B -->|yes| C["return the base answer"]
  B -->|no| D["a = f(node.left)\nb = f(node.right)\n(trust both)"]
  D --> E["combine a, b and node.val"]
  E --> F["return ONE answer to the caller"]`} />

The Keeper’s three questions, in the orchard’s words:

1. **What does the call promise?** What is settled about a subtree when its call returns.
2. **Why is this move safe?** The children kept their promise; this node only combines.
3. **When do I stop?** At the empty spot below a leaf — and earlier, when nothing below can change the answer.

### Two directions: the Climber and the Messenger

Information can travel two ways through a tree, and naming the direction is half of every solution.

| | The Climber (top-down) | The Messenger (bottom-up) |
|---|---|---|
| Information flows | root → leaves, as **parameters** | leaves → root, as **return values** |
| A node knows | everything on the path **above** it | everything in the subtree **below** it |
| Typical questions | depth so far, sum still to find, allowed range of values | height, size, balanced or not, the best path below |
| In this book | Chapters 3 (second version), 8, 9, side quest 3 | Chapters 1–7, side quests 5 and 6 |

Some problems need both at once: the Climber carries a running maximum down while the Messenger carries a count back up (side quest 3).

And one idea needs a third character. Sometimes the answer to the question is **not** the thing the parent needs to hear. Then the Messenger carries what the parent needs, and every fork also sends a number to **Best**, at the gate board. The function **returns one thing and records another**. Chapter 5 is built around that sentence; it is the most important idea in this book.

<h3 id="orders">Three orders: where the work happens</h3>

Every depth-first walk passes each node three times: on the way down, between its two subtrees, and on the way back up. **Where you put the work decides the order in which nodes are handled:**

- **Preorder — node, left, right.** Work on the way down. The node is handled before anything below it: copying a tree, writing it down (Chapter 12), handing state to the children.
- **Inorder — left, node, right.** Work between the subtrees. In a binary search tree, this visits values in **sorted order** (Chapters 9 and 10).
- **Postorder — left, right, node.** Work on the way back up. The node is handled after both children have answered: heights, sizes, balance, any bottom-up combine.

<Figure caption="LeetCode’s favourite small tree, [3, 9, 20, null, null, 15, 7], listed three ways. Preorder writes 3 before anything below it. Inorder writes everything left of 3 (just 9) before 3. Postorder writes 3 last, after both of its subtrees have been handled.">

The three orders are the same walk with the `add` line moved:

```java id=orders
public List<Integer> preorder(TreeNode root) { List<Integer> out = new ArrayList<>(); pre(root, out); return out; }
public List<Integer> inorder(TreeNode root) { List<Integer> out = new ArrayList<>(); in(root, out); return out; }
public List<Integer> postorder(TreeNode root) { List<Integer> out = new ArrayList<>(); post(root, out); return out; }

private void pre(TreeNode node, List<Integer> out) {
    if (node == null) return;
    out.add(node.val);                     // on the way down
    pre(node.left, out);
    pre(node.right, out);
}
private void in(TreeNode node, List<Integer> out) {
    if (node == null) return;
    in(node.left, out);
    out.add(node.val);                     // between the subtrees
    in(node.right, out);
}
private void post(TreeNode node, List<Integer> out) {
    if (node == null) return;
    post(node.left, out);
    post(node.right, out);
    out.add(node.val);                     // on the way back up
}
```

`TreeNode` is LeetCode’s usual shape: an `int val` and two child pointers, `left` and `right`.

### What it costs

**Time: O(n).** Each node is visited once and does constant work, as long as the combine step is O(1). **Space: O(h)**, where h is the height: the call stack holds one frame for each node on the current path. For a balanced tree h is about log₂ n; for a **vine** (every node has one child) h = n. Say “O(n) time, O(h) space, and h can be n” out loud; Chapter 10 shows what happens when h is a million.

### When this pattern fires

- **The input is a tree**, or anything shaped like one: an org chart, a folder hierarchy, an expression, a decision tree.
- **The question is about every node or about paths:** height, balance, root-to-leaf paths, the best path between any two nodes, ancestors.
- **A binary search tree**, and the question involves order: the k-th smallest, “is it valid?”, a range.
- **Rebuild or transmit a tree:** two listings, a string, a copy.

The brute force it replaces is usually **work repeated at every node**. Measuring a subtree’s height separately at every node costs O(n²) on a vine; returning heights from below costs O(n). Checking every pair of nodes for the longest or best path is O(n²) pairs, each walked in O(n); one bottom-up pass with a board does it in O(n).

<h2 id="invert">Chapter 1 · The mirror orchard</h2>

<Scene chapter="Chapter 1" title="The mirror orchard" mood="dawn">

A duke across the gorge has bought a cutting of the old tree, but his cliff faces the other way. He wants his tree to grow as the **mirror image** of yours: whatever hangs on your left must hang on his right, at every fork, all the way down.

The grafters line up at the trunk with saws. *"Start at the top,"* one says, *"swap the two big branches, then climb down and swap again."* Another wants to start at the tips.

The Keeper doesn’t pick a side. *"Suppose the left branch came back to you already mirrored, and the right branch too,"* she says. *"What would be left for you to do at the trunk?"*

</Scene>

**Problem: Invert Binary Tree · DFS basics**

**The contract:** `invertTree(node)` mirrors the whole subtree hanging from `node` and returns its root. Trust it for both children. Then the trunk’s job is tiny: hang the mirrored right subtree on the left, and the mirrored left subtree on the right.

    <Tree level={figures.invertAfter} name="after" />

</Figure>

<Trace title="Mirror the orchard" steps={invert} takeaway="Remember: trust the call. invertTree(child) returns a fully mirrored subtree; the current node only swaps the two results and returns itself." />

**Why it works:** the base case mirrors the empty tree (nothing to do). If both children come back mirrored, swapping them mirrors the whole subtree, because a mirror image is exactly “swap left and right, at every level”. Each call does one swap, so every fork is swapped exactly once.

**What stays true:** when `invertTree(node)` returns, the subtree below `node` is the mirror of what it was, and nothing outside that subtree has been touched.

<Reveal q="Does it matter whether you swap before or after the recursive calls?">

No. Swapping the two child pointers first and then inverting each child (preorder) works too, because mirroring a subtree doesn’t depend on which side it hangs from. Any order that swaps every node exactly once is correct, including an iterative walk with a stack or a queue. What breaks is assigning one pointer before you have saved the other — see the bug below.

</Reveal>

**Say it before you code:** contract — returns the mirrored subtree · base case — `null` returns `null` · direction — bottom-up (either works) · **O(n) time, O(h) space**.

<HintLadder hints={hints.invert}>

```java id=invertTree
public TreeNode invertTree(TreeNode root) {
    if (root == null) return null;              // an empty tree is its own mirror
    TreeNode left = invertTree(root.left);      // trust the call: the left subtree, mirrored
    TreeNode right = invertTree(root.right);    // trust the call: the right subtree, mirrored
    root.left = right;                          // swap the two mirrored halves
    root.right = left;
    return root;
}
```

**O(n) time, O(h) space** for the call stack. LeetCode allows at most 100 nodes here.

</HintLadder>

**Catch the bug:** the tempting two-liner assigns before it saves.

```java fragment
root.left = invertTree(root.right);    // left now points at the RIGHT subtree...
root.right = invertTree(root.left);    // ...which is inverted again and hung on the right as well
```

The original left subtree is never touched again, and the same damage happens at every level. On `[4, 2, 7, 1, 3, 6, 9]` every node ends up with two pointers to one copy of its right subtree: `[4, 7, 7, 9, 9, 9, 9]`. The 2, 1, 3 and 6 are gone. Save both results in locals first. [Solve Invert Binary Tree](https://leetcode.com/problems/invert-binary-tree/).

<h2 id="same-tree">Chapter 2 · Two cuttings</h2>

<Scene chapter="Chapter 2" title="Two cuttings" mood="dawn">

A buyer arrives with two cuttings in pots and a claim: they are the **same tree**, grown from the same branch. To prove it, he reads out the fruit on each, top to bottom: *one, two*. And again from the second pot: *one, two*.

You look closer. On the first tree the 2 hangs from the left of the 1. On the second, it hangs from the right.

The Keeper hands you a second rope. *"Two Climbers,"* she says, *"one on each tree, moving together. What must be true at every step for the trees to be the same — and what happens when one of them steps into thin air?"*

</Scene>

**Problem: Same Tree · DFS basics, two trees in lockstep**

**The contract:** `isSameTree(p, q)` returns `true` exactly when the two subtrees have the same shape and the same value at every position. Two trees are the same when **their roots match, their left subtrees are the same, and their right subtrees are the same**. That sentence is the code.

The only care needed is with empty spots, and it comes first: both empty is a match; exactly one empty is not. Only after that is it safe to read `p.val`.

<Figure caption="p = [1, 2] and q = [1, null, 2]. Listed root-first, both read 1, 2 — but the 2 hangs on different sides. Walking them together, the left pair is (2, empty): a mismatch.">

    <Tree level={figures.sameP} name="p" tones={{ 1: 'red' }} />
    <Tree level={figures.sameQ} name="q" tones={{ 2: 'red' }} />
  </div>
</Figure>

<Trace title="Two Climbers, one step at a time" steps={same} takeaway="Remember: both empty → true; one empty → false; then compare values and recurse on both pairs." />

**Why it works:** if the two roots match and both pairs of subtrees are identical (trust the calls), the trees agree at every position. If any check fails, there is a position where they differ.

**What stays true:** a call that returns `true` has checked every position of its two subtrees; `&&` stops the first time a call returns `false`, so the walk ends at the first difference.

<Reveal q="Why not just compare the two root-first listings?">

Because a listing without markers for the empty spots forgets the shape. `[1, 2]` and `[1, null, 2]` both list as 1, 2. Write a `#` for every empty spot and the listings become `1,2,#,#,#` and `1,#,2,#,#` — different, and now comparing strings would work. That idea is the whole of Chapter 12.

</Reveal>

**Say it before you code:** contract — `true` iff identical · base cases — both null, one null · direction — two trees, same direction, together · **O(min(m, n)) time, O(min(h₁, h₂)) space**: the walk can never go deeper or wider than the smaller tree.

<HintLadder hints={hints.same}>

```java id=isSameTree
public boolean isSameTree(TreeNode p, TreeNode q) {
    if (p == null && q == null) return true;     // both empty: identical
    if (p == null || q == null) return false;    // exactly one empty: the shapes differ
    return p.val == q.val                        // only now is it safe to read values
        && isSameTree(p.left, q.left)
        && isSameTree(p.right, q.right);
}
```

**O(min(m, n)) time, O(min(h₁, h₂)) space.**

</HintLadder>

**Catch the bug:** comparing values first (`if (p.val != q.val)` on line 1) throws `NullPointerException` as soon as one side is empty. And comparing value listings without markers says `[1, 2]` and `[1, null, 2]` are the same. [Solve Same Tree](https://leetcode.com/problems/same-tree/).

<h2 id="max-depth">Chapter 3 · How long a rope?</h2>

<Scene chapter="Chapter 3" title="How long a rope?" mood="dusk">

The rope-maker needs one number before the harvest: how many forks hang on the **longest** line from the trunk down to any fruit? One rope, cut once, must reach every tip.

Two pickers argue. The first wants to climb down every branch and keep a tally of how deep she has been. The second wants to sit at the trunk and wait for the branches to tell him how deep they go.

*"Both of you are right,"* the Keeper says, *"and you have just met the Climber and the Messenger. One of you carries a number down. The other waits for numbers to come up. Which number does each of you carry?"*

</Scene>

**Problem: Maximum Depth of Binary Tree · Bottom-up (and top-down)**

**Bottom-up, the Messenger:** `maxDepth(node)` returns the number of nodes on the longest path from `node` down to a leaf. An empty tree has depth 0. Otherwise it is one for this node, plus the deeper of its two sides: `1 + max(left, right)`.

**Top-down, the Climber:** carry the depth of the current node as a parameter. Every node updates the deepest value seen so far; the children are visited with `depth + 1`.

<Figure caption="[3, 9, 20, null, null, 15, 7], each node labelled with what maxDepth returns for it. The leaves report 1; node 20 reports 1 + max(1, 1) = 2; the root reports 1 + max(1, 2) = 3.">
  <Tree level={figures.depth.level} notes={figures.depth.notes} tones={{ 0: 'gold' }} />
</Figure>

<Trace title="Down and back up" steps={depth} takeaway="Remember: bottom-up returns 1 + max(left, right) with 0 for an empty tree; top-down passes depth + 1 to each child and keeps the largest." />

**Why it works:** the longest path from a node goes through one of its children (or stops at the node, if it is a leaf). Trusting the calls, the children already know their depths; the deeper one, plus this node, is the answer.

**What stays true:** bottom-up — each return value is the exact depth of that subtree. Top-down — when the Climber stands on a node, his `depth` parameter is exactly the number of nodes from the root to here, and `best` is the deepest node seen so far.

<Reveal q="Which direction should you reach for first?">

Bottom-up when the answer for a node depends on what is **below** it (heights, sizes, balance). Top-down when it depends on what is **above** it (depth so far, a sum still to find, the bounds a search tree imposes). Depth is the rare question where both read naturally — which is exactly why it is the right place to learn the difference.

</Reveal>

**Say it before you code:** contract — returns the depth of the subtree · base case — 0 for `null` · direction — bottom-up (or carry depth down) · **O(n) time, O(h) space**.

<HintLadder hints={hints.depth}>

```java id=maxDepth
public int maxDepth(TreeNode root) {
    if (root == null) return 0;                                   // an empty tree has depth 0
    return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}
```

The same answer with the Climber carrying the depth down:

```java id=maxDepthTopDown
private int best;                               // deepest node seen so far

public int maxDepth(TreeNode root) {
    best = 0;
    visit(root, 1);
    return best;
}

private void visit(TreeNode node, int depth) {  // depth = nodes from the root down to here
    if (node == null) return;
    best = Math.max(best, depth);
    visit(node.left, depth + 1);
    visit(node.right, depth + 1);
}
```

**O(n) time, O(h) space** for both.

</HintLadder>

**Catch the bug:** swap `max` for `min` to get the *minimum* depth, and it breaks. On the vine `[2, null, 3, null, 4, null, 5, null, 6]`, `1 + Math.min(left, right)` returns **1**: the root’s empty left side counts as a path of length 0. But an empty spot is not a leaf; the answer is 5. When one side is empty, only the other side has leaves:

```java id=minDepth
public int minDepth(TreeNode root) {
    if (root == null) return 0;
    if (root.left == null) return 1 + minDepth(root.right);    // an empty side is not a leaf:
    if (root.right == null) return 1 + minDepth(root.left);    // only the other side has leaves
    return 1 + Math.min(minDepth(root.left), minDepth(root.right));
}
```

<h2 id="balanced">Chapter 4 · The wind inspector</h2>

<Scene chapter="Chapter 4" title="The wind inspector" mood="storm">

The autumn gales are coming, and the wind inspector has a rule: a tree survives only if, **at every fork**, the two sides hang to within one fork of each other. A lopsided fork snaps.

She looks at the old pear tree from the trunk. Left side: three forks deep. Right side: three forks deep. *"Perfectly even,"* she says, and reaches for her stamp.

The Keeper points halfway down the left side, where one branch hangs two forks deep and its partner is bare wood. *"Even at the top,"* she says. *"But the storm doesn’t only blow on the trunk. How does that fork tell the trunk it is about to snap — without everyone measuring everything again?"*

</Scene>

**Problem: Balanced Binary Tree · Bottom-up with an early verdict**

A tree is height-balanced when, **at every node**, the heights of the two subtrees differ by at most 1. Each node needs its children’s heights to check itself, and the parent needs this node’s height in turn. So the Messenger carries the height up — and needs a way to say “broken” too.

The trick: **return −1 for “this subtree is unbalanced”**. No real height is negative, so −1 can never be confused with one. Each node checks its children’s reports: if either is −1, or they differ by more than 1, it returns −1; otherwise it returns its height.

<Figure caption="[1, 2, 2, 3, null, null, 3, 4, null, null, 4]. At the root the two sides are both height 3 — even. But each node 2 has one side of height 2 and one of height 0: a gap of 2. The tree is not balanced.">
  <Tree level={figures.balanced.level} notes={figures.balanced.notes} tones={{ 1: 'red', 2: 'red' }} />
</Figure>

<Trace title="Where does it lean?" steps={balanced} takeaway="Remember: return the height, or −1 the moment anything below is unbalanced, and pass −1 straight up." />

**Why it works:** a node is balanced exactly when both children are balanced and their heights differ by at most 1. A non-negative report from a child certifies both facts for that child’s subtree at once; this node adds its own check.

**What stays true:** a non-negative return value means the whole subtree is balanced **and** is its exact height. −1 means some node inside it is not balanced.

<Reveal q="Why not a separate isBalanced() at every node that calls height()?">

It is correct, and it is the version most people write first. But each node then re-measures its whole subtree. On a vine of n nodes that is n + (n − 1) + … + 1 = O(n²) work; on a balanced tree, O(n log n). Returning the height and the verdict together visits each node once: **O(n)**.

</Reveal>

**Say it before you code:** contract — returns the height, or −1 if unbalanced · base case — 0 for `null` · direction — bottom-up, stop early on −1 · **O(n) time, O(h) space**.

<HintLadder hints={hints.balanced}>

```java id=isBalanced
public boolean isBalanced(TreeNode root) {
    return height(root) != -1;
}

private int height(TreeNode node) {             // the height, or -1 if anything here is unbalanced
    if (node == null) return 0;
    int left = height(node.left);
    if (left == -1) return -1;                  // the verdict is already in: pass it up
    int right = height(node.right);
    if (right == -1) return -1;
    if (Math.abs(left - right) > 1) return -1;  // this node is the one that leans
    return 1 + Math.max(left, right);
}
```

**O(n) time, O(h) space.**

</HintLadder>

**Catch the bug:** checking the gap only at the root, `Math.abs(height(root.left) - height(root.right)) <= 1`, says **yes** to the figure’s tree (3 and 3). The rule holds at every node, so every node must check it. [Solve Balanced Binary Tree](https://leetcode.com/problems/balanced-binary-tree/).

<h2 id="diameter">Chapter 5 · The longest zip line</h2>

<Scene chapter="Chapter 5" title="The longest zip line" mood="dusk">

For the harvest festival the guild strings a zip line along the branches of the old tree: from one fruiting tip, up through the forks, and down to another tip, never using a branch twice. The longer the better. The children have been promised the **longest** one.

Everyone assumes it runs over the trunk. You measure, and it doesn’t: the longest route bends at a fork two-thirds of the way down the left side and never comes near the top.

The Messenger is confused. *"So what do I carry up?"* he asks. *"The length of the route through my fork? My parent can’t use that — he can’t hang a third rope off a bend."*

The Keeper nods toward the gate, where Best is wiping his chalk board clean. *"Then perhaps you carry one number up,"* she says, *"and send another one to the gate."*

</Scene>

**Problem: Diameter of Binary Tree · Bottom-up: return one thing, record another**

This chapter holds the single most important idea in tree problems. Take it slowly.

**Every path in a tree has exactly one highest node — the place where it bends.** At that node, the path goes down one arm into the left subtree and down another arm into the right subtree. The longest path that bends at a node therefore has length

```text
(longest arm down the left) + (longest arm down the right)  =  L + R   edges
```

where `L` and `R` are the heights of the two subtrees, counted in nodes. (A height of 2 below means 2 edges from this node down that side; an empty side contributes 0.)

So the diameter is the largest `L + R` over **all** nodes. To compute `L + R` at a node, you need the heights of its children. And the children can only give you heights if **height** is what the Messenger carries.

But the answer is not a height. Look at what each fork could report:

- **Its height, `1 + max(L, R)`.** The parent can extend that: one arm, plus the edge up to the parent. This is what the parent needs.
- **Its bend, `L + R`.** The parent can’t use it: adding the parent to a path that already bends here makes a fork, a Y-shape, not a path.

The two numbers serve two different audiences. So the function does both: **it returns the height to its parent, and it sends the bend to the gate board.** When the last Messenger reaches the root, the return value is just the root’s height. The answer is on the board.

<Mermaid code={`flowchart LR
  K["children report heights L and R"] --> N["this node"]
  N -->|"L + R: a bend, cannot be extended"| B[("gate board: Best = max(Best, L + R)")]
  N -->|"1 + max(L, R): one arm, the parent can extend it"| P["parent"]`} />

<Figure caption="[1, 2, null, 3, 4, 5, null, null, 6, 7, null, null, 8], each node labelled with the height it reports. The longest path, 7–5–3–2–4–6–8, bends at node 2: L + R = 3 + 3 = 6 edges. The root never sees it: its own bend is 4 + 0 = 4, and it returns its height, 5. The diameter is what Best holds: 6.">
  <Tree level={figures.diameter.level} notes={figures.diameter.notes} path={figures.diameter.path} tones={{ 1: 'gold' }} />
</Figure>

Three different numbers come out of that tree, and confusing them is how this problem is usually failed: **the root returns 5** (a height), **the path through the root is 4**, and **the diameter is 6**. Try the Messenger drill in the [practice cliff](#playground); one of its cases bends below the root on purpose.

<Trace title="Report up, write to the gate" steps={diameter} takeaway="Remember: return 1 + max(L, R) to the parent; send L + R to the board at every node; when the root returns, read the board." />

**Why it works:** every path has one highest node, and at that node its length is at most `L + R` — with equality for the path that goes down the longest arm on each side. The walk visits every node, so it computes `L + R` at every possible bend and keeps the largest.

**What stays true:** when `height(node)` returns, (1) its return value is the exact height of `node`’s subtree, and (2) `best` is at least the length of every path whose bend lies inside that subtree.

**When the last call returns:** say both values out loud before you write any code. “The helper returns the root’s height. `best` holds the longest bend anywhere. I return `best`.” This is the narration interviewers listen for.

<Reveal q="Isn’t a field like best a global variable? Can I avoid it?">

It is shared state, scoped to one call of the public method — that’s why the code resets it at the start. If you prefer no field, pass a one-element array (`int[] best = {0}`) down to the helper, or return a pair `(height, bestInside)` from every call and combine the pairs: `bestInside = max(leftBest, rightBest, L + R)`. All three are the same idea — the Messenger carries one number for the parent, and the record is kept somewhere he can’t mix it up.

</Reveal>

<Reveal q="Edges or nodes? LeetCode counts this diameter in edges.">

`L + R` with heights counted in nodes is exactly the number of **edges** on the bent path: L edges down one side, R down the other. If a problem wants the number of **nodes** on the path, it is `L + R + 1`. A single node has diameter 0 edges, 1 node. Check which one the problem asks before you submit.

</Reveal>

**Say it before you code:** contract — returns the height; records the bend · base case — 0 for `null` · direction — bottom-up, plus a board · **O(n) time, O(h) space**.

<HintLadder hints={hints.diameter}>

```java id=diameter
private int best;                                  // the gate board: the longest bend seen anywhere

public int diameterOfBinaryTree(TreeNode root) {
    best = 0;
    height(root);                                  // its return value (the root's height) is not the answer
    return best;
}

private int height(TreeNode node) {                // promise: nodes on the longest path down from node
    if (node == null) return 0;
    int left = height(node.left);
    int right = height(node.right);
    best = Math.max(best, left + right);           // the path that bends HERE: two arms, in edges
    return 1 + Math.max(left, right);              // the parent can extend only ONE arm
}
```

**O(n) time, O(h) space.**

</HintLadder>

**Catch the bug:** computing `height(root.left) + height(root.right)` once, at the root, finds only paths through the root. On the figure’s tree it returns **4** instead of 6. Every node is a possible bend. [Solve Diameter of Binary Tree](https://leetcode.com/problems/diameter-of-binary-tree/).

<h2 id="max-path-sum">Chapter 6 · Honey and wasps</h2>

<Scene chapter="Chapter 6" title="Honey and wasps" mood="storm">

The bee-keepers have hung hives at every fork of the cliff tree. Most forks give honey. Some give wasps, and wasps cost you: a fork worth −10 takes ten jars off whatever run passes through it.

The keepers want the sweetest run along the branches — from any fork to any fork, no branch twice. It needn’t touch the trunk, or a tip.

You recognise the shape at once: a path with one bend, the Messenger carrying an arm up, Best at the gate. But the wasps worry you. *"What if one whole arm is wasps?"*

*"Then don’t take it,"* says the Keeper. *"A run may stop wherever it likes. When is an arm worth nothing at all?"*

</Scene>

**Problem: Binary Tree Maximum Path Sum · Bottom-up: return one thing, record another**

The same shape as Chapter 5, with values instead of lengths:

- The Messenger carries the **gain**: the best sum of a path that starts at this node and goes **down one side** (or stops here). `gain(node) = node.val + max(0, gain(left), gain(right))`, written below as two clamped arms.
- Every node sends its **bend** to the board: `node.val + left + right`, where each arm has been **clamped at 0**. A negative arm is dropped; the path can always stop at this node.
- The board starts at `Integer.MIN_VALUE`, not 0: the path must contain at least one node, and if every value is negative the answer is negative.

<Figure caption="LeetCode’s [−10, 9, 20, null, null, 15, 7]. Node 20 reports gain 20 + 15 = 35 to its parent and writes its bend, 15 + 20 + 7 = 42, on the board. The root’s bend is −10 + 9 + 35 = 34 and it returns −10 + 35 = 25. The answer is the board: 42.">
  <Tree level={figures.maxPath.level} notes={figures.maxPath.notes} path={figures.maxPath.path} tones={{ 0: 'red' }} />
</Figure>

<Trace title="When is an arm worth nothing?" steps={maxPath} takeaway="Remember: clamp each arm at 0, record node + left + right, return node + max(left, right), and start the board at Integer.MIN_VALUE." />

**Why it works:** the best path bends at some highest node. Its best version takes, on each side, either nothing or the best downward path from that child — which is exactly the clamped gain. The walk evaluates every possible bend.

**What stays true:** `gain(node)` is the best sum of a downward path starting at `node` (it includes `node.val`, so it can be negative), and `best` is at least the sum of every path whose bend lies inside the subtree already walked.

<Reveal q="Why clamp the arms but never the node itself?">

Because the bend node is on the path by definition; it is the one node the path cannot skip. The arms are optional: “stop here” is always allowed, and it is worth 0 extra. So arms are clamped at 0; the node’s own value is always counted. That is also why a tree of all negatives returns its least negative value, never 0.

</Reveal>

**Say it before you code:** contract — returns the best one-sided gain; records the best bend · base case — gain 0 for `null` · direction — bottom-up, plus a board starting at `Integer.MIN_VALUE` · **O(n) time, O(h) space**.

<HintLadder hints={hints.maxPath}>

```java id=maxPathSum
private int best;                                    // the board: the best bend seen anywhere

public int maxPathSum(TreeNode root) {
    best = Integer.MIN_VALUE;                        // values can all be negative: 0 would be a lie
    gain(root);
    return best;
}

private int gain(TreeNode node) {                    // promise: best sum of a path starting here, going down
    if (node == null) return 0;
    int left = Math.max(0, gain(node.left));         // a losing arm is dropped, not carried
    int right = Math.max(0, gain(node.right));
    best = Math.max(best, node.val + left + right);  // the path that bends HERE
    return node.val + Math.max(left, right);         // only one arm can continue up to the parent
}
```

**O(n) time, O(h) space.** LeetCode’s bounds (at most 3 × 10⁴ nodes, values within ±1000) keep every sum within ±3 × 10⁷, inside `int`.

</HintLadder>

**Catch the bug:** two classics. Starting `best` at 0: on `[−3]` it returns **0**, a path that doesn’t exist (the answer is −3). Forgetting to clamp: on `[2, −1]` the root takes the −1 arm and returns **1** instead of 2. [Solve Binary Tree Maximum Path Sum](https://leetcode.com/problems/binary-tree-maximum-path-sum/).

<Scene chapter="Chapter 7" title="Two goats on the cliff" mood="dusk">

Two goats have wandered down the cliff tree and stuck themselves at two different forks, bleating. There is one rope long enough for one rescue, and it must be tied at the **lowest** fork from which both goats can be reached by climbing only downward.

You can’t see either goat from the trunk. But every fork can shout up to the one above it.

**Problem: Lowest Common Ancestor of a Binary Tree · Bottom-up search**

**The contract:** `lowestCommonAncestor(node, p, q)` returns

- `p` (or `q`) if exactly one of them is in this subtree,
- the lowest common ancestor if **both** are,
- `null` if neither is.

The base case covers the first line: if `node` is `null`, `p` or `q`, return it. Otherwise ask both children. If **both** sides report something, `p` and `q` are split across this node — it is the lowest node that sees both, so return it. If only one side reports something, pass that up unchanged.

<Figure caption="LeetCode’s [3, 5, 1, 6, 2, 0, 8, null, null, 7, 4], with p = 6 and q = 4. Each node is labelled with what its call returns. Node 2 passes q up; node 5 hears 6 from the left and 4 from the right, so it returns itself; everything above just passes 5 along.">
  <Tree level={figures.lca.level} notes={figures.lca.notes} tones={{ 3: 'blue', 10: 'blue', 1: 'gold' }} spread={64} />
</Figure>

<Trace title="What does each fork shout?" steps={lca} takeaway="Remember: return the node if it is null, p or q; if both children return something, return the node; otherwise return whichever child found something." />

**Why it works:** the lowest common ancestor is the unique node where `p` and `q` either sit in different subtrees, or where the node is one of them and the other lies below. The first case is detected by “both sides non-null”. In the second case, the call returns the node at once — and since the problem promises both exist, if nothing turns up elsewhere, the other one must be below it.

**What stays true:** each call returns the most informative thing its subtree contains: the meeting point if both are inside, otherwise whichever one is inside, otherwise `null`. Once a meeting point is returned, every ancestor sees it on one side and `null` on the other, and passes it up untouched.

<Reveal q="What if q might not be in the tree at all?">

Then this code is wrong: for p = 5 and a missing q, it returns 5. The early return at `p` assumed the other node exists. When existence isn’t promised (LeetCode’s premium “LCA II”), walk the whole tree, count how many of p and q you actually found, and return the answer only if the count is 2.

</Reveal>

**Say it before you code:** contract — returns p, q, their meeting point, or null · base case — null, p or q return themselves · direction — bottom-up · **O(n) time, O(h) space**. Compare nodes by reference (`root == p`), not by value.

<HintLadder hints={hints.lca}>

```java id=lca
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    if (root == null || root == p || root == q) return root;      // found one (or nothing)
    TreeNode left = lowestCommonAncestor(root.left, p, q);
    TreeNode right = lowestCommonAncestor(root.right, p, q);
    if (left != null && right != null) return root;               // split here: the lowest meeting point
    return left != null ? left : right;                           // pass up whatever was found
}
```

**O(n) time, O(h) space.**

</HintLadder>

**Catch the bug:** dropping the “both sides” line and always passing up `left != null ? left : right`. On the figure with p = 6 and q = 4, node 5 passes up 6, and the answer comes out **6** — which is not an ancestor of 4. [Solve Lowest Common Ancestor of a Binary Tree](https://leetcode.com/problems/lowest-common-ancestor-of-a-binary-tree/).

<h2 id="path-sum-ii">Chapter 8 · Twenty-two plums</h2>

<Scene chapter="Chapter 8" title="Twenty-two plums" mood="dawn">

The jam-maker wants crates of **exactly twenty-two** plums, and she wants each crate picked along one run: from the trunk straight down to a fruiting tip, taking every plum at every fork on the way. She wants a list of every run that works.

The Climber ties on his rope and takes a slate. At the trunk he writes 22. At each fork he picks the plums and subtracts. He also chalks the fork’s number on his rope, so he can tell the jam-maker the route.

Halfway down, he reaches a tip with 2 left on the slate and 2 plums on the branch. Then he has to climb back up and try the other side.

*"Careful,"* says the Keeper. *"What comes off the rope on the way back up? And what do you hand the jam-maker — the rope, or a copy?"*

</Scene>

**Problem: Path Sum II · Top-down state, with backtracking**

The answer depends on the whole path from the root, so the Climber carries it down:

- **`remaining`**: the target minus everything on the path so far. Passed by value, so each call gets its own copy, and nothing needs undoing.
- **`path`**: one shared list of the nodes from the root to here. Added to on the way down, so it **must be undone on the way back up** — that is backtracking.

At a **leaf** (both children empty) with `remaining == 0`, record a **copy** of the path.

<Figure caption="LeetCode’s [5, 4, 8, 11, null, 13, 4, 7, 2, null, null, 5, 1] with target 22. Each node shows what is left to find after taking it. Two leaves reach 0: 5–4–11–2 and 5–8–4–5. Leaf 7 overshoots (−5) and leaf 1 falls short (4).">
  <Tree level={figures.pathSum.level} notes={figures.pathSum.notes} path={figures.pathSum.path} pathTone="green" tones={{ 8: 'green', 11: 'green' }} spread={62} />
</Figure>

<Trace title="Down with a slate, up with a rope" steps={pathSum} takeaway="Remember: subtract on the way down, record a COPY at a real leaf when nothing is left, and remove the node from the path on the way back up." />

**Why it works:** the walk visits every node, so it reaches every leaf; at each leaf, `path` is exactly the root-to-leaf path and `remaining` is exactly target minus its sum.

**What stays true:** on entry to `walk(node)` and again on exit, `path` holds exactly the nodes from the root down to `node`’s parent. Every add has one matching remove.

<Reveal q="Values can be negative. Can the Climber stop as soon as remaining drops below 0?">

No. A later negative value can bring it back: with target 1, the path 2 → −1 is fine even though `remaining` is −1 after the 2. Pruning on a negative remainder is only safe when every value is non-negative, and the problem doesn’t promise that.

</Reveal>

**Say it before you code:** contract — `walk(node, remaining, path)` adds every qualifying root-to-leaf path through `node` · base case — return at `null` · direction — top-down, with backtracking · **O(n) visits, plus O(h) to copy each recorded path: O(n · h), so O(n²) in the worst case; O(h) extra space besides the output.**

<HintLadder hints={hints.pathSum}>

```java id=pathSum
public List<List<Integer>> pathSum(TreeNode root, int targetSum) {
    List<List<Integer>> result = new ArrayList<>();
    walk(root, targetSum, new ArrayList<>(), result);
    return result;
}

private void walk(TreeNode node, int remaining, List<Integer> path, List<List<Integer>> result) {
    if (node == null) return;
    path.add(node.val);                                   // step down: the path grows
    remaining -= node.val;                                // a local copy: nothing to undo
    if (node.left == null && node.right == null && remaining == 0)
        result.add(new ArrayList<>(path));                // a COPY: path keeps changing after this
    walk(node.left, remaining, path, result);
    walk(node.right, remaining, path, result);
    path.remove(path.size() - 1);                         // step back up: undo the add
}
```

LeetCode’s bounds (at most 5000 nodes, values and the target within ±1000) keep every sum far inside `int`.

</HintLadder>

**Catch the bug:** three classics. Adding `path` itself instead of a copy: every stored answer is the same list, which is empty when the walk ends — LeetCode’s example returns `[[], []]`. Checking `remaining == 0` at an **empty spot** instead of at a leaf: on `[1, 2]` with target 1 it records `[1]`, though 1 is not a leaf (and real leaves get recorded twice, once per empty child). Forgetting the `remove`: the right side sees nodes from the left side’s path. [Solve Path Sum II](https://leetcode.com/problems/path-sum-ii/).

<h2 id="validate-bst">Chapter 9 · The sorted grove</h2>

<Scene chapter="Chapter 9" title="The sorted grove" mood="dawn">

On the east cliff grows the sorted grove. Its grafters swear by one rule: at every fork, **everything** hanging on the left is smaller than the fork, and **everything** on the right is larger. Buyers pay double for sorted trees, because you can find any fruit by turning left or right at each fork.

The inspector checks one tree fork by fork. Left child smaller than its parent? Yes. Right child larger? Yes. Every fork passes. She stamps it.

A buyer brings it back the next day. He went looking for a 3, turned left at the trunk because 3 is smaller than 5, and never found it. The 3 is hanging on the right.

*"Every fork passed,"* the inspector says.

*"Every fork passed its parent,"* says the Keeper. *"What does a fork owe to all the forks above it?"*

</Scene>

**Problem: Validate Binary Search Tree · Top-down bounds**

A binary search tree (BST) requires, at **every** node, that all values in its left subtree are **strictly smaller** and all values in its right subtree are **strictly larger** (LeetCode’s definition; no duplicates). Comparing a node with its parent checks only part of that.

**Pass a window down.** Each node must fit strictly inside `(low, high)`. The root’s window is unbounded. Going **left**, the floor stays and the **ceiling drops** to the node’s value. Going **right**, the **floor rises** to the node’s value and the ceiling stays. Two numbers summarise every constraint from every ancestor.

<Figure caption="[5, 4, 6, null, null, 3, 7], each node with the window its ancestors give it. Every parent–child pair looks fine (3 < 6), but 3 sits in 5’s right subtree, so its window is (5, 6). 3 is below the floor: not a BST.">
  <Tree level={figures.validate.level} notes={figures.validate.notes} tones={{ 5: 'red' }} spread={66} />
</Figure>

<Trace title="Carry the window down" steps={validate} takeaway="Remember: left lowers the ceiling to the parent, right raises the floor to the parent, and compare strictly with bounds wider than int." />

**Why it works:** an ancestor constrains a node only through the side the node hangs on. Going down, the most recent ancestor you went left from is the tightest ceiling, and the most recent you went right from is the tightest floor — exactly what `(low, high)` remembers. So a node fits its window if and only if it satisfies every ancestor at once.

**What stays true:** when `valid(node, low, high)` is called, `(low, high)` is exactly the set of values a node at this position may hold, and every node visited so far has fit its window.

<Reveal q="Is there a way that doesn’t carry bounds?">

Yes: **a tree is a BST exactly when its inorder listing is strictly increasing.** Walk left, node, right, and remember only the previous value; any value that isn’t strictly larger than the previous one breaks it. Same O(n) time and O(h) space. Use `null` (or a `long`) as “nothing yet”, so that a first value of `Integer.MIN_VALUE` isn’t mistaken for a duplicate.

```java id=isValidBSTInorder
private Integer prev;                          // the last value visited in order; null = none yet

public boolean isValidBST(TreeNode root) {
    prev = null;
    return inorder(root);
}

private boolean inorder(TreeNode node) {
    if (node == null) return true;
    if (!inorder(node.left)) return false;
    if (prev != null && node.val <= prev) return false;   // must be STRICTLY increasing
    prev = node.val;
    return inorder(node.right);
}
```

</Reveal>

**Say it before you code:** contract — `true` iff every value in the subtree fits strictly inside `(low, high)` · base case — `null` is valid · direction — top-down bounds · **O(n) time, O(h) space**.

<HintLadder hints={hints.validate}>

```java id=isValidBST
public boolean isValidBST(TreeNode root) {
    return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);       // wider than any int: no edge cases
}

private boolean valid(TreeNode node, long low, long high) {   // every value here must be inside (low, high)
    if (node == null) return true;
    if (node.val <= low || node.val >= high) return false;
    return valid(node.left, low, node.val)                    // going left: the ceiling drops to my value
        && valid(node.right, node.val, high);                 // going right: the floor rises to my value
}
```

**O(n) time, O(h) space.**

</HintLadder>

**Catch the bug:** two, both on LeetCode’s test list. Checking each node only against its children passes `[5, 4, 6, null, null, 3, 7]`, which is invalid. And starting the bounds as `int`s, `(Integer.MIN_VALUE, Integer.MAX_VALUE)`, rejects the one-node tree `[2147483647]`, because 2147483647 is not strictly below `Integer.MAX_VALUE`. `long` bounds (or `Integer` bounds where `null` means “none”) fix it. [Solve Validate Binary Search Tree](https://leetcode.com/problems/validate-binary-search-tree/).

<Scene chapter="Chapter 10" title="The night harvest" mood="night">

You look at the sorted tree, then at the basket. *"Why is the top of the basket always the next smallest?"*

*"Count to three and tell me,"* says the Keeper. *"Then tell me why you never had to look at the rest of the tree."*

**Problem: Kth Smallest Element in a BST · Inorder = sorted**

In a BST, **inorder (left, node, right) visits the values in increasing order**: everything left of a node is smaller, so it comes first; everything right is larger, so it comes after. The k-th node visited in order is the k-th smallest. Stop there.

The **iterative inorder walk** makes stopping easy, and it doesn’t use the call stack at all:

1. **Go left as far as you can**, putting every node you pass into the Basket (a stack).
2. **Pop** the top: it is the smallest value not yet visited. Visit it.
3. **Step right** once, and repeat from 1.

<Figure caption="[5, 3, 6, 2, 4, null, null, 1], each node labelled with its place in sorted order. To answer k = 3 the walk pushes 5, 3, 2, 1, then pops 1, 2, 3. Nodes 4, 5 and 6 are never visited.">
  <Tree level={figures.kth.level} notes={figures.kth.notes} tones={{ 1: 'gold' }} />
</Figure>

<Trace title="The Basket" steps={kth} takeaway="Remember: push the whole left chain, pop to visit, then step right. Stop at the k-th pop: O(h + k)." />

Try **The Basket** in the [practice cliff](#playground). One of its wrong buttons visits a node before its left side, and the drill shows you which smaller value you just skipped.

**Why the Basket works:** the basket holds, bottom to top, the ancestors of `cur` whose left subtrees are still being explored, in decreasing order of value. When `cur` falls off the bottom of a left chain, nothing smaller than the basket’s top is left unvisited, so the top is the next value in sorted order.

**What stays true:** values come out of the basket in strictly increasing order (non-decreasing if the tree allows duplicates), and the k-th one out is the k-th smallest.

<Reveal q="And recursively?">

The recursive inorder walk works too, if the counter lives somewhere every call shares (a field), so a call deep on the left can tell the root “I already found it”:

```java id=kthSmallestRecursive
private int count, answer;

public int kthSmallest(TreeNode root, int k) {
    count = k;
    walk(root);
    return answer;
}

private void walk(TreeNode node) {
    if (node == null || count == 0) return;        // count == 0: already found, stop everywhere
    walk(node.left);
    if (count > 0 && --count == 0) answer = node.val;
    walk(node.right);
}
```

</Reveal>

**Say it before you code:** contract — the k-th node visited in order · stop at the k-th pop · direction — inorder (left, node, right) · **O(h + k) time, O(h) space.**

<HintLadder hints={hints.kth}>

```java id=kthSmallest
public int kthSmallest(TreeNode root, int k) {
    Deque<TreeNode> basket = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !basket.isEmpty()) {
        while (cur != null) {                // walk the left chain, saving each fork to come back to
            basket.push(cur);
            cur = cur.left;
        }
        cur = basket.pop();                  // the smallest value not yet visited
        if (--k == 0) return cur.val;
        cur = cur.right;                     // its right subtree comes next in sorted order
    }
    return -1;                               // k > number of nodes (LeetCode promises it won't be)
}
```

**O(h + k) time, O(h) space.**

</HintLadder>

<h3 id="vines">When the tree is a vine</h3>

Every recursive solution in this book uses **O(h) stack space**, and h can be n. A tree built by inserting sorted values into a BST is a **vine**: one long chain. Java does not optimise tail calls, and its default thread stack typically holds thousands to tens of thousands of frames, depending on the frame size and the `-Xss` setting.

The checker for this page does the experiment. On a vine of **10,000** nodes, the recursive `maxDepth` from Chapter 3 finishes with default settings. On a vine of **1,000,000** nodes it throws `StackOverflowError`, while the iterative walks below handle it. Most of this book’s LeetCode problems cap n at 10⁴ or fewer, where recursion is accepted. Know the risk anyway, and know the fix: **any recursion can become a loop with your own stack, which lives on the heap.**

The general iterative inorder walk, and an iterative depth that carries the Climber’s parameter alongside each node:

```java id=inorderTraversal
public List<Integer> inorderTraversal(TreeNode root) {
    List<Integer> out = new ArrayList<>();
    Deque<TreeNode> basket = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !basket.isEmpty()) {
        while (cur != null) { basket.push(cur); cur = cur.left; }
        cur = basket.pop();
        out.add(cur.val);
        cur = cur.right;
    }
    return out;
}
```

```java id=maxDepthIterative
public int maxDepth(TreeNode root) {
    if (root == null) return 0;
    Deque<TreeNode> nodes = new ArrayDeque<>();
    Deque<Integer> depths = new ArrayDeque<>();        // the parameter the Climber would have carried
    nodes.push(root);
    depths.push(1);
    int best = 0;
    while (!nodes.isEmpty()) {
        TreeNode node = nodes.pop();
        int d = depths.pop();
        best = Math.max(best, d);
        if (node.left != null) { nodes.push(node.left); depths.push(d + 1); }
        if (node.right != null) { nodes.push(node.right); depths.push(d + 1); }
    }
    return best;
}
```

<Reveal q="Follow-up: the BST changes often, and k-th smallest is asked often. Now what?">

Store in every node the **size of its subtree**, and keep it updated on insert and delete. Then at each node: if `k ≤ size(left)`, go left; if `k == size(left) + 1`, this is it; otherwise go right with `k − size(left) − 1`. Each query is O(h), and O(log n) if the tree is kept balanced. This is an *order-statistic tree*.

</Reveal>

**Catch the bug:** the recursive version with the counter passed as an `int` **parameter**. Java passes ints by value, so a decrement inside the left call never reaches the parent. On `[5, 3, 6, 2, 4, null, null, 1]` with k = 3, no call ever sees its copy reach 0, and the function returns its default, **−1**. Keep the counter in a field, as above. [Solve Kth Smallest Element in a BST](https://leetcode.com/problems/kth-smallest-element-in-a-bst/) · [Binary Tree Inorder Traversal](https://leetcode.com/problems/binary-tree-inorder-traversal/) (do it iteratively).

**Problem: Construct Binary Tree from Preorder and Inorder Traversal · Construction**

- **Preorder** lists a subtree’s root **first**, then its whole left subtree, then its whole right subtree.
- **Inorder** lists the left subtree, then the root, then the right subtree. So **the root’s position in inorder splits the rest into left and right**, and tells you each side’s size.

Keep one cursor into preorder. To build the subtree whose inorder is `inorder[lo..hi]`: the next unused preorder value is its root; find it in inorder at `mid`; build the left subtree from `inorder[lo..mid − 1]`, **then** the right from `inorder[mid + 1..hi]`. Build left first, because that is the order preorder lists them. A map from value to inorder index makes each lookup O(1).

<Figure caption="preorder [3, 9, 20, 15, 7] names the root, 3. Its position in inorder [9, 3, 15, 20, 7] splits the rest: [9] is the left subtree, [15, 20, 7] the right. Recursing, 20 is the next root, and it splits [15, 20, 7] into 15 and 7.">

  <ArrayStrip name="preorder" values={figures.build.pre} pointers={[{ at: 0, label: 'root' }]} tones={{ 0: 'hot' }} />
  <ArrayStrip name="inorder" values={figures.build.inorder} pointers={[{ at: 1, label: 'root' }]} regions={[{ from: 0, to: 0, label: 'left', tone: 'blue' }, { from: 2, to: 4, label: 'right', tone: 'green' }]} tones={{ 1: 'hot' }} />
</Figure>

<Trace title="Which ledger names the root?" steps={build} takeaway="Remember: the next preorder value is the root; its inorder position splits left from right; build left first." />

**Why it works:** in both listings, every subtree occupies one contiguous block. In preorder that block starts with its root and lists the left block before the right block; in inorder the root sits between the two blocks. So the shared cursor, consumed left subtree first, always points at the root of the subtree being built.

**What stays true:** when `build(lo, hi)` starts, `preorder[next]` is the root of the subtree whose inorder is `inorder[lo..hi]`; when it returns, `next` has moved past exactly that subtree’s values.

<Reveal q="Why must the values be unique? And what about postorder + inorder?">

With duplicates, “find the root in inorder” is ambiguous: preorder `[1, 1]` with inorder `[1, 1]` fits both a left child and a right child. LeetCode promises unique values.

With **postorder + inorder**, the root is the **last** postorder value. Walk the cursor from the end, and build the **right** subtree first, because postorder read backwards lists root, right, left. Preorder + postorder alone can’t always tell a lone child’s side: `[1, 2]` and `[1, null, 2]` have the same preorder (1, 2) and the same postorder (2, 1).

</Reveal>

**Say it before you code:** contract — `build(lo, hi)` returns the subtree whose inorder is `inorder[lo..hi]` · base case — empty range returns `null` · direction — preorder cursor, left first · **O(n) time with the map, O(n) space** (the map, plus O(h) stack).

<HintLadder hints={hints.build}>

```java id=buildTree
private int next;                                  // index of the next unused root in preorder
private Map<Integer, Integer> where;               // value -> its index in inorder

public TreeNode buildTree(int[] preorder, int[] inorder) {
    next = 0;
    where = new HashMap<>();
    for (int i = 0; i < inorder.length; i++) where.put(inorder[i], i);
    return build(preorder, 0, inorder.length - 1);
}

private TreeNode build(int[] preorder, int lo, int hi) {   // the subtree whose inorder is inorder[lo..hi]
    if (lo > hi) return null;
    TreeNode root = new TreeNode(preorder[next++]);        // preorder: the root comes first
    int mid = where.get(root.val);                         // inorder: left part | root | right part
    root.left = build(preorder, lo, mid - 1);              // LEFT first: preorder lists it next
    root.right = build(preorder, mid + 1, hi);
    return root;
}
```

**O(n) time, O(n) space.** Searching inorder with a loop instead of the map costs O(n) per node: O(n²) on a vine.

</HintLadder>

**Catch the bug:** building the right subtree before the left. The cursor then hands 9 — the root of the *left* subtree — to the right side, whose inorder range doesn’t contain it, and the ranges go wrong from there. On LeetCode’s example the cursor runs off the end of preorder and the code throws `ArrayIndexOutOfBoundsException`. [Solve Construct Binary Tree from Preorder and Inorder Traversal](https://leetcode.com/problems/construct-binary-tree-from-preorder-and-inorder-traversal/).

**Problem: Serialize and Deserialize Binary Tree · Construction**

**Write it preorder, with a marker for every empty spot.** Each node writes its value, then its left subtree, then its right subtree; an empty spot writes `#`. Commas separate tokens.

**Read it back in the same order.** Take the next token. `#` means empty: return `null`. Otherwise make the node, then read its left subtree, then its right subtree. The reader makes exactly the decisions the writer made, in the same order, so the shape comes back exactly. Duplicates and negative values are fine.

<Figure caption="[1, 2, 3, null, null, 4, 5] with every empty spot drawn as #. Root first, left before right: 1,2,#,#,3,4,#,#,5,#,#. Five nodes, six markers: a tree of n nodes always has exactly n + 1 empty spots.">
  <Tree level={figures.serialize.level} nulls={true} spread={44} />
  <ArrayStrip name="letter" values={figures.serialize.text.split(',')} tones={{ 2: 'ghost', 3: 'ghost', 6: 'ghost', 7: 'ghost', 9: 'ghost', 10: 'ghost' }} />
</Figure>

<Trace title="Write it, read it back" steps={serialize} takeaway="Remember: preorder plus a # for every empty spot is a complete set of instructions; read it back with one shared cursor in the same order." />

**Why it works:** a preorder listing alone is ambiguous only because it hides where each subtree ends. A `#` for every empty spot marks every ending. Reading recursively, each call consumes exactly the tokens its own subtree wrote — its value, its left part, its right part — and leaves the cursor on the next subtree’s first token.

**What stays true:** when `read` returns a subtree, the cursor has advanced past exactly that subtree’s tokens.

<Reveal q="Why exactly n + 1 markers?">

Each of the n nodes has 2 child slots: 2n slots. Every node except the root fills exactly one slot, so n − 1 slots are filled and 2n − (n − 1) = **n + 1** are empty. The letter always has 2n + 1 tokens. (LeetCode’s own level-order format, `[1, 2, 3, null, null, 4, 5]`, is another valid encoding; it just trims the trailing nulls.)

</Reveal>

**Say it before you code:** contract — `serialize` writes preorder with markers; `deserialize` reads one subtree per call · base case — `#` is `null` · direction — preorder both ways · **O(n) time and O(n) space** for each.

<HintLadder hints={hints.serialize}>

```java id=Codec
class Codec {
    public String serialize(TreeNode root) {
        StringBuilder sb = new StringBuilder();
        write(root, sb);
        return sb.toString();
    }

    private void write(TreeNode node, StringBuilder sb) {
        if (sb.length() > 0) sb.append(',');
        if (node == null) { sb.append('#'); return; }   // the empty spot is written, not skipped
        sb.append(node.val);
        write(node.left, sb);
        write(node.right, sb);
    }

    public TreeNode deserialize(String data) {
        Deque<String> tokens = new ArrayDeque<>(Arrays.asList(data.split(",")));
        return read(tokens);
    }

    private TreeNode read(Deque<String> tokens) {
        String token = tokens.poll();
        if (token.equals("#")) return null;
        TreeNode node = new TreeNode(Integer.parseInt(token));
        node.left = read(tokens);                      // the same order it was written: node, left, right
        node.right = read(tokens);
        return node;
    }
}
```

**O(n) time and space** for both directions; the empty tree is the one-token letter `#`.

</HintLadder>

**Catch the bug:** leaving out the markers. Then `[1, 2]` and `[1, null, 2]` both become `1,2`, and the reader cannot know which one to grow — the bug from Chapter 2 again, in a new costume.
```java id=lcaBst
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    TreeNode cur = root;
    while (cur != null) {
        if (p.val < cur.val && q.val < cur.val) cur = cur.left;          // both on the left
        else if (p.val > cur.val && q.val > cur.val) cur = cur.right;    // both on the right
        else return cur;                       // they split here, or cur is one of them
    }
    return null;
}
```

**O(h) time, O(1) space.** LeetCode’s BST has unique values and both nodes exist.

<h2 id="house-robber-iii">Side quest 5 · The fruit thief</h2>

**The card says:** a thief wants to strip fruit from the forks of a tree, but if he touches two forks joined directly by a branch, the branch snaps. Which forks give him the most fruit?

**The reasoning:** at each fork he either **takes** it or **skips** it, and the parent’s choice depends on which one the child made. One number can’t carry both futures, so the Messenger carries a **pair**: `(best if this node is skipped, best if it is taken)`.

- **Take** this node: its children must be skipped: `node.val + left.skip + right.skip`.
- **Skip** this node: each child is free to do whichever is better: `max(left) + max(right)`.

<Figure caption="LeetCode’s [3, 4, 5, 1, 3, null, 1], each node with its pair (skip, take). Node 4: skip = 1 + 3 = 4, take = 4. Node 5: skip = 1, take = 5. Root: skip = max(4, 4) + max(1, 5) = 9, take = 3 + 4 + 1 = 8. Answer 9: take 4 and 5.">
  <Tree level={figures.rob.level} notes={figures.rob.notes} tones={{ 1: 'green', 2: 'green' }} spread={64} />
</Figure>

<Reveal q="Why not just take every other level?">

Because sometimes skipping **two** levels in a row is best. On the vine `[4, 1, null, 2, null, 3]`, the even levels give 4 + 2 = 6 and the odd levels give 1 + 3 = 4, but taking 4 and 3 is allowed and gives **7**. The pair tries every choice at every node; alternating levels tries only two.

</Reveal>

<HintLadder hints={hints.rob}>

```java id=rob
public int rob(TreeNode root) {
    int[] r = best(root);
    return Math.max(r[0], r[1]);
}

private int[] best(TreeNode node) {                   // {best if node is skipped, best if node is taken}
    if (node == null) return new int[]{0, 0};
    int[] l = best(node.left), r = best(node.right);
    int skip = Math.max(l[0], l[1]) + Math.max(r[0], r[1]);
    int take = node.val + l[0] + r[0];                // taking me forces both children to be skipped
    return new int[]{skip, take};
}
```

**O(n) time, O(h) space.** This is dynamic programming on a tree: each subtree’s answer is computed once and combined.

</HintLadder>

**Transfer test:** Binary Tree Cameras (hard) asks for the fewest cameras so that every node is watched by itself, its parent or a child. What does each call return now? (A small set of states — “has a camera”, “watched without one”, “not watched yet” — and the parent decides from its children’s states.) [Solve House Robber III](https://leetcode.com/problems/house-robber-iii/).

<h2 id="flatten">Side quest 6 · One long rope</h2>

**The card says:** don’t answer a question about the tree — **rewire** it, in place, into a single rope: every `left` pointer empty, and each `right` pointer leading to the next node in **preorder**.

**The reasoning:** a linked chain is easiest to build **from its end**. If you visit the nodes in exactly the reverse of preorder — right subtree, then left subtree, then the node — then when you reach a node, everything after it in the final rope is already built, and `prev` points at its head. The node only has to hook itself on: `node.right = prev; node.left = null; prev = node`.

<Figure caption="LeetCode’s [1, 2, 5, 3, 4, null, 6] becomes the rope 1 → 2 → 3 → 4 → 5 → 6: its preorder. The walk handles 6 first, then 5, 4, 3, 2, and 1 last.">
  <Tree level={figures.flatten.level} />
  <ArrayStrip name="rope" values={figures.flatten.chain} join="→" indices={false} />
</Figure>

<Reveal q="Can it be done in O(1) extra space?">

Yes, with a loop and no stack. At each node that has a left child, find the **rightmost** node of its left subtree, hang the node’s right subtree there, move the left subtree to the right, clear `left`, and step right. Each edge is walked a constant number of times: O(n) time, O(1) space. It is the same rewiring trick that powers Morris traversal (see Look these up yourself).

</Reveal>

<HintLadder hints={hints.flatten}>

```java id=flatten
private TreeNode prev;                  // the head of the rope built so far

public void flatten(TreeNode root) {
    prev = null;
    unroll(root);
}

private void unroll(TreeNode node) {    // reverse preorder: right, left, then the node
    if (node == null) return;
    unroll(node.right);
    unroll(node.left);
    node.right = prev;                  // everything after me is already a rope
    node.left = null;
    prev = node;
}
```

**O(n) time, O(h) space.**

</HintLadder>

**Transfer test:** turn a BST into a sorted doubly linked list, in place. (The order you want is inorder now; visit in reverse inorder — right, node, left — and link each node to the head built so far.) [Solve Flatten Binary Tree to Linked List](https://leetcode.com/problems/flatten-binary-tree-to-linked-list/).

<h2 id="choose-the-tool">Fog on the cliff</h2>

<Scene title="Fog on the cliff" mood="storm">

The fog comes in thick one morning, and the harvest-master wants the **nearest** ripe fruit — the tip closest to the trunk — before the pickers lose the light.

The Climber does what he always does. He takes the left rope, goes down, and keeps going down. The left side of the old tree is the deepest part of the cliff, three hundred forks of it. By the time he has reported back, the shallow tip on the right, three forks below the trunk, has been sitting there all morning.

The Keeper watches from the lighthouse steps. *"He found it,"* she says. *"Eventually. But the question was about nearness, and he never once looked at the tree a row at a time. When the question is about rows, the climbing guild is the wrong guild."*

</Scene>

Depth-first walks are the right tool when **the answer for a node is built from the answers below it or the state above it**. Reach for something else when:

- **The question is about rows or nearness:** the shallowest leaf, level-by-level values, the view from the right side, the zigzag order. A **row-by-row walk with a queue** handles one level at a time and can stop at the first leaf it meets. (Minimum depth works either way; on a lopsided tree the queue version touches far fewer nodes.)
- **The tree is very deep:** same algorithm, but iterative, with your own stack ([When the tree is a vine](#vines)).
- **The same question is asked many times** (LCA of many pairs, k-th smallest after many updates): **preprocess or augment** — binary lifting, Euler tour, subtree sizes. See Look these up yourself.
- **The structure has cycles or shared children:** it is a **graph**, and a DFS needs a visited set or it will loop forever.

<Mermaid code={`flowchart TD
  Q["A question about a tree"] --> R{"About rows or nearest?"}
  R -->|yes| BFS["Row-by-row walk with a queue"]
  R -->|no| D{"Needs what is below a node?"}
  D -->|yes| UP["Messenger: return from children\n(+ a board if the answer is not what the parent needs)"]
  D -->|no| DOWN["Climber: pass state down as parameters"]
  UP --> H{"Height could be huge?"}
  DOWN --> H
  H -->|yes| IT["Same walk, explicit stack"]
  H -->|no| REC["Recursion is fine"]`} />

<Reveal q="Right side view: climb or go row by row?">

Both work in O(n). Row by row is the natural fit: keep the current row, record its last node, build the next row from the children. The climbing version visits the right child before the left, carries the depth down, and records a node when its depth is seen for the first time. If you can say why both are correct, you understand both tools; pick the one you can defend.

</Reveal>

<h2 id="exit-ticket">The picker’s exam · Build a solution with the labels removed</h2>

<Scene title="No chapter titles" mood="dawn">

On the morning of the exam the Keeper hands you three cards with no chapter names and no hints, and points you at the practice cliff.

*"Pick one,"* she says. *"Before you write a line, tell me what your function promises to return, which way the information flows, whether you need the gate board, and what it costs."*

Choose one. Keep the chapters closed. Write the contract, the base case, the direction and the complexity before any code.

1. **The longest same-value path.** Count the edges of the longest path in which every node has the same value. The path need not pass through the root. Test a single node, all values equal, and a tree where the best path bends below the root.
2. **Running totals in the sorted grove.** In a BST, replace every value with the sum of all values greater than or equal to it. Test a single node, a vine, and `[4, 1, 6, 0, 2, 5, 7]`.
3. **The widest gap.** Return the largest |a − b| where node a is an ancestor of node b. Test a vine that only increases, and a tree whose largest gap is between the root and a deep leaf.

<Reveal q="I’ve written and tested it. What should my reasoning contain?">

**Longest same-value path:** Chapter 5 with a condition. The helper returns the longest **same-value arm** going down from this node, in edges. For each child, the arm on that side is `1 + child’s arm` if the child has the same value, and 0 otherwise. Record `left + right` on the board; return `max(left, right)`. Return one thing, record another.

**Running totals:** reverse inorder — right, node, left — visits values from largest to smallest. Carry a running sum (a field); at each node add its value to the sum, then overwrite the value with the sum. Chapter 10’s order, backwards.

**Widest gap:** the Climber carries the minimum and maximum seen on the path down (side quest 3’s idea, twice). At each node, the best gap involving it as the lower end is `max(|val − min|, |val − max|)`; take the maximum over all nodes.

Now explain why a slightly wrong version fails one of your tests — the root-only bend, a forgotten reset of the running sum between calls, carrying only the maximum. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

Passing this once is a useful checkpoint. Rebuild one of these on another day, with a changed input and without the headings choosing the pattern for you.

<h2 id="cheat-sheet">The Keeper’s rope notes</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Mirror / swap every node | Recurse on both children, swap the two results | The call returns its subtree, mirrored |
| Are two trees identical? | Walk both together; null checks before values | Both empty = match; one empty = no match |
| Height, depth, size | `1 + max(left, right)`, 0 for null (or carry depth down) | Each return is the exact height of that subtree |
| Balanced at every node | Return height, or −1 for “broken”; stop early | Non-negative return = balanced and its height |
| Longest path between any two nodes | Return height; board = max(left + right) | Return is for the parent; the board is the answer |
| Best path sum, values may be negative | Clamp arms at 0; board starts at `Integer.MIN_VALUE` | Gain = best one-sided path starting here |
| Lowest common ancestor | Return null / p / q / the node where both sides report | The first node to hear from both sides |
| All root-to-leaf paths with a sum | Carry remaining + path down; copy at a leaf; remove on the way up | Path = root to here, on entry and on exit |
| Is it a valid BST? | Pass (low, high) down with long bounds; or inorder strictly increasing | Every node fits its ancestors’ window |
| k-th smallest in a BST | Iterative inorder with a stack; stop at the k-th pop | Pops come out in sorted order |
| Very deep tree | The same walk with an explicit stack | The stack holds what the call stack would have |
| Rebuild from preorder + inorder | Preorder cursor names the root; inorder map splits; left first | `preorder[next]` is the root of the range being built |
| Send a tree as text | Preorder with `#` for every empty spot; read back in the same order | Each read consumes exactly its own subtree |
| Symmetric | `mirror(a.left, b.right) && mirror(a.right, b.left)` | Outside with outside, inside with inside |
| Subtree of another tree | Identical-check at every node | The whole subtree must match |
| Depends on the path above | Carry it down (max so far, min and max, bounds) | The parameter summarises the ancestors |
| LCA in a BST | Both smaller → left; both larger → right; else here | The split point is the answer |
| Choose nodes, never parent and child | Return a pair (skip, take) | The parent picks from the children’s pairs |
| Rewire into a preorder rope | Reverse preorder (right, left, node) with `prev` | Everything after the node is already a rope |
| Rows, nearest, view from a side | A row-by-row walk with a queue | One level at a time |

Every recursive tree solution here costs **O(n) time and O(h) space**, with h between log₂ n and n. The exceptions are worth knowing: Subtree of Another Tree is O(m · n); Kth Smallest stops early at O(h + k); LCA of a BST is O(h) time and O(1) space; Path Sum II pays O(n · h) to copy its answers; and the Grafter’s map costs O(n) space.

## Five bugs the Keeper keeps in her pocket

1. **Reading `.val` before the null checks.** Base cases come first, every time: both-null, then one-null, then values.
2. **Answering with the return value when the answer is on the board.** The root returns a height; the diameter is in `best`. Say both before you code.
3. **Checking only the parent.** Balance must hold at every node; BST order must hold against every ancestor. Carry bounds down or return verdicts up.
4. **Recording a live list.** In Path Sum II, `result.add(path)` stores a list that will be empty by the end. Store `new ArrayList<>(path)`, and undo every add on the way back up.
5. **Starting a best at 0, or a bound at an `int` extreme.** All-negative trees need `Integer.MIN_VALUE`; BST bounds need `long` or `null` so that `Integer.MIN_VALUE` and `Integer.MAX_VALUE` are legal values.
