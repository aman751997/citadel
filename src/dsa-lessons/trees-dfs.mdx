<h2 id="prologue">Prologue · How recursion on a tree works</h2>

A **binary tree** is a node with two slots, `left` and `right`. Each slot holds another binary tree, or nothing. Read that twice: **a tree is made of smaller trees.** So a function on a tree can be made of the same function on its smaller trees.

You never see the whole tree from one node. Each call of your function stands on one node and sees only the two subtrees below it. The skill is deciding what to ask them and what to do with their answers.

### The contract: trust the call

Before any code, write one sentence: **what does `f(node)` promise to return for the subtree hanging from `node`?** Then build the function in three moves:

1. **Base case first.** What is `f(null)`? Usually `0`, `null`, `true` or an empty list. It needs no work.
2. **Trust the call.** Assume `f(node.left)` and `f(node.right)` already keep the promise. Do not trace inside them.
3. **Combine.** Build this node's answer from the two answers and `node.val`.

Why is trusting safe? The two children are **strictly smaller trees**, and the smallest tree, the empty one, is the base case. If the combine step is right whenever the children's answers are right, then the answer is right for size 0, then size 1, then size 2, and so on. That is induction. In an interview you can say: "each call handles its own subtree; I only need to check one level."

<Mermaid code={`flowchart TD
  A["f(node)"] --> B{"node == null?"}
  B -->|yes| C["return the base answer"]
  B -->|no| D["a = f(node.left)\nb = f(node.right)\n(trust both)"]
  D --> E["combine a, b and node.val"]
  E --> F["return ONE answer to the caller"]`} />

Three questions before every solution:

1. **What does the call promise?** What is settled about a subtree when its call returns.
2. **Why is this move safe?** The children kept their promise; this node only combines.
3. **When do I stop?** At the empty spot below a leaf, and earlier when nothing below can change the answer.

### What goes down, what comes up

Information travels two ways through a tree. Naming the direction is half of every solution.

| | Passed down | Returned up |
|---|---|---|
| Carried by | **parameters** of the call | the **return value** of the call |
| A node knows | everything on the path **above** it | everything in the subtree **below** it |
| Typical questions | depth so far, sum still to find, allowed range of values | height, size, balanced or not, the best path below |
| In this chapter | Chapters 8, 9, 10; Maximum Depth (second version); Count Good Nodes | Chapters 1 to 7; House Robber III |

Some problems use both at once: Count Good Nodes passes the running maximum down and returns a count up.

Every dry run on this page draws the same four things, so you can read them the same way each time:

- the **tree**, with the current node highlighted and the nodes still waiting on the stack marked;
- the **call stack**, one entry per call that has started and not yet returned;
- **passed DOWN**: the parameters of the call on top of the stack;
- **returned UP**: the value each finished call gave back to its parent.

### Return value or shared field?

Usually the question's answer is the root's return value. Maximum Depth is that: the root returns the answer.

Sometimes the answer is **not what the parent needs**. For the longest path between any two nodes, a node must hand its parent the length of one straight arm (the parent can extend only one arm), but the answer is the best bent path found at any node. Then the function does two jobs:

- it **returns** what the parent needs (a height), and
- it **records** the answer in a shared field (a variable the helper updates, such as `best`) as a side effect.

When the root's call ends, its return value is not the answer. You read the field. Chapters 5 and 6 are built on this. The shared field can be an instance variable, a one-element array passed down, or a pair returned from each call. All three do the same job.

Rule of thumb: **if the parent can use the answer for the subtree, return it. If the best answer can sit at any node and the parent cannot extend it, record it and return something else.**

<h3 id="orders">Three orders: when do I do my work?</h3>

A depth-first walk touches each node three times: on the way down, between its two subtrees, and on the way back up. **Where you put the work decides the order.**

| Order | Work happens | Typical use |
|---|---|---|
| **Preorder** (node, left, right) | on the way down, before any subtree | copying or writing a tree (Chapter 12), updating state before the children run |
| **Inorder** (left, node, right) | between the two subtrees | a binary search tree comes out in sorted order (Chapters 9 and 10) |
| **Postorder** (left, right, node) | on the way back up, after both subtrees | anything built from the children's answers: height, size, balance, diameter |

The three orders are the same walk with one line moved:

```java id=orders
public List<Integer> preorder(TreeNode root) { List<Integer> out = new ArrayList<>(); pre(root, out); return out; }
public List<Integer> inorder(TreeNode root) { List<Integer> out = new ArrayList<>(); in(root, out); return out; }
public List<Integer> postorder(TreeNode root) { List<Integer> out = new ArrayList<>(); post(root, out); return out; }

private void pre(TreeNode node, List<Integer> out) {
    if (node == null) return;
    out.add(node.val);                     // on the way down
    pre(node.left, out);
    pre(node.right, out);
}
private void in(TreeNode node, List<Integer> out) {
    if (node == null) return;
    in(node.left, out);
    out.add(node.val);                     // between the subtrees
    in(node.right, out);
}
private void post(TreeNode node, List<Integer> out) {
    if (node == null) return;
    post(node.left, out);
    post(node.right, out);
    out.add(node.val);                     // on the way back up
}
```

`TreeNode` is LeetCode's usual shape: an `int val` and two child pointers, `left` and `right`.

### What it costs

**Time O(n).** Each node is visited once and does constant work, as long as the combine step is O(1). **Space O(h)**, where h is the height: the call stack holds one frame per node on the current path. A balanced tree has h about log₂ n. A **vine** (every node has one child) has h = n. Say "O(n) time, O(h) space, and h can be n" out loud. [When the tree is a vine](#vines) shows what happens when h is a million.

### How to recognise it

- **The input is a tree**, or shaped like one: an org chart, a folder hierarchy, an expression, a decision tree.
- **The question is about every node or about paths:** height, balance, root-to-leaf paths, the best path between any two nodes, ancestors.
- **A binary search tree** and the question involves order: the k-th smallest, "is it valid?", a range.
- **Rebuild or transmit a tree:** two listings, a string, a copy.

The brute force it replaces is usually **work repeated at every node**. Measuring each subtree's height separately costs O(n²) on a vine, and returning heights from below costs O(n). Checking every pair of nodes for the best path is O(n²) pairs, each walked in O(n), and one bottom-up pass with a shared field does it in O(n).

<h2 id="invert">Chapter 1 · Invert Binary Tree</h2>

### Problem

Mirror a binary tree: at every node, the left subtree becomes the right subtree and the other way round.

`[4, 2, 7, 1, 3, 6, 9]` becomes `[4, 7, 2, 9, 6, 3, 1]`.

<Figure caption="Every node swapped its two children. Values never moved between nodes, only the child pointers changed.">
  <div style="display:flex;flex-wrap:wrap;gap:1.5rem;justify-content:center">
    <Tree level={figures.invertBefore} name="before" />
    <Tree level={figures.invertAfter} name="after" />
  </div>
</Figure>

### How to recognise it

- The task changes the tree itself, not a number about it.
- The rule is the same at every node ("swap", "mirror", "copy").
- Nothing at one node depends on any other node's value.

### Brute force

Build a second tree: walk the first and create each node's mirrored copy. That is O(n) time and O(n) extra space, so it is not slow, only wasteful. The real choice is how to do the swap in place. The risk is in the details of the pointer assignments, not in the speed.

### Intuition

Suppose the left subtree came back already mirrored, and the right one too. What is left to do at this node? Only hang the mirrored right subtree on the left and the mirrored left subtree on the right. A mirror image is exactly "swap left and right, at every level", so one swap per node is the whole job.

**The contract:** `invertTree(node)` mirrors the subtree hanging from `node` and returns its root. Passed down: nothing. Returned up: the node itself, so the parent can hang it.

### Dry run

Watch the call stack. Each call finishes its children first, then swaps. The tree changes on each return.

<DryRun title="Invert Binary Tree" frames={invertFrames([4, 2, 7, 1, 3, 6, 9])} predict />

### Algorithm

1. If the node is `null`, return `null`.
2. Invert the left subtree and keep the result in a local variable.
3. Invert the right subtree and keep the result in a local variable.
4. Set `node.left` to the inverted right result and `node.right` to the inverted left result.
5. Return the node.

### Java solution

<HintLadder hints={hints.invert}>

```java id=invertTree
public TreeNode invertTree(TreeNode root) {
    if (root == null) return null;              // an empty tree is its own mirror
    TreeNode left = invertTree(root.left);      // trust the call: the left subtree, mirrored
    TreeNode right = invertTree(root.right);    // trust the call: the right subtree, mirrored
    root.left = right;                          // swap the two mirrored halves
    root.right = left;
    return root;
}
```

</HintLadder>

### Why it works

- **Settled:** when `invertTree(node)` returns, the subtree below `node` is the mirror of what it was, and nothing outside it has been touched.
- **Why the move is safe:** the base case mirrors the empty tree (nothing to do). If both children come back mirrored, swapping them mirrors the whole subtree.
- **When we stop:** at the empty spots below the leaves. Each node is swapped exactly once.

### Complexity

- **Time O(n):** one constant-time swap per node.
- **Space O(h):** the call stack. The LeetCode limit is 100 nodes here.

### Edge cases and mistakes

- Empty tree, a single node, a vine.
- The classic bug: assigning one pointer before saving the other.

```java fragment
root.left = invertTree(root.right);    // left now points at the RIGHT subtree...
root.right = invertTree(root.left);    // ...which is inverted again and hung on the right as well
```

The original left subtree is never touched again, and the same damage repeats at every level. On `[4, 2, 7, 1, 3, 6, 9]` every node ends up pointing twice to one copy of its right subtree: `[4, 7, 7, 9, 9, 9, 9]`. The 2, 1, 3 and 6 are gone. Save both results in locals first.

### Practice

<Trace title="Mirror the tree" steps={invert} takeaway="Remember: trust the call. invertTree(child) returns a fully mirrored subtree; the current node only swaps the two results and returns itself." />

<Reveal q="Does it matter whether you swap before or after the recursive calls?">

No. Swapping the two child pointers first and then inverting each child (preorder) works too, because mirroring a subtree does not depend on which side it hangs from. Any order that swaps every node exactly once is correct, including an iterative walk with a stack or a queue. What breaks is assigning one pointer before saving the other.

</Reveal>

**Variations to try:** check whether two trees are mirror images (Side quest 1); invert only below a given depth; count how many nodes had two children.

<h2 id="same-tree">Chapter 2 · Same Tree</h2>

### Problem

Given two binary trees, return `true` if they have the same shape and the same value at every position.

`p = [1, 2]` and `q = [1, null, 2]` are **not** the same, even though both list as 1, 2.

<Figure caption="p = [1, 2] and q = [1, null, 2]. Listed root-first, both read 1, 2, but the 2 hangs on different sides. Walking the two trees together, the left pair is (2, empty): a mismatch.">
  <div style="display:flex;flex-wrap:wrap;gap:2.5rem;justify-content:center">
    <Tree level={figures.sameP} name="p" tones={{ 1: 'red' }} />
    <Tree level={figures.sameQ} name="q" tones={{ 2: 'red' }} />
  </div>
</Figure>

### How to recognise it

- Two trees, one question about whether they match.
- A comparison that must hold at every position, not just at the root.
- Later chapters reuse this as a building block (Subtree, Symmetric).

### Brute force

Write each tree as a list and compare the lists. Without a marker for empty spots, the shape is forgotten: `[1, 2]` and `[1, null, 2]` look identical. With markers it works in O(n) time but needs O(n) extra space for the two lists. Walking both trees together needs no lists at all.

### Intuition

Two trees are the same when **their roots match, their left subtrees are the same, and their right subtrees are the same.** That sentence is the code. The only care is with empty spots, and it comes first: both empty is a match; exactly one empty is not. Only after that is it safe to read `p.val`.

**The contract:** `isSameTree(p, q)` is `true` exactly when the two subtrees are identical. Passed down: the matching pair of children. Returned up: `true` or `false`.

### Dry run

Two trees walked in lockstep. The stack holds pairs. Watch the `&&` stop the walk at the first mismatch.

<DryRun title="Same Tree" frames={pairFrames([1, 2, 3], [1, 2, 4], 'same')} predict />

### Algorithm

1. If both nodes are `null`, return `true`.
2. If exactly one is `null`, return `false`.
3. If the values differ, return `false`.
4. Return `isSameTree(p.left, q.left) && isSameTree(p.right, q.right)`.

### Java solution

<HintLadder hints={hints.same}>

```java id=isSameTree
public boolean isSameTree(TreeNode p, TreeNode q) {
    if (p == null && q == null) return true;     // both empty: identical
    if (p == null || q == null) return false;    // exactly one empty: the shapes differ
    return p.val == q.val                        // only now is it safe to read values
        && isSameTree(p.left, q.left)
        && isSameTree(p.right, q.right);
}
```

</HintLadder>

### Why it works

- **Settled:** a call that returns `true` has checked every position of its two subtrees.
- **Why the move is safe:** if the roots match and both pairs of subtrees are identical (trust the calls), the trees agree at every position. Any failed check is a position where they differ.
- **When we stop:** at the first `false` (the `&&` skips the rest), or when both sides run out together.

### Complexity

- **Time O(min(m, n)):** the walk cannot go deeper or wider than the smaller tree.
- **Space O(min(h₁, h₂)):** the call stack.

### Edge cases and mistakes

- Both empty (`true`), one empty (`false`), same values but different shape.
- Comparing values first (`if (p.val != q.val)` on line 1) throws `NullPointerException` as soon as one side is empty.
- Comparing value listings without markers says `[1, 2]` and `[1, null, 2]` are the same.

### Practice

<Trace title="Two nodes, one step at a time" steps={same} takeaway="Remember: both empty → true; one empty → false; then compare values and recurse on both pairs." />

<Reveal q="Why not just compare the two root-first listings?">

A listing without markers for the empty spots forgets the shape. `[1, 2]` and `[1, null, 2]` both list as 1, 2. Write a `#` for every empty spot and the listings become `1,2,#,#,#` and `1,#,2,#,#`, which differ, so comparing strings would work. That idea is the whole of Chapter 12.

</Reveal>

**Variations to try:** compare two trees by structure only (ignore values); compare them as mirror images (Side quest 1); return the first position where they differ.

<h2 id="max-depth">Chapter 3 · Maximum Depth of Binary Tree</h2>

### Problem

Return the number of nodes on the longest path from the root down to a leaf.

`[3, 9, 20, null, null, 15, 7]` has depth 3 (3 → 20 → 15).

<Figure caption="Each node labelled with what maxDepth returns for it. The leaves report 1; node 20 reports 1 + max(1, 1) = 2; the root reports 1 + max(1, 2) = 3.">
  <Tree level={figures.depth.level} notes={figures.depth.notes} tones={{ 0: 'gold' }} />
</Figure>

### How to recognise it

- A number about the **whole tree** that is built from its two sides: depth, height, size.
- The same question makes sense for every subtree.
- This is the smallest example of both directions: you can pass the depth down, or return it up.

### Brute force

For every node, walk up to the root and count the steps, then take the largest. That is O(n · h) time, up to O(n²) on a vine. Measuring a node's depth separately for each node repeats work: every node on a path re-counts the same ancestors.

### Intuition

**Bottom-up (return up).** The longest path from a node goes through one of its children, or stops at the node if it is a leaf. Trust the calls: the children already know their depths. The deeper one, plus this node, is the answer: `1 + max(left, right)`, with 0 for an empty tree.

**Top-down (pass down).** Each call receives its own depth as a parameter and updates a shared `best`. The children are called with `depth + 1`. This is a preorder walk: the work happens on the way down.

Both are correct. Bottom-up returns the answer; top-down records it in a field.

### Dry run

First bottom-up. Watch the **returned UP** panel fill from the leaves toward the root.

<DryRun title="Maximum Depth, bottom-up" frames={maxDepthFrames([3, 9, 20, null, null, 15, 7])} predict />

Now top-down. The depth is a **passed DOWN** parameter, and nothing useful is returned.

<DryRun title="Maximum Depth, top-down" frames={maxDepthDownFrames([3, 9, 20, null, null, 15, 7])} predict />

### Algorithm

Bottom-up:

1. If the node is `null`, return 0.
2. Ask the left subtree for its depth, then the right.
3. Return `1 + max(left, right)`.

Top-down:

1. Keep a field `best = 0`. Call `visit(root, 1)`.
2. In `visit`, if the node is `null`, return. Otherwise set `best = max(best, depth)`.
3. Visit both children with `depth + 1`. Return `best` at the end.

### Java solution

<HintLadder hints={hints.depth}>

```java id=maxDepth
public int maxDepth(TreeNode root) {
    if (root == null) return 0;                                   // an empty tree has depth 0
    return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}
```

The same answer with the depth passed down:

```java id=maxDepthTopDown
private int best;                               // deepest node seen so far

public int maxDepth(TreeNode root) {
    best = 0;
    visit(root, 1);
    return best;
}

private void visit(TreeNode node, int depth) {  // depth = nodes from the root down to here
    if (node == null) return;
    best = Math.max(best, depth);
    visit(node.left, depth + 1);
    visit(node.right, depth + 1);
}
```

</HintLadder>

### Why it works

- **Settled:** bottom-up, each return value is the exact depth of that subtree. Top-down, when a call stands on a node its `depth` is exactly the number of nodes from the root to here, and `best` is the deepest node seen so far.
- **Why the move is safe:** the longest path from a node goes through a child (or ends at the node), and the children already know their depths.
- **When we stop:** at the empty spots. The root's return value (or the final `best`) is the answer.

### Complexity

- **Time O(n):** each node is visited once.
- **Space O(h):** the call stack.

### Edge cases and mistakes

- Empty tree (0), one node (1), a vine (n).
- The classic bug: swap `max` for `min` to get the **minimum** depth and it breaks. On the vine `[2, null, 3, null, 4, null, 5, null, 6]`, `1 + Math.min(left, right)` returns **1**, because the root's empty left side counts as a path of length 0. But an empty spot is not a leaf; the answer is 5. When one side is empty, only the other side has leaves:

```java id=minDepth
public int minDepth(TreeNode root) {
    if (root == null) return 0;
    if (root.left == null) return 1 + minDepth(root.right);    // an empty side is not a leaf:
    if (root.right == null) return 1 + minDepth(root.left);    // only the other side has leaves
    return 1 + Math.min(minDepth(root.left), minDepth(root.right));
}
```

<h2 id="balanced">Chapter 4 · Balanced Binary Tree</h2>

### Problem

A tree is height-balanced when, **at every node**, the heights of its two subtrees differ by at most 1. Return whether the tree is balanced.

`[3, 9, 20, null, null, 15, 7]` is balanced. `[1, 2, 2, 3, null, null, 3, 4, null, null, 4]` is not.

<Figure caption="At the root the two sides are both height 3, so the root looks even. But each node 2 has one side of height 2 and one of height 0: a gap of 2. The tree is not balanced.">
  <Tree level={figures.balanced.level} notes={figures.balanced.notes} tones={{ 1: 'red', 2: 'red' }} />
</Figure>

### How to recognise it

- A condition that must hold **at every node**, not only at the root.
- Each node's check needs facts about its two subtrees (their heights).
- The parent also needs this node's height, so one number has to do two jobs.

### Brute force

At every node, call a separate `height()` on both sides and compare. That is correct, and it is the version most people write first. But each node re-measures its whole subtree. On a vine of n nodes that is n + (n − 1) + … + 1 = **O(n²)**; on a balanced tree, O(n log n).

### Intuition

Each node needs its children's heights to check itself, and its parent needs this node's height. So the call returns the height, and it also needs a way to say "something below me is broken". **Return −1 for "unbalanced".** No real height is negative, so −1 can never be confused with one. Each node checks its children's reports: if either is −1, or they differ by more than 1, it returns −1. Otherwise it returns its height.

**The contract:** `height(node)` returns the height of the subtree, or −1 if any node inside it is unbalanced. Passed down: nothing. Returned up: height or −1.

### Dry run

Watch the −1 rise and stop the walk. Once the left side reports −1, the right side is never visited.

<DryRun title="Balanced Binary Tree" frames={balancedFrames([1, 2, 2, 3, null, null, 3, 4, null, null, 4])} predict />

### Algorithm

1. `isBalanced(root)` is `height(root) != -1`.
2. In `height(node)`: if the node is `null`, return 0.
3. Get the left height. If it is −1, return −1 now.
4. Get the right height. If it is −1, return −1.
5. If the two heights differ by more than 1, return −1.
6. Otherwise return `1 + max(left, right)`.

### Java solution

<HintLadder hints={hints.balanced}>

```java id=isBalanced
public boolean isBalanced(TreeNode root) {
    return height(root) != -1;
}

private int height(TreeNode node) {             // the height, or -1 if anything here is unbalanced
    if (node == null) return 0;
    int left = height(node.left);
    if (left == -1) return -1;                  // the verdict is already in: pass it up
    int right = height(node.right);
    if (right == -1) return -1;
    if (Math.abs(left - right) > 1) return -1;  // this node is the one that leans
    return 1 + Math.max(left, right);
}
```

</HintLadder>

### Why it works

- **Settled:** a non-negative return value means the whole subtree is balanced **and** is its exact height. −1 means some node inside it is not balanced.
- **Why the move is safe:** a node is balanced exactly when both children are balanced and their heights differ by at most 1. A non-negative report certifies the first part for each child; this node adds its own check.
- **When we stop:** at the first −1 (it is passed straight up), or when the root returns.

### Complexity

- **Time O(n):** each node is visited once, and the combine step is O(1).
- **Space O(h):** the call stack.

### Edge cases and mistakes

- Empty tree (balanced), a vine of length 3 (not balanced).
- Checking the gap only at the root, `Math.abs(height(root.left) - height(root.right)) <= 1`, says **yes** to the figure's tree (3 and 3). The rule holds at every node, so every node must check it.
- Forgetting to pass −1 upward lets a parent compute `1 + max(-1, 2)` and hide the failure.

<h2 id="diameter">Chapter 5 · Diameter of Binary Tree</h2>

### Problem

Return the length, in **edges**, of the longest path between any two nodes. The path need not pass through the root.

`[1, 2, 3, 4, 5]` has diameter 3 (the path 4–2–1–3).

This chapter holds the most important idea in tree problems: **return one thing, record another.** Take it slowly.

### How to recognise it

- "Longest / best path **between any two nodes**", not from the root.
- The best path can bend at any node, and a bent path cannot be extended by the parent.
- The thing the parent needs (one arm) is not the thing the question asks (the bend).

### Brute force

At every node, call `height()` on both sides and add them. Take the largest sum. It is correct, but each `height()` re-walks a whole subtree, so a vine costs O(n²). Checking every pair of nodes is even worse: O(n²) pairs, each path found in O(n).

### Intuition

**Every path in a tree has exactly one highest node: the place where it bends.** At that node the path goes down one arm into the left subtree and down another into the right. The longest path that bends at a node has length

```text
(longest arm down the left) + (longest arm down the right)  =  L + R   edges
```

where `L` and `R` are the heights of the two subtrees, counted in nodes (an empty side contributes 0). The diameter is the largest `L + R` over **all** nodes.

To compute `L + R` at a node you need its children's heights, so **height** is what each call returns. But the answer is not a height. Look at what each node could report:

- **Its height, `1 + max(L, R)`.** The parent can extend it: one arm, plus the edge up. This is what the parent needs.
- **Its bend, `L + R`.** The parent cannot use it: adding the parent to a path that already bends here makes a fork, a Y-shape, not a path.

The two numbers serve two audiences. So the function **returns the height to its parent and records the bend in a shared field `best`.** When the root's call ends, its return value is just the root's height. The answer is in `best`.

<Mermaid code={`flowchart LR
  K["children return heights L and R"] --> N["this node"]
  N -->|"L + R: a bend, cannot be extended"| B[("shared field: best = max(best, L + R)")]
  N -->|"1 + max(L, R): one arm, the parent can extend it"| P["parent"]`} />

<Figure caption="[1, 2, null, 3, 4, 5, null, null, 6, 7, null, null, 8], each node labelled with the height it returns. The longest path, 7–5–3–2–4–6–8, bends at node 2: L + R = 3 + 3 = 6 edges. The root never sees it: its own bend is 4 + 0 = 4, and it returns its height, 5. The diameter is what best holds: 6.">
  <Tree level={figures.diameter.level} notes={figures.diameter.notes} path={figures.diameter.path} tones={{ 1: 'gold' }} />
</Figure>

Three different numbers come out of that tree, and confusing them is how this problem is usually failed: **the root returns 5** (a height), **the path through the root is 4**, and **the diameter is 6**.

**The contract:** `height(node)` returns the number of nodes on the longest straight path down from `node`, and updates `best` with the bend at `node`. Passed down: nothing. Returned up: the height. Shared field: `best`.

### Dry run

Watch two things at once: the **returned UP** panel (heights, going to the parents) and the **shared fields** panel (`best`, updated at every node, not only the root). The last frame reads `best`, not the root's return value.

<DryRun title="Diameter of Binary Tree" frames={diameterFrames([1, 2, null, 3, 4, 5, null, null, 6, 7, null, null, 8])} predict />

### Algorithm

1. Keep a field `best = 0`.
2. In `height(node)`: if the node is `null`, return 0.
3. Get `left = height(node.left)` and `right = height(node.right)`.
4. Record the bend: `best = max(best, left + right)`.
5. Return `1 + max(left, right)` to the parent.
6. The public method calls `height(root)`, ignores its return value, and returns `best`.

Say it before you code: "The helper returns the root's height. `best` holds the longest bend anywhere. I return `best`."

### Java solution

<HintLadder hints={hints.diameter}>

```java id=diameter
private int best;                                  // shared field: the longest bend seen anywhere

public int diameterOfBinaryTree(TreeNode root) {
    best = 0;
    height(root);                                  // its return value (the root's height) is not the answer
    return best;
}

private int height(TreeNode node) {                // promise: nodes on the longest path down from node
    if (node == null) return 0;
    int left = height(node.left);
    int right = height(node.right);
    best = Math.max(best, left + right);           // the path that bends HERE: two arms, in edges
    return 1 + Math.max(left, right);              // the parent can extend only ONE arm
}
```

</HintLadder>

### Why it works

- **Settled:** when `height(node)` returns, (1) its return value is the exact height of the subtree, and (2) `best` is at least the length of every path whose bend lies inside that subtree.
- **Why the move is safe:** every path has one highest node, and at that node its length is at most `L + R`, with equality for the path that takes the longest arm on each side. The walk visits every node, so it evaluates every possible bend.
- **When we stop:** after the root returns. `best` is final.

### Complexity

- **Time O(n):** each node is visited once.
- **Space O(h):** the call stack.

### Edge cases and mistakes

- A single node (diameter 0), a vine (diameter n − 1), a longest path that avoids the root.
- Computing `height(root.left) + height(root.right)` once, at the root, finds only paths through the root. On the figure's tree it returns **4** instead of 6. Every node is a possible bend.
- Edges or nodes: `L + R` is the number of **edges**. A problem that asks for **nodes** wants `L + R + 1`. Check what is asked.
- Forgetting to reset `best` at the start of the public method: LeetCode reuses the object across test cases.

### Practice

<Trace title="Report up, record the bend" steps={diameter} takeaway="Remember: return 1 + max(L, R) to the parent; record L + R in best at every node; when the root returns, read best." />

Try the first drill in the [playground](#playground); one of its cases bends below the root on purpose.

<Reveal q="Is a field like best a global variable? Can I avoid it?">

It is shared state, scoped to one call of the public method, which is why the code resets it at the start. If you prefer no field, pass a one-element array (`int[] best = {0}`) down to the helper, or return a pair `(height, bestInside)` from every call and combine the pairs: `bestInside = max(leftBest, rightBest, L + R)`. All three are the same idea: one number goes to the parent, and the record is kept somewhere it cannot get mixed up with it.

</Reveal>

<Reveal q="Edges or nodes? LeetCode counts this diameter in edges.">

`L + R`, with heights counted in nodes, is exactly the number of **edges** on the bent path: L edges down one side and R down the other. If a problem wants the number of **nodes** on the path, it is `L + R + 1`. A single node has diameter 0 edges and 1 node.

</Reveal>

**Variations to try:** longest path where all values are equal (exit ticket); longest path in nodes instead of edges; return the two end nodes of the diameter.

<h2 id="max-path-sum">Chapter 6 · Binary Tree Maximum Path Sum</h2>

### Problem

A path is any sequence of connected nodes, going up and down, using each node at most once. It needs at least one node, but need not touch the root or a leaf. Return the largest sum of node values over all paths. Values can be negative.

`[-10, 9, 20, null, null, 15, 7]` gives 42 (the path 15 → 20 → 7).

### How to recognise it

- The same shape as the diameter: the best path between any two nodes.
- Values instead of lengths, and some values are negative, so a path may want to stop early.
- "Path may start and end anywhere."

### Brute force

For every node, find the best downward sum on each side with a separate walk, and add the node. Each separate walk covers a whole subtree, so a vine costs O(n²). Trying every pair of endpoints and summing the path is O(n²) pairs times O(n).

### Intuition

The same shape as Chapter 5, with values instead of lengths:

- Each call returns the **gain**: the best sum of a path that starts at this node and goes **down one side** (or stops here). `gain(node) = node.val + max(0, gain(left), gain(right))`.
- Every node records its **bend** in `best`: `node.val + left + right`, where each arm has been **clamped at 0**. A negative arm is dropped, because the path can always stop at this node.
- `best` starts at `Integer.MIN_VALUE`, not 0: the path needs at least one node, and if every value is negative the answer is negative.

<Figure caption="LeetCode's [−10, 9, 20, null, null, 15, 7]. Node 20 returns gain 20 + 15 = 35 to its parent and records its bend, 15 + 20 + 7 = 42, in best. The root's bend is −10 + 9 + 35 = 34 and it returns −10 + 35 = 25. The answer is best: 42.">
  <Tree level={figures.maxPath.level} notes={figures.maxPath.notes} path={figures.maxPath.path} tones={{ 0: 'red' }} />
</Figure>

**The contract:** `gain(node)` returns the best sum of a downward path starting at `node`. It also updates `best` with the best path bending at `node`. Passed down: nothing. Returned up: the gain. Shared field: `best`.

### Dry run

Same structure as the diameter. The returned value is a one-sided gain; the shared field holds the answer. Watch a negative arm get dropped.

<DryRun title="Binary Tree Maximum Path Sum" frames={maxPathFrames([-10, 9, 20, null, null, 15, 7])} predict />

### Algorithm

1. Keep a field `best = Integer.MIN_VALUE`.
2. In `gain(node)`: if `null`, return 0.
3. `left = max(0, gain(node.left))` and `right = max(0, gain(node.right))`.
4. Record the bend: `best = max(best, node.val + left + right)`.
5. Return `node.val + max(left, right)`.

### Java solution

<HintLadder hints={hints.maxPath}>

```java id=maxPathSum
private int best;                                    // shared field: the best bend seen anywhere

public int maxPathSum(TreeNode root) {
    best = Integer.MIN_VALUE;                        // values can all be negative: 0 would be a lie
    gain(root);
    return best;
}

private int gain(TreeNode node) {                    // promise: best sum of a path starting here, going down
    if (node == null) return 0;
    int left = Math.max(0, gain(node.left));         // a losing arm is dropped, not carried
    int right = Math.max(0, gain(node.right));
    best = Math.max(best, node.val + left + right);  // the path that bends HERE
    return node.val + Math.max(left, right);         // only one arm can continue up to the parent
}
```

</HintLadder>

### Why it works

- **Settled:** `gain(node)` is the best sum of a downward path starting at `node` (it includes `node.val`, so it can be negative), and `best` is at least the sum of every path whose bend lies inside the subtree already walked.
- **Why the move is safe:** the best path bends at some highest node. Its best version takes, on each side, either nothing or the best downward path from that child, which is exactly the clamped gain.
- **When we stop:** after the root returns. `best` is the answer, not the root's return value.

### Complexity

- **Time O(n):** each node is visited once.
- **Space O(h):** the call stack. LeetCode's bounds (at most 3 × 10⁴ nodes, values within ±1000) keep every sum within ±3 × 10⁷, inside `int`.

### Edge cases and mistakes

- A single negative node, all-negative trees, a path that avoids the root.
- Starting `best` at 0: on `[-3]` it returns **0**, a path that does not exist (the answer is −3).
- Forgetting to clamp: on `[2, -1]` the root takes the −1 arm and returns **1** instead of 2.

### Practice

<Trace title="When is an arm worth nothing?" steps={maxPath} takeaway="Remember: clamp each arm at 0, record node + left + right, return node + max(left, right), and start best at Integer.MIN_VALUE." />

<Reveal q="Why clamp the arms but never the node itself?">

The bend node is on the path by definition; it is the one node the path cannot skip. The arms are optional: "stop here" is always allowed and is worth 0 extra. So arms are clamped at 0, and the node's own value is always counted. That is also why a tree of all negatives returns its least negative value, never 0.

</Reveal>

**Variations to try:** return the path itself (store the best bend's endpoints); require the path to start at the root; require it to end at a leaf.

<h2 id="lca">Chapter 7 · Lowest Common Ancestor of a Binary Tree</h2>

### Problem

Given a binary tree and two nodes `p` and `q` that are both in it, return their **lowest common ancestor**: the lowest node that has both as descendants (a node counts as its own descendant).

In `[3, 5, 1, 6, 2, 0, 8, null, null, 7, 4]`, `p = 6` and `q = 4` give 5.

### How to recognise it

- "Lowest common ancestor", "first shared parent", "meeting point of two nodes".
- You can see neither node from the root, but each subtree can report what it contains.
- The answer is a node, not a number.

### Brute force

Find the path from the root to `p`, and the path from the root to `q`, store both, and compare them from the top. The last node the two paths share is the answer. That is O(n) time and O(h) extra space, and it takes two passes plus two lists. It is not slow, but one pass with no lists is cleaner.

### Intuition

Decide what each call shouts up to its parent. **The contract:** `lowestCommonAncestor(node, p, q)` returns

- `p` (or `q`) if exactly one of them is in this subtree,
- the lowest common ancestor if **both** are,
- `null` if neither is.

The base case covers the first line: if `node` is `null`, `p` or `q`, return it. Otherwise ask both children. If **both** sides report something, `p` and `q` are split across this node: it is the lowest node that sees both, so return it. If only one side reports something, pass it up unchanged.

<Figure caption="LeetCode's tree with p = 6 and q = 4. Each node is labelled with what its call returns. Node 2 passes q up; node 5 hears 6 from the left and 4 from the right, so it returns itself; everything above just passes 5 along.">
  <Tree level={figures.lca.level} notes={figures.lca.notes} tones={{ 3: 'blue', 10: 'blue', 1: 'gold' }} spread={64} />
</Figure>

### Dry run

Passed down: just the two targets. Returned up: `null`, one of the targets, or the meeting point. Watch the node where two non-null answers arrive.

<DryRun title="Lowest Common Ancestor" frames={lcaFrames([3, 5, 1, 6, 2, 0, 8, null, null, 7, 4], 6, 4)} predict />

### Algorithm

1. If the node is `null`, `p` or `q`, return the node.
2. Ask the left subtree, then the right.
3. If both answers are non-null, return this node.
4. Otherwise return whichever answer is non-null (or `null` if neither is).

Compare nodes by reference (`root == p`), not by value.

### Java solution

<HintLadder hints={hints.lca}>

```java id=lca
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    if (root == null || root == p || root == q) return root;      // found one (or nothing)
    TreeNode left = lowestCommonAncestor(root.left, p, q);
    TreeNode right = lowestCommonAncestor(root.right, p, q);
    if (left != null && right != null) return root;               // split here: the lowest meeting point
    return left != null ? left : right;                           // pass up whatever was found
}
```

</HintLadder>

### Why it works

- **Settled:** each call returns the most informative thing its subtree contains: the meeting point if both targets are inside, otherwise whichever one is inside, otherwise `null`.
- **Why the move is safe:** the lowest common ancestor is the unique node where `p` and `q` sit in different subtrees, or where the node is one of them and the other lies below. "Both sides non-null" detects the first case. In the second case the call returns the node at once, and since the problem promises both exist, the other one must be below it.
- **When we stop:** at the root. Once a meeting point is returned, every ancestor sees it on one side and `null` on the other, and passes it up untouched.

### Complexity

- **Time O(n):** each node is visited at most once.
- **Space O(h):** the call stack.

### Edge cases and mistakes

- `p` is an ancestor of `q` (the answer is `p`), `p == q`, both in the same subtree.
- Dropping the "both sides" line and always passing up `left != null ? left : right`: on the figure with p = 6 and q = 4, node 5 passes up 6 and the answer comes out **6**, which is not an ancestor of 4.
- Comparing by value when values can repeat.

<h2 id="path-sum-ii">Chapter 8 · Path Sum II</h2>

### Problem

Given a binary tree and a `targetSum`, return **all root-to-leaf paths** whose values add up to the target, each path as a list of values.

`[5, 4, 8, 11, null, 13, 4, 7, 2, null, null, 5, 1]` with target 22 gives `[[5, 4, 11, 2], [5, 8, 4, 5]]`.

<Figure caption="Each node shows what is left to find after taking it. Two leaves reach 0: 5–4–11–2 and 5–8–4–5. Leaf 7 overshoots (−5) and leaf 1 falls short (4).">
  <Tree level={figures.pathSum.level} notes={figures.pathSum.notes} path={figures.pathSum.path} pathTone="green" tones={{ 8: 'green', 11: 'green' }} spread={62} />
</Figure>

### How to recognise it

- The answer is a set of **root-to-leaf paths**, not a single number.
- Whether a path qualifies depends on **everything above** a node: the sum so far.
- "Return all paths" signals backtracking: build the path, record it, undo it.

### Brute force

Collect every root-to-leaf path first (copy each into a list), then sum each one and keep the matches. That is correct, and costs O(n · h) for the copies. The improvement is not asymptotic; it is to carry the sum down so that you never re-add a path and never copy a path that does not match.

### Intuition

The answer depends on the whole path from the root, so the call carries it down:

- **`remaining`**: the target minus everything on the path so far. Passed by value, so each call gets its own copy and nothing needs undoing.
- **`path`**: one shared list of the nodes from the root to here. It is added to on the way down, so it **must be undone on the way back up**. That is backtracking.

At a **leaf** (both children empty) with `remaining == 0`, record a **copy** of the path.

**The contract:** `walk(node, remaining, path)` adds every qualifying root-to-leaf path through `node` to the result. Passed down: `remaining` (and the shared `path`). Returned up: nothing.

### Dry run

Watch the **path** list grow on the way down and shrink on the way up. The leaf with `remaining` 0 records a copy.

<DryRun title="Path Sum II" frames={pathSumFrames([5, 4, 8, 11, null, 13, 4, 7, 2], 22)} predict />

### Algorithm

1. Start with `path = []` and `remaining = targetSum`.
2. In `walk(node, remaining, path)`: if the node is `null`, return.
3. Add `node.val` to `path` and subtract it from `remaining`.
4. If the node is a leaf and `remaining == 0`, add a **copy** of `path` to the result.
5. Walk the left child, then the right child.
6. Remove the last element of `path` (undo step 3).

### Java solution

<HintLadder hints={hints.pathSum}>

```java id=pathSum
public List<List<Integer>> pathSum(TreeNode root, int targetSum) {
    List<List<Integer>> result = new ArrayList<>();
    walk(root, targetSum, new ArrayList<>(), result);
    return result;
}

private void walk(TreeNode node, int remaining, List<Integer> path, List<List<Integer>> result) {
    if (node == null) return;
    path.add(node.val);                                   // step down: the path grows
    remaining -= node.val;                                // a local copy: nothing to undo
    if (node.left == null && node.right == null && remaining == 0)
        result.add(new ArrayList<>(path));                // a COPY: path keeps changing after this
    walk(node.left, remaining, path, result);
    walk(node.right, remaining, path, result);
    path.remove(path.size() - 1);                         // step back up: undo the add
}
```

LeetCode's bounds (at most 5000 nodes, values and the target within ±1000) keep every sum far inside `int`.

</HintLadder>

### Why it works

- **Settled:** on entry to `walk(node)` and again on exit, `path` holds exactly the nodes from the root down to `node`'s parent. Every add has one matching remove.
- **Why the move is safe:** the walk visits every node, so it reaches every leaf. At each leaf, `path` is exactly the root-to-leaf path and `remaining` is exactly target minus its sum.
- **When we stop:** when every call has returned, and `path` is empty again.

### Complexity

- **Time O(n · h):** O(n) visits, plus O(h) to copy each recorded path. That is O(n²) in the worst case.
- **Space O(h)** extra, besides the output.

### Edge cases and mistakes

- Empty tree, target 0 with an empty path, negative values.
- Adding `path` itself instead of a copy: every stored answer is the same list, which is empty when the walk ends. LeetCode's example returns `[[], []]`.
- Checking `remaining == 0` at an **empty spot** instead of at a leaf: on `[1, 2]` with target 1 it records `[1]`, though 1 is not a leaf (and real leaves get recorded twice, once per empty child).
- Forgetting the `remove`: the right side sees nodes from the left side's path.

### Practice

<Trace title="Down with a sum, up with an undo" steps={pathSum} takeaway="Remember: subtract on the way down, record a COPY at a real leaf when nothing is left, and remove the node from the path on the way back up." />

<Reveal q="Values can be negative. Can the walk stop as soon as remaining drops below 0?">

No. A later negative value can bring it back: with target 1, the path 2 → −1 is fine even though `remaining` is −1 after the 2. Pruning on a negative remainder is only safe when every value is non-negative, and the problem does not promise that.

</Reveal>

**Variations to try:** return only the number of matching paths; paths that may start and end anywhere (Path Sum III, which uses prefix sums); return the path with the largest sum.

<h2 id="validate-bst">Chapter 9 · Validate Binary Search Tree</h2>

### Problem

A binary search tree (BST) requires, at **every** node, that all values in its left subtree are **strictly smaller** and all values in its right subtree are **strictly larger**. Return whether the tree is a valid BST.

`[2, 1, 3]` is valid. `[5, 4, 6, null, null, 3, 7]` is not: 3 sits in 5's right subtree.

<Figure caption="[5, 4, 6, null, null, 3, 7], each node with the window its ancestors give it. Every parent–child pair looks fine (3 < 6), but 3 sits in 5's right subtree, so its window is (5, 6). 3 is below the floor: not a BST.">
  <Tree level={figures.validate.level} notes={figures.validate.notes} tones={{ 5: 'red' }} spread={66} />
</Figure>

### How to recognise it

- A rule about order that must hold between a node and **all** its ancestors, not just its parent.
- "Valid BST", "in range", "sorted structure".
- A tempting wrong answer: compare each node with its two children.

### Brute force

At every node, scan its entire left subtree for a value that is too big and its right subtree for one that is too small. That is correct, but each node rescans its subtree: O(n²) on a vine.

### Intuition

Comparing a node with its parent checks only part of the rule. **Pass a window down.** Each node must fit strictly inside `(low, high)`. The root's window is unbounded. Going **left**, the floor stays and the **ceiling drops** to the node's value. Going **right**, the **floor rises** to the node's value and the ceiling stays. Two numbers summarise every constraint from every ancestor.

**The contract:** `valid(node, low, high)` is `true` exactly when every value in the subtree fits strictly inside `(low, high)`. Passed down: the window. Returned up: `true` or `false`.

### Dry run

Watch the **passed DOWN** window change as the call goes left and right. The node 3 is fine next to its parent 6, but its window is (5, 6).

<DryRun title="Validate Binary Search Tree" frames={validateFrames([5, 4, 6, null, null, 3, 7])} predict />

### Algorithm

1. Call `valid(root, -infinity, +infinity)`, using `long` bounds.
2. If the node is `null`, return `true`.
3. If `node.val <= low` or `node.val >= high`, return `false`.
4. Return `valid(node.left, low, node.val) && valid(node.right, node.val, high)`.

### Java solution

<HintLadder hints={hints.validate}>

```java id=isValidBST
public boolean isValidBST(TreeNode root) {
    return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);       // wider than any int: no edge cases
}

private boolean valid(TreeNode node, long low, long high) {   // every value here must be inside (low, high)
    if (node == null) return true;
    if (node.val <= low || node.val >= high) return false;
    return valid(node.left, low, node.val)                    // going left: the ceiling drops to my value
        && valid(node.right, node.val, high);                 // going right: the floor rises to my value
}
```

</HintLadder>

### Why it works

- **Settled:** when `valid(node, low, high)` is called, `(low, high)` is exactly the set of values a node at this position may hold, and every node visited so far has fit its window.
- **Why the move is safe:** an ancestor constrains a node only through the side the node hangs on. The most recent ancestor you went left from is the tightest ceiling, and the most recent you went right from is the tightest floor, which is exactly what `(low, high)` remembers.
- **When we stop:** at the first `false` (the `&&` stops), or at the empty spots.

### Complexity

- **Time O(n):** each node is checked once.
- **Space O(h):** the call stack.

### Edge cases and mistakes

- Empty tree (valid), duplicates (invalid with strict rules), a vine.
- Checking each node only against its children passes `[5, 4, 6, null, null, 3, 7]`, which is invalid.
- Starting the bounds as `int`s, `(Integer.MIN_VALUE, Integer.MAX_VALUE)`, rejects the one-node tree `[2147483647]`, because 2147483647 is not strictly below `Integer.MAX_VALUE`. `long` bounds (or `Integer` bounds where `null` means "none") fix it.

### Practice

<Trace title="Carry the window down" steps={validate} takeaway="Remember: left lowers the ceiling to the parent, right raises the floor to the parent, and compare strictly with bounds wider than int." />

<Reveal q="Is there a way that does not carry bounds?">

Yes: **a tree is a BST exactly when its inorder listing is strictly increasing.** Walk left, node, right, and remember only the previous value; any value that is not strictly larger than the previous one breaks it. Same O(n) time and O(h) space. Use `null` (or a `long`) as "nothing yet", so that a first value of `Integer.MIN_VALUE` is not mistaken for a duplicate.

```java id=isValidBSTInorder
private Integer prev;                          // the last value visited in order; null = none yet

public boolean isValidBST(TreeNode root) {
    prev = null;
    return inorder(root);
}

private boolean inorder(TreeNode node) {
    if (node == null) return true;
    if (!inorder(node.left)) return false;
    if (prev != null && node.val <= prev) return false;   // must be STRICTLY increasing
    prev = node.val;
    return inorder(node.right);
}
```

</Reveal>

**Variations to try:** allow duplicates on the left; return the node that breaks the rule; count the nodes that are valid roots of a BST.

<h2 id="kth-smallest">Chapter 10 · Kth Smallest Element in a BST</h2>

### Problem

Given a BST and an integer `k`, return the k-th smallest value (1-indexed).

`[5, 3, 6, 2, 4, null, null, 1]` with `k = 3` gives 3.

<Figure caption="Each node labelled with its place in sorted order. To answer k = 3 the walk pushes 5, 3, 2, 1, then pops 1, 2, 3. Nodes 4, 5 and 6 are never visited.">
  <Tree level={figures.kth.level} notes={figures.kth.notes} tones={{ 1: 'gold' }} />
</Figure>

### How to recognise it

- A **BST** and a question about **order or rank**: k-th smallest, successor, range.
- You may stop early, once you have the k-th value.
- Words like "in sorted order" hint at inorder.

### Brute force

Collect every value into a list, sort it, and take the element at index k − 1. That is O(n log n) time and O(n) space. A heap of the k smallest values is O(n log k). Both ignore that the tree already stores the sorted order.

### Intuition

In a BST, **inorder (left, node, right) visits the values in increasing order**: everything left of a node is smaller, so it comes first; everything right is larger, so it comes after. The k-th node visited in order is the k-th smallest. Stop there.

The **iterative inorder walk** makes stopping easy, and it uses your own stack instead of the call stack:

1. **Go left as far as you can**, pushing every node you pass onto the stack.
2. **Pop** the top: it is the smallest value not yet visited. Visit it.
3. **Step right** once, and repeat from 1.

**The contract:** the stack holds the ancestors of the current position whose left subtrees are still being explored. Passed down: `cur`, the node being explored. Returned up: nothing; a counter decides when to stop.

### Dry run

The stack plays the role of the call stack. Watch the top of the stack: it is always the next value in sorted order once `cur` falls off the bottom of a left chain.

<DryRun title="Kth Smallest, with an explicit stack" frames={kthFrames([5, 3, 6, 2, 4, null, null, 1], 3)} predict />

### Algorithm

1. Start with `cur = root` and an empty stack.
2. While `cur` is not `null` or the stack is not empty:
3. While `cur` is not `null`: push it and move to `cur.left`.
4. Pop the top into `cur`. Decrease `k`. If `k` is 0, return `cur.val`.
5. Move to `cur.right`.

### Java solution

<HintLadder hints={hints.kth}>

```java id=kthSmallest
public int kthSmallest(TreeNode root, int k) {
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !stack.isEmpty()) {
        while (cur != null) {                // walk the left chain, saving each node to come back to
            stack.push(cur);
            cur = cur.left;
        }
        cur = stack.pop();                  // the smallest value not yet visited
        if (--k == 0) return cur.val;
        cur = cur.right;                     // its right subtree comes next in sorted order
    }
    return -1;                               // k > number of nodes (LeetCode promises it won't be)
}
```

</HintLadder>

### Why it works

- **Settled:** the stack holds, bottom to top, the ancestors of `cur` whose left subtrees are still being explored, in decreasing order of value. Values come out of the stack in strictly increasing order, and the k-th one out is the k-th smallest.
- **Why the move is safe:** when `cur` falls off the bottom of a left chain, nothing smaller than the stack's top is left unvisited, so the top is the next value in sorted order.
- **When we stop:** at the k-th pop. Nodes beyond it are never touched.

### Complexity

- **Time O(h + k):** the left chain down to the minimum, then k pops.
- **Space O(h):** the stack.

### Edge cases and mistakes

- `k = 1` (the leftmost node), `k = n` (the rightmost), a vine.
- The recursive version with the counter passed as an `int` **parameter**: Java passes ints by value, so a decrement inside the left call never reaches the parent. On `[5, 3, 6, 2, 4, null, null, 1]` with k = 3, no call ever sees its copy reach 0, and the function returns its default, **−1**. Keep the counter in a field:

```java id=kthSmallestRecursive
private int count, answer;

public int kthSmallest(TreeNode root, int k) {
    count = k;
    walk(root);
    return answer;
}

private void walk(TreeNode node) {
    if (node == null || count == 0) return;        // count == 0: already found, stop everywhere
    walk(node.left);
    if (count > 0 && --count == 0) answer = node.val;
    walk(node.right);
}
```

### Practice

<Trace title="The stack" steps={kth} takeaway="Remember: push the whole left chain, pop to visit, then step right. Stop at the k-th pop: O(h + k)." />

Try the third drill in the [playground](#playground). One of its wrong buttons visits a node before its left side, and the drill shows you which smaller value you just skipped.

<Reveal q="Follow-up: the BST changes often, and k-th smallest is asked often. Now what?">

Store in every node the **size of its subtree**, and keep it updated on insert and delete. Then at each node: if `k ≤ size(left)`, go left; if `k == size(left) + 1`, this is it; otherwise go right with `k − size(left) − 1`. Each query is O(h), and O(log n) if the tree is kept balanced. This is an *order-statistic tree*.

</Reveal>

<h3 id="vines">When the tree is a vine</h3>

Every recursive solution in this chapter uses **O(h) stack space**, and h can be n. A tree built by inserting sorted values into a BST is a **vine**: one long chain. Java does not optimise tail calls, and its default thread stack typically holds thousands to tens of thousands of frames, depending on the frame size and the `-Xss` setting.

The checker for this page does the experiment. On a vine of **10,000** nodes, the recursive `maxDepth` from Chapter 3 finishes with default settings. On a vine of **1,000,000** nodes it throws `StackOverflowError`, while the iterative walks below handle it. Most of this chapter's LeetCode problems cap n at 10⁴ or fewer, where recursion is accepted. Know the risk anyway, and know the fix: **any recursion can become a loop with your own stack, which lives on the heap.**

The general iterative inorder walk, and an iterative depth that stores the parameter next to each node on the stack:

```java id=inorderTraversal
public List<Integer> inorderTraversal(TreeNode root) {
    List<Integer> out = new ArrayList<>();
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while (cur != null || !stack.isEmpty()) {
        while (cur != null) { stack.push(cur); cur = cur.left; }
        cur = stack.pop();
        out.add(cur.val);
        cur = cur.right;
    }
    return out;
}
```

```java id=maxDepthIterative
public int maxDepth(TreeNode root) {
    if (root == null) return 0;
    Deque<TreeNode> nodes = new ArrayDeque<>();
    Deque<Integer> depths = new ArrayDeque<>();        // the parameter a recursive call would have received
    nodes.push(root);
    depths.push(1);
    int best = 0;
    while (!nodes.isEmpty()) {
        TreeNode node = nodes.pop();
        int d = depths.pop();
        best = Math.max(best, d);
        if (node.left != null) { nodes.push(node.left); depths.push(d + 1); }
        if (node.right != null) { nodes.push(node.right); depths.push(d + 1); }
    }
    return best;
}
```

**Variations to try:** the k-th largest (walk right first); the in-order successor of a node; the sum of all values in a range `[lo, hi]`.

<h2 id="build-tree">Chapter 11 · Construct Binary Tree from Preorder and Inorder Traversal</h2>

### Problem

You are given two listings of the same tree with **unique** values: its preorder and its inorder. Rebuild the tree.

`preorder = [3, 9, 20, 15, 7]`, `inorder = [9, 3, 15, 20, 7]` gives `[3, 9, 20, null, null, 15, 7]`.

<Figure caption="preorder [3, 9, 20, 15, 7] names the root, 3. Its position in inorder [9, 3, 15, 20, 7] splits the rest: [9] is the left subtree, [15, 20, 7] the right. Recursing, 20 is the next root, and it splits [15, 20, 7] into 15 and 7.">
  <Tree level={figures.build.level} tones={{ 0: 'gold' }} />
  <ArrayStrip name="preorder" values={figures.build.pre} pointers={[{ at: 0, label: 'root' }]} tones={{ 0: 'hot' }} />
  <ArrayStrip name="inorder" values={figures.build.inorder} pointers={[{ at: 1, label: 'root' }]} regions={[{ from: 0, to: 0, label: 'left', tone: 'blue' }, { from: 2, to: 4, label: 'right', tone: 'green' }]} tones={{ 1: 'hot' }} />
</Figure>

### How to recognise it

- Two traversals given, a tree wanted.
- One of them (preorder or postorder) names roots; inorder separates left from right.
- Unique values, so "find the root in inorder" has one answer.

### Brute force

Take the next preorder value as the root, **scan** the inorder array to find it, split, and recurse on copies of the sub-arrays. The scan costs O(n) per node, so a vine costs O(n²), and copying the sub-arrays adds more. Two fixes: index ranges instead of copies, and a map from value to inorder position instead of a scan.

### Intuition

- **Preorder** lists a subtree's root **first**, then its whole left subtree, then its whole right subtree.
- **Inorder** lists the left subtree, then the root, then the right subtree. So **the root's position in inorder splits the rest into left and right**, and tells you each side's size.

Keep one cursor into preorder. To build the subtree whose inorder is `inorder[lo..hi]`: the next unused preorder value is its root; find it in inorder at `mid`; build the left subtree from `inorder[lo..mid − 1]`, **then** the right from `inorder[mid + 1..hi]`. Build left first, because that is the order preorder lists them.

**The contract:** `build(lo, hi)` returns the subtree whose inorder is `inorder[lo..hi]`. Passed down: the range `(lo, hi)`. Shared: the preorder cursor `next`. Returned up: the finished subtree's root.

### Dry run

Watch the preorder cursor and the inorder range together. Each call takes the next preorder value, finds it in inorder, and splits its range.

<DryRun title="Construct from Preorder and Inorder" frames={buildFrames([3, 9, 20, 15, 7], [9, 3, 15, 20, 7])} predict />

### Algorithm

1. Put every `inorder[i] -> i` into a map. Set `next = 0`.
2. `build(lo, hi)`: if `lo > hi`, return `null`.
3. Take `preorder[next]` as the root value and advance `next`.
4. Look up its inorder index `mid`.
5. Set `root.left = build(lo, mid − 1)`, **then** `root.right = build(mid + 1, hi)`.
6. Return the root.

### Java solution

<HintLadder hints={hints.build}>

```java id=buildTree
private int next;                                  // index of the next unused root in preorder
private Map<Integer, Integer> where;               // value -> its index in inorder

public TreeNode buildTree(int[] preorder, int[] inorder) {
    next = 0;
    where = new HashMap<>();
    for (int i = 0; i < inorder.length; i++) where.put(inorder[i], i);
    return build(preorder, 0, inorder.length - 1);
}

private TreeNode build(int[] preorder, int lo, int hi) {   // the subtree whose inorder is inorder[lo..hi]
    if (lo > hi) return null;
    TreeNode root = new TreeNode(preorder[next++]);        // preorder: the root comes first
    int mid = where.get(root.val);                         // inorder: left part | root | right part
    root.left = build(preorder, lo, mid - 1);              // LEFT first: preorder lists it next
    root.right = build(preorder, mid + 1, hi);
    return root;
}
```

</HintLadder>

### Why it works

- **Settled:** when `build(lo, hi)` starts, `preorder[next]` is the root of the subtree whose inorder is `inorder[lo..hi]`; when it returns, `next` has moved past exactly that subtree's values.
- **Why the move is safe:** in both listings every subtree occupies one contiguous block. In preorder the block starts with its root and lists the left block before the right block. In inorder the root sits between the two blocks. So the shared cursor, consumed left subtree first, always points at the root of the subtree being built.
- **When we stop:** at empty ranges (`lo > hi`).

### Complexity

- **Time O(n):** one constant-time map lookup per node.
- **Space O(n):** the map, plus O(h) for the call stack. Searching inorder with a loop instead of the map costs O(n) per node: O(n²) on a vine.

### Edge cases and mistakes

- A single node, a vine (all left or all right), empty input.
- Building the right subtree before the left. The cursor then hands 9, the root of the *left* subtree, to the right side, whose inorder range does not contain it. On LeetCode's example the cursor runs off the end of preorder and the code throws `ArrayIndexOutOfBoundsException`.
- Off-by-one in the ranges: left is `lo..mid − 1`, right is `mid + 1..hi`.

### Practice

<Trace title="Which listing names the root?" steps={build} takeaway="Remember: the next preorder value is the root; its inorder position splits left from right; build left first." />

<Reveal q="Why must the values be unique? And what about postorder + inorder?">

With duplicates, "find the root in inorder" is ambiguous: preorder `[1, 1]` with inorder `[1, 1]` fits both a left child and a right child. LeetCode promises unique values.

With **postorder + inorder**, the root is the **last** postorder value. Walk the cursor from the end, and build the **right** subtree first, because postorder read backwards lists root, right, left. Preorder + postorder alone cannot always tell a lone child's side: `[1, 2]` and `[1, null, 2]` have the same preorder (1, 2) and the same postorder (2, 1).

</Reveal>

**Variations to try:** rebuild from inorder and postorder; rebuild a BST from its preorder alone (sorted order is implied); check whether two listings belong to any tree.

<h2 id="serialize">Chapter 12 · Serialize and Deserialize Binary Tree</h2>

### Problem

Design an encoding that turns any binary tree into a string, and a decoder that turns the string back into the **same** tree. Values may repeat and may be negative.

`[1, 2, 3, null, null, 4, 5]` encodes as `1,2,#,#,3,4,#,#,5,#,#`.

<Figure caption="[1, 2, 3, null, null, 4, 5] with every empty spot drawn as #. Root first, left before right: 1,2,#,#,3,4,#,#,5,#,#. Five nodes, six markers: a tree of n nodes always has exactly n + 1 empty spots.">
  <Tree level={figures.serialize.level} nulls={true} spread={44} />
  <ArrayStrip name="letter" values={figures.serialize.text.split(',')} tones={{ 2: 'ghost', 3: 'ghost', 6: 'ghost', 7: 'ghost', 9: 'ghost', 10: 'ghost' }} />
</Figure>

### How to recognise it

- "Encode and decode", "send over the wire", "save and restore" a tree.
- One string only, no second listing, and duplicates allowed.
- The decoder must know where each subtree ends.

### Brute force

Write only the values, in any single traversal order. That is not enough: `[1, 2]` and `[1, null, 2]` both become `1,2`, so the decoder cannot tell them apart. Two traversals together (Chapter 11) fix it, but need unique values and two strings. The fix for one string is to also write down where nothing grows.

### Intuition

**Write it preorder, with a marker for every empty spot.** Each node writes its value, then its left subtree, then its right subtree; an empty spot writes `#`. Commas separate tokens.

**Read it back in the same order.** Take the next token. `#` means empty: return `null`. Otherwise make the node, then read its left subtree, then its right subtree. The reader makes exactly the decisions the writer made, in the same order, so the shape comes back exactly.

**The contract:** `write(node)` appends the whole subtree's tokens; `read()` consumes exactly one subtree's tokens and returns it. Passed down: nothing (the cursor is shared). Returned up (reading): the finished subtree.

### Dry run

First writing. Every call appends one token, and the empty spots write `#`.

<DryRun title="Serialize: write preorder with markers" frames={serializeWriteFrames([1, 2, 3, null, null, 4, 5])} predict />

Now reading the same letter back. The cursor moves one token per call, and each call returns the subtree it consumed.

<DryRun title="Deserialize: read in the same order" frames={serializeReadFrames('1,2,#,#,3,4,#,#,5,#,#')} predict />

### Algorithm

Serialize:

1. If the node is `null`, append `#`. Otherwise append its value.
2. Then write the left subtree, then the right subtree.

Deserialize:

1. Split the string into tokens and read them in order.
2. If the token is `#`, return `null`.
3. Otherwise create a node, set `left = read()`, then `right = read()`, and return it.

### Java solution

<HintLadder hints={hints.serialize}>

```java id=Codec
class Codec {
    public String serialize(TreeNode root) {
        StringBuilder sb = new StringBuilder();
        write(root, sb);
        return sb.toString();
    }

    private void write(TreeNode node, StringBuilder sb) {
        if (sb.length() > 0) sb.append(',');
        if (node == null) { sb.append('#'); return; }   // the empty spot is written, not skipped
        sb.append(node.val);
        write(node.left, sb);
        write(node.right, sb);
    }

    public TreeNode deserialize(String data) {
        Deque<String> tokens = new ArrayDeque<>(Arrays.asList(data.split(",")));
        return read(tokens);
    }

    private TreeNode read(Deque<String> tokens) {
        String token = tokens.poll();
        if (token.equals("#")) return null;
        TreeNode node = new TreeNode(Integer.parseInt(token));
        node.left = read(tokens);                      // the same order it was written: node, left, right
        node.right = read(tokens);
        return node;
    }
}
```

</HintLadder>

### Why it works

- **Settled:** when `read` returns a subtree, the cursor has advanced past exactly that subtree's tokens.
- **Why the move is safe:** a preorder listing alone is ambiguous only because it hides where each subtree ends. A `#` for every empty spot marks every ending. Each reading call consumes exactly the tokens its own subtree wrote: its value, its left part, its right part.
- **When we stop:** when the first call returns, every token has been consumed.

### Complexity

- **Time O(n)** and **space O(n)** for each direction. The empty tree is the one-token letter `#`.

### Edge cases and mistakes

- Empty tree (`#`), a single node (`5,#,#`), negative values and duplicates.
- Leaving out the markers: `[1, 2]` and `[1, null, 2]` both become `1,2`, and the reader cannot know which one to grow. This is the bug from Chapter 2 in a new costume.

### Practice

<Trace title="Write it, read it back" steps={serialize} takeaway="Remember: preorder plus a # for every empty spot is a complete set of instructions; read it back with one shared cursor in the same order." />

<Reveal q="Why exactly n + 1 markers?">

Each of the n nodes has 2 child slots: 2n slots. Every node except the root fills exactly one slot, so n − 1 slots are filled and 2n − (n − 1) = **n + 1** are empty. The letter always has 2n + 1 tokens. (LeetCode's own level-order format, `[1, 2, 3, null, null, 4, 5]`, is another valid encoding; it just trims the trailing nulls.)

</Reveal>

**Variations to try:** serialize a BST with distinct values without markers (the preorder alone is enough, as the values give the shape); serialize level by level; serialize an N-ary tree with child counts.

<h2 id="symmetric">Side quest 1 · Symmetric Tree</h2>

### Problem

You are given one tree, not two. Is it the **mirror image of itself**?

`[1, 2, 2, 3, 4, 4, 3]` is symmetric. `[1, 2, 2, null, 3, null, 3]` is not.

<Figure caption="[1, 2, 2, 3, 4, 4, 3] is symmetric: the outside pair (3, 3) and the inside pair (4, 4) match. [1, 2, 2, null, 3, null, 3] is not: both 3s hang on the right, so the outside pair is (empty, 3).">
  <div style="display:flex;flex-wrap:wrap;gap:2rem;justify-content:center">
    <Tree level={figures.symmetric} tones={{ 3: 'blue', 6: 'blue', 4: 'purple', 5: 'purple' }} />
    <Tree level={[1, 2, 2, null, 3, null, 3]} tones={{ 4: 'red', 6: 'red' }} />
  </div>
</Figure>

### How to recognise it

- One tree, a question about its left half versus its right half.
- The word "mirror" or "symmetric".
- It is Same Tree (Chapter 2) with the pairing changed.

### Brute force

Invert a copy of the tree and compare it with the original using Same Tree, or compare level-by-level listings with markers. Both work in O(n) time but use O(n) extra space for the copy or the lists. Walking the two halves together needs neither.

### Intuition

Chapter 2 walked two trees in the **same** direction. Here, walk the root's two subtrees in **opposite** directions: the left subtree's left must mirror the right subtree's right (the outside pair), and the left subtree's right must mirror the right subtree's left (the inside pair). Same null handling, same value check, only the pairing changes.

**The contract:** `mirror(a, b)` is `true` exactly when `a` and `b` are mirror images. Passed down: the two nodes. Returned up: `true` or `false`.

### Dry run

The pair on top of the stack is `(left side, right side)`. Look at which children get paired.

<DryRun title="Symmetric Tree" frames={pairFrames([1, 2, 2, 3, 4, 4, 3], [], 'mirror')} predict />

### Algorithm

1. An empty tree is symmetric. Otherwise call `mirror(root.left, root.right)`.
2. If both are `null`, return `true`. If exactly one is `null`, or the values differ, return `false`.
3. Return `mirror(a.left, b.right) && mirror(a.right, b.left)`.

### Java solution

<HintLadder hints={hints.symmetric}>

```java id=isSymmetric
public boolean isSymmetric(TreeNode root) {
    return root == null || mirror(root.left, root.right);
}

private boolean mirror(TreeNode a, TreeNode b) {
    if (a == null && b == null) return true;
    if (a == null || b == null || a.val != b.val) return false;
    return mirror(a.left, b.right)           // outside with outside
        && mirror(a.right, b.left);          // inside with inside
}
```

</HintLadder>

### Why it works

- **Settled:** a call that returns `true` has verified that its two subtrees are exact reflections.
- **Why the move is safe:** a reflection swaps left and right, so the outer child of one side matches the outer child of the other, and the inner with the inner.
- **When we stop:** at the first `false`, or when every pair has run out.

### Complexity

- **Time O(n)**, **space O(h)**.

### Edge cases and mistakes

- Empty tree, a single node (symmetric), two children with different values.
- Pairing `(a.left, b.left)` is Same Tree, not mirror. On `[1, 2, 2, 3, 4, 4, 3]` it wrongly reports false.

### Practice

<Reveal q="Transfer test: given two trees A and B, is B the mirror image of A?">

It is `mirror(A, B)` itself. The root pair is just one more pair; the single-tree version starts one level down.

</Reveal>

<h2 id="subtree">Side quest 2 · Subtree of Another Tree</h2>

### Problem

Given a big tree and a small one, does some node of the big tree have a subtree **identical** to the small one, all the way down to the leaves?

`root = [3, 4, 5, 1, 2]`, `subRoot = [4, 1, 2]` gives `true`. Add a single child 0 under the 2 and it gives `false`.

<Figure caption="The small tree [4, 1, 2] matches the subtree at node 4 of [3, 4, 5, 1, 2]. Add a single child 0 under the 2 and it no longer matches: a subtree means everything below the node, not a prefix of it.">
  <div style="display:flex;flex-wrap:wrap;gap:2rem;justify-content:center">
    <Tree level={figures.subtreeRoot} tones={{ 1: 'green', 3: 'green', 4: 'green' }} />
    <Tree level={figures.subtreeSub} tones={{ 0: 'green', 1: 'green', 2: 'green' }} />
  </div>
</Figure>

### How to recognise it

- Two trees, one nested inside the other.
- "Subtree" means a node plus **everything** below it.
- You already own the identical-trees check (Chapter 2).

### Brute force

Try every node of the big tree as the start of a match, and compare with Same Tree. That is the standard solution: O(m · n) in the worst case, where m and n are the two sizes. A faster approach (below, in the Reveal) serializes both trees and searches one string inside the other.

### Intuition

The match could start at any node, so try every node: identical here, or found somewhere in the left subtree, or in the right. Two recursions, one inside the other. The outer one chooses where to start, the inner one (Same Tree) checks.

**The contract:** `isSubtree(root, sub)` is `true` when some node of `root` starts a subtree identical to `sub`. Passed down: the same `sub`. Returned up: `true` or `false`.

### Dry run

Watch each node of the big tree being tried as the start of a match. The check fails for a reason each time; the search moves on until one works.

<DryRun title="Subtree of Another Tree" frames={subtreeFrames([3, 5, 4, 6, 2, 1, 2], [4, 1, 2])} predict />

### Algorithm

1. If the big tree is empty, return whether the small tree is also empty.
2. If `same(root, sub)`, return `true`.
3. Otherwise return `isSubtree(root.left, sub) || isSubtree(root.right, sub)`.

### Java solution

<HintLadder hints={hints.subtree}>

```java id=isSubtree
public boolean isSubtree(TreeNode root, TreeNode subRoot) {
    if (root == null) return subRoot == null;
    return same(root, subRoot)                     // does the match start right here?
        || isSubtree(root.left, subRoot)           // or somewhere on the left,
        || isSubtree(root.right, subRoot);         // or somewhere on the right
}

private boolean same(TreeNode a, TreeNode b) {     // the identical-trees check
    if (a == null && b == null) return true;
    if (a == null || b == null || a.val != b.val) return false;
    return same(a.left, b.left) && same(a.right, b.right);
}
```

</HintLadder>

### Why it works

- **Settled:** every node already tried failed the identical-trees check.
- **Why the move is safe:** a copy of `sub` would have to start at some node, and the search tries all of them.
- **When we stop:** at the first match, or when every node has been tried.

### Complexity

- **Time O(m · n)** in the worst case: each of the m nodes may start a comparison that runs up to n steps.
- **Space O(h)** for the call stack.

### Edge cases and mistakes

- Small tree equal to the big one, small tree a single leaf, a match that is a prefix but not a full subtree (the figure's second tree).
- Comparing only values at the matching node and not the whole subtree.

### Practice

<Reveal q="It is O(m · n) in the worst case. Is there anything faster?">

Yes. Serialize both trees with markers (Chapter 12), with a separator before each value so that 2 cannot match the end of 12, and search for the small string inside the big one with KMP in O(m + n). Or hash every subtree bottom-up (a Merkle-style hash) and compare hashes. In an interview, give the O(m · n) version first and name these as the follow-up.

</Reveal>

<Reveal q="Transfer test: count how many nodes of the big tree root a copy of the small one.">

Replace the `||` with a sum: `(same(root, sub) ? 1 : 0) + count(left) + count(right)`.

</Reveal>

<h2 id="good-nodes">Side quest 3 · Count Good Nodes in Binary Tree</h2>

### Problem

A node is **good** if no node on the path from the root down to it has a larger value. Count the good nodes.

`[3, 1, 4, 3, null, 1, 5]` gives 4.

<Figure caption="Each node shows the largest value above it. Good: 3 (the root), 4, the lower 3 (3 ≥ 3: ties are good) and 5. Not good: both 1s. Answer 4.">
  <Tree level={figures.good.level} notes={figures.good.notes} tones={{ 0: 'green', 2: 'green', 3: 'green', 6: 'green', 1: 'red', 5: 'red' }} spread={70} />
</Figure>

### How to recognise it

- A property of a node that depends on its **ancestors** ("no larger value above it").
- The final answer is a **count over the subtree**.
- Both directions at once: something flows down, something flows up.

### Brute force

For each node, walk up through its ancestors and check whether any is larger. With parent pointers that is O(n · h): up to O(n²) on a vine. The ancestors' maximum is shared by every node on the same path, so it can be carried down instead of re-walked.

### Intuition

Whether a node is good depends on what is **above** it, so the call receives one number as a parameter: the largest value on the path so far. The count, on the other hand, is a sum over the subtree, so each call **returns** it. Both directions in one function: a parameter going down, a return value coming up.

**The contract:** `count(node, maxAbove)` returns the number of good nodes in the subtree, given that `maxAbove` is the largest value on the path above `node`. Passed down: `max(maxAbove, node.val)`. Returned up: the count.

### Dry run

Watch **passed DOWN** (the running maximum) and **returned UP** (the counts) change independently in the same walk.

<DryRun title="Count Good Nodes" frames={goodNodesFrames([3, 1, 4, 3, null, 1, 5])} predict />

### Algorithm

1. Call `count(root, Integer.MIN_VALUE)`: nothing is above the root.
2. If the node is `null`, return 0.
3. The node is good if `node.val >= maxAbove`.
4. Pass `max(maxAbove, node.val)` to both children.
5. Return `(good ? 1 : 0) + count(left) + count(right)`.

### Java solution

<HintLadder hints={hints.good}>

```java id=goodNodes
public int goodNodes(TreeNode root) {
    return count(root, Integer.MIN_VALUE);           // nothing above the root
}

private int count(TreeNode node, int maxAbove) {     // maxAbove flows DOWN; the count flows UP
    if (node == null) return 0;
    int good = node.val >= maxAbove ? 1 : 0;
    int carry = Math.max(maxAbove, node.val);
    return good + count(node.left, carry) + count(node.right, carry);
}
```

</HintLadder>

### Why it works

- **Settled:** `maxAbove` is the largest value on the path from the root to the parent of the current node.
- **Why the move is safe:** a node is good exactly when it is at least as large as everything above it, and the maximum summarises everything above it.
- **When we stop:** at the empty spots; the root's return value is the answer.

### Complexity

- **Time O(n)**, **space O(h)**.

### Edge cases and mistakes

- A single node (good), strictly decreasing values (only the root), ties (good: `>=`, not `>`).
- Passing `node.val` down instead of the running maximum.

### Practice

<Reveal q="Transfer test: find the largest |a − b| where a is an ancestor of b.">

Carry both the minimum and the maximum seen on the path down. At each node, compare its value with both and keep the biggest gap in a shared field (or return it up).

</Reveal>

<h2 id="lca-bst">Side quest 4 · Lowest Common Ancestor of a Binary Search Tree</h2>

### Problem

Chapter 7 again, but the tree is a **binary search tree**.

In `[6, 2, 8, 0, 4, 7, 9, null, null, 3, 5]`, `p = 3` and `q = 5` give 4.

<Figure caption="p = 3 and q = 5: both are smaller than 6 (go left), both larger than 2 (go right), and at 4 they split: 3 left, 5 right. The answer is 4, found by visiting 3 nodes.">
  <Tree level={figures.lcaBst.level} tones={{ 0: 'dim', 1: 'dim', 4: 'gold', 9: 'blue', 10: 'blue' }} path={[0, 1, 4]} spread={60} />
</Figure>

### How to recognise it

- A common-ancestor question on a **BST**.
- Order lets you skip whole subtrees.

### Brute force

Ignore the BST property and use the general solution from Chapter 7: O(n) time, searching both sides at every node. It is correct, but it ignores the ordering that tells you which side to search.

### Intuition

You no longer need to search both sides, because the values tell you where `p` and `q` are. From the root: if both are **smaller** than the current node, both are in the left subtree, and so is their meeting point, so go left. If both are **larger**, go right. Otherwise they split here (or the current node **is** one of them): this is the lowest common ancestor. One path down, no recursion needed.

**The contract:** at each step, the LCA lies in the subtree rooted at `cur`. Each step discards one whole subtree.

### Dry run

Each frame discards one side of the tree. The queued nodes are `p` and `q`.

<DryRun title="LCA in a BST" frames={lcaBstFrames([6, 2, 8, 0, 4, 7, 9, null, null, 3, 5], 3, 5)} predict />

### Algorithm

1. Start at the root.
2. If `p.val` and `q.val` are both smaller than `cur.val`, move left.
3. If both are larger, move right.
4. Otherwise return `cur`.

### Java solution

<HintLadder hints={hints.lcaBst}>

```java id=lcaBst
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    TreeNode cur = root;
    while (cur != null) {
        if (p.val < cur.val && q.val < cur.val) cur = cur.left;          // both on the left
        else if (p.val > cur.val && q.val > cur.val) cur = cur.right;    // both on the right
        else return cur;                       // they split here, or cur is one of them
    }
    return null;
}
```

</HintLadder>

LeetCode's BST has unique values and both nodes exist.

### Why it works

- **Settled:** the lowest common ancestor is always inside the subtree of `cur`.
- **Why the move is safe:** if both values are smaller than `cur.val`, both nodes are in `cur`'s left subtree, so no ancestor above that subtree can be lower than the answer.
- **When we stop:** when the two values split around `cur`, or `cur` equals one of them.

### Complexity

- **Time O(h)**, **space O(1)**.

### Edge cases and mistakes

- `p` is the ancestor of `q`, `p == q`, one of the values equals the root.
- Using `<=` in the first two tests moves past a node that is itself `p` or `q`.

### Practice

<Reveal q="Transfer test: in a BST, return every value in the range [lo, hi].">

Which subtrees can you skip without looking inside? Go left only if `lo < node.val`, go right only if `node.val < hi`, and record `node.val` when it lies in the range.

</Reveal>

<h2 id="house-robber-iii">Side quest 5 · House Robber III</h2>

### Problem

Each node holds money. You may take any set of nodes, but never a node and its parent. Maximise the total.

`[3, 4, 5, 1, 3, null, 1]` gives 9 (take 4 and 5).

<Figure caption="LeetCode's [3, 4, 5, 1, 3, null, 1], each node with its pair (skip, take). Node 4: skip = 1 + 3 = 4, take = 4. Node 5: skip = 1, take = 5. Root: skip = max(4, 4) + max(1, 5) = 9, take = 3 + 4 + 1 = 8. Answer 9: take 4 and 5.">
  <Tree level={figures.rob.level} notes={figures.rob.notes} tones={{ 1: 'green', 2: 'green' }} spread={64} />
</Figure>

### How to recognise it

- Choose nodes, with a rule that links a node to its parent or children.
- The parent's choice depends on which choice each child made.
- It is dynamic programming on a tree.

### Brute force

Recurse with two choices at each node: take it (then recurse on its grandchildren) or skip it (then recurse on its children). Without remembering results, the same subtree is solved again and again, and the running time can be exponential. Taking every other level is also wrong, as the Reveal below shows.

### Intuition

At each node you either **take** it or **skip** it, and the parent's choice depends on which one the child made. One number cannot carry both futures, so each call returns a **pair**: `(best if this node is skipped, best if it is taken)`.

- **Take** this node: its children must be skipped, so `node.val + left.skip + right.skip`.
- **Skip** this node: each child is free to do whichever is better, so `max(left) + max(right)`.

**The contract:** `best(node)` returns `{skip, take}` for the subtree. Passed down: nothing. Returned up: the pair.

### Dry run

The **returned UP** panel now holds pairs. Watch a node combine its children's pairs into its own.

<DryRun title="House Robber III" frames={robFrames([3, 4, 5, 1, 3, null, 1])} predict />

### Algorithm

1. An empty tree returns `{0, 0}`.
2. Get the pairs `l` and `r` from the children.
3. `skip = max(l[0], l[1]) + max(r[0], r[1])`.
4. `take = node.val + l[0] + r[0]`.
5. Return `{skip, take}`. The answer is the larger of the root's two values.

### Java solution

<HintLadder hints={hints.rob}>

```java id=rob
public int rob(TreeNode root) {
    int[] r = best(root);
    return Math.max(r[0], r[1]);
}

private int[] best(TreeNode node) {                   // {best if node is skipped, best if node is taken}
    if (node == null) return new int[]{0, 0};
    int[] l = best(node.left), r = best(node.right);
    int skip = Math.max(l[0], l[1]) + Math.max(r[0], r[1]);
    int take = node.val + l[0] + r[0];                // taking me forces both children to be skipped
    return new int[]{skip, take};
}
```

</HintLadder>

### Why it works

- **Settled:** each pair holds the best total for the subtree in both situations, so the parent never has to look inside.
- **Why the move is safe:** taking a node forbids exactly its children, and skipping it forbids nothing, so the two formulas cover every legal choice.
- **When we stop:** at the root; the answer is `max(skip, take)`.

### Complexity

- **Time O(n)**, **space O(h)**. Each subtree's answer is computed once and combined.

### Edge cases and mistakes

- A single node, a vine, all zeros.
- Returning one number: the parent cannot tell whether the child was taken.
- Using `take = node.val + max(left) + max(right)`, which lets a taken node keep a taken child.

### Practice

<Reveal q="Why not just take every other level?">

Because sometimes skipping **two** levels in a row is best. On the vine `[4, 1, null, 2, null, 3]`, the even levels give 4 + 2 = 6 and the odd levels give 1 + 3 = 4, but taking 4 and 3 is allowed and gives **7**. The pair tries every choice at every node; alternating levels tries only two.

</Reveal>

<h2 id="flatten">Side quest 6 · Flatten Binary Tree to Linked List</h2>

### Problem

Do not answer a question about the tree. **Rewire** it, in place, into a single chain: every `left` pointer empty, and each `right` pointer leading to the next node in **preorder**.

`[1, 2, 5, 3, 4, null, 6]` becomes `1 → 2 → 3 → 4 → 5 → 6`.

<Figure caption="LeetCode's [1, 2, 5, 3, 4, null, 6] becomes the chain 1 → 2 → 3 → 4 → 5 → 6: its preorder. The walk handles 6 first, then 5, 4, 3, 2, and 1 last.">
  <Tree level={figures.flatten.level} />
  <ArrayStrip name="list" values={figures.flatten.chain} join="→" indices={false} />
</Figure>

### How to recognise it

- Change the structure in place, with an order given (preorder, inorder).
- "Linked list" output from a tree.
- Building a chain is easiest from its end.

### Brute force

Collect the nodes in preorder into a list, then walk the list and rewire each node. That is O(n) time and O(n) extra space. The in-place version below needs only the call stack.

### Intuition

A linked chain is easiest to build **from its end**. If you visit the nodes in exactly the reverse of preorder (right subtree, then left subtree, then the node), then when you reach a node, everything after it in the final chain is already built, and `prev` points at its head. The node only has to hook itself on: `node.right = prev; node.left = null; prev = node`.

**The contract:** after `unroll(node)` returns, `prev` is the head of a chain holding `node`'s subtree in preorder followed by everything handled earlier. Passed down: nothing. Shared: `prev`.

### Dry run

The tree drawn keeps its original shape, so you can see the visiting order (right first). The list below it is what `prev` heads.

<DryRun title="Flatten Binary Tree to Linked List" frames={flattenFrames([1, 2, 5, 3, 4, null, 6])} predict />

### Algorithm

1. Keep a field `prev = null`.
2. In `unroll(node)`: if `null`, return.
3. `unroll(node.right)`, then `unroll(node.left)`.
4. Set `node.right = prev`, `node.left = null`, and `prev = node`.

### Java solution

<HintLadder hints={hints.flatten}>

```java id=flatten
private TreeNode prev;                  // the head of the list built so far

public void flatten(TreeNode root) {
    prev = null;
    unroll(root);
}

private void unroll(TreeNode node) {    // reverse preorder: right, left, then the node
    if (node == null) return;
    unroll(node.right);
    unroll(node.left);
    node.right = prev;                  // everything after me is already a list
    node.left = null;
    prev = node;
}
```

</HintLadder>

### Why it works

- **Settled:** everything handled so far forms one chain, headed by `prev`, in preorder.
- **Why the move is safe:** reverse preorder handles a node only after everything that follows it in preorder, so one pointer assignment finishes the chain.
- **When we stop:** after the root; `prev` is the root and the chain is complete.

### Complexity

- **Time O(n)**, **space O(h)**.

### Edge cases and mistakes

- Empty tree, a tree with only left children, only right children.
- Visiting left before right and then assigning pointers: the right subtree is overwritten before it is handled.
- Forgetting to set `node.left = null`.

### Practice

<Reveal q="Can it be done in O(1) extra space?">

Yes, with a loop and no stack. At each node that has a left child, find the **rightmost** node of its left subtree, hang the node's right subtree there, move the left subtree to the right, clear `left`, and step right. Each edge is walked a constant number of times: O(n) time, O(1) space. It is the same rewiring trick that powers Morris traversal (see Look these up yourself).

</Reveal>

<h2 id="choose-the-tool">When DFS is the wrong tool</h2>

Depth-first walks are right when **the answer for a node is built from the answers below it, or from the state above it**. Reach for something else when:

- **The question is about rows or nearness:** the shallowest leaf, level-by-level values, the view from the right side, the zigzag order. A **row-by-row walk with a queue** handles one level at a time and can stop at the first leaf it meets. Minimum depth works either way, but on a lopsided tree the queue version touches far fewer nodes. A DFS that goes down a 300-node-deep left side before it ever looks at a leaf three levels below the root on the right is doing the wrong work first.
- **The tree is very deep:** same algorithm, but iterative, with your own stack ([When the tree is a vine](#vines)).
- **The same question is asked many times** (LCA of many pairs, k-th smallest after many updates): **preprocess or augment**: binary lifting, Euler tour, subtree sizes. See Look these up yourself.
- **The structure has cycles or shared children:** it is a **graph**, and a DFS needs a visited set or it will loop forever.

<Mermaid code={`flowchart TD
  Q["A question about a tree"] --> R{"About rows or nearest?"}
  R -->|yes| BFS["Row-by-row walk with a queue"]
  R -->|no| D{"Needs what is below a node?"}
  D -->|yes| UP["Return from the children\n(+ a shared field if the answer is not what the parent needs)"]
  D -->|no| DOWN["Pass state down as parameters"]
  UP --> H{"Height could be huge?"}
  DOWN --> H
  H -->|yes| IT["Same walk, explicit stack"]
  H -->|no| REC["Recursion is fine"]`} />

<Reveal q="Right side view: DFS or row by row?">

Both work in O(n). Row by row is the natural fit: keep the current row, record its last node, build the next row from the children. The DFS version visits the right child before the left, passes the depth down, and records a node when its depth is seen for the first time. If you can say why both are correct, you understand both tools; pick the one you can defend.

</Reveal>

<h2 id="exit-ticket">Exit ticket · Build a solution with the labels removed</h2>

Choose one. Keep the chapters closed. Before any code, write the contract (what the call returns), the base case, the direction (what is passed down, what is returned up), whether you need a shared field, and the complexity.

1. **The longest same-value path.** Count the edges of the longest path in which every node has the same value. The path need not pass through the root. Test a single node, all values equal, and a tree where the best path bends below the root.
2. **Running totals in a search tree.** In a BST, replace every value with the sum of all values greater than or equal to it. Test a single node, a vine, and `[4, 1, 6, 0, 2, 5, 7]`.
3. **The widest gap.** Return the largest |a − b| where node a is an ancestor of node b. Test a vine that only increases, and a tree whose largest gap is between the root and a deep leaf.

<Reveal q="I have written and tested it. What should my reasoning contain?">

**Longest same-value path:** Chapter 5 with a condition. The helper returns the longest **same-value arm** going down from this node, in edges. For each child, the arm on that side is `1 + child's arm` if the child has the same value, and 0 otherwise. Record `left + right` in `best`; return `max(left, right)`. Return one thing, record another.

**Running totals:** reverse inorder (right, node, left) visits values from largest to smallest. Carry a running sum (a field); at each node add its value to the sum, then overwrite the value with the sum. Chapter 10's order, backwards.

**Widest gap:** pass the minimum and maximum seen on the path down (Side quest 3's idea, twice). At each node, the best gap involving it as the lower end is `max(|val − min|, |val − max|)`; take the maximum over all nodes.

Now explain why a slightly wrong version fails one of your tests: the root-only bend, a forgotten reset of the running sum between calls, carrying only the maximum. That counterexample is stronger evidence of understanding than a memorised template.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Mirror / swap every node | Recurse on both children, swap the two results | The call returns its subtree, mirrored |
| Are two trees identical? | Walk both together; null checks before values | Both empty = match; one empty = no match |
| Height, depth, size | `1 + max(left, right)`, 0 for null (or carry depth down) | Each return is the exact height of that subtree |
| Balanced at every node | Return height, or −1 for “broken”; stop early | Non-negative return = balanced and its height |
| Longest path between any two nodes | Return height; best = max(left + right) | Return is for the parent; best is the answer |
| Best path sum, values may be negative | Clamp arms at 0; board starts at `Integer.MIN_VALUE` | Gain = best one-sided path starting here |
| Lowest common ancestor | Return null / p / q / the node where both sides report | The first node to hear from both sides |
| All root-to-leaf paths with a sum | Carry remaining + path down; copy at a leaf; remove on the way up | Path = root to here, on entry and on exit |
| Is it a valid BST? | Pass (low, high) down with long bounds; or inorder strictly increasing | Every node fits its ancestors’ window |
| k-th smallest in a BST | Iterative inorder with a stack; stop at the k-th pop | Pops come out in sorted order |
| Very deep tree | The same walk with an explicit stack | The stack holds what the call stack would have |
| Rebuild from preorder + inorder | Preorder cursor names the root; inorder map splits; left first | `preorder[next]` is the root of the range being built |
| Send a tree as text | Preorder with `#` for every empty spot; read back in the same order | Each read consumes exactly its own subtree |
| Symmetric | `mirror(a.left, b.right) && mirror(a.right, b.left)` | Outside with outside, inside with inside |
| Subtree of another tree | Identical-check at every node | The whole subtree must match |
| Depends on the path above | Carry it down (max so far, min and max, bounds) | The parameter summarises the ancestors |
| LCA in a BST | Both smaller → left; both larger → right; else here | The split point is the answer |
| Choose nodes, never parent and child | Return a pair (skip, take) | The parent picks from the children’s pairs |
| Rewire into a preorder list | Reverse preorder (right, left, node) with `prev` | Everything after the node is already a list |
| Rows, nearest, view from a side | A row-by-row walk with a queue | One level at a time |

### Five common bugs

1. **Reading `.val` before the null checks.** Base cases come first, every time: both-null, then one-null, then values.
2. **Answering with the return value when the answer is in a shared field.** The root returns a height; the diameter is in `best`. Say both before you code.
3. **Checking only the parent.** Balance must hold at every node; BST order must hold against every ancestor. Pass bounds down or return verdicts up.
4. **Recording a live list.** In Path Sum II, `result.add(path)` stores a list that will be empty by the end. Store `new ArrayList<>(path)`, and undo every add on the way back up.
5. **Starting a best at 0, or a bound at an `int` extreme.** All-negative trees need `Integer.MIN_VALUE`; BST bounds need `long` or `null` so that `Integer.MIN_VALUE` and `Integer.MAX_VALUE` are legal values.

<h2 id="revision">Revision</h2>

**How to recognise it.** The input is a tree, or a structure shaped like one. The question is about every node or about paths: height, balance, best path, ancestors, root-to-leaf sums, order in a BST, or rebuilding and sending a tree. Rows and nearness point to BFS instead.

**Core algorithm.**

1. Write the contract: what does `f(node)` return for its subtree?
2. Write the base case for `null`.
3. Trust both children, then combine their answers with `node.val`.
4. Decide what flows **down** (parameters), what flows **up** (return value), and whether the answer is a **shared field** because the parent cannot use it.
5. Choose when to do the work: preorder (on the way down), inorder (between the subtrees), postorder (on the way back up).

**Common mistakes.**

- Reading `.val` before the null checks.
- Reading the root's return value when the answer lives in a shared field (diameter, max path sum).
- Checking only the parent, not every ancestor (balance, BST bounds).
- Storing a live `path` instead of a copy; forgetting to undo the add.
- Starting `best` at 0 or using `int` bounds where values can hit the limits.
- Building the right subtree before the left from a preorder cursor.

**Complexity.** O(n) time and O(h) space for every recursive solution here, where h runs from log₂ n to n. Exceptions: Path Sum II pays O(n · h) to copy answers, Subtree of Another Tree is O(m · n), Kth Smallest is O(h + k), LCA in a BST is O(h) time and O(1) space, and building from two listings needs an O(n) map.

**Three representative problems.**

1. [Diameter of Binary Tree](https://leetcode.com/problems/diameter-of-binary-tree/): return the height, record the bend.
2. [Validate Binary Search Tree](https://leetcode.com/problems/validate-binary-search-tree/): pass a window of allowed values down.
3. [Lowest Common Ancestor of a Binary Tree](https://leetcode.com/problems/lowest-common-ancestor-of-a-binary-tree/): return what each subtree found, and meet where two answers arrive.

**Look these up yourself** — real ideas this book didn’t have room for:

- **Morris traversal** — inorder in O(1) extra space by temporarily threading right pointers back to ancestors.
- **Self-balancing BSTs (AVL, red-black)** — keep h = O(log n), so every O(h) bound in this book becomes O(log n).
- **Order-statistic trees** — subtree sizes in every node: k-th smallest and rank in O(log n) with updates.
- **Binary lifting and Euler tour + RMQ** — preprocess once, then answer LCA queries in O(log n) or O(1).
- **Rerooting DP** — compute a bottom-up answer for every node as the root, in two passes instead of n.
- **Merkle hashing of subtrees** — find duplicate subtrees or answer Subtree of Another Tree in near-linear time.
- **Catalan numbers** — how many tree shapes n nodes can make, and why one plain traversal can’t pin down the shape.
- **Structural induction** — the formal name for “trust the call”: prove it for the empty tree and for one combine step.
