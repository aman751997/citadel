<h2 id="prologue">Prologue · Words that begin alike</h2>

Suppose you store 10,000 words and people keep asking: does any word start with `tran`? Is `tram` a word? A list scans all 10,000 words for every question. A trie answers each question by walking a few nodes, however many words are stored.

A **trie** (from re*trie*val, pronounced "try"; also called a prefix tree) stores a set of words as paths from a root. Each edge carries **one letter**. Each node therefore stands for exactly one prefix: the letters on the path from the root down to it. **Words that begin alike share the nodes of their common beginning.**

A path can stop anywhere, so every node also carries a flag, **`isEnd`**: true when an inserted word ends exactly here. Without it, `app` and `apple` would look the same, because every node of `app` already exists on the way to `apple`.

<Figure caption="A trie holding app, apple, apt and bat. Green nodes have isEnd = true. app and apple share three nodes; apt shares two of them. Asking whether any word begins with ap is a walk of two steps, whatever else is stored.">

  APPL -->|e| APPLE["apple ✓"]

Three questions to ask of every trie problem:

1. **What is settled?** The node you stand on *is* the letters walked so far. Every stored word with that beginning lives below it, and no other word does.
2. **Why is this move safe?** Following the next letter's edge discards only words that differ from the query at that letter. They can never match.
3. **When do I stop?** When the letters run out (then `isEnd` answers "is this a word?", and merely being there answers "does any word start this way?"), or when the next edge is missing (no stored word continues this way).

### When this pattern fires

You are asked about **prefixes**, or about **many words at once** against the same input, and checking words one by one would repeat the same letter comparisons.

- **"Does any word start with...", autocomplete, suggestions as you type.** Scanning n stored words costs O(n · L) per question. A trie walk costs **O(L)**, independent of n.
- **Patterns with wildcards over a dictionary** (`b.d`). The walk branches only at the wildcards.
- **Find all dictionary words in a grid or a text.** One walk of the input serves every word that shares those letters.
- **Shortest or longest stored prefix of a word** (replace words with roots; routers do longest-prefix matching on addresses).
- **Maximise XOR.** A trie over the *bits* of numbers, walked greedily from the highest bit.

<h2 id="implement-trie">Chapter 1 · Implement Trie (Prefix Tree)</h2>

### Problem

Build a class with `insert(word)`, `search(word)` (was this exact word inserted?) and `startsWith(prefix)` (was any inserted word starting with this prefix?). Words are lowercase `a` to `z`.

Insert `apple`. Then `search("app")` is `false`, `startsWith("app")` is `true`, `search("apple")` is `true`.

### How to recognise it

- Many words are stored once and queried many times.
- The questions mention **prefixes**: "starts with", autocomplete, "any word that begins...".
- You need to design a class with insert and lookup operations.

### Brute force

Keep the words in a list or a `HashSet`. `search` is fast with a set: O(L) to hash the word. But `startsWith` has to test every stored word: **O(n · L) per question**. With 100,000 words and 100,000 prefix questions that is about 10¹⁰ letter comparisons.

### Intuition

Words that start the same way could share the storage for that start. Picture a tree where each edge carries one letter and each word is a path from the root. Then:

- A shared beginning is stored **once**.
- Checking a prefix means following its letters. If every edge exists, a word starts this way. The walk costs O(L), whatever is stored.
- Following a prefix does not prove that the prefix is itself a word. That is what `isEnd` records.

A node is two things: an array of 26 child references (`children[c - 'a']`) and the boolean `isEnd`. The root is an ordinary node for the empty prefix.

### Algorithm

All three operations are **one walk** from the root, one letter per step.

1. **insert:** for each letter, if the child slot is null, create a node there. Step onto the child. After the last letter, set `isEnd = true`.
2. **search:** walk the letters. A null child means `false`. After the last letter, **return `isEnd`**.
3. **startsWith:** the same walk. A null child means `false`. Finishing the walk means `true`. No flag check.

Put the walk in one private helper so `search` and `startsWith` cannot drift apart.

### Java solution

Work through the hints first, then reveal the code.

<HintLadder hints={hints.trie}>

```java id=Trie
class Trie {
    private static class Node {
        Node[] children = new Node[26];          // one slot per letter 'a'..'z'
        boolean isEnd;                           // an inserted word ends exactly here
    }

    private final Node root = new Node();        // the empty prefix

    public void insert(String word) {
        Node node = root;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new Node();   // grow
            node = node.children[i];                                        // follow
        }
        node.isEnd = true;                                                  // mark the word end
    }

    public boolean search(String word) {
        Node node = walk(word);
        return node != null && node.isEnd;       // arriving is not enough: isEnd decides
    }

    public boolean startsWith(String prefix) {
        return walk(prefix) != null;             // arriving is enough
    }

    private Node walk(String s) {                // the one walk all three share
        Node node = root;
        for (char c : s.toCharArray()) {
            node = node.children[c - 'a'];
            if (node == null) return null;       // no stored word continues this way
        }
        return node;
    }
}
```

</HintLadder>

**Array or map?** The 26-slot array gives O(1) child lookup with no hashing, and visits children in alphabetical order, which helps later. It wastes memory when nodes are sparse and only works for a small, known alphabet. For Unicode, mixed case or arbitrary characters, store children in a map that holds only the children that exist.

```java id=MapTrie
class MapTrie {
    private static class Node {
        Map<Character, Node> children = new HashMap<>();   // only the letters that actually occur
        boolean isEnd;
    }

    private final Node root = new Node();

    public void insert(String word) {
        Node node = root;
        for (char c : word.toCharArray()) node = node.children.computeIfAbsent(c, k -> new Node());
        node.isEnd = true;
    }

    public boolean search(String word) {
        Node node = walk(word);
        return node != null && node.isEnd;
    }

    public boolean startsWith(String prefix) {
        return walk(prefix) != null;
    }

    private Node walk(String s) {
        Node node = root;
        for (char c : s.toCharArray()) {
            node = node.children.get(c);
            if (node == null) return null;
        }
        return node;
    }
}
```

| | `Node[26]` children | `HashMap` children |
|---|---|---|
| Child lookup | O(1), one array index | O(1) expected, one hash |
| Memory per node | 26 slots, used or not | proportional to real children, but each entry costs more |
| Alphabet | small and known (`a`-`z`, bits, digits) | large or unknown (Unicode, mixed case, symbols) |
| Children in sorted order | free (index order) | needs a `TreeMap` or a sort |

### Why it works

- **Settled:** every node stands for exactly one prefix (the letters on its path). A node exists if and only if some inserted word has that prefix. `isEnd` is true if and only if that prefix was itself inserted.
- **Why the move is safe:** a node exists only if some inserted word passed through it, so arriving at the end of a prefix proves an inserted word starts with it. `isEnd` is set only on the last node of an inserted word, so it is true exactly for prefixes inserted as words.
- **When we stop:** when the letters run out, or when a child is missing (then no stored word has this beginning).

### Complexity

- **Time O(L) per operation** for a word of length L, independent of how many words are stored.
- **Space:** at most one node per inserted letter, so O(total letters) nodes. Each node carries 26 slots, so up to O(total letters × 26) references. For 10,000 words of 8 letters with no sharing at all, that is 80,000 nodes and 2,080,000 slots: roughly 8 MB at the 4 bytes per reference a 64-bit JVM typically uses. Real words share beginnings, so it is usually far less.

### Edge cases and mistakes

- Inserting a word that is a prefix of one already stored (`app` after `apple`): no new node, but `isEnd` must still be set.
- Inserting the same word twice: harmless with a flag.
- `search` for a longer word than any stored (`apples`): the walk falls off.
- A name that uses characters outside `a`-`z` crashes `c - 'a'`. Use map children for such input.

The most common bug is a `search` that forgets `isEnd`:

```java fragment
public boolean search(String word) {
    return walk(word) != null;    // BUG: that is startsWith. insert("apple"), then search("app") returns true
}
```

<Reveal q="Why not keep a HashSet of the words, and scan it for startsWith?">

A `HashSet<String>` answers `search` in O(L): hash the word, look it up. But `startsWith` has to test every stored word: O(n · L) per question. With 100,000 words and 100,000 prefix questions that is about 10¹⁰ letter comparisons. The trie answers each in O(L), however many words are stored. If you never ask about prefixes, the HashSet wins: see <a href="#choose-the-tool">When a trie is the wrong tool</a>.

</Reveal>

<Reveal q="Then why not a HashSet of every prefix of every word?">

It works for `startsWith`, and for small inputs it is a fair answer. But a word of length L adds L prefixes, and hashing each costs up to O(L), so an insert is O(L²) and the memory is the sum of all those prefix strings. Worse, the set can only say yes or no: it can't list the words under a prefix, branch at a wildcard, or walk a grid in lockstep. The trie stores each shared beginning once and keeps the structure the later chapters need.

</Reveal>

**Variations to try:** `delete(word)`; `countWordsWithPrefix(prefix)`; a trie whose children are bits instead of letters.

<h2 id="wildcard-search">Chapter 2 · Design Add and Search Words</h2>

### Problem

`addWord(word)` stores a word. `search(word)` may contain dots, and **each dot matches exactly one letter of any kind**.

After `addWord("bad")`, `addWord("dad")`, `addWord("mad")`: `search("pad")` is `false`, `search("bad")` is `true`, `search(".ad")` is `true`, `search("b..")` is `true`.

### How to recognise it

- A dictionary, plus queries with unknown letters: `.`, `?`, "blurred" characters.
- The unknown letter is a single character, so the length is fixed.
- Chapter 1's structure, but a query can't follow one fixed path.

### Brute force

Keep the words in a list and compare the pattern against every word of the same length: O(n · L) per search. With a `HashSet` you could try every letter at each dot, but with d dots that is 26^d lookups. LeetCode allows only 2 dots, so 676 lookups is fine there, but it explodes for more.

### Intuition

`addWord` is Chapter 1's `insert`, unchanged. Only `search` changes.

- At a **letter**, there is still exactly one edge to follow, or none.
- At a **dot**, any child might lead to a match and you can't know which. So **try every existing child in turn**, depth first, and return true the moment one succeeds.
- If a child fails, **back out** and give the next child its turn. Only when every child has failed does the dot fail.

The recursion carries two things: the position `i` in the pattern and the node you stand on.

### Dry run

Words `ax` and `by`, pattern `.y`. The dot tries `a` first and fails, then backs out and tries `b`. Queued nodes are children still waiting for their turn.

<DryRun title="search(.y) with ax and by" frames={wildcardFrames(['ax', 'by'], '.y')} predict />

### Algorithm

`search(word, i, node)`:

1. If `i == word.length`, return `node.isEnd`. The pattern is used up, so a word must end exactly here.
2. If `word[i]` is a letter, move to that child. If it is null, return `false`. Otherwise return `search(word, i + 1, child)`.
3. If `word[i]` is a dot, loop over every non-null child. If `search(word, i + 1, child)` is true, return `true` immediately.
4. After the loop, return `false`: every child failed.

### Java solution

<HintLadder hints={hints.wildcard}>

```java id=WordDictionary
class WordDictionary {
    private static class Node {
        Node[] children = new Node[26];
        boolean isEnd;
    }

    private final Node root = new Node();

    public void addWord(String word) {                       // Chapter 1's insert, unchanged
        Node node = root;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new Node();
            node = node.children[i];
        }
        node.isEnd = true;
    }

    public boolean search(String word) {
        return search(word, 0, root);
    }

    private boolean search(String word, int i, Node node) {
        if (i == word.length()) return node.isEnd;           // pattern used up: a word must end here
        char c = word.charAt(i);
        if (c != '.') {
            Node next = node.children[c - 'a'];              // a letter: one branch, or none
            return next != null && search(word, i + 1, next);
        }
        for (Node next : node.children)                      // a dot: every branch gets a turn
            if (next != null && search(word, i + 1, next)) return true;
        return false;                                        // only after every child has failed
    }
}
```

</HintLadder>

### Why it works

- **Settled:** a call `search(word, i, node)` stands on a node whose prefix matches `word[0..i-1]`. It returns true exactly when some stored word below `node` matches the rest, `word[i..]`.
- **Why the move is safe:** a word matches when its letter at each position equals the pattern's letter (or the pattern has a dot). The recursion explores precisely the trie paths that satisfy that, position by position.
- **When we stop:** at the end of the pattern (then `isEnd` decides, which also makes lengths agree), at a missing child, or on the first success.

### Complexity

- **addWord: O(L).**
- **search: O(L) with no dots.** With d dots at most 26^d paths survive the dot levels, so O(26^d · L), and never more than the number of nodes in the trie, because only existing children are tried.
- **Space:** the trie, plus recursion depth at most L (25 on LeetCode).

### Edge cases and mistakes

- All dots (`...`): returns true only if some word has that length.
- A pattern longer than every word: false, because the trie runs out.
- A pattern that matches a **prefix** of a word but not the word: `isEnd` is false, so false.

The classic bug is to return from inside the loop, which gives only the first child a turn.

```java fragment
for (Node next : node.children)
    if (next != null) return search(word, i + 1, next);   // BUG: the first child's answer is final
return false;
// words "ax" and "by": search(".y") tries a, fails, and returns false. "by" never gets a turn
```

<Reveal q="With at most two dots, couldn't you keep a HashSet and try all 26 × 26 letters for the dots?">

Yes. With at most 2 dots that is at most 676 lookups of O(L) each, which is honest and fast enough. LeetCode caps the dots at 2 for exactly this reason. But it scales as 26^d: with 6 dots it is over 300 million lookups. The trie's search never visits more nodes than the trie holds, because it only explores edges that exist. Say both in an interview, then choose the trie.

</Reveal>

**Variations to try:** count how many stored words match (do not stop at the first success); allow `*` to match any run of letters.

<h2 id="word-search-ii">Chapter 3 · Word Search II</h2>

### Problem

Given a board of letters and a list of words, return every word that can be traced on the board through horizontally or vertically adjacent cells, using no cell twice in one word.

Board `[[o,a,a,n],[e,t,a,e],[i,h,k,r],[i,f,l,v]]` with words `[oath, pea, eat, rain]` gives `[eat, oath]` in any order.

### How to recognise it

- A **list of many words** and a grid (or a text) to find them in.
- Each word is a path on the board, so this is backtracking over cells (Word Search I).
- The words are many and share beginnings, so repeating the grid walk per word is the waste to remove.

### Brute force

Run Word Search I once per word. A path of k cells has at most 4 choices for the first step and 3 for each later step, so from one start cell there are at most 1 + 4 + 12 + ... + 4 · 3⁸ = **39,365** paths of up to 10 cells. Over the 144 start cells of a 12 × 12 board that is about **5.7 million** steps per word, and 30,000 words make roughly **1.7 × 10¹¹**. Words that share a beginning (`oath`, `oat`, `oak`) repeat the same grid walk.

### Intuition

Insert **all words into one trie**, then walk the board and the trie **in lockstep**. The DFS carries a trie node. It steps into a neighbouring cell only if the current node has a child for that cell's letter. If it doesn't, no word begins with the letters walked so far, so stopping loses nothing, and that stop serves **every word at once**.

Three small additions make it fast and correct:

1. **Store the whole word on its end node** (a `String word` field instead of a boolean), so you can report it without rebuilding it.
2. **Consume a found word:** set the field to null, so it is reported exactly once.
3. **Prune:** on the way back, if a node has no children and no word, unlink it from its parent. Later walks then stop one step earlier. A **child counter** per node makes "is it empty?" an O(1) check.

| Setup | none | insert 30,000 × 10 = 300,000 letters |
| What stops a walk early | the one word's next letter | **every** word's next letter at once |

### Dry run

A small board with words `oath`, `oaf` and `pea`. Watch three things: a neighbour is entered only when the trie has that child; `oath` is cleared from the trie the moment it is found; and the dead `oat` and `oath` nodes are unlinked on the way back, while `oa` and `oaf` stay because `oaf` is still unfound.

<DryRun title="Word Search II on a 3 by 2 board" frames={wordSearchFrames([['o', 'a'], ['e', 't'], ['i', 'h']], ['oath', 'oaf', 'pea'])} predict />

### Algorithm

1. **Insert every word** into a trie. Count each node's children, and store the word on its end node.
2. **Start a DFS from every cell**, carrying the trie node you came from.
3. In `dfs(r, c, parent)`: stop if the cell is out of bounds or marked `#` (on the current path).
4. Look up the cell's letter among `parent`'s children. If there is none, stop.
5. If the node holds a word, add it to the answer and set the field to null.
6. **Mark** the cell `#`, recurse into the four neighbours with this node, then **restore** the letter.
7. **Prune:** if the node now has no children and no word, unlink it from `parent` and decrement the parent's child count.

### Java solution

<HintLadder hints={hints.wordSearch}>

```java id=findWords
static class TrieNode {
    TrieNode[] children = new TrieNode[26];
    int childCount;                  // children still attached (for O(1) pruning)
    String word;                     // the whole word, on its end node; null elsewhere
}

public List<String> findWords(char[][] board, String[] words) {
    TrieNode root = new TrieNode();
    for (String w : words) {                                 // plant every word
        TrieNode node = root;
        for (char c : w.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) { node.children[i] = new TrieNode(); node.childCount++; }
            node = node.children[i];
        }
        node.word = w;
    }
    List<String> found = new ArrayList<>();
    for (int r = 0; r < board.length; r++)
        for (int c = 0; c < board[0].length; c++)
            dfs(board, r, c, root, found);
    return found;
}

private void dfs(char[][] board, int r, int c, TrieNode parent, List<String> found) {
    if (r < 0 || c < 0 || r >= board.length || c >= board[0].length) return;
    char ch = board[r][c];
    if (ch == '#') return;                                   // already on the current path
    TrieNode node = parent.children[ch - 'a'];
    if (node == null) return;                                // no unfound word continues this way
    if (node.word != null) {                                 // a word ends here
        found.add(node.word);
        node.word = null;                                    // consume it: reported once
    }
    board[r][c] = '#';                                       // mark
    dfs(board, r + 1, c, node, found);
    dfs(board, r - 1, c, node, found);
    dfs(board, r, c + 1, node, found);
    dfs(board, r, c - 1, node, found);
    board[r][c] = ch;                                        // restore on the way back
    if (node.childCount == 0 && node.word == null) {         // prune: nothing left below
        parent.children[ch - 'a'] = null;
        parent.childCount--;
    }
}
```

</HintLadder>

### Why it works

- **Settled:** when the DFS stands on cell `(r, c)` with trie node `node`, the letters along the current path spell `node`'s prefix, every cell on the path is marked `#`, and the trie still holds every word not yet found.
- **Why the move is safe:** every hidden word is traced along some path of distinct cells from some start cell. The DFS follows that path as long as the trie has the matching edges, and it does, because a word's own nodes are never pruned while the word is unfound (a node is pruned only when it holds no word and has no children). When the node is null, no word has this path's letters as a beginning, so no extension can produce one.
- **When we stop:** each DFS call stops at the border, a marked cell, or a missing child. The whole search ends when every start cell has been tried.

### Complexity

- **Time:** O(W) to insert, where W is the total number of letters, plus O(M · N · 4 · 3^(L-1)) for the search on an M × N board with words of length at most L. The bound counts paths, not words, which is the whole point.
- **Space:** O(W) for the trie plus O(L) recursion depth. The board is restored exactly as given.

### Edge cases and mistakes

- A word longer than the number of cells: it can never be completed.
- A word needing the same cell twice (`aba` on `[[a,b]]`): the `#` mark forbids it.
- Duplicate words in the list: they share one end node and are reported once.
- Forgetting `node.word = null` reports a word once per path that traces it. On `[["a","a"]]` with words `["a"]` the answer is `["a", "a"]`.
- Forgetting `board[r][c] = ch` leaves `#` where a letter should be, and later starts silently miss words.

```java fragment
if (node.word != null) found.add(node.word);   // BUG: never consumed. [["a","a"]], ["a"] gives ["a", "a"]
```

### Practice

<Reveal q="Pruning doesn't change the answer. Why bother?">

Because it changes the running time on the inputs that hurt. Take a 12 × 12 board of nothing but `a` and the single word of ten `a`s. Without pruning, the word is found from the first cell, and then each of the other 143 start cells still walks every path of up to ten `a`s, up to 39,365 each, for a word that is already found. With pruning, the moment the word is consumed its node is empty, so it is cut, then its parent, and so on up to the root: the next 143 starts stop after one lookup. Pruning keeps the trie as small as the work that is left.

</Reveal>

<Reveal q="Why null the word instead of collecting results in a HashSet?">

A set would also remove duplicates, but the search would keep re-walking to found words and re-adding them. Nulling the field consumes the word: later walks pass through silently, and an empty node becomes prunable. One field write does both jobs.

</Reveal>

<h2 id="count-and-erase">Side quest 1 · Counts and erase (Implement Trie II)</h2>

### Problem

The same word may be inserted many times, and words can be **erased**. Answer `countWordsEqualTo(word)` and `countWordsStartingWith(prefix)`.

`insert(apple)`, `insert(apple)`, `insert(app)`: `countWordsEqualTo(apple)` is 2, `countWordsStartingWith(app)` is 3. After `erase(apple)`, they are 1 and 2.

### How to recognise it

- Duplicates matter, so a boolean flag is not enough.
- "How many words start with..." instead of "is there one".
- Deletion is allowed, so stale branches are a risk.

### Brute force

Keep a `HashMap<String,Integer>` of counts. `countWordsEqualTo` is O(L), but `countWordsStartingWith` scans every key: O(n · L).

### Intuition

A flag can't count, so give every node two counters: **`pass`**, the number of stored words that pass through (or end at) this node, and **`end`**, the number that end exactly here. Insert adds 1 to `pass` on every node it walks, and 1 to `end` on the last. Both counts are then one walk away.

**Erasing** walks the word again, subtracting 1 from `pass` on each node. The moment a child's `pass` reaches 0, no stored word goes through it any more. Cut it off at the parent and stop: everything below it existed only for this copy.

### Dry run

### Algorithm

1. **insert:** walk the word; on every node you step onto, `pass++`. On the last node also `end++`.
2. **countWordsEqualTo:** walk; return the last node's `end`, or 0 if the walk falls off.
3. **countWordsStartingWith:** walk; return the last node's `pass`, or 0.
4. **erase:** walk the word; for each node, `pass--`. If a node's `pass` becomes 0, set the parent's child slot to null and return. If the loop finishes, `end--` on the last node.

### Java solution

<HintLadder hints={hints.countErase}>

```java id=TrieII
class Trie {
    private static class Node {
        Node[] children = new Node[26];
        int pass;      // stored words that pass through (or end at) this node
        int end;       // stored words that end exactly here
    }

    private final Node root = new Node();

    public void insert(String word) {
        Node node = root;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new Node();
            node = node.children[i];
            node.pass++;
        }
        node.end++;
    }

    public int countWordsEqualTo(String word) {
        Node node = walk(word);
        return node == null ? 0 : node.end;
    }

    public int countWordsStartingWith(String prefix) {       // prefix has at least one letter
        Node node = walk(prefix);
        return node == null ? 0 : node.pass;
    }

    public void erase(String word) {                         // the word is guaranteed to be stored
        Node node = root;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            Node next = node.children[i];
            if (--next.pass == 0) {                          // nobody passes here any more:
                node.children[i] = null;                     // cut the whole branch and stop
                return;
            }
            node = next;
        }
        node.end--;
    }

    private Node walk(String s) {
        Node node = root;
        for (char c : s.toCharArray()) {
            node = node.children[c - 'a'];
            if (node == null) return null;
        }
        return node;
    }
}
```

</HintLadder>

### Why it works

- **Settled:** for every node, `pass` equals the number of stored words with this node's prefix, and `end` the number equal to it.
- **Why the move is safe:** an erase changes exactly the nodes on one word's path, each by one. A node with `pass = 0` has no stored word through it, so its whole subtree is unreachable and may be dropped.
- **When we stop:** after the last letter, or at the first node that is cut.

### Complexity

**O(L) per operation.** Duplicates cost nothing extra: they only raise counters. The root carries no counter, which is why the prefix must be non-empty (LeetCode guarantees it).

### Edge cases and mistakes

- Erasing one of several duplicates: `pass` drops but stays positive, nothing is cut.
- Counting a prefix that was never inserted: the walk falls off, return 0.
- An `erase` that only does `end--` on the last node leaves every `pass` stale: insert `apple`, erase it, and `countWordsStartingWith("app")` still says 1.

### Practice

<Reveal q="In Chapter 1's trie, why can't you delete a word just by setting isEnd = false?">

Because the nodes stay. Insert `apple`, then "delete" it by clearing the flag: `search("apple")` is false, but `startsWith("app")` is still **true**. The nodes are there, and the promise "every node lies on a stored word's path" is broken. Real deletion must also remove the nodes that no stored word needs: walk back up from the end and unlink each node that has no children and no flag (a child counter makes that check O(1)), or keep `pass` counts and cut where `pass` reaches 0, as here.

</Reveal>

<h2 id="replace-words">Side quest 2 · Replace Words</h2>

### Problem

Given a dictionary of **roots** and a sentence, replace each word by the **shortest** root it starts with. Leave words with no root unchanged.

Roots `cat, bat, rat`, sentence `the cattle was rattled by the battery` becomes `the cat was rat by the bat`.

### How to recognise it

- "Shortest" or "longest" stored prefix of each query word.
- Many roots and many words, so comparing every root to every word is wasteful.

### Brute force

For every word, test every root with `startsWith` and keep the shortest match: O(roots × words × L).

### Intuition

Insert the roots. Walk each sentence word from the trie's root. The walk meets prefixes **in order of length**, so the **first end mark** you meet is the shortest root. Stop there. If a child is missing before any end mark, no root fits.

### Dry run

<DryRun title="Replace Words" frames={replaceFrames(['cat', 'bat', 'rat'], 'the cattle was rattled by the battery')} predict />

### Algorithm

1. Insert every root; set `isEnd` on its last node.
2. Split the sentence into words.
3. For each word, walk from the root one letter at a time.
4. If a child is missing, keep the word. If the new node has `isEnd`, use the prefix walked so far.
5. If the word ends first, keep the word. Join the results with single spaces.

### Java solution

<HintLadder hints={hints.replaceWords}>

```java id=replaceWords
static class TrieNode {
    TrieNode[] children = new TrieNode[26];
    boolean isEnd;
}

public String replaceWords(List<String> dictionary, String sentence) {
    TrieNode root = new TrieNode();
    for (String r : dictionary) {
        TrieNode node = root;
        for (char c : r.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new TrieNode();
            node = node.children[i];
        }
        node.isEnd = true;
    }
    StringBuilder out = new StringBuilder();
    for (String word : sentence.split(" ")) {
        if (out.length() > 0) out.append(' ');
        out.append(shortestRoot(root, word));
    }
    return out.toString();
}

private String shortestRoot(TrieNode root, String word) {
    TrieNode node = root;
    for (int i = 0; i < word.length(); i++) {
        node = node.children[word.charAt(i) - 'a'];
        if (node == null) return word;                       // fell off: no root fits
        if (node.isEnd) return word.substring(0, i + 1);     // the first end mark is the shortest root
    }
    return word;                                             // every root is longer than the word
}
```

</HintLadder>

### Why it works

- **Settled:** after k letters the walk stands on the node for the first k letters, and none of the shorter prefixes were roots.
- **Why the move is safe:** prefixes grow one letter at a time, so the first end mark is the shortest root. A longer root can never be shorter.
- **When we stop:** at the first end mark, at a missing child, or when the word runs out.

### Complexity

**O(D + S) time**, where D is the total length of the roots and S the length of the sentence. O(D) space for the trie.

### Edge cases and mistakes

- A root equal to the whole word (`cat` for `cat`): replaced by itself.
- A word shorter than every root: unchanged.
- Walking past the first end mark (remembering the *last* one) returns the **longest** root: roots `a, aa, aaa` turn `aaaa` into `aaa` instead of `a`.

### Practice

<Reveal q="The sentence is “the cattle was rattled by the battery” with roots cat, bat, rat. Walk “cattle”: where do you stop?">

c, a, t, and *t* has an end mark (`cat`), so stop: `cattle` becomes `cat`. `the` falls off at the root (no *t* branch). The sentence becomes `the cat was rat by the bat`. Comparing every root against every word would cost O(roots × words × L); one walk per word costs O(L).

</Reveal>

<h2 id="longest-word">Side quest 3 · Longest Word in Dictionary</h2>

### Problem

Find the longest word in the list that can be **built one letter at a time** by other words in the list: every shorter beginning of it must also be a word. Ties go to the alphabetically smallest; return `""` if none.

`[w, wo, wor, worl, world]` gives `world`. `[a, banana, app, appl, ap, apply, apple]` gives `apple`.

### How to recognise it

- "Built one letter at a time", "every prefix is also in the list".
- A tie-break on alphabetical order.

### Brute force

For each word, check that all its prefixes are in a `HashSet`: O(n · L²) with substring hashing. Simple and acceptable; the trie version is a single O(total letters) walk.

### Intuition

In the trie, "every beginning is a word" means **every node on the path has `isEnd`**. So walk depth first from the root and enter only children that have `isEnd`. Visit children `a` to `z`, and replace the best word only when the new one is **strictly longer**. Depth-first in alphabetical order meets words in alphabetical order, so the first word found at the best length is the smallest.

### Dry run

The word `banana` is the longest overall, but `b` is not a word, so the walk never enters that branch.

<DryRun title="Longest Word in Dictionary" frames={longestWordFrames(['a', 'banana', 'app', 'appl', 'ap', 'apply', 'apple'])} predict />

### Algorithm

1. Insert every word, storing the whole word on its end node.
2. Set `best = ""`.
3. `dfs(node, depth)`: if `depth > best.length()`, set `best = node.word`.
4. For each child in order `a` to `z`, if it exists **and** has a word, call `dfs(child, depth + 1)`.
5. Return `best`.

### Java solution

<HintLadder hints={hints.longestWord}>

```java id=longestWord
static class TrieNode {
    TrieNode[] children = new TrieNode[26];
    String word;                                       // set on end nodes
}

private String best = "";

public String longestWord(String[] words) {
    TrieNode root = new TrieNode();
    for (String w : words) {
        TrieNode node = root;
        for (char c : w.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new TrieNode();
            node = node.children[i];
        }
        node.word = w;
    }
    best = "";
    dfs(root, 0);
    return best;
}

private void dfs(TrieNode node, int depth) {
    if (depth > best.length()) best = node.word;      // strictly longer only: a..z order keeps the smallest
    for (TrieNode child : node.children)              // children in order a..z
        if (child != null && child.word != null)      // enter only nodes that end a word
            dfs(child, depth + 1);
}
```

</HintLadder>

### Why it works

- **Settled:** every node on the current DFS path has a word, so the path spells a buildable word.
- **Why the move is safe:** skipping a child without a word loses nothing, since no word under it can be built letter by letter. Strictly longer plus alphabetical visiting order keeps the smallest tie.
- **When we stop:** when every end-marked branch has been explored.

### Complexity

**O(W) time and space**, W the total number of letters. Without a trie: sort the words, keep a set of buildable words, and accept a word if it has one letter or its prefix without the last letter is already buildable: O(W log n) for the sort.

### Edge cases and mistakes

- No single-letter word: the answer is `""`.
- Two words of the best length: the alphabetically smaller wins because of the strict `>`.
- Returning the longest word overall ignores the rule: on the example above that is `banana`.

### Practice

<Reveal q="Words a, banana, app, appl, ap, apply, apple. Why not banana?">

`banana` is the longest word, but `b` is not in the list, so the walk never enters the *b* branch: node `b` has no end mark. Along *a*: a, ap, app, appl all have one; under `appl` both `apple` and `apply` do, and *e* comes before *y*, so `apple` is found first and `apply` is not strictly longer. Answer: **apple**.

</Reveal>

<h2 id="search-suggestions">Side quest 4 · Search Suggestions System</h2>

### Problem

As a customer types a search word letter by letter, show after each letter up to **three products** that start with the letters typed so far, alphabetically smallest first.

Products `mobile, mouse, moneypot, monitor, mousepad`, typed `mouse`: after `m` and `mo` show `mobile, moneypot, monitor`; after `mou`, `mous` and `mouse` show `mouse, mousepad`.

### How to recognise it

- Results change as the query grows by one letter.
- "Top 3 by alphabet" or any fixed small result per prefix.

### Brute force

For each typed prefix, filter every product with `startsWith`, sort the matches and take three: O(n · L) per keystroke plus a sort.

### Intuition

Two honest ways, and both rest on the same fact: after sorting, **all words with a given prefix sit next to each other**.

- **Trie with lists.** Sort the products first, then insert them **in sorted order**. Each node keeps a list of at most three words: the first three that pass through it. Because they arrive sorted, those are the three smallest with that prefix. Each keystroke is one step down and one ready-made list. This is the typeahead idea in miniature: prepare the answer at every node before anyone types.
- **Sorted array alone.** Binary search for the first word at or after the prefix, then read up to three words forward while they still start with the prefix.

<Figure caption="The products sorted: mobile, moneypot, monitor, mouse, mousepad. Every word starting with mo is in one contiguous run, and the first three are the answer for m and mo. For mou the run begins at mouse: mouse, mousepad.">
  <ArrayStrip values={['mobile', 'moneypot', 'monitor', 'mouse', 'mousepad']} regions={[{ from: 0, to: 2, label: 'after mo', tone: 'gold' }, { from: 3, to: 4, label: 'after mou', tone: 'green' }]} tones={{ 0: 'hot', 1: 'hot', 2: 'hot', 3: 'done', 4: 'done' }} />
</Figure>

### Dry run

The array shows the run for each typed prefix. The map shows the list each trie node would keep, which is exactly the first three of the run.

<DryRun title="Search Suggestions System" frames={suggestFrames(['mobile', 'mouse', 'moneypot', 'monitor', 'mousepad'], 'mouse')} predict />

### Algorithm

1. Sort the products.
2. Insert them in sorted order. On every node you step onto, add the product to that node's list if it has fewer than 3.
3. Walk the search word one letter at a time. After each step, append the node's list (or an empty list once you have fallen off).

Sorted-array version: for each prefix, binary search for the first index with `sorted[i] >= prefix`, then take up to three words while `startsWith(prefix)`.

### Java solution

<HintLadder hints={hints.suggestions}>

```java id=suggestedProducts
static class TrieNode {
    TrieNode[] children = new TrieNode[26];
    List<String> top = new ArrayList<>();                    // up to 3 smallest products below this node
}

public List<List<String>> suggestedProducts(String[] products, String searchWord) {
    String[] sorted = products.clone();
    Arrays.sort(sorted);                                     // sorted, so the first 3 to arrive are the answer
    TrieNode root = new TrieNode();
    for (String p : sorted) {
        TrieNode node = root;
        for (char c : p.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new TrieNode();
            node = node.children[i];
            if (node.top.size() < 3) node.top.add(p);
        }
    }
    List<List<String>> answer = new ArrayList<>();
    TrieNode node = root;
    for (char c : searchWord.toCharArray()) {
        node = node == null ? null : node.children[c - 'a'];  // once fallen off, stay off
        answer.add(node == null ? new ArrayList<>() : node.top);
    }
    return answer;
}

// The same answers from the sorted array alone: binary search for the first word >= the prefix.
public List<List<String>> suggestedProductsSorted(String[] products, String searchWord) {
    String[] sorted = products.clone();
    Arrays.sort(sorted);
    List<List<String>> answer = new ArrayList<>();
    String prefix = "";
    for (char c : searchWord.toCharArray()) {
        prefix += c;
        int lo = 0, hi = sorted.length;                      // first index with sorted[i] >= prefix
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (sorted[mid].compareTo(prefix) < 0) lo = mid + 1; else hi = mid;
        }
        List<String> three = new ArrayList<>();
        for (int i = lo; i < sorted.length && three.size() < 3 && sorted[i].startsWith(prefix); i++)
            three.add(sorted[i]);
        answer.add(three);
    }
    return answer;
}
```

</HintLadder>

### Why it works

- **Settled:** a node's list holds the three smallest products with that node's prefix.
- **Why the move is safe:** insertion is in sorted order, so the first three to reach a node are its three smallest. Later arrivals are larger and can be ignored.
- **When we stop:** after the last typed letter. Once the walk falls off the trie, every longer prefix is empty too.

### Complexity

- **Trie:** O(n log n · L) to sort (string comparisons), O(total letters) to insert, then O(1) per keystroke.
- **Sorted array:** the same sort, then O(L log n) per keystroke for the binary search, with no extra memory beyond the sorted copy.

### Edge cases and mistakes

- A search word whose first letters match nothing: all later lists are empty.
- Fewer than three products match: return what exists.
- Inserting without sorting keeps the first three products *in input order*. On `mobile, mouse, moneypot, monitor, mousepad`, typing `m` then shows `mobile, mouse, moneypot` instead of `mobile, moneypot, monitor`.

### Practice

**Transfer test:** the box must now rank by **popularity**, not alphabet, and popularity changes all day. Which version survives, and what must each node keep? (The trie: see the next side quest.)

<h2 id="max-xor">Side quest 5 · Maximum XOR of Two Numbers</h2>

### Problem

Given non-negative integers, return the largest `x ^ y` over all pairs. Up to 200,000 numbers.

`[3, 10, 5, 25, 2, 8]` gives `28`, from `5 ^ 25`.

### How to recognise it

- "Maximum XOR", "largest XOR of a pair".
- Numbers as bit strings, and a goal that rewards high bits.
- A trie over **bits**, not letters.

### Brute force

Try every pair: about 2 × 10¹⁰ pairs for 200,000 numbers. Far too slow.

### Intuition

Write every number as **31 bits, highest first** (values are below 2³¹) and insert it into a trie whose nodes have **two children**: bit 0 and bit 1. To find the best partner for `x`, walk down from bit 30 and at each level **prefer the child with the opposite bit**, because that makes this bit of the XOR a 1. If the opposite child doesn't exist, take the same bit and that XOR bit stays 0.

**Why greedy is safe:** a 1 in bit `b` is worth 2^b, and all the lower bits together are worth at most 2^b − 1. So winning the highest bit you can is never wrong, whatever happens below. That one inequality is the whole proof.

<Figure caption="5 and 25 in five bits (bit 4 on the left). The best partner for 5 = 00101 is 25 = 11001: opposite bits at bits 4, 3, 2, 1 and 0 where the trie allows (the walk prefers 1, 1, 0, 1, 0; only 25 has the top bit set). 00101 ^ 11001 = 11100 = 28, the answer.">
  <ArrayStrip name="5" values={[0, 0, 1, 0, 1]} indices={false} />
  <ArrayStrip name="25" values={[1, 1, 0, 0, 1]} indices={false} />
  <ArrayStrip name="5 ^ 25 = 28" values={[1, 1, 1, 0, 0]} indices={false} tones={{ 0: 'done', 1: 'done', 2: 'done' }} />
</Figure>

### Dry run

Four numbers in five bits (the Java uses 31). Each number is inserted, then queries the trie for its best partner. Predict whether the walk can take the opposite bit before each step.

<DryRun title="Maximum XOR" frames={maxXorFrames([3, 10, 5, 25])} predict />

### Algorithm

1. For each `x` in the array:
2. **Insert** `x`: walk bits 30 down to 0, creating the child for each bit if missing.
3. **Query** `x`: walk bits 30 down to 0 with a result `xor = 0`. At each bit, if the child for the opposite bit exists, set that bit in `xor` and step into it. Otherwise step into the same-bit child.
4. Keep `best = max(best, xor)`.

### Java solution

<HintLadder hints={hints.maxXor}>

```java id=findMaximumXOR
static class BitNode {
    BitNode[] child = new BitNode[2];                // child[0] for bit 0, child[1] for bit 1
}

public int findMaximumXOR(int[] nums) {
    BitNode root = new BitNode();
    int best = 0;
    for (int x : nums) {
        BitNode node = root;                         // plant x, highest bit first
        for (int b = 30; b >= 0; b--) {              // values are below 2^31, so bit 30 is the top
            int bit = (x >> b) & 1;
            if (node.child[bit] == null) node.child[bit] = new BitNode();
            node = node.child[bit];
        }
        node = root;                                 // best partner for x among everything planted
        int xor = 0;
        for (int b = 30; b >= 0; b--) {
            int bit = (x >> b) & 1;
            if (node.child[bit ^ 1] != null) {       // the opposite bit exists: this XOR bit becomes 1
                xor |= 1 << b;
                node = node.child[bit ^ 1];
            } else {
                node = node.child[bit];              // forced: same bit, XOR bit stays 0
            }
        }
        best = Math.max(best, xor);
    }
    return best;
}
```

</HintLadder>

### Why it works

- **Settled:** after the walk reaches depth `d`, the XOR bits chosen so far are the largest possible for the top `d` bits, over every number inserted.
- **Why the move is safe:** a 1 at bit `b` beats any combination of lower bits, so taking the opposite child when it exists can never lose.
- **When we stop:** after bit 0.

### Complexity

**O(31 · n) time and O(31 · n) nodes.** Inserting `x` before querying means the trie is never empty, and every node lies on some inserted number's full 31-bit path, so when the opposite child is missing the same-bit child always exists.

### Edge cases and mistakes

- A single number: `x ^ x = 0`.
- Equal numbers: also 0.
- Walking from bit 0 upwards makes the greedy choice on the *least* valuable bit first. On `[3, 10, 5, 25, 2, 8]` it returns 19 instead of 28.

### Practice

**Transfer test:** queries now come as `(x, limit)`: the best `x ^ y` using only numbers `y <= limit`. How do you make sure the trie contains exactly the allowed numbers when each query is answered? (Sort the queries by limit and the numbers ascending; insert numbers as the limit grows: an offline sweep.) The bit tricks themselves live in the <a href={`${BASE}dsa/lessons/bit-manipulation/`}>Math & Bit Manipulation</a> pattern on the roadmap.

<h2 id="top-k-autocomplete">Side quest 6 · Top-K typeahead</h2>

### Problem

A search box. `record(query)` notes one more search for a query. `suggest(prefix)` must instantly return the **k most-searched** queries starting with `prefix`: most searches first, ties alphabetical.

With k = 2, after recording `car` twice, `cat` twice, `cart` and `dog`: `suggest("ca")` is `[car, cat]`.

### How to recognise it

- Ranking by a changing count, not just alphabet.
- "Instant" answers per prefix, so no work at query time.
- This is the in-memory core of every typeahead design.

### Brute force

On each `suggest`, collect every query below the prefix node and sort by count: fine for `zyg`, hopeless for `a`, which may have millions of queries below it.

### Intuition

Move the work to update time. **Every node keeps its own list of its best k.** `suggest` then reads one list. When `record` bumps a query's count, only the nodes **on that query's path** can change, and at each of them: add the query if missing, re-sort, drop the (k + 1)-th.

  R(("root · car, cat")) -->|c| C["c · car, cat"]

### Dry run

Record six searches with k = 2, then ask for `ca`. The map shows the cached lists on the path of each recorded query.

<DryRun title="Top-K typeahead" frames={typeaheadFrames(['car', 'cat', 'cart', 'car', 'cat', 'dog'], 2, 'ca')} predict />

### Algorithm

1. `record(query)`: bump the query's count in a map.
2. Walk the query from the root, creating nodes as needed. At the root and at every node you step onto, call `refresh(list, query)`.
3. `refresh`: add the query if it is not in the list, sort by (count descending, then alphabet), and drop the last entry if the list is longer than k.
4. `suggest(prefix)`: walk the prefix (return an empty list if you fall off) and return a copy of that node's list.

### Java solution

<HintLadder hints={hints.typeahead}>

```java id=Typeahead
class Typeahead {
    private static class Node {
        Node[] children = new Node[26];
        List<String> top = new ArrayList<>();          // best k queries below this node, best first
    }

    private final Node root = new Node();
    private final Map<String, Integer> count = new HashMap<>();
    private final int k;
    private final Comparator<String> better = (a, b) -> {
        int ca = count.get(a), cb = count.get(b);
        return ca != cb ? Integer.compare(cb, ca) : a.compareTo(b);   // more searches first, then a..z
    };

    public Typeahead(int k) { this.k = k; }

    public void record(String query) {
        count.merge(query, 1, Integer::sum);
        Node node = root;
        refresh(node.top, query);                      // the root answers the empty prefix
        for (char c : query.toCharArray()) {
            int i = c - 'a';
            if (node.children[i] == null) node.children[i] = new Node();
            node = node.children[i];
            refresh(node.top, query);                  // only nodes on this path can change
        }
    }

    public List<String> suggest(String prefix) {
        Node node = root;
        for (char c : prefix.toCharArray()) {
            node = node.children[c - 'a'];
            if (node == null) return new ArrayList<>();
        }
        return new ArrayList<>(node.top);              // a copy: callers can't disturb the cache
    }

    private void refresh(List<String> top, String query) {
        if (!top.contains(query)) top.add(query);
        top.sort(better);
        if (top.size() > k) top.remove(top.size() - 1);   // drop the (k + 1)-th
    }
}
```

</HintLadder>

### Why it works

- **Settled:** every node's list is the top k, by the current counts, of all queries recorded below it.
- **Why the move is safe:** when `q`'s count rises, every other query's count is unchanged, and they were all ranked below the k cached ones (or are among them). So the new top k of a node is the top k of (the old list plus `q`), exactly what add, re-sort, trim computes.
- **When we stop:** `record` stops after the last letter; `suggest` after the prefix.

### Complexity

- **record:** O(L · k log k).
- **suggest:** O(P + k) for a prefix of length P.
- **Space:** O(nodes × k) references. That is the price of answering every keystroke without a search.

### Edge cases and mistakes

- Returning the cached list itself lets callers disturb it. Return a copy.
- The root's list answers the empty prefix.
- **Counts that can go down break the cache.** If a cached query's count falls, the rightful replacement may be some query that was never cached, and the node can't know which without walking its whole subtree.

### Practice

<Reveal q="Why is a cached top-k list still correct after a count goes up, and what breaks if counts can go down?">

When `q`'s count rises, every other query's count is unchanged, and they were all ranked below the k cached ones (or are among them). So the new top k of a node is simply the top k of (the old list plus `q`): exactly what add, re-sort, trim computes. **Decreases break this.** That is why production typeahead systems don't update counts live: they **rebuild the lists offline** from search logs (say, hourly) and swap the new trie in. See the <a href={`${BASE}sd/lessons/search/`}>Search lesson's typeahead section</a> and the Typeahead walkthrough on the <a href={`${BASE}sd/`}>System Design roadmap</a>.

<h2 id="choose-the-tool">When a trie is the wrong tool</h2>

A trie is the right tool when **prefixes matter**, or when **many words are tested against one input** and should share the work. It is the wrong one, or an expensive one, when:

| Situation | Better tool | Why |
|---|---|---|
| Only exact-word lookups, never prefixes | `HashSet<String>` | One hash of the word; no per-letter nodes or 26-slot arrays to pay for |
| A fixed dictionary, tight memory, prefix questions | **Sorted array + binary search** | Words sharing a prefix are contiguous; O(L log n) per question, memory is just the words |
| Prefix yes/no only, small inputs | `HashSet` of all prefixes | Simple and O(L) per query, but O(L²) per insert, and it can't list or rank words |
| The pattern can appear **anywhere** in a word (substring) | A plain scan, or a suffix array / suffix automaton | A trie indexes beginnings only; "ear" inside "bear" is invisible to it |
| Huge or unknown alphabet | Trie with `HashMap` children (or a radix tree) | 26-slot arrays assume a small fixed alphabet |

<Reveal q="A fixed list of 2 million words, many prefix questions, and memory is tight. Trie or sorted array?">

With little sharing, 2 million words of 8 letters can need up to 16 million nodes, and at 26 slots each that is 416 million references before counting the nodes themselves. A sorted array holds the 2 million strings and nothing else; binary search finds the first word at or after the prefix in O(L log n), and the matching words follow contiguously. Choose the trie when the set changes often, when you need wildcards or lockstep walks, or when per-node data (counts, cached top-k) is the point. Compressed tries (radix trees) and automata close much of the memory gap: see *Look these up yourself*.

</Reveal>

1. **The listening post.** Letters arrive one at a time on a wire. After each letter, report whether some word from a fixed dictionary **ends exactly at the latest letter**. Test: a word that is a suffix of another, a one-letter word, a stream where nothing matches.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**The listening post:** insert the words **reversed**. | Add words; ask "is it a word?" and "does any word start with...?" | 26-slot nodes + `isEnd`; one shared walk | The node you stand on is the prefix you walked; only `isEnd` makes it a word |
| A huge or unknown alphabet | The same walk with `HashMap` children | Children hold only letters that occur |
| Search with `.` wildcards | DFS over `(i, node)`; at a dot try every child | Return true on the first success; at the end, `isEnd` decides |
| Find all dictionary words in a grid | Insert all words; DFS the board carrying a node | Step only where an edge exists; consume found words; restore cells; prune empty nodes |
| Count words / prefixes, with duplicates and erase | `pass` and `end` counters per node | Cut a branch when its `pass` reaches 0 |
| Shortest root that begins each word | Walk the word; stop at the first end mark | The walk meets prefixes shortest first |
| Longest word built one letter at a time | DFS a to z through end-marked nodes only | Replace only on strictly longer: the first found is the smallest |
| Top 3 alphabetical per keystroke | Sort, insert in order, keep 3 per node, or binary search a sorted array | Words sharing a prefix are contiguous in sorted order |
| Maximum XOR of a pair | Two-child trie over bits 30..0; prefer the opposite bit | A higher bit outweighs all lower bits together |
| Top k by popularity per prefix | Each node caches its own top k; refresh along the recorded path | Valid while counts only increase; otherwise rebuild |
| Only exact lookups, or substrings | HashSet, or a scan / suffix structure | A trie earns its memory only when beginnings matter |

A trie does **not** mean small memory. A 26-slot node is mostly empty slots; per-node lists multiply memory by k. Count what each node carries before you promise a bound.

### Five classic bugs

1. **`search` without `isEnd`.** Returning "the walk finished" answers `startsWith`. After inserting `apple`, `search("app")` must be false.
2. **The first child's answer is final.** At a dot, `return search(child)` inside the loop gives only one branch a chance. Return true on success; return false only after the loop.
3. **The unconsumed word, the unrestored cell.** In Word Search II, forget `node.word = null` and words repeat; forget `board[r][c] = ch` and later walks miss words.
4. **Deleting by clearing a flag.** The nodes stay, and `startsWith` keeps answering yes for a word that is gone. Unlink nodes no word needs (child counts or `pass` counters).
5. **`c - 'a'` on anything that isn't `a`-`z`.** An uppercase letter or a space gives a negative or too-large index and an `ArrayIndexOutOfBoundsException`. Check the alphabet the problem promises; otherwise use map children.

<h2 id="revision">Revision</h2>

**How to recognise it.** Many words stored once and queried many times; questions about **prefixes**; wildcards over a dictionary; many words searched in one grid or text; shortest or longest stored prefix; maximum XOR over bits.

**Core algorithm.** A node is 26 child slots (or a map, or 2 slots for bits) plus a flag or counters. Every operation is one walk from the root, one letter per step: grow missing children on insert, return `isEnd` for `search`, just arrive for `startsWith`. At a wildcard, try every child with DFS. In a grid, carry the trie node alongside the cell, consume found words, restore cells, and prune empty nodes.

**Common mistakes.**

- `search` that forgets `isEnd` (it becomes `startsWith`).
- Returning from inside the dot loop, so only the first child gets a turn.
- Not consuming a found word or not restoring the board in Word Search II.
- Deleting by clearing a flag, or an `erase` that leaves `pass` counters stale.
- Walking past the first end mark for the shortest root; walking XOR bits lowest first.
- `c - 'a'` on a character outside `a`-`z`.

**Complexity.** Insert, search and prefix queries cost O(L), independent of how many words are stored. Space is O(total letters) nodes, times 26 slots for array children. Wildcards cost O(26^d · L) at worst for d dots, never more than the number of nodes. Word Search II is O(W) to build plus O(M · N · 4 · 3^(L-1)) to search.

**Three representative problems.**

1. [Implement Trie (Prefix Tree)](https://leetcode.com/problems/implement-trie-prefix-tree/): one walk; `isEnd` decides `search`.
2. [Design Add and Search Words Data Structure](https://leetcode.com/problems/design-add-and-search-words-data-structure/): DFS that tries every child at a dot.
3. [Word Search II](https://leetcode.com/problems/word-search-ii/): trie and grid in lockstep, with consume and prune.

**Look these up yourself:** real ideas this page didn't have room for:

- **Radix / Patricia trees:** merge chains of single-child nodes into one edge; the standard fix for trie memory.
- **Aho–Corasick automaton:** many-pattern search in a text in O(text + patterns + matches); the grown-up listening post.
- **Ternary search trees:** three children per node (less, equal, greater): trie-like prefix search with far less memory.
- **Suffix arrays and suffix automata:** index every suffix so substring questions become prefix questions.
- **Minimal acyclic automata / finite state transducers:** share endings as well as beginnings; search engines use them to store huge term dictionaries.

- **Persistent binary tries:** side quest 5 over any range of an array, by keeping every version of the trie.
