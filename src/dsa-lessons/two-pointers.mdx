<h2 id="prologue">How to think about this pattern</h2>

A **pointer** is just an index you keep track of. In this chapter every pointer gets one job, and it only moves when it can justify the move.

Before you move a pointer, answer three questions:

1. **What is already settled?** A matched pair, a kept prefix, a sorted suffix.
2. **Why is this move safe?** Which answers have become impossible, or which value can now be placed for good?
3. **When do I stop?** No pair left, nothing unread, or no unknown region left.

The statement that stays true after every move is called the **invariant**. It does not need formal wording. "Everything before `write` is the correct answer so far" is a perfectly good invariant.

<Figure caption="Everything outside the two pointers is settled. The remaining work lives between them, and every move makes that stretch smaller.">

</Figure>

The brute force for most of these problems checks every pair, which is O(n²). A pointer that moves only when it can prove something is finished visits each position once. Most of this chapter is about finding that proof.

**How to use this chapter.** For each problem, stop after reading "Problem" and "Brute force" and try to find the improvement yourself. Then read the intuition, step through the dry run (turn on Predict to guess each move before it is shown), and only then look at the algorithm and the code. The goal is not to remember the Java. It is to be able to rebuild it.

<h2 id="mirror-check">1. Valid Palindrome</h2>

### Problem

Given a string, decide whether it reads the same forwards and backwards. Ignore case and anything that is not a letter or digit.

Example: `"A man, a plan, a canal: Panama"` gives `true`. `"0P"` gives `false`.

### How to recognise it

- The answer depends on a symmetry: position `i` must match position `n - 1 - i`.
- You compare two ends of one sequence and work toward the middle.
- Some characters must be skipped, which rules out simply reversing and comparing.

### Brute force

Build a cleaned copy (lowercase, letters and digits only), reverse it, compare. This is O(n) time but O(n) extra space, and it hides the idea. The version to aim for needs no copy: **O(n) time, O(1) space**.

### Intuition

Fold the word in half. The first and last meaningful characters must be equal, then the second and second-to-last, and so on. So keep one pointer at each end and move inward.

The only new question is what to do when a pointer lands on punctuation. It is not a mismatch, it just does not count. So skip it first, then compare.

<Figure caption="Folding racecar. Everything outside the pointers has matched. One unchecked pair remains, then the middle letter, which needs no partner.">

</Figure>

### Algorithm

1. Put `left` at index 0 and `right` at the last index.
2. While `left < right`:
   1. Move `left` right while it points at a non-letter, non-digit.
   2. Move `right` left while it points at a non-letter, non-digit.
   3. If the two characters differ (ignoring case), return false.
   4. Move both pointers inward.
3. Return true.

### Java solution

Try writing it from the algorithm before opening the hints.

<HintLadder hints={hints.palindrome}>

```java id=isPalindrome
public boolean isPalindrome(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        while (left < right && !Character.isLetterOrDigit(s.charAt(left))) left++;
        while (left < right && !Character.isLetterOrDigit(s.charAt(right))) right--;
        if (Character.toLowerCase(s.charAt(left)) !=
            Character.toLowerCase(s.charAt(right))) return false;
        left++;
        right--;
    }
    return true;
}
```

</HintLadder>

### Why it works

- **Settled:** everything outside the pointers has matched or been ignored.
- **Why the move is safe:** a matched pair never needs looking at again, and an ignored character never affects the answer.
- **Stop:** when the pointers meet or cross there is no unchecked pair left. A single middle character needs no partner.

### Complexity

- **Time O(n):** each position is visited at most once by one of the pointers.
- **Space O(1):** two indexes. Nothing is sorted or copied.

This fits the problem's ASCII input.

### Edge cases and mistakes

- Skip punctuation *before* comparing, not after.
- Keep `left < right` in the inner skipping loops too. A string made only of punctuation (`".,"`) would otherwise run the pointers past each other.
- Digits count, so `"0P"` is false.

<h2 id="find-a-pair">2. Two Sum II (sorted input)</h2>

### Problem

Given a sorted array and a target, find two different positions whose values add up to the target. LeetCode returns 1-based positions.

Example: `[2, 7, 11, 15]`, target 18 gives positions `2` and `3` (7 + 11).

### How to recognise it

- The input is **sorted**.
- You want a pair (two values) that meets a sum condition.
- A single decision should tell you which direction to search.

### Brute force

Try every pair with two nested loops: O(n²) time, O(1) space. Almost all of that work is wasted, because sorted order lets one comparison rule out many pairs at once.

### Intuition

Start with the widest pair: smallest value on the left, largest on the right.

- **Sum too small?** Even pairing the left value with the *largest* remaining value is not enough. So the left value cannot work with anyone. Discard it and move `left` right.
- **Sum too big?** Even pairing the right value with the *smallest* remaining value is too much. Discard it and move `right` left.
- **Equal?** Done.

One move removes a value from every pair it could have been part of. That is where O(n²) becomes O(n).

<Figure caption="2 + 15 = 17 is too small, and 15 was the best partner 2 could have, so 2 is out for good. Next 7 + 15 = 22 is too big, and 7 was the best partner 15 could have, so 15 is out. Then 7 + 11 = 18.">
  <ArrayStrip values={[2, 7, 11, 15]} pointers={[{ at: 1, label: 'LEFT' }, { at: 2, label: 'RIGHT' }]} tones={{ 0: 'out', 3: 'out', 1: 'hot', 2: 'hot' }} regions={[{ from: 0, to: 0, label: 'too small for anyone', tone: 'dim' }, { from: 3, to: 3, label: 'too big for anyone', tone: 'dim' }]} />
</Figure>

### Dry run

Sorted `[1, 3, 4, 6, 8, 11]`, target 10. This run uses 0-based indexes; LeetCode adds 1.

<DryRun title="Two Sum II" frames={twoSumSortedFrames([1, 3, 4, 6, 8, 11], 10)} predict />

You can also try this one in the <a href="#playground">playground</a>: its four cases include negatives, duplicates and no answer.

### Algorithm

1. `left = 0`, `right = n - 1`.
2. While `left < right`, compute `sum = nums[left] + nums[right]`.
3. If `sum == target`, return the positions.
4. If `sum < target`, `left++`. Otherwise `right--`.
5. If the pointers meet, there is no pair.

### Java solution

<HintLadder hints={hints.pair}>

```java id=twoSum
public int[] twoSum(int[] nums, int target) {
    int left = 0, right = nums.length - 1;
    while (left < right) {
        long sum = (long) nums[left] + nums[right];
        if (sum == target) return new int[]{left + 1, right + 1};
        if (sum < target) left++;
        else right--;
    }
    return new int[]{-1, -1};
}
```

</HintLadder>

### Why it works

- **Settled:** every value outside `[left, right]` was discarded because it cannot pair with anything still in range.
- **Why the move is safe:** a too-small sum with the biggest partner means no partner is big enough; a too-big sum with the smallest partner means none is small enough.
- **Stop:** if a valid pair exists, it is always inside the current boundaries, so when they meet there is none.

### Complexity

- **Time O(n):** at most n - 1 inward moves.
- **Space O(1)** for already sorted input.

### Edge cases and mistakes

- Use `left < right`. With `<=`, `[3]` would "make" 6 by using the same element twice.
- Equal values are fine: `[2, 2]` makes 4 using two different positions.
- Negative numbers are fine when the array is sorted.
- LeetCode wants 1-based positions, hence the `+ 1`. The `long` cast stops integer overflow.

### Practice

<Reveal q="Would the same moves work on [7, 2, 15, 11]? What about negative numbers?">

The unsorted array breaks the reasoning: moving a pointer no longer reliably changes the sum in the direction you need. Sorting can help, but adds work and changes positions. For an unsorted problem asking for original indexes, a hash map is another option.

Negative numbers are fine when the array is sorted. In `[-8, -3, 2, 6]`, target -1, the ends add to -2. Move left: -8 still cannot reach the target with anyone left.

</Reveal>

<h2 id="build-a-triplet">3. 3Sum</h2>

### Problem

Given an array, return every unique triplet of values that adds up to 0.

Example: `[-1, 0, 1, 2, -1, -4]` gives `[[-1, -1, 2], [-1, 0, 1]]`.

### How to recognise it

- You want triplets (or k values) with a sum condition.
- The answer must contain no duplicates.
- Sorting the input is allowed, because positions do not matter.

### Brute force

Three nested loops over all triplets: O(n³). You would also need a set to remove duplicate answers.

### Intuition

Three numbers sounds new, but hold one still. If the fixed number is -2, the other two must add to +2, which is Two Sum II on the part to its right.

So: sort, fix one position, run the pair search to the right of it, and repeat for the next position. Cost: n choices times an O(n) scan, which is O(n²).

<Figure caption="The fixed value stays put. The pointers search only to its right for a pair that cancels it.">
  <ArrayStrip values={[-2, 0, 0, 2, 2]} pointers={[{ at: 0, label: 'FIXED', tone: 'purple' }, { at: 1, label: 'LEFT' }, { at: 4, label: 'RIGHT' }]} tones={{ 0: 'purple' }} regions={[{ from: 1, to: 4, label: 'pair search: need +2', tone: 'gold' }]} />
</Figure>

The extra skill is **avoiding duplicate answers**: skip a fixed value equal to the previous fixed value, and after recording a triplet skip repeated pair values.

### Dry run

Sorted `[-2, -2, 0, 0, 2, 2]`. Watch how the second `-2` is skipped and how the pointers move after a hit.

<DryRun title="3Sum" frames={dry.threeSumFrames([-2, -2, 0, 0, 2, 2])} predict />

### Algorithm

1. Sort the array.
2. For each `fixed` position (stop two before the end):
   1. Skip it if it equals the previous fixed value.
   2. Stop completely if `nums[fixed] > 0`.
   3. Set `left = fixed + 1`, `right = n - 1`.
   4. While `left < right`: if the sum is below 0 move `left`; if above 0 move `right`; if 0, record the triplet, move both pointers, and skip repeated values on both sides.

### Java solution

<HintLadder hints={hints.triplets}>

```java id=threeSum
public java.util.List<java.util.List<Integer>> threeSum(int[] nums) {
    java.util.Arrays.sort(nums);
    var result = new java.util.ArrayList<java.util.List<Integer>>();
    for (int fixed = 0; fixed < nums.length - 2; fixed++) {
        if (fixed > 0 && nums[fixed] == nums[fixed - 1]) continue;
        if (nums[fixed] > 0) break; // Every remaining value is positive.
        int left = fixed + 1, right = nums.length - 1;
        while (left < right) {
            long sum = (long) nums[fixed] + nums[left] + nums[right];
            if (sum < 0) left++;
            else if (sum > 0) right--;
            else {
                result.add(java.util.List.of(nums[fixed], nums[left], nums[right]));
                left++;
                right--;
                while (left < right && nums[left] == nums[left - 1]) left++;
                while (left < right && nums[right] == nums[right + 1]) right--;
            }
        }
    }
    return result;
}
```

</HintLadder>

### Why it works

- **Settled:** earlier fixed values have had all their triplets found, and values outside the pair pointers are ruled out for this fixed value.
- **Why the move is safe:** it is the Two Sum II argument, with target `-nums[fixed]`.
- **Stop:** every sorted triplet has a first position, and each first position was tried. Starting `left` after `fixed` prevents reusing an element.

### Complexity

- **Time O(n²):** up to n fixed positions, each with an O(n) scan (sorting is O(n log n) and does not dominate).
- **Space O(1)** for the pointer scan. Sorting workspace and the returned triplets are extra. This version sorts the input in place.

The same idea gives **4Sum**: fix two positions, search a pair, O(n³). Each extra fixed loop adds a factor of n. Use a wide type for sums.

### Edge cases and mistakes

- After a hit, move **both** pointers. Otherwise the loop finds the same answer forever.
- Remove duplicate **results**, not duplicate **input values**: `[0, 0, 0]` and `[-1, -1, 2]` need repeated inputs.
- Fixed values below `n - 2`, so there is room for two more.

### Practice

<Trace title="Three becomes two" steps={triplets} takeaway="Fix one, search two, skip repeated answers. Keep duplicate input values available when a valid triplet needs them." />

<Reveal q="Why not remove duplicate numbers before starting?">

Because `[0, 0, 0]` is a valid triplet. So is `[-1, -1, 2]`. You need enough positions to form the answer. Avoid duplicate **results**, not duplicate **input values**.

</Reveal>

<h2 id="biggest-container">4. Container With Most Water</h2>

### Problem

You are given the heights of vertical lines. Pick two lines. The water between them rises to the height of the **shorter** line. Find the largest area.

Example: `[1, 8, 6, 2, 5, 4, 8, 3, 7]` gives `49` (lines at positions 1 and 8: height 7, width 7).

### How to recognise it

- You choose **one pair** to maximise a formula that depends on both elements and the distance between them.
- Original positions matter (width), so you cannot sort.
- One of the two values is clearly the limiting one (the shorter wall).

### Brute force

Compute the area of every pair: O(n²) time, O(1) space.

### Intuition

Start with the widest container. Width is as large as it will ever be, so any better container must be taller.

Now one wall has to move inward, which loses width. Which one? The area is capped by the **shorter** wall. If you move the *taller* wall, the width drops and the height is still capped by the same short wall, so the area cannot improve. Moving the short wall is the only move that might help.

So the short wall is dead weight with every remaining partner. Drop it.

<Figure caption="The best container uses the walls at positions 1 and 8: height min(8, 7) = 7, width 7, area 49. The outermost pair only manages 1 x 8 = 8, because the wall of height 1 caps everything.">
  <Bars heights={[1, 8, 6, 2, 5, 4, 8, 3, 7]} pair={[1, 8]} lines pointers={[{ at: 1, label: 'L' }, { at: 8, label: 'R' }]} />
</Figure>

### Dry run

<DryRun title="Container With Most Water" frames={dry.containerFrames([1, 8, 6, 2, 5, 4, 8, 3, 7])} predict />

### Algorithm

1. `left = 0`, `right = n - 1`, `best = 0`.
2. While `left < right`:
   1. Area = `min(height[left], height[right]) * (right - left)`. Update `best`.
   2. Move the pointer at the shorter wall inward (either one if equal).
3. Return `best`.

### Java solution

<HintLadder hints={hints.container}>

```java id=maxArea
public int maxArea(int[] height) {
    int left = 0, right = height.length - 1, best = 0;
    while (left < right) {
        int area = Math.min(height[left], height[right]) * (right - left);
        best = Math.max(best, area);
        if (height[left] <= height[right]) left++;
        else right--;
    }
    return best;
}
```

</HintLadder>

### Why it works

- **Settled:** `best` covers every pair we have ruled out.
- **Why the move is safe:** keeping the short wall and shrinking the width cannot beat the area we just measured, so every pair involving that short wall (with the remaining partners) is no better.
- **Stop:** when the pointers meet, every pair has either been measured or ruled out. Any better answer would still have to lie between the pointers, and there is nothing between them.

### Complexity

- **Time O(n):** one inward step per iteration.
- **Space O(1).**

### Edge cases and mistakes

- Measure **before** moving.
- Do not sort. Positions give the widths.
- Do not add areas together. You want the single largest.
- Ties: either side may move.
- The problem's limits fit `int`. Use `long` if your inputs can overflow the product.

<h2 id="catch-the-rain">5. Trapping Rain Water</h2>

### Problem

Each bar has a height and width 1. After rain, how many units of water sit on top of the bars?

Example: `[0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]` gives `6`.

### How to recognise it

- You need a total, not a single best pair, and it depends on the tallest bars on each side of every position.
- Same two-ended shape as Container, but every bar is solid and every hollow counts.

### Brute force

For each position, scan left for the tallest bar and right for the tallest bar. Water above it is `min(leftMax, rightMax) - height`. That is O(n²) time. Precomputing prefix and suffix maximum arrays makes it O(n) time but O(n) space.

### Intuition

Water above a bar is set by the **lower** of the tallest wall to its left and the tallest wall to its right.

Walk in from both ends, keeping `leftMax` and `rightMax`. Suppose `leftMax <= rightMax`. For the next bar on the left, the true right-side maximum is at least `rightMax`, which is at least `leftMax`. So the lower wall is `leftMax`, and we know the water there **without knowing the rest of the array**. Settle that bar and move on.

The side with the smaller max is always the one you can settle.

<Figure caption="The puddles: 1 + 1 + 2 + 1 + 1 = 6 units. Each blue number is min(tallest wall left, tallest wall right) minus the bar's own height.">
  <Bars heights={[0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]} water={[0, 0, 1, 0, 1, 2, 1, 0, 0, 1, 0, 0]} />
</Figure>

### Dry run

<DryRun title="Trapping Rain Water" frames={dry.rainFrames([2, 0, 3, 0, 1])} predict />

### Algorithm

1. `left = 0`, `right = n - 1`, `leftMax = height[left]`, `rightMax = height[right]`, `water = 0`.
2. While `left < right`:
   1. If `leftMax <= rightMax`: move `left` right, update `leftMax` with the new bar, add `leftMax - height[left]`.
   2. Otherwise do the same on the right side.
3. Return `water`.

### Java solution

<HintLadder hints={hints.rain}>

```java id=trap
public int trap(int[] height) {
    if (height.length < 3) return 0;
    int left = 0, right = height.length - 1;
    int leftMax = height[left], rightMax = height[right];
    int water = 0;
    while (left < right) {
        if (leftMax <= rightMax) {
            left++;
            leftMax = Math.max(leftMax, height[left]);
            water += leftMax - height[left];
        } else {
            right--;
            rightMax = Math.max(rightMax, height[right]);
            water += rightMax - height[right];
        }
    }
    return water;
}
```

</HintLadder>

### Why it works

- **Settled:** every position the pointers have passed has its final water amount.
- **Why the move is safe:** the side with the smaller max has a wall at least that tall on the opposite side, so the smaller max alone decides the water there.
- **Stop:** the pointers meet, so no bar is unprocessed.

### Complexity

- **Time O(n):** each bar is processed once.
- **Space O(1).**

On the dry run's input the inside bars contribute 2, 0 and 1: total 3. On the Trace's input `[4, 1, 0, 2, 5]` they contribute 3, 4 and 2: total 9. The problem limits fit `int`.

### Edge cases and mistakes

- Update the max **before** subtracting, so a taller new bar adds zero rather than negative water.
- Using only the immediate neighbours misses taller walls farther away.
- Do not mix up the two water problems: **Container = best single pair; Rain = sum above every bar.**
- Fewer than 3 bars hold nothing.

<h2 id="keep-the-good-stuff">6. Move Zeroes</h2>

### Problem

Move every 0 to the end of the array, keeping the order of the other values. Do it in place.

Example: `[0, 1, 0, 3, 12]` becomes `[1, 3, 12, 0, 0]`.

### How to recognise it

- "In place", "keep the relative order" and "filter" in the same problem.
- The output is a prefix of kept values, with the rest as leftovers.

### Brute force

Copy the nonzero values to a new array, then pad with zeroes: O(n) time but O(n) space, and not in place. Or shift the whole suffix left every time you meet a zero: O(n²).

### Intuition

You need to know where the next nonzero value belongs. That is just the count of nonzero values found so far. So give that count a pointer: `write`. A second pointer, `read`, walks the array once.

- `read` sees 0: nothing to keep. Only `read` moves.
- `read` sees a nonzero: it belongs at `write`. Put it there, then advance both.

Swapping (instead of overwriting) leaves the zeroes behind in the gap.

<Figure caption="Mid-run: the kept values are final and in order, scanned zeroes wait behind them, and the rest is unread.">
  <ArrayStrip values={[1, 3, 0, 0, 12, 0, 5]} pointers={[{ at: 2, label: 'WRITE' }, { at: 4, label: 'READ', tone: 'blue' }]} tones={{ 0: 'done', 1: 'done', 2: 'out', 3: 'out' }} regions={[{ from: 0, to: 1, label: 'kept, in order', tone: 'green' }, { from: 2, to: 3, label: 'scanned zeroes', tone: 'dim' }, { from: 4, to: 6, label: 'unread', tone: 'blue' }]} />
</Figure>

### Dry run

<DryRun title="Move Zeroes" frames={dry.moveZeroesFrames([0, 1, 0, 3, 12])} predict />

### Algorithm

1. `write = 0`.
2. For each `read` from 0 to n - 1:
   1. If `nums[read] != 0`, swap `nums[read]` with `nums[write]` (skip if same index), then `write++`.
3. Everything from `write` onward is zero.

### Java solution

<HintLadder hints={hints.compact}>

```java id=moveZeroes
public void moveZeroes(int[] nums) {
    int write = 0;
    for (int read = 0; read < nums.length; read++) {
        if (nums[read] != 0) {
            if (read != write) {
                int temp = nums[write];
                nums[write] = nums[read];
                nums[read] = temp;
            }
            write++; // A value was kept, even if no swap was needed.
        }
    }
}
```

</HintLadder>

### Why it works

Freeze the loop just before reading a value:

```text
[ finished nonzero values | scanned zeroes | unread values ]
  0                write                  read
```

- **Settled:** everything before `write` is the nonzero values in original order.
- **Why the move is safe:** a nonzero value is placed at `write` and never touched again; zeroes only drift right.
- **Stop:** `read` reaches the end, so nothing is unread.

This promise is for the **swapping version**. Other read/write problems can leave arbitrary ignored values in the middle, so do not assume that zone is always zero.

### Complexity

- **Time O(n):** one pass.
- **Space O(1).**

The nonzero order is preserved.

### Edge cases and mistakes

- `write` advances whenever a value is kept, even when no swap was needed (`read == write`).
- Do not shift the whole suffix per zero: that makes it O(n²).
- All zeroes, no zeroes, and a single element all work unchanged.

<h2 id="control-duplicates">7. Remove Duplicates I and II</h2>

### Problem

Given a **sorted** array, remove duplicates in place so each value appears at most once (I) or at most twice (II). Return the new length. Only the first that many slots matter.

Example (II): `[1, 1, 1, 2, 2, 3]` becomes `[1, 1, 2, 2, 3]`, length 5.

### How to recognise it

- Sorted input, "in place", "return the new length".
- A rule about how many copies are allowed.

### Brute force

Remove an element by shifting the rest left every time you find a surplus copy: O(n²). Or copy into a new array or use a map of counts: O(n) space.

### Intuition

Same two jobs as Move Zeroes: `read` visits everything, `write` is the length of the kept prefix. Only the keep rule changes.

Because the array is sorted, equal values sit together. To check whether the kept prefix already holds K copies of the current value, compare the value with the kept element **K places back** (`nums[write - K]`). If they are equal, the prefix already ends with K copies, so skip. If not, keep it.

- Limit 1: compare with `nums[write - 1]`.
- Limit 2: compare with `nums[write - 2]`.

<Figure caption="The third 1 arrives. write looks two kept slots back and finds another 1, so two copies are already inside. read moves on and write stays.">
  <ArrayStrip values={[1, 1, 1, 2, 2, 3]} pointers={[{ at: 0, label: 'WRITE - 2', tone: 'purple' }, { at: 2, label: 'READ · WRITE', tone: 'gold' }]} tones={{ 0: 'purple', 1: 'done' }} regions={[{ from: 0, to: 1, label: 'kept: two 1s already inside', tone: 'green' }]} />
</Figure>

### Dry run

Limit 2, input `[1, 1, 1, 2, 2, 3]`:

<DryRun title="Remove Duplicates II" frames={dry.dedupeFrames([1, 1, 1, 2, 2, 3], 2)} predict />

Limit 1 on `[0, 0, 1, 1, 2]`, the easier version:

<DryRun title="Remove Duplicates I" frames={dry.dedupeFrames([0, 0, 1, 1, 2], 1)} />

### Algorithm

1. `write = 0`.
2. For each `read`:
   1. If `write < K` or `nums[read] != nums[write - K]`, copy `nums[read]` to `nums[write]` and `write++`.
3. Return `write`.

### Java solution

<HintLadder hints={hints.duplicates}>

```java id=removeDuplicates
public int removeDuplicates(int[] nums) {
    int write = 0;
    for (int read = 0; read < nums.length; read++) {
        if (write == 0 || nums[read] != nums[write - 1]) {
            nums[write++] = nums[read];
        }
    }
    return write;
}

public int removeDuplicatesII(int[] nums) {
    int write = 0;
    for (int read = 0; read < nums.length; read++) {
        if (write < 2 || nums[read] != nums[write - 2]) {
            nums[write++] = nums[read];
        }
    }
    return write;
}
```

</HintLadder>

### Why it works

- **Settled:** everything before `write` is the correct answer so far, in order, with at most K copies of each value.
- **Why the move is safe:** sorted order groups equal values, so if the value K places back equals the current one, the prefix already ends with K copies. Skipping the new copy keeps the limit.
- **Stop:** `read` reaches the end. Values after the prefix do not have to look tidy.

### Complexity

- **Time O(n)** for both versions.
- **Space O(1).**

### Edge cases and mistakes

- Java's short-circuit `||` protects the negative index: when `write < 2` the second condition is never evaluated.
- Return the new logical length, not the original length. For `[1, 1, 1, 2]` with two copies allowed it returns 3, and only `[1, 1, 2]` matters; the remaining slot is ignored.
- For a positive limit K, generalise to `write < K || nums[read] != nums[write - K]`. If K is zero the retained length is zero.
- The rule depends on sorted input.

<h2 id="sort-three-colors">8. Sort Colors</h2>

### Problem

The array holds only 0, 1 and 2. Sort it in place in one pass, without a library sort.

Example: `[2, 0, 2, 1, 1, 0]` becomes `[0, 0, 1, 1, 2, 2]`.

### How to recognise it

- A tiny, fixed set of values (three categories).
- "One pass", "in place", "no counting sort".
- This is also called the **Dutch National Flag** partition.

### Brute force

Library sort: O(n log n). Or count the 0s, 1s and 2s, then overwrite: O(n) time, O(1) space but two passes. The one-pass version is what interviewers want.

### Intuition

Two jobs need three positions. Keep three zones in the array plus an unknown zone:

- `[0, low)` holds 0s.
- `[low, mid)` holds 1s.
- `[mid, high]` is **unknown**.
- everything after `high` holds 2s.

`mid` inspects the first unknown value:

- **0:** swap with `low`, then advance both `low` and `mid`. What comes from `low` is a known 1 (or itself), so `mid` can safely move on.
- **1:** already in the right zone. Advance `mid`.
- **2:** swap with `high`, then move `high` left. **Do not advance `mid`.** The value that came from `high` is unknown, so it still needs inspecting.

<Figure caption="Four zones, one invariant: only the unknown middle stretch still needs looking at.">
  <ArrayStrip values={[0, 0, 1, 1, 2, 0, 1, 2, 2]} pointers={[{ at: 2, label: 'LOW', tone: 'red' }, { at: 4, label: 'MID', tone: 'gold' }, { at: 6, label: 'HIGH', tone: 'blue' }]} tones={{ 0: 'done', 1: 'done', 2: 'done', 3: 'done', 7: 'blue', 8: 'blue' }} regions={[{ from: 0, to: 1, label: '0s', tone: 'red' }, { from: 2, to: 3, label: '1s', tone: 'dim' }, { from: 4, to: 6, label: 'unknown', tone: 'gold' }, { from: 7, to: 8, label: '2s', tone: 'blue' }]} />
</Figure>

### Dry run

Watch the 2-swap carefully: the question there is the whole problem.

<DryRun title="Sort Colors" frames={dry.colorsFrames([2, 0, 2, 1, 1, 0])} predict />

### Algorithm

1. `low = 0`, `mid = 0`, `high = n - 1`.
2. While `mid <= high`:
   1. `nums[mid] == 0`: swap with `low`; `low++`, `mid++`.
   2. `nums[mid] == 1`: `mid++`.
   3. `nums[mid] == 2`: swap with `high`; `high--` (no change to `mid`).

### Java solution

<HintLadder hints={hints.colors}>

```java id=sortColors
public void sortColors(int[] nums) {
    int low = 0, mid = 0, high = nums.length - 1;
    while (mid <= high) {
        if (nums[mid] == 0) {
            int temp = nums[low];
            nums[low] = nums[mid];
            nums[mid] = temp;
            low++;
            mid++;
        } else if (nums[mid] == 1) {
            mid++;
        } else { // The input contains only 0, 1, and 2.
            int temp = nums[high];
            nums[high] = nums[mid];
            nums[mid] = temp;
            high--;
        }
    }
}
```

</HintLadder>

### Why it works

- **Settled:** 0s before `low`, 1s from `low` to `mid`, 2s after `high`.
- **Why the move is safe:** a swap with `low` brings a known 1 (or the same cell when `low == mid`); a swap with `high` brings an unknown value, so `mid` stays.
- **Stop:** when `mid` passes `high` the unknown zone is empty.

<Reveal q="Why is a swap with low safe to move past, but a swap with high isn't?">

When `low < mid`, the zone from `low` to `mid - 1` is already known to contain 1s. A swap with `low` therefore sends a known 1 to `mid`. When `low == mid`, it is a self-swap that settles the 0.

The value at `high` is still in the unknown zone. It could be anything. Advancing `mid` after receiving it would skip its inspection.

</Reveal>

### Complexity

- **Time O(n):** every iteration shrinks the unknown zone by one, even when `mid` stays put.
- **Space O(1).**

Partitioning objects this way does not generally preserve their original order within a group.

### Edge cases and mistakes

- Use `mid <= high`: when they are equal, one unknown value still needs inspection.
- The classic bug is an extra `mid++` after the high swap. Trace `[1, 2, 0]`: the buggy version ends as `[1, 0, 2]`. One tiny input exposes it.

<h2 id="merge-safely">9. Merge Sorted Array</h2>

### Problem

`nums1` has `m` real values followed by `n` empty slots (zeroes). `nums2` has `n` values. Both real parts are sorted. Merge `nums2` into `nums1` in place so the whole array is sorted.

Example: `nums1 = [1, 4, 7, 0, 0, 0]`, `m = 3`, `nums2 = [2, 5, 6]`, `n = 3` gives `[1, 2, 4, 5, 6, 7]`.

### How to recognise it

- Two sorted sequences combined into one.
- The destination is one of the inputs, with free space at its end.
- "In place" with no extra array.

### Brute force

Copy `nums2` into the free slots and sort: O((m + n) log (m + n)). Or merge into a new array from the front and copy back: O(m + n) time, O(m + n) space.

### Intuition

The normal merge writes the smallest value first, at the front. But the front of `nums1` is occupied by values we still need to read, so the first write would overwrite one of them.

Flip the direction. The **back** of `nums1` is empty, and the largest unread value is the next thing that belongs at the back. So compare the last unread value of each array, write the larger at the back, and move inward.

Writing from the back never overwrites an unread `nums1` value, because `write` stays at or ahead of `i` while `nums2` still has values.

<Figure caption="Free slots are at the back. write fills them with the larger of the two unread tails, so nothing unread is ever overwritten.">
  <ArrayStrip name="nums1" values={[1, 4, 7, '·', '·', '·']} pointers={[{ at: 2, label: 'i' }, { at: 5, label: 'WRITE', tone: 'green' }]} tones={{ 3: 'ghost', 4: 'ghost', 5: 'ghost' }} regions={[{ from: 0, to: 2, label: 'unread', tone: 'blue' }, { from: 3, to: 5, label: 'free space', tone: 'green' }]} />
  <ArrayStrip name="nums2" values={[2, 5, 6]} pointers={[{ at: 2, label: 'j', tone: 'purple' }]} regions={[{ from: 0, to: 2, label: 'unread', tone: 'purple' }]} />
</Figure>

### Dry run

<DryRun title="Merge Sorted Array" frames={dry.mergeFrames([1, 4, 7, 0, 0, 0], 3, [2, 5, 6], 3)} predict />

### Algorithm

1. `i = m - 1`, `j = n - 1`, `write = m + n - 1`.
2. While `j >= 0`:
   1. If `i >= 0` and `nums1[i] > nums2[j]`, write `nums1[i]` at `write` and `i--`.
   2. Otherwise write `nums2[j]` at `write` and `j--`.
   3. `write--`.
3. Stop when `nums2` is used up.

### Java solution

<HintLadder hints={hints.merge}>

```java id=merge
public void merge(int[] nums1, int m, int[] nums2, int n) {
    int i = m - 1, j = n - 1, write = m + n - 1;
    while (j >= 0) {
        if (i >= 0 && nums1[i] > nums2[j]) {
            nums1[write--] = nums1[i--];
        } else {
            nums1[write--] = nums2[j--];
        }
    }
}
```

</HintLadder>

### Why it works

- **Settled:** everything after `write` is the final sorted suffix.
- **Why the move is safe:** the larger of the two unread tails is the largest unread value overall, so it is the right value for the largest free slot.
- **Stop:** when `j < 0`, everything left in `nums1` is already where it belongs. If `i` runs out first, the loop copies the rest of `nums2`.

### Complexity

- **Time O(m + n):** each value is written once.
- **Space O(1)** beyond the given buffer.

### Edge cases and mistakes

- Spare slots hold zeroes, but zero can also be real data. Use `m` and `n` to know what is real, never the contents.
- Try `m = 0` (copy all of `nums2`) and `n = 0` (nothing to do).
- This is the same merge as the forward one into a separate array. The destination's layout decides which direction is safe.

<h2 id="match-in-order">10. Append Characters to Make Subsequence</h2>

### Problem

Given strings `source` and `target`, find the minimum number of characters to append to the end of `source` so that `target` becomes a subsequence of it. A subsequence keeps order but may skip characters.

Example: `source = "axby"`, `target = "abc"` gives `1` (append "c").

### How to recognise it

- The word "subsequence": order matters, gaps are allowed.
- Two strings, one scanned fully, one matched piece by piece.

### Brute force

Generate subsequences of the source and look for the longest prefix of the target: exponential. A more sensible brute force tries every start position for each target character, which is quadratic in the worst case.

### Intuition

Walk the source once. Keep a second pointer `needed` at the next target character you are waiting for.

- If the current source character equals `target[needed]`, take it and advance `needed`.
- Otherwise ignore it.

Taking the **earliest** match is safe: an earlier match leaves at least as much source text for the remaining characters as a later match would. You never lose an opportunity by accepting it. At the end, whatever was never matched must be appended.

  <ArrayStrip name="target" values={['a', 'b', 'c']} pointers={[{ at: 2, label: 'NEEDED', tone: 'purple' }]} tones={{ 0: 'done', 1: 'done', 2: 'hot' }} regions={[{ from: 0, to: 1, label: 'matched in order', tone: 'green' }, { from: 2, to: 2, label: 'append', tone: 'gold' }]} />
</Figure>

### Dry run

<DryRun title="Append Characters" frames={dry.subsequenceFrames('axby', 'abc')} predict />

### Algorithm

1. `needed = 0`.
2. For each `read` over the source, while `needed < target.length()`:
   1. If `source[read] == target[needed]`, `needed++`.
3. Return `target.length() - needed`.

### Java solution

<HintLadder hints={hints.subsequence}>

```java id=appendCharacters
public int appendCharacters(String source, String target) {
    int needed = 0;
    for (int read = 0; read < source.length() && needed < target.length(); read++) {
        if (source.charAt(read) == target.charAt(needed)) needed++;
    }
    return target.length() - needed;
}
```

</HintLadder>

### Why it works

- **Settled:** the target prefix before `needed` has been matched in order using source characters already visited.
- **Why the move is safe:** matching as early as possible never hurts later matches.
- **Stop:** when the source ends (or the target is fully matched), the unmatched target suffix is exactly what must be appended.

### Complexity

- **Time O(source length)** in the worst case.
- **Space O(1).**

This is for the problem's lowercase-letter input.

### Edge cases and mistakes

- Return 0 if everything matched. The `needed < target.length()` guard also handles an empty target without reading past it.
- Do not sort either string: that destroys the order.
- Advance `needed` only on a match. Advancing both pointers on a mismatch pretends you matched a character you never saw.

<h2 id="square-the-array">11. Squares of a Sorted Array</h2>

### Problem

Given a sorted array (possibly with negatives), return the squares of each value in sorted order.

Example: `[-7, -3, 2, 5]` gives `[4, 9, 25, 49]`.

### How to recognise it

- Sorted input, but the transformation (squaring) breaks the order.
- The largest output comes from one of the two ends.

### Brute force

Square everything, then sort: O(n log n) time. It ignores the structure the input already has.

### Intuition

Squaring turns large negative numbers into large positives. The biggest square always comes from one of the ends: the most negative value or the largest positive value.

So compare the two end squares, put the larger at the **back** of the result, and move that pointer inward. Repeat. It is the opposite-ends idea from Part One combined with the write-from-the-back idea from Merge Sorted Array.

</Figure>

### Dry run

<DryRun title="Squares of a Sorted Array" frames={dry.squaresFrames([-7, -3, 2, 5])} predict />

### Algorithm

1. `left = 0`, `right = n - 1`, a result array of size n.
2. For `write` from n - 1 down to 0:
   1. Square both ends.
   2. Put the larger at `result[write]` and move the pointer it came from inward.
3. Return the result.

### Java solution

<HintLadder hints={hints.squares}>

```java id=sortedSquares
public int[] sortedSquares(int[] nums) {
    int left = 0, right = nums.length - 1;
    int[] result = new int[nums.length];
    for (int write = nums.length - 1; write >= 0; write--) {
        int leftSquare = nums[left] * nums[left];
        int rightSquare = nums[right] * nums[right];
        if (leftSquare > rightSquare) {
            result[write] = leftSquare;
            left++;
        } else {
            result[write] = rightSquare;
            right--;
        }
    }
    return result;
}
```

</HintLadder>

### Why it works

- **Settled:** the result after `write` is final and sorted. Every value still waiting lies between `left` and `right`.
- **Why the move is safe:** values in the unread range are bounded in absolute value by the two ends, so one end holds the largest remaining square.
- **Stop:** after n writes every input has been used.

### Complexity

- **Time O(n).**
- **Space O(n)** for the returned array, O(1) other working space.

Squares fit `int` under this problem's bounds. General integer inputs may need a `long[]` result and casts before multiplying.

### Edge cases and mistakes

- Fill from the back with the **larger** square. Filling from the front with the larger gives the wrong order.
- The loop is driven by the output, so the last remaining value is processed too. (A pair-search loop with `left < right` would skip it.)
- All negatives, all positives and a single element all work.

### Practice

<Trace title="Borrow two moves you already know" steps={squares} takeaway="Choose the larger square from the ends and write it into the last free output slot. You combined opposite-end selection with backwards writing." />

<Reveal q="Why does this loop run until write reaches 0, unlike the pair-search loop with left &lt; right?">

The final remaining value still needs to be squared and written. You are not trying to form a pair; you are consuming every input position exactly once.

</Reveal>

<h2 id="one-deletion">Variation 1. Valid Palindrome with one deletion</h2>

### Problem

Like Valid Palindrome, but you may delete **at most one** character. Every character counts.

Example: `"abca"` gives `true` (delete `b` or `c`). `"abc"` gives `false`.

### How to recognise it

A palindrome check where exactly one mismatch may be forgiven.

### Brute force

Try deleting each character and check the rest: n checks of O(n) each is O(n²).

### Intuition

Ordinary palindrome checking stops at the first mismatch. Now we spend our one deletion there. If the two ends differ, deleting something inside leaves those ends still facing each other, so a successful deletion must remove **one of the two mismatched ends**. Try both, and check each remaining range as a plain palindrome with no deletions left.

### Dry run

`"cbbcc"` shows why you need both branches:

<DryRun title="One deletion on cbbcc" frames={dry.oneDeletionFrames('cbbcc')} predict />

### Algorithm

1. Move inward while the ends match.
2. At the first mismatch, return `isPalindromeRange(left + 1, right) || isPalindromeRange(left, right - 1)`.
3. If no mismatch occurs, return true.

### Java solution

<HintLadder hints={['Find the first mismatch after matching inward.', 'At that mismatch, try a range that skips left and a range that skips right.', 'Each remaining range must be a plain palindrome. Two linear checks still give O(n) total time.']}>

```java id=validPalindromeOneDeletion
public boolean validPalindromeOneDeletion(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        if (s.charAt(left) != s.charAt(right)) {
            return isPalindromeRange(s, left + 1, right)
                || isPalindromeRange(s, left, right - 1);
        }
        left++;
        right--;
    }
    return true;
}
private boolean isPalindromeRange(String s, int left, int right) {
    while (left < right) {
        if (s.charAt(left++) != s.charAt(right--)) return false;
    }
    return true;
}
```

</HintLadder>

### Why it works

Everything outside the mismatch has matched. The only way to fix the mismatch is to drop one of its two characters, and those are the only two options.

### Complexity

**O(n) time, O(1) extra space.** At most two linear scans follow the first mismatch.

### Edge cases and mistakes

Always deleting the left endpoint is wrong. In `cbbcc`, after the outer `c`s match, `bbc` remains. Deleting the left `b` leaves `bc`, which fails. Deleting the right `c` leaves `bb`, which works. You need the OR of both checks.

This version allows *at most* one deletion, so a string that is already a palindrome is valid.

### Practice

<Reveal q="Why is always deleting the left endpoint wrong? Try cbbcc.">

The outer c's match, leaving `bbc`. Deleting the left b leaves `bc`, which fails. Deleting the right c leaves `bb`, which works. You need the OR of both range checks; you don't get to guess one branch.

</Reveal>

<h2 id="count-pairs">Variation 2. Count the pairs, including duplicates</h2>

### Problem

Sorted array and a target. Count the pairs that sum to the target. First clarify what counts as a different answer.

For `[1, 1, 2, 2]`, target 3:

| The question asks for... | Answer | Why |
|---|---|---|
| One valid pair | `[1, 2]` | Any valid pair is enough |
| Unique value pairs | 1 | Only the value combination 1 + 2 |
| Pairs of positions, with i &lt; j | 4 | Either of two 1s can pair with either of two 2s |

### How to recognise it

Two Sum II, but the question asks how many, with repeated values.

### Brute force

Check every pair of positions: O(n²).

### Intuition

Scan by sum as before. At a match, count the **run** of equal values at each end instead of moving each pointer once. If the end values differ, they contribute **left copies x right copies**.

If the endpoints are equal, sorted order makes every value between them equal too. With m remaining positions any two form a pair: **m x (m - 1) / 2**. Count them and finish.

### Dry run

`[1, 1, 2, 2, 3, 3]`, target 4 exercises both rules:

<DryRun title="Count pairs with duplicates" frames={dry.countPairsFrames([1, 1, 2, 2, 3, 3], 4)} predict />

### Algorithm

1. `left = 0`, `right = n - 1`, `count = 0`.
2. Sum too small: `left++`. Too big: `right--`.
3. On a match with different end values: count both runs, add the product, skip both runs.
4. On a match with equal end values: add `size x (size - 1) / 2` and stop.

### Java solution

<HintLadder hints={['Move by the sum until you find a match.', 'On a match, count whole runs of equal values instead of moving each end once.', 'Different end values: multiply run lengths. Equal end values: choose any two remaining positions and stop.']}>

```java id=countPairs
public long countPairs(int[] nums, int target) {
    int left = 0, right = nums.length - 1;
    long count = 0;
    while (left < right) {
        long sum = (long) nums[left] + nums[right];
        if (sum < target) left++;
        else if (sum > target) right--;
        else if (nums[left] == nums[right]) {
            long size = right - left + 1;
            count += size * (size - 1) / 2;
            break;
        } else {
            int lowValue = nums[left], highValue = nums[right];
            long lowCopies = 0, highCopies = 0;
            while (left <= right && nums[left] == lowValue) {
                lowCopies++;
                left++;
            }
            while (right >= left && nums[right] == highValue) {
                highCopies++;
                right--;
            }
            count += lowCopies * highCopies;
        }
    }
    return count;
}
```

</HintLadder>

### Why it works

Every pair of positions with that sum has one value from each run (or both from the single equal block), so each is counted once, and skipping the runs removes only values already counted.

### Complexity

**O(n) time, O(1) space** for sorted input. The answer can be quadratic in n even though the work is linear, so `long` protects the count. For **unique value pairs**, add 1 per match and skip both runs.

### Edge cases and mistakes

3Sum skips duplicate *results*. Position-pair counting must include the combinations that duplicate positions create. The question decides the rule.

### Practice

<Reveal q="Four 2s, target 4. Why isn't the answer 4 x 4?">

That would allow a position to pair with itself and count each pair in both orders. The six valid index pairs are `(0,1)`, `(0,2)`, `(0,3)`, `(1,2)`, `(1,3)`, and `(2,3)`.

</Reveal>

### LeetCode

No single LeetCode problem matches exactly. The neighbours are [Two Sum II](https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/) (one pair) and [3Sum](https://leetcode.com/problems/3sum/) (unique results).

<h2 id="count-less">Variation 3. Count every pair below a target</h2>

### Problem

Sorted `[1, 2, 4, 7]`, target 6. Count position pairs whose sum is **strictly less** than 6. Answer: 2 (`1 + 2` and `1 + 4`).

### How to recognise it

"How many pairs" with an inequality instead of an exact sum. One decision can settle many pairs.

### Brute force

Check all pairs: O(n²).

### Intuition

Look at `left` and `right`. If `nums[left] + nums[right] < target`, then `nums[right]` is the **biggest** partner `left` could have, and it works. So every value between them works too: that is `right - left` pairs counted in one step. Then `left` is finished, so move it. If the sum is not below the target, `right` is too big for everyone remaining, so move `right`.

<Figure caption="1 + 4 is under 6, and 4 is the biggest partner 1 can have, so every partner between them works too. One decision, right - left = 2 pairs.">

</Figure>

### Dry run

<DryRun title="Count pairs below a target" frames={dry.countBelowFrames([1, 2, 4, 7], 6)} predict />

### Algorithm

1. `left = 0`, `right = n - 1`, `count = 0`.
2. While `left < right`: if the sum is below the target, add `right - left` and `left++`. Otherwise `right--`.

### Java solution

<HintLadder hints={['A match with the largest remaining partner can tell you about all smaller partners.', 'When the end sum is below the target, add right − left for this left position.', 'Then advance left. Otherwise move right. Stop when left and right meet.']}>

```java id=countPairsBelow
public long countPairsBelow(int[] nums, long target) {
    int left = 0, right = nums.length - 1;
    long count = 0;
    while (left < right) {
        if ((long) nums[left] + nums[right] < target) {
            count += right - left;
            left++;
        } else {
            right--;
        }
    }
    return count;
}
```

</HintLadder>

### Why it works

All qualifying pairs involving retired left positions have been counted exactly once, and the remaining range still holds every uncounted candidate.

### Complexity

**O(n) time, O(1) space** for sorted input.

### Edge cases and mistakes

Counting pairs at or below a target changes `<` to `<=`. Say which comparison the problem requires before coding. Keep sums in `long`.

### Practice

**Transfer test:** how could two calls to this function count sums in an inclusive interval `[low, high]`? Keep the upper-bound arithmetic in `long`.

<h2 id="two-way-partition">Variation 4. Split into two groups</h2>

### Problem

Put every value below a pivot first and everything else after. Order inside a group does not matter. Return the size of the first group.

Example: `[5, 1, 4, 2]`, pivot 3 can become `[1, 2, 4, 5]` with return value 2.

### How to recognise it

You need groups, not a fully sorted array.

### Brute force

Sort everything: O(n log n), more work than the task needs.

### Intuition

This is Move Zeroes with a different keep rule. `read` inspects each value; `write` marks the end of the group of values below the pivot. Before `write`: values that pass. Between `write` and `read`: inspected values that do not. At and after `read`: unknown.

### Dry run

<DryRun title="Partition around a pivot" frames={dry.partitionFrames([5, 1, 4, 2], 3)} predict />

### Algorithm

1. `write = 0`.
2. For each `read`: if `nums[read] < pivot`, swap into `write` and `write++`.
3. Return `write`.

### Java solution

<HintLadder hints={['The task needs groups, not fully sorted values.', 'read inspects each value; write marks the next slot for a value below the pivot.', 'Swap each matching value into write and advance write. Always advance read. Return write as the group boundary.']}>

```java id=partitionLess
public int partitionLess(int[] nums, int pivot) {
    int write = 0;
    for (int read = 0; read < nums.length; read++) {
        if (nums[read] < pivot) {
            int temp = nums[write];
            nums[write] = nums[read];
            nums[read] = temp;
            write++;
        }
    }
    return write;
}
```

</HintLadder>

### Why it works

Everything before `write` is below the pivot, everything between `write` and `read` is not, and each iteration moves `read` forward.

### Complexity

**O(n) time, O(1) extra space.**

### Edge cases and mistakes

All values remain present, but the original order of the non-matching group is not guaranteed. Partitioning `[5, 4, 1]` below 3 produces `[1, 4, 5]`, reversing the two large values.

### Practice

**Transfer test:** replace "below pivot" with "even". What changes in the code? Then require both groups to keep their original order: why isn't the same swap rule sufficient?

<h2 id="target-difference">Variation 5. Look for a difference</h2>

### Problem

Sorted `[1, 3, 8, 12]`, find two different positions where larger minus smaller equals 5. Answer: yes (`8 - 3`).

### How to recognise it

Sorted input, a pair condition on the **difference**, not the sum.

### Brute force

Check every pair: O(n²).

### Intuition

A sum search starts at opposite ends. A difference search needs both readers moving the **same** way, because the difference shrinks as the two get close. Start both near the beginning, call them smaller and larger.

- Difference too small: raise the larger value, so the larger reader moves right.
- Difference too big: raise the smaller value, so the smaller reader moves right.

Each reader moves forward at most n times.

### Dry run

<DryRun title="Target difference" frames={dry.differenceFrames([1, 3, 8, 12], 5)} predict />

### Algorithm

1. `left = 0`, `right = 1`.
2. While `right < n`: if they are the same position, advance `right`. Compute `nums[right] - nums[left]`: equal means found, smaller than target means `right++`, otherwise `left++`.

### Java solution

<HintLadder hints={['Both readers move forward, but their jobs are smaller candidate and larger candidate.', 'Keep the positions distinct. If they meet, move the larger-value reader ahead.', 'Compare larger minus smaller to the target. Increase the larger reader if too small, the smaller reader if too big.']}>

```java id=hasPairDifference
public boolean hasPairDifference(int[] nums, int target) {
    if (target < 0) return false; // This asks for larger minus smaller.
    int left = 0, right = 1;
    while (right < nums.length) {
        if (left == right) {
            right++;
            continue;
        }
        long difference = (long) nums[right] - nums[left];
        if (difference == target) return true;
        if (difference < target) right++;
        else left++;
    }
    return false;
}
```

</HintLadder>

### Why it works

If the difference is too small, this larger value with this smaller value or any later one only gets smaller, so this larger value is finished and the larger reader moves. If it is too big, this smaller value with this larger value or any later one only gets bigger, so this smaller value is finished and the smaller reader moves.

### Complexity

**O(n) time, O(1) space** for sorted input.

### Edge cases and mistakes

Copying the sum-search movement rules can skip valid pairs. Derive the direction from the expression you are actually comparing. A target difference of zero needs two equal values at different positions, not one value paired with itself.

### Practice

**Transfer test:** why do the readers both move right here, but opposite readers move inward for a sum? Answer from the formula, not from memory.

<h2 id="intersection">Variation 6. Keep only what both inputs contain</h2>

### Problem

Two sorted arrays. Return the **unique** values that appear in both.

Example: `[1, 1, 4, 7]` and `[1, 3, 4, 4]` give `[1, 4]`.

### How to recognise it

Two sorted sequences, and you want what they share rather than their union.

### Brute force

For each value in one array, scan the other: O(m x n). Or put one array in a set: O(m + n) time, O(m) space.

### Intuition

Give each array a reader. Compare the two current values.

- Equal: it is in both. Emit it once and advance both.
- One is smaller: that value cannot match the other array's current value or anything after it (those are at least as large). Advance the smaller reader.

### Dry run

<DryRun title="Sorted intersection" frames={dry.intersectionFrames([1, 1, 4, 7], [1, 3, 4, 4])} predict />

### Algorithm

1. `i = 0`, `j = 0`.
2. While both are in range: advance the smaller; on equality, emit if it differs from the last emitted value and advance both.

### Java solution

<HintLadder hints={['A smaller current value has no partner in the other remaining sorted suffix.', 'Give each input one reader. Only matching values go into the result.', 'Advance the smaller reader; on equality, emit if new and advance both. Stop when either input ends.']}>

```java id=intersectionUnique
public java.util.List<Integer> intersectionUnique(int[] a, int[] b) {
    var result = new java.util.ArrayList<Integer>();
    int i = 0, j = 0;
    while (i < a.length && j < b.length) {
        if (a[i] < b[j]) i++;
        else if (a[i] > b[j]) j++;
        else {
            if (result.isEmpty() || result.get(result.size() - 1) != a[i]) {
                result.add(a[i]);
            }
            i++;
            j++;
        }
    }
    return result;
}
```

</HintLadder>

### Why it works

A value is dropped only when the other array's remaining values are all at least as large, so it cannot have a partner. Matches are emitted once.

### Complexity

**O(m + n) time**, O(k) space for k returned values, O(1) other space. For a multiset intersection, emit on every match: matching one position from each input naturally returns the smaller copy count.

### Edge cases and mistakes

Merging continues until all values are placed. Intersection stops when **either** input ends. An empty input gives an empty result.

### Practice

**Transfer test:** merging continues until all values are placed. Intersection stops when either input ends. Explain that difference before changing the loop condition.

<h2 id="choose-the-tool">When not to use two pointers</h2>

Try opposite-end sum moves on **unsorted** `[3, 2, 4]`, target 6. The ends add to 7, which is too big, so the rule says move `right`. That discards 4 and loses the only answer, 2 + 4.

The rule did not fail by accident. Its proof **needed sorted order**, and nobody checked. A pattern name does not supply a missing condition.

Before choosing two pointers, ask whether each move can settle a value or eliminate a whole group of possibilities. If not, consider another tool:

- Unsorted Two Sum that needs original indexes, in O(n): a **hash map**.
- Sorting paired values and indexes is another option when O(n log n) is acceptable.

</Reveal>

<h2 id="wider-family">Related pointer patterns</h2>

Some pointer techniques have their own chapters. The shared idea is **two positions with a relationship worth preserving**.

| Relative movement | What it tells you | Where it belongs |
|---|---|---|
| One pointer moves one hop, another two | In a cycle, they eventually meet | <a href={`${BASE}dsa/lessons/linked-lists/`}>Fast/slow pointers · Linked Lists</a> |
| Both move with a fixed gap | The trailing position is a known distance behind | <a href={`${BASE}dsa/lessons/linked-lists/`}>Nth node from the end · Linked Lists</a> |
| Two boundaries enclose a range | State tracks what is inside; expand or shrink to keep a condition | <a href={`${BASE}dsa/lessons/sliding-window/`}>Sliding Window</a> |
| Both move outward from a center | Every inner pair already matches; check the next outer pair | <a href={`${BASE}dsa/lessons/dp-1d/`}>Palindrome expansion · 1-D DP</a> |

**Fast/slow is not read/write.** Both positions follow the structure; neither builds an output prefix. Starting them together is not evidence of a cycle: compare after advancing.

**Fixed gap is not target difference.** A fixed gap preserves a number of positions or hops. The difference search compares values and changes the gap as needed.

**An expanding center has two starting shapes.** Try `aba` (one middle character) and `abba` (a gap between two). Check both kinds. Trying every center is O(n²) worst case with O(1) extra space.

**A window needs its own movement proof.** With negative numbers, removing a left value can increase a sum and extending can decrease it. Do not transplant a positive-only rule without checking.

1. **Count within a band.** Sorted input, count position pairs with a sum in inclusive `[low, high]`. Include duplicates. Test an empty input, all-equal values, and bounds near integer limits.
2. **Change the filter.** Keep at most three copies in a sorted array. Return the correct prefix length. Test fewer than three values, a long repeated run, and an all-distinct input.
3. **Change the output.** Return the multiset intersection of two sorted arrays, keeping the smaller frequency of each value. Test one empty input and uneven duplicate runs.

<Reveal q="I've written and tested it. What should my reasoning contain?">

**Band count:** `countPairsBelow(nums, (long) high + 1) - countPairsBelow(nums, low)`, assuming `low <= high`. Each call has its own fresh pointers. Counts and the upper-bound addition use `long`.

**Three copies:** keep if `write < 3 || nums[read] != nums[write - 3]`. The compared value belongs to the kept prefix. Return `write`; ignore the tail.

**Multiset intersection:** advance the smaller reader; on equality, emit one and advance both. Unlike unique intersection, do not suppress repeated matches. Stop when either sequence ends.

Now explain why a slightly wrong version fails on one of your tests. That counterexample is stronger evidence of understanding than a memorised template.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Start with... | The invariant |
|---|---|---|
| Symmetry, ignoring some characters | Two ends; skip, compare, move both | Everything outside has matched or been ignored |
| Sorted input + target pair | Two ends; move by the sum | No possible answer has been thrown away |
| Unique triplets | Fix one + pair search + skip repeated results | Each unique triplet is returned once |
| Largest container between lines | Measure area; move shorter side | Ruled-out pairs cannot beat the best measured |
| Water above bars | Left/right maxima; settle the lower known wall | Processed positions have final water amounts |
| Move zeroes / filter in place | Reader + writer | Kept prefix is final and in order |
| At most K duplicates | Reader + writer; compare K kept slots back | Kept prefix respects the copy limit |
| Three categories in place | low / mid / high | Only the middle unknown zone needs inspection |
| Merge two sorted sequences | One reader each + output writer | Written output is final; unread data is safe |
| Subsequence with gaps | Source reader + next needed target character | Target prefix matched in order |
| Sorted squares | Compare end squares; fill output backwards | Written suffix holds the largest squares in order |
| One deletion allowed | At the first mismatch, check both endpoint-removal branches | Each branch has no deletion left |
| Count duplicate position pairs | Count runs at matched ends | Every distinct position pair counted once |
| Count sums below a bound | Add a whole partner range when its largest member works | Retired left positions have all pairs counted |
| Partition into two groups | Read + boundary writer | Known prefix satisfies the predicate; all values kept |
| Sorted target difference | Two readers moving forward | Movement follows the difference; positions distinct |
| Sorted intersection | Advance the smaller reader; emit on equality | Output values appeared in both inputs |

Two pointers does **not** automatically mean O(n) time or O(1) space. Count every loop and every output structure. 3Sum has repeated scans; sorted squares builds an output array.

### Five bugs to watch for

1. **Moving without a reason.** Say what has become impossible or settled before moving.
2. **Overwriting something unread.** Decide whether a copy, swap, or backwards write protects it. In-place does not always mean swapping.
3. **Counting swaps instead of kept values.** `write` advances whenever a value is kept, including self-position cases.
4. **Skipping unknown values.** After Sort Colors swaps with `high`, inspect `mid` again.
5. **Borrowing the wrong loop boundary.** Pair search stops when pointers meet; partitioning and writing may still have one value to process. Trace that last iteration.

<h2 id="revision">Revision summary</h2>

**How to recognise it.** Sorted input with a pair or sum condition; symmetry between two ends; in-place filtering or partitioning; merging or matching two sorted sequences; a formula over a pair of positions (container).

**Core algorithm.** Give each pointer one job. State what is settled, move a pointer only when that move discards something that provably cannot be part of the answer, and stop when the unknown region is empty.

- *Opposite ends:* start at both ends; move the pointer whose value cannot work with anything remaining.
- *Read and write:* `read` visits everything, `write` marks the end of the kept prefix.
- *One reader per sequence:* advance the smaller (or larger) one; write into space that holds nothing unread.

**Common mistakes.**

- Using `<=` where `<` is needed (pair search) or the reverse (partition, write loops).
- Forgetting to move both pointers after a hit, or to skip repeated results.
- Advancing `mid` after taking a value from `high` in Sort Colors.
- Treating `0` in spare slots as data, or relying on sorted order that is not there.

**Complexity.** Usually O(n) time and O(1) extra space. 3Sum is O(n²). Sorted squares needs O(n) for the output array. Sorting first adds O(n log n).

**Three representative problems.**

1. [Two Sum II](https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/) (opposite ends)
2. [Move Zeroes](https://leetcode.com/problems/move-zeroes/) (read and write)
3. [Merge Sorted Array](https://leetcode.com/problems/merge-sorted-array/) (one reader per sequence, write from the back)
