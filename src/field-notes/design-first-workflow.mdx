**Honesty guard.** I wrote and run this workflow as backend lead on a multi-tenant healthcare SaaS platform. The "after" numbers are from the next few stories, a small sample. Say "about three rounds", not a percentage.

## 60-second pitch

One story (suspending and reactivating users) needed **11 review rounds**. Looking back, **18 of the 47 findings in rounds 6 to 11 were bugs our own earlier fixes had created.** We fixed one finding at a time without ever drawing the whole picture, so each fix opened a door next to it. Work crept into code the ticket never asked about, and once we reversed a signed decision because a reviewer argued for it. Afterwards I wrote a design-first workflow: before any code, list every way the thing can be reached (the **doors**), every starting state, the result and side effects for each pair (the **map**), and three to five **promises** that must always hold. Get it signed. Build exactly that, test from the map, and if review round 3 still finds important issues, **stop**: the design is wrong, not the code. The next stories converged in about three rounds.

## Concepts (general first)

- **Doors × states.** Most "fix one, break another" bugs come from a rule implemented per entry point. Enumerate every entry point (UI, API, scheduler, internal service calls) and every state, then make every door call **one** shared rule.
- **Promises.** A handful of invariants ("deactivated is final", "suspend ends every session"). Reviewers check code against promises, not against taste.
- **Table test from the map.** One test row per map row, written from the signed design, so tests don't just mirror the code.
- **Stop rule.** Repeated important findings late in review mean the model is missing something. More patches make it worse; go back and fix the design.
- **Signed decisions stay signed.** A reviewer's argument against a decision goes back to the decision owner; it isn't applied on the spot.

## How it works (the 8 steps)

1. **Understand**: ticket, epic, siblings; trace the code end to end; table of each acceptance criterion vs what exists (file:line).
2. **Ask** (gate 1): one batch of questions whose answers change what gets built; record each as a decision.
3. **Design** (gate 2, sign-off): doors, map, promises, scope with follow-ups, test plan.
4. **Build exactly the design**: table test first, shared rules in one place.
5. **Prove it**: unit, table test, end-to-end on the local stack; baseline the suite before blaming a failure.
6. **Trim**: remove anything the design doesn't need.
7. **Review against the design** (gate 3), with the stop rule.
8. **Ship and record**: PR linking the design, plain-language and test-results pages.

## Decisions vs alternatives

| Choice | Alternative | Why |
|---|---|---|
| Design on a shared page, signed before code | Design in the PR description | Reviewers and the product owner can challenge it before code exists |
| Stop rule at round 3 | Keep iterating | Late repeated findings signal a model gap; iterating made it worse last time |
| Out-of-scope findings → smallest guard or a follow-up ticket | Fix everything found | Scope creep caused half the regressions |
| Reviewer can't change a signed decision | Accept good arguments immediately | Decisions belong to their owner; ask, don't flip |

## War stories

**1. The 18 of 47.** Situation: a status feature with many entry points. Bug: each review finding was patched in the door where it was found; sibling doors kept the old rule, and later fixes conflicted with earlier ones. Fix: a written map of every door and state, one shared rule. Lesson: count how many of your findings your own fixes created; that number tells you whether you have a design problem.

**2. The stop rule doing its job.** In a later security fix, review round 2 found that a code check called another service. Instead of patching it (which round 1 had done), I went back to the design and stored the needed value at creation time. The fix got smaller, not bigger.

**3. A test that encoded the bug.** Writing tests from the map exposed an existing test that asserted the vulnerable behaviour. Tests written from code would have kept it.

## Q&A drill

- **"How did you get the team to adopt it?"** I used it first on my own stories, published it as a short page with the real numbers, and made the gates lightweight: one question batch, one sign-off. Results did the persuading.
- **"Doesn't upfront design slow you down?"** The design step takes hours; the 11-round story cost days. The map also becomes the test plan, so it's not extra work.
- **"What if the design is wrong?"** That's what the stop rule is for: go back, fix the map, re-sign. It happened once since, and the result was a smaller fix.
