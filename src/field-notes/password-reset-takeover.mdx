**Honesty guard.** I found, designed and built this fix as backend lead on a multi-tenant healthcare SaaS platform. Status: built, proven on the full local stack (unit, Postgres integration and 30 end-to-end checks with a real inbox), three internal review rounds plus a PR review. **In review, not yet live.** No production numbers to quote.

## 60-second pitch

While tracing another feature I noticed our forgot-password endpoint returned the **actual reset token** in its response, the same value the email link carried. Anyone who knew an admin's email could reset that admin's password without ever opening the email. Platform support accounts, which can see every customer, were fully exposed. Customer tenants were only safe because a *second*, unrelated bug happened to block the last step. The rule I set myself: **nothing that works today may break**, across two frontends my team didn't own. I split the value the browser holds (a harmless **handle**) from the **proof** (a secret that only travels in the email, plus a random code stored as a hash). The browser keeps the same field name, so neither frontend changed. Then I capped guessing: 4-digit codes meant a per-reset try limit wasn't enough on its own, so I added a per-user hourly limit, made atomic with a Postgres advisory lock after a reviewer showed parallel requests could beat it.

## Concepts (general first)

- **Possession proof.** A reset link works because only the inbox owner can read it. Any value the API returns to an anonymous caller must therefore be *unable* to finish the reset on its own.
- **Handle vs secret.** Give the client an opaque identifier for the flow; keep the authorising secret on a side channel (the email). The handle becomes powerful only after the side-channel proof is presented to the server.
- **Derived codes are not secrets.** A code computed from a value the attacker already holds (with public code and no server key) proves nothing. Generate codes randomly and store only a hash.
- **Two limits, not one.** With 4 digits (10,000 codes), "5 tries per reset" alone lets an attacker loop: new reset, 5 guesses, repeat. You also need a cap on how often new codes can be requested.
- **Check-then-act races.** "Count, then insert" is not a limit under concurrency. Each parallel request reads the old count. Serialise per user (advisory lock, row lock or atomic counter).
- **Transactional outbox** (context): the platform's audit trail uses an outbox (write the event in the same transaction, deliver after commit with retries) to get Kafka-like delivery without a broker.

## How it's built

| Piece | Where |
|---|---|
| One component owns every rule; all 7 endpoints (admin + user flows) call it | `PasswordResetChallenge` |
| `issue`: read tenant limits first (no DB work yet), then one transaction under a per-user advisory lock: count this hour, end older resets, save handle + secret + BCrypt(code) + the tenant's try limit | `issue`, `lockResetsOf` (native `pg_advisory_xact_lock(hashtextextended(user_id, ...))`) |
| `verifyCode`: lock the reset row, compare BCrypt, count misses, kill the reset at the stored limit | `verifyCode` with a `PESSIMISTIC_WRITE` lookup |
| `requireUsable`: link secret, or a handle whose code was verified | `requireUsable` |
| Hourly count by user id with a native query, so the caller's tenant filter can't hide rows | `countRecentForUser` |
| Migration adds `request_handle`, `otp_hash`, `otp_attempts`, `otp_max_attempts`, `otp_verified_at` | one Flyway migration |
| Resets created before the deploy keep the old behaviour until they expire | `otp_hash IS NULL` branch |

## Decisions vs alternatives

| Decision | Alternative | Why I chose it |
|---|---|---|
| Keep the response field name, change what it holds | Remove the field | Both frontends store it and send it to the code and complete steps; removing it breaks every tenant's reset |
| Link secret completes on its own | Require the code with the link too | Only the inbox owner sees the link; requiring both needed frontend work in two apps |
| 5 tries per reset **and** 5 resets per hour, config defaults with per-tenant override | One global limit | 4-digit codes can be looped; tenants differ |
| Store the tenant's try limit on the reset at creation | Look it up at every code check | A code check must not depend on another service being up (found in review round 2) |
| Per-user advisory lock around issue | Unique time bucket / atomic counter | Smallest change, no schema; serialises exactly the operation that races |
| Keep pre-deploy resets working until expiry | Invalidate them in the migration | Product rule: nobody mid-reset is disrupted. Window is short (30 min admin, 24 h user) and recorded as a known limit |

## War stories

**1. The bug was "safe by accident".** Situation: customer tenants couldn't complete the takeover. Bug: only because a separate tenant-filter bug hid their reset rows. Fix: closed the leak for everyone and made the order explicit — the tenant-filter fix must ship *after* this one, or fixing one bug would expose every tenant. Lesson: when a vulnerability is blocked by another bug, write down the dependency before anyone "fixes" the blocker.

**2. A test that asserted the bug.** An existing unit test expected the token in the email to equal the token in the response. That was the vulnerability, encoded as a requirement. I flipped it: the test now proves they differ.

**3. Round 1 patched a symptom; round 2 found the cause.** Review round 1 found a call to another service (to read the tenant's limit) made while holding a database row lock. I moved the lookup before the lock. Round 2 pointed out the real issue: the code check shouldn't depend on that service at all. Storing the limit on the reset when it's created removed the call, the extra transaction code and a query. Lesson: "store the fact you need" beats "fetch it faster".

**4. The race I under-rated.** I'd listed "count then insert" as a minor accepted limit. A reviewer showed each parallel request leaves its **own live reset with 5 guesses**: 1,000 parallel requests give about 5,000 guesses at 10,000 codes, roughly a coin flip. Fix: a per-user advisory lock, plus an integration test firing 12 parallel requests that must produce exactly 5 resets and 1 live one. I removed the lock and confirmed the test fails before trusting it. Lesson: when judging a race, count what each racer *leaves behind*, not how often it slips through.

**5. Secrets in logs, missed twice.** I removed the reset value from six log and exception sites; an automated reviewer found two more on a late error path. Lesson: grep for the pattern, not the lines you're looking at.

## Q&A drill

- **"Why not just stop returning the token?"** Because both frontends use that field as the handle for the next two steps. Removing it breaks every tenant's reset. The fix is to change what the field *means*, not whether it exists.
- **"Isn't the handle still dangerous?"** Only after the server has seen the right emailed code for it. Before that, `complete` with the handle gets 401. That's the whole point of the split.
- **"Why hash a 4-digit code with BCrypt?"** So a database read doesn't hand out live codes, and comparisons happen only on the server. The try limit, not the hash, is what stops online guessing.
- **"What's an advisory lock and why here?"** A Postgres lock on a number you choose (here, derived from the user id), held until the transaction ends. It serialises "count, end old, insert" per user without a new table or a unique constraint.
- **"How do you avoid breaking existing users at deploy?"** Rows created before the migration have no handle or code hash; they keep the old behaviour until they expire. Short window, documented.
