<h2 id="prologue">Prologue · The thick arrow</h2>

Here is a failure that happens in real systems. At midnight on New Year's Eve, a photo app gets ten times its normal upload rate. The upload endpoint accepts each photo, holds the connection while a congested phone sends 2 MB at walking pace, then streams the same bytes on to storage. Every worker thread in the fleet is waiting on a phone. The feed API needs a thread for a tenth of a second, and cannot get one.

CPU on the app servers is 12%. They are not out of compute. They are out of waiting slots.

The fix is to move one arrow on the architecture diagram: the arrow that carries the photo bytes. It should not run through machines you have to scale.

This lesson is the toolbox for every design with **large, mostly immutable bytes**: photos, videos, documents, pastes, backups, build artefacts, ML datasets. It is the core of Pastebin, Instagram, YouTube, Dropbox and "design S3", and a supporting box in nearly every other design.

**The rule: big bytes never flow through your app servers.** They live in **object storage** under a key. They arrive through **presigned uploads**. They leave through a **CDN**. Your services only handle **metadata about them**. If a design streams a 2 GB video through an app server, the interview is going badly.

**Two common slips this lesson guards against.**

- **Layer conflation.** "The cache" in a media design could mean the browser, the CDN or Redis. Name which one.
- **Cache hand-waves.** A CDN is a cache, so the four promises from <a href={`${BASE}sd/lessons/caching/`}>Caching</a> apply to it: the key, the TTL (with a reason), invalidation, and a failure plan. Part Four makes you say all four for the edge.

<h2 id="why-not-db">Chapter 1 · Why not store files in the database</h2>

A **blob** (binary large object) is a payload your system stores and returns but never looks inside: a photo, a video, a PDF, a paste.

Databases are built for the opposite: small rows, indexes, transactions, queries over fields. Put terabytes of payload in one and every database chore starts carrying it.

A real example. A team stores avatars in the `users` table as a `BYTEA` column, because it is one less system to run. It works at ten thousand users. At twenty million, a replica dies and the rebuild takes most of a working day. The nightly backup runs into the morning. The replica lag graph spikes whenever many people change their avatar.

**Worked numbers.** 20M users × 200 KB avatar = **4 TB**. 20M × 1 KB of profile columns = **20 GB**. The avatars are 4 TB ÷ 4.02 TB ≈ **99.5%** of the table.

```text
Replica rebuild at 200 MB/s     4 TB  → 20,000 s ≈ 5.6 hours      20 GB → 100 s
Backups, snapshots, restores    every byte, every time
Replication stream              each avatar change ships 200 KB to every replica
Storage price                   replicated SSD block storage, ×3 copies: easily several times
                                the per-GB price of object storage (check your provider)
Serving                         every image request needs an app server and a DB connection;
                                a CDN can't read your database
```

One precision point an interviewer may push on: **not every query slows down.** Postgres stores large values out of line (TOAST), so a query that does not select the avatar column does not read those bytes. The damage is to backups, replication, cost and serving (the operational life of the database), and to any `SELECT *`.

### The metadata split

This pattern is used by every file and media design. The bytes go to object storage under a key. A row in your database records the facts about them:

```sql
CREATE TABLE photos (
  id            BIGINT       PRIMARY KEY,          -- public id, random or Snowflake
  owner_id      BIGINT       NOT NULL REFERENCES users(id),
  storage_key   TEXT         NOT NULL,             -- 'photos/7f/7f3a9c…/orig', chosen by the server
  content_hash  CHAR(64),                          -- SHA-256 hex, filled in after upload
  size_bytes    BIGINT,
  mime_type     TEXT,
  width_px      INT,
  height_px     INT,
  status        TEXT         NOT NULL,             -- 'pending' | 'active' | 'deleted'
  visibility    TEXT         NOT NULL DEFAULT 'public',
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX photos_by_owner ON photos (owner_id, created_at DESC);
```

**The database answers every question**: "list my photos newest first", "is this photo mine?", "is it private?". **The object store only serves bytes by exact key.** The row is a few hundred bytes. The object is megabytes.

| | Database row | Object storage |
|---|---|---|
| Holds | Facts you query, filter, join, check | Opaque bytes |
| Access | By any indexed field, in transactions | By exact key, whole object or byte range |
| Size sweet spot | Bytes to a few KB per row | KB to terabytes per object |
| Scales by | Sharding, replicas (your problem) | The provider's problem |
| Served to users | Through your API | Directly (presigned URL) or through a CDN |

**When a blob may stay in the database:** it is tiny and few (a 2 KB icon per tenant), or it must commit atomically with other rows and is small. A Microsoft Research study, *To BLOB or Not To BLOB* (Sears, van Ingen, Gray, 2006), found databases competitive for objects up to roughly a few hundred KB and file systems better above about 1 MB. The crossover depends on the system, but the shape of the answer has held.

<Reveal q="Pastebin pastes average 10 KB. Shouldn't they just live in the database?">

You could, and for a small pastebin it would work. The split still wins on three counts. The **size tail**: allow 10 MB pastes and a few of them dominate the bytes. A **lean database**: metadata stays hot in memory and backups stay fast. **Cacheable reads**: paste bodies are immutable, so a CDN can serve them without touching your servers.

Say it as a judgment call: *"Small pastes would fit in the DB, but the tail and the CDN make the split worth it."* Chapter 17 runs the numbers.

</Reveal>

<h2 id="object-model">Chapter 2 · Object, file and block storage</h2>

Three kinds of storage exist, and designs mix them up. The difference is what you address by and what you can change.

| | Block storage | File storage | Object storage |
|---|---|---|---|
| Address by | Block number on a volume | Path in a directory tree | Key in a flat bucket |
| Interface | Raw disk (a VM mounts it and formats it) | POSIX file API or NFS/SMB mount | HTTP: PUT, GET, HEAD, DELETE, LIST |
| In-place edits | Yes, any block | Yes, any byte range | No: whole-object writes |
| Shared by many machines | Usually one machine at a time | Yes (network file system) | Yes, by anyone with permission |
| Good for | Database disks, boot volumes, low-latency random IO | Shared home directories, legacy apps needing file semantics | Photos, video, backups, logs, datasets, static sites |
| Cost and scale | Most expensive per GB, sized per volume | Middle, scales less than object | Cheapest per GB, effectively unlimited |

One-line rule: **block for a database's own disk, file when software insists on a file system, object for everything else that is big and written once.** The rest of this lesson is about object storage.

### The object model, in five sentences

1. A **bucket** is a named container with its own settings: region, access policy, versioning, lifecycle rules, event notifications.
2. Inside it, a **key** (any string, like `photos/7f/7f3a9c/orig`) maps to an **object**: the bytes plus a little metadata (size, content type, an `ETag`, your custom headers).
3. The namespace is **flat**. A "folder" is just a shared **prefix**. Listing `photos/7f/` means "list keys starting with that string", paginated. Nothing "deletes a folder"; you delete every key under the prefix.
4. Objects are **written whole**. There is no "change bytes 100 to 200". You PUT the whole object again, under the same key (overwrite) or a new one. Reads can fetch a byte range.
5. Access is plain **HTTP**. That is the property the rest of the lesson exploits: clients can talk to the store directly.

| Property | What it means for your design |
|---|---|
| Key → bytes, no queries | Every question goes to your metadata database. Never "scan the bucket" on a request path |
| Practically unlimited capacity | Never estimate yourself out of object storage. Estimate to choose a **storage class** (Chapter 8) |
| Whole-object writes | Big mutable files get **chunked** (Chapter 7). Small edits should not rewrite gigabytes |
| HTTP access | **Presigned URLs** let clients upload and download without you (Chapter 4) |
| Versioning (optional) | An overwrite or delete keeps the old version: your undo button against bugs (Chapter 3) |

**Consistency: know the date.** For years S3 was eventually consistent for some operations: an overwrite or a LIST right after a write could return stale results. **Since December 2020, S3 provides strong read-after-write consistency** for object PUTs (new and overwrite), DELETEs and LISTs, automatically. Bucket-level configuration changes are still eventually consistent. Google Cloud Storage also documents strong consistency for object operations and listings. For any other provider, an older system, or a self-hosted S3-compatible store, **check its documented model**. "S3-compatible" describes the API, not the guarantees.

**Concurrent writes: last writer wins.** Two PUTs to the same key with no conditions: one silently replaces the other. Avoid shared mutable keys: **the server chooses a fresh key per upload** (a random id or hash), so writers never collide. Where you genuinely need "create only if absent" or compare-and-swap, some stores support conditional writes (S3 added `If-None-Match: *` in August 2024, and `If-Match` with an ETag after that; check what your store supports).

**Request rates are per prefix.** Object stores partition the key space by prefix. AWS documents at least 3,500 writes and 5,500 reads per second **per partitioned prefix**, scaling up gradually as load grows, and you may see `503 Slow Down` while it does. A single hot **key** cannot be split, which is one more reason hot objects belong behind a CDN (Chapter 13).

<Trace title="Know your object store" steps={objectModel} takeaway="Flat keys, whole-object writes, last writer wins. S3 is strongly read-after-write consistent since December 2020; check anyone else's docs." />

<Reveal q="A teammate wants keys like users/{name}/avatar.jpg. What goes wrong?">

Three things. Users can change their names, and object keys cannot be renamed, only copied and deleted. Writers can collide on one key (last writer wins). And readable names leak information if a key is ever exposed.

Use **server-chosen, opaque, immutable keys** (`avatars/7f3a9c…`) and keep the human facts in the metadata row.

</Reveal>

**A common slip:** "S3 is eventually consistent, so after upload I'll wait before reading." That was true before December 2020. Say the current guarantee, and the caveat that it is S3's, not every store's.

<h2 id="durability">Chapter 3 · Durability is not availability</h2>

Two different promises hide behind "reliable". Someone reads the product page aloud: "Eleven nines! So it's never down." An SRE replies that it was down for four hours last year. It did not lose anything. It just would not give it back.

- **Durability** is the probability that **stored bytes are not lost**. S3 Standard is designed for 99.999999999% (eleven nines) annual durability.
- **Availability** is the fraction of time **requests succeed**. S3 Standard is designed for 99.99%. The contractual SLA is lower. One-zone classes are designed for less, because one zone can go away.

**These figures are provider-dependent and change over time. Treat them as the shape of the answer and check the current provider documentation before quoting them as fact.**

**Worked numbers.** Eleven nines is an annual loss probability of 10⁻¹¹ per object. With 10 million objects: 10⁷ × 10⁻¹¹ = 10⁻⁴ objects lost a year, about **one object every 10,000 years** on average. Four nines of availability allows 0.0001 × 525,960 minutes ≈ **53 minutes a year** of failed requests. Durability is astronomically better than availability, and the two are bought differently.

| | Durability | Availability |
|---|---|---|
| Question it answers | Will my bytes still exist? | Can I read or write right now? |
| Typical design figure (S3 Standard) | 11 nines | 4 nines |
| Failure it covers | Disk, rack, zone loss | Outage, throttling, network partitions |
| What you do about the rest | Versioning, backup copy | Retries, CDN with stale-if-error, multi-region reads |

### How stores buy durability: replication vs erasure coding

- **Replication**: keep N full copies on different machines, racks and zones. Three copies survive any two losses and cost **3×** raw space. Repair is simple: copy one surviving replica.
- **Erasure coding** (Reed-Solomon `(k, m)`): split the object into `k` data fragments, compute `m` parity fragments, store all `k + m` in different places. **Any `k` of them rebuild the object.** RS(10, 4) survives the loss of **any 4 of 14** fragments at **1.4×** raw space.

<Figure caption="Reed-Solomon (10, 4): fourteen fragments in different failure domains, any ten of which reconstruct the object.">
  <Mermaid code={`flowchart LR
    O["Object"] --> S["split into 10\ndata fragments"]
    S --> P["compute 4\nparity fragments"]
    P --> F["14 fragments spread over\ndisks, racks and zones"]
    F --> R["read any 10\nto rebuild"]`} />
</Figure>

| | 3× replication | RS(10, 4) erasure coding |
|---|---|---|
| Raw space for 5.5 PB | 16.5 PB | 7.7 PB |
| Survives | Any 2 losses | Any 4 losses |
| Repair one lost piece | Copy 1 replica | Read 10 fragments, recompute (network-heavy) |
| Read latency | Read one copy | Read across fragments (or the data fragments directly, when healthy) |
| Good for | Small, hot, latency-sensitive data | Large, warm and cold bulk data |

Large stores commonly erasure-code bulk data and spread fragments across availability zones. Many pack small objects into larger extents before coding, so per-object overhead stays low. In an interview, one sentence is enough: *"the store erasure-codes across zones for durability; that's the provider's problem"*. But know what the sentence means.

### Durability is not backup

Eleven nines faithfully preserves your mistakes. A buggy job that deletes `photos/` is durably recorded. Protection against **you** comes from:

- **Versioning**: deletes and overwrites keep the previous version.
- **Object lock / WORM retention** for compliance data.
- **Replication to a separate account or region** that the same credentials cannot delete.

<Trace title="Durability, availability, and you" steps={durability} takeaway="Durability: bytes not lost. Availability: requests succeed. Erasure coding buys durability cheaply. Versioning protects against your own bugs." />

<Reveal q="Why don't you multiply object storage by 3 in a storage estimate, when you do for a database?">

A managed object store replicates or erasure-codes **internally** and bills you for the **logical** bytes you stored. The redundancy is priced into its per-GB rate.

If you run the store yourself (Ceph, MinIO, HDFS), the multiplier is yours: ×3 for replication, about ×1.4 for RS(10, 4). Say which one you are estimating.

</Reveal>

**A common slip:** "Eleven nines, so we don't need backups." Durability protects against disks dying. It does nothing about a bad deploy, a compromised credential or a mistaken lifecycle rule. Name versioning or a cross-account copy.

<h2 id="presigned">Chapter 4 · Presigned uploads</h2>

**The problem.** Proxying uploads through the API makes slow clients expensive. A 2 MB photo over a congested 2 Mbps phone link takes 8 seconds, and the app server holds a worker thread for all of it.

**Worked numbers.** Assumptions from <a href={`${BASE}sd/lessons/estimation/`}>Estimation</a>: 5M uploads a day at 2 MB gives 5M ÷ 10⁵ × 3 = **150 uploads/s** at a normal peak. A New Year's midnight runs **10×**, 1,500/s. Phone uplinks: 2 Mbps. Fleet: 27 app servers × 200 worker threads = **5,400 threads**.

```text
One upload       2 MB × 8 = 16 Mb ÷ 2 Mbps = 8 s holding a thread
In flight        Little's law: 1,500/s × 8 s = 12,000 uploads      vs 5,400 threads → starved
Normal peak      150/s × 8 s = 1,200 threads ≈ 22% of the pool doing nothing but waiting
Feed needs       15,000 req/s × 0.1 s = 1,500 threads, which it couldn't get
Bandwidth        1,500 × 2 MB = 3 GB/s = 24 Gbps in, and the same 24 Gbps out to storage
                 = 48 Gbps through the app tier (the whole feed API is 2.4 Gbps)
If buffered      12,000 × 2 MB = 24 GB of RAM across the fleet just holding photos
With presigned   app work per upload ≈ 5 ms (auth, insert row, sign): 1,500 × 0.005 = 7.5 threads
```

The app tier does not run out of CPU. It runs out of **waiting slots**, because slow clients turn a 2 MB request into an 8-second request. Proxying also makes every byte cross your network twice, and makes your autoscaling track **upload bandwidth** instead of business logic.

**What a presigned URL is.** A time-limited, signed permission slip for **one operation on one key**. Your server computes it locally with its storage credentials (an HMAC signature, no call to the store needed) and hands it to the client. The client then talks to the store directly. The store checks the signature and expiry and accepts or rejects. **Uploads and downloads both use them: your API does auth and metadata, the store does bytes.**

<Figure caption="Before and after. Top: every byte crosses the app tier twice and pins a thread for 8 seconds. Bottom: the app tier spends 5 ms granting permission.">

    participant C as Phone
    participant API as App server
    participant S as Object storage
    Note over C,S: Proxying, the version that melts
    C->>API: POST 2 MB photo, 8 s on a slow link
    API->>S: PUT the same 2 MB
    S-->>API: 200 OK
    API-->>C: 201 Created
    Note over C,S: Presigned, the fix
    C->>API: I want to upload photo.jpg, 2 MB, image/jpeg

    C->>S: PUT bytes directly, the app tier never sees them
    S-->>API: event, object created
    API->>API: validate, then mark row active`} />

Issuing one in Python with boto3 (the `sha256` header pins the checksum, covered below):

```python
import secrets, boto3

s3 = boto3.client("s3")

def start_upload(user_id: int, content_type: str, size: int):
    if content_type not in ("image/jpeg", "image/png") or size > 10_000_000:
        raise ValueError("rejected before signing")
    key = f"photos/{secrets.token_hex(16)}/orig"      # server-chosen, opaque
    db.execute("INSERT INTO photos (owner_id, storage_key, status) "
               "VALUES (%s, %s, 'pending')", (user_id, key))
    url = s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": "media", "Key": key, "ContentType": content_type},
        ExpiresIn=900,                                 # 15 minutes
    )
    return {"upload_url": url, "key": key}
```

The client then does `PUT <upload_url>` with the same `Content-Type`. A mismatch fails the signature check.

### Rules for issuing one

Each rule closes a real hole.

| Rule | Because |
|---|---|
| **The server chooses the key** | A client-chosen key can overwrite someone else's object or plant files on paths you serve |
| **One method, one key** | A PUT URL cannot be used to GET or to write elsewhere |
| **Short expiry** (minutes) | It is a **bearer** token: anyone holding it can use it until it expires, and you generally cannot revoke a single URL early |
| **Pin what you can** | Sign the content type. To cap size, S3's presigned **POST** policy supports a `content-length-range` condition (a presigned PUT does not enforce a maximum by itself) |
| **Never trust what arrives** | After upload, check size and real type (magic bytes, not the extension), scan if needed, re-encode images, **strip EXIF location data** |

For **downloads** of private objects, the same idea in reverse: the API checks access, then returns a short-lived presigned GET (or, at scale, a CDN signed URL, Chapter 14).

### Checksums: proving the bytes arrived intact

TCP and TLS protect each hop, but a bug in a client, a proxy or a disk can still deliver different bytes than were sent. A checksum catches that.

1. The client computes a checksum of the file (SHA-256 or CRC32C; check which algorithms your store supports).
2. It sends the checksum with the upload (S3 supports `x-amz-checksum-sha256` and similar headers, and `Content-MD5`).
3. The store recomputes it while receiving and **rejects the upload on a mismatch**.
4. You keep the hash in the metadata row (`content_hash`) for later integrity checks and dedup.

Do not treat the `ETag` as a content hash. For a simple unencrypted PUT it is often the MD5 of the bytes, but for multipart uploads and for some encryption modes it is **not** an MD5 of the whole object. Use an explicit checksum field.

<Trace title="Count the waiting" steps={presigned} takeaway="Slow clients turn small requests into long ones. Let the store hold the slow connections. Your server signs a narrow, short-lived permission and gets out of the way." />

<Reveal q="The interviewer asks: 'Isn't the presigned URL a security risk? Anyone with the link can upload.'">

Yes, for its lifetime it is a bearer credential. That is why it is narrow (one method, one server-chosen key, pinned content type, size-limited where the store supports it) and short (minutes).

Uploading to it achieves nothing on its own: the object stays invisible until your service validates it and flips the metadata row to active. Worst case, an attacker who steals a URL uploads junk to a key you will reject and clean up.

</Reveal>

**A common slip:** "The API receives the file and stores it in S3." It is harmless-sounding and it tells the interviewer you have not run this at scale. Lead with the presigned flow and say *why* in numbers: slow clients × upload rate = held connections.

<h2 id="upload-states">Chapter 5 · The upload state machine</h2>

**The problem.** A support ticket arrives: "My photo uploaded, the progress bar finished, but it never appears." An engineer finds the row: status `pending`, created yesterday. The object is in storage, perfectly fine. The completion event never arrived, or it arrived and the handler threw. Two systems disagree and nothing is checking.

The database and the object store are **two systems with no shared transaction**. You cannot commit "row is active" and "bytes exist" atomically. So you order the steps so **every failure is harmless**, and you run a job that repairs the leftovers.

<Figure caption="The upload state machine. Every arrow is idempotent, and the sweeper covers every arrow that can go missing.">
  <Mermaid code={`stateDiagram-v2
    [*] --> pending: API inserts row, signs URL
    pending --> processing: object-created event, or client confirms
    processing --> active: validated, thumbnails made, EXIF stripped
    processing --> rejected: wrong type, too big, failed scan
    pending --> expired: sweeper finds no object after 24 h
    active --> deleted: user deletes, row first
    deleted --> [*]: object deleted async, sweeper retries`} />
</Figure>

**How the loop closes:**

- **Two signals, one idempotent handler.** The store's event notification (S3 sends object-created events to a queue or function) and the client's own "I'm done" call both trigger the same handler: HEAD the key, check size and type, move `pending → processing`. Handling it twice is harmless.
- **Events are not a guarantee of timeliness or uniqueness.** S3 documents event notifications as delivered **at least once**, usually within seconds but sometimes a minute or more. Expect duplicates and delays.
- **A sweeper reconciles.** Every few minutes: rows `pending` for longer than the URL expiry plus a margin → HEAD the key. If the object exists, process it. If not, mark the row expired. For objects with no row, run a periodic listing job, or upload into a staging prefix with a lifecycle rule that deletes anything older than a day.
- **Processing is asynchronous.** Thumbnails, transcoding and scanning go on a queue (see <a href={`${BASE}sd/lessons/queues-streams/`}>Queues & streams</a> and <a href={`${BASE}sd/lessons/pattern-async-jobs/`}>Async jobs</a>). The row goes `active` only when the derived objects exist, so a feed never shows a photo without its thumbnail.

The idempotent handler in Python, with the transition done as one conditional UPDATE so concurrent duplicates cannot both win:

```python
def on_object_created(key: str):
    head = s3.head_object(Bucket="media", Key=key)       # does it really exist? how big?
    updated = db.execute(
        "UPDATE photos SET status='processing', size_bytes=%s "
        "WHERE storage_key=%s AND status='pending'", (head["ContentLength"], key))
    if updated == 0:
        return                                           # duplicate event, already handled
    queue.publish("process_photo", {"key": key})
```

**Deleting is the same problem backwards.** Mark the row `deleted` first (users stop seeing it immediately), then delete the object and its derived variants asynchronously, with the sweeper retrying failures. The failure you allow is orphaned bytes (a small cost, cleaned up later), never a row pointing at nothing (a broken image in every feed). Remember the CDN still holds copies, Chapter 12.

<h2 id="multipart">Chapter 6 · Multipart and resumable uploads</h2>

**The problem.** A single PUT is all or nothing. A user uploads a 20-minute video on a train, the tunnel hits at 99%, and the app starts again from zero.

**Multipart upload** splits the object into parts that upload **independently**:

1. **Initiate.** The API starts a multipart upload and gets an **upload id**. It presigns a URL per part (or per batch of parts).
2. **Upload parts.** The client PUTs each part, in parallel if it helps, and records each part's returned `ETag`. A failed part is retried alone.
3. **Complete.** The client (or API) sends the list of part numbers and ETags and the store assembles the object. Or **abort**, which discards the parts.

**Resuming** after the app is killed: the client keeps the upload id and asks the store which parts already arrived (S3's `ListParts`), then uploads only the rest.

**Worked numbers: a 2 GB clip on a 10 Mbps uplink.**

```text
Whole upload     2,000 MB × 8 = 16,000 Mb ÷ 10 Mbps = 1,600 s ≈ 27 min
Single PUT       drop at 99% → lose ≈ 1,584 s, restart from zero
8 MB parts       2,000 ÷ 8 = 250 parts; a drop loses one part: 64 Mb ÷ 10 Mbps = 6.4 s
Part sizing      S3: parts 5 MiB to 5 GiB (last part may be smaller), at most 10,000 parts,
                 objects up to 48.8 TiB
                 → part size ≥ object size ÷ 10,000: 100 GB needs parts of at least 10 MB
```

**Integrity with parts.** Checksum each part so a corrupted part is caught and retried alone (S3 supports per-part checksums). Verify the assembled object's recorded hash after completion if you need a whole-file guarantee, as the multipart `ETag` is not a simple MD5 of the file.

**Housekeeping that bites.** Parts of an upload that is never completed or aborted **stay stored and billed**. Add a lifecycle rule that aborts incomplete multipart uploads after a few days. And parallel parts help most on fat or high-latency links. On one congested phone link they mainly add resilience, not speed.

<h2 id="dedup">Chapter 7 · Chunking and dedup</h2>

**The problem.** A file-sync feature shows a spike of identical 500 MB uploads every Monday morning: a whole team syncs the same onboarding video. The same video is stored two hundred times. And when someone fixes a typo in a 1 GB design file, the client uploads a gigabyte.

**Content addressing** names each piece of data by a cryptographic hash of its bytes (SHA-256). Same bytes, same name, across files, users and time. Three things fall out:

- **Dedup.** Before uploading a chunk, check whether that hash is already stored. If it is, do not store it again; reference it.
- **Delta sync.** A file is a **manifest**: an ordered list of chunk hashes. When it changes, only chunks whose hashes changed are uploaded.
- **Integrity.** The name verifies the content. A corrupted chunk does not match its own hash.

That triplet, **chunk, hash, dedup**, is the heart of the Dropbox walkthrough and of <a href={`${BASE}sd/lessons/pattern-sync-collab/`}>Sync & collaboration</a>.

<Figure caption="Content-addressed storage. Two files share chunks. Each manifest is a list of hashes. Each chunk is stored once.">
  <Mermaid code={`flowchart LR
    A["File A manifest\nh1, h2, h3"] --> C1[("chunk h1")]
    A --> C2[("chunk h2")]
    A --> C3[("chunk h3")]
    B["File B manifest\nh1, h2, h4"] --> C1
    B --> C2
    B --> C4[("chunk h4")]`} />
</Figure>

**Worked numbers.** A 500 MB file in 4 MB chunks is 125 chunks. A second user with the same file: all 125 hashes already exist, so **no new chunk storage**, one new manifest. Note what did the work: **your chunking layer, not the object store.** S3 does not deduplicate identical objects for you. Two PUTs of the same bytes are two billed objects.

| | Fixed-size chunking | Content-defined chunking |
|---|---|---|
| Boundaries | Every N bytes | Where a rolling hash of the content hits a pattern |
| Edit in place (same length) | One chunk changes | One chunk changes |
| **Insert** one byte at the start | Every later boundary shifts: all 125 chunks change | Boundaries move with the data: about 1 or 2 chunks change |
| Cost | Trivial | CPU for the rolling hash, variable chunk sizes |

rsync's rolling checksum and modern backup tools use the content-defined family of ideas.

**Deleting shared chunks** needs **reference counting** (decrement on manifest delete, delete the chunk at zero, carefully, because a concurrent upload may be about to reuse it) or periodic **mark-and-sweep** garbage collection over all live manifests. Most designs pick GC with a grace period, because refcounts drift under failures.

### The privacy caveat: say it unprompted

Suppose the client sends hashes first and the server answers "already have it" **for chunks stored by anyone**:

- **Existence leak.** An attacker who suspects someone holds a specific file (a leaked document) hashes it, "uploads" it, and watches whether the bytes were needed. For files with a small unknown part (a form letter with a PIN), they can try every variant.
- **Access hole.** If "already have it" links the chunk into the requester's account on the hash alone, **knowing a hash becomes enough to download the file.** A hash is not proof of possession.

Mitigations: **dedup only within a user or tenant** (much of the savings in many workloads, none of the cross-user leak). **Dedup server-side** after receiving the bytes, so the client cannot observe it (saves storage, not upload bandwidth). Or a **proof-of-ownership** step. Encrypting content per user removes cross-user dedup entirely; that is the trade.

**Pastebin flavour.** Key the paste body by `sha256(content)`: two identical pastes share one object, two metadata rows. But **never use the hash as the public paste id**: anyone could compute the URL of a paste whose text they can guess, and identical "private" pastes would share a URL. Public id: random. Storage key: hash.

<Trace title="Name it by its content" steps={dedup} takeaway="Hash the chunk, store it once, sync only what changed, and remember that a visible dedup answer is a side channel." />

<Reveal q="Why SHA-256 and not a fast hash like CRC32 or MD5 for chunk identity?">

Identity must survive adversaries, not just accidents. CRC32 has only 32 bits, so accidental collisions are routine at billions of chunks. MD5 collisions can be manufactured on purpose, which would let an attacker make two different chunks share an identity. SHA-256 has no known practical collisions.

Use fast checksums (CRC32C) for transport integrity, and a cryptographic hash for identity.

</Reveal>

<h2 id="tiers">Chapter 8 · Storage classes and cost</h2>

**The problem.** Finance forwards the storage invoice: "Is this right?" It is. A photo app has three years of photos, sixteen petabytes, all in the default storage class. Access logs show photos older than a month get almost no views, and older than a year, nearly none. The company is paying front-row prices for an attic.

**Storage classes** trade the price of keeping bytes against the price and speed of reading them. Names below are S3's. Other clouds have close equivalents. **Prices and rules change. The relative magnitudes are what to carry; check current price sheets.**

| Class (S3 name) | Storage price vs Standard | Read | The catch |
|---|---|---|---|
| **Standard** | 1 | Milliseconds | None. The default for anything hot |
| **Standard-IA** (infrequent access) | about ½ | Milliseconds | Per-GB retrieval fee, 30-day minimum billed duration, objects billed as at least 128 KB |
| **One Zone-IA** | a bit below IA | Milliseconds | One availability zone: lost if that zone is lost. Only for re-creatable data (thumbnails you can regenerate) |
| **Glacier Instant Retrieval** | about ⅙ | Milliseconds | Higher retrieval fee, 90-day minimum |
| **Glacier Flexible Retrieval** | lower still | Minutes to hours (restore first) | Must restore before reading, 90-day minimum |
| **Glacier Deep Archive** | about 1/20 or less ($0.00099 vs $0.023 per GB-month, first 50 TB, is about 1/23 in AWS us-east-1 list prices, price list dated 2026-10-15) | Hours | 180-day minimum. For compliance and "just in case" |
| **Intelligent-Tiering** | moves objects for you | Milliseconds for the frequent and infrequent tiers | Small per-object monitoring fee, tiny objects are not tiered |

**Lifecycle rules** move or delete objects automatically by age (filtered by prefix, tag or size): *"after 30 days → Standard-IA. After 365 days → Glacier Instant Retrieval. Abort incomplete multipart uploads after 7 days. Delete `tmp/` after 1 day."*

  <Mermaid code={`flowchart LR

    S -->|"day 30"| IA["Standard-IA\n30 to 365 days\nprice about 0.5"]

**Worked numbers (assumption for this example: 15 TB of new photos a day).** 5M uploads × 3 MB (a 2 MB original plus about 1 MB of renditions) = 15 TB a day, 5,475 TB a year, 16,425 TB after three years. Relative prices 1 : ½ : ⅙.

```text
Standard  (last 30 days)        15 TB × 30  =    450 TB × 1   =    450 units
Standard-IA (days 30–365)       15 TB × 335 =  5,025 TB × 1/2 =  2,513 units
Glacier IR (older than a year)  16,425 − 5,475 = 10,950 TB × 1/6 = 1,825 units
Tiered total                                                    ≈ 4,788 units
All Standard                    16,425 TB × 1                   = 16,425 units
                                → tiered ≈ 29% of the bill, about 3.4× cheaper per month
```

### The fees that eat the savings

- **Retrieval.** Cold classes charge per GB read. If old photos are actually viewed (a "this day three years ago" feature), retrieval can cost more than you saved. The **CDN absorbs repeat reads** of the same object, which helps.
- **Minimum size.** Standard-IA bills each object as at least 128 KB. A 20 KB thumbnail is billed at 6.4× its size, at about half the price (Standard-IA is $0.0125 vs $0.023, so 54%, in us-east-1 list prices, October 2026): roughly **3.2× to 3.5× more** than leaving it in Standard. Keep tiny objects in Standard (or pack them). (Since September 2024, S3 lifecycle rules do not transition objects under 128 KB by default. You need an object size filter to force it.)
- **Minimum duration.** Delete an IA object after 10 days and you still pay for 30.
- **Transition requests.** Lifecycle transitions are billed per object. Moving billions of tiny objects costs real money.

When the access pattern is unknown, **Intelligent-Tiering** moves objects between tiers by observed access, for a small monitoring fee per object.

### Other cost levers

Storage is often not the biggest line. Check these too (all provider-dependent; look at the current price sheet):

| Lever | Why it matters | What to do |
|---|---|---|
| **Egress** (data transferred out to the internet) | Per-GB cost often exceeds storage cost for popular media | Serve through a CDN. A high **byte** hit ratio cuts origin egress, and CDN per-GB rates are usually lower and negotiable at volume |
| **Request fees** | GET, PUT and LIST are billed per thousand. Billions of tiny objects make this large | Pack tiny objects, avoid LIST on request paths, let the CDN absorb repeat GETs |
| **Cross-region and cross-zone transfer** | Replicating or reading across regions is billed per GB | Keep processing in the bucket's region, replicate only what needs it |
| **Right-size renditions** | Every extra rendition is stored forever | Generate lazily (Chapter 16), delete unused variants, serve modern formats (WebP, AVIF) |
| **Delete what is dead** | Orphans, abandoned multipart parts, old versions | Lifecycle rules for incomplete uploads and noncurrent versions, the sweeper from Chapter 5 |
| **Dedup and compression** | Fewer bytes stored | Chapter 7. Compress text-like blobs, but photos and video are already compressed |

<Trace title="Read the bill" steps={tiers} takeaway="Price bytes by how long they stay hot. Lifecycle rules do the moving. Minimum sizes, minimum durations and retrieval fees decide whether it pays." />

**A common slip:** "Move everything older than 30 days to Glacier." Glacier Flexible Retrieval and Deep Archive need a **restore** before reading, minutes to hours. A user tapping an old photo cannot wait hours. Pick an instant-retrieval tier for anything users can still open, and say the minimum-size and retrieval caveats.

<h2 id="cdn">Chapter 9 · How a CDN works</h2>

**The problem.** A user in Jakarta opens the app. The feed JSON arrives quickly, then ten grey squares sit there for two seconds before photos fill in one by one, each image crossing an ocean to a bucket in Virginia. One origin region is far from most users.

A **CDN** (content delivery network) is a global fleet of reverse proxies, called **points of presence (PoPs)** or edges, that cache HTTP responses close to users. The machine you own and the CDN reads from is the **origin**: here, the object store. How a phone reaches its nearest PoP (GeoDNS or anycast), and what a CDN does for uncacheable API traffic (terminating TLS nearby, reusing warm connections to the origin), is in <a href={`${BASE}sd/lessons/networking/`}>Networking</a>. This chapter is about the bytes.

**How a request flows.**

1. The phone requests `https://cdn.example.com/photos/7f3a/w640.jpg`. DNS or anycast routes it to the nearest PoP.
2. The PoP looks up the **cache key** (Chapter 10). **Hit and still fresh**: it answers immediately.
3. **Miss, or stale**: it fetches from the origin (or from a shield, Chapter 13), stores the response according to its `Cache-Control` headers, and answers.
4. The next user near that PoP gets a hit.

**Pull vs push:**

| | Pull CDN (the default) | Push / pre-positioning |
|---|---|---|
| How | Edge misses, fetches from origin, caches per the response's headers | You upload or pre-warm content to the edge ahead of demand |
| Like | Cache-aside, at the edge | Write-through, at the edge |
| Good for | Almost everything: photos, assets, segments, the long tail | Big, predictable releases: a game patch at 10:00, a season premiere |
| Cost | First request per PoP is slow, misses spike under purges | You manage what goes where, and pay to store things nobody may request |

Video giants run the push model at enormous scale: Netflix's Open Connect, for example, publicly describes filling its caching appliances with predicted-popular titles during off-peak hours.

**The arithmetic.** It is the cache rule from Caching again, with bytes: **origin egress = (1 − h) × total egress**.

**Worked numbers (assumptions from Estimation).** 500M feed opens a day × 10 images × 200 KB = 1 PB/day, 10 GB/s average, **30 GB/s (240 Gbps) at peak**.

| CDN hit ratio | Origin egress at peak | Note |
|---|---|---|
| 90% | 3 GB/s | Still a very busy origin |
| 95% | 1.5 GB/s | The estimation lesson's assumption |
| 99% | 0.3 GB/s | 5× less than at 95%. The last points matter most |

**Request hit ratio is not byte hit ratio.** 990 thumbnail hits of 20 KB and 10 video-segment misses of 4 MB: 99% of requests hit, but only 19.8 MB of 59.8 MB came from cache, a **33% byte hit ratio**. Origin bandwidth and your egress bill follow bytes. Origin request load follows requests. Track both.

    U1["Phones in Jakarta"] --> E1["PoP Jakarta"]
    U2["Phones in Lagos"] --> E2["PoP Lagos"]
    U3["Phones in Lima"] --> E3["PoP Lima"]
    E1 -->|"miss"| O[("Origin\nobject storage")]
    E2 -->|"miss"| O
    E3 -->|"miss"| O`} />
</Figure>

**What to put on a CDN:** static assets, always. Images and video segments, always (at the serving layer, a video platform is largely a CDN with a transcoding pipeline behind it). Public, identical-for-everyone pages and API responses, sometimes, with short TTLs. **Per-user, authenticated API responses, rarely**: they cannot be shared between users. Say so if asked, and say what the CDN does for them anyway (TLS termination near the user).

<h2 id="cache-keys">Chapter 10 · Cache keys</h2>

**The problem.** The CDN dashboard says the hit ratio for images is 61%. It should be well above 90%, because the photos never change. Sampling the logs shows the same photo requested as `?w=400&h=300`, as `?h=300&w=400`, and with a marketing tag appended by the email team. The CDN is not wrong. It was told these are three different things.

The **cache key** is promise number one at the edge: what exactly makes two requests "the same"? The defaults differ by vendor (checked 2026-10-19 in each vendor's docs). **Cloudflare** keys on the full URL (scheme, host, path and the **full query string**, compared as strings), plus a few headers such as `Origin`. **Fastly** hashes the URL (path and query string) and the Host header, and ignores the HTTP method and whether the request came over TLS. **Amazon CloudFront** keys on only the distribution's domain name and the URL path: query strings, headers and cookies are left out until you add them in a cache policy. Check which one you run. Every difference that does not change the response is a wasted miss.

**Normalise the key:**

- **Sort query parameters** so order does not matter.
- **Allow-list the parameters that change the response** (`w`, `h`, `fmt`) and drop everything else (`utm_*`, click ids, cache-busters you did not mean).
- **Keep auth out of the key.** Signature parameters on signed URLs (Chapter 14) are unique per user. If they are in the key, every user is a miss.
- **Lowercase and canonicalise** where your origin treats variants the same.

**`Vary` adds request headers to the key.** `Vary: Accept-Encoding` is normal (a gzip copy and a Brotli copy). `Vary: User-Agent` or `Vary: Cookie` shards the cache into thousands of near-empty slices. If the response genuinely differs by device or format, map the header into a **few buckets** at the edge and key on the bucket (Chapter 16).

**Cookies and `Authorization`.** By the HTTP caching rules (RFC 9111), a shared cache must not reuse a response to a request carrying `Authorization` unless the response explicitly allows it (`public`, `s-maxage` or `must-revalidate`). Cookies are not in the default cache key for CloudFront (it uses only domain and path), Fastly (URL and Host) or Cloudflare (full URL plus a few headers), and each vendor has its own rules for caching responses that set cookies, so check yours. Serve public images from a **cookieless domain or path** so they cache cleanly.

| Request | Default key (string compare) | Normalised key |
|---|---|---|
| `/p/7f3a.jpg?w=400&h=300` | one entry | `/p/7f3a.jpg?h=300&w=400` |
| `/p/7f3a.jpg?h=300&w=400` | a second entry | same entry |
| `/p/7f3a.jpg?h=300&w=400&utm_source=mail` | a third entry | same entry (utm dropped) |

<Trace title="What makes two requests the same?" steps={cacheKeys} takeaway="The cache key is a promise: only what changes the response belongs in it. Sort, allow-list, and never Vary on a high-cardinality header." />

**A common slip:** blaming the TTL for a low hit ratio. With immutable images, a low hit ratio is almost always **key fragmentation** (query strings, Vary, cookies) or a long tail. Look at the keys first.

<h2 id="headers">Chapter 11 · TTLs and versioned URLs</h2>

**The problem.** Release night: the web team ships a fix for a checkout bug. Half an hour later, support still gets the bug reported. The CDN has `app.js` with a one-day TTL, and so does every browser that loaded the page today. Purging the CDN is easy. Purging browsers is not possible. So the real fix is to design so you never need to.

Promise number two is **how long, and who**. The origin says it in the `Cache-Control` response header. <a href={`${BASE}sd/lessons/caching/`}>Caching</a> introduced it. Here is the edge-level detail:

| Directive | Meaning | Use it for |
|---|---|---|
| `max-age=N` | Fresh for N seconds, in browsers **and** shared caches | The default lifetime |
| `s-maxage=N` | Fresh for N seconds in **shared caches only** (CDNs, proxies). Overrides `max-age` there | Long at the edge (purgeable), short in browsers (not purgeable) |
| `public` | Any cache may store it, even for authenticated requests | Public assets fetched with credentials |
| `private` | Only the browser may store it, **never the CDN** | Per-user responses |
| `no-cache` | **May** be stored, but must be revalidated before every use | HTML entry points that must always be current |
| `no-store` | Must not be stored anywhere | Sensitive data |
| `immutable` | Will not change while fresh: browsers that honour it skip revalidation on reload (RFC 8246) | Fingerprinted assets |
| `stale-while-revalidate=N` | Serve stale for up to N s while refreshing in the background (RFC 5861) | Smoothing refreshes |
| `stale-if-error=N` | Serve stale for up to N s if the origin errors (RFC 5861) | Riding out origin outages |

Some CDNs also read their own header (`CDN-Cache-Control`, standardised in RFC 9213, or vendor-specific ones) so you can steer the edge without touching what browsers see.

**`no-cache` vs `no-store`** is a frequent mix-up. `no-cache` does not mean "do not cache". It means "cache it, but ask the origin before using it". `no-store` means "do not keep it at all".

**Revalidation is cheap.** When a cached copy goes stale, the cache asks the origin "has it changed?" with `If-None-Match: "etag"` (or `If-Modified-Since`). If not, the origin answers **304 Not Modified** with no body. Validators turn expiry from "refetch everything" into "a tiny round trip".

```http
GET /app.js HTTP/1.1
If-None-Match: "9f3ab2"

HTTP/1.1 304 Not Modified
ETag: "9f3ab2"
Cache-Control: public, max-age=60
```

### Invalidation vs versioned URLs

There are two ways to make users see new content. They differ in who does the work:

| | Invalidate (purge) | Versioned (fingerprinted) URL |
|---|---|---|
| Idea | Keep the URL, tell caches to drop their copy | Change the URL whenever the content changes |
| Reaches browsers? | No, CDN only | Yes, a new URL is a new cache key everywhere |
| Speed | Seconds to minutes, varies by CDN | Instant: the HTML names the new URL |
| Failure mode | Forgotten purge, partial purge, refill storm | HTML cached too long, still pointing at old URLs |
| Best for | Content that must disappear or change in place | Everything you control the URL of: JS, CSS, images, avatars |

**Fingerprinted URLs design the invalidation problem away.** Put a hash of the content in the file name: `app.9f3ab2.js`, `avatars/7f3a9c.jpg`. Serve it with `Cache-Control: public, max-age=31536000, immutable`. A deploy publishes **new URLs**. The HTML (served with `no-cache` or a short TTL) points to them. Old URLs stop being requested and age out. Nothing is purged, nothing is stale. It also works for user content: a new avatar is a new key and the profile row points at it.

  <Mermaid code={`flowchart LR
    H["index.html\nno-cache"] --> A1["app.9f3ab2.js\nmax-age 1 year, immutable"]
    H --> A2["styles.c41d07.css\nmax-age 1 year, immutable"]
    D["Deploy"] -->|"new build"| H2["index.html now names\napp.e81b44.js"]

<h2 id="purge">Chapter 12 · Invalidation</h2>

**The problem.** Legal calls on a Friday afternoon: a photo must come down now. The row is marked deleted and the object is deleted, yet the photo still loads from the CDN for anyone with the link. An engineer hits purge. Ninety seconds later it is gone from the edge. Twenty minutes later someone still has it on screen, from their own browser cache.

Promise number three: **how the edge learns the truth changed**. Fingerprinted URLs avoid the question for content that is replaced. For content that must **disappear** or change in place, you purge:

- **By URL**: exact objects. **By prefix or wildcard**: where supported. **By tag**: the origin labels responses with tags (Fastly calls them surrogate keys; Cloudflare and CloudFront have cache tags too), and one call purges everything carrying a tag, like "every image of user 42".
- **Latency varies widely by CDN**, from well under a second to several minutes (Fastly advertises "150 ms instant purge" on its caching page, a marketing figure checked 2026-10-19, not a guarantee), and some charge per purge path beyond an allowance (CloudFront: the first 1,000 paths a month are free, and a path with a `*` wildcard counts as one). Check yours, and do not design a correctness guarantee around a purge.
- **Purge only clears the CDN.** Browsers and apps that already hold a copy keep it until their `max-age` runs out. For content that might have to vanish (private photos, anything takedown-prone), keep **browser TTLs short** and use `s-maxage` for the edge, or serve it through **expiring signed URLs** (Chapter 14) so even a leaked link dies.
- **A purge is a mass expiry.** Purge a hot object at 200 PoPs and you get up to 200 near-simultaneous origin fetches, more if PoPs do not collapse concurrent misses. It is a cache stampede at continental scale. The origin shield (next chapter) is the fix.

**Soft purge** (supported by some CDNs) marks the object stale instead of removing it, so the edge can keep serving it while it revalidates in the background. It trades a short staleness window for no refill storm.

<Trace title="Make it disappear" steps={purge} takeaway="Purge reaches the CDN, not browsers, and it causes a refill burst. Prefer new URLs for changes. Plan short browser TTLs for anything that may have to vanish." />

**A common slip:** "We'll purge the CDN when content changes" as the whole invalidation story. Say what reaches the browsers, how long the purge takes, and what the origin sees afterwards.

<h2 id="shield">Chapter 13 · Origin shield and hot objects</h2>

**The problem.** A celebrity posts a photo at 20:00. By 20:01 it is the most requested object the service has ever served: fifty thousand requests a second from every continent. The CDN holds, but the origin graph jumps anyway. The photo is new, so every PoP misses at once, and some PoPs miss several times before their first fetch returns. The object store's error rate ticks up: throttling, on one key.

Promise number four: **the failure plan**. At the edge, that means the hot new object and the refill storm.

- **Request collapsing (coalescing).** When many requests miss on the same key at the same PoP, one goes to the origin and the rest wait for its response. It is the per-key lock from Caching's stampede chapter, done by the CDN.
- **Origin shield / tiered caching.** PoPs do not miss to the origin. They miss to a **regional or shield cache**, which misses to the origin. 200 PoPs become one (or a few) origin fetchers per object. It also raises the effective hit ratio, since a PoP's miss is often the shield's hit.
- **Long TTLs on immutable URLs**, so a hot object is fetched about once per shield per TTL.
- **`stale-while-revalidate` and `stale-if-error`**, so a refresh or an origin hiccup never turns into user-visible errors.
- **Pre-warming** for predictable spikes (a scheduled launch): request the objects through the shield before the crowd arrives.

<Figure caption="Tiered caching. Each layer collapses concurrent misses, so a burst of 50,000 requests a second becomes one origin fetch.">
  <Mermaid code={`flowchart LR

    U --> P2["PoP 2"]
    U --> P3["... PoP 200"]
    P1 -->|"collapsed misses"| SH["Origin shield\nregional cache"]
    P2 --> SH
    P3 --> SH
    SH -->|"one fetch"| O[("Origin\nobject storage")]`} />
</Figure>

**Why not serve hot objects straight from the store?** One key lives in one partition of the store's key space. AWS documents at least 5,500 GETs a second per prefix, and scaling up takes time, during which a store returns throttling errors (S3's `503 Slow Down`). Fifty thousand requests a second for one key, direct, invites exactly that, and every viewer pays the full distance to one region. Behind a shield, the store sees roughly one request per TTL.

<h2 id="private">Chapter 14 · Signed URLs for private content</h2>

**The problem.** A product team launches paid video lessons that only buyers can watch, and wants them fast. The speed is at the edge, so the permission check has to happen at the edge. How does a cache in Lagos know who paid, without calling home on every request?

**Signed CDN URLs and signed cookies** carry the same idea as presigned URLs, checked at the edge. Your API checks the purchase, then gives the client a signature over a **policy**: which resource (one URL or a path pattern like `/courses/42/*`), until when, and optionally from which IP range. The edge verifies the signature with a key you registered with it (a public key, or a shared secret on some CDNs) and serves from cache. No call home.

- **Signed URL**: one resource. Good for a single download.
- **Signed cookie**: a path pattern. Good for **many files**. A 2-hour HLS video in 6-second segments is 7,200 ÷ 6 = **1,200 segments per rendition**. Signing each segment URL would mean a per-user playlist. One cookie covers them all and the playlists stay shared and cacheable.
- **Keep signatures out of the cache key.** Every user's signature is unique. If it is in the key, the hit ratio is zero. Check how your CDN handles its own signing parameters.
- **Lock the origin.** If the bucket is publicly readable, the signature check is a door in a wall with no wall. The origin should accept requests **only from the CDN**: for example CloudFront's origin access control on an S3 bucket, or a secret header the origin requires.
- **Expiries** are short for downloads (minutes) and session-length for streaming. A leaked link dies on its own.

| | Presigned URL (store) | Signed URL or cookie (CDN) |
|---|---|---|
| Checked by | The object store | The CDN edge |
| Served from | Origin, every time | Cache, so fast and cheap on repeat |
| Good for | Uploads, rare private downloads | Private content read many times |
| Key set up with | Your storage credentials | A key pair registered with the CDN |

<h2 id="video">Chapter 15 · Video: ranges, chunks, adaptive bitrate</h2>

**The problem.** A 2-hour concert video. A viewer on a train drags the playhead to 41:10, goes through a tunnel, then comes out with one bar of signal. The video keeps playing, blurrier for twenty seconds, then sharp again. How does that work with nothing but files and HTTP?

**Range requests.** HTTP lets a client ask for part of an object: `Range: bytes=0-1048575` (the first MiB). A server that supports it answers **`206 Partial Content`** with a `Content-Range` header (and advertises `Accept-Ranges: bytes`).

```http
GET /video.mp4 HTTP/1.1
Range: bytes=1048576-2097151

HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/734003200
Accept-Ranges: bytes
```

This powers seeking in a progressive download, resuming a broken download, and parallel downloads of big files. Object stores and CDNs support ranges. How a CDN caches them varies (some fetch the whole object on a range miss, others fetch and cache it in slices), so check yours for very large files.

**Segmented streaming (HLS and DASH)** goes further. At upload, the video is transcoded into a **ladder** of renditions (say 1080p at about 5 Mbps down to 360p at under 1 Mbps). Each rendition is cut into **segments** of a few seconds (commonly 2 to 6 s). A **manifest**, an `.m3u8` playlist for HLS or an `.mpd` file for DASH, lists the renditions and their segments.

- The player downloads the manifest, picks a rendition from its **measured bandwidth**, and fetches segments one by one.
- **Adaptive bitrate**: segments of every rendition line up in time, so at any segment boundary the player can switch up or down. That was the train tunnel.
- **Seeking** is arithmetic: 41:10 = 2,470 s. With 6-second segments, ⌊2,470 ÷ 6⌋ = **segment 411**, covering 2,466 to 2,472 s.
- Each segment is a **small, immutable file**: 6 s at 5 Mbps = 30 Mb = **3.75 MB**. Perfect CDN material: long TTLs, high hit ratios on popular videos.

| | Range request on one MP4 | Segmented HLS/DASH |
|---|---|---|
| Unit | Byte range of one big file | Small separate files |
| Quality switching | No (one bitrate) | Yes, at each segment boundary |
| CDN friendliness | Depends on how the CDN caches ranges | Excellent: plain small immutable GETs |
| Good for | Downloads, short clips, simple video tags | Long video, mobile networks, live |

**TTLs for video:** segments are long (they never change). **VOD manifests** are long (a finished video's playlist does not change). **Live manifests** are very short, about a segment duration or less, because a new segment is appended every few seconds. The segments themselves are still long-lived.

<h2 id="image-edge">Chapter 16 · Image variants</h2>

**The problem.** An avatar appears in comment threads, profile headers, notifications, share cards, and at three screen densities. Product wants each one crisp and small. The pipeline makes one thumbnail. Do you pre-generate forty files per user, or generate each one the first time someone needs it?

| | Pre-generate at upload | Transform at the edge, on demand |
|---|---|---|
| How | The processing job writes a fixed set of renditions | The URL says what is wanted (`/img/7f3a.jpg?w=320&fmt=webp`). The edge or an image service resizes from the original on a miss and caches the result |
| Storage | Every variant for every image, even never-viewed ones | Only variants someone requested (cached, often not stored permanently) |
| New size next quarter | Backfill billions of images | Just request it |
| Risk | Wasted storage | Unbounded variants, CPU on misses |

Many CDNs offer image transformation. You can also run a small resizing service behind the CDN. Either way, **bound the inputs**:

- **Allow-list widths** (say 160, 320, 640, 1080) and snap anything else to the nearest. An open `w=` parameter lets anyone request w=1 through w=4000: thousands of uncached variants, each costing a resize.
- **Format negotiation without key explosion.** Browsers advertise AVIF/WebP support in the `Accept` header, but raw `Accept` strings vary across browsers and versions. Map `Accept` into a **format bucket** (avif, webp, jpeg) at the edge and put the bucket in the cache key: **4 widths × 3 formats = at most 12 variants** per image.
- **Sign transformation URLs** if variants are expensive, so only your pages can request them.

<Trace title="Bound the variants" steps={images} takeaway="Generate variants lazily at the edge, but only from an allow-list: a fixed set of widths and a few format buckets in the cache key." />

**A common slip:** "We resize on the fly" with no limit. The interviewer hears "unbounded cache key and unbounded CPU". Say the allow-list.

```text
Egress       10M × 10 KB = 100 GB/day ÷ 10⁵ ≈ 1 MB/s avg (exact 1.16) → 3 MB/s peak ≈ 24 Mbps
                                                                              → bandwidth is NOT the driver
Dedup        if 10% of pastes are exact duplicates: saves ≈ 0.37 TB/year      → nice, not decisive
```

**Conclusions.** The split is justified by the **size tail** and a **lean metadata database**, not by bandwidth. The paste body is immutable, so it is served by a **CDN with a long TTL**, keyed by the content hash, with the public id random (Chapter 7).

**Expiry:** the metadata row carries `expires_at` and reads check it, so an expired paste returns 404 instantly. A sweeper deletes the object later (or store bodies under per-retention prefixes such as `exp-7d/` with matching lifecycle rules, because lifecycle rules filter on prefix, tag and age, not on a date in your database). And the CDN TTL must never outlive the paste: cap `s-maxage` at the time remaining, and purge on early delete.

**Photo sharing.** Assumptions: 50M DAU, 5M uploads a day, 2 MB original plus about 1 MB renditions, 500M feed opens × 10 images × 200 KB, peak 3× (the numbers from the estimation lesson, now with this lesson's levers).

```text
Uploads in   5M × 2 MB = 10 TB/day → 100 MB/s avg → 300 MB/s peak = 2.4 Gbps → presigned, multipart for video
Storage      5M × 3 MB = 15 TB/day → 5.5 PB/year logical
             self-run: × 3 replicas ≈ 16.5 PB raw  vs  RS(10, 4) × 1.4 ≈ 7.7 PB raw
Tiering      after 3 years, Standard → IA → instant archive ≈ 29% of the all-Standard bill
Egress       1 PB/day → 10 GB/s avg → 30 GB/s (240 Gbps) peak                → CDN, no question
Origin       hit ratio 95% → 1.5 GB/s peak;  99% → 0.3 GB/s                  → fingerprinted URLs, shield
App tier     upload requests: 150/s peak × 5 ms ≈ 1 thread; no bytes          → stateless, small
```

<h2 id="interview-script">Say it in the room</h2>

The interviewer has drawn a phone and a feed: "Users upload profile pictures and photos, and everyone sees them. How do the bytes work?" Do not draw an arrow from the phone to the API for the bytes.

<AnswerModes id="blob-upload-and-serve" q="Design the media path: upload, store and serve photos and video at scale.">
  <Fragment slot="short">

Bytes never touch the app tier. Each photo is a metadata row (owner, server-chosen key, size, hash, status) plus an object in object storage. The client gets a short-lived presigned PUT (multipart for video), uploads directly, and an idempotent event handler plus a sweeper moves the row from pending to active after validation. Serving goes through a CDN with fingerprinted immutable URLs and an origin shield. Private files use signed URLs.

  </Fragment>
  <Fragment slot="medium">

Metadata and bytes are separate. The row in Postgres holds id, owner, **server-chosen storage key**, size, SHA-256, status. The bytes are in object storage.

**Upload.** The API authorises, inserts a `pending` row, and returns a **presigned PUT**: one key, 15-minute expiry, content type pinned. The client sends a checksum and the store verifies it. Video uses **multipart** with 8 MB parts so a drop costs one part. The store's object-created event, and a sweeper for missed events, triggers async processing: validate the real type, strip EXIF, make renditions, then flip the row to `active`.

**Serve.** About 30 GB/s at peak, so a **CDN** with an origin shield sits in front of the store. Objects are **fingerprinted** with `max-age=31536000, immutable`, so a new avatar is a new key and we never purge for updates. The cache key allow-lists width and format. At a 95% hit ratio the origin sees 1.5 GB/s, at 99% 0.3 GB/s.

  </Fragment>
  <Fragment slot="deep">

Everything in the medium answer, plus the numbers and failure plans.

**Storage.** About 15 TB a day, 5.5 PB a year. The managed store erasure-codes internally. Versioning protects against our own deletes. Lifecycle rules move photos to infrequent access after 30 days and an instant-retrieval archive after a year, under a third of the all-hot bill (watch minimum sizes and retrieval fees). Abandoned multipart uploads are aborted by a lifecycle rule.

**Consistency.** The DB and the store have no shared transaction, so every step is idempotent and ordered so failures leave orphans, never dangling pointers. Deletes mark the row first, then remove objects asynchronously.

**Edge.** Request collapsing at PoPs and a shield make a viral object one origin fetch. `stale-if-error` rides out origin errors. Private photos use signed URLs with short expiry, and the bucket accepts only the CDN. Purge is for takedowns and reaches only the CDN, so private content also gets short browser TTLs. If the CDN fails we degrade (lower resolutions, no autoplay) and, at larger scale, fail over to a second CDN.

**Video.** Async transcoding into a bitrate ladder, 2 to 6 s HLS/DASH segments, long TTLs on segments and VOD manifests, very short on live manifests.

  </Fragment>
</AnswerModes>

**Five follow-ups you will get:**

<Reveal q="1 · Why not just proxy uploads through the API? It's simpler.">

Slow clients turn a 2 MB upload into an 8-second request. At 1,500 uploads a second that is 12,000 held threads against a fleet of 5,400, plus every byte crossing our network twice: 48 Gbps through an app tier whose real API traffic is 2.4 Gbps. Presigned uploads cost us about 5 ms per upload instead.

</Reveal>

<Reveal q="2 · The upload finished but the event got lost. What does the user see?">

The row stays `pending`, so the photo does not appear yet. The handler is idempotent and is triggered by both the store's event and the client's "done" call. A sweeper reconciles pending rows older than the URL expiry by HEADing the key: process it if it exists, expire the row if not. Events are at-least-once, so duplicates are harmless.

</Reveal>

<Reveal q="3 · A user changes their avatar. How does everyone see the new one?">

The new avatar gets a **new key**, and the profile row points to it. Old URLs are not invalidated. They are simply no longer referenced, and they age out. No purge, no stale browser caches. For a takedown, where the old image must vanish, we purge the CDN and rely on short browser TTLs or expiring signed URLs, because a purge cannot reach browsers.

</Reveal>

<Reveal q="4 · A photo goes viral. What protects the store?">

An immutable URL with a long TTL, request collapsing at each PoP, and an origin shield so 200 PoPs become one origin fetcher. One hot key on the store directly would hit its per-prefix request limits and get throttled. Through the CDN it is about one fetch per TTL.

</Reveal>

<Reveal q="5 · Two users upload the same file. Do you store it twice?">

With content-addressed chunks, no: the second upload matches existing hashes and only a manifest is created. But if the client can see "already have it" across users, that leaks whether someone else has the file, and trusting a client-supplied hash as proof of possession would let anyone fetch a file by its hash. So I would dedup within a user or tenant, or server-side after the bytes arrive.

</Reveal>

### Five mistakes to leave behind

1. **Proxying bytes through the API.** Presign, and say the held-connection arithmetic.
2. **Treating the upload as done when the bytes land.** Pending → active, idempotent handler, sweeper.
3. **"We dedup by hash" with no privacy scope.** Per-user, server-side, or proof of possession.
4. **Long TTLs on mutable URLs** (or on the HTML). Long TTLs belong to fingerprinted, immutable URLs.
5. **"Eleven nines, so it's safe."** Durability is not availability, and it is not backup.

**Keep it warm.** With a study partner, do an 8-minute mini-design: "profile picture upload and serving at Instagram scale." Include the presigned upload, the metadata row and its states, a CDN with fingerprinted immutable URLs, and the bandwidth estimate that justifies the CDN. Then do it again for Pastebin and notice which sentences change.

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| Photos, video, files, pastes | Metadata row in the DB + object in storage, server-chosen key |
| "Object vs file vs block?" | Block: DB disks. File: POSIX shared folders. Object: flat key to whole object, cheap, effectively unlimited |
| "The API receives the upload" | Presigned PUT, one key, short expiry. Bytes never touch the app tier |
| Integrity | Client checksum verified by the store, hash in the row. ETag is not a content hash for multipart |
| Large files, mobile networks | Multipart, about 8 MB parts, retry per part, resume by upload id. Abort-incomplete lifecycle rule |
| "When is the upload done?" | `pending → active` via idempotent handler on event + client call, plus a sweeper |
| Deleting | Row first, object async, sweeper for orphans. Purge the CDN if it must vanish |
| Same files, many users; file sync | Content-hash chunks, manifests, dedup, scoped for privacy. Content-defined chunking for inserts |
| "Is S3 consistent?" | Strong read-after-write since Dec 2020 (objects and LIST). Check other stores |
| "11 nines" | Durability, not availability. Erasure coding. Versioning protects against you. S3 Standard's design figure; others differ |
| Storage growing by PB/year | Lifecycle: Standard → IA → instant archive. Mind min size, min duration, retrieval fees |
| Bill is large | Egress first (CDN, byte hit ratio), then requests, cross-region, unused renditions, orphans |
| Global readers, big egress | CDN. Origin = (1 − h) × egress. Watch byte hit ratio |
| Low CDN hit ratio on static content | Key fragmentation: sort and allow-list query params, no Vary on User-Agent/Cookie |
| Deploys or updated media | Fingerprinted URLs + `max-age=31536000, immutable`. HTML `no-cache` |
| Different TTL for edge and browser | `s-maxage` for the CDN, short `max-age` for browsers |
| "Take it down now" | Purge (CDN only) + short browser TTLs or expiring signed URLs |
| Viral object, purge storms | Request collapsing + origin shield + long TTLs + stale-if-error |
| Paid or private media | Signed URLs (one file) or cookies (many segments). Origin locked to the CDN |
| Video | Transcode ladder → HLS/DASH segments. Long TTL segments, short live manifests. Ranges for seeking |
| Many image sizes | Edge transformation from an allow-list of widths × format buckets |
| Pastebin | Hash as storage key, random public id, `expires_at` check, CDN TTL ≤ time left |

- **Signed URL key rotation**: how CDNs let you rotate signing keys without breaking live sessions.
- **Egress pricing and "data transfer out"**: why moving bytes often costs more than storing them, and how CDN contracts change the picture.
