<h2 id="prologue">Prologue · The four promises</h2>

Here is a failure that happens in real systems. A profile service warms its Redis cache at 2:00 AM with a one-hour TTL. At 3:00:00 every one of those keys expires in the same second. Millions of requests miss Redis together and hit MySQL, and the database falls over. Redis looked healthy the whole time.

"We added Redis" is not a design. It says nothing about the thing that went wrong. A cache in a design should answer four questions out loud:

1. **Key shape.** Exactly what string maps to exactly what value.
2. **TTL, and why that number.** How stale an answer you are willing to serve. (TTL means time to live: how long an entry stays before Redis deletes it.)
3. **Invalidation story.** How the cache finds out that the data changed.
4. **Failure plan.** What happens when the cache is cold, down, or stampeded.

A common slip in mock interviews is saying "cache in Redis" with no key shape, no TTL reason and no invalidation strategy. Interviewers mark that down. The four promises fix it.

<h2 id="why-cache">Chapter 1 · The arithmetic of misses</h2>

**What is it?** A cache sits in front of a slower source of truth (here, MySQL) and remembers recent answers. A **hit** means the cache had the answer. A **miss** means it did not, so the request goes on to the database.

**Why do we need it?** Two numbers decide whether a cache helps.

**Latency.** Rough orders of magnitude, as generally accepted rules of thumb: reading main memory takes about 100 ns. A network round trip inside one data centre takes about 0.5 ms. A Redis `GET` in the same data centre is usually well under a millisecond. A database query that touches disk or does real work takes several milliseconds to tens of milliseconds. The cache wins because it skips the work and the disk, not because Redis is magic.

**Hit ratio, h.** The fraction of reads the cache answers.

- **Database load = (1 − h) × read QPS.** The database only sees misses.
- **Average latency ≈ hit latency + (1 − h) × source latency.** Every read pays for the cache lookup. Only misses also pay for the database.

**Assumption for this example:** 200,000 profile reads per second at peak, and a MySQL setup that handles about 20,000 reads per second comfortably.

| Hit ratio | Misses reaching the DB | Average latency (1 ms cache, 10 ms DB) |
|---|---|---|
| 80% | 40,000/s: **overload** | 1 + 0.20 × 10 = 3.0 ms |
| 90% | 20,000/s: at the limit | 1 + 0.10 × 10 = 2.0 ms |
| 95% | 10,000/s: healthy | 1 + 0.05 × 10 = 1.5 ms |
| 99% | 2,000/s: idle | 1 + 0.01 × 10 = 1.1 ms |

The database feels the **miss rate**, not the hit rate. Going from 90% to 99% hits cuts database load **tenfold**. That is why the failure chapters matter. Anything that briefly drops the hit ratio, such as a mass expiry or a restart, multiplies database load.

<Trace title="Do the arithmetic" steps={hitRatio} takeaway="The database sees (1 − h) × QPS. Small changes in hit ratio are huge changes in miss rate." />

**When should I use it?** When reads far outnumber writes and the same keys repeat. Say the read/write ratio and why keys repeat.

**When is a cache the wrong tool?** If the workload is write-heavy, or every read is unique (a search with a random query), the hit ratio will be poor and the cache just adds a network hop.

**Interview takeaway.** "At 200K reads/s against a 20K/s database I need at least a 90% hit ratio, so I will aim for 95% or better."

<h2 id="layers">Chapter 2 · Where caches live</h2>

A single profile request passes through several places that could have remembered the answer. Most real outages in this area are two layers disagreeing about what is true.

<Figure caption="Each layer trades freshness for distance. The further left the answer is found, the faster and the staler it may be.">
  <Mermaid code={`flowchart LR
    B["Browser / app\nHTTP cache"] --> CDN["CDN edge"] --> GW["API gateway\nresponse cache"] --> APP["App server\nin-process L1"] --> R[("Distributed cache\nRedis / Memcached")] --> DB[("Database\nbuffer pool")] --> D[("Disk")]`} />
</Figure>

| Layer | Holds | Typical TTL | Invalidate by |
|---|---|---|---|
| Browser / app | Responses the server marks cacheable (`Cache-Control: max-age`) | Seconds to a year (immutable assets) | Changing the URL (fingerprinted file names) or validators (`ETag`, then `304 Not Modified`) |
| CDN | Static assets, public pages, images, video segments | Minutes to forever | Purge API, versioned URLs, `s-maxage` |
| Gateway | Whole API responses for identical requests | Seconds | TTL. Rarely worth more |
| In-process L1 | Tiny, very hot objects (config, a celebrity profile) | About 1 to 5 seconds | TTL. It can't hear about changes easily |
| Distributed cache | The working set: profiles, sessions, feeds, counters | Minutes to hours | Delete on write, CDC, TTL |
| DB buffer pool | Pages of the database itself | Managed by the DB | Automatic |

"L1" here means the first, smallest cache a request checks, inside the app process. The shared Redis is then the second level.

In an interview, "the cache" almost always means the distributed layer. Mentioning the others when they genuinely help is free credit: "Avatars are immutable and fingerprinted, so they go to the CDN with a one-year max-age and never reach us."

<Reveal q="Why is an in-process L1 cache usually limited to a few seconds of TTL?">

Each app server has its own copy, and the copies don't hear about writes. Delete-on-write would have to reach every server (a pub/sub broadcast). That is possible but adds machinery. A one-second TTL bounds the staleness without any of that. It suits read-mostly hot objects and is wrong for anything a user must see change immediately.

</Reveal>

<h2 id="patterns">Chapter 3 · Who fills the cache?</h2>

**What is it?** There are five common read and write patterns. They look alike. The question that separates them is: **when the data is not in the cache, who loads it? And when someone writes, who updates the cache?**

**Why do we need to know?** Because the choice decides how much code the app owns, how fresh reads are after a write, and what you lose when the cache dies.

### Cache-aside (lazy loading)

The default for about nine designs in ten. The **application** owns all the logic. The cache is a dumb key-value store that knows nothing about MySQL.

```python
import json, redis, pymysql

r = redis.Redis(decode_responses=True)
db = pymysql.connect(db="app", cursorclass=pymysql.cursors.DictCursor)

def get_profile(user_id):
    key = f"v1:profile:user:{user_id}"
    cached = r.get(key)                      # GET key
    if cached is not None:
        return json.loads(cached)            # hit
    with db.cursor() as cur:                 # miss: the APP loads it
        cur.execute("SELECT id, name, bio FROM users WHERE id=%s", (user_id,))
        row = cur.fetchone()
    if row is not None:
        r.set(key, json.dumps(row), ex=900)  # SET key val EX 900
    return row

def update_bio(user_id, bio):
    with db.cursor() as cur:
        cur.execute("UPDATE users SET bio=%s WHERE id=%s", (bio, user_id))
    db.commit()
    r.delete(f"v1:profile:user:{user_id}")   # DEL, never SET (Chapter 5)
```

Only data that is actually read gets cached, so the cache holds the hot set. If Redis is down, the app can still read MySQL. It gets slower, not broken, provided the database can take the load (Chapter 10).

### Read-through

The **cache layer** loads from the database on a miss. The app only ever calls `cache.get(key)`. You give the cache a loader function once.

```python
class ReadThroughCache:
    def __init__(self, redis_client, loader, ttl):
        self.r, self.loader, self.ttl = redis_client, loader, ttl

    def get(self, key):
        v = self.r.get(key)
        if v is None:
            v = self.loader(key)             # the CACHE layer calls the DB
            self.r.set(key, v, ex=self.ttl)
        return v
```

Plain Redis does not do this by itself. Read-through comes from a library or a caching service in front of the store. It is the same flow as cache-aside, with the loading code moved out of the app.

### Write-through

Every write goes to the cache and the database **as one operation**, and the call returns only when both are done. The cache is always warm for data that was just written.

```python
def save_profile_write_through(user):
    with db.cursor() as cur:                       # 1. database first
        cur.execute("UPDATE users SET bio=%s WHERE id=%s",
                    (user["bio"], user["id"]))
    db.commit()
    r.set(f"v1:profile:user:{user['id']}",         # 2. then cache
          json.dumps(user), ex=900)
```

This is a simple sketch, and it has the Chapter 5 race: two concurrent writers can set the cache in the opposite order from their database writes. A real write-through layer serializes writes per key, or uses versions.

### Write-behind (write-back)

Write to the cache only, return immediately, and **flush to the database later**, asynchronously.

```python
def increment_views(post_id):
    r.hincrby("views:pending", post_id, 1)         # fast, in memory only

def flush_views():                                 # runs every few seconds
    pending = r.hgetall("views:pending")
    for post_id, n in pending.items():
        with db.cursor() as cur:
            cur.execute("UPDATE posts SET views=views+%s WHERE id=%s",
                        (int(n), post_id))
        db.commit()
        r.hincrby("views:pending", post_id, -int(n))
```

The write is acknowledged before the database has it. If Redis dies before a flush, those writes are gone. That is acceptable for an approximate view counter and dangerous for user posts or payments.

### Write-around

Writes go **straight to the database and skip the cache**. The cache is filled only by reads. It is the write half of cache-aside without the delete, so a stale copy may remain until its TTL ends or a delete is added. Good for data that is written once and rarely read soon (log records, uploads).

### Who loads data after a miss, and who writes

| Pattern | Who loads on a miss | Who writes on update | Good for | Watch out |
|---|---|---|---|---|
| **Cache-aside** | The **app** reads the DB and calls `SET` | App writes the DB, then `DEL`s the key | The default | First read after a change is a miss |
| **Read-through** | The **cache layer** calls the loader | Usually the app writes the DB and invalidates | Same as cache-aside with less app code | Couples the cache to your data access |
| **Write-through** | Misses still need a loader (read-through or aside) | Cache and DB are written together, synchronously | Read-after-write freshness | Slower writes. Fills with data nobody reads |
| **Write-behind** | Same as write-through | Only the cache is written. A background job flushes the DB | Absorbing write bursts (counters, metrics) | **Data loss** if the cache dies before flushing |
| **Write-around** | A later read misses, then the app loads it | Only the DB is written | Written once, rarely read soon | First read is always a miss. Stale copy if the key was cached earlier |

The pair people confuse most is **cache-aside vs read-through**. In both, a miss ends up in the database. The only difference is who runs that code: your app (aside) or the cache layer (read-through). The other confused pair is **write-through vs write-behind**: both write to the cache first, but write-through waits for the database and write-behind does not.

**Interview takeaway.** "I would use cache-aside: the app reads the DB on a miss and populates Redis. On writes it updates MySQL and deletes the key. I would only use write-behind for data I can afford to lose, like view counters."

<h2 id="invalidation">Chapter 4 · When the data changes</h2>

**What is it?** Invalidation is how a cache learns that a stored value is no longer true.

**Why do we need it?** Say a user edits their bio and an hour later friends still see the old one. If the only mechanism is a one-hour TTL, that is the design working as written. Every cached value is a promise that the data has not changed. Something has to break that promise when it stops being true.

### The three strategies

| Strategy | How | When it's right |
|---|---|---|
| **TTL only** | Entries expire. You accept staleness up to the TTL | Where bounded staleness is fine: public profiles, product pages, rankings |
| **Delete on write** | After the DB write commits, `DEL` the key. The next read repopulates | Default when writes go through your service |
| **Change-data-capture (CDC)** | A consumer reads the database's change log (the MySQL binlog, for example, via Debezium) and deletes affected keys | Many writers: other services, batch jobs, admin scripts touch the same tables |

They are usually combined: delete on write, CDC for writers you don't control, and a TTL as the backstop for everything.

### Delete vs update on write

After a write you can either **delete** the cached key or **update** it with the new value. Delete is the safer default.

| | Delete the key | Update (SET the new value) |
|---|---|---|
| Next read | One miss, then reloaded from the DB | Hit, if the update landed |
| Two racing writers | Cannot install a stale value | Cache can end up holding the older value (Chapter 5) |
| Computing the value | Done by the reader, once, when needed | Done by every writer, even if nobody reads it |
| Failure case | Lost delete leaves the old value until the TTL | Same, and the wrong value may be permanent without a TTL |

Delete is self-healing. The worst case is one extra miss. An update can store a wrong value.

### CDC-driven invalidation

Delete-on-write only works for writes that go through your code. If five other services, a nightly batch and an admin script also write to `users`, any of them can change a row and leave the cache stale.

With CDC, a connector (for example Debezium) tails the MySQL binlog. Every committed change appears as an event, whoever made it. A small consumer turns each event into a `DEL`.

```python
# consumer of change events (for example from a Kafka topic fed by Debezium)
for event in change_events("app.users"):
    user_id = event["after"]["id"] if event["after"] else event["before"]["id"]
    r.delete(f"v1:profile:user:{user_id}")
```

Properties to know:

- It catches **every committed write**, so no writer can forget.
- It fires only **after commit**, so the delete can't happen before the data is visible in MySQL.
- It is **asynchronous**, so there is a small lag. Staleness is bounded by that lag plus the TTL.
- Deletes are idempotent, so processing an event twice is harmless.
- It is another system to run. If your service is the only writer, plain delete-on-write is simpler.

<Trace title="Choose the invalidation" steps={invalidation} takeaway="Delete on write when you own the writes. CDC when you don't. A TTL always, as the backstop." />

### Picking the TTL number

Say it as a business statement: "15 minutes, because a stale bio for 15 minutes hurts nobody, and we delete on the owner's write anyway." For prices or inventory, use seconds, or don't cache the authoritative check at all. Cache the product page and re-check stock at checkout.

**Interview takeaway.** "On writes I delete the key after the DB commit, never update it. A CDC consumer on the binlog covers other writers, and a TTL backstops any lost delete."

<h2 id="races">Chapter 5 · The races</h2>

**What is it?** A race is a bug that only appears when two operations interleave in an unlucky order. Caches have several. They are hard to see because the database is always right and the cache is quietly wrong.

**Why do we need to know them?** They are the main reason a cache serves stale data for hours even though "we delete on write". Each one below names the exact order of events and the fix.

### Race 1: set-after-set (update on write)

If writers `SET` the cache after writing MySQL, their cache writes can arrive in the opposite order to their database writes. The cache ends up holding the loser.

<Figure caption="Writer A’s database write happens first, but its cache write lands last. The cache disagrees with the database until the TTL saves you, if there is one.">
  <Mermaid code={`sequenceDiagram
    participant A as Writer A
    participant B as Writer B
    participant DB
    participant C as Cache
    A->>DB: UPDATE bio = v1
    B->>DB: UPDATE bio = v2
    B->>C: SET bio = v2
    A->>C: SET bio = v1
    Note over DB,C: DB holds v2, cache holds v1`} />
</Figure>

With no TTL, the cache is wrong forever. With delete-on-write this race cannot happen: both writers `DEL`, and the next reader loads the truth.

### Race 2: the read-then-delete race

Even delete-on-write has a gap. A reader misses and reads the old row. Then it stalls (a GC pause, a slow network). Meanwhile a writer commits the new value and deletes the key. The reader wakes up and `SET`s the old value it read earlier.

<Figure caption="The reader’s SET lands after the writer’s DEL, so it re-inserts a value that was already out of date.">
  <Mermaid code={`sequenceDiagram
    participant R as Reader
    participant W as Writer
    participant DB
    participant C as Cache
    R->>C: GET (miss)
    R->>DB: SELECT bio (reads v1)
    W->>DB: UPDATE bio = v2
    W->>C: DEL
    R->>C: SET bio = v1
    Note over DB,C: DB holds v2, cache holds v1`} />
</Figure>

This window is narrow: the reader has to be slower than a database write plus a delete. It is rare, but at high traffic rare events happen daily.

<Trace title="Find the stale value" steps={race} takeaway="Delete-on-write shrinks the window. A TTL bounds it. Leases or versioned writes close it." />

### Race 3: wrong order, delete before the DB write

A frequent mistake is to delete the key first and then update MySQL. Between the two steps a reader misses, loads the old row from MySQL and caches it. Then the writer's update lands. The cache holds the old value, and no later delete is coming.

```text
writer: DEL key
reader: GET miss, SELECT (still the old row), SET old value
writer: UPDATE row (new value committed)
result: cache holds the old value
```

The rule: **update the database first, delete the cache second.** That is why Chapter 3's code orders it that way.

### Race 4: the delete is lost

The DB commit succeeds, then the process crashes or Redis is unreachable before `DEL`. The cache keeps the old value until the TTL ends. Fixes: a TTL backstop, retrying the delete, writing the "invalidate key X" intent to an outbox table in the same MySQL transaction, or CDC, which deletes from the binlog regardless of what the app did.

### Race 5: replica lag

If the reader loads from a MySQL **read replica**, the replica may not have the new row yet. The sequence: writer commits on the primary and deletes the key, a reader misses, reads the lagging replica (old value), and caches it. The cache is stale and the primary is right. Fixes: read from the primary on a cache miss for data that must be fresh, or delay the delete by more than the usual replica lag (see double delete below). Note that CDC on the primary's binlog does not wait for replicas by itself, so it has the same race unless the consumer delays or checks replica lag before deleting.

### How to close the gaps

| Technique | What it does | What it does not do |
|---|---|---|
| **Short TTL** | Bounds the damage. The honest default | Doesn't prevent staleness inside the TTL |
| **Delayed double delete** | Delete after the write. Then delete again after a short delay (say 500 ms to a few seconds) to catch a reader that cached the old value in the gap | Guarantees nothing. A slower reader or bigger replica lag still wins. Describe it as a mitigation |
| **Lease / token** | On a miss the cache hands the reader a token. A delete invalidates outstanding tokens. A `SET` with an invalid token is rejected | Needs cache support (Facebook's memcache leases are the well-known example. In Redis you build it yourself) |
| **Versioned writes** | Store a version with the value. Only overwrite with a newer version | Needs a version from the DB and a compare-and-set |

**Delayed double delete** in code:

```python
def update_bio(user_id, bio):
    key = f"v1:profile:user:{user_id}"
    with db.cursor() as cur:
        cur.execute("UPDATE users SET bio=%s WHERE id=%s", (bio, user_id))
    db.commit()
    r.delete(key)
    schedule(delay_seconds=1, fn=lambda: r.delete(key))  # job queue or timer
```

**Versioned writes.** Add a `version` column to MySQL and increment it on every update (`UPDATE users SET bio=%s, version=version+1 WHERE id=%s`). The reader's cache write is then a compare-and-set that only succeeds if the version is newer. It must run atomically inside Redis, so use a Lua script:

```python
SET_IF_NEWER = r.register_script("""
local cur = redis.call('HGET', KEYS[1], 'v')
if (not cur) or tonumber(cur) < tonumber(ARGV[1]) then
  redis.call('HSET', KEYS[1], 'v', ARGV[1], 'data', ARGV[2])
  redis.call('PEXPIRE', KEYS[1], ARGV[3])
  return 1
end
return 0
""")

def cache_row(row):                      # row includes id and version
    SET_IF_NEWER(keys=[f"v1:profile:user:{row['id']}"],
                 args=[row["version"], json.dumps(row), 900_000])
```

One caveat: if the writer simply `DEL`s the key, the stored version is gone and a stale reader can set the old value again. To close that, the writer does not delete. After committing, it runs the same script with the new version and empty data, plus a short `PEXPIRE` (a few seconds to a minute, longer than your slowest reader). That is a **tombstone**. Readers treat empty data as a miss and reload from MySQL. A stale reader still holding the old version loses the compare-and-set.

Limits of this approach: it needs a version column, every reader must use the hash layout (`HGET` on `data`), and once the tombstone expires a very slow reader could still re-insert an old value. It bounds the problem, it does not remove it. Treat this as a design sketch and test it before relying on it.

**Delete beats update, in one line.** An update can install a stale value if two operations reorder. A delete cannot install anything, so the worst outcome is one extra miss.

### Strong consistency is not on offer

With cache-aside, expect **eventual consistency with bounded staleness**. Anything stronger needs the database in the read path.

<Reveal q="The interviewer asks: 'So is your cache strongly consistent with the database?' What do you say?">

No, and say so plainly. Cache-aside with delete-on-write gives **eventual consistency with bounded staleness**: almost always fresh, stale for at most the TTL in rare races. If a path truly needs the latest value (a balance before a payment, stock at checkout), it reads the database, or uses versioned writes. The cache serves the paths that tolerate staleness. Naming which paths are which is the answer they want.

</Reveal>

**Interview takeaway.** "Update the database first, then delete. Don't SET on write. Racing readers can still re-cache a stale value, so I keep a TTL, and for the strict cases I add versioned writes."

<h2 id="keys">Chapter 6 · Key design</h2>

A bad key scheme causes collisions, impossible invalidation and a hit ratio near zero. Rules that prevent it:

- **Namespace every key.** `profile:user:123` or `feed:user:123:page:1`, not `123`. This prevents collisions between features, allows targeted invalidation and makes debugging humane.
- **Tenant in the key** for multi-tenant systems: `t:42:profile:user:123`. It also stops one tenant's bug from reading another tenant's data.
- **Version prefix** as an escape hatch: `v2:profile:user:123`. When the cached shape changes, bump the version. During a rolling deploy, old code reads `v1:` keys and new code reads `v2:` keys, so neither tries to parse the other's format. Old keys age out by TTL. Without this, half the servers can write shapes the other half can't read.
- **Granularity.** Cache whole objects by default (`profile:user:123` holds JSON). Split into fields (a Redis hash) only when fields change at very different rates or are read separately.
- **Composite results** (a feed page, a search result) are expensive to invalidate precisely. Give them short TTLs, or cache the ids and fetch each item from its own key.
- **Hash tags in Redis Cluster.** The part of a key inside `{...}` decides its slot. Chapter 12 covers when to use them.

**A common trap:** keys built from unbounded user input (a raw search string) create unlimited distinct keys and a near-zero hit ratio. Normalise the input (lowercase, trim, sort filters) and cap what you cache.

**Interview takeaway.** "Keys are namespaced, include the tenant and a schema version, and are built from normalised input so the key space stays bounded."

<h2 id="stampede">Chapter 7 · Stampede and stale-while-revalidate</h2>

**What is it?** Say a popular Redis key expires at 9:00 AM. 10,000 requests ask for it in the next 50 ms. All of them miss Redis, so all 10,000 run the same MySQL query and then all 10,000 `SET` the same value. This is a **cache stampede**.

**Why do we need to fix it?** The database sees a spike exactly when it was relying on the cache. If the query is slow, the pile-up makes it slower, requests time out, and retries make it worse.

Try it. Set the hit ratio to 0, then switch the mitigation (lock, jitter, stale-while-revalidate) and watch how many queries reach the database:

### Fix 1: single-flight (request coalescing) inside one process

Within one app server, make concurrent requests for the same key share a single in-flight database call.

```python
import threading

_inflight = {}                       # key -> (event, result holder)
_lock = threading.Lock()

def single_flight(key, load):
    with _lock:
        entry = _inflight.get(key)
        leader = entry is None
        if leader:
            entry = (threading.Event(), {})
            _inflight[key] = entry
    event, box = entry
    if leader:
        try:
            box["value"] = load()
        finally:
            with _lock:
                del _inflight[key]
            event.set()
    else:
        event.wait()
    return box.get("value")
```

With 200 app servers this reduces 10,000 queries to at most 200, one per server. For one query total, you need a cross-server lock.

### Fix 2: a per-key lock (lease) in Redis

The first request that misses takes a short lock. The others either wait briefly and re-read the cache, or serve a stale copy.

```text
SET lock:profile:42 <random-token> NX PX 3000
```

`NX` means "set only if the key does not exist", so exactly one caller wins. `PX 3000` expires the lock after 3000 ms, so a crashed holder cannot block everyone forever.

```python
import uuid, time

RELEASE = r.register_script("""
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
""")

def get_with_lock(user_id):
    key = f"v1:profile:user:{user_id}"
    lock = f"lock:{key}"
    for _ in range(5):
        cached = r.get(key)
        if cached is not None:
            return json.loads(cached)
        token = uuid.uuid4().hex
        if r.set(lock, token, nx=True, px=3000):      # I won the lock
            try:
                row = load_from_mysql(user_id)
                r.set(key, json.dumps(row), ex=900)
                return row
            finally:
                RELEASE(keys=[lock], args=[token])    # only delete MY lock
        time.sleep(0.05)                              # someone else is loading
    return load_from_mysql(user_id)                   # give up waiting
```

Details that matter:

- **The token** makes release safe. If your load takes longer than 3 s, the lock expires and another process takes it. A plain `DEL` would then delete their lock. The Lua script deletes only if the token still matches.
- **Waiters add latency**, bounded here to about 250 ms before falling back to the database.
- **The lock does not protect correctness.** If it expires mid-load, two loaders may run. That is fine here because the result is idempotent, a cache fill. (This is not the same as a lock guarding money.)

### Fix 3: probabilistic early refresh (XFetch)

Instead of waiting for expiry, each reader may refresh a little early, with a probability that rises as the expiry nears. One reader usually refreshes before anyone sees a miss. No locks are needed.

```python
import math, random, time

def should_refresh(delta, expires_at, beta=1.0):
    # delta: how long recomputing took, stored with the value
    return time.time() - delta * beta * math.log(random.random()) >= expires_at
```

`log(random())` is negative, so the check pushes "now" forward by a random amount. The slower the recompute (`delta`), the earlier it starts. This is the XFetch algorithm. It needs `delta` and the expiry stored with the value.

### Fix 4: jittered TTLs

If a batch of keys is created together with the same TTL, they expire together. Add randomness:

```python
ttl = int(900 * random.uniform(0.9, 1.1))   # 15 min ± 10%
r.set(key, value, ex=ttl)
```

This is free. Always do it. It fixes the avalanche version of the problem (many keys, same second). It does nothing for one popular key.

### Fix 5: stale-while-revalidate (SWR)

**What is it?** Serve the old value immediately while one request refreshes it in the background. Readers never wait for the database.

**Single TTL vs SWR, precisely.** With a single TTL, the key has one deadline. When it passes, Redis deletes the key, and the next request has nothing to serve. With SWR, the entry has **two** deadlines:

- **Soft expiry:** "this value is old enough to refresh." Stored *inside* the value as a timestamp.
- **Hard expiry:** "this value is too old to serve at all." This is the real Redis TTL, set later than the soft expiry.

| | Single TTL | Stale-while-revalidate |
|---|---|---|
| Deadlines | One | Two: soft (inside the value), hard (the Redis TTL) |
| Before the deadline | Serve from cache | Before soft: serve from cache |
| Just after it | Key is gone. Request waits on the database | Between soft and hard: serve the **old value now**, one request refreshes in the background |
| Who waits for the DB | Every request that misses (unless locked) | Nobody, except after hard expiry |
| If the refresh fails | Request errors or retries | Old value keeps being served until hard expiry |
| Cost | Simple | Serves data up to (hard − fresh) seconds old. Needs a wrapper around the value |

Example: soft expiry 10 minutes, hard expiry 15 minutes.

```text
t = 0..10 min    fresh. Serve from cache.
t = 10..15 min   stale. Serve the old value, ONE request refreshes in the background.
t > 15 min       key is gone. Normal miss. Use the lock from Fix 2.
```

```python
def get_swr(user_id):
    key = f"v1:profile:user:{user_id}"
    raw = r.get(key)
    if raw is None:                                   # past hard expiry
        return load_and_store(user_id)                # use the lock from Fix 2
    entry = json.loads(raw)                           # {"data":..., "soft": ts}
    if time.time() > entry["soft"]:                   # past soft expiry
        if r.set(f"lock:{key}", "1", nx=True, px=3000):  # one refresher only
            executor.submit(load_and_store, user_id)  # background thread
    return entry["data"]                              # serve now, stale or not

def load_and_store(user_id):
    row = load_from_mysql(user_id)
    entry = {"data": row, "soft": time.time() + 600}
    r.set(f"v1:profile:user:{user_id}", json.dumps(entry), ex=900)  # hard expiry
    return row
```

HTTP has the same idea for browsers and CDNs: `Cache-Control: max-age=600, stale-while-revalidate=300` means fresh for 600 s, then usable for 300 s more while a refresh happens (RFC 5861).

### Which fix when

| Fix | Prevents | Cost |
|---|---|---|
| Single-flight | Many queries from one server | Per-process only |
| Lock / lease | Many queries across servers | Waiters add latency. Lock needs a timeout and a token |
| SWR | Waiting, and mass recompute | Serves slightly stale data. Two deadlines to manage |
| XFetch | The miss itself | Needs stored recompute time. Probabilistic |
| Jitter | Many keys expiring in the same second | None. Always do it |

The 3 AM incident from the prologue needed two of these: **jitter** (the whole warm-up batch expired in one second) and **a per-key lock or SWR** (a few keys with enormous read volume).

**Interview takeaway.** "On a stampede, one request recomputes while the rest wait or get the stale copy. I use a lock with `SET NX PX` or stale-while-revalidate, and I jitter TTLs so keys don't expire together."

<h2 id="hot-keys">Chapter 8 · Hot keys</h2>

**What is it?** A hot key is one key with extreme read volume. Say a celebrity's profile takes 500,000 reads per second.

**Why is it a problem?** It is a concentration problem, not a capacity problem. A key lives on exactly one shard (one primary), so adding shards or buying bigger machines does not spread its load. That one shard hits 100% CPU while the others idle. A hot key differs from a stampede: the key is cached fine, it just draws more traffic than one Redis node can serve.

**Fixes, first to last:**

- **In-process L1 cache** with about a 1 s TTL on every app server. With 200 app servers, Redis sees about 200 reads per second for that key instead of 500,000. Staleness is capped at one second.

```python
import time

_l1 = {}                                   # key -> (expires_at, value)

def get_hot(key, load_from_redis):
    hit = _l1.get(key)
    if hit and hit[0] > time.monotonic():
        return hit[1]
    value = load_from_redis(key)
    _l1[key] = (time.monotonic() + 1.0, value)
    return value
```

- **Key splitting (replication).** Store copies as `profile:user:123#0` to `#N-1`, which usually hash to different slots (so different shards), and read a random one. Writes (and deletes) must touch all N copies.

```python
N = 8
def read_hot(user_id):
    return r.get(f"profile:user:{user_id}#{random.randrange(N)}")

def invalidate_hot(user_id):
    r.delete(*[f"profile:user:{user_id}#{i}" for i in range(N)])
```

- **Request coalescing** (the Chapter 7 single-flight) so concurrent requests in one server share one fetch.
- **Detect it.** Find hot keys by sampling (`redis-cli --hotkeys` only works when `maxmemory-policy` is an LFU policy) or client-side counters. Say you would monitor for them rather than assume.
- **Client-side caching with server tracking** (Redis 6+): the server tells clients when their locally held keys change. Look it up if you need L1 without waiting out the TTL.

| | L1 in-process | Key splitting |
|---|---|---|
| Reduces load on Redis | Hugely (per app server) | Spreads over N shards |
| Staleness | Up to the L1 TTL | None beyond normal |
| Invalidation | Hard. Rely on short TTL | Delete N keys |
| Extra memory | Per app server | N copies in Redis |
| Best for | Read-mostly, tolerates 1 s stale | Must be fresh, load is huge |

**Interview takeaway.** "Sharding doesn't help a hot key because it lives on one shard. I would put a one-second in-process cache in front, or split the key into N copies."

<h2 id="penetration">Chapter 9 · Penetration and avalanche</h2>

**What is penetration?** Requests for keys that do not exist bypass the cache every time. Say a scraper walks profile ids 1, 2, 3 up to 900 million. Most don't exist. Every request misses Redis, because there is nothing to cache, and lands on MySQL.

**Why is it different from a stampede?** A stampede is about a key that exists and expired. Penetration is about keys that never exist, so no TTL or lock helps. Caching more doesn't help either.

**Fixes:**

- **Negative caching.** Cache the "not found" result too, with a short TTL (say 60 s), so repeated lookups stop at the cache. Delete it when the object is created.

```python
MISSING = "__none__"

def get_profile_neg(user_id):
    key = f"v1:profile:user:{user_id}"
    cached = r.get(key)
    if cached == MISSING:
        return None                          # known not to exist
    if cached is not None:
        return json.loads(cached)
    row = load_from_mysql(user_id)
    if row is None:
        r.set(key, MISSING, ex=60)           # short TTL
        return None
    r.set(key, json.dumps(row), ex=900)
    return row
```

- **Bloom filter** of valid ids in front of the lookup. A Bloom filter is a compact bit structure that answers "is this id in the set?" It never says "absent" for something present (no false negatives), so a "no" can be trusted and the request is rejected without touching MySQL. A rare false "maybe" just falls through to the database. It can live in the app or in Redis through a module (RedisBloom. Check current docs).
- **Rate-limit or block** the caller. Penetration is often abuse.
- **Validate input.** Reject ids that can't be valid (wrong format, out of range) before any lookup.

| | Negative caching | Bloom filter |
|---|---|---|
| Memory | One small key per missing id seen | Fixed, small, for all ids |
| Protects against | Repeated lookups of the same missing key | Random, never-repeating missing keys too |
| Weakness | Attacker uses a new random id each time, so the cache never helps | Must be updated when new ids are created. Standard Bloom filters can't delete |
| Staleness | Id created within the TTL looks missing until deleted | Same until the filter is updated |

**What is avalanche?** A large fraction of keys disappears at once. Two causes: a mass expiry (a warm-up batch with one TTL), or the cache itself restarting empty. The database sees a wall of misses. Fixes: jittered TTLs (Chapter 7), replicas and failover so a node's death doesn't empty a shard, warm-up, and the load-shedding in the next chapter.

**Interview takeaway.** "For ids that don't exist I use negative caching with a short TTL plus a Bloom filter, and I rate-limit the caller. For avalanche I jitter TTLs and plan the cold start."

<h2 id="cache-down">Chapter 10 · When the cache is down</h2>

**What is it?** Redis is unreachable, restarted empty, or slow. Your app still has to answer.

**The first question in every design:** if the cache vanished, would MySQL survive the full read load? With the Chapter 1 numbers (200,000 reads/s against a 20,000 reads/s database) the answer is no. The cache is **load-bearing**, not an optimisation, and the design must say what happens when it fails.

**What to do:**

- **Fail open.** If the cache call errors or times out, treat it as a miss and go to the database. Use a very short client timeout (tens of milliseconds) so a sick Redis doesn't add seconds to every request.
- **Circuit breaker.** After N failures in a window, stop calling Redis for a few seconds, go straight to the next step, and probe occasionally to see if it recovered. This avoids paying the timeout on every request.
- **Load shedding.** Cap concurrent database queries. Beyond that, fail fast or serve a degraded response (a stale copy, a simplified page) instead of queueing until everything times out.
- **Warm-up.** After a cold start the hit ratio is 0%, which is the most dangerous period. Pre-load the known hot set (top N keys, or replay recent access logs), or let traffic in gradually.
- **Persistence where it matters.** Redis can snapshot (RDB) or log writes (AOF) so a restart isn't fully cold. Treat the cache as rebuildable, never as the only copy of data.
- **Replicas and failover** so one node's death doesn't empty a shard (Chapter 12).

```python
import time, threading

db_slots = threading.BoundedSemaphore(50)        # at most 50 concurrent DB reads
breaker = {"fails": 0, "open_until": 0.0}

def cache_get(key):
    if time.monotonic() < breaker["open_until"]:
        return None                              # breaker open: skip Redis
    try:
        v = r.get(key)                           # client has socket_timeout=0.05
        breaker["fails"] = 0
        return v
    except redis.RedisError:
        breaker["fails"] += 1
        if breaker["fails"] >= 5:
            breaker["open_until"] = time.monotonic() + 5
        return None                              # fail open: treat as a miss

def get_profile_safe(user_id):
    v = cache_get(f"v1:profile:user:{user_id}")
    if v is not None:
        return json.loads(v)
    if not db_slots.acquire(blocking=False):     # load shedding
        raise ServiceBusy()                      # map to HTTP 503 + Retry-After
    try:
        return load_from_mysql(user_id)
    finally:
        db_slots.release()
```

This sketch skips the breaker's half-open probe and thread safety on the counters. A real library handles both.

| | Fail open | Fail closed |
|---|---|---|
| Cache down means | Go to the database | Return an error |
| Good when | Database can carry some load, or you shed the rest | Data must come from the cache (a session store, a rate-limit counter) |
| Risk | Database overload | Outage |

**A common trap:** "The cache is just an optimisation." That is true only if you have checked that the database can carry the load without it. Say the check out loud.

**Interview takeaway.** "I would say up front whether the cache is load-bearing. If so, the app fails open with short timeouts, a circuit breaker, a cap on concurrent DB queries, and a warm-up plan for restarts."

<h2 id="eviction">Chapter 11 · Eviction and sizing</h2>

### Size the working set, not the dataset

**Assumption for this example:** 50 million profiles at about 2 KB each is **100 GB** total. Daily actives touch roughly 10% of profiles, a **10 GB working set**. A cache node with about 25 GB usable memory holds it with room for overhead. (Redis has per-key overhead, so budget extra.)

So capacity needs **one** node. You cluster for **throughput** (200,000 reads/s is more than you would want on one node. A simple-GET Redis node handles very roughly 100,000 ops/s, so benchmark it) and for **availability** (replicas). That chain, dataset to working set to node size to why a cluster, is what "no hand-waving" sounds like.

### Eviction: what leaves when memory is full

Redis starts evicting when memory reaches `maxmemory`. The `maxmemory-policy` setting says what to remove.

| Policy | Evicts | Applies to |
|---|---|---|
| `noeviction` | Nothing. Writes fail when full | All keys |
| `allkeys-lru` | Least recently used | All keys |
| `volatile-lru` | Least recently used | Only keys with a TTL |
| `allkeys-lfu` | Least frequently used | All keys |
| `volatile-lfu` | Least frequently used | Only keys with a TTL |
| `allkeys-random` / `volatile-random` | Random key | All / TTL keys |
| `volatile-ttl` | Key closest to expiry | Only keys with a TTL |

For a pure cache, `allkeys-lru` or `allkeys-lfu` is the usual choice. `volatile-*` policies only touch keys with a TTL, so if none have one, they behave like `noeviction`. Redis's own default is `noeviction`. Its LRU and LFU are approximations based on sampling a few keys, which is good enough and cheap.

**LRU vs LFU.**

| | LRU (least recently used) | LFU (least frequently used) |
|---|---|---|
| Question it asks | When was this last touched? | How often is this touched? |
| Good when | Recency predicts reuse | The hot set is stable |
| Weakness | **Scan pollution**: a one-time scan makes cold keys look recent and pushes hot keys out | Slow to adapt: an old favourite with a high count lingers (Redis decays counts over time) |
| Example | Users browsing recent items | A nightly job reads every profile once. LFU ignores it, LRU gets flushed |

<h2 id="clusters">Chapter 12 · Sharding, replication, failover</h2>

**What is it?** Splitting keys across several Redis nodes (sharding) and keeping copies for safety (replication).

**Why do we need it?** One node runs out of network or CPU before memory, and one node dying empties your cache. The goal is to spread keys so that adding a node moves only a little data.

### Sharding

- **Consistent hashing** (common with Memcached clients). Nodes and keys hash onto a ring. A key belongs to the next node clockwise. Adding a node moves only about 1/N of the keys. Virtual nodes (each machine appears at many points on the ring) smooth out imbalance. Compare plain `hash(key) mod N`: changing N remaps nearly every key, which is an avalanche.
- **Hash slots** (Redis Cluster). Every key maps to one of **16,384 slots**: `CRC16(key) mod 16384`. Slots are assigned to primaries and moved between them when the cluster resizes. Clients learn the slot map and talk to the right node.
- **Hash tags.** If a key contains `{...}`, only that part is hashed. `{user:123}:profile` and `{user:123}:settings` land in the same slot, so multi-key commands and Lua scripts across them work. Overusing one tag creates a hot slot.

| | Consistent hashing | Redis Cluster hash slots |
|---|---|---|
| Who decides placement | Client library | Cluster slot map, clients follow redirects |
| Unit of movement | Ranges on the ring | Whole slots (16,384 of them) |
| Resize moves | About 1/N of keys | Only the slots you migrate |
| Multi-key operations | Not guaranteed | Only within one slot (hash tags) |

Try it: start with `mod`, add a shard, and count the keys that move. Then switch to the ring and hash slots.

### Replication and failover

Each primary has one or more replicas. If a primary fails, a replica is promoted. Caveats to say aloud:

- **Replication is asynchronous.** The primary acknowledges a write before replicas have it. If it fails at that moment, the promoted replica is missing the last few writes. That can include a recent `DEL`, which brings a stale value back. Fine for a cache, worth saying. (`WAIT 1 100` blocks up to 100 ms and returns how many replicas have the write, 0 if none do, for example when the replica is down. It does not undo the write on the primary, so it does not make Redis strongly consistent.)
- **Failover takes time.** There is a detection timeout (`cluster-node-timeout` in Redis Cluster, or Sentinel's equivalent) plus election. During it, that shard's keys are unavailable. Your fail-open path from Chapter 10 handles it.
- **Reads from replicas can be stale** by the replication lag. Use them only for data that tolerates it.
- **A shard with no replica to promote** loses its slots. By default Redis Cluster stops serving when slots are uncovered (`cluster-require-full-coverage` is `yes` by default). Decide whether you want that or partial service.
- **After failover the promoted node's hit ratio is fine**, but a primary that restarts empty means a cold shard. Warm it before sending traffic.

### Redis vs Memcached

| | Redis | Memcached |
|---|---|---|
| Data types | Strings, hashes, lists, sets, sorted sets, streams | Strings (blobs) |
| Persistence | Optional (RDB snapshots, AOF) | None |
| Replication / failover | Built in | Client-side or none |
| Threads | Command execution mostly single-threaded per node (I/O threads optional) | Multi-threaded |
| Pick when | You need structures (leaderboards, rate limiters, sessions) or replication | You need a simple, very fast blob cache |

**Interview takeaway.** "Redis Cluster hashes keys into 16,384 slots spread over primaries, with replicas for failover. Replication is async, so a failover can lose recent writes, which is acceptable for a cache."

<h2 id="consistency">Chapter 13 · What you can promise</h2>

Name the guarantee per path, not for the whole system. Two different promises are easy to mix up: "will I see my own edit?" and "will my friends see it soon?"

- **Bounded staleness** for most readers: "at most the TTL, usually much less."
- **Read-your-own-writes** for the author. Delete-on-write already gives it in the common case. For a guarantee, route the author's reads to the primary database for a short window after their write, or write the author's own session copy.
- **Strong consistency** where money or inventory is involved: don't serve it from the cache. Cache the page, and check the truth at the decision point.

**Interview takeaway.** "Most readers get bounded staleness, the author gets read-your-own-writes by reading the primary briefly after an edit, and money or stock reads go to the database."

**Follow-ups you will get:**

<Reveal q="1 · Why not update the cache on write instead of deleting?">

Concurrent writers can apply their cache SETs in the opposite order to their database writes, leaving the older value cached, forever without a TTL. A delete can't install a stale value. The worst case is one extra miss.

</Reveal>

<Reveal q="2 · What happens when a very popular key expires?">

A stampede. One request takes a short per-key lock (`SET lock NX PX`) and recomputes. The rest wait briefly or get the stale copy (stale-while-revalidate). TTLs are jittered so keys warmed together don't expire together.

</Reveal>

<Reveal q="3 · One key gets 500K reads per second. Sharding didn't help. Why, and what now?">

A key lives on exactly one shard, so more shards don't spread it. Put a ~1 s in-process L1 cache on each app server (200 servers means about 200 Redis reads/s for that key), or split the key into N suffixed copies and read a random one.

</Reveal>

<Reveal q="4 · How big is the cache, and why that many nodes?">

Working set, not dataset: 50M profiles × 2 KB = 100 GB total, about 10% active = 10 GB. It fits on one node, so the cluster exists for throughput (200K ops/s) and availability (replicas), not capacity.

</Reveal>

<Reveal q="5 · Is the cache consistent with the database?">

Eventually, with bounded staleness: fresh in the common case, stale for at most the TTL in rare races. Paths that need the truth, such as balances or inventory at checkout, read the database. The author's own reads go to the primary for a short window after a write.

</Reveal>

<Reveal q="6 · Cache-aside vs read-through?">

Both load from the database on a miss. In cache-aside the application runs that code. In read-through the cache layer does, through a loader you register. Same flow, different owner.

</Reveal>

<Reveal q="7 · Single TTL vs stale-while-revalidate?">

A single TTL has one deadline. After it the key is gone and a request waits on the database. SWR has a soft expiry inside the value and a hard expiry as the Redis TTL. Between them readers get the old value immediately while one request refreshes it in the background.

</Reveal>

<Reveal q="8 · Does delayed double delete fix the race?">

It narrows it. A second delete shortly after the first removes a value a slow reader cached in the gap. But a reader slower than the delay, or a lagging replica, can still cache stale data. It is a mitigation. Versioned writes or a TTL actually bound the problem.

</Reveal>

<Reveal q="9 · What if Redis goes down?">

First say whether the cache is load-bearing. If it is: fail open with short timeouts, a circuit breaker so we stop calling Redis, a cap on concurrent database queries with degraded responses beyond it, and a warm-up plan for when it returns empty.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| "Make reads faster" | Cache-aside, then the four promises |
| Read-heavy, repeated keys | Hit ratio target from (1 − h) × QPS ≤ DB budget |
| Data changes through your service | Update DB, then delete the key. TTL backstop |
| Many writers to the same table | CDC-driven deletes |
| "Is it consistent?" | Bounded staleness. Truth-critical paths read the DB |
| A hot key expired, DB spiked | Stampede: single-flight, lock `SET NX PX`, SWR, jitter |
| One key melts one shard | Hot key: in-process L1, key splitting |
| Lookups for ids that don't exist | Penetration: negative cache, Bloom filter |
| Many keys gone at once | Avalanche: jitter, replicas, warm-up |
| "What if Redis dies?" | Load-bearing? Then fail open, breaker, shedding, warm-up |
| "How big?" | Working set, then node size, then cluster for throughput and availability |
| Shape change in a deploy | Version prefix in keys |
| Static assets, images | CDN with fingerprinted URLs, long max-age |
| Race on writes | Delete not update, DB first then delete, versions if strict |

**Common mistakes**

1. **"Cache it in Redis."** Without key, TTL reason, invalidation and failure plan, it isn't a design.
2. **Updating the cache on write.** Delete instead.
3. **Deleting before the database write.** Update the database first.
4. **TTLs that all expire together.** Jitter them.
5. **Assuming the cache is optional.** Check whether the database survives without it.
6. **Promising strong consistency.** Promise bounded staleness, and name the paths that bypass the cache.
7. **Calling a lock a correctness tool.** A cache-fill lock only reduces load. It can expire mid-load.

**Keep it warm:** run a drill with a study partner, five rounds: a cache for a feed, a session store, a rate limiter, typeahead and a product catalogue. Ninety seconds each: key shape, TTL and reason, invalidation, failure mode.
