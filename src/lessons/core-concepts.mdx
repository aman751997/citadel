<h2 id="prologue">Prologue · One bad evening</h2>

Here is an outage that touches almost every idea in this lesson. It is an illustrative composite, not a real company's incident.

A product launches at 7 PM. At 7:02 search p99 latency jumps to 9 seconds. Then the feed times out. Then checkout times out, even though checkout never calls search. It takes 21 minutes to stop. The causes, found later:

- One search shard out of 100 had a slow disk, and every search asks all 100 shards.
- The feed service called search with no timeout.
- Feed and checkout shared one thread pool, so threads stuck on search starved checkout.
- Phones, the gateway and the feed service each retried failed calls up to three times.
- The database leader was so overloaded that it missed heartbeats. A replica a few hundred writes behind was promoted, and the old leader kept accepting writes for a few seconds.

Every item has a name: **tail latency, timeout, bulkhead, retry storm, failover, split brain, replication lag**. Interviewers ask about these names, and they test whether you can reason with them rather than recite them. That is what this lesson is for.

**The rule: for every box you draw, answer four questions out loud.**

1. **Which layer is it?** So you and the interviewer mean the same box.
2. **Where does its state live?** So you know what is lost when it dies, and whether it can scale out.
3. **What happens when it is slow?** Timeouts, the tail, and what waits on it.
4. **What happens when it is gone?** Redundancy, failover, retries, and what the user sees.

<Figure caption="The four questions. Part One answers the first two; Parts Two to Four answer the last two.">
  <Mermaid code={`flowchart LR
    L["1 · Which layer?\nedge, gateway, service,\ncache, data, async"] --> S["2 · Where is the state?\ntoken, store, blob,\nqueue, nowhere"]
    S --> W["3 · When it is slow?\ntimeouts, tail,\nbulkheads"]

Two habits are worth fixing early. One is **layer conflation**: answering a different layer than the one asked (tenant isolation when the question was per-object authorization). The other is **dodging**: saying "partitions are rare, so..." instead of reasoning aloud when a question gets uncomfortable. Chapters 1 and 8 target them.

<h2 id="layers">Chapter 1 · Which box are we talking about?</h2>

**What is it?** A web system is a stack of layers. Each layer exists to protect the ones below it from work they do not need to do. "Layer" is the first word of every system design answer because the same noun ("cache", "rate limit", "consistency") means different boxes at different layers.

**The problem it solves.** Two engineers argue for five minutes about "the cache". One means the CDN, the other means Redis. They are describing different boxes with different failure modes, so the argument cannot end. Naming the layer first prevents that.

<Figure caption="The layers of a typical web system. The synchronous path runs top to bottom; the async tier takes work that does not need to finish before the user gets an answer.">
  <Mermaid code={`flowchart TB
    C["Client\napp or browser"] --> DNS["DNS\nname to address"]
    DNS --> CDN["CDN / edge\nstatic and cacheable content, TLS"]
    CDN --> LB["Load balancer\nL4 or L7, health checks"]
    LB --> GW["API gateway\nauth, rate limits, routing"]
    GW --> SVC["Services\nstateless business logic"]
    SVC --> CACHE[("Cache\nhot reads")]
    SVC --> DATA[("Data tier\ndatabase, blob store, search index")]
    SVC --> Q[["Queue / stream"]]
    Q --> WK["Workers\nasync jobs"]
    WK --> DATA`} />
</Figure>

| Layer | Its job | The question it answers | Deep lesson |
|---|---|---|---|
| Client | Render, cache locally, retry politely | "What does the user see when we fail?" | — |
| DNS | Turn a name into an address; route by geography | "How do users reach the nearest region? How fast can we fail over?" | <a href={`${BASE}sd/lessons/networking/`}>Networking</a> |
| CDN / edge | Serve static and cacheable content close to users | "Why does this request ever reach us?" | <a href={`${BASE}sd/lessons/blob-cdn/`}>Blob & CDN</a> |
| Load balancer | Spread connections or requests across healthy servers | "Which server gets it, and how do we know it is alive?" | <a href={`${BASE}sd/lessons/load-balancing/`}>Load balancing</a> |
| API gateway | Authenticate, rate-limit, route, shape requests | "Who is calling, and are they allowed this much?" | <a href={`${BASE}sd/lessons/load-balancing/`}>Load balancing</a>, <a href={`${BASE}sd/lessons/rate-limiter/`}>Rate limiter</a> |
| Services | Business logic, ideally stateless | "What does the system do?" | Chapter 2 |
| Cache | Remember hot answers | "How do we survive the read load?" | <a href={`${BASE}sd/lessons/caching/`}>Caching</a> |
| Data tier | The source of truth: database, blobs, search index | "What must never be lost or wrong?" | <a href={`${BASE}sd/lessons/databases/`}>Databases</a> |
| Async tier | Queues, streams, workers | "What can happen after we answer?" | <a href={`${BASE}sd/lessons/queues-streams/`}>Queues & streams</a> |

**The same word lives at many layers.** Before you answer a question containing one of these words, say which layer you mean:

| The word | It could mean |
|---|---|
| "Cache" | Browser, CDN, gateway response cache, in-process L1, Redis, the database's own buffer pool |
| "Load balancing" | DNS across regions, L4 (connections), L7 (HTTP requests), client-side picking a replica |
| "Rate limiting" | At the edge per IP, at the gateway per API key or tenant, inside a service as a concurrency limit protecting one dependency |
| "Consistency" | Between database replicas, between cache and database, between two services, and ACID's "C", which is something else again (invariants) |
| "Partition" | A **network** partition (nodes cannot talk) or a **data** partition (a shard). Chapter 8 vs Chapter 10 |
| "Authorization" | Identity (who), tenant (which company), role (what kind of user), resource (which object) |

**A common slip.** Asked about *resource-level* authorization, a candidate answers *tenant isolation*: a correct answer to a different question. The fix takes five seconds: "Just to be sure, you mean per-object access within a tenant, not isolation between tenants?" Interviewers read that as precision, not stalling.

<Trace title="Name the layer" steps={layers} takeaway="Same word, many boxes. Say which layer you mean before you answer, especially for cache, rate limit, consistency, partition and authorization." />

<Reveal q="The interviewer points at your load balancer: 'Isn't that a single point of failure?' What do you say?">

It would be, if it were one machine. In practice it is a redundant pair (or a fleet) sharing a virtual IP that fails over, or a managed cloud load balancer that is already a distributed service, and DNS can spread users across several load balancers or regions. Say which of these you assume. Then add the useful part: health checks on the servers behind it, so it stops sending traffic to a dead one.

</Reveal>

**When to use this habit.** Always, for any word on the list above. **The trap:** one box labelled "backend". It hides every decision this lesson is about. Draw the layers, and later questions have somewhere to land.

<h2 id="scaling">Chapter 2 · One bigger box, or many?</h2>

**What is it?** **Vertical scaling (scale up)** means a bigger machine: more cores, more memory, faster disks. **Horizontal scaling (scale out)** means more machines sharing the work.

**The problem it solves.** One server hits a ceiling. A blog post sends ten times the usual traffic, so you buy a bigger server. The next post needs a bigger one again, until no bigger machine exists, and meanwhile one machine is a single point of failure.

| | Vertical | Horizontal |
|---|---|---|
| Code changes | None | Services must be stateless, or state must be split |
| Ceiling | The biggest machine you can buy | Very high, if the work divides |
| Cost curve | Rises steeply at the top end | Roughly linear in machines |
| Failure | One machine: a single point of failure | Lose one of many: lose a slice of capacity |
| Distributed-systems problems | None | All of the rest of this lesson |

**The trade-off and the senior answer.** It is not "always horizontal". It is **scale up while it is cheap, and design so you can scale out.** One well-provisioned database server goes a very long way, and splitting data across machines (Chapter 10) brings real costs. Stateless services are the opposite: they scale out so easily there is rarely a reason not to.

**What "stateless" means.** Any request can go to any instance, and an instance keeps nothing that must outlive the request. State still exists. It lives somewhere designed to keep it:

| State | Where it goes |
|---|---|
| Who is logged in | A signed token (e.g. a JWT) the client sends, or a shared session store |
| User data | The database |
| Uploaded files | Blob storage; jobs carry the object key, never a local path |
| Hot reads | A distributed cache |
| Work to do later | A queue |
| Long-lived connections (WebSockets) | Inherently stateful: a registry maps user to connection server |
| Configuration, feature flags | A config service that pushes changes |

<Figure caption="Why in-memory sessions break scale-out: the second request lands on a server that has never heard of the user. A shared store (or a signed token) fixes it.">
  <Mermaid code={`sequenceDiagram

**Worked numbers (assumption for this example).** One API server sustains 2,000 requests/s at a 70% CPU target. Peak forecast: 15,000 requests/s.

- 15,000 / 2,000 = 7.5, so **8 servers** carry peak.
- Add one for a server failure and one for a rolling deploy: **10 servers**.
- None of that works while sessions sit in one server's memory: user 42 logs in on server 3, the next request lands on server 7, and they are logged out.

<Trace title="Where does the state go?" steps={scaling} takeaway="Stateless tier: move state into stores designed for it, then add machines. Data tier: scale up first, and split only when the numbers force you." />

<Reveal q="Sticky sessions keep each user on one server. Why not just use them and keep sessions in memory?">

They work as a performance optimization, never as the only copy of state. If the server dies, its users lose their sessions. Load cannot be rebalanced evenly because users are pinned. Deploys have to drain long-lived users slowly. Put the session in a token or a shared store; stickiness can then be a cache-locality bonus, not a correctness requirement.

</Reveal>

**When to use what.** Scale the stateless tier out from the start (it is nearly free once state is external). Scale the database up first, then add read replicas (Chapter 7), then partition (Chapter 10). **The trap:** "we will scale horizontally" said about the whole system at once. The database is the hard part.

<h2 id="throughput">Chapter 3 · Latency, throughput and queues</h2>

**What is it?** **Latency** is how long one request takes. **Throughput** is how many requests finish per second. They are different questions about the same system: "how long does my request wait?" versus "how many can you finish?"

Think of a road. Latency is how long one car takes to drive it; throughput is how many cars pass a point each hour. Adding lanes raises throughput, but one car is no faster. A traffic jam raises every car's travel time without letting more cars through.

| | Latency | Throughput |
|---|---|---|
| Question | How long does one request take? | How many requests finish per second? |
| Unit | ms (report as percentiles) | requests/s, MB/s |
| More servers | Does not help, unless requests were queueing | Raises it, if work divides |
| Batching | Worsens it (items wait for the batch) | Improves it |

**The problem it solves.** "Is it fast?" has no answer until you say which one you mean. A system can have high throughput and bad latency (a big batch pipeline) or the reverse (one fast box that cannot take more than 100 requests per second).

**How they connect: Little's Law.** It holds for any stable system:

> **In-flight requests = arrival rate × time in system.** L = λ × W.

**Worked numbers (assumption for this example).** A feed service takes 2,000 requests/s at 50 ms each.

- In flight: 2,000/s × 0.05 s = **100** requests at any moment.
- A dependency slows and feed latency rises to 2 s. In flight needed: 2,000 × 2 = **4,000**.
- The service has **200** worker threads. It can finish at most 200 / 2 s = **100 requests/s**. The other 1,900 each second queue, time out, and get retried.

That is the outage in one line of arithmetic: **a slow dependency raises your concurrency until you run out of it.** Chapter 13 fixes it.

**Utilization and queues.** As a server nears 100% busy, waiting time does not grow gently; it explodes. In the simplest queueing model (M/M/1: random arrivals, random service times, one server), average response time = service time / (1 − utilization). Real systems differ in detail, never in shape.

<Figure caption="M/M/1 response time in multiples of the service time S at 50%, 75%, 80%, 90% and 95% utilization: 2S, 4S, 5S, 10S, 20S.">
  <Bars heights={[2, 4, 5, 10, 20]} pointers={[{ at: 0, label: '50%' }, { at: 1, label: '75%' }, { at: 2, label: '80%' }, { at: 3, label: '90%', tone: 'red' }, { at: 4, label: '95%', tone: 'red' }]} tones={{ 3: 'hot', 4: 'hot' }} />

That is why capacity plans aim for 60 to 70% utilization at peak, not 95%. The last 25% of "headroom" is where latency lives.

**Batching** groups many small operations into one (a database group commit, a producer batching messages). Throughput rises, and each item waits a little longer for its batch. Say which one you are buying.

**Latency numbers worth remembering**, rounded for a whiteboard (typical orders of magnitude; real hardware varies):

| Operation | Time |
|---|---|
| Main memory read | ~100 ns |
| SSD random read | ~100 µs (about 1,000× RAM) |
| Round trip inside one data centre | ~0.5 ms |
| HDD seek | ~10 ms |
| Round trip across a continent or ocean | ~70 to 150 ms |

Consequences you will use. A **5 ms budget** forbids disk seeks and cross-region hops. A "feels instant" budget of about **100 ms** allows a short chain of data-centre round trips, not a cross-ocean one per step. A chatty service making **20 sequential same-DC calls** has spent about 10 ms on the network before doing any work.

<Trace title="Little's Law, live" steps={throughput} takeaway="In flight = rate × latency. When latency rises, concurrency rises with it, and every fixed pool becomes a cliff. Run below ~70% utilization; the queue lives in the last 30%." />

**When to use it.** Use Little's Law whenever you size a thread pool, connection pool or queue consumer: concurrency needed = rate × latency, then add headroom. **The trap:** "add more servers to make it faster". More servers raise throughput. A single request only gets faster if it was waiting in a queue. If it is slow because it makes 20 sequential calls, the fix is fewer or parallel calls.

<h2 id="tail-latency">Chapter 4 · The slowest of a hundred</h2>

**What is it?** **Percentiles** describe the latency distribution. p50 (the median) is the latency half of requests beat. **p99** is the latency 99% of requests beat, so one request in a hundred is slower. p99.9 is one in a thousand. **Tail latency** is the slow end of that distribution.

**The problem it solves.** Averages hide the tail completely: a 40 ms average is compatible with 2% of requests taking two seconds. And the tail matters more than it looks, because of fan-out.

**Why the tail dominates fan-out.** If a user request calls *n* backends in parallel and must wait for all of them, it is slow whenever **any** call is slow. With each call slow with probability *p*, independently:

> **P(user request is slow) = 1 − (1 − p)ⁿ**

**Worked numbers**, each call slow 1% of the time:

| Fan-out n | 1 − 0.99ⁿ | Slow user requests |
|---|---|---|
| 1 | 0.01 | 1% |
| 10 | 1 − 0.904 | about 9.6% |
| 100 | 1 − 0.366 | **about 63%** |
| 1,000 | 1 − 0.00004 | about 99.996% |

At fan-out 100, a 1-in-100 event per leaf becomes the *normal* experience for users. Even at 1-in-1,000 per call, fan-out 100 gives 1 − 0.999¹⁰⁰ ≈ **9.5%** slow requests. To keep users at 1% slow with fan-out 100, each leaf must be slow only about **0.01%** of the time. This is the example from Dean and Barroso's *The Tail at Scale*: a 1-in-100 slow server, 100 servers per request, 63% of requests slow.

    R --> L2["Leaf 2 · 12 ms"]
    R --> L3["…"]
    R --> L61["Leaf 61 · 1,000 ms"]
    R --> L100["Leaf 100 · 11 ms"]
    L61 --> W["The response waits\nfor the slowest leaf"]`} />
</Figure>

**What reduces the tail:**

- **Hedged requests.** If a leaf has not answered by its p95, send a duplicate to another replica and take whichever answers first. That adds about 5% more calls and cuts the tail sharply, because two replicas are rarely slow together. Only for reads or idempotent calls.
- **Smaller fan-out.** Partition so common queries touch fewer leaves (Chapter 10).
- **Deadlines with partial results.** Answer with the leaves that responded in time. Fine for search ranking, unacceptable for an account balance. That is a product decision; say it as one.
- **Find the cause.** Garbage-collection pauses, noisy neighbours, background compaction, a dying disk. Tails have causes, and per-leaf p99 dashboards find them.

<Trace title="Feel the tail" steps={tail} takeaway="Fan-out turns rare into normal: 1 − (1 − p)ⁿ. Measure p99 and p99.9, not averages; hedge reads, shrink fan-out, and set deadlines." />

<Reveal q="Why not set each leaf's timeout to its p99 and just drop the slow ones?">

You can. That is "deadline with partial results", and search engines do it. But it changes the answer, not just the speed. Dropping 1% of shards drops 1% of documents from ranking, which is usually invisible. Dropping a shard from a balance, an inventory count or a permission check is a wrong answer. Say which kind of data you are serving before you choose.

</Reveal>

**When to use what.** Hedge reads when the tail is a few slow replicas. Cut fan-out when you control the data layout. Use partial results only where a slightly incomplete answer is acceptable. **The trap:** an SLO written as an average ("average latency under 100 ms"). Write it as a percentile with a window: "p99 under 200 ms over five minutes".

<h2 id="availability">Chapter 5 · What the nines cost</h2>

**What is it?** **Availability** is the fraction of time (or of requests) the system serves successfully. It is usually quoted in "nines". Each extra nine divides the allowed downtime by ten.

**The problem it solves.** "Highly available" means nothing until it is a number. A product manager asks for "five nines". Five nines is about five minutes of downtime a year, and one bad deploy can spend that in a minute. A number makes the cost and the trade-offs discussable.

| Availability | Downtime per year | Per 30 days | What it usually takes |
|---|---|---|---|
| 99% | ~3.65 days | ~7.2 hours | One server and hope |
| 99.9% | ~8.8 hours | ~43 minutes | Redundancy, health checks, failover |
| 99.99% | ~53 minutes | ~4.3 minutes | Multiple zones, automated failover, on-call |
| 99.999% | ~5.3 minutes | ~26 seconds | Multi-region active-active, rehearsed failure, a lot of money |

Two rules:

1. **Never claim nines without a reason.** "Five nines" for a photo-sharing app is slop. "99.9% is fine for the feed; 8.8 hours down a year is annoying, not catastrophic" is judgment.
2. **Serial components multiply.** If a request needs A *and* B, availability = A × B. Two 99.9% services in a row give 0.999² ≈ **99.8%**; four give 0.999⁴ ≈ **99.6%**. Every box in the critical path costs availability, which is a reason boxes must earn their place and non-critical calls should be asynchronous.

**How redundancy fixes it.** If a request needs A *or* B (either can serve), it fails only when both are down: availability = 1 − (1 − A)(1 − B). Two 99% replicas give 1 − 0.01 × 0.01 = **99.99%**, **if their failures are independent.** They usually are not fully: the same rack, the same bad deploy, the same bug, the same region. Spreading replicas across failure domains (zones, regions) and deploying gradually earns the independence the formula assumes.

  <Mermaid code={`flowchart LR

      direction LR

      direction LR
      A2["A 99%"]
      B2["B 99%"]
    end`} />
</Figure>

**Single points of failure (SPOFs)** are components whose failure alone takes the system down. Hunt them layer by layer (Chapter 1): one load balancer, one primary database with manual failover, one region, one DNS provider, one config service everything reads at startup. Redundancy comes in a few shapes:

| Shape | How | Cost |
|---|---|---|
| **Active-active** | All copies serve traffic | Must handle shared state and conflicts; capacity for one loss must already be running |
| **Active-passive** (hot standby) | A standby takes over on failure | Failover time; the standby must actually work (test it) |
| **N+1 / N+2** | One or two more instances than load needs | Cheap for stateless tiers |

**Availability vs durability.** These are different promises. Availability is "can I use it now?"; durability is "is my data still there?". A photo service can be down for an hour and lose nothing; it must never lose a photo it said it saved. Make both promises separately.

<Trace title="Count the nines" steps={availability} takeaway="Series multiplies availability down; redundancy multiplies unavailability down, but only for independent failures. Find the SPOF at every layer, and make failover automatic." />

<Reveal q="Can your service be more available than a database it cannot work without?">

Not on the paths that need it. If every request reads that database, its downtime is your downtime, so your availability is at most its availability. The ways around it are design choices: serve from a cache or a replica when the primary is down (reads keep working, staleness grows), queue writes for later where the product allows it, or degrade the feature instead of the whole page. Each one turns a hard dependency into a soft one.

</Reveal>

**When to use what.** Choose the nines from the cost of downtime, not from ambition. Spend redundancy on the critical path first. **The trap:** "we will add retries for availability". Retries hide brief blips. They do nothing for a dependency that is down for ten minutes, and against an overloaded one they make things worse (Chapter 12).

<h2 id="liveness">Chapter 6 · Dead, or just slow?</h2>

**What is it?** Distributed systems must decide which machines are alive, who is the leader, and who may do a job right now. The tools are **heartbeats**, **leases**, **fencing tokens** and **consensus** (majority voting).

**The problem it solves.** From the outside you cannot tell a dead machine from a slow one. A message that does not arrive could mean the node crashed, the network dropped it, or the node is paused (garbage collection, a swapping disk, a hypervisor hiccup). Now picture a database leader so overloaded that it stops sending heartbeats for a few seconds. The cluster decides it is dead and promotes a follower. The old leader catches its breath, still accepts writes, and still believes it is the leader. For a few seconds there are two. This is **split brain**.

**Heartbeats.** Each node sends "I am alive" every interval; if a peer misses several in a row, it is *suspected* dead. The timeout is a trade-off:

- **Short** (e.g. 3 missed heartbeats at 1 s): fast detection, but GC pauses and network blips cause false alarms, and an unnecessary failover is itself an outage.
- **Long**: fewer false alarms, slower recovery from real failures.

No setting turns a suspicion into proof. So anything a "dead" node does after waking up must be **checked**, not trusted.

**Leases.** A lease is a lock with an expiry: "you are the leader (or own this job) for the next 10 seconds." The holder renews well before expiry (say every 3 seconds); if it cannot renew, it must stop acting as the holder. A dead holder simply stops renewing, so crashes are self-healing. In Redis terms, taking and renewing a lease looks like this (the redis lesson owns the details):

```text
SET lease:search-leader node-A NX PX 10000   -- acquire, only if nobody holds it
PEXPIRE lease:search-leader 10000            -- renew (only valid if you still own it)
```

Two caveats matter:

- **Clocks.** Measure lease time with a monotonic clock, and have the holder assume its lease ends a little *early* to allow for clock drift.
- **Pauses.** A holder can check "my lease is valid", pause for 15 seconds, then write. The check was true when it ran. So the resource being protected must check too.

**Fencing tokens** close that gap. Each new lease carries a number higher than every one before it. Storage remembers the highest number it has seen and rejects writes with a lower one.

<Figure caption="A paused former leader wakes up and tries to write with an old token. Storage has already seen token 34 and refuses 33.">
  <Mermaid code={`sequenceDiagram
    participant A as Node A
    participant L as Lock / lease service
    participant B as Node B
    participant S as Storage
    A->>L: acquire lease
    L-->>A: granted, token 33, 10 s
    Note over A: GC pause 15 s
    B->>L: acquire lease
    L-->>B: granted, token 34
    B->>S: write, token 34
    S-->>B: ok (highest seen = 34)
    A->>S: write, token 33
    S-->>A: rejected, 33 is older than 34`} />
</Figure>

| | Heartbeat | Lease | Fencing token |
|---|---|---|---|
| What it does | Tells peers you are alive | Gives you the right to act for a limited time | Lets storage reject an old holder |
| Who decides | Each peer, by timeout | The lease service, by expiry | The resource, by comparing numbers |
| Weakness | Cannot distinguish dead from slow | A paused holder can outlive its lease | Needs the resource to cooperate |

**Leader election.** Many systems choose one node to make decisions (order writes, assign work) because one decider is simpler than many agreeing on every step. Electing it safely is a **consensus** problem, solved by algorithms such as Raft and Paxos, usually through a coordination service like ZooKeeper or etcd rather than hand-written code. The core ideas:

- **Majority vote.** A candidate needs votes from a majority of the cluster, and each node votes once per **term** (an increasing election number). Any two majorities of the same cluster overlap, so two leaders cannot both win the same term. That overlap prevents split brain.
- **Terms work as fencing.** Messages from an older term are rejected, so a deposed leader that wakes up finds its writes refused.
- **Randomized timeouts.** Raft gives each follower a random election timeout (the paper suggests 150 to 300 ms), so usually one node times out first and wins before others compete.

**Worked numbers.** A cluster of **2f + 1** nodes survives **f** failures: 3 nodes survive 1, 5 survive 2. Four nodes need a majority of 3, so they survive only 1, the same as three nodes with one more machine to fail. That is why consensus clusters are odd-sized.

<Trace title="Who is alive, who is leader" steps={liveness} takeaway="A timeout is a suspicion, not a proof. Leases expire; fencing tokens make storage reject the holder who woke too late; majorities overlap, so there is one leader per term." />

<Reveal q="Two leaders existed for three seconds. What would have prevented the damage?">

Two things. Leader terms enforced as fencing: once the new leader's term began, the replicas and storage should refuse anything stamped with the old term, so the old leader's writes fail instead of landing. And a less hair-trigger failure detector: an overloaded leader missing heartbeats for a couple of seconds is a reason to shed load (Chapter 14), not necessarily a reason to fail over, since failover under overload often makes things worse.

</Reveal>

**When to use it.** Use a coordination service (etcd, ZooKeeper) for leader election and locks rather than writing consensus yourself. Use leases whenever one actor must own something temporarily, and add fencing whenever the protected resource can reject stale writers. **The trap:** "a Redis lock with a TTL makes it safe". Without fencing, a paused holder can wake after the TTL and keep writing while the new holder works. The <a href={`${BASE}sd/lessons/pattern-contention/`}>contention lesson</a> builds locks and fencing out in full.

<h2 id="replication">Chapter 7 · Replication</h2>

**What is it?** **Replication** keeps copies of the same data on several machines, to survive failures, to spread read load, and to put data near users.

**The problem it solves, and what it costs.** Imagine a service whose database leader dies. Its replica was replicating asynchronously, about 200 ms behind. Everything in those 200 ms, acknowledged to users with a green tick, is gone, and users file "my post disappeared" tickets. When exactly is something *saved*? Replication answers that, and the answer is a trade-off.

**How leader-follower works.** All writes go to the leader; it streams its change log to followers, which apply it in order. Reads can go to the leader (fresh) or followers (possibly stale). The lever is *when the leader says "done"*:

<Figure caption="Synchronous: the client hears 'ok' after a follower has the write. Asynchronous: the client hears 'ok' first; the follower catches up later.">
  <Mermaid code={`sequenceDiagram
    participant C as Client
    participant L as Leader
    participant F as Follower
    Note over C,F: Synchronous
    C->>L: write x = 5
    L->>F: replicate x = 5
    F-->>L: ack
    L-->>C: ok
    Note over C,F: Asynchronous
    C->>L: write x = 6
    L-->>C: ok
    L->>F: replicate x = 6 (later)`} />
</Figure>

| Mode | Write latency | If the leader dies | If a follower is down |
|---|---|---|---|
| **Synchronous** | + one round trip to the follower | No acknowledged writes lost | Writes stall (unless you drop to async) |
| **Asynchronous** | Lowest | Up to the replication lag of acknowledged writes lost | Nothing; it catches up later |
| **Semi-synchronous** (one follower sync, the rest async) | + one round trip | At least one up-to-date copy survives | Promote another follower to be the sync one |

**Worked numbers (assumption for this example).** 1,000 writes/s, async replica about 200 ms behind. A failover loses up to 1,000 × 0.2 = **~200 acknowledged writes**. Most systems choose async and accept that risk. The senior move is to *say* you accept it, or to make one follower synchronous for data that must not be lost.

**Failover** has three steps and two classic dangers. Detect the leader is gone (a timeout, Chapter 6), choose the most up-to-date follower, and point clients at it. The dangers are **lost writes** (async lag) and **split brain** (the old leader returns still believing it leads; fencing by term fixes it).

**Replication topologies, side by side:**

| | Single-leader | Multi-leader | Leaderless (Dynamo-style) |
|---|---|---|---|
| Who takes writes | One leader | A leader per region | Any replica |
| Conflicts | None (one order) | Yes; need a merge rule | Yes; quorums plus version tracking |
| Typical use | Most OLTP databases | Multi-region writes, offline-capable apps | Highly available key-value stores |
| Watch out for | Failover, lag | "Last write wins" silently drops a write | Sloppy quorums, stale reads |

Resolving a multi-leader conflict by "last write wins" silently drops one write; CRDTs or application-level merges keep both.

**Quorums: agreeing without agreeing on everything.** N replicas. A write succeeds once **W** acknowledge; a read asks **R** and takes the newest version. If **W + R > N**, every read set overlaps every write set in at least one node, so a read that starts after a write completes reaches at least one node holding it. (Pigeonhole: two groups that sum to more than N must share a member.)

| N, W, R | W + R > N? | Shape |
|---|---|---|
| 3, 2, 2 | 4 > 3 yes | The classic balance; tolerates one slow or dead node on both reads and writes |
| 3, 1, 3 | 4 > 3 yes | Fast writes, expensive reads (every replica must answer) |
| 3, 3, 1 | 4 > 3 yes | Fast reads, writes need every replica (read-heavy systems) |
| 3, 1, 1 | 2 ≤ 3 no | Fastest, and reads may miss the latest write: eventual consistency |

<Trace title="Replicas under pressure" steps={replication} takeaway="Sync costs latency, async costs acknowledged writes on failover. Quorums overlap when W + R > N." />

<Reveal q="Does W + R > N make a leaderless store linearizable?">

Not by itself, and saying so is a senior signal. **Sloppy quorums** (writing to stand-in nodes during a failure) can put the W acknowledgements outside the usual N. **Concurrent writes** resolved by timestamps can lose one write to clock skew. A write that **failed** overall may still have landed on some replicas, so later reads disagree. And **read-repair timing** can let one reader see the new value while a later reader still sees the old. Quorums give a strong overlap guarantee; linearizability needs more (consensus, or careful read-repair rules). *Designing Data-Intensive Applications* walks through each case.

</Reveal>

**When to use what.** Async single-leader for most systems; add one sync follower for data you cannot lose; multi-leader only when regions must accept writes independently and you have a merge rule. **The trap:** "we will add read replicas" and nothing else. Replica reads can be stale. Say which reads may be stale (a feed) and which must go to the leader (a user reading what they just wrote). Chapter 9 names that guarantee.

<h2 id="cap">Chapter 8 · CAP and PACELC</h2>

**What is it?** CAP is a precise statement about what a replicated system can promise **while the network is partitioned**. It is the most misquoted theorem in system design, so the exact claim comes first.

**The problem it solves.** Two data centres are connected by a link, and the link breaks for forty minutes. Inside each region everything is healthy. A request arrives on each side for the same data. Either each side answers on its own, and the answers may disagree, or one side refuses until the link heals. There is no third option. CAP names the choice.

**The three terms, in their strict meaning:**

- **C, consistency**, here means **linearizability**: the system behaves as if there were one copy, and every read sees the latest completed write. (Not ACID's "C", which is about invariants.)
- **A, availability**, means every request to a node that has not crashed gets a non-error response. (Not "99.99% uptime".)
- **P, partition tolerance**, means the system keeps working when the network drops or delays messages between nodes.

**What CAP claims.** (Brewer's conjecture, proved by Gilbert and Lynch in 2002.) **If a network partition happens, a system must give up either linearizability or availability for the requests it cannot coordinate.** When there is no partition, it can have both.

**What CAP does not claim:**

| Common misreading | What is actually true |
|---|---|
| "Pick any two of three" | You cannot pick "CA" for a system on more than one machine. Partitions happen (cables, switches, a long GC pause looks the same). The choice is C or A **during a partition**. |
| "A database is CP or AP, full stop" | The choice can differ per operation and per data (and many systems are tunable). Labels are shorthand. |
| "CP means the system is down a lot" | CP only refuses requests on the side that cannot reach a majority, only while partitioned. A CP system can run at 99.99%. |
| "AP means no consistency" | AP systems cannot be linearizable during a partition but can offer eventual, causal or session guarantees. |
| "CAP says something about latency" | It does not. Latency trade-offs when there is no partition are PACELC's territory. |
| "CAP's availability is the nines" | CAP's A is a per-request property during a partition, not an uptime percentage. |

<Figure caption="A partition always eventually happens. The design question is what each side does while it lasts.">
  <Mermaid code={`flowchart TD
    P["Network partition happens\n(it always eventually does)"] --> Q{"A request arrives on one side.\nWhat do we do?"}
    Q -->|"Refuse until nodes\ncan agree again"| C["CP\nConsistent; some\nrequests fail"]
    Q -->|"Keep serving; sides may\ndiverge, reconcile later"| A["AP\nAvailable; reads may\nbe stale or conflict"]`} />
</Figure>

**A tiny example.** A seat-booking row `seat 14C = free` is replicated in region 1 and region 2, and the link between them drops.

```text
Region 1: user books 14C  ->  ?
Region 2: user books 14C  ->  ?

CP choice: only the side with the majority (region 1) accepts. Region 2 returns an error.
           Result: one booking, one error. No double sale.
AP choice: both accept. After the link heals the system sees two bookings for 14C
           and must compensate (refund one, apologise). Result: both users got "yes".
```

**Interview usage.** Make the CAP call in the requirements phase, per kind of data, with a product reason.

- Banking ledger, seat booking, inventory, username claims: **CP**. "A wrong answer is worse than no answer."
- Social feed, like counts, view counts, presence: **AP**. "A stale answer is fine; an error page is not."

Never say "we need full consistency and five nines". It shows you do not see the trade-off.

**PACELC: what CAP leaves out.** CAP is silent about the 99.9% of the time when there is no partition. Daniel Abadi's PACELC fills it in: **if Partition, choose A or C; Else, choose Latency or Consistency.** Even with a perfect network, keeping replicas consistent means waiting for them.

| System style | During a partition | Else (normal operation) | Label |
|---|---|---|---|
| Dynamo-style stores (Cassandra, Riak) with default settings | Stay available | Answer from nearby replicas, fast | PA/EL |
| Consensus-replicated databases (Spanner-style) | Stay consistent | Wait for a quorum on every write | PC/EC |
| Tunable stores (Cassandra with QUORUM reads and writes) | Move toward C | Pay a quorum round trip | Configured per query |

Synchronous replication to another region is consistent, and every write pays the round trip. Asynchronous is fast, with replica lag. Saying "and even without partitions, it is latency versus consistency, that is PACELC" earns credit in one sentence. (Vendor behaviour changes between versions; check current docs before quoting labels for a product.)

<Trace title="Choose your side" steps={cap} takeaway="During a partition: C or A, per data, with a product reason. Otherwise: latency or consistency (PACELC)." />

<Reveal q="If AP systems give up consistency, do they give you no guarantees at all?">

No. "AP" means they cannot be *linearizable* during a partition. Most still promise **eventual consistency** (replicas converge once writes stop and the network heals), and many add session guarantees such as read-your-writes on top. Causal consistency, a strong model (next chapter), is about the strongest that can stay available during a partition. AP is a ceiling on consistency, not the absence of it.

</Reveal>

**When to use it.** Use CAP when the interviewer asks about partitions or multi-region; answer per data item. **The trap:** dodging. "Partitions are rare enough to ignore" and "we will use a database that handles it" both refuse the question. Name the side, name the data, give the product reason.

<h2 id="consistency">Chapter 9 · Consistency models</h2>

**What is it?** A **consistency model** is a promise about what reads can see after writes. It is not a yes/no property; it is a **ladder**, from expensive guarantees at the top to cheap ones at the bottom. Each rung forbids a specific user-visible bug.

**The problem it solves.** Four support tickets arrive: "I changed my bio and it changed back when I refreshed." "The comment count went 41, 39, 42." "A reply showed up before the question it answered." "My friend and I were both told the username 'alice' was ours." Four bugs, four different promises that were never made.

<Figure caption="The consistency ladder. Higher rungs forbid more anomalies; climbing costs coordination, latency, and availability during partitions.">
  <Mermaid code={`flowchart TB
    LIN["Linearizable\nbehaves like one copy, in real time"] --> SEQ["Sequential\none order for everyone, may lag real time"]
    SEQ --> CAU["Causal\ncauses before effects, for everyone"]
    CAU --> SES["Session guarantees\nread-your-writes · monotonic reads"]
    SES --> EV["Eventual\nreplicas converge once writes stop"]`} />
</Figure>

**Precise definitions, with a small example each.** Take one register `x`, initially 0. Client A writes `x = 1` and gets its acknowledgement at time T. Client B starts a read *after* T.

- **Linearizable.** Every operation appears to take effect atomically at one instant between its start and its end, and that order respects real time. B must read 1 (or something newer). This is the single-copy illusion.
- **Sequential.** All clients see the writes in *one agreed order*, which also respects each client's own order, but it need not match real time. B may still read 0 for a while, as long as everybody sees the same history. Linearizable forbids this; sequential allows it.
- **Causal.** If operation B depends on A (a reply to a question), everyone sees A before B. Unrelated writes may show up in different orders for different readers.
- **Read-your-writes.** After *you* write, *your* later reads see that write (or newer). Others may lag.
- **Monotonic reads.** Once you have seen a value, you never see an older one. The count goes 41, 42, never 41, 39.
- **Eventual.** If writes stop, all replicas converge to the same value. Nothing is promised in the meantime.

| Rung | The promise | The bug it forbids | Typical cost |
|---|---|---|---|
| **Linearizable** | Acts like a single copy: once a write is acknowledged, every later read, anywhere, sees it | Two people win the username "alice"; a seat sold twice; a lock held by two | A leader or consensus on every operation; minority side unavailable in a partition |
| **Sequential** | One agreed order of writes, may lag real time | Two viewers seeing chat messages in different orders | One ordered log applied identically everywhere |
| **Causal** | Causes are seen before effects | A reply before its question; an old boss seeing a post made after being removed from the audience | Track dependencies (version vectors); stays available in a partition |
| **Read-your-writes** | You see your own writes | Your bio "reverting" after you edit it | Route your reads to the leader briefly, or carry your last-write position in the session |
| **Monotonic reads** | No going back in time | The count going 41, 39, 42 | Pin a session to one replica, or track the last position seen |
| **Eventual** | Replicas converge | Nothing in the meantime | Nearly free: async replication |

Two more session guarantees complete the set: **monotonic writes** (your writes apply in the order you made them) and **writes-follow-reads** (a write you make after reading something is ordered after what you read). Causal consistency includes all four.

**Look-alikes to keep separate:**

| Term | About | Meaning |
|---|---|---|
| **Linearizability** | One object, real time | Reads and writes behave like one copy |
| **Serializability** | Transactions | Several operations behave as if run one at a time, in some order (not necessarily real-time order) |
| **Strict serializability** | Both | Transactions in an order consistent with real time |
| **ACID "C"** | Invariants | The database moves between states that satisfy your rules; unrelated to the above |
| **Cache staleness** | A cache | Bounded staleness; see the <a href={`${BASE}sd/lessons/caching/`}>caching lesson</a> |

**A concrete implementation: read-your-writes.** The simplest version routes a user's reads to the leader for a short time after they write:

```python
READ_YOUR_WRITES_WINDOW = 5  # seconds; assumption: replica lag is normally under 1 s

def get_profile(user_id):
    last_write = redis.get(f"last_write:{user_id}")      # set by the write path with EX 5
    db = leader if last_write else pick_replica()
    return db.query("SELECT bio FROM profiles WHERE user_id = %s", (user_id,))
```

It works per *user*, not per device, because the key is the user id. Edge case: if you only remember the position in a browser cookie, the same user on a laptop gets no protection.

**The senior move: different data in the same system gets different models.** In a payment system, the ledger is linearizable, "your recent transactions" is read-your-writes, and spending analytics is eventual.

<Trace title="Which rung is missing?" steps={consistency} takeaway="Name the rung, not 'strong'. Linearizable for uniqueness and money; causal for conversations; read-your-writes and monotonic reads for the person refreshing; eventual for counts." />

<Reveal q="Read-your-writes is in place. The user edits their bio on their phone and opens their laptop. Will they see it?">

Not necessarily. Read-your-writes is usually implemented per *session*: the phone's session remembers its last-write position, but the laptop is a new session that knows nothing about it and may read a lagging replica. If the promise is "a user always sees their own edits on every device", the last-write position must be tracked per *user*, server-side, not per device.

</Reveal>

**When to use it.** Pay for linearizability only for uniqueness, money and locks. Use causal or session guarantees where users would notice time going backwards. Use eventual for counts and feeds. **The trap:** "we need strong consistency" with no rung and no data named.

<h2 id="partitioning">Chapter 10 · Partitioning (sharding)</h2>

**What is it?** **Partitioning** (sharding) puts *different* data on different machines; replication puts *the same* data on several. Real systems do both: each partition is replicated.

**The problem it solves.** A table reaches 40 TB, and the busiest write hour is more than one primary can take. Replicas give copies, but copies do not help when one machine cannot hold or write it all. Data has to be cut into pieces. The wrong cut is expensive to undo.

<Figure caption="Three partitions, each with its own leader and followers. Partitioning gives scale; replication gives survival.">
  <Mermaid code={`flowchart LR
    R["Router\nkey → partition"] --> P1["Partition 1\nleader + 2 followers"]
    R --> P2["Partition 2\nleader + 2 followers"]
    R --> P3["Partition 3\nleader + 2 followers"]`} />
</Figure>

**Choose the partition key with two tests.** Does it spread load evenly? Do your common queries stay inside one partition? They often conflict, and that tension is the deep dive. The <a href={`${BASE}sd/lessons/databases/`}>databases lesson</a> works through examples.

| | Hash partitioning | Range partitioning |
|---|---|---|
| How | hash(key) picks the partition | Contiguous key ranges per partition (A to F, G to M, ...) |
| Load spread | Even, because the hash scrambles keys | Can concentrate: today's writes all land in the newest range |
| Range scans | Must ask every partition | One or a few partitions |
| Pick when | Point lookups dominate (caches, key-value) | Ordered scans dominate (time series, logs) |

**Hot partitions** are the recurring disease: a celebrity's user id, today's date, a viral post. First fixes: add a small bucket to the key (`date#hash(user) % 16` splits today's writes 16 ways, and costs 16 reads to reassemble, so say the cost), put a short-lived cache in front of hot *reads*, or split the hot partition.

**Consistent hashing, the intuition.** The naive placement is `hash(key) % N`. It spreads keys evenly until N changes.

**Worked numbers.** 10 nodes become 11. A key stays put only if `h % 10` equals `h % 11`. Across any 110 consecutive hash values that happens for exactly 10 of them, so **100/110 ≈ 91% of keys move**. For a cache, that is a near-total cold start.

Consistent hashing places nodes and keys on the same ring; a key belongs to the next node clockwise. Adding a node takes over only one arc, so only about **1/N of keys move** (1/11 ≈ 9% here). **Virtual nodes** (each machine at many points on the ring) smooth uneven arcs and spread a dead node's load over everyone. Try it:

The <a href={`${BASE}sd/lessons/pattern-partitioning/`}>partitioning pattern lesson</a> takes this all the way.

**Two meanings of "partition".** A *network* partition (Chapter 8) is machines that cannot talk. A *data* partition is a shard. If a question is ambiguous, ask.

<Trace title="Where to cut" steps={partitioning} takeaway="Hash for spread, range for scans; every scheme gets hot spots. Modulo moves almost everything on resize; consistent hashing moves ~1/N." />

**When to use it.** Only when one primary cannot hold or write the data, after scaling up, caching and replicas. **The trap:** "shard by user_id" and stop. Say what happens to the user with 50 million followers, and which queries now cross partitions and so lose joins and single-node transactions.

<h2 id="ids">Chapter 11 · Unique IDs</h2>

**What is it?** A primary key in a distributed system has to be **unique without coordination**, and usually also **compact**, **roughly time-ordered** (so B-tree inserts append instead of scattering), and **not guessable** where it is public.

**The problem it solves.** After a table is split into eight shards, two different orders from two different users are both numbered 4,200,117, because each shard kept counting from its own auto-increment. An ID must stay unique across machines that do not talk to each other on every insert.

| Scheme | Size | Time-ordered? | Coordination | Catch |
|---|---|---|---|---|
| Auto-increment | 64 bits | Yes | One counter per database | Breaks when you shard; leaks your volume |
| **UUIDv4** | 128 bits | No (122 random bits) | None | Random inserts scatter across index pages |
| **UUIDv7** | 128 bits | Yes (48-bit millisecond timestamp first) | None | Larger than 64 bits; the timestamp is visible |
| **Snowflake-style** | 64 bits | Yes | A unique machine id per generator | Machine-id assignment; clock going backwards |
| Ticket server / range allocation | 64 bits | Roughly | A central allocator hands out blocks | The allocator must stay available |

<Figure caption="Two time-ordered layouts. UUIDv7 (RFC 9562) puts a Unix-millisecond timestamp first; a Snowflake-style id packs timestamp, machine and sequence into 64 bits.">
  <ArrayStrip name="UUIDv7" values={['unix_ts_ms', 'ver', 'rand_a', 'var', 'rand_b']} indices={false} regions={[{ from: 0, to: 0, label: '48 bits', tone: 'gold' }, { from: 1, to: 1, label: '4', tone: 'dim' }, { from: 2, to: 2, label: '12', tone: 'blue' }, { from: 3, to: 3, label: '2', tone: 'dim' }, { from: 4, to: 4, label: '62 bits', tone: 'blue' }]} />
  <ArrayStrip name="Snowflake" values={['sign', 'timestamp', 'machine', 'sequence']} indices={false} regions={[{ from: 0, to: 0, label: '1 bit', tone: 'dim' }, { from: 1, to: 1, label: '41 bits', tone: 'gold' }, { from: 2, to: 2, label: '10 bits', tone: 'purple' }, { from: 3, to: 3, label: '12 bits', tone: 'green' }]} />
</Figure>

**Worked numbers for the classic Snowflake layout:**

- 41 bits of milliseconds: 2⁴¹ ms ≈ **69.7 years** from your chosen epoch.
- 10 bits of machine id: **1,024** generators.
- 12 bits of sequence: **4,096 ids per millisecond per generator**, about 4.1 million per second.
- UUIDv4's 122 random bits: a billion ids have roughly a 1-in-10¹⁹ chance of any collision. Randomness is not the risk; index locality is.

**Clock skew** is the Snowflake trap. If NTP moves the clock backwards, the generator could reissue a (timestamp, machine, sequence) it already used. The fix: remember the last timestamp, and refuse or wait until the clock passes it. Because each machine has its own clock, ids from different machines are only *roughly* ordered: fine for index locality, wrong as proof of which event happened first.

**Public ids.** Sequential ids reveal how many orders you take and invite enumeration (`/orders/4200118`). Never let an id be the authorization check: check the caller against the resource (Chapter 1's resource layer).

<Trace title="Pick the id" steps={ids} takeaway="Unique without coordination, compact, time-ordered: UUIDv7 or Snowflake. Never let a clock run backwards into an id." />

<Reveal q="Can you sort Snowflake ids to get the exact global order of events?">

Only approximately. Within one generator, ids are strictly increasing. Across generators, ordering is only as good as clock agreement; with a few milliseconds of skew, an event that happened later on machine B can get a smaller id than one on machine A. For "roughly newest first" in a feed, that is fine. For "which bid came first" in an auction, order through one leader or a log instead.

</Reveal>

**When to use what.** UUIDv7 when you want no coordination and are fine with 128 bits; Snowflake when you need 64-bit ids and can assign machine ids; auto-increment when a single database is truly enough. **The trap:** random UUIDv4 as a clustered primary key on a large write-heavy table.

<h2 id="retries">Chapter 12 · Retries and idempotency</h2>

**What is it?** A **retry** repeats a failed call. An operation is **idempotent** if doing it twice has the same effect as doing it once. Retries are only safe on idempotent operations, so the two ideas go together.

**The problem it solves, and the danger.** Networks drop packets, so retries are essential. But in the prologue, one user tap became twenty-seven searches against a shard that was already drowning, and checkout retries charged some customers twice. A timeout does not say whether the operation happened, only that you did not hear back.

**Retry the transient, not the permanent.** Timeouts, connection resets, `503 Service Unavailable` and `429 Too Many Requests` (honour its `Retry-After`) are worth retrying. A `400 Bad Request`, a validation error, or "insufficient funds" will fail the same way every time.

**Idempotent or not?**

| Operation | Idempotent? | Why |
|---|---|---|
| Set the bio to X | Yes | Twice leaves the same state |
| Delete photo 7 | Yes (the end state is the same) | The second delete finds nothing |
| Charge ₹500 | No | Twice charges twice |
| Add 1 to a counter | No | Twice adds 2 |
| HTTP GET, PUT, DELETE | By definition yes | The spec says so; your handler must honour it |
| HTTP POST | Not by default | Needs an idempotency key |

(HTTP calls GET "safe" too: no side effects. Safe implies idempotent; idempotent does not imply safe, because DELETE changes state.)

**Idempotency keys.** The client generates one id per *logical* operation and sends it with every attempt. The server records key to result; a repeat key returns the stored result instead of acting again. The check and the record must be atomic with the operation itself.

```http
POST /payments HTTP/1.1
Idempotency-Key: 7d1f6c3e-2f4a-4c1b-9a77-1c9e6f0b2a10
Content-Type: application/json

{"order_id": 981, "amount": 500, "currency": "INR"}
```

```sql
CREATE TABLE idempotency_keys (
  idem_key    VARCHAR(64) PRIMARY KEY,
  request_hash CHAR(64)   NOT NULL,
  response    JSON        NULL,
  created_at  TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- inside the same transaction as the charge:
INSERT INTO idempotency_keys (idem_key, request_hash) VALUES (?, ?);   -- duplicate key error means a retry
-- ... charge, then UPDATE idempotency_keys SET response = ? WHERE idem_key = ?; COMMIT;
```

The primary key makes the second insert fail, so only one attempt can proceed. Storing `request_hash` lets the server reject the same key reused with a different body. The <a href={`${BASE}sd/lessons/pattern-contention/`}>contention lesson</a> covers the in-progress state in full.

**Exponential backoff with jitter.** Wait longer after each failure, up to a cap, and randomize:

```python
import random, time

def call_with_retries(send, key, max_attempts=4, base=0.1, cap=10.0):
    for attempt in range(max_attempts):
        result = send(idempotency_key=key)          # same key every attempt
        if result.ok or not result.retryable:
            return result
        ceiling = min(cap, base * 2 ** attempt)     # 0.1, 0.2, 0.4 ... capped at 10 s
        time.sleep(random.uniform(0, ceiling))      # "full jitter"
    return result
```

<Figure caption="Backoff ceilings for attempts 0 to 8 with base 100 ms and a 10 s cap, in units of 100 ms. Full jitter sleeps a random time below each bar, so clients that failed together do not come back together.">
  <Bars heights={[1, 2, 4, 8, 16, 32, 64, 100, 100]} pointers={[{ at: 7, label: 'cap', tone: 'red' }]} tones={{ 7: 'hot', 8: 'hot' }} />
</Figure>

Without jitter, 1,000 clients that failed together retry together: a wall of 1,000 requests at 100 ms, another at 300 ms, each hitting a server that is trying to recover. Jitter turns the walls into a trickle.

**Retry storms.** Retries multiply across layers. Three layers with three attempts each gives 3 × 3 × 3 = **27 attempts** at the bottom for one user action. Three rules contain it:

- **Retry at one layer**, usually the one closest to the failure, and let the others fail fast.
- **Retry budgets.** Cap retries as a fraction of traffic (the Google SRE book describes a per-client budget of about 10%), so a failing dependency sees at most about 1.1× normal load, not 3×.
- **Deadlines.** Pass the remaining time budget downstream; do not retry work whose caller has already given up.

<Trace title="Retry or not" steps={retries} takeaway="Retry transient failures of idempotent operations, at one layer, with exponential backoff, full jitter and a budget. A timeout means 'unknown', not 'failed'." />

<Reveal q="A client times out on POST /orders and retries, but generates a fresh idempotency key for the retry. What happens?">

Two orders. The server sees two different keys and correctly treats them as two operations. The key must be generated **once per logical operation** (when the user taps "Buy"), stored by the client, and reused on every retry of that operation. This is the most common way idempotency keys fail in real code.

</Reveal>

**When to use it.** Retry for brief blips on idempotent or keyed calls. Do not retry against a dependency that is clearly overloaded; shed instead (Chapter 14). **The trap:** "we will retry on failure". Say *which* failures, *which* operations, *how many* times, with *what* backoff, at *which* layer.

<h2 id="isolation">Chapter 13 · Timeouts, breakers and bulkheads</h2>

**What is it?** Three defences that stop one slow dependency from taking you down: **timeouts** (stop waiting), **circuit breakers** (stop calling), and **bulkheads** (limit how much of your capacity one dependency can use).

**The problem it solves.** A hung dependency is worse than a dead one. A dead one refuses connections and you fail in a millisecond. A hung one accepts and never answers, and every caller waits holding a thread, a connection and memory. In the prologue the feed service had 20 busy threads at 7:01 and 200 of 200 at 7:03, all waiting on search. Little's Law (Chapter 3) says how fast that fills any pool.

**Timeouts on every network call.** Set them from the dependency's measured latency (a little above its p99.9) and inside your own deadline. If your API promises 1 s, two sequential 800 ms timeouts cannot both fit. Watch for library defaults: some HTTP clients wait forever unless told otherwise (check each client's docs; Java's `HttpURLConnection` treats 0 as infinite and 0 is its default).

**Circuit breakers.** Count recent failures to a dependency. Past a threshold, *open* the circuit: fail immediately, without calling, and serve a fallback. After a cool-down, go *half-open*: let a few trial calls through. Success closes the circuit; failure opens it again.

<Figure caption="The circuit breaker state machine. Open protects both sides: the caller stops waiting, the dependency gets room to recover.">
  <Mermaid code={`stateDiagram-v2
    [*] --> Closed
    Closed --> Open: failure rate over threshold
    Open --> HalfOpen: cool-down elapsed
    HalfOpen --> Closed: trial calls succeed
    HalfOpen --> Open: a trial call fails`} />
</Figure>

**Bulkheads.** Ships have watertight compartments so one hole does not sink the ship. Give each dependency its own pool or concurrency limit: recommendations may use at most 20 of the feed's 200 threads, search at most 60. When search hangs, *its* 60 fill up and its calls fail fast; checkout's threads are untouched.

```python
import threading

search_slots = threading.BoundedSemaphore(60)      # bulkhead for search

def call_search(query):
    if not search_slots.acquire(blocking=False):   # fail fast, do not queue
        raise Overloaded("search bulkhead full")
    try:
        return http.get("/search", params={"q": query}, timeout=0.8)
    finally:
        search_slots.release()
```

**Fallbacks and graceful degradation.** Decide in advance what a feature looks like without each dependency: the feed without recommendations, search results without personalization, a cached profile instead of a fresh one.

| | Timeout | Circuit breaker | Bulkhead |
|---|---|---|---|
| Protects | One call's wait | Future calls to a failing dependency | Everything else from that dependency |
| Triggered by | One call exceeding a time limit | Failure or latency rate over a window | Concurrency reaching a limit |
| Cost if misset | Too short cuts good calls, too long holds threads | Too sensitive opens on blips | Too small rejects healthy traffic |

<Trace title="Contain the damage" steps={isolation} takeaway="Timeouts on every call; breakers that fail fast and probe; bulkheads so one dependency can only drown its own pool; a planned fallback for each." />

<Reveal q="Why not set the timeout to the dependency's average latency?">

Because about half of healthy calls are slower than average, so you would cut off a large share of perfectly good requests, and then retry them, adding load. Timeouts belong just above the high percentiles (p99 to p99.9) of healthy behaviour: long enough not to fire on normal slowness, short enough that a hung dependency releases your threads quickly.

</Reveal>

**When to use it.** Timeouts always. Breakers for dependencies that can fail for minutes. Bulkheads when several features share a resource. **The trap:** "we will add a circuit breaker" as a magic word. Say what trips it (error rate or latency over a window), what the caller does while it is open (the fallback), and how it closes (half-open probes).

<h2 id="overload">Chapter 14 · Overload and back-pressure</h2>

**What is it?** What a system does when more work arrives than it can do. The tools are **load shedding** (reject the excess), **back-pressure** (make producers slow down) and **rate limiting** (a per-client policy).

**The problem it solves.** Say peak traffic is 15,000 requests per second and capacity is 10,000. A system that queues the extra grows its queue by 5,000 every second. Requests wait, time out, clients retry, and the server spends the rest of the night serving people who have already given up. A system that tries to serve everyone serves no one.

**Why overload collapses throughput.** Past capacity, queues grow. Queued requests wait longer than clients will wait, so the server works on requests whose callers have left: work that produces nothing (low *goodput*). Clients retry, adding more. Throughput can fall *below* capacity just when demand is highest.

<Figure caption="Offered load above capacity. Queueing everything wastes the capacity on dead requests; shedding keeps goodput at the limit.">
  <Mermaid code={`flowchart LR
    IN["15,000 req/s offered"] --> E{"Edge: over capacity?"}
    E -->|"10,000 admitted"| S["Service\nserves fast"]
    E -->|"5,000 shed\n503 + Retry-After"| X["Rejected cheaply"]`} />
</Figure>

**Load shedding.** Reject the excess early and cheaply, ideally at the edge, with `503` and a `Retry-After`. **Worked numbers (assumption):** 15,000 offered, 10,000 capacity: shed 5,000 / 15,000 = **one third**, and serve the other 10,000 fast. Shed the least valuable work first (prefetches, analytics, background refreshes, retries) before logins and checkouts. Tag priority at the edge so every layer makes the same choice.

**Back-pressure.** When a consumer cannot keep up, the producer should *feel* it. A bounded queue that blocks or rejects is the smallest example:

```python
import queue

jobs = queue.Queue(maxsize=1000)            # bounded on purpose

def submit(job):
    try:
        jobs.put(job, timeout=0.05)         # wait briefly, then push back on the caller
    except queue.Full:
        raise Overloaded("try again later") # caller sees 503 or slows down
```

Other forms: a consumer that pulls only what it can handle (Kafka consumers pull; reactive streams signal demand), and TCP's flow control at the transport layer. An unbounded queue does not remove overload; it postpones it and turns it into an out-of-memory crash or hours of lag.

**Rate limiting** is a *policy* limit per client (fairness, abuse, cost) rather than a reaction to current load. The usual algorithm is the **token bucket**: each client's bucket holds up to B tokens and refills at r per second; a request spends a token or gets `429 Too Many Requests`. It belongs at the edge or gateway (say the layer). The <a href={`${BASE}sd/lessons/rate-limiter/`}>rate limiter walkthrough</a> designs one end to end.

**Load shedding vs back-pressure vs rate limiting:**

| | Load shedding | Back-pressure | Rate limiting |
|---|---|---|---|
| Reacts to | The server's current load | A consumer falling behind | A client's usage policy |
| Who slows down | The excess requests are rejected | The producer is slowed or blocked | The over-quota client is rejected |
| Typical signal | `503` + `Retry-After` | Full queue, blocked put, pull-based demand | `429` + `Retry-After` |
| Where | Edge, or any service | Between producer and consumer | Edge or gateway |

**Autoscaling helps, slowly.** New instances take minutes to start; a surge can kill you in seconds, and the database does not autoscale at all. Shedding buys the minutes.

| Tool | Protects | Decides on | The caller sees |
|---|---|---|---|
| Timeout | The caller's threads | Elapsed time | An error after a bounded wait |
| Circuit breaker | The caller, and the sick dependency | Recent error or latency rate | A fast failure or a fallback |
| Bulkhead | Everything else from one dependency | Per-pool concurrency | Failures only in that feature |
| Back-pressure | A consumer and its queue | Queue depth | The producer slows or is rejected |
| Load shedding | The service's capacity right now | Current load, priority | `503` + `Retry-After` |
| Rate limiting | Fairness between clients | Per-client counter | `429` + `Retry-After` |

<Trace title="Shed, push back, limit" steps={overload} takeaway="Past capacity, queueing makes everyone fail. Shed early by priority, bound every queue, rate-limit per client at the edge." />

<Reveal q="Why not just autoscale instead of shedding load?">

Use both, because they work on different timescales. Shedding reacts in milliseconds and keeps the service inside its capacity while autoscaling spends minutes adding more. And the bottleneck often cannot autoscale: a primary database, a third-party API with its own limits, a licensed dependency. Shedding protects those as well.

</Reveal>

**When to use it.** Shed by priority whenever offered load can exceed capacity; bound every queue; rate-limit per client at the gateway. **The trap:** "an unbounded queue absorbs spikes". A queue absorbs a spike only if consumers later catch up. If arrivals exceed service for long, latency becomes the queue's length and memory runs out. Bound it, and say what happens when it is full.

**Five follow-ups you will get:**

<Reveal q="1 · There is a network partition between your two regions. What happens to likes, and to username sign-up?">

Likes are AP: both regions keep counting locally, and the per-region counters are summed when the link heals, so nobody sees an error and counts are briefly different. Usernames are CP: the claim goes to a single leader (or a consensus store); the region that cannot reach it refuses sign-ups with a clear error rather than risking two owners of one name. CAP's choice is per data, with a product reason.

</Reveal>

<Reveal q="2 · Your search service fans out to 100 shards. Why is p99 so much worse than any single shard's?">

Because the request waits for the slowest of 100. If each shard is slow 1% of the time, 1 − 0.99¹⁰⁰ ≈ 63% of searches hit at least one slow shard. I would cut it with hedged requests after the p95, smaller fan-out through better partitioning, and a deadline that returns partial results, which is acceptable for search ranking.

</Reveal>

<Reveal q="3 · A downstream service starts hanging. Walk me through what your service does.">

The call times out at a value just above the dependency's p99.9, so threads come back. Failures trip the circuit breaker; while open, calls fail immediately and we serve the fallback. The dependency has its own bulkhead, so it can only exhaust its own share of threads. After a cool-down the breaker goes half-open and probes with a few calls. Retries, if any, happen at one layer with backoff, jitter and a budget, so we do not pile onto it.

</Reveal>

<Reveal q="4 · How do you make 'create order' safe to retry?">

The client generates an idempotency key when the user taps Buy and sends it on every attempt. The server stores key and result atomically with creating the order; a repeat key returns the stored result. A timeout means "unknown", so without the key a retry could create a second order. Retries use exponential backoff with full jitter, at one layer only.

</Reveal>

<Reveal q="5 · Your system has a leader. How is it chosen, and what stops two leaders?">

Through consensus: Raft via etcd or ZooKeeper rather than hand-rolled. A candidate needs a majority vote, one vote per node per term, and any two majorities overlap, so only one leader wins a term. Leadership is a lease, renewed early. A paused old leader can wake believing it still leads, so every write carries the term or a fencing token, and storage rejects older ones. Five nodes survive two failures.

</Reveal>

| "What if it fails?" | Retry idempotent only, one layer, backoff + jitter + budget, idempotency keys |
| "What if it is slow?" | Timeouts, circuit breaker with fallback, bulkheads |
| "Traffic spike?" | Shed by priority, bounded queues, back-pressure, rate limits at the gateway |

## Five mistakes to leave behind

1. **Answering the wrong layer.** One clarifying clause first: which cache, which limit, which authorization layer.
2. **"We need full consistency and five nines."** Pick C or A per data during a partition, and a number of nines with a reason.
3. **Quoting averages.** Tails decide user experience, and fan-out multiplies them.
4. **"We will retry."** Without idempotency, backoff, jitter, a single layer and a budget, retries are an attack on yourself.
5. **Unbounded anything.** No timeout, no queue limit, no pool limit: each one turns a slow component into a total outage.

**Keep it warm.** With a study partner, run a **CAP speed round**. Name ten systems rapid-fire: ledger, like counter, DNS, seat booking, chat history, presence, shopping cart, username registry, feature flags, analytics dashboard. For each, in 30 seconds: CP or AP, the consistency rung, and a one-line product reason. Then pick availability nines for each and defend the cost.

**Look these up yourself**

- **Vector clocks and version vectors**: how leaderless stores detect concurrent writes instead of guessing with timestamps.
- **CRDTs**: data types (counters, sets, text) that merge without conflicts, the engine behind many AP designs.
- **Hybrid logical clocks and TrueTime**: how CockroachDB and Spanner order events across machines despite clock skew.
- **Sloppy quorums and hinted handoff**: what Dynamo-style stores do when the "right" N replicas are not reachable.
- **Adaptive concurrency limits** (e.g. Netflix's concurrency-limits library): letting a service discover its own capacity from latency instead of hand-set rate limits.
- **Cell-based architecture and blast radius**: splitting a system into independent copies so one bad deploy or poison request cannot take down everyone.
- **Kingman's formula**: why variability, not just utilization, drives queueing delay.
- **Linearizability vs serializability vs strict serializability**: the three words most often confused in database interviews.
