<h2 id="prologue">Prologue · A bet on the questions</h2>

Imagine a design review for a secondhand-gear marketplace: buy and sell inside a mobile app, launch in six weeks. Someone writes **DATABASE: MongoDB (it scales)** on the whiteboard. Nobody has listed what the app will ask the data.

That is the mistake this lesson is about. **Every database is a bet on which questions you will ask.** Teams lose that bet with Mongo and with MySQL alike, for the same reason: they picked the store before they wrote down the questions.

Every system design reaches this point right after the API: *where does the data live?* Interviewers do not care which logo you pick. They care whether your reason survives two follow-ups: "why that one?" and "what happens when it grows?"

A common slip is to name a many-to-many relationship and index only one side. Chapter 3 gives a full worked schema with every query it serves. The *unique ID generator* question is answered in Chapter 13, and shard-key practice leans on Chapter 12.

**The data layer is five decisions, made in this order, each with a reason:**

1. **Access patterns.** The queries, their rates, their latency budgets, and which must be transactional.
2. **Store.** The engine whose native access path matches the hottest pattern.
3. **Model and keys.** Tables or documents, relationships, primary keys, IDs.
4. **Indexes.** One for each query shape you serve, columns in the right order.
5. **Copies and splits.** Replication for availability and reads; partitioning and sharding for size and writes.

<h2 id="choose-store">Chapter 1 · MySQL until proven otherwise</h2>

The marketplace has six questions to answer. *Show a listing. Show a seller's active listings. Check out: order, payment and stock, all or nothing. Show the latest messages in a conversation. Search listings by text. Find fraud rings.* Do all six want the same database?

**Start from a default: a relational database (here, MySQL with InnoDB) until proven otherwise.** It gives you ACID transactions, joins, constraints, secondary indexes, ad-hoc queries and decades of tooling. Assumption for this lesson: one well-provisioned MySQL primary handles thousands of writes a second and terabytes of data. The exact ceiling depends on hardware, row size and query shape, so benchmark it. Most systems in interviews never outgrow it.

**You leave the default for a specific reason:** an access pattern the relational model serves badly, or a volume one node cannot hold.

| Store | Data shape | Built for | Weak at | Marketplace use | Examples |
|---|---|---|---|---|---|
| **Relational** | Tables of rows, foreign keys | Transactions across rows, joins, constraints, questions you have not thought of yet | Scaling writes past one node without sharding or a distributed SQL engine | Users, listings, orders, payments | MySQL, PostgreSQL |
| **Key-value** | An opaque value per key | Get and put by exact key, very low latency, huge scale | Any question not keyed by the key | Sessions, carts, idempotency keys | Redis (in memory), DynamoDB |
| **Wide-column** | Partition key → rows sorted by clustering columns | Heavy writes; reading one partition in sorted order | Ad-hoc queries, joins, read-modify-write, queries without the partition key | Chat messages, activity feeds | Cassandra, ScyllaDB, HBase, Bigtable |
| **Document** | Nested JSON-like documents | Loading and saving a whole aggregate by id; varying attributes | Many-to-many joins across documents; invariants across documents | Product catalogue with category-specific attributes | MongoDB, Couchbase (MySQL also has a `JSON` type) |
| **Graph** | Nodes and typed edges | Multi-hop traversals | Bulk aggregation; sharding a densely connected graph | Fraud rings, "people you may know" | Neo4j, Amazon Neptune |
| **Time-series** | (series, timestamp) → value | Append-mostly ingest, time-range scans, downsampling, retention | Updates; lookups by anything but series and time | Metrics, price history, telemetry | Prometheus, InfluxDB, TimescaleDB |
| **Search** | Inverted index over text and fields | Full text, typo tolerance, relevance ranking, facets | Being the source of truth; transactions; read-after-write (refresh is near real time) | Listing search, typeahead | Elasticsearch, OpenSearch |

### SQL versus NoSQL: what actually differs

The real difference is not "scale". Relational databases shard too. It is this: **NoSQL stores ask you to know your query patterns up front and shape the data for them; SQL lets you ask new questions later.** Cassandra is fast because each partition is a sorted, write-optimised run of rows. It punishes the day you need a query you did not model.

| | Relational (MySQL) | Typical NoSQL (key-value, wide-column, document) |
|---|---|---|
| Schema | Declared up front, enforced by the database | Flexible; the application enforces shape |
| New query tomorrow | Add an index or write a join | Often a new table or a copy of the data |
| Joins | Native | Usually none; denormalise or join in the application |
| Transactions | Multi-row, multi-table | Often one key or one partition (some stores now offer more) |
| Scaling writes | Vertical first, then shard with extra tooling | Designed to partition from day one |
| Strength | Correctness, flexibility, mature tooling | Predictable latency at huge scale on known access paths |

Two facts keep you honest. **"NoSQL means no transactions" is out of date**: MongoDB has multi-document transactions, DynamoDB has transactional writes, Cassandra has compare-and-set "lightweight transactions". The question is what is *cheap* in each store, not what is possible. And two more families exist: **distributed SQL** (Spanner, CockroachDB, TiDB, YugabyteDB) spreads SQL and transactions across nodes and pays with coordination latency on writes; **columnar warehouses** (BigQuery, Redshift, ClickHouse) scan a few columns over billions of rows for analytics, not for your per-request path.

**One source of truth, many derived copies.** Using several stores is normal, but each fact has one home. The search index, the graph, the cache and the warehouse are *derived*: fed from the source by change-data-capture (CDC, reading the database's change log; for MySQL that is the binlog) or events (see <a href={`${BASE}sd/lessons/queues-streams/`}>Queues & streams</a>), and rebuildable from it.

**Worked numbers: the six questions.** The rates are assumptions for this example.

| Question | Peak rate (assumed) | Shape | Where it runs |
|---|---|---|---|
| Show a listing | 20,000 reads/s | One row by id, plus seller and photos | MySQL, behind a cache |
| Seller's active listings | 300 reads/s | One seller's rows, newest first | MySQL, composite index (Chapter 5) |
| Checkout | ~120 writes/s | Order + payment + stock, all or nothing | MySQL transaction |
| Latest messages | ~35,000 writes/s | Append-heavy; one conversation in time order | Wide-column, partitioned by conversation |
| Text search | 2,000 queries/s | Relevance, typos, filters | Search index fed by CDC |
| Fraud rings | A few a minute | Three-hop traversals | Graph store fed by events |

The interview shape, in one breath: *"I'll start with MySQL for the transactional entities. Messages are append-heavy, time-ordered and read by conversation, which fits a wide-column store like Cassandra partitioned by `conversation_id`."* Specific data, specific store, specific reason.

<Reveal q="“Why not one NoSQL database for everything? It scales.”">

For most data, scale is not the scarce resource. Flexibility is. Orders at 120 writes a second fit one MySQL primary for years. Put them in a store keyed for one access pattern and every new finance question becomes a new table or a full scan, and checkout atomicity becomes code you write and debug. Use the specialised store where an access pattern demands it (messages, search, traversals), and keep the transactional core relational.

</Reveal>

**Catch the trap:** logo-dropping. *"Cassandra because it scales"*, *"NoSQL is standard for chat"*. Each dies to *"why exactly?"*. Always say the data, its access pattern, the store, and the reason they fit.

<h2 id="modeling">Chapter 2 · Model the questions, not the nouns</h2>

Imagine a first draft schema with twelve tables, normalised, one per noun in the product spec: users, listings, photos, offers, reviews. Now write the query behind the home screen. It joins seven tables, 20,000 times a second. Nouns tell you what exists. Questions tell you how it must be laid out.

**Model from access patterns.** For every screen and API, write down the query, its rate, its latency budget and whether it must be transactional (the table in Chapter 1). Then shape the data so the hottest questions touch the fewest rows and places.

**Relationships, and where each one lives:**

- **One-to-one** (a user and their settings): if the two are read together, put them in the same row. Split them only if one side is large, rarely read, or has different access rules. Then key the second table by the first one's id, so the database enforces the "one".
- **One-to-many** (a seller and their listings): a foreign key on the *many* side. **Index it.** InnoDB requires an index on a foreign-key column and creates one if you do not (PostgreSQL does not). Without an index, "listings of seller 42" scans the table, and deleting a user scans listings to check for references.
- **Many-to-many**: a join table. It gets the whole next chapter.

```sql
CREATE TABLE users (
  id          BIGINT PRIMARY KEY,
  handle      VARCHAR(64) NOT NULL UNIQUE,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP   -- store UTC
) ENGINE=InnoDB;

-- 1:1, keyed by the user itself so there can only ever be one row per user
CREATE TABLE user_settings (
  user_id      BIGINT PRIMARY KEY,
  language     VARCHAR(8) NOT NULL DEFAULT 'en',
  push_offers  BOOLEAN NOT NULL DEFAULT TRUE,
  FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB;

-- 1:N, the foreign key lives on the many side
CREATE TABLE listings (
  id           BIGINT PRIMARY KEY,
  seller_id    BIGINT NOT NULL,
  title        VARCHAR(200) NOT NULL,
  price_cents  BIGINT NOT NULL CHECK (price_cents > 0),     -- enforced from MySQL 8.0.16; 8.0.15 and older accept it and ignore it
  status       ENUM('active', 'sold', 'removed') NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (seller_id) REFERENCES users(id),
  INDEX listings_by_seller (seller_id, status, created_at DESC)
) ENGINE=InnoDB;
```

**In a document store, embed or reference?** Embed what is *owned, bounded and read together*: an order's line items, a shipping address. Reference what is *shared or unbounded*: the seller (shared by many listings), the comments on a photo (unbounded).

**Normalise first, then denormalise on purpose.** Normalised data stores each fact once and joins at read time. Denormalising copies a fact next to where it is read. It is a trade, never a free speed-up:

| You gain | You pay |
|---|---|
| Fewer joins; one-key or one-partition reads | Every change to the fact must update every copy (write fan-out) |
| Predictable read latency on the hot path | Copies drift unless one owner keeps them in step: the same transaction, an event consumer, or a reconciliation job |
| A shape that fits one partition of a NoSQL store | Backfills whenever the fact's shape changes; more storage |

**Rule: denormalise facts that are read far more often than they change, and name who keeps the copy correct.**

**Worked numbers: the like count.** The feed shows a like count on every post: 400,000 post views a second, against about 5,000 likes a second (assumed). Normalised, every view runs `COUNT(*)` over the likes table. A viral post with 3 million likes makes each view walk 3 million index entries. Denormalised, each like adds one to a `like_count` column on the post (5,000 small updates a second spread across many posts), and every view reads one column.

The new cost: a single viral post getting 2,000 likes a second turns its row into a **hot row**, because each `UPDATE` holds that row's lock until commit and the next one waits. Shard the counter across several rows and sum them on read (the sharded-counter tool in <a href={`${BASE}sd/lessons/pattern-timeseries/`}>Time-series</a>).

**Single-table thinking, briefly.** In a wide-column store you design **one table per query**: `messages_by_conversation` and `conversations_by_user` hold overlapping data, each partitioned for one read. In DynamoDB's single-table style, several entity types share one table with keys shaped for the queries (partition key `USER#42`, sort key `ORDER#2026-10-07#981`), so "this user's orders, newest first" is one partition read. Both are denormalisation by design: you trade write fan-out and rigidity for one-hop reads, and you must know the questions before you write the first row.

<Reveal q="Joins are slow, so should a serious design avoid them?">

No. A join on indexed keys that returns a handful of rows costs well under a millisecond of database work. Joins hurt in two places: when one request joins many rows on a hot path (the seven-join home screen at 20,000 a second), and across shards, where the database cannot join at all and the application must. Denormalise for those cases, not as a reflex.

</Reveal>

**Catch the trap:** *"I'll denormalise for performance."* Say which fact you copy, which read it serves, and who updates the copies, and what a reader sees while they disagree.

<h2 id="many-to-many">Chapter 3 · Many to many</h2>

A product asks for Events: people host meetups, you RSVP, you see who is going, and you see your own calendar. A first sketch adds an `attendee_ids` array column to `events`. "Who is going to Saturday's photo walk?" works. "Which events is user 42 going to?" does not. **Every many-to-many has two questions, one from each side. Design for both.**

**A many-to-many relationship** is one where each side can have many of the other: a user attends many events; an event has many attendees. Users follow many users; users are followed by many users. Neither side can hold the relationship in one column without breaking the other side's question.

**Why an array or comma-separated column fails:**

- **The reverse question scans.** "Which events is user 42 going to?" must look inside every event row. (MySQL 8.0.17+ has multi-valued indexes on JSON arrays, which help lookups, but the next three problems remain.)
- **No integrity.** Nothing stops an id that points at a deleted user, or the same id twice.
- **Contention.** Every RSVP rewrites one ever-growing row that thousands of people update at once.
- **Nowhere to put facts about the relationship**: the RSVP answer, who invited whom, when.

**The fix is a join table** (also called a junction or associative table): **one row per pair**, a composite primary key that forbids duplicates, foreign keys to both sides, **an index in each direction**, and the relationship's own attributes on the row.

```sql
CREATE TABLE events (
  id          BIGINT PRIMARY KEY,
  host_id     BIGINT NOT NULL,
  title       VARCHAR(200) NOT NULL,
  starts_at   DATETIME NOT NULL,             -- an instant, stored in UTC
  ends_at     DATETIME NOT NULL,
  tz          VARCHAR(64) NOT NULL,          -- IANA zone for display, e.g. 'Europe/Berlin'
  FOREIGN KEY (host_id) REFERENCES users(id),
  CHECK (ends_at > starts_at)
) ENGINE=InnoDB;

CREATE TABLE event_attendees (
  event_id    BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  rsvp        ENUM('yes', 'no', 'maybe') NOT NULL,
  invited_by  BIGINT NULL,
  starts_at   DATETIME NOT NULL,             -- copied from events (see below)
  PRIMARY KEY (event_id, user_id),           -- serves "who is coming to event 9?"
  INDEX event_attendees_by_user (user_id, starts_at),  -- the reverse direction, already in time order
  FOREIGN KEY (event_id) REFERENCES events(id),
  FOREIGN KEY (user_id)  REFERENCES users(id),
  FOREIGN KEY (invited_by) REFERENCES users(id)
) ENGINE=InnoDB;
```

`starts_at` on the join table is a deliberate **denormalisation**: "my upcoming events" is answered from one index, in order, without visiting every event. The cost is the one Chapter 2 warned about: rescheduling an event with 1,000 attendees updates 1,000 attendee rows, in the same transaction as the event. Rescheduling is rare; opening your calendar happens every time the app starts. The trade is worth it, and you can say why.

**The queries it serves:**

```sql
-- 1. Who is coming to event 9?  (primary key: leading event_id)
SELECT u.id, u.handle, a.rsvp
FROM event_attendees a JOIN users u ON u.id = a.user_id
WHERE a.event_id = 9 AND a.rsvp = 'yes';

-- 2. My next 20 events  (reverse index: leading user_id, then starts_at)
SELECT e.id, e.title, e.starts_at, a.rsvp
FROM event_attendees a JOIN events e ON e.id = a.event_id
WHERE a.user_id = 42 AND a.starts_at >= UTC_TIMESTAMP()
ORDER BY a.starts_at LIMIT 20;

-- 3. Is user 42 going to event 9?  (one primary-key lookup)
SELECT rsvp FROM event_attendees WHERE event_id = 9 AND user_id = 42;

-- 4. RSVP, safely retryable: a second tap updates instead of duplicating
INSERT INTO event_attendees (event_id, user_id, rsvp, starts_at)
SELECT id, 42, 'yes', starts_at FROM events WHERE id = 9
ON DUPLICATE KEY UPDATE rsvp = 'yes';

-- 5. Does event 9 clash with anything user 42 already said yes to?
SELECT e.id, e.title
FROM event_attendees a
JOIN events e ON e.id = a.event_id
JOIN events n ON n.id = 9
WHERE a.user_id = 42 AND a.rsvp = 'yes' AND e.id <> 9
  AND e.starts_at < n.ends_at          -- two intervals overlap when each
  AND e.ends_at   > n.starts_at;       -- starts before the other ends
```

**A self-referencing many-to-many: follows.** Same shape, both columns point at users.

```sql
CREATE TABLE follows (
  follower_id  BIGINT NOT NULL,
  followee_id  BIGINT NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (follower_id, followee_id),                -- "whom do I follow?"
  INDEX follows_by_followee (followee_id, follower_id),  -- "who follows me?"
  CHECK (follower_id <> followee_id)
) ENGINE=InnoDB;

-- Mutuals: people 42 follows who follow 42 back
SELECT f1.followee_id
FROM follows f1
JOIN follows f2 ON f2.follower_id = f1.followee_id AND f2.followee_id = f1.follower_id
WHERE f1.follower_id = 42;
```

**Worked numbers: how big is the follow graph?** Assume 50 million users following 200 accounts on average: **10 billion rows**. A row of two 8-byte columns plus a timestamp and per-row overhead is roughly 50 bytes. In InnoDB the secondary index on `(followee_id, follower_id)` stores its two columns, and its entry already contains the primary key, so figure roughly 30 bytes per row there. That is about 80 to 110 bytes per follow, so **10 × 10⁹ × ~100 B ≈ 1 TB** before replication. One large node can hold that; the write rate and the celebrity rows are what push you to shard.

**When you do shard, the reverse index becomes a second table**: `following` partitioned by `follower_id`, `followers` partitioned by `followee_id`, so a follow is two writes to two shards. Write one and derive the other from an event or the change log, and accept a moment where they disagree.

### Worked example: a calendar

The *Google Calendar* interview question is this chapter plus time.

- **Attendance is the many-to-many above**, with RSVP on the join row.
- **Single events** store instants in UTC plus the event's IANA zone name for display. (MySQL's `TIMESTAMP` converts through the session time zone and stops at 2038-01-19 03:14:07 UTC; `DATETIME` runs to year 9999 and is stored as given; MySQL 8.0 manual, checked 2026-10-19. Many teams store UTC in `DATETIME` instead.)
- **Recurring events store the rule, not the instances.** A series row holds an iCalendar recurrence rule (RFC 5545 `RRULE`, for example `FREQ=WEEKLY;BYDAY=MO`), the local start time and the zone. Either **expand on read** for the window being viewed, or **materialise instances** for a rolling horizon (say, the next year) so free/busy and clash checks become plain index range queries. That costs storage and a background job to extend the horizon, in exchange for simple reads.
- **Exceptions** (one meeting moved, one cancelled) are override rows keyed by `(series_id, original_start)`, or excluded dates.
- **Clashes** use the overlap rule from query 5: intervals `[s1, e1)` and `[s2, e2)` overlap exactly when `s1 < e2` and `s2 < e1`.

When a clash must be *impossible* rather than merely detected (one meeting room, never double-booked), note that **MySQL has no exclusion constraint** (PostgreSQL does). The usual MySQL options:

```sql
-- Option 1: fixed slots. A unique key makes a double booking impossible.
CREATE TABLE room_slots (
  room_id     BIGINT NOT NULL,
  slot_start  DATETIME NOT NULL,           -- e.g. 30-minute slots, UTC
  booking_id  BIGINT NOT NULL,
  PRIMARY KEY (room_id, slot_start)
) ENGINE=InnoDB;
-- A 90-minute booking inserts 3 rows in one transaction. A clash fails with a duplicate-key error.

-- Option 2: free-form ranges. Serialise per room with a row lock, then check overlap.
BEGIN;
SELECT id FROM rooms WHERE id = 5 FOR UPDATE;          -- everyone booking room 5 queues here
SELECT 1 FROM room_bookings
 WHERE room_id = 5 AND starts_at < :new_end AND ends_at > :new_start LIMIT 1;
-- app: if a row came back, ROLLBACK. Otherwise INSERT the booking, then COMMIT.
```

<Reveal q="Why store a weekly 9 a.m. meeting as local time plus a zone, rather than as a UTC time?">

Daylight saving. 9:00 in New York is 13:00 UTC in summer (UTC−4) and 14:00 UTC in winter (UTC−5). A series stored as "every Monday at 13:00 UTC" drifts to 8:00 local when the clocks change in November. Store the wall-clock time and the zone for the rule; convert each instance to UTC when you expand it.

</Reveal>

**Many-to-many in a NoSQL store** is the same two-direction idea. In DynamoDB's adjacency-list style, an item with partition key `EVENT#9` and sort key `USER#42` holds the RSVP; querying `EVENT#9` lists attendees. A global secondary index that swaps the two keys answers "events for `USER#42`". Base table plus inverted index is exactly a join table plus its reverse index.

<h2 id="storage-engines">Chapter 4 · How an index is stored</h2>

Suppose a device-events table takes 40,000 inserts a second and the disk is pinned at 100% utilisation while CPU is fine. The index structure is the reason. A tree of pages and a stack of sorted files both keep data sorted; they disagree about *when* to pay for it.

An index exists so the database can **seek** instead of **scan**: jump to the rows it needs in a sorted structure, rather than reading fifty million rows to find twenty. There are two great families of sorted structure on disk.

### The B+tree (InnoDB, and most relational databases)

Data lives in fixed-size **pages**: **16 KB by default in InnoDB** (`innodb_page_size`; 8 KB in PostgreSQL). A **B+tree** is a B-tree variant where internal pages hold only keys and child pointers, and **all the data sits in the leaf pages**, which are linked to their neighbours for range scans. A lookup goes root, internal page, leaf. Each page holds many entries, so the tree is shallow.

To write, the engine finds the leaf, changes it in place (splitting it if it is full), and records the change in the **redo log** (the write-ahead log) first, so a crash can be recovered. InnoDB also keeps **undo logs** (old row versions, used for rollback and MVCC snapshots) and a **doublewrite buffer** so a half-written 16 KB page after a crash can be repaired.

<Figure caption="A B+tree lookup is one root-to-leaf path. Leaves are linked, so a range scan walks sideways.">
  <Mermaid code={`flowchart TD
    R["Root page\n… | 3,000,000 | 6,000,000 | …"] --> I1["Internal page\n… | 3,010,000 | 3,020,000 | …"]
    R --> I2["Internal page\n…"]
    I1 --> L1["Leaf page\nkeys 3,010,000 – 3,010,399"]
    I1 --> L2["Leaf page\nkeys 3,010,400 – 3,010,799"]
    L1 -.->|next leaf| L2`} />
</Figure>

**Worked numbers: how deep?** Take a deliberately round example of 400 keys per page. One level reaches 400 keys, two reach 160,000, three reach 64 million, and **four reach 25.6 billion**. In real InnoDB a `BIGINT` primary-key internal page fits roughly a thousand child pointers (an estimate; it depends on key size), while a leaf holds fewer, bigger entries, because it holds whole rows. The conclusion does not change: **a billion-row index is three to four levels deep**. The root and upper pages are hit so often that they stay in memory (the **buffer pool**), so a lookup costs about **one or two disk reads**.

### Clustered and secondary indexes in InnoDB

This is the single most useful InnoDB fact for design questions.

- **The primary key is the clustered index.** InnoDB stores the whole row *inside the leaves of the primary-key B+tree*. The table *is* that tree, sorted by primary key. (With no primary key, InnoDB uses the first `UNIQUE NOT NULL` index, else a hidden 6-byte row id. Always define a primary key.)
- **A secondary index stores the indexed columns plus the primary-key columns** in its leaves. The primary key is the pointer back to the row.

So a lookup through a secondary index is **two B+tree walks**: find the primary-key value in the secondary index, then walk the clustered index to fetch the row. That second step is called a *bookmark lookup* or *back to the table*.

<Figure caption="Lookup by a secondary index: walk the secondary tree to get the primary key, then walk the clustered tree to get the row.">
  <Mermaid code={`flowchart LR
    Q["WHERE seller_id = 42"] --> S["Secondary index\n(seller_id, ...) leaves hold\nindexed columns + PK"]
    S -->|"PK values 901, 977, ..."| C["Clustered index (PK)\nleaves hold full rows"]
    C --> ROW["row data"]`} />
</Figure>

Consequences you can say in an interview:

1. **A wide or random primary key taxes every secondary index.** Each secondary entry carries a copy of the PK. A 16-byte UUID instead of an 8-byte `BIGINT` adds 8 bytes to *every entry of every secondary index* (assumption: five secondary indexes on a billion-row table is about 40 GB extra, before page overhead).
2. **Insert order into the clustered index matters.** An increasing key appends to the right edge. A random key lands on random leaf pages, splits them, and leaves them partly empty (Chapter 13).
3. **Primary-key lookups and range scans are the cheapest reads.** Rows with nearby keys are physically near each other.
4. **Twenty rows through a secondary index can mean twenty random primary-key lookups.** If the query selects only columns present in the secondary index, the second walk is skipped. That is a *covering index* (Chapter 5).

**In PostgreSQL** the contrast is: rows live in an unordered heap and every index, including the primary key, points into it.

### The LSM-tree (Cassandra, ScyllaDB, HBase, RocksDB)

The LSM-tree (log-structured merge-tree) never updates in place.

1. A write is appended to a **commit log** (for crash recovery) and inserted into the **memtable**, a sorted structure in memory. That is the whole write: sequential I/O only.
2. When the memtable fills, it is flushed to disk as an immutable sorted file, an **SSTable**.
3. **Compaction** runs in the background, merging SSTables, keeping the newest version of each key and dropping overwritten values and old **tombstones** (deletes are written as markers, not erasures).
4. A read checks the memtable, then SSTables from newest to oldest. Each SSTable carries a **Bloom filter** that can say "definitely not here", so most files are skipped without touching disk.

<Figure caption="LSM write path: cheap sequential writes now, sorting and merging later in the background.">
  <Mermaid code={`flowchart LR
    W["write"] --> CL["commit log\n(append only)"]
    W --> MT["memtable\n(sorted, in memory)"]
    MT -->|"flush when full"| S3["SSTable (newest)"]
    S3 --> C["compaction\nmerge + drop old versions"]
    S2["SSTable"] --> C
    S1["SSTable (oldest)"] --> C
    C --> M["one larger SSTable"]`} />
</Figure>

**Write amplification** is the bytes the engine writes to disk divided by the bytes you asked it to write. Both families pay it, at different times:

- **B+tree**: change a 100-byte row and the engine eventually writes its whole 16 KB page (up to 160 times the data, if nothing else on the page changed before flush), plus the redo log record and the doublewrite copy. InnoDB's *change buffer* softens this for secondary-index changes by batching them (MySQL 8.0 manual, "Change Buffer"; it does not apply to the clustered index, and unique indexes need a duplicate check, so the benefit is for non-unique ones).
- **LSM**: each byte goes to the commit log, then to a flushed SSTable, then is rewritten every time compaction merges it into a larger file. Over a key's life that can be **ten times or more**, depending on the strategy and workload. The difference is that these are large sequential writes, done in the background.

| | B+tree (InnoDB) | LSM-tree |
|---|---|---|
| Write path | Find the leaf page, change it in place (plus redo log) | Append to the log and memtable; sort and merge later |
| Write cost | Random page writes; a whole page per small change | Sequential writes; compaction rewrites data several times |
| Read cost | One root-to-leaf path, ~1–2 disk reads | Memtable plus possibly several SSTables; Bloom filters bound it |
| Range scans | Excellent: leaves are in key order | Good, but merges across files |
| Space | Partly empty pages after splits | Old versions and tombstones until compaction; compresses well |
| Latency | Steady | Compaction competes for disk and can cause spikes |
| Fits | Read-heavy and update-heavy transactional work | Write-heavy, append-mostly data |

<Trace title="Choose the engine" steps={storage} takeaway="B+trees pay at write time with random page rewrites and read predictably. LSM-trees write sequentially and pay later in compaction, with Bloom filters keeping reads cheap." />

<Reveal q="If LSM-trees write so well, why isn't every database an LSM?">

Reads may consult several files, compaction competes with foreground traffic and causes latency spikes, and tuning it is a craft of its own. B+trees give steady reads and in-place updates, which suits read-heavy, update-heavy transactional work. Some ecosystems offer both: MySQL-compatible servers such as Percona Server and MariaDB can run InnoDB (B+tree) or MyRocks (an LSM engine built on RocksDB) side by side.

</Reveal>

**Catch the trap:** *"NoSQL is faster."* Speed comes from the storage engine and the access path, not the label. A B+tree database drowns in scattered inserts; an LSM store suffers under read-modify-write and ad-hoc reads.

<h2 id="composite-indexes">Chapter 5 · Composite indexes, covering indexes and EXPLAIN</h2>

Suppose the seller dashboard takes four seconds. `EXPLAIN ANALYZE` shows an index scan that walked thirty-one million entries and threw away all but twenty. "But there is an index," someone says, "on `created_at` and `seller_id`." The order of the columns is the whole game.

**A composite index is sorted by its first column, then by the second within each first, and so on**, like a phone book sorted by surname, then first name:

- "Okafor, Dev": both columns, one seek.
- Every Okafor: the **leftmost prefix**, one seek, then read along.
- Every Dev: the second column alone. The Devs are scattered through every surname, so you read the whole book.
- Surnames from O to P, first name Dev: a range on the first column. You walk the whole O-to-P section checking first names. The range stops the second column from narrowing the seek; it can only filter.

**The rules that follow:**

1. **Leftmost prefix.** An index on `(a, b, c)` serves filters on `a`; on `a` and `b`; on `a`, `b` and `c`. Not on `b` alone or `c` alone. (MySQL 8.0.13+ can sometimes use an *index skip scan* when the leading column has few distinct values; EXPLAIN shows `Using index for skip scan`. Never design on it.)
2. **Equality columns first, then the range or sort column.** After the first range column, later columns cannot narrow the seek.
3. **`ORDER BY` comes free when it follows the equality prefix in index order.** The engine reads rows already sorted and stops at the `LIMIT`, with no sort step (no `Using filesort`). MySQL 8 supports true descending index columns, and can also read an ascending index backwards.
4. **Order the equality columns by what else they must serve.** "Most selective column first" matters less than people think for pure equality lookups. Pick the order whose prefixes also serve your other queries.
5. **A covering index answers from the index alone** (next section).
6. **Every index is paid for on every write.** Each insert, each delete, and each update to an indexed column must maintain every index.

<Figure caption="Index on (seller_id, status, created_at DESC). One seek lands on seller 42's active listings, already newest first; read 20 entries and stop.">
  <ArrayStrip values={['41·active·10-02', '42·active·10-06', '42·active·10-04', '42·active·09-30', '42·sold·10-05', '43·active·10-07']} indices={false} pointers={[{ at: 1, label: 'seek here', tone: 'gold' }]} regions={[{ from: 1, to: 3, label: 'seller 42, active, newest first', tone: 'green' }]} tones={{ 0: 'ghost', 4: 'ghost', 5: 'ghost' }} />
</Figure>

```sql
-- The dashboard query
SELECT id, title, price_cents
FROM listings
WHERE seller_id = 42 AND status = 'active'
ORDER BY created_at DESC
LIMIT 20;

-- Equality, equality, then the sort column
CREATE INDEX listings_by_seller ON listings (seller_id, status, created_at DESC);
```

**Worked numbers.** `listings` holds 50 million rows. With the old index on `(created_at, seller_id)`, the engine walks backwards through time checking every listing for seller 42; for a seller whose last listing is months old, that is tens of millions of entries. With `(seller_id, status, created_at DESC)` it descends about three or four levels and reads one leaf page of 20 entries, then fetches 20 rows through the clustered index.

The write side: a table with **six secondary indexes means seven structures to update per insert** (clustered plus six). At 120 inserts a second that is nothing; on the 35,000-a-second messages table it would be 245,000 structure updates a second. Index the queries you serve, and no others.

### Covering indexes

A **covering index** contains every column the query touches, so the engine answers from the index and never goes back to the clustered index. In EXPLAIN this shows as `Extra: Using index`.

In InnoDB every secondary index already carries the primary key. So `SELECT id ... WHERE seller_id = 42` is already covered by an index on `seller_id`. MySQL has no `INCLUDE` clause (PostgreSQL does), so to cover more columns you append them to the index key:

```sql
-- Covers id (implicit PK), price_cents and title for the dashboard query
CREATE INDEX listings_by_seller_cov
  ON listings (seller_id, status, created_at DESC, price_cents, title);
```

The trade: the extra columns sit at the end of the key, so they do not change the seek, but they make the index bigger, make every write to those columns touch the index, and there is a maximum key length (MySQL 8.0 manual, checked 2026-10-19: 3,072 bytes with the default 16 KB page and DYNAMIC row format, less for smaller pages or older row formats; at most 16 columns). Covering pays off for hot, read-heavy queries over a few narrow columns. Do not append a long `TEXT` column.

### Reading EXPLAIN

`EXPLAIN` shows the plan without running the query. `EXPLAIN ANALYZE` (MySQL 8.0.18+) actually runs it and adds real row counts and timings. The `rows` column in plain EXPLAIN is an **estimate** from index statistics.

```text
mysql> EXPLAIN SELECT id, title FROM listings
       WHERE seller_id = 42 AND status = 'active' ORDER BY created_at DESC LIMIT 20\G
         table: listings
          type: ref
possible_keys: listings_by_seller
           key: listings_by_seller
       key_len: (bytes of the key actually used)
           ref: const,const
          rows: 380
      filtered: 100.00
         Extra: NULL      (no Using filesort: the index order serves ORDER BY)
```

The illustrative output above is typical, not exact; versions differ. The columns to read first:

| Column | What it tells you | Read it as |
|---|---|---|
| `type` | How the table is accessed | Best to worst: `const`/`eq_ref` (one row by unique key), `ref` (equal-match on an index), `range` (index range), `index` (full index scan), `ALL` (full table scan) |
| `key` | Which index was chosen | `NULL` means no index. Compare with `possible_keys` |
| `key_len` | How many bytes of the index were used | Tells you how many leading columns served the seek. A shorter key_len than expected means later columns only filtered |
| `rows` | Estimated rows examined | Compare to the rows you return. 20 returned from 3 million examined is the bug |
| `filtered` | Percent of examined rows expected to pass the remaining conditions | Low means wasted reads |
| `Extra` | Extra facts | See below |

| `Extra` value | Meaning | Good or bad |
|---|---|---|
| `Using index` | Covering index, no row lookup | Good for hot reads |
| `Using where` | Some conditions are checked after rows are read | Neutral; bad if `rows` is huge |
| `Using index condition` | Index condition pushdown: the engine filters on index columns before fetching rows | Good |
| `Using filesort` | A separate sort step (the name does not mean a disk file) | Bad on large sets: look for an index that gives the order |
| `Using temporary` | An internal temporary table (often with GROUP BY or DISTINCT) | Watch on large sets |

**Why the optimiser ignores an index you thought it would use:**

- **A function on the column**: `WHERE DATE(created_at) = '2026-10-07'` cannot seek. Rewrite as a range: `created_at >= '2026-10-07' AND created_at < '2026-10-08'`. (MySQL 8.0.13+ also allows functional indexes.)
- **Type or collation mismatch**: comparing a `VARCHAR` column to a number, or joining columns with different character sets, can force a scan or cast.
- **Leading wildcard**: `LIKE '%fender'` cannot use the index; `LIKE 'fender%'` can.
- **Low selectivity**: if `status = 'sold'` matches 90% of the table, scanning is cheaper than 90% of the table in random lookups. That is the right choice, not a bug.
- **Stale statistics**: after bulk loads, `ANALYZE TABLE` refreshes them.
- **Dropping an index safely**: make it *invisible* first (`ALTER TABLE ... ALTER INDEX name INVISIBLE`, MySQL 8.0). The optimiser stops using it but it is still maintained, so you can bring it back instantly. The `sys` schema (`sys.schema_unused_indexes`) lists candidates, but check usage over a full business cycle.

<Trace title="Order the columns" steps={indexes} takeaway="Leftmost prefix; equality first, then range or sort; cover the hot query when it pays; and remember every index taxes every write." />

<Reveal q="There's an index on (a, b). Do you also need one on (a)?">

No. Through the leftmost-prefix rule, `(a, b)` already serves queries on `a` alone. A separate `(a)` index only adds write cost. An index on `(b)`, though, is a genuinely different index, because the `(a, b)` one cannot help a query that filters on `b` alone.

</Reveal>

**Catch the trap:** *"I'll add an index."* Which columns, in which order, serving which query? Unindexed queries on big tables in your design are the interviewer's easiest kill shot; the second easiest is an index in the wrong order.

<h2 id="acid">Chapter 6 · All or nothing</h2>

A wallet feature lets sellers keep earnings in the app. A deploy restarts the payments service in the middle of a transfer. The log shows a buyer's wallet debited €25 and the seller never credited. But when you look in the database, neither the debit nor the credit is there. The log said the transfer *started*. The database keeps only what **commits**.

A **transaction** groups several reads and writes into one unit. **ACID** names four guarantees, and each has a limit worth saying out loud.

| Letter | The promise | Not a promise of | How InnoDB keeps it |
|---|---|---|---|
| **Atomicity** | All of a transaction's writes take effect, or none do | Anything about concurrency | Undo log; incomplete transactions are rolled back on crash recovery |
| **Consistency** | Each transaction moves the data from one valid state to another, by your invariants | CAP's "every replica returns the latest write", a different idea with the same name | Constraints you declare (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys) plus your application logic |
| **Isolation** | Concurrent transactions do not see each other's partial work | Behaving as if run one at a time, unless you ask for SERIALIZABLE | MVCC snapshots and row locks, to the degree the isolation level says (next chapter) |
| **Durability** | Once commit returns, the data survives a crash | Surviving the loss of the machine or disk; that is replication and backups | Redo log flushed to disk at commit, when configured for it (see below) |

```sql
START TRANSACTION;
UPDATE wallets SET balance_cents = balance_cents - 2500
 WHERE user_id = 7 AND balance_cents >= 2500;      -- app checks ROW_COUNT() = 1, else ROLLBACK
UPDATE wallets SET balance_cents = balance_cents + 2500
 WHERE user_id = 9;
INSERT INTO wallet_transfers (transfer_id, from_user, to_user, amount_cents)
VALUES ('tr_8f3a', 7, 9, 2500);                     -- transfer_id is UNIQUE: a retried request cannot apply twice
COMMIT;
```

**Durability is a setting, not a given.** In InnoDB, `innodb_flush_log_at_trx_commit = 1` flushes the redo log to disk at every commit; `sync_binlog = 1` does the same for the binary log. With both at 1 a committed transaction survives a crash. Lower values trade a window of lost commits for speed. Engines use *group commit* (one flush for many transactions that commit together), so durability does not cost one flush per transaction.

**Autocommit.** By default each statement runs as its own transaction. So `UPDATE ... SET n = n + 1` is atomic by itself. Logic that spans several statements (read, decide, write) needs an explicit `START TRANSACTION`.

**Transactions stop at the edge of one database.** A transfer that spans two services or two shards has no single `COMMIT`. Two-phase commit exists, but it blocks if the coordinator fails at the wrong moment, so most designs use sagas, idempotency keys and an outbox, the tools in <a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a>.

<h2 id="isolation">Chapter 7 · What the others can see</h2>

Here is a real class of bug. An on-call rota has one rule: at least one engineer on call, always. The app enforces it: *count who is on call; if it is two or more, let me go off call.* One Friday night, two engineers tap *Go off call* in the same second. Each transaction counts two. Each takes one person off. Both commit. No error, no deadlock, every statement did what it was told. At 2 a.m. the pager rings into an empty rota.

The database broke no rule it had been given. Nobody asked it for the guarantee they needed.

**Isolation is the illusion that transactions run one at a time.** The full illusion, **SERIALIZABLE**, costs throughput or retries, so databases offer weaker levels. Each weaker level lets certain **anomalies** through. Learn the five by their shape:

1. **Dirty read.** You read another transaction's uncommitted write, which may later roll back. *You see a balance mid-transfer that never really existed.*
2. **Non-repeatable read** (read skew). You read the same row twice in one transaction and get different values, because someone committed in between.
3. **Phantom.** You run the same query twice and *different rows* match, because someone inserted or deleted matching rows.
4. **Lost update.** Two transactions each read a value, compute in the application, and write back; the second write silently erases the first.
5. **Write skew.** Two transactions read the same facts, then write *different* rows based on what they read. Each is valid alone; together they break an invariant. The empty rota.

(Every level prevents *dirty writes*, overwriting another transaction's uncommitted write, with row locks.)

**What the SQL standard says.** The standard defines four levels by three phenomena only:

| Level | Dirty read | Non-repeatable read | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | prevented | possible | possible |
| REPEATABLE READ | prevented | prevented | possible |
| SERIALIZABLE | prevented | prevented | prevented |

Lost update and write skew are not in that list, which is why engines with the same level names behave differently.

### How InnoDB implements the levels

**InnoDB's default is REPEATABLE READ** (PostgreSQL's is READ COMMITTED). To understand InnoDB, learn two kinds of read:

- **Consistent (snapshot) read**: a plain `SELECT`. It reads from an MVCC snapshot, using undo logs to reconstruct old row versions, and takes no locks. Under REPEATABLE READ the snapshot is established by the transaction's **first consistent read** (or immediately with `START TRANSACTION WITH CONSISTENT SNAPSHOT`) and reused for the whole transaction. Under READ COMMITTED each statement gets a fresh snapshot.
- **Locking / current read**: `SELECT ... FOR UPDATE`, `SELECT ... FOR SHARE`, `UPDATE`, `DELETE`. These read the **latest committed** version, not the snapshot, and lock what they touch.

This split explains most surprises. Under REPEATABLE READ a transaction can *read* 100 from its snapshot while the latest committed value is already 120, and `UPDATE ... SET balance = balance + 50` will correctly apply to 120, because the update is a current read.

**Locks InnoDB takes** (the ones interviews ask about):

| Lock | What it covers | When |
|---|---|---|
| **Record lock** | One index record | Locking reads and writes on an index entry |
| **Gap lock** | The gap *between* index records (not the records) | REPEATABLE READ locking reads on ranges |
| **Next-key lock** | A record plus the gap before it | Default for locking reads under REPEATABLE READ; how InnoDB blocks phantom inserts into a range you locked |
| **Insert intention lock** | A signal that an insert wants a spot inside a gap | Inserts; it waits if another transaction holds a gap lock there |

Two practical facts follow. First, under **READ COMMITTED** InnoDB does not take gap locks for searches and index scans (only for foreign-key and duplicate-key checks), so phantoms can appear but there are fewer lock waits and deadlocks. It needs `binlog_format` set to ROW (or MIXED): with STATEMENT, writes at READ COMMITTED fail with error 1665. Second, a locking read or write that **cannot use an index** locks every row it scans (and, under REPEATABLE READ, the gaps), which can stall a whole table. This is one more reason to index the columns of your `WHERE` clauses.

**What each level does for each anomaly in InnoDB, with PostgreSQL for contrast:**

| Anomaly | READ COMMITTED (both) | REPEATABLE READ: InnoDB | REPEATABLE READ: PostgreSQL | SERIALIZABLE: InnoDB | SERIALIZABLE: PostgreSQL |
|---|---|---|---|---|---|
| Dirty read | prevented | prevented | prevented | prevented | prevented |
| Non-repeatable read | possible | prevented for plain `SELECT`s (one snapshot) | prevented | prevented | prevented |
| Phantom | possible | plain `SELECT`s see one snapshot; locking reads use next-key locks | prevented (snapshot) | prevented | prevented |
| Lost update (read in app, then write back) | possible | **possible** | prevented: the second writer gets a serialisation error and must retry | prevented (locks, may deadlock) | prevented |
| Write skew | possible | **possible** | possible | prevented | prevented |

- **READ UNCOMMITTED** in InnoDB can show dirty reads. Almost nobody should use it. (PostgreSQL treats it as READ COMMITTED.)
- **InnoDB SERIALIZABLE** (with autocommit off) turns plain `SELECT`s into `SELECT ... FOR SHARE`. Conflicting transactions then wait for each other, and when they wait in a cycle InnoDB detects the **deadlock** and rolls one back (error 1213). Retry it. A lock that is waited on for too long fails with error 1205 (`innodb_lock_wait_timeout`, 50 seconds by default).
- **PostgreSQL SERIALIZABLE** uses a different technique (Serializable Snapshot Isolation): it aborts one transaction with a serialisation failure instead of blocking. Either way, **your code must retry**.
- The names do not travel between engines. For any other engine, read its documentation. Kleppmann's Hermitage tests (linked at the end) show what real systems do.

**Fixing write skew without SERIALIZABLE.** Lock the rows your decision depends on:

```sql
START TRANSACTION;
SELECT name FROM rota
 WHERE shift_id = 12 AND on_call = TRUE
 FOR UPDATE;                                -- locks every on-call row for this shift
-- app: only if 2 or more rows came back...
UPDATE rota SET on_call = FALSE WHERE shift_id = 12 AND name = 'A';
COMMIT;
```

The second engineer's identical `SELECT ... FOR UPDATE` now waits for the first to commit, then sees only one on-call row (it is a current read, so it sees the latest data), and refuses. For the lock to be narrow and fast, `(shift_id, on_call)` needs an index.

**This only works when the rows exist.** If the rule is about *absence* ("no booking exists for this room at this time"), there is nothing to lock. Under REPEATABLE READ, a `FOR UPDATE` range scan takes gap locks that block inserts into that gap, but two transactions can each hold a gap lock and then block each other's insert, ending in a deadlock. Prefer a unique constraint (a slot table, Chapter 3), a lock on a parent row (the room), or SERIALIZABLE with retries. Gap-lock behaviour is subtle: check the docs for the exact locks your query takes (`performance_schema.data_locks` in MySQL 8 shows them).

**Choosing a level in practice:** a common default is the engine's default plus targeted fixes (atomic statements, `FOR UPDATE`, constraints). Many teams also choose READ COMMITTED on InnoDB to cut gap-lock deadlocks, then rely on explicit locks. Reach for SERIALIZABLE, with a retry loop, when an invariant spans rows no single statement or constraint can protect.

<Reveal q="“Which isolation level would you run checkout in?”">

On InnoDB I would keep the default or use READ COMMITTED, *with the statements enforcing the invariants themselves*: a conditional stock decrement (`... <h2 id="concurrency-control">Chapter 8 · Two buyers, one guitar</h2>

A marketplace's first real bug report: two buyers, two order confirmations, one 1962 guitar. The checkout code does: *select the stock; if it is above zero, insert the order and decrement.* Two buyers, same millisecond, both read 1.

Read-then-write is the bug. **Close the gap between the check and the change.** In order of preference:

**1. Make it one atomic statement.** The database checks and changes under a row lock; the loser simply matches zero rows.

```sql
UPDATE inventory SET stock = stock - 1
 WHERE item_id = 7 AND stock > 0;           -- ROW_COUNT() = 1: you got it. 0: sold out.
```

**2. Let a constraint say no.** For a one-of-a-kind listing, a unique key makes a second live order impossible whatever the code does. MySQL has no partial unique index, so use a generated column that is `NULL` for cancelled orders (a unique index allows many `NULL`s):

```sql
ALTER TABLE orders
  ADD COLUMN live_listing_id BIGINT
    GENERATED ALWAYS AS (IF(status <> 'cancelled', listing_id, NULL)) STORED,
  ADD UNIQUE INDEX one_live_order_per_listing (live_listing_id);
```

**3. Pessimistic: lock first, then decide.** When the decision needs logic the database cannot express in one statement:

```sql
START TRANSACTION;
SELECT stock, price_cents FROM inventory WHERE item_id = 7 FOR UPDATE;   -- others wait here
-- app: check stock, apply today's discount rules...
UPDATE inventory SET stock = stock - 1 WHERE item_id = 7;
INSERT INTO orders (id, item_id, buyer_id, price_cents, status) VALUES (...);
COMMIT;
```

**4. Optimistic: read freely, write only if nothing changed.** A version column turns the write into a compare-and-set:

```sql
SELECT title, description, version FROM listings WHERE id = 42;    -- version = 7
-- ...ten minutes in the edit form...
UPDATE listings
   SET description = 'Sunburst finish, new frets', version = version + 1
 WHERE id = 42 AND version = 7;             -- ROW_COUNT() = 0: someone saved first. Reload and reapply.
```

**5. SERIALIZABLE and retry**, when the invariant is too wide for any of the above (Chapter 7).

| | Optimistic (version, compare-and-set) | Pessimistic (`SELECT ... FOR UPDATE`) |
|---|---|---|
| The bet | Conflicts are rare | Conflicts are likely |
| Cost with no conflict | Nothing extra | A lock held for the transaction |
| Cost on conflict | The loser redoes its work | The loser waits |
| Danger | Retry storms on hot rows | Lock waits, deadlocks, locks held across slow calls |
| Fits | Edit forms, profiles, long human think time, low contention | Short critical sections on contended rows: stock, seats, balances |

</Figure>

**Lock hygiene.** Hold a row lock for milliseconds, never across human think time and never across a call to another service. Lock rows in a consistent order (by id) so two transactions cannot deadlock. `NOWAIT` fails fast instead of queueing; `SKIP LOCKED` lets job-queue workers each grab a different row (both in MySQL 8.0+). Find who is blocking whom with `sys.innodb_lock_waits` or `performance_schema.data_lock_waits`, and long-open transactions in `information_schema.innodb_trx`.

**Worked numbers: a hot row's ceiling is one over the lock time.** If each purchase holds the guitar's stock row for 2 ms, that row serialises at most **1 ÷ 0.002 s = 500 purchases a second**. Call the payment provider inside the transaction, 300 ms while holding the lock, and the ceiling collapses to **about 3 a second**, with every other buyer queued behind it (and some hitting the 50-second lock wait timeout). Take the payment outside the lock: reserve, commit, charge, confirm.

<Reveal q="Ticketmaster-style seat holds: optimistic or pessimistic?">

Neither in the long-lock sense. Each seat is a row, and a hold is one atomic conditional update: `UPDATE seats SET held_by = ?, held_until = UTC_TIMESTAMP() + INTERVAL 10 MINUTE WHERE seat_id = ? AND (held_by IS NULL OR held_until < UTC_TIMESTAMP())`. One row changed means you hold it; payment happens later, outside any database lock, and an unpaid hold simply expires. The waiting-room and fairness parts live in <a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a>.

<h2 id="replication">Chapter 9 · Leader and followers</h2>

A seller changes a price from €400 to €350, saves, and the page comes back showing €400. She saves again, and then both edits land. The timeline: write to the primary at 14:02:11.200, read from replica two at 14:02:11.450, and replica two was 900 ms behind. Everything worked, just not in the order she lived it.

**Why replicate:** to survive a machine dying (availability), to spread reads (scale), to put data near users (latency), and to keep heavy reads such as reports away from the primary (isolation).

**Leader-follower** (MySQL now says *source* and *replica*) is the default. All writes go to the source. Here is how MySQL does it:

1. The source writes every committed change to its **binary log** (binlog). Use `binlog_format = ROW`: it logs the changed rows, which is the safe, deterministic format.
2. Each replica's **I/O (receiver) thread** copies binlog events into a local **relay log**.
3. The replica's **applier (SQL) threads** replay the relay log. Applying can be multi-threaded (`replica_parallel_workers`). Before MySQL 8.0.27 the default was 0 (one applier thread); from 8.0.27 it is 4 (MySQL 8.0 manual, checked 2026-10-19).
4. **GTIDs** (global transaction ids, `gtid_mode = ON`) label every transaction `source_uuid:n`, so a replica can say exactly which transactions it has, which makes failover and re-pointing safe.

<Figure caption="MySQL replication. Replication is asynchronous by default: the source does not wait for the replica.">
  <Mermaid code={`flowchart LR
    W["Writes"] --> P[("Source\nbinlog")]
    P -->|"binlog events"| IO1["Replica 1\nI/O thread → relay log"]
    P -->|"binlog events"| IO2["Replica 2\nI/O thread → relay log"]
    IO1 --> A1["applier threads → data"]
    IO2 --> A2["applier threads → data"]
    A1 --> READS["Reads"]
    A2 --> READS`} />
</Figure>

| Mode | Commit returns when… | On leader failure | Write latency |
|---|---|---|---|
| **Asynchronous** (the default) | the source has it | The unreplicated tail is lost | Lowest |
| **Semi-synchronous** | at least one replica has *received* it (written to its relay log) | Nothing acknowledged is lost, if that replica is promoted | One extra round trip |
| **Fully synchronous** (a general concept, not a standard MySQL mode) | every replica has it | Nothing lost | Highest; one slow replica stalls every write |

Two precise points on semi-synchronous replication in MySQL. With `AFTER_SYNC` wait point (the default; MySQL 8.0 manual, checked 2026-10-19), the source waits for the replica's acknowledgement *before* making the commit visible to other sessions, so a failover does not lose data a client already saw. And the acknowledgement means "received", not "applied", so **a semi-sync replica can still serve stale reads**. If no replica acknowledges within the timeout, the source silently falls back to asynchronous. MySQL **Group Replication** and InnoDB Cluster go further (a consensus protocol among members); check the docs for their exact guarantees.

Whatever you choose, *say* what you accept: *"async, so a failover can lose the last second of writes."*

**Failover** promotes a replica when the source dies. Three things go wrong: the async tail is lost (and if the new source reissues ids the old one had already used, data can collide); the old source comes back believing it still leads (**split brain**, so fence it off and keep it `read_only`); and a timeout that is too short fails over during a mere slow patch.

**Replication lag creates three classic anomalies:**

| Missing guarantee | Symptom | Fix |
|---|---|---|
| **Read-your-own-writes** | Your own edit vanishes after reload | Read what the user just changed from the source for a short window; or remember the write's GTID and read from a replica only once it has applied it |
| **Monotonic reads** | A comment appears, vanishes, reappears | Pin each user to one replica (hash the user id) |
| **Consistent prefix** | An answer appears before its question | Keep causally related writes in the same partition, or track causality |

Waiting for a position is concrete in MySQL: `SELECT WAIT_FOR_EXECUTED_GTID_SET('uuid:1-12345', 1)` on the replica blocks until that GTID set has been applied (or the timeout, in seconds, expires). To learn a write's GTID, the client can read it from the OK packet using `session_track_gtids = OWN_GTID`, or the application can query `@@gtid_executed` on the source; driver support varies (PyMySQL 1.2 and MySQL Connector/Python 9.4 do not expose it), so check yours. A simpler alternative is a short "read from the source" window after each write.

**Measuring lag.** `SHOW REPLICA STATUS` (`SHOW SLAVE STATUS` before 8.0.22) reports `Seconds_Behind_Source`. It is only a rough guide: it is based on timestamps, can read 0 while the replica is stuck waiting for events, and can jump. A heartbeat row updated on the source every second (the technique behind `pt-heartbeat`) and compared on the replica is more trustworthy.

**What causes lag:** one big transaction (a 10-minute `UPDATE` on the source takes about that long to apply on the replica); a write burst the applier cannot parallelise; a replica on weaker hardware; DDL; and heavy reads on the replica competing for I/O.

**Worked numbers: replicas scale reads, never writes.** The listings table takes 40,000 reads and 2,000 writes a second (assumed). Four replicas serve 10,000 reads a second each, and **every replica still replays all 2,000 writes a second**. A fifth replica adds read capacity; write capacity does not move. Lag is usually milliseconds, but under a write burst or one huge transaction it can stretch to seconds or minutes.

<Trace title="Read the lag" steps={replicationLag} takeaway="Async replication means stale followers and a lossy failover. Give the author read-your-writes, give everyone monotonic reads, and say what failover can lose." />

<Reveal q="Does read-your-own-writes mean sending all of a user's reads to the source?">

No. That would make the source the bottleneck again. Send only reads of what the user just changed, for a short window (their profile for ten seconds after editing it), or have the client carry the GTID of its last write and let any replica that has applied it serve the read.

</Reveal>

**Catch the trap:** *"We'll add read replicas."* Say what lag does to your users, and which reads must not go to a replica.

<h2 id="multi-leader">Chapter 10 · More than one leader</h2>

A product lead asks for two things: low write latency for users in Brazil and Japan, and an Events calendar that works offline on the subway. That is multi-leader replication asked for twice. If two places can accept a write to the same row, at the same moment, without talking first, who wins?

**Multi-leader replication**: several nodes (one per region, or every offline phone) accept writes and replicate to each other asynchronously. A calendar app that works offline *is* a multi-leader system: every device is a leader until it syncs. The gain is local write latency and writes that survive a partition. **The price is conflicts**: two leaders accept different writes to the same record, and both must eventually agree.

For MySQL, treat multi-source or active-active setups with care. Two sources can both accept writes, but MySQL itself will not resolve conflicts for you (Group Replication in multi-primary mode is optimistic: conflicting transactions fail certification and are rolled back; MySQL 8.0 manual, checked 2026-10-19). A single writer with replicas is far simpler.

| Conflict strategy | How | Cost |
|---|---|---|
| **Avoid them** | Route all writes for a record to its home region | Awkward when the home region fails; the most practical default |
| **Last write wins** | Keep the version with the highest timestamp | Silently discards writes; clock skew picks the "winner" |
| **Merge** | Application logic combines versions (union of RSVPs) | Code per data type |
| **CRDTs** | Data types that merge automatically (counters, sets, text) | Only some shapes fit; see <a href={`${BASE}sd/lessons/pattern-sync-collab/`}>Sync & collaboration</a> |
| **Keep both, ask** | Store siblings; a person resolves | Pushes work onto users |

**Leaderless replication** (the design in Amazon's 2007 Dynamo paper; used by Cassandra and Riak; not to be confused with the DynamoDB service, which works differently inside). Every replica accepts writes. A write goes to all **N** replicas holding the key and succeeds after **W** acknowledge; a read asks **R** replicas and keeps the newest version it sees.

**If W + R > N, every read set overlaps every write set**, so at least one replica in any read has the latest acknowledged write. Replicas that missed writes are repaired by *read repair* (fix stale replicas a read noticed), *hinted handoff* (a stand-in holds writes for a down node, then hands them over) and *anti-entropy* (background comparison, often with Merkle trees). Cassandra lets you choose the level per request: `ONE`, `QUORUM`, `ALL`.

  <ArrayStrip name="read R = 2" values={['A', 'B', 'C']} indices={false} tones={{ 0: 'ghost', 1: 'blue', 2: 'blue' }} pointers={[{ at: 1, label: 'overlap', tone: 'gold' }]} />

**Worked numbers: the quorum table.**

| N | W | R | W + R > N? | Writes survive … down | Reads survive … down |
|---|---|---|---|---|---|
| 3 | 2 | 2 | yes (4 > 3) | 1 | 1 |
| 3 | 1 | 1 | **no** (2) | 2 | 2 |
| 3 | 3 | 1 | yes (4 > 3) | 0 | 2 |
| 5 | 3 | 3 | yes (6 > 5) | 2 | 2 |

**Overlap is not the same as strong consistency.** Concurrent writes to the same key, a write that succeeded on some replicas but failed overall, *sloppy* quorums that write to stand-in nodes during a partition, and timestamp-based conflict resolution can all still return stale or lose data. Quorums give you a strong probability of fresh reads, not linearizability. The theory sits in <a href={`${BASE}sd/lessons/core-concepts/`}>Core concepts</a> (CAP, the consistency ladder, quorums).

</Reveal>

<h2 id="capacity">Chapter 11 · Will it fit?</h2>

Before anyone may say the word *shard*, write two numbers on the board: rows per day and bytes per row, and finish the arithmetic. Half the sharding projects ever started should have been a bigger disk and an archive job. The other half started a year too late.

**The recipe:** rows per day → bytes per row, *including each index* → × 365 → × replication factor → compare with what one node holds comfortably. Then check peak writes per second against what one node sustains.

**Worked numbers** (assumptions in the first rows; sizes before compression):

| | Orders | Messages |
|---|---|---|
| Rows per day | 2 million | 20M daily users × 50 = **1 billion** |
| Average writes/s | 2,000,000 ÷ 86,400 ≈ 23 | 10⁹ ÷ 86,400 ≈ 11,600 |
| Peak (assumed multiplier) | 5× ≈ 116/s | 3× ≈ 35,000/s |
| Bytes per row with indexes | ~1 KB (wide row, several indexes) | ~200 B row + 2 index entries × ~40 B ≈ 280 B |
| Per day | 2 GB | 280 GB |
| Per year, one copy | 730 GB | ~102 TB |
| Per year, 3 copies | ~2.2 TB | ~307 TB |
| Verdict | **One primary and two replicas, for years** | **Partition from day one** |

For messages, at a comfortable ~10 TB per node (leaving room for compaction, rebuilds and growth; your number depends on your hardware): 102 TB ÷ 10 TB ≈ 10.2, so **11 nodes per copy per year, about 31 with three copies**, and next year adds as many again.

**Before you shard, climb this ladder.** Each rung is cheaper than the next:

1. **A bigger machine.** Vertical scaling goes further than people expect.
2. **Read replicas and caches** for read load (Chapter 15).
3. **Archive or expire cold data.** Most queries touch the last few months.
4. **Partition the table inside one MySQL server** (next chapter). It keeps indexes smaller and turns retention into an instant `DROP PARTITION` instead of a giant `DELETE`.
5. **Shard** across machines.

<Reveal q="Messages are partitioned by conversation. Why do designs often add a time bucket to the partition key?">

Because one conversation partition grows forever. An extreme group chat posting a message every second writes about 86,400 × 200 B ≈ 17 MB a day, so a month is about 0.5 GB in one partition. A key like `(conversation_id, month)` caps it; if that is still too large for your store's comfortable partition size (check its current guidance), bucket by day. Reading "the latest 50" then touches the current bucket, and occasionally the one before.

</Reveal>

**Catch the trap:** proposing sharding with no numbers, or doing the numbers without indexes and replication, which easily multiply raw size by four.

<h2 id="sharding">Chapter 12 · Partitioning versus sharding</h2>

Messages will be split from day one; that is settled. The argument is now about the key. Half the room wants `message_id` ("perfectly even!"). The other half wants `conversation_id`. The deciding question: *when a phone opens a chat, what does it ask for?*

### Two words that get mixed up

| | Partitioning (inside MySQL) | Sharding |
|---|---|---|
| What it is | One logical table split into physical partitions, on **one server** | Data split across **several servers**, each a separate database |
| Who routes queries | MySQL (partition pruning) | Your application, a proxy, or middleware such as Vitess |
| Helps with | Dropping old data fast, smaller indexes, pruning scans, maintenance | Data size and write throughput beyond one machine |
| Does not help with | Write capacity: it is still one primary | Nothing is free: loses joins and transactions across shards |
| Joins and transactions | Work normally | Cross-shard joins and transactions are gone or expensive |

**MySQL partitioning, concretely:**

```sql
CREATE TABLE messages (
  conversation_id BIGINT NOT NULL,
  message_id      BIGINT NOT NULL,
  created_at      DATETIME NOT NULL,
  body            VARCHAR(2000) NOT NULL,
  PRIMARY KEY (message_id, created_at)        -- every unique key must include the partitioning column
) ENGINE=InnoDB
PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
  PARTITION p202611 VALUES LESS THAN ('2026-12-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);

ALTER TABLE messages DROP PARTITION p202610;  -- retention: near-instant, unlike a huge DELETE
```

The main rules (MySQL 8.0 manual, checked 2026-10-19; the manual has the full list):

- **Every unique key, including the primary key, must contain all columns of the partitioning expression.** This is why `created_at` appears in the primary key above.
- **InnoDB partitioned tables cannot have foreign keys**, as parent or child.
- **Pruning only happens when the query filters on the partitioning column.** `EXPLAIN` shows the touched partitions in its `partitions` column. A query without it checks every partition.
- There is a maximum number of partitions per table (8,192). Asking for 8,193 fails with error 1499.
- It is still one server. Partitioning does nothing for write throughput or for losing the machine.

### Sharding: choosing the key

**Sharding** splits rows across nodes by a **shard (partition) key**; each row lives on exactly one shard (plus its replicas).

| Strategy | How | Good at | Bad at |
|---|---|---|---|
| **Hash** | Partition from a hash of the key | Even spread | Range scans across keys: they hit every shard |
| **Range** | Each shard owns a contiguous key range | Ordered range scans | A hot tail when keys grow monotonically (time, auto-increment): every new write hits the last shard |
| **Hash, then range** (compound) | Hash the first part to pick the shard; sort by the second inside it | Even spread *and* ordered reads within a shard: Cassandra's partition key plus clustering columns | Queries must supply the first part |
| **Directory** | A lookup table maps key → shard | Flexible placement (big tenants on their own shard) | An extra hop; the directory must be highly available |

**The whole game is choosing the key.** Test every candidate against two questions:

1. **Does it spread load evenly?** Sharding posts by `user_id` puts a celebrity's storm on one shard (a hot shard). Sharding by `post_id` spreads evenly.
2. **Do the common queries stay on one shard?** "All messages in conversation X" wants `conversation_id`: one shard answers. Shard by `message_id` and every conversation read becomes a scatter-gather across all shards, then a merge.

These two often conflict, and that tension *is* the deep dive. Say it explicitly: *"`user_id` keeps a user's data together for cheap queries but risks hot shards for power users; I'll take `user_id` and handle the celebrity case separately."*

**Name the cross-shard consequences before the interviewer does:**

- **No cross-shard joins.** Denormalise, or join in the application.
- **No cross-shard transactions.** Sagas and idempotency (<a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a>).
- **Secondary indexes get harder.** A *local* index (each shard indexes its own rows) makes any query by another column a scatter-gather. A *global* index is partitioned by the indexed value: one-shard reads, but every write now updates another shard too, usually asynchronously.
- **Uniqueness is only enforceable on the shard key.** Unique emails across user shards need a lookup table sharded by email.
- **Auto-increment ids collide** across shards (Chapter 13).

**Hot keys** (one key with far more traffic than the rest) do not spread however many shards you add, because a key lives on exactly one. Serve hot *reads* from a cache in front (the celebrity chapter in <a href={`${BASE}sd/lessons/caching/`}>Caching</a>); split hot *writes* by **salting** the key into sub-keys (`listing:77#0` … `#9`) and summing on read; or give the hottest tenants their own shard.

**Resharding.** Never map keys with `hash(key) mod N`: changing N moves almost every key. Going from 4 to 5 shards, a key stays put only if its hash leaves the same remainder mod 4 and mod 5, which is 4 of every 20 values, so **80% of the data moves**. Going from 16 to 17, about 94% moves. Instead, **pre-split into many fixed logical partitions** and map those to nodes; growing moves whole partitions. Consistent hashing gets the same effect with a ring. Both are taught in <a href={`${BASE}sd/lessons/pattern-partitioning/`}>Partitioning</a>.

<Figure caption="Fixed logical partitions. Keys never change partition; only the partition map changes when nodes are added.">
  <Mermaid code={`flowchart LR
    K["key"] -->|"hash mod 1024"| P["logical partition\n0 … 1023"]
    P -->|"partition map"| N1["node 1\npartitions 0–63"]
    P --> N2["node 2\npartitions 64–127"]
    P --> N16["node 16\npartitions 960–1023"]`} />
</Figure>

<ShardingSim shards={4} keys={1000} mode="mod" />

**Worked numbers.** 1,024 logical partitions on 16 nodes is 64 per node. Add a 17th node and it takes about 1,024 ÷ 17 ≈ 60 partitions, so **about 6% of the data moves**, against 94% with `mod N`. And the hot key: one flash-sale listing at 50,000 reads a second against a shard that serves about 10,000 needs a cache in front, not more shards. Its view counter, salted into 10 sub-keys, puts about 5,000 writes a second on each.

<Trace title="Choose the key" steps={sharding} takeaway="The hot query must carry the shard key; the key must spread load; hot keys need caching or salting; pre-split so growth moves partitions, not keys." />

<Reveal q="You shard users by user_id. How does login-by-email find the right shard?">

With a second table, `email → user_id`, sharded by email: a global secondary index you maintain yourself. Login reads it, then goes to the user's shard. It is also the only place a unique-email rule can be enforced, so the signup flow writes it first: claim the email, then create the user.

</Reveal>

**Catch the trap:** a shard key that the hottest query does not carry. And sharding before the numbers in Chapter 11 say you must.

<h2 id="ids">Chapter 13 · ID strategies</h2>

Suppose a shard split goes smoothly until someone notices *order 1048577 exists twice*. Each shard had its own auto-increment counter, and each was sure it was the only one. An ID is a promise that nobody, anywhere, will ever say the same number. One database keeps that promise by counting. Twenty databases cannot, unless they agree on how.

**What you want from an ID:** unique without coordination; compact (it sits in every index, and in InnoDB it is copied into every secondary index, so 64 bits beats 128); roughly time-ordered (inserts append to the index, and "newest first" comes free); not guessable when exposed in URLs; cheap to generate at your peak rate.

**Auto-increment** (`BIGINT UNSIGNED AUTO_INCREMENT`) is simple, dense and ordered on one node. Its limits:

- **One writer.** Two shards with their own counters both issue 42. (MySQL can offset counters with `auto_increment_increment` and `auto_increment_offset`, so shard 1 issues odd numbers and shard 2 even, but adding a shard means renumbering the scheme.)
- **Overflow.** A signed 32-bit `INT` stops at 2,147,483,647. At 1,000 inserts a second that is **under 25 days**. Use `BIGINT` from day one.
- **It leaks.** Sequential ids reveal your volume and let anyone enumerate your objects.
- **Gaps and order.** InnoDB does not give back values from rolled-back transactions or failed inserts, so gaps are normal, and concurrent transactions can commit out of id order.

**UUIDv4**: 122 random bits in 128; no coordination; collisions are not a practical worry. But random keys **land on random pages of the clustered index**: every insert touches a different leaf, pages split everywhere, they end up partly empty and the buffer pool thrashes. Because InnoDB clusters rows by primary key, the table scatters too, and every secondary index carries the 16-byte key (36 characters if someone stored it as text, which is much worse: store `BINARY(16)`).

**UUIDv7** (RFC 9562, 2024): a 48-bit Unix millisecond timestamp, then version and variant bits, then random bits. Same 128 bits as v4, but **time-ordered**, so inserts append. Order *within* one millisecond depends on the implementation. **ULID** is the same idea in a 26-character string. MySQL's `UUID()` makes a version 1 UUID whose time bits are in the wrong order for indexing; `UUID_TO_BIN(uuid, 1)` (MySQL 8.0) swaps them into a sortable layout and stores `BINARY(16)`. MySQL 8.0 has no built-in v7 generator (manual, checked 2026-10-19), so generate v7 ids in the application.

**Snowflake** (Twitter, 2010): a 64-bit integer built from three fields.

<Figure caption="Snowflake: 1 unused sign bit, 41 bits of milliseconds since a custom epoch, 10 bits of machine id, 12 bits of sequence. 1 + 41 + 10 + 12 = 64.">
  <ArrayStrip name="Snowflake" values={['0', '41 · ms since epoch', '10 · machine', '12 · sequence']} indices={false} tones={{ 0: 'ghost', 1: 'blue', 2: 'purple', 3: 'done' }} />
  <ArrayStrip name="UUIDv7" values={['48 · unix ms', '4 · version', '12 · random', '2 · variant', '62 · random']} indices={false} tones={{ 0: 'blue', 1: 'ghost', 2: 'done', 3: 'ghost', 4: 'done' }} />
</Figure>

**Worked numbers.** 2⁴¹ ms ≈ 2.2 × 10¹² ms ≈ **69.7 years** from your chosen epoch, which is why Snowflake counts from a recent custom epoch, not 1970. 2¹² = **4,096 ids per millisecond per machine**, about 4.1 million a second. 2¹⁰ = **1,024 machines** (Twitter split those bits into 5 for the datacenter and 5 for the worker).

**The parts that make Snowflake an interview answer, not a diagram:**

- **Machine ids must be unique.** Assign them from configuration, or lease them from a coordination service (ZooKeeper, etcd) so two live nodes can never share one.
- **Clock skew.** If the clock moves backwards (an NTP correction), the generator must **refuse, or wait, until the clock passes the last timestamp it used**; otherwise it can repeat a timestamp and, with the same machine id and sequence, issue a duplicate. Twitter's original implementation refused.
- **Sequence exhaustion.** More than 4,096 ids in one millisecond: wait for the next millisecond.
- **Ordering is per machine.** Ids from one machine are strictly increasing; across machines they are only *roughly* time-ordered, because clocks differ by milliseconds.
- **JavaScript.** 64-bit ids exceed 2⁵³, the largest integer a JavaScript number holds exactly. Send them as strings in JSON.

**Ticket servers / range allocation:** a central service hands each app server a block of ids (say 10,000 at a time). Dense, compact, roughly ordered; the allocator must stay available, and a crashed server wastes the rest of its block.

| Strategy | Size | Time-ordered? | Coordination | Catch |
|---|---|---|---|---|
| **Auto-increment** | 64-bit (use `BIGINT`) | Yes, on one node | A single writer | Breaks when you shard; leaks volume |
| **UUIDv4** | 128-bit | No | None | Random inserts scatter the clustered index |
| **UUIDv7 / ULID** | 128-bit | By millisecond | None | Twice the size of 64-bit; order within a millisecond is implementation-defined |
| **Snowflake** | 64-bit | Roughly (exactly, per machine) | Machine-id assignment | Clock skew; ~69-year horizon; JavaScript precision |
| **Ticket server / ranges** | 64-bit | Roughly | A central allocator | Must stay available; gaps on crash |

**Interview default:** *"Snowflake-style or UUIDv7: time-ordered, so the clustered index appends instead of scattering, and no coordination per id."*

<Trace title="Name a billion things" steps={ids} takeaway="Time-ordered ids keep B+tree inserts at the right edge. Snowflake: 41 + 10 + 12 bits, ~69 years, 4,096 per ms per machine, and it must never run its clock backwards." />

<Reveal q="“Design a unique ID generator.” What do you ask, and what do you say, in sixty seconds?">

Ask: must ids fit in 64 bits? Must they sort by time? What peak rate, and across how many datacenters? Must they be unguessable? Then: *"Snowflake layout: 41 bits of milliseconds from a custom epoch (about 69 years), 10 bits of machine id leased from etcd so no two live nodes share one, 12 bits of sequence (4,096 per millisecond per node). </Reveal>

<h2 id="pooling">Chapter 14 · Too many connections</h2>

Black Friday, 9:00 a.m. The autoscaler grows the app from forty pods to a hundred and twenty in four minutes. Then every new pod crashes on startup with `Too many connections` (MySQL error 1040). Database CPU: 30%. Memory: fine. Connections: all of them. How many queries can that machine actually run at once, and how many connections did we ask it to hold open?

**A connection is not free.** MySQL runs one thread per connection, each with its own buffers. The default `max_connections` is 151 (MySQL 8.0 manual, checked 2026-10-19); your server may set another value. A database can only *execute* as many queries at once as it has cores and I/O to run them. Thousands of mostly idle connections add memory and scheduling overhead and buy nothing. (PostgreSQL is heavier still: a process per connection.)

**Pooling** reuses a small set of connections:

- **In the application** (HikariCP in Java, SQLAlchemy's pool in Python): each process keeps a pool and borrows a connection per transaction.
- **An external proxy** (ProxySQL, or a managed proxy such as RDS Proxy) sits between many app processes and the database, multiplexing thousands of client connections onto a few dozen server connections. It can also route reads to replicas. Multiplexing breaks anything tied to a session (`SET` variables, temporary tables, session locks `GET_LOCK`, user variables), so check what your code relies on.

<Figure caption="Many pods, few database connections. The proxy absorbs the autoscaler's enthusiasm.">
  <Mermaid code={`flowchart LR
    A1["pod 1 … pod 120\n(10 client connections each)"] -->|"1,200 client connections"| B["ProxySQL\nconnection pooling"]
    B -->|"~40 server connections"| P[("MySQL primary")]`} />
</Figure>

**Worked numbers: Little's law sizes the pool.** Busy connections = arrival rate × time each one is held. At 5,000 queries a second holding a connection for 4 ms each: **5,000 × 0.004 = 20** connections busy on average. Add headroom for bursts and you need tens of server connections, not the 1,200 that 120 pods × 10 would open directly. (HikariCP's pool-sizing guide starts from roughly cores × 2 plus the number of disks, then measures.)

**Long transactions are worse than many.** A transaction left open ("idle in transaction") holds its connection and its row locks. In InnoDB it also holds an old MVCC snapshot, so the **purge** of old row versions from the undo log cannot advance, and the *history list length* grows (visible in `SHOW ENGINE INNODB STATUS`). Find them in `information_schema.innodb_trx`. Never hold a transaction open across a network call, and set sensible client-side timeouts.

<Trace title="Count the connections" steps={pooling} takeaway="Server connections should track what the database can execute in parallel (rate × hold time), not how many pods you run. Put a pooler in between." />

**Catch the trap:** *"We scale the app tier horizontally."* Every new pod multiplies database connections. Say where the pool or proxy sits.

<h2 id="replicas-vs-cache">Chapter 15 · Replica or cache?</h2>

The listing page is slow again at lunch, and two proposals arrive within the hour: two more read replicas, or a Redis cache. The question to ask: *what do the slow reads have in common?* Logs show 90% of the reads are for the same ten thousand listings. The other 10% are sellers' sales reports, and no two are alike.

| | Read replica | Cache |
|---|---|---|
| Holds | A full copy of the database | The hot working set, as values under keys you designed |
| Serves | Any query: joins, reports, the long tail | Lookups by those keys |
| Freshness | Replication lag: milliseconds, with spikes | TTL plus the invalidation you design |
| Cost per read | A real query on a full database server | A memory lookup, usually under a millisecond |
| Cost per write | Replays every write | An invalidation per write |
| Best when | Reads are diverse; reports need isolating; you also want a failover standby | A small set of keys is read over and over |

**Often both:** cache the hot keys, send the long tail and the reports to replicas, and send read-your-own-writes to the source.

<Figure caption="Where each kind of read goes.">
  <Mermaid code={`flowchart LR
    R["Reads"] --> H{"Hot repeated key?"}
    H -->|yes| C["Cache (Redis)"]
    H -->|"no: long tail, reports"| RR["Read replica"]
    W["Author reads own write"] --> P[("MySQL source")]
    C -.->|miss| RR`} />
</Figure>

**Worked numbers.** 40,000 reads a second; 90% (36,000) go to 10,000 popular listings of about 4 KB each, which is **40 MB**: trivially small for a cache. At a 95% hit ratio on those, 1,800 misses a second fall through, plus 4,000 long-tail reads, so **about 5,800 reads a second reach the database tier** instead of 40,000. Two more replicas would have bought capacity for the same hot pages at the price of two more full database servers. Designing the cache itself (key, TTL, invalidation, failure plan) is <a href={`${BASE}sd/lessons/caching/`}>Caching</a>.

<Reveal q="Cache misses are filled from a read replica. What can go wrong?">

A stale value can be cached right after an invalidation. The writer updates the source and deletes the key; a reader misses, reads a replica that has not applied the write yet, and puts the *old* value back, where it stays until the TTL expires. Fill misses for recently written keys from the source, use versioned values that refuse to overwrite newer data, or keep the TTL short enough that the window does not matter.

</Reveal>

**Catch the trap:** replicas for a hot-key problem, or a cache for ad-hoc report queries. Match the tool to the shape of the reads.

<h2 id="migrations">Chapter 16 · Changing a live schema</h2>

Here is a four-minute outage caused by a statement that never started. A one-line migration (add a column) on a busy table should have taken milliseconds. Instead it waited for a lock behind one slow analytics query, and while it waited, every other query on that table queued behind *it*. Now a team needs `users.name` renamed to `display_name`: two hundred million rows, with old and new code running side by side for an hour during the deploy. How do you change the shape of a table that nobody is allowed to stop using?

Two facts make schema changes dangerous. **Old and new code run at the same time** during every rolling deploy, so the schema must work for both at every instant. And **DDL needs a metadata lock (MDL)** on the table. In MySQL the `ALTER` must wait for every open transaction that has touched the table to finish, and while it waits, *new* queries on the table queue behind the waiting `ALTER`. A single forgotten open transaction plus one `ALTER` can stop all traffic to that table. That is the four minutes.

**Expand, migrate, contract** (also called parallel change). Every step is backward compatible, deployed and verified on its own:

1. **Expand.** Add the new column, nullable.
2. **Dual-write.** Deploy code that writes both `name` and `display_name`, still reading `name`.
3. **Backfill** existing rows in small batches.
4. **Switch reads** to `display_name` (still writing both). Verify: zero rows where the two differ.
5. **Stop writing** `name`.
6. **Contract.** Drop `name`.

Until step 6, every step can be rolled back by redeploying the previous code.

<Figure caption="Expand → migrate → contract. At every arrow, old and new code can run side by side.">
  <Mermaid code={`flowchart LR
    E["1 · Add column\n(nullable)"] --> D["2 · Write both"]
    D --> B["3 · Backfill\nin batches"]
    B --> R["4 · Read new"]
    R --> S["5 · Stop writing old"]
    S --> C["6 · Drop old column"]`} />
</Figure>

```sql
-- Give up and retry rather than queue everyone behind a waiting ALTER.
-- lock_wait_timeout governs metadata lock waits; its default is a year.
SET SESSION lock_wait_timeout = 2;

-- Ask for the cheap algorithm explicitly: the statement errors out instead of silently
-- falling back to a slow table copy.
ALTER TABLE users ADD COLUMN display_name VARCHAR(100) NULL, ALGORITHM=INSTANT;

-- Backfill one batch at a time; pause between batches so replicas keep up
UPDATE users SET display_name = name
 WHERE id >= 1 AND id < 10001 AND display_name IS NULL;

-- Add an index without blocking writes
ALTER TABLE users ADD INDEX users_by_display_name (display_name), ALGORITHM=INPLACE, LOCK=NONE;
```

**What MySQL's online DDL gives you.** `ALGORITHM=INSTANT` changes only metadata (adding a column is supported in 8.0, and some other changes). `ALGORITHM=INPLACE` rebuilds without copying the table to a new one, and `LOCK=NONE` allows concurrent reads and writes. Which changes support which mode depends on the version and the operation, so check the online DDL docs before relying on it. Making a column `NOT NULL` is an in-place change that rebuilds the table, so run it only after the backfill is complete, and consider a tool for huge tables. **gh-ost** and **pt-online-schema-change** copy the table in the background, keep it in sync, and swap it in. The DDL is also replicated, so a long `ALTER` can show up as replication lag.

**Worked numbers: the backfill.** 200 million rows in batches of 10,000 is **20,000 batches**. At about 0.2 s per batch plus a 0.3 s pause, that is 20,000 × 0.5 s = 10,000 s, **about 2.8 hours**. Slow on purpose: each batch holds its row locks briefly, and the pauses keep replication lag (and Chapter 9's anomalies) away.

<Trace title="Run the database" steps={running} takeaway="Hot repeated keys → cache; diverse reads → replicas. Change schemas by expand, migrate, contract, never in one step." />

<Reveal q="Why not backfill with a single UPDATE of all 200 million rows?">

One giant transaction holds a lock on every row it touched until it commits, blocking every concurrent update to those users. It produces a huge burst of binlog that every replica must apply as one big transaction, a lag spike that turns into read-your-own-writes bugs across the product. It grows the undo log massively. And if it fails at 90%, all of it rolls back. Batches keep every lock short and let the replicas keep up.

</Reveal>

**Catch the trap:** *"We'll do it in a maintenance window."* The modern answer is zero downtime: expand, migrate, contract, plus a short lock timeout on every DDL statement.

<h2 id="interview-script">Say it in the room</h2>

The interviewer has drawn a marketplace with chat on the whiteboard and asks, almost lazily: *"Where does the data live?"* The strong move is to start with the questions, not a logo.

<AnswerModes id="databases-where-does-data-live" q="Where does the data live in this marketplace?">

<Fragment slot="short">

"I start with access patterns. Users, listings and orders are relational and transactional, so MySQL with InnoDB, a primary and replicas. Messages are append-heavy and read by conversation, so a wide-column store partitioned by conversation. Search is a derived index fed by CDC. Each choice has a reason and a cost I can name."

</Fragment>

<Fragment slot="medium">

"First the access patterns. Users, listings and orders are relational: an order, its payment and the stock decrement commit together. At about 120 writes a second at peak they fit one **MySQL** primary with two replicas for years, roughly 730 GB a year. Messages are different: about 35,000 writes a second at peak, 280 GB a day, always read as the latest page of one conversation. That fits a **wide-column store partitioned by conversation and month**. Listing search goes to **Elasticsearch fed by CDC** from the binlog; MySQL stays the source of truth.

For the schema, follows and attendance are join tables: primary key one way, reverse index the other. The dashboard index is `(seller_id, status, created_at)`: equality first, then the sort. Stock is one conditional `UPDATE ... WHERE stock > 0`, and listing edits use a version column. Replicas are async, so the author's own reads go to the source for a few seconds after a write. IDs are Snowflake-style 64-bit so inserts append to the clustered index."

</Fragment>

<Fragment slot="deep">

"Everything starts from the access patterns, rates and latency budgets, and whether a path needs a transaction.

**Relational core.** Orders, payments, stock: MySQL 8 on InnoDB, REPEATABLE READ default. I do not rely on the isolation level for invariants. Stock decrements are single conditional statements, payments have a unique idempotency key, and rules over several rows use `SELECT ... FOR UPDATE` on an indexed predicate or a unique constraint. I keep transactions to milliseconds and never hold one across a provider call.

**Indexes.** Composite indexes follow equality then range or sort, I verify with EXPLAIN (type, key, rows, no filesort), and covering indexes only for hot read paths because every index taxes writes.

**Copies.** Binlog replication with GTIDs, asynchronous by default, semi-sync if I cannot lose acknowledged commits. Replicas scale reads, not writes. Read-your-own-writes by routing the author to the source briefly or waiting for the GTID. Failover can lose the async tail, and I fence the old source.

**Splits.** Numbers first: orders do not need it. Retention on big tables by partitioning inside MySQL. Messages are sharded by conversation with a time bucket, with fixed logical partitions so adding nodes moves partitions, not rehashes keys.

**Operations.** A pooler between pods and MySQL sized by rate × hold time, and schema changes by expand, migrate, contract with a short lock timeout."

</Fragment>

</AnswerModes>

**Five follow-ups you will get:**

<Reveal q="1 · Why not put everything in one NoSQL store?">

Because the transactional core needs atomic multi-row writes, constraints and questions nobody has asked yet, and at about 120 writes a second it does not need horizontal scale. I use a partitioned store only where an access pattern demands it (messages) and feed derived stores (search, cache) from the source of truth.

</Reveal>

<Reveal q="2 · How do you shard messages, and what about a huge group chat?">

Partition key `(conversation_id, month)`, clustering by message id descending, so "latest 50" is one partition slice. The month bucket caps partition size for very busy chats: an extreme chat at one message a second is about 0.5 GB a month. Nodes are added by moving whole logical partitions, never by re-hashing mod N, which would move about 80% of the data going from 4 to 5 nodes.

</Reveal>

<Reveal q="3 · A seller edits a price, reloads, and sees the old price. Why, and what's the fix?">

Async replication lag: the reload hit a replica that had not applied the write. Read-your-own-writes: route that seller's reads of what they just changed to the source for a short window, or carry the write's GTID and read from a replica only once it has applied it (`WAIT_FOR_EXECUTED_GTID_SET`). Everyone else keeps reading replicas.

</Reveal>

<Reveal q="4 · Which isolation level, and where could it bite you?">

InnoDB's default, REPEATABLE READ (or READ COMMITTED to reduce gap-lock deadlocks), with the invariants enforced in the statements: the conditional stock decrement, a unique idempotency key on payments, all in one transaction. It would bite on read-then-write code (lost updates) and on rules spanning several rows (write skew), so those get `SELECT ... FOR UPDATE`, a constraint, or SERIALIZABLE with a retry loop.

</Reveal>

<Reveal q="5 · How do you add a NOT NULL column to a 2-billion-row table with no downtime?">

Expand, migrate, contract. Add it nullable with `ALGORITHM=INSTANT` and a short `lock_wait_timeout` so it cannot queue the table behind a metadata lock. Deploy code that writes it, backfill in batches with pauses so replicas keep up, then enforce `NOT NULL`. In MySQL that is an in-place table rebuild, so for a table this size use an online schema-change tool such as gh-ost, or check the online DDL docs for your version. Drop anything old last.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| "Where does the data live?" | Access patterns first; a relational database (MySQL) until proven otherwise |
| Append-heavy, read by one key in time order | Wide-column, partition by that key (+ time bucket) |
| Free text, typos, ranking | Search index fed by CDC; not the source of truth |
| Multi-hop relationships | Graph store, derived from the source |
| Metrics, retention, downsampling | Time-series store |
| Varying attributes, read whole by id | Document model (or a MySQL `JSON` column) |
| One-to-one | Same row, or a table keyed by the parent's id |
| One-to-many | Foreign key on the many side, and index it |
| Many-to-many | Join table: composite PK one way, reverse index the other, relationship facts on the row |
| "Denormalise for speed" | Which fact, which read, who keeps the copies right |
| Clustered vs secondary (InnoDB) | PK tree holds the rows; secondary leaves hold index columns + PK; two walks unless covering |
| Composite index | Equality columns first, then range or sort; leftmost prefix |
| Query reads few columns | Covering index (append columns; `Using index`) |
| "Why is it slow?" | EXPLAIN: type, key, rows, Extra (`Using filesort`, `Using temporary`) |
| "Index everything" | Every index taxes every write |
| Read, compute, write back | Lost update: atomic `UPDATE`, `FOR UPDATE`, or version column |
| Invariant across rows | Write skew: `FOR UPDATE` on the rows, a constraint, or SERIALIZABLE + retry |
| Isolation defaults | InnoDB REPEATABLE READ; Postgres READ COMMITTED |
| "My edit disappeared" | Replica lag → read-your-own-writes |
| Multi-region writes | Conflict strategy per data type |
| Leaderless | W + R > N for overlap; N − W and N − R failures tolerated |
| "Do we need to shard?" | rows/day × bytes (with indexes) × 365 × replicas |
| Partitioning vs sharding | Partitioning: one server (pruning, retention). Sharding: many servers (size, writes) |
| Shard key | Spreads load? Hot query on one shard? |
| Growing the cluster | Fixed logical partitions or consistent hashing, never mod N |
| Unique IDs | Snowflake (41/10/12) or UUIDv7; clock skew → refuse until caught up |
| Pods × pool > max_connections | Pooler or proxy; size by rate × hold time |
| Hot repeated reads vs diverse reads | Cache vs replicas |
| Schema change | Expand → migrate → contract, with `lock_wait_timeout` |

## Five mistakes to leave behind

1. **Naming a database before the access patterns.** The logo is the last word of the answer, not the first.
2. **A many-to-many with one index**, or an array column. Both questions, both indexes.
3. **Indexes in the wrong order**, or indexes on everything. Equality first, then range; every index costs writes.
4. **Trusting the default isolation level** with read-then-write code. READ COMMITTED loses updates; so does InnoDB's REPEATABLE READ.
5. **Sharding without numbers, or by a key the hot query does not carry.** And never `mod N`.

**Keep it warm:** run the **shard-key gauntlet**: six systems (chat, tweets, orders, metrics, URL shortener, Uber driver locations). For each, ninety seconds: the partition key, the query it keeps on one shard, and the hot-spot risk. Then one rep on many-to-many: model students and courses, or playlists and songs, from scratch, with the join table, both indexes, a relationship attribute and the three queries it serves.
