<h2 id="prologue">Prologue · An if-statement that took everything down</h2>

Here is a failure that happens in real systems. A marketplace has a small config service that answers `isEnabled("new-checkout")`. Every other service calls it over HTTP on every request, with a 30-second timeout. One Tuesday the config service is redeployed. For a few minutes every call to it hangs. Checkout, search and profile pages all stall at the same time, even though none of them changed.

The code at the center of it is one line: `if (flags.isEnabled("new-checkout"))`. Flags exist so you can turn things off safely. Here the flag system turned everything off. Why can an if-statement do that, and what makes sure it never can?

Interviewers ask about flag platforms because the problem **looks small** and is really a distributed config problem plus a statistics problem. It is also an unusual design where **read latency of about zero is a hard requirement**: flag checks sit in the hot path of every request, thousands of times per second per process.

The bug in the incident is the naive design: **every flag check is a network call.** That puts a remote service on the hot path and makes it a single point of failure for the whole product. The real design flips it. Push the rules to the application and evaluate them locally.

<Figure caption="Left: the design that failed, a network call per check. Right: push the rules, evaluate locally. The flag service leaves the request path.">
  <Mermaid code={`flowchart LR
    subgraph Naive["Naive: ask on every check"]
      R1["request"] --> APP1["app code"] -->|"HTTP per check<br/>30 s timeout"| FS1["flag service"]
    end
    subgraph Real["Real: push rules, evaluate locally"]
      FS2["flag service"] -.->|"rules streamed<br/>in the background"| SDK["SDK in the app<br/>full ruleset in memory"]
      R2["request"] --> APP2["app code"] -->|"function call<br/>microseconds"| SDK
    end`} />
</Figure>

A flag platform is four promises, which you should be able to say aloud:

1. **Evaluation is local.** It is a pure function over an in-memory ruleset. No network on the hot path.
2. **Assignment is deterministic.** `hash(flagKey + userKey)` decides, so a user gets the same answer everywhere, with nothing stored.
3. **Changes propagate in seconds.** They are streamed and versioned, with polling and last-known-good as fallbacks. A kill switch is only as good as this.
4. **The flag system cannot take the product down.** Every check has a safe default. A dead control plane freezes the rules; it never breaks the app.

For experiments there is a fifth: **measure honestly**. That means exposure logging, a fixed sample size, a sample-ratio check and guardrail metrics.

The pitch for the whole product is the **kill switch**: a bad change behind a flag, toggled off, has a blast radius measured in seconds, with no rollback deploy. Say that before the interviewer asks what flags are for.

<h2 id="four-kinds">Chapter 1 · Four kinds of flag</h2>

Imagine exporting every flag a company has ever created: 2,000 rows. The oldest, `enable_new_search_2019`, is still read on every search request. Nobody knows if it is on. Some of those flags should have died in a week and some should never die. Which is which?

A flag is a decision moved out of the code and into data, so it can change without a deploy. **Why** it was moved decides how long it should live, who may change it, and what its default must be. The classic four kinds come from Pete Hodgson's taxonomy on martinfowler.com (linked at the end):

| Kind | Purpose | Lifetime | Changes | Safe default if the flag system is unreachable |
|---|---|---|---|---|
| **Release toggle** | Ship unfinished code dark; release separately from deploy; ramp 1% to 100% | Days to weeks. **Delete at 100%** | Often, during the ramp | **Off**: the old, proven path |
| **Experiment flag** | Split users into variants and measure | Weeks, until the decision | Rarely (changing weights mid-test ruins it) | **Control**, and log no exposure |
| **Ops kill switch** | Degrade on purpose under load or failure: turn off recommendations, a costly query, a third-party call | **Long-lived, by design** | Rarely, but must land in seconds | **Normal operation**: the feature stays on |
| **Permission / entitlement flag** | Who may use a feature: beta programme, plan tier, internal staff | Long-lived | When customers change | **Careful**: deny is safe for security, but must not take away what someone paid for |

Two points are worth saying in an interview.

- **Defaults differ by kind.** "Default off" is right for a release toggle and wrong for a kill switch. If a kill switch defaults to off and a pod boots while the flag service is down, you have switched off a working feature for no reason. Name kill switches so that the code default is the healthy state.
- **Entitlements are a smell in a flag system.** "Pro plan gets bulk listing" is a business rule that never expires and must survive a flag outage. Many teams keep plans and permissions in the billing or authorization service and use a flag only to *launch* the feature. This is a senior signal: the flag system is the wrong source of truth for money.

**Release toggle versus kill switch.** They look the same in code (an if around a feature) and are opposites in practice:

| | Release toggle | Kill switch |
|---|---|---|
| Normal state | Off, then ramping, then on | On, all the time |
| Who flips it | The feature team, on a plan | Whoever is on call, in an emergency |
| Ends with | Deleting the flag and the old path | Nothing; it stays |
| Default on flag-system failure | Old path (off) | Feature stays on |

A common slip: "we'll put it behind a flag" with no kind, owner or end date. Every flag you add is a branch nobody will remember. Say the kind and the exit plan together: "a release toggle, owned by the checkout team, deleted when it has served 100% for a week."

<h2 id="evaluation">Chapter 2 · The rule walk</h2>

Imagine a product lead dictating the rollout plan for a new checkout: "Off by default. On for staff. On for the beta segment. In India and Brazil, half of paying users. Everyone else, ten percent. And never for Dara, who is demoing the old one to investors." That is six rules. In what order does the code read them?

Every serious flag system evaluates a flag the same way. A **context** goes in (a stable key plus attributes), a **variation** comes out, and a fixed order of checks decides which.

<Figure caption="The rule walk. Top to bottom, the first match wins. Every exit reports a reason, which is how you debug why a given user saw the new checkout.">
  <Mermaid code={`flowchart TD
    S["evaluate(flag, context)"] --> N{"ruleset loaded and<br/>flag exists?"}
    N -->|"no"| D["caller's default<br/>NOT_INITIALIZED / FLAG_NOT_FOUND"]
    N -->|"yes"| O{"flag on?"}
    O -->|"no"| OFF["off variation<br/>OFF: the kill switch"]
    O -->|"yes"| T{"user individually<br/>targeted?"}
    T -->|"yes"| TG["their variation<br/>TARGET"]
    T -->|"no"| RL{"rules in order:<br/>all clauses match?"}
    RL -->|"rule i"| SV["serve: fixed variation<br/>or rollout by bucket<br/>RULE i"]
    RL -->|"none"| FT["fallthrough: fixed<br/>or rollout<br/>FALLTHROUGH"]`} />
</Figure>

The vocabulary, which most vendors share with small differences (check your vendor's docs):

- **Context**: who is asking. A stable **key** (user id, device id for logged-out users, or an organisation id) plus attributes (`country`, `plan`, `email`, `appVersion`). The OpenFeature standard calls this the evaluation context.
- **Variation**: a value the flag can return. `true`/`false`, a string, a number, or a JSON blob (remote config).
- **Clause**: one test on one attribute, such as `country IN [IN, BR]`. A **rule** is clauses ANDed together plus what to serve.
- **Segment**: a named, reusable audience. An explicit list of keys, or everyone matching some clauses. "beta-testers" is defined once and used by fifty flags.
- **Serve**: either a fixed variation or a **percentage rollout**, a split of 10,000 buckets among variations (next chapter).
- **Fallthrough**: what everyone who matched no rule gets.

Here is the model as Java. Records keep it immutable, which matters later: an evaluation reads one ruleset object that nothing will modify underneath it.

```java id=model group=flags
/** Who is asking: a stable key plus attributes that rules can target. */
record Context(String key, Map<String, String> attributes) {
    String get(String attribute) { return "key".equals(attribute) ? key : attributes.get(attribute); }
}
enum Op { IN, NOT_IN, ENDS_WITH, IN_SEGMENT }
/** One test on one attribute: country IN [IN, BR]. For IN_SEGMENT, the values are segment keys. */
record Clause(String attribute, Op op, List<String> values) {}
/** A reusable audience: listed keys, or anyone matching all of its clauses. */
record Segment(Set<String> included, List<Clause> clauses) {}
/** One variation's share of the 10,000 buckets. */
record Slice(String variation, int weight) {}
/** Split by bucket. bucketBy names the attribute that is hashed: "key", or "org" to keep a company together. */
record Rollout(String bucketBy, List<Slice> slices) {
    Rollout {
        int total = 0;
        for (Slice s : slices) {
            if (s.weight() < 0) throw new IllegalArgumentException("negative weight");
            total += s.weight();
        }
        if (total != 10_000) throw new IllegalArgumentException("weights must sum to 10,000, got " + total);
    }
}
/** What a rule hands out: one fixed variation, or a rollout. Exactly one of the two is non-null. */
record Serve(String variation, Rollout rollout) {}
record Rule(List<Clause> clauses, Serve serve) {}
/** salt is normally the flag key; changing it re-randomises everyone (Chapter 3). */
record Flag(String key, String salt, boolean on, String offVariation,
            Map<String, String> targets, List<Rule> rules, Serve fallthrough) {}
record Ruleset(long version, Map<String, Flag> flags, Map<String, Segment> segments) {}
/** The answer, why (for debugging and exposure logs), and the bucket when a rollout decided it. */
record Evaluation(String variation, String reason, int bucket) {}
```

And the walk itself. It is a **pure function**: no I/O, no clock, no randomness. That is what makes it microseconds, and what makes every SDK instance holding the same ruleset give the same answer.

```java id=evaluate group=flags
static Evaluation evaluate(Ruleset rs, String flagKey, Context ctx, String fallback) {
    if (rs == null) return new Evaluation(fallback, "NOT_INITIALIZED", -1);   // no ruleset yet
    Flag flag = rs.flags().get(flagKey);
    if (flag == null) return new Evaluation(fallback, "FLAG_NOT_FOUND", -1);  // typo, or deleted
    if (!flag.on()) return new Evaluation(flag.offVariation(), "OFF", -1);    // the kill switch
    String targeted = flag.targets().get(ctx.key());
    if (targeted != null) return new Evaluation(targeted, "TARGET", -1);       // named users first
    for (int i = 0; i < flag.rules().size(); i++) {                           // first matching rule wins
        Rule rule = flag.rules().get(i);
        if (allMatch(rule.clauses(), ctx, rs, true)) return serve(flag, rule.serve(), ctx, "RULE " + i, fallback);
    }
    return serve(flag, flag.fallthrough(), ctx, "FALLTHROUGH", fallback);     // everyone else
}

static Evaluation serve(Flag flag, Serve serve, Context ctx, String reason, String fallback) {
    if (serve.rollout() == null) return new Evaluation(serve.variation(), reason, -1);
    String unit = ctx.get(serve.rollout().bucketBy());          // usually the user key; "org" for B2B
    if (unit == null) return new Evaluation(fallback, "MISSING_ATTRIBUTE", -1);
    int bucket = bucket(flag.salt(), unit);
    int upper = 0;
    for (Slice slice : serve.rollout().slices()) {             // slices own consecutive bucket ranges
        upper += slice.weight();
        if (bucket < upper) return new Evaluation(slice.variation(), reason, bucket);
    }
    throw new IllegalStateException("weights must sum to 10,000");   // Rollout's constructor prevents this
}

static boolean allMatch(List<Clause> clauses, Context ctx, Ruleset rs, boolean segmentsAllowed) {
    for (Clause c : clauses) if (!matches(c, ctx, rs, segmentsAllowed)) return false;
    return true;                                                // no clauses: matches everyone
}

static boolean matches(Clause c, Context ctx, Ruleset rs, boolean segmentsAllowed) {
    if (c.op() == Op.IN_SEGMENT) {
        if (!segmentsAllowed) return false;                     // segments don't nest here: no cycles
        for (String key : c.values()) {
            Segment s = rs.segments().get(key);
            if (s == null) continue;
            if (s.included().contains(ctx.key())) return true;
            if (!s.clauses().isEmpty() && allMatch(s.clauses(), ctx, rs, false)) return true;
        }
        return false;
    }
    String value = ctx.get(c.attribute());
    if (value == null) return false;                            // a missing attribute never matches, NOT_IN included
    return switch (c.op()) {
        case IN -> c.values().contains(value);
        case NOT_IN -> !c.values().contains(value);
        case ENDS_WITH -> c.values().stream().anyMatch(value::endsWith);
        case IN_SEGMENT -> false;                               // handled above
    };
}
```

The plan above, in this model:

- The flag is `on`.
- Dara is an individual **target** serving `off`. Targets are checked before rules, so she is safe even though she is staff.
- Rule 0: `IN_SEGMENT staff, beta` serves `on`.
- Rule 1: `country IN [IN, BR]` AND `plan NOT_IN [free]` serves a 50/50 rollout.
- Fallthrough: a 10% rollout.

The checker runs this exact shape case by case, then 30,000 evaluations over 3,000 random rulesets against an independently written oracle.

**What stays true:** the answer depends only on (ruleset version, flag key, context). Two SDKs with the same ruleset version agree on every user, which is what makes debugging, experiments and the next chapter possible.

<Reveal q="Why does a missing attribute make NOT_IN return false instead of true?">

Because "we don't know this user's plan" is not evidence that they are not on the free plan. If NOT_IN matched on missing data, a context built without the `plan` attribute (a background job, a logged-out page, a bug in one service) would sail into the "paying users" rule. Rules should fail closed on missing data and let the user fall through to the conservative default. The `reason` field makes this debuggable: you see `FALLTHROUGH` where you expected `RULE 1` and go find the service that forgot to send `plan`.

</Reveal>

A common slip is order-dependent rules nobody can read. Rules run top to bottom and the first match wins, so moving a rule changes who gets what. A good admin UI shows the order, previews "who would this change affect?", and records the reason for each evaluation. Say all three.

<h2 id="bucketing">Chapter 3 · Same user, same answer</h2>

The first version of a 10% rollout is often `Math.random() < 0.10`. The support ticket arrives soon after: "The checkout keeps changing every time I refresh." Two questions expose the problem. Ten percent of what: requests, or people? And when you go to twenty-five percent, what happens to the ten percent you already had?

A rollout percentage must mean **a fixed set of people**, not a coin flip per request. Two wrong answers first:

```java fragment
boolean on = Math.random() < 0.10;            // per request: the same user flips between variants
```

| Approach | Sticky per user? | Cost | Verdict |
|---|---|---|---|
| Random per request | No. Users flap on every refresh, and in an experiment every user lands in both arms | Free | Never |
| Store a row per user and flag ("user 42 is treatment") | Yes, until the row is lost | A database lookup on the hot path, for billions of user x flag rows | Only for rare cases (below) |
| **Hash and bucket** | Yes, as long as rules and salt do not change | A few dozen nanoseconds, no storage | **Default** |

**The right answer: compute it.**

```text
bucket = hash(flagKey + "." + userKey) mod 10,000          -> a number in 0 ... 9,999
serve  = the variation whose bucket range contains bucket    (10% = buckets 0 ... 999)
```

It is deterministic, stateless, needs no storage, and gives the same result on every server, in every region, after every restart. Ten thousand buckets gives rollouts in steps of 0.01%, fine enough to start at 0.1% on a huge service.

**Why the flag key is in the hash.** Without it, `hash(userKey)` gives each user one bucket for *every* flag. Every flag at 10% would pick **the same 10% of users**. One unlucky cohort would receive every half-built feature at once, and every experiment's treatment group would be the same people, so the effects pile up and contaminate each other. With the flag key in the input, each flag gets its own independent shuffle. The checker measures it: two flags at 50% overlap on about 25% of users with the key, and on exactly 100% with this version, which one team shipped first:

```java id=unsalted group=flags
// BUG: the flag key is ignored, so every flag gives a user the same bucket.
static int bucketUnsalted(String flagKey, String userKey) {
    return bucket("kestrel", userKey);
}
```

**Why ramps are sticky.** Each variation owns a fixed, contiguous range of buckets. Going from 10% to 25% moves the boundary from 1,000 to 2,500 and nobody's bucket changes. **Everyone already in stays in; the ramp only adds people.** Here are eight real buckets from the lesson's Java for `new-checkout`:

<HintLadder labels={['A small nudge', 'Name the moving parts', 'The property to protect', 'Compare with the Java']} hints={[

  'Hash the flag key and the user key together into a 64-bit number, reduce it to 0-9,999, and compare it with the rollout boundaries (weights in basis points).',
  'Ramping 10% to 25% must only add users. If each variation owns a fixed contiguous range and a ramp only moves a boundary, nobody inside moves. Also: every SDK language must compute the same bucket, so define the hash over UTF-8 bytes, not a language built-in.',

```java id=bucket group=flags
import java.nio.charset.StandardCharsets;

/**
 * A stable bucket in [0, 10000) for this flag and this unit (user, device, org). Same inputs, same
 * bucket: in every process, after every restart, in every language that runs these steps on UTF-8.
 */
static int bucket(String salt, String unitKey) {
    byte[] bytes = (salt + "." + unitKey).getBytes(StandardCharsets.UTF_8);
    long h = 0xcbf29ce484222325L;              // FNV-1a, 64-bit: offset basis
    for (byte b : bytes) {
        h ^= (b & 0xff);
        h *= 0x100000001b3L;                   // FNV prime; overflow is intended (arithmetic mod 2^64)
    }
    h ^= h >>> 33; h *= 0xff51afd7ed558ccdL;   // MurmurHash3's fmix64 finaliser, so that every input
    h ^= h >>> 33; h *= 0xc4ceb9fe1a85ec53L;   // bit affects every output bit
    h ^= h >>> 33;
    return (int) Long.remainderUnsigned(h, 10_000);
}
```

</HintLadder>

**Cost:** O(length of the keys) per evaluation, a few dozen nanoseconds of hashing, no memory, no I/O. Real vendors pick their own hash (SHA-1 and MurmurHash3 are both common; check your vendor's docs). Any well-mixed hash works **as long as every SDK in every language computes the identical function**. The checker verifies this one against an independent re-implementation on thousands of random strings, including accents, CJK and emoji.

Three refinements interviewers like:

- **Bucket by the right unit.** For a B2B feature, bucket by `org`, not user, so a whole company sees the same thing (`bucketBy` in the model). For logged-out traffic, bucket by a device or anonymous id, and accept that a user who logs in may switch arms.
- **Ramps are monotonic; re-splits are not.** Moving the 10%/90% boundary keeps everyone. Changing a three-way 33/33/34 split to 50/50 moves the *middle* range and reshuffles some users between arms. That is fine for a release and fatal mid-experiment.
- **Re-salting is a feature.** Change the salt and everyone gets a fresh bucket, which is how you start a new experiment iteration without carrying over the last cohort. The checker confirms a new salt keeps only about 10% of the old 10% cohort, exactly what independence predicts.

**Catch the bug.** You will see this line in real code reviews. It has three bugs:

```java id=weakBucket
// Three bugs in one line. Do not ship.
static int weakBucket(String flagKey, String userKey) {
    return Math.abs((flagKey + userKey).hashCode()) % 100;
}
```

1. **`Math.abs` of `Integer.MIN_VALUE` is still negative.** `"polygenelubricants".hashCode()` is exactly `Integer.MIN_VALUE`, so flag `"polygene"` and user `"lubricants"` get bucket **-48**, which no range contains. The checker runs exactly this input.
2. **`String.hashCode` is Java-only.** Your Node edge worker and your iOS app will put the same user in a different bucket. Bucketing must be a cross-language spec, not a library call.
3. **`hashCode` doesn't mix.** `hash(prefix + suffix) = hash(prefix) x 31^len + hash(suffix)`, so changing the flag key just shifts every user by roughly the same offset. The flag key is in the input and the flags are still correlated: two 50% flags overlap on about **12%** of users instead of 25% in the checker's run. (And 100 buckets cannot express 0.1%.)

<Reveal q="Some platforms do store assignments. When is that the right call?">

When the assignment must survive **rule changes**, not just restarts. Hashing is sticky only while the rules stay the same: if someone edits a long-running experiment's targeting, users can move. Some experimentation platforms therefore record the first assignment and honour it afterwards (often in a cache or a profile store, not on the hot path of every check). Say it as the exception, "hashing by default; persisted assignments for the few experiments that must be immune to edits", not as the design.

</Reveal>

<h2 id="planes">Chapter 4 · Two planes</h2>

Draw a horizontal line. Above it, people change a flag a few times an hour and want an audit trail and an approval. Below it, ten million checks a second want an answer in a microsecond. These two jobs have almost nothing in common, so they should not be the same service.

Split the system the way networks do:

- **Control plane**: where humans and automation **change** flags. Admin UI and API, the flag store (a relational database: versioned, transactional), the audit log, approvals, scheduling. Low volume, strongly consistent, and it can be down for minutes without hurting a single user request.
- **Data plane**: where flags are **evaluated**. SDKs inside every application process hold the full ruleset in memory, fed by a distribution tier (streaming servers, relays, a CDN). Enormous volume, must never block, tolerates seconds of staleness.

**Worked numbers: evaluations are free.** Assumption for this example: 500,000 requests per second at peak, about 20 flag checks per request.

- Flag checks: 500,000 x 20 = **10,000,000 evaluations per second**.
- Local cost: on the order of a microsecond each (a map lookup, a few string comparisons, one hash; benchmark your SDK). 10,000,000 x 1 microsecond = **10 CPU-seconds per second**, about 10 cores across a fleet of 10,000 instances. A thousandth of a core each.
- Remote alternative: even batching one call per request, that is 500,000 RPCs per second to the flag service, an extra round trip on every request, and an availability ceiling. **If every request needs the flag service, the product can be no more available than the flag service.**
- Memory: 2,000 flags x about 1 KB of rules each is about **2 MB** of JSON. Parsed into objects it is a few times that. Trivial per process.

<Reveal q="When is it right for the data plane to call a server instead of evaluating locally?">

When the ruleset cannot or should not be in the process. (1) **Client devices**: browsers and phones must not hold everyone's rules (Chapter 6). (2) **Huge segments**: a list of 1,000,000 user ids at about 20 bytes each is 20 MB, too big to ship to every SDK, so some platforms keep big segments in a separate store the SDK queries and caches (check your vendor's docs for how they handle it). (3) **Languages without an SDK**, served by a local sidecar or relay that evaluates over localhost. Even then the call goes to something close and cached, never a cross-region hop on every check.

</Reveal>

A common slip is "the flag service is highly available, so calling it is fine." Availability multiplies: a request that depends on the flag service *and* the database *and* the cache is less available than any one of them. The design that wins removes the dependency instead of hardening it.

<h2 id="distribution">Chapter 5 · Polling, streaming and versions</h2>

Say an SDK polls for rules every 30 seconds. It works until the night a recommendation model starts timing out and an engineer flips its kill switch. The error graph keeps climbing for another 28 seconds, because that is how long it takes for the next poll to pick up the change. The lever was pulled and nothing happened yet.

Getting a ruleset to 10,000 processes is a fan-out problem with three questions: **how do changes travel, how big are they, and how does an SDK know it has not missed one?**

**How changes travel.** The choices are the same as for any server-to-client push (<a href={`${BASE}sd/lessons/pattern-realtime/#transport`}>Realtime: which pipe?</a>):

| Mechanism | Propagation | Cost at 10,000 SDKs | Fits |
|---|---|---|---|
| **Polling** every 30 s with `ETag` / `If-None-Match` | Up to 30 s (average about 15 s) | 10,000 / 30 = about **333 requests/s**, almost all `304 Not Modified` | Fallback; simple environments; serverless functions that cannot hold a connection |
| **Long-polling** | About a second | One parked request per SDK, re-issued after each change | Where SSE is blocked by a proxy |
| **Server-Sent Events (SSE)** stream | About a second | 10,000 mostly idle connections | **Default** for server SDKs: one-way, plain HTTP, auto-reconnect |
| **WebSocket** | About a second | Same as SSE | Only if you also need client-to-server messages (you do not) |

Flags flow one way, so the realtime lesson's rule applies: **one-way push means SSE, with polling as the fallback.** Ten thousand idle connections are a few streaming nodes, not a fleet (a node can hold tens of thousands of idle connections; benchmark yours).

**Polling versus streaming, precisely.** Both can be correct. They differ in who starts the conversation and what staleness costs:

| | Polling | Streaming |
|---|---|---|
| Who initiates a change delivery | The SDK, on a timer | The server, the moment the change commits |
| Staleness | Up to the interval | About a network round trip |
| Idle cost | One cheap request per SDK per interval | One open connection per SDK |
| Failure mode | A slow, bounded delay | A silent dead connection or a missed message (so you need versions and heartbeats) |
| Works behind strict proxies and serverless | Yes | Sometimes not |

Polling with a conditional request is cheap because the server can answer without the body:

```http
GET /sdk/envs/prod/ruleset HTTP/1.1
If-None-Match: "v41"

HTTP/1.1 304 Not Modified
```

A minimal fallback poller in Python. It keeps serving the old ruleset on any failure and saves the last good one to disk:

```python
def poll_forever(url, store, path, interval=30):
    etag = None
    while True:
        try:
            r = requests.get(url, headers={"If-None-Match": etag} if etag else {}, timeout=3)
            if r.status_code == 200:
                store.apply_snapshot(r.json())      # ignored if the version is not newer
                etag = r.headers.get("ETag")
                write_atomically(path, r.text)       # last-known-good for the next cold start
        except requests.RequestException:
            pass                                     # keep serving the in-memory ruleset
        time.sleep(interval * random.uniform(0.8, 1.2))   # jitter so SDKs do not poll in lockstep
```

**How big.** Never push the whole ruleset per change:

- Full snapshot to everyone: 10,000 x 2 MB = **20 GB per change**.
- Just the changed flag (about 1 KB): 10,000 x 1 KB = **10 MB per change**.

So: **deltas on the stream, snapshots only at startup and after a gap.** Snapshots are written once per version to object storage behind a CDN at a **versioned, immutable URL** (`/env/prod/ruleset/v41.json`), so they cache forever and the origin never sees the herd.

**How an SDK knows it missed nothing: versions.** The control plane gives every change in an environment the next version number. An SDK holding version 41 that receives 42 applies it. Receiving 41 again, it ignores it. Receiving 43, it knows it **missed 42** and fetches a fresh snapshot instead of guessing. (Some vendors version each flag rather than the environment; the gap-detection idea is the same.)

The SDK's store, with exactly those three outcomes. Readers never lock: they read one immutable `Ruleset` through a `volatile` field, and the stream thread swaps in a new one per change (copy-on-write: a 2,000-entry map copy, a few times an hour, is nothing).

```java id=store group=flags
enum Applied { APPLIED, IGNORED_OLD, NEED_SNAPSHOT }

/** The SDK's copy of the ruleset: lock-free reads of an immutable snapshot, one writer swapping it. */
static final class FlagStore {
    private volatile Ruleset current;                 // null until the first snapshot

    Ruleset current() { return current; }

    /** Startup, reconnect, or resync after a gap. Never step backwards. */
    synchronized boolean applySnapshot(Ruleset snapshot) {
        if (current != null && snapshot.version() <= current.version()) return false;
        current = snapshot;
        return true;
    }

    /** One change from the stream. The environment's version counts up by exactly one per change. */
    synchronized Applied applyPatch(long version, String flagKey, Flag flagOrNullToDelete) {
        Ruleset now = current;
        if (now == null) return Applied.NEED_SNAPSHOT;
        if (version <= now.version()) return Applied.IGNORED_OLD;            // duplicate or replay
        if (version > now.version() + 1) return Applied.NEED_SNAPSHOT;       // we missed one: resync
        Map<String, Flag> flags = new HashMap<>(now.flags());                // copy on write
        if (flagOrNullToDelete == null) flags.remove(flagKey); else flags.put(flagKey, flagOrNullToDelete);
        current = new Ruleset(version, Map.copyOf(flags), now.segments());
        return Applied.APPLIED;
    }

    /** What application code calls. Reads the volatile once, so one evaluation sees one ruleset. */
    String variation(String flagKey, Context ctx, String fallback) {
        return evaluate(current, flagKey, ctx, fallback).variation();
    }
}
```

The checker drives random snapshot/patch sequences against a simple model, and runs a writer applying 20,000 patches while three reader threads evaluate continuously, asserting that no reader ever sees a torn ruleset or a version going backwards.

**Scale tricks, each one sentence in an interview:**

- **Relays.** A relay per region or cluster holds one upstream stream and serves hundreds of local SDKs. 10,000 SDKs behind 50 relays is 50 upstream connections. Relays also keep serving the last ruleset if the upstream is unreachable.
- **Jittered reconnects.** If a streaming node with 10,000 connections restarts, all 10,000 reconnect. Spread over 30 seconds with jitter, that is about 333 reconnects per second. If each pulled a 2 MB snapshot it would be about 667 MB/s, which is why snapshots come from the CDN and why a reconnecting SDK first asks for deltas since its last version.
- **Polling stays on as a fallback**, at a slower interval, so a broken stream degrades to "slower" rather than "frozen".

<Trace title="Ship the rules" steps={distribution} takeaway="Deltas on an SSE stream for speed, versioned snapshots on a CDN for startup and gaps, relays for fan-out, polling as the fallback. Versions that count up by one make gaps detectable." />

<Reveal q="Why not just use Kafka to distribute flag changes to SDKs?">

Kafka is a fine **internal** backbone: the control plane can publish changes to a topic that the streaming tier consumes. But SDKs live in customer processes, browsers and phones across the internet. They need HTTP-friendly, firewall-friendly, auto-reconnecting delivery and a way to bootstrap from a snapshot. A Kafka client in every app process, holding consumer-group state, is heavy machinery for a few changes an hour. Use a log behind the streaming tier if you like; give the SDKs SSE plus snapshots.

</Reveal>

A common slip is "we push changes over WebSocket" with no answer for the missed message. Every push channel drops messages during reconnects. The senior sentence is about **versions and resync**, not the transport.

<h2 id="client-side">Chapter 6 · Flags in the browser</h2>

A security researcher opens the web app's JavaScript bundle and finds the complete flag ruleset: the email addresses of 312 beta testers, a segment called `acquisition-target-sellers`, and a flag named `launch-pay-q3` that has not been announced. Nothing was hacked. The ruleset was simply sent to the browser.

Server SDKs can hold the whole ruleset because the server is yours. **A browser or phone is not.** Anything sent to a client is public: targeting lists (other users' emails and ids), segment names, unreleased feature names, internal attributes. So client-side flags flip the model:

- **Server-evaluated payload.** The client sends its context (or just its session) to a flag endpoint you control. The server evaluates **only the flags marked client-visible** for **that user** and returns a small map such as `{ "new-header": true, "checkout-layout": "B" }`. No rules leave the server. Updates arrive on a per-user stream or poll.
- **Edge evaluation.** The same, at a CDN edge worker holding a replica of the ruleset, so evaluation happens close to the user. The edge still returns results, never rules.
- **Bootstrap to avoid flicker.** If the page renders with defaults and then flips when flag values arrive, users see a flash and experiments get muddied. Evaluate during the server render, embed the values in the HTML, and let the client SDK stream only changes after that.
- **Mobile.** Cache the last values on the device for offline starts. Re-evaluate when the context changes (a login is a new key, so call the SDK's identify method).
- **Client keys are public.** The client-side id that identifies the environment is shipped in the bundle. It must only grant "evaluate my flags", never read rules or write anything. Server SDK keys are secrets.

```http
POST /client/envs/prod/evaluate HTTP/1.1
Authorization: <public client id>

{ "context": { "key": "user-42", "plan": "pro", "appVersion": "8.2.0" } }

HTTP/1.1 200 OK
{ "version": 18204, "flags": { "new-header": true, "checkout-layout": "B" } }
```

<h2 id="availability">Chapter 7 · The flag service is down</h2>

Suppose the flag service's database fails over badly and the control plane is down for six hours. If the design is right, the dashboards stay flat and nobody outside the platform team notices. The harder follow-up is: what if a pod had **started** during those six hours?

Walk the failure cases one at a time, because each has a different answer:

| Situation | What the SDK does | Why |
|---|---|---|
| **Running, stream drops** | Keep serving the in-memory ruleset; reconnect with jittered backoff; fall back to polling | The ruleset does not go bad because the network did |
| **Control plane down for hours** | Keep serving last-known-good; export **ruleset age** as a metric; alert past a bound (say 10 minutes) | Stale-but-consistent beats a mass flip. The alert matters because kill switches will not land |
| **Pod starts, service down, disk cache present** | Load the last-known-good ruleset from local disk (or a relay's copy), serve it, keep retrying | Same rules as its neighbours, minus recent changes |
| **Pod starts, nothing available** | Wait a **bounded** time (a second or two), then serve **code defaults**; never block startup indefinitely | The flag system must never stop you from scaling or restarting |
| **Unknown flag** (typo, deleted) | Return the code default with reason `FLAG_NOT_FOUND`; count it | A typo must not throw in the request path |

**Fail-safe defaults are a design decision per flag**, which is why Chapter 1 put them in a table: release toggles default to the old path, kill switches to normal operation, experiments to control. The default lives **in the code** at the call site (`variation("new-checkout", ctx, "off")`), so it is reviewed like code.

**Fail open or fail closed?** The phrase means different things per flag, so name the default instead:

| Flag | "Open" (feature on) | "Closed" (feature off) | Usual choice |
|---|---|---|---|
| Release toggle for new code | Risks shipping unfinished code to everyone | Old path, known good | Closed (off) |
| Kill switch around a working feature | Feature keeps running | Feature disappears for everyone | Open (on) |
| Entitlement | Gives away paid features | Paying customers lose what they bought | Decide per feature; prefer reading it from the billing system |

**Stale bounds.** Expose `ruleset_age_seconds` and `ruleset_version` per instance. Version skew across the fleet tells you which pods missed changes; age past a few minutes pages someone. Do *not* auto-revert to defaults when stale: that turns an outage in the flag system into a global flip of every ramped feature.

    D -->|"yes"| E["serve it<br/>retry in background<br/>alert on ruleset age"]

<h2 id="consistency">Chapter 8 · Seconds of disagreement</h2>

A product lead ramps the new checkout to 25% at 14:00:00. A customer's cart page, served at 14:00:00.4, shows the new checkout button. The payment page, served by a different pod at 14:00:00.9, shows the old flow. The customer gets an error that should be impossible. Every pod got the change, just not at the same instant.

Flag distribution is **eventually consistent with a small, bounded lag**: typically a second or two on a healthy stream, up to the polling interval on the fallback. For most flags that is fine. Three places where it is not:

- **Multi-step flows.** Evaluate once at the start (or at session creation) and **carry the decision** in the session, a cookie, or the request context passed to downstream services. Downstream services read the decision instead of re-evaluating. The checkout flow stays on the path it started on.
- **Many services in one request.** If the gateway, the cart service and the pricing service each evaluate the same flag, they can disagree for a second. Evaluate at the edge of the request and propagate the result (a header or context field).
- **The kill switch.** Its value is measured in seconds-to-effect. Streaming, relays and a propagation SLO ("99% of SDKs apply a change within 5 seconds", measured by having SDKs report their version) are what make "toggle off" an incident tool rather than a hope.

**Evaluate once and carry versus re-evaluate.** They differ in what they protect:

| | Re-evaluate everywhere | Evaluate once, carry the result |
|---|---|---|
| Consistency inside a flow | Can flip mid-flow during propagation | Stable for the whole flow |
| Reaction to a kill switch | Immediate (each call sees the new rule) | Delayed until the flow ends, so keep flows short or let a kill switch override the carried value |
| Coupling | Each service needs its own SDK and context | Services must forward a header or field |

**What you can promise:** per-instance monotonic versions (an SDK never goes backwards; the store above enforces it), bounded propagation, and the same answer for the same ruleset version. You cannot promise that every process flips at the same instant, and you should not try: a synchronous global commit would put the control plane back on the hot path.

<Reveal q="The admin who just flipped a flag refreshes the dashboard and sees the old value. How do you fix that?">

That is read-your-writes in the *control* plane, not the data plane. The admin UI should read from the flag store (the source of truth) or wait for the write's version, not from an SDK or a cache. Separately, show "propagated to 9,940 of 10,000 SDKs" using the versions SDKs report. That is the honest answer to "has my change landed?".

</Reveal>

A common slip is promising "instant" propagation. Say "seconds, measured" and name what you do in the flows that cannot tolerate a mid-flow flip.

<h2 id="safety">Chapter 9 · Safe changes and kill switches</h2>

At 17:04 on a Friday someone sets `new-search-ranking` from 10% to 100% in production. They meant staging. By 17:11 search conversion is down by a third and nobody knows why, because nothing was deployed. Forty minutes later someone finds it in the audit log. A flag change is a deploy without a deploy pipeline.

Treat flag changes with the same care as code changes, scaled to risk:

- **Audit log**: who, what (before and after), when, which environment, and a free-text reason. Immutable and queryable. It answers "who turned this on Friday at 5 p.m.?" in seconds, and it should be on the incident dashboard. "Recent flag changes" is the first thing to check when nothing was deployed.
- **Approvals**: four-eyes review for production changes to flags marked critical, like a pull request. Scheduled changes ("ramp to 50% Monday 10:00") so nobody ships at 5 p.m. on a Friday.
- **Environment guardrails**: production visually distinct, separate permissions per environment, no copy-paste of rules between environments without a diff.
- **Guarded (progressive) rollouts with automatic rollback**: ramp in steps (1%, 5%, 25%, 50%, 100%) with a bake time at each, comparing the **treatment's** error rate and latency against the **control's** at the same moment. If treatment is significantly worse, the platform rolls back to 0% by itself and pages the owner.

<Figure caption="A guarded rollout. Each step bakes while the platform compares treatment against control; a regression anywhere rolls straight back to 0%.">
  <Mermaid code={`flowchart LR
    S1["1%<br/>bake 10 min"] -->|"healthy"| S2["5%<br/>bake 30 min"]
    S2 -->|"healthy"| S3["25%<br/>bake 1 h"]
    S3 -->|"healthy"| S4["50%<br/>bake 1 h"]
    S4 -->|"healthy"| S5["100%<br/>schedule cleanup"]
    S1 -->|"treatment worse<br/>than control"| RB["Roll back to 0%<br/>page the owner"]
    S2 --> RB
    S3 --> RB
    S4 --> RB`} />
</Figure>

**Worked numbers: why 1% is enough to catch it.** Assumption: 500,000 requests per second. At 1%, the treatment sees **5,000 requests per second, 300,000 per minute**. If control errors at 0.1% and the new path at 0.5%, one minute of treatment shows about **1,500 errors where control's rate predicts 300**. That is unmistakable within a minute, at a cost of 1% of users seeing an elevated error rate for that minute. On a low-traffic endpoint (50 requests per second), 1% is 30 requests per minute, so the same signal takes hours. Either bake longer or start at a larger percentage.

**Compare against control, not a fixed threshold.** A fixed "roll back above 1% errors" fires during an unrelated outage and misses a regression that doubles a 0.1% error rate. Comparing arms at the same time cancels out everything except the change. Also require a minimum sample before deciding.

**Canary versus flag.** They are often confused, and they protect against different things:

| | Canary deploy | Flag rollout |
|---|---|---|
| What is split | *Requests* | *Users* |
| Routed to | New binaries, at the load balancer (<a href={`${BASE}sd/lessons/load-balancing/#deploys`}>Load balancing: leaving quietly, arriving slowly</a>) | A new code path inside the same binary |
| Catches | "The new build crashes or leaks memory" | "The new feature is wrong" |
| Stickiness per user | Usually none | Yes, by bucketing |
| Undo | Roll back the deploy | Toggle off, no deploy |

Use both. A canary proves the build is healthy; a flag lets you expose the feature to users gradually.

**Designing the kill switch.** A kill switch is only worth having if it works when you need it:

1. **Make it a flag, not a deploy.** The point is seconds to effect with no pipeline.
2. **Default to healthy.** The code default is "feature on" (Chapter 1).
3. **Wrap the dependency, not just the button.** Put it around the costly call (the model, a third-party API) so that off means the call is skipped and a cheaper fallback is returned.
4. **Evaluate fresh.** It should not be carried in a long-lived session (Chapter 8).
5. **Test it.** Flip it in staging, and in production on a schedule. An untested kill switch tends to fail on the day it matters (it throws when off, or the fallback path was never exercised).
6. **Keep it separate from the ramp flag.** The ramp flag is deleted at 100%; the kill switch stays.
7. **Measure seconds to effect.** SDKs report their version; the propagation SLO is the number.

**Kill switch versus circuit breaker.** Both turn a failing dependency off. The difference is who decides:

| | Kill switch | Circuit breaker |
|---|---|---|
| Trigger | A human (or an alerting automation) | Automatic, from live error rates in the process |
| Speed | Seconds, limited by propagation | Milliseconds, local to each process |
| Good for | Known risky features, cost control, "stop the bleeding" decisions | Short bursts of dependency failure |
| Risk | Someone must notice; control plane must be reachable | Can flap or trip too eagerly |

Real systems use both: the breaker handles the first seconds and the kill switch is the deliberate decision after.

<h2 id="experiments">Chapter 10 · A/B tests end to end</h2>

Product wants to know whether the new checkout sells more. The easy answer is to compare this week, with it, to last week, without it. That fails: last week had a holiday and this week had a celebrity post. Every week is different. How do you build two groups that differ in exactly one thing?

An **A/B test** (online controlled experiment) is a flag with a purpose: split users randomly into **control** and **treatment**, change one thing, and compare a metric. Randomisation is the whole point. It makes the two groups alike in everything *except* the change, so a difference in outcome can be credited to the change.

The machinery, end to end:

1. **Assignment**: the experiment flag's rollout (50/50, or 90/10 to limit risk) using the same deterministic bucketing. Assignment must not depend on behaviour: decide before the user does anything, from the hash, not from what they clicked.
2. **Exposure logging**: when the code path *actually evaluates* the flag for a user, the SDK emits an **exposure event** `(experiment, variation, userKey, timestamp)`. Not when they were assigned, but when they reached the code. Users who never reach checkout cannot be affected by a checkout change, and counting them dilutes the effect toward zero.
3. **Metric events**: the product's normal analytics. Purchases, clicks, latency, crashes, each with a user key and timestamp.
4. **The join**: for each experiment, take exposed users, attach their metric events **after first exposure**, aggregate per variation.
5. **The statistics**: per-metric difference with a confidence interval, the sample-ratio check, guardrails (next chapter).

**Assignment versus exposure.** The two are easy to mix up and mixing them biases results:

| | Assignment | Exposure |
|---|---|---|
| What it is | The bucket maps the user to an arm | The user actually hit the flagged code |
| When it is known | Any time, by hashing | Only when the code runs |
| Who it covers | Every user, including those who never visit checkout | Only users who could be affected |
| Use in analysis | To check the split (SRM) | To compute the effect |

**Worked numbers: deduplicate exposures.** Assumption for this example: 5% of the 10,000,000 evaluations per second are experiment flags, so **500,000 exposure candidates per second** at peak. Logged raw at 200 bytes each and sustained, that would be 43 billion events and about 8.6 TB a day. But analysis only needs each user's **first** exposure per experiment. With 20 million daily users each exposed to about 10 experiments, that is **200 million events a day** (about 2,300 per second on average) and **40 GB a day**. So the SDK deduplicates in memory (a bounded set of recently logged user x flag x variation), and a stream job deduplicates across servers.

The arithmetic: 500,000/s x 86,400 s = 43.2 billion/day x 200 B = 8.6 TB. 20,000,000 x 10 = 200,000,000/day x 200 B = 40 GB. 200,000,000 / 86,400 = about 2,315/s.

An SDK-side dedupe is a few lines (bounded so it cannot leak memory):

```python
seen = LRU(maxsize=100_000)           # recent (flag, variation, user) triples

def maybe_log_exposure(flag, variation, user_key):
    key = (flag, variation, user_key)
    if key in seen:
        return
    seen.add(key)
    events.enqueue({"flag": flag, "variation": variation, "user": user_key, "ts": time.time()})
```

<Reveal q="This is a marketplace. Why might a plain user-level A/B test of a new pricing algorithm give the wrong answer?">

Because buyers and sellers interact. If treatment buyers see lower prices and buy up the cheap inventory, control buyers see less of it. The arms are not independent, and the measured lift is inflated (or invented). This is **interference**. Marketplaces use cluster-randomised experiments (randomise by city or market), switchback tests (alternate the whole market between arms over time windows), or two-sided designs. You do not need the details in an interview; naming the problem is the signal.

</Reveal>

A common slip is "we'll log every evaluation." It is the most expensive sentence in the design. Log first exposures, deduplicated, and send aggregate counters for everything else.

<h2 id="statistics">Chapter 11 · Four sentences of statistics</h2>

Day three of an experiment. The product lead messages three times: "p = 0.04!! Can we ship?" A good reply is a question. If you flipped two identical coins every day for twenty days and checked each evening, how often would one of them look "significantly" better at least once? More often than you would think.

Interviews want this depth and no more, in four sentences:

1. **Randomisation is the point.** Hash bucketing gives unbiased cohorts. Assignment must come before (and not correlate with) behaviour.
2. **Fix the sample size or duration up front.** Peeking at p-values daily and stopping when it looks good manufactures false positives.
3. **Log exposure, not assignment.** Analyse only users who actually reached the flagged code path.
4. **Guardrail metrics alongside the goal metric.** The experiment that lifts clicks 2% and hurts retention should die automatically.

If they push deeper, it is a data-science interview. Say you would pull in the stats platform. But carry the intuition and a few numbers behind each sentence.

**How big a sample?** A rule of thumb (Lehr's rule, for a two-sided test at alpha = 0.05 with 80% power): **n per arm is about 16 x variance / delta squared**. For a conversion rate p, variance = p(1 - p).

- Checkout converts at 10%, so variance = 0.1 x 0.9 = 0.09. You want to detect a lift of 0.5 percentage points (10.0% to 10.5%), so delta = 0.005.
- n is about 16 x 0.09 / 0.000025 = **57,600 users per arm**, about 115,000 in total. Halve the effect you want to detect and you need **four times** the users.
- Then run whole weeks anyway, because Monday's shoppers differ from Saturday's.

**Peeking.** A p-value of 0.05 means "5% false positives **if you look once**". Each additional look is another chance for noise to cross the line. A simulation of an experiment with **no real effect**, checked at 20 equally spaced points with "stop at the first p < 0.05", declares a false winner **about 25% of the time** (about 14% with 5 looks, about 20% with 10; these come from the lesson author's simulation, so treat them as illustrative). Fixes: commit to the sample size up front, or use **sequential testing** methods designed for continuous monitoring (some platforms offer "always-valid" p-values; look them up below).

**Sample ratio mismatch (SRM).** If you designed a 50/50 split, the exposed counts should be close to 50/50. A significant deviation means something in assignment or logging is broken, and every metric is suspect, because whatever lost users from one arm probably lost a non-random kind of user.

- Designed 50/50; observed **50,000 control, 51,500 treatment** (101,500 total, expected 50,750 each).
- chi-square = 750^2 / 50,750 + 750^2 / 50,750 = about **22.17**. The threshold for p = 0.001 at one degree of freedom is **10.83**. SRM: stop and debug.
- Observed 50,000 vs 50,300 gives chi-square of about 0.90: ordinary noise.
- Typical causes: treatment logs exposure on a code path control does not have; the new page crashes before logging; a redirect drops users in one arm; bot filtering hits one arm harder.

```java id=srm
/** Chi-square statistic (1 degree of freedom) comparing observed arm sizes with the designed split. */
static double srmChiSquare(long control, long treatment, double controlShare) {
    double total = control + treatment;
    double expectedControl = total * controlShare, expectedTreatment = total * (1 - controlShare);
    double dc = control - expectedControl, dt = treatment - expectedTreatment;
    return dc * dc / expectedControl + dt * dt / expectedTreatment;
}

/** 10.83 is the chi-square value for p = 0.001 at one degree of freedom: alarm only on a real mismatch. */
static boolean sampleRatioMismatch(long control, long treatment, double controlShare) {
    return srmChiSquare(control, treatment, controlShare) > 10.83;
}
```

The checker verifies the numbers above, an exact 90/10 split scoring zero, 89,000/11,000 on a 90/10 design flagged, and 2,000 fair coin-flip splits almost never tripping the alarm. A strict threshold is deliberate: SRM checks run on every experiment, every day.

**Guardrails.** Besides the goal metric, every experiment watches metrics it must **not** hurt: error rate, p99 latency, crash rate, revenue per user, unsubscribes. A significant guardrail regression stops the experiment automatically, using the same machinery as Chapter 9's guarded rollout. Pick the guardrails before the experiment starts, for the same reason you fix the sample size.

<h2 id="flag-debt">Chapter 12 · Flag debt</h2>

A well-documented example of what a dead flag can cost is the Knight Capital incident of August 2012 (described in the SEC's 2013 order). New code went out to the firm's order servers, all but one. A flag that used to switch on an old, retired feature had been reused for the new one. On the one server that missed the deploy, the reused flag woke the old code up. The firm lost more than $460 million in about 45 minutes. Two lessons follow: **never reuse a flag key**, and **delete dead code paths, not just flags.**

Flag debt is the everyday version. Every live flag is a branch in the code and a dimension in your test matrix: 10 independent boolean flags touching one code path give 2^10 = **1,024** combinations, and nobody tests them all.

<Figure caption="A flag's life. Release toggles and experiments must reach 'removed'; only kill switches and entitlements may stay permanent, on purpose, with an owner.">
  <Mermaid code={`flowchart LR
    C["Created<br/>kind, owner,<br/>expiry date"] --> R["Ramping<br/>or experimenting"]
    R --> F["Fully on or off<br/>100% one variation"]
    F -->|"stale detector:<br/>unchanged N days"| CL["Cleanup ticket<br/>remove code path"]
    CL --> RM["Removed<br/>key retired forever"]
    C -->|"kill switch or<br/>entitlement"| P["Permanent<br/>owner, tested yearly"]`} />
</Figure>

**Hygiene that works:**

- **Metadata at creation**: kind, owner team, expected removal date, linked ticket. The platform refuses a release toggle without an expiry date.
- **Stale detection**, automatically: a flag serving one variation to 100% of traffic for N days with no rule changes; a flag with **zero evaluations** for N days (dead in production); a flag past its expiry date. Each produces a cleanup ticket for the owner, and a weekly report per team.
- **Code references**: scan repositories for flag keys so you know where to delete, and which flags exist in code but not in the platform (or the reverse). Some vendors offer this as a CI integration.
- **Removal is a code change first**: delete the losing branch, deploy, confirm zero evaluations, *then* archive the flag. Retire the key permanently.
- **Budgets**: a cap on active release toggles per team turns cleanup into a habit instead of a heroic quarter.

A common slip is "we clean up flags periodically." Interviewers hear "never". Say what detects a stale flag and who gets the ticket.

<h2 id="environments">Chapter 13 · Environments and tenants</h2>

Say the marketplace opens its flag platform to sellers who build storefront plugins. Overnight the platform has two hundred customers, each with dev, staging and production. One of them creates 40,000 flags with a script. The question is no longer how to serve flags to ourselves, but how to serve them to people who are not us.

**Environments.** A flag's *definition* (key, variations, kind) is shared across environments; its *targeting* is per environment. Each environment has its own ruleset, its own version sequence, its own SDK keys and its own permissions. Promoting a rollout from staging to production is an explicit, reviewed copy with a diff, never shared state.

**Multi-tenant platforms.** Each customer organisation owns projects and environments, and an environment is the unit of everything:

- **Isolation**: SDK keys scoped to exactly one environment; every query in the control plane filtered by tenant (the same instinct as tenant-prefixed cache keys in <a href={`${BASE}sd/lessons/caching/#keys`}>Caching: naming things</a>, and the War Room <a href={`${BASE}sd/war/multi-tenancy/`}>multi-tenancy</a> dossier).
- **Partition the data plane by environment**: streaming connections, change topics and CDN snapshot paths are all keyed by environment id, so a change in one tenant's environment fans out only to that environment's SDKs.
- **Noisy neighbours**: per-tenant limits on flags, rules, segment sizes and change rate. The customer with 40,000 flags gets a ruleset 20 times bigger than average; their snapshots cost them, not everyone.
- **Per-tenant targeting inside your own product**: for B2B features, target and bucket by `org`, so one customer's whole team sees the same thing.

<Figure caption="Everything is keyed by environment: keys, version sequence, snapshot path and stream.">
  <Mermaid code={`flowchart LR
    O["Organisation"] --> P["Project"]
    P --> F["Flag definition<br/>key, variations, kind"]
    P --> E1["Environment: prod"]
    P --> E2["Environment: staging"]
    E1 --> C1["Targeting, version 18204<br/>SDK keys, snapshot path"]
    E2 --> C2["Targeting, version 912<br/>SDK keys, snapshot path"]`} />
</Figure>

A common slip is forgetting that the environment, not the flag, is the unit of distribution and isolation. Say "everything is keyed by environment" early in the platform design.

<h2 id="walkthrough">Chapter 14 · A flag platform, out loud</h2>

This is a 45-minute round compressed to its spoken lines, following the <a href={`${BASE}sd/lessons/delivery-framework/`}>delivery framework</a>. Read it aloud once. The prompt: "Design a feature flag and experimentation platform. Think LaunchDarkly." The numbers below are illustrative assumptions, labelled as such.

**0:02 · Roadmap and requirements**

> **You:** "I'll spend about six minutes on requirements and scale, a couple on entities and the API, build a simple design that works, then go deep on the two or three hard parts, and wrap up. Would you like numbers up front or as they matter?"
>
> **Interviewer:** "As they matter."
>
> **You:** "Functional: customers define flags with variations, targeting rules, segments and percentage rollouts, per environment. Their applications evaluate flags through SDKs, server-side and client-side. Changes reach running applications quickly, including a kill switch. And experiments: assignment, exposure tracking and results. Out of scope unless you want them: billing, the admin UI's design, a full stats engine; I'll design the pipeline that feeds it."

**0:05 · Non-functionals with numbers**

> **You:** "The defining requirement: **evaluation adds no network call and the platform can never take a customer's product down.** So evaluation is local, microseconds. Propagation: a change reaches 99% of SDKs within about five seconds, which is what makes a kill switch useful. The control plane needs strong consistency and an audit trail; the data plane favours availability and tolerates seconds of staleness. Privacy: client devices never see rules."
>
> "Scale, assumed: 2,000 customer organisations with three environments each, 6,000 environments, averaging 500 flags at about 1 KB of rules: about 500 KB of ruleset per environment, 3 GB in total, so all of it fits in memory on every streaming node. A million connected server SDK instances. About 100,000 flag changes a day, which is only about 1.2 a second. Evaluation volume is huge but it happens in customers' processes, so it costs us nothing. What reaches us is summary counts and exposure events."

**0:08 · Core entities**

> **You:** "Organisation has many Projects; a Project has many Environments and many Flags. A Flag's definition (key, kind, variations) is per project; its **targeting** (on/off, targets, rules, rollout, fallthrough) is per environment, so Flag-to-Environment is many-to-many through a FlagConfig. Segments are per environment. Every change creates an AuditEntry and bumps the environment's Version. Experiments reference a flag in an environment, a set of metrics and guardrails. SDK keys belong to exactly one environment."

**0:10 · API**

```text
Control plane (authenticated users, audited)
  PUT  /projects/{p}/flags/{key}                       define flag: kind, variations, owner, expiry
  PATCH /envs/{e}/flags/{key}  { ops, comment }        change targeting -> new env version, audit entry
  POST /envs/{e}/flags/{key}/approvals                 request / approve a change
Data plane (SDK keys)
  GET  /sdk/envs/{e}/ruleset            -> 302 to CDN  /rulesets/{e}/v{n}.json   (startup, resync)
  GET  /sdk/envs/{e}/stream?since={n}   -> SSE: patch events with versions
  POST /sdk/events                      <- batched exposures and summary counts
Client side (public client id, never rules)
  POST /client/envs/{e}/evaluate  { context }  -> { flagKey: variation, ... }  client-visible flags only
```

> **You:** "Changes carry a comment for the audit log. The ruleset endpoint redirects to an immutable, versioned CDN URL. The stream takes a `since` version so a reconnecting SDK gets just the deltas it missed."

**0:15 · High-level design, one requirement at a time**

> **You:** "Change a flag: the admin API validates the change, writes the new config and an audit entry and increments the environment's version in **one database transaction**, then publishes the change through a transactional outbox, so a committed change is never lost between the database and the bus. A publisher writes the full snapshot for that version to object storage behind the CDN, and puts the delta on the change bus."
>
> "Evaluate: server SDKs fetch the snapshot at startup, subscribe to the stream from that version, and evaluate every check locally from memory. Client SDKs call the evaluate endpoint, served from an edge worker or our evaluation service, and get only their own results."
>
> "Experiments: SDKs emit deduplicated exposure events and summary counts to an ingestion tier that writes to a log. A stream job deduplicates and lands them in a warehouse next to the customer's metric events, and a stats job computes results, the SRM check and guardrails."

The change itself is one transaction (SQL sketch; the outbox row is published after commit):

```sql
BEGIN;
UPDATE flag_config SET rules = :new_rules, version = :v + 1
 WHERE env_id = :e AND flag_key = :k AND version = :v;      -- optimistic check
UPDATE environment SET version = version + 1 WHERE id = :e;
INSERT INTO audit_log (env_id, flag_key, actor, before_state, after_state, reason) VALUES (...);
INSERT INTO outbox (env_id, env_version, payload) VALUES (:e, :v_env + 1, :delta);
COMMIT;
```

    API -->|"2 txn: config +<br/>audit + version"| PG[("Relational DB<br/>flags, audit,<br/>outbox")]

**0:24 · Deep dive 1: bucketing and evaluation**

> **You:** "Evaluation is a pure function: flag off gives the off variation; then individual targets; rules in order, first match wins; then the fallthrough. Percentages use `hash(salt + userKey) mod 10,000`, where the salt defaults to the flag key. The flag key is in the hash so that different flags pick independent cohorts, otherwise the same 10% of users would be in every rollout and every experiment, and the results would contaminate each other. Each variation owns a fixed range of buckets, so ramping from 10% to 25% only adds users; nobody flips. And the hash is specified over UTF-8 bytes so every SDK language computes the same bucket."

**0:29 · Deep dive 2: propagation and fan-out**

> **You:** "A million SDK connections at, say, 50,000 idle connections per streaming node is 20 nodes; I'd run double for headroom. Fan-out is cheap because we push deltas: an average environment has about 170 SDKs, so a 1 KB change is about 170 KB of traffic; our largest customer's 10,000 SDKs is 10 MB. Pushing full 500 KB snapshots instead would be about 83 MB per change on average, so snapshots only serve startup and resync. Every change carries the environment's next version; an SDK applies version n+1, ignores old ones, and on a gap fetches the snapshot. If a streaming node dies, its 50,000 SDKs reconnect with jitter and ask for deltas since their version; anyone too far behind pulls a snapshot from the CDN. 50,000 x 500 KB is 25 GB, which over 30 seconds of jitter is about 833 MB/s, a CDN's job and not our origin's. I'd measure propagation by having SDKs report their version, and alert on the 99th percentile lag."

**0:34 · Deep dive 3: availability and safety**

> **You:** "The platform must never take a customer down. SDKs keep the last ruleset in memory and on disk; if we're down they keep serving it and report its age. A cold start with nothing available waits a second or two, then uses the defaults in the customer's code. Client SDKs cache their last values on the device. On the safety side: every change is audited with a reason, critical production flags need an approval, and guarded rollouts compare treatment against control error rates and roll back automatically. For experiments, exposures are deduplicated first-exposure events, every experiment gets an automatic SRM check, and results use fixed horizons or sequential tests so peeking does not manufacture winners."

**0:39 · Wrap-up**

> **You:** "To recap: local evaluation, deterministic bucketing, versioned deltas over SSE with CDN snapshots, last-known-good everywhere, audited and guarded changes, and an exposure pipeline into a stats engine. At 10x, the first pressure is connection count and the event pipeline, not evaluation: relays and more streaming nodes for the first, partitioning the log by environment for the second. Big segments would move to a separate store the SDK queries and caches. I'd monitor propagation lag, ruleset age per SDK, stream connection churn, event-ingest lag and SRM alerts. With more time I'd add stale-flag detection with code references, and mutually exclusive experiment layers."

**Check the numbers yourself:** 2,000 x 3 = 6,000 environments; 500 flags x 1 KB = 500 KB each; 6,000 x 500 KB = 3 GB. 100,000 changes / 86,400 s = about 1.16/s. 1,000,000 / 6,000 = about 167 SDKs per environment, so 167 KB per 1 KB change; 167 x 500 KB = about 83 MB per change as full snapshots. 1,000,000 / 50,000 = 20 nodes. 50,000 x 500 KB = 25 GB; / 30 s = about 833 MB/s.

<h2 id="interview-script">Say it in the room</h2>

The interviewer leans back: "So, feature flags. Isn't that just a database table with booleans in it?" Here is how to answer at three depths. Say your own answer first, then open the model answer.

<AnswerModes id="feature-flags-table-of-booleans" q="Isn't a feature flag service just a table of booleans?">
<Fragment slot="short">
The table is the easy part. The hard requirement is that a flag check sits in every request's hot path, so it cannot be a network call, and the flag system cannot take the product down. SDKs hold the ruleset in memory and evaluate locally. Changes stream in as versioned deltas, with last-known-good and safe code defaults when the service is unreachable.
</Fragment>
<Fragment slot="medium">
The table is the easy part. The hard requirement is that a flag check sits in every request's hot path, so it **cannot be a network call** and the flag system **cannot take the product down**. I split it into a **control plane** (admin API, a versioned, audited database, approvals) and a **data plane** where SDKs hold the whole ruleset in memory and evaluate in microseconds. Evaluation is a pure function: off switch, individual targets, rules in order, then a fallthrough. Percentages use **hash of flag key plus user key, mod 10,000**, so the same user stays in the same bucket with no storage, different flags are independent, and ramps only add users. Changes travel as **versioned deltas over SSE** in about a second, with CDN snapshots for startup and gaps and polling as a fallback. SDKs keep **last-known-good** and fall back to safe code defaults, chosen per kind of flag.
</Fragment>
<Fragment slot="deep">
**Why not a table.** Flag checks happen about 20 per request at 500K requests per second, which is 10M evaluations per second. A network call per check would add latency to every request and cap availability at the flag service's availability.

**Architecture.** Control plane: relational database as truth, audit log, approvals, a transactional outbox to publish changes. Data plane: SDKs with full ruleset, streaming tier, relays, versioned snapshots on a CDN.

**Evaluation and bucketing.** Pure function over (ruleset version, flag, context). `bucket = hash(salt + "." + key) mod 10,000`, salt defaults to the flag key, UTF-8 bytes, same hash in every SDK. Ramps move a boundary; re-splits move users, so never re-split mid-experiment.

**Distribution.** SSE deltas, snapshots from CDN, versions that count up by one for gap detection, jittered reconnects, polling fallback, relays for fan-out.

**Failure.** Last-known-good in memory and on disk; bounded cold-start wait; code defaults per kind (old path, healthy, control). Alert on ruleset age; never auto-revert on staleness.

**Safety and experiments.** Audit, approvals, guarded rollouts against control, kill switches that are tested. Experiments: first-exposure logging, SRM check, fixed sample size or sequential tests, guardrails.

**Cleanup.** Owner and expiry at creation, stale detection, never reuse a key.
</Fragment>
</AnswerModes>

**Five follow-ups you will get:**

<Reveal q="1 · How do you make sure a user does not flip between variants?">

Deterministic hashing: `bucket = hash(flagKey + "." + userKey) mod 10,000`, and each variation owns a fixed range of buckets. Same inputs, same bucket, on every server, with nothing stored. Ramping moves a boundary, so users already in stay in. The flag key keeps different flags independent. The hash is specified over UTF-8 bytes so every SDK language agrees. Users flip only if the rules or salt change, and for experiments that must survive edits, some platforms persist the first assignment.

</Reveal>

<Reveal q="2 · The flag service is down. What happens?">

Nothing visible. SDKs evaluate from memory, so running services carry on with the last ruleset. They report its age and we alert past a few minutes, because kill switches will not land. New pods load last-known-good from disk or a relay; with nothing at all they wait a bounded second or two and then use the code defaults, which are chosen per kind: old path for release toggles, normal operation for kill switches, control for experiments. We never mass-revert to defaults because the control plane is down.

</Reveal>

<Reveal q="3 · How fast does a kill switch take effect, and how do you know?">

Seconds. The change commits, goes out through an outbox to the streaming tier, and reaches SDKs over SSE as a versioned delta. SDKs report the version they hold, so the dashboard can say "applied by 99% of SDKs in 2.1 seconds" and we alert on the propagation percentile. Polling at 30 seconds is only the fallback; on its own it would mean up to 30 seconds of a fire still burning.

</Reveal>

<Reveal q="4 · How do flags work in a browser or mobile app?">

Clients never get the ruleset, because it contains other users' emails, segments and unreleased feature names. The server or an edge worker evaluates the client-visible flags for this user and returns just the results. The server render embeds them in the HTML so there is no flicker; mobile caches last values for offline starts and re-evaluates on login. The client-side id is public and can only fetch the user's own results. Anything security-relevant is also enforced on the server.

</Reveal>

<Reveal q="5 · How do you know an experiment's result is real?">

Four checks. Randomisation by hash, decided before behaviour. Analysis on users with an exposure event, not everyone assigned. An SRM check first: if a designed 50/50 comes out 50,000 versus 51,500, chi-square is about 22 against a threshold of 10.83 and the pipeline is broken, so we do not read the results. A sample size fixed in advance (about 57,600 per arm to detect 10% to 10.5% conversion) or a sequential method, because daily peeking with stop-on-significance gives about a 25% false-positive rate over 20 looks. And guardrail metrics that stop the test if it hurts errors, latency or revenue.

</Reveal>

## Five mistakes to leave behind

1. **A network call per flag check.** Push rules, evaluate locally.
2. **`Math.random()` or `hashCode()` for rollouts.** Use a specified, well-mixed hash of flag key and user key.
3. **"Default off" for everything.** Defaults depend on the kind; a kill switch defaults to healthy.
4. **Shipping the ruleset to the browser.** Clients get answers, not rules.
5. **Reading an experiment before checking SRM, or stopping on the first good day.** Check the split, fix the sample size, watch guardrails.

**Keep it warm:** with a study partner, do a 10-minute mini-design of flags for your own product. Then take any earlier mock (rate limiter, feed) and add the "rollout: 1%, flags, guardrails, kill switch" ending in 60 seconds. That ending upgrades every design you present.

**Look these up yourself**

- **Sequential testing and always-valid p-values (e.g. mSPRT)** — how platforms let you watch results continuously without the peeking penalty.
- **CUPED (variance reduction with pre-experiment data)** — the same experiment needs fewer users when you subtract what you could already predict.
- **Multiple comparisons** — twenty metrics at p &lt; 0.05 will usually produce one false "win"; how platforms correct for it.
- **Holdout groups** — a small slice kept away from all launches for months to measure the cumulative effect of a quarter's changes.
- **Novelty and primacy effects** — why a new design's first week can over- or under-state its long-run effect.
- **Mutually exclusive experiments and layers** — keeping two conflicting experiments from hitting the same user.
- **Prerequisite flags and flag dependencies** — "this flag only evaluates if that one is on", and the cycles to forbid.
- **Interference in two-sided marketplaces** — cluster randomisation and switchback experiments when users affect each other.
