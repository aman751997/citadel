<h2 id="prologue">Prologue · Why GPUs look idle while users wait</h2>

Here is a failure that happens when a team self-hosts a large model. A chat feature launches. Within twenty minutes the support channel fills with screenshots of a blinking cursor and no text. The dashboard says:

- Time to first token, p95: **38 seconds**.
- Request queue: growing.
- GPU compute utilisation: **31%**.

Someone says the GPUs are bored, so just add more. That is the wrong reading. The GPUs were not short of arithmetic. They were **out of memory for conversations**, and the compute counters read low because of how text generation works. By the end of Chapter 4 you can explain both facts with numbers.

"Design ChatGPT's serving layer" is a common senior-level question. Candidates fail it by applying web-service intuition, because LLM inference breaks three assumptions at once:

1. **Requests last seconds to minutes**, not milliseconds, and the length is unknown when the request arrives.
2. **The bottleneck is GPU memory** (both capacity and bandwidth), not CPU or I/O.
3. **The output arrives one piece at a time**, so "latency" means two different things.

If you call LLMs from an application, you already know prompt caching, token limits and streaming from the client side. This lesson is the server side, which is where the interview question lives.

**An LLM serving design answers four questions, out loud:**

1. **What does one request cost?** Prompt tokens of compute, output tokens of sequential steps, and gigabytes of memory held for the request's whole life.
2. **How do many requests share a GPU?** Continuous batching, paged KV memory, prefix reuse.
3. **Who gets in, and who waits?** Admission by memory budget, token-based limits, priority tiers.
4. **What do users feel?** Time to first token and the pace of the stream, not total time.

**Words used throughout** (each is defined again where it first matters):

| Term | Plain meaning |
|---|---|
| Token | A chunk of text (often a few characters) that the model reads and writes. |
| Parameters / weights | The model's learned numbers. A "70B" model has 70 billion of them. |
| HBM | The GPU's main memory (high-bandwidth memory). Weights and caches live here. |
| FLOP | One arithmetic operation. TFLOP/s = trillions per second. |
| Memory bandwidth | How many bytes per second the chip can read from HBM. |
| Context | All tokens (prompt plus output so far) the model can look at for one request. |
| Batch | The set of requests processed together in one step. |
| Replica | One complete copy of the model, possibly spread over several GPUs. |
| SLO | A latency or availability target, such as "p95 under 1 second". |

<h2 id="autoregressive">Chapter 1 · One token at a time</h2>

**What is it?** A language model reads **tokens**: chunks from a fixed vocabulary, often a few characters long. For English a common rule of thumb is about ¾ of a word per token (check your tokenizer; code and other languages differ). Everything here is counted in tokens: prompts, outputs, limits, prices.

A decoder-only model is a function. Given the tokens so far, it outputs a probability for every possible *next* token. The server picks one (the most likely, or a random draw weighted by probability and a temperature setting), appends it, and asks again. Token 2 cannot be computed until token 1 exists. That loop is called **autoregressive generation**.

**Why does it matter for serving?** The loop has two phases with very different costs:

1. **Prefill.** The whole prompt is known up front, so all prompt tokens go through the model **in one parallel pass**. This pass also writes each prompt token's keys and values into the KV cache (below), and its last position predicts the **first output token**. It is a big matrix-times-matrix job: **compute-bound** and fast per token.
2. **Decode.** Every later token needs **its own pass**, processing one new token per sequence while looking at everything before it. Each pass reads the *entire* set of weights to do a small amount of arithmetic. It is **memory-bandwidth-bound** and repeats once per output token. This is the long tail.

**The KV cache.** Attention is the step where each new token looks back at every earlier token. For each earlier token it needs two vectors, a **key** and a **value**, at every layer. Recomputing them for the whole history at every step would make step 400 redo the work of steps 1 to 399. So the server **keeps them** in GPU memory for the life of the request. That is the KV cache. It is what makes each decode step cheap, and it is the fact that drives the whole design, because it is **big, per-request, and growing**.

**What follows from this:**

- **Output length is unknown at arrival.** You cannot size a request by its prompt. A "hi" may produce two thousand tokens.
- **Two latencies.** The pause before the first word (queue plus prefill) and the pace afterwards (decode) are different problems with different fixes.
- **Long-lived, stateful requests.** A request holds GPU memory for its whole life, so it is pinned to one replica. You cannot move it mid-flight the way you retry a stateless HTTP call.
- **Streaming is natural.** Tokens exist one at a time, so you send them one at a time.

<Trace title="Count the passes" steps={generation} takeaway="One parallel prefill pass emits token 1; every later token is one decode step. The KV cache trades memory for not recomputing the past." />

<Reveal q="Why can't you run the decode steps of one request in parallel across many GPUs to finish faster?">

Each step's input is the previous step's output, so the dependency is sequential by construction. You can make *each step* faster (split the weights across GPUs: tensor parallelism, Chapter 11), or produce *several tokens per step* with a guess-and-check trick (speculative decoding, Chapter 9). You cannot parallelise across the steps of one sequence. Parallelism across *different* requests is free, and that is batching.

</Reveal>

<h2 id="metrics">Chapter 2 · TTFT, inter-token latency and goodput</h2>

**What is it?** Because output arrives in pieces, one "latency" number hides what users feel. These are the metrics to name:

| Metric | Definition | What drives it | Target (state as an assumption) |
|---|---|---|---|
| **TTFT** (time to first token) | Request arrival to first token received | Queue wait + prefill (+ network, tokenisation) | p95 under ~1 s for chat |
| **ITL / TPOT** (inter-token latency, time per output token) | Gap between consecutive tokens. TPOT = (E2E − TTFT) ÷ (output tokens − 1) | Decode step time: batch size, KV size, model size | ~20 to 50 ms, faster than people read |
| **E2E latency** | Arrival to last token | TTFT + (tokens − 1) × TPOT, so mostly **answer length** | Rarely the right SLO for chat |
| **Throughput** | Output tokens/s (and requests/s) per replica or fleet | Batch size, hardware, model | Maximise subject to the two SLOs |
| **Goodput** | Throughput of requests that **met** the SLO | Everything above | The number to optimise |
| **Cost per million tokens** | Fleet $/hour ÷ millions of tokens per hour | Utilisation, batch size, model size | Business constraint |

"Tokens/second" is ambiguous. Per user it is 1 ÷ ITL (a speed the reader feels). Per replica it is the sum over all users in the batch (a capacity number). Say which one you mean.

**Worked numbers.** A request waits 300 ms in the queue, prefill takes 150 ms, then 200 tokens stream 25 ms apart:

- TTFT = 300 + 150 = **450 ms**.
- E2E = 0.45 s + 199 × 0.025 s ≈ **5.4 s**.
- If the same request asked for 2,000 tokens, E2E would be 0.45 + 1,999 × 0.025 ≈ **50 s**, and nothing would be wrong.

<Figure caption="One request's timeline. TTFT ends at the first token. Everything after it is decode at the ITL rhythm, so E2E mostly measures answer length.">
  <Mermaid code={`flowchart LR
    A["arrival"] --> Q["queue wait\n300 ms"]
    Q --> PF["prefill\n150 ms"]
    PF --> F["token 1\nTTFT = 450 ms"]
    F --> D["199 more tokens\n25 ms apart (ITL)"]
    D --> E["last token\nE2E ≈ 5.4 s"]`} />
</Figure>

**Why TTFT and ITL pull against each other.** Bigger batches raise throughput but make each decode step longer (worse ITL). Admitting a new request means running its prefill, which briefly delays everyone else's decode (an ITL spike), while refusing it raises *its* TTFT. Every scheduler is a deal between those two numbers.

**Goodput is the honest scoreboard:** tokens per second from requests that kept both promises. A configuration that pushes tokens/s up by letting 30% of requests miss the TTFT target has *lower* goodput.

**Read speed sets the ITL bar.** 30 ms per token is about 33 tokens/s, roughly 25 words a second, far faster than anyone reads. Going from 30 ms to 10 ms is invisible to a chat user and expensive for you. It matters for agents and code tools that consume the whole output before acting.

<Reveal q="Your agent product calls the model, waits for the full JSON, then calls a tool. Which latency matters now?">

E2E, because the consumer is a program that cannot act on half an answer. For agents, total time per call compounds across steps, so you care about TPOT × output length. Push for **shorter outputs** (terse, structured responses), smaller models for simple steps, and speculative decoding. Name the consumer before you pick the metric.

</Reveal>

<h2 id="memory">Chapter 3 · Where 320 GB goes</h2>

**What is it?** GPU memory holds three things: **the weights**, **the KV cache**, and **working space** (activations, runtime buffers, the serving framework's own overhead). Only the KV cache grows with traffic.

**Weights = parameters × bytes per parameter.**

| Precision | Bytes / param | 8B model | 70B model |
|---|---|---|---|
| FP16 / BF16 | 2 | 16 GB | **140 GB** |
| INT8 / FP8 | 1 | 8 GB | 70 GB |
| INT4 | 0.5 | 4 GB | 35 GB (+ a few % for scales) |

A 70B model in BF16 does not fit on one 80 GB GPU before it has served a token. That forces a choice: split it across GPUs (Chapter 11) or shrink it (Chapter 10).

**KV cache per token = 2 × layers × kv_heads × head_dim × bytes per element.** The 2 is one key and one value. `kv_heads` is the number of key/value heads. With **grouped-query attention (GQA)** many query heads share a few KV heads, so it is much smaller than the number of query heads.

**Worked example.** Assumption for this lesson: an illustrative 70B-class model with 80 layers, 64 query heads but 8 KV heads (GQA), head_dim 128, BF16. Real models differ; look up the config of the one you serve.

```python
def weights_bytes(params, bytes_per_param):
    return params * bytes_per_param

def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per_elem):
    return 2 * layers * kv_heads * head_dim * bytes_per_elem   # 2 = one K and one V

GB = 1e9
w = weights_bytes(70e9, 2)                       # BF16
per_tok = kv_bytes_per_token(80, 8, 128, 2)
budget = 4 * 80 * GB - w - 0.10 * 4 * 80 * GB   # 10% reserve
print(w / GB, per_tok, budget / GB)              # 140.0 327680 148.0
print(int(budget // per_tok), int(budget // (per_tok * 4096)))   # 451660 110
```

- Per token: 2 × 80 × 8 × 128 × 2 bytes = **327,680 bytes ≈ 0.33 MB**.
- One 4,096-token conversation: 327,680 × 4,096 ≈ **1.34 GB**.
- One 32,768-token context: ≈ **10.7 GB**. A 131,072-token (128K) context: ≈ **43 GB**, more than half an 80 GB GPU for *one user*.
- Without GQA (64 KV heads, classic multi-head attention) every figure is 8× bigger: 2,621,440 bytes ≈ 2.6 MB per token, ≈ **10.7 GB** for a 4K conversation. GQA exists largely to make serving affordable.

**The budget for one replica.** Assumptions: 4 GPUs × 80 GB = 320 GB with tensor parallelism (Chapter 11), and about 10% of memory reserved for activations and runtime (frameworks expose this as a memory-utilisation setting).

- Weights: 140 GB. Reserve: 32 GB.
- **KV budget: 320 − 140 − 32 = 148 GB**, which is 148 × 10⁹ ÷ 327,680 ≈ **451,000 tokens** of KV across *all* in-flight requests.

**Why the KV cache bounds concurrency.** Divide the budget by the cost of one conversation:

| Context per request | KV per request | Concurrent requests per replica |
|---|---|---|
| 1,300 tokens | 0.43 GB | ≈ 347 |
| 4,096 tokens | 1.34 GB | ≈ 110 |
| 32,768 tokens | 10.7 GB | ≈ 13 |
| 4,096 tokens, **no GQA** | 10.7 GB | ≈ 13 |

That explains the opening incident: a product that stuffs long histories into every request and allows long outputs fills the KV pool with a few dozen requests. The scheduler reserves memory for the worst case, the queue grows, and the arithmetic units sit mostly idle. **The GPUs were not bored. Their memory was full.**

<h2 id="bandwidth">Chapter 4 · Memory-bound decode</h2>

**What is it, and why does utilisation look low?** Every decode step multiplies a tiny input (one token per sequence) by **every weight in the model**. The weights sit in HBM and must be streamed through the chip each step. Two hardware numbers decide which one you wait on. Assumptions for this arithmetic (check current specs for your accelerator):

- **Compute:** about 1,000 TFLOP/s of dense BF16 per GPU (peak).
- **Memory bandwidth:** about 3 TB/s per GPU (peak), so about 12 TB/s across a 4-GPU replica.

**Arithmetic intensity** is FLOPs per byte moved. The break-even point (the "ridge point") is 1,000 × 10¹² ÷ 3 × 10¹² ≈ **333 FLOPs per byte**. Each BF16 weight (2 bytes) does about 2 FLOPs per token it touches (one multiply, one add), so about **1 FLOP per byte per token**. A pass over the weights becomes compute-bound only when it serves roughly **300+ tokens at once**.

- **Prefill** serves thousands of prompt tokens per weight read: **compute-bound**.
- **Decode** serves one token per sequence, so only as many tokens as the **batch size**. Below a few hundred, it is **memory-bound**.

<Figure caption="Why decode leaves the arithmetic units idle: the step time is the time to stream the weights, and the math for a few tokens finishes far sooner.">
  <Mermaid code={`flowchart LR
    H[("HBM\n140 GB weights\n+ KV cache")] -->|"stream every step\n12 TB/s"| C["compute units\nmath for 1 to 64 tokens\nfinishes early"]
    C --> T["next token(s)"]
    T -->|"next step"| H`} />
</Figure>

**Worked numbers (decode, illustrative 70B, 4 GPUs, peak bandwidth).** Step time is the bytes read divided by bandwidth.

| Batch | Bytes read per step | Step time (= ITL) | Throughput |
|---|---|---|---|
| 1 | 140 GB of weights | 140 ÷ 12,000 s ≈ **11.7 ms** | ≈ 86 tokens/s |
| 64, each with ~2,048 tokens of KV | 140 GB + 64 × 2,048 × 327,680 B ≈ 140 + 43 = 183 GB | ≈ **15.2 ms** | 64 ÷ 0.0152 ≈ **4,200 tokens/s** |

Same weight read, 64 users served: roughly **50×** the throughput for a step only about 30% longer. Real systems achieve less than peak bandwidth, but the shape holds. This is why "31% utilisation" proves nothing about headroom: memory-bound decode always looks underused on compute counters.

**Prefill, worked.** FLOPs per token ≈ 2 × parameters, so a 2,000-token prompt on a 70B model ≈ 2 × 70 × 10⁹ × 2,000 = **280 TFLOP**. At an assumed 50% of peak on 4 GPUs (2,000 TFLOP/s effective), that is **0.14 s**. Prefill time grows with prompt length, which is why long RAG prompts raise TTFT and why prefix caching (Chapter 7) is a TTFT lever.

Notice the second term in the batch-64 row: **KV reads also grow with batch and context.** At long contexts the KV bytes can rival the weights, and ITL rises with every token every sequence adds. Long-context traffic is therefore expensive twice, in memory capacity *and* in bandwidth.

<Trace title="Memory-bound or compute-bound?" steps={bandwidth} takeaway="Decode streams all weights per step for a handful of tokens: memory-bound, so batch to reuse each read. Prefill reuses each read across the whole prompt: compute-bound." />

<Reveal q="If decode is memory-bound, why not make the batch as large as possible?">

Three limits. **KV capacity:** every sequence in the batch holds its cache (Chapter 3). **ITL:** each sequence's KV must also be read every step, so step time rises with batch and context, and pushing too far breaks the ITL SLO. **The ridge point:** past a few hundred tokens per step, decode becomes compute-bound and extra batch stops being free. The right batch is the largest one that keeps both latency SLOs, which is what goodput measures.

</Reveal>

<h2 id="batching">Chapter 5 · Static vs continuous batching</h2>

**What is it, and what problem does it solve?** Chapter 4 showed that one weight read can serve many sequences. **Batching** means running several requests in the same step to share that read. The question is how the batch is formed.

**Static (request-level) batching.** Collect N requests, run them together until **all** finish, then take the next N. Imagine a batch of 8: seven answers finish in 50 tokens, the eighth writes 2,000 tokens. The seven slots sit empty for the other 1,950 steps and the queue waits outside. Slot utilisation is (7 × 50 + 2,000) ÷ (8 × 2,000) ≈ **15%**.

**Continuous (in-flight, iteration-level) batching.** The scheduler **rebuilds the batch at every decode step**. A sequence that emits its stop token leaves at once, and a waiting request joins at the next step (its prefill is folded into that step). You get the throughput of batching with latency close to solo serving. It was published as iteration-level scheduling in the Orca paper (OSDI 2022) and popularised by vLLM. Today it is the default in mainstream serving engines.

| | Static batching | Continuous batching |
|---|---|---|
| Batch membership changes | Only when the whole batch ends | Every decode step |
| Short request next to a long one | Waits for the long one | Leaves immediately |
| Queued request | Waits for the next batch | Joins at the next step if memory allows |
| Fits | Offline jobs with similar lengths | Interactive traffic with unknown output lengths |

<Figure caption="Same requests, two schedulers. Static: slots idle (faded) until the long request ends. Continuous: a freed slot is refilled at the next step (blue = a newcomer joining mid-flight).">
  <ArrayStrip name="Static, step 60" values={['A ✓', 'B ✓', 'C ✓', 'D ✓', 'E ✓', 'F ✓', 'G ✓', 'H …']} indices={false} tones={{ 0: 'out', 1: 'out', 2: 'out', 3: 'out', 4: 'out', 5: 'out', 6: 'out', 7: 'hot' }} regions={[{ from: 0, to: 6, label: 'idle until H finishes', tone: 'dim' }]} />

</Figure>

**How it works.** Each step the scheduler (1) admits waiting requests whose prompt fits in free KV blocks, (2) runs one step for everything in the batch, (3) removes finished sequences and returns their blocks. A toy version with a six-block pool (16 tokens per block):

```python
from collections import deque

BLOCK = 16                      # tokens per KV block
free_blocks = 6                 # a tiny KV pool so the effect is visible
waiting = deque([("A", 30, 4), ("B", 30, 8), ("C", 30, 4)])  # (name, prompt tokens, output tokens)
running = {}                    # name -> [tokens_so_far, tokens_left, blocks_held]

def blocks(tokens):
    return -(-tokens // BLOCK)  # ceil

step = 0
while waiting or running:
    step += 1
    # 1. admit while the prompt (plus one block of headroom) fits in free KV blocks
    while waiting and blocks(waiting[0][1]) + 1 <= free_blocks:
        name, prompt, out = waiting.popleft()
        running[name] = [prompt, out, blocks(prompt)]
        free_blocks -= blocks(prompt)
    # 2. one decode step for everyone running
    for name in list(running):
        r = running[name]
        r[0] += 1; r[1] -= 1
        if blocks(r[0]) > r[2]:               # last block is full: grab another
            r[2] += 1; free_blocks -= 1
        if r[1] == 0:                          # finished: blocks return to the pool now
            free_blocks += r[2]; del running[name]
    print(step, sorted(running), "free blocks:", free_blocks)
```

```text
1 ['A', 'B'] free blocks: 2
2 ['A', 'B'] free blocks: 2
3 ['A', 'B'] free blocks: 0
4 ['B'] free blocks: 3
5 ['B', 'C'] free blocks: 1
...
```

C waits for four steps. When A finishes, its three blocks go back to the pool and C joins at the next step while B is still running. This toy has a real hole: at step 3 the pool hit zero. If B had needed one more block it could not get it. Real engines handle that with preemption (below).

**Admission is a memory budget.** The scheduler admits a request when there is **KV memory** for its prompt now and room for its output as it grows, not when a request count is below some number. "Our concurrency limit is a memory budget, not a QPS number" is the senior signal of this whole topic.

**What if memory runs out mid-flight?** Sequences grow every step. If the KV pool fills, the scheduler **preempts** someone. It either **swaps** their KV blocks to CPU memory and back later, or **drops** them and **recomputes** the KV from the tokens so far when they resume. Older vLLM versions offered both; current vLLM (V1) defaults to **recompute** because it has lower overhead there (vLLM docs, checked 2026-10-19). Check what your engine does. Preemptions show up as ITL stalls. A rising preemption rate means admission is too greedy.

| Approach | Utilisation | TTFT under mixed lengths | Notes |
|---|---|---|---|
| No batching | Very low | Good until the queue builds | Wastes almost all bandwidth |
| Static batching | Medium | Poor: convoy effect | Fine for offline jobs with similar lengths |
| Continuous batching | High | Good | The default answer |
| Continuous + length-bucketed queues | High | Slightly better | Auxiliary; output length is still a guess |

<Trace title="Schedule the batch" steps={batching} takeaway="Rebuild the batch every step; admit by free KV blocks; preempt when the pool runs dry." />

<Reveal q="Why not reserve each request's KV for its max_tokens up front, so preemption never happens?">

You can, and many early servers did, but it wastes most of the memory. A request with `max_tokens` = 4,096 that answers in 200 tokens held 20× the KV it needed for its whole life, and that reservation caps concurrency. The modern compromise: allocate as you grow (paging, next chapter), admit with a projection based on typical lengths, and accept occasional preemption. Capping `max_tokens` per product tier still matters, because it bounds the worst case.

</Reveal>

<h2 id="paging">Chapter 6 · Paged KV memory</h2>

**What is the problem?** If each sequence's KV cache must be one contiguous region, you must reserve for the worst-case length up front (wasted space inside each reservation: **internal fragmentation**), and freed regions of odd sizes cannot be reused well (**external fragmentation**). The vLLM paper (Kwon et al., SOSP 2023) measured earlier systems storing real token data in only 20.4% to 38.2% of their KV memory (the rest was lost to fragmentation and reservation). Wasted memory means smaller batches, which means less throughput (Chapter 4).

**PagedAttention (vLLM's idea).** Operating systems solved this with virtual memory. Split the KV cache into fixed-size **blocks** of a few tokens each (vLLM's default block size is 16 tokens in recent versions; older versions and some hardware platforms pick another value; vLLM docs and source, checked 2026-10-19). Each sequence has a **block table** that maps its logical positions to physical blocks anywhere in GPU memory. The attention kernel follows the table.

- **Allocate on demand:** a new block only when the last one fills. Waste is at most one partly filled block per sequence.
- **No external fragmentation:** any free block fits any sequence.
- **Sharing:** two sequences with the same prefix can point at the **same physical blocks** (reference-counted, copy-on-write when one diverges). This is the basis of prefix caching and of cheap parallel sampling (n answers to one prompt).

  <Mermaid code={`flowchart LR

      P5["P5"]
      P7["P7"]
      PF["free blocks …"]
    end
    subgraph A["Sequence A · block table"]
      A0["logical 0"]
      A1["logical 1"]
      A2["logical 2"]
    end

      B1["logical 1"]
    end
    A0 --> P0
    A1 --> P7
    A2 --> P3

    B1 --> P5`} />
</Figure>

The paper reported roughly **2 to 4× higher throughput** than the systems it compared against at the same latency, mostly because more sequences fit in the same memory. Exact gains depend on workload; the mechanism is what to remember.

| | Contiguous reservation | Paged blocks |
|---|---|---|
| Memory reserved per request | Worst-case length | One block at a time |
| Waste | Large, inside and between reservations | At most one partial block per sequence |
| Sharing a prefix | Copy it | Point at the same blocks |
| Cost | Simple kernels | An indirection in attention reads |

<Reveal q="Paging adds an indirection to every attention read. Why is it worth it?">

Decode is limited by how many sequences fit in memory (batch size), not by a small extra lookup in the attention kernel. Trading a little kernel complexity for near-zero fragmentation means more sequences per step, and more sequences per weight read is the throughput lever from Chapter 4.

</Reveal>

<h2 id="prefix-caching">Chapter 7 · Prefix caching</h2>

**What is it?** The KV for a given sequence of tokens is deterministic for a given model. If many requests start with the **byte-identical** prefix (a system prompt, tool definitions), compute its KV once, keep the blocks, and let later requests **reuse** them. Prefill then runs only on the new suffix.

**Why?** Imagine every request starts with the same 1,000 tokens (persona, safety rules, tool schemas) and 50 requests arrive per second. Without caching, the server recomputes those 1,000 tokens 50 times a second.

- **What hits:** system prompts, tool schemas, few-shot examples, RAG documents reused across questions, and, the big one for chat, **earlier turns of the same conversation**, since every turn resends the whole history.
- **How engines find matches:** vLLM's automatic prefix caching hashes full KV blocks by their token content and the hash of the block before them (vLLM docs, checked 2026-10-19). SGLang's RadixAttention keeps a radix tree of cached prefixes. Details vary; check your engine's docs.
- **Eviction:** cached blocks are reclaimable. Under memory pressure, LRU-style eviction drops the coldest prefixes.
- **Public APIs** expose the same idea as prompt caching: several providers bill cached input tokens at a discount and document a minimum prefix length and a cache lifetime. For example, Anthropic's docs list a minimum cacheable length per model (512 to 4,096 tokens), a 5-minute default lifetime, and cache reads at 0.1x the base input price or lower; OpenAI's docs list 1,024 tokens minimum for its newest models and cached reads at 0.1x or lower (both checked 2026-10-19). Prices and limits change, so read the page for your model.

**Worked numbers.** Prompt of 1,000 tokens, of which 600 are a cached prefix. Prefill work per request drops from 1,000 to **400** tokens: 400 × 140 GFLOP = 56 TFLOP instead of 140 TFLOP. At 2,000 TFLOP/s effective, prefill time goes from **70 ms to 28 ms**. At 100 requests/s the fleet needs 5.6 PFLOP/s instead of 14 PFLOP/s. Chapter 15 shows what that does to the GPU count.

**Routing makes or breaks it.** Each replica caches in its own GPU memory. If turn 5 of a conversation lands on a different replica than turns 1 to 4, the history must be prefilled again. So route with **session affinity** or **prefix-aware routing** (hash the prefix and prefer the replica that likely holds it; some routers track KV state per replica), balanced against load so one replica does not become a hot spot.

**Multi-tenant caveat.** Sharing KV blocks across tenants can leak information: a request that is faster because of a cache hit reveals that someone else sent that prefix. Research has demonstrated such timing differences against hosted APIs. A safe default is to scope the cache key by tenant (or by organisation) and share only what is truly common, such as a public system prompt.

| Tactic | Saves | Costs |
|---|---|---|
| Static system prompt first, variable parts last | Makes prefixes identical | Prompt-template discipline |
| Session-affinity routing | Re-prefill of chat history | Load imbalance; fall back to least-loaded |
| Larger cache share of memory | More hits | Fewer KV blocks for live sequences |
| Cache scoped per tenant | Prevents cross-tenant timing leaks | Fewer shared hits |

<h2 id="disaggregation">Chapter 8 · Prefill and decode fight on one GPU</h2>

**What is the problem?** Prefill is a burst of compute. Decode is a steady trickle bound by bandwidth. Put them on the same GPU and a **long prefill stalls every decode in the batch**. Say a seller pastes a 12,000-token catalogue: for about a second every other conversation on that replica freezes mid-sentence, and the ITL graph shows a spike each time a big prompt arrives. In the other direction, a stream of decode steps delays new prefills, so TTFT grows.

Two answers, in order of how established they are:

1. **Chunked prefill** (common in mainstream engines): split a long prompt's prefill into chunks of a few hundred to a few thousand tokens and **piggyback** each chunk on a decode step, so no single step gets much longer. Sarathi-Serve (OSDI 2024) is the paper to name. Cost: the long prompt's own TTFT rises a little.
2. **Disaggregated prefill/decode** (emerging; real deployments and papers exist, details vary): run prefill on one pool of GPUs and decode on another, and **transfer the KV cache** between them over a fast interconnect. Each pool is sized and tuned for its own bound. DistServe and Splitwise (Patel et al., ISCA 2024) argued for it. DistServe framed the win as goodput under separate TTFT and ITL targets; Splitwise reported throughput, cost and power (for example up to 1.4x throughput at 20% lower cost).

  <Mermaid code={`flowchart LR
    R["router"] --> PF["prefill pool\ncompute-bound\nsized for FLOPs"]
    PF -->|"KV cache transfer\n(fast interconnect)"| DC["decode pool\nmemory-bound\nsized for KV + bandwidth"]
    DC -->|"tokens"| C["client stream"]`} />
</Figure>

| | Colocated + chunked prefill | Disaggregated |
|---|---|---|
| Complexity | One pool | Two pools, KV transfer, two schedulers |
| ITL stability | Good | Best: decode never shares with prefill |
| Cost of transfer | None | KV bytes over the network (a 4K-token prompt is about 1.34 GB in our model) |
| When it wins | Most deployments | Large fleets with long prompts and strict, separate SLOs |

Transfer cost, worked: 1.34 GB over an assumed 50 GB/s link is about 27 ms, but over a 100 Gbit/s (12.5 GB/s) network it is about 107 ms. Link speed decides whether disaggregation pays.

<Reveal q="When would disaggregation be a bad idea?">

When prompts are short (transfer overhead dominates and there is little prefill to isolate), when the fleet is small (two pools cannot each be kept busy), or when the network between pools is slow. Shipping a gigabyte of KV per request over a congested link can cost more TTFT than the prefill itself. Lead with chunked prefill and mention disaggregation as the scale-out option, with that caveat.

</Reveal>

<h2 id="speculative">Chapter 9 · Speculative decoding</h2>

**What is it?** A small, fast **draft** model proposes the next k tokens (say k = 4). The large **target** model then runs **one forward pass over all k proposed positions**, a tiny prefill, and computes what it would have produced at each. Accept drafted tokens left to right while they pass the acceptance test. At the first rejection, take the target's own token instead. Every target pass yields at least one token, and up to k + 1.

**Why is it cheap?** Decode is memory-bound (Chapter 4). One pass over the weights scoring 5 positions costs nearly the same as scoring 1.

**Why is it safe?** With the standard rejection-sampling rule (Leviathan et al.; Chen et al., 2023, DeepMind), the output follows the **target model's distribution**, up to floating-point rounding. It is a latency trick, not an approximation.

**Expected tokens per target pass**, if each token is accepted independently with probability α: (1 − α^(k+1)) ÷ (1 − α). For α = 0.7 and k = 4 that is (1 − 0.168) ÷ 0.3 ≈ **2.8 tokens per pass**, before subtracting the draft model's cost. If the draft step costs a fraction c of a target step, the net speed-up is roughly 2.8 ÷ (1 + 4c): about 2.0× at c = 0.1 (an approximation that ignores verification overhead).

<Figure caption="One round of speculative decoding with k = 4: three drafts accepted, the fourth rejected and replaced by the target's own token. Four tokens for one target pass.">
  <Mermaid code={`sequenceDiagram
    participant D as Draft model (small)
    participant T as Target model (large)
    D->>D: propose t1 t2 t3 t4 (4 cheap steps)
    D->>T: verify all 4 in one forward pass
    T-->>T: accept t1 t2 t3, reject t4
    T->>T: emit its own token in place of t4
    Note over D,T: 4 tokens out for 1 target pass`} />
</Figure>

**Variants to name** (the field moves fast): extra prediction heads on the target itself (Medusa, EAGLE-style) instead of a separate draft model, and **n-gram / prompt-lookup** drafts that copy spans from the prompt (good for editing and code, where the output repeats the input).

**When it helps less:** at **large batch sizes** the GPU approaches the compute bound, so verification is no longer free and the speed-up shrinks or vanishes. It shines for low-latency, small-batch traffic (interactive coding, agents) and on predictable text.

<h2 id="quantization">Chapter 10 · Fewer bits</h2>

**What is it?** **Quantisation** stores numbers with fewer bits. Finance sees the GPU bill and someone proposes running the 70B model in 4-bit: a quarter of the memory, so a quarter of the GPUs. The right reply is "and what does it get wrong that it used to get right?" Three things can be quantised, with different payoffs:

| What | Example | Saves | Speeds | Risk |
|---|---|---|---|---|
| **Weights only** | INT8, INT4 (GPTQ, AWQ-style methods) | Weight memory: 140 → 70 → 35 GB | **Decode** (fewer bytes per step) | Small at 8-bit; can be noticeable at 4-bit on reasoning and code. Evaluate |
| **Weights + activations** | FP8, INT8 (W8A8) | Memory and compute | Prefill and decode on hardware with fast low-precision math | Needs calibration; hardware-dependent |
| **KV cache** | FP8 KV | KV per token: 327,680 → 163,840 bytes | More concurrent sequences, less KV bandwidth | Usually small; long-context tasks are most sensitive |

**Worked numbers.** INT4 weights for the 70B model are about 35 GB (plus a few % for scales), so the model **fits on one 80 GB GPU** with about 37 GB left for KV after an 8 GB reserve. Decode at batch 1 reads about 35 GB per step instead of 140 GB, a large ITL cut on a memory-bound workload. FP8 KV doubles how many conversations fit in the same KV budget: 37 GB ÷ 327,680 ≈ 113,000 tokens at BF16 KV, ≈ 226,000 at FP8 KV.

<Figure caption="Same 70B model, three weight precisions. Fewer bytes per weight frees memory for KV and cuts bytes streamed per decode step. KV is not shrunk unless you quantise it too.">
  <Mermaid code={`flowchart LR
    B["BF16\n140 GB\n4 GPUs"] --> I8["INT8 / FP8\n70 GB\n2 GPUs"]
    I8 --> I4["INT4\n35 GB\n1 GPU"]
    I4 --> Q["check quality on\nyour own tasks"]`} />
</Figure>

**The trade-off, said properly:** quantisation buys memory and bandwidth. It costs some accuracy, unevenly across tasks. **Run your own evals** on the product's real prompts, not just a public benchmark, and compare with the full-precision model before shipping. Also say the alternative: a smaller model at full precision may beat a bigger model at 4-bit for your task.

<Reveal q="Why does weight-only INT4 speed up decode much more than prefill?">

Decode is memory-bound: its time is mostly streaming weights, so 4× fewer weight bytes is close to 4× less waiting (minus dequantisation overhead and the KV reads, which do not shrink). Prefill is compute-bound, so weight bytes are not its bottleneck, and with weight-only quantisation the math typically still runs in 16-bit after dequantising, so prefill gains little.

</Reveal>

<h2 id="parallelism">Chapter 11 · One model, many GPUs</h2>

**What is it?** When a model does not fit on one GPU you split it. Where you cut depends on how often the pieces must talk. Servers typically hold 8 GPUs wired with a fast link, with a slower network between servers.

- **Tensor parallelism (TP):** split **every layer's** weight matrices across GPUs. Each computes its slice, and they combine results with a collective operation (all-reduce) **at every layer**, on every token. Each GPU reads only 1/N of the weights per step, so **per-token latency drops**. It is chatty, so keep it **inside one server** on the fast link. TP = 4 is our 70B replica.
- **Pipeline parallelism (PP):** split the model **by layers** into stages on different GPUs or servers. Activations hop from stage to stage. Little communication, so it **crosses servers** fine. But one token still passes every stage in sequence, so PP fits bigger models without making one request faster, and it needs many micro-batches in flight to avoid idle "bubbles".
- **Data / replica parallelism (DP):** **full copies** of the (possibly TP/PP-split) model serving different requests. Throughput scales linearly. This is how the fleet grows, and each replica is the unit you autoscale.

For **mixture-of-experts** models, a fourth axis appears: **expert parallelism**, with different experts on different GPUs and tokens routed to the GPU that holds their expert. Name it if the interviewer mentions MoE.

      R1["Replica 1\nTP=4: GPU0-3"]
      R2["Replica 2\nTP=4: GPU4-7"]
    end
    subgraph S2["Server 2 (8 GPUs, fast link)"]
      R3["Replica 3\nTP=4"]
      R4["Replica 4\nTP=4"]
    end
    LB["router"] --> R1
    LB --> R2
    LB --> R3

</Figure>

| | Splits | Communication | Helps latency? | Use when |
|---|---|---|---|---|
| Tensor | Each layer's matrices | Every layer, every token; needs a fast link | **Yes** | Model does not fit one GPU; within a server |
| Pipeline | Groups of layers | Activations between stages | No (adds hops) | Model does not fit one server |
| Data / replica | Requests | None between replicas | No: adds throughput | Always, to scale the fleet |
| Expert (MoE) | Experts | Token routing to experts | Depends | MoE models |

<Reveal q="TP = 8 instead of TP = 4 for the 70B model: what do you gain and lose?">

Gain: each GPU holds 17.5 GB of weights instead of 35, so per-token latency drops further and the per-replica KV budget grows (640 − 140 − 64 = 436 GB with a 10% reserve, about 1.33 million tokens). Lose: twice as many GPUs per replica means half as many replicas for the same fleet, and all-reduce overhead grows with N, so throughput per GPU usually falls. It is a latency-versus-cost dial: TP = 8 for a premium low-latency tier, TP = 4 or quantised TP = 2 for the cheap tier.

</Reveal>

<h2 id="streaming">Chapter 12 · Streaming</h2>

**What is it, and why?** A full answer can take 30 seconds. So tokens are sent as they are generated. The same nine-second answer feels far faster when the first words appear after half a second, because the user is now measuring TTFT. The transport choice (from the <a href={`${BASE}sd/lessons/networking/#realtime`}>networking lesson</a>: one-way push means SSE, not WebSockets):

| | SSE | WebSockets | Plain chunked HTTP / gRPC streaming |
|---|---|---|---|
| Direction | Server → client | Both ways | Server → client (gRPC: both) |
| Fit for chat | **Default**: one request in, a stream of tokens out | When the client also streams (voice, live interrupts, collaborative agents) | Service-to-service |
| Gotchas | Proxies that buffer responses; per-host connection limits on HTTP/1.1 | You write reconnect and replay | Same buffering concerns |

Public APIs of major model providers document SSE-style streaming: a `text/event-stream` response with an event per chunk of text and a final event carrying usage counts.

```text
POST /v1/conversations/c_81/messages      (Accept: text/event-stream)

event: message_start   data: {"message_id":"m_9","model":"assist-70b"}
event: delta           data: {"text":"Vintage"}
event: delta           data: {"text":" road bike,"}
...
event: message_end     data: {"stop_reason":"end_turn","input_tokens":1012,"output_tokens":287}
```

**What the server must get right:**

- **Disable buffering** at every proxy and load balancer on the path, or tokens arrive in clumps (for nginx, `proxy_buffering off`). Flush per event.
- **Heartbeats** (SSE comment lines every ~15 s) during long pauses (tool calls, queueing) so idle timeouts do not cut the stream.
- **Cancellation is a capacity feature.** When the client disconnects or presses Stop, abort the sequence and **free its KV blocks** immediately. Otherwise the GPU keeps generating to nobody while holding memory a queued request needs.
- **Resume is hard.** Generation is stateful on one replica, so you cannot reattach to a half-written answer elsewhere. Persist the completed (or partial) message. On a dropped connection, show what was saved and let the user regenerate.
- **Streaming and safety.** Output moderation must run on partial text (chunked classification), or the stream must be held back a little: a real latency/safety trade-off (Chapter 17).

<Figure caption="The stream, with a cancellation. The disconnect propagates all the way to the scheduler, which frees the sequence's KV blocks.">
  <Mermaid code={`sequenceDiagram
    participant C as Client
    participant G as Gateway
    participant R as Replica (scheduler)
    C->>G: POST message (SSE)
    G->>R: generate (stream)
    R-->>G: token, token, token
    G-->>C: event: delta ...
    C--xG: user presses Stop (connection closed)
    G->>R: abort(request_id)
    R->>R: free KV blocks, slot to next request`} />
</Figure>

<Reveal q="A load balancer has a 60-second idle timeout and some answers take 90 seconds. Do streams break?">

Not while tokens flow, because every event resets the idle timer. They break during **silent** stretches: a long queue wait, a long prefill, or a tool call in an agent loop. Send SSE comment heartbeats every ~15 s, and set the total-request timeout above your maximum generation time (max_tokens × worst ITL + TTFT budget), not at a web-service default.

</Reveal>

<h2 id="architecture">Chapter 13 · Gateway, router, queue, multi-tenancy</h2>

**What is it?** Imagine the product now runs two models (a 70B for hard questions, an 8B for quick ones), forty fine-tuned customer "styles", a free tier and a paid API. One enterprise customer wants its own fine-tune and a guarantee that its traffic never waits behind free users. Every one of those requirements is a decision about **who gets KV memory next**. The boxes in front of the GPUs make that decision in layers.

<Figure caption="The serving path. Each box makes a different decision: the gateway decides if you may ask, the router decides where, the scheduler decides when.">
  <Mermaid code={`flowchart LR
    C["clients"] --> GW["Edge / LLM gateway\nauth · token budgets\nsafety · tier"]
    GW --> RT["Router\nmodel + adapter\nprefix / session affinity\nleast-loaded"]
    RT --> Q1["queue: 70B\npriority by tier"]
    RT --> Q2["queue: 8B"]
    Q1 --> R1["replica\ncontinuous batch\npaged KV"]
    Q1 --> R2["replica"]
    Q2 --> R3["replica + LoRA adapters"]
    R1 -.->|"metrics: queue depth,\nKV utilisation, TTFT"| AS["autoscaler"]
    AS -.-> R2`} />
</Figure>

- **Gateway** (the <a href={`${BASE}sd/lessons/llm-gateway/`}>LLM gateway lesson</a> covers it in depth): authentication, per-tenant **token budgets**, abuse and safety checks, tier assignment, usage metering. It rejects early and cheaply.
- **Router:** picks the **model pool** (and adapter), then a replica. It prefers the replica that holds the conversation's prefix (Chapter 7) and falls back to least-loaded by **KV utilisation and queue length**, not round-robin. Ordinary <a href={`${BASE}sd/lessons/load-balancing/`}>load balancing</a> by connection count misleads here, because one connection may hold 10 GB of KV.
- **Queue + scheduler** (per replica or per pool): continuous batching, admission by KV blocks, priority ordering.
- **Replicas:** the engine (vLLM, TensorRT-LLM, SGLang, TGI and similar) running TP-split models.

**Multi-model and LoRA serving.** A full fine-tune is a full copy, 140 GB each, so forty of them is forty replicas' worth of weights. **LoRA adapters** are small low-rank deltas on top of a shared base model (often tens to hundreds of MB, depending on rank and layers). A multi-LoRA server keeps **one base model** loaded and many adapters in memory (paging cold ones from CPU or disk), and can **batch requests for different adapters together** in one step (S-LoRA and Punica are the papers). Route by `(base model, adapter)` and keep hot adapters resident.

**Multi-tenancy.** Many customers share the same GPUs. The noisy-neighbour problem is a memory problem: one tenant's long prompts and long outputs can fill the KV pool. The controls, from cheapest to most isolating:

| Control | What it bounds | Cost |
|---|---|---|
| Token-per-minute budget and concurrent-stream cap (Chapter 17) | A tenant's share of compute and KV | Needs accurate metering |
| Priority tiers in the queue | Who waits when the fleet is full | Lower tiers see worse TTFT |
| Per-tenant `max_tokens` and prompt-length caps | Worst-case KV per request | May block legitimate long jobs |
| Tenant-scoped prefix cache | Cross-tenant timing leaks | Fewer shared hits |
| Dedicated replica pool for one tenant | Full isolation, a hard latency promise | Idle capacity you pay for |

**Priority tiers and admission control.**

| Tier | Promise | When the fleet is full |
|---|---|---|
| Enterprise / paid interactive | Tight TTFT SLO; reserved capacity or priority | Admitted first; may preempt lower tiers |
| Free interactive | Best effort | Queue with a cap; downgrade to the small model; then shed with "busy, try again" |
| Batch / offline (evals, bulk rewrites) | Hours, cheap | Fills troughs; paused at peak |

Admission estimates each request's cost, **prompt tokens + expected (capped) output**, against free KV and the tenant's budget. A bounded queue with a maximum wait beats an unbounded one: past a few seconds of queueing, failing fast with a retry hint is kinder than a spinner.

**Timeouts and cancellation.** Every request carries a **deadline** (TTFT budget, max generation time) and a `max_tokens` cap per tier. A request that exceeds its queue deadline is rejected before prefill, so it wastes no GPU. A client disconnect or Stop aborts the sequence and frees KV (Chapter 12). Client retries need jitter and a budget, or an overload becomes a retry storm.

<h2 id="autoscaling">Chapter 14 · Autoscaling and queueing</h2>

**Why is GPU autoscaling slow?** Say a promotion goes viral on a Friday evening. The autoscaler fires at 18:02 and the new replicas report ready at 18:09. For seven minutes the queue grows. A web server boots in seconds. A model replica must first get a GPU node (possibly provisioning one, the slowest and least predictable step), pull the container image, **download the weights** (140 GB at an assumed 2 GB/s from object storage is **70 s** on its own), load them into GPU memory, and warm up (kernel compilation, CUDA-graph capture, a few test requests). End to end, **minutes** is common. Measure yours.

<Figure caption="Cold start of a new replica. Every step before 'ready' is time the queue keeps growing.">
  <Mermaid code={`flowchart LR
    A["autoscaler fires"] --> N["get a GPU node\n(0 to many minutes)"]
    N --> I["pull image"]
    I --> W["download weights\n140 GB at 2 GB/s ≈ 70 s"]
    W --> L["load to GPU\nmemory"]
    L --> U["warm-up"]
    U --> R["ready for traffic"]`} />
</Figure>

**Why queues blow up near full utilisation.** The queue is where users wait, so queueing theory gives a useful rule of thumb. In the simplest model (one server, random arrivals, random service times, called M/M/1), mean waiting time as a multiple of service time is ρ ÷ (1 − ρ), where ρ is utilisation.

```python
for rho in (0.5, 0.8, 0.9, 0.95, 0.99):
    print(rho, round(rho / (1 - rho), 1))   # 1.0, 4.0, 9.0, 19.0, 99.0
```

Going from 80% to 95% busy multiplies the wait by almost 5. A GPU fleet is not exactly M/M/1 (batching and many slots change the numbers), but the shape holds: **running replicas near 100% busy turns small bursts into long TTFT.** That is why you keep headroom (Chapter 15) and why an unbounded queue is dangerous. **Little's law** (in-flight = arrival rate × time in system) gives the other useful identity: at 100 requests/s and 9.5 s per request, about 950 sequences are in flight.

**Levers for the cold-start gap:**

- **Warm pool:** a few loaded replicas ready to take interactive traffic (they can serve batch work until needed).
- **Weights close to the GPU:** pre-staged on local NVMe or a node-local cache, fast checkpoint formats (for example safetensors), parallel loading.
- **Predictive scaling** for known daily peaks, reactive scaling for surprises.
- **Batch traffic as a buffer:** run offline jobs on spare capacity and pause them to free capacity instantly at peak.
- **Degrade, do not drown:** route free-tier overflow to the small model while replicas boot.

**Scale on the right signals:**

| Signal | Use | Why |
|---|---|---|
| Queue depth / queue wait time | **Primary** scale-up trigger | Directly measures requests waiting for capacity |
| KV cache utilisation | Primary, with preemption rate | The real resource; near-full means admission is about to stall |
| TTFT p95 | SLO guard | What users feel; lags slightly |
| GPU compute utilisation | Not for scaling decode | Reads low while memory is full (Chapter 4) |
| CPU utilisation | No | Irrelevant to GPU serving |

Scale **down** slowly (drain in-flight streams, which can last minutes) and scale **up** early, because being late costs a queue the size of the boot time.

<Reveal q="Why not keep enough replicas for the all-time peak?">

GPU-hours are the dominant cost and peaks may be 2 to 3× the average. Idle accelerators bill exactly like busy ones. The usual answer: provision for the predictable daily peak plus a warm buffer, autoscale for the rest, and fill the troughs with batch work so the GPUs you keep are earning (Chapter 16).

</Reveal>

<h2 id="capacity">Chapter 15 · How many GPUs?</h2>

**What is it?** Capacity planning turns the traffic into a replica count. "Peak is 100 requests a second, so a hundred GPUs?" is wrong: requests are the wrong unit. State the assumptions first; every number below is only as good as these.

| | Value |
|---|---|
| Model | Illustrative 70B-class, BF16, KV 327,680 bytes/token |
| Replica | 4 GPUs (TP = 4), 320 GB HBM, 148 GB KV budget |
| Hardware (assumed peak; check specs) | ~1,000 TFLOP/s and ~3 TB/s per GPU |
| Achieved efficiency (assumed) | Prefill at 50% of peak FLOPs gives 2 PFLOP/s per replica; decode at 70% of peak bandwidth gives 8.4 TB/s per replica |
| Peak load | 100 requests/s |
| Per request | 1,000 prompt tokens (600 hit the prefix cache, so 400 to prefill), 300 output tokens |
| SLOs | TTFT p95 under 1 s, ITL about 30 ms or better |

**Step 1 · Demand.** Output: 100 × 300 = **30,000 tokens/s** of decode. Prefill: 100 × 400 = **40,000 uncached prompt tokens/s** × 2 × 70 × 10⁹ FLOPs = **5.6 PFLOP/s**.

**Step 2 · Prefill share of each replica's time.** With N replicas each spends 5.6 ÷ (2 × N) of every second on prefill. At N = 10 that is **28%**.

**Step 3 · Decode step time in the remaining time.** A step reads the weights plus every in-flight sequence's KV. In steady state, Little's law ties the batch to the step time: B = (requests/s per replica) × 300 tokens × step time. With an average context during decode of about 1,150 tokens:

```python
KV = 327_680                      # bytes per token, from the memory example
WEIGHTS = 140e9
BW = 8.4e12                       # assumed: 70% of 12 TB/s per 4-GPU replica
PREFILL_FLOPS = 2e15              # assumed: 50% of peak per replica
req_s, out_tok, prefill_tok = 100, 300, 400          # 400 = 1,000 prompt - 600 cached
avg_ctx = 1150                                       # average context while decoding

def itl(replicas):
    prefill_share = req_s * prefill_tok * 140e9 / (replicas * PREFILL_FLOPS)
    kv_read = (req_s / replicas) * out_tok * avg_ctx * KV   # KV bytes read per second of decode
    step = WEIGHTS / ((1 - prefill_share) * BW - kv_read)
    batch = (req_s / replicas) * out_tok * step
    return prefill_share, step * 1000, batch

for n in (6, 8, 10, 13):
    p, ms, b = itl(n)
    print(n, n * 4, f"{p:.0%}", f"{ms:.1f} ms", round(b), f"{b * 1300 * KV / 1e9:.0f} GB")
```

| Replicas (GPUs) | Prefill share | ITL | Batch per replica | KV in use per replica |
|---|---|---|---|---|
| 6 (24) | 47% | ≈ 54 ms, misses | ≈ 270 | ≈ 115 GB |
| 8 (32) | 35% | ≈ 35 ms, misses | ≈ 130 | ≈ 55 GB |
| 10 (40) | 28% | ≈ 28.5 ms, meets only at 100% busy | ≈ 85 | ≈ 36 GB |
| 13 (52) | 22% | ≈ 24.5 ms, meets with headroom | ≈ 56 | ≈ 24 GB |

(KV in use = batch × 1,300 tokens × 327,680 bytes. At N = 10 the step time is 140 × 10⁹ ÷ (0.72 × 8.4 × 10¹² − 10 × 300 × 1,150 × 327,680) ≈ 28.5 ms.)

**Step 4 · Headroom.** Ten replicas meet ITL only at 100% busy, with no room for bursts, queueing spikes or a failed replica (Chapter 14 shows why). Add about 30%: **13 replicas = 52 GPUs**. Memory is not binding here (24 GB of a 148 GB KV budget). **Bandwidth and prefill time are.** Change the workload to 32K-token RAG prompts and memory binds first, so redo the table.

**Step 5 · Sanity check with Little's law.** In flight ≈ 100 requests/s × (0.5 s TTFT + 300 × 0.03 s) ≈ **950 sequences**, about 73 per replica at 13 replicas, consistent with the batch column.

  <Mermaid code={`flowchart LR
    T["requests/s\n× tokens per request"] --> D["demand:\nprefill FLOP/s\ndecode tokens/s"]
    D --> R["replicas that meet\nTTFT and ITL"]
    R --> H["+ ~30% headroom"]
    H --> K["check KV memory\n(Little's law)"]
    K --> B["benchmark one replica\nto replace assumptions"]`} />
</Figure>

**What prefix caching was worth.** Without it, all 1,000 prompt tokens need prefill: 14 PFLOP/s. At 10 replicas the prefill share becomes 70% and ITL ≈ **100 ms**, far over the SLO. At 13 replicas it is still ≈ 47 ms. You would need about 19 replicas at 100% busy to get under 30 ms, against 10 with the cache. **The cache saved nearly half the fleet.**

Agree, and say how you would replace the assumptions: **benchmark one replica** with a replay of production-shaped traffic (real prompt and output length distributions, real prefix-hit rate), sweep the request rate, and find the highest rate at which p95 TTFT and p95 ITL still meet SLO. That is goodput per replica. Fleet = peak rate ÷ goodput per replica × headroom. The back-of-envelope gives the order of magnitude and which resource binds; the benchmark gives the number for the budget.

</Reveal>

<h2 id="cost">Chapter 16 · Cost per million tokens</h2>

**What is it?** Finance asks "what does one answer cost us?" Requests vary 100× in tokens, so the unit is **cost per million tokens = fleet $/hour ÷ millions of tokens per hour**.

Assumption: **$2.50 per GPU-hour** (illustrative; check current pricing for your provider and commitment).

- Fleet: 52 GPUs × $2.50 = **$130/hour**.
- At peak: 30,000 output tokens/s × 3,600 = **108 million output tokens/hour**, so $130 ÷ 108 ≈ **$1.20 per million output tokens** (prompt processing folded in).
- Averaged over a day at **40% of peak** with the same fleet left running: about **$3.00 per million**. Utilisation is the biggest lever on the bill.

Public price lists typically charge more for output tokens than input tokens, and less again for cached input. That matches the physics: decode is sequential and bandwidth-bound, prefill is parallel, and cached prefill is nearly free.

| Lever | Mechanism | Watch out |
|---|---|---|
| **Right-size the model** | Route easy turns to a small model (8B on 1 GPU vs 70B on 4) | Routing quality; evaluate per task |
| **Utilisation** | Autoscale; fill troughs with batch jobs | Cold starts; batch jobs must be preemptible |
| **Batching + paging** | More sequences per weight read | ITL SLO |
| **Prefix caching** | Skip repeated prefill (nearly half the fleet in Chapter 15) | Prompt-template discipline; routing affinity |
| **Quantisation** | Fewer bytes per weight and per KV entry | Quality evals |
| **Shorter outputs** | Cap `max_tokens` per tier; ask for concise answers | Product quality |
| **Response caching** | Whole answers for exact-repeat prompts (FAQ-style). Semantic caching is riskier | Personalised or sampled answers cannot be reused safely |
| **Speculative decoding** | Fewer target passes at small batch | Little gain at high batch |

<h2 id="edge">Chapter 17 · Guarding the door</h2>

**What is it?** Imagine that overnight one free account sends 4,000 requests, each with a 30,000-token prompt and `max_tokens` set to the maximum. It is inside the requests-per-minute limit. It is not inside anything else, and it fills the KV pool of three replicas. The request limit worked perfectly and limited the wrong thing.

**Rate limit tokens, not requests.** One request can cost 100× another. Limit:

- **Tokens per minute per tenant**: a token bucket (the <a href={`${BASE}sd/lessons/rate-limiter/`}>rate-limiter lesson's</a> bucket, refilled with LLM tokens). Reserve `prompt + max_tokens` at admission and **refund** the unused part when the request ends.
- **Concurrent streams per tenant**: long streams hold GPU memory for minutes, so a concurrency cap bounds one tenant's share of KV.
- **Per-request caps**: maximum prompt length and `max_tokens` by tier.

Same bucket, different currency. Try it with a burst, then think of each "request" as costing many tokens:

<TokenBucketSim capacity={10} refill={5} rate={3} burst={15} mode="bucket" />

**Safety and abuse at the edge** (the <a href={`${BASE}sd/lessons/llm-gateway/`}>LLM gateway lesson</a> owns the details):

- **Input checks** before spending GPU: moderation classifiers, prompt-injection heuristics for tool-using agents, PII redaction where policy requires it.
- **Output checks on a stream:** classify partial output in chunks, and stop the stream and replace the message if it crosses a line. Holding back a small buffer trades a little TTFT for safety.
- **Abuse economics:** free accounts are the attack surface. Use sign-up friction, per-account and per-IP budgets, and anomaly detection on token spend.
- **Audit and privacy:** log metadata and usage per tenant, and store prompt and response content only as policy allows (see <a href={`${BASE}sd/war/pii-and-blind-index/`}>War Room: PII</a> and <a href={`${BASE}sd/war/multi-tenancy/`}>War Room: multi-tenancy</a>).

<Reveal q="Why check budgets at the gateway and not just at the replica scheduler?">

Rejection should be cheap. A request rejected at the gateway costs microseconds of CPU. One admitted to a replica costs a queue slot and, after prefill, gigabytes of KV. The scheduler still enforces memory, but the policy questions (who is this, how much have they spent, is this content allowed) are answered before the GPU sees anything.

</Reveal>

**0:38 · Wrap-up.** "SLOs are TTFT and ITL; replicas run continuous batching, paged KV and prefix caching, about 130 four-GPU replicas for the smart model at peak; admission by KV memory and token budgets; tiered degradation. I would monitor TTFT and ITL p95, queue wait, KV utilisation, preemption rate, goodput and cost per million tokens. At 10× the pressure is cost: quantisation after evals, more small-model routing, and possibly disaggregated prefill and decode. With more time: multi-region failover and retrieval."

Swap overload for **latency per call**. Agents consume whole outputs, so E2E per call matters and compounds across steps. Talk about speculative decoding (code is predictable; prompt-lookup drafts copy from the file), smaller models for routine steps, tight `max_tokens`, prefix caching of the large, stable repository context across steps, and session affinity so each agent's growing context stays on one replica's cache.

<AnswerModes id="llm-serving-overview" q="How would you design the serving layer for a chat LLM?">
  <Fragment slot="short">

Requests run for seconds, output length is unknown, and the bottleneck is GPU memory, not CPU. Each request has a compute-bound prefill (sets time to first token) and a memory-bound decode loop (sets inter-token latency). The KV cache makes concurrency a memory budget. So: continuous batching with paged KV and prefix caching, admission by free KV blocks, SSE streaming with cancellation, token-based rate limits, and autoscaling on queue depth and KV utilisation with a warm pool.

  </Fragment>
  <Fragment slot="medium">

LLM serving breaks web intuitions three ways: requests run for seconds with unknown output length, the bottleneck is GPU memory, and output streams token by token. Each request has a **prefill** (whole prompt in one compute-bound pass, setting time to first token) and a **decode** loop (one token per step, memory-bandwidth-bound, setting inter-token latency). Decode needs the **KV cache**: for a 70B-class model with grouped-query attention, about a third of a megabyte per token, so a 4K conversation holds over a gigabyte for its whole life. **Concurrency is a memory budget.**

Replicas run **continuous batching** with **paged KV memory** and **prefix caching**. Admission is by free KV blocks, and the router prefers the replica holding the conversation's prefix. Tokens stream over **SSE**, and a disconnect cancels generation to free memory. In front, a gateway enforces **tokens-per-minute** budgets and concurrent-stream caps, plus safety checks. I scale on **queue depth and KV utilisation**, keep a warm pool because replicas take minutes to load, and degrade free traffic to a smaller model under overload. **Five follow-ups you will get:**

<Reveal q="1 · Walk me through the GPU memory for one replica.">

Weights = parameters × bytes: 70B in BF16 = 140 GB, so four 80 GB GPUs with tensor parallelism. Reserve about 10% for activations and runtime: 32 GB. KV budget 148 GB. KV per token = 2 × layers × KV heads × head dim × bytes = 2 × 80 × 8 × 128 × 2 ≈ 0.33 MB, so about 451,000 tokens in flight: about 110 conversations at 4K, 13 at 32K. (Model shape and GPU size are illustrative assumptions.)

</Reveal>

<Reveal q="2 · What is continuous batching and why does it matter?">

The scheduler re-forms the batch at every decode step: finished sequences leave immediately and waiting requests join. Static batching moves at the pace of the longest answer. Continuous batching keeps the batch full, which matters because decode is memory-bound and every extra sequence shares the same weight read.

</Reveal>

<Reveal q="3 · How do you autoscale, and what's the catch?">

Scale on queue wait, KV cache utilisation and TTFT, not GPU compute utilisation (which reads low for memory-bound decode) and not CPU. The catch is cold start: getting a node, pulling weights (140 GB is over a minute at 2 GB/s alone), loading and warming takes minutes. So: warm pool, locally staged weights, predictive scaling for daily peaks, and tiered degradation to cover the gap.

</Reveal>

<Reveal q="4 · A tenant is hogging the cluster within their request limit. Fix?">

Request limits are the wrong unit. Limit tokens per minute (reserve prompt + max_tokens at admission, refund the unused part), cap concurrent streams per tenant because each holds KV for its whole life, and cap prompt length and max_tokens by tier. Enforce at the gateway so rejection is cheap.

</Reveal>

<Reveal q="5 · How would you cut latency for a single user, not throughput?">

Tensor parallelism across more GPUs (each reads fewer weight bytes per step), quantised weights, speculative decoding (several tokens per target pass at small batch), a smaller batch or a lightly loaded premium tier, and for TTFT: prefix caching, chunked prefill and shorter prompts. Each costs throughput per GPU, so it is a priced tier, not a default.

</Reveal>

## Common mistakes

1. **Web-service intuition.** Requests per second, CPU autoscaling and round-robin all measure the wrong resource.
2. **Forgetting the KV cache.** Weights fit does not mean users fit. Budget weights + KV + reserve.
3. **Total latency as the SLO.** Say TTFT and ITL.
4. **Static batching.** Say continuous batching with admission by KV memory.
5. **GPU counts without assumptions.** State tokens per request, prompt/output split, SLOs and per-replica throughput, then multiply.
