<h2 id="prologue">Prologue · Where the missing 620 milliseconds went</h2>

Here is a measurement that surprises many backend engineers. An API is deployed in Virginia. The server answers in 50 ms. A user in Delhi opens the app on a fresh session and waits **670 ms** for the first byte.

The server did its job in 50 ms. The other 620 ms went to the network, before and around the actual request. This lesson explains exactly where, and what you can do about each piece.

Most design answers say "the client sends a request" and move on to the boxes. This lesson is about that first arrow and every arrow after it. It is in Module 1 because every design runs on it: the latency budget, the protocol between services, how the server pushes updates, where TLS ends, and what happens when a call times out.

Interviewers probe it in three ways:

1. **Directly.** "What happens when you type a URL and press enter?" The answer shows whether you know the layers or only the names.
2. **Inside a design.** "Why gRPC here?" "How does the driver's location reach the rider?" "Is your load balancer L4 or L7?"
3. **Under failure.** "The call to payments timed out. Did the payment happen?"

**Two common slips this lesson fixes.** *Layer conflation*: saying "the load balancer" when you mean three different boxes, or mixing up what TCP promises with what HTTP promises. And *silent skips*: drawing an arrow without saying what travels over it. Every arrow gets a sentence here.

<h2 id="one-request">Chapter 1 · What one request costs</h2>

Start with a **cold start**: the client has never talked to this server today, so it has no cached address and no open connection. Before the request can be asked, three things must happen.

<Figure caption="One request, cold. The phone finds the server's address, opens a connection, secures it, and only then asks its real question. TLS ends at the load balancer. Everything behind it is inside the data centre.">
  <Mermaid code={`sequenceDiagram
    participant C as Phone
    participant R as DNS resolver
    participant LB as Load balancer
    participant S as App server
    C->>R: where is api.example.com?
    R-->>C: 203.0.113.10 (TTL 60 s)
    C->>LB: TCP SYN
    LB-->>C: SYN-ACK
    C->>LB: ACK + TLS ClientHello
    LB-->>C: ServerHello, certificate, Finished
    C->>LB: Finished + GET /feed
    LB->>S: GET /feed (plain HTTP, pooled connection)
    S-->>LB: 200 OK
    LB-->>C: 200 OK, first byte`} />
</Figure>

| Step | What it buys | Cost on a cold connection |
|---|---|---|
| **DNS lookup** | The server's IP address | Zero if cached on the phone. One short trip to a nearby resolver if cached there. Several trips if nobody has it (Chapter 2) |
| **TCP handshake** | A reliable, ordered byte stream | 1 round trip to the server |
| **TLS 1.3 handshake** | Encryption and proof of the server's identity | 1 more round trip (TLS 1.2 needed 2) |
| **HTTP request and response** | The actual answer | 1 round trip, plus server time, plus more trips for large responses |
| **Inside the data centre** | Load balancer to app to cache to database | About 0.5 ms per hop, plus the work |

**Round-trip time (RTT)** is how long one message takes to go there and back. Physics sets it before any software runs. Light in optical fibre covers about **200 km per millisecond**. Delhi to Virginia is roughly 12,000 km, so even a perfectly straight cable gives `2 × 12,000 / 200 = 120 ms`. Real cables wander and routers queue, so assume **about 200 ms**.

Assumptions for this example: RTT 200 ms, DNS answer cached at a resolver 20 ms away, server time 50 ms.

`20 (DNS) + 200 (TCP) + 200 (TLS 1.3) + 200 (request and response) + 50 (server) = 670 ms`

**Three round trips across the ocean before the first byte, and only one of them carries the question.** Every fix in this lesson attacks one of those round trips: reuse the connection, shorten the handshake, or move the handshake closer to the user.

**A common slip:** "The request goes to the server and the server responds." That sentence skips four steps and three round trips. Say the steps once, briefly (DNS, TCP, TLS, HTTP, where TLS terminates) and the interviewer knows you understand the layers.

<h2 id="dns">Chapter 2 · DNS: who remembers the answer, and for how long</h2>

**DNS turns a name into an IP address.** It is a distributed, hierarchical, heavily cached database. Nobody holds the whole thing. Everyone caches pieces of it.

**Why it matters for design.** DNS is how clients find your servers, and the cache time on a DNS record decides how fast you can move traffic. A common outage story: a primary region fails, the team changes the DNS record to the standby within two minutes, and the outage still lasts another 58 minutes because the record had a one-hour TTL. The record was changed in two minutes. The internet believed the old one for an hour.

When a phone needs `api.example.com`, the lookup walks down until someone has the answer:

<Figure caption="A fully cold lookup. In practice almost every step is answered from a cache: the browser's, the operating system's, or most often the recursive resolver's.">
  <Mermaid code={`sequenceDiagram
    participant P as Phone (stub resolver)
    participant R as Recursive resolver
    participant Root as Root server
    participant TLD as .com TLD server
    participant A as example.com authoritative
    P->>R: api.example.com?
    R->>Root: api.example.com?
    Root-->>R: ask the .com servers
    R->>TLD: api.example.com?
    TLD-->>R: ask example.com's name servers
    R->>A: api.example.com?
    A-->>R: A 203.0.113.10, TTL 60
    R-->>P: 203.0.113.10 (cached for 60 s)`} />
</Figure>

- **Stub resolver**: the small client in the phone's operating system. It asks one recursive resolver and caches the reply.
- **Recursive resolver**: run by the ISP, the company network, or a public service. It does the walk for you and caches every answer, so for popular names the walk almost never happens.
- **Authoritative server**: holds the records for your domain. You control it, and with it the **TTL** (time to live: how long caches may keep an answer).
- DNS queries normally use **UDP port 53**: one small question, one small answer, no handshake. Large responses fall back to TCP. Encrypted DNS (DNS over HTTPS or TLS) exists for privacy.

You can watch this yourself:

```text
$ dig api.example.com +noall +answer
api.example.com.   58   IN   A   203.0.113.10
```

The `58` is the seconds left in the resolver's cache. Run it again and the number drops.

Records to name: **A** (name to IPv4), **AAAA** (name to IPv6), **CNAME** (name to another name, such as a load balancer's hostname), **NS** (who is authoritative for a zone). Failed lookups are cached too ("negative caching"), so a name queried before it existed can stay "not found" for a while.

**The TTL is a design lever.**

| TTL | Good | Bad |
|---|---|---|
| **Low (30–60 s)** | Fast failover and migrations. Changes reach users in about a minute | More cache misses, so more users pay a full lookup. More queries to your authoritative servers |
| **High (hours to a day)** | Lookups almost always cached. Tiny DNS load | A wrong or stale record haunts users for the full TTL |

**Worked numbers** (assumption: 10,000 recursive resolvers serve your users, each refetching once per TTL). At a 60 s TTL that is `10,000 / 60 ≈ 167` queries per second to your DNS. At 24 hours it is `10,000 / 86,400 ≈ 0.12` per second. Either is trivial for a DNS provider. The real cost of a low TTL is **latency for users whose resolver has to look again**, not the DNS bill.

**DNS as a traffic tool:**

- **GeoDNS / latency-based DNS**: return a different IP depending on where the query comes from. The cheapest way to send users to the nearest data centre.
- **Weighted DNS**: send 5% of answers to a new region as a canary.
- **Health-checked failover**: stop returning the IP of a dead region. Only as fast as the TTL lets caches notice.

<Trace title="The TTL decides" steps={dns} takeaway="A DNS change reaches users only as fast as the old TTL expires. Lower TTLs before a planned move, never during the outage." />

<Reveal q="GeoDNS sent a user in Delhi to the Frankfurt servers instead of Mumbai. How can that happen?">

The authoritative server never sees the phone. It sees the **recursive resolver** that asked. If the phone uses a public resolver whose nearest site is in Europe, or a company VPN that exits in Europe, GeoDNS maps the resolver's location, not the user's. The EDNS Client Subnet extension lets a resolver pass along part of the client's address to fix this, but not every resolver sends it. Anycast (Chapter 10) sidesteps the problem by routing on the packet's actual path.

</Reveal>

**A common slip:** "We'll fail over with DNS, it's instant." It is only as fast as the TTL that was cached *before* the failure, and some clients cache longer than the TTL says. Application runtimes keep their own DNS caches (the JVM's `networkaddress.cache.ttl` setting is the classic one to check: Oracle documents the default as "cache forever" when a security manager is installed and implementation-specific otherwise, and OpenJDK uses 30 seconds without one). Serious failover pairs DNS with anycast or load-balancer health checks.

<h2 id="handshakes">Chapter 3 · TCP and TLS handshakes</h2>

**Why saying hello costs more than the conversation.** Each handshake message crosses the gap, and every crossing costs half a round trip. Count the crossings before the server even learns what you wanted.

**TCP's three-way handshake.** The client sends **SYN** ("I want to talk, my starting sequence number is x"). The server replies **SYN-ACK** ("got it, mine is y"). The client sends **ACK**, and is allowed to put data in that same packet. TCP costs **one round trip** before the client can send.

**TLS 1.3's handshake** rides on top. The client's first message (**ClientHello**) already carries its half of a key exchange. The server answers in one flight: **ServerHello** with its half, then, already encrypted, its **certificate** (proof it really is `api.example.com`), a signature over the handshake, and **Finished**. The client checks the certificate, sends its own **Finished**, and sends the HTTP request right behind it. TLS 1.3 costs **one round trip**. The older TLS 1.2 full handshake needed **two**.

**QUIC (the transport under HTTP/3)** runs over UDP and merges both handshakes. Its first packets carry the TLS 1.3 ClientHello, so transport and encryption are agreed in **one round trip**.

<Figure caption="A cold HTTPS connection over TCP with TLS 1.3. The request leaves after two round trips. Its first response byte arrives after the third.">
  <Mermaid code={`sequenceDiagram
    participant C as Phone (Delhi)
    participant S as Server (Virginia)
    Note over C,S: RTT 1 · TCP
    C->>S: SYN
    S-->>C: SYN-ACK
    Note over C,S: RTT 2 · TLS 1.3
    C->>S: ACK + ClientHello (key share)
    S-->>C: ServerHello, certificate, Finished
    Note over C,S: RTT 3 · HTTP
    C->>S: Finished + GET /feed
    S-->>C: 200 OK (first byte)`} />
</Figure>

**Worked example.** Same assumptions as Chapter 1: RTT 200 ms, DNS 20 ms, server time 50 ms.

| Connection | Round trips before the request leaves | Round trips to first byte | Time to first byte |
|---|---|---|---|
| TCP + TLS 1.2 (full handshake) | 3 | 4 | 20 + 4 × 200 + 50 = **870 ms** |
| **TCP + TLS 1.3** | **2** | **3** | 20 + 3 × 200 + 50 = **670 ms** |
| TCP + TLS 1.3 with 0-RTT resumption | 1 (TCP still needs its round trip) | 2 | 20 + 2 × 200 + 50 = **470 ms** |
| **QUIC (HTTP/3), first visit** | **1** | **2** | 20 + 2 × 200 + 50 = **470 ms** |
| QUIC with 0-RTT resumption | 0 | 1 | 20 + 200 + 50 = **270 ms** |
| Reused, already-open connection | 0 | 1 | 200 + 50 = **250 ms** (no DNS needed) |

Read the table from the bottom up and you have the performance strategy: **the cheapest handshake is the one you never do again.** Keep connections alive and reuse them (Chapter 13), use TLS 1.3, offer HTTP/3, and when you cannot avoid a handshake, do it close to the user (Chapter 10).

**0-RTT, and its catch.** A client that connected recently holds a resumption ticket from the server. Next time it can send the request *inside its first flight* ("early data"), with zero waiting. Interviewers who ask about 0-RTT want all three caveats:

1. **It needs a previous visit.** A first-ever connection costs at least 1 RTT (QUIC) or 2 RTT (TCP + TLS 1.3).
2. **Early data can be replayed.** An attacker who records the first flight can resend it, and TLS 1.3 gives early data no inherent replay protection. So servers accept only **safe, idempotent requests** (a `GET` of the feed) in early data. A `POST /payments` waits for the full handshake. HTTP has a status code for this: **425 Too Early**.
3. **The server may refuse it.** The client then resends after the normal handshake, and you are back to the 1-RTT numbers.

<Trace title="Count the round trips" steps={roundTrips} takeaway="TCP + TLS 1.3: two round trips before the request, three to the first byte. QUIC: one before. 0-RTT: none, for idempotent requests on a return visit only." />

<Reveal q="The handshakes are done. Why does a 100 KB response on a brand-new connection still take longer than the same response on a warm one?">

**TCP slow start.** A new connection does not know how much the network can carry, so it begins with a small congestion window (commonly 10 segments, about 14 KB) and roughly doubles it each round trip while nothing is lost. In the ideal case a 100 KB response goes out in three flights (about 14 KB, then 29 KB, then 58 KB), so the last byte lands about **two round trips after the first**. A warm connection has already grown its window and sends it in one go. Another reason to reuse connections.

</Reveal>

**A common slip:** "HTTPS is slow because encryption is expensive." The CPU cost of modern encryption is small. The cost users feel is **round trips**, and TLS 1.3 cut its share to one.

<h2 id="tcp-udp">Chapter 4 · TCP vs UDP</h2>

Say a team adds video calls to a product. In testing, one engineer joins from a train. His video freezes for a full second, then fast-forwards, and his voice comes out chipmunk-quick as it catches up. That freeze is what happens when you send live video over a transport built for perfect delivery.

**TCP is registered mail.** It promises a **reliable, ordered byte stream**: every byte arrives, exactly once, in the order sent. To keep the promise it numbers every byte, waits for acknowledgements, and **retransmits** anything missing. It also runs **flow control** (do not overrun the receiver) and **congestion control** (slow start, and backing off when packets drop, so one connection does not flood the internet).

**UDP is shouting across a room.** It sends independent **datagrams** with port numbers and a checksum, and nothing else: no handshake, no acknowledgements, no retransmission, no ordering. A datagram may arrive late, twice, out of order, or not at all. Anything more, the application builds itself.

| | **TCP** | **UDP** |
|---|---|---|
| Guarantees | Delivery, ordering, no duplicates, congestion control | None: fire and forget |
| Connection | Handshake first (1 RTT) | None |
| Unit | A byte stream with no message boundaries, so apps add framing (length prefixes) | Datagrams, each one a message |
| Cost | Handshake, retransmission waits, **head-of-line blocking** | Nearly free. The app owns loss and congestion |
| Use | Almost everything: HTTP/1.1 and HTTP/2, databases, most RPC | Live audio and video, game state, DNS, and QUIC, where a late packet is worse than a lost one |

**Head-of-line blocking** is the cost of the ordering promise. If packet 42 is lost, packets 43, 44 and 45 may already have arrived, but TCP **cannot hand them to the application** until 42 is retransmitted, which takes at least one more round trip.

<Figure caption="Packet 42 is lost. TCP holds 43 to 45 back until 42 is resent: the frozen video. UDP hands 43 to 45 over at once and the app hides the gap.">

  <ArrayStrip name="UDP" values={['41', '42', '43', '44', '45']} indices={false} pointers={[{ at: 1, label: 'LOST', tone: 'red' }]} tones={{ 0: 'done', 1: 'out', 2: 'done', 3: 'done', 4: 'done' }} regions={[{ from: 2, to: 4, label: 'played on time', tone: 'green' }]} />

**When UDP wins:**

- **Late data is worthless.** A video frame from two seconds ago is garbage, and audio must play on schedule. Drop it and conceal the gap.
- **The newest message replaces the old one.** A game sends a player's position 30 times a second. A lost update is superseded by the next.
- **One tiny question, one tiny answer.** DNS: a handshake would cost more than the query.
- **You want different reliability rules.** QUIC builds its own per-stream reliability on UDP to escape TCP's head-of-line blocking.

The line to remember: **"Video calls use UDP because a two-second-old frame is garbage. Better to drop it than block newer frames behind it."** Browser real-time media (WebRTC) runs over UDP for this reason, falling back to TCP-based relays only when a network blocks UDP.

<Trace title="What does TCP do with the packets behind a lost one?" steps={transport.slice(0, 1)} takeaway="TCP orders bytes, so one loss blocks everything behind it." />

<Reveal q="If UDP has no congestion control, what stops a video app from flooding the network?">

The app must do it. Real-time media stacks measure loss and delay and **adapt the bitrate**, sending lower-quality video when the path is congested. QUIC implements congestion control itself, just as TCP does. "UDP is faster" is only true because you have taken on TCP's jobs yourself. A UDP sender that ignores congestion hurts everyone sharing the link, including itself.

</Reveal>

**A common slip:** "UDP is faster, so use it for performance." For ordinary request/response traffic you would rebuild acknowledgements, retransmission, ordering and congestion control, badly. Use UDP when **late is as bad as lost**, or use a protocol (QUIC) that already did the rebuilding.

<h2 id="http-versions">Chapter 5 · HTTP/1.1, HTTP/2 and HTTP/3</h2>

Take a marketplace listing page that loads 80 small files: thumbnails, icons, scripts. On office Wi-Fi it is instant. On a phone on a train it crawls, even though the servers speak HTTP/2. HTTP/2 multiplexes, so it should be fine on one connection. But one connection is exactly the problem, as we will see.

Each HTTP version fixed the biggest bottleneck of the one before and left the next one exposed.

**HTTP/1.1.** Connections are **persistent by default** (keep-alive), so many requests reuse one TCP + TLS handshake. Without it (HTTP/1.0) every request paid the full handshake. But each connection carries **one request at a time**: the next request waits for the previous response. (Pipelining, sending several requests without waiting, is in the spec, but responses must return in order and broken proxies mishandled it, so browsers never enabled it.) Browsers cope by opening **about six parallel connections per host**, and sites coped with hacks: domain sharding, sprite sheets, concatenated files.

**Keep-alive has a time limit.** Either side may close an idle connection, and servers and load balancers do, commonly after a few tens of seconds to minutes (an AWS Application Load Balancer's idle timeout is 60 seconds by default; check your own server and balancer settings). A client that reuses a connection the server just closed gets a reset on its next request. Chapter 13 covers how to handle that.

**HTTP/2.** One connection, many **streams**. Requests and responses are cut into binary **frames**, interleaved on the wire, and reassembled per stream, so 80 requests go out at once without waiting for each other. Headers are compressed (HPACK), which matters when every request repeats the same cookies. Its server-push feature never caught on and browsers have largely dropped it. HTTP/2 made domain sharding and sprite hacks unnecessary. **What it could not fix:** all those streams share **one TCP byte stream**, so one lost packet stalls *every* stream until it is retransmitted. On a lossy network, one HTTP/2 connection can do worse than six HTTP/1.1 connections.

**HTTP/3.** The same HTTP semantics over **QUIC**, which runs on UDP and does its own reliability **per stream**. A lost packet delays only the stream it belonged to. QUIC also brings TLS 1.3 inside the transport (1-RTT setup, 0-RTT on resumption) and identifies connections by a **connection ID** instead of the IP-and-port pair, so a phone moving from Wi-Fi to cellular keeps its connection instead of starting a new handshake. HTTP/3 compresses headers with QPACK, a cousin of HPACK designed for streams that may arrive out of order.

| Version | Fixed | Left broken |
|---|---|---|
| **HTTP/1.0** | Nothing | New TCP connection per request by default |
| **HTTP/1.1** | Persistent connections (keep-alive) | One request at a time per connection. Browsers open about 6 connections per host |
| **HTTP/2** | Multiplexed streams on one connection. Header compression | **TCP-level** head-of-line blocking: one lost packet stalls every stream |
| **HTTP/3 (QUIC)** | Independent streams. 1-RTT handshake (0-RTT resume). Connection migration | Needs UDP to get through. More CPU per byte on many servers today. The first visit usually still starts on HTTP/2 |

**Worked numbers** (assumption: 80 small files, 50 ms RTT, bandwidth is not the bottleneck). HTTP/1.1 with 6 connections: `⌈80 / 6⌉ = 14` request rounds in sequence, about `14 × 50 = 700 ms`. HTTP/2 on one connection: all 80 requests leave together, so about one round trip plus transfer time, until a packet is lost, when every stream waits.

**How a browser finds HTTP/3.** It usually connects over TCP first (HTTP/2), and the server advertises HTTP/3 in an `Alt-Svc` response header (or a DNS HTTPS record). Later connections try QUIC. If a network blocks UDP, the browser falls back to TCP. "We support HTTP/3" never means "we stopped supporting HTTP/2".

**One design fact:** HTTP/2 multiplexing is why **gRPC**, built on it, carries many concurrent internal calls over a handful of connections. Inside a data centre packet loss is low, so HTTP/2 between services is fine. HTTP/3's gains matter most at the **edge, on mobile**.

<h2 id="api-styles">Chapter 6 · REST, gRPC and GraphQL</h2>

Three API styles sit on top of HTTP, and each solves a different problem. A typical architecture discussion has three camps: the mobile team wants GraphQL, the platform team wants gRPC everywhere, and the partner team needs a public API that "any developer with curl" can use. Do not pick yet. Ask three questions: who is calling, what shape of data do they need, and what has to cache it?

**REST + JSON.** Resources at URLs (`/listings/42`), verbs with meaning (`GET` reads, `POST` creates, `PUT` replaces, `DELETE` removes), and status codes everyone understands. Its strength is that it **is the web**: a `GET` response can be cached by browsers, CDNs and proxies with standard headers (`Cache-Control`, `ETag`), any language can call it, and you can debug it with curl. Its weaknesses: the server decides the response shape, so clients **over-fetch** (a 40-field listing when the card shows 4) or **under-fetch** (one request for the feed, then one per author). A schema is optional (OpenAPI), not enforced.

**gRPC.** You write the contract in a `.proto` file, and tools generate typed client and server code in every language. Messages are **Protocol Buffers**: compact binary, typically smaller and faster to parse than the same data as JSON. It runs on **HTTP/2**, so many calls share one connection, and it supports four call shapes: unary (one request, one response), **server streaming**, **client streaming** and **bidirectional streaming**. Deadlines travel with each call, so a downstream service knows how long the caller will wait. Weaknesses: **browsers cannot call it natively** (their APIs do not expose HTTP/2 framing and trailers, and gRPC-Web through a proxy covers unary and server streaming only), payloads are not human-readable, and long-lived HTTP/2 connections need **request-aware load balancing** (Chapter 9).

**GraphQL.** One endpoint and a typed **schema** of everything the API can return. The client sends a query naming **exactly the fields it wants**, across related objects, and gets that shape back in one response. It fixes over- and under-fetching for clients with many different screens. The costs move to the server. Each field is resolved by a function, so a naive implementation fires **N+1 queries** (one for the posts, then one per author), fixed by **batching** resolvers (the DataLoader pattern). Queries arrive as `POST`s to one URL, so ordinary **HTTP caching stops working** unless you use persisted queries over `GET`. A client can ask for an enormous nested query, so you need **depth and cost limits**. Real-time updates come through **subscriptions**, usually over WebSockets.

The same read, three ways:

```http
GET /listings/42 HTTP/1.1
Host: api.example.com
```

```text
rpc GetListing (GetListingRequest) returns (Listing);   // .proto: typed, generated clients
```

```json
{ "query": "{ listing(id: 42) { title price seller { name } } }" }
```

| | **REST + JSON** | **gRPC** | **GraphQL** |
|---|---|---|---|
| Contract | Optional (OpenAPI) | Required `.proto`, code-generated | Required schema, typed |
| Payload | JSON text | Protobuf binary | JSON text |
| Transport | Any HTTP version | HTTP/2 | Usually HTTP `POST` (subscriptions over WebSockets) |
| Streaming | Not built in (use SSE, chunked responses) | Server, client and bidirectional | Subscriptions |
| Browser support | Native | Needs gRPC-Web + proxy | Native |
| Fetch shape | Fixed per endpoint: over- and under-fetching | Fixed per method | Client chooses fields |
| HTTP/CDN caching | Easy for `GET` | Not with standard HTTP caches | Hard (one `POST` URL). Persisted `GET` queries help |
| Best for | Public APIs, CRUD, the interview default | Internal service-to-service, streaming between services | Many client screens with nested, varied reads |

**Worked numbers.** A home screen needs the user, the 20 latest posts in their feed, and each post's author. With REST that is `1 + 1 + 20 = 22` requests. HTTP/2 can run them in parallel, but the authors cannot be requested until the feed arrives, so at least **2 dependent round trips**, `2 × 200 = 400 ms` from Delhi. With GraphQL (or a purpose-built REST endpoint like `/home`, a "backend for frontend") it is **1 round trip**, 200 ms. The round-trip saving is real, but you do not need GraphQL for one screen. GraphQL earns its cost when there are *many* screens with *changing* needs.

**A sensible default:** REST for the public API, gRPC inside when microservices come up. Reach for GraphQL only when the problem is literally "many clients need flexible nested reads".

<Reveal q="The interviewer says, “GraphQL solves N+1.” Do you agree?">

Only from the client's side. The client makes one request instead of N+1, but a naive server then runs one database query per author, which is N+1 moved from the network to the database. The fix is **batching**: collect every author id requested in one tick and load them with a single `WHERE id IN (…)` query (the DataLoader pattern), plus caching per request.

</Reveal>

**A common slip:** "gRPC, because it's faster." Faster is true and incomplete. Say the two catches in the same breath: browsers need a REST or gRPC-Web edge, and the load balancer must balance requests, not connections.

<h2 id="realtime">Chapter 7 · When the server speaks first</h2>

Say a marketplace wants a seller to see a buyer's offer instantly, not on refresh. The reflex is "WebSockets". Before using it, ask three questions: how often do updates arrive, does the client ever need to talk back in real time, and how many clients are watching at once?

HTTP is **the client asks, the server answers**. When the server has news first, there are four ways to deliver it.

**Short polling.** The client asks every N seconds: "anything new?" Simple, stateless, works through every proxy. Latency up to N seconds, and most responses are empty.

**Long polling.** The client asks, and the server **holds the request open** until there is news (or a timeout, say 30 s). Then it responds and the client asks again at once. Near-instant delivery over plain HTTP, but every message costs a full response plus a new request, and the client must send a cursor ("everything after message 1,042") so nothing falls into the gap between requests.

**Server-Sent Events (SSE).** One long-lived HTTP response with `Content-Type: text/event-stream`. The server writes events into it as they happen. **Server-to-client only**, UTF-8 text only. The browser's `EventSource` API **reconnects automatically** and sends a `Last-Event-ID` header so the server can resume. Over HTTP/1.1, each SSE stream holds one of the browser's roughly 6 connections per host (shared across tabs). HTTP/2 lifts that limit by multiplexing.

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 1043
event: offer
data: {"listing": 42, "amount": 9500}

```

**WebSockets.** Starts as an HTTP/1.1 request with `Upgrade: websocket`. The server answers **101 Switching Protocols**, and the same TCP connection becomes a **full-duplex** channel of text or binary frames in both directions. Lowest overhead per message. No built-in reconnect or replay, so you write those. Works through most networks when run over TLS on port 443 (`wss://`).

    Note right of S: nothing for 30 s
    S-->>C: 204 No Content (timeout)
    C->>S: GET /offers?after=1043`} />

| | Latency | Direction | Server cost | Pick when |
|---|---|---|---|---|
| **Short polling** | Up to N s | Client asks | One request per client per N s, mostly empty. Stateless | Updates are rare or delay is fine: order status, a dashboard refreshing every 30 s |
| **Long polling** | Near-instant | Client asks, server holds | One held request per client + one request per message | Push is needed but SSE/WebSockets are blocked or unavailable |
| **SSE** | Instant | Server to client | One open connection per client | One-way push: notifications, live scores, LLM token streams |
| **WebSockets** | Instant | Both ways | One open connection per client + connection state | Two-way and frequent: chat with typing indicators, games, collaborative editing |

**Worked numbers** (assumption: 1 million sellers watching for offers).

- Short polling every 5 s: `1,000,000 / 5 = 200,000` requests per second, almost all empty.
- Long polling with a 30 s hold: `1,000,000 / 30 ≈ 33,000` requests per second when idle, plus one per delivered offer.
- SSE or WebSockets: 1 million open connections and near-zero requests when idle. Heartbeats every 30 s add about 33,000 tiny frames per second. If each connection costs roughly 10 KB of server memory (estimate it for your stack), that is about **10 GB** across the connection fleet.

**The decision rule: "Poll if you can, SSE if the server only pushes, WebSocket only when the client also sends in real time."** Long polling is the fallback when the persistent options are blocked.

Persistent connections make servers **stateful**: it now matters which server holds a user's connection. The routing problem (a connection registry or pub/sub), heartbeats, reconnect with jitter, and catch-up from storage are the deep dive of the <a href={`${BASE}sd/lessons/pattern-realtime/`}>Realtime pattern</a>. This chapter's job is choosing the transport.

<Trace title="Pick the transport" steps={realtime} takeaway="Rare updates: poll. Server-only push: SSE. Two-way, frequent: WebSockets, and accept the stateful-server problem that comes with them." />

<Reveal q="Long polling and SSE both hold a request open. What is the actual difference?">

**How many events one response carries.** A long-poll response carries one event (or one batch) and then ends. The client must send a new request, paying headers and a round trip each time. An SSE response never ends: it carries event after event on the same response. Both are plain HTTP and both need a resume cursor, but SSE has no per-message request cost.

</Reveal>

**A common slip:** "Real-time, so WebSockets." Jumping to the most complex transport for a status page that changes four times an hour is box inflation. Ask the three questions out loud, and let the answer pick.

<h2 id="proxies">Chapter 8 · Forward and reverse proxies</h2>

Here is a bug that appears the first day a rate limiter goes live behind a load balancer. It blocks half of a city. The logs show every request coming from the same three IP addresses. Those are the company's own load balancers: every box between the phone and the database is a proxy, and the question is whose side it is on.

A **proxy** sits in the middle of a connection and speaks for someone.

- A **forward proxy** speaks **for clients**. The client is configured to send through it, such as a company's outbound proxy that filters and logs browsing. The **server sees the proxy's address**, not the client's.
- A **reverse proxy** speaks **for servers**. Clients think it *is* the server. It hides how many servers there are and where they live. **Load balancers, API gateways and CDN edges are all reverse proxies.**

<Figure caption="Same mechanism, opposite loyalties. A forward proxy hides the clients from the internet. A reverse proxy hides the servers.">
  <Mermaid code={`flowchart LR
    subgraph Office["Client side"]
      U1["Laptop"] --> FP["Forward proxy"]
      U2["Laptop"] --> FP
    end
    FP --> NET(("Internet"))
    NET --> RP["Reverse proxy\n(LB / gateway / CDN)"]
    subgraph DC["Server side"]
      RP --> A1["App 1"]
      RP --> A2["App 2"]
    end`} />
</Figure>

| | Forward proxy | Reverse proxy |
|---|---|---|
| Acts for | Clients | Servers |
| Who knows it exists | The client (configured to use it) | Nobody outside: it looks like the server |
| Typical jobs | Egress filtering, logging, caching for an office | TLS termination, load balancing, caching, compression, buffering slow clients, hiding topology, absorbing attacks |
| In a system design | Rarely drawn | On almost every diagram |

**What a reverse proxy does for you:**

- **Terminates TLS.** The load balancer decrypts, so app servers see plain HTTP. That is simpler, and it lets the proxy read the URL to route (L7, next chapter). Certificates live in one place.
- **Buffers slow clients.** A phone on a weak signal may take seconds to upload a request. The proxy absorbs it and hands your app server the complete request in one go, so app threads are not tied up waiting on someone's 3G.
- **Caches, compresses, shields.** Static responses, gzip/brotli, request size limits, and one choke point for blocking abusive traffic.

**The client's real address.** Behind a proxy, every connection to your app comes from the proxy. An L7 proxy passes the original address in a header: `X-Forwarded-For`, or the standard `Forwarded` header. An L4 proxy cannot add HTTP headers, so it uses the **PROXY protocol** (a small preamble on the TCP connection) if both sides support it. Trust these values **only when your own proxy set them**, because a client can send a fake `X-Forwarded-For` of its own.

```http
GET /feed HTTP/1.1
Host: api.example.com
X-Forwarded-For: 198.51.100.7, 10.0.3.12
```

Read the list from the right: the last address was added by the proxy nearest you. Count back only as many hops as you own.

<Reveal q="TLS terminates at the load balancer. Is traffic behind it unencrypted, and is that acceptable?">

Often yes: inside a private network, many systems run plain HTTP behind the load balancer. Whether that is acceptable depends on the threat model and the rules you operate under. Payment and health data regimes, and "zero trust" designs, typically **re-encrypt**: the load balancer opens a new TLS connection to the backend, or services use **mutual TLS** (both sides present certificates), often handled by a service mesh. Say which you chose and why. For a fintech-style system, "TLS to the edge, then mTLS between services" is a safe default.

</Reveal>

**A common slip:** rate limiting, geo-blocking or audit logging "by client IP" in a system full of proxies. Name the header you read, and say that only your edge may set it.

<h2 id="l4-l7">Chapter 9 · L4 vs L7 load balancers, gateways, stateless servers</h2>

A real incident pattern: one of ten pods runs at 90% CPU, the other nine are idle, health checks are green, and the load balancer shows even connection counts. The explanation uses envelopes. The load balancer only reads the envelope. Each client sent one envelope, and inside it were ten thousand letters.

The **L4 / L7** names come from the OSI model's transport layer (4) and application layer (7). The difference is **what the balancer can see, and so what it can decide**.

- An **L4 load balancer** sees IP addresses and ports, the envelope. It picks a backend **when a connection opens** and forwards that connection's packets there for its whole life. It does not read HTTP, so with TLS it usually passes the encrypted bytes straight through. Very fast, protocol-agnostic (anything over TCP or UDP), cheap per connection.
- An **L7 load balancer** terminates the client's connection (and TLS), **parses each HTTP request**, and opens its own connections to the backends. It can route by path, host, header or cookie, balance **per request**, retry a failed request on another backend, add headers, and rate-limit. It costs more CPU per request: it is a full proxy with two connections for every one.

| | **L4 (transport)** | **L7 (application)** |
|---|---|---|
| Sees | IPs, ports, TCP/UDP | Full HTTP: method, path, headers, cookies |
| Balances | Connections | Requests |
| TLS | Usually passed through | Terminated (can re-encrypt to backends) |
| Can do | Spread connections, very fast, any protocol | Route `/video/*` vs `/api/*`, retries, auth, rate limits, header rewrites |
| Typical examples | AWS NLB, IPVS, many hardware balancers | AWS ALB, nginx, Envoy, HAProxy in HTTP mode |

**The gRPC trap.** A gRPC client opens **one HTTP/2 connection** and sends all its calls down it as streams. An L4 balancer sees one connection and pins it to one backend, so one busy client puts all its load on one pod, no matter how many pods exist. Fix: an **L7 balancer that understands HTTP/2** and spreads individual calls (Envoy is the usual example), or **client-side load balancing** where the gRPC client holds connections to many backends.

**A common real shape** is both: an L4 layer at the front holding one stable address and spreading raw connections across a fleet of L7 proxies, which do TLS and routing.

    L4 --> P2["L7 proxy / gateway\nTLS, auth, routing"]
    P1 -->|"/api/*"| API["API service"]
    P1 -->|"/video/*"| MED["Media service"]
    P2 -->|"/api/*"| API

**API gateway.** An L7 reverse proxy that also owns the **cross-cutting API concerns**: authenticate the token once at the edge, enforce rate limits and quotas, route to the right microservice, circuit-break failing downstreams, transform requests, and log and trace everything. For a monolith or single service, "load balancer" is enough. For microservices with a public API, draw a gateway and **say two of its jobs out loud**. Balancing algorithms (round robin, least connections, consistent hashing), health checks and the gateway in depth live in <a href={`${BASE}sd/lessons/load-balancing/`}>Load balancers & API gateways</a>.

**The stateless rule**, which every design depends on. Everything behind the balancer should be **stateless**: any server can handle any request, and session identity comes from a signed token (a JWT) or a shared session store, not server memory. Stateless servers mean horizontal scaling, rolling deploys and instant failover. If a server holds state (WebSocket connections, an upload in progress), say how requests find the right server. That is a deep dive, not an accident.

<Trace title="Which box, and why" steps={balancing} takeaway="L4 balances connections. L7 balances requests. Long-lived multiplexed connections (gRPC, HTTP/2) need L7 or client-side balancing. Stateless servers make all of it work." />

<Reveal q="A million phones hold WebSocket connections. L4 or L7 in front?">

Either can work. The reasoning is what counts. Each connection is one long "request" lasting hours, so per-request smarts are used once, at connect time. The job is spreading and **pinning** long-lived connections cheaply, which L4 does well. An L7 balancer also works if it supports the upgrade and long idle timeouts, and it can route the initial handshake by path or hash on user id. What breaks things is re-balancing mid-connection, or an idle timeout shorter than your heartbeat interval.

</Reveal>

**A common slip:** "Isn't the load balancer a single point of failure?" Have the sentence ready: balancers run as redundant pairs or fleets behind a floating virtual IP, several addresses can be published in DNS, and at global scale **anycast** (next chapter) announces one address from many places.

<h2 id="edge">Chapter 10 · CDNs, GeoDNS and anycast: moving the handshake</h2>

Back to the 670 ms problem. "Can't we just build a data centre in India?" Eventually, but that is a year of work and a database migration. We cannot move Virginia closer. Can we move the handshake?

A **CDN** is a network of reverse proxies, **points of presence (PoPs)**, in hundreds of cities. It does two jobs, and interviews usually only mention the first:

1. **Cache responses near users.** Images, video segments, scripts, public pages. A hit never leaves the city. (Keys, TTLs and invalidation are the caching lesson's subject. Immutable, fingerprinted URLs are the usual trick.)
2. **Terminate connections near users, even for responses it cannot cache.** The phone's TCP and TLS handshakes go to a PoP 10 ms away. The PoP keeps **warm, pooled connections** to the origin, so only the request itself crosses the ocean.

**Worked numbers.** Delhi phone, cold, uncacheable `GET /feed`. Assumptions: RTT 20 ms to a PoP in Delhi, 200 ms from the PoP to Virginia over an already-open connection, DNS 20 ms, server 50 ms.

| Path | Arithmetic | First byte |
|---|---|---|
| Direct to Virginia (Chapter 3) | 20 + 200 (TCP) + 200 (TLS) + 200 (request) + 50 | **670 ms** |
| Via the Delhi PoP | 20 + 20 (TCP) + 20 (TLS) + 20 (request to PoP) + 200 (PoP to origin and back, warm) + 50 | **330 ms** |

Same server, same code, same ocean, **half the wait**, because two of the three ocean round trips became trips across town.

**How does the phone reach the nearest PoP?** Two techniques:

- **GeoDNS** (Chapter 2): the CDN's DNS returns a different PoP's IP depending on the resolver's location.
- **Anycast**: **the same IP address is announced from every PoP** using BGP, the internet's routing protocol. Routers forward packets along the best route they know, so a packet to that address lands at the PoP that is **closest in routing terms**, usually though not always the closest geographically. If a PoP goes down, it stops announcing the address and traffic flows to the next-nearest one as routing updates, with no client TTLs involved. Attack traffic is spread across every PoP. The DNS root servers use anycast for these reasons.

| | GeoDNS | Anycast |
|---|---|---|
| How | Different answers per resolver location | One IP announced from many places |
| Failover speed | Bounded by DNS TTLs and caches | As fast as routing updates. No client caches |
| Accuracy | Location of the resolver, not the user | Location in the routing graph |
| Watch out | Users on far-away public resolvers or VPNs | A route change mid-connection can send packets to a PoP that has no state for that connection |

<Reveal q="Anycast sends packets to the nearest site. What happens to a TCP connection if the routing changes halfway through?">

The new packets arrive at a different PoP that has never seen the connection, and it resets them. Routes rarely change within the lifetime of a typical connection, so CDNs accept the rare reset, and clients reconnect. That is why anycast was first a natural fit for single-packet UDP exchanges like DNS, and why operators running TCP over anycast watch route stability closely.

</Reveal>

**A common slip:** "Put the API behind the CDN so it gets cached." Per-user, authenticated responses mostly cannot be cached at a shared edge. Say what the CDN does for them anyway: **terminates TLS near the user and reuses warm connections to the origin**. Media and static assets are the cacheable part, covered in <a href={`${BASE}sd/lessons/blob-cdn/`}>Blob storage & CDNs</a>.

<h2 id="nat">Chapter 11 · NAT and firewalls: doors that only open outward</h2>

A natural question: "When an offer arrives, why can't our server just connect to the seller's phone and tell it?" Because the server does not know where the phone is. Its address is shared with thousands of other phones, and its front door only opens from the inside. This section gives just enough NAT and firewall knowledge to explain four design decisions.

**NAT (network address translation).** Most devices do not have their own public IP address. A home router, or a mobile carrier's **carrier-grade NAT** shared by thousands of phones, rewrites outgoing packets so they come from one public address, and remembers the mapping (`private address:port ↔ public address:port`) so replies can find their way back. **Unsolicited inbound packets have no mapping and are dropped.**

What that means for designs:

1. **Servers cannot call phones.** All push is built on connections **the client opened**: long polling, SSE, WebSockets, or the platform push services (APNs on iOS, FCM on Android), which keep one such connection per device on your behalf.
2. **Idle mappings expire.** NAT devices, firewalls and load balancers forget connections that have been silent for a while: sometimes tens of seconds, sometimes minutes, often configurable on your own load balancers. That is why long-lived connections send **heartbeats** at an interval shorter than the shortest idle timeout on the path.
3. **Many users share one address.** Rate limiting purely by IP throttles an entire mobile carrier's users together. Limit by account or API key, and by IP only as a coarse backstop.
4. **Peer-to-peer is hard.** Two phones behind NAT cannot simply connect. Video calls use **STUN** to discover public addresses and attempt a direct path, and **TURN** relays when that fails. One sentence in an interview is enough.

**Firewalls and private subnets.** In a cloud design, only the load balancer is reachable from the internet, usually on **443 only** (plus 80 to redirect to HTTPS). App servers and databases live in **private subnets** with no public address. Security groups allow just the traffic each tier needs (load balancer to app on its port, app to database on its port). Servers reach out to the internet, to call a payment provider for example, through a **NAT gateway**. Corporate networks often allow little besides 443, and some block UDP entirely, which is why WebSockets run over `wss://` on 443 and why HTTP/3 always keeps a TCP fallback.

**A common slip:** "The server sends the notification to the phone's IP." There is no reachable phone IP. Push rides on a connection the phone opened and keeps alive.

<h2 id="timeouts-retries">Chapter 12 · Timeouts, retries and idempotency</h2>

A real support ticket pattern: a buyer was charged twice for one listing. The phone sent the payment. The payment service charged the card and committed. Then the response got lost in a tunnel. The phone waited ten seconds, decided it had failed, and tried again. Both requests did exactly what they were told. That is the problem.

**A timeout is not a failure. It is "I don't know."** Every network call has **three outcomes**: success, failure, and **unknown**. When a call times out, the request might never have arrived, might have been processed with the response lost, or might still be running. The client cannot tell which.

**Timeouts: every call needs a number.** An unset timeout is a timeout of infinity: one slow dependency then holds threads and connections until the caller falls over too.

- **Connect timeout**: short. Inside a data centre a healthy connect takes about a millisecond, so a second or so is generous.
- **Read (request) timeout**: set from the latency you observe (somewhat above the dependency's p99), not a round number pulled from the air.
- **End-to-end deadline**: the user will wait, say, 2 s in total. Pass the *remaining* budget downstream (gRPC carries deadlines with each call), so a service does not keep working on a request its caller has abandoned.

```python
import requests

resp = requests.post(
    "https://payments.internal/charges",
    json={"listing": 42, "amount": 9500},
    headers={"Idempotency-Key": key},   # generated once per logical payment
    timeout=(1.0, 3.0),                 # (connect, read) seconds. Never omit it
)
```

In Python's `requests`, omitting `timeout` means waiting forever.

**Retries: only when the next attempt can differ.**

- Retry **transient** failures: connection refused or reset, `503 Service Unavailable`, `429 Too Many Requests` (honour its `Retry-After`), and timeouts, **only if the operation is idempotent** (below). Never retry a `400`: the same bad request gets the same answer.
- **Exponential backoff with jitter**: wait about 100 ms, then 200, 400, and so on, with randomness, so a thousand clients that failed together do not retry together. "Full jitter" picks a random delay between zero and the backoff cap.
- **A retry budget**: cap retries at a small fraction of traffic (for example 10%), so a struggling service gets a little extra load, not triple. (10% is a common starting point, not a rule.)
- **Retry at one layer.** Retries multiply down a call chain:

<Figure caption="Three retrying layers, three attempts each. One tap becomes 27 calls to the service that is already down.">
  <Mermaid code={`flowchart LR
    A["App\n1 tap"] -->|"3 attempts"| G["Gateway\nreceives 3"]
    G -->|"3 each"| O["Orders\nreceives 9"]
    O -->|"3 each"| I["Inventory (down)\nreceives 27"]`} />

Multiply that by every user tapping at once, and a brief inventory hiccup becomes a **retry storm** that keeps it down. Retry at the edge (or one chosen layer), fail fast elsewhere, and put a **circuit breaker** in front of a failing dependency, so callers stop hammering it and probe for recovery instead (covered in the load-balancing lesson).

**Idempotency: making "try again" safe.** An operation is **idempotent** if doing it twice leaves the same result as doing it once. HTTP defines which methods promise this:

| Method | Safe (no side effects) | Idempotent |
|---|---|---|
| `GET`, `HEAD`, `OPTIONS` | Yes | Yes |
| `PUT`, `DELETE` | No | Yes: setting the same state twice, or deleting twice, ends in the same state |
| `POST` | No | **No**: two POSTs can create two orders |
| `PATCH` | No | Not guaranteed |

To make a `POST` safe to retry, use an **idempotency key**:

1. The client generates a unique key (a UUID) **once per logical operation**, per "pay for listing 42" and not per attempt, and sends it as a header on every attempt.
2. The server records the key **in the same transaction as the effect**, in a table with a unique constraint on the key, along with the response.
3. A repeat with the same key returns the **stored response** instead of charging again. If the first attempt is still in progress, the repeat waits or gets a "try later" answer.

```sql
CREATE TABLE idempotency_keys (
  idem_key   VARCHAR(64) PRIMARY KEY,
  payment_id BIGINT NULL,
  response   JSON NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

START TRANSACTION;
INSERT INTO idempotency_keys (idem_key) VALUES ('k7');        -- duplicate key error on a repeat
INSERT INTO payments (listing_id, amount) VALUES (42, 9500);
UPDATE idempotency_keys SET payment_id = LAST_INSERT_ID(), response = '{"payment": 991}' WHERE idem_key = 'k7';
COMMIT;
```

If two attempts arrive at the same moment, the primary key makes the second `INSERT` wait on the first's lock and then fail with a duplicate-key error. The server catches it, reads the stored response and returns it. Also store a hash of the request body, so a reused key with a different body is rejected rather than silently returning the wrong result.

**Exactly-once delivery over an unreliable network is impossible**, because the sender can never be sure the last message arrived. What real systems deliver is **at-least-once delivery plus idempotent processing**, which gives an **effectively-once** result. Say it in those words.

<Trace title="Retry or not?" steps={retries} takeaway="A timeout means unknown. Retry only transient failures, with backoff, jitter and a budget, at one layer, and only operations made idempotent with a key." />

<Reveal q="PUT is idempotent by definition. So retrying a PUT is always safe?">

Repeating the same `PUT` leaves the same final state, **if nothing else happened in between**. If another client updates the resource between your first attempt and your retry, your retry silently overwrites their change. Conditional requests fix it: send `If-Match` with the `ETag` you read, and the server rejects the write (`412 Precondition Failed`) if the resource changed. Idempotent is about repeating *your* request, not about concurrency with others.

</Reveal>

**A common slip:** "If the call fails, we retry." Which failures? How many times, at which layer, with what backoff? Is the operation idempotent, and if not, what makes it so? An answer without those is the one interviewers mark down.

<h2 id="pooling">Chapter 13 · Keep-alive and connection pools</h2>

A familiar Friday-night incident: the autoscaler takes app servers from 20 to 100 in eight minutes, and then the database stops accepting connections. Every new server opened its own pool. The system did not run out of database. It ran out of doors.

**A new connection is expensive**: a TCP round trip, a TLS round trip, key-exchange CPU on both ends, a fresh slow-start window, and on the server real resources (PostgreSQL, for example, starts a separate backend process per connection). Doing that per request is waste.

**A connection pool** keeps a set of open connections and lends them out: borrow, use, return. Requests skip the handshakes, and the number of connections stays bounded. The same idea applies everywhere: app to database, app to cache, service to service over HTTP keep-alive, the CDN PoP to the origin. In Python, a `requests.Session` reuses connections for you. Calling `requests.get` repeatedly does not.

**Sizing with Little's law.** On average, **busy connections = request rate × time each request holds a connection**.

- One app server: 200 queries per second, 10 ms each: `200 × 0.010 = 2` connections busy on average. A pool of about 10 covers bursts and slow queries.
- The fleet: `100 servers × 10 = 1,000` connections to one database. PostgreSQL's default `max_connections` is 100, and it handles hundreds or thousands of mostly idle connections poorly. Fix: a **connection pooler** in between (PgBouncer in transaction mode is the standard example) that multiplexes many client connections onto a few dozen real ones.

**What goes wrong with pools:**

- **Silent idle kills.** A load balancer, NAT or firewall drops a connection that sat idle past its timeout. The pool hands it out and the first request fails.
- **Pool exhaustion.** Every connection is borrowed by a slow query, and new requests wait forever. Set an **acquire timeout** and fail fast.
- **Stale DNS.** Pooled connections keep talking to the old IP after a failover changes DNS. A maximum connection lifetime makes the pool re-resolve and reconnect.
- **Bigger is not faster.** A database has a fixed number of cores and disks. Past a modest level of concurrency, extra connections add contention. Size from Little's law plus headroom, not "as many as threads".

**What happens when the load balancer closes an idle connection.** This is the failure to be able to walk through:

1. The pool holds an open connection that has been idle for 5 minutes. The load balancer's idle timeout is 60 seconds.
2. At 60 s the load balancer silently drops its state for that connection. Often it sends nothing to either end, so both still believe the connection is open.
3. The app borrows it and writes a request. The load balancer has no record, so it answers with a TCP reset (or nothing, and the request waits until the read timeout).
4. The app sees "connection reset by peer" or a timeout on a request that never reached the backend.

Fixes, in order: set the pool's **idle timeout and max lifetime below** the shortest idle timeout on the path (for example 50 s against 60 s), enable TCP keepalive or application pings so the path stays warm, validate a connection before lending it or retry once on a fresh connection, and make sure the retry is safe (idempotent, or the failure was provably before the request was sent).

  <Mermaid code={`sequenceDiagram
    participant A as App pool
    participant LB as Load balancer (idle timeout 60 s)
    participant S as Backend
    A->>LB: request 1 (new connection)
    LB->>S: forwarded
    S-->>A: response 1
    Note over A,LB: 5 minutes idle. LB drops its state at 60 s
    A->>LB: request 2 on the old connection
    LB--xA: TCP reset
    Note over A: retry once on a fresh connection`} />
</Figure>

With HTTP/2 or gRPC between services, one connection multiplexes many calls, so the pool can be a handful of connections per backend. Keep more than one, so a single slow connection is not a bottleneck and an L7 balancer can spread them.

<Reveal q="The database is slow, so someone doubles every app server's pool size. What happens?">

Usually it gets **slower**. More concurrent queries compete for the same CPU, locks and disk. Latency per query rises, which (by Little's law) holds connections longer, which fills the bigger pool too. Throughput tends to peak at a modest concurrency. The fix is fewer, faster queries, a pooler, or more database capacity, not more doors to the same room.

</Reveal>

**A common slip:** autoscaling the app tier without saying what happens to downstream connection counts. "Each new server opens 10 connections, so at 100 servers that is 1,000, and a pooler sits in front of the database" is one sentence and shows you have run this in production.

**Five follow-ups you will get:**

<Reveal q="1 · Exactly how many round trips before the first byte on a cold HTTPS connection?">

TCP + TLS 1.3: two before the request leaves (TCP, then TLS), three to the first response byte. TLS 1.2 adds one more. HTTP/3 over QUIC merges the handshakes: one before the request, two to the first byte. 0-RTT resumption sends the request in the first flight, but only on a return visit and only for idempotent requests, because early data can be replayed. Plus the DNS lookup if it is not cached.

</Reveal>

<Reveal q="2 · Why does your video feature use UDP when everything else uses TCP?">

Because late is as bad as lost. TCP delivers in order, so one lost packet blocks every packet behind it until it is retransmitted: head-of-line blocking, which shows up as a frozen frame. Over UDP the app plays what arrived, conceals the gap, and adapts its bitrate to congestion itself.

</Reveal>

<Reveal q="3 · Why gRPC between services and not REST? Any downsides?">

Typed contracts with generated clients, compact protobuf, HTTP/2 multiplexing, streaming, and deadlines that propagate. Downsides: browsers cannot call it natively (REST or gRPC-Web at the edge), payloads are not human-readable, and because calls ride one long-lived HTTP/2 connection, an L4 balancer pins all of a client's calls to one backend. You need L7 or client-side load balancing.

</Reveal>

<Reveal q="4 · The server needs to tell the client something. How?">

The server cannot open a connection to a phone behind NAT, so it rides one the client opened. Rare updates: poll. One-way push: SSE, which reconnects automatically and resumes with Last-Event-ID. Two-way and frequent: WebSockets, and then servers are stateful, so I need a connection registry or pub/sub to find which server holds a user, heartbeats, and catch-up from storage on reconnect.

</Reveal>

<Reveal q="5 · The payment call timed out. What does the client do?">

A timeout means "unknown": the charge may have happened. The client retries with backoff, sending the **same idempotency key** it generated for this payment. The server stored the key with the result in the same transaction as the charge, so a repeat returns the original result instead of charging again. That is at-least-once delivery with idempotent processing: effectively once.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| "What happens when I type a URL?" | DNS (cached, TTL), TCP (1 RTT), TLS 1.3 (1 RTT), HTTP (1 RTT), where TLS terminates, stateless servers |
| Far-away users, slow first load | Count round trips. Terminate TLS at a nearby edge. HTTP/3. Keep-alive. 0-RTT for idempotent requests only |
| DNS failover, migrations | Low TTL set *before* the move. Runtimes cache too. Pair with anycast or health checks |
| Live audio, video, game state | UDP (or WebRTC): late is as bad as lost |
| Lossy mobile networks | HTTP/2 suffers TCP head-of-line blocking. HTTP/3 over QUIC fixes it |
| Public API | REST + JSON, cacheable `GET`s |
| Internal service calls | gRPC: protobuf, HTTP/2, deadlines, with L7 or client-side balancing |
| Many screens, nested varied reads | GraphQL with batching (N+1) and query cost limits, or a BFF endpoint |
| Rare server updates | Short polling |
| One-way push, token streams | SSE |
| Two-way, frequent | WebSockets + registry/pub-sub, heartbeats, catch-up |
| "Your load balancer?" | L7 at the edge (TLS, path routing). L4 for raw connections, non-HTTP, huge connection counts |
| Client IP behind proxies | `X-Forwarded-For` / `Forwarded` set by your edge only. PROXY protocol at L4 |
| "Server pushes to the phone" | NAT: the client opens the connection. Heartbeats keep it alive |
| Timeouts and retries | Every call has a timeout. Retry transient errors at one layer with backoff, jitter, budget |
| Retrying a POST | Idempotency key stored with the effect. At-least-once + idempotent = effectively once |
| Random resets after idle | Pool idle timeout below the load balancer's. Validate or retry once on a fresh connection |
| Autoscaling the app tier | Pools multiply. Little's law. A pooler in front of the database |

## Five mistakes to leave behind

1. **"The request goes to the server."** Say DNS, TCP, TLS, HTTP, and where TLS ends, in one breath.
2. **"TLS adds a round trip or two" without knowing which.** TLS 1.3 is one. TCP + TLS 1.3 is two before the request. QUIC is one. 0-RTT is replayable.
3. **"Real-time means WebSockets."** Poll if you can, SSE if the server only pushes, WebSockets only for frequent two-way traffic.
4. **"gRPC because it's faster"** without the browser and load-balancing catches.
5. **Retrying without idempotency.** A timeout is "I don't know". Only a key makes the retry safe.

**Practice:** with a study partner, narrate the full life of `POST /orders` from a phone in Delhi to a service in us-east: every hop, every handshake, where TLS ends, where state lives, what happens if the response is lost. Five minutes, no notes. It drills the two common slips from this lesson, layer conflation and silent skips.
