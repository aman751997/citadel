<h2 id="prologue">Prologue · Why this pattern exists</h2>

Imagine a video app whose upload endpoint transcodes the video before it responds. A one-minute clip takes about two minutes to transcode. The load balancer gives up at 60 seconds and cuts the connection. The phone shows an error and the user taps retry. The first transcode is still running, so now there are two. A support engineer later counts the transcodes for one unlucky video: seven.

Nothing in that story is exotic. It is what happens when slow work lives inside a request. The fix is one template, and this lesson teaches it.

**Work that can't finish inside a request (too slow, too big, too bursty, too flaky, or due at a later time) becomes a job: persisted, queued, run by workers that scale, and tracked by a status.** Every long-running feature in a design is this template with different nouns. Learn it once and YouTube, the web crawler, the notification system, the code judge, the job scheduler and "export my data" become variations.

**Trigger words:** "process the video", "generate a report", "send to everyone", "crawl", "index", "run nightly", "it can take minutes", "the user shouldn't wait".

**Why this matters if you have built it before.** If you run an event-driven pipeline at work, you already own this template. The <a href={`${BASE}sd/war/event-driven-ai-pipeline/`}>War Room entry on the event-driven AI pipeline</a> is it in production: a trigger on upload, durable queues, a DLQ with no TTL and a replay script, a webhook back when the work is done, a push to the page. Interviews don't test whether you can build it. They test whether you can **say why each piece is there**, out loud, under a clock. Two slips are common: leaving out the failure path because "obviously there are retries", and freezing on the crawler, which has no user-facing API to hide behind.

**A few terms, defined once.**

- **Job:** one unit of background work, stored as a row with a status.
- **Queue:** a buffer of job ids waiting for a worker (RabbitMQ, SQS, a Redis list or stream, or a database table).
- **Worker:** a stateless process that takes a job from the queue and does it.
- **Idempotent:** doing it twice has the same effect as doing it once.
- **DLQ (dead-letter queue):** a side queue where messages go after they have failed too many times.

<h2 id="why-async">Chapter 1 · When a request is the wrong container</h2>

**What is it?** A request is a promise to answer *now*. Some work can't keep that promise. Making it a job means answering "accepted" now and doing the work later.

**Why do we need it?** Four signals say a piece of work should become a job:

| Signal | Example | Why a request is the wrong container |
|---|---|---|
| **Longer than a request should live** | Transcoding (minutes), a year-long PDF export, an ML batch | Load balancers, proxies and phones time out (often 30-60 s). A timeout is not a cancellation, so the work keeps running and the retry starts another |
| **Bursty** | Month-end exports, a contest's final minutes, a viral upload wave | A queue absorbs the burst. Workers drain it at the rate you can afford instead of the rate users arrive |
| **Retriable and flaky** | Calling a slow third-party API, sending email, fetching a web page | Failures should be retried with backoff without the user holding a connection open |
| **Not now** | "Every Monday at 9", "in three days unless they buy" | No request exists at the moment the work is due |

**Worked numbers, the video upload.** Little's law says: *things in a system = arrival rate × time each one spends there.* Assumptions for this example: 30 uploads/s at peak, 120 s per transcode.

```text
In flight = 30 uploads/s × 120 s = 3,600 requests
```

3,600 requests are held open at once, each pinning a thread, a connection and a load-balancer slot. And none of them can succeed, because the load balancer cuts at 60 s. As a job, the request does a few milliseconds of work (insert a row, enqueue an id) and returns. The 3,600 become 3,600 rows and 3,600 messages, which cost almost nothing to hold.

**What async costs. Say it, don't hide it:**

- **The user doesn't get the answer in the response.** They get a tracking number, and the UI needs a "processing" state.
- **More moving parts:** a queue, workers, a status store, a failure path.
- **Duplicates become normal.** Workers die mid-job and the work runs again (Chapter 4). Most of this lesson is about making that harmless.

**When is something simpler enough?** If the work takes tens of milliseconds and the user needs the result to render the page, keep it in the request. If it only needs to be "fire and forget" and losing it is fine, an in-process background task may be enough. The moment you must not lose it, or it must survive a deploy, you need a persisted job.

<Trace title="Should it be a job?" steps={whyAsync} takeaway="Rate × duration = requests held open. Work longer than a timeout, bursty, retriable or due later becomes a job." />

**Common slip:** "We'll just make it async" for work that takes 20 ms and that the user needs to see the result of. A queue in front of a fast, needed answer adds latency and failure modes. The trigger is duration, burstiness, retries or timing. Say which one.

**Interview takeaway:** "Rate times duration gives requests held open. If that exceeds what timeouts and thread pools allow, or the work is bursty, flaky or scheduled, it's a job: accept, return an id, work in the background."

<h2 id="template">Chapter 2 · The job template</h2>

**What is it?** The canonical shape of every async feature. Five sentences:

1. **Persist the job first, then enqueue its id.** The database row is the truth; the queue is a delivery mechanism. If the enqueue fails or a message is lost, a **reconciler** (a periodic sweep) re-enqueues rows stuck in `queued` past a threshold. A queue-only job vanishes silently when its message does.
2. **Return `202 Accepted` with a job id immediately,** and a status URL: `Location: /jobs/7f3a`.
3. **Workers pull, lease, do, update status.** They are stateless, replaceable, and scaled on how far behind the queue is (Chapter 8).
4. **Status flows back.** Polling `GET /jobs/{id}` is the default. Push (SSE or WebSocket) when a person is watching a progress bar. A **webhook** when the client is another server.
5. **Failures are the design.** Retries with backoff and jitter, then a dead-letter queue and an alert. A worker that dies mid-job loses its lease, the job comes back, someone else runs it, **so the work must be idempotent.**

**Why do we need each piece?** Take any piece away and you get a specific failure. No row: nothing to poll, nothing to reconcile. No 202: the client holds a connection. No lease: a crashed worker's job stays "running" forever. No idempotency: the retry doubles the effect.

**The job row, as MySQL.** This is the table to draw next to the job-store cylinder:

```sql
CREATE TABLE jobs (
  id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,   -- the tracking number
  tenant_id       BIGINT UNSIGNED NOT NULL,
  type            VARCHAR(32) NOT NULL,
  status          ENUM('queued','running','retrying','succeeded',
                       'failed','dead','cancelled') NOT NULL DEFAULT 'queued',
  attempt         INT NOT NULL DEFAULT 0,        -- bumped on each claim; also the fencing token (Ch. 3)
  max_attempts    INT NOT NULL DEFAULT 5,
  lease_owner     VARCHAR(64) NULL,
  lease_until     DATETIME(3) NULL,              -- when an un-heartbeated claim expires (Ch. 4)
  run_after       DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),   -- backoff and scheduling
  priority        TINYINT NOT NULL DEFAULT 5,
  progress_done   INT NOT NULL DEFAULT 0,        -- Ch. 9
  progress_total  INT NULL,
  input_ref       VARCHAR(512) NULL,             -- object keys, never the bytes
  output_ref      VARCHAR(512) NULL,
  last_error      TEXT NULL,
  idempotency_key VARCHAR(64) NOT NULL,
  created_at      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                  ON UPDATE CURRENT_TIMESTAMP(3),
  UNIQUE KEY uq_tenant_idem (tenant_id, idempotency_key),   -- a retried POST returns the same job
  KEY ix_claim (status, run_after, priority)
);
```

**The API handler in Python.** The unique key makes a retried POST return the same job instead of a second one:

```python
def create_export(db, queue, tenant_id, idem_key, params):
    try:
        with db.cursor() as cur:
            cur.execute(
                "INSERT INTO jobs (tenant_id, type, idempotency_key, input_ref) "
                "VALUES (%s, 'export', %s, %s)", (tenant_id, idem_key, params))
        db.commit()
        created = True
    except IntegrityError:                  # duplicate (tenant_id, idempotency_key)
        db.rollback()
        created = False
    with db.cursor() as cur:
        cur.execute("SELECT id FROM jobs WHERE tenant_id=%s AND idempotency_key=%s",
                    (tenant_id, idem_key))
        job_id = cur.fetchone()[0]
    if created:
        queue.publish(job_id)               # crash before this line? the reconciler re-enqueues
    return 202, {"jobId": job_id, "status": "queued"}, {"Location": f"/jobs/{job_id}"}
```

The gap between `commit()` and `publish()` is a **dual write**: two systems, no shared transaction. The reconciler closes it: every minute, `SELECT id FROM jobs WHERE status='queued' AND created_at < NOW() - INTERVAL 2 MINUTE` and re-publish. Re-publishing is safe because workers claim by conditional update (Chapter 3), so a duplicate message does nothing. The more general fix is an <a href={`${BASE}sd/lessons/queues-streams/`}>outbox</a>.

**Where the queue lives. Three honest options:**

| | The database is the queue | A broker (RabbitMQ, SQS) beside the database | Redis (list or stream) beside the database |
|---|---|---|---|
| How | Workers claim rows with `SELECT ... FOR UPDATE SKIP LOCKED` (MySQL 8.0+, PostgreSQL 9.5+) | Row in the DB, job id in the broker | Row in the DB, job id in a Redis list or stream |
| Strengths | One system, transactional with your data, no dual write | Per-message ack, visibility timeouts or redelivery, DLQ built in | Very fast, simple, already deployed in many stacks |
| Limits | Polling load and row churn at high rates; fine up to hundreds or low thousands of jobs/s on good hardware (benchmark it) | Insert plus publish is a dual write, closed by the reconciler or an outbox | Durability depends on persistence settings; a plain list loses in-flight work if a consumer dies (Chapter 4) |
| Pick when | Modest rates and you want simplicity | High rates, many worker types, or a broker already exists | You already run Redis and can accept its durability trade-offs |

**Claiming from the database queue in MySQL.** MySQL has no `UPDATE ... RETURNING`, so claim in a short transaction:

```python
def claim_one(db, worker_id):
    with db.cursor() as cur:
        cur.execute(
            "SELECT id FROM jobs "
            "WHERE status IN ('queued','retrying') AND run_after <= NOW(3) "
            "ORDER BY status, run_after LIMIT 1 "
            "FOR UPDATE SKIP LOCKED")          # skip rows other workers have locked
        row = cur.fetchone()
        if row is None:
            db.rollback()
            return None
        cur.execute(
            "UPDATE jobs SET status='running', attempt=attempt+1, lease_owner=%s, "
            "lease_until=NOW(3) + INTERVAL 60 SECOND WHERE id=%s", (worker_id, row[0]))
        cur.execute("SELECT attempt FROM jobs WHERE id=%s", (row[0],))
        attempt = cur.fetchone()[0]
    db.commit()
    return row[0], attempt
```

`SKIP LOCKED` is the key: without it, ten workers all block on the same first row. With it, each worker gets a different row. The `ORDER BY` must follow the index (`ix_claim` is `status, run_after, priority`). If MySQL has to sort (`Using filesort` in `EXPLAIN`, for example with `ORDER BY priority DESC, created_at`), a locking read locks every matching row before it picks one, so the first worker holds them all and the others get nothing back. Check with `EXPLAIN`; for priorities, claim from one queue or index per priority.

**Why not Kafka for jobs?** A log hands each partition to one consumer and tracks one offset per partition. A ten-minute job at the head of a partition blocks everything behind it, and you can't acknowledge job 5,013 while 5,012 is still running. Logs fit event streams. **Per-message-ack queues fit independent jobs.** (Newer Kafka versions are adding queue-style consumption; check its current status before relying on it.) The difference is the subject of <a href={`${BASE}sd/lessons/queues-streams/`}>Queues & streams</a>, Chapter 2.

**Status back to the client:**

| Mechanism | When | The detail that scores |
|---|---|---|
| **Polling** `GET /jobs/{id}` | Default; jobs of seconds to hours | Return `Retry-After` or a suggested interval; cache the status read |
| **SSE / WebSocket push** | A person watching a progress bar | Keep polling as the fallback for reconnects |
| **Webhook** | The client is a server (partner integration) | Sign it, retry with backoff, receiver idempotent on job id |
| **Email / push notification** | Long jobs where the user has left | "Your export is ready" with a short-lived download link |

**Subtle difference: polling vs push vs webhook.** Polling is the client asking and is robust, because a missed answer is just asked again. Push is the server talking to a connected browser and breaks on reconnect. A webhook is the server calling another server and needs signing, retries and a receiver that tolerates duplicates.

<Reveal q="A user got two files from two clicks. Which line of the template would have stopped the second export?">

The **idempotency key** on `POST /exports`. The client generates a key per logical request and reuses it on retry. The API stores it with a unique constraint on `(tenant_id, idempotency_key)`. The second click finds the existing job 81 and returns the same 202: one job, one file, one email. Without a key, two clicks are two legitimately different jobs as far as the server can tell. <a href={`${BASE}sd/lessons/delivery-framework/#api`}>The delivery framework's API chapter</a> covers the header; <a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a> covers idempotency end to end.

</Reveal>

**Common slip:** drawing the queue without the job row. "Put it on Kafka and workers process it" has no answer to "how does the user know it's done?", "what if the message is lost?", or "what did job 81 fail with?". The row is where status, attempts, errors and outputs live.

**Interview takeaway:** "Insert the row, then enqueue the id, return 202 with a job id. The row is the truth, the queue is delivery, and a reconciler re-enqueues anything stuck in queued."

<h2 id="state-machine">Chapter 3 · The job state machine</h2>

**What is it?** A job is a small **state machine**, and its row stores which state it is in. Imagine a support engineer asking, "The customer says job 42 has been running since yesterday. Is it?" The worker that claimed it was replaced by an autoscaler at 2 AM and nothing has touched the row since. It is "running" only in the sense that nobody told the database otherwise. A state machine with explicit lease and failure states prevents that.

<Figure caption="The job state machine. Workers move jobs forward; the reconciler rescues jobs whose workers vanished; a human (or a fixed bug) redrives the dead.">
  <Mermaid code={`stateDiagram-v2
    [*] --> queued: API inserts row
    queued --> running: worker claims, takes lease
    running --> succeeded: outputs written, conditional update
    running --> retrying: transient error or lease expired
    retrying --> queued: backoff elapsed
    running --> failed: permanent error
    running --> dead: attempts exhausted
    dead --> queued: redrive after fix
    queued --> cancelled: user cancels
    running --> cancelled: worker sees flag
    succeeded --> [*]
    failed --> [*]`} />
</Figure>

| State | Meaning | Who moves it out |
|---|---|---|
| `queued` | Waiting for a worker | A worker's claim; the user's cancel |
| `running` | A worker holds a lease | That worker (succeeded / failed / retrying); the reconciler when the lease expires |
| `retrying` | Failed transiently; waiting until `run_after` | The claim query, which skips rows not yet due |
| `succeeded` | Outputs exist; `output_ref` set | Nobody, terminal |
| `failed` | Permanent error (bad input); the user is told why | Nobody, terminal. The user fixes input and submits a new job |
| `dead` | Transient errors outlasted every attempt | An operator's redrive, after the cause is fixed |
| `cancelled` | User asked to stop | Nobody, terminal |

**Two rules make the machine safe under concurrency:**

- **Every transition is a conditional update.** If it changes 0 rows, you didn't own the job any more, and you stop.
- **The attempt number is a fencing token.** A worker that paused (a long GC, a network partition) and wakes up after its lease expired holds an old attempt number, so its writes match nothing.

```python
def finish(db, job_id, attempt, output_ref):
    with db.cursor() as cur:
        cur.execute(
            "UPDATE jobs SET status='succeeded', output_ref=%s "
            "WHERE id=%s AND status='running' AND attempt=%s",
            (output_ref, job_id, attempt))
        owned = cur.rowcount == 1           # 0 means: not ours any more, stop
    db.commit()
    return owned
```

This is the same idea as fencing tokens for distributed locks in <a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a>, made cheap by a column you already have. The simulation below shows the underlying idea with a version number: a write that checks the version loses cleanly instead of overwriting a newer value.

**Subtle difference: `failed` vs `dead`.** *Failed* means "this input can never work", so the user needs to hear it in seconds. *Dead* means "something on our side kept breaking", so an operator needs to hear it, and the job should be redriven once the cause is fixed.

| | `failed` | `dead` |
|---|---|---|
| Cause | Bad input, unsupported format, 4xx | Transient errors that outlasted all attempts |
| Retried? | Never | Yes, until the cap |
| Who is told | The user, immediately | An operator, by alert |
| What happens next | User submits a corrected job | Operator redrives after the fix |

<h2 id="leases">Chapter 4 · Leases and crashed workers</h2>

**What is it?** A worker that takes a job can die at any instant: before it starts, halfway, or after doing the work but before saying so. **The queue or job store can't tell those apart.** So the system assumes the worst and gives the job to someone else, which means the job may run twice. The mechanism that makes this work is the **lease**: claiming a job grants a time-limited right to run it. While the worker is alive it **heartbeats**, extending the lease. If the heartbeats stop, the lease expires and the job becomes claimable again.

**Why do we need it?** Say transcoding moves to cheap pre-emptible machines that the cloud provider can take back with a short warning, several times an hour. Without leases, a video taken by a vanished worker stays "running" forever. With leases, the job comes back within a minute.

**Three ways to implement a lease, and what differs:**

| | Broker ack / visibility timeout | Database `lease_until` | Redis key with TTL |
|---|---|---|---|
| How it works | A received message is hidden or unacknowledged. SQS hides it for N seconds (delete = ack, `ChangeMessageVisibility` = extend). RabbitMQ requeues an unacked message when the consumer's channel closes | Row has `lease_until`; heartbeat extends it; a reconciler moves `running` rows with `lease_until` in the past to `retrying` | `SET lease:job:42 workerA NX PX 60000`; heartbeat extends only if the value is still yours |
| Who notices a crash | The broker | A sweeper | The key simply expires; someone must then re-offer the job |
| Fencing token? | No | Yes: `attempt` | No, still need `attempt` in the DB |
| Watch out for | Visibility caps (SQS allows at most 12 hours from first receive, and extending does not reset it) and ack timeouts on long jobs | Sweeper lag; clock source (use the DB's `NOW()`) | A lease key is not a fence; a paused worker can still write |

**Subtle difference: RabbitMQ's ack vs SQS's visibility timeout.** In RabbitMQ the message stays assigned to a consumer until it acks, nacks, or the connection drops, so a stuck-but-connected consumer holds it until RabbitMQ's delivery acknowledgement timeout (`consumer_timeout`, 30 minutes by default). The broker checks this about once a minute, so a short timeout is enforced at the next check, not to the second. Tested with `consumer_timeout = 10000` (10 s): on RabbitMQ 3.13.7, classic and quorum queues both closed the channel with `PRECONDITION_FAILED - delivery acknowledgement on channel 1 timed out` about 60 s after the delivery, and the message went back to the queue. On 4.3.6, a quorum queue cancelled the consumer after 10 s (the channel stayed open), but a classic queue did not enforce the timeout at all in 330 s of waiting. Treat the 4.x classic-queue case as unclear: the docs describe the timeout without that exception, so do not rely on it there. A job longer than the timeout needs a higher setting or a design that acks early. In SQS the message reappears after the visibility timeout whatever the consumer is doing, so there is no "stuck consumer holds it" case, but a slow healthy worker gets a duplicate unless it extends the timeout.

**Sizing the lease.** The lease length is how long a crash goes unnoticed. Too short and healthy slow jobs get handed out twice. Too long and a crashed job sits idle. **Short lease plus heartbeat** gives both: a 60-second lease renewed every 20 seconds. A crash is noticed within a minute; a healthy two-hour job keeps renewing.

**A Python worker with a heartbeat thread.** Heartbeat in a separate thread so long computation doesn't starve it:

```python
import threading

def heartbeat(db_factory, job_id, attempt, stop, lost):
    db = db_factory()                        # own connection: connections are not thread-safe
    while not stop.wait(20):                 # every 20 s until told to stop
        with db.cursor() as cur:
            cur.execute(
                "UPDATE jobs SET lease_until = NOW(3) + INTERVAL 60 SECOND "
                "WHERE id=%s AND status='running' AND attempt=%s", (job_id, attempt))
            ok = cur.rowcount == 1
        db.commit()
        if not ok:                           # reclaimed by someone else, or cancelled
            lost.set()
            return

def run_job(db, db_factory, job_id, attempt):
    stop, lost = threading.Event(), threading.Event()
    t = threading.Thread(target=heartbeat, args=(db_factory, job_id, attempt, stop, lost))
    t.start()
    try:
        build_export(job_id, should_stop=lost.is_set)   # checks the flag between chunks
        if not lost.is_set():
            finish(db, job_id, attempt, f"exports/{job_id}/sales.csv")
    finally:
        stop.set(); t.join()
```

If the heartbeat's update matches 0 rows the lease was lost, so the worker abandons the job at the next safe point rather than writing a result nobody will accept.

**The same idea with RabbitMQ and Redis.** With RabbitMQ (pika), turn on manual acks and a prefetch of 1 so a consumer holds one job at a time, and ack only after the row is updated:

```python
channel.basic_qos(prefetch_count=1)
def on_message(ch, method, props, body):
    job_id = int(body)
    claimed = claim_by_id(db, job_id, worker_id)     # conditional UPDATE; None if already taken
    if claimed:
        run_job(db, db_factory, job_id, claimed.attempt)
    ch.basic_ack(method.delivery_tag)                # ack last; a crash before this redelivers
channel.basic_consume(queue="jobs", on_message_callback=on_message, auto_ack=False)
```

Production caveat: pika's `BlockingConnection` must keep processing I/O to send its own AMQP heartbeats. For multi-minute jobs, run the work in a thread and ack from the connection's thread via `connection.add_callback_threadsafe`, or the broker will think the consumer died.

A Redis lease and its safe extension (extend only if you still own it, which needs one atomic step):

```text
SET lease:job:42 worker-A NX PX 60000        # take the lease; NX = only if absent
```

```lua
-- extend.lua  KEYS[1]=lease key  ARGV[1]=my worker id  ARGV[2]=new ttl in ms
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
```

A plain `PEXPIRE` would extend someone else's lease after yours expired. The Lua script makes check-and-extend atomic. Even so, a Redis lease alone can't stop a paused worker from writing, which is why `attempt` in the database stays the fencing token.

**Crash, then redelivery, then idempotency. This is the pattern's core insight, and the follow-up every interviewer runs.** You can't prevent the second run; you make it harmless (Chapter 6).

**Restart or resume?** Restarting from the beginning is the default: simple, and correct if the work is idempotent. Resuming from a **checkpoint** pays off only when jobs are long and pre-emption is common. The better answer is usually to **make the job smaller**: split the video into chunks (Chapter 11), the export into id ranges. Then a crash costs one chunk, not the whole job.

**Graceful shutdown.** On a deploy or pre-emption warning, a worker should stop claiming, finish or release its current job (set the lease to expire now), and exit. Then deploys don't look like crashes.

<h2 id="retries">Chapter 5 · Retries, DLQs and poison messages</h2>

**What is it?** The retry policy decides what happens when an attempt fails: whether to try again, how long to wait, when to stop, and where the job goes at the end. Picture a queue whose oldest job is forty minutes old and climbing while the workers are healthy but busy failing: one user uploaded a file with a codec the encoder can't read, then uploaded it again eleven times. Every worker that picks one up crashes, the job reappears, and another worker picks it up, while thousands of good videos wait.

**Why do we need it?** Without a policy, transient failures lose work, permanent failures loop forever, and retries pile onto a struggling dependency. <a href={`${BASE}sd/lessons/queues-streams/#poison`}>Queues & streams, Chapter 8</a> covers the broker mechanics (redrive policies, retry topics, head-of-line blocking on logs). At the job level there are five decisions.

<Figure caption="One failed attempt, as a decision. The permanent branch never retries; the transient branch backs off; the end of the line is a DLQ with an alert.">
  <Mermaid code={`flowchart TD
    F["attempt failed"] --> C{"error type?"}
    C -->|"permanent\nbad input, 4xx"| FA["status = failed\ntell the user now"]
    C -->|"transient\ntimeout, 5xx, lost lease"| N{"attempts left?"}
    N -->|"yes"| B["status = retrying\nrun_after = now + backoff + jitter"]
    B --> Q["back to queued"]
    N -->|"no"| D["status = dead\ncopy to DLQ + alert"]
    D --> R["operator fixes cause\nredrive to queued"]`} />
</Figure>

1. **Classify the error.** *Permanent*: bad input, unsupported format, a 4xx from a dependency, a validation failure. **Fail now**, tell the user, keep the input for inspection. *Transient*: timeout, 5xx, throttling, lost lease. **Retry.**
2. **Back off exponentially, with jitter.** Delay before attempt *n* is about `base × 2^n`, capped, then randomised (for example "full jitter": a random value between 0 and that number). Without jitter, every job that failed at 14:00:00 retries at 14:00:01, 14:00:03, 14:00:07, in lockstep, hammering the recovering dependency.
3. **Size the retry window** to the failures you want to ride out (arithmetic below).
4. **Cap the attempts; then `dead` plus the DLQ.** A dead job is not deleted. It is kept with its last error.
5. **Alert and redrive.** A DLQ nobody watches is a slower way to lose work. Once the bug is fixed, move dead jobs back to `queued`. This is safe because the work is idempotent.

**Worked numbers, the retry window.** Assumption for this example: the thumbnail service has outages of up to 20 minutes.

| Policy | Delays between attempts | Total backoff | Survives a 20-minute outage? |
|---|---|---|---|
| A: 6 attempts, base 1 s, ×2 | 1, 2, 4, 8, 16 s | 31 s | **No.** Every affected job is dead in half a minute |
| B: 8 attempts, base 30 s, ×2 | 30, 60, 120, 240, 480, 960, 1,920 s | 3,810 s, about **63.5 min** | **Yes**, with margin |

Policy A is what many libraries default to, and it is right for a blip. For outages you need minutes of backoff, or a **circuit breaker** that pauses the stage entirely while the dependency is down, so jobs wait in the queue instead of spending their attempts.

**Retries multiply load.** If each of three layers retries 3 times, one user action can become 3 × 3 × 3 = 27 calls to the bottom dependency during an outage, exactly when it can least afford them. Retry at **one** layer (usually the job) and let inner calls fail fast.

**Backoff in Python, with the row as the schedule:**

```python
import random

def backoff_seconds(attempt, base=30, cap=3600):
    return random.uniform(0, min(cap, base * 2 ** attempt))      # full jitter

def on_failure(db, job_id, attempt, err, transient):
    with db.cursor() as cur:
        if not transient:
            cur.execute("UPDATE jobs SET status='failed', last_error=%s "
                        "WHERE id=%s AND attempt=%s AND status='running'", (str(err), job_id, attempt))
        else:
            cur.execute(
                "UPDATE jobs SET last_error=%s, "
                "status = IF(attempt >= max_attempts, 'dead', 'retrying'), "
                "run_after = NOW(3) + INTERVAL %s SECOND "
                "WHERE id=%s AND attempt=%s AND status='running'",
                (str(err), int(backoff_seconds(attempt)), job_id, attempt))
    db.commit()
```

The `retrying` row is picked up again by the claim query once `run_after` has passed (Chapter 2), or by the reconciler that re-publishes it.

**Retries with RabbitMQ: TTL plus dead-letter exchange.** RabbitMQ has no "deliver this in 30 seconds" per message that is reliable for arbitrary delays, so a common recipe is a **wait queue** whose messages expire into the main queue:

```python
channel.queue_declare("jobs", durable=True, arguments={
    "x-dead-letter-exchange": "jobs.dlx"})                       # nack(requeue=False) goes to the DLX
channel.queue_declare("jobs.wait.30s", durable=True, arguments={
    "x-message-ttl": 30000,                                       # expire after 30 s ...
    "x-dead-letter-exchange": "",                                 # ... into the default exchange
    "x-dead-letter-routing-key": "jobs"})                         # ... which routes back to "jobs"
channel.queue_declare("jobs.dead", durable=True)                  # the DLQ, bound to jobs.dlx
```

Use one wait queue per delay step (30 s, 2 min, 10 min). A per-queue TTL works because every message waits the same time, so the oldest is always at the head. Mixing per-message TTLs in one queue can leave a short-TTL message stuck behind a long one: in classic queues an expired message is only removed once it reaches the head of the queue, so until then it still counts as in the queue. If the database is your truth, the simpler path is `run_after` in the row and no wait queues at all.

**Subtle difference: DLQ vs redrive vs retry.**

| | What it is | When it happens | Who triggers it |
|---|---|---|---|
| **Retry** | Automatic re-attempt with backoff | After a transient failure, within the attempt cap | The system |
| **DLQ** | A parking place for jobs that exhausted attempts | After the last attempt fails | The system |
| **Redrive** | Moving DLQ jobs back to `queued` | After the cause is fixed | An operator or script |

**Poison messages.** A **poison message** is one that fails every time it is processed, usually in a way that crashes the worker. The danger is not the one bad job. It is that a message that kills its consumer is never acknowledged, so the broker redelivers it immediately, and a hot loop burns the fleet while good work waits behind it. The video with the unreadable codec is one.

*How it differs from a transient failure:* a transient failure may succeed on a later attempt; a poison message never will. You can't know in advance, so the defences are structural:

- **Count deliveries, and count them before the work starts.** Incrementing `attempt` on claim (not after failure) means a worker that crashes still burns an attempt. After `max_attempts`, the job goes `dead`. Brokers have equivalents: RabbitMQ quorum queues track a delivery count and support a delivery limit (20 by default in RabbitMQ 4.x, no limit in 3.13). After the limit the message goes to the dead-letter exchange, or is dropped if the queue has none. The limit counts returns from a crashed or disconnected consumer; a plain `nack` with requeue did not count in a 4.3 test, so a consumer that keeps nacking can loop forever. Classic queues only mark a message `redelivered`. Redis Streams keep a per-message delivery count visible via `XPENDING`.
- **Validate at the boundary.** Parse and sanity-check the payload (size, schema, format) before the expensive step, and fail permanently on garbage.
- **Isolate the blast radius.** Run risky parsing (codecs, PDFs, archives) in a subprocess or sandbox so a crash kills the child, not the worker, and the parent records a permanent failure.
- **Quarantine, don't discard.** Dead-letter the message with its last error and alert. Someone must be able to inspect and replay it.
- **Don't let one tenant's poison crowd out others:** per-tenant concurrency caps (Chapter 7) limit how many workers a bad batch can occupy.

<h2 id="effects">Chapter 6 · Idempotent effects</h2>

**What is it?** Idempotent means running the work twice has the same effect as running it once. The tricky part is that delivery is **at-least-once**: a worker can always die between doing the work and recording it, so you can't stop a rerun, only make it harmless.

**Why do we need it?** Say an export worker builds the CSV, uploads it, emails the link, then marks the job done. A deploy lands between the email and the database write. The job is redelivered. The user gets two emails with two links. "Can't we just turn on exactly-once?" You can't make it run once. You can make running it again do nothing.

<Figure caption="The crash window. The email went out, the status write never happened, so the redelivered job sends it again unless a marker stops it.">
  <Mermaid code={`sequenceDiagram
    participant W1 as Worker 1
    participant M as Mail provider
    participant DB as Job store
    participant W2 as Worker 2
    W1->>M: send export-ready email
    Note over W1: process killed here
    Note over DB: status still running
    DB->>W2: lease expired, redeliver job
    W2->>DB: INSERT effect marker (job, email)
    DB-->>W2: marker row already exists? skip send
    W2->>DB: status succeeded`} />
</Figure>

**Delivery is at-least-once; you make the *effect* exactly-once.** (Why delivery can't be exactly-once across a network is <a href={`${BASE}sd/lessons/queues-streams/#delivery`}>Queues & streams, Chapter 4</a>; the dedup-table recipe is <a href={`${BASE}sd/lessons/queues-streams/#idempotency`}>Chapter 5</a>.) Three tools cover almost everything:

**1. Deterministic outputs.** Name every output by the job's inputs, never by the attempt: `exports/81/sales-2025.csv`, `videos/9/720p/chunk-0007.ts`. A rerun overwrites the same object with the same bytes. A random name per attempt leaves orphans and forces you to decide which copy is real.

**2. Conditional state transitions.** Completion is `UPDATE ... WHERE id = 81 AND attempt = :mine AND status = 'running'`. Downstream triggers (the next stage, the email) fire only for the worker whose update changed a row.

**3. Markers for effects outside your systems.** An email, a charge or a third-party call can't join your transaction. Give each one a marker keyed by the job:

```sql
CREATE TABLE effects (
  job_id  BIGINT UNSIGNED NOT NULL,
  effect  VARCHAR(32) NOT NULL,
  PRIMARY KEY (job_id, effect)
);
```

```python
def send_once(db, job_id, send):
    with db.cursor() as cur:
        cur.execute("INSERT INTO effects (job_id, effect) VALUES (%s, 'email') "
                    "ON DUPLICATE KEY UPDATE job_id = job_id", (job_id,))
        first_time = cur.rowcount == 1
    db.commit()
    if first_time:
        send()           # crash here: the marker says sent, the email never went out (at-most-once)
```

That version records first, then sends, which can lose an email. The order is a choice you make out loud:

| Order | If it crashes in between | Fits |
|---|---|---|
| Record marker, then send | The email is never sent (at-most-once) | Effects where a duplicate is worse than a miss |
| Send, then record marker | The email is sent twice (at-least-once) | Receipts and "your export is ready"; a rare duplicate is fine |
| Pass the job id as the provider's **idempotency key** | The provider deduplicates | Payment and messaging providers that support it; best when available |

**Subtle difference: atomic vs idempotent.** An atomic operation can't be seen half-done. An idempotent operation can safely be repeated. A database transaction is atomic but not idempotent: running the same "add 10" transaction twice adds 20. Making it idempotent means keying it (`WHERE not already applied`).

**The point of no return.** Some effects can't be undone or deduplicated (a push notification already on someone's lock screen). Put them **last**, after every step that can fail, so a retry rarely reaches them twice.

<Trace title="Make twice harmless" steps={effects} takeaway="Deterministic output keys, conditional completion, and a marker or provider idempotency key for each external effect." />

What I guarantee is that the effect happens once: outputs are written to deterministic keys, completion is a conditional update on the attempt number, and the one external effect, the email, uses the job id as its dedup key. A redelivery redoes some work and changes nothing."* Saying *delivered at least once, effect exactly once* is the whole answer.

<h2 id="fairness">Chapter 7 · Fairness and priorities</h2>

**What is it?** Fairness is deciding whose job runs next when there is more work than workers. A plain queue is first-come, first-served, which sounds fair until one tenant floods it.

**Why do we need it?** Say an enterprise customer's integration requests an export for each of their million products on day one. Small customers' single exports sit "queued" for eight minutes. The queue is working perfectly. That is the problem.

**Worked numbers.** Assumptions for this example: one FIFO queue, 2,000 jobs/s of worker capacity, the big tenant enqueues 1,000,000 jobs. A small tenant's single job lands behind them and waits 1,000,000 ÷ 2,000 = **500 s, about 8.3 minutes**. Nobody did anything wrong; one tenant's burst simply became everyone's latency.

**Priorities come first, and they bring their own problem:**

- **Separate queues per class**: interactive (a user is waiting), standard, bulk. Workers poll the high queue first.
- **Strict priority starves.** If interactive work alone can saturate the fleet, bulk jobs never run. Starvation is the predictable result of strict priority under load, not a rare edge case.
- **Aging** fixes starvation crudely: a job's effective priority rises the longer it waits, so eventually it wins.

**Subtle difference: priority vs fairness.** Priority answers "which kind of work matters more". Fairness answers "which owner should get a turn". A priority queue can still let one tenant's million high-priority jobs starve everyone else's high-priority jobs. You usually need both.

**Fairness across tenants is a scheduling decision:**

| Scheme | How | Gives you |
|---|---|---|
| **Per-tenant queues, round-robin** | One logical queue per tenant; the dispatcher takes one job from each non-empty queue in turn | A small tenant waits about one "turn", not behind a million jobs |
| **Weighted fair scheduling** | Each class or tenant gets a weight and receives throughput in proportion when there is contention (deficit round-robin is a classic implementation) | Guaranteed shares, no starvation, and a paid tier can buy a bigger weight |
| **Per-tenant concurrency cap** | At most N running jobs per tenant | One tenant can't occupy every worker, even with long jobs |
| **Admission control** | Per-tenant rate limits or quotas at the API (`429` with `Retry-After`) | Bounds the backlog itself; see <a href={`${BASE}sd/lessons/rate-limiter/`}>Rate limiter</a> |

**Worked numbers, weights.** Interactive and bulk share 2,000 jobs/s, weighted 4 : 1. When both have work, bulk gets 1 ÷ (4 + 1) = **20% = 400 jobs/s**, never zero. A good scheduler is **work-conserving**: when interactive is idle, bulk gets all 2,000. The million-job tenant then drains in 500 s when the fleet is otherwise quiet, or 1,000,000 ÷ 400 = 2,500 s, about **42 minutes**, at worst while interactive saturates. Nobody else waits behind it.

<Figure caption="Per-tenant queues feeding a weighted scheduler. The million-job tenant fills its own queue, not everyone’s.">
  <Mermaid code={`flowchart LR
    A[("tenant A\n1,000,000 jobs")] --> S["Scheduler\nweighted round-robin\n+ per-tenant cap"]
    B[("tenant B\n1 job")] --> S
    C[("tenant C\n12 jobs")] --> S
    S --> W["Workers\n2,000 jobs/s"]`} />
</Figure>

**Implementation honesty.** "A queue per tenant" with ten thousand tenants means ten thousand queues to poll. Common shapes: the database-as-queue with a claim query that picks the tenant with the fewest running jobs; a small dispatcher that keeps a ring of active tenants; or a few shared queues plus per-tenant caps enforced at claim time. Pick one and say how the worker finds its next job.

A per-tenant concurrency cap in Redis is a counter with a safety expiry, so a crashed worker can't hold a slot forever:

```text
INCR running:tenant:7          # at claim time; if the result is above the cap, DECR and skip this job
EXPIRE running:tenant:7 3600   # safety expiry; the real value is recomputed by a reconciler
DECR running:tenant:7          # when the job finishes
```

This counter drifts if a worker dies between `INCR` and `DECR`, so recompute it from the `running` rows now and then. The jobs table is the truth; Redis is a fast approximation. RabbitMQ's own priority queues exist, but they only order messages within one queue and add per-priority overhead, so check the docs before using many levels.

**Admission control, the front door.** Fair scheduling decides how a backlog drains; a rate limit keeps the backlog from growing without bound. The simulation shows the token bucket most APIs use: bursts are allowed up to the bucket size, then requests get `429`.

<TokenBucketSim />

**When is something simpler enough?** A single tenant or a handful of trusted internal callers rarely needs more than two priority queues and a worker cap. Reach for weighted fair scheduling when tenants are many, unequal and external.

**Interview takeaway:** "FIFO turns one tenant's burst into everyone's latency. I'd use per-tenant queues or claim-time caps with weighted fair scheduling, plus API quotas so the backlog itself is bounded."

<h2 id="scaling">Chapter 8 · Sizing, scaling and back-pressure</h2>

**What is it?** Three connected questions: how many workers you need, what signal says "add more", and what the system does when work arrives faster than it can be done (back-pressure).

**Why do we need it?** Say a video product grows to a million uploads a day. Every evening the oldest transcode job is forty minutes old. An autoscaler set to keep CPU at 70% does nothing, because the workers spend half their time waiting on storage so CPU sits at 55%. Meanwhile the cluster sized for the evening peak sits two-thirds idle at 4 AM.

**Sizing workers: Little's law again.** *Busy workers = arrival rate × time per job.* Then divide by a target utilisation (60-80%), because a fleet at 100% has no slack and its queue grows without bound.

**Worked numbers.** Assumptions for this example: 1,000,000 uploads/day, about 1 minute each; the full rendition ladder costs about **4 core-minutes per video-minute** (benchmark your encoder and settings); peak is 3× average; 32-core machines; an illustrative **$0.04 per core-hour** (check current prices).

```text
Work         1,000,000 videos × 1 min × 4 core-min = 4,000,000 core-min/day
Average      4,000,000 ÷ 1,440 min ≈ 2,778 cores busy  → ≈ 87 machines
Peak (3×)    ≈ 8,333 cores                             → ≈ 261 machines
Cost         4,000,000 core-min = 66,667 core-hours × $0.04 ≈ $2,667/day of real work
Peak 24/7    8,333 cores × 24 h × $0.04               ≈ $8,000/day, 3× the work
```

**Three ways to provision, and what each costs:**

| Strategy | Machines | What users feel | Bill |
|---|---|---|---|
| Provision for peak, always on | ~261 | No queue, ever | ~$8,000/day; two-thirds idle at night |
| Provision near average, let the queue absorb peaks | e.g. 4,200 cores, about 131 machines | A wait at peak (below) | About half the peak bill |
| Autoscale on queue age, with a floor | 87-261, following load | Short waits while new machines boot | Close to the $2,667 of real work, plus headroom |

**Worked numbers, what "let the queue absorb it" means.** Provision 4,200 cores. A 2-hour evening peak brings 8,333 core-minutes of work per minute. The backlog grows by 8,333 − 4,200 ≈ **4,133 core-minutes every minute**. After 2 hours that is about **496,000 core-minutes** of queued work. A video uploaded at the end of the peak waits about 496,000 ÷ 4,200 ≈ **118 minutes**. If the night runs at half the average (about 1,389 cores of arrivals), the backlog drains at 4,200 − 1,389 ≈ 2,811 per minute, about **3 hours**. Two-hour waits are not acceptable for "your video is processing", which is why the real answer is **autoscaling plus priorities** (short videos and first renditions first, Chapter 17), with the queue absorbing only the few minutes it takes new machines to boot.

**What to autoscale on.** Not CPU. Workers can be saturated or I/O-bound whatever the backlog. Use:

- **Age of the oldest queued job.** It is what users feel ("ready in about 4 minutes"). Alert and scale on it.
- **Backlog per worker** = queued work ÷ workers, against a target ("each worker should have at most 2 minutes of work waiting"). Depth alone means nothing without job duration: 10,000 one-millisecond jobs are nothing; 10,000 ten-minute jobs are a crisis.
- **Scale per stage.** Each stage of a pipeline has its own queue and its own fleet (Chapter 10).

**Back-pressure** is how the system says "slow down" instead of drowning. Four mechanisms, from gentlest to harshest:

| Mechanism | How it works | Real knob |
|---|---|---|
| **Pull-based workers** | Workers take work at their own rate, so they can't be overwhelmed; the queue grows instead | Queue age is the signal |
| **Prefetch limit** | A consumer holds at most N unacknowledged messages, so a slow worker doesn't hoard a pile | RabbitMQ `basic_qos(prefetch_count=N)`; SQS max messages per receive; Redis Streams `COUNT` on `XREADGROUP` |
| **Bounded queue** | When the queue is full, new work is refused or the oldest is dropped | RabbitMQ `x-max-length` with `overflow` set to `reject-publish`; Redis Stream `MAXLEN`; a database count check at the API |
| **Admission control** | Per-tenant quotas at the API: `429` with `Retry-After` | Chapter 7 |

An unbounded queue just turns overload into ever-later results. Whether to **reject new work** or **drop old work** depends on the product: a "your export" request should be rejected visibly, while stale metrics samples can be shed.

**Protect downstream.** Scaling workers moves the bottleneck to whatever they write to. Doubling transcoders doubles writes to object storage and the job store. Check they can take it, or cap concurrency per dependency.

**Subtle difference: back-pressure vs load shedding vs autoscaling.** Back-pressure slows or refuses *producers*. Load shedding *drops* work to protect the system. Autoscaling adds *capacity*. A healthy design uses autoscaling for normal growth, back-pressure for sustained overload, and shedding only for the least valuable work.

**Pre-emptible (spot) machines** fit job workers unusually well: the lease-and-idempotency machinery from Part Two already handles a machine disappearing. Run a floor of on-demand capacity for interactive work and burst on spot for bulk. (Pricing and eviction behaviour vary by provider; check current terms.)

For work where seconds matter (a code judge during a contest), keep a **pre-warmed pool** sized by Little's law (Chapter 16). <h2 id="progress">Chapter 9 · Progress and cancellation</h2>

**What is it?** Progress is a cheap, derived number saying how far a job has got. Cancellation is how a user stops a job that is queued or already running.

**Why do we need it?** Picture a progress bar on a two-hour concert video: 73%, then 73% for six minutes, then 100%. Was it stuck? Nobody knows. And when the user clicks cancel on the next one, nothing happens for a quarter of an hour, and then it publishes anyway. Both are design gaps, not bugs in one worker.

**Progress** should be defined in units the job really has: chunks done ÷ chunks total, rows exported ÷ rows estimated, pages crawled this run. Then:

- **Write it rarely.** Per chunk, or at most every few seconds per job, never per frame or per row. Thousands of workers writing progress every millisecond is a self-inflicted database load.
- **Store it on the job row** (or a fast side store for very chatty jobs), and serve it from `GET /jobs/{id}`. Push via SSE or WebSocket only when someone is watching.
- **Report stage as well as percent.** "Transcoding 180 / 300 chunks" beats "60%". A per-stage view would have explained the stalled bar: packaging, one serial step, was running.
- **ETA** = remaining work ÷ recent throughput for this job, and say it is an estimate.

A cheap way to keep chatty progress out of MySQL is a Redis hash, flushed to the row at most every few seconds:

```text
HSET progress:job:81 done 180 total 300 stage transcoding
EXPIRE progress:job:81 86400
```

```python
r.hset(f"progress:job:{job_id}", mapping={"done": done, "total": total, "stage": "transcoding"})
```

**Subtle difference: heartbeat vs progress.** A heartbeat says "this worker is alive". Progress says "this job is moving". A worker can heartbeat while stuck in an infinite loop. Alert on both: expired leases catch dead workers, and "lease renewed but no progress for N minutes" catches stuck ones.

**Checkpoints for long jobs.** A 3-hour export over 50 million rows should save a **cursor** (the last exported id) every few thousand rows, alongside the part number in a multipart upload. A crash then resumes from the cursor instead of from row zero. The output key stays deterministic, so the resumed run writes the same parts.

**Cancellation is a state, not a signal.** You can't reach into a queue and pluck out a job's 140 pending tasks, and you shouldn't kill shared worker processes.

1. **Mark the job `cancelled`** (a conditional update, since it might have just succeeded).
2. **Queued work skips itself.** A worker that dequeues a task checks the parent job's status first and acks without working if it is cancelled.
3. **Running work stops at safe points.** Workers check the flag at each heartbeat or between chunks, abort, and release their lease.
4. **A sweeper cleans up** partial outputs under the job's prefix.
5. **Past the point of no return, say so.** If publishing has started, "cancel" may mean "delete after it completes". The UI should tell the truth.

<h2 id="pipelines">Chapter 10 · Staged pipelines</h2>

**What is it?** A **pipeline** is a graph of stages. Each stage is the job template (its own queue, its own workers, its own retries), and finishing one stage enqueues the next. The item being processed (a video) carries a state machine of its own: `uploaded → validating → transcoding → packaging → ready`.

**Why do we need it?** Say the product owner asks for thumbnails, then a preview GIF, then captions from the audio, then a banned-content check before anyone sees an upload. The transcode job becomes a 40-minute script that does seven things. One step fails on an odd aspect ratio and the retry starts the whole 40 minutes again.

<Figure caption="A video service as a staged pipeline. Each box is a stage with its own queue and fleet; branches run in parallel; publish waits for what it needs.">
  <Mermaid code={`flowchart LR
    U["upload complete"] --> V["validate + probe\nscan content"]
    V --> SP["split into chunks"]
    SP --> T["transcode\nchunk × rendition\nthousands of cores"]
    T --> P["package\nHLS segments + manifests"]
    V --> TH["thumbnails\na few workers"]
    V --> CA["captions\nGPU workers"]
    P --> PUB["publish\nstatus = ready, CDN"]
    TH --> PUB`} />
</Figure>

**Why stages beat one large job:**

- **Independent retry.** A failed thumbnail retries the thumbnail, not the transcode.
- **Independent scaling.** Transcode needs thousands of cores, thumbnails a few, captions GPUs. One job type would have to run on the most expensive machine for its whole length.
- **Parallelism.** Branches with no dependency (thumbnails, captions) run alongside transcoding. Inside a stage, fan-out splits one item into many tasks (Chapter 11).
- **Failure isolation.** A broken caption model stalls captions, not playback. Decide per branch whether it **blocks publish** (content scan: yes) or **arrives later** (captions: publish without, add when ready).

**Between stages, pass references.** A message carries `{ videoId, stage, inputKey }`, never the 4 GB file. This is the **claim-check** pattern. Workers read and write object storage directly. Messages stay small, brokers stay happy, and a stage can be rerun from its stored input.

**A stage worker in Python with RabbitMQ.** One queue per stage; finishing the stage publishes to the next queue, but only if the stage's conditional update changed a row:

```python
def on_transcode_task(ch, method, props, body):
    msg = json.loads(body)                       # {"videoId": 9, "task": "c42-720p", "inputKey": "..."}
    outputs = transcode(msg["inputKey"], out_key=f"videos/9/720p/{msg['task']}.ts")   # deterministic key
    remaining = mark_task_done_and_count(db, msg["videoId"], msg["task"])             # Ch. 11
    if remaining == 0 and try_fire_packaging(db, msg["videoId"]):                     # fire exactly once
        publish(ch, queue="package", body={"videoId": msg["videoId"]})
    ch.basic_ack(method.delivery_tag)
```

Because `ack` is last, a crash between the publish and the ack redelivers the task; the conditional mark makes the second run count zero. In production you would put the "publish next stage" step behind an outbox or a reconciler too, since the mark and the publish are a dual write.

**Self-feeding pipelines.** In most pipelines work flows one way. In a **web crawler**, the fetch stage produces new work for itself: every fetched page yields links, which become new fetch jobs. That loop needs a guard against infinite work: dedup and budgets (Chapters 14-15).

**Subtle difference: a staged pipeline vs one big job in a costume.** If step four fails and steps one to three run again, it is one big job. In a real pipeline each step has a queue and retries alone.

| | Mega-job | Staged pipeline |
|---|---|---|
| Retry unit | The whole job | One stage or task |
| Scaling | One fleet shape for everything | Per-stage fleets (CPU, GPU, small) |
| Failure | One failure fails all | Isolated per branch |
| Cost | Simple | More queues, more state to track |

**When is something simpler enough?** Two steps that always run together on the same machine (resize then compress) can stay one job. Split when the steps have different resource needs, different failure modes, or different retry costs.

<h2 id="fan-in">Chapter 11 · Fan-out and fan-in</h2>

**What is it?** **Fan-out** turns one item into many independent tasks. **Fan-in** notices when all of them have finished and fires the next stage exactly once.

**Why do we need it?** A two-hour concert takes ninety minutes to transcode on one machine. Cutting it into one-minute chunks and transcoding all of them at once finishes in minutes. But then packaging must start only when *every* chunk is done. Say a viewer reports a video that skips from minute 41 to minute 43: packaging started while chunk 42 was still running. Who decided all the chunks were done?

**Worked numbers, why fan out.** A 60-minute video at 4 core-minutes per video-minute is **240 core-minutes** of work. Even a 32-core machine with perfect parallelism needs 7.5 minutes, and a single encode rarely uses 32 cores perfectly, so one-machine jobs run much longer. Split into 60 one-minute chunks × 5 renditions = **300 tasks of about 0.8 core-minutes each**. With 300 free cores, wall-clock time is roughly the slowest task plus the split and package steps: minutes, not tens of minutes.

**Splitting video correctly.** Chunks must start on a **keyframe** (split on closed GOP boundaries) so each can be encoded alone. Force keyframes at a fixed interval in every rendition so segment boundaries line up across renditions, because the player switches bitrate at those boundaries (<a href={`${BASE}sd/lessons/blob-cdn/#video`}>Blob storage & CDN, Chapter 15</a>). The cost of chunking: per-task overhead, and encoder rate control can't see across chunk boundaries, so quality can vary slightly at the seams. Chunk size is the dial: smaller chunks, more parallelism and more overhead.

<Figure caption="Fan-out to 300 tasks, fan-in by counting completions once each. The stage transition is itself conditional, so exactly one worker fires packaging.">
  <Mermaid code={`flowchart LR
    S["split\nvideo 9"] --> T1["chunk 1 × 360p"]
    S --> T2["chunk 1 × 720p"]
    S --> T3["…"]
    S --> T4["chunk 60 × 1080p"]
    T1 --> F{"mark task done\nif not already,\nremaining − 1"}
    T2 --> F
    T3 --> F
    T4 --> F
    F -->|"remaining = 0\nand state = transcoding"| P["package video 9\n(fired once)"]`} />
</Figure>

**Fan-in, the classic answer, and its bug.** "Set a counter to 300; each finished task does an atomic decrement; whoever hits zero fires the next stage." Atomic is not the same as idempotent. A task that decrements and then dies before acknowledging is **redelivered and decrements again**. The counter reaches zero one task early, and packaging starts with a hole at minute 42.

**Count each task once, in MySQL:**

```python
def mark_task_done_and_count(db, video_id, task_id):
    """Returns remaining tasks, or -1 if this task was already counted."""
    with db.cursor() as cur:
        cur.execute("UPDATE tasks SET state='done' WHERE id=%s AND state <> 'done'", (task_id,))
        if cur.rowcount == 0:                # redelivered: already counted, change nothing
            db.rollback()
            return -1
        cur.execute("UPDATE videos SET remaining = remaining - 1 WHERE id=%s", (video_id,))
        cur.execute("SELECT remaining FROM videos WHERE id=%s", (video_id,))
        remaining = cur.fetchone()[0]        # we hold the row lock, so this value is exact
    db.commit()
    return remaining

def try_fire_packaging(db, video_id):
    with db.cursor() as cur:                 # exactly one caller changes a row
        cur.execute("UPDATE videos SET state='packaging' "
                    "WHERE id=%s AND state='transcoding' AND remaining=0", (video_id,))
        fired = cur.rowcount == 1
    db.commit()
    return fired
```

- **The simplest version** skips the counter. After marking its task done, each worker checks that no tasks are left not-done, then attempts the conditional stage transition. 300 rows is a cheap count, and every step is idempotent.
- **In Redis**, "add task id to a done-set; only if it was new, decrement" must be one atomic step, so use one Lua script. Keep the task table as the truth you can recount from if Redis loses data:

```lua
-- KEYS[1] = set of finished task ids, KEYS[2] = remaining counter, ARGV[1] = task id
if redis.call('SADD', KEYS[1], ARGV[1]) == 1 then
  return redis.call('DECR', KEYS[2])     -- first time we see this task
end
return -1                                -- duplicate delivery: counted already
```

- **The next stage must be idempotent too.** Two workers might race to fire it; the conditional transition lets one win, and packaging writes deterministic keys anyway.

**Subtle difference: atomic vs idempotent, again, with a concrete case.**

| Approach | Redelivered completion | Result |
|---|---|---|
| Atomic `DECR` only | Decrements again | Fires one task early, with a hole |
| Mark task done conditionally, then count in one transaction | Mark matches 0 rows, no decrement | Correct |
| Redis `SADD` + `DECR` in one Lua script | `SADD` returns 0, no decrement | Correct, with the table as recount source |

**Fan-in needs a failure path.** If task 233 is dead-lettered, `remaining` sits at 1 forever and the video is "processing" until someone complains. Either a dead child **fails the parent** (or marks it partially ready, if that's a product choice), or a sweeper fails parents with no progress past a deadline. "Wait for all" must always come with "...or until this deadline".

<Trace title="Count the last chunk once" steps={fanIn} takeaway="Atomic is not idempotent. Mark each task done conditionally and count in the same transaction; fire the next stage with a conditional transition; give the parent a deadline." />

<Reveal q="Could you avoid fan-in altogether by having the packaging stage poll “are all 300 chunks there yet?” every few seconds?">

Yes, it is a legitimate design and sometimes simpler: a packaging job for video 9 is scheduled once, checks the task table (or lists the output prefix), and re-schedules itself with a delay until everything is present or a deadline passes. The cost is latency (up to one polling interval) and wasted checks, in exchange for no counter at all. Saying "a completion-triggered fan-in, or a self-rescheduling check with a deadline; I'd pick the trigger for latency" shows you see both.

</Reveal>

**Common slip:** "A Redis counter, decrement on completion." The interviewer's next question is "what if a completion is delivered twice?" Have the conditional-mark answer ready before they ask.

**Interview takeaway:** "Mark each task done conditionally and decrement in the same transaction, so a redelivery counts zero. Fire the next stage with a conditional state change, and give the parent a deadline so a dead child can't leave it at 99%."

<h2 id="orchestration">Chapter 12 · Orchestration vs choreography</h2>

**What is it?** Two ways to connect stages. In **choreography**, each stage reacts to events from the previous one. In **orchestration**, one coordinator tells each stage what to do next and records the result.

**Why do we need to choose?** Imagine support asks for a page that shows, for any video, which stage it is in, what failed, and a button to rerun from that stage. The engineer who built the pipeline opens seven repositories to work out what happens after "chunks transcoded", because the answer is spread across seven subscriptions. The plan exists. It is just not written down anywhere.

| | **Choreography** | **Orchestration** |
|---|---|---|
| How | Each stage reacts to events: "transcoded" means packaging subscribes; "packaged" means publish subscribes | One coordinator (an orchestrator service or a workflow engine) tells each stage what to do next and records the result |
| Where the plan lives | Implicitly, in everyone's subscriptions | Explicitly, in one workflow definition |
| Strengths | Loose coupling; a new listener (analytics) joins without touching anyone | One place to see status, set timeouts, retry from a stage, add compensation, change the order |
| Weaknesses | "Where is video 9?" has no single answer; cycles and lost steps are hard to spot | The coordinator is a dependency every stage talks to; it must be durable itself |
| Fits | Side reactions to facts: notify followers, update search, analytics | The core flow of one item through ordered stages with deadlines |

Most real systems use both: **orchestrate the core flow, choreograph the side effects.** The orchestrator publishes `VideoReady`; anyone may listen.

**A homemade orchestrator is just a table.** One row per video per stage:

```sql
CREATE TABLE video_stages (
  video_id    BIGINT UNSIGNED NOT NULL,
  stage       ENUM('validate','transcode','package','publish') NOT NULL,
  status      ENUM('pending','running','succeeded','failed') NOT NULL DEFAULT 'pending',
  attempt     INT NOT NULL DEFAULT 0,
  started_at  DATETIME(3) NULL,
  finished_at DATETIME(3) NULL,
  last_error  TEXT NULL,
  PRIMARY KEY (video_id, stage)
);
-- "Where is video 9?"  SELECT stage, status, last_error FROM video_stages WHERE video_id = 9;
-- "Rerun from package": UPDATE video_stages SET status = 'pending' WHERE video_id = 9 AND stage IN ('package','publish');
```

**Workflow engines, at intuition level.** Engines such as Temporal (and Cadence, which it came from) and AWS Step Functions let you write the plan once and make it *durable*: the engine records each step's result, so a crashed coordinator resumes where it left off; steps get retry policies and timeouts; a workflow can wait for days on a timer or a human approval. Two details are worth knowing, hedged:

- **Replay-based engines (Temporal-style)** rebuild a workflow's state by re-running its code against the recorded history, so workflow code must be **deterministic**: clock, randomness and I/O go through the engine's APIs or into "activities". Check the engine's docs for the exact rules.
- **State-machine engines (Step Functions-style)** describe the flow as a JSON/YAML state machine with built-in parallel and map steps for fan-out. Check current limits on history size and execution duration before betting a design on them.

In an interview you rarely need to name an engine. Say: *"An orchestrator with a durable state table per video, one row per stage with status, attempt and timestamps. A workflow engine would give me that off the shelf."*

**Trade-offs and when to use which.** Choose orchestration when you need to answer "where is it?", retry from a stage, enforce deadlines, or compensate (undo earlier stages). Choose choreography for independent consumers that react to a fact and where no one needs a global view. The risk of choreography is invisible cycles and lost steps; the risk of orchestration is a coordinator that becomes a bottleneck or a single point of failure unless it is itself durable and replicated.

**Interview takeaway:** "I'd orchestrate the core flow with a durable state table (or a workflow engine) and choreograph side effects like notifications and analytics off the events it publishes."

<h2 id="scheduler">Chapter 13 · Schedulers</h2>

**What is it?** A scheduler fires jobs at a time: "every Monday at 9 AM", "in three days". It turns time into jobs.

**Why do we need it?** "Run this at 9 AM daily" adds hard sub-problems to the template. Imagine a weekly summary email sent every Monday at 9 AM local time. For resilience the scheduler runs on two nodes, and on the first Monday every user gets two summaries. On the second Monday a deploy takes the scheduler down from 8:55 to 9:20 and nobody gets anything.

**Problem 1: firing on time at scale.** Don't scan the whole schedules table every second.

- **Due-time index.** Each schedule row stores `next_run_at` (computed from its rule and time zone), indexed. Each tick selects due rows, enqueues a job for each, computes the next occurrence and writes it back.
- **Delay queues and timing wheels** for short delays (seconds to minutes): a broker's per-message delay, or an in-memory timing wheel, a ring of buckets one per tick, each holding the timers due then. Long or cancellable delays belong in the database (<a href={`${BASE}sd/lessons/queues-streams/#delay`}>Queues & streams, Chapter 11</a>).
- **Time zones:** store the rule and the IANA zone (Europe/London), not a fixed UTC instant, so 9 AM stays 9 AM across daylight-saving changes.

**Problem 2: firing exactly once when the scheduler is replicated.** Two nodes both see "9:00 job due". This is contention. Two layers:

- **Coordination:** a lease per firing (a lock with a TTL and a heartbeat), **or** partition the schedule space so each node owns a slice, **or** let the database hand out disjoint rows with `SKIP LOCKED`.
- **Idempotent execution as the backstop.** The execution key is `(schedule_id, scheduled_time)`, unique in the jobs table. A second fire for Monday 9:00 hits the constraint and does nothing. Name both layers.

**A tick in MySQL and Python** that uses `SKIP LOCKED` for coordination and a unique key as the backstop:

```sql
ALTER TABLE jobs ADD COLUMN execution_key VARCHAR(80) NULL, ADD UNIQUE KEY uq_exec (execution_key);
```

```python
def tick(db):
    with db.cursor() as cur:
        cur.execute("SELECT id, tenant_id, rrule, tz, next_run_at FROM schedules "
                    "WHERE next_run_at <= NOW() ORDER BY next_run_at LIMIT 500 "
                    "FOR UPDATE SKIP LOCKED")               # two nodes get different rows
        for sid, tenant, rrule, tz, due in cur.fetchall():
            cur.execute(
                "INSERT INTO jobs (tenant_id, type, idempotency_key, execution_key) "
                "VALUES (%s, 'weekly_summary', %s, %s) "
                "ON DUPLICATE KEY UPDATE id = id",
                (tenant, f"sched-{sid}-{due:%Y%m%d%H%M}", f"{sid}:{due:%Y-%m-%dT%H:%M}"))
            cur.execute("UPDATE schedules SET next_run_at=%s WHERE id=%s",
                        (next_occurrence(rrule, tz, after=due), sid))
    db.commit()    # job insert and next_run_at move together, so a crash repeats neither
```

The insert and the `next_run_at` update commit in one transaction, so a crash between them repeats neither. The unique `execution_key` is the safety net if the schedule row is ever reset by hand.

**Why not one scheduler node?** It trades correctness for availability: one node down means no schedule fires. Say why you rejected it, and you've had the whole senior conversation.

**Problem 3: misfires.** When the scheduler was down at 9:00, what should happen at 9:20? There is no universal answer, so make it a **per-schedule policy**: *fire once now* (a weekly report: late is better than never) or *skip* (a "good morning" push at 9:20 is pointless). Never "fire every missed tick" by accident. A once-a-minute job down for a day would fire 1,440 times.

**Subtle difference: delay queue vs due-time index vs cron.**

| | Best for | Weakness |
|---|---|---|
| **Broker delay or TTL queue** | Short delays (retries, reminders in minutes) | Hard to cancel or inspect; limited maximum delays |
| **Due-time index in the DB** | Recurring or long delays, cancel, audit | Polling tick; granularity is the tick interval |
| **Cron on one box** | Side projects | Single point of failure; double fire when duplicated |

This is why "design a distributed job scheduler" is a top-tier question: it is this pattern plus <a href={`${BASE}sd/lessons/pattern-contention/`}>contention</a> plus <a href={`${BASE}sd/lessons/queues-streams/`}>queues</a>, composed.

    S1["scheduler node 1"] -->|"due rows,\nSKIP LOCKED or lease"| DB[("schedules\nnext_run_at indexed")]
    S2["scheduler node 2"] -->|"due rows,\nSKIP LOCKED or lease"| DB

<h2 id="frontier">Chapter 14 · The crawler frontier</h2>

**What is it?** A crawler is a **self-feeding pipeline**: fetching a page produces new URLs to fetch. Its heart is the **URL frontier**, the set of URLs waiting to be fetched. The frontier must answer two questions at once: **which URL is most worth fetching next** (priority) and **which hosts may be contacted right now** (politeness).

**Why do we need it?** A first crawler is a loop: pop a URL, fetch it, push its links. It works for an hour. Then the operator of a small recipe site emails: your crawler sent 3,000 requests in a minute and our server fell over. Politeness has to be built into the data structure, not left to a sleep call.

**The two-level frontier** (the design described for the Mercator crawler and taught in *Introduction to Information Retrieval*, chapter 20):

- **Front queues: priority.** A prioritiser assigns each new URL a score (site importance, how often the page changes, depth from a seed) and puts it in one of F priority queues.
- **Back queues: politeness.** Each back queue holds URLs for **exactly one host**. A table maps host to back queue.
- **A min-heap of hosts by next-allowed time.** A fetcher pops the host whose time has come, takes one URL from its back queue, fetches, and puts the host back with `next_allowed = now + gap`. When a back queue empties, it is refilled from the front queues (biased toward high priority).

<Figure caption="The frontier. Priority decides what’s worth fetching; per-host queues and a heap of next-allowed times decide what’s allowed now.">
  <Mermaid code={`flowchart LR
    N["new URLs\n(normalised, unseen)"] --> PR["prioritiser"]
    PR --> F1[("front: high")]
    PR --> F2[("front: medium")]
    PR --> F3[("front: low")]
    F1 --> R["router\nhost → back queue"]
    F2 --> R
    F3 --> R
    R --> B1[("back: recipes.example")]
    R --> B2[("back: news.example")]
    R --> B3[("back: … one per host")]
    H{"heap of hosts\nby next-allowed time"} --> FE["fetchers"]
    B1 -.-> H
    B2 -.-> H
    B3 -.-> H`} />
</Figure>

**The heap of hosts in Redis.** A sorted set whose score is "next allowed time" is exactly this heap. The one subtlety is crash safety: if a fetcher pops a host and dies, that host disappears. The fix is a lease. Popping re-inserts the host with a *later* score, and finishing the fetch resets it to `now + gap`:

```lua
-- pop_host.lua  KEYS[1]=hosts:ready  ARGV[1]=now_ms  ARGV[2]=lease_ms
local h = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, 1)
if #h == 0 then return nil end
redis.call('ZADD', KEYS[1], tonumber(ARGV[1]) + tonumber(ARGV[2]), h[1])   -- lease: reappears if we die
return h[1]
```

```python
host = r.evalsha(pop_host_sha, 1, "hosts:ready", now_ms(), 60_000)
if host:
    url = r.lpop(f"backq:{host}")                       # one URL for this host
    fetch_and_store(url)
    r.zadd("hosts:ready", {host: now_ms() + gap_ms(host)})   # next allowed time
```

Without the Lua script, two fetchers could both read the same due host before either removes it. The script makes read-and-claim atomic, and the lease-style re-insert is the same idea as a job lease from Chapter 4.

**Politeness, concretely:**

- **One connection per host at a time**, and a **gap** between requests: a fixed 1-10 s, or adaptive (Mercator's heuristic waited a multiple of the last download time, so slow servers get gentler treatment).
- **Back off on distress.** A `429` or `503` (honour `Retry-After`), rising latency or errors means widen that host's gap. Persistent errors mean pause the host.
- **Identify yourself.** A user-agent with a URL explaining the crawler and how to contact you.

**robots.txt**, the Robots Exclusion Protocol, standardised as RFC 9309:

- Fetch `/robots.txt` once per host, **cache it** (the RFC says crawlers shouldn't use a cached copy for more than 24 hours, except when the file is unreachable), and check every URL against the rules for your user-agent before enqueueing or fetching.
- Error handling is specified: broadly, a 4xx for robots.txt means the crawler may access everything, while a 5xx or network failure means **assume everything is disallowed** until it can be read. Check the RFC for the exact rules.
- `Crawl-delay` is a common but **non-standard** directive (it is not in RFC 9309). Honouring it is polite; don't promise it as part of the standard.

**DNS is a hidden bottleneck.** Every fetch needs an IP address. At hundreds of pages per second, uncached lookups add tens of milliseconds each and can overload resolvers. Keep a **local DNS cache per crawler node** (respecting TTLs), and resolve ahead of time for hosts about to come up in the heap. Early crawler papers reported DNS as a surprisingly large share of fetch time; measure yours.

**Distributing the crawler: partition by host.** With ten crawler nodes, assign each **host** to a node by hash. Then one node owns each host's back queue, politeness clock, robots.txt cache, DNS entry and page budget, so politeness becomes a local rule, not a distributed lock. Links discovered for another node's host are forwarded to it in batches. Partitioning by full-URL hash would scatter one host's pages across every node, and no node could enforce its gap alone.

**Subtle difference: partition by URL hash vs by host hash.**

| | Hash of the full URL | Hash of the host |
|---|---|---|
| Load balance | Very even | Uneven: a huge site lands on one node |
| Politeness | Needs cross-node coordination per host | Local to one node |
| Robots/DNS cache | Duplicated on every node | One owner per host |
| Verdict | Wrong for crawlers | Right, with a per-host budget for the huge sites |

**Worked numbers, how many hosts must be in rotation.** Assumption: 386 pages/s (1 billion a month, Chapter 18) with a 2-second gap and one request per host at a time. Each host yields at most 0.5 pages/s, so at least 386 ÷ 0.5 ≈ **772 hosts** must be ready at every moment, more at peak. A frontier dominated by a few huge sites stalls on politeness however many fetchers you add. Keep many hosts active, and spread priority across hosts, not just pages.

<Trace title="Be polite by construction" steps={frontier} takeaway="Per-host back queues with a heap of next-allowed times; partition by host so each host has one owner; rate ÷ (1 ÷ gap) = hosts needed." />

**Common slip:** "Fetchers sleep a second between requests." Forty fetchers sleeping a second can still send forty requests a second to one host. Politeness belongs to the host, so put it where the host's queue lives.

**Interview takeaway:** "Priority front queues feed per-host back queues, and a heap of hosts by next-allowed time gates fetching. Partition by host so politeness is local, and at 386 pages a second with a 2-second gap I need at least 772 active hosts."

<h2 id="dedup">Chapter 15 · Crawler dedup and traps</h2>

**What is it?** Three ways a crawler wastes itself: fetching the **same URL** twice, storing the **same content** under different URLs, and wandering into **infinite URL spaces**. This chapter is how to stop each.

**Why do we need it?** Imagine that after two weeks one small shop's site has served two million pages. Its event calendar has a "next month" link on every page, and every month, forever, is a real page with a real URL. Meanwhile storage grows faster than the page count: the same article is stored forty times under forty URLs with different tracking parameters.

<Figure caption="The dedup funnel. Normalise first, then check URL, content, and traps in that order, each cheaper than the one after it.">
  <Mermaid code={`flowchart LR
    L["extracted link"] --> N["normalise URL"]
    N --> T{"trap rules?\ndepth, length,\nhost budget"}
    T -->|"reject"| X1["drop"]
    T -->|"ok"| B{"seen?\nBloom filter"}
    B -->|"seen"| X2["drop\n(rarely wrong)"]
    B -->|"new"| FR["frontier"]
    FR --> F["fetch"]
    F --> H{"content hash\nor SimHash seen?"}
    H -->|"duplicate"| AL["store alias only"]
    H -->|"new"| ST["store page"]`} />
</Figure>

**1. URL dedup: "have I seen this URL?"**

- **Normalise first:** lowercase scheme and host, drop default ports and `#fragments`, resolve `../`, sort query parameters, strip known tracking parameters, settle trailing slashes. Then dedup on the normalised form.
- **A Bloom filter** answers "seen?" in a small fixed amount of memory. It has **no false negatives** (a seen URL always reports seen) and a tunable **false-positive rate**: a genuinely new URL wrongly reported as seen and therefore **never crawled**.

**Worked numbers, Bloom sizing.** For *n* items and false-positive rate *p*, the optimal filter uses *m = −n · ln p ÷ (ln 2)²* bits and *k = (m ÷ n) · ln 2* hash functions.

| n (URLs) | p | Bits per URL | Memory | Hashes |
|---|---|---|---|---|
| 10 billion | 1% | about 9.6 | about **12 GB** | 7 |
| 10 billion | 0.1% | about 14.4 | about **18 GB** | 10 |
| 10 billion, exact set of 8-byte fingerprints | n/a | 64 | about **80 GB** | n/a |

The exact set is also feasible on a sharded store (and with 64-bit fingerprints, about 3 accidental collisions are expected across 10 billion URLs, by birthday arithmetic, *n² ÷ 2⁶⁵*). The Bloom filter saves roughly 7× the memory in exchange for skipping about 1% of new URLs. Partitioned by host across ten nodes, each node holds about a tenth. Say which you'd choose and why: *"1% coverage loss is fine for discovery; I'd use 0.1% if missing pages costs us."*

**In Redis,** the RedisBloom module provides a Bloom filter with real commands (check that your Redis offering includes the module):

```text
BF.RESERVE seen:urls 0.01 1000000000     # 1% error rate, capacity 1 billion
BF.ADD seen:urls "https://example.com/a" # returns 1 if new, 0 if probably seen
```

`BF.ADD` returning 0 means "probably seen": that is the answer that can wrongly skip a new URL. For an exact check, use a set of 8-byte fingerprints or a Redis hash per host instead, at the memory cost above.

**2. Content dedup: "have I stored this page?"**

- **Exact duplicates:** hash the normalised content (for example SHA-256 of the extracted text). Same hash means store once, record the URL as an alias.
- **Near duplicates** (same article with a different ad, date or session id): **SimHash** gives each page a 64-bit fingerprint where similar pages have fingerprints differing in few bits. A 2007 paper on near-duplicate detection for web crawling (Manku, Jain, Das Sarma) used 64-bit SimHash with a Hamming distance of 3 as the threshold at the scale of billions of pages.

**3. Traps: infinite URL spaces.** Calendars, session ids in URLs, faceted search with endless filter combinations, and pages that generate links to themselves with one more path segment. Dedup can't help, because every URL is genuinely new. Bound the damage:

- **Per-host page budget** per crawl cycle (scaled by the host's importance).
- **Depth limit** from the seed, and **URL length** limit.
- **Pattern rules:** repeated path segments (`/a/b/a/b/a/b`), date paths far in the future, too many query parameters.
- **Yield monitoring:** a host whose pages are mostly near-duplicates gets its budget cut automatically.

**Subtle difference: the three kinds of "duplicate".**

| | Same URL | Same content, different URL | Infinite URL space |
|---|---|---|---|
| Example | Link found on 500 pages | One article with 40 tracking-parameter variants | Calendar "next month" forever |
| Tool | Normalise + Bloom filter / seen set | Content hash (exact), SimHash (near) | Budgets, depth and length limits, pattern rules |
| Does dedup help? | Yes | Yes, after the fetch | No: every URL is new |

**Recrawl: staying fresh.** A crawl is never finished; pages change. Store per URL: last fetch time, content hash, and an estimated change interval.

- **Adaptive revisit:** if the content hash changed since last time, halve the interval (down to a floor, say an hour); if not, double it (up to a ceiling, say 30 days).
- **Conditional fetches** (`If-Modified-Since`, `If-None-Match`) let unchanged pages answer `304` with no body, cheaper for both sides.
- A **recrawl scheduler** is the job scheduler from Chapter 13: URLs with `next_fetch_at <= now` feed the frontier, sharing the crawl budget with discovery. Say the split ("about 70% recrawl, 30% new") as a tunable, not a fact.

<Trace title="Don’t fetch, store or wander twice" steps={dedup} takeaway="Normalise, then Bloom-filter URLs (no false negatives; false positives are skipped pages). Hash content for exact dups, SimHash for near dups. Budgets and pattern rules for traps." />

<Reveal q="Why not just keep a set of every URL in Redis instead of a Bloom filter?">

You can: sharded by host, 10 billion URLs as 8-byte fingerprints is about 80 GB plus per-key overhead, which a Redis cluster could hold (Redis has real per-key overhead, so measure; a sorted on-disk structure is cheaper still). The Bloom filter's appeal is about 12 GB for the same job with no per-key overhead, at the cost of 1% skipped URLs and no deletions. Neither is "the" answer. The answer is the arithmetic, and the coverage loss you accept.

</Reveal>

**Common slip:** "A Bloom filter prevents duplicate crawling" with the error direction backwards. A Bloom filter never makes you crawl a page twice; it occasionally makes you **skip** a new one. Say which way it errs.

**Interview takeaway:** "Normalise, then a Bloom filter for seen URLs (it never re-crawls, it skips about p of new ones), content hash plus SimHash for duplicate pages, and budgets and depth limits for traps, because dedup can't see an infinite URL space."

<h2 id="code-judge">Chapter 16 · Code judges, exports and notifications</h2>

**What is it?** Two more jobs in the same template, and one with a twist. A **code judge** (the LeetCode question in the bank) is the template where **the work itself is hostile**: it runs code that strangers wrote.

**Why do we need a hardened design?** Imagine a coding contest with thirty thousand people. Ten minutes before the end the judge queue's oldest submission is six minutes old, and a submission has just been found trying to open a network connection to the internal metadata service. Not malicious, just curious. This time. The queue must scale, the sandbox must be strong, and one user's loop must not fill the pool.

- **Template:** `POST /submissions` creates a row (`queued`), a queue per language feeds judge workers, the status goes to `running`, then a verdict (`accepted`, `wrong answer`, `time limit`, `runtime error`, `compile error`) that the client polls or gets pushed.
- **Sandbox every run:** no network; CPU, memory, process-count and wall-time limits; a read-only filesystem plus a small scratch directory; a non-root user. Containers share the host kernel, so put them inside a **stronger boundary** (a user-space kernel such as gVisor, or a lightweight VM such as Firecracker) and throw the sandbox away after each run.
- **Idempotency:** a judged submission's verdict is a pure function of code + tests + limits, so a rerun after a crash produces the same verdict. Completion is still a conditional update, so a zombie can't overwrite.
- **Fairness:** per-user concurrency caps and rate limits so one user submitting in a loop can't fill the pool; contest submissions on their own queue with priority over practice runs.

A baseline container invocation (necessary but not sufficient on its own):

```bash
docker run --rm --network none --read-only --tmpfs /tmp:size=16m \
  --memory 256m --cpus 1 --pids-limit 64 --user 65534:65534 \
  --cap-drop ALL --security-opt no-new-privileges \
  judge-python python /tmp/solution.py < input.txt
```

Each flag closes a specific hole: no network (no metadata-service probing), read-only root, bounded memory and processes (no fork bombs), no capabilities. The wall-time limit is enforced by the worker killing the container after N seconds. A plain container still shares the host kernel, so for hostile code add gVisor or a microVM as the outer boundary.

**Worked numbers, the contest spike.** Assumptions: 30,000 users submit about 3 times each in the last 10 minutes, so 90,000 ÷ 600 s = **150 submissions/s**. Each takes about 2 s of sandbox time (compile plus tests). Little's law: 150 × 2 = **300 sandboxes busy**. At a 70% utilisation target: 300 ÷ 0.7 ≈ **430 pre-warmed sandboxes**. Autoscaling on queue age would react minutes too late, so **scale ahead on the contest schedule**, since the contest end time is known in advance.

**The other two family members, in one table:**

| Problem | The template, re-skinned | The detail that scores |

| **Report / data export** | `POST /exports` creates a job; a worker streams rows to object storage as a multipart upload; `succeeded` with a short-lived presigned download link; email | Read from a replica or snapshot so the export doesn't hammer the primary; checkpoint by id cursor for long exports; idempotency key on the POST; the link expires |

**Subtle difference: a plain job vs a hostile job.** An export worker trusts its input (it wrote the query) and can fail a few ways. A judge worker trusts nothing, so its safety comes from isolation and discarding state, not from the worker's code being careful.

**0:05 · Non-functionals with numbers**

> "Scale: I'll assume 500 hours of video uploaded every minute, the order of magnitude YouTube has cited publicly, and a billion views a day. Uploads must be resumable, because phones lose signal. **0:08 · The bridge**

> "So: upload, process, watch; 240 gigabits a second in, 120,000 cores of transcoding, about 10 terabits a second out. The design is a pipeline feeding a CDN, and the hard part is the pipeline. Does that match?"

The interviewer says yes and tells you to continue.

**0:09 · Core entities**

> "**Video**: id, owner, title, duration, status. **Channel**: one-to-many with videos. An **upload session** for the resumable upload's parts. A **processing job** per video, with a **task** per chunk and rendition; that's where the pipeline's state lives. And **renditions**: a manifest per bitrate plus segments, all in object storage."

**0:11 · API**

```http
POST /videos               { title, sizeBytes, contentType }  Idempotency-Key: k1
                           -> 201 { videoId, uploadId, partUrls[] }    (presigned multipart)
POST /videos/{id}/complete { parts: [etag...] }

GET  /videos/{id}          -> 200 { status, stage, progress, manifestUrl? }
GET  cdn/v/{id}/master.m3u8 -> manifest; segments follow, all from the CDN
```

> "The create is idempotent so a retried tap doesn't make two videos. Bytes go straight to object storage through presigned part URLs, so a dropped connection resumes from the last part. The complete call returns 202 because it's a job. Playback never touches our API: the player fetches the manifest and segments from the CDN."

**0:15 · High-level design, one requirement at a time**

> "Upload: the client asks the video service for an upload; we insert the video row as `uploading` and return presigned part URLs; the client uploads parts directly to object storage and calls complete. >

**0:25 · Deep dive 1: fan-out, fan-in and time-to-playable**

> "The hardest part is turning one upload into thousands of tasks and back into one playable video, quickly. A 60-minute video is 240 core-minutes of work; split into 60 one-minute chunks times 5 renditions it's 300 tasks of under a core-minute each, so with free capacity it finishes in a couple of minutes instead of most of an hour. Chunks start on keyframes, and every rendition gets keyframes at the same fixed interval so segments line up for bitrate switching."
>
> "Fan-in: each task, when it finishes, marks itself done with a conditional update and decrements the video's remaining count in the same transaction, so a redelivered completion counts zero, not twice. When remaining hits zero, a conditional state change from `transcoding` to `packaging` lets exactly one worker fire the packager. If any task dies, the video job fails with a reason rather than sitting at 99%."
>
> "And time-to-playable: I'd put the 360p rendition's tasks on a high-priority queue and publish as soon as it's packaged, adding higher renditions to the master manifest as they finish. The creator sees 'live in SD, HD processing' in a couple of minutes."

**0:31 · Deep dive 2: sizing, cost and fairness**

> "120,000 cores on average. At an illustrative 4 cents a core-hour that's about 16 cents per hour of video, around $115,000 a day, so cost is a first-class requirement. Three levers. Spot capacity: our leases and idempotent tasks already survive a machine vanishing, so pre-emption is just a retry. Autoscaling on queue age per stage, not CPU, with a floor. And priorities: first renditions and short videos first; bulk re-encodes of old catalogue run at low weight. Fairness: one channel uploading 10,000 videos gets a per-channel concurrency cap and weighted fair share, so a new creator's single video isn't stuck behind them."

**0:35 · Deep dive 3: failures**

> "Worker dies mid-chunk: the lease expires in about a minute, another worker reruns that one chunk. Outputs use deterministic keys like `videos/9/720p/chunk-0042`, so it just overwrites. A corrupt or unsupported file is a permanent error: fail the job in seconds and tell the creator, no retries. A flaky dependency like the thumbnail service gets exponential backoff with jitter over about an hour, then dead-letter with an alert and a redrive once fixed. And a reconciler re-enqueues jobs stuck in `queued` and fails jobs with no progress past a deadline."

**0:38 · Wrap-up**

> "To recap: resumable direct uploads, a staged pipeline with chunked fan-out and an idempotent fan-in, low rendition first, and a CDN for everything viewers touch. At 10×, storage is the first pressure, about 5 PB a day if renditions double the original, so lifecycle tiering for old renditions, and possibly encoding the top renditions only for videos that get views. View counts I'd do with sharded counters aggregated asynchronously. I'd monitor time-to-playable p95, queue age per stage, DLQ rate, transcode cost per video-hour, and CDN hit ratio."

<Reveal q="The interviewer asks: “Why split into chunks at all? Why not one task per rendition?”">

Per-rendition tasks give you 5-way parallelism. A 60-minute 1080p encode is still one long task: slow to finish, and a crash at minute 50 redoes all of it. Chunks give 300-way parallelism and make a crash cost one minute of video. The costs: a split step, a fan-in, per-task overhead, and slight quality variation at chunk seams because the encoder can't plan across boundaries. For short clips (under a minute or two) I'd skip chunking: per-rendition tasks are simpler and fast enough.

<h2 id="crawler">Chapter 18 · Web crawler walkthrough</h2>

"Design a web crawler." There is no user and no API to hide behind, so this round tests whether you can decompose a system from nothing. Write the four numbers in the corner. Under them, instead of an API, write *data flow*.

**0:03 · Requirements**

> "Functional: start from seed URLs; fetch pages; extract links and add new ones; store raw HTML and metadata for a downstream indexer; recrawl pages to keep them fresh. Out of scope: rendering JavaScript-heavy pages, images and video, the index and ranking themselves. Tell me if you want any of them."

**0:05 · Non-functionals with numbers**

> "Scale: a billion pages a month. That's 10⁹ over 2.6 million seconds, about 386 pages a second on average; I'll plan for about 800 at peak. Average page 100 KB, so about 39 MB a second, roughly 310 megabits; bandwidth isn't the constraint. Storage is 100 TB a month raw, less after compression. Politeness is a hard requirement: obey robots.txt, one connection per host, a gap between requests. Robust to traps and malformed pages. Fresh: important pages recrawled within a day. And fault-tolerant: a crashed node must not lose its frontier."

**0:08 · The bridge**

> "So a self-feeding pipeline at about 400 pages a second where politeness, dedup and traps are the hard parts, not raw throughput. Since there's no user-facing API, I'll replace the API step with a data-flow sketch. OK?"

**0:09 · Core entities**

> "A **URL record**: normalised URL, host, priority, last fetch, next fetch, content hash. A **host record**: robots rules and when we fetched them, next-allowed time, page budget, cached IP. And **page content** in object storage, keyed by content hash, with URLs as aliases."

**0:11 · Data flow, instead of an API**

```text
seeds -> frontier (priority queues -> per-host queues -> heap by next-allowed time)
      -> fetcher (DNS cache, robots check, conditional GET)
      -> content store (dedup by content hash / SimHash)  -> indexer (downstream)
      -> parser -> link extractor -> normalise + trap filters + robots
      -> seen-URL check (Bloom filter) -> forward to owning node by host hash -> frontier
recrawl scheduler (next_fetch_at <= now) -> frontier
```

**0:15 · High-level design**

> "Ten crawler nodes. Each owns a slice of hosts by hash, and holds those hosts' frontier queues, robots cache, DNS cache and Bloom-filter shard. A fetcher takes the host whose next-allowed time has come, takes its highest-priority URL, checks robots, fetches with If-Modified-Since, stores the content, and hands it to the parser. New links are normalised, filtered, checked against the seen set, and sent to whichever node owns their host. Fetched URLs get a next-fetch time; the recrawl scheduler feeds them back when due. The frontier is persisted, with per-host queues in a durable store and an in-memory window, and URLs are leased to fetchers, so a crash re-offers them."

**0:25 · Deep dive 1: the frontier and politeness**

> "Politeness first, because it's a hard requirement. Each host has one back queue and a next-allowed time in a heap; a fetcher only takes a host whose time has come, then pushes it back with now plus the gap. With a 2-second gap a host gives at most half a page a second, so to hit 386 pages a second I need at least 772 hosts ready at any moment. The frontier has to keep many hosts warm, and priority has to spread across hosts. A 429 or 503 widens that host's gap and honours Retry-After. robots.txt is fetched once per host and cached for up to a day; if it's unreachable with a server error, I treat the host as disallowed until I can read it. Partitioning by host makes all of this local, with no distributed locks."

**0:31 · Deep dive 2: dedup**

> "Two kinds. URLs: normalise, then check a Bloom filter. For 10 billion URLs at a 1% false-positive rate that's about 12 GB with 7 hashes, split across ten nodes. A false positive means a new URL is skipped, about 1%, and I'd go to 0.1%, about 18 GB, if coverage matters. An exact set of 8-byte fingerprints would be about 80 GB, also feasible, so I'd say the trade out loud. Content: SHA-256 of the extracted text catches exact copies under different URLs; a 64-bit SimHash with a small Hamming threshold catches near-duplicates like the same article with a different ad."

**0:35 · Deep dive 3: traps and freshness**

> "Traps are infinite URL spaces, like calendars, session ids and faceted filters, where every URL is genuinely new, so dedup doesn't help. Per-host page budgets per cycle, a depth limit, a URL length limit, and pattern rules for repeating path segments; a host whose pages are mostly near-duplicates gets its budget cut. Freshness: each URL keeps an estimated change interval, halved when the content hash changed and doubled when it didn't, between an hour and 30 days, and conditional GETs make unchanged pages cost a 304."

**0:38 · Wrap-up**

> "Recap: host-partitioned nodes, a two-level frontier that makes politeness local, Bloom plus content-hash dedup, budgets against traps, adaptive recrawl. At 10×, 4,000 pages a second, DNS and frontier storage come first: more resolver capacity and prefetching, and the per-host queues spill to disk. Node failure: its host range is reassigned, and its persisted frontier and leased URLs are picked up by the new owner. I'd monitor pages per second, per-host error and 429 rates, frontier size and age, duplicate rate, and the share of budget going to recrawl versus discovery."

**Check the numbers yourself.** 30 days × 86,400 = 2,592,000 s; 10⁹ ÷ 2,592,000 ≈ 385.8 pages/s. × 100 KB ≈ 38.6 MB/s × 8 ≈ 309 Mbps. 10⁹ × 100 KB = 100 TB/month. 385.8 ÷ 0.5 ≈ 772 hosts. The one-billion-pages-a-month target and 100 KB average page are illustrative assumptions.

<h2 id="interview-script">Interview answers</h2>

The interviewer has a design on the board and adds, almost lazily: *"Users can also request a PDF of their whole year. It takes about two minutes to generate. Where does that go?"* Here is how to answer in three depths.

<AnswerModes id="aj-export-answer" q="Users can request a PDF of their whole year; it takes about two minutes. Where does that go?">
  <Fragment slot="short">

It's a job. `POST /exports` with an idempotency key inserts a job row, enqueues the job id, and returns 202 with the id. Workers claim it with a lease, make the PDF at a deterministic key, and mark it done with a conditional update. The client polls `GET /jobs/{id}` and gets a short-lived download link. Failures retry with backoff, then dead-letter with an alert.

  </Fragment>
  <Fragment slot="medium">

Two minutes is longer than any request should live, and month-end makes it bursty, so it's a job. `POST /exports` with an idempotency key inserts a job row (status queued, tenant, attempt, input) and then enqueues the job id, and returns **202 with the job id** and a status URL. The row is the truth; a reconciler re-enqueues rows stuck in queued, so a lost message can't lose the job.

Workers claim a job with a **lease**, sixty seconds renewed by heartbeat, so if a worker dies the job is back within a minute with the attempt number bumped. That means it can run twice, so the work is **idempotent**: the PDF goes to a deterministic key, completion is a conditional update on the attempt number, and the "export ready" email has its own dedup marker.

Transient failures retry with exponential backoff and jitter; bad input fails immediately with a reason; after the attempt cap it's **dead-lettered** with an alert and a redrive path. Workers autoscale on the age of the oldest job, and tenants get a fair share so one big customer can't starve everyone. The client polls, or we push if they're watching, and gets a short-lived download link.

  </Fragment>
  <Fragment slot="deep">

Everything in the two-minute answer, plus the numbers and the failure modes. If month-end brings 20 exports a second at 2 minutes each, that is 2,400 busy workers (20 × 120 s), about 3,400 at 70% utilisation. I'd provision a floor near the average and autoscale on queue age, accepting a short wait while machines boot, and check that the replica the exports read from can take the load, because scaling workers moves the bottleneck downstream.

Poison input is handled by counting attempts on claim, so a file that crashes the renderer is dead-lettered after N tries, not retried forever. Fairness: per-tenant caps and weights, plus API quotas with 429 and Retry-After. Cancellation is a state on the row that workers check at heartbeats. If RabbitMQ is down, accepted jobs sit as queued rows and the reconciler re-publishes them. If the database fails over, stale workers' conditional updates match nothing and deterministic outputs make reruns overwrite harmlessly.

If this grows to 100× I'd keep the database as truth but move delivery to a broker, shard job rows by tenant, and batch progress writes.

  </Fragment>

**Five follow-ups you will get:**

<Reveal q="1 · A worker crashes halfway. What exactly happens?">

Its heartbeats stop, its lease expires within about a minute, and the job becomes claimable again (the reconciler moves it to retrying, or the broker's visibility timeout makes the message visible). Another worker claims it as attempt n + 1 and starts from the beginning, or from the last checkpoint for very long jobs. Outputs overwrite the same deterministic keys. If the first worker was only paused and wakes up, its completion update includes the old attempt number and changes nothing.

</Reveal>

<Reveal q="2 · Can you guarantee the job runs exactly once?">

Delivery is at least once. A worker can always die between doing the work and recording it. I guarantee the **effect** happens once: deterministic output keys, conditional completion, and a marker or provider idempotency key for each external effect such as the email. Running twice redoes some work and changes nothing visible.

</Reveal>

<Reveal q="3 · One customer submits a million jobs. What happens to everyone else?">

With one FIFO queue at 2,000 jobs/s, everyone else waits about 8 minutes. So: per-tenant queues (or a claim query that picks the tenant with the fewest running jobs), weighted fair scheduling, and a per-tenant concurrency cap, plus quotas at the API so the backlog itself is bounded. The big tenant's million jobs consume the big tenant's share, and a small tenant's job waits about one turn.

</Reveal>

<Reveal q="4 · How many workers do you need, and how do you scale them?">

Little's law: arrival rate × time per job, divided by a 60-80% utilisation target. For the export: if month-end brings 20 exports a second at 2 minutes each, that's 2,400 busy workers (20 × 120 s), about 3,400 at 70%. Provision a floor near the average, autoscale on queue age (not CPU), and accept a short wait while machines boot. Check that the database or replica the exports read from can take the extra load, because scaling workers moves the bottleneck downstream.

</Reveal>

<Reveal q="5 · Now it’s a video: one upload becomes 300 parallel tasks. How do you know when they’re all done?">

Each task marks itself done with a conditional update and decrements the parent's remaining count in the same transaction, so a redelivered completion counts zero. When remaining reaches zero, a conditional state change from transcoding to packaging lets exactly one worker fire the next stage. If any task is dead-lettered, the parent fails, or a sweeper fails parents with no progress past a deadline, so nothing sits at 99% forever.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Say... |
|---|---|
| "It can take minutes", "send to all", "nightly" | It's a job: row, enqueue, 202 + job id, workers, status |
| Order of writes | Row first, then enqueue; a reconciler re-enqueues stuck rows (or an outbox) |
| "How does the user know?" | Poll `GET /jobs/{id}` by default; SSE/WebSocket for a watcher; signed, retried webhook for a server |
| A job's lifecycle | queued, running, succeeded / failed / retrying, dead; cancelled; every transition conditional |
| "Worker crashes mid-job" | Lease + heartbeat, expires, reclaimed with attempt + 1, idempotent rerun |
| "Exactly once?" | Delivered at least once; effect once via deterministic keys, conditional completion, effect markers |
| Errors | Classify: permanent fails fast; transient backs off with jitter over a window longer than the outage |
| A message that crashes workers | Poison: count attempts on claim, cap, validate, sandbox, dead-letter and alert |
| Retries exhausted | Dead + DLQ + alert + redrive after the fix |
| One tenant floods the queue | Per-tenant queues, weighted fair scheduling, concurrency caps, API quotas |
| Strict priority | Starvation; add weights or aging |
| "How many workers?" | Little's law ÷ utilisation; provision near average; autoscale on queue age |
| Producers outrun workers | Back-pressure: bounded queue or quota with 429, prefetch limits, autoscale; shed only low-value work |
| A progress bar | Throttled counter in real units (chunks), per stage; heartbeat ≠ progress |
| Cancel | A flag on the job; workers check at safe points; a sweeper cleans outputs |
| Multi-step work | Stages, each with its own queue; messages carry keys, not bytes |
| Parallel chunks then "next step" | Fan-in: conditional mark-done + count in one transaction; conditional stage transition; parent deadline |
| "Where is video 9?" | Orchestrate the core flow (state table or workflow engine); choreograph side effects |
| "Every Monday at 9" | Indexed next_run_at; lease, partition or SKIP LOCKED per firing; unique execution key; misfire policy |
| A crawler | Per-host back queues + heap of next-allowed times; partition by host; robots.txt cached up to 24 h |
| Crawler dedup | Normalise; Bloom filter (skips about p of new URLs); content hash + SimHash |
| Crawler traps | Per-host budgets, depth and length limits, pattern rules |
| Untrusted code | No network, resource limits, read-only FS, gVisor/microVM, discard after each run |
| A known spike (contest, launch) | Pre-warm on schedule; autoscaling is minutes late |

## Common mistakes to leave behind

1. **A queue with no job row.** No status, no attempts, no errors, nothing to poll, nothing to reconcile.
2. **"The worker is idempotent" as a slogan.** Say the output key, the conditional completion, and the effect marker.
3. **An atomic counter for fan-in.** Atomic is not idempotent; count each task once.
4. **"Failed jobs go to a DLQ."** And then? The alert, failed versus dead, and the redrive.
5. **Autoscaling on CPU.** Scale on queue age or backlog per worker, and check the downstream.
6. **Counting attempts only after failure.** A crash-looping poison message never reaches the failure handler.

**Look these up yourself**

- **Deficit round-robin and weighted fair queuing**: the classic algorithms behind "weights 4 : 1", and how they stay fair with jobs of different sizes.
- **Per-title / content-aware encoding**: choosing the bitrate ladder per video instead of one fixed ladder; a big cost lever at video scale.
- **Sagas and compensation**: undoing earlier stages when a later one fails, the natural next step after orchestration.
- **Retry budgets**: capping retries as a fraction of total traffic so retries can never amplify an outage.
- **Lease-based leader election (and why fencing still matters)**: how a scheduler or orchestrator picks one active node.
- **Headless-browser crawling**: rendering JavaScript-heavy pages, why it costs orders of magnitude more per page, and how crawlers decide which pages need it.
- **Sitemaps and change-frequency signals**: how sites tell crawlers what changed, and how far to trust them.
- **Speculative execution of stragglers**: re-running the slowest tasks of a fan-out on another machine, as MapReduce did, to cut tail latency.
