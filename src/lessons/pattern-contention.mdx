<h2 id="prologue">Prologue · Two different bugs</h2>

Imagine a ticket on-sale: 50,000 seats, opening at 10:00 sharp, two million people waiting. Ten minutes later it says "sold out". The next morning support reports two problems:

1. A few hundred seats were sold to two people each.
2. Some customers were charged twice for one order. Their banking app retried the request because the first response was slow.

These are different bugs with the same cause.

The first is **contention**: many actors try to change one scarce thing at the same moment. The second is **duplication**: one actor's single intent arrives more than once, because networks time out and clients retry. Both break the same promise, **it happens once, to one winner**, and a small toolbox fixes both.

**The pattern in one sentence:** several concurrent actors compete to change the same scarce resource (the last seat, the same ₹500, one job), and your design must guarantee it happens **once, to one winner**, under retries, crashes and races.

**Trigger words:** "book", "reserve", "purchase", "only one", "inventory", "double-charge", "flash sale", "redeem", "run this job exactly once", "at most N per user". When money or scarce inventory appears in a question, this pattern is the deep dive.

**Where it shows up.** The three walkthroughs in this module are Ticketmaster, a payment system and a distributed job scheduler. The same tools answer Airbnb booking, flash sales, coupon redemption, inventory, a distributed lock service and, at its limit, a stock exchange.

**A common slip.** Engineers who ship payment code every day often name the framework feature ("we use the idempotency middleware") instead of the mechanism (a unique key claimed atomically, a stored request hash, a replayed response). Interviewers push past the library. This lesson is about saying the mechanism.

<h2 id="problem">The gap between check and change</h2>

Every contention bug has the same shape: **read, decide in the application, write back**. Between the read and the write is a gap, and another request can act inside it. Both decisions were correct when they were made. Together they are wrong.

The buggy hold code, in MySQL terms:

```sql
SELECT status FROM event_seats WHERE event_id = 77 AND seat_id = 'B-4-17';   -- both buyers see AVAILABLE
-- app: if status == 'AVAILABLE' ...
UPDATE event_seats SET status = 'HELD', held_by = :buyer
 WHERE event_id = 77 AND seat_id = 'B-4-17';                                  -- both succeed; last write wins
```

<ThreadTimelineSim scenario="check-then-act" />

"It's in a transaction" does not save you. MySQL InnoDB defaults to **REPEATABLE READ** and Postgres to READ COMMITTED. Neither stops a plain read followed by an unconditional write. (Postgres REPEATABLE READ would abort the second writer. InnoDB's would not.) The isolation chapter later in this part shows exactly what each level prevents. The fix in this lesson is not "raise the isolation level". It is to **close the gap**: make the check and the change one indivisible step, or make sure only one actor can be in the gap at a time.

**Three questions to ask of any contended resource:**

1. **What exactly is scarce?** One seat, a count of units, one job run, a balance. This sets the **lock granularity**: lock the *seat*, not the *event*; the *account*, not the *whole ledger*. Coarser locks mean more waiting for no extra safety.
2. **Where does the truth live?** One row in one database is the easy case. Truth split across services is the hard case.
3. **How long is the critical section?** One statement (microseconds), one transaction (milliseconds), or minutes of human checkout? The longer it is, the less you can hold a lock across it, and the more you need holds with expiry.

**Worked numbers: the shape of an on-sale.** Assumptions for this example: 2,000,000 people arrive within 2 minutes of opening; 50,000 seats; an average order of 2 seats.

- Winning orders: 50,000 ÷ 2 = **25,000**. Success rate: 25,000 ÷ 2,000,000 = **1.25%**.
- Arrival rate: 2,000,000 ÷ 120 s ≈ **16,700 people per second**. If all of them try to hold seats directly, that is about 16,700 contended writes per second against one database.
- Contention concentrates: if 30% of attempts want the 500 best seats, that is about **5,000 attempts per second** on 500 rows. Those seats are gone within the first second. The rest are losers.

**98.75% of the work is telling people "no".** Design so "no" is cheap, fast and honest. That sentence shapes every box in the Ticketmaster walkthrough.

**Catch the trap:** solving contention before naming the resource. "We'll use a distributed lock" on what? A lock on the whole event pushes two million people through one door. Say the granularity first.

<h2 id="atomic">One statement</h2>

**Start here, not with locks.** The cheapest correct answer is usually a **conditional write**: one statement that checks and changes in one atomic step. InnoDB takes an exclusive row lock for the length of that statement. A second writer waits for the lock, then **re-checks the condition against the newly committed row**.

```sql
UPDATE event_seats
   SET status = 'HELD', held_by = :hold_id, held_until = NOW(3) + INTERVAL 10 MINUTE
 WHERE event_id = :event AND seat_id = :seat
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < NOW(3)));
-- ROW_COUNT() = 1 -> you won.  ROW_COUNT() = 0 -> someone beat you.  No lock objects anywhere.
```

The shortest form interviewers like is `UPDATE seats SET held_by = ? WHERE id = ? AND held_by IS NULL`. **The row count is the answer.** Your code never reads and then decides. It asks the database to decide and reports what happened.

Two MySQL details matter here:

- **Affected rows means changed rows.** By default MySQL reports rows whose values actually changed, not rows that matched. Here the statement always changes a matched row (status goes to `HELD`), so 1 or 0 is reliable. If an UPDATE could set a column to the value it already has, a matched row would report 0. Drivers have a "found rows" flag (`CLIENT_FOUND_ROWS`) that switches to counting matches; PyMySQL and MySQL Connector/Python leave it off by default, and with it on a no-op UPDATE reports 1. Check what your driver does before relying on the count.
- **Use the database's clock** (`NOW(3)`), not the application server's. App servers drift apart. One clock gives one answer to "has this hold expired?".

**Several seats at once, all or nothing.** A buyer picks four seats together. Hold them in one statement and compare the count:

```sql
START TRANSACTION;
UPDATE event_seats
   SET status = 'HELD', held_by = :hold_id, held_until = NOW(3) + INTERVAL 10 MINUTE
 WHERE event_id = :event AND seat_id IN (:s1, :s2, :s3, :s4)
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < NOW(3)));
-- app: if ROW_COUNT() <> 4 -> ROLLBACK (someone took one of them), else COMMIT
COMMIT;
```

The rollback releases the seats you did get, so a buyer never ends up with three of four. Two multi-seat holds can still lock rows in different orders and deadlock. InnoDB detects this and aborts one transaction with error 1213. Treat that exactly like a lost race: retry once or report "seats taken". Sorting seat ids before locking removes most of them.

**Counts work the same way.** For interchangeable units (5,000 general-admission tickets, stock of a product, remaining uses of a coupon):

```sql
UPDATE inventory SET remaining = remaining - :qty
 WHERE sku = :sku AND remaining >= :qty;     -- 0 rows -> sold out, or not enough left
```

`remaining = remaining - :qty` is a relative update done inside the database, so it never loses another session's change. The app-side version, `SELECT remaining` then `UPDATE SET remaining = :computed`, is the lost update. As a safety net, an unsigned column or a `CHECK (remaining >= 0)` constraint (enforced from MySQL 8.0.16) makes a bug fail loudly instead of overselling.

**A unique key is a lock the database never forgets to take.** When the rule is "at most one of these", let an index say no:

| Rule | MySQL constraint |
|---|---|
| One redemption of a coupon per user | `UNIQUE (coupon_id, user_id)` on redemptions |
| One live booking per seat per event | `UNIQUE (event_id, seat_id)` on tickets. To allow re-booking after a cancel, add a generated column `live_seat VARCHAR(16) AS (IF(status = 'CANCELLED', NULL, seat_id))` and put `UNIQUE (event_id, live_seat)` on it. A unique index allows many NULLs, so cancelled rows never collide. MySQL has no partial indexes, so this is the usual substitute |
| One run of a cron job per scheduled minute | `UNIQUE (job_id, scheduled_at)` on job runs |
| One effect per idempotency key | `PRIMARY KEY (client_id, idem_key)` |
| No overlapping stays on a listing | MySQL has no exclusion constraint (Postgres does: `EXCLUDE USING gist`). Use one row per `(listing_id, night)` with a unique key, see the Airbnb section later |

```sql
INSERT INTO coupon_redemptions (coupon_id, user_id) VALUES (:coupon, :user);
-- second attempt fails with error 1062 (ER_DUP_ENTRY): atomically, under any concurrency.

-- Variant that does not raise: a harmless no-op update on conflict.
INSERT INTO coupon_redemptions (coupon_id, user_id) VALUES (:coupon, :user)
  ON DUPLICATE KEY UPDATE coupon_id = coupon_id;
-- ROW_COUNT() = 1 -> inserted (you are first).  0 -> a row already existed.
```

Prefer this over `INSERT IGNORE`. `IGNORE` downgrades many other errors (bad data, truncation) to warnings too, and you want those to fail loudly.

Constraints shine where row locks cannot help: **the rule is about absence** ("no booking exists yet"), and there is no row to lock until someone creates it. Redis has the same idea: `SET key value NX` (set only if absent), and a Lua script that checks and decrements in one step. The <a href={`${BASE}sd/lessons/rate-limiter/`}>rate limiter lesson</a> uses exactly this.

**In-memory analogy.** A compare-and-set (CAS) on a number is the same move as a conditional UPDATE: "change it only if it still has the value I saw". Watch two threads do it with no lock, one retrying after a failed CAS.

<Reveal q="The conditional UPDATE runs under REPEATABLE READ. Why can't two buyers both get 1 row updated?">

Because an `UPDATE` does not use the snapshot the transaction started with. It is a **current read**: it locks the newest committed version of each row it touches. The first writer locks the row and the second waits. When the first commits, the second's `WHERE` is evaluated against the newly committed row. `status` is now `HELD` with a future `held_until`, so the condition is false and zero rows change. The check and the change are atomic because the database does both under one row lock. (Postgres gets the same result at READ COMMITTED by re-evaluating the `WHERE` against the new row version.)

</Reveal>

**Catch the trap:** reading the seat, checking it in application code, then writing an unconditional `UPDATE`, even inside a transaction. A transaction gives you atomic commit, not a guard. Put the condition in the `WHERE`.

<h2 id="db-locks">Lock it, or bet on it</h2>

Sometimes the decision needs logic one statement cannot express. Example rule: "no more than six tickets per account per event, counted across every order the account has made." You now have two families of tools. The <a href={`${BASE}sd/lessons/databases/#concurrency-control`}>Databases lesson, Chapter 8</a> builds both on a small example. Here is when each wins under contention.

**Pessimistic: lock first, then decide.** `SELECT ... FOR UPDATE` locks the rows it reads until the transaction ends. Other writers, and other locking reads, wait.

```sql
START TRANSACTION;
SELECT tickets_bought FROM account_event_limits
 WHERE account_id = :acct AND event_id = :event FOR UPDATE;   -- other orders for this account wait here
-- app: if tickets_bought + 4 > 6 -> ROLLBACK, "limit reached"
UPDATE event_seats SET status = 'HELD', held_by = :hold_id, held_until = NOW(3) + INTERVAL 10 MINUTE
 WHERE event_id = :event AND seat_id IN (:s1, :s2, :s3, :s4)
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < NOW(3)));   -- need ROW_COUNT() = 4
UPDATE account_event_limits SET tickets_bought = tickets_bought + 4
 WHERE account_id = :acct AND event_id = :event;
COMMIT;
```

Look at the granularity. The lock is on **this account's** counter for this event, not on the event. Two different fans never wait for each other.

The counter row must exist before anyone locks it. Create it first with `INSERT ... ON DUPLICATE KEY UPDATE account_id = account_id`. Do not rely on `FOR UPDATE` against a missing row: under InnoDB's default REPEATABLE READ it takes a **gap lock**, and two sessions can both hold a gap lock on the same empty spot. Each then tries to insert, each waits for the other's gap lock, and InnoDB aborts one with a deadlock. This is a classic MySQL surprise.

**Two variants worth naming (MySQL 8.0 and later):**

- **`SKIP LOCKED`**: when the caller wants *any* row from a pool (general admission, the next job in a queue table, any free bed), skip rows others have locked and take the next unlocked one. Two buyers get two different rows instead of one waiting for the other.
- **`NOWAIT`**: fail at once (error 3572) instead of queueing. Good when waiting is worse than "try again".

```sql
START TRANSACTION;
SELECT ticket_id FROM ga_tickets
 WHERE event_id = :event AND status = 'AVAILABLE'
 ORDER BY ticket_id LIMIT 1
   FOR UPDATE SKIP LOCKED;          -- session 1 gets id 1, session 2 skips it and gets id 2
UPDATE ga_tickets SET status = 'HELD', held_by = :hold_id, held_until = NOW(3) + INTERVAL 10 MINUTE
 WHERE ticket_id = :id_from_select;
COMMIT;                              -- locks are released at COMMIT, not before
```

Two cautions. First, **give the locking read an index** such as `(event_id, status, ticket_id)`. Without one, InnoDB scans and locks every row it examines, and your "skip locked" query locks half the table. Second, SKIP LOCKED returns an inconsistent view on purpose: it is right for "give me any free row" and wrong for "give me an exact count".

**Optimistic: read freely, write only if nothing changed.** Add a version column and make the write a compare-and-set:

```sql
SELECT description, version FROM events WHERE id = :event;       -- version = 7
-- ...ten minutes in the organiser's edit form...
UPDATE events SET description = :new, version = version + 1
 WHERE id = :event AND version = 7;                               -- ROW_COUNT() = 0 -> someone saved first; reload
```

No lock is held while the human thinks. The loser finds out at write time and redoes its work. (JPA's `@Version` generates exactly this `WHERE`.) Because `version = version + 1` always changes the row, the affected-rows count is reliable whichever way your driver counts.

Try the three strategies side by side below. Two writers sell one item from the same row. With "no version check" you will see the lost update. With the version check, the loser gets 0 rows and retries. With `FOR UPDATE`, the second writer just waits.

**Optimistic vs pessimistic: the exact difference.**

| | Pessimistic (`FOR UPDATE`) | Optimistic (version column) |
|---|---|---|
| Assumption | Conflicts are likely | Conflicts are rare |
| When the conflict is detected | Before you work: you wait for the lock | At write time: 0 rows updated |
| What the loser does | Waits (or gets a timeout / deadlock error) | Redoes its work, usually in a retry loop |
| Held across user think time? | Never: a row lock held for minutes blocks everyone | Yes: nothing is held |
| Cost with no conflict | A lock held for the transaction | Nothing extra |
| Cost on a hot row | Queue behind the lock; ceiling = 1 ÷ lock time | Retry storm; grows with the square of contenders |
| Best fit | Short decisions across several rows | Edit forms, profiles, low contention |

**Worked numbers: what each bet costs on a hot row.**

- **Pessimistic ceiling = 1 ÷ lock time.** Hold a seat row for 2 ms and it serialises at most 1 ÷ 0.002 = **500 changes per second**. Call the payment provider (300 ms) while holding it and the ceiling collapses to 1 ÷ 0.3 ≈ **3 per second**. Never hold a lock across a network call to someone else.
- **Optimistic under contention is quadratic.** If N writers hit one row together and every loser retries at once, round 1 has N attempts, round 2 has N − 1, and so on: N(N + 1) ÷ 2 attempts for N successful writes. For N = 100 that is **5,050 attempts** to do 100 writes. Add exponential backoff with jitter and a retry cap, or do not use optimistic locking on hot rows.

**Summary of all four tools:**

| | Atomic statement | Unique constraint | Pessimistic (`FOR UPDATE`) | Optimistic (version) |
|---|---|---|---|---|
| Critical section | One statement | One insert | A short transaction with app logic | Anything, including human think time |
| Cost on conflict | Loser gets 0 rows instantly | Loser gets error 1062 | Loser waits | Loser redoes its work |
| Danger | Cannot express multi-row logic | Only "at most one" rules | Lock waits, deadlocks, locks across slow calls | Retry storms on hot rows |
| Fits | Seat holds, stock decrements | Redemptions, idempotency keys, one-per-X rules | Limits across rows, short contended decisions | Edit forms, profiles, rare conflicts |

**Lock hygiene.** Hold row locks for milliseconds. Never hold them across human think time or a call to another service. Lock rows in a consistent order (by id) so transactions cannot deadlock. Lock the smallest thing that is actually scarce. Always be ready for errors **1213** (deadlock: the whole transaction was rolled back, retry it) and **1205** (lock wait timeout: by default only the statement is rolled back, so you decide whether to roll back the transaction).

<h2 id="isolation">What isolation levels prevent</h2>

An **isolation level** sets what one transaction can see of another's work while both are running. A weaker level is faster and allows more strange outcomes. These strange outcomes have names:

- **Dirty read**: you read data another transaction has not committed yet (and it may roll back).
- **Non-repeatable read**: you read a row twice in one transaction and get different values, because someone committed in between.
- **Phantom**: you run the same range query twice and get different sets of rows.
- **Lost update**: two transactions read a value, both compute a new one in the application, both write. One write silently wipes the other.
- **Write skew**: two transactions each read overlapping data, each writes a *different* row, and together they break a rule neither broke alone. Example: two doctors on call both check "at least one other doctor is on call" and both go off call.

**InnoDB's four levels.** The default is REPEATABLE READ. A plain `SELECT` reads from a **snapshot** taken at the transaction's first read. Statements that write or lock (`UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`, `FOR SHARE`) are **current reads**: they see and lock the newest committed rows. This difference explains most surprises.

| Level (MySQL name) | Dirty read | Non-repeatable read | Phantom on plain SELECT | Lost update (read in app, then write) | Write skew |
|---|---|---|---|---|---|
| READ UNCOMMITTED | possible | possible | possible | possible | possible |
| READ COMMITTED | prevented | possible (each statement gets a fresh snapshot) | possible | possible | possible |
| REPEATABLE READ (default) | prevented | prevented (one snapshot per transaction) | prevented for plain reads; locking reads and writes use next-key locks | **possible** | possible |
| SERIALIZABLE | prevented | prevented | prevented | prevented in effect (turns into a deadlock error instead) | prevented, by locking |

Read the "lost update" column carefully. The classic read-modify-write is possible at **every** level except SERIALIZABLE, and in SERIALIZABLE it appears as an aborted transaction, not as a quiet success. This is why raising the isolation level is not the fix in this lesson.

**What InnoDB actually does:**

- **READ COMMITTED**: each plain SELECT sees the latest committed data. Gap locks are mostly off, so locking reads lock only the matching index records. Fewer deadlocks, but phantoms are possible. Many large MySQL shops choose it deliberately for contended workloads.
- **REPEATABLE READ**: one snapshot per transaction for plain SELECTs. Locking reads and range updates take **next-key locks** (a record lock plus a gap lock before it), which blocks other sessions from inserting into the scanned range. That is how InnoDB prevents phantoms for locking statements.
- **SERIALIZABLE**: with autocommit off, InnoDB turns every plain SELECT into `SELECT ... FOR SHARE`. Two transactions that both read a row and then both try to update it each hold a shared lock the other needs to upgrade. InnoDB detects the cycle and aborts one with error 1213.

**Two REPEATABLE READ surprises worth knowing:**

1. **Snapshot versus current read.** Your plain SELECT shows 10, someone commits 9, you still see 10. Your own `UPDATE ... SET qty = qty - 1` then reads the current 9 and writes 8. Mixing the two in one transaction gives results neither read alone would predict.
2. **Duplicate-key and the invisible row.** Your INSERT fails with 1062 because someone else just committed that key. A plain SELECT in your same transaction may **not** see their row, because it is newer than your snapshot. To read the existing row, use a current read (`SELECT ... FOR UPDATE` or `FOR SHARE`), or run the claim as its own autocommit statement.

```sql
-- Session A                                 -- Session B
START TRANSACTION;
SELECT qty FROM stock WHERE id = 1;          -- 10
                                             UPDATE stock SET qty = 9 WHERE id = 1; COMMIT;
SELECT qty FROM stock WHERE id = 1;          -- still 10 (snapshot)
UPDATE stock SET qty = qty - 1 WHERE id = 1; -- current read: 9 - 1 = 8
SELECT qty FROM stock WHERE id = 1;          -- 8
COMMIT;
```

**What each tool needs.**

| Problem | Not solved by | Solved by |
|---|---|---|
| Lost update on one row | REPEATABLE READ | Relative update (`qty = qty - 1`), conditional `WHERE`, version column, or `FOR UPDATE` |
| Write skew across rows | REPEATABLE READ | Lock a common parent row (`FOR UPDATE` on the account/event), a constraint that encodes the rule, or SERIALIZABLE with retries |
| "At most one" with no row yet | `FOR UPDATE` on a missing row (gap-lock deadlocks) | A unique key |
| Phantom insert into a range you checked | READ COMMITTED | Locking read at REPEATABLE READ (next-key locks), or a unique key on the thing you are protecting |

**The recommendation for this lesson (a design choice, not a law):** keep the default isolation level, and make every contended rule explicit: a conditional write, a unique key, a brief `FOR UPDATE` on the smallest scarce row, or a version column. Use SERIALIZABLE only when the invariant spans too many rows for those, and then wrap the transaction in a retry loop for error 1213.

<h2 id="distributed-locks">Leases and fencing</h2>

Here is a realistic failure. A nightly payout job takes a Redis lock with a 30-second TTL so only one worker pays organisers. Worker 1 hits a 40-second garbage-collection pause. The lock expires. Worker 2 takes it and starts paying. Worker 1 wakes up, still believing it holds the lock, and finishes its payouts too. Every organiser is paid twice.

The question to answer is: **who is allowed to stop a holder that does not know it has lost?**

**When you need a distributed lock at all.** The critical section spans more than one database statement *and* more than one system (call a third party, then write two stores), or the resource is not a database row (a file, a printer, a job). Inside one database, prefer Part One's tools. They release automatically on commit or crash.

**The Redis lock, done properly.**

```text
# acquire: set only if absent (NX), with a 30 s expiry (PX), value = random token
SET lock:payout-2026-10-08 9f2c71aa NX PX 30000
# -> OK means you hold it for 30 s.  (nil) means someone else does.
```

```lua
-- release: delete only if the value is still MY token. Must be one atomic script.
-- KEYS[1] = lock key, ARGV[1] = my token
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

- **`NX`**: set only if absent, so the acquire is atomic.
- **`PX 30000`**: the TTL. A crashed holder must not wedge the system forever, so every distributed lock is really a **lease**: a lock that expires on its own.
- **The random token**: so a holder whose lease expired cannot delete the *next* holder's lock with a plain `DEL`.

**Two conversations interviewers want.**

**1 · Expiry versus the slow holder.** A lease protects you from a *dead* holder by assuming that after the TTL the holder has stopped. But a process can pause for any length of time (a GC pause, a VM migration, a swapped page, a slow network) and resume *without knowing time passed*. Checking "do I still hold it?" right before the write does not help: the pause can land between the check and the write. A longer TTL only moves the window.

**The fix is a fencing token.** The lock service hands out a number that increases with every grant: 33, then 34. The holder sends its number with every write. **The protected resource remembers the highest number it has seen and rejects anything lower.** A zombie holder with 33 is refused once 34 has written. This moves the guarantee from "the holder behaves" to "the storage checks", and storage, unlike a paused process, is awake.

In MySQL the fence is one more condition, and the row count tells the worker whether it was accepted:

```sql
UPDATE payouts
   SET status = 'PAID', paid_at = NOW(3), fence = :token
 WHERE id = :id AND fence <= :token;     -- <= so the CURRENT holder may write more than once
-- ROW_COUNT() = 0 -> a newer holder has written: stop, you are a zombie
```

A plain Redis `SET ... NX` has no counter to give you. You can keep one with `INCR` next to the lock, but the honest answer is that **a fencing token only works if the resource checks it**. Without fencing, a TTL lock is advisory, not safe. Saying that sentence is a strong signal in an interview.

**2 · Where does the lock live, and what if it fails?** A single Redis primary with asynchronous replication can fail over and lose a just-granted lock, so two clients both hold it. **Redlock** (acquire the lock on a majority of N independent Redis nodes, for example 3 of 5, within a time well under the TTL) was proposed for this. **Its safety is debated.** Martin Kleppmann argued it depends on timing assumptions (bounded pauses, network delay, clock drift) and provides no fencing token. Salvatore Sanfilippo (antirez) replied that the assumptions are reasonable in practice. You do not need to settle the debate in an interview. Say:

> "For **efficiency** (avoiding duplicate work where a rare double is harmless) a single Redis lock is fine. For **correctness** (money, inventory) I won't rely on any lock alone. I'd use a consensus-backed lock service that gives me a fencing token and make the write check it, or skip the lock and use a conditional write in the database."

**Consensus-backed locks** (the "design a lock service like Chubby" question). Google's Chubby, Apache ZooKeeper and etcd run a consensus protocol (Paxos, Zab, Raft) across an odd number of replicas, so a lock grant survives the loss of a minority of machines and two clients cannot both be granted it. They pair locks with **sessions or leases** kept alive by heartbeats, and they expose an increasing number you can use as a fence: Chubby calls it a **sequencer**; in ZooKeeper the zxid of the lock node serves; etcd keys carry revisions. The <a href={`${BASE}sd/lessons/core-concepts/#liveness`}>Core concepts lesson, Chapter 6</a> covers heartbeats, leases and majority voting from first principles.

**MySQL also has locks you can use as a lease.** `GET_LOCK('name', timeout)` is a named advisory lock tied to one database connection, released when the connection ends. It is handy for "only one worker runs this cron" on a single MySQL server. It does not survive failover to a replica and it has no fencing token, so treat it like the Redis lock: fine for efficiency, not for correctness.

| Lock | Survives | Gives a fence | Use for |
|---|---|---|---|
| DB row lock / conditional write | Anything the database survives | The row version, if you add one | Default whenever the truth is one database |
| MySQL `GET_LOCK` | Holder crash (connection drops) | No | Efficiency on one server: dedupe a cron |
| Redis `SET NX PX` + token | Holder crash (TTL); not failover or long pauses | No (add an `INCR` counter) | Efficiency: dedupe work, throttle a cron |
| Redlock | Some node failures, under timing assumptions | No | Debated; name the debate |
| ZooKeeper / etcd / Chubby | A minority of replicas failing | Yes (zxid, revision, sequencer) | Correctness across services, leader election |

A small Python sketch of the safe use of a Redis lease. The important part is the last two lines: the write itself is guarded, not the process.

```python
token = uuid4().hex
if not r.set("lock:payout", token, nx=True, px=30_000):
    return                                   # someone else is paying
fence = r.incr("fence:payout")               # increasing number for this grant (see caveat)
try:
    pay_organisers(fence)                    # every write ends with: WHERE fence <= :fence
finally:
    r.eval(RELEASE_LUA, 1, "lock:payout", token)   # release only if the token is still mine
# Caveat: INCR and SET are two commands. Do both in one Lua script, and remember that after a Redis
# failover the counter may go backwards. A consensus store gives you a fence that cannot.
```

<Reveal q="The interviewer: “Why not just make the TTL ten minutes so pauses can’t outlast it?”">

No pause bound is guaranteed. Long GC pauses, VM live migration and network partitions have all lasted longer than anyone planned. A long TTL also makes every real crash expensive: a dead holder now blocks the resource for ten minutes. The TTL trades availability against safety without ever giving you safety. Fencing gives you safety at any TTL, so you can keep the TTL short.

</Reveal>

**Catch the trap:** "Redis lock with a TTL, so it's safe." It is safe against crashes and unsafe against pauses. Add: *"...and every write carries the fencing token, which storage checks."*

<h2 id="serialize">One line, one writer</h2>

The most robust way to avoid fighting over a resource is to **stop sharing it**. Route every change for one key to one writer, which applies them in order. No locks, no retries: contention becomes a queue.

- **Partitioned log.** Put requests on a Kafka topic keyed by the resource id (seat block, account, symbol). Every request for one key lands in one partition and is consumed by one consumer, in order. Scale by spreading keys across partitions. See <a href={`${BASE}sd/lessons/queues-streams/#ordering`}>Queues & streams, Chapter 7</a> for ordering per key.
- **Single-threaded owner.** An in-memory, single-threaded process owns each key and applies changes one at a time. This is the actor model, and it is also Redis itself: commands on one node run one at a time, which is why a Lua script is atomic.
- **The limit case: a stock exchange.** Every order for one symbol touches the same order book, and fairness demands a strict order. Exchanges avoid locking: a **sequencer** stamps each order with a total order, and a **single-threaded in-memory matching engine per symbol** applies them, journaling the input so state can be rebuilt by replay. Martin Fowler's write-up of the LMAX architecture is the classic public description.

| | Locks / conditional writes | Serialise through one writer |
|---|---|---|
| Latency | Immediate answer | A queue hop; the answer comes asynchronously unless the caller waits |
| Throughput on one hot key | Bounded by lock time | Bounded by one thread, but no lock overhead, often far higher |
| Failure | Database handles it | You must handle owner failover (replay the log; fence the old owner) |
| Fits | Most product systems | Exchanges, per-account ledgers, very hot keys, ordered workflows |

<Figure caption="Serialising. All requests for one key go to one partition and one consumer, so changes to that key never race.">
  <Mermaid code={`flowchart LR
    R1["Request seat 17"] --> P["Partition by key\nhash(seat block)"]
    R2["Request seat 17"] --> P
    R3["Request seat 90"] --> P
    P --> C1["Consumer 1\nowns keys A..M\none at a time"]
    P --> C2["Consumer 2\nowns keys N..Z\none at a time"]
    C1 --> DB[("Seats DB")]
    C2 --> DB`} />
</Figure>

**Catch the trap:** "put it on a queue" as a contention fix for something the user is waiting on. If the buyer needs "you got the seat" now, a queue only moves the wait. Say how the answer gets back (the caller polls or waits on a reply), and keep the per-key consumer fast.

<h2 id="holds">Held, not sold</h2>

A real checkout takes minutes: pick two seats, type a card number, wait for a bank verification screen, enter a one-time code, pay. You cannot lock a row for four minutes. But you cannot let someone else buy those seats while the first person types.

The answer is a **hold** (or reservation). It separates "this is mine for now" from "this is mine". The seat moves through a small **state machine**, and every transition is a conditional write.

<Figure caption="The seat state machine. Every arrow is one conditional UPDATE; the words after the comma are its WHERE clause.">
  <Mermaid code={`stateDiagram-v2
    [*] --> AVAILABLE
    AVAILABLE --> HELD: hold, if AVAILABLE
    HELD --> HELD: re-hold by another buyer, old hold expired
    HELD --> BOOKED: confirm, my hold still live
    HELD --> AVAILABLE: release or sweeper, hold expired
    BOOKED --> AVAILABLE: refund or cancel
    BOOKED --> [*]`} />
</Figure>

The three statements, in MySQL:

```sql
-- 1. HOLD (shown earlier): AVAILABLE, or HELD with an expired hold, becomes HELD
-- 2. CONFIRM: only my live hold becomes BOOKED
UPDATE event_seats
   SET status = 'BOOKED', booking_id = :booking, held_until = NULL
 WHERE event_id = :event AND seat_id IN (:s1, :s2)
   AND status = 'HELD' AND held_by = :hold_id AND held_until > NOW(3);
-- need ROW_COUNT() = 2, else ROLLBACK and void the card authorisation

-- 3. SWEEPER (tidy only, batched so it never holds many locks at once)
UPDATE event_seats SET status = 'AVAILABLE', held_by = NULL, held_until = NULL
 WHERE status = 'HELD' AND held_until < NOW(3)
 LIMIT 1000;
-- index (status, held_until) keeps this from scanning the table; repeat until ROW_COUNT() = 0
```

**Three design rules.**

1. **Correctness never waits for a sweeper.** The hold statement treats an expired hold as available (`held_until < NOW(3)` in its `WHERE`) and the confirm statement requires a live one (`held_until > NOW(3)`). The sweeper flips expired holds back to `AVAILABLE` every few seconds, but only to keep the seat map accurate and notify the waitlist. If it falls behind, nobody is double-sold. (Same idea as Pastebin's read-path expiry check in the delivery-framework lesson.)
2. **Never charge for a seat you can't confirm.** Card payments separate **authorisation** (the bank reserves the funds) from **capture** (the money moves). Authorise, then confirm the seats with the conditional `HELD → BOOKED` update, then capture. If confirm finds the hold gone, **void** the authorisation: no money moved, nothing to refund.
3. **The server's clock is longer than the buyer's.** Show the buyer 10 minutes. Expire the hold server-side at 10 minutes plus a grace (say 2 minutes), and refuse to *start* a checkout in the last minute. A payment that completes at 9:59 on the buyer's timer always finds its hold alive.

<Figure caption="Authorise, confirm, capture. Money moves only after the seat is secured; a lapsed hold ends in a void, not a refund.">
  <Mermaid code={`sequenceDiagram
    participant B as Buyer
    participant K as Booking service
    participant P as Payment service
    participant D as MySQL
    B->>K: checkout (hold h1, Idempotency-Key)
    K->>P: authorise card
    P-->>K: authorised
    K->>D: UPDATE HELD to BOOKED where hold h1 live
    alt row count = seats
        K->>P: capture
        P-->>K: captured
        K-->>B: booked
    else hold already lapsed
        K->>P: void authorisation
        K-->>B: seats no longer available
    end`} />
</Figure>

**Worked numbers: what a hold TTL costs.** Assumptions for this example: the waiting room (next chapter) admits 100 buyers per second; each holds 2 seats; 20% abandon without paying; TTL 10 minutes.

- Seats held per second: 100 × 2 = **200**. All 50,000 seats are held after 50,000 ÷ 200 = **250 s**, about four minutes. The site says "sold out".
- But 20% of those holds belong to people who walked away: 0.2 × 50,000 = **10,000 seats**. Holds made between 0 and 250 s expire between **600 s and 850 s**, and those seats come back on sale.
- So "sold out" at four minutes really meant **"all held"**. Keep the waiting room open (with an honest message) until holds settle, and offer returning seats to the people still in line.
- The TTL is a dial. A 5-minute TTL brings the 10,000 seats back between 300 s and 550 s, but buyers fumbling bank verification lose their seats more often. Pick it from checkout-duration data, for example "p95 checkout is 4 minutes, so 10 minutes holds".

| TTL | Abandoned seats return | Risk |
|---|---|---|
| Short (3–5 min) | Fast; less false "sold out" | Real buyers time out during bank verification |
| Long (15+ min) | Slowly; long false "sold out" | Scalpers and bots hoard seats cheaply; cap holds per account |
| 10 min + server grace | Balanced; tune from p95 checkout time | Must still handle the late-payment race (rule 2) |

<Reveal q="Should holds live in Redis (with key TTLs) instead of the database?">

You can. A Redis key per seat, `SET seat:B-4-17 hold-9 NX EX 600`, is a hold that expires on its own, and it absorbs a big read/write burst. But now there are two sources of truth: Redis says who holds the seat, the database says who bought it. You must make the confirm step check Redis atomically with the database write, and decide what happens when Redis fails over and loses a hold. For most on-sales the database can carry the hold writes **because the waiting room meters them** (a few hundred per second), so keep holds in the database and use Redis for the seat-map cache and the queue. Say the condition that flips it: hold traffic beyond what one primary can take even after metering. Then Redis (or sharded inventory) becomes the hot path, with the database confirming.

</Reveal>

**Catch the trap:** "the seat is released when the hold expires". Released by whom? If the answer is "a cron job", the interviewer asks what happens when it falls behind. Put the expiry in the `WHERE`.

<h2 id="waiting-room">Two million at the door</h2>

If you replay the first minute of an on-sale, the hold endpoint is not the first thing to fail. The seat map is: two million browsers refreshing it every couple of seconds is a million requests a second for a picture of seats that are already gone. The contention was only the part of the crowd that reached the database. This is a crowd problem first.

**A virtual waiting room** puts a queue in front of the purchase flow. Everybody who arrives gets a place in line. The system **admits** people into the seat map and checkout at a controlled rate. Inside, contention is back to manageable per-seat conditional writes and short holds.

**How it works, mechanically:**

1. **Join.** On arrival the user gets a position from an atomic counter (`INCR queue:event-77` in Redis). The server returns a **signed token** carrying the event, the position and an issue time. Nothing else is stored per user.
2. **Fairness at opening.** Everyone who arrived *before* the on-sale starts has equal claim. A counter would reward whoever's clock and network were fastest. A common choice: randomise positions among early arrivals, then first-come-first-served for everyone after. Say which you chose and why.
3. **Wait.** The client polls for the single global number **"now serving"**, which an admission controller advances at the admission rate (for example +100 every second). Because that number is the same for every user, the poll response is cacheable at the CDN for a second. Two million pollers cost the origin almost nothing.
4. **Admit.** When `position ≤ now serving`, the server exchanges the queue token for a short-lived signed **admission token**. The API gateway checks that signature (no database lookup) on every seat-map, hold and checkout request. Without it, you get the waiting room.
5. **Sell out honestly.** Show the estimated wait and the tickets remaining. When everything is held, say so, and keep the line alive, because abandoned holds come back (see the holds chapter).

<Figure caption="The waiting room meters the crowd. Only admitted users reach the seat map and the hold path, so the database sees hundreds of writes a second, not tens of thousands.">
  <Mermaid code={`flowchart LR
    U["2M fans"] -->|"join"| Q["Waiting room\nINCR position, signed token"]
    U -.->|"poll now-serving\nCDN-cached 1 s"| CDN["CDN edge"]
    AC["Admission controller\n+100 per second"] --> CDN
    Q -->|"admission token"| GW["API gateway\nverifies signature"]
    GW --> MAP["Seat map\ncached per section"]
    GW --> HOLD["Hold service\nconditional UPDATE"]
    HOLD --> DB[("Seats DB")]`} />
</Figure>

**Worked numbers.** Assumptions from the prologue (2,000,000 people in 2 minutes, 25,000 winning orders), plus: admission 100 users/s; an admitted user spends about 4 minutes in the flow; pollers poll every 10 s; seat-map viewers refresh every 2 s.

- **Waiting-room polls:** 2,000,000 ÷ 10 s = **200,000 requests/s**. But every one asks for the same number, so the CDN answers them. Origin load: about one request per second per edge location.
- **Inside the room (Little's law: concurrent = rate × time):** 100 × 240 s = **24,000** shoppers.
- **Seat-map reads:** without the room, 2,000,000 ÷ 2 s = **1,000,000 reads/s**. With it, 24,000 ÷ 2 s = **12,000 reads/s**, served from a per-section cache with a 1-second TTL. With 100 sections, the database sees about **100 reads/s**. The map can be a second stale because the hold is the truth.
- **Hold writes:** about 100 per second, two orders of magnitude below the 16,700/s of an unmetered crowd and far below the 500/s ceiling of any one hot row.
- **Wait estimate:** position ÷ admission rate. Position 30,000 waits 30,000 ÷ 100 = **300 s**. With 25,000 winning orders, people past roughly the 30,000–40,000 mark are likely to get nothing (some admitted users abandon, so it is not exactly 25,000). Tell them early.

**Choosing the admission rate.** It is a capacity dial, not a fairness one. Set it so admitted users can actually complete checkout (the hold path, the payment provider's rate limits, the seat-map cache) with headroom. Admitting faster than seats are released only adds people who will see "taken".

| Without a waiting room | With one |
|---|---|
| 16,700 hold attempts/s; most fail; DB hot | ~100 holds/s; most succeed |
| 1M seat-map reads/s | ~12K/s, cache-served |
| Refresh-button lottery; bots win | An explicit, explainable order |
| "Sold out" with no information | Position, wait estimate, tickets left |

<Trace title="Meter the crowd" steps={crowd} takeaway="Wait ≈ position ÷ admission rate. Make the poll a shared, cacheable number; put the per-user state in a signed token." />

<Reveal q="Bots join the queue a thousand times each. What does the design do?">

The waiting room makes bots cheaper to see, not impossible. Require a logged-in, verified account to join (one position per account), rate-limit joins per IP and device, put a challenge in front of the join, and cap tickets per account at the hold step (the per-account counter from the locks chapter). The admission token is bound to the account, so a bot cannot share one position with a thousand clients. Full bot defence is its own design; name these layers and move on.

</Reveal>

**Catch the trap:** "we'll autoscale the booking service." Autoscaling adds web servers. The contended rows, the payment provider's limits and the database primary do not autoscale. The waiting room protects the parts that cannot grow.

<h2 id="idempotency">Idempotency keys</h2>

Take a customer tapping *Pay*. The request reaches your server, the server charges the card, and the response is lost (a phone going through a tunnel). The banking app waits ten seconds and retries. The server sees a brand-new request and charges again. The server was correct both times: it was asked twice.

An operation is **idempotent** when doing it twice has the same effect as doing it once. Networks retry, users double-click, load balancers replay, queues deliver at least once. A retried "charge ₹500" must not charge twice. Some operations are naturally idempotent (`SET status = 'SHIPPED'`, `PUT /profile`, `DELETE photo 7`). Anything that *creates* or *adds* (a charge, an order, `likes + 1`) needs help.

**The idempotency key, end to end.**

<Figure caption="The client's key turns a retry into a replay. The unique key makes the claim atomic; the stored response makes the replay identical.">
  <Mermaid code={`sequenceDiagram
    participant C as Client
    participant P as Payment API
    participant DB as idempotency store
    C->>P: POST /charges, Idempotency-Key a1b2, Rs 500
    P->>DB: INSERT a1b2, hash(request), IN_PROGRESS (unique key)
    DB-->>P: ok, first time
    P->>P: charge the card
    P->>DB: a1b2 becomes COMPLETED, store response
    P-->>C: 200 charged
    Note over C,P: response lost, client retries
    C->>P: POST /charges, Idempotency-Key a1b2, Rs 500
    P->>DB: INSERT a1b2 gives duplicate key
    DB-->>P: existing row, COMPLETED, same hash
    P-->>C: 200 (stored response replayed, no second charge)`} />
</Figure>

**1 · The client generates the key.** One per **logical operation** (when the user taps *Pay*), stored with the pending action and **reused on every retry**. Only the client knows two requests are the same attempt. A fresh key on retry is the most common real bug: the server correctly treats it as a new payment. (A UUID is fine. Scope it per client or account so two customers cannot collide.)

**2 · The server claims the key atomically.** A table with a primary key on `(client_id, idem_key)`:

```sql
CREATE TABLE idempotency_keys (
  client_id     BIGINT        NOT NULL,
  idem_key      VARCHAR(64)   NOT NULL,
  request_hash  BINARY(32)    NOT NULL,     -- SHA-256 of method + path + canonical body
  status        ENUM('IN_PROGRESS','COMPLETED') NOT NULL,
  response_code SMALLINT      NULL,
  response_body JSON          NULL,
  locked_until  DATETIME(3)   NULL,         -- to recover abandoned IN_PROGRESS rows
  created_at    DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (client_id, idem_key),
  KEY idx_created (created_at)              -- for pruning old keys
) ENGINE=InnoDB;

-- the claim: the first request inserts; a concurrent duplicate fails with error 1062
INSERT INTO idempotency_keys (client_id, idem_key, request_hash, status, locked_until)
VALUES (:client, :key, :hash, 'IN_PROGRESS', NOW(3) + INTERVAL 30 SECOND);
```

Never "check if it exists, then insert". Both checks can pass.

**3 · Decide by state and hash.** When the insert fails with 1062, read the existing row with a **current read** (`SELECT ... FOR SHARE`) or in a separate autocommit statement. A plain SELECT inside a REPEATABLE READ transaction can miss a row committed after your snapshot (see the isolation chapter).

| Existing row | Same request hash? | Response |
|---|---|---|
| `COMPLETED` | Yes | **Replay** the stored status and body, byte for byte |
| `COMPLETED` or `IN_PROGRESS` | **No** | **Reject** (`422`): same key with a different payload is a client bug. Never replay (wrong answer) and never execute (double effect) |
| `IN_PROGRESS`, lock still valid | Yes | **`409 Conflict`**: "still processing, retry shortly" |
| `IN_PROGRESS`, `locked_until` passed | Yes | The first attempt died mid-flight: **recover** it (see step 5) |

(The IETF draft Idempotency-Key header spec suggests the same codes (400 for a missing key, 422 for a reused key with a different payload, 409 for a request still in flight); it has expired as a draft, so treat it as a guide. Stripe's API also errors on a reused key with different parameters.)

A Python sketch of the handler. It shows the decision table in code and where the effect and the record meet:

```python
def handle(client_id, key, body, do_charge):
    h = sha256(canonical(body)).digest()
    try:
        db.execute(CLAIM_SQL, (client_id, key, h))              # autocommit: row visible to others at once
    except IntegrityError as e:
        if e.errno != 1062:
            raise
        row = db.query_one(READ_SQL_FOR_SHARE, (client_id, key))  # FOR SHARE: a current read
        if row.request_hash != h:
            return 422, {"error": "key reused with a different request"}
        if row.status == "COMPLETED":
            return row.response_code, row.response_body          # replay
        if row.locked_until > now():
            return 409, {"error": "in progress, retry shortly"}
        return recover(client_id, key, h)                         # stale IN_PROGRESS: see below

    with db.transaction():                                        # effect + completion record: one commit
        result = do_charge(body)                                  # local effect only: orders, ledger rows
        db.execute(COMPLETE_SQL, (200, json(result), client_id, key))
    return 200, result
```

**4 · Make the effect and the record atomic, where you can.** If the operation is local (insert an order, append ledger entries), do it **in the same database transaction** that flips the key to `COMPLETED`. Crash before commit: neither happened, and the retry does the work. Crash after: the retry replays. This is the dedup-table pattern from <a href={`${BASE}sd/lessons/queues-streams/#idempotency`}>Queues & streams, Chapter 5</a>, one hop earlier at the API edge.

**5 · When the effect is outside your database, chain the keys.** You cannot put the card network inside your transaction. So: record the attempt, then call the provider **with your own idempotency key** (derived from the client's, for example `charge:a1b2`), then record the result. If you crash between the call and the record, the recovery path calls the provider **again with the same key**, and the provider dedupes it and returns the original result. Idempotency is only end to end if every hop that can repeat is keyed. Stripe's engineering blog describes this style ("atomic phases" and "recovery points") for exactly this reason.

**6 · Keys expire.** Keep them longer than any client will retry. 24 hours is a common choice (Stripe's API v1 docs say keys can be pruned once they are at least 24 hours old). Delete old rows in batches (`DELETE ... WHERE created_at < ... LIMIT 5000`) or partition by day, so the table does not grow forever. A retry after expiry is a new request, so the client's retry policy must give up before then.

**Retries, the client's half.** Retry only what can succeed next time: timeouts, connection resets, `503`, `429` (honour `Retry-After`), `409` in-progress. Never retry a `400` or "card declined". Use **exponential backoff with full jitter** and a cap, at **one layer** (three layers each retrying three times is 27 attempts), always with **the same key**. The <a href={`${BASE}sd/lessons/core-concepts/#retries`}>Core concepts lesson, Chapter 12</a> has the arithmetic.

**Idempotency key vs unique constraint vs conditional update: the difference.**

| | What it identifies | Who supplies it | Duplicate answer |
|---|---|---|---|
| Idempotency key | One *intent* (one tap of Pay) | The client | Replay the stored response |
| Unique business constraint | One *fact* (a coupon used by a user) | The schema | Error 1062: "already done" |
| Conditional update | One *state transition* (AVAILABLE to HELD) | The WHERE clause | 0 rows: "someone else got there" |

**Worked numbers: the size of the dedup table.** At 10,000,000 payments a day with a 24-hour key retention, about 10 million rows live at once. At roughly 500 bytes each (key, hash, stored response) that is about 5 GB plus index, an ordinary table. Retention, not traffic, sets the size.

<h2 id="exactly-once">Effectively once</h2>

Say a receipt service is described as "exactly-once, because Kafka". How many emails does the customer get if the email provider accepts the send and the consumer crashes before committing its offset? Two. Exactly-once is a property of the whole path, and Kafka only owns part of it.

**Exactly-once *delivery* across a network is not available.** A sender that hears nothing can either resend (risking a duplicate: **at-least-once**) or not resend (risking a loss: **at-most-once**). What you can build is **exactly-once effect**, often called **effectively-once**:

> **at-least-once delivery + idempotent processing = effectively once.**

The three ingredients, which this lesson has now built:

1. **Never lose it.** Persist before acknowledging; retry until acknowledged; use the outbox for side effects (below).
2. **Recognise a repeat.** A stable id per logical operation: the client's idempotency key, a producer-assigned event id, `(job_id, scheduled_at)`.
3. **Make the repeat harmless.** A unique key or dedup row committed **atomically with the effect**, a conditional state transition, or a downstream idempotency key.

**The outbox, for side effects.** When the payment commits, the system must also tell the ticketing service, send a receipt and notify the organiser. Writing to the database and then publishing to a broker is a **dual write**: a crash between them loses the event. Instead, insert the event into an `outbox` table **in the same transaction** as the payment, and let a relay publish it at least once. Consumers dedupe by event id. The full mechanism is <a href={`${BASE}sd/lessons/queues-streams/#outbox`}>Queues & streams, Chapter 6</a>.

```sql
START TRANSACTION;
UPDATE payments SET state = 'SUCCEEDED' WHERE id = :id AND state IN ('SUBMITTED', 'UNKNOWN');
-- ROW_COUNT() = 0 -> already settled: ROLLBACK and stop (the duplicate is harmless)
INSERT INTO outbox (event_id, topic, payload) VALUES (UUID(), 'PaymentSucceeded', :json);
COMMIT;   -- the state change and the event become visible together, or not at all
```

**What "exactly-once" in a product name means.** Kafka's exactly-once semantics (idempotent producer plus transactions) make a read-process-write pipeline **within Kafka** effectively once: consumed offsets and produced records commit together. The moment the effect leaves Kafka (an email, a card charge, a write to your MySQL), you are back to at-least-once plus idempotency. Stream processors such as Flink make similar promises about their own state. Say "within the boundary of X", and name the boundary.

<Figure caption="Effectively once, end to end. Each hop either commits its dedup marker with its effect, or passes a key to the next hop that does.">
  <Mermaid code={`flowchart LR
    C["Client\nkey a1b2"] -->|"retries, same key"| API["Payment API\nidempotency row"]
    API -->|"same txn"| DB[("payments + ledger\n+ outbox")]
    API -->|"key charge:a1b2"| PSP["Payment provider\ndedupes by key"]
    DB --> R["Outbox relay\nat-least-once"]
    R --> K["Broker"]

**Catch the trap:** a dedup check in Redis *before* the work and a write to MySQL *after* it. A crash between them, or two consumers at once, breaks it. The marker must commit with the effect, in the same store.

<h2 id="ledger">Money is append-only</h2>

Finance asks a simple question: how much do we owe the promoter? It should be one query. It takes two days if the payments table has a `balance` column that the refund code, the fee code and a support tool all update in place, and none of them left a trace of what the number was before.

**Never `UPDATE balance = balance - 500` as the only record.** Financial state is an **append-only double-entry ledger**:

- Every money movement is a **transaction** made of two or more **entries**, each against an **account** (a customer, an organiser's payable balance, the platform's fee revenue, the money sitting at the payment provider).
- **Entries in a transaction sum to zero.** With a signed convention (debits positive, credits negative), money can only move, never appear or vanish.
- **Entries are never updated or deleted.** A refund or a correction is a *new* transaction with opposite entries.
- **A balance is derived**: the sum of an account's entries. You may cache it (a balances table updated in the same transaction, or periodic snapshots), but it must always be recomputable from the entries.

**Worked example: a ₹1,000 ticket with a 10% fee.**

| Transaction | Account | Entry |
|---|---|---|
| T1 · charge | Provider clearing (money the provider owes us) | +₹1,000 |
| T1 · charge | Organiser payable | −₹900 |
| T1 · charge | Platform fee revenue | −₹100 |
| | **Sum** | **₹0** |
| T2 · full refund | Provider clearing | −₹1,000 |
| T2 · full refund | Organiser payable | +₹900 |
| T2 · full refund | Platform fee revenue | +₹100 |
| | **Sum** | **₹0** |

After T2, every balance is back to zero, and both events are still on the record. An update cannot give you that.

**The MySQL schema and the insert.** Store money as **integers in the smallest unit** (paise), never as `FLOAT`. The `UNIQUE` reference makes posting idempotent: the same charge cannot be posted twice.

```sql
CREATE TABLE ledger_transactions (
  txn_id       BIGINT AUTO_INCREMENT PRIMARY KEY,
  external_ref VARCHAR(64) NOT NULL,                 -- e.g. 'charge:pay_881', 'refund:ref_12'
  kind         VARCHAR(16) NOT NULL,
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uq_ref (external_ref)
) ENGINE=InnoDB;

CREATE TABLE ledger_entries (
  entry_id     BIGINT AUTO_INCREMENT PRIMARY KEY,
  txn_id       BIGINT NOT NULL,
  account_id   BIGINT NOT NULL,
  amount_paise BIGINT NOT NULL,                      -- signed: debit +, credit -
  currency     CHAR(3) NOT NULL,
  KEY idx_account (account_id),
  FOREIGN KEY (txn_id) REFERENCES ledger_transactions (txn_id)
) ENGINE=InnoDB;

-- Post the ₹1,000 charge: one transaction, three entries, all or nothing.
START TRANSACTION;
INSERT INTO ledger_transactions (external_ref, kind) VALUES ('charge:pay_881', 'CHARGE');
-- error 1062 here means "already posted": ROLLBACK, treat as success
SET @t = LAST_INSERT_ID();
INSERT INTO ledger_entries (txn_id, account_id, amount_paise, currency) VALUES
  (@t, 10,  100000, 'INR'),     -- provider clearing
  (@t, 20,  -90000, 'INR'),     -- organiser payable
  (@t, 30,  -10000, 'INR');     -- platform fee revenue
SELECT SUM(amount_paise) FROM ledger_entries WHERE txn_id = @t;   -- app asserts 0, else ROLLBACK
COMMIT;
```

**What MySQL does not do for you.** It cannot enforce "entries of a transaction sum to zero" with a constraint across rows. You enforce it in the code that posts (assert the sum, then commit) and verify it with a nightly check: `SELECT txn_id FROM ledger_entries GROUP BY txn_id HAVING SUM(amount_paise) <> 0` must return nothing. To enforce *append-only*, give the application's database user only `INSERT` and `SELECT` on the ledger tables, with no `UPDATE` or `DELETE` grant. A refund is then a new transaction:

```sql
INSERT INTO ledger_transactions (external_ref, kind) VALUES ('refund:pay_881', 'REFUND');
-- entries: provider clearing -100000, organiser payable +90000, platform fee revenue +10000
```

**Why interviewers care.** An update destroys history: no audit, no dispute resolution, no reconciliation. An append-only ledger makes every balance explainable. One sentence, *"double-entry, append-only, balances are derived"*, unlocks the payments walkthrough. Say it with the mechanism, not the framework name.

**Worked numbers: size.** Assume 10,000,000 payments a day, 3 entries each, about 100 bytes per entry: 30,000,000 entries a day, **3 GB a day, about 1.1 TB a year** (about 11 billion rows a year). Big, but append-only data partitions cleanly by time, and old partitions go to cheaper storage.

**Contention inside the ledger: the hot house account.** Every payment credits *platform fee revenue*. If that account's running balance lives in one row, every payment updates one row. Average 10,000,000 ÷ 86,400 ≈ **116 payments/s**. At a 5× peak, about **579/s**, which is above the **500/s** ceiling of a row held for 2 ms. Fixes, cheapest first:

1. Do not maintain a synchronous running balance for house accounts. Derive it, or update it asynchronously from the entries.
2. **Split the account into N sub-accounts**, pick one at random per entry, and sum them for the real balance.
3. Batch entries into the house account every second.

Customer accounts rarely need this: one customer does not pay 500 times a second.

<Reveal q="If balances are derived, how do you stop a customer's wallet going negative when two spends race?">

The derivation is for truth. The guard is still a contention tool. Keep a cached balance row per wallet, updated **in the same transaction** as the entries, with a condition: `UPDATE wallets SET balance = balance - 500 WHERE id = :w AND balance >= 500`. One row changed: append the entries and commit. Zero: insufficient funds, roll back. The cache can always be rebuilt from the entries, and the conditional update guards the invariant. A nightly job recomputes balances from entries and alerts on any mismatch.

</Reveal>

**Catch the trap:** "store the balance on the user row." Fine as a cache with a guard. Wrong as the only record. Say *derived*, *append-only*, *sum to zero*.

<h2 id="payments">The answer that never came</h2>

Take a charge of ₹2,400. The call to the payment provider times out after ten seconds. The code marks the payment FAILED and releases the seats. The customer tries again and pays. The next morning the provider's settlement report lists *two* charges. The first one was not a failure. It was a question nobody waited to hear the answer to.

**The payment state machine.** Every payment is a row with a state, and every move between states is a conditional update, exactly like a seat. A duplicate "mark succeeded" on a payment that is already `SUCCEEDED` is an illegal transition and changes nothing. (A status column with legal transitions enforced in the database is the same idea as an appointment-status field. Use whichever example you have shipped.)

<Figure caption="Payment states. UNKNOWN is the state most designs forget: the provider may or may not have charged the card.">
  <Mermaid code={`stateDiagram-v2
    [*] --> CREATED
    CREATED --> SUBMITTED: call provider with key
    SUBMITTED --> SUCCEEDED: provider says yes
    SUBMITTED --> FAILED: provider says no
    SUBMITTED --> UNKNOWN: timeout or 5xx
    UNKNOWN --> SUCCEEDED: retry same key or status query
    UNKNOWN --> FAILED: retry same key or status query
    SUCCEEDED --> REFUNDED: refund
    SUCCEEDED --> [*]
    FAILED --> [*]`} />
</Figure>

```sql
UPDATE payments SET state = 'SUCCEEDED', provider_ref = :ref, updated_at = NOW(3)
 WHERE id = :id AND state IN ('SUBMITTED', 'UNKNOWN');   -- ROW_COUNT() = 0 -> already settled; do nothing
```

**Calling the payment service provider (PSP).**

- **Persist before you call.** Insert the payment as `CREATED`, move it to `SUBMITTED`, then call. If you crash mid-call, a row exists to recover.
- **Always send an idempotency key to the PSP**, stable per payment attempt (for example the payment id). Retries reuse it.
- **Never hold a database transaction or lock open across the call.** 300 ms inside a lock is 3 payments/s.
- **A timeout is "unknown", not "failed".** Move to `UNKNOWN`. Resolve it by retrying **with the same key** (the PSP returns the original outcome) or by querying the PSP for the payment's status. Never retry with a new key, and never release goods or tell the user "failed" while the money might have moved.

**Webhooks.** PSPs report asynchronous outcomes (bank verification finished, a dispute opened) by calling your webhook endpoint. They deliver **at least once** and possibly out of order. Verify the signature, insert the provider's event id into a dedup table, apply the change through the state machine's conditional update (which ignores stale transitions), and respond `2xx` only after commit.

**Reconciliation, the safety net under everything.** Once a day (or more often), compare **your ledger** to **the PSP's settlement report** (and the bank's statement), transaction by transaction:

| Mismatch | Likely cause | Action |
|---|---|---|
| PSP charged, we show `UNKNOWN` or `FAILED` | A timeout we never resolved | Mark succeeded and fulfil, or refund, by policy |
| We show `SUCCEEDED`, PSP has no charge | A bug, or a webhook we misread | Investigate; never silently fix |
| Amounts differ | Currency, fees, partial capture | Post an adjusting ledger transaction |
| Charged twice for one order | A retry with a fresh key | Refund one; find the key bug |

Reconciliation exists because **every distributed system has a crack you did not think of**. Interviewers listen for it in any payments design. It also turns a double charge into a next-morning refund instead of a chargeback.

**Side effects through the outbox.** On `SUCCEEDED`, the same transaction writes the ledger entries **and** an outbox event (`PaymentSucceeded`). Ticket issuance, receipts and merchant webhooks consume it and dedupe by event id.

<Trace title="Money under uncertainty" steps={payments} takeaway="A timeout is UNKNOWN: resolve it with the same key, a status query, or reconciliation. Corrections are new balanced transactions. House accounts are hot rows." />

**Catch the trap:** "if the PSP call fails, we retry." A timeout is not a failure, and a retry with a new key is a second payment. Say *UNKNOWN*, *same key*, *reconcile*.

<h2 id="scheduler-mechanics">Jobs that run once</h2>

Think of a scheduler that releases tickets at noon, sends reminders a day before and settles payouts at 2 a.m. One week a payout batch runs twice. A worker stalled on a slow disk, the scheduler decided it was dead and gave the job to another worker, and then the first worker recovered and finished. The job ran exactly once on each of two machines.

A distributed scheduler has **two** contention points: **creating** a run at the scheduled time (several scheduler instances may try) and **executing** it (several workers may grab it, and a "dead" one may come back).

**Creating runs: let a unique key decide.** Give every run a deterministic identity, `(job_id, scheduled_at)`, with a unique key. Two scheduler instances that both wake at midnight both try to insert run `(42, 2026-10-09 00:00)`. One succeeds and the other is a no-op. You can still elect a leader (via ZooKeeper or etcd) to avoid wasted work, but correctness no longer depends on the election being perfect.

```sql
CREATE TABLE job_runs (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  job_id       BIGINT       NOT NULL,
  scheduled_at DATETIME     NOT NULL,
  due_at       DATETIME(3)  NOT NULL,
  state        ENUM('QUEUED','RUNNING','DONE','DEAD') NOT NULL DEFAULT 'QUEUED',
  owner        VARCHAR(64)  NULL,
  lease_until  DATETIME(3)  NULL,
  fence        BIGINT       NOT NULL DEFAULT 0,
  attempt      INT          NOT NULL DEFAULT 0,
  UNIQUE KEY uq_run (job_id, scheduled_at),
  KEY idx_due (state, due_at)
) ENGINE=InnoDB;

-- materialiser: safe to run on several instances
INSERT INTO job_runs (job_id, scheduled_at, due_at) VALUES (42, '2026-10-09 00:00:00', '2026-10-09 00:00:00')
  ON DUPLICATE KEY UPDATE job_id = job_id;     -- ROW_COUNT() = 1 created, 0 already there
```

**Executing runs: leases, heartbeats, fences.** MySQL has no `UPDATE ... RETURNING`, so the claim is two statements in one short transaction: lock one due row with `SKIP LOCKED`, then update it.

```sql
START TRANSACTION;
SELECT id, fence FROM job_runs
 WHERE due_at <= NOW(3)
   AND (state = 'QUEUED' OR (state = 'RUNNING' AND lease_until < NOW(3)))
 ORDER BY due_at LIMIT 1
   FOR UPDATE SKIP LOCKED;                       -- two workers never get the same row
UPDATE job_runs
   SET state = 'RUNNING', owner = :worker, lease_until = NOW(3) + INTERVAL 30 SECOND,
       fence = fence + 1, attempt = attempt + 1
 WHERE id = :id;
COMMIT;                                          -- the worker's fence is the old fence + 1

-- heartbeat every 10 s: renew only if I still own this fence
UPDATE job_runs SET lease_until = NOW(3) + INTERVAL 30 SECOND
 WHERE id = :run AND owner = :worker AND fence = :fence;     -- ROW_COUNT() = 0 -> I lost it: stop work
```

- **Lease**: the worker owns the run until `lease_until`. A crash means it simply stops renewing, and another worker reclaims the run after expiry.
- **Heartbeat**: renew every 10 s for a 30 s lease, so two missed heartbeats are tolerated. A heartbeat that changes 0 rows means "you lost the lease": stop.
- **Fence**: incremented on every claim. Every effect the job writes carries it, and the target rejects lower fences (`... WHERE fence <= :fence`). The stalled worker from the example above would have been refused.
- **At-least-once execution plus idempotent jobs.** Leases guarantee a run is eventually executed, not that it executes once: a worker can finish the work and die before marking it done. So jobs must be idempotent. "Settle payouts for 2026-10-08" writes payouts keyed by `(organiser, date)`, so a second run finds them and changes nothing. A reminder job records `(event, user, reminder_type)` before sending.
- **Retries and the dead-letter queue.** On failure, schedule the next attempt with exponential backoff (`due_at = NOW(3) + backoff(attempt)`). After N attempts (say 5), move the run to `DEAD` (a dead-letter state or queue) and alert a human. Never retry forever: a poison job burns workers and hides the error. See <a href={`${BASE}sd/lessons/queues-streams/#poison`}>Queues & streams, Chapter 8</a>.

**Cron fan-out.** A recurring job is a **definition** (a cron expression). The scheduler materialises the next run(s) a little ahead of time, for example every minute it creates runs due in the next few minutes. Many jobs share popular times (midnight, the top of the hour), which creates spikes.

**Worked numbers.** Assumptions for this example: 10,000,000 runs a day; 50,000 runs in flight at peak; heartbeat 10 s, lease 30 s; 1,000 worker slots; average run 2 s; 1,000,000 runs scheduled for exactly midnight.

- Average rate: 10,000,000 ÷ 86,400 ≈ **116 runs/s**.
- Heartbeat writes: 50,000 ÷ 10 s = **5,000 writes/s**, more than the runs themselves. Lengthen the heartbeat for long jobs, or keep leases in a store built for it.
- Dead-worker detection: at most **30 s** after its last renewal, plus the claim loop's polling interval.
- Midnight: 1,000 slots ÷ 2 s = **500 runs/s** of throughput, so 1,000,000 runs take 1,000,000 ÷ 500 = **2,000 s ≈ 33 minutes** to drain, and the last run starts half an hour late. Spread the same million runs across the hour (let users choose "hourly, any minute"; Jenkins's `H` cron syntax does this by hashing the job name) and the rate is 1,000,000 ÷ 3,600 ≈ **278 runs/s**, under capacity, no backlog.

<Trace title="Runs, leases, zombies" steps={scheduler} takeaway="A unique run id makes creation idempotent. Leases plus heartbeats recover crashed workers; fences stop paused ones; idempotent jobs make at-least-once safe; a DLQ stops infinite retries." />

**Catch the trap:** "the scheduler guarantees exactly-once execution." It cannot. Say: *at-least-once execution, idempotent jobs, fencing against zombies: effectively once.*

**0:08 · The bridge**

> "So: view, hold-and-pay, ticket; strongly consistent seat ownership under a 2-million-person spike; available, slightly stale browsing. The spike and the seat contention are the design. Does that match?"

**0:09 · Core entities**

> "**Event** and **Venue**. **Seat**, really *event-seat*: one row per seat per event, with a status, who holds it and until when. **Hold**, which groups the seats one buyer is checking out. **Booking** with its state, **Payment** with its state, and **Ticket**, issued per seat once booked. **0:11 · API**

```http

**0:15 · High-level design, one requirement at a time**

> "View: event pages are mostly static, so the CDN serves them. The seat map goes through the gateway to an event service that reads seat status from a cache per section, refreshed from a read replica every second."

**0:25 · Deep dive 1: no seat sold twice**

> "The signature problem. Options: a Redis lock per seat, a pessimistic row lock held through checkout, or a conditional update plus a hold with an expiry. The Redis lock adds a second source of truth that can disagree with the database and needs fencing to be safe. Holding a row lock through a four-minute checkout is impossible, because the ceiling of a row is one over the lock time. So: **a hold is a conditional update, and the expiry is in its WHERE clause.** The seat's states are available, held, booked."
>
> "Confirm is also conditional: held to booked, only where held-by is my hold and held-until is in the future. Payment is **authorise, confirm, capture**. If confirm fails because my hold lapsed, we void the authorisation, so nobody is charged for a seat they didn't get. The server-side hold runs two minutes longer than the timer the buyer sees, so a payment finishing on time always finds its hold."
>
> "The sweeper releases expired holds every few seconds for the seat map; correctness doesn't depend on it. A double-click on *Hold* carries the same idempotency key and gets the same hold back."

**0:31 · Deep dive 2: the flash crowd**

> "Without metering, 16,700 hold attempts a second hit one primary, aimed at a few hundred popular rows, and a million seat-map reads a second hit the event service. So a **virtual waiting room**: each arrival gets a position from an atomic counter and a signed token; positions before opening are randomised so the fastest network doesn't win. Clients poll a single *now serving* number, which is the same for everyone, so the CDN answers two million pollers."
>
> "I'd admit about 100 people a second. With about four minutes in the flow, that's 24,000 people inside: 12,000 seat-map reads a second, served from a one-second cache, and about 100 holds a second, which one MySQL primary handles easily. All seats are held after about 250 seconds. If 20% of holders abandon, 10,000 seats come back between 10 and 14 minutes in, so 'sold out' at minute four means 'all held': we keep the line alive and admit people as seats return. Position 30,000 waits about five minutes; people far back are told early that tickets are unlikely."

**0:36 · Deep dive 3: payments in one breath**

> "Checkout has its own idempotency key; the payment service stores key, request hash and result. A provider timeout makes the payment *unknown*, never *failed*: we retry with the same provider key or query status, and a daily reconciliation against the provider's report catches anything left. I can go deeper on payments if you'd like."

**0:38 · Wrap-up**

> "Recap: view is CDN plus a one-second seat-map cache; hold is a conditional update with expiry; pay is authorise-confirm-capture with idempotency keys; tickets go out through an outbox. At 10x, meaning ten such on-sales at once, events are independent, so I'd shard seat data by event id. The single hottest event is still one shard, and the waiting room's admission rate is what keeps it within bounds. If the primary fails, holds and checkouts pause for the failover window while the waiting room keeps people in line; browsing continues from cache. I'd monitor hold success rate, hold-to-booking conversion, expired holds, queue length and wait, provider latency and the count of unknown payments, plus an invariant check that booked seats never exceed capacity, which should be impossible, so it pages. With more time: bot defence and per-account ticket limits."

<h2 id="payments-walkthrough">Payments, sketched</h2>

**Entities (0:09–0:11).** **Payment** (state machine), **IdempotencyKey**, **ProviderAttempt** (each call to the PSP, with its own key), **LedgerTransaction** and **LedgerEntry**, **Account**, **Refund**, **OutboxEvent**, **WebhookEvent** (inbound, deduped).

**API (0:11–0:15).**

                          -> 201 { paymentId, state }   (replayed on retry; 422 if key reused with a different body)

An outbox relay feeds a broker, which feeds the merchant-webhook sender and receipts. A reconciliation job reads the PSP's daily settlement file and the ledger.

**Deep dives (0:25–0:38), the three that score:**

1. **Idempotency, end to end.** Client key, then `(merchant_id, key)` primary key with request hash, then `IN_PROGRESS` / `COMPLETED`, then replay, 422 on mismatch, 409 while in flight, then our own key to the PSP per attempt, then a recovery job for stale `IN_PROGRESS` rows that re-calls the PSP with the same key. *Line:* "Every hop that can repeat is keyed, and each key's record commits with its effect."
2. **The unknown state.** Timeout, then `UNKNOWN`, then retry with the same key and backoff, or a status query. A webhook may settle it first; the conditional transition ignores whichever arrives second. Reconciliation catches the rest. *Line:* "A timeout is a question, not an answer."
3. **The ledger.** Double-entry, append-only, entries sum to zero; refunds are new transactions; balances derived and cached with a guard; house accounts split into sub-accounts because every payment touches them (579/s against a 500/s single-row ceiling). Size: 30M entries/day, ~3 GB/day, ~1.1 TB/year, partitioned by month.

**Wrap-up (0:38–0:41).** First bottleneck at 10× (≈ 5,800/s at peak): the single MySQL primary. Shard by merchant id, so a payment, its keys, its ledger entries and its outbox rows live on one shard and transactions stay local; house accounts become per-shard sub-accounts. Failure: if the PSP is down, payments fail fast with a clear error, with no queueing of card charges for later. Monitor: unknown-state count and age, reconciliation mismatches, PSP error rate and latency, idempotency 409/422 rates, ledger imbalance (must be zero).

<Reveal q="The interviewer: “Why not use two-phase commit between your database and the PSP?”">

The PSP does not take part in your transaction protocol (it is an HTTP API, not an XA resource), and you would not want your database's locks held for the length of a card network round trip. The pattern instead is **persist intent, call with an idempotency key, record the outcome**, with a recovery path that replays the call safely and reconciliation as the backstop. Sagas generalise this for multi-step flows: each step has a compensating action (void an authorisation, refund a capture).

</Reveal>

<h2 id="scheduler-walkthrough">A job scheduler, sketched</h2>

The prompt: "A million jobs, some every minute, some once next Tuesday. Workers die. Make sure each runs." Then, almost as an afterthought: "Exactly once." The word to push back on is *exactly*.

**Requirements.** Create one-off and recurring (cron) jobs; run each at roughly its time (within a few seconds); retry failures with backoff; surface status and failures; a dead-letter for jobs that keep failing. Out of scope: workflow DAGs between jobs, the job code itself. Non-functionals: **every due run executes at least once**, **no run's effects happen twice** (push back: *"exactly-once execution isn't possible across machines. I'll give at-least-once execution with idempotent jobs and fencing, which is effectively once"*). Assumed load: 10,000,000 runs/day (≈ 116/s), with top-of-hour spikes; the scheduler itself highly available.

**Entities.** **Job** (definition: owner, cron expression or run time, payload, retry policy), **JobRun** (job id, scheduled time, state, attempt, owner, lease-until, fence), **Worker**.

**API.**

```http
POST   /jobs              { schedule | runAt, payload, retryPolicy }   Idempotency-Key  -> 201 { jobId }
GET    /jobs/{id}/runs    ?cursor=...                                  -> 200 { runs, nextCursor }
POST   /jobs/{id}/pause   ;  DELETE /jobs/{id}
POST   /runs/{id}/retry   (redrive a dead run)
```

**High-level.** Job definitions in a database. A **materialiser** (several instances; optionally leader-elected) turns cron definitions into `job_runs` rows a few minutes ahead, with `UNIQUE (job_id, scheduled_at)` making double materialisation harmless. **Workers** claim due runs with `FOR UPDATE SKIP LOCKED` and a lease (or the runs are pushed onto a queue by a dispatcher), heartbeat while running, and write results carrying the run's fence. Failed runs are rescheduled with backoff. After N attempts they become `DEAD` and alert.

<Figure caption="Job scheduler. The unique run id makes creation idempotent; leases recover crashed workers; fences stop paused ones.">
  <Mermaid code={`flowchart LR
    API["Jobs API"] --> JD[("job definitions")]
    MAT["Materialiser x N\ncron to runs ahead"] --> JD
    MAT -->|"INSERT, unique (job_id, scheduled_at)"| JR[("job_runs\nstate, lease, fence")]
    W["Workers\nclaim SKIP LOCKED\nheartbeat 10 s"] --> JR
    W -->|"writes carry fence"| T[("Job targets\nreject stale fence")]
    JR -->|"attempt over 5"| DLQ["DEAD runs\nalert + redrive"]`} />
</Figure>

**Deep dives.**

1. **Effectively-once execution.** Unique run id (creation); lease and heartbeat (crash recovery: a dead worker's run is reclaimed within 30 s of its last renewal); fence on every write (zombie workers refused); idempotent job bodies (a worker that finished but died before marking done is harmless). *Line:* "At-least-once from leases, at-most-once *effect* from fences and idempotent jobs."
2. **The midnight spike.** 1,000,000 runs at midnight against 500 runs/s of capacity is a 33-minute drain. Options: more workers for the spike (autoscale on due-but-unclaimed runs), priorities so payouts beat newsletters, and spreading flexible jobs across the hour (≈ 278/s, no backlog).
3. **The scheduler's own state at scale.** Heartbeats alone are 5,000 writes/s at 50,000 in-flight runs. Partition `job_runs` by time bucket or shard by job id; or keep leases in a store designed for frequent small writes; or lengthen heartbeats for long jobs. Claiming via `SKIP LOCKED` scales to thousands of claims per second per database (an assumption to measure on your hardware); beyond that, a dispatcher pushes due runs onto a partitioned queue.

**Wrap-up.** At 10×, the `job_runs` table and heartbeat writes are first: shard by job id with a materialiser per shard. If a materialiser dies, others (or a new leader) pick up within seconds, and the unique key prevents doubles. Monitor: due-but-unclaimed count and age (lateness), lease expiries (worker deaths), retries and dead runs, fence rejections (should be rare; each one is a zombie caught).

The <a href={`${BASE}sd/lessons/pattern-async-jobs/`}>Async jobs & pipelines</a> lesson owns the job template (persist, enqueue, status, workers). This chapter owns the "once" part.

<h2 id="transfer">Same problem, new settings</h2>

The nouns change. The three questions stay the same: what is scarce, where does the truth live, and how long is the critical section?

| Setting | What is scarce | The move |
|---|---|---|
| **Ticketmaster** (walkthrough) | One seat per event | Waiting room + seat hold with TTL + conditional update; authorise-confirm-capture |
| **Payment system** (walkthrough) | One logical charge; consistent balances | Idempotency keys + state machine + double-entry ledger + reconciliation |
| **Job scheduler** (walkthrough) | One execution per run | "Exactly-once" = at-least-once trigger + lease (lock with TTL + heartbeat) + idempotent jobs + fencing |
| **Airbnb booking** | Nights on a listing's calendar | One row per (listing, night) with a unique key, inserted in one transaction (MySQL has no exclusion constraint; Postgres does). A pending-request hold with expiry while the host decides or payment completes |
| **Hotel booking** | A *count* of rooms of a type per night | Per (hotel, room type, night) inventory rows with a conditional decrement for every night of the stay, in one transaction (lock rows in date order). Overbooking, if the business allows it, is a deliberate limit above capacity |
| **Flash sale** | A count of units | Inventory as an atomic decrement (Redis Lua or `DECR` with a floor check), split into N buckets if one key is too hot (10,000 units into 10 keys of 1,000). | **Inventory / e-commerce checkout** | Stock of a SKU | `UPDATE ... SET stock = stock - :q WHERE stock >= :q`; reserve at checkout, not at add-to-cart; release on expiry |
| **Coupon redemption** | One use per user; N uses total | `UNIQUE (coupon_id, user_id)` + `UPDATE coupons SET remaining = remaining - 1 WHERE id = ? AND remaining > 0`, both in one transaction |
| **Distributed lock service (Chubby)** | Lock ownership | Consensus (Raft / Paxos) across 3 or 5 replicas, sessions with leases and heartbeats, and a sequencer or fencing token checked by the resource; name the Redlock debate |
| **Stock exchange** | The order book of one symbol | Contention taken to its limit: a sequencer for total order and a single-threaded in-memory matching engine per symbol, which avoids locking by serialising |
| **Two riders matched to one driver** | One driver | Conditional update on the driver's state (`AVAILABLE` to `OFFERED` where available), an offer with a short TTL, decline or expiry returns the driver |

**Airbnb in MySQL.** A range is not a point, so turn it into points: one row per night, unique on `(listing_id, night)`. All nights of a stay insert in one transaction, so any collision rolls back the whole stay.

```sql
CREATE TABLE listing_nights (
  listing_id BIGINT NOT NULL,
  night      DATE   NOT NULL,
  booking_id BIGINT NOT NULL,
  PRIMARY KEY (listing_id, night)
) ENGINE=InnoDB;

START TRANSACTION;
INSERT INTO listing_nights (listing_id, night, booking_id) VALUES
  (500, '2026-10-03', 9001), (500, '2026-10-04', 9001), (500, '2026-10-05', 9001);
-- any overlapping night already booked -> error 1062 -> ROLLBACK, whole stay refused
COMMIT;
```

**Hotel inventory in MySQL.** A count per night, decremented for every night of the stay in one transaction:

```sql
START TRANSACTION;
UPDATE room_inventory SET available = available - 1
 WHERE hotel_id = 3 AND room_type = 'DELUXE' AND night BETWEEN '2026-10-03' AND '2026-10-05'
   AND available > 0;
-- app: need ROW_COUNT() = 3 (one per night), else ROLLBACK
COMMIT;
```

**Worked numbers: the flash sale, bucketed.** 10,000 units, 1,000,000 buyers in a minute. Without a waiting room, every buyer decrements one Redis key, and one shard serialises all of it. With 10 buckets of 1,000 units each, ten keys (on different shards) share the load. A buyer whose bucket is empty tries another, and the sale is over when all ten report zero. The decrement is still atomic per bucket, so no unit is sold twice.

<Reveal q="Airbnb: why doesn't a unique constraint on (listing_id, check_in) prevent double bookings?">

Because two overlapping stays can start on different days: 3–6 October and 5–8 October share the night of the 5th but have different check-in dates. The rule is about **ranges**, not points. Either turn the range into points (one row per night, each unique on `(listing_id, night)`, all inserted in one transaction so any collision rolls back the whole stay) or, in Postgres, guard the range directly with an exclusion constraint (`EXCLUDE USING gist (listing_id WITH =, stay WITH &&)`). Per-night rows also make the calendar query trivial.

</Reveal>

<h2 id="interview-script">Say it in the room</h2>

The question: "What happens if two people book the last room at the same time?" A weak answer is "we lock it". <Fragment slot="deep">

**Resource and granularity.** One room-night. Rows in `room_inventory` keyed by (hotel, room type, night), or one row per room. The lock granularity is that row, never the whole hotel.

**Hold.** `UPDATE ... SET status='HELD', held_by=?, held_until=NOW(3)+INTERVAL 10 MINUTE WHERE ... AND (status='AVAILABLE' OR (status='HELD' AND held_until < NOW(3)))`. `ROW_COUNT()` equals the number of rooms requested or I roll back. Isolation stays at the default; correctness comes from the WHERE, not from the isolation level, because REPEATABLE READ does not prevent a lost update from an app-computed write.

**Why not a lock.** A row lock held through checkout (minutes) caps a hot row at 1 ÷ lock time and holds connections. A Redis lock adds a second source of truth and needs fencing to be safe against pauses. A conditional update has neither problem.

**Confirm and money.** Confirm: HELD to BOOKED only where held-by is mine and held-until is in the future. Authorise the card first, confirm, then capture. If confirm changes 0 rows, void the authorisation. The server hold outlives the buyer's visible timer by a grace period.

**Idempotency.** Client key with a unique claim `(client_id, idem_key)`, request hash, IN_PROGRESS / COMPLETED. Replay on the same hash, 422 on a different hash, 409 while in flight. The provider call carries its own derived key. A timeout leaves the payment UNKNOWN, resolved by same-key retry or status query. Reconciliation against the settlement report catches the rest.

**Crowd and failure.** If a burst can reach this path, a waiting room meters admission to about a hundred holds a second. If the primary fails over, writes pause, browsing continues from cache, and idempotency keys plus conditional writes make retries safe. I monitor hold success, expired holds, unknown-payment count and age, and an invariant check that bookings never exceed capacity.

**Cross-service locks.** If I ever need one, it is a lease with a fencing token that the storage checks.

</Fragment>

**Five follow-ups you will get:**

<Reveal q="1 · Why not a distributed lock on the room?">

The database can do it atomically for free, and a separate lock is a second source of truth that can disagree with it. A TTL lock is also unsafe without fencing: a paused holder can wake after expiry and write. I would use a distributed lock only when the critical section spans systems, and then with a fencing token the resource checks.

</Reveal>

<Reveal q="2 · Optimistic or pessimistic?">

For a single contended row, neither in the classic sense. A conditional update is the cheapest. If the decision spans rows (a per-account limit), a brief `SELECT ... FOR UPDATE` on the smallest scarce row, held for milliseconds. Optimistic versions fit low-contention edits with human think time. On a hot row they cause quadratic retries: 100 contenders cost 5,050 attempts.

</Reveal>

<Reveal q="3 · The client retried with the same key but a different amount. What happens?">

422. I store a hash of the canonical request with the key. Same key and same hash replays the stored response. Same key and a different hash is a client bug, and I neither replay (wrong answer) nor execute (double effect). If the original is still in flight, 409 and the client backs off.

</Reveal>

<Reveal q="4 · What happens when the payment succeeds after the hold expired?">

It cannot capture money for a seat it does not get, because I authorise first, confirm the seat with a conditional update that requires a live hold, and capture only after confirm. If confirm fails, I void the authorisation. To make that rare, the server-side hold outlives the buyer's visible timer by a grace period, and checkout cannot start in the last minute.

</Reveal>

<Reveal q="5 · Can you guarantee exactly-once?">

Not delivery: a sender that hears nothing must either resend or risk a loss. I guarantee exactly-once **effect**: at-least-once delivery, a stable id per logical operation, and a dedup record or conditional transition committed atomically with the effect. Where an effect leaves my database, I pass a key to the next hop, and reconciliation catches anything that slips through.

</Reveal>

<Reveal q="6 · Does raising the isolation level to SERIALIZABLE fix this in MySQL?">

It closes the gap, because InnoDB turns plain reads into locking reads, but it does it with shared locks that make concurrent read-then-write transactions deadlock; one is rolled back with error 1213 and you must retry. It also costs throughput on every table you touch. A conditional UPDATE gives the same safety for this one rule without the deadlocks, so I keep the default level and make the contended rule explicit.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Say... |
|---|---|
| "Book", "reserve", "the last one" | Granularity first, then a conditional UPDATE; row count = who won |
| "At most one per user / per X" | A unique key (per-night rows for date ranges in MySQL) |
| Any one of N identical rows | `FOR UPDATE SKIP LOCKED` (MySQL 8.0+, indexed) |
| A decision across several rows | Brief `SELECT ... FOR UPDATE` on the smallest scarce row |
| Human edit form, rare conflicts | Optimistic version column |
| "Is it safe inside a transaction?" | Not by itself: REPEATABLE READ allows lost updates from app-computed writes |
| Hot row, many contenders | Ceiling = 1 ÷ lock time; optimistic = N(N+1)/2 attempts; meter or split |
| Lock across services | Lease (`SET NX PX` + token) **and** a fencing token the storage checks |
| "Is Redlock safe?" | Debated (timing assumptions, no fence); for correctness: consensus lock + fence, or a DB guard |
| Everyone needs the same key | Serialise: one writer per key (partitioned log, single-threaded engine) |
| Checkout takes minutes | Hold with TTL in the WHERE; sweeper only tidies; available, held, booked |
| Payment after hold expired | Authorise, confirm, capture; void on failure; server grace > visible timer |
| Flash crowd | Waiting room: atomic position, signed token, CDN-cached now-serving, admission rate |
| Retries, double taps | Client key per intent; unique claim; request hash; replay / 422 / 409; TTL ~24 h |
| Duplicate key then SELECT shows nothing | Snapshot predates the other commit; use FOR SHARE or an autocommit claim |
| External side effect | Key the downstream call; outbox for events; consumers dedupe by event id |
| "Exactly-once" | At-least-once + idempotent effect = effectively once; name the boundary |
| Money | Integer paise; double-entry, append-only, sum to zero, balances derived; corrections are new transactions |
| PSP timeout | UNKNOWN, then same key / status query, then reconciliation |
| Cron "exactly once" | Unique (job_id, scheduled_at); lease + heartbeat; fence; idempotent job; DLQ after N |
| Top-of-hour spike | Capacity ÷ run time vs runs due; spread flexible jobs |
| MySQL errors to handle | 1062 duplicate key (expected outcome), 1213 deadlock (retry whole transaction), 1205 lock wait timeout (statement rolled back), 3572 NOWAIT |

## Five mistakes to leave behind

1. **Read, decide in code, write back.** Put the condition in the `WHERE`, or a unique key in the schema.
2. **A TTL lock without fencing.** Safe against crashes, unsafe against pauses.
3. **A lock held across a slow call.** 300 ms inside a lock is 3 per second. Hold, commit, pay, confirm.
4. **A fresh idempotency key on retry, or none downstream.** The key is per intent, reused on every retry, and every hop that can repeat needs one.
5. **"Failed" after a timeout.** It is unknown. Same key, status query, reconciliation.

**Keep it warm:** run a **race-condition gauntlet**. Five scenarios (a double-booked hotel room, a double-charged card, a cron job that ran twice, an oversold flash sale, two riders matched to one driver), two minutes each: name the race, pick the cheapest sufficient tool, name its failure mode. Then do a timed mock of Ticketmaster, followed by payments.
