<h2 id="prologue">Prologue · The query that melted the database</h2>

Imagine a "places near me" feature launches. It runs this query against a table of 100 million places, with an index on `lat`:

```sql
SELECT id, name FROM places
WHERE lat BETWEEN 12.9536 AND 12.9896      -- 4 km tall
  AND lng BETWEEN 77.5762 AND 77.6130;     -- 4 km wide
```

It passed every test, because the tests had a thousand places. At lunchtime, thousands of people search at once and the primary database hits 100% CPU. The next chapter shows exactly why.

The root cause: **an ordinary index sorts along one line, and "near" is a two-dimensional idea**. Almost every geospatial design, from "restaurants near me" to "match this rider with a driver", answers it with the same three moves:

1. **Turn the map into cells**, so "near this point" becomes "in this cell or the cells next to it", which is a key lookup.
2. **Filter by cell, refine by distance.** Cells are a cheap, coarse filter. The exact distance is computed only on the few hundred candidates the cells return.
3. **Ask whether the things move.** Restaurants sit still: index them once and cache freely. Drivers move every few seconds: keep only their latest position, in memory, and let it expire.

**Trigger words:** "nearby", "within X km", "closest drivers", "in this map area", "location-based", "match riders to drivers", "show cars on the map".

This lesson serves four bank questions: **Yelp / nearby search**, **Uber / Lyft** (both with full walkthroughs here), **DoorDash**, **Tinder**, and the **Google Maps routing** entry points at the routing chapter. Three habits to keep: say why the naive index fails before you fix it, always say the edge caveat, and compute the driver write rate out loud, because that number licenses the in-memory answer.

<h2 id="naive-index">Chapter 1 · The strip around the planet</h2>

**What the index really reads.** An index on `lat` is a sorted list of latitudes. It finds the first row whose latitude is above the box's south edge and walks forward until the north edge. It knows nothing about longitude, so every row in between comes back, on every continent. The box is 4 km tall, and so is the strip, but the strip goes all the way around the Earth.

**Worked numbers.** At latitude 13°, the circumference along that latitude is 40,075 km × cos 13° ≈ **39,000 km**. The strip is 4 km tall and 39,000 km long; the box you wanted is 4 km wide. If places were spread evenly, the index reads about 39,000 ÷ 4 ≈ **9,800 times** more rows than the answer area. Places are not spread evenly (oceans are empty, cities are dense), but every city at the same latitude lands in your strip. At 100 million places and thousands of searches a second, that is the 100% CPU graph.

**"Then index (lat, lng) together."** A composite B-tree sorts by `lat` first and by `lng` only among rows with the *same* `lat`. A range on the first column makes the second column useless for seeking: the phone-book rule from <a href={`${BASE}sd/lessons/databases/#composite-indexes`}>Databases · composite indexes</a>. The engine still walks the whole strip; it only checks `lng` from the index entry instead of the row. Cheaper, still planet-wide.

| Approach | What the index can seek | Rows examined for a 4 km box |
|---|---|---|
| Index on `lat` | One latitude band | The whole planet-wide strip |
| Index on `lat` and one on `lng` | One band each; intersect with a bitmap | Two planet-wide strips |
| Composite `(lat, lng)` | The `lat` range only | The strip, filtered inside the index |
| **Cell id** (geohash, S2, H3) or a **spatial index** (R-tree, quadtree) | Both dimensions together | Roughly the box |

<Reveal q="Why does the query look fine in testing?">

Because the cost scales with the number of rows in the strip, not with the size of the answer. With a thousand test places the strip holds a handful of rows and the query takes a millisecond. With a hundred million places it holds hundreds of thousands. The query plan is the same; only the data changed. So a geo design should name how many rows the index touches, not just which index it uses.

</Reveal>

**A common slip:** jumping straight to "use geohash". The interviewer wants to hear *why* the obvious index fails, in one sentence: *"A B-tree on latitude returns a band around the whole planet, and longitude can't narrow it, so I need an index that keeps both dimensions together."*

<h2 id="distance">Chapter 2 · As the crow flies</h2>

A fair question: why not compute the distance from the user to every place and sort? Two things first: how distance on a sphere works, and what 100 million distance calculations cost.

**Distance on a sphere.** Latitude and longitude are angles, not metres. One degree of latitude is about 111 km everywhere. One degree of longitude is about 111 km × cos(latitude): 111 km at the equator, about 108 km at 13°, about 56 km at 60°, zero at the poles. Treating degrees as a flat grid is the first geo bug.

**Haversine** gives the great-circle distance between two points (R ≈ 6,371 km, angles in radians):

```text
a = sin²(Δφ / 2) + cos φ1 · cos φ2 · sin²(Δλ / 2)
d = 2R · asin(√a)                 φ = latitude, λ = longitude
```

**The flat (equirectangular) approximation** is good inside a city:

```text
x = Δλ · cos(mean φ)
y = Δφ
d = R · √(x² + y²)
```

**Worked numbers** (checked with a script). From (12.9716, 77.5946) to (12.9800, 77.6100): haversine gives **1.912 km**, and the flat formula gives the same to the metre. The approximation drifts over hundreds of kilometres and near the poles, which "near me" rarely needs. Haversine itself assumes a sphere; the Earth is slightly flattened, so it can be off by up to about half a percent. Nobody choosing a restaurant notices.

**Why not compute every distance?** A haversine costs tens of nanoseconds. Assumption for this example: 50 ns. 100,000,000 × 50 ns = **5 seconds of CPU per search**. Distance answers "how far?" and is the wrong tool for "which ones?".

**The rule this lesson is built on: filter by cell, then refine by exact distance.** Cells cut 100 million places to a few hundred candidates; distance on a few hundred costs microseconds. Cells are *approximate on purpose*: they include some places outside the radius (refine them away) and, if you are careless, miss some just inside it (next part).

**A common slip:** latitude and longitude in the wrong order. User interfaces say "lat, lng"; GeoJSON, PostGIS's `ST_MakePoint(x, y)` and Redis `GEOADD` all take **longitude first**. A swapped pair often still looks valid and lands the user in the ocean or on another continent. Say the order out loud when you write an API or a query.

<h2 id="geohash">Chapter 3 · Halving the world</h2>

**What it is.** A **geohash** turns a point into a short string by halving the world over and over, alternating between longitude and latitude. Points that share a string prefix are in the same rectangular cell.

**How it works.**

1. Start with longitude in [−180, 180] and latitude in [−90, 90].
2. **Odd-numbered bits (1st, 3rd, 5th…) cut longitude; even-numbered bits cut latitude.** If the value is at or above the midpoint, write 1 and keep the upper half; otherwise write 0 and keep the lower half.
3. Every 5 bits become one **base32** character from `0123456789bcdefghjkmnpqrstuvwxyz` (no a, i, l or o).

**Worked encoding** for latitude 12.9716, longitude 77.5946:

| Bit | Cuts | Range before | Midpoint | Value ≥ mid? | Bit |
|---|---|---|---|---|---|
| 1 | lng | −180 … 180 | 0 | 77.59 ≥ 0 | 1 |
| 2 | lat | −90 … 90 | 0 | 12.97 ≥ 0 | 1 |
| 3 | lng | 0 … 180 | 90 | no | 0 |
| 4 | lat | 0 … 90 | 45 | no | 0 |
| 5 | lng | 0 … 90 | 45 | yes | 1 |
| 6 | lat | 0 … 45 | 22.5 | no | 0 |
| 7 | lng | 45 … 90 | 67.5 | yes | 1 |
| 8 | lat | 0 … 22.5 | 11.25 | yes | 1 |
| 9 | lng | 67.5 … 90 | 78.75 | no | 0 |
| 10 | lat | 11.25 … 22.5 | 16.875 | no | 0 |

  <ArrayStrip name="Bits" values={['1', '1', '0', '0', '1', '0', '1', '1', '0', '0']} indices={false} tones={{ 0: 'blue', 1: 'purple', 2: 'blue', 3: 'purple', 4: 'blue', 5: 'purple', 6: 'blue', 7: 'purple', 8: 'blue', 9: 'purple' }} regions={[{ from: 0, to: 4, label: '11001 → t', tone: 'gold' }, { from: 5, to: 9, label: '01100 → d', tone: 'green' }]} />
</Figure>

After those ten bits the point is somewhere in longitude 67.5–78.75 and latitude 11.25–16.875: the cell `td`, about 1,200 km wide. Keep going and the same point is `tdr1v9q`.

**Why we need it: a shared prefix means the same cell.** Every point inside cell `tdr1v` has a geohash starting with `tdr1v`. So "everything in this cell" is a **string prefix range**, which an ordinary B-tree, a sorted set or a key-value store already answers:

```sql
SELECT id FROM places WHERE geohash LIKE 'tdr1v%';   -- a range scan on a plain index
```

Two dimensions became one ordered line. (The line is a **Z-order curve**: it visits the four quarters of every cell in a Z shape, then the quarters of those, and so on.)

**Precision: how big is a cell?** Each character adds 5 bits, alternating which axis gets 3 and which gets 2, so cells alternate between roughly square and 2:1 rectangles. Widths below are at the equator; **multiply width by cos(latitude)** elsewhere (at 60° north a cell is half as wide).

| Length | Cell size at the equator (width × height) | Feels like |
|---|---|---|
| 1 | ≈ 5,000 × 5,000 km | A continent |
| 2 | ≈ 1,250 × 620 km | A large country |
| 3 | ≈ 156 × 156 km | A region |
| 4 | ≈ 39 × 19.5 km | A metro area |
| 5 | ≈ 4.9 × 4.9 km | A district |
| 6 | ≈ 1.2 × 0.61 km | A neighbourhood |
| 7 | ≈ 153 × 152 m | A few blocks |
| 8 | ≈ 38 × 19 m | A building |
| 9 | ≈ 4.8 × 4.8 m | A parking space |

Computed from 360° and 180° halved by the bit counts, times about 111 km per degree. Precision 6 is only about 0.6 km tall, and that matters in the next chapter.

**Implementation.** Store a `geohash` column (say 9–12 characters) with a B-tree index, or use the cell at your chosen precision as a key: `places:cell:tdr1v9`. A coarser cell is just a shorter prefix of the same string, so one column serves every precision. A minimal encoder in Python:

```python
BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"

def geohash(lat, lng, precision=7):
    lat_r, lng_r = [-90.0, 90.0], [-180.0, 180.0]
    out, bits, ch, even = "", 0, 0, True        # even=True means "cut longitude"
    while len(out) < precision:
        rng, val = (lng_r, lng) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        ch <<= 1
        if val >= mid: ch |= 1; rng[0] = mid
        else:          rng[1] = mid
        even = not even
        bits += 1
        if bits == 5: out += BASE32[ch]; bits, ch = 0, 0
    return out

geohash(12.9716, 77.5946)   # 'tdr1v9q'
```

**Trade-offs.** Simple, portable, any sorted store works. But cells are fixed rectangles that shrink toward the poles and have edges (next chapter).

**Use it when** you want a database, Redis or a key-value store to do the work and cells of one size are acceptable.

**Interview takeaway:** "Geohash interleaves longitude and latitude bits into a base32 string, so a shared prefix means the same cell and a radius search becomes a few prefix range scans."

<Reveal q="Why interleave the bits instead of writing all the longitude bits, then all the latitude bits?">

Because then the prefix would be pure longitude: every place with the same first 15 bits would lie in a thin north-south strip around the whole planet, the B-tree failure from Chapter 1 turned sideways. Interleaving means each extra pair of bits shrinks the cell in **both** directions, so a prefix describes a compact rectangle.

</Reveal>

**A common slip:** "A shared prefix means nearby, so different prefixes mean far apart." The first half is true. The second is false, and the next chapter is about why.

<h2 id="edges">Chapter 4 · Cell edges and neighbours</h2>

**The problem.** Cells have borders, and two points can sit metres apart on either side of one. Their geohashes then differ at the character where the border was drawn, sometimes the last one, sometimes much earlier. Concretely (all verified by script):

- A user at (12.9720, 77.5963) is in `tdr1v9`. A café at (12.9720, 77.5965), **22 m** east, is in `tdr1vc`. Different at precision 6.
- Cell `tdr1v`'s northern neighbours are `tdr4h`, `tdr4j` and `tdr4n`. Different at precision **4**.
- Two points **22 m** apart, at latitude +0.0001 and −0.0001 on longitude 0, are `s00000` and `kpbpbp`. Different from the **first** character, because the equator is the second cut of all.

**A shared prefix proves closeness; a different prefix proves nothing.** So "query my cell" is wrong near every edge, and every user is near some edge at some precision.

**The fix, always said together with geohash: query the cell plus its 8 neighbours, then filter by exact distance.** Computing a neighbour is cheap: decode the cell's box, step one cell width or height, encode again (libraries do it for you). Nine prefix lookups, then haversine on the candidates.

**Choosing the precision for a radius.** The user is somewhere inside the centre cell. The 3 × 3 block extends at least one full cell beyond the user in every direction. So **the block covers a circle of radius r whenever the cell's shorter side is at least r**.

**Worked numbers: a 2 km search at latitude 13°** (areas computed from the cell sizes above).

- Precision 6 cells are about 1.19 × 0.61 km. 0.61 km is less than 2 km, so the 3 × 3 block can fall short to the north and south. **Too fine** for "cell + 8".
- Precision 5 cells are about 4.76 × 4.89 km. Both sides exceed 2 km. **Covers.**
- Cost of that safety: the block is about 9 × 23.3 ≈ **209 km²**; the circle is π × 2² ≈ **12.6 km²**. If places were spread evenly, about 1 candidate in 17 is inside the radius and **94%** are thrown away by the distance check.

**The alternative: cover the circle with smaller cells.** Take every precision-6 cell that touches the circle's bounding box. For the same 2 km search that is **28 to 40 cells** depending on where the user stands (about 20 to 29 km², roughly 1.6 to 2.3 times the circle). More lookups, though adjacent cells often form contiguous prefix ranges, and far fewer wasted candidates. Libraries call this a **covering**; S2 and H3 have functions for it.

| Strategy | Lookups | Area scanned (2 km radius) | Use when |
|---|---|---|---|
| Own cell only | 1 | One cell | Never for a radius search: misses edges |
| Cell + 8 neighbours, shorter side ≥ r | 9 | ≈ 17× the circle | The default: simple, always correct |
| Covering with finer cells | 28–40 | ≈ 1.6–2.3× the circle | Dense areas where candidates are expensive |

<Trace title="Edges, neighbours, refine" steps={edges} takeaway="Read the cell and its 8 neighbours at a precision whose shorter side is at least the radius. Then compute the exact distance. Always." />

<Reveal q="What about the antimeridian (±180° longitude) and the poles?">

At ±180° the "east neighbour" wraps around to −180°; a correct neighbour function handles it, a naive one returns nothing. Near the poles, longitude cells become thin slivers, so "cell + 8" covers far less ground east-west than the table suggests. Most consumer products can mention these and move on (few restaurants at the poles); a global logistics or aviation system cannot, and that is one reason S2 exists.

</Reveal>

**Interview takeaway:** "A shared prefix proves closeness, a different prefix proves nothing, so I read the cell plus its 8 neighbours at a precision where the cell is at least as wide as the radius, then filter by exact distance."

<h2 id="quadtree">Chapter 5 · A map that splits where it is crowded</h2>

**The problem.** A search downtown returns twelve thousand candidates to refine. The same search at the edge of the desert returns four. Same radius, three thousand times the work. Geohash is a **fixed grid**: at precision 6, every cell on Earth is the same size, whether it holds 5,000 cafés or nothing.

**What it is.** A **quadtree** sizes cells to the data:

1. Start with one node covering the whole map.
2. **When a node holds more than a capacity (say 100 points), split it into four quadrants** and push its points down.
3. Repeat. Dense areas get deep, small cells; empty areas stay as one big leaf.

**Queries.** For a radius search, descend from the root into every node whose box intersects the circle's bounding box, collect points from the leaves, then refine by distance. For "the k nearest", walk leaves best-first: a priority queue ordered by the distance from the point to each node's box, popping nodes until k points are closer than the next box.

**It lives in memory.** A quadtree is a pointer structure built for one machine's RAM, not a database index. That is fine, because the data is small.

**Worked numbers (100 million places).** Assumptions: 8-byte id plus two 8-byte coordinates.

- Each entry is 24 bytes. 100,000,000 × 24 B = **2.4 GB**.
- With a capacity of 100 per leaf, at least 100,000,000 ÷ 100 = **1 million leaves**. A balanced tree would be log₄(1,000,000) ≈ **10 levels** deep; dense cities go deeper, deserts shallower.
- Nodes add a few million × tens of bytes: hundreds of MB at most. The whole index fits on one server, so you **replicate** it for throughput and availability rather than shard it for size. Same capacity-versus-throughput distinction as sizing a cache.

**Updates and rebuilds.** Building from scratch means inserting 100 million points: minutes of CPU, not milliseconds (benchmark it). Places change slowly (assumption: about a million edits a day, roughly 10 a second), so apply edits in place, rebuild periodically from the source-of-truth database to repair drift, and take a replica out of rotation while it rebuilds. Quadtrees are much less comfortable with **moving** points: every move is a delete and an insert, and points crossing in and out of busy leaves cause splits and merges. That is one reason moving objects get a different design (Part Three).

| | Geohash (fixed grid) | Quadtree (adaptive) |
|---|---|---|
| Cell size | Same everywhere at a precision | Shrinks where data is dense |
| Lives in | Any store with a sorted index or key lookup | Memory of a service you build |
| Updates | Change one string | Delete + insert, sometimes split/merge |
| Work per query | Varies wildly with density | Roughly even |
| Pick when | You want a database or Redis to do it | Density varies wildly and you own the index service |

<Trace title="Grow the tree" steps={quadtree} takeaway="Quadtrees split where it is crowded, live in memory, and want slowly changing data: apply rare edits, rebuild periodically, replicate." />

<Reveal q="Is geohash a kind of quadtree?">

Close to it. Each geohash character picks one of 32 children (5 bits) of the previous cell, so a geohash is a path down a fixed-depth tree of cells, flattened into a string. What a quadtree adds is **adaptivity**: it stops splitting where there is nothing to split. What geohash adds is **portability**: the tree becomes strings any database can sort.

</Reveal>

**A common slip:** "We'll put the quadtree in the database." Most databases have no quadtree column type, and a service you hand-roll needs a build, a refresh path and replicas. Say where it lives and how it is rebuilt.

**Interview takeaway:** "A quadtree splits a cell only where it holds too many points, so work per query stays even. It lives in memory, so I would replicate it, apply the slow edit stream in place and rebuild it from the database."

<h2 id="s2-h3">Chapter 6 · S2 and H3</h2>

Two production cell systems deserve a paragraph each in an interview. Both are **hierarchical** (cells contain smaller cells, each with a compact integer id) and both fix things geohash does badly. Treat the specifics below as intuition and check the projects' docs before quoting exact numbers.

**Google S2.** Project the sphere onto the six faces of a cube, cut each face as a quadtree, and number the cells along a **Hilbert curve**, a space-filling curve whose consecutive cells are always physically adjacent, unlike the Z-order curve, which jumps. Cell ids are 64-bit integers with 31 levels (0 to 30); the finest cells are around a square centimetre. Cells at a level are *roughly* equal in area anywhere on Earth, which geohash is not. S2's **region coverer** describes any shape (a circle, a delivery zone) as a small set of cells at mixed levels, which turns "points inside this shape" into a handful of integer range scans. Good when shapes are irregular or coverage is global.

**Uber H3.** A grid of **hexagons** (plus exactly 12 pentagons per resolution, which a sphere forces) with 16 resolutions, 0 to 15; each finer resolution has about 7 times as many cells. The property worth saying: **every hexagon has six neighbours, all with centres the same distance away.** A square has four edge neighbours and four corner neighbours √2 ≈ 1.41 times farther. So "this cell and its ring" means the same thing everywhere, which makes smoothing, flow and supply-and-demand maths (surge pricing, demand heatmaps) cleaner. The trade-off: hexagons do not nest perfectly (a parent's seven children only approximately cover it), so H3 suits analysis and aggregation better than exact containment. Uber open-sourced it. Name it in any Uber-flavoured question.

| | Geohash | S2 | H3 |
|---|---|---|---|
| Cell shape | Lat/lng rectangles | Quadrilaterals on a cube | Hexagons (+12 pentagons) |
| Id | Base32 string | 64-bit integer | 64-bit integer |
| Neighbours | 8, two different distances | 8, varied | 6, one distance |
| Equal-area-ish | No: shrink toward the poles | Roughly | Roughly |
| Strength | Simple; any sorted store | Coverings of arbitrary shapes; global | Rings, smoothing, aggregation |
| Say it for | Yelp, most "near me" | Region coverage, geofences at scale | Uber, surge, demand heatmaps |

<Reveal q="With S2’s Hilbert curve, do you still need to check neighbours?">

Yes. The Hilbert curve guarantees that consecutive cells *on the curve* are adjacent in space; it does not guarantee the reverse. Two adjacent cells can still be far apart on the curve. Any cell system has edges, so every radius query still reads a covering (or a cell and its ring) and refines by exact distance.

</Reveal>

**A common slip:** reciting "H3 has 16 resolutions" without a reason to use it. The reason is the uniform ring of neighbours; say that, and the details are optional.

<h2 id="off-the-shelf">Chapter 7 · PostGIS, Redis GEO and search engines</h2>

Before building an index, name the ones you can use.

**PostGIS (Postgres): R-tree over GiST.** An **R-tree** groups nearby objects into bounding rectangles, groups those rectangles into bigger ones, and so on; a query descends only into rectangles that intersect the search area. It indexes **shapes**, not only points: delivery zones, building footprints, routes. PostGIS builds R-tree-style indexes on Postgres's GiST framework:

```sql
CREATE INDEX places_location_gix ON places USING GIST (location);   -- location geography(Point, 4326)

-- everything within 2 km, nearest first
SELECT id, name,
       ST_Distance(location, ST_SetSRID(ST_MakePoint(77.5946, 12.9716), 4326)::geography) AS metres
FROM places
WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(77.5946, 12.9716), 4326)::geography, 2000)
ORDER BY metres
LIMIT 20;
```

`ST_DWithin` uses the index to filter by bounding box and then checks exact distance: the filter-then-refine move, done for you. For "the 10 nearest" with no radius, PostGIS supports index-assisted k-nearest-neighbour ordering with the `<->` operator. Longitude first in `ST_MakePoint`. Check the current PostGIS docs for exact behaviour on your version.

**Redis GEO.** Redis stores geo points in a **sorted set** whose score is a 52-bit interleaved geohash. A radius search computes the cell and its neighbours at a suitable precision, range-scans them, and filters by distance: this lesson, in a command.

```text
GEOADD drivers:blr 77.5946 12.9716 driver:42                         # longitude first
GEOSEARCH drivers:blr FROMLONLAT 77.5946 12.9716 BYRADIUS 2 km ASC COUNT 20 WITHDIST
ZREM drivers:blr driver:42                                            # it's a sorted set
```

`GEOSEARCH` arrived in Redis 6.2 and replaces the older `GEORADIUS`, which Redis now lists as deprecated. Two consequences: it is **in memory** (fast, great for moving points), and **members of a sorted set have no TTL of their own**: only whole keys expire, which shapes the driver design in Chapter 8.

**Search engines.** Elasticsearch and OpenSearch index `geo_point` fields (Lucene uses multi-dimensional point trees) and combine a distance filter with full-text relevance and facets in one query. Right when "near me" is part of a search with text ("vegan ramen near me"). The text side is in <a href={`${BASE}sd/lessons/search/#geo-vector`}>Search · near me</a>.

**Worked numbers: when Postgres is enough.** Assumption: a city-guide feature with 3 million places at 200 searches a second. The GiST index on 3 million points is small and hot in memory, each search touches a few hundred index entries, and 200/s is well within what a primary plus a read replica serves (benchmark your queries). Nothing custom is justified. A catalogue of 100 million places at 7,500 searches a second at peak is a different conversation (Chapter 14), and even then the database stays the source of truth.

| Option | Strength | Weakness | Pick when |
|---|---|---|---|
| **PostGIS** (R-tree via GiST) | Points and shapes, SQL, transactions | One primary for writes; read scaling via replicas | Moderate scale, already on Postgres: the default |
| **Geohash column + B-tree** | Works in any database or KV store | You own neighbours and refine | No spatial extension available |
| **Redis GEO** | In memory, very fast writes | Memory-bound; no per-member TTL | Moving objects, hot read paths |
| **Elasticsearch geo** | Geo + text + facets together | Near-real-time refresh; ops weight | Search with a location filter |
| **Custom quadtree / S2 / H3 service** | Tuned to your data and access pattern | You build, sync and run it | Very large scale or special maths (matching, surge) |

<Part n="Part Three" title="Things that move">

Restaurants sit still. Drivers report their position every few seconds. That one fact changes where the data lives.

</Part>

<h2 id="moving">Chapter 8 · Moving objects and update rates</h2>

**Static versus moving objects is the real design split.**

| | Static (restaurants, stores, chargers) | Moving (drivers, couriers, friends) |
|---|---|---|
| Writes | Rare edits | Every few seconds, per object |
| What matters | The current row | Only the **latest** position |
| Staleness | Minutes are fine | Seconds matter; silence means gone |
| Lives in | Database (+ geo index), cached per cell | Memory: Redis GEO or a location service |
| History | Is the data | Goes to a stream for analytics and billing, not the hot index |

**Worked numbers.** Say these out loud: the estimate is what licenses the design. Assumption for this example: 1,000,000 online drivers, each reporting every 4 seconds.

- **Writes:** 1,000,000 ÷ 4 s = **250,000 writes per second**, all day at peak, each overwriting the last.
- **Memory:** each latest position (id, lat, lng, heading, timestamp) is about 100 bytes raw. 1,000,000 × 100 B = **100 MB**. Even with several hundred bytes per entry of Redis overhead, it is **under 1 GB**. Capacity is trivial; you cluster for **throughput and availability**.
- **Ingress bandwidth:** 250,000 × 100 B = **25 MB/s**, about 200 Mbit/s. Real, not scary.
- **History, if you kept every point:** 25 MB/s × 86,400 s ≈ **2.16 TB per day**. That belongs in a log and cold storage, not in the index you query to find a driver.

**Update rate is a trade-off, not a constant.** Reporting every second gives smoother maps and fresher matching, but four times the writes (1,000,000 drivers is then 1,000,000 writes/s). Reporting every 15 seconds cuts load but a car at 50 km/h moves about 200 m between reports, which hurts matching accuracy. Practical levers:

- **Adaptive rate.** Fast while on a trip or moving, slow when parked or idle; faster near a pending offer.
- **Throttle at the source.** Skip an update when the driver has not moved more than a few metres.
- **Batch on the device.** Collect several GPS points and send once, if the use case tolerates the delay (trip history does; matching does not).
- **Different rates for different readers.** Matching needs fresh data about *available* drivers; the rider watching a car approach needs frequent updates for *one* driver only. Do not pay the high rate for everyone.

**Why not the primary database?** Every update rewrites a row and its index entries (and the geohash index entry whenever the driver crosses a cell), appends to the write-ahead log and replicates, 250,000 times a second, to preserve history nobody queries from there. That is far beyond the comfortable write rate of one primary, and a position four seconds old is worthless.

**The design: an in-memory geo grid, sharded by region, keyed by cell, with TTLs.**

<Figure caption="Location ingestion. The hot path keeps only the latest position in memory; the full history flows to a log for trips, billing and models.">
  <Mermaid code={`flowchart LR
    D["Driver app\nevery 4 s"] -->|"WebSocket"| G["Location gateway\nstateful connections"]
    G --> L["Location service"]
    L -->|"GEOADD to cell key\nTTL 90 s"| R[("Redis GEO\nsharded by city")]
    L -->|"HSET driver:id\nlat, lng, ts, status"| R
    L -->|"append"| K[("Kafka\nlocation stream")]
    K --> H[("Cold storage\ntrip history, ETA models")]`} />
</Figure>

- **Shard by region** (city or metro). A "drivers near this point" query almost always stays in one region, so it hits one shard. Sharding by driver id would make every nearby query ask every shard.
- **Key by cell and time bucket**, because Redis can expire keys but not members of a sorted set: write each update into `drivers:{city}:{geohash5}:{bucket}`, where the bucket is the current 30-second window, with a 90-second key TTL. A driver who goes silent stops appearing in new buckets, and old buckets expire on their own. A query reads the current and previous bucket for the 9 cells around the rider (18 keys in one pipeline).
- **Keep one authoritative record per driver:** `driver:{id}` holds latest lat, lng, timestamp and status (AVAILABLE, OFFERED, ON_TRIP). Cell keys may briefly hold a stale copy (a driver who crossed into a new cell still sits in the old cell's bucket until it expires), so the matcher **dedupes candidates by id and re-checks each one against this record**: fresh timestamp (say under 15 s), status AVAILABLE, real distance from the latest position.
- **The simpler alternative:** one geo key per city plus a `lastseen:{city}` sorted set scored by timestamp, and a sweeper every few seconds that removes drivers older than 30 s from both. Fewer keys, one moving part (the sweeper) to monitor.

**Per-shard check.** Assumption: the largest city has 60,000 drivers online. 60,000 ÷ 4 = **15,000 writes/s** on that shard, comfortable for one in-memory node (Redis-class nodes handle very roughly 100,000 simple operations a second; benchmark). If a region outgrows one node, split it by cell, and remember a query near the split reads both sides.

<h2 id="matching">Chapter 9 · One driver, two riders</h2>

**The problem.** Two riders outside the same bar tap "Request" within the same second. Both requests find driver 4417, sixty metres away. Both send him an offer. He accepts the first; the second rider watches a car approach, then turn away. The post-mortem is one line: *two matchers read AVAILABLE before either wrote OFFERED.*

**Matching is a pipeline: candidates → shortlist → ETA → claim → offer.**

1. **Candidates** from the geo grid: the rider's cell and its neighbours, deduped, each re-checked against `driver:{id}` (fresh, AVAILABLE, right vehicle type). Typically dozens.
2. **Shortlist** the ~10 nearest by straight-line distance. Cheap.
3. **ETA** for the shortlist from the routing service (next chapter). Road time, not crow-flies distance, decides who is closest.
4. **Claim** the best driver atomically, with an expiry.
5. **Offer** it to the driver's app; on accept, the ride and driver both move to ASSIGNED. On decline or timeout, release and go to the next candidate.

**The race and the claim.** "Check status, then set OFFERED" is two steps, and two matchers can both pass the check. The fix is the contention pattern: **one atomic conditional write**.

```text
SET hold:driver:4417 ride:R1 NX PX 15000      # succeeds for exactly one ride
# the other matcher gets nil, so it tries its next candidate

# on accept: promote only if the hold is still ours (a small Lua script makes this one atomic step)
if GET hold:driver:4417 == "ride:R1" then set driver status ASSIGNED, record on the ride, DEL the hold
```

- **Holds expire.** If the driver ignores the offer, or the matcher crashes mid-offer, the key expires after 15 s and the driver is available again. A hold without an expiry is a leak.
- **The durable record.** The assignment is committed in the rides database with a conditional update, so a retried accept is idempotent and a rider never gets two cars:

```sql
UPDATE rides SET driver_id = 4417, status = 'ASSIGNED'
WHERE id = 'R1' AND status = 'MATCHING';   -- 1 row updated: we won. 0 rows: already assigned or cancelled
```

- **Idempotent requests.** A rider double-tapping "Request" sends the same idempotency key, so one ride is created, not two.

**Worked numbers.** Assumption: 20 million rides a day. 20,000,000 ÷ 100,000 (≈ seconds in a day) = **200 requests/s**, about **600/s** at a 3× peak. Each request: one pipelined read of 18 cell keys, ~10 ETA calls, one or two `SET NX`. So the routing service sees about 600 × 10 = **6,000 ETA calls/s**. Calling it for all 40 candidates would be 24,000/s: cheap filter first, expensive refine second, the same move as cells then haversine.

<Reveal q="Should a matcher grab the nearest driver for each request as it arrives, or wait and match several at once?">

Greedy, request by request, is simple and fast, and right most of the time. Its weakness shows in dense, busy areas: giving the nearest driver to the first request may leave the second with a driver ten minutes away, when swapping would have given both four-minute pickups. **Batch matching** collects requests and available drivers in an area for a second or two and solves a small assignment problem minimising total ETA. It costs a little latency for better global outcomes. Say greedy first, and offer batching for hot areas (Chapter 11).

</Reveal>

<h2 id="eta-routing">Chapter 10 · ETA, not distance</h2>

**Straight-line distance is a filter, not an answer.** The nearest courier is 400 metres away and the app promises him in two minutes. He arrives in nineteen: there is a river between them and the nearest bridge is three kilometres north. Roads bend, rivers need bridges, one-way streets loop, and traffic changes speed by the hour. The decision "which driver?" must use **ETA**: estimated travel time over the road network.

**Intuition for how ETA is computed:**

- **The road graph.** Intersections are nodes, road segments are edges, each edge's weight is its expected travel time *now* (length ÷ live speed from recent GPS traces on that segment).
- **Snap to the graph.** GPS points are noisy; "map matching" snaps the driver and the pickup to the most likely road segment. A spatial index helps here: finding road segments near a point is a geo query.
- **Shortest path.** Dijkstra's algorithm is correct but explores in every direction. **A\*** steers the search toward the goal with a distance-based heuristic. At continental scale, systems precompute shortcuts (**contraction hierarchies** are the classic technique) so a query explores a tiny fraction of the graph and answers in milliseconds. Live traffic complicates the precomputation; variants exist that re-weight quickly (look these up).
- **Correct it with data.** Real ETAs blend the route time with learned corrections (time of day, pickup difficulty, how long drivers really take to turn around).

    B -->|"routing service\nroad graph + live traffic"| C["10 ETAs"]

</Figure>

**This is also the answer to "Design Google Maps directions".** That question is mainly a **graph shortest-path** problem (road graph, A*, contraction hierarchies, traffic ingestion), not a proximity-index question. <h2 id="hot-cells">Chapter 11 · Hot cells in dense places</h2>

**A hot cell is a concentration problem, and you have to say which kind.** Imagine a 60,000-seat stadium letting out. By two minutes after the final whistle the matching dashboard for one cell is red: hold conflicts climbing, offers timing out, riders cancelling. The request rate is *three a second*, and the system handles six hundred. What is on fire?

**1. Demand piles onto too little supply (the stadium).** 60,000 fans; assumption: 10% want a ride within 30 minutes: 6,000 ÷ 1,800 s ≈ **3.3 requests/s**. Throughput is trivial. The problem is that every request sees the same few hundred drivers, they all race for the same holds, most claims fail and retry, and pickups get worse. Fixes:

- **Batch matching** for that area every second or two (Chapter 9's Reveal): fewer conflicts, better total ETA.
- **Widen the ring** when the shortlist is exhausted: the next ring of cells, then the next.
- **Surge pricing**, intuitively: per cell per minute, compare demand (requests, app opens) with supply (available drivers); when the ratio climbs, raise the price multiplier along a curve, smoothed over the cell's neighbours (H3 rings make this uniform), capped by policy. Higher prices dampen demand and pull drivers in from nearby cells. Real models are richer; the shape is ratio → multiplier → smooth → cap.
- **Pickup zones and queues** at venues: a physical design fix that turns chaos into a line.

**2. Too many reads on one cell (downtown at lunch, the "cars on the map" view).** Here throughput is the problem. Fixes: cache per cell (next chapter), finer cells or a covering so each query reads fewer candidates, `COUNT` limits on geo searches, read replicas of the hot shard.

**3. One region outgrows its shard (New Year's Eve in one city).** Location writes for a city land on one shard. 60,000 drivers is 15,000 writes/s, which is fine; if one region outgrows a node, **split it by cell** across shards. Queries near the split read both; a cell-to-shard map (like a quadtree, it can be finer where it is dense) routes them.

| Hot cell | Symptom | First fix |
|---|---|---|
| Stadium, airport rank | Hold conflicts, timeouts, cancels, low QPS | Batch matching, wider ring, surge, pickup zones |
| Downtown lunch searches | One cell's keys take most reads | Per-cell cache, finer cells, replicas |
| One giant city | One location shard near its write limit | Split the region by cell |

<h2 id="cell-cache">Chapter 12 · Cache by cell, not by coordinates</h2>

**The problem.** A first design caches results under `nearby:{lat}:{lng}`. After a day it has eleven million distinct keys and a hit ratio of 0.3%. Every user stands somewhere slightly different, so every key is unique: a very expensive write-only cache.

**Cache by cell, not by coordinates.** Exact coordinates are unbounded user input: the key-cardinality trap from <a href={`${BASE}sd/lessons/caching/#keys`}>Caching · naming things</a>. Snap to a cell and the keys become bounded and shared by everyone nearby. Two layers, each with the four promises (key, TTL, invalidation, failure):

**Layer 1: cell contents (makes the index cheap).**

- **Key:** `cell:v1:{geohash6}:{category}` → the compact candidate list for that cell: id, lat, lng, rating, review count, opening hours (~40 bytes each).
- **TTL:** 30 minutes with jitter, since places change rarely.
- **Invalidation:** a place edit deletes **exactly one key**, the cell containing it (both cells if it moved), driven by CDC from the places table, with the TTL as backstop. Searches read the cells they need and merge, so a neighbour's search sees the change too.
- **Failure:** the database index can serve misses at the miss rate; check it can survive the full load before calling the cache optional.

**Layer 2: first-page results (absorbs repeated popular queries).**

- **Key:** `nearby:v1:{geohash7}:{category}:{filtersHash}` → the ranked top 20 ids. Precision 7 is about 150 m, so everyone standing in those few blocks shares one key. Normalise filters (sorted, lowercase) before hashing.
- **TTL:** 5 minutes with jitter, because ranking includes "open now" and ratings drift. Better: cache the hours and evaluate "open now" at read time, so the TTL can stay long without serving closed restaurants.
- **Invalidation:** TTL only. A precise delete would have to find every result containing the edited place; a short TTL is the honest answer.
- **Accuracy cost:** ranking is computed from the cell's centre, so distances shown can be off by up to about 110 m (half the cell's diagonal, 107 m at 13° by script). Fine for "near me"; recompute exact distances from the cached ids if the UI shows metres.

**Worked numbers: why layer 1 lives in process at large scale.** Assumption: a dense downtown has 100 restaurants per km². A precision-6 cell (≈ 0.73 km² at 13°) holds about 73 × 40 B ≈ **2.9 KB**. A 1 km search reads about 8 to 15 cells (call it 12) ≈ **35 KB per search**. At 7,500 searches/s that is about **260 MB/s** out of a Redis cluster. Possible, wasteful, and the entire index is only 2.4 GB, so at this scale the index service keeps every cell's list **in its own memory** (refreshed from CDC) and Redis keeps only layer 2. At moderate scale, Redis for both is fine.

<h2 id="ranking">Chapter 13 · Closest is not best</h2>

User research on a nearby-search app returns a line worth underlining: *"It keeps showing me the closest place, which is a petrol station with a sandwich fridge."* Sorting by distance alone is wrong for discovery. A usable ranking combines a few signals, after the hard filters:

1. **Hard filters first:** category, **open now**, price, within the radius.
2. **Distance, with decay:** a smooth function such as e^(−d / 1 km), so 300 m and 400 m barely differ but 300 m and 3 km do.
3. **Quality, smoothed:** a 4.8 with 12 reviews is weaker evidence than a 4.2 with 800. A **Bayesian average** pulls thin ratings toward a prior: (C × m + Σ ratings) ÷ (C + n), with m = 3.8 (the typical rating) worth C = 50 reviews.
4. **Relevance and personal signals** (text match, the user's history) if the product has them; see <a href={`${BASE}sd/lessons/search/#relevance`}>Search · relevance</a>.

**Worked numbers.** Score = 0.5 × (smoothed rating ÷ 5) + 0.5 × e^(−distance in km).

| | Raw | Smoothed rating | Distance term | Score |
|---|---|---|---|---|
| A | 4.2★, 800 reviews, 300 m | (190 + 3,360) ÷ 850 ≈ 4.18 | e^−0.3 ≈ 0.74 | 0.5 × 0.835 + 0.5 × 0.741 ≈ **0.79** |
| B | 4.8★, 12 reviews, 1.5 km | (190 + 57.6) ÷ 62 ≈ 3.99 | e^−1.5 ≈ 0.22 | 0.5 × 0.799 + 0.5 × 0.223 ≈ **0.51** |

A wins: well established, and five times closer. The 0.5/0.5 weights are a product decision you would tune with experiments; say that.

**Open now is harder than it looks.** Hours are in the *place's* local time zone, some spans cross midnight (18:00–02:00), holidays override them, and daylight-saving changes shift them. Store hours as structured intervals per weekday in local time plus a time-zone id, and evaluate at query time against the current instant.

</Figure>

<h2 id="yelp">Chapter 14 · Yelp walkthrough</h2>

**0:03 · Roadmap and requirements**

> "Six minutes on requirements and scale, a couple on entities and the API, a working design, then two or three deep dives and a wrap-up. Functional: users search for places near a location, filtered by category and open-now; they see a place's details; they can post a review and rating. Out of scope: reservations, photos, ads, the business-owner portal, personalised recommendations. Places are added and edited by an internal service I'll treat as a writer."

**0:05 · Non-functionals with numbers** (assumptions for this example)

> "100 million places. 50 million daily users, five searches each: 250 million searches a day, about 2,500 a second, 7,500 at a 3× peak. Place edits, about a million a day, roughly 10 a second, so reads outnumber writes by hundreds to one. Search p99 under 200 milliseconds. Search favours availability; a new or edited place should be visible within minutes. Storage: a place row about 1 KB, so 100 GB, and the geo part (id plus two coordinates, 24 bytes each) is only 2.4 GB. That number will matter."

**0:08 · The bridge:** "Read-heavy radius search over 100 million mostly static places, 7,500 per second at peak, minutes of staleness allowed, and a geo index small enough to hold in memory."

**0:09 · Core entities:** Place (id, name, location, category, hours with a time zone, rating aggregate), Review (one place, one user), User. The rating aggregate on Place is derived from reviews.

**0:11 · API**

> "Radius capped at, say, 25 km, defaulting to 1 km. The cursor encodes the last item's score and id so pages are stable. Reviews take an idempotency key because a double-tap should not post twice."

**0:15 · High-level design**

> "Client → load balancer → stateless search service. It asks a geo index for candidates, ranks them, hydrates the top 20 from a place cache and returns. Postgres is the source of truth. **0:25 · Deep dive 1: finding candidates**

> "A B-tree on latitude would read a strip around the planet, so I need a cell index. Options: PostGIS on read replicas, a geohash column, or an in-memory index. At 7,500 searches a second and a 2.4 GB geo dataset, I'll hold the whole index in memory in a small service: a hash map from precision-6 geohash cell to a compact list of places. A 1 km search reads every precision-6 cell touching the 2-by-2-km box around the user, about 8 to 15 cells because precision-6 cells are only 0.6 km tall, then computes exact distance and drops anything beyond 1 km. That covering handles cell edges; a café 20 metres across a boundary is still found. For larger radii I switch to precision 5 with the cell plus 8 neighbours. Four replicas give throughput and let one rebuild from Postgres while three serve; CDC applies the ten edits a second in between. If the index service is down, PostGIS on a replica is the slow fallback."

**0:31 · Deep dive 2: caching and hot cells**

> "Downtown at lunch, the same queries repeat. I cache the first page per precision-7 cell, about 150 metres: key `nearby:v1:{geohash7}:{category}:{filtersHash}`, top 20 ids, five-minute TTL with jitter. Open-now is evaluated at read time from cached hours, so a closed place never shows. Invalidation is TTL-only for results. Place details are cache-aside on `place:{id}` with delete-on-write from CDC. If Redis is down, the index service handles full load because it is in memory, so the cache is not load-bearing. Distances in cached results are from the cell centre, off by at most about 110 metres; I recompute them for display."

**0:35 · Deep dive 3: ranking**

> "Filter by category, open-now and radius; then score with a blend of smoothed rating and distance decay: a Bayesian average so a 4.8 with twelve reviews does not beat a 4.2 with eight hundred, and e to the minus distance so 300 and 400 metres barely differ. Weights tuned by experiment. Hours are stored per weekday in the place's local time with a time-zone id."

**0:38 · Wrap-up**

> "Radius search via an in-memory cell index with covering and exact refine, cached per cell, ranked by rating and distance; Postgres is the truth and feeds everything through CDC. At 10× searches, add replicas: the index is read-only and 2.4 GB. At 10× places, 24 GB still fits in memory, but I'd shard the index by region. If the Postgres primary fails, edits pause for failover; search keeps working. I'd monitor search p99, candidates per query by cell, cache hit ratio, and CDC lag. With more time: text search with Elasticsearch."

**Check the numbers yourself:** 50M × 5 = 250M/day ÷ 10⁵ = 2,500/s; × 3 = 7,500/s. 1M edits ÷ 10⁵ = 10/s. 100M × 1 KB = 100 GB; 100M × 24 B = 2.4 GB. A precision-6 cell is about 1.19 × 0.61 km at 13°, so a 1 km radius needs more than the 3 × 3 block; covering the 2 × 2 km box takes 8 to 15 such cells depending on where the user stands (script-checked). Precision 7 is about 150 m square, half-diagonal ≈ 107 m.

<h2 id="uber">Chapter 15 · Uber walkthrough</h2>

**0:05 · Roadmap and requirements**

> "Drivers share their location while online; a rider requests a ride from a pickup to a drop-off and is matched with a nearby driver, who can accept or decline; both see each other's live location until the trip ends. Out of scope: payments, ratings, scheduled rides, pooling. I'll say where surge would sit."

**0:08 · Non-functionals with numbers** (assumptions for this example)

> "1 million drivers online at peak, each reporting every 4 seconds: 250,000 location writes a second. 20 million rides a day is about 200 requests a second, 600 at peak. An offer within a few seconds. Locations fresh to within about 5 seconds. Assignment strongly consistent: never two riders on one driver, never two drivers for one ride. Location ingest favours availability: losing one update is fine, the next arrives in 4 seconds."

**0:11 · The bridge:** "A huge stream of ephemeral writes, a modest rate of matches that need a strong claim, and live updates both ways."

**0:12 · Core entities:** Rider; Driver; Ride (durable, status, assigned driver); DriverLocation (ephemeral, latest only); Offer (a time-limited hold of one driver for one ride).

**0:15 · API**

```text
WS   /driver/connect                    driver → { lat, lng, heading, ts } every 4 s
                                        server → offer { rideId, pickup, expiresAt }
POST /rides  { pickup, dropoff, product }   (Idempotency-Key) → 202 { rideId, status: MATCHING }
POST /offers/{rideId}/accept | /decline     → 200 | 409 if the offer expired
WS   /rides/{id}/live                   rider ← status changes, driver location
```

> "Locations ride a persistent connection: at 250,000 a second, per-request HTTP overhead adds up, and the same socket delivers offers. Ride creation is idempotent so a double-tap makes one ride. Accept returns 409 if the hold already expired."

**0:20 · High-level design**

> "Driver app → WebSocket gateways → location service → Redis GEO sharded by city, plus a Kafka stream for history. Rider app → ride service, which writes the ride to Postgres as MATCHING and hands it to matching. Matching reads candidates from the geo grid, gets ETAs from a routing service, claims a driver with a hold, and pushes the offer through the gateway holding that driver's socket. On accept, the ride service records the assignment and subscribes the rider's connection to the driver's location channel."

**0:32 · Deep dive 1: storing locations**

> "250,000 writes a second of latest-only data. A database primary would rewrite rows, indexes and the log for history nobody queries there, so it's memory. 1 million drivers times about 100 bytes is 100 MB, so the cluster is for throughput and availability. Shard by city, since a nearby query stays in one city; the biggest city at 60,000 drivers is 15,000 writes a second on its shard. Redis can't expire members of a sorted set, so each update goes into a key per precision-5 cell per 30-second bucket with a 90-second TTL: silent drivers vanish on their own. Each driver also has one hash with latest position, timestamp and status, and the matcher re-checks every candidate against it. Every update also goes to Kafka, about 25 MB a second, two terabytes a day, for trip history and ETA models, compressed into cold storage."

**0:39 · Deep dive 2: matching without double assignment**

> "Matching reads the rider's cell and 8 neighbours from the current and previous buckets, 18 keys in one pipeline, dedupes, keeps fresh AVAILABLE drivers, shortlists ten by straight-line distance, and asks the routing service for road ETAs: 600 requests a second times ten is 6,000 ETA calls. Then the claim: SET NX on the driver's hold key with a 15-second expiry. Exactly one matcher wins; a loser moves to its next candidate immediately. Accept is a compare-and-set, only if the hold is still this ride's, and the assignment commits in Postgres with a conditional update on status MATCHING, so retries are harmless. Decline or timeout: the hold expires and we offer the next candidate. If the shortlist runs out, widen the ring."

**0:46 · Deep dive 3: hot cells and surge**

> "A stadium emptying is only about 3 requests a second; the problem is supply. All those requests see the same few hundred drivers and race for holds. For areas like that I'd batch: every couple of seconds, match waiting riders and free drivers jointly to minimise total ETA. Surge sits here: per H3 cell per minute, demand over supply, mapped to a capped multiplier and smoothed over the neighbouring ring. Separately, the cars-on-the-map view is the biggest read load, 2 million open apps every 5 seconds is 400,000 reads a second, so I serve it from per-cell snapshots refreshed every few seconds, never from the matching path."

**0:52 · Wrap-up**

> "Locations in memory, sharded by city, expired by silence; matching by distance then ETA, with an atomic expiring hold and a conditional commit; live updates over WebSockets with per-trip pub/sub. At 10× drivers, 2.5 million writes a second: split big cities by cell across shards and add gateways. If a city's Redis shard fails, a replica takes over; we lose a few seconds of positions and drivers refill it within 4 seconds. If the routing service is slow, match on straight-line distance with a wider margin. I'd monitor offer acceptance rate, time-to-match p99, hold conflict rate per cell, location freshness lag, and gateway connection counts."

**Check the numbers yourself:** 1,000,000 ÷ 4 = 250,000/s. 1M × 100 B = 100 MB. 250,000 × 100 B = 25 MB/s × 86,400 ≈ 2.16 TB/day. 20M ÷ 10⁵ = 200/s; × 3 = 600/s; × 10 ETAs = 6,000/s. 60,000 ÷ 4 = 15,000/s. 2M ÷ 5 = 400,000/s. Stadium: 6,000 ÷ 1,800 s ≈ 3.3/s.

<Reveal q="Tinder: why not keep profiles in Redis GEO like drivers?">

Because they do not move like drivers. A profile's location changes when the user opens the app (a few times a day, not every 4 seconds), so the write rate is modest and the data must persist with the profile. The real cost is in the filters and the exclusion of already-seen profiles, not the geo lookup. A database or search index with a geo filter, plus a per-user "already swiped" structure, fits. Choose the store from the write rate, not from the word "location".

</Reveal>

<h2 id="interview-script">Say it in the room</h2>

The interviewer draws a dot on a map and asks: *"How would you find the ten closest things to this?"* Answer with what the index actually reads, not with "an index on latitude and longitude".

<AnswerModes id="geo-main-answer" q="How would you find the ten closest things to this point?">
<Fragment slot="short">

"A B-tree on latitude returns a band around the whole planet, so I use cells: geohash, where a shared prefix means the same cell. A query reads the user's cell plus its eight neighbours, at a precision whose cell side is at least the radius, because points metres apart can sit on either side of a cell edge, then computes exact distance on those candidates. At moderate scale PostGIS with a GiST index does this for me. If the things move, like drivers, I keep only their latest position in an in-memory grid sharded by region, with TTLs."

</Fragment>
<Fragment slot="medium">

"A B-tree on latitude returns a band around the whole planet, and adding longitude to the index does not narrow the seek, so I need an index that keeps both dimensions together. I map each point to a cell, geohash, and store the cell id with a normal index. A query reads the user's cell **plus its eight neighbours**, at a precision whose cell side is at least the radius, then computes the exact distance and drops the rest. At moderate scale, PostGIS with a GiST index does exactly this. If density varies a lot and I own the index, a quadtree adapts cell size in memory.

The next question is whether things move. Static places go in the database and are cached per cell, never by raw coordinates. Moving things like drivers, a million every 4 seconds, are 250,000 writes a second but only about 100 MB, so they go in an in-memory grid sharded by region, with TTLs so silent drivers disappear. Matching shortlists by distance, decides by road ETA, and claims a driver with an atomic, expiring hold so two riders never get the same car."

</Fragment>

Everything in the medium answer, plus the depth to offer when asked: precision 6 cells are 1.2 × 0.6 km, so a 2 km radius needs precision 5 with cell + 8 or a covering of 28 to 40 finer cells; quadtree (uneven density, in memory, replicated), S2 (coverings of shapes) and H3 (equidistant neighbours for surge) as the alternatives; driver cell keys per 30-second bucket with a 90-second TTL plus a per-driver record re-checked by the matcher; matching as `SET NX PX` hold, compare-and-set on accept and a conditional UPDATE on the ride row; hot cells named as supply, read or write problems; caching by cell with one-key invalidation. The five follow-ups below are the usual probes.

**Five follow-ups you will get:**

<Reveal q="1 · What if the closest result is just across a cell boundary?">

Two points metres apart can have different prefixes: a shared prefix proves closeness, a different one proves nothing. So I always read the cell and its 8 neighbours (or a covering of the circle), at a precision whose shorter cell side is at least the radius, then filter by exact distance.

</Reveal>

<Reveal q="2 · Downtown has thousands of places per cell; the suburbs have three. Does that matter?">

Yes: candidate counts, and so latency, vary wildly with a fixed grid. Options: finer cells or a covering in dense areas, a `COUNT` limit with distance ordering, or a quadtree that splits only where it is crowded, so each leaf holds at most about 100 points. At 100 million places the whole index is 2.4 GB, so an in-memory quadtree with replicas is reasonable.

</Reveal>

<Reveal q="3 · Why not store driver locations in the database?">

250,000 writes a second, each rewriting a row, an index entry and the log, for history nobody queries there. Only the latest position matters and it is about 100 MB in total, so it lives in memory (Redis GEO sharded by city, keyed by cell and time bucket with TTLs) and the history goes to Kafka.

</Reveal>

<Reveal q="4 · Two riders get matched to the same driver. How do you prevent it?">

The claim is one atomic conditional write: `SET hold:driver:{id} {rideId} NX PX 15000`. Exactly one succeeds; the other moves to its next candidate. The hold expires if the driver does not respond or the matcher crashes, and the accept commits with a conditional update on the ride's status, so retries are harmless.

</Reveal>

<Reveal q="5 · How would you cache nearby search?">

By cell, never by raw coordinates (unbounded keys, near-zero hits). Cell contents keyed `cell:v1:{geohash6}:{category}`, invalidated by deleting the one cell an edited place sits in; first-page results keyed by a ~150 m precision-7 cell plus normalised filters, with a 5-minute jittered TTL, and open-now evaluated at read time. The index can carry the load without the cache, so it is not load-bearing.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| "Near me", "within X km" | B-tree on lat returns a planet-wide strip, so a cell index |
| Geohash | Interleaved bits, base32; shared prefix = same cell; **+ 8 neighbours, then exact distance** |
| Choosing precision | Cell's shorter side ≥ radius for "cell + 8"; precision 5 ≈ 4.9 km, 6 ≈ 1.2 × 0.6 km, 7 ≈ 150 m |
| Many wasted candidates | A covering of finer cells, or a quadtree |
| Density varies wildly, you own the index | Quadtree in memory; replicas; rebuild periodically |
| Shapes (zones, geofences) | R-tree (PostGIS GiST); filter by box, refine with exact geometry |
| Global coverage, irregular regions | S2 cells and coverings |
| Surge, heatmaps, neighbour smoothing | H3 hexagons: six equidistant neighbours |
| Moderate scale, on Postgres | PostGIS `ST_DWithin`: don't build |
| Things move every few seconds | Compute writes/s and MB; in-memory grid by region and cell; TTL by silence; history to Kafka; tune the update rate |
| Assign one driver | Shortlist by distance → ETA → atomic hold with expiry → conditional commit |
| "Which driver is closest?" | ETA over the road graph, not crow-flies distance |
| Stadium, airport | Supply problem: batch matching, wider ring, surge, pickup zones |
| Hot read cell | Per-cell cache, finer cells, replicas |
| Cache nearby | Key by cell, never by coordinates; one-cell invalidation |
| Ranking | Filters, then smoothed rating × distance decay; open-now in local time |
| Directions | Graph shortest path (A*, contraction hierarchies), not a geo index |

## Five mistakes to leave behind

1. **"Index lat and lng."** Say what it reads: a strip around the planet.
2. **Geohash without neighbours.** The café 22 m away is behind the edge. Cell + 8, then exact distance.
3. **Moving objects in the primary database.** Compute 250,000 writes/s and 100 MB first; the answer is memory with TTLs.
4. **Matching without an atomic, expiring claim.** Check-then-set double-books; a hold without expiry leaks drivers.
5. **Caching by raw coordinates.** Unbounded keys, a hit ratio near zero. Cache by cell.

**Keep it warm:** a 12-minute mini-design, *"find nearby EV charging stations, with live availability"*: a static geo index, a fast-changing availability layer, and cell caching. Then a weekend mock of **Yelp** or **Uber** on the clock, using Chapters 14 and 15 as the answer key afterwards, not before.
