<h2 id="prologue">Prologue · Adding one cache node</h2>

Here is an incident that happens in real systems. A team runs a cache cluster of 10 nodes. The dashboards say the nodes are running hot, so an engineer adds an 11th node. It takes four minutes. A moment later the database's read rate jumps from 20,000 per second to 180,000 per second and stays there.

Every cache node is up and healthy. But each of them is now missing most of the keys that users ask for. Why did adding one node out of eleven lose about nine tenths of the cache, and not one tenth?

The cache placed keys with `node = hash(key) mod N`. When N went from 10 to 11, the answer to that formula changed for about 91% of the keys. Those keys are still sitting in memory on the node the old formula pointed at, and nobody will ask for them there again.

This lesson is about cutting data across machines so that changing the number of machines moves as little data as possible. Then it covers everything that comes with it: copies, disagreements between copies, failures, and routing.

**Trigger words:** any "design a distributed X" (cache, key-value store, object store, counter), "how does it scale horizontally?", "what happens when you add a node?", "what happens when a node dies?"

**Why it matters for interviews.** "Design a distributed cache (Redis)" and "design a key-value store (Dynamo)" are common infra rounds, and "design S3" leans on this lesson too. In these rounds you cannot hide behind a box labelled "database", because you are building the database. Two skills matter: starting from a blank page with no product to lean on, and drawing the ring, the arcs and the replica walk while you talk. Each chapter ends with something you can say out loud.

<h2 id="why-partition">Chapter 1 · Why partition at all</h2>

**What is it?** **Partitioning** (also called sharding) splits a dataset by key so that each machine holds and serves only part of it. **Replication** keeps copies of the same part on several machines. They solve different problems, and every system in this lesson does both.

**Why do we need it?** Say you want a shopping-cart service. The easy design is one Postgres or MySQL box. Before you accept it, ask three questions: how much data, how many writes per second, and what happens to the business if that one box is down for an hour. You partition for one of three reasons, and you should say which one applies:

1. **Capacity.** The data does not fit on one machine's disk or memory.
2. **Throughput.** One machine cannot take the write rate. Replicas scale reads, never writes, because every replica replays every write.
3. **Blast radius.** One machine's failure, slow query or hot key should take down a slice of users, not all of them.

**Worked numbers.** Assumption for this example: 2 billion items of 1 KB each, which is **2 TB** of raw data, with peak traffic of **200,000 reads/s and 50,000 writes/s**. One machine with a 4 TB disk could hold one copy. It cannot take 50,000 durable writes per second while also serving 200,000 reads, and its failure would stop every cart. So: partition for throughput and blast radius, replicate for survival. Chapter 17 finishes this sizing.

**How to judge a scheme.** A partitioning scheme is judged on four days, not one:

1. The normal day: is the load even?
2. The day you **add a node**: how much data moves?
3. The day a node **dies**: who takes its load?
4. The day one key becomes **famous**: can anything spread it?

<Reveal q="Someone asks: 'Why not just buy a bigger box?' When is that the right answer?">

Often. Vertical scaling has no routing, no cross-partition queries and no rebalancing. If the data fits, the write rate fits with headroom, and a replica with fast failover covers the failure case, a bigger box is the senior answer. The <a href={`${BASE}sd/lessons/databases/#capacity`}>databases lesson</a> works through "will it fit?" Partition when the numbers say you must, and say which number forced it.

</Reveal>

**A common slip:** saying "we'll shard it" with no reason attached. Name the number that forced the cut: capacity, write throughput, or isolation.

**Interview takeaway:** "I would partition because write throughput is 50,000/s and one node tops out well below that, and I would replicate three times so one node failing does not lose data."

<h2 id="mod-n">Chapter 2 · Hash mod N and its cost</h2>

**What is it?** The simplest placement rule: `node = hash(key) mod N`, where N is the number of nodes. It spreads keys evenly, needs no stored state, and every client computes the same answer.

**Why does it break?** It is fine as long as N never changes. When N changes, **a key stays put only if its hash leaves the same remainder under both values of N**. Almost nothing does.

**How much moves, 10 → 11?** Remainders mod 10 and mod 11 repeat together every 110 values. Within each block of 110 consecutive hash values, a key stays only when `h mod 10 = h mod 11`, which happens for exactly h = 0 to 9: 10 values. So **100 of every 110 keys move, which is 10/11 ≈ 91%**. In general, going from N to N + 1 moves **N/(N + 1)** of the keys. That gets *worse* as the cluster grows.

```python
def moved_fraction(old_n: int, new_n: int, keys: int = 1_000_000) -> float:
    moved = sum(1 for h in range(keys) if h % old_n != h % new_n)
    return moved / keys

print(moved_fraction(10, 11))   # about 0.909
print(moved_fraction(10, 9))    # about 0.900  (one node died)
print(moved_fraction(10, 20))   # about 0.500  (doubling)
```

| Change | Fraction of keys that move | The ideal (the new or dead node's share) |
|---|---|---|
| 4 → 5 nodes | 80% | 20% |
| 10 → 11 | 91% | 9% |
| 16 → 17 | 94% | 6% |
| 10 → 9 (one dies) | 90% | 10% |
| 10 → 20 (doubling) | 50% | 50% |

The Java checker for this lesson (`tests/java/pattern-partitioning/Check.java`) computes each row exactly and also measures 91% on 100,000 real hashed keys. Doubling moves exactly half the keys (each node sends half its keys to its new partner), which is the minimum for doubling. Some systems grow only by doubling for that reason. Everyone else wants to add one node at a time.

**What 91% means in practice.**

- For a cache, it is a near-total cold start. 91% of reads miss at once, and the database feels the miss rate (see the <a href={`${BASE}sd/lessons/caching/#why-cache`}>arithmetic of misses</a>).
- For a store, it is moving 91% of the data over the network to add 10% capacity.

**Common slips:** "use a prime number of nodes" or "rehash in the background". Neither changes the arithmetic. The fix is to stop letting N appear in the formula.

**When is mod N still fine?** When N truly never changes, or only doubles, or when the data is rebuildable and a cold start is cheap. A fixed number of logical partitions that you map to machines (Chapter 6) is the usual fix.

**Interview takeaway:** "Mod N moves N over N+1 of the keys when you add a node, about 91% going from 10 to 11. For a cache that is a cold start and a database stampede, so I would use consistent hashing or a fixed slot map."

<h2 id="ring">Chapter 3 · The hash ring</h2>

**What is it?** **Consistent hashing** (Karger and colleagues, 1997) puts keys and nodes into the same hash space and bends that space into a circle, the **ring**. A key's owner is **the first node at or after the key's position, walking clockwise**, wrapping past the top back to the start.

**Why do we need it?** Chapter 2 showed that mod N ties every key's location to the node count. On a ring, a key's location depends only on its neighbours. Adding or removing a node only affects the keys next to it.

**How does it work?**

1. Pick a hash space, for example 0 to 2^64 − 1, and treat it as a circle.
2. Hash each node's name to a position. Hash each key to a position.
3. A key belongs to the first node clockwise from its position.
4. Add a node: it lands somewhere and takes over the slice between its predecessor and itself. That slice came from exactly one node (the old owner). Nobody else is touched.
5. Remove a node: its slice joins its successor's. Only its own keys move.

With N roughly equal nodes, a new node takes **about 1/(N + 1) of the keys**, which is the minimum possible. Say this sentence: **adding or removing a node moves about 1/N of the keys, not almost all of them.**

**Who uses it.** Dynamo and Cassandra place data on a token ring. Memcached client libraries in the "ketama" style put servers on a ring so adding a server does not flush the cache. Load balancers use relatives of it for sticky routing (the <a href={`${BASE}sd/lessons/load-balancing/`}>load-balancing lesson</a>). Redis Cluster and Kafka use the fixed-slot cousin in Chapter 6.

<Reveal q="The ring fixes movement. What problem does the last trace step reveal?">

Two, really. **Unequal arcs**: three random points on a circle almost never divide it into thirds, so one node owns far more than its share. And **failure dumping**: when B dies, its whole arc goes to one successor, which suddenly carries double load and may fall over next, handing everything to *its* successor. Both have the same fix: the next chapter.

</Reveal>

**Trade-offs.** Lookups need a sorted structure (O(log N) with a tree or sorted array). Every client needs the same node list. And a bare ring with one position per node is uneven.

**A common slip:** describing the ring and stopping. Consistent hashing without virtual nodes is half an answer.

**Interview takeaway:** "Keys and nodes share a hash circle; a key goes to the next node clockwise. Adding a node takes one arc from one neighbour, so about 1 over N of the keys move, instead of almost all of them."

<h2 id="vnodes">Chapter 4 · Virtual nodes</h2>

**What is it?** **Virtual nodes** (vnodes, tokens) place each physical node at **many** points on the ring, typically tens to hundreds. A node owns the sum of many small arcs instead of one large one.

**Why do we need it?** Imagine a 10-node ring where one node ends up with 29% of the data and two others have under 3%. The hash function is uniform, but ten random points do not cut a circle into ten equal pieces. Hash uniformity is not the same as fairness. One mechanism fixes three problems:

1. **Even load.** A sum of many random pieces is much more even than one random piece.
2. **Failure spreading.** A dead node's arcs have many different successors, so its load spreads across *all* survivors instead of one unlucky neighbour.
3. **Heterogeneous hardware.** A machine with twice the disk gets twice the tokens.

**Worked numbers: the load-variance argument.** With one token per node, the ring is cut by N random points. The largest of N random gaps averages **H(N) / N** of the circle, where H(N) = 1 + 1/2 + … + 1/N. For N = 10, H₁₀ ≈ 2.93: **the busiest node carries about 2.9× its fair share**. With V tokens per node, each node's share is a sum of V small arcs, and the relative spread of a sum of V independent pieces shrinks like **1/√V**: about 10% at V = 100 and about 6% at V = 256. The busiest of ten nodes then lands roughly 1.5 standard deviations above the mean.

**The price of vnodes.** A bigger ring to store and gossip (10 nodes × 256 = 2,560 tokens). More, smaller ranges to repair and stream. And with replication, a node's replicas are spread over many peers, so *more* combinations of two simultaneous failures touch some key. Cassandra used 256 tokens per node by default for years; newer versions default to far fewer (the current docs show 16), paired with a token allocator that places tokens deliberately instead of randomly. The Dynamo paper's later "strategy 3" cuts the ring into Q equal fixed partitions and hands those out, which is Chapter 6.

**The ring in code.** A sorted map from token to node *is* the ring: `ceilingEntry(hash)` finds the next token clockwise, and `firstEntry()` is the wrap-around. (Java is used here because `TreeMap` is the natural ring, and this block is compiled and tested.)

```java id=ring group=partitioning
import java.nio.charset.StandardCharsets;

/** 64-bit hash: FNV-1a over the UTF-8 bytes, then MurmurHash3's finalizer to scramble similar inputs. */
static long hash64(String s) {
    long h = 0xcbf29ce484222325L;                       // FNV-1a offset basis
    for (byte b : s.getBytes(StandardCharsets.UTF_8)) {
        h ^= (b & 0xff);
        h *= 0x100000001b3L;                            // FNV-1a prime
    }
    h ^= h >>> 33; h *= 0xff51afd7ed558ccdL;            // fmix64: "node-1#7" and "node-1#8"
    h ^= h >>> 33; h *= 0xc4ceb93fe53a87cdL;            // must land far apart on the ring
    h ^= h >>> 33;
    return h;
}

/** A consistent-hash ring. Each physical node owns `vnodes` points (tokens); a key belongs to the next token clockwise. */
static final class ConsistentHashRing {
    private final int vnodes;
    private final TreeMap<Long, String> ring = new TreeMap<>();   // token -> physical node, sorted = the ring
    private final Set<String> nodes = new HashSet<>();

    ConsistentHashRing(int vnodes) {
        if (vnodes < 1) throw new IllegalArgumentException("need at least one token per node");
        this.vnodes = vnodes;
    }

    void addNode(String node) {
        if (!nodes.add(node)) return;
        for (int i = 0; i < vnodes; i++) ring.putIfAbsent(hash64(node + "#" + i), node);
    }

    void removeNode(String node) {
        if (!nodes.remove(node)) return;
        for (int i = 0; i < vnodes; i++) ring.remove(hash64(node + "#" + i), node); // only our own tokens
    }

    /** The owner: first token at or after hash(key), wrapping past the end of the ring to the start. */
    String nodeFor(String key) {
        if (ring.isEmpty()) throw new IllegalStateException("no nodes");
        Map.Entry<Long, String> e = ring.ceilingEntry(hash64(key));
        return (e != null ? e : ring.firstEntry()).getValue();
    }

    /** Replicas: keep walking clockwise for one lap, skipping nodes already chosen, until n distinct nodes. */
    List<String> preferenceList(String key, int n) {
        List<String> out = new ArrayList<>();
        long h = hash64(key);
        for (Collection<String> half : List.of(ring.tailMap(h, true).values(), ring.headMap(h, false).values()))
            for (String node : half) {
                if (out.size() == n) return out;
                if (!out.contains(node)) out.add(node);
            }
        return out;                                      // fewer than n nodes exist
    }
}
```

**What the checker proves about this code** (`tests/java/pattern-partitioning/Check.java`):

- Lookups match a brute-force scan of every token on 300 random rings and do not depend on the order nodes were added.
- Adding an 11th node to a 256-vnode ring moved **9.8%** of 100,000 keys (ideal 9.1%), *every one of them to the new node*.
- Removing a node moved *only* that node's keys, and they landed on all 10 survivors. With one token per node, they all landed on exactly one neighbour.
- `putIfAbsent` and the two-argument `remove(token, node)` make a (vanishingly rare) token collision harmless: a node can only ever remove its own tokens.

**Big-O.** Lookup is O(log T) for T = N × V tokens (a tree search). Add or remove is O(V log T). The hash function matters more than it looks: plain FNV on `node-1#7` and `node-1#8` gives nearby values, so tokens would clump. The finalizer scatters them.

Recovery speed. When a replacement must re-stream the dead node's data, it pulls small ranges from many peers in parallel instead of one huge range from one peer. Ten senders at a throttled rate each finish roughly ten times sooner than one sender, and no single survivor's disk is saturated by the rebuild.

|---|---|---|
| Load balance (10 nodes) | Busiest ≈ 2.9× fair share | Busiest ≈ 1.09× at 256 vnodes |
| Dead node's load goes to | One neighbour | All survivors |

<h2 id="rendezvous">Chapter 5 · Rendezvous hashing</h2>

**What is it?** **Rendezvous hashing** (highest random weight, Thaler and Ravishankar) is a ring-free alternative. For a key, compute `score = hash(node, key)` for every node and pick the node with the highest score. Think of every node bidding on every key.

**Why do we need it?** For a small set of nodes (a routing tier choosing one of 20 storage nodes, say) a ring plus vnodes is more machinery than you need. Rendezvous gives the same movement properties with no ring, no tokens and no vnodes.

**How does it work?**

- **Adding a node:** a key moves only if the new node outbids the current winner, which happens for about **1/(N + 1)** of keys, all moving *to* the new node.
- **Removing a node:** only its keys move, each to its own runner-up. Runners-up are independent per key, so the dead node's load **spreads evenly over every survivor, with no vnodes**.
- **Cost:** a lookup computes N hashes, O(N). Trivial for 20 storage nodes or 50 proxies; too slow per request for 10,000 nodes (use a hierarchy: rendezvous over groups, then within a group).
- **Replicas:** take the top 3 scores instead of the top 1.

```java id=rendezvous group=partitioning
/** Rendezvous (highest-random-weight) hashing: every node scores every key; the highest score owns it. */
static final class Rendezvous {
    private final List<String> nodes = new ArrayList<>();

    void addNode(String node) { if (!nodes.contains(node)) nodes.add(node); }
    void removeNode(String node) { nodes.remove(node); }

    String nodeFor(String key) {
        String best = null;
        long bestScore = 0;
        for (String node : nodes) {
            long score = hash64(node + "|" + key);
            if (best == null || score > bestScore || (score == bestScore && node.compareTo(best) < 0)) {
                best = node;
                bestScore = score;
            }
        }
        if (best == null) throw new IllegalStateException("no nodes");
        return best;
    }
}
```

The checker compares it with an independent "max by score" oracle and confirms the two properties: adding an 11th node moved **9.1%** of keys, all to the newcomer; removing a node sent its keys to all 10 survivors, each getting its share within 4%.

| | Ring + vnodes | Rendezvous |
|---|---|---|
| Lookup cost | O(log T) | O(N) hashes |
| State | Token list (can be large) | Just the node list |
| Add a node moves | ~1/(N+1), from many peers | ~1/(N+1), from all nodes |
| Dead node's keys go | Spread over many successors (needs vnodes) | Each key to its own runner-up (evenly, automatically) |
| Best for | Large clusters, leaderless stores | Small node sets, proxy or replica choice |

**A common slip:** reaching for rendezvous at 10,000 nodes. The O(N) lookup is the ceiling; use a hierarchy or a ring there.

**Interview takeaway:** "For a small, changing node set I would use rendezvous hashing: every node scores the key and the highest wins. It moves only the new node's share and spreads a dead node's keys evenly, with no vnode bookkeeping."

<h2 id="slots">Chapter 6 · Fixed slot maps</h2>

**What is it?** A **fixed slot map** separates two mappings that mod N glued together:

1. **key → slot**, with a fixed number of slots that never changes: `slot = hash(key) mod S`.
2. **slot → node**, a small table that operators (or a balancer) change.

**Why do we need it?** Keys never change slot, so growing the cluster only edits the second table and moves **whole slots**. It is the "pre-split into many fixed logical partitions" idea from the <a href={`${BASE}sd/lessons/databases/#sharding`}>databases lesson</a>. You get explicit control: you can see which slot lives where, move one at a time, and keep a leader and replicas per slot.

**How Redis Cluster does it.** Redis Cluster uses **16,384 slots**: `slot = CRC16(key) mod 16384`. **Hash tags** make related keys share a slot: only the part inside the first non-empty `{…}` is hashed, so `{user:42}:cart` and `{user:42}:profile` land together and multi-key commands work on them.

```text
CLUSTER KEYSLOT user:42
(integer) 15880
CLUSTER KEYSLOT {user:42}:cart
(integer) 15880
CLUSTER KEYSLOT {user:42}:profile
(integer) 15880
CLUSTER KEYSLOT user:42:cart
(integer) 12984
```

The first three are the same slot, because only `user:42` is hashed. The last one has no braces, so the whole string is hashed and it lands elsewhere. (The slot numbers are computed with CRC16 XMODEM mod 16384; verify with `CLUSTER KEYSLOT` on your own cluster.)

**Moving a slot while serving traffic.** The slot is marked `MIGRATING` on the source and `IMPORTING` on the target. Keys move a batch at a time. During the move:

- The source answers for keys it still has.
- For a key already moved, the source replies **`ASK`**: a one-off redirect. The client sends `ASKING` then the command to the target, and does *not* update its map.
- When the slot is done, the map changes, and any node replies **`MOVED`** for that slot: update your map permanently.

**Worked numbers.** 3 primaries hold 5,461, 5,461 and 5,462 slots (16,384 = 3 × 5,461 + 1). Add a 4th and balance evenly: 16,384 ÷ 4 = **4,096 slots** each, so the newcomer takes 4,096 slots, **25% of keys**, the minimum. With 30 primaries, each holds about 546 slots; a 31st takes about 528, **3.2%** of keys. Compare mod N, which would move 30/31 ≈ 97%.

**Other systems in the same family.** **Kafka** fixes partitions per topic, and a key's partition is `hash(key) mod partitions`. That is why *adding partitions* to a keyed topic breaks per-key ordering for existing keys: it is mod N again, applied at the partition level. **Elasticsearch** fixes an index's primary shard count at creation for the same reason. The Dynamo paper's later strategy cuts the ring into Q equal partitions and assigns them to nodes, for simpler bootstrapping and archiving.

**Consistent hashing vs fixed slots.** They look alike, because both move only the new node's share. The difference is where the indirection lives:

| | Ring (consistent hashing) | Fixed slot map |
|---|---|---|
| What is fixed forever | The hash function and ring space | The slot count (e.g. 16,384) |
| What changes on scale-out | Node positions on the ring | The slot → node table |
| Who decides what moves | The hash positions (automatic) | An operator or balancer (explicit) |
| Movement unit | An arc | A whole slot |
| Natural fit | Leaderless stores, elastic caches | Leader-per-slot clusters, explicit control |

| Scheme | Lookup | Add a node moves | A node dies | State to share | Pick when |
|---|---|---|---|---|---|
| **mod N** | O(1), no state | ~N/(N+1) of keys | ~90% remap | none | N never changes (or only doubles) |
| **Ring + vnodes** | O(log T) | ~1/(N+1), from many peers | spread over all | the token list | Leaderless stores; elastic caches |
| **Rendezvous** | O(N) hashes | ~1/(N+1) | spread evenly | the node list | Small node sets; proxy or replica choice |
| **Fixed slots** | O(1) table | whole slots, chosen by a balancer | promote that slot's replica | slot → node table | Clusters with leaders per slot; explicit control |
| **Ranges** (next) | O(log R) | split ranges | promote range replica | range → node table | Ordered scans |

<h2 id="ranges">Chapter 7 · Range partitioning</h2>

**What is it?** **Range partitioning** gives each partition a contiguous slice of the **sorted** key space (A to F on one node, G to M on the next). You lose the hash's even spread and gain **ordered scans**: "all events of March" touches one or a few partitions instead of all of them. Bigtable (tablets), HBase (regions), Spanner and CockroachDB (splits and ranges) all work this way.

**Why do we need it?** Say an event store must answer "every event from device 7 between 9 and 10". On a hash ring that hour is scattered across all nodes, so you must ask every one of them (a scatter-gather). With ranges, the query is one contiguous scan.

**How does it work?**

- **Splits.** When a range grows past a size (say 10 GB) or gets too much traffic, it splits at a middle key into two ranges, and one can move to another node. Splitting is cheap: it is a metadata change, and data moves later or not at all.
- **Merges.** Adjacent ranges that shrank (after deletes or TTLs) merge, so the map does not fill with empty slivers.
- **Pre-splitting.** A brand-new table is one range on one node. Bulk-loading it hammers that node until splits catch up. Pre-split at known boundaries before a big load.
- **The hot tail.** With monotonically growing keys (timestamps, auto-increment ids) **every new write lands in the last range**. Splitting does not help: the new last range is just as hot.

<Figure caption="Range partitions are contiguous slices of sorted keys. Today's writes all hit the newest range.">
  <Mermaid code={`flowchart LR
    W["new writes\nkey = timestamp"] --> R3
    R1["range 1\nJan 1 to Jan 31"] --> R2["range 2\nFeb 1 to Feb 28"] --> R3["range 3\nMar 1 to now\nHOT"]
    Q["scan: Feb 10 to Feb 20"] -.-> R2`} />
</Figure>

| | Hash | Range |
|---|---|---|
| Load spread | Even, because the hash scrambles keys | Can hotspot: today's writes all land in the newest range |
| Range scans | Scatter-gather to every node | One or a few partitions |
| Rebalance unit | Arc, vnode or slot | Split or merge a range |
| Pick when | Point lookups dominate (caches, KV) | Ordered scans dominate (metrics, logs, listings) |

**Compound keys, the hybrid worth knowing.** Hash on a partition key, sort within it by a second key: `(device_id) → timestamp`. "Device 7's events this hour" is one partition and one ordered scan; different devices spread across the cluster. This is Cassandra's partition key plus clustering columns and DynamoDB's partition key plus sort key. One sentence connects three technologies.

```sql
-- Cassandra-style CQL: device_id is hashed to pick the partition,
-- ts is the clustering column that keeps rows sorted inside it.
CREATE TABLE events (
  device_id bigint,
  ts        timestamp,
  payload   blob,
  PRIMARY KEY ((device_id), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

-- One partition, one ordered scan:
SELECT * FROM events
 WHERE device_id = 7 AND ts >= '2026-03-01 09:00' AND ts < '2026-03-01 10:00';
```

<Reveal q="Metrics are range-partitioned by timestamp so dashboards can scan time windows. All writes hit the newest range. Fix it without losing the scans.">

Prefix the time with a small hash bucket: key = `(hash(series) mod k, timestamp)`. Current writes spread over k ranges; a time-window read asks k partitions and merges, a fan-out you state out loud ("k = 16, so 16 parallel reads"). Pure hashing would spread writes and kill the scans you partitioned for. The <a href={`${BASE}sd/lessons/pattern-timeseries/`}>time-series pattern lesson</a> builds a metrics system on exactly this.

</Reveal>

**A common slip:** choosing range partitioning for its scans and forgetting that the newest range is the hottest. Say the write pattern of your key before you choose.

**Interview takeaway:** "If queries scan in order I range-partition and split ranges by size and load. If keys grow monotonically I add a hash bucket prefix so writes spread, and I state the cost: reads fan out to that many partitions."

<h2 id="hot-keys">Chapter 8 · Hot keys and hot partitions</h2>

**What is it?** Every partitioning scheme has the same failure: one key or range takes far more than its share. A celebrity's profile. Today's date. A viral post's view counter. One tenant a hundred times bigger than the rest. It has many names (hot key, hot shard, hot partition, hot Kafka partition), but it is one problem.

**Why do more nodes not help?** Say a singer with forty million followers posts a photo. One Redis shard goes to 100% CPU while thirty-nine others idle. Adding shards does not help, because a key lives in exactly one partition (plus its replicas). Ten more shards spread *other* keys.

<Figure caption="Hot key: all the traffic for one key lands on one shard. Fixes either shorten the path (cache above the shard) or split the key (copies or salts).">
  <Mermaid code={`flowchart LR
    U["200 app servers\n400,000 reads/s for key K"] --> L1["L1 cache per server\n1 s TTL"]
    L1 -->|"about 200 reads/s"| SH["shard owning K"]
    U2["writers\n100,000 incr/s"] -->|"random suffix 0 to 15"| S0["views:42 sub-key 0"]
    U2 --> S1["views:42 sub-key 1"]
    U2 --> S15["views:42 sub-key 15"]`} />
</Figure>

The toolkit, in escalation order:

| Fix | For | How | Cost |
|---|---|---|---|
| **Cache in front** | Hot reads | A tiny in-process cache (~1 s TTL) on every app server; Redis sees one read per server per second | Bounded staleness (<a href={`${BASE}sd/lessons/caching/#hot-keys`}>caching lesson, hot keys</a>) |
| **Read from replicas** | Hot reads | Spread reads of that partition over all its replicas | Replica lag; only ×RF |
| **Key replication** | Hot reads | Store copies `profile:42#0…#7` on different shards, read a random one | Writes must update all copies |
| **Salting** | Hot writes | Split the key into sub-keys (`views:42#0…#15`), write to a random one | Reads sum all sub-keys, or a roll-up does |
| **Better key** | Hot ranges | `date` → `date#hash(user) mod 16`: today's writes go 16 ways | 16 reads to reassemble: say the cost |
| **Split the partition** | Hot ranges | Bigtable-style stores split by load as well as size | Does not help one single key |
| **Isolate** | One giant tenant | Give the biggest tenants their own partitions or nodes, via a directory | A lookup table to run |

**Worked numbers.** A celebrity profile at 400,000 reads/s against shards that serve about 100,000: with 200 app servers each holding a 1-second L1 copy, Redis sees about **200 reads/s** for that key. A view counter at 100,000 increments/s against a partition budget of 10,000 writes/s: salted 16 ways, each sub-key takes **6,250/s**, and the read pays 16 lookups (or a roll-up job writes the total every second).

```python
import random, redis
r = redis.Redis()
SALTS = 16

def incr_views(post_id: int) -> None:
    # Each write goes to ONE random sub-key, so write load divides by SALTS.
    r.incr(f"views:{post_id}#{random.randrange(SALTS)}")

def read_views(post_id: int) -> int:
    # The total no longer lives in one place: 16 reads, pipelined into one round trip.
    pipe = r.pipeline()
    for i in range(SALTS):
        pipe.get(f"views:{post_id}#{i}")
    return sum(int(v) for v in pipe.execute() if v is not None)
```

Caveat: the sub-keys hash to different slots, which is exactly the point, so `read_views` is not atomic. The total can be slightly stale while increments continue. For a view counter that is fine. For a balance that must be exact, do not salt.

**Detect it, do not assume it.** Sample the top keys per node (Redis has tooling for this; most stores expose per-partition request rates), alert on a partition far above the median, and know which fix you would apply before the singer posts.

**Interview takeaway:** "A hot key lives in one partition, so more nodes do not help. For reads I put a one-second in-process cache in front or copy the key under suffixes. For writes I salt into sub-keys and sum on read. I watch per-partition rates to catch it early."

<h2 id="rebalancing">Chapter 9 · Rebalancing safely</h2>

**What is it?** When placement changes (a node is added or removed), **data must physically move while traffic continues**. Rebalancing is the process that does this without losing writes or hurting latency.

**Why is it dangerous?** Say a new storage node is racked and ready. If you just announce it, every peer starts streaming to it at full disk speed, and for forty minutes every read in the cluster is three times slower. Data does not teleport. It moves at disk speed, while people are using it.

**Four rules make it safe:**

1. **Stream, do not stop.** The new owner pulls its ranges from the current owners in the background (bulk files where the engine allows, such as SSTables), while the current owners keep serving.
2. **Throttle.** Movement is background work with a budget, so foreground latency holds.
3. **One owner at a time.** The old owner stays authoritative until the new one has the bulk copy **plus** everything written during the copy (a change log, forwarded writes, or a final catch-up pass). Then ownership flips atomically: a new version of the partition map (an **epoch**), so stale clients and stale nodes can be told "you are behind".
4. **Do not confuse a blip with a departure.** A node missing heartbeats during a GC pause is *temporarily* down: keep writing around it (hinted handoff, Chapter 11) and wait. Moving hundreds of GB for a 40-second pause adds load at the worst time and must then be undone. The Dynamo paper makes permanent membership changes an explicit administrator action for this reason.

Redis Cluster's version of this is the `MIGRATING`/`IMPORTING` flow from Chapter 6. MongoDB's balancer moves chunks between shards on the same principle.

**Worked numbers.** The 30-node store of Chapter 17 holds 6 TB (three replicas of 2 TB). A 31st node takes about 1/31 of it: **6 TB ÷ 31 ≈ 194 GB**. Throttled to 100 MB/s cluster-wide, that is 194,000 MB ÷ 100 MB/s ≈ **1,940 s, about 32 minutes**. Unthrottled at several GB/s it would finish faster and hurt every read for the duration. Assumption: plan the throttle from your latency budget, not from the disk's maximum.

**Rebalancing cost, side by side.** What moves, and how much, when a cluster grows from N to N + 1:

| Scheme | Data that moves | Moves from | Who decides |
|---|---|---|---|
| mod N | N/(N+1) of all keys (10 → 11: 91%) | Every node | Nobody; it happens when clients change N |
| Ring + vnodes | ≈ 1/(N+1) | Many peers, small ranges | Hash positions |
| Rendezvous | ≈ 1/(N+1) | All nodes | Scores |
| Fixed slots | Whole slots, ≈ 1/(N+1) | Chosen donors | Operator or balancer |
| Range split | Only the split range, if moved at all | One node | Size or load triggers |

<h2 id="replication">Chapter 10 · Replication and who orders writes</h2>

**What is it?** Partitioning chooses *which* data a node holds. Replication chooses *how many* nodes hold each partition and *who orders the writes*. (Background: <a href={`${BASE}sd/lessons/core-concepts/#replication`}>core concepts, Copies</a> and <a href={`${BASE}sd/lessons/databases/#replication`}>databases, Leader and followers</a>.)

**Why do we need to decide this?** Say you want three copies of every cart, and the cart should still accept an item when a data centre is having a bad day. Two designs exist ("leader" and "leaderless"), and they answer very differently when a machine fails or two writes collide.

**Where the replicas live.** On a ring, a key's **preference list** is the next N *distinct physical* nodes clockwise: skip further tokens of a node you already picked. The `preferenceList` method in Chapter 4 does exactly that, and the checker verifies each entry against an oracle. In production, also skip nodes in a rack or availability zone you already used, so one zone outage never takes all copies. With slots or ranges, the partition map simply lists N nodes per partition.

<Figure caption="Leader per partition: all writes for a partition go through its leader, which replicates to followers. Leaderless: the coordinator sends the write to all N replicas and waits for W acknowledgements.">
  <Mermaid code={`flowchart LR
    subgraph L["Leader per partition"]
    C1["client"] --> LD["leader"]
    LD --> F1["follower"]
    LD --> F2["follower"]
    end
    subgraph LL["Leaderless"]
    C2["client"] --> CO["any node as coordinator"]
    CO --> A["replica A"]
    CO --> B["replica B"]
    CO --> D["replica C"]
    end`} />
</Figure>

**Who orders writes: two families.**

| | Leader per partition | Leaderless (Dynamo-style) |
|---|---|---|
| How | One replica of each partition is leader; all writes for it go through the leader, followers replay its log | Any replica (or a coordinator) sends the write to all N replicas; success after W acknowledge |
| Ordering | One total order per partition | No single order; concurrent writes possible |
| Compare-and-set, uniqueness | Easy: the leader decides | Hard: needs consensus or a lightweight transaction |
| Leader dies | Partition unwritable until failover (seconds); with async replication, the tail can be lost | Nothing to fail over; writes continue to other replicas |
| Examples | Redis Cluster (async), Kafka partitions, Spanner / CockroachDB (a consensus group per range), Amazon DynamoDB the service (per its 2022 paper) | Dynamo (the 2007 paper), Cassandra, Riak |
| Pick when | You need per-key ordering or CAS; reads must be fresh from the leader | Writes must always be accepted (AP); conflicts can be merged |

Note the name clash: **Dynamo**, the 2007 paper, is leaderless. **DynamoDB**, the AWS service, is described in its own 2022 paper as using a replication group per partition with a leader elected by Multi-Paxos. In an interview, "Dynamo-style" means the paper.

**Leaders per partition spread the leadership.** With 1,000 partitions on 30 nodes, each node leads about 33 partitions and follows about 66 (at RF 3, where RF is the replication factor). There is no single "leader node" to overload, and a node failure triggers 33 small, independent failovers.

**Interview takeaway:** "Three replicas on three distinct nodes in three zones. If I need per-key ordering or compare-and-set I use a leader per partition. If writes must always succeed I go leaderless and handle conflicts."

<h2 id="quorums">Chapter 11 · Quorums, hinted handoff, read repair</h2>

**What is it?** In a leaderless store, each operation goes to the key's N replicas, and the client waits only for some of them:

- **N** = number of replicas of each key.
- **W** = acknowledgements needed for a write to succeed.
- **R** = replies needed for a read; the read returns the newest version among them (and reconciles it, Chapter 12).

**Why do we need quorums?** Waiting for all N replicas means one slow or dead replica blocks everything. Waiting for only one means a read can hit a replica that missed the latest write. Quorums sit between those: wait for enough replicas that reads and writes are guaranteed to meet.

**The rule: if W + R > N, every read set overlaps every write set** in at least one replica. The reason is pigeonhole: a write reached W of the N replicas, a read asks R of them, and W + R > N means the two groups cannot be disjoint. The overlapping replica holds the newest write, so a read that starts after a write completed sees it (given a way to tell which version is newer, which is Chapter 12). The full table of N/W/R shapes also lives in <a href={`${BASE}sd/lessons/core-concepts/#replication`}>core concepts</a>.

| N | W | R | W + R > N? | Behaviour |
|---|---|---|---|---|
| 3 | 2 | 2 | yes (4 > 3) | Balanced. One replica may be down on both paths. The usual default |
| 3 | 3 | 1 | yes | Fast reads, writes need every replica: one failure blocks writes |
| 3 | 1 | 3 | yes | Fast writes, reads need every replica: one failure blocks reads |
| 3 | 1 | 1 | no (2 ≤ 3) | Fastest, but a read can miss the only replica that has the write. Eventual consistency |
| 3 | 2 | 1 | no (3 ≤ 3) | A read may land on the one replica that missed the write |

You can check the overlap rule by brute force:

```python
import itertools

def always_overlaps(n: int, w: int, r: int) -> bool:
    replicas = range(n)
    return all(set(ws) & set(rs)
               for ws in itertools.combinations(replicas, w)
               for rs in itertools.combinations(replicas, r))

print(always_overlaps(3, 2, 2))   # True   (2 + 2 > 3)
print(always_overlaps(3, 2, 1))   # False  (2 + 1 = 3, not greater)
print(always_overlaps(5, 3, 3))   # True
```

**Two precise points.**

- **W > N/2** means two writes' acknowledging sets overlap each other too. That helps detect conflicts, but it does not order concurrent writes. Ordering needs versions (Chapter 12) or a leader.
- **R + W > N is about overlap, not linearizability.** Chapter 11's Reveal below explains why.

**Latency is the hidden win.** A quorum waits for the **W-th fastest** reply. With replicas answering in 2 ms, 3 ms and 40 ms (one in a GC pause), a W = 2 write returns in **3 ms**; the slow replica still receives the write. Quorums cut tail latency as well as surviving failures.

**Sloppy quorum and hinted handoff.** What if two of the N home replicas are unreachable? A **strict** quorum fails the write. A **sloppy** quorum (Dynamo's choice, for always-writable carts) writes to the first W *healthy* nodes further along the ring, even if they are not home replicas. A stand-in stores the write with a **hint**: "this belongs to A". When A comes back, the stand-in **hands off** the write and deletes its copy. That delivery step is **hinted handoff**.

<Figure caption="Sloppy quorum: A and B are unreachable; the write lands on C and on stand-in D, which holds a hint for A and delivers it when A returns.">
  <Mermaid code={`sequenceDiagram
    participant Co as Coordinator
    participant A as A (home, down)
    participant B as B (home, down)
    participant C as C (home)
    participant D as D (stand-in)
    Co-xA: put k (timeout)
    Co-xB: put k (timeout)
    Co->>C: put k
    Co->>D: put k, hint: for A
    C-->>Co: ack
    D-->>Co: ack (W = 2 met)
    Note over A,D: later, A is back
    D->>A: hinted handoff: k
    A-->>D: ack, D drops its copy`} />
</Figure>

**The catch, which interviewers love:** with a sloppy quorum, the W acknowledgements may come from outside the home set, so **W + R > N no longer guarantees overlap**. A reader that reaches A and B (back up, but before handoff) gets R = 2 replies without the new value. Sloppy quorums trade the overlap guarantee for write availability. And hints are kept only for a window (Cassandra's default is three hours, `max_hint_window`). A node down longer needs full repair (Chapter 13).

**Read repair.** On a read, the coordinator asks R replicas (often with a digest from some of them). If the replicas disagree, it picks the newest version and writes it back to the stale replicas. This fixes hot keys quickly and does nothing for keys nobody reads.

| | Hinted handoff | Read repair | Anti-entropy (Chapter 13) |
|---|---|---|---|
| Triggered by | A write while a home replica was down | A read that saw replicas disagree | A scheduled background job |
| Fixes | Writes missed in a short outage | Keys that are actually read | Everything, including keys nobody reads |
| Limit | Hint window (hours); hints can be lost if the stand-in dies | Cold keys stay stale | Costs I/O; runs on a schedule |

<Trace title="Count to a quorum" steps={quorums} takeaway="W + R > N overlaps reads and writes. Quorums wait for the W-th fastest reply. Sloppy quorums keep writes flowing and give up the overlap guarantee until hinted handoff finishes." />

<Reveal q="Does W + R > N make the store linearizable?">

No, and saying so is a senior signal. Sloppy quorums break the overlap. Concurrent writes resolved by timestamps lose one write. A write that failed overall may have landed on some replicas, so later reads disagree. And without care in read repair, one reader can see the new value while a later reader sees the old. Quorums give a strong *overlap* guarantee. Linearizability needs a leader with consensus, or careful quorum read-repair rules (<a href={`${BASE}sd/lessons/core-concepts/#consistency`}>the consistency ladder</a>).

</Reveal>

**A common slip:** quoting W + R > N while also using sloppy quorums, as if both held at once. Say which one you chose, and why the product needs it.

**Interview takeaway:** "N = 3, W = 2, R = 2, so reads and writes overlap in at least one replica, and one node can be down. With sloppy quorums and hinted handoff I keep accepting writes during an outage, and I say plainly that the overlap guarantee is suspended until the hints are delivered."

<h2 id="conflicts">Chapter 12 · Conflicts: LWW vs vector clocks</h2>

**What is it?** In a leaderless store, writes can be **concurrent**: neither writer saw the other's write. When replicas later compare notes, the store must decide what to keep.

**Why is it a real problem?** Take a support ticket from a shop buyer: "I added a lamp on my phone and a rug on my laptop, a second apart. The cart has the rug. Where is my lamp?" Both writes were acknowledged and both had timestamps. The store kept the one with the later timestamp, as configured, and threw the other away without telling anyone. It did what it was asked to do. It was asked the wrong thing.

**Last-write-wins (LWW).** Stamp each write with a timestamp; keep the highest. It is cheap, built into Cassandra, and it **silently loses data**:

- Two read-modify-writes from the same starting cart (`{mug}` → `{mug, lamp}` and `{mug}` → `{mug, rug}`): LWW keeps one whole value. The lamp is gone, even with perfect clocks.
- With **clock skew**, the *earlier* write can carry the later timestamp and win. Node clocks drift by milliseconds or more.

LWW is honest when the newest value genuinely supersedes the old: a presence status, a last-seen time, a settings toggle, an immutable value written once. Say *"LWW is fine here because losing the older write is the correct behaviour"*, or do not use it. The <a href={`${BASE}sd/lessons/pattern-sync-collab/`}>sync and collaboration lesson</a> goes deeper on conflict strategies.

**Version vectors (Dynamo called them vector clocks).** Each value carries a map from replica to counter: how many writes coordinated by each replica this version has seen. Compare two vectors counter by counter:

- every counter ≤ the other's, and they differ → **before**: the other one supersedes it, discard it;
- each side is ahead somewhere → **concurrent**: keep **both** as *siblings* and reconcile.

**Worked example: the lamp, saved.**

| Step | What happens | Vector |
|---|---|---|
| 1 | Replica A coordinates "create cart `{mug}`" | `{A:1}` |
| 2 | A coordinates "add bowl" | `{A:2}` |
| 3 | The phone, having read `{A:2}`, adds a lamp via replica B | `{A:2, B:1}` |
| 4 | The laptop, also having read `{A:2}`, adds a rug via replica C | `{A:2, C:1}` |
| 5 | A read finds both: B:1 vs 0 and C:0 vs 1 → **concurrent** | two siblings |
| 6 | The client merges the carts (union), writes through A with the merged context | `{A:3, B:1, C:1}` |

Step 6's vector is the element-wise max `{A:2, B:1, C:1}`, then A increments its own counter. It dominates both siblings, so they can be dropped.

The Dynamo paper's shopping cart worked this way, with one known wrinkle: a union merge can resurrect an item that was deleted on one side. The checker replays this table step by step and tests the comparison on 3,000 random vector pairs against an oracle.

```java id=versions group=partitioning
enum Order { BEFORE, AFTER, EQUAL, CONCURRENT }

/** A version vector: one counter per replica that coordinated a write. Immutable. */
static final class VersionVector {
    private final TreeMap<String, Long> counters;

    VersionVector() { this(new TreeMap<>()); }
    private VersionVector(TreeMap<String, Long> counters) { this.counters = counters; }

    /** The vector a replica stamps on a new write that it coordinates. */
    VersionVector increment(String replica) {
        TreeMap<String, Long> next = new TreeMap<>(counters);
        next.merge(replica, 1L, Long::sum);
        return new VersionVector(next);
    }

    /** Element-wise max: the vector of a value that has seen everything both sides saw. */
    VersionVector merge(VersionVector other) {
        TreeMap<String, Long> next = new TreeMap<>(counters);
        other.counters.forEach((r, c) -> next.merge(r, c, Math::max));
        return new VersionVector(next);
    }

    /** BEFORE: every counter here is <= other's and they differ. CONCURRENT: each side has something the other lacks. */
    Order compare(VersionVector other) {
        boolean less = false, greater = false;
        Set<String> all = new TreeSet<>(counters.keySet());
        all.addAll(other.counters.keySet());
        for (String r : all) {
            long a = counters.getOrDefault(r, 0L), b = other.counters.getOrDefault(r, 0L);
            if (a < b) less = true;
            if (a > b) greater = true;
        }
        if (less && greater) return Order.CONCURRENT;
        if (less) return Order.BEFORE;
        if (greater) return Order.AFTER;
        return Order.EQUAL;
    }

    long get(String replica) { return counters.getOrDefault(replica, 0L); }

    @Override public String toString() { return counters.toString(); }
}
```

**The merge function the application owns.** The store only detects concurrency. Deciding what a merge means is application logic:

```python
def merge_carts(siblings: list[set[str]]) -> set[str]:
    # Union keeps every concurrent add. Known flaw: an item removed on one
    # side comes back, because "absent" and "never saw it" look the same.
    return set().union(*siblings)

# phone: {mug, bowl, lamp}   laptop: {mug, bowl, rug}
print(merge_carts([{"mug", "bowl", "lamp"}, {"mug", "bowl", "rug"}]))
# {'mug', 'bowl', 'lamp', 'rug'}
```

On the wire, the client sends back the vector it read, as an opaque context:

```http

```

```http

```

**Practical notes.**

- Vectors grow with the number of coordinating replicas. Dynamo truncated the oldest entries past a threshold (10 in the paper), accepting rare false "concurrent" verdicts.
- The client must send back the **context** (the vector it read) with its write. That is why Dynamo's API is `get(key) → (values, context)` and `put(key, context, value)`.
- Riak later refined this into *dotted* version vectors to avoid sibling explosion.
- Strictly, a **vector clock** tracks events per process and a **version vector** tracks versions of one data item per replica. They look the same, and interviews use the words loosely. Dynamo's "vector clocks" are version vectors.

**The third option: CRDTs.** Instead of keeping siblings for the application to merge, choose data types whose merge is automatic and order-independent: a counter that sums per-replica counts, a set with add-wins semantics. Chapter 20 builds a counter; the <a href={`${BASE}sd/lessons/pattern-sync-collab/`}>sync and collaboration lesson</a> covers the family.

**LWW versus version vectors, precisely:**

| | Last-write-wins | Version vectors |
|---|---|---|
| Each write carries | A timestamp | A map of replica → counter |
| Concurrent writes | One silently wins | Both kept as siblings |
| Depends on clocks? | Yes, so skew can make the older write win | No wall clocks, only counters |
| Who resolves | The store, automatically | The application or a CRDT, on read |
| Extra cost | None | Vector size, siblings to store, merge code |
| Right when | The newest value truly replaces the old (last seen, a toggle) | Users add to shared state (carts, lists) |

<h2 id="anti-entropy">Chapter 13 · Merkle-tree repair</h2>

**What is it?** **Anti-entropy** is the background process that makes replicas converge for *all* keys, not just the ones read (read repair) or written during a short outage (hinted handoff). A **Merkle tree** is the data structure that makes it cheap: it ships hashes instead of data.

**Why do we need it?** Say a node was down for six hours, past the hint window. It is back and missing some writes. Nobody knows which. Copying all 400 GB from a peer is wasteful, because most of it is already identical. You need to find *which parts differ* without comparing every key.

**How does it work?**

1. Each replica hashes its keys into a fixed number of **buckets** for a key range. Each bucket's hash covers its keys and values.
2. Each parent's hash covers its two children, up to one root.
3. Two replicas compare **roots**. Equal means the whole range agrees.
4. Otherwise they compare the two children and **descend only into subtrees whose hashes differ**.
5. At the leaves, they exchange just the keys in differing buckets.

<Figure caption="Eight buckets, one differing key (in bucket 5). Seven comparisons: the root, then both children at each level along the path. Grey subtrees matched and were never opened.">
  <Mermaid code={`flowchart TD
    R["root ≠"] --> L["0–3 ="]
    R --> RR["4–7 ≠"]
    L -.- L1["(skipped)"]
    RR --> A["4–5 ≠"]
    RR --> B["6–7 ="]
    A --> B4["bucket 4 ="]
    A --> B5["bucket 5 ≠\nexchange its keys"]
    style R fill:#f85149,color:#0d1117
    style RR fill:#f85149,color:#0d1117
    style A fill:#f85149,color:#0d1117
    style B5 fill:#e3b341,color:#0d1117

    style B fill:#3fb950,color:#0d1117

</Figure>

**Worked numbers.** With 2^d buckets and one differing key, the walk does **1 + 2d** comparisons: the root, then two children at each of d levels. Eight buckets (d = 3): **7**. About a million buckets (d = 20): **41**, instead of 1,048,576 bucket comparisons, and then only one bucket's keys cross the network. When many buckets differ, the walk opens more of the tree, never more than its 2^(d+1) − 1 nodes. The checker counts exactly 7 and 41, and compares the diff with a bucket-by-bucket oracle on 1,000 random replica pairs.

```java id=merkle group=partitioning
/** A Merkle tree over a fixed number of key buckets (a power of two). Leaves hash their bucket; parents hash children. */
static final class MerkleTree {
    final int buckets;
    final long[] tree;            // heap layout: tree[1] is the root, children of i are 2i and 2i+1, leaves at buckets..2*buckets-1

    MerkleTree(Map<String, String> data, int buckets) {
        if (buckets < 1 || Integer.bitCount(buckets) != 1) throw new IllegalArgumentException("buckets must be a power of two");
        this.buckets = buckets;
        List<List<String>> rows = new ArrayList<>();
        for (int b = 0; b < buckets; b++) rows.add(new ArrayList<>());
        for (Map.Entry<String, String> e : new TreeMap<>(data).entrySet())        // sorted: same data, same hash
            rows.get(bucketOf(e.getKey(), buckets)).add(e.getKey() + "=" + e.getValue());
        tree = new long[2 * buckets];
        for (int b = 0; b < buckets; b++) tree[buckets + b] = hash64(String.join("\n", rows.get(b)));
        for (int i = buckets - 1; i >= 1; i--) tree[i] = hash64(tree[2 * i] + ":" + tree[2 * i + 1]);
    }

    static int bucketOf(String key, int buckets) { return (int) Long.remainderUnsigned(hash64(key), buckets); }

    /** Walk both trees from the root, descending only where hashes differ. Returns the differing buckets. */
    List<Integer> diff(MerkleTree other, int[] comparisons) {
        if (other.buckets != buckets) throw new IllegalArgumentException("trees must have the same shape");
        List<Integer> out = new ArrayList<>();
        ArrayDeque<Integer> todo = new ArrayDeque<>(List.of(1));
        while (!todo.isEmpty()) {
            int i = todo.poll();
            comparisons[0]++;
            if (tree[i] == other.tree[i]) continue;              // whole subtree agrees: skip it
            if (i >= buckets) out.add(i - buckets);              // a leaf: this bucket's keys must be exchanged
            else { todo.add(2 * i); todo.add(2 * i + 1); }
        }
        Collections.sort(out);
        return out;
    }
}
```

**In real stores.** Trees are kept per key range (per vnode range or partition), because two replicas only share ranges, not whole node contents. Building a tree means reading the range, so repair is scheduled and throttled like streaming. Cassandra runs it as `nodetool repair`; operators schedule it on a cadence. Trade-off: a Merkle tree is stale as soon as writes arrive, so trees are rebuilt periodically and the comparison is "as of" a snapshot.

**The three repair paths, together:** **hinted handoff** for short outages, **read repair** for keys that are read, **Merkle anti-entropy** for everything else. Name all three when asked "how do replicas converge?"

<h2 id="gossip">Chapter 14 · Gossip and failure detection</h2>

**What is it?** **Gossip** is how nodes learn who exists and who is alive without a central registry. **Failure detection** decides whether a silent node is down. Neither is a fact. Both are good enough.

**Why do we need it?** With thirty nodes, someone has to keep the list of which nodes exist and which are alive. A central registry becomes a single point of failure, and it fails exactly when you need it. Gossip has no centre.

**How gossip works.** Each node keeps a table of every node it knows about: address, tokens, status, and a heartbeat counter it increments for itself. Every second, each node picks a random peer and they exchange tables, keeping the newer entry for each node. Information spreads like a rumour.

<Figure caption="Each round, every node that knows a fact tells one random peer. The set of informed nodes roughly doubles at first.">
  <Mermaid code={`flowchart LR
    R0["round 0\n1 node knows"] --> R1["round 1\n2 nodes"] --> R2["round 2\n4 nodes"] --> R3["round 3\n8 nodes"] --> RN["...about log2 N + ln N rounds\nuntil all N know"]`} />
</Figure>

**Worked numbers.** With **push** gossip (each informed node tells one random peer per round), a fact reaches all of N nodes in about **log₂ N + ln N** rounds: the informed set roughly doubles until most know, then a few more rounds catch the stragglers. For 1,000 nodes that is 10 + 7 ≈ **17 rounds**; a simulation averaged 18. **Push-pull** (both sides exchange) about halves it: about 9 rounds in the same simulation. At one round per second, membership news crosses a 1,000-node cluster in under 20 seconds, with no central server and every node sending one message a second. Dynamo and Cassandra gossip membership and token ownership this way. Seed nodes help new nodes join and prevent the cluster splitting into islands.

**Failure detection: suspicion, not proof.** A fixed timeout ("dead after 3 missed heartbeats") is wrong on both sides: too short convicts every GC pause, too long leaves real failures unnoticed. The <a href={`${BASE}sd/lessons/core-concepts/#liveness`}>core concepts lesson</a> covers why you cannot tell dead from slow. **Phi-accrual detection** (Hayashibara and colleagues) outputs a *suspicion level* instead of a verdict:

- Keep the recent history of heartbeat inter-arrival times.
- For the current silence, compute **φ = −log₁₀(probability that a live node would be this late)**. φ = 1 means a 10% chance it is just late; φ = 2, 1%; φ = 3, 0.1%.
- Each consumer picks its own threshold.

**Worked numbers.** Model gaps as exponential with mean m (a simplification Cassandra uses): P(silence > t) = e^(−t/m), so **φ = 0.434 × t/m**. With 1-second heartbeats, 5 s of silence gives φ ≈ 2.2. Cassandra's default conviction threshold is **φ = 8** (`phi_convict_threshold`), reached at t = 8 ÷ 0.434 ≈ **18.4 seconds** of silence. The adaptive part: when the network gets jittery, observed gaps grow, the mean grows, and the conviction deadline stretches by itself instead of a fixed timeout firing on every blip.

```python
import math

def phi(silence_s: float, mean_gap_s: float) -> float:
    # exponential model: P(still silent at t) = exp(-t / mean)
    return -math.log10(math.exp(-silence_s / mean_gap_s))

print(round(phi(5, 1.0), 1))     # 2.2
print(round(phi(18.4, 1.0), 1))  # 8.0  (the conviction point at threshold 8)
print(round(phi(18.4, 2.0), 1))  # 4.0  (jittery network: same silence, less suspicion)
```

Permanent removal (and streaming its ranges elsewhere) is a separate, deliberate decision, usually an operator's, because a transient failure that triggers hundreds of GB of movement makes the outage worse. This is Chapter 9's fourth rule.

</Reveal>

<h2 id="routing">Chapter 15 · Who knows the map?</h2>

**What is it?** A request arrives for `cart:9913`. Somebody has to know which node owns it. **Routing** is the answer to "who holds the partition map, and how does a request use it?"

**Why does it matter?** The map changes (nodes join, slots move, leaders fail over). Whoever holds a stale copy sends requests to the wrong node. There are three common answers, and all three are used in production.

<Figure caption="Three routing styles. Smart client: one hop. Proxy: dumb clients, one extra hop. Any-node coordinator: the node you hit forwards to the owners.">
  <Mermaid code={`flowchart LR
    C1["client with cached map"] -->|"1 hop"| O1["owner node"]
    C2["client"] --> PX["proxy tier\nholds the map"] --> O2["owner node"]
    C3["client"] --> AN["any node\n(coordinator)"] --> O3["owner nodes"]`} />
</Figure>

| Routing | How | Hops | Strengths | Costs |
|---|---|---|---|---|
| **Partition-aware client** | The client library caches the partition map and goes straight to the owner; a wrong guess gets a redirect (`MOVED`) and a map refresh | 1 | Lowest latency; no middle tier | Fat clients in every language; map staleness handled by redirects |
| **Proxy / router tier** | Clients talk to a stateless proxy that knows the map (twemproxy and mcrouter for caches, MongoDB's mongos) | 2 | Dumb clients; one place to change routing, pool connections, add metrics | One more hop and one more tier to scale and keep available |
| **Any-node coordinator** | Client hits any node (often via a load balancer); that node coordinates the request with the owners (Dynamo, Cassandra) | 1–2 | Simple clients, no extra tier; every node knows the ring via gossip | Usually one extra internal hop; coordinators carry fan-out load |

**Where the map lives.** Either in a strongly consistent coordination store (ZooKeeper or etcd: HBase, Kafka's older controllers, many sharded SQL setups), with clients watching for changes, or **gossiped** among nodes (Dynamo, Cassandra, Redis Cluster's cluster bus). Coordination stores give one authoritative map with epochs; gossip avoids a dependency and converges in seconds. Either way, **version the map** so a node can say "you are behind" instead of silently serving the wrong range.

**Token-aware load balancing** combines the first and third: Cassandra drivers can pick a replica of the key as the coordinator, removing the extra hop.

<Trace title="Find the owner" steps={routing} takeaway="Smart clients for one hop; proxies for dumb clients; any-node coordinators for simplicity. MOVED updates the map; ASK does not." />

**A common slip:** drawing a "router" box and moving on. Say where its map comes from, how it learns of changes, and what happens when it is stale.

**Interview takeaway:** "Our own services embed a partition-aware client for one hop. Stale maps get a MOVED reply and a refresh. The map is versioned with an epoch so a node can tell a client it is behind."

<h2 id="storage-engine">Chapter 16 · What each node writes</h2>

**What is it?** The storage engine on each node decides how writes become bytes on disk. Dynamo-style stores almost always sit on an **LSM-tree** (Cassandra, ScyllaDB, RocksDB-backed stores; Dynamo itself had pluggable engines). The full comparison with B-trees is in the <a href={`${BASE}sd/lessons/databases/#storage-engines`}>databases lesson</a>.

**Why LSM?** Say each node takes 30,000 small writes a second, all over its key space. A B-tree updates pages in place, which means random disk writes, and the disk is pinned. An LSM turns those writes into sequential appends and pays later, in big sequential gulps called compaction.

<Figure caption="LSM write path and read path on one node.">
  <Mermaid code={`flowchart LR
    W["write"] --> CL["commit log\nappend only"]
    W --> MT["memtable\nsorted, in memory"]
    MT -->|"full: flush"| SS1["SSTable (immutable, sorted)"]
    SS1 -->|"background"| CP["compaction merges SSTables\nkeeps newest version"]
    RD["read"] --> MT
    RD --> BF["Bloom filter per SSTable\nskip files without the key"] --> SS1`} />
</Figure>

**How it works:**

1. A write appends to a **commit log** (durability) and inserts into the **memtable** (sorted, in memory). Sequential I/O only.
2. A full memtable is flushed as an immutable sorted file, an **SSTable**.
3. **Compaction** merges SSTables in the background, keeping the newest version of each key.
4. A read checks the memtable, then SSTables newest first; a **Bloom filter** per SSTable skips files that definitely do not hold the key.

**Three ways the engine meets this lesson:**

- **Streaming is cheap.** SSTables are immutable sorted files, so rebalancing can ship whole files (or slices) instead of re-inserting rows.
- **Deletes are tombstones**, which compaction eventually purges. If a replica missed the delete and repair does not run before the tombstone is purged, the next repair sees the old value on the lagging replica, treats it as missing elsewhere, and copies it everywhere: **zombie data**. Rule: run full repair more often than tombstones are kept (Cassandra's `gc_grace_seconds`, ten days by default).
- **LWW timestamps live here.** Compaction keeps the version with the highest timestamp, so LWW is the engine's natural merge. That is why it is the default and why Chapter 12 matters.

**Worked numbers.** In Chapter 17's cluster, each node holds 2 billion × 3 ÷ 30 = **200 million** items. Bloom filters at about 10 bits per key give about a 1% false-positive rate: 200 million × 10 bits = **250 MB of memory per node**, which is why Bloom-filter memory belongs in node sizing.

| | LSM-tree | B-tree |
|---|---|---|
| Write pattern | Sequential appends; compaction later | Random in-place page updates |
| Write throughput | High | Lower for random writes |
| Read | May check several files (Bloom filters help) | One tree walk |
| Cost to watch | Compaction I/O, read amplification, tombstones | Page splits, write amplification |

<Trace title="Write it down" steps={storage} takeaway="LSM engines turn random writes into appends and pay in compaction. Tombstones must outlive the repair interval, or deleted data comes back." />

**Interview takeaway:** "LSM because writes dominate and become sequential appends. Deletes are tombstones that must outlive the repair cycle, or a replica that missed the delete resurrects the item."

<h2 id="sizing">Chapter 17 · Sizing on the whiteboard</h2>

**What is it?** A quick calculation that turns requirements into a node count, done twice: once for capacity, once for throughput. The larger answer wins, and you say which one it was.

**Assumptions for this example:** 2 billion items × 1 KB; peak 200,000 reads/s at R = 2 and 50,000 writes/s at N = 3 (every replica receives every write; W only says how many we wait for); disks kept under 50% full for compaction headroom; a node comfortably serves about **20,000 replica operations per second** (an assumption: benchmark your engine and hardware); 2 TB disks.

| Quantity | Arithmetic | Result |
|---|---|---|
| Raw data | 2 × 10⁹ × 1 KB | 2 TB |
| With 3 replicas | 2 TB × 3 | 6 TB |
| Disk with 50% headroom | 6 TB × 2 | 12 TB |
| Nodes for capacity | 12 TB ÷ 2 TB | **6** |
| Replica reads/s | 200,000 × 2 | 400,000 |
| Replica writes/s | 50,000 × 3 | 150,000 |
| Nodes for throughput | 550,000 ÷ 20,000 | 27.5 → **about 28–30** |
| Data per node at 30 nodes | 12 TB ÷ 30 | 400 GB of disk |
| Items per node | 2 × 10⁹ × 3 ÷ 30 | 200 million |
| Adding a 31st node moves | 6 TB ÷ 31 | ≈ 194 GB (≈ 32 min at 100 MB/s) |

```python
raw_tb = 2e9 * 1e3 / 1e12            # 2 TB
disk_tb = raw_tb * 3 * 2             # 3 replicas, 50% headroom -> 12 TB
nodes_capacity = disk_tb / 2         # 2 TB disks -> 6
replica_ops = 200_000 * 2 + 50_000 * 3   # R=2 reads, N=3 writes -> 550,000/s
nodes_throughput = replica_ops / 20_000  # 27.5
print(nodes_capacity, nodes_throughput)  # 6.0 27.5
```

**Throughput, not capacity, sets the node count**: the data fits on 6 nodes; the request rate needs about 30. Say that sentence. Then partitions: 30 nodes × 16 vnodes = 480 tokens (or, with a slot map, a few thousand fixed partitions so each node holds dozens and moves are fine-grained).

<Trace title="Size the cluster" steps={sizing} takeaway="Count replica operations, not client requests. Compute both the capacity floor and the throughput floor; the larger one wins, and say which it was." />

**A common slip:** sizing only by storage. A store that fits on 6 nodes but needs 30 for throughput is the common case, and the interviewer wants to hear you notice.

**Interview takeaway:** "Capacity needs 6 nodes, throughput needs about 30 once I count replica operations, so throughput sets the count and each node holds about 400 GB."

<h2 id="cache-round">Chapter 18 · Design a distributed cache</h2>

**What is the question?** "Design a distributed in-memory cache, like Redis or Memcached." You get no help and no product to lean on, so the structure of your answer matters as much as the content. The checkpoints below (minutes into a 45-minute round) show a good pace.

The round follows the <a href={`${BASE}sd/lessons/delivery-framework/`}>delivery framework</a> budget: intro 3, requirements 6, entities 2, API 4, high-level 10, deep dives 13, wrap-up 3, questions 4. Each block below is what you would say.

**0:03 · Roadmap and requirements**

> "About six minutes on requirements and scale, a couple on entities and API, a simple design that works, then two or three deep dives, and a short wrap-up."
>
> "One question shapes everything: is this a pure cache, where every value can be rebuilt from a source of truth so losing recent writes on a failure is acceptable, or something teams rely on to keep data? I'll assume a pure cache."
>
> "Functional: get, set with an optional TTL, delete, and an atomic increment for counters. Values are opaque bytes up to, say, 1 MB. Clients are our own services. Out of scope: rich data structures, pub/sub, persistence beyond optional warm restarts, cross-region replication."

**0:06 · Non-functionals with numbers**

> "Target 2 million operations a second at peak, 90% reads, p99 under 1 ms inside a data centre. About a billion keys at 1 KB average: 1 TB of values, plus per-key overhead, so call it 1.1 TB. Highly available: losing a node must not cold-start a big slice of the cache, because the databases behind it cannot take the misses. Consistency: eventual; a failover may lose the last moments of writes."
>
> "Two numbers decide things. At 50 GB usable per node, capacity needs 22 primaries. At about 100,000 simple operations a second per primary, kept at 70%, throughput needs 2 million ÷ 70,000 ≈ 29, so call it 30 primaries, each with a replica. Throughput wins. Network is easy: 2 million × 1 KB is 2 GB/s across 30 nodes, about half a gigabit each."

**0:09 · Core entities**

> "Entry: key, value, expiry, and access metadata for eviction. Slot: one of a fixed 16,384. Node: a primary or a replica, owning a set of slots. And the slot map: slot to primary and replicas, with an epoch number. The slot map is the interesting entity. It is the only thing that changes when we scale."

**0:11 · API**

> "Client library calls: get(key) returns bytes or a miss; set(key, value, ttl); delete(key); incr(key, delta) returns the new value. On the wire, a simple binary protocol over long-lived TCP connections. Errors the client must handle: MOVED, meaning update your slot map; ASK, meaning try this other node once; and timeouts, which the application treats as a miss."

**0:15 · High-level design**

<Figure caption="Distributed cache: smart client, 30 primaries owning slots, async replicas in another zone.">
  <Mermaid code={`flowchart LR
    APP["app + cache client\nholds slot map and L1"] -->|"CRC16(key) mod 16384\none hop"| P1["primary 1\nslots 0 to 545"]
    APP --> P2["primary 2"]
    APP --> P30["primary 30"]
    P1 -.->|"async"| R1["replica 1\nother zone"]
    P2 -.-> R2["replica 2"]
    P30 -.-> R30["replica 30"]
    P1 <-->|"gossip + epochs"| P2`} />
</Figure>

> "Keys map to slots by CRC16 mod 16,384, fixed forever. Slots map to 30 primaries, about 546 each. A smart client library holds the slot map and talks directly to the owning primary: one hop. Each primary has a replica in another zone, fed asynchronously. Inside a node: one hash table, an event loop, values in memory, a per-node memory limit with eviction. The slot map lives in the cluster itself and is gossiped, with epochs so stale maps are detected; a coordination store like etcd would also work."
>
> "A get: the client hashes the key, finds slot 3999, sends to that primary, gets the value. If the map is stale, the node replies MOVED with the right address; the client updates its map and retries."

**0:25 · Deep dive 1: partitioning and resharding**

> "Why slots and not mod N: going from 30 to 31 primaries with mod N would move 30/31, about 97%, of keys: a cold cache and a database stampede. With slots, the 31st primary takes about 528 slots, 3.2% of keys. Moving a slot: mark it migrating on the source and importing on the target, move keys in throttled batches; a client asking the source for a key already moved gets ASK and asks the target once; when the slot is done the map's epoch advances and everyone gets MOVED. Related keys that need multi-key operations share a hash tag, the braces in `{user:42}:cart`, so they share a slot."

**0:30 · Deep dive 2: memory, eviction and hot keys**

> "Each node evicts when full. Approximate LRU by sampling: pick a few random keys, evict the least recently used, so we do not keep a linked list across a billion keys. LFU if scans pollute the cache. Expiry is lazy on access plus a periodic sampler, so expired keys do not sit in memory. The other memory problem is popularity. One celebrity key at 400,000 reads a second exceeds any single primary, and more shards do not help: one key, one slot. The client library gets an optional L1: a tiny in-process cache with a 1-second TTL for keys flagged hot, so 200 app servers send about 200 reads a second for it. Hot writes, like a counter, get salted into sub-keys."

**0:34 · Deep dive 3: replication and failover**

> "Replicas are async, so a write is acknowledged after the primary has it. When a primary stops answering, a majority of the other primaries must agree it has failed; its replica then wins an election among them and is promoted with a new, higher epoch. A cache accepts losing the last moments of writes; I would say that explicitly. The epoch fences the old primary if it comes back. While a slot's primary is gone, reads for those slots can be served by the replica if the caller accepts staleness. And the thing I would watch: if a whole zone fails, 30 replicas promote at once, so the remaining zone must have headroom, which is why we run at 70%."

**0:38 · Wrap-up**

> "Recap: a 30-primary cluster, 16,384 slots, smart clients, async replicas in another zone, sampled eviction, hot-key L1. At 10× scale the first limits are per-primary operations, which more primaries fix cheaply because slots move, and the slot map's gossip traffic. I would monitor hit ratio, per-slot ops to find hot keys, eviction rate, replica lag, and memory fragmentation. Next: optional snapshotting for warm restarts, and cross-region invalidation if we go multi-region."

**Check the numbers yourself:** 1.1 TB ÷ 50 GB = 22. 2,000,000 ÷ (100,000 × 0.7) ≈ 28.6 → 30. 16,384 ÷ 30 ≈ 546; 16,384 ÷ 31 ≈ 528 (3.2%). 2,000,000 × 1 KB = 2 GB/s = 16 Gbit/s, ÷ 30 ≈ 0.53 Gbit/s. mod N 30 → 31 moves 30/31 ≈ 97%.

**Cache vs store, the difference that changes the design:**

| | Pure cache | Store people rely on |
|---|---|---|
| Replication | Async; may lose the last writes on failover | Quorums or consensus, durable log |
| On node loss | Misses are acceptable, but avoid a cold-start storm | Data must survive; repair needed |
| Eviction | Yes, by design | No: capacity planning instead |
| Typical placement | Fixed slots or ring | Ring or ranges plus replication |

> "Item: key, value, version vector. Node, with its tokens on the ring. A key's preference list: three distinct nodes in three zones. A hint: a write held for a node that is down. And per key range, a Merkle tree for repair."

**0:15 · API**

> "get(key, consistency) returns a list of values plus an opaque context, a list because concurrent versions can exist. put(key, value, context, consistency): the context is the version vector the writer read, so the store knows what this write supersedes. delete is a put of a tombstone. Consistency levels: ONE, QUORUM, ALL, default QUORUM. Over HTTP: GET and PUT on `/kv/{key}`, context in a header."

> "No master. Every node is equal. Keys and nodes sit on a consistent-hash ring with vnodes, 16 to 256 tokens per node, so load is even, a dead node's work spreads over everyone, and bigger machines get more tokens. A request reaches any node through a load balancer, or a token-aware client picks a replica directly; that node coordinates. It finds the key's preference list, the next three distinct nodes clockwise, one per zone, sends to all three, and waits for W = 2 acks on writes, R = 2 replies on reads. Two plus two is more than three, so normal reads overlap the latest write. Each node stores data in an LSM engine: commit log, memtable, SSTables, Bloom filters. Membership travels by gossip."
>
> "Sizing: 6 TB with replicas, 12 TB of disk with compaction headroom, so six nodes for capacity. But 400,000 replica reads plus 150,000 replica writes is 550,000 operations a second; at 20,000 per node that is about 30 nodes. Throughput sets the count; each holds about 400 GB."

**0:32 · Deep dive 1: partitioning and replication**

> "Adding a 31st node takes about 1/31 of the data, 194 GB, streamed as SSTable slices from many peers in parallel, throttled to about 100 MB/s cluster-wide, about half an hour, with old owners serving until the new one catches up. Removing a node is an explicit operator action, never a reaction to a timeout. Without vnodes, one neighbour would inherit a dead node's whole arc; with 256 tokens the busiest node sits about 10% above average instead of nearly 3×."

**0:38 · Deep dive 2: conflicts**

> "Because we never refuse a write, two writes to one cart can happen concurrently, a phone and a laptop. Last-write-wins would silently drop one: the lamp vanishes. So each value carries a version vector. On read, if one version dominates, return it; if they are concurrent, return both siblings with a merged context; the cart service unions them and writes back, and the new vector dominates both. I would allow LWW per table where it is correct, like a last-seen timestamp. Union has one known wart, a deleted item can come back, which we can fix with a cart CRDT that tracks removals."

**0:43 · Deep dive 3: failures and repair**

> "Three layers. Short outages: a sloppy quorum. If a home replica is down, the coordinator writes to the next healthy node with a hint, and hands it off when the node returns. That is what makes add-to-cart always succeed, and I will say the cost: during that window, W + R > N no longer guarantees overlap. Reads: read repair writes the newest version back to stale replicas. Everything else: Merkle-tree anti-entropy per key range in the background; with a million buckets, finding one bad key takes about 41 hash comparisons, and only that bucket moves. Failure detection: gossip carries heartbeats; phi-accrual turns silence into suspicion, at φ = 8 with 1-second heartbeats about 18 seconds, and suspicion only reroutes traffic, it never moves data."

**0:48 · Deep dive 4: the storage engine and deletes**

> "LSM because writes dominate per node and turn into appends. Deletes are tombstones, and they must live longer than our repair cycle: say tombstones kept ten days, repair every seven, or a replica that missed the delete resurrects the item. Bloom filters cost about 10 bits per key: 200 million keys per node is 250 MB of memory, part of node sizing."

**0:52 · Wrap-up**

> "Recap: a leaderless ring of 30 nodes, three zones, N = 3, W = R = 2 by default, sloppy quorums with hinted handoff for always-on writes, version vectors with sibling merge, three repair paths. At 10×, the first limits are hot keys, handled by salting and client caching, and repair cost, which pushes us toward incremental repair. I would monitor p99 per coordinator, hints pending, sibling counts, repair lag versus the tombstone window, and per-node load. If you wanted compare-and-set, I would add a consensus path per key, or choose a leader-per-partition design instead."

<Reveal q="The interviewer changes one requirement: 'Strong consistency, and we need compare-and-set.' What changes?">

The replication family. Keep partitioning (ranges or slots work well), but give each partition a **leader elected by consensus** (Raft or Paxos per partition, as Spanner, CockroachDB and the DynamoDB service do). <h2 id="unlocks">Chapter 20 · Same pattern, other systems</h2>

**What is it?** The same ring, slot and range ideas answer several other interview questions. Pick the one that matches the access pattern.

**S3-like object storage.** Two partitioned layers with different shapes:

- **Metadata** (bucket, key → size, version, chunk locations): needs `LIST` by prefix in order, so it is **range-partitioned on (bucket, key)**, with ranges split automatically by size and by load. A hot prefix gets split; that is why object stores document request rates *per prefix* and why spreading keys across prefixes once mattered (AWS documents per-prefix limits; check current docs). Metadata wants strong consistency (read-after-write on a new object), so each range has a consensus-replicated leader.
- **Data** (the bytes): immutable chunks placed by **hash** of the chunk id onto **placement groups** (a fixed slot map: Ceph, for example, maps objects to placement groups and then uses its CRUSH algorithm to map groups to disks). Durability comes from **erasure coding** rather than three copies: 6 data + 3 parity chunks survive any 3 losses for **1.5×** storage, against 3× for replication. 10 PB of objects is 15 PB raw instead of 30 PB. The <a href={`${BASE}sd/lessons/blob-cdn/#durability`}>blob storage lesson</a> covers durability, multipart uploads and versioning.

**Distributed counters.** Two different problems:

- **One hot counter in one region** (100,000 increments/s on a viral post): salting into 16 sub-keys, 6,250/s each, reads sum them or a roll-up stores the total. Also batch: a server accumulates 100 increments and writes +100. The <a href={`${BASE}sd/lessons/pattern-timeseries/`}>time-series pattern lesson</a> builds this out.
- **A counter written in several regions that may be partitioned:** a **G-counter** CRDT. Each region increments only its own entry; merge takes the per-region max; the value is the sum. Worked: `{US:120, EU:75, AP:40}` = 235. During a partition, US counts 5 more (`US:125`) and EU 3 more (`EU:78`). Merging in either order gives `{US:125, EU:78, AP:40}` = **243 = 235 + 8**: no increment lost. LWW on a single integer would have kept one region's total; incrementing one integer in place in both regions would have double-counted the base. Unlikes need a second G-counter of decrements (a **PN-counter**).

```python
class GCounter:
    def __init__(self, region: str, counts: dict[str, int] | None = None):
        self.region = region
        self.counts = dict(counts or {})

    def incr(self, n: int = 1) -> None:
        self.counts[self.region] = self.counts.get(self.region, 0) + n   # only touch our own entry

    def merge(self, other: "GCounter") -> None:
        for r, c in other.counts.items():
            self.counts[r] = max(self.counts.get(r, 0), c)               # per-region max

    def value(self) -> int:
        return sum(self.counts.values())

us = GCounter("US", {"US": 120, "EU": 75, "AP": 40})
eu = GCounter("EU", {"US": 120, "EU": 75, "AP": 40})
us.incr(5); eu.incr(3)            # both sides keep counting during the partition
us.merge(eu); eu.merge(us)        # partition heals, merge in any order
print(us.value(), eu.value())     # 243 243
```

**Five follow-ups you will get:**

<Reveal q="1 · What exactly happens when you add a node?">

On a ring with vnodes, the new node's tokens each take over one small arc from that arc's current owner, so it receives about 1/(N + 1) of the data from many peers. It streams those ranges in the background, throttled; the old owners keep serving until it has caught up, including writes made during the copy; then the partition map's epoch advances and requests go to the new owner. No other key moves.

</Reveal>

<Reveal q="2 · Why virtual nodes? Isn't the hash uniform already?">

The hash makes each position uniform; it does not make the gaps between N random positions equal. With one token per node the largest arc averages H(N) / N, about 2.9× fair share for 10 nodes. With V tokens, each node's share is a sum of V arcs and its spread shrinks like 1/√V. Vnodes also scatter a dead node's load over all survivors, and let bigger machines take more tokens.

</Reveal>

<Reveal q="3 · One key gets 500,000 requests a second. Now what?">

More nodes will not help: a key lives in one partition. Reads: an in-process cache with a ~1 s TTL on each app server, reads spread across replicas, or the key copied under N suffixes. Writes: salt into sub-keys and sum on read (or roll up). And detect it with per-partition and top-key metrics rather than waiting for the page.

</Reveal>

<Reveal q="4 · Two replicas of a key's three die. What happens to reads and writes?">

With N = 3 and strict quorums of 2, keys whose preference list included both dead nodes cannot reach W or R: they become unavailable. With sloppy quorums, writes go to the next healthy nodes with hints and succeed; reads might miss the newest value until handoff. Either way, failure detection only reroutes; re-replicating to new nodes is a deliberate step once the nodes are declared gone, and Merkle repair finishes the job.

</Reveal>

<Reveal q="5 · Two clients write the same key at the same time. Who wins?">

It depends on what I chose, and I would say it per table. Last-write-wins keeps the higher timestamp and silently drops the other, which is fine for a last-seen time and wrong for a cart. For carts, version vectors detect that neither write saw the other; the store keeps both as siblings and the application merges them, or the value is a CRDT that merges itself. If the requirement is "exactly one winner", like a username, that needs a leader or consensus, not a quorum.

</Reveal>

## Five mistakes to leave behind

1. **`hash mod N` with no comment.** Say what adding one node moves, or do not use it.
2. **A ring without vnodes.** Uneven arcs and a dead node's whole load on one neighbour.
3. **"Add more shards" for a hot key.** One key, one partition. Cache, replicate or salt.
4. **W + R > N quoted next to sloppy quorums.** You get one or the other during an outage.
5. **Last-write-wins for anything users add to.** Version vectors or CRDTs, or say what is lost.

**Keep it warm.** With a friend or a timer, narrate consistent hashing from a blank page in **5 minutes**: ring, placement, adding a node, vnodes, replica walk, as if asked "how would your cache scale?" **Further study**

- [Dynamo: Amazon's Highly Available Key-value Store](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) (SOSP 2007) — the source of Chapter 19: rings with virtual nodes, preference lists, sloppy quorums, hinted handoff, vector clocks, Merkle anti-entropy, gossip. Read sections 4 and 6.
- *Designing Data-Intensive Applications* (Martin Kleppmann) — chapter 6 (partitioning: rebalancing, request routing) and chapter 5 (leaderless replication, quorums, concurrent writes and version vectors).
- [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/) — hash slots, hash tags, MOVED and ASK, slot migration, failover.
- *Bigtable: A Distributed Storage System for Structured Data* (OSDI 2006) — range partitioning into tablets, splits, and a master that assigns them.
- *Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service* (USENIX ATC 2022) — how the service differs from the paper: leader per partition, Multi-Paxos, adaptive capacity for hot partitions.
- [Consistent hashing](https://en.wikipedia.org/wiki/Consistent_hashing) and [Rendezvous hashing](https://en.wikipedia.org/wiki/Rendezvous_hashing) (Wikipedia) — history, variants, and the load-balance analysis.
- [Merkle tree](https://en.wikipedia.org/wiki/Merkle_tree) and [Conflict-free replicated data type](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type) (Wikipedia) — the structures behind Chapters 13 and 20.
- *The φ Accrual Failure Detector* (Hayashibara, Défago, Yared, Katayama, 2004) — the paper behind Chapter 14's suspicion levels.

**Look these up yourself**

- **Jump consistent hash** (Lamping and Veach) — a tiny, stateless algorithm with perfect balance when nodes are numbered and only appended; why it cannot remove an arbitrary node.
- **Maglev hashing** — Google's lookup-table consistent hashing for load balancers: faster lookups, near-perfect balance, slightly more movement.
- **Bounded-load consistent hashing** — capping each node at (1 + ε) × average and spilling to the next node; a tool against hot spots in caches.
- **SWIM** — a membership protocol that replaces all-to-all heartbeats with indirect probes and piggybacked gossip; scales to large clusters.
- **Dotted version vectors** — how Riak fixed sibling explosion when many clients write through one coordinator.
- **Hybrid logical clocks** — timestamps that respect causality while staying close to wall time; used by stores that need LWW without skew surprises.
- **Copysets** — choosing replica sets deliberately so that a few simultaneous failures are much less likely to lose all copies of some partition.
- **Incremental repair** — repairing only data written since the last repair, and why it makes tombstone windows easier to meet.
