<h2 id="prologue">Prologue · Two laptops, one file</h2>

Here is a real kind of bug report. A user edits a slide deck on a plane. Her co-founder edits the same deck on another plane. Both land and both laptops sync. Her three hours of slides are gone.

The logs show what happened. Both laptops uploaded `q3-deck.key` within forty seconds of each other. The server took the second upload, called it version 9 and moved on. Version 8 (the first laptop's work) still sits in cold storage, referenced by nothing. Nobody's screen ever said "conflict".

Everyone draws sync as one arrow between two boxes. This lesson is about what that arrow does when the two sides disagree.

The pattern is about **copies**. A phone, a laptop, a browser tab and a server all hold the same shared state. Each can change it while the others aren't looking, either offline or just in the same second as someone else. Later the copies meet and the system must **reconcile** them. Every sync design answers three questions:

1. **What changed?** Detect edits cheaply and move only the changed bytes.
2. **What did the editor start from?** Without the *base version*, "different" can't be split into "newer" and "concurrent".
3. **When two changes are concurrent, what happens?** The ladder below. Choosing the right rung per kind of data is most of the work.

<Figure caption="The escalation ladder. Climb only as high as the data needs; each rung costs more machinery than the one below.">
  <Mermaid code={`flowchart TB
    R1["Rung 1 · Detect and punt\nkeep both: conflicted copy\nopaque files"] --> R2["Rung 2 · Last-writer-wins\nnewest replaces older\ncursors, toggles, presence"]
    R2 --> R3["Rung 3 · Transform (OT)\nreorder edits through a server\nlive text, Google Docs style"]
    R3 --> R4["Rung 4 · Merge by construction (CRDT)\nany order converges\noffline-first, peer-to-peer"]`} />
</Figure>

**Where it shows up.** Two classic interview questions live here, **Dropbox / Google Drive** and **Google Docs**, at opposite ends of the ladder. Calendars, Figma-style canvases, shared carts, note apps and every "works offline" mobile app sit in between.

**Interview angle.** Google Docs separates people who have heard of OT from people who can say why the server exists. And "I will not auto-merge here" is a senior answer, not a cop-out, when the data is opaque.

<h2 id="replicas">Chapter 1 · Every device is a leader</h2>

An offline-capable client is a **multi-leader replica** (the general theory is in <a href={`${BASE}sd/lessons/databases/#multi-leader`}>Databases · More than one leader</a>). The moment a laptop can save while offline, it is a database that accepts writes. You don't have one leader. You have one per device.

When two writes to the same thing meet, the system must decide whether one **happened after** the other or whether they are **concurrent**:

- **Sequential.** Laptop B downloaded version 8, then edited it. B's edit *knew about* version 8, so it simply replaces it. No conflict.
- **Concurrent.** A and B both edited version 8 without seeing each other's change. Neither knows about the other. That is a conflict.

**The base version is the whole trick.** Every write says "I started from version N". If N is still current, apply it. If not, someone got there first.

</Figure>

### One authority: a version counter is enough

If one server orders every commit (a Dropbox-style product), each file carries one number. A commit says "parent = 8". The server accepts it only if the file is still at 8. Every concurrent edit is caught.

### No authority: version vectors

Now remove the server. Two phones sync directly, or a leaderless store accepts writes on any node. There is no single counter to compare. Each replica keeps a **version vector**: one counter per replica, `{A: 2, B: 1}`.

The rules are short:

1. A replica that writes increments **its own** entry.
2. Merging two vectors takes the **element-wise maximum**.
3. To compare, vector X **dominates** Y if every entry in X is at least the matching entry in Y. If X dominates Y, Y happened before X, and X simply replaces it. If **neither** dominates, the writes are concurrent: a real conflict.

| Event | Vector | Relation to the previous |
|---|---|---|
| A writes the first version | `{A:1}` | start |
| B syncs it, then edits | `{A:1, B:1}` | dominates `{A:1}`: sequential |
| A edits again, without seeing B | `{A:2}` | vs `{A:1, B:1}`: neither dominates, **concurrent** |
| Someone resolves, writing a merged value | `{A:2, B:1}` | element-wise max, dominates both |

**Vector clock vs version vector.** The mechanics are the same. A *vector clock* orders events across processes (messages, debugging). A *version vector* tracks versions of one data item across replicas. Many sources use the terms loosely. A **Lamport clock** is a single counter: it gives an order that respects causality, but `L(a) &lt; L(b)` does not prove `a` happened before `b`, so it cannot detect concurrency by itself.

**Cost.** A vector has one entry per replica that ever wrote, so it grows with the number of writers. Stores with many clients typically key the vector by server node rather than by client, or prune old entries and accept a rare false conflict. Check your store's docs for exactly what it does.

<Trace title="Compare the vectors" steps={vectors} takeaway="One authority → a parent check and a counter. No authority → a vector; if neither side dominates, the writes are concurrent." />

**Worked numbers: how often does this happen?** The Dropbox-style design later in this lesson sees about 40 million commits a day. If just 0.1% are concurrent with another device's edit, that is **40,000 conflicts a day**. Each is either shown to a person or silently resolved. The design decides which.

**A common slip:** "We sync the latest version to every device." Latest by what? Wall-clock time is not an order (next chapter). Say "each commit names its parent version; the server accepts it only if the parent is current".

<h2 id="lww">Chapter 2 · Last-writer-wins and the edit that vanished</h2>

**Last-writer-wins (LWW)**: stamp every write with a timestamp; on conflict keep the highest. It is cheap, needs no coordination, and is the default conflict rule in several Dynamo-style stores. It also **silently loses data**: the "loser" vanishes and nobody decided that it should.

Two separate problems hide in it:

1. **The policy problem.** Even with perfect clocks, LWW drops one of two concurrent writes. For a document, a cart or a counter, both writes mattered.
2. **The clock problem.** Device clocks skew by seconds or worse. NTP narrows server skew to milliseconds, not zero. "Last" is partly fiction, so the winner is sometimes the *earlier* write.

Here is the whole mechanism, and how it loses data, in a few lines:

```python
def lww_merge(a, b):
    return a if a["ts"] >= b["ts"] else b

phone  = {"title": "Q3 plan",    "body": "draft A", "ts": 1000.2}   # edited the body
laptop = {"title": "Q3 plan v2", "body": "draft",   "ts": 1000.9}   # edited the title
print(lww_merge(phone, laptop))
# {'title': 'Q3 plan v2', 'body': 'draft', 'ts': 1000.9}   the body edit is gone
```

Two things went wrong at once. The writes touched *different* fields yet one whole record won. And if the laptop's clock ran 1 second slow, the phone would have "won" and the title edit would be the one lost. Either way, no error and no log line.

<Trace title="Who wins?" steps={lww} takeaway="LWW is a product decision: newest replaces older. It is honest only when the older value is genuinely worthless once a newer one exists." />

| Data | LWW honest? | Why |
|---|---|---|
| Cursor position, presence ("online"), typing indicator | **Yes** | Only the newest value has meaning |
| A settings toggle, a profile photo | **Yes**, usually | Newest intent supersedes; say it out loud |
| A document, a file's contents | **No** | Both edits were work |
| A shopping cart, RSVP list | **No** | It is a set: merge with union (an add-wins set) |
| A like counter | **No** | Two +1s must become +2: per-replica counts summed (a G-counter CRDT) |

**The sentence to use:** "LWW is acceptable here because losing the older write is the correct product behaviour." If you can't finish that sentence truthfully, don't use LWW.

<Reveal q="Can you fix LWW by using a better clock, such as a hybrid logical clock or the server's receive time?">

A better clock fixes the **clock** problem, not the **policy** problem. Server receive time gives a consistent order (whichever upload arrived later wins), so skew no longer picks the winner. But two concurrent edits still produce one survivor and one silent loss. For data where both writes matter you need conflict *detection* (parent versions or vectors) and then a rung that keeps or merges both.

</Reveal>

**A common slip:** reaching for LWW because the store you named (Cassandra, DynamoDB) does it by default. Defaults are not designs. Say which data uses it and why losing the older write is fine for that data.

<h2 id="chunking">Chapter 3 · Chunking and content hashes</h2>

A user saves a 200 MB video project after changing one title card. It takes five minutes on hotel wifi, every save. The client splits files into 4 MB blocks and uploads only blocks whose hash changed, so it should have sent one block. Why didn't it?

The app writes a header with an edit count at the very start of the file. The header grew by one byte. Every byte after it moved one place, so every block changed. The cause is **where the block boundaries go**.

Two ideas come from <a href={`${BASE}sd/lessons/blob-cdn/#dedup`}>Blob storage · The same file twice</a>, and Dropbox-style sync is built on them:

- **Split a file into chunks and name each chunk by its content hash** (SHA-256). A file becomes an ordered list of hashes. This is **content-addressed storage**.
- **Only upload chunks the server doesn't already have.** Unchanged chunks cost nothing to re-sync.

**Fixed-size chunking** cuts every 4 MB. Overwrite bytes in place and only one chunk changes. But **insert** one byte and every following byte shifts right. The boundaries stay at multiples of 4 MB, so *every* chunk after the insertion holds different bytes. A 200 MB file is 50 chunks; one byte at the front means **50 new chunks, 200 MB of upload**.

**Content-defined chunking (CDC)** cuts where the **content** says so. Slide a window over the bytes and compute a **rolling hash** of the last few dozen bytes at every position ("rolling" because each step updates the hash in constant time as one byte enters and the oldest leaves). Declare a boundary wherever that hash matches a pattern, for example its top 22 bits are all zero. That happens about once per 4 million bytes, so chunks average about 4 MB.

**Why CDC survives insertions.** A boundary depends only on the bytes just before it. Insert a byte: the chunk containing it changes. The next boundary after the edit sits on the same content as before, so it is found again, and from there every chunk is identical to the old version. The chunking **re-synchronises itself**. One insertion changes about one chunk.

Here is a compact CDC chunker using a **gear hash**, the rolling hash behind the FastCDC family. Each step shifts the hash left one bit and adds a random 64-bit value for the incoming byte. After 64 shifts a byte's contribution has fallen off the top, so the hash at any position depends **only on the last 64 bytes**. That is the window, with no explicit window bookkeeping. (Testing the *top* bits matters: the low bits of a gear hash only see the last few bytes.)

```java id=chunker group=chunking
/** Splits bytes into chunks. Each method returns the end offset (exclusive) of every chunk. */
static final class Chunker {
    static final long[] GEAR = new long[256];     // one random 64-bit value per byte value
    static {
        Random random = new Random(2026);         // any fixed table works — but every client must share it
        for (int i = 0; i < 256; i++) GEAR[i] = random.nextLong();
    }

    /** Fixed-size chunking: a boundary every `size` bytes, wherever it falls. */
    static List<Integer> fixed(byte[] data, int size) {
        List<Integer> ends = new ArrayList<>();
        for (int end = size; end < data.length; end += size) ends.add(end);
        if (data.length > 0) ends.add(data.length);
        return ends;
    }

    /**
     * Content-defined chunking: cut where a rolling hash of the last 64 bytes has its top
     * `bits` bits all zero (probability 1 in 2^bits per byte), never before `min` bytes and
     * always by `max` bytes. Average chunk ≈ min + 2^bits.
     */
    static List<Integer> contentDefined(byte[] data, int min, int bits, int max) {
        long mask = -1L << (64 - bits);           // the top `bits` bits
        List<Integer> ends = new ArrayList<>();
        int start = 0;
        long hash = 0;
        for (int i = 0; i < data.length; i++) {
            hash = (hash << 1) + GEAR[data[i] & 0xff];   // gear hash: a byte's influence shifts out after 64 steps
            int length = i - start + 1;
            if ((length >= min && (hash & mask) == 0) || length >= max) {
                ends.add(i + 1);
                start = i + 1;
            }
        }
        if (start < data.length) ends.add(data.length);
        return ends;
    }
}
```

**Why the min and max.** Without a minimum, unlucky content produces tiny chunks (more metadata per byte). Without a maximum, content that never matches the pattern, such as a file of zeros, produces one giant chunk. Clamping both keeps sizes predictable.

The checker for this page runs a scaled-down experiment: a file of about 50 average-sized chunks, one byte inserted at the front or middle. Across 120 random edits, fixed chunking re-uploaded **every chunk from the edit onwards**, while CDC never produced more than **two** new chunks (almost always one). An in-place overwrite changed one fixed chunk and at most two CDC chunks.

<Trace title="Count the chunks" steps={chunking} takeaway="Fixed boundaries stay put while content slides under them. Content-defined boundaries move with the content and re-synchronise after the edit." />

| Edit to the 200 MB file | Fixed 4 MB chunks | CDC, ~4 MB average | Whole-file upload |
|---|---|---|---|
| Overwrite a title card in place | 1 chunk · 4 MB | 1–2 chunks · 4–8 MB | 200 MB |
| Insert one byte at the front | **50 chunks · 200 MB** | 1–2 chunks · 4–8 MB | 200 MB |
| Rename the file | 0 bytes | 0 bytes | 0 bytes (metadata only) |

On 5 Mbit/s wifi, 200 MB takes 200 × 8 / 5 = 320 seconds (about five minutes) and 4 MB takes 6.4 seconds. CDC turns a front-of-file edit from a 25–50× penalty into a non-event.

**Chunk size is a dial.** Smaller chunks dedup better and re-upload less per edit, but mean more hashes, more round trips and more metadata rows. Megabyte-scale chunks are a common choice for sync products. Backup tools often use kilobyte-scale chunks because they care more about dedup ratio than metadata size.

**Fixed vs content-defined, side by side**

| | Fixed-size | Content-defined |
|---|---|---|
| Boundary rule | Every N bytes | Where a rolling hash matches a pattern |
| Insert near the start | Every later chunk changes | About one chunk changes |
| CPU | Trivial | A hashing pass over every byte |
| Seek to chunk k | Arithmetic | Needs the chunk index |
| Best for | In-place edits, same-length rewrites (VM images, databases) | Documents, archives, anything that shifts on insert |

**Interview takeaway.** "Content-defined chunks hashed on the client; the server tells us which hashes it lacks; we upload only those."

<Reveal q="If CDC is strictly better at insertions, why would anyone still use fixed-size chunks?">

Fixed chunks are trivial to compute, need no per-byte hashing pass, match how many apps write files (in place, same length) and let you seek to "chunk k" by arithmetic. CDC costs a full hashing pass and gives variable sizes. If files are mostly edited in place or replaced wholesale, fixed chunks lose little. Say which kind of files you expect.

</Reveal>

**A common slip:** "We'll only upload the diff." Diff against what, computed where? Say it as above: chunks, hashes, missing-hash check.

<h2 id="metadata">Chapter 4 · A file is a list</h2>

The server does not store "a file". It stores a line like this:

`q3-deck.key  v9  →  [ a71f…, 03c2…, e9d0… ]`

The bytes live somewhere else, named by their hashes. So what does saving a file write, and in what order?

Two stores with very different shapes:

| Store | Holds | Size (numbers from Chapter 9) | Access |
|---|---|---|---|
| **Block store** (object storage) | Chunks, keyed by SHA-256 | ~32 PB after dedup | Write once, read many; never updated in place |
| **Metadata service** (a relational DB, sharded) | Namespaces, file entries, versions, chunk lists, the journal | ~10 TB | Small rows, transactions, "everything after position N" |

**The metadata model** (names, not full DDL):

- **Namespace**: a sync root, one user's Drive or one shared folder. Everything is sharded by `namespace_id`, because every sync query is "what changed in *this* namespace".
- **FileEntry**: `(namespace_id, path)` → current revision, or a deleted marker (Chapter 7).
- **FileVersion**: `(namespace_id, path, rev)` → parent rev, size, **ordered list of chunk hashes**, author device, time.
- **Journal**: `(namespace_id, position)` → which path changed to which rev. Positions only grow. Devices sync from this (next chapter).
- **Chunk**: `hash` → size, location, reference count or GC bookkeeping.

**Saving a file: chunks first, metadata last.**

<Figure caption="The commit protocol. The version becomes visible only at the commit, and by then every chunk it names already exists.">
  <Mermaid code={`sequenceDiagram
    participant C as Client
    participant M as Metadata service
    participant B as Block store
    C->>C: chunk + hash: h1, h2, h7
    C->>M: which of h1, h2, h7 are missing?
    M-->>C: missing: h7
    C->>B: PUT h7 (presigned URL)
    B-->>C: stored (hash verified)
    C->>M: commit path, parent v8, chunks h1 h2 h7, commit id c-91
    M->>M: one transaction: check parent = current, write v9, append journal entry
    M-->>C: ok, rev v9, journal position 41212`} />
</Figure>

- **Ask before uploading.** "Which of these hashes are missing?" is the dedup step. Scope the answer to the user or namespace. A global "already have it" leaks whether *anyone* stores that file and lets a known hash stand in for the bytes (argument in <a href={`${BASE}sd/lessons/blob-cdn/#dedup`}>Blob storage</a>).
- **Upload directly to the block store** with presigned URLs, so app servers never carry the bytes. The block service **verifies the hash** of what it received; a client can't claim `h7` and upload something else.
- **Commit in one transaction**: check the parent, write the version, append to the journal. That transaction is the moment the new version exists.
- **Make the commit retry-safe** with the parent version plus a client-generated commit id. A retry after a timeout either finds its own commit (success) or a different one (conflict, Chapter 6).

<Trace title="Save it in the right order" steps={commit} takeaway="Missing-hash check → upload only those chunks → one conditional, idempotent commit that names its parent." />

**Worked numbers.** A typical 1 MB document is one chunk. Saving it after a small edit: one "missing?" call, one 1 MB PUT, one commit transaction writing two rows. Renaming a 2 GB video: zero chunk uploads, one commit with the same chunk list and a new path.

<Reveal q="Chunks are shared between files and versions. When can a chunk be deleted?">

Only when no live version references it. Two common approaches: **reference counts** updated with each version write and delete (fast, but counts drift under failures and races), or periodic **mark-and-sweep** over all live manifests with a grace period, so a chunk uploaded seconds ago for a commit in flight isn't collected. Many designs run mark-and-sweep, sometimes with refcounts as a hint. Version history means chunks of a "deleted" file stay alive for the retention window (say 30 days) on purpose.

</Reveal>

**A common slip:** committing metadata first "so the UI is fast". Another device reads the journal, sees v9, asks for `h7`, and gets a 404. Visible metadata must only ever point at bytes that exist.

<h2 id="sync-protocol">Chapter 5 · The cursor</h2>

At scale, the first sync design that comes to mind is to have every client list every folder every minute and compare. Ten million devices re-reading a phone book to learn that nothing changed: the list endpoint ends up at 70% of database CPU. The fix is for a device to remember one number.

A device tracks sync state with **three journals**, not a full scan:

1. **The local watcher.** The client subscribes to file-system events (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows). Events are hints: they can be dropped, merged, or arrive mid-save. So the client **debounces** (waits until size and mtime stop changing), re-hashes, and compares with its own record. A periodic full rescan catches anything the watcher missed.
2. **The local database.** A small embedded database (think SQLite) holding, for every synced path, the rev and chunk list the device last agreed with the server: the **base** for the next edit. Comparing disk against this tells the client what *it* changed.
3. **The server journal and the cursor.** Each namespace has an append-only journal with increasing positions. A device's **cursor** is the last position it applied. Sync down is one question: "give me every entry after 41,212".

<Figure caption="Sync down: the notification says only 'something changed'; the cursor fetch is the source of truth.">
  <Mermaid code={`sequenceDiagram
    participant D as Device
    participant N as Notification service
    participant M as Metadata service
    participant B as Block store
    D->>N: long-poll: namespace 7, cursor 41212
    Note over N: held up to ~60 s
    M-->>N: namespace 7 advanced to 41215
    N-->>D: changed
    D->>M: list changes after 41212
    M-->>D: 3 entries, new cursor 41215
    D->>B: GET missing chunks
    D->>D: assemble file in temp, atomic rename, record rev + cursor locally`} />
</Figure>

**Why a cursor and not a timestamp.** "Changes since 10:04:31" double-counts or drops entries that share a millisecond, and clocks skew. A journal position is exact, gap-free and resumable. A device offline for three days sends its cursor and pages through what it missed.

**Notify, then pull.** A cheap long-poll (or WebSocket; see <a href={`${BASE}sd/lessons/pattern-realtime/`}>Realtime</a>) that carries **only "something changed"** keeps the protocol safe:

- A lost notification costs latency, never correctness: the next poll, or a periodic check every few minutes, still fetches by cursor.
- The notification server holds no data and no state worth losing. If it dies, clients reconnect elsewhere.
- Fan-out is cheap: one commit wakes the few devices watching that namespace.

**Applying a change safely.** Download chunks to a temp file, verify hashes, then **atomically rename** over the old file. Never write in place, or a crash leaves half a file. If the user edited the local file since the base rev, this is a conflict (next chapter), not an overwrite.

<Trace title="Stay in sync" steps={protocol} takeaway="Watch locally, debounce, compare with the last-synced base. Sync down by cursor, woken by a data-free notification." />

**Worked numbers.** 5 million devices connected at peak, each holding one long-poll. Assumption: 100,000 idle connections per notification server (benchmark it; idle connections are mostly memory). That is **50 servers**. Commits peak at about 1,400 per second; each wakes the user's other devices (say two), so about **2,800 wake-ups per second**, which is trivial. Polling would have been 5 million devices × one list call a minute ≈ 83,000 requests per second, nearly all returning "nothing new".

**A common slip:** pushing file contents over the notification channel. Devices may be offline, slow or on metered data. The notification is a hint; the device pulls what it needs by cursor.

<h2 id="conflicts">Chapter 6 · Conflicted copies</h2>

The fix for the lost Q3 deck is one `if` in the commit transaction: compare the commit's parent rev against the file's current rev.

- **Parent = current** → apply; the new version's parent is the old one. Sequential history.
- **Parent ≠ current** → someone committed in between. The edit is **concurrent**.

**Resolution for opaque files: punt, visibly.** The server rejects the stale commit. The client:

1. keeps its local edit, **renamed**: `q3-deck (Ana's conflicted copy 2026-10-08).key`,
2. uploads it as a **new file** (its chunks are probably already uploaded, so this is just a commit),
3. downloads the server's current version into the original path,
4. tells the user.

Both versions survive; a person who understands a Keynote deck picks one. **Auto-merging opaque bytes is never right**: a `.docx` is a zip of XML, a `.psd` is a layered binary, and a byte merge produces corruption.

<Figure caption="Rung one: detect by parent version, keep both, tell the human.">
  <Mermaid code={`flowchart LR
    C["commit\nparent v8"] --> Q{"current\n= v8?"}
    Q -->|"yes"| W["write v9\nappend journal"]
    Q -->|"no, v9 exists"| X["reject: stale"]
    X --> R["client renames local edit:\nconflicted copy"]
    R --> U["commit copy as new file"]
    R --> D["download v9 into\noriginal path"]`} />
</Figure>

**Smarter than punting, when the type allows.** Some types do have a merge: plain text with a three-way merge (base, mine, theirs, as git does), or a JSON settings file merged per key. A product can offer type-specific merges and fall back to conflicted copies. Default to punting and name the exceptions.

<Trace title="Detect the conflict" steps={conflicts} takeaway="Parent ≠ current means concurrent. With one ordering authority, a version counter detects every conflict; resolve opaque files by keeping both." />

**Worked numbers.** At 40 million commits a day, a conflict rate of 0.01% is **4,000 conflicted copies a day**, each a confused user. So real sync clients work to *avoid* conflicts: sync quickly after each save (shrinking the concurrency window from hours to seconds) and treat one user's own devices kindly (an edit on the phone after a sync is sequential, not concurrent).

<Reveal q="Two devices both rename the same folder to different names while offline. Is that the same kind of conflict?">

Same detection, harder resolution. A rename touches every path under the folder, and two renames can't both be kept as copies without duplicating the whole tree. Common answers: give folders stable ids so a rename changes one field on one row (pick one name deterministically and log it), or apply the first rename and make the second fail visibly. The honest interview line: "Directory operations (rename, move, delete of a non-empty folder) are where file sync gets hard, so I'd give folders stable ids."

</Reveal>

**A common slip:** "Conflicts are rare, so last-writer-wins is fine." Rare times 40 million commits a day is thousands of silently destroyed files. Rare is a reason to make conflicts cheap and visible, not to drop data.

<h2 id="deletes">Chapter 7 · Deletes and tombstones</h2>

A customer deletes a 30 GB folder on Monday. On Wednesday it reappears. She deletes it again Thursday. On Friday it is back.

The cause is a desktop that sleeps most of the week. Each time it wakes, it sees 30 GB on its disk that the server doesn't list, and helpfully uploads it. The server forgot it ever had the files, so the laptop's memory won.

**A delete must be recorded, not just performed.** If deleting a file removes its row, a device that still has the file can't tell "deleted on the server" from "new on my disk". The fix is a **tombstone**: the FileEntry stays, marked deleted at rev N, and the journal gets an entry "path deleted at position 41,300". The sleeping desktop syncs from its cursor, sees the delete and removes its local copy.

**Edit versus delete.** A deletes a file; B, offline, edits it. The safe rule is **edit beats delete**: restore the file with B's edit (or as a conflicted copy) and tell the user. A delete is cheap to repeat; an edit is not.

**How long do tombstones live?** Until every device that might still hold the file has synced past them. For a server-centred product you can bound that: devices that haven't synced in, say, 90 days must do a **full resync** (compare everything, server wins on deletes older than the horizon) instead of a cursor sync. Then tombstones older than 90 days can be compacted. The deleted file's *chunks* follow the retention policy separately (Chapter 4).

<Trace title="Make deletes stick" steps={deletes} takeaway="Deletes are journal entries with tombstones. Edit beats delete. Tombstones live until every device has synced past them; bound it with a resync horizon." />

<Reveal q="Why can't the client just keep a list of files it deleted and tell other devices directly?">

The devices that need to know are exactly the ones that are offline, and they may come back in any order. The server journal is the one place every device reads from, so the delete belongs there. A local "I deleted this" list also doesn't help a brand-new device or a reinstalled client.

</Reveal>

**A common slip:** "Deletes just remove the row." That works until the first device sleeps through one. Say *tombstone*, and say how long it lives.

<h2 id="extras">Chapter 8 · Faster than the cloud</h2>

A customer has forty designers in one office on one slow internet line. One saves a 500 MB render and the other thirty-nine laptops each download it from the cloud through the same line. Why is the file going to another continent and back thirty-nine times?

Extras worth one sentence each in an interview, said after the core works:

- **LAN sync.** Devices on the same local network discover each other (broadcast or multicast announcement) and fetch chunks from a peer that already has them. The server still decides *what* to sync (journal, hashes, permissions); peers only serve *bytes*, verified by hash, so a peer can't inject anything. For the office: one download over the internet line, 39 over the LAN. The line carries **500 MB instead of 19.5 GB**.
- **Delta sync inside a chunk.** If a 4 MB chunk changed by a few bytes, send a binary delta against the old chunk (the rsync algorithm: the receiver sends block checksums of its old copy, the sender finds matching blocks with a rolling checksum and transmits only the rest). Saves bandwidth on in-place edits of large chunks, costs CPU and complexity.
- **Compression** of chunks on the wire (and often at rest): cheap for text, useless for already-compressed media.
- **Streaming sync.** Start downloading chunks on other devices as soon as they are uploaded, before the commit, so a big file appears almost at once after the commit. Only the commit makes it *visible*.
- **Selective sync / on-demand files.** Devices hold placeholders and fetch content on open, essential once a team folder is bigger than a laptop disk.

**A common slip:** leading with LAN sync. These are wrap-up material. The interviewer first needs chunks, the commit protocol, the cursor and conflicts.

<h2 id="drive-numbers">Chapter 9 · The numbers</h2>

Assumptions for this example: ten million users, 4,000 files each, 1 MB a file, two million people a day touching twenty files. Work it out.

**Storage.**

```text
Logical data     10M users × 4,000 files × 1 MB        = 40 PB, 40 billion files
Dedup            assume 20% duplicate bytes per user    → 32 PB physical
Durability       erasure coding at ~1.5× overhead        → 48 PB raw disk  (3× replication: 96 PB)
File metadata    40B files × ~250 B per current version  = 10 TB  → shard by namespace_id
Chunk index      ~40B chunks × ~64 B (hash, size, place) ≈ 2.6 TB (most files are one chunk)
```

**Traffic.**

```text
Commits          2M daily users × 20 files       = 40M/day ≈ 460/s average, ~1,400/s peak (3×)
Upload           40M × ~1 MB changed (delta)     = 40 TB/day ≈ 460 MB/s ≈ 3.7 Gbit/s; ~11 Gbit/s peak
Download         each commit to ~2 other devices = 80 TB/day ≈ 930 MB/s average
Connections      ~5M devices online at peak ÷ 100K per server ≈ 50 notification servers
```

**What the numbers decide.**

- **Bytes and metadata must be split.** 32 PB belongs in object storage; 10 TB of small transactional rows belongs in a sharded relational store.
- **The metadata shard key is the namespace**, because every hot query ("changes after cursor N", "commit to this path") is per namespace. A huge team folder is the hot-shard risk; it can get its own shard.
- **Commit QPS is modest** (~1,400/s). The metadata tier is sized by data volume and query shape, not write rate.
- **Bandwidth is the real cost**: 11 Gbit/s up at peak, more down. Delta sync, dedup, LAN sync and a CDN for downloads all attack it. This is why Chapter 3 matters.

<Reveal q="Dedup across users would save more storage. Why did the assumptions say 'per user'?">

Cross-user dedup lets a client learn whether *anyone* has a file (upload skipped) and, done naively, lets a known hash stand in for the bytes. Per-user (or per-team) dedup keeps most of the practical win (copies, re-uploads, old versions) with no cross-user leak. You can still dedup across users server-side, after receiving bytes, where clients can't observe it; that saves storage but not upload bandwidth. <a href={`${BASE}sd/lessons/blob-cdn/#dedup`}>Blob storage</a> has the full argument.

</Reveal>

<h2 id="why-merge">Chapter 10 · Why positions break</h2>

A first prototype saves the whole document every two seconds, last write wins. Two people type in the same paragraph. One person's sentence appears, disappears, reappears, and disappears for good. That is LWW doing exactly what it says, every two seconds.

The next idea is to send edits instead of documents. Three designs and why each fails:

| Design | What happens with two typists | Verdict |
|---|---|---|
| **Save the whole document, LWW** | Each save erases the other person's keystrokes since their last refresh | Loses edits continuously |
| **Lock the paragraph while someone types** | The second person waits; a dropped connection leaves a paragraph locked | Not collaboration, and fragile |
| **Send position-based edits, apply as received** | "Insert at 5" was relative to a document that no longer exists once the other edit lands first | **Screens diverge** |

The third design is almost right. Edits as **operations** (`insert(pos, char)`, `delete(pos)`) are small, fast and say what the user meant. The problem is that **positions are relative to the document the editor saw**.

**The tiny example used for the rest of this part.** The document is `"cat"`. Alice types `s` at position 3, giving `"cats"`. At the same moment Bob types `b` at position 0, giving `"bcat"`. Each receives the other's op and applies it as-is:

- Alice: `"cats"` then `insert(b, 0)` gives `"bcats"`.
- Bob: `"bcat"` then `insert(s, 3)` gives `"bcast"`.

Two screens, two documents, forever. Something must make concurrent operations mean the same thing on both sides. There are two families: **rewrite the operation** (OT) or **stop using positions** (CRDTs). The simulation in Chapter 14 lets you run all three.

**A common slip:** "We'll use WebSockets so edits are instant." Instant delivery makes divergence happen faster. The transport is <a href={`${BASE}sd/lessons/pattern-realtime/`}>Realtime</a>'s problem; this chapter's problem is meaning.

<h2 id="ot">Chapter 11 · Operational transformation</h2>

**Operational transformation (OT)**: when op `a` must be applied after a concurrent op `b` (both made against the same document), compute `a' = T(a, b)`, the version of `a` that means the same thing in the document where `b` already happened.

For `"cat"`: Bob's `b` went in at 0, so everything after it moved one place right. Alice wanted her `s` after the `t`. Where is the `t` now? At 3, so her `s` goes at 4.

For single-character insert and delete, the rules are short:

| `a` \ `b` already applied | `b` = insert at q | `b` = delete at q |
|---|---|---|
| **`a` = insert at p** | q &lt; p, or q = p and b's site is lower → **p + 1**; else p | q &lt; p → **p − 1**; else p |
| **`a` = delete at p** | q ≤ p → **p + 1**; else p | q &lt; p → **p − 1**; q = p → **no-op** (already gone); else p |

**The worked example.** Doc `"cat"`, Alice `insert(s, 3)`, Bob `insert(b, 0)`. The server orders Bob first.

- `T(Alice, Bob)`: Bob inserted at 0 &lt; 3, so Alice's op becomes `insert(s, 4)`. Server: `"bcat"` then `"bcats"`.
- `T(Bob, Alice)`: Alice inserted at 3, after 0, so Bob's op is unchanged. Alice's screen: `"cats"` then `insert(b, 0)` gives `"bcats"`.

<Figure caption="The same two edits, applied in opposite orders, converge because each side transforms the other's op against its own.">
  <Mermaid code={`sequenceDiagram
    participant A as Alice
    participant S as Server (sequencer)
    participant B as Bob
    Note over A,B: doc "cat"
    A->>A: insert s at 3 → "cats"
    B->>B: insert b at 0 → "bcat"
    B->>S: insert b at 0 (rev 0)
    A->>S: insert s at 3 (rev 0)
    S->>S: order Bob then Alice. T(Alice, Bob) = insert s at 4
    S-->>A: insert b at 0 → "bcats"
    S-->>B: insert s at 4 → "bcats"
    Note over A,B: both "bcats"`} />
</Figure>

**The property that makes it work** (called TP1 in the literature): for any two concurrent ops,

> apply(apply(doc, a), T(b, a)) = apply(apply(doc, b), T(a, b))

**Why order matters.** `insert(s, 3)` is correct only against `"cat"`. Against `"bcat"` it is the wrong edit. An op is meaningful only relative to the document state it was made on, so if you reorder ops (as concurrency forces you to), you must transform them to the new state. The transform below is the rule for that.

```java id=op group=ot
/** One single-character edit: 'I' insert ch at pos, 'D' delete the char at pos, 'N' do nothing. */
record Op(char kind, int pos, char ch, int site) {
    static Op ins(int pos, char ch, int site) { return new Op('I', pos, ch, site); }
    static Op del(int pos, int site) { return new Op('D', pos, '\0', site); }
    static Op noop(int site) { return new Op('N', 0, '\0', site); }
    Op at(int newPos) { return new Op(kind, newPos, ch, site); }
}

static String apply(String doc, Op op) {
    return switch (op.kind()) {
        case 'I' -> doc.substring(0, op.pos()) + op.ch() + doc.substring(op.pos());
        case 'D' -> doc.substring(0, op.pos()) + doc.substring(op.pos() + 1);
        default -> doc;
    };
}

/**
 * Rewrite `a` so it means the same thing after `b` has been applied.
 * Precondition: a and b were both made against the same document, by different sites.
 */
static Op transform(Op a, Op b) {
    if (a.kind() == 'N' || b.kind() == 'N') return a;
    if (b.kind() == 'I') {
        // b's new character lands before a's position: shift right. On a tie, an insert
        // from the lower site goes first, and a delete always moves past the new character.
        boolean before = b.pos() < a.pos()
                || (b.pos() == a.pos() && (a.kind() == 'D' || b.site() < a.site()));
        return before ? a.at(a.pos() + 1) : a;
    }
    // b removed the character at b.pos.
    if (b.pos() < a.pos()) return a.at(a.pos() - 1);
    if (b.pos() == a.pos() && a.kind() == 'D') return Op.noop(a.site());   // both deleted it
    return a;
}
```

**How this is tested.** The checker for this page verifies TP1 for **every** pair of ops on every document up to five characters (in both argument orders), and on 5,000 random pairs on documents up to 26 characters. It also checks **intent**: with distinct letters, surviving original characters keep their order, a character deleted by both is deleted once, and each inserted character keeps the same left neighbour it was typed after.

<Trace title="Transform it" steps={ot} takeaway="Inserts before you push you right; deletes before you pull you left; deleting a deleted character is a no-op; ties need one rule both sides share." />

**Catch the bug.** The version people write first treats "same position" as "before" for every case:

```java fragment
// Looks right, and passes every test where the two positions differ.
static Op transformInsertInsert(Op a, Op b) {
    return b.pos() <= a.pos() ? a.at(a.pos() + 1) : a;   // tie: BOTH sides shift right
}
```

Doc `"cat"`, Alice inserts `!` at 3, Bob inserts `?` at 3. Each side shifts the other's op right: Alice sees `"cat!?"`, Bob sees `"cat?!"`, and they never reconcile. The checker reproduces exactly this divergence. **Concurrent inserts at one position need a deterministic tie-break both sides agree on** (here, the lower site id goes first; with it, both see `"cat!?"`).

<Reveal q="Real editors don't send one op per character. How does this extend to strings and formatting?">

Real OT systems use ops over ranges ("retain 10, insert 'hello', retain 40, delete 3") and add attributes for formatting (bold from 5 to 9). The transform rules grow, but the idea is the same: shift ranges past concurrent inserts, shrink them past concurrent deletes, and break ties deterministically. Range ops also batch keystrokes: a client typically sends whatever was typed since its last op was acknowledged, as one op. Rich-text OT (tables, lists, comments) is where the real engineering effort lives.

</Reveal>

<h2 id="sequencer">Chapter 12 · One sequencer per document</h2>

Two people are easy. With five people over bad wifi, ops arrive in different orders at every laptop. Each op must be transformed against the others, but in what order? Academic OT papers spent two decades disproving each other's algorithms for exactly this. Google-Docs-style OT avoids the problem by having someone decide the order.

**The sequencer.** Every op for a document goes through **one server** that owns the document's session. It stamps each op with the next **revision number**, and that order is the order. The design goes back to the Jupiter collaboration system (Xerox PARC, mid-1990s), and Google has publicly described Google Docs as using operational transformation with a central server.

**Why one ordering point makes OT tractable.** With a canonical order, each op only needs transforming against the ops ordered before it that its author hadn't seen: a sequence of the simple two-op transforms from Chapter 11. Without one, every client must converge regardless of the order ops reach it, which requires a stronger property (TP2) that many published transform functions turned out not to satisfy.

```java id=session group=ot
/** The single ordering point for one document: every op gets a revision number here. */
static final class DocSession {
    private String doc;
    private final List<Op> log = new ArrayList<>();   // log.get(r) took revision r to r + 1

    DocSession(String initial) { doc = initial; }

    /** A client made `op` while it had seen revisions [0, baseRev). Returns the op as recorded. */
    synchronized Op receive(Op op, int baseRev) {
        if (baseRev < 0 || baseRev > log.size()) throw new IllegalArgumentException("unknown revision " + baseRev);
        for (int r = baseRev; r < log.size(); r++) op = transform(op, log.get(r));   // catch up on what it missed
        doc = apply(doc, op);
        log.add(op);
        return op;   // broadcast to every client in the room; the author treats it as its ack
    }

    synchronized String text() { return doc; }
    synchronized int revision() { return log.size(); }
}
```

**The client half** (the checker implements it and drives it): a client applies its own edits locally at once, so typing never waits for the network, and keeps **at most one op in flight**, buffering the rest.

- **Local edit:** apply it; if nothing is in flight, send it with the client's current revision; otherwise append it to the buffer.
- **Ack for its own op:** revision + 1; send the first buffered op (already transformed against everything received meanwhile).
- **Someone else's op:** transform it against the in-flight op and each buffered op (and them against it, in turn), apply the result, revision + 1.

The checker runs 1,500 random sessions of two to four clients, with edits, sends and deliveries interleaved randomly, and asserts that every client ends with the server's text and revision.

**It is not a scaling problem**, and saying why is the senior insight. The coordination is **per document**, and one document's load is tiny:

- A hot document with 50 people typing about 5 characters a second is **250 ops per second**. An in-memory sequencer does that without noticing.
- Assumption: 1 million open documents, about 3 million editors, around 1 op per second each on average (bursts of typing, long pauses) gives **3 million ops per second fleet-wide**, spread over documents. At 10,000 documents per session server, that is **about 100 servers**.
- Route by document id (a registry or consistent hashing; the same move as one matching engine per stock symbol in <a href={`${BASE}sd/lessons/pattern-contention/`}>Contention</a>).

**Failure.** Ack an op only after it is durably appended to the op log. The log is keyed by `(doc_id, rev)` with a uniqueness constraint, so if an old owner that lost its lease (a "zombie") tries to append rev 1,042 after the new owner already did, the write fails. **The revision number is the fencing token.** Clients resend un-acked ops with their base revision to the new owner, which loads snapshot + log and transforms as usual. Edits during failover are delayed, never lost.

<Trace title="Who orders the edits?" steps={sequencer} takeaway="One sequencer per document gives one order, so simple transforms converge. Load is per document, so the fleet shards by doc id." />

<Reveal q="If the server orders everything anyway, why not lock the document and apply edits one at a time? Why transform at all?">

Because the clients don't wait. Each client applies its own keystrokes instantly, so its op was made against a document that is already stale when it arrives. The server must turn "insert at 3 in revision 40" into the right position at revision 43. Transform lets the UI be instant *and* the order be single. Without it, typing would round-trip to the server before appearing: 100 to 200 ms of lag per keystroke.

</Reveal>

**A common slip:** "OT needs a central server, so it doesn't scale." Central *per document*. Say the per-doc op rate and the sharding key in the same breath.

<h2 id="crdt">Chapter 13 · CRDTs</h2>

Now remove the server. A notes app must work underground for an hour, and sometimes the phone syncs to the laptop over Bluetooth with no server in the loop. There is no sequencer and no canonical order. Every device merges whatever arrives, whenever it arrives.

A **CRDT** (conflict-free replicated data type) is a data structure whose merge is designed so that **any replicas that have seen the same set of updates hold the same state, whatever order they saw them in**. No server, no transform, no coordination.

**The simplest one: a grow-only counter (G-counter).** Each replica keeps its own count; the value is the sum; merge takes the element-wise max. Phone `{phone: 3, laptop: 1}` and laptop `{phone: 2, laptop: 4}` merge to `{phone: 3, laptop: 4}` = 7, in either order, as often as you like. That is a **state-based** CRDT: ship the whole state; merge is commutative, associative and idempotent.

**Text: a sequence CRDT.** Positions move, names don't. Give **every character a permanent, unique id** and express edits by id:

- Insert: "put `s` (id 4@alice) after the character with id 3@alice".
- Delete: "character 2@alice is deleted". It becomes a **tombstone** that stays in the structure, because another replica might still say "insert after 2@alice".

Since ids never shift, there is nothing to transform. The only question is ordering **concurrent inserts after the same character**. The RGA (Replicated Growable Array) answer: ids are Lamport timestamps plus the site, and the larger id goes first. Yjs and Automerge use related id-based designs with heavy optimisation.

```java id=rga group=rga
/** A replicated text where every character has a permanent, unique name (an RGA). */
static final class Rga {
    /** Lamport clock + site: unique, and totally ordered. */
    record Id(long clock, int site) implements Comparable<Id> {
        public int compareTo(Id o) {
            return clock != o.clock ? Long.compare(clock, o.clock) : Integer.compare(site, o.site);
        }
    }
    record Insert(Id id, Id after, char ch) {}    // after == null means "at the very start"
    record Delete(Id target) {}

    static final class Node {
        final Id id; final char ch; boolean deleted;
        Node(Id id, char ch) { this.id = id; this.ch = ch; }
    }

    private final int site;
    private long clock;
    private final List<Node> nodes = new ArrayList<>();   // document order, tombstones included

    Rga(int site) { this.site = site; }

    /** Local edit: put ch at visible position `index`. Returns the op to broadcast. */
    Insert insert(int index, char ch) {
        Id after = index == 0 ? null : visible(index - 1).id;
        Insert op = new Insert(new Id(clock + 1, site), after, ch);
        apply(op);
        return op;
    }

    /** Local edit: delete the character at visible position `index`. */
    Delete delete(int index) {
        Delete op = new Delete(visible(index).id);
        apply(op);
        return op;
    }

    void apply(Insert op) {
        if (find(op.id()) >= 0) return;                        // already have it: duplicates are harmless
        clock = Math.max(clock, op.id().clock());
        int i = op.after() == null ? 0 : find(op.after()) + 1;
        // Skip anything with a bigger id: concurrent inserts at the same spot that sort first,
        // and the characters later typed after them.
        while (i < nodes.size() && nodes.get(i).id.compareTo(op.id()) > 0) i++;
        nodes.add(i, new Node(op.id(), op.ch()));
    }

    void apply(Delete op) {
        nodes.get(find(op.target())).deleted = true;            // a tombstone: the name must stay findable
    }

    boolean has(Id id) { return find(id) >= 0; }

    String text() {
        StringBuilder sb = new StringBuilder();
        for (Node n : nodes) if (!n.deleted) sb.append(n.ch);
        return sb.toString();
    }

    int tombstones() {
        int count = 0;
        for (Node n : nodes) if (n.deleted) count++;
        return count;
    }

    private int find(Id id) {
        for (int i = 0; i < nodes.size(); i++) if (nodes.get(i).id.equals(id)) return i;
        return -1;
    }

    private Node visible(int index) {
        for (Node n : nodes) if (!n.deleted && index-- == 0) return n;
        throw new IndexOutOfBoundsException();
    }
}
```

**Why the skip rule works.** A character typed after X always has a larger Lamport clock than X. So when a new character arrives "after R", everything with a bigger id sitting right after R is either a concurrent insert at R that should come first, or something typed after one of those. Skip them all. Stop at the first smaller id: that is an older neighbour, and the new character belongs before it.

**The worked example, CRDT-style.** `"cat"` built on Alice's replica as ids 1@A, 2@A, 3@A. Alice types `s` after 3@A (id 4@A); Bob types `b` at the start (id 4@B). Both replicas end with **`"bcats"`**. Then both type at the end at once: Alice `!` (5@A), Bob `?` (5@B). Clocks tie, B's site is larger, so `?` goes first and both show **`"bcats?!"`**. (OT's tie-break put the lower site first; any deterministic rule works as long as everyone uses the same one.)

**Op-based vs state-based.** RGA above is **op-based**: replicas exchange operations, which is compact, but requires every op to be delivered (at least once; duplicates are ignored here) and to arrive after the character it refers to. **State-based** CRDTs ship whole state (or deltas) and merge; they tolerate any delivery but send more. The checker delivers ops to two to four replicas in random orders, with 10% duplicates, holding back only ops whose referenced character hasn't arrived yet. In 1,500 runs every replica converges.

<Trace title="Name every character" steps={crdt} takeaway="Ids instead of positions: nothing to transform, merge in any order. The price: an id per character and tombstones that can't easily be collected." />

**Worked numbers: the metadata bill.** A naive per-character id (8-byte clock plus 8-byte site) is 16 bytes on top of a 1-byte character: about **17× the text**. A document where 100,000 characters were typed is about **1.7 MB** of structure, and if 60,000 were later deleted it still holds **100,000 elements** for 40,000 visible characters. The checker confirms the shape at small scale (100 inserts, 60 deletes, 40 visible, 60 tombstones). Production CRDTs compress hard (Yjs, for example, stores runs of consecutive characters typed by one client as a single item), so real overhead is far smaller. The interview point: **CRDT metadata grows with history, not with the visible document, and tombstones can only be collected once every replica has seen the delete.**

<Reveal q="Can you garbage-collect tombstones in a CRDT?">

Only once you know no replica will ever refer to them again: every replica has seen the delete and has no pending op that says "insert after" that character. A server-backed system can establish that (all clients acked past revision N). A truly peer-to-peer, offline-first system often can't, since a phone in a drawer for a month might return with an op pointing at a tombstone. So practical systems either keep tombstones (compressed) or use a server-coordinated compaction point and force long-offline replicas to resync.

</Reveal>

**A common slip:** "CRDTs merge automatically, so there are no conflicts." There are no *divergences*. Two people concurrently changing the same word still produce a merged result someone may dislike ("teh catt"). CRDTs guarantee convergence, not good intent.

<h2 id="ot-vs-crdt">Chapter 14 · OT or CRDT</h2>

Two design docs land the same day. One proposes OT with session servers for the online editor. The other proposes a CRDT synced over anything (server, Bluetooth, a USB stick) for the notes app. Why build two different things? Because the constraints differ.

Run the same three pairs of edits through each strategy below. Pick "Naive" first and watch the screens diverge; then try OT and CRDT, and the third scenario (both delete the same letter), where naive converges on the wrong text.

<CollabEditSim />

| | OT (with a sequencer) | Sequence CRDT |
|---|---|---|
| **Coordination** | A central server per document orders ops | None needed; any replica merges any other |
| **Offline** | Short offline works (buffer, then transform on reconnect); long offline means a big transform at the server | Natural: merge whenever, in any order |
| **Peer-to-peer** | No | Yes |
| **Metadata** | Ops carry positions; the document is plain text | An id per character (compressed in practice) plus tombstones |
| **Complexity lives in** | Transform functions, especially rich text | Data structure, id design, GC of tombstones |
| **History / audit** | The op log at the server is the history | Needs its own persistence; the merge doesn't give you a log of record |
| **Permissions** | Checked at the sequencer on every op | Enforced where ops are accepted, usually a server anyway |
| **Known in the wild** | Google Docs (publicly described as OT) | Yjs, Automerge; Figma has described a server-authoritative design inspired by CRDTs |

**The interview verdict.** "Google-Docs-style, always-online, and we need a server anyway for permissions, history and persistence, so OT with a per-document sequencer is the proven choice, and the server's log doubles as version history. If the product is offline-first or peer-to-peer, I'd use a CRDT and accept the metadata cost." Naming both and choosing beats reciting the internals of either.

<Trace title="Choose the merge" steps={choose} takeaway="A server you need anyway → OT through it. No reliable server, long offline, peer-to-peer → CRDT. Either way, say the cost you accept." />

<Reveal q="Can you use a CRDT with a central server?">

Yes, and many products do. The server acts as an always-online peer: it relays ops, persists the document, enforces permissions and can coordinate tombstone compaction. You keep the order-independent merge (great for flaky connections and offline edits) and get the operational benefits of a server. The difference from OT is that the server is a convenience, not a correctness requirement.

</Reveal>

<h2 id="presence">Chapter 15 · Presence</h2>

Fifty people open the same planning doc and start scrolling, selecting and typing. The session server hits 100% CPU. It is not the edits. It is the cursors: every mouse twitch is being forwarded to forty-nine people.

**Presence** (who is here, where their cursor is, what they've selected) is the feature users notice first and the one with the worst fan-out.

**Worked numbers for one document**, 50 editors:

| Policy | Messages the server sends per second |
|---|---|
| Every cursor update (10/s each) forwarded to 49 others | 50 × 10 × 49 = **24,500** |
| Throttle each client to 2 updates/s | 50 × 2 × 49 = **4,900** |
| Batch: one frame per recipient every 100 ms with all changed cursors | 50 × 10 = **500 frames** |

**Design rules for presence:**

- **Ephemeral, newest-wins.** Cursor positions are the textbook honest use of LWW. Keep them **in memory** on the session server, send them over the same socket as ops, and **never persist** them. If the server restarts, clients re-announce.
- **Throttle at the client, batch at the server.** Coalesce updates so only the latest position per user goes out in each frame.
- **Cursors must be transformed too.** A cursor at position 10 must move to 11 when someone inserts before it. Send cursors tagged with the revision they refer to and transform them like a zero-width insert. (In a CRDT, anchor the cursor to a character id instead; it moves for free.)
- **Cap the room.** Beyond some number of simultaneous editors, show viewers without live cursors or degrade to periodic updates. Google's help pages say up to 100 people can work on a Docs, Sheets or Slides file at once; beyond that, only the owner and some editors can edit.
- Transport, heartbeats and presence timeouts belong to <a href={`${BASE}sd/lessons/pattern-realtime/`}>Realtime</a>.

<Trace title="Count the cursors" steps={presence} takeaway="Presence is ephemeral and newest-wins: in memory, throttled, batched, never logged. N editors means N × (N − 1) unless you batch." />

**A common slip:** putting presence in the op log or database "for consistency". It is ten times chattier than edits and worthless a second later.

<h2 id="history">Chapter 16 · Snapshots, the log and undo</h2>

A two-year-old design doc takes nine seconds to open. The server replays every op since the document was created: 400,000 of them. Then product asks for something harder: Undo should undo *my* typing, not Bob's.

**Snapshots + op log.** The op log is the source of truth and the version history; a **snapshot** is a cached materialisation of the document at some revision.

- **Write path:** append op to the log (that is the ack); every N ops (say 1,000) or every few minutes, write a snapshot `(doc_id, rev, content)`.
- **Load path:** read the latest snapshot, then the ops after it. Never more than about 1,000 ops to replay.
- **History:** "show me this doc last Tuesday" is the nearest snapshot before Tuesday plus ops up to that moment. Named versions are bookmarked revisions.
- **Compaction:** old ops can be squashed into coarser history (keep hourly snapshots after 30 days, say) and archived to cheaper storage.

**Worked numbers.** Assumption: about 50 bytes per stored op. A doc with 100,000 ops has a **5 MB** log; replaying it all on open is slow and gets slower forever. With a snapshot every 1,000 ops, open is one snapshot (about the document's size, tens of KB for a typical doc) plus at most 1,000 ops (about **50 KB**). Fleet-wide, 3 million ops/s × 50 B = 150 MB/s ≈ **13 TB of op log a day**, which is why compaction and tiering are part of the design.

**Undo in a shared document** (the hard, hedged part). Single-user undo pops the last op. In a shared doc that would undo whoever typed last. Users expect **selective undo: reverse my own last action**. The usual approach is to compute the **inverse** of my op (delete what I inserted, re-insert what I deleted), **transform it past every op applied since**, and send it as a new op. Edge cases (undoing an insert someone else has since edited inside, redo after others' edits, formatting ops) are subtle, and editors handle them with per-user undo stacks and careful rules (Yjs, for example, ships an undo manager that tracks changes by origin). In an interview: name selective undo, the inverse-and-transform idea, and that it is hard.

<Trace title="Load fast, undo kindly" steps={history} takeaway="Snapshot every N ops; load = snapshot + tail. Undo = inverse of my op, transformed forward, sent as a new op." />

<Reveal q="Should the editor store the document as a row it updates on every op, instead of a log?">

No. That turns every keystroke into a full-document write and throws away history. The log is append-only (cheap, sequential, naturally ordered by revision) and is both the durability mechanism and the history. The current document lives in the session server's memory while the doc is open, and in snapshots when it isn't.

</Reveal>

<h2 id="local-first">Chapter 17 · Offline-first</h2>

A user rides the subway for forty minutes with a notes app, makes a dozen edits, two of them to a note her partner also edited at home. When she surfaces everything merges and she can't find the seams. That is what "works offline" should mean.

**Offline-first** means the app reads and writes a **local store** first and treats the network as a sync channel, not a requirement. **Local-first** (a term from Ink & Switch's 2019 essay) goes further: the user's device holds the primary copy, the app works without the vendor's servers, and collaboration is layered on, with CRDTs as the usual engine.

The recipe, for any app:

1. **Local store first.** All reads hit local data; writes commit locally and land in an **outbox** of pending ops.
2. **Sync when you can.** Push the outbox (idempotently: ops carry ids), pull remote changes by cursor.
3. **Resolve per data type**, using the ladder. This is the part to say in an interview:

| Data | Rung | How |
|---|---|---|
| A file attachment | 1 · punt | Parent version mismatch → conflicted copy |
| A note's body text | 4 · CRDT (or 3 · OT via server) | Sequence merge |
| A note's title, a calendar event's time | 2 · LWW **per field** | Newest per field; concurrent edits to *different* fields both survive |
| Tags on a note, RSVP list, cart items | 4 · set CRDT | Add-wins set: union, deletes only remove what they saw |
| A "times opened" counter | 4 · counter CRDT | Per-device counts, summed |
| Cursor, "online now" | 2 · LWW | Ephemeral |

**Per-field LWW is the quiet hero.** Storing an event as one blob and LWW-ing it loses Alice's title change when Bob moves the time. Storing it as fields and LWW-ing each field keeps both. That is the honest answer for calendar events and **Figma-style canvases** (each object's properties: newest x-position wins, which is what users want).

<Reveal q="An offline-first app syncs through your server. A user was offline for two weeks and comes back with 3,000 queued ops. What do you worry about?">

Three things. **Volume**: page the outbox upload and the downstream catch-up; don't make one giant request. **Validity**: permissions may have changed (they were removed from the shared note), so the server must re-check each op and reject gracefully with a clear message. **Merge cost**: with OT, the server must transform 3,000 ops against two weeks of others' ops, which is expensive, so cap offline duration or convert to a three-way merge of states. With a CRDT, merge is cheap but tombstones from two weeks ago had better still exist. "Long offline is a different code path" is the senior line.

</Reveal>

**A common slip:** one conflict policy for the whole app. Real apps mix rungs per field; the design should say which field gets which.

Without it, the central sequencer reads as a single point of everything, and you spend your deep-dive time defending it.

</Reveal>

<h2 id="interview-script">Say it in the room</h2>

The interviewer asks, "Two users edit the same thing at the same time. What happens?" It is an innocent question and it is the whole module. Ask one thing first: *what kind of thing?*

<AnswerModes id="two-users-same-thing" q="Two users edit the same thing at the same time. What happens?">
  <Fragment slot="short">

It depends on the data. Opaque files: detect with a parent version and keep both as a conflicted copy. Cursors and toggles: last-writer-wins, said out loud. Live text: merge with OT through one sequencer per document, or a CRDT if it must work offline or peer to peer.

  </Fragment>
  <Fragment slot="medium">

"It depends on the data, so I'd pick per type. For opaque files, I detect and punt: every commit names its parent version, and if the server has moved on, the client keeps its edit as a conflicted copy. I won't auto-merge bytes. For values where the newest genuinely supersedes (a cursor, presence, a toggle) I'd use last-writer-wins and say that losing the older write is intended. For live text, edits must merge: as operations transformed through a single sequencer per document. That's OT, Google Docs style. Concurrent inserts shift each other's positions and everyone converges. The sequencer is per document, so a few hundred ops a second at most, sharded by doc id, and its op log doubles as version history. If it has to work offline for days or peer to peer, I'd use a CRDT: every character gets a permanent id, so merges commute, at the cost of id metadata and tombstones. Underneath any of these, sync moves only what changed: content-defined chunks addressed by hash, a journal with cursors, and data-free notifications."

  </Fragment>
  <Fragment slot="deep">

Add the failure cases and numbers. Detection: parent version when one server orders commits, version vectors when it does not. LWW loses data even with perfect clocks, so it is only for data where the newest value supersedes. OT: `T(a, b)` rewrites a position past a concurrent op; TP1 means both orders converge; same-position inserts need a tie-break; a single sequencer avoids needing TP2. CRDT: ids not positions, tombstones, metadata grows with history. Failure: ack only after the durable append keyed by (doc, rev), which fences zombie owners. Scale: 250 ops/s on a hot doc, about 100 session servers for 1M open docs, 24,500 cursor messages per second collapsed to 500 frames by throttling and batching.

  </Fragment>
</AnswerModes>

**Five follow-ups you will get:**

<Reveal q="1 · Why content-defined chunking rather than fixed blocks?">

An insertion shifts all later bytes. Fixed boundaries stay put, so every later block changes: one byte at the front of a 200 MB file re-uploads all of it. Content-defined boundaries are chosen by a rolling hash of nearby bytes, so they move with the content and re-synchronise right after the edit. One or two chunks change.

</Reveal>

<Reveal q="2 · How does a device that was offline for a week catch up?">

It sends its cursor, the last journal position it applied in each namespace, and pages through every entry after it: edits, renames and tombstones. It downloads only the chunks it lacks. Its own offline edits commit with their base revisions; any that conflict become conflicted copies. If it has been offline past the tombstone horizon, it does a full resync instead.

</Reveal>

<Reveal q="3 · Walk me through OT on a tiny example.">

"cat". Alice inserts s at 3, Bob inserts b at 0, concurrently. The server orders Bob first. Bob's insert is before position 3, so Alice's op becomes insert s at 4, giving "bcats". Alice receives Bob's op; her insert was after 0, so it is unchanged, giving "bcats". Same-position inserts need a tie-break such as lower site first; deleting an already-deleted character becomes a no-op.

</Reveal>

<Reveal q="4 · OT or CRDT: which would you pick?">

Always-online editor that needs a server anyway for permissions, persistence and history: OT through a per-document sequencer, proven and simple to reason about with one order. Offline-first or peer to peer: a CRDT, because any replica can merge in any order; accept the per-character id metadata (compressed in practice) and plan for tombstones. A hybrid (CRDT with a server as relay and archive) is common too.

</Reveal>

<Reveal q="5 · The session server for a busy document crashes. What happens?">

Edits pause for the failover window and nothing acknowledged is lost, because an op is acked only after it is durably appended to the log. The lease expires, a new owner loads the latest snapshot plus the log tail, and clients reconnect and resend un-acked ops with their base revision and client op id. The unique (doc, revision) key in the log stops a zombie owner from appending.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Say… |
|---|---|
| "Sync across devices", "works offline" | Every device is a leader; commits name their parent version |
| No central server to order writes | Version vectors: if neither dominates, concurrent |
| Opaque files edited concurrently | Rung 1: reject the stale commit, conflicted copy, tell the user, no auto-merge |
| Cursor, presence, a toggle | Rung 2: LWW, and say why losing the older value is correct |
| Event fields, canvas object properties | LWW **per field**, not per object |
| Big files, small edits | Content-defined chunks (rolling hash), SHA-256 names, upload only missing |
| "Which chunks to upload?" | Ask the server which hashes are missing, scoped per user/team |
| Saving a version | Chunks first, then one conditional, idempotent commit |
| "How do devices learn of changes?" | Journal per namespace, cursor fetch, data-free long-poll |
| Deleted file came back | Tombstones in the journal; edit beats delete; resync horizon |
| Office full of devices, one slow line | LAN sync: peers serve hash-verified chunks |
| Live co-editing of text | Rung 3: OT through one sequencer per document |
| "Doesn't a central server bottleneck?" | Per document: ~250 ops/s on a hot doc; shard by doc id |
| Offline-first, peer to peer | Rung 4: CRDT, unique ids, commutative merge; pay metadata + tombstones |
| Counters, sets across replicas | G-counter (per-replica counts), add-wins set |
| Many cursors | In memory, throttle, batch per recipient, transform with ops |
| Slow document open, history | Snapshot every N ops; load = snapshot + tail; log is history |
| "Undo" in a shared doc | Selective undo: inverse of my op, transformed forward; hard, say so |

## Common mistakes

1. **Last-writer-wins on data where both writes mattered.** Name the rung per data type and justify any LWW.
2. **Fixed-size chunks with no answer for insertions.** Say content-defined chunking and why it re-synchronises.
3. **Committing metadata before the bytes exist.** Chunks first, commit last, parent version in the commit.
4. **Deletes that just remove a row.** Tombstones, edit-beats-delete, a tombstone horizon.
5. **"OT needs a central server, so it won't scale."** Per document, not global: give the per-doc op rate and the shard key.

<h2 id="beyond">Beyond this page</h2>

**Further study**

- *Designing Data-Intensive Applications* (Martin Kleppmann), chapter 5, "Replication": multi-leader replication, handling write conflicts, detecting concurrent writes with version vectors, and a first look at CRDTs and OT. The theory under Part One.
- [Local-first software](https://www.inkandswitch.com/local-first/) (Ink & Switch, 2019): the essay that named local-first and argues for CRDTs as its engine. Chapter 17's source.
- [How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/) (Figma blog): a server-authoritative design inspired by CRDTs, with per-property last-writer-wins. A useful contrast with both OT and pure CRDTs.
- [Operational transformation (Wikipedia)](https://en.wikipedia.org/wiki/Operational_transformation): the history from Ellis and Gibbs (1989) through Jupiter, the transformation properties (TP1, TP2), and why so many algorithms were found incorrect.
- [Conflict-free replicated data type (Wikipedia)](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type): state-based versus op-based, G-counters, sets, sequences, with pointers to Shapiro et al.'s 2011 papers.
- [Yjs documentation](https://docs.yjs.dev/) and [Automerge](https://automerge.org/): two production CRDT libraries; read how they represent text and handle undo.
- [The rsync algorithm](https://rsync.samba.org/tech_report/) (Tridgell and Mackerras): rolling checksums and delta transfer, the ancestor of Chapter 3 and Chapter 8's delta sync.
- [FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia) (USENIX ATC 2016): the gear-hash chunker family used in Chapter 3, and how to tune it.

**Look these up yourself**

- **The Jupiter collaboration system** (Nichols et al., 1995): the client/server OT protocol that Google-Docs-style editors descend from; compare it with Chapter 12's one-op-in-flight client.
- **"What's different about the new Google Docs"** (Google Drive blog, 2010): Google's own short description of moving Docs to operational transformation.
- **Dropbox engineering posts on sync** (for example, their writing on rebuilding the sync engine): how a real client models local, remote and synced trees. Search the Dropbox tech blog rather than trusting a summary.
- **Three-way merge**: how git merges text with a common ancestor, and why it needs the base version just like a conflicted-copy check.
- **Hybrid logical clocks**: timestamps that respect causality and stay close to wall time; a better clock for LWW, though still LWW.
- **Dotted version vectors**: a refinement of version vectors used to avoid false conflicts in Dynamo-style stores.
- **Interleaving anomalies in text CRDTs**: why some sequence CRDTs interleave two people's concurrently typed words character by character, and how newer designs avoid it.
- **Peritext**: a CRDT for rich-text formatting, and why bold and italics are harder than plain characters.
- **Merkle trees for sync**: comparing large trees of hashes to find differences quickly; used in anti-entropy and some file sync designs.
