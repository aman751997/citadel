<h2 id="prologue">Prologue · Why an average can lie</h2>

Here is a failure that happens in real monitoring systems. Support has forty tickets about slow checkouts, but the latency dashboard is flat and green: p99 at 310 ms, as it has been all week.

The panel's query is "average of p99, across hosts". Thirty-nine hosts are healthy. One host has a bad disk and every request on it takes four seconds. The average of forty p99 values barely moved, so the dashboard looked fine while users suffered. (Chapter 10 does the arithmetic.)

Later that night the metrics cluster itself falls over. A team had added a `user_id` label to a request metric that afternoon. (Chapter 5.)

Both failures come from one fact: **nobody reads individual samples**. People read summaries over time windows, so the design questions are: which summaries do we read, how are they built, and when are they wrong?

**The pattern in one sentence.** Millions of tiny timestamped events arrive; people read **summaries over windows** (p99 for the last 5 minutes, top 10 today, views this hour). The design job is to absorb the firehose cheaply and precompute the summaries readers actually ask for.

**Trigger words:** "metrics", "monitoring", "analytics", "dashboard", "leaderboard", "trending", "view counts", "alert on thresholds", "clicks per campaign", "top K", "unique visitors", "telemetry".

Like caching's four promises, this pattern has **four dials you set out loud in every design**:

1. **What is one series, and how many are there?** The unit you store, and its cardinality.
2. **What summary, at what resolution, over what window?** The question the reader asks.
3. **Where is it computed: write time or read time?** Pre-aggregation versus query-time aggregation.
4. **How late, how wrong, how long?** Lateness you wait for, approximation error you accept, retention you keep.

Interviews ask this pattern directly (metrics/Datadog, ad-click aggregator, top-K, leaderboard) and hide it inside others (YouTube view counts, trending hashtags, Strava heatmaps, tracing). It is the third appearance of **"move work to write time"**, the same trade as feed fan-out and typeahead's precomputed top-K.

<h2 id="shape">Chapter 1 · Write a firehose, read a summary</h2>

A **time series** is a sequence of `(timestamp, value)` points identified by a **metric name plus a set of tags** (also called labels or dimensions): `http_requests{service="checkout", region="eu", status="5xx"}`. Each distinct combination of name and tags is one series.

Four properties shape every design decision:

- **Append-only.** Points arrive in roughly time order and are never updated. No in-place writes, no row locks, no read-modify-write.
- **Recent is hot.** Most queries look at the last hour or day; alerts look at the last few minutes. Old data is read rarely and coarsely.
- **Queried by range and tags.** "These series (selected by tags), over this time range, aggregated like this." Almost never "point number 81,233,007".
- **Write-heavy by a lot.** Our running example, a metrics system for 10,000 hosts, writes about 1,000,000 samples/s and reads about 1,200 queries/s, though each query touches many points.

**Worked numbers: where the reads come from.** Assumption: 500 dashboards open during the day, 20 panels each, refreshing every 30 s: 500 × 20 ÷ 30 ≈ **333 queries/s**. Plus 50,000 alert rules evaluated every 60 s: 50,000 ÷ 60 ≈ **833 queries/s**. Total about **1,200 queries/s**, against 10,000 hosts × 1,000 series ÷ 10 s = **1,000,000 samples/s** (the same numbers as <a href={`${BASE}sd/lessons/estimation/#metrics`}>Estimation · a million samples a second</a>). Note that **alerting, not humans, is the biggest reader**.

| Property | What it rules out | What it invites |
|---|---|---|
| Append-only | B-tree in-place updates, row locks | Log-structured, sequential writes, immutable blocks |
| Recent is hot | Treating all data the same | Memory for the newest hours, cheap storage for old data |
| Range + tags | Point lookups by id | Grouping by series, sorting by time, a tag index |
| Write-heavy | Expensive work per write | Batching, compression, cheap appends |

<Trace title="Read the shape" steps={shape} takeaway="Append-only, recent-hot, read by range and tags. Questions about individual users belong in an event store, not a metrics store." />

**Common slip:** "Store each event as a row in Postgres." It works on day one. At a million inserts a second, with indexes, it is the wrong tool, and it invites per-user questions that a metrics design should send elsewhere.

<h2 id="ingest">Chapter 2 · A million samples a second</h2>

Imagine the first prototype: every host sends each sample as its own HTTP request. It works for twelve hosts. At two hundred, the collectors spend all their CPU on TLS handshakes and request parsing. The system is not drowning in data; it is drowning in envelopes.

The standard ingest path has four stages, each absorbing a different problem:

<Figure caption="The firehose. Agents batch, collectors validate and route, a durable log buffers, writers own series and build blocks.">
  <Mermaid code={`flowchart LR
    subgraph H["10,000 hosts"]
      AG["agent\nlocal pre-aggregation\n10 s batches"]
    end
    AG -->|"~1,000 batches/s\n~100 MB/s"| LB["load balancer"]
    LB --> C["collectors\nauth, validate,\ndrop bad labels"]
    C -->|"key = series id"| K[("Kafka\nreplicated log")]
    K --> W["writers\nown series, head block\nin memory + WAL"]
    W --> B[("blocks\nlocal disk / object store")]`} />
</Figure>

- **Agents** run on every host. They gather samples, **pre-aggregate locally** (a StatsD-style agent turns 5,000 counter increments a second into one number per flush), and send **one compressed batch per interval**. 10,000 hosts flushing every 10 s is **1,000 requests/s**, not 1,000,000.
- **Collectors** are stateless: authenticate, validate, enforce label rules and per-team quotas (Chapter 5), and route. Scale them behind a load balancer.
- **Kafka** decouples ingest from storage. Writers can restart, deploy or fall behind without losing data; the log is the buffer and the replay source. It is keyed by **series id** (a hash of metric name plus sorted tags), so every sample of a series lands on one partition, in order.
- **Writers** (ingesters) consume partitions, append each sample to its series' open chunk in memory, write a write-ahead log (WAL), and periodically cut immutable blocks (Chapter 4).

**Push or pull?** Agents can **push** (Datadog-style agents, OpenTelemetry exporters), or the system can **pull** by scraping each target's `/metrics` endpoint on a schedule (Prometheus). Pull makes "target is down" obvious (the scrape fails) and keeps the server in control of load. Push suits short-lived jobs, hosts behind NAT, and SaaS where the vendor can't reach your network. Either is fine. Say which and why.

**Worked numbers: sizing the log.** Assumption: about 100 B per sample on the wire, so 1,000,000 samples/s is **100 MB/s**. Using the assumption from <a href={`${BASE}sd/lessons/queues-streams/#sizing`}>Queues & streams · sizing</a> (about 10 MB/s per partition), that needs at least **10 partitions**. Give it 64 so writers can scale out about sevenfold (64 ÷ 9) without remapping series.

Retention of 24 hours: 100 MB/s × 86,400 s = 8.64 TB a day. Batches compress; assume about 5× for repetitive label text (measure it), so about 1.7 TB, × 3 replicas ≈ **5.2 TB** of Kafka disk. Writers: at an assumed 200,000 samples/s per node run at 60%, 1,000,000 ÷ 120,000 ≈ 8.3, so **9 writers**, as in the estimation lesson.

| Choice | Option A | Option B | Say |
|---|---|---|---|
| Collection | Push (agents) | Pull (scrape) | Pull for a fleet you control; push for SaaS and short jobs |
| Buffer | Write straight to the TSDB | Durable log first | Log first at scale: replay, smoothing, independent deploys |
| Kafka key | Random | Series id | Series id: in-order, one owner per series |
| Back-pressure | Drop at the agent | Buffer on the agent's disk | Buffer a few minutes, then drop and count drops. Monitoring must never take down the host it monitors |

<Trace title="Shape the firehose" steps={ingest} takeaway="Batch at the edge, key the log by series id, let writers own series. Request count, not bytes, is usually the first wall." />

<Reveal q="Kafka lag on the metrics topic reaches 4 minutes. What breaks first, and what do you do?">

Alerting breaks first: rules evaluate on data that hasn't arrived, so "no requests" rules fire falsely and real problems are seen 4 minutes late. Scale writers up to the partition count (that's why you gave the topic headroom), and check whether one writer is stuck on a hot or bloated series. Make alert evaluation **lag-aware**: never judge a minute whose data the pipeline hasn't finished writing (Chapter 17). Page on pipeline lag itself. See <a href={`${BASE}sd/lessons/queues-streams/#lag`}>Queues & streams · lag</a> for the drain-time arithmetic.

</Reveal>

**Common slip:** "Hosts write directly to the database." Then every database hiccup pushes back into ten thousand production hosts, and every deploy of the storage tier loses samples. The log in the middle is the shock absorber.

<h2 id="compression">Chapter 3 · Sixteen bytes into two</h2>

Take one host's CPU series: timestamps ten seconds apart, give or take a second, and values that wander between 41.0 and 43.5. A raw sample is an 8-byte timestamp and an 8-byte float: **16 B**. How much of that is news?

Consecutive points of one series are almost the same as the previous one. Facebook's Gorilla paper (VLDB 2015) showed two simple tricks that exploit this. You need the **intuition**, not the bit layout.

**Timestamps: delta-of-delta.** Store the first timestamp, then the first delta, then only *the change in the delta*. A steady scrape interval makes that change zero.

```text
timestamp        1000   1010   1020   1030   1041   1050
delta              -     10     10     10     11      9
delta-of-delta     -      -      0      0      1     -2
```

In Gorilla's scheme a zero delta-of-delta costs **one bit**, and small jitter costs a handful of bits (a short prefix plus a few value bits). Fully regular series spend about one bit per timestamp.

**Values: XOR with the previous value.** Equal floats XOR to all zeros, stored as one bit. Close floats share their sign, exponent and leading mantissa bits, so the XOR is a run of zeros, a few meaningful bits, and more zeros. The encoder stores "how many leading zeros, how many meaningful bits, and those bits".

```text
12.0  = 0x4028000000000000
12.5  = 0x4029000000000000
XOR   = 0x0001000000000000   -> 15 leading zeros, 1 meaningful bit, 48 trailing zeros
```

**How much does it save?** The paper reports about **1.37 bytes per point** on Facebook's production data, roughly 12× smaller than 16 B. Treat that as "one to two bytes per sample for well-behaved series", not a guarantee: noisy values (random-looking floats, high-precision measurements) compress far worse. The estimation lesson's **2 B per sample** is the safe whiteboard number, and this lesson keeps it.

**What it costs:** a chunk must be decoded from its start, so you cut series into chunks (say, about two hours, or about a hundred-odd samples) and decompress only the chunks a query overlaps. The encoding is also why **samples must arrive in order per series**, another reason the log is keyed by series id.

<Trace title="Squeeze the series" steps={compression} takeaway="Regular timestamps become zeros; repeated or close values become short XORs. Lossless, about one to two bytes per sample when the data is well behaved." />

**Common slip:** quoting "12× compression" as a fact about your system. Say "Gorilla-style encoding gets to about a byte or two per sample on regular data; we'd measure ours". Interviewers punish confident numbers that depend on data you haven't seen.

<h2 id="tsdb">Chapter 4 · Series, blocks and an index</h2>

Picture a grid. Rows are series, columns are two-hour slices of time. Every write lands in the right-most column. Every query reads a few rows and a few columns. Deleting old data means tearing off the left edge of the grid. That picture is most of a time-series database.

A TSDB (Prometheus's TSDB, InfluxDB, VictoriaMetrics, M3, and the storage behind hosted products) is organised around three ideas:

1. **Series id.** Hash the metric name plus *sorted* tags into an id. Samples are grouped by series, so a series' points sit together and compress together.
2. **Time blocks.** Data is cut into blocks by time (Prometheus uses two-hour blocks by default, compacted into larger ones later). The newest block, the **head**, lives in memory with a write-ahead log. Older blocks are immutable files.
3. **Inverted index.** For each `tag=value`, a sorted **posting list** of series ids, the same structure as a search engine's index (see <a href={`${BASE}sd/lessons/search/#inverted-index`}>Search · the back of the book</a>). A query intersects posting lists to find its series.

<Figure caption="A query walks index → series ids → only the chunks that overlap its time range. Retention drops whole blocks.">
  <Mermaid code={`flowchart LR
    Q["avg(cpu) by service\nregion=eu, last 6 h"] --> IX["inverted index\n__name__=cpu ∩ region=eu"]
    IX --> IDS["series ids\n17, 42, 97, ..."]
    IDS --> B1["block 06:00-08:00"]
    IDS --> B2["block 08:00-10:00"]
    IDS --> B3["head 10:00-now\n(in memory)"]
    B1 --> AGG["decode chunks,\naggregate by service"]
    B2 --> AGG
    B3 --> AGG`} />
</Figure>

**Why this is LSM-shaped.** Write-heavy, append-only workloads fit **LSM trees** (memtable, flushed immutable files, background compaction) because writes are sequential and nothing updates in place. A TSDB is a specialised LSM: the head block is the memtable, blocks are the sorted files, and compaction merges small blocks into bigger ones. The full story is in <a href={`${BASE}sd/lessons/databases/#storage-engines`}>Databases · two ways to keep a book sorted</a>. In an interview, two sentences are plenty.

**Retention is a file delete.** Because blocks are cut by time, dropping data older than 15 days means deleting whole blocks: no tombstones, no row-by-row deletes. Design the layout so the most common delete is free.

**Time-bucketed storage in a general-purpose store.** If you build on a wide-column store instead of a TSDB, you reproduce the same idea by hand. Put a time bucket in the partition key so a partition never grows without bound, and let the store expire whole buckets:

```sql
-- CQL (Cassandra); runs as written on Cassandra 5.0
CREATE TABLE samples (
  series_id bigint,
  day       date,
  ts        timestamp,
  value     double,
  PRIMARY KEY ((series_id, day), ts)
) WITH default_time_to_live = 1296000          -- 15 days in seconds
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_unit': 'DAYS',
                    'compaction_window_size': 1};
```

One partition holds one series for one day (8,640 samples at 10 s), sorted by time. A time-window compaction strategy keeps each day's files together, so expiry drops whole files instead of rewriting them. The trade-off: you now build the tag index, rollups and compression yourself.

**Three ways to build the store**, each worth one sentence:

| Option | Layout | Good for | Watch out |
|---|---|---|---|
| **Purpose-built TSDB** | Series + time blocks + tag index, Gorilla-style chunks | Metrics: high write rate, tag queries, rollups | Cardinality limits (next chapter); weak at ad-hoc event analytics |
| **Wide-column store** (Cassandra, Bigtable) | Partition key `(series_id, day)`, clustering key timestamp | Teams already running it; very high write rates | You build the tag index, rollups and compression; the day bucket keeps partitions bounded |
| **Columnar OLAP** (ClickHouse, Druid, Pinot) | Rows sorted by `(metric, tags, time)`, compressed per column | High-cardinality event analytics, ad-hoc group-bys | Heavier per-query cost than a TSDB for simple dashboards |

**Where blocks live.** Many modern designs keep the last couple of hours on the writers (memory plus WAL) and upload finished blocks to **object storage**, where a query tier reads them. Disk becomes cheap and nearly unlimited; the hot head stays fast. Replication of the head comes from Kafka (replay from offsets) or from running two writers per partition.

<Trace title="Read through the layout" steps={layout} takeaway="Index → series → chunks in the time range. Blocks cut by time make retention a file delete." />

**Common slip:** partitioning by time *only* (one big table per day, all series mixed). Every write hits today's partition (a hot spot), and every query scans all of today's series to find its few. Group by series, slice by time.

<h2 id="cardinality">Chapter 5 · The label that ate the cluster</h2>

Look at a graph of *active series* for a metrics cluster: flat at ten million for a year, then a cliff straight up after a two-line change that added `user_id` to a latency metric. Memory on every writer climbs until the kernel starts killing them, one by one. The sample rate didn't change. The change gave the system a hundred million new names.

**Cardinality** is the number of distinct series. It multiplies: every label's distinct values multiply with every other label's. Each series costs an index entry, an open in-memory chunk on its writer, and per-series metadata: **memory first, disk second**. That is why cardinality, not volume, is what usually kills a time-series system, and why it is the metrics walkthrough's favourite deep dive.

**Worked numbers.** `http_request_duration` with labels service × endpoint × status class × region: 4,000 service-endpoint pairs × 5 × 3 = **60,000 series**. Add `user_id`. With 10M daily users, each touching about 10 endpoint-status combinations: 10⁷ × 10 = **10⁸ new series per day**, ten times the whole system's 10 million series. Assumption: a few KB of memory per active series (index, head chunk, bookkeeping; measure it): 10⁸ × 3 KB = **300 GB of RAM** from one label.

A quieter multiplier: **histograms are many series**. In the Prometheus model, a histogram with 10 buckets is 10 bucket series plus a sum and a count, so the 60,000 above becomes about 720,000. Budget for it.

**How to cap it**, layered, cheapest first:

1. **Label rules at the collector.** An allowlist of labels per metric; drop or rewrite unbounded ones (`user_id`, `request_id`, raw URLs with ids in the path become route templates like `/orders/:id`).
2. **Per-team series quotas.** A team over its quota gets new series rejected and an alert, rather than taking down everyone. A noisy neighbour's blast radius is its own quota.
3. **Detect early.** Track new series per metric per minute (a HyperLogLog per metric, Chapter 12, is the cheap counter) and alert on sudden jumps.
4. **Bucket the long tail.** Keep the top N values of a label and fold the rest into `other`.
5. **Send "who" questions elsewhere.** Metrics answer *how much*; events answer *who*. Per-user or per-request questions go to an event, log or tracing store (columnar, built for high-cardinality group-bys), usually sampled.

<Trace title="Count the series" steps={cardinality} takeaway="Labels multiply. Unbounded labels never reach the TSDB: drop them at the collector, cap per team, detect new-series spikes, and send per-user questions to an event store." />

<Reveal q="A product lead asks for “p99 latency per customer” for the 50 enterprise customers. Is that a cardinality problem?">

Not necessarily. **Bounded** cardinality is fine. 50 customers × the existing label set is a 50× multiplier on one metric, which you can afford for a key metric if you budget it (and keep `customer` off the others). The problem is *unbounded* values: every user, every request id, every URL. Say the bound out loud: "50 enterprise customers, others folded into `other`, on this one metric."

</Reveal>

**Common slip:** "We'll add more nodes." Series cost memory on the write path and index entries on the read path. An unbounded label grows faster than you can buy hardware. Stop it at the door.

<h2 id="rollups">Chapter 6 · The retention ladder</h2>

Suppose a vendor quote for a year of metrics is twenty times what you expected. One line explains it: one year, full resolution. Who looks at last March in ten-second steps? Nobody.

**Rollups (downsampling)** replace many fine points with a few summary numbers over a coarser interval, kept on a **resolution ladder**: raw data for days, coarse data for months or years. Old-data queries stay fast because they read coarse rollups, and storage collapses.

**What a rollup stores.** Not the average. Store **min, max, sum and count** per interval (plus a histogram for latency metrics, Chapter 10). Averages don't average, but **sums and counts do**, so any coarser average is sum ÷ count. Min of mins and max of maxes are exact. For **counters** (monotonically increasing totals), roll up the *increase* in each interval, handling counter resets when a process restarts.

**Worked numbers: the ladder.** The full derivation is in <a href={`${BASE}sd/lessons/estimation/#metrics`}>Estimation · a million samples a second</a>; here is the result. Assumptions: 10M series, one sample per 10 s, about 2 B per raw sample compressed, and a rollup row of about 40 B (min, max, sum, count plus a timestamp, which compresses less well than raw samples).

```text
Raw 10 s        about 200 GB/day, kept 15 days          ≈ 3 TB
Hourly rung     360 raw samples ≈ 720 B → one 40 B row: about 18x smaller
                10M series × 24 rows/day × 40 B = 9.6 GB/day
                kept 1 year                             ≈ 3.5 TB
Total           ≈ 6.5 TB logical (× 3 replicas ≈ 19.5 TB)
Without rollups 1 year raw: 200 GB × 365 = 73 TB logical, about 20x more
```

Two things to say out loud. First, **retention is the storage design**: the hourly rung keeps a year in about 3.5 TB, versus 73 TB raw. Second, **a 1-minute rung does not save disk**: 10M series × 1,440 rows × 40 B ≈ 576 GB/day, about three times the raw tier's 200 GB/day, because a 40 B row replaces only six samples (about 12 B). It exists for **query cost**: a 7-day panel reads 7 × 1,440 = 10,080 points per series instead of 60,480 raw. If you add one, keep it only for days, not months, or use a 5-minute rung (about 115 GB/day).

<Figure caption="The cost-driven ladder: two rungs. A background job builds the hourly rung from raw.">
  <Mermaid code={`flowchart LR
    I["1M samples/s"] --> R["Raw 10 s\n15 days\n3 TB"]
    R -->|"per hour:\nmin, max, sum, count"| H["1 hour\n1 year\n3.5 TB"]`} />
</Figure>

**Which rung does a query read?** The query planner picks the **coarsest rung that still gives about one point per pixel**. A 1,000-pixel chart over 30 days: raw is 259,200 points per series, 1-minute 43,200, hourly 720, so read hourly. Over the last 6 hours: raw is 2,160 points, so read raw.

**How rollups are built.** Either a streaming job aggregates as data arrives (and must handle late data, Chapter 9), or a background job rolls up each closed block after the fact, which is simpler because late samples are already in the block. Many systems do both: streaming for the first rung, batch compaction for the coarse ones.

**Rollups versus sampling.** Both shrink data, but differently. A rollup keeps a summary of *every* point, so totals stay exact. Sampling keeps *some* points and throws the rest away, so totals must be scaled up and rare events can vanish. Use rollups for metrics; use sampling for traces and logs.

<h2 id="pre-aggregation">Chapter 7 · Write time or read time?</h2>

Imagine the main incident dashboard takes eleven seconds to load and accounts for a third of the query cluster's CPU. Every engineer on an incident has it open, and each refresh decodes every host's raw series to draw two hundred lines.

The naive design stores every raw event and computes `AVG(...)` at query time, which dies at scale with a dashboard scanning a hundred million rows per refresh. The opposite extreme computes everything on ingest and can't answer anything new. Real systems split the work:

| | Pre-aggregation (write time) | Query-time aggregation (read time) |
|---|---|---|
| Work happens | Once, as data arrives | On every query |
| Reads | Tiny precomputed rows | Scan raw points for the range |
| Answers | Only the questions you predicted | Any question over data you kept |
| Freshness | Seconds behind (window close) | As fresh as raw ingest |
| Cost driver | Stream jobs, extra storage per rollup | Query CPU, scales with viewers × refresh rate |
| Use for | Dashboards everyone opens, alert rules, billing counts | Incidents, ad-hoc exploration, recent data |

**Worked numbers.** "Requests per second by service, last 24 hours" over 10,000 host series: raw is 10,000 × 8,640 = **86.4 million points** per refresh. Pre-aggregated by service at 1 minute: 200 × 1,440 = **288,000 points**, 300× fewer, and the same for every viewer.

**The rule:** pre-aggregate **known, repeated** questions (the top dashboards, every alert rule, billing); keep a **short raw window** for questions nobody predicted. In Prometheus terms the pre-aggregated series are *recording rules*: named, stored results of a query, refreshed on a schedule.

<Trace title="Pick where the work happens" steps={preagg} takeaway="Pre-aggregate what everyone reads; keep raw data for the questions nobody predicted." />

<Reveal q="Isn't a rollup just a cache? Say the four cache promises for it.">

It is a cache of answers, and the same four promises apply. **Key:** `(metric, group-by tags, resolution, window start)`. **Lifetime:** the rung's retention, by design. **Invalidation:** none needed if the window is closed, except late data, which the correction path (Chapter 9) handles by rewriting the window. **Failure:** if the rollup job falls behind, queries fall back to raw data for recent ranges, and lag is alerted on.

</Reveal>

**Common slip:** "We'll precompute everything." You can't precompute questions you haven't been asked, and every rollup multiplies storage and stream-job work. Name the few you precompute and why.

<h2 id="windows">Chapter 8 · Three ways to cut time</h2>

An ads product needs three numbers: clicks per ad per minute (for invoices), "clicks in the last five minutes" (a live widget), and how long people browse before they click. Are these the same kind of window? No.

A stream processor (Flink, Kafka Streams, Spark Structured Streaming, the Dataflow model) groups an endless stream into finite **windows** so it can emit results.

```text
time  12:00   12:01   12:02   12:03   12:04   12:05
       |-------|-------|-------|-------|-------|      tumbling 1 min: each event in exactly one window

       |---------------------------------------|      sliding 5 min, every 1 min:
               |---------------------------------...  each event in five windows
                       |-------------------------...

user A  x x  x          x x                           session (gap 5 min): one window per burst
        |----|          |--|                          of activity, per key; length varies
```

| Window | Shape | Use for | Watch out |
|---|---|---|---|
| **Tumbling** | Fixed size, no overlap | Per-minute counts, billing, rollups. Totals add up | Spikes split across a boundary look smaller |
| **Sliding (hopping)** | Fixed size, advances by a smaller step | "Last 5 minutes, updated every minute", moving averages, alert rules | Each event is in size ÷ step windows; never sum them |
| **Session** | Per key, closes after a gap of inactivity | User sessions, browsing before a click | Unbounded length; state per active key |

A cheap way to build a sliding window: keep tumbling **1-minute buckets** and combine the latest five. That is how "last hour" leaderboards and trending work later in this lesson. Say "buckets"; don't invent sliding-window machinery on the spot.

**Sliding versus tumbling in one example.** 300 clicks arrive between 12:00:50 and 12:01:10, so 150 fall on each side of the minute boundary. Tumbling per-minute counts show 150 and 150, and a "more than 200 per minute" alert never fires. A 1-minute window sliding every 10 seconds sees all 300 at 12:01:10 and does fire. The boundary hid the spike. That is why alert rules use sliding windows and billing uses tumbling ones.

<h2 id="watermarks">Chapter 9 · When is a minute over?</h2>

A phone on the underground buffers twelve clicks and sends them when the train surfaces, ninety seconds later. The live dashboard has already published the minute those clicks belonged to. Which number is the true one? And how long should the dashboard have waited? Both questions are the same question.

Every event has two times:

- **Event time**: when it happened (stamped by the device or the first server).
- **Processing time**: when your job sees it.

They differ by network delay, retries, offline phones, and consumer lag. **Count by event time**, or a backlog replay will dump an hour of clicks into the current minute.

But with event time, how do you know a minute is complete? A **watermark** is the job's running claim: *"I believe I have now seen every event with event time ≤ W."* A window `[12:00, 12:01)` fires when the watermark passes 12:01. The usual heuristic is **bounded out-of-orderness**: W = the largest event time seen − an allowed delay (here 30 s).

<Figure caption="Watermark = largest event time seen − 30 s. Window [12:00, 12:01) fires only when the watermark reaches 12:01, on the arrival of 12:01:31, with four events, including the out-of-order 12:00:50.">
  <ArrayStrip name="Event time" values={['12:00:10', '12:00:40', '12:00:55', '12:01:05', '12:00:50', '12:01:20', '12:01:31']} indices={false} tones={{ 0: 'done', 1: 'done', 2: 'done', 3: 'ghost', 4: 'done', 5: 'ghost', 6: 'hot' }} pointers={[{ at: 4, label: 'out of order', tone: 'blue' }, { at: 6, label: 'W = 12:01:01', tone: 'gold' }]} />
</Figure>

The same logic in a few lines of Python (a toy: one key, in-memory state, no checkpointing):

```python
from collections import defaultdict

class TumblingCounter:
    def __init__(self, size=60, max_delay=30):
        self.size, self.delay = size, max_delay
        self.open = defaultdict(int)   # window_start -> count
        self.max_ts = None
        self.late = 0

    def on_event(self, ts):
        start = ts - ts % self.size
        if self.max_ts is not None and start + self.size <= self.max_ts - self.delay:
            self.late += 1             # its window already fired
            return []
        self.open[start] += 1
        self.max_ts = ts if self.max_ts is None else max(self.max_ts, ts)
        watermark = self.max_ts - self.delay
        return [(s, self.open.pop(s)) for s in sorted(self.open)
                if s + self.size <= watermark]
```

Fed the seven events above in arrival order (as seconds since 12:00:00), it returns `[(0, 4)]` exactly once, on `12:01:31`. An eighth event stamped `12:00:58` is then counted in `late`.

**What about events behind the watermark?** They are **late**. The watermark was a guess, and some events will always miss it. Options, chosen by product:

- **Drop and count.** Fine for a live dashboard; publish the late fraction so you know what it misses.
- **Allowed lateness.** Keep window state a little longer and emit an *updated* result (the sink must accept updates, so use upserts).
- **Side output → correction path.** Late events go to a separate stream, or to the batch job that recomputes from the raw log (Chapter 16). Billing uses this.

The trade is unavoidable: **a longer watermark delay means more complete results and slower ones**. Two-hour-offline phones should not make every dashboard two hours late; give them a correction path instead.

**Idle partitions stall watermarks.** A job with many input partitions takes the *minimum* watermark across them. If one partition has no traffic, its watermark never advances and every window waits. Stream frameworks have an "idle source" setting for this; check your engine's docs.

<Reveal q="The stream job is down for 20 minutes, then catches up. With processing-time windows, what does the dashboard show? With event-time windows?">

This is the reason to say "event time" out loud in any aggregation design.

</Reveal>

<h2 id="percentiles">Chapter 10 · The average of two p99s</h2>

Back to the prologue. Rebuild the incident with two servers instead of forty: one fast, busy server and one slow, quiet one. What is the p99 of the fleet? The tempting answer is to average.

A percentile is a **position in a sorted list**. p99 is the value below which 99% of observations fall. **You cannot combine two p99s**, not by averaging, not by weighting, not by taking the max, because the merged list's 99th-percentile position depends on the whole distributions, which the two numbers threw away.

**Worked numbers (nearest-rank).** Server A: 1,000 requests, 985 at 10 ms and 15 at 500 ms. Its p99 is the 990th value: **500 ms**. Server B: 10 requests, all 2,000 ms: p99 = **2,000 ms**.

- Average of p99s: (500 + 2,000) ÷ 2 = **1,250 ms**.
- True p99: merged 1,010 requests; the ⌈0.99 × 1,010⌉ = 1,000th value. Values 1-985 are 10 ms, 986-1,000 are 500 ms. True p99 = **500 ms**.

The average was 2.5× too high here. With other mixes it is too low, as in the prologue, where 39 healthy hosts hid one terrible one. Either way, it isn't p99. **One sentence, big signal: "percentiles don't average, so I store mergeable distributions."**

**What to store instead: mergeable distributions.**

- **Fixed-bucket histograms.** Counts per latency bucket (≤10, ≤50, ≤100, ≤250, ≤500, ≤1,000, ≤2,500 ms, +∞). Merging is **adding counts** across hosts and across time. A quantile is read off the merged histogram by finding the bucket holding rank ⌈0.99n⌉ and interpolating, so the error is bounded by the **bucket width**. Here the merged rank 1,000 lands in (250, 500]: "p99 is between 250 and 500 ms".
- **HDR Histogram.** Log-linear buckets configured by significant digits: bounded *relative* error over a huge range, fixed memory.
- **t-digest.** Clusters values into centroids, small near the tails, so extreme percentiles are accurate. Mergeable, approximately.
- **DDSketch.** Logarithmic buckets with a guaranteed relative error; fully mergeable (it came out of Datadog).

With any of these, each host sends a distribution per window (plus count and sum), the rollup ladder merges distributions instead of numbers, and p99 for any service and any range is computed at query time from the merged distribution.

<h2 id="counters">Chapter 11 · One number, too hot</h2>

Say a video goes viral on a Sunday morning. Its view counter, one Redis key, takes a hundred thousand increments a second. One shard runs at 100% CPU while the other fifteen idle.

This is a **hot key** (the fourth costume of the same problem: hot cache key, hot shard, hot partition, hot counter). One key lives on one shard, so bigger machines and more shards don't spread it.

**Sharded counter.** Split the counter into N sub-keys, `views:v123:0` to `views:v123:15`. Increment a random one. **Read = sum of all 16**. At 100,000 increments/s, each sub-key takes 100,000 ÷ 16 = **6,250/s**.

```python
import random
SHARDS = 16

def add_view(r, video_id, n=1):
    r.incrby(f"views:{video_id}:{random.randrange(SHARDS)}", n)

def get_views(r, video_id):
    pipe = r.pipeline(transaction=False)
    for i in range(SHARDS):
        pipe.get(f"views:{video_id}:{i}")
    return sum(int(v or 0) for v in pipe.execute())
```

Reads pay a small fan-in: 16 `GET`s, pipelined. In Redis Cluster the sub-keys deliberately land in different slots so the load spreads, which means one multi-key `MGET` won't work across them; use a cluster-aware client that groups the commands per node. The sum is not an atomic snapshot (increments can land between the 16 reads), which is fine for a view count. In a relational database the same trick is N counter rows per item (see the like-count example in <a href={`${BASE}sd/lessons/databases/#modeling`}>Databases</a>).

<Figure caption="Increments spread over 16 sub-keys; the reader sums them. Batching in the app divides the write rate again.">
  <Mermaid code={`flowchart LR
    A1["app server 1\nbuffer, flush every 2 s"] -->|"INCRBY views:v123:k"| S0[("sub-key 0")]
    A1 --> S5[("sub-key 5")]
    A2["app server 2"] --> S5
    A2 --> S9[("sub-key 9")]
    S0 --> R["read: sum of 16"]
    S5 --> R
    S9 --> R
    R --> DB[("database\nflushed total")]`} />
</Figure>

**Batch in the app.** View counts tolerate seconds of lag, so each app server accumulates increments in memory and flushes one `INCRBY 100` instead of 100 `INCR`s. That cuts writes a hundredfold more, at the cost of losing up to one flush interval if a server crashes. Say the trade: "a few seconds of views can be lost on a crash; for views that's fine; for money it isn't."

**Periodic flush to truth.** The authoritative count lives in a database; the hot counter is flushed there every few seconds, and the page reads the cached total.

<Reveal q="Why not just queue every increment and apply them one by one?">

A queue doesn't remove the bottleneck; it moves it. The consumer still applies 100,000 updates a second to one key. Queueing helps only if the consumer **batches** (sums 1,000 increments and writes one), which is the app-side batching above with an extra hop.

</Reveal>

<h2 id="hyperloglog">Chapter 12 · Counting distinct items</h2>

Say a product team wants "unique viewers" on every campaign, per day, for a year. The first prototype keeps a set of user ids per campaign per day. On day three it has used more memory than the rest of the ads system combined.

**Distinct counts don't add, and exact sets are big.** 100 million user ids × 8 B = 800 MB per set, per campaign, per day.

**HyperLogLog (HLL)** estimates distinct counts in fixed, tiny memory. The intuition: hash every item to random-looking bits. In a stream of random hashes, seeing one that starts with *k* zero bits suggests you've seen about 2^k distinct items (a run of 20 zeros is a one-in-a-million event). One such estimate is noisy, so HLL splits the hashes into *m* buckets (registers) by their first bits, keeps the longest zero run per register, and combines them with a harmonic mean. The standard error is about **1.04 ÷ √m**.

Redis's HLL uses m = 16,384 registers: 1.04 ÷ 128 ≈ **0.81% standard error** in at most **12 KB**, whether it has seen a thousand ids or a billion. Commands: `PFADD`, `PFCOUNT`, `PFMERGE`.

```text
PFADD   uv:c42:2026-10-08:13  user:1 user:2 user:3   # one sketch per campaign per hour
PFADD   uv:c42:2026-10-08:14  user:2 user:9
PFCOUNT uv:c42:2026-10-08:13  uv:c42:2026-10-08:14   # distinct across both hours: 4
PFMERGE uv:c42:2026-10-08  uv:c42:2026-10-08:13 uv:c42:2026-10-08:14   # keep a daily sketch
```

(`user:2` appears in both hours but counts once. Adding the two hourly counts would give 5.)

**The superpower is merging.** The HLL of a union is the register-wise **max** of the HLLs. So keep one sketch per campaign per hour, and "unique viewers this week" is `PFMERGE` of 168 sketches, then one `PFCOUNT`, with the same error. Adding hourly counts would count a returning viewer once per hour.

**Worked numbers.** 1,000 campaigns × 365 days × 12 KB ≈ **4.5 GB** for a year of daily uniques, and any range by merge. (Redis stores small HLLs sparsely, so real memory is often less.) Exact sets: hundreds of GB *per day*.

**What it can't do:** list the ids, or answer "did user 42 view?" (a Bloom filter answers membership), and intersections ("viewed both campaigns") via inclusion-exclusion are noisy for small overlaps.

| Question | Structure | Answer is |
|---|---|---|
| How many **distinct** items? | HyperLogLog | An estimate, about 0.81% standard error |
| How **often** does item x appear? | Count-Min Sketch | An overcount, never an undercount |
| Have I **seen** item x? | Bloom filter | "Definitely not" or "probably yes" |

<h2 id="count-min">Chapter 13 · A table that never undercounts</h2>

Say search wants "how often was each query typed in the last hour?" for trending. There are hundreds of millions of distinct strings, most typed once. Exact counters would not fit. Imagine instead a small grid of counters, two rows of five. Every word lands in one box per row. Boxes are shared. So which box do you believe?

**Count-Min Sketch (CMS)** estimates *how often* each item appears, in fixed memory. It is **d rows × w columns** of counters, with one hash function per row.

- **Update(x):** for each row *i*, add 1 to `C[i][h_i(x)]`.
- **Query(x):** the **minimum** of `C[i][h_i(x)]` over the rows.

Each counter holds x's true count **plus** whatever collided with it. Collisions only add, so every row overestimates, and the minimum is the least-polluted guess. **It never undercounts; it may overcount.**

**Tiny worked example.** Stream: cat, dog, cat, eel, fox, cat, dog (cat ×3, dog ×2, eel ×1, fox ×1). Pretend hashes: row 1: cat→0, dog→2, eel→0, fox→4; row 2: cat→2, dog→3, eel→3, fox→1.

**Error intuition.** With N total updates spread over w columns, one counter collects about N ÷ w of noise on average. The guarantee: with w = ⌈e ÷ ε⌉ and d = ⌈ln(1 ÷ δ)⌉, the overcount is at most **εN** with probability at least 1 − δ. Take ε = 0.1% and δ = 1%: w = ⌈2,718.3⌉ = 2,719, d = ⌈4.6⌉ = 5, so 13,595 counters × 4 B ≈ **54 KB**. For a billion searches in an hour, the overcount is at most about **a million** with 99% probability.

Read that honestly: **Count-Min is excellent for heavy hitters** (terms counted in the tens of millions) **and useless for the long tail** (a term typed 50 times is lost in the noise). That is exactly what top-K needs.

*Checked by experiment.* A simulated stream of 200,000 Zipf-distributed words over 50,000 distinct terms, with this 2,719 × 5 sketch, gave a worst overcount of 87 against the bound of 0.001 × 200,000 = 200. Every item was within the bound. The bound is a ceiling, not a typical error.

**Merging:** two sketches with the same dimensions and hash functions merge by **adding cell by cell**, so per-minute sketches combine into an hour, and per-server sketches into a fleet.

**Conservative update (a common improvement).** On update, only raise the counters that are currently at the minimum for that item. It still never undercounts and usually overcounts less, but the sketches then no longer merge by simple addition with the same guarantee, so use it where you don't merge.

```python
import hashlib, math

class CountMin:
    def __init__(self, eps=0.001, delta=0.01):
        self.w = math.ceil(math.e / eps)
        self.d = math.ceil(math.log(1 / delta))
        self.t = [[0] * self.w for _ in range(self.d)]

    def _cols(self, item):
        for i in range(self.d):
            h = hashlib.blake2b(f"{i}:{item}".encode(), digest_size=8).digest()
            yield i, int.from_bytes(h, "big") % self.w

    def add(self, item, n=1):
        for i, c in self._cols(item):
            self.t[i][c] += n

    def estimate(self, item):
        return min(self.t[i][c] for i, c in self._cols(item))
```

**The sentence to say:** *"Exact counting of every term doesn't fit memory across all the windows and shards we need; a Count-Min Sketch gives frequency estimates with bounded overcount in kilobytes, paired with a small heap of the current top-K."* Interviewers accept the name plus the property; they rarely want the internals derived.

<h2 id="top-k">Chapter 14 · The ten loudest</h2>

Imagine a first "trending now" page built by sixteen stream workers, each sending its own top ten to a merger. On launch day the page shows ten mid-sized hashtags. The real story of the day, a hashtag everybody used, spread evenly across all sixteen workers, doesn't appear at all.

**Exact top-K on one machine.** Count with a hash map, then keep a **min-heap of size K**: for each item, if the heap has fewer than K entries or the item beats the heap's minimum, push it (and pop the minimum). O(n log K) time, O(distinct + K) memory. The min-heap is the door guard who admits only the best K (see <a href={`${BASE}dsa/lessons/heaps/`}>DSA: Heaps</a>).

**Distributed top-K: local lists don't merge.** If an item's count is **split across shards**, it can be just below the cut on every shard and still win globally. Shard A: x=10, y=9. Shard B: z=10, y=9. Shard C: w=10, y=9. Every local top-1 is a 10; the true winner is y with **27**.

**Fixes:**

- **Partition by item.** Key the stream by item (hashtag, video id), so each item's full count lives on one shard. Then any global top-K item is in its own shard's top K, and **merging the shards' top-K lists is exact**. This is the standard answer. Hot items (one hashtag with a third of all traffic) get pre-aggregated per producer first, then sent as partial sums.
- **Over-fetch.** Ask each shard for its top 2K or 10K. Usually right, not guaranteed. Algorithms that make this exact in rounds exist (look up TPUT); in an interview, "partition by item" wins.

**Count-Min + heap (unbounded keyspace).** For each arriving item: update the sketch, read its estimate, and if it beats the heap's minimum (or the heap isn't full), insert or update it in a **K-entry heap of candidates**. Memory is the sketch plus K entries, regardless of how many distinct items exist.

```python
class TopK:
    def __init__(self, k, eps=0.001, delta=0.01):
        self.k, self.cms, self.cand = k, CountMin(eps, delta), {}

    def add(self, item):
        self.cms.add(item)
        est = self.cms.estimate(item)
        if item in self.cand or len(self.cand) < self.k:
            self.cand[item] = est
        else:
            lowest = min(self.cand, key=self.cand.get)   # O(k); use a real heap at scale
            if est > self.cand[lowest]:
                del self.cand[lowest]
                self.cand[item] = est

    def top(self):
        return sorted(self.cand.items(), key=lambda kv: -kv[1])
```

On the same simulated Zipf stream, this returned exactly the true top 10. Overcounts can let an unlucky small item into the candidates; keep a few more than K candidates and the error stays in the noise for true heavy hitters.

**Deterministic heavy hitters: Misra-Gries and Space-Saving.** Count-Min is probabilistic and needs a separate candidate list. These two keep only a fixed number of counters and have guarantees without randomness.

- **Misra-Gries with k counters:** if the item is tracked, increment it; else if there is a free counter, start it at 1; else decrement every counter by 1 and drop zeros. Every item with true frequency above N ÷ (k + 1) is guaranteed to still be in the table, and counts underestimate by at most N ÷ (k + 1). With k = 20 and N = 200,000, the threshold is about 9,524, and the experiment above kept every item above it.
- **Space-Saving with m counters:** when a new item arrives and the table is full, it *replaces* the smallest counter and inherits its count plus one. Estimates overcount by at most N ÷ m, so it is the "never undercounts" cousin of Count-Min.

Say "heavy hitters" and name one of these; they are the standard answer when the interviewer asks for a deterministic guarantee.

**Windowed top-K ("last hour").** Keep **per-minute buckets** (per-minute count tables or per-minute sketches) and combine the latest 60: add counts (or add sketches cell by cell), then rank the union of the per-minute candidates. Don't merge 60 per-minute top-K *lists*: that is the split-count trap again, split across time instead of shards. As each minute ages out, drop its bucket.

**Top versus trending.** "Top" is the biggest count; "trending" is the biggest **surprise**: current rate divided by a baseline (the same hour last week, or a slow exponential moving average). A perennial giant is top but not trending. Exponential **decay** of scores (multiply every count by, say, 0.9 each minute) is the cheap way to favour recent activity without keeping buckets.

**Exact or approximate? Say the regime.** With a **bounded keyspace** (10 million videos), exact counts in a sorted set or hash map are simple and fit (10M × ~100 B ≈ 1 GB). With an **unbounded keyspace** (every search string, every URL) across many windows and dimensions, sketches win: per country (200) × per 5-minute window kept for an hour (12) × 54 KB ≈ **130 MB** of Count-Min, where exact tables could need gigabytes per window. **Picking the regime before picking the tool is the whole judgment being tested.**

<h2 id="leaderboards">Chapter 15 · Who is winning?</h2>

Say a one-puzzle-a-day game reaches twenty million players by the end of its first month. Every player wants three things: the top ten, their own rank, and the people just above them. Rank is the expensive word in that sentence.

**Redis sorted sets** are the default leaderboard: each member has a score, kept in a skip list (plus a hash for member lookup), so ranks are known without scanning.

```text
ZINCRBY  lb:daily:2026-10-08  50  player:42          # add 50 points          O(log N)
ZREVRANGE lb:daily:2026-10-08  0  9  WITHSCORES      # top 10                  O(log N + 10)
ZREVRANK lb:daily:2026-10-08  player:42              # my rank (0-based)       O(log N)
ZREVRANGE lb:daily:2026-10-08  r-5  r+5  WITHSCORES  # the 5 above and below   O(log N + 11)
ZSCORE   lb:daily:2026-10-08  player:42              # my score                O(1)
```

(Since Redis 6.2, `ZRANGE ... REV` is the preferred spelling of `ZREVRANGE`; both work.)

**Worked numbers.** Assumption: 20M members × roughly 100 B each (skip-list node, hash entry, member string; measure it) ≈ **2 GB**, which fits one node. Writes: 20M players × 10 score updates a day = 2 × 10⁸ ÷ 10⁵ ≈ **2,000/s** average, perhaps 10,000/s at a 5× peak. Reads: 20M × 5 leaderboard views a day ≈ **1,000/s** average. A Redis primary handles very roughly 100,000 simple ops/s (benchmark yours), so one primary plus replicas carries it. The cluster exists for availability, not capacity.

**Periods.** One key per period (`lb:daily:2026-10-08`) with a TTL; weekly = `ZUNIONSTORE` of seven dailies (or a separate weekly key incremented alongside). Resets become "start writing a new key".

**Ties.** Equal scores are ordered by member name, which is rarely what players expect. To let the earlier achiever win, encode time into the score: `score = points × 10⁶ + (999,999 − seconds into the week)`. Scores are doubles, exact for integers up to 2⁵³ ≈ 9 × 10¹⁵; 10⁶ points × 10⁶ ≈ 10¹² is far inside that.

**Friends leaderboards.** Don't keep a sorted set per user. Fetch the ~200 friends' scores (`ZMSCORE`, one call) and sort in the app.

**Sharding limits.** One sorted set lives on one shard, so past one primary's write rate or memory (say 500M players), you split:

| Split by | Top-K | One player's rank | Watch out |
|---|---|---|---|
| **Hash of player id** (16 sets) | Exact: best 10 of the 16 shards' top 10s (each player is in one shard) | Sum of `ZCOUNT` above my score across all 16 | Rank is a fan-out; cache it for a few seconds |
| **Score range** (tiers) | Read the top tier only | Count of all higher tiers + my rank in my tier | Players move between shards as scores change; tiers go hot |
| **Approximate for the tail** | Exact top from a small set of leaders | "Top 3%" from a score histogram | Players outside the top thousands rarely need an exact rank |

**Source of truth.** Redis is the serving structure, not the ledger. Score events go to a database or log; the leaderboard can be rebuilt from them after a failover loses the last few writes.

<h2 id="ad-clicks">Chapter 16 · Every click is money</h2>

An advertiser's finance team emails a spreadsheet: their own logs show 1,000,312 clicks for October; the invoice says 1,003,904. Opening the raw click log shows the same click id three times: a double tap, then a client retry after a timeout. Exactly-once is not something you buy. You build it, and then you check it.

Counting clicks for billing combines everything above with the delivery rules from <a href={`${BASE}sd/lessons/queues-streams/#delivery`}>Queues & streams · delivery</a>: delivery is **at-least-once**; you make the **effect** exactly-once.

1. **A stable id per click.** The ad server mints a `click_id` at impression time and signs it into the click URL; the redirect service logs `(click_id, ad_id, event_time, ...)` to Kafka, keyed by `ad_id`. Double taps and retries now carry the same id.
2. **Dedup in the stream job.** Keyed state "seen click ids", with a TTL longer than any realistic retry (a day, say). Exact state is affordable: about 10⁹ ids a day × ~40 B ≈ **40 GB**, spread across the job's RocksDB state. Not a Bloom filter: its false positives would silently **drop real clicks**, which is underbilling you can't trace.
3. **Event-time tumbling windows** per `(ad_id, minute)`, with a watermark and a late-data side output (Chapter 9).
4. **Checkpoints.** Flink-style checkpoints snapshot window state together with Kafka offsets. After a crash, the job rewinds to the checkpoint and **replays**, so the sink will see some results twice.
5. **An idempotent sink.** Upsert `count = N` for key `(ad_id, minute)`, never `count += N`. A replay rewrites the same value. (Kafka-to-Kafka pipelines can use transactions instead.)
6. **Reconciliation.** Raw clicks also land in object storage. A nightly batch job recomputes exact counts with complete data (including very late events) and compares. **Batch is the invoice, streaming is the dashboard**, and drift beyond a threshold pages someone.

```sql
-- the sink write: replay-safe because it overwrites, never adds
INSERT INTO ad_minute_clicks (ad_id, minute, clicks)
VALUES (42, '2026-10-08 12:00:00', 317)
ON DUPLICATE KEY UPDATE clicks = VALUES(clicks);   -- MySQL; Postgres: ON CONFLICT ... DO UPDATE
```

<h2 id="alerting">Chapter 17 · Twenty-five pages an hour</h2>

Say checkout p99 hovers right at its 500 ms threshold, and every crossing is a new page. By dawn the on-call engineer has silenced the alert entirely, which is how, the following week, a real latency regression goes unnoticed for an hour. An alert that cries wolf is worse than no alert, because it trains people to ignore it.

**Alert rules are queries on a schedule.** "Page if p99 of checkout > 500 ms" is a query evaluated every minute (about 833 queries/s for 50,000 rules, Chapter 1), which is why rules run against **1-minute rollups and recording rules**, not raw data. At larger scale, simple threshold rules can be evaluated **in the stream** as data arrives.

**Making alerts trustworthy:**

- **Duration ("for: 5m").** The condition must hold for several consecutive evaluations before firing. Kills single-sample spikes.
- **Hysteresis.** Fire above 500 ms, resolve only below 450 ms, so a value hovering at the line doesn't flap.
- **Respect ingest lag.** Never evaluate a minute whose data the pipeline hasn't finished writing: the watermark idea again. Otherwise every ingest backlog fires "requests = 0" across the fleet.
- **"No data" is its own state,** not zero. A dead service and a quiet one look the same to a naive rule.
- **Alert on symptoms, not causes.** Page on what users feel (error rate, latency against an SLO, ideally as burn-rate alerts); send causes (CPU, disk) to dashboards and tickets.

**Alert storms.** A rack switch dies: 400 "host down" and 1,600 "service degraded" alerts in two minutes. The alert router (Prometheus's Alertmanager is the classic example) should **group** by cluster and alert name, **inhibit** child alerts while a parent like "rack down" is firing, **deduplicate** across replicas of the evaluator, and **rate-limit** notifications, so a human gets one page naming the scope.

**Who watches the watchers?** The monitoring system must be monitored from **outside** itself: a "dead man's switch" alert that always fires, and an external service that pages if it ever *stops* arriving.

**0:08 · Non-functionals with numbers**

>

**0:12 · The bridge**

> **Candidate:** "So: tagged metrics in, tag-and-range queries out, threshold alerts; a million samples a second, ten million series, 15 days raw, a year rolled up, alerting the most available part. Does that match what you had in mind?"
>
> **Interviewer:** "Yes. Watch the series count."

**0:12 · Core entities**

> **Candidate:** "Metric: a name and type. Series: a metric plus one set of tag values; that's the unit of storage and the thing whose count we have to control. Sample: timestamp and value, belonging to one series. Rollup: a series at a coarser resolution, with min, max, sum and count, or a histogram. **0:15 · API**

> **Candidate:** "Ingest: `POST /v1/series` with a batch, each item a metric name, tags, type, and points, authenticated by an API key per team. **0:20 · High-level design**

> **Candidate:** "Write path: an agent on each host aggregates locally and sends one compressed batch every 10 seconds, a thousand requests a second fleet-wide, not a million. **0:32 · Deep dive 1: ingest and cardinality**

> **Candidate:** "The thing that kills these systems is series count, not sample rate. Labels multiply: one request metric with service, endpoint, status and region is 60,000 series; add user_id with 10 million daily users touching 10 combinations each, and it's 100 million new series a day, ten times everything else, and each costs a few KB of writer memory. So collectors enforce a label allowlist per metric and rewrite raw paths to route templates; every team has a series quota, and over-quota series get rejected with an alert to the owner, not a cluster-wide outage. We track new series per metric per minute with a HyperLogLog and alert on jumps. Per-user questions go to the event store, not here."
>
> "Kafka: 100 MB/s at about 10 MB/s per partition needs ten; I'd give it 64 for headroom. 24 hours of retention is about 5 TB with compression and three replicas, which also covers a day-long writer outage. Writers: about nine at 200,000 samples a second each, 60% utilised. If agents can't reach us, they buffer a few minutes on disk, then drop and count drops. Monitoring must never take down the host."

**0:39 · Deep dive 2: storage, rollups and percentiles**

> **Candidate:** "Storage: the head block in writer memory, two-hour immutable blocks in object storage, each with a posting-list index from tag-value to series ids. Gorilla encoding, delta-of-delta timestamps and XOR'd values, gets regular series to about one or two bytes a sample; I'll use two. Raw: a million a second times 10⁵ seconds times 2 bytes is about 200 GB a day, 3 TB for 15 days. Hourly rollups of min, max, sum and count are 40-byte rows replacing about 720 bytes of raw samples, so about 18 times smaller: 9.6 GB a day, 3.5 TB for a year. Total about 6.5 TB, versus 73 TB for a year of raw. A 1-minute rung would cost more than raw per day, so I'd only add it for query speed, and only for a few days. Retention is dropping whole blocks."
>
> "Latency metrics are histograms, not p99s, because percentiles don't average: each host sends bucket counts, rollups add them, and p99 is read off the merged histogram at query time. The query planner picks the coarsest rung with about one point per pixel; the top dashboards and every alert rule read pre-aggregated recording rules: 288,000 points instead of 86 million for the main service dashboard."

**0:45 · Deep dive 3: alerting**

> **Candidate:** "Fifty thousand rules a minute is about 830 queries a second, on pre-aggregated data. Rules have a duration and hysteresis so they don't flap. The evaluator only judges minutes the pipeline has finished (it reads ingest lag), and 'no data' is its own state, so a backlog doesn't page the fleet. The router groups by cluster and alert, inhibits children under a parent like 'rack down', and dedups across two evaluator replicas. Alerting runs in its own deployment with priority on the query tier, and an external dead man's switch pages if the whole pipeline goes quiet."

**0:52 · Wrap-up**

> **Candidate:** "To recap: a million samples a second through batched agents and a series-keyed log, Gorilla-compressed blocks with a tag index, a retention ladder that keeps a year in a few terabytes instead of 73, mergeable histograms for percentiles, and lag-aware alerts that page once per real problem. <h2 id="sketch-ads">Chapter 19 · Sketch: ad-click aggregator</h2>

Twelve minutes instead of sixty. The prompt: "Per-campaign ad-click dashboard. Clicks also drive billing."

**Requirements.** Count clicks per ad and per campaign per minute; advertisers see counts within about 5 seconds on a dashboard; invoices must be exact; query ranges up to 90 days. Assumption for this example: 1B clicks/day ≈ 10,000/s average (÷10⁵), 50,000/s peak; 10M active ads.

**Design** (Chapter 16's figure): redirect service with signed `click_id` → Kafka keyed by `ad_id` (salted for hot ads) → stream job: dedup by `click_id` in keyed state, 1-minute event-time tumbling windows, watermark of a few seconds, late events to a side output → upsert `(ad_id, minute) → count` in an OLAP store (columnar, sorted by ad and time) → query service. <h2 id="sketch-leaderboard">Chapter 20 · Sketch: a game leaderboard</h2>

**Requirements.** Global daily and weekly leaderboards, top 100, my rank, players around me, friends' board. 20M players, 2,000 score updates/s average, 1,000 reads/s average (Chapter 15).

<h2 id="sketch-trending">Chapter 21 · Sketch: top-K trending</h2>

A football final ends in penalties, and within a minute half of a social app is posting the same hashtag. The product wants it on the trending page before the players leave the pitch, per country, and not the hashtags that are always big.

**Requirements.** "Top 10 trending hashtags in the last hour, per country, refreshed every minute." Billions of posts a day; unbounded hashtag space; approximate is fine.

**Design.** Posts → extract hashtags → Kafka keyed by hashtag (so each tag's count lives on one worker; pre-aggregate hot tags per producer) → per worker, per country, per minute: a Count-Min Sketch plus a candidate heap → every minute, merge the last 60 minute-buckets (add sketches, union candidates), score each candidate as **current rate ÷ baseline** for "trending" (or raw count for "top"), and keep the best 10 → a small aggregator merges the workers' per-country lists (exact, because workers own disjoint tags) → write the result to a cache keyed by country; clients read the cache.

    W --> M["every minute:\nmerge last 60 buckets\nscore = rate / baseline"]

**Five follow-ups you will get:**

<Reveal q="1 · Someone adds user_id as a tag. What happens, and what stops it?">

Series multiply: 10M users × ~10 combinations is 100M new series a day, each costing writer memory and index entries, so the cluster falls over on memory before disk. Collectors drop unbounded labels by allowlist, per-team quotas cap the blast radius, and a HyperLogLog of new series per metric alerts on jumps. Per-user questions go to an event store.

</Reveal>

<Reveal q="2 · How do you show p99 across 200 hosts and 30 days?">

Each host sends a histogram (or a mergeable sketch like DDSketch or t-digest) per window. Rollups add bucket counts across hosts and time; p99 is read from the merged distribution at query time. Averaging p99s is wrong: a quiet slow host and a busy fast one make the average meaningless.

</Reveal>

<Reveal q="3 · How much storage, and how do you keep it bounded?">

1M samples/s × 10⁵ s × ~2 B ≈ 200 GB/day raw; 15 days = 3 TB. Hourly rows (40 B replacing about 720 B) are about 18× smaller: 9.6 GB/day, 3.5 TB for a year. A year of raw would be 73 TB. Time-partitioned blocks make dropping old data a file delete.

</Reveal>

<Reveal q="4 · Events arrive late or out of order. How are your per-minute numbers right?">

Window by event time, not processing time. A watermark (largest event time seen minus an allowed delay) decides when a minute closes. Late events are counted as late and either dropped (dashboards), applied as updates via allowed lateness, or sent to a correction path that rewrites the window (anything that bills).

</Reveal>

<Reveal q="5 · How do you stop alert fatigue?">

Rules hold for a duration before firing and resolve below a lower threshold (hysteresis); they evaluate only minutes the pipeline has completed; "no data" is a separate state. The router groups related alerts, inhibits children under a parent outage, deduplicates, and rate-limits, so a rack failure is one page. Page on user-facing symptoms; send causes to dashboards.

</Reveal>

## Five mistakes to leave behind

1. **Averaging percentiles.** Store mergeable distributions; read the percentile last.
2. **Unbounded labels.** One `user_id` tag can outgrow the rest of the system.
3. **Keeping everything at full resolution.** The retention ladder *is* the storage design.
4. **Processing-time windows.** Count by event time, with a watermark and a late-data policy.
5. **Merging local top-K lists from shards that split items.** Partition by item first.

A good habit: put a small grey number next to any live dashboard, such as "late events, last hour: 0.02%". It is the dashboard admitting what it doesn't know.

- **Space-Saving and Misra–Gries** — deterministic heavy-hitter algorithms that keep K counters and guarantee every item above N ÷ K is found.

- **Tail-based sampling for tracing** — buffering whole traces to keep the interesting ones, and what it costs in memory.
