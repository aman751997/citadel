<h2 id="prologue">Prologue · Why limit requests at all</h2>

Here is a failure that happens in real systems. A partner's integration calls your search API. Their client hits a timeout and retries immediately. The retry times out too, and every worker in their fleet does the same. Soon one API key is sending 40,000 requests a second.

Nothing on your side says no. The gateway forwards everything, the search cluster queues everything, and every other customer's requests wait behind one customer's retry loop. Someone ends the incident by revoking the key by hand.

A **rate limiter** is the thing that would have said no. For every request it answers: may this caller have one more right now? There are four common reasons to build one, and you should say which apply:

1. **Protect capacity.** One caller must not be able to use what everyone shares (the incident above).
2. **Fairness.** Each customer gets what their plan says, no matter what other customers do.
3. **Cost.** Some requests cost real money: an SMS, a paid upstream API, a GPU-second of an LLM.
4. **Abuse and security.** Password guessing, scraping, card testing, sign-up spam.

**Where it shows up in interviews.** "Design a rate limiter" is a common warm-up question. It also appears as one sentence inside almost every other design ("the gateway rate-limits per API key"). If you can defend a limiter in depth, that sentence stops being a hand-wave.

**Common slips to avoid.**

- Spending twenty minutes on algorithms before drawing a single box. Do requirements in about six minutes and reach the algorithm around the 25-minute mark.
- Not saying what you are leaving out (volumetric DDoS, billing, the admin UI), so the interviewer wonders.
- Saying "counters in Redis" with no key shape, TTL or failure plan. It is the same red flag as "cache it in Redis".
- Mixing up layers. "Rate limiting" means different things at the edge, the gateway and inside a service. Ask which one, then answer.

<h2 id="requirements">Chapter 1 · Who gets how much</h2>

Start by asking what is being limited, for whom, and by how much. Take this example product: an API sold in three plans. Free keys get a taste, Pro keys pay for real volume, and Enterprise customers must never be cut off in the middle of a campaign, because they pay for overage.

**Functional requirements** (what the limiter does):

1. **Limit requests per API key, and per key per endpoint.** The plan sets the overall rate. Expensive endpoints (creating records, search) get their own tighter rules.
2. **Unauthenticated traffic falls back to per-IP limits.** Use the client address your own edge recorded, never one the client sent (Chapter 3).
3. **On breach, reject cleanly.** HTTP 429 with `Retry-After` and rate-limit headers, before any backend work is done.
4. **Limits are configurable per plan** (Free, Pro, Enterprise) through an admin portal. Changes apply within seconds, without a deploy.

**Out of scope, said out loud:** volumetric DDoS at the network layer (absorbed upstream by the network or CDN provider, before requests are even HTTP), the billing pipeline that charges overage, the admin UI, and cost-weighted limits (an LLM call that "costs" 500 tokens). Then add: "Tell me if you want any of those."

### What identity do you limit by?

The identity matters more than the algorithm. "100 requests per minute" means nothing until you say per what.

| Identity | Use when | Weakness |
|---|---|---|
| **API key** | Authenticated partners. The main case. | A leaked key is shared by whoever stole it. |
| **User id** | Logged-in end users of your own app | Needs auth first. One user may hold many keys. |
| **IP address** | Unauthenticated traffic, floods | Many honest users share one IP behind an office NAT or mobile carrier. Attackers rotate IPs cheaply. |
| **Account / phone number / card** | Abuse-sensitive actions (login, OTP, payments) | Only the service that understands the action knows it. |

### Per-user limits vs a global limit

These are different tools, and interviewers like to check that you know it.

| | Per-identity limit | Global limit |
|---|---|---|
| Question it answers | Is this caller taking more than its share? | Is the whole system about to be overloaded? |
| Counter key | One key per identity (`rl:{k_8f3a}:all`) | One key for everybody |
| Protects | Fairness between callers | Total capacity |
| Problem | Needs a counter per identity (small) | One counter every request touches: a hot key (Chapter 13) |

Per-identity limits are the main design here. For total capacity, prefer **load shedding** (each server rejects work when its own queue or CPU is saturated, with no shared counter) over a single global counter. Say that, and mention that a global counter is a hot key if you do build one.

### The plans as numbers

Each rule has a **sustained rate** (the long-run average) and a **burst** (how many requests may arrive at once). Chapter 8 shows why these are two separate knobs.

Assumption for this example: the plan numbers below.

| Plan | Sustained | Burst | Mode |
|---|---|---|---|
| Unauthenticated (per IP) | 30 / min (0.5 / s) | 10 | Hard |
| Free | 60 / min (1 / s) | 10 | Hard |
| Pro | 600 / min (10 / s) | 100 | Hard |
| Enterprise | 6,000 / min (100 / s) | 1,000 | **Soft** up to 2x plan, then hard |
| Write endpoints (e.g. create record) | one tenth of the plan's rate | one tenth of the plan's burst | Hard |

**Hard vs soft limits.** A **hard** limit rejects with 429. A **soft** limit lets the request through but signals it: a warning header, an overage counter for billing, an alert to the account team. "Never cut off" is a soft limit. A soft limit still needs a hard **ceiling** (here 2x plan), because the backend has a capacity even when the contract is generous.

A third option is **throttling**: delay requests in a queue instead of rejecting them. It suits background traffic that can wait. Chapter 9 shows why it is usually wrong for API callers.

### Non-functional requirements

Each one needs a number or a choice.

| Quality | The requirement | What it decides |
|---|---|---|
| **Latency** | The check adds **p99 under 5 ms**, hard ceiling 10 ms | One round trip to something in memory. Nothing on disk. |
| **Scale** | **1M requests/s** at peak across the gateway fleet (about 100K today, so design for 10x). About 50K API keys and 200 internal services. | Shared state must be sharded for throughput. |
| **Availability** | If the limiter breaks, traffic still flows (**fail-open**) with an audit trail. Security limits fail closed instead. | Timeouts, a circuit breaker, a local fallback (Chapter 14) |
| **Accuracy** | Near-exact. A small, *stated* over-admission (about 1%) is acceptable. | Which algorithm, and whether hot keys may be counted locally |
| **Config freshness** | A plan change applies within seconds | Config cached locally, pushed on change |

**Accuracy vs cost is the trade-off under the whole design.** An exact global count means every check touches one shared counter: a network round trip per request and a hot spot per busy key. An approximate count lets gateways decide locally and reconcile later: microseconds instead of milliseconds, at the price of a bounded error. Say which one each rule gets. "Login attempts: exact. Search requests: approximate, within 1%."

### Only the numbers that decide something

All of these are assumptions for this example. Measure your own.

- **Latency.** 1M checks a second with a 5 ms budget means a single round trip to something in memory. Anything disk-backed is out. That leaves Redis (or similar), or local memory.
- **Memory.** 50K keys x about 10 tracked limits each x about 100 B per counter (key, a couple of numbers, store overhead) = **50 MB**. Per-IP state for about 1M recently active IPs x 100 B = **100 MB**. It fits in one Redis node many times over. Any cluster we build is for throughput and availability, not capacity.
- **Throughput.** 1M checks a second is far beyond one Redis node (very roughly 100K simple operations a second; benchmark it). So shard by key across a cluster. Each decision touches one shard.

**The bridge sentence** to say before moving on: "So: per-key and per-endpoint limits by plan, per-IP for anonymous traffic, 429 with Retry-After on breach, soft limits with a ceiling for Enterprise. Under 5 ms at a million checks a second, failing open except for security limits. Does that match what you had in mind?"

<Reveal q="The interviewer asks: “What about DDoS?” Do you design for it?">

Say where it lives, and park it. A volumetric attack (millions of packets per second, SYN floods, reflection) is stopped at the network layer by the hosting or CDN provider, long before a request becomes HTTP. An application-layer limiter would be overwhelmed before it ran. What this design does cover is the HTTP-level version: one key or one IP sending far more valid requests than it should, which is the incident in the prologue.

Say: "Volumetric DDoS is upstream and out of scope. Per-IP limits at the edge handle the HTTP-level floods."

</Reveal>

**A common slip:** "Limit each user to 100 requests per minute." Per what identity? Over what window, with what burst? Hard or soft? Which endpoints? A limit is a sentence with five blanks, and a number alone fills only one.

<h2 id="entities-api">Chapter 2 · The contract</h2>

Look at the partner's retry code from the incident. The loop catches a timeout and retries at once. There is no backoff. There is also nothing to back off from, because the server never told the client to slow down. The client was not malicious. It was uninformed. The contract in this chapter is how you inform it.

### Core entities

Two minutes, names and relationships:

- **Plan**: Free, Pro, Enterprise.
- **ApiKey**: belongs to one plan (and a customer).
- **LimitRule**: for a plan, an endpoint pattern (or "all"), a sustained rate, a burst, a mode (hard or soft plus ceiling).
- **Bucket state**: the live counter for one key under one rule (tokens and a timestamp).

Check the cardinality of each pair. A plan has many keys and a key has one plan: one-to-many. A plan has many rules: one-to-many. A key is governed by many rules, and each rule governs many keys: many-to-many. That last relationship **carries data** (the tokens and the timestamp), so the relationship itself is an entity. **Bucket state is the join of ApiKey and LimitRule.**

    PLAN ||--o{ LIMIT_RULE : "defines"

### The config model

The config (owned by the admin portal) is tiny and read-heavy:

```sql
CREATE TABLE plans       (id INT PRIMARY KEY, name VARCHAR(32));
CREATE TABLE limit_rules (plan_id INT, endpoint VARCHAR(128), rate_per_sec DOUBLE,
                          burst INT, mode ENUM('hard','soft'), ceiling_multiplier DOUBLE,
                          PRIMARY KEY (plan_id, endpoint));
CREATE TABLE api_keys    (key_id VARCHAR(64) PRIMARY KEY, plan_id INT, customer_id BIGINT);
```

Every gateway caches all of it in memory (a few MB) and refreshes when the admin portal publishes a change, with a periodic poll as a backstop in case a message is lost. That meets the hot-reload requirement with zero network hops per request. **Counter state lives in Redis, not in the SQL database.** Chapter 12 designs its keys.

### The API

The limiter is not a public service. Its API is an internal check that the gateway calls on every request:

```text
check(identity, route, cost = 1)
  -> { allowed, remaining, limit, resetAfterSec, retryAfterSec, overage }
```

`cost` is 1 for ordinary requests. It lets the same machinery limit weighted work later (an LLM call priced in tokens). The admin side is ordinary REST: `PUT /plans/{plan}/rules/{endpoint}` with the rate, burst and mode.

### What the client sees

This is the part the partner in the prologue never got:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 10
Content-Type: application/json

{"error": "rate_limited", "message": "Pro plan: 600 requests/min. Retry after 1 s."}
```

- **429 Too Many Requests** (RFC 6585) means this client exceeded its own allowance.
- **503 Service Unavailable** is the honest status when the server itself is overloaded and is shedding load from clients that are within their limits. Overload is not the client's fault. Both may carry `Retry-After`. (gRPC's equivalent of 429 is `RESOURCE_EXHAUSTED`.) Real APIs are not uniform here, and some use 403 for rate limits, so document yours.
- **`Retry-After`** (RFC 9110) is either a whole number of seconds or an HTTP date. A token bucket's true wait might be 0.05 s. You send **1**, because you always round up.
- **`X-RateLimit-Limit / -Remaining / -Reset`** are a common convention, not a standard, and their meaning varies. Some APIs send `Reset` as a Unix timestamp (GitHub documents epoch seconds), others as seconds remaining. Pick one and document it. For a token bucket, `Remaining` is the whole tokens left, and `Reset` is the time until the bucket is full again (here 100 tokens / 10 per second = 10 s).
- **A standard is on its way.** An IETF HTTP APIs working group draft proposes `RateLimit` and `RateLimit-Policy` header fields. Its syntax has changed across versions and it was still a draft when this was written. Mention it, and check its current status before relying on it.
- **Send the headers on every response, not just on 429s.** A `Remaining: 3` on a 200 lets a good client slow down before it hits the wall.
- **A 429 from the gateway is always safe to retry**, even for a non-idempotent `POST`, because the limiter rejected it before any backend work happened. This is a property of putting the check first.
- **Soft limits** pass the request and add a warning (a custom header such as `X-RateLimit-Overage: true`) plus an overage counter that billing reads later.

### 429 vs 503 at a glance

| | 429 Too Many Requests | 503 Service Unavailable |
|---|---|---|
| Whose fault | This client went over its limit | The server is overloaded or down |
| Typical cause | Per-key or per-IP limiter | Load shedding, dependency failure |
| What the client should do | Slow down to its own allowed rate | Back off, retry later |
| Counts against the client's quota | Yes (they were over) | No |

### The client's half of the contract

A client should honour `Retry-After`, add random **jitter** (a small random delay) on top, and back off exponentially if it is rejected again. Without jitter, ten thousand rejected clients all come back in the same second and recreate the spike. A client SDK that does this by default is the cheapest rate limiter you will ever ship.

```python
import random, time
import requests

def call_with_backoff(url, max_tries=5):
    delay = 1.0
    for attempt in range(max_tries):
        resp = requests.get(url, timeout=5)
        if resp.status_code not in (429, 503):
            return resp
        if attempt == max_tries - 1:
            break                                               # out of tries: do not sleep for nothing
        wait = float(resp.headers.get("Retry-After", delay))   # server's hint wins
        time.sleep(wait + random.uniform(0, wait))              # jitter spreads the herd
        delay = min(delay * 2, 60)                              # exponential backoff
    raise RuntimeError("still rate limited after retries")
```

This sketch assumes `Retry-After` is in seconds, not an HTTP date. A production client should parse both forms.

<h2 id="placement">Chapter 3 · Where the gate stands</h2>

A limiter can sit at many points on the request path. **Each point sees different information**, and that decides what it can limit by.

A real example of getting this wrong: a limiter goes live and immediately blocks half of one city. Every request appeared to come from the same three addresses, which were the company's own load balancers. It counted perfectly. It just counted the wrong thing, in the wrong place.

<Figure caption="Every hop could host a limiter. Left of the gateway nobody knows the API key. Right of it, each service sees only its own slice of traffic.">
  <Mermaid code={`flowchart LR
    C["Client SDK\nself-throttle"] --> EDGE["Edge · CDN / WAF\nraw IP, coarse floods"]
    EDGE --> LB["Load balancer"]
    LB --> GW["API gateway\nkey, plan, route\n★ main limiter"]
    GW --> S1["Search service\nin-process middleware"]
    GW --> S2["OTP service\nper phone number"]
    S1 --> SC["Sidecar\nservice-to-service"]
    SC --> DB[("Search cluster")]`} />
</Figure>

| Where | Sees | Good for | Blind to |
|---|---|---|---|
| **Client SDK** | Only its own requests | Being polite: pacing, honouring Retry-After | Everyone else. Attackers do not use your SDK. |
| **Edge (CDN / WAF)** | Raw client IP, path, headers, before your servers | Cheap drops of per-IP floods and scrapers | The API key's plan (usually not authenticated yet) |
| **API gateway** | Authenticated key, plan, route, every endpoint | **Per-key, per-plan, per-endpoint limits**. The main case. | Business meaning inside the body (which phone number?) |
| **In-service middleware** | The business action: "send SMS to this number", "export report" | Abuse-sensitive and cost-sensitive limits | Traffic to other services |
| **Sidecar (service mesh)** | One service's inbound and outbound calls | Limits between internal services, language-agnostic | Plans and customers |
| **In front of a dependency** | Calls to one database or upstream API | Concurrency limits protecting that dependency | Who the end customer was |

**The answer is usually layered**, and saying so is the strong move:

- Per-IP flood control at the edge.
- Per-key, per-plan limits at the gateway (this design).
- Per-action limits inside the services that understand the action.
- A concurrency limit in front of fragile dependencies.

Then say which layer the question is about. <a href={`${BASE}sd/lessons/core-concepts/`}>Core concepts</a> lists "rate limiting" among the words that need a layer attached.

### The "same three addresses" bug, precisely

Behind a load balancer, the connection's source address is the load balancer. The real client address travels in `X-Forwarded-For` (or the standard `Forwarded` header), and a client can send a fake one of its own. Limit by the address **your own edge wrote** (the right-most entry that your trusted proxies added), never the left-most value a client could forge. <a href={`${BASE}sd/lessons/networking/#proxies`}>Networking</a> has the full story.

```text
X-Forwarded-For: 6.6.6.6, 203.0.113.7
                 ^ client typed this     ^ your edge appended the real peer address
Use 203.0.113.7 (when exactly one trusted proxy sits in front of you)
```

### Rate limit vs concurrency limit

| | Rate limit | Concurrency limit |
|---|---|---|
| Caps | Requests per unit time | Requests in flight right now |
| Example | 600 per minute | At most 20 running queries |
| Protects | Fairness, cost | A slow dependency (a database, an upstream API) |
| Reacts to slowness | No. Same rate even if responses take 10 s. | Yes. Slow responses fill the slots and new work is refused. |

A slow database is hurt by in-flight work, not by the rate on paper. That is why a concurrency limit belongs in front of fragile dependencies.

<Trace title="Place the gate" steps={placement} takeaway="The edge knows the IP, the gateway knows the key and plan, the service knows the business action. Limit each thing where it is visible." />

<Reveal q="Should the 200 internal services be rate-limited too?">

Yes. A retry storm from an internal service is one of the most common self-inflicted outages. The partner in the prologue could just as easily have been your own recommendations job. Give each calling service an identity (a service key, or the mesh's mTLS identity) and a limit at the gateway or sidecar, sized from its normal traffic with headroom. Pair it with **concurrency limits** in front of fragile dependencies: a rate limit caps requests per second, while a concurrency limit caps requests in flight, which is what protects a slow database.

</Reveal>

**A common slip:** "Put a rate limiter in front of the API." In front of which hop, keyed by what? An answer without a layer and an identity is two blanks short.

**One functional requirement at a time, traced out loud.** The request path, numbered:

In words:

1. A request arrives at the gateway with an API key.
2. The limiter middleware resolves the key's plan and matching rules from its in-memory config. No network hop.
3. It makes **one call to Redis**: a script that refills, checks and spends from every bucket this request touches, atomically.
4. If allowed, the gateway attaches the rate-limit headers and forwards the request.
5. If not, it returns 429 with Retry-After, and the backend never sees it.
6. If Redis does not answer within 3 ms, it fails open: allow the request and emit an audit event.

For config, the admin portal writes rules to the database and publishes a change. Gateways reload in seconds, and poll every minute in case a message is lost.

### Every box earns one sentence

- **Limiter as gateway middleware.** Limits must apply before any backend work is spent, and the gateway is where the key and plan are known.
- **Redis.** 200 gateway instances need one shared count per key, at in-memory latency.
- **SQL database.** Config is small, relational and admin-edited. It is never on the request path.
- **Audit queue.** Fail-open must never be silent (Chapter 14), and the gateway cannot wait on a database write to record it.

### Library in the gateway, or a separate rate-limit service?

| | Library inside the gateway | Separate rate-limit service |
|---|---|---|
| Network hops per check | 1 (to Redis) | 2 (to the service, then to Redis) |
| Language support | One language per library | Any gateway can call it |
| Logic changes | Redeploy gateways | Redeploy one service |
| Example | Middleware calling Redis directly | Envoy's global rate-limit service |

With a 5 ms budget, commit to the library, and say the flip condition: "If we had many gateway technologies, I would centralise it as a service and pay the extra hop."

### Worked numbers for the path

A same-datacentre round trip is about 0.5 ms (see <a href={`${BASE}sd/lessons/core-concepts/`}>Core concepts</a>). A short Redis script runs in microseconds. So a check costs roughly **0.5 to 1 ms at the median and a couple of milliseconds at p99** under load, inside the 5 ms budget (assumption: your numbers will differ, so measure). Bandwidth: a check and its reply are about 150 B, so 1M checks/s is about 150 MB/s (about 1.2 Gbit/s) spread across the whole cluster, a few MB/s per node. Say "non-issue" and move on.

<Reveal q="Why not count in each gateway’s memory and skip Redis entirely?">

Because the gateways do not share memory. With 200 instances behind a round-robin load balancer, each one would enforce the full limit on its own slice. A Pro key allowed 10/s could get up to 200 x 10 = 2,000/s. Dividing the limit by 200 breaks the other way: a client whose requests happen to bunch on a few gateways gets throttled at a fraction of its plan.

Local counting can work if the load balancer routes each key to one gateway (consistent hashing on the key), or for very hot keys with leasing (Chapter 13). But the default needs one shared count.

</Reveal>

<h2 id="fixed-window">Chapter 5 · Fixed window and the boundary burst</h2>

Take a client limited to 100 requests a minute. Look at its traffic graph: a flat line, then at exactly 11:59:59 a spike of 100 requests, and one second later at 12:00:00 a second spike of 100. That is 200 requests in about one second. The limiter's logs say the client never exceeded 100 in a minute. Both statements are true. This chapter shows how.

### What is it?

A **fixed window counter** cuts time into aligned windows (minute 11:59, minute 12:00) and keeps one counter per key per window. A request increments the counter. If it would exceed the limit, reject. When a new window starts, the counter starts at zero.

- **Memory:** one small counter per key per window (old windows simply expire).
- **Cost:** one atomic increment. In Redis it is a single `INCR` on a key that includes the window number.
- **The flaw:** the counter forgets everything at the boundary.

### The boundary burst, stated exactly

Any span of time one window long overlaps at most two aligned windows. So a fixed window admits **at most 2 x limit in any window-length span**, and it can reach that bound in two adjacent seconds. This matters because the limiter's job was to stop a spike, and the worst case is a spike.

### Implementation

First the Java version, which is compiled and tested by this lesson's checker:

```java id=fixedWindow group=limiters
import java.util.function.LongSupplier;

/** One counter per aligned window. Simple and cheap — and it admits 2 × limit across a boundary. */
static final class FixedWindowCounter {
    private final long limit;
    private final long windowNanos;
    private final LongSupplier clock;       // injected: System::nanoTime in production, a fake in tests
    private long window = Long.MIN_VALUE;   // which window `count` belongs to
    private long count;

    FixedWindowCounter(long limit, long windowNanos, LongSupplier clock) {
        if (limit < 1 || windowNanos < 1) throw new IllegalArgumentException("limit and window must be positive");
        this.limit = limit;
        this.windowNanos = windowNanos;
        this.clock = clock;
    }

    synchronized boolean tryAcquire() {
        long w = Math.floorDiv(clock.getAsLong(), windowNanos);
        if (w != window) { window = w; count = 0; }   // a new window: forget everything
        if (count >= limit) return false;
        count++;
        return true;
    }
}
```

Every limiter in this lesson takes its **clock as a parameter** (`LongSupplier`): `System::nanoTime` in production, a hand-moved fake in tests. That is how the checker asserts exact behaviour at boundaries (100 admitted at 59 s, 100 more at 60 s) instead of sleeping and hoping. `synchronized` makes each check-and-increment one atomic step per limiter. Chapter 11 is the distributed version of the same problem.

In a real distributed system the counter lives in Redis, shared by all gateways. The Python version:

```python
import time
import redis

r = redis.Redis(socket_timeout=0.003)   # 3 ms: a slow limiter must not slow the API

def allow_fixed_window(identity: str, limit: int, window_s: int) -> bool:
    window = int(time.time() // window_s)            # which window are we in
    key = f"rl:{{{identity}}}:w:{window}"            # window number is part of the key
    pipe = r.pipeline(transaction=True)              # MULTI ... EXEC: both commands run together
    pipe.incr(key)
    pipe.expire(key, window_s * 2)                   # old windows clean themselves up
    count, _ = pipe.execute()
    return count <= limit                            # decide AFTER the atomic increment
```

The Redis commands behind it:

```text
MULTI
INCR   rl:{k42}:w:29437891
EXPIRE rl:{k42}:w:29437891 120
EXEC
```

Three details matter:

- **Decide after incrementing.** `INCR` returns the new value atomically, so two gateways can never both see "99". One of them gets 100, the other 101.
- **The window number is in the key**, so a missed `EXPIRE` leaks a little memory. It cannot block a customer forever (Chapter 11 shows the bad version).
- **`time.time()` here is the gateway's clock.** If two gateways disagree by a second, they disagree on which window it is. For a rough quota that is fine. For tighter limits, take the time from Redis (Chapter 12).

### When should I use it?

Rough internal quotas ("about 1,000 exports an hour per team"), daily caps, and anything where a 2x edge burst hurts nobody. It is one Redis command and a few bytes. Picking it deliberately ("the boundary burst is fine for a daily quota") is a better answer than reaching for a fancier algorithm by reflex.

**Interview takeaway:** "A fixed window is one INCR and a few bytes, but it resets at the boundary, so it can let through twice the limit in a second. I would use it for rough quotas, not for spike protection."

<h2 id="sliding-log">Chapter 6 · Sliding window log</h2>

The first fix for the boundary burst, and the one every careful engineer reaches for, is: do not count per window. Remember when each request happened, and at any moment count the ones in the last sixty seconds. It is exact. The question is what it costs for a Pro key at full speed.

### What is it?

A **sliding window log** keeps the timestamp of every admitted request. To check a new request at time `now`: drop timestamps at or before `now - window`, count what remains, and admit if the count is below the limit.

<Figure caption="Limit 3 per second. The window is always the last second before now. At 1.0 s the three entries from 0.0 s have slid out, so three more are admitted. At 0.999 s they were still inside.">
  <Mermaid code={`flowchart LR
    A["t=0.0 s\n3 requests logged"] --> B["t=0.999 s\nlog still has 3\nreject"]
    B --> C["t=1.0 s\nentries from 0.0 s evicted\nlog has 0\nadmit up to 3"]`} />
</Figure>

### Why does it work?

Whenever the log admits a request at time `s`, at most `limit - 1` earlier admissions are in `(s - W, s]`. For any later moment `t >= s`, the span `(t - W, s]` sits inside `(s - W, s]`. So no window-length span ever holds more than `limit` admissions. It is **exact, with no boundary**. At 12:00:00 it still sees the 100 requests from 11:59:59 and admits nothing.

### What does it cost?

Memory proportional to the limit. Assumption for this example: Pro keys allow 600 a minute, 50,000 keys are at full use, and each entry in a Redis sorted set takes about 100 B (measure with `MEMORY USAGE`).

```text
50,000 keys x 600 timestamps x 100 B = 3 GB
50,000 keys x 1 counter      x 100 B = 5 MB
```

That is **600 times more memory** for the same promise, plus a sorted-set write and trim on every request.

### Implementation

```java id=slidingLog group=limiters
/** Exact: remembers the time of every admitted request in the last window. Memory grows with the limit. */
static final class SlidingWindowLog {
    private final int limit;
    private final long windowNanos;
    private final LongSupplier clock;                              // must be monotonic (System::nanoTime)
    private final ArrayDeque<Long> admitted = new ArrayDeque<>();  // timestamps, oldest first

    SlidingWindowLog(int limit, long windowNanos, LongSupplier clock) {
        if (limit < 1 || windowNanos < 1) throw new IllegalArgumentException("limit and window must be positive");
        this.limit = limit;
        this.windowNanos = windowNanos;
        this.clock = clock;
    }

    synchronized boolean tryAcquire() {
        long now = clock.getAsLong();
        // Evict everything that has slid out: keep only timestamps in (now - window, now].
        while (!admitted.isEmpty() && now - admitted.peekFirst() >= windowNanos) admitted.pollFirst();
        if (admitted.size() >= limit) return false;
        admitted.addLast(now);
        return true;
    }
}
```

Comparing `now - t >= window` rather than `t <= now - window` is deliberate. `System.nanoTime` values can be any number, including negative, and differences are the overflow-safe way to compare them.

In Redis the log is a sorted set per key, scored by timestamp, run inside a Lua script so the steps are atomic. The Python caller:

```python
SLIDING_LOG_LUA = """
local now    = tonumber(ARGV[1])      -- ms
local window = tonumber(ARGV[2])      -- ms
local limit  = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now - window)  -- drop everything <= now - window
if redis.call('ZCARD', KEYS[1]) >= limit then return 0 end
redis.call('ZADD', KEYS[1], now, ARGV[4])                      -- ARGV[4]: unique member
redis.call('PEXPIRE', KEYS[1], window)
return 1
"""
sliding_log = r.register_script(SLIDING_LOG_LUA)   # uses `r` and `time` from above; also needs `import uuid`

def allow_log(identity, limit, window_ms):
    now = int(time.time() * 1000)
    member = f"{now}-{uuid.uuid4().hex[:8]}"     # members must be unique
    return sliding_log(keys=[f"rl:{{{identity}}}:log"], args=[now, window_ms, limit, member]) == 1
```

The trap: **sorted-set members are unique.** Two requests in the same millisecond with `member = now` collapse into one entry, and the second is never counted. So the member is the timestamp plus a request id. This version takes `now` from the caller for brevity. Chapter 12 explains why the script should use Redis's own clock.

**A design choice to say out loud.** This version logs only *admitted* requests. Some implementations log every attempt, so a client that keeps hammering stays blocked until it stops. That is stricter, and the log then grows with abuse instead of with the limit. Either is defensible. Choose one.

### When should I use it?

Low limits that must be exact and auditable: "5 password attempts per account per 15 minutes", "3 payouts per day". Small limits mean small logs, and exactness is the requirement. For a Pro API key doing 600 a minute, it is too expensive.

**Interview takeaway:** "A sliding log is exact because it remembers every request time, but memory grows with the limit, 600 times a counter for a 600-per-minute key. I would use it for small, strict limits like login attempts."

<h2 id="sliding-counter">Chapter 7 · Sliding window counter</h2>

The log is exact but expensive. A cheaper idea: keep only the counts of the previous window and the current window, and guess how many of last window's requests are still inside the sliding minute. What would you guess if you only kept the count?

### What is it?

A **sliding window counter** keeps two counters per key: the previous window's count and the current window's count. It estimates the sliding window by assuming the previous window's requests were **spread evenly**, and counts the fraction of that window that the sliding window still overlaps:

```text
estimate = previous x (W - elapsed) / W + current          admit while estimate < limit
```

### Worked numbers at the boundary

After 100 requests at 11:59:59:

- At 12:00:00 the estimate is 100 x 60/60 + 0 = 100. Nothing passes.
- At 12:00:01 it is 100 x 59/60, about 98.3, so **two** requests fit (98.3 + 1 = 99.3 is under 100, 98.3 + 2 = 100.3 is not).

The fixed window let 100 through in that second. The sliding counter lets 2. **The boundary spike is gone.**

### The error, honestly

The estimate is exact when the previous window's traffic was evenly spread. If it was not, the error at `elapsed` seconds into the window is bounded by the previous count times the misjudged fraction:

- The true count can be **higher by at most previous x elapsed / W** (previous traffic bunched at its end).
- It can be **lower by at most previous x (W - elapsed) / W** (previous traffic bunched at its start).

Right after a boundary the possible over-count is near zero, which is why there is no spike. In a pathological pattern (the previous window's 100 requests all in its last instant, then the current window's traffic spread evenly) the true trailing-minute count can creep toward 2 x limit near the end of the window. It can never arrive as a burst. The checker for this page constructs exactly that case. On real traffic the approximation is very close: Cloudflare described running this scheme across their network and reported a very small error rate (see Beyond this page).

### Implementation

```java id=slidingCounter group=limiters
/** Two counters per key. Estimates the sliding window by weighting the previous window by its overlap. */
static final class SlidingWindowCounter {
    private final long limit;
    private final long windowNanos;
    private final LongSupplier clock;
    private long window = Long.MIN_VALUE;   // index of the current aligned window
    private long current;                   // admitted in the current window
    private long previous;                  // admitted in the window before it

    SlidingWindowCounter(long limit, long windowNanos, LongSupplier clock) {
        if (limit < 1 || windowNanos < 1) throw new IllegalArgumentException("limit and window must be positive");
        Math.multiplyExact(2 * limit, windowNanos);   // the integer comparison below must not overflow
        this.limit = limit;
        this.windowNanos = windowNanos;
        this.clock = clock;
    }

    synchronized boolean tryAcquire() {
        long now = clock.getAsLong();
        long w = Math.floorDiv(now, windowNanos);
        if (w != window) {
            previous = (w == window + 1) ? current : 0;   // skipped a whole window? nothing recent remains
            current = 0;
            window = w;
        }
        long into = now - w * windowNanos;               // 0 .. windowNanos - 1
        // estimate = previous × (W − into) / W + current; admit while estimate < limit.
        // Multiplied through by W so the arithmetic stays exact in integers.
        if (previous * (windowNanos - into) + current * windowNanos >= limit * windowNanos) return false;
        current++;
        return true;
    }
}
```

Two details the checker pins down:

- **Multiplying through by W** keeps the comparison exact. There are no floating-point "99.99999 &lt; 100" surprises at the boundary.
- **A skipped window resets `previous` to zero.** If the key was idle for a whole minute, the minute before that is not "previous".

In Redis this is two keys (or one hash) with `INCR` on the current one, plus a read of the previous one. Because it reads then decides, run it inside a script, or accept that two gateways can briefly both admit near the limit.

| | Fixed window | Sliding window counter |
|---|---|---|
| State per key | 1 counter | 2 counters |
| 100 at 11:59:59 then 12:00:00 | 200 pass | 100 pass, then about 2 in the next second |
| Accuracy | Approximate (up to 2x at the boundary) | Close, with a bounded error |
| Redis ops | One INCR | A read plus an INCR (script it) |

<h2 id="token-bucket">Chapter 8 · Token bucket</h2>

Here is a customer complaint that windows handle badly. A mobile app opens and fires twelve requests at once (profile, feed, settings, badges), then nothing for a minute. Under a strict "1 per second" limit, eleven of the twelve fail on every app launch. The customer is not abusing anything. They are just bursty. Can a limit be generous for a moment and strict over time?

### What is it?

A **token bucket** gives each key a bucket that holds at most **B tokens** (the burst). Tokens drip in at **r per second** (the sustained rate). A request takes one token. With no token, it is rejected. A full bucket stops filling.

<Figure caption="Two knobs, set independently: capacity is how big a burst may be, refill rate is the long-run average. Over any span of T seconds, at most B + r·T requests pass.">
  <Mermaid code={`flowchart LR
    R["Refill\n10 tokens / s"] -->|"drip"| B[("Bucket\nat most 100 tokens")]
    Q["Request"] --> D{"At least\none token?"}
    B -.-> D
    D -->|"yes"| A["Take one\nserve + headers"]
    D -->|"no"| X["429\nRetry-After"]`} />
</Figure>

For the bursty mobile customer: B = 20, r = 1/s. The twelve-request launch passes. A client sending steadily faster than 1/s still drains the bucket and gets throttled. **Over any span of T seconds, at most B + r·T requests pass**: a burst, then the rate.

Play with it. Spend the burst, then watch the refill hold the client to its rate.

<TokenBucketSim mode="bucket" capacity={10} refill={5} rate={3} burst={15} />

### How does it work? Lazy refill, no timer thread

You never run a job that adds tokens. Store two numbers per bucket: `tokens` and `lastRefill`. On each request, compute what the elapsed time earned:

```text
tokens = min(B, tokens + (now - lastRefill) x r)        then spend one if tokens >= 1
```

**Worked numbers.** The Pro bucket (B = 100, r = 10/s) holds 3 tokens at 12.40 s. The next request arrives at 12.85 s. Refill: 3 + 0.45 x 10 = 7.5. Spend one: **6.5**. Memory is two numbers per key regardless of traffic, so the 50 MB estimate from Chapter 1 holds at any request rate.

**The headers fall out of the state:**

- `Remaining` = whole tokens left.
- `Retry-After` = time until one token exists = (1 - tokens) / r, rounded up to a whole second.
- `Reset` = time until the bucket is full = (B - tokens) / r.

### Implementation: Java (compiled and tested)

```java id=tokenBucket group=limiters
/** Holds up to `capacity` tokens and earns one every `periodNanos`. A request spends one token. */
static final class TokenBucket {
    private final long capacity;
    private final long periodNanos;   // 1 / refill rate: 100 ms means 10 tokens per second
    private final LongSupplier clock;
    private long tokens;
    private long lastRefill;          // time up to which refill has been credited

    TokenBucket(long capacity, long periodNanos, LongSupplier clock) {
        if (capacity < 1 || periodNanos < 1) throw new IllegalArgumentException("capacity and period must be positive");
        this.capacity = capacity;
        this.periodNanos = periodNanos;
        this.clock = clock;
        this.tokens = capacity;                // a new client starts full and may burst
        this.lastRefill = clock.getAsLong();
    }

    synchronized boolean tryAcquire() {
        refill(clock.getAsLong());
        if (tokens == 0) return false;
        tokens--;
        return true;
    }

    /** Tokens left right now: the X-RateLimit-Remaining value. */
    synchronized long available() {
        refill(clock.getAsLong());
        return tokens;
    }

    /** How long until one token exists: the Retry-After value (round up to whole seconds for HTTP). */
    synchronized long nanosUntilNextToken() {
        long now = clock.getAsLong();
        refill(now);
        return tokens > 0 ? 0 : periodNanos - (now - lastRefill);
    }

    // Lazy refill: no timer thread. Credit the whole tokens earned since lastRefill, and keep the
    // partial progress towards the next one by advancing lastRefill only by whole periods.
    private void refill(long now) {
        if (tokens == capacity) {                          // full: idle time is not banked
            lastRefill = Math.max(lastRefill, now);
            return;
        }
        long elapsed = now - lastRefill;
        if (elapsed < periodNanos) return;                 // not one whole token yet (or the clock went backwards)
        long earned = elapsed / periodNanos;
        if (earned >= capacity - tokens) {                 // full: time beyond that is not banked
            tokens = capacity;
            lastRefill = now;
        } else {
            tokens += earned;
            lastRefill += earned * periodNanos;
        }
    }
}
```

**Why it works, and what stays true.** The bucket's real level is always `tokens` whole tokens plus a partial token worth `(now - lastRefill) / period`, capped at the capacity. The Java keeps whole tokens in a `long` so every decision is exact, and keeps the partial token in the *timestamp*. Two consequences the checker tests:

- **Full means full.** While the bucket is full, time passing earns nothing, so `lastRefill` follows `now`. Without that line, a bucket that sat full for 8 seconds and then spent one token would "remember" those 8 seconds and hand back the next token early. (An earlier draft of this lesson had exactly that bug, and random tests against an independent model caught it.)
- **A clock that steps backwards earns nothing** (`elapsed < period` returns early). Use `System.nanoTime`, which is monotonic. Wall-clock time (`System.currentTimeMillis`) can jump backwards when NTP corrects it.

### Implementation: Python (single process)

The same idea in Python, with a float level. Simpler to read, and fine for one process:

```python
import threading, time

class TokenBucket:
    def __init__(self, capacity: float, refill_per_sec: float):
        self.capacity, self.rate = capacity, refill_per_sec
        self.tokens, self.last = capacity, time.monotonic()   # monotonic: immune to wall-clock jumps
        self.lock = threading.Lock()

    def try_acquire(self, cost: float = 1.0) -> bool:
        with self.lock:                                       # check-then-spend must be one step
            now = time.monotonic()
            self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
            self.last = now
            if self.tokens < cost:
                return False
            self.tokens -= cost
            return True
```

Floats accumulate tiny rounding errors. That is acceptable here. The Java version and the Redis script in Chapter 11 keep integers to avoid it. This class protects only one process. Across many gateways you need the shared version in Chapter 11.

### A bug worth recognising

This shape shows up in code reviews and looks harmless:

```java fragment
long earned = (now - lastRefill) / periodNanos;   // whole tokens only
tokens = Math.min(capacity, tokens + earned);
lastRefill = now;                                  // BUG: throws away the partial token every call
```

A client polling every 90 ms against a 100 ms refill earns 0 whole tokens per call, and `lastRefill = now` erases the 90 ms of progress each time. The bucket **never refills while the client keeps polling**. The checker runs exactly this: over 9 seconds of 90 ms retries, the buggy bucket admits 0 and the correct one admits 90 (9 s x 10/s). The fix is to advance `lastRefill` by whole periods (as above) or to store the level at a finer grain (the Redis script in Chapter 11 keeps credit in milliseconds).

### Many keys in one process

A map from key to bucket, created exactly once:

```java id=keyed group=limiters
/** One bucket per key, created exactly once even when the first requests for a key race. */
static final class KeyedLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final Function<String, TokenBucket> newBucket;

    KeyedLimiter(Function<String, TokenBucket> newBucket) { this.newBucket = newBucket; }

    boolean tryAcquire(String key) {
        return buckets.computeIfAbsent(key, newBucket).tryAcquire();   // atomic create-if-missing
    }

    int trackedKeys() { return buckets.size(); }
}
```

`computeIfAbsent` is the whole point. The tempting `if (!map.containsKey(k)) map.put(k, new TokenBucket(...))` lets two threads each create a bucket for a brand-new key, and each bucket hands out a full burst. That is double the limit on exactly the first, busiest second. The checker hammers 50 new keys from 12 threads and asserts one bucket and exactly 20 admissions per key. In production, also **evict idle buckets** (a cache with expire-after-access, such as Caffeine) or the map grows with every IP that ever visited.

### Trade-offs and when to use it

- Pros: constant state per key, a configurable burst, lazy refill, and the headers are easy to compute.
- Cons: two knobs to explain and tune. A new key starts full, so a fresh client may burst immediately.
- Use it for public APIs with bursty clients. It is the usual answer.

**Interview takeaway:** "Token bucket: capacity is the burst, refill rate is the average. Over T seconds at most B plus r times T requests pass. State is two numbers, refill is computed lazily on each request."

<h2 id="leaky-gcra">Chapter 9 · Leaky bucket and GCRA</h2>

The token bucket has a twin. Telecom engineers built it to police ATM cells. It stores one number instead of two, and it never refills anything. First, a naming problem.

### The leaky bucket has two meanings. Say which one you mean.

- **As a queue (a traffic shaper).** Requests pour into a bucket that holds at most B. They leak out to the backend at a constant rate r. A full bucket rejects. The output is perfectly smooth, and every queued request **waits**. A full queue of 100 draining at 10/s makes the newest request wait **10 seconds**. This is right for outgoing calls to a strict third party (a payment provider that rejects anything over 50/s) or background jobs. It is usually wrong for an API caller, who would rather get a fast 429 than a slow answer. NGINX's `limit_req` is documented as this kind of leaky bucket, with a `burst` queue and a `nodelay` option.
- **As a meter.** Do not queue. Just check whether this request would overflow a bucket that leaks at rate r, and reject if so. That is the token bucket seen from the other side: water level instead of tokens remaining.

<Figure caption="Same name, two machines. The queue spends latency to smooth output. The meter rejects instead, and is equivalent to a token bucket.">
  <Mermaid code={`flowchart LR
    subgraph SHAPER["Leaky bucket as a queue"]
      direction LR
      I1["Requests"] --> Q1[["Queue ≤ 100"]] -->|"exactly 10 / s"| O1["Backend"]
    end
    subgraph METER["Leaky bucket as a meter = token bucket"]
      direction LR
      I2["Request"] --> M2{"Would it\noverflow?"}
      M2 -->|"no"| O2["Serve now"]
      M2 -->|"yes"| X2["429"]
    end`} />

|---|---|---|---|
| Over the limit | Reject | Wait in queue (reject only when full) | Reject |
| Bursts | Allowed up to B | Smoothed out | Allowed up to B |
| Added latency | None | Up to B / r | None |
| Good for | API limits | Outgoing calls to a strict third party | Same as token bucket |

### GCRA: the meter with the cleverest bookkeeping

**GCRA (generic cell rate algorithm)** stores one time instead of tokens and a timestamp: **TAT**, the theoretical arrival time at which the client is exactly back on schedule. Let **T** = 1 / r (the time one request "costs") and **tau = (B - 1) x T** (how far ahead of schedule a client may run: the burst, expressed as time).

```text
on request at now:
    if TAT - now > tau:  reject            (Retry-After = TAT - tau - now)
    else:                TAT = max(TAT, now) + T;  allow
```

### Why it is the token bucket in disguise

At any moment the bucket holds `B - (TAT - now) / T` tokens (or B, if TAT is in the past). "At least one token" means `B - (TAT - now) / T >= 1`, which rearranges to `TAT - now <= (B - 1) x T = tau`. That is exactly GCRA's test.

**Worked numbers.** After the request in the figure, TAT = 12.6 s. If the stored TAT were 22.0 s at 12.0 s, the client would be 10.0 s ahead, more than tau = 9.9 s. Rejected, with Retry-After 0.1 s. And indeed 100 - 10.0 / 0.1 = 0 tokens. The checker does not take this on faith: it drives the token bucket, GCRA and an independent continuous-bucket model with thousands of random request sequences and asserts they make **the same decision, and report the same wait, every time**.

### Implementation

```java id=gcra group=limiters
/** GCRA: the same limiter as TokenBucket, stored as a single number — the theoretical arrival time. */
static final class Gcra {
    private final long periodNanos;      // T: the time one request "costs" (1 / rate)
    private final long toleranceNanos;   // τ = (burst − 1) × T: how far ahead of schedule a client may run
    private final LongSupplier clock;
    private long tat;                    // theoretical arrival time: when the client is back on schedule

    Gcra(long burst, long periodNanos, LongSupplier clock) {
        if (burst < 1 || periodNanos < 1) throw new IllegalArgumentException("burst and period must be positive");
        this.periodNanos = periodNanos;
        this.toleranceNanos = Math.multiplyExact(burst - 1, periodNanos);
        this.clock = clock;
        this.tat = clock.getAsLong();    // on schedule: the full burst is available
    }

    synchronized boolean tryAcquire() {
        long now = clock.getAsLong();
        if (tat - now > toleranceNanos) return false;     // too far ahead of schedule
        tat = Math.max(tat, now) + periodNanos;           // book this request's slot
        return true;
    }

    /** Retry-After: how long until the request would conform. */
    synchronized long nanosUntilAllowed() {
        return Math.max(0, tat - toleranceNanos - clock.getAsLong());
    }
}
```

### One number means lock-free is easy

The whole state fits in an `AtomicLong`, so a compare-and-set loop replaces the lock:

```java id=atomicGcra group=limiters
/** GCRA's whole state is one long, so it can be lock-free: compare-and-set the TAT, retry on a race. */
static final class AtomicGcra {
    private final long periodNanos;
    private final long toleranceNanos;
    private final LongSupplier clock;
    private final AtomicLong tat;

    AtomicGcra(long burst, long periodNanos, LongSupplier clock) {
        if (burst < 1 || periodNanos < 1) throw new IllegalArgumentException("burst and period must be positive");
        this.periodNanos = periodNanos;
        this.toleranceNanos = Math.multiplyExact(burst - 1, periodNanos);
        this.clock = clock;
        this.tat = new AtomicLong(clock.getAsLong());
    }

    boolean tryAcquire() {
        while (true) {
            long now = clock.getAsLong();
            long current = tat.get();
            if (current - now > toleranceNanos) return false;
            long next = Math.max(current, now) + periodNanos;
            if (tat.compareAndSet(current, next)) return true;   // lost a race? re-read and decide again
        }
    }
}
```

A retry loop is fine *inside one process*, where a lost race costs nanoseconds. The same idea across the network (read, compute, compare-and-set in Redis, retry on conflict) costs a round trip per retry, which is why Chapter 11 uses a script instead. The checker runs 16 threads against every limiter in this lesson with a frozen clock and asserts **exactly** the limit is admitted, not one more. With a moving clock it asserts the B + r·T bound.

### When should I use it?

- GCRA: when you want the token bucket's behaviour with the least state, or a lock-free or single-key design. The `redis-cell` module implements it as a single command.
- Leaky bucket as a queue: shaping outgoing traffic, or background jobs that can wait.
- Neither is needed if a plain token bucket is already clear to your team.

<h2 id="races">Chapter 11 · Two gateways, one token</h2>

A real failure pattern: a limiter reads the counter from Redis, decides in the gateway, and writes the new value back. In testing, with one gateway, it is perfect. In production, with forty gateways, a customer limited to 100 a minute is measured at 140. Every line of code is correct. The lines just run on different machines at the same time.

### The race: read-then-write from many machines

Two gateways serve the same key in the same millisecond:

<Figure caption="Both gateways read 99, both admit, both write 100. One increment is lost and 101 requests got through. At 1M checks a second this is not rare. It is constant.">
  <Mermaid code={`sequenceDiagram
    participant A as Gateway A
    participant R as Redis
    participant B as Gateway B
    A->>R: GET rl:k42 → 99
    B->>R: GET rl:k42 → 99
    Note over A,B: both see room under 100
    A->>R: SET rl:k42 100
    B->>R: SET rl:k42 100
    Note over A,B: 101 admitted, counter says 100`} />

Redis executes each command atomically, but **a sequence of commands from different clients interleaves**. Single-threaded execution gives you atomic commands and atomic scripts. It does not give you atomic conversations. There are three fixes, in increasing power, and some options to avoid.

### Fix 1: one atomic command

For a fixed window, `INCR` returns the new count atomically, so decide after incrementing: allow if the result is at most the limit. The key needs an expiry so old windows disappear, and that is a second command, which brings its own race:

```text
INCR   rl:{k42}:m:29437891          -> 101      (the window number is in the key)
EXPIRE rl:{k42}:m:29437891 120
```

If the gateway dies between the two, the key never expires.

- **With the window number in the key**, that leaks a little memory.
- **With a key that has no window in its name** (`rl:k42`, "reset by the TTL"), it is far worse. The count never resets, and once it passes the limit **that customer is blocked forever**.

Make the pair atomic. Options: wrap them in `MULTI`/`EXEC` (no decision is needed between them, so a transaction suffices), use a tiny script (`INCR`, then `EXPIRE` only when the result is 1), or on Redis 7 and later use `EXPIRE ... NX`, which sets a TTL only if the key has none.

### Fix 2: a Lua script for anything that decides

A token bucket must read, compute the refill, decide and write. Redis runs a Lua script **to completion before executing any other command**, so the whole read-refill-decide-write is atomic and costs **one round trip**.

```lua
-- Token bucket, atomic. KEYS[1] = bucket key
-- ARGV[1] = capacity (tokens), ARGV[2] = refill period (ms per token), ARGV[3] = cost (tokens)
local capacity = tonumber(ARGV[1])
local period   = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local full     = capacity * period       -- credit is kept in milliseconds: one token = `period` ms

local t   = redis.call('TIME')           -- the server's clock, one per key: { seconds, microseconds }
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local s      = redis.call('HMGET', KEYS[1], 'credit', 'ts')
local credit = tonumber(s[1]) or full    -- a missing key is a full bucket
local ts     = tonumber(s[2]) or now

if now > ts then                         -- lazy refill; a clock that stepped back earns nothing
  credit = math.min(full, credit + (now - ts))
  ts = now
end

local allowed, retry_ms = 0, 0
if credit >= cost * period then
  credit = credit - cost * period
  allowed = 1
else
  retry_ms = cost * period - credit      -- time until enough credit exists
end

redis.call('HSET', KEYS[1], 'credit', credit, 'ts', ts)
redis.call('PEXPIRE', KEYS[1], full - credit + 1000)   -- refilled to full = same as no key; let it go
return { allowed, math.floor(credit / period), retry_ms }
```

How to read it:

- The bucket's level is kept as **milliseconds of credit**. One token is `period` ms. Pro is 100 ms per token with capacity 100, so a full bucket is 10,000 ms.
- Every number stays a whole number, so there is no floating-point drift in the comparison, and the refill is simply "add the elapsed milliseconds".
- It returns `allowed`, the whole tokens remaining (for `X-RateLimit-Remaining`), and the milliseconds until enough credit exists (round up to seconds for `Retry-After`).
- `cost` must not exceed `capacity`, or the request can never pass. Validate it in config.
- Load the script once and call it by its hash with `EVALSHA`. Redis 7 also offers named Functions for the same purpose.
- Calling `TIME` inside a script that then writes is allowed on Redis 5 and later, which replicate a script's effects rather than re-running it.

This script was run for this lesson in a Lua VM against a mock Redis and an independent model of the bucket, over 3,000 random sequences including clock steps backwards, and matched on every decision, remaining count and retry time. It was also run against a live Redis 7.4 and behaved the same (a full bucket of 5 admitted 5 calls, then refused with a retry time). Treat it as the starting point for your own integration test.

Calling it from Python with `redis-py`:

```python
import math
import redis

r = redis.Redis(host="redis", socket_timeout=0.003, socket_connect_timeout=0.003)
token_bucket = r.register_script(TOKEN_BUCKET_LUA)   # SCRIPT LOAD once, then EVALSHA on each call

def check(identity: str, capacity: int, period_ms: int, cost: int = 1):
    key = f"rl:{{{identity}}}:all"                    # braces = hash tag (Chapter 12)
    allowed, remaining, retry_ms = token_bucket(keys=[key], args=[capacity, period_ms, cost])
    return {
        "allowed": allowed == 1,
        "remaining": remaining,
        "retry_after_s": math.ceil(retry_ms / 1000),  # always round UP for Retry-After
    }
```

`register_script` returns a callable that sends `EVALSHA`. If the server answers `NOSCRIPT` (it has not seen the script yet, for example after a restart), the client loads the script with `SCRIPT LOAD` and retries `EVALSHA`.

From the result, the gateway builds the response:

```python
def headers_for(result, limit, capacity, period_ms):
    h = {"X-RateLimit-Limit": str(limit), "X-RateLimit-Remaining": str(result["remaining"])}
    if not result["allowed"]:
        h["Retry-After"] = str(max(1, result["retry_after_s"]))
    return h
```

### Several limits, one call

A request usually touches two buckets: the key's overall plan limit and the endpoint's limit. Pass both keys to one script, check both, and spend from both **only if both allow**. Otherwise a request rejected by the endpoint limit would still burn a token from the plan limit. One script, one round trip, all-or-nothing. In Redis Cluster that requires both keys in the same slot (Chapter 12).

### Fix 3: what not to reach for

| Option | Why not here |
|---|---|
| **Distributed lock (e.g. Redlock)** around read-modify-write | Two extra round trips per request, plus a new failure mode when a lock holder stalls |
| **WATCH / MULTI / EXEC with retry** (optimistic) | Correct, but hot keys conflict constantly, and retries make the tail latency unbounded, exactly when traffic peaks |
| **SQL row with `SELECT ... FOR UPDATE`** | Disk-backed, lock-heavy, and nowhere near a million checks a second |

<Trace title="Lose no updates" steps={races} takeaway="Each Redis command is atomic. Sequences are not. INCR for counting, MULTI or EXPIRE NX for the TTL, a Lua script for anything that decides." />

<Reveal q="Redis is single-threaded. So how can there be a race at all?">

Each *command* runs alone, so a single `INCR` can never lose an update. But "GET, compute in the gateway, SET" is three separate steps, and Redis happily runs another client's commands between them. The fix is to move the whole decision into one command: `INCR` when counting is enough, a script when the logic needs to read before it writes.

</Reveal>

<h2 id="keys">Chapter 12 · Names, slots and clocks</h2>

Counters need the same discipline as any cache entry: a key shape, an expiry and a failure plan. A limiter adds one more question: whose clock?

### Key shape

Namespace, identity, rule, and (for windowed algorithms) the window number:

```text
rl:{k_8f3a}:all                       token bucket: key k_8f3a, overall plan limit
rl:{k_8f3a}:ep:search                 token bucket: same key, search endpoint
rl:{ip:203.0.113.7}:anon              per-IP bucket for unauthenticated traffic
rl:{k_8f3a}:all:m:29437891            fixed window: minute number = floor(unix seconds / 60)
```

A design doc might write the pattern as `rl:{tenant}:{user}:{window}`, with braces meaning "fill this in". **In Redis Cluster, braces are not decoration.** The text inside the first `{...}` is the **hash tag**, as long as it is not empty (with `{}` the whole key is hashed). Only that part is hashed (CRC16, modulo 16,384 slots). So:

- `rl:{k_8f3a}:all` and `rl:{k_8f3a}:ep:search` share a slot. That is what lets one atomic script check both. Cluster rejects a script whose keys live in different slots.
- `rl:{tenant42}:{user7}:...` hashes only `tenant42`. Every user of that tenant lands in **one slot** (slot 14,826), and a big tenant becomes a hot shard. Put the tag on exactly what must be co-located (one key's or one user's limits) so different keys still spread across the cluster.

### TTL, and why that number

For a token bucket: **the time to refill completely, plus a little slack.** Once the bucket would be full again, the stored state says exactly what a missing key says ("full"). So expiring it loses nothing, and it garbage-collects every IP that visited once. The script sets it on every call.

A TTL that is too short is a bug. A key that expires while the bucket is half empty is read as full and hands out free tokens.

| Algorithm | TTL |
|---|---|
| Token bucket | Time to refill completely, plus slack |
| Fixed window | Window length, plus slack |
| Sliding log | Window length |

### Memory, measured

About 100 B per small hash in Redis is the planning number used throughout this lesson (two fields plus per-key overhead). Confirm with `MEMORY USAGE` on a real key before you size a cluster on it.

### Whose clock? Clock skew

If each gateway computes the refill with its own clock, the elapsed time between two requests served by different gateways includes their **clock skew** (the difference between their clocks). Gateways with clocks 50 ms apart, on a key refilling at 1,000 tokens a second, can mint **up to 50 free tokens** each time the key's traffic moves to the gateway whose clock runs ahead. A gateway whose clock runs behind earns nothing, thanks to the `now > ts` guard in the script.

**Use the Redis server's clock inside the script** (`redis.call('TIME')`). Then each key is measured by one clock: the primary that owns its slot. After a failover the new primary's clock may differ slightly. The guard makes a backwards step cost a moment of refill rather than mint tokens.

| | Gateway clock | Redis `TIME` inside the script |
|---|---|---|
| Who measures elapsed time | Whichever gateway served the request | The one primary that owns the key |
| Skew between measurements | Up to the gateway skew (NTP keeps it small but not zero) | None for a given key |
| Cost | Free | None extra, it is inside the same script |

<h2 id="hybrid">Chapter 13 · The hot key</h2>

A load test at the design target shows twenty-nine of thirty Redis primaries idling at two-thirds of their planned load. One is pinned at 100%. The cause is one internal service calling the API under a single service key at 200,000 requests a second. Sharding does not help, because a key is a key. It lives in one place.

### Worked numbers first

Assumptions: the design target is 1M checks a second, and a Redis primary handles about **50,000 script calls a second**. That is a deliberately conservative planning number, since a short script does several operations and simple `GET`s run faster. Benchmark it.

Run primaries at about 70% so a failover or a burst has room: 1,000,000 / (50,000 x 0.7) = about 29, so **about 30 primaries**, each with a replica. (At today's 100K: 100,000 / 35,000 = about 3 primaries.) Capacity needed one node. Throughput and availability needed thirty. That is the sentence.

Now the hot key: 200,000 checks a second on one key, which lives on one shard that tops out near 50,000. The key alone needs four shards' worth of throughput, and **no amount of sharding splits one key**. It is the same concentration problem as a hot cache key. The fix is to stop sending every request for that key to Redis.

| Approach | How | Redis calls for the 200K/s key | Error |
|---|---|---|---|
| **Per-request script** (the default) | Every check is one script call | 200,000 / s. **Impossible on one shard.** | None |
| **Local counting, periodic sync** | Each gateway admits locally from the last global value it saw. Every 100 ms it pushes its count and reads the global one. | 200 gateways x 10 syncs = 2,000 / s | **Over-admits** up to one sync interval of traffic: 200,000 x 0.1 s = **20,000** requests when the bucket runs dry |
| **Token leasing** | Each gateway takes tokens from the global bucket in batches of 100 (one script call granting what is available) and spends them locally | 200,000 / 100 = **2,000 / s** | **Never over-admits.** Up to 200 x 100 = 20,000 leased tokens can sit unused on gateways, so the key may see a few early 429s right at its limit |
| **Sticky routing** | The load balancer sends each key to one gateway (consistent hashing). Count in memory there. | 0 | Exact-ish, but the hot key now overloads *one gateway*, and resizing the fleet resets buckets |

### Lease vs sync: the difference that matters

| | Token leasing | Local counting with sync |
|---|---|---|
| Who spends first | Redis (tokens are taken before use) | The gateway (counts after the fact) |
| Failure direction | Under-admit: stranded tokens, early 429s | Over-admit: up to one sync interval |
| Safe for money or security limits | Yes | No |
| Complexity | Lease sizing, returning unused tokens | Sync schedule, merge logic |

### The leasing script

It is the Chapter 11 script with one change: when `cost` tokens are not all available, grant the whole tokens that are, and return how many.

```lua
-- same TIME / HMGET / lazy-refill code as the token-bucket script, then:
local want  = tonumber(ARGV[3])
local avail = math.floor(credit / period)
local grant = math.min(want, avail)         -- partial grant instead of reject
credit = credit - grant * period
redis.call('HSET', KEYS[1], 'credit', credit, 'ts', ts)
redis.call('PEXPIRE', KEYS[1], full - credit + 1000)
return { grant, math.floor(credit / period) }
```

The gateway spends the grant locally and asks again when it runs out. If a gateway dies holding a lease, those tokens are lost until the bucket refills, which is why the batch stays small relative to the limit.

**Commit:** "Per-request scripts for the long tail of keys. Each gateway counts requests per key locally, and a key above about 500 requests a second on one gateway switches to leasing, with the batch size shrinking as the global bucket runs low so fewer tokens are stranded. That takes the 200K key from 200,000 Redis calls a second to 2,000, never over-admits, and costs at most 20,000 stranded tokens. That is 0.08 s of that key's 250K/s limit."

**A common slip:** committing to the sync-and-reconcile version and calling the error "a few hundred requests". The arithmetic says otherwise. When the bucket runs dry, nobody knows until the next sync, so **a whole interval of traffic** gets through: 20,000 for this key. That can still be acceptable (a tenth of a second of this key's traffic), but say the real number. Leasing moves the error to the safe side.

<h2 id="failure">Chapter 14 · When Redis is down</h2>

Imagine a bad config push restarts the limiter's Redis cluster, and for four minutes every rate-limit check times out. What should happen? In a good design, nobody outside notices. The gateways keep serving, a dashboard line labelled FAIL-OPEN lights up, and the audit queue records every unlimited request. The login service, on purpose, stops letting people try passwords.

### Fail open or fail closed depends on what the limiter protects

It depends on consequences, not taste:

| The limiter protects... | Example | When the store is down | Why |
|---|---|---|---|
| **Capacity and fairness** | Per-key API limits | **Fail open**, to a coarse local limit, with a loud alert | Blocking every paying customer because a protection layer died is worse than briefly over-serving |
| **Security** | Password attempts, OTP verification | **Fail closed**, or to a strict local limit | Failing open means unlimited guessing for as long as the outage lasts |
| **Money** | Sending SMS, calls to a paid upstream API | **Fail closed** (or a strict local cap) | Each request costs real money. SMS pumping fraud exploits exactly this. |

### Fail open, done properly

1. **A tight timeout.** The Redis call gets 3 ms. Beyond that the answer is too late to be useful.
2. **A circuit breaker.** Without one, *every* request waits the full 3 ms for a dead Redis, which eats most of the 5 ms budget. The breaker opens after repeated failures, skips Redis entirely, and lets a trickle of probe calls test for recovery.
3. **A coarse local fallback, not "unlimited".** Each gateway keeps an in-memory bucket per key at, say, ten times its fair share. A Pro key's 10/s divided by 200 gateways, times 10, is 0.5/s per gateway, or 100/s across the fleet. Honest clients rarely notice uneven load balancing with 10x headroom. A retry storm like the one in the prologue (40,000/s) is cut to 100/s: **400 times less**.
4. **A per-gateway load-shedding limit that never depends on Redis**, protecting the backends no matter what the per-key layer is doing.
5. **Never silent.** Every fail-open decision emits an audit event (asynchronously, through the queue), and the fail-open rate is the **top alert on the limiter's dashboard**. A silent fail-open is "no limits, and nobody knows".

<Figure caption="The check path with its failure plan. The breaker turns a dead store into a fast local decision instead of a 3 ms wait on every request.">
  <Mermaid code={`flowchart LR
    REQ["Request"] --> BR{"Breaker\nclosed?"}
    BR -->|"yes"| RS["Redis script\n3 ms timeout"]
    RS -->|"answer"| DEC["Allow / 429"]
    RS -->|"timeout or error"| FB["Local fallback bucket\n10× fair share"]
    BR -->|"open"| FB
    FB --> DEC
    FB -.-> AUD["Audit event\n+ fail-open alert"]`} />
</Figure>

A sketch in Python. It is deliberately small and not production-ready: the breaker is not thread-safe, and the local buckets need eviction.

```python
import time, redis

class Breaker:
    def __init__(self, threshold=5, cooldown_s=5.0):
        self.threshold, self.cooldown = threshold, cooldown_s
        self.failures, self.opened_at = 0, None
    def can_call(self):
        if self.opened_at is None:
            return True
        return time.monotonic() - self.opened_at >= self.cooldown   # half-open: let a probe through
    def record(self, ok):
        if ok:
            self.failures, self.opened_at = 0, None
        else:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = time.monotonic()

breaker = Breaker()
local_buckets = {}                                   # identity -> TokenBucket (Chapter 8 class)

def check_with_fallback(identity, capacity, period_ms, fail_closed=False):
    if breaker.can_call():
        try:
            result = check(identity, capacity, period_ms)       # the Redis script (Chapter 11)
            breaker.record(True)
            return result
        except (redis.exceptions.TimeoutError, redis.exceptions.ConnectionError):
            breaker.record(False)
    if fail_closed:                                              # login, OTP, SMS
        return {"allowed": False, "remaining": 0, "retry_after_s": 5}
    bucket = local_buckets.setdefault(identity, TokenBucket(capacity * 10 / 200, 1000 / period_ms * 10 / 200))   # 10x fair share (Pro: 0.5/s)
    emit_fail_open_audit(identity)                               # never silent
    return {"allowed": bucket.try_acquire(), "remaining": -1, "retry_after_s": 1}
```

### What happens when Redis comes back?

Replication is asynchronous, so a failover can lose the latest writes. Some buckets go back to an older, fuller state, and a key with no stored state reads as a *full* bucket. Expect a brief over-admission after a failover or a cold restart, and say so: "At most about one burst per key, which is inside our stated accuracy."

<h2 id="regions">Chapter 15 · Many regions</h2>

An Enterprise contract says 6,000 requests a minute, not 6,000 per region. So which region holds the count? A cross-region round trip costs **tens of milliseconds to well over a hundred**, so no request can wait on another region within a 5 ms budget. Every option counts locally. They differ in how regions learn about each other.

| Option | How | Cost | Error |
|---|---|---|---|
| **One global counter** in one region | Every region calls it | A cross-region round trip per request. That region becomes everyone's dependency. | None, and unusable here |
| **Static split** | 6,000 / 3 = 2,000 per region | Nothing | **Unfair when traffic is uneven.** A customer with 90% of traffic in the EU wants 5,400/min there and is throttled at 2,000 while paying for 6,000. |
| **Weighted split, rebalanced** | Shares follow each region's recent traffic, recomputed every few seconds | A small background sync | Briefly unfair after a sudden shift |
| **Local buckets + async sync** | Each region enforces the global limit using its own count plus the others' counts as of the last sync | A background sync every second | **Over-admits** by at most (regions - 1) x (burst + rate x lag): 2 x (1,000 + 100 x 1) = **2,200** extra requests, once, for an Enterprise key |

Where the bound comes from: each region sees its own spending exactly, so what it cannot see is the other regions' spending during the last sync lag. No region can spend more than its burst plus rate x lag in that time. (This bound is an illustrative derivation for the example numbers, not a universal guarantee.)

    end

<h2 id="wrap-up">Chapter 16 · The last three minutes</h2>

A senior reviewer reads a design doc from the bottom up, because the last section tells them whether the author has ever been paged. Close with these five things:

1. **Recap against the contract.** "Per-key, per-endpoint and per-IP limits by plan. 429 with Retry-After and headers. Soft limits with a ceiling for Enterprise. One Redis script per check, about a millisecond. Fail open to a local limit for API limits, fail closed for security limits."
2. **Bottleneck at 10x the design (10M checks a second).** Redis throughput, first: more primaries (about 300 at our planning number) and a lower threshold for switching keys to leasing, so fewer checks reach Redis at all. Config is already local and does not move. Gateway CPU next.
3. **Failure modes.** Redis down: fail open (or closed) as above, with the breaker. A failover: brief over-admission, about one burst per key. A bad config push (a plan set to 0): every customer rejected, so config changes are validated, staged, and can be rolled back in one click.
4. **Monitor.** Fail-open events (the top alert), Redis p99 and error rate, 429 rate per plan and per endpoint (a product signal as much as an ops one: a plan whose customers hit 429 constantly may be mispriced), the hottest keys, and leasing activity.
5. **What I would build next.** Per-customer overrides on top of plan defaults, a gradual throttling tier before the hard 429 (warn, then slow, then reject), anomaly detection on per-IP fallback traffic, and cost-weighted limits for expensive calls (an LLM request priced in tokens: the same bucket, a different currency).

**The one-breath version:** "At 10x the bottleneck is Redis ops per second, so more primaries and more keys on local leases. I would want the fail-open alert, Redis p99, and 429s per plan on a dashboard before launch."

### How would you debug "I am being rate limited and I should not be"?

A common production follow-up. Work from the response to the state:

1. **Read the 429.** Which limit fired (plan or endpoint)? What did `Limit`, `Remaining` and `Reset` say?
2. **Identify the identity the limiter used.** Was it the API key, or an IP that is really a shared NAT or a load balancer address? The wrong IP source is the most common cause.
3. **Inspect the bucket.** `HGETALL rl:{k_8f3a}:all` (credit and ts) and `PTTL` show the live state and the TTL.
4. **Check the rule.** Did a recent config push change the rate, burst or mode for this plan?
5. **Check the clients.** Is the customer retrying without backoff, so their own retries keep the bucket empty?
6. **Check the dashboard.** Is the 429 rate up for everyone (a bad rule or fallback) or for one key (that customer)?

<h2 id="walkthrough">Chapter 17 · The full round, out loud</h2>

A 45-minute round, compressed to its spoken lines. Read it aloud once, then try it cold. The times are checkpoints, not a script to memorise.

**0:03 · Roadmap and requirements**

> **Say:** "Here is how I would like to use our time: about six minutes on requirements and scale, a couple on the core entities and the API, a simple design that works, then two or three deep dives on the hardest parts, and a short wrap-up. Would you like capacity estimates up front, or as they become relevant?"
>
> "First, which layer? A gateway limiter for API customers, or a limit inside one service?" (Suppose the answer is: the gateway.)
>

Over the limit we return 429 with Retry-After and rate-limit headers, before any backend work. Plan limits are configurable and apply within seconds. Enterprise gets a soft limit: overage passes, is flagged and billed, up to a hard ceiling at 2x. Out of scope: volumetric DDoS, which the network provider absorbs before it is HTTP; billing; the admin UI. Tell me if you want any of those."

**0:06 · Non-functionals with numbers**

> **Say:** "The check is on every request, so it must add under 5 ms at p99. Design for a million requests a second at peak across the gateway fleet, ten times today, with about 50,000 API keys and 200 internal services. If the limiter fails, API traffic keeps flowing: fail open, loudly. But security limits like login attempts fail closed. Accuracy: near-exact. I will accept about 1% over-admission and say where it comes from."
>
> "Two numbers decide things. A million checks a second under 5 ms means one round trip to something in memory. And memory is small: 50,000 keys times about ten limits times 100 bytes is 50 MB, plus 100 MB for active IPs. So any cluster we build is for throughput and availability, not capacity."

**0:08 · The bridge**

> **Say:** "So: per-key, per-endpoint and per-IP limits by plan, 429s with Retry-After, soft limits with a ceiling, under 5 ms at a million checks a second, failing open except for security limits. Does that match?"

**0:09 · Core entities**

> **Say:** "Plan; ApiKey, many keys per plan; LimitRule, a plan has many, each with an endpoint, a rate, a burst and a mode. The live state is a bucket per key per rule. Keys and rules are many-to-many, and the relationship carries data, tokens and a timestamp, so bucket state is its own entity. Config lives in the SQL database; bucket state in Redis."

**0:11 · API**

> **Say:** "Internally, the gateway calls check with the identity, the route and a cost, normally 1, and gets back allowed, remaining, reset and retry-after. Externally: on every response, X-RateLimit-Limit, Remaining and Reset. On rejection, 429 with Retry-After in whole seconds, rounded up. 503, not 429, if we are shedding load from clients within their limits. A 429 is always safe to retry, even for a POST, because nothing ran. Admin side: PUT a rule per plan and endpoint."

**0:15 · High-level design**

> **Say:** "The limiter lives in the API gateway, as middleware, because that is where the key and plan are known and it runs before any backend work. Edge per-IP limits handle floods earlier. Services keep their own business limits, like SMS per phone number. I will focus on the gateway."
>
> "A request arrives. The middleware resolves the plan and rules from config cached in memory, so zero hops. One Redis script call checks and spends from the key's buckets atomically. Allowed: forward with headers. Rejected: 429. Redis slower than 3 ms: fail open and emit an audit event. Config: the admin portal writes the database and publishes a change. Gateways reload in seconds, with a poll as backstop. A check costs about a millisecond: one same-datacentre round trip."

**0:25 · Deep dive 1: the algorithm**

> **Say:** "The hard part is how we count. Fixed window is one INCR but lets 2x the limit through at a boundary: 100 at 11:59:59 and 100 at 12:00:00. A sliding log is exact but stores every timestamp: 600 per Pro key, 3 GB instead of 5 MB. A sliding counter fixes the boundary with two numbers and a small error. I will take a token bucket: constant state per key, so the 50 MB holds; burst size becomes a product setting per plan instead of an accident; and the refill is computed lazily from a timestamp, so no background jobs. For login attempts I would use a sliding log: small, exact, auditable."

**0:31 · Deep dive 2: correctness across 200 gateways**

> **Say:** "If gateways read the bucket, decide, and write it back, two of them can both spend the last token: a lost update. So the whole refill-check-spend runs as one Lua script in Redis. Redis runs a script to completion, so it is atomic, in one round trip. The script uses Redis's own clock, so gateway clock skew cannot mint tokens. Keys look like `rl:{k_8f3a}:all` and `rl:{k_8f3a}:ep:search`. The hash tag keeps one key's buckets in one slot, so one script checks both and spends only if both allow. Each key's TTL is its time to refill completely. After that, a missing key means a full bucket anyway."
>
> "Throughput: at a conservative 50,000 script calls a second per primary and 70% utilisation, a million checks needs about 30 primaries, each with a replica. One problem sharding cannot fix: a single internal key at 200,000 a second lives on one shard. For hot keys, gateways lease tokens in batches of 100: 2,000 Redis calls a second instead of 200,000, and never over the limit."

**0:35 · Deep dive 3: failure**

> **Say:** "When Redis is down, what we do depends on what the limiter protects. API limits fail open to a local per-gateway bucket at ten times each gateway's fair share, so a runaway client is still cut 400-fold. That sits behind a circuit breaker so a dead Redis does not add 3 ms to every request, and fail-open is the top alert. Login and SMS limits fail closed. After a failover we can briefly over-admit, about one burst per key."

**0:38 · Wrap-up**

> **Say:** "To recap: every limit we listed is enforced at the gateway in about a millisecond, with clean 429s. At 10x, Redis ops per second is the first bottleneck: more primaries and more keys on leases. I would monitor fail-open events first, then Redis p99, 429s per plan, and the hottest keys. Next I would build per-customer overrides, a warn-then-slow tier before hard rejection, and cost-weighted limits for expensive calls."

**Check the numbers yourself:** 50,000 x 10 x 100 B = 50 MB. 1,000,000 x 100 B = 100 MB. 50,000 x 600 x 100 B = 3 GB vs 50,000 x 100 B = 5 MB (600x). 1,000,000 / (50,000 x 0.7) = about 28.6, so about 30 primaries. 200,000 / 100 = 2,000 lease calls a second. 40,000 / (0.5 x 200) = 400. Pro bucket: 3 + 0.45 x 10 - 1 = 6.5.

### Five follow-ups you will get

<Reveal q="1 · What is the boundary problem with fixed windows, and how do the others avoid it?">

A fixed window resets at the boundary, so 100 requests at 11:59:59 and 100 at 12:00:00 both pass a 100-per-minute limit: 2x in about a second. A sliding log has no boundary. It counts the actual last 60 seconds, at the cost of a timestamp per request. A sliding counter weights the previous window by its overlap, so right after the boundary the previous minute still counts almost fully. A token bucket never had windows: at most B at once, then r per second.

</Reveal>

<Reveal q="2 · Two gateways check the same bucket at the same time. What goes wrong, and what is your fix?">

Read-decide-write from two machines is a lost update: both read one token, both admit, both write zero. Each Redis command is atomic but the sequence is not. I run refill, check and spend as one Lua script, which Redis executes to completion before any other command, in one round trip. For a plain fixed window, `INCR` alone is enough, with the expiry made atomic too (`MULTI`, a script, or `EXPIRE NX`). Not a distributed lock (extra round trips) and not optimistic retries (unbounded tail latency on hot keys).

</Reveal>

<Reveal q="3 · Redis is down. What happens?">

It depends on what the limiter protects. API capacity limits fail open: a circuit breaker stops waiting on Redis, each gateway falls back to a local bucket at about ten times its fair share so a runaway client is still stopped, every fail-open decision is audited, and fail-open is the top alert. Login and SMS limits fail closed or to a strict local cap, because there the limiter is the protection. After recovery, expect a brief over-admission, since failover loses recent writes and a missing key reads as a full bucket.

</Reveal>

<Reveal q="4 · One key sends 200,000 requests a second. What breaks, and what do you do?">

The key lives on one Redis shard, which handles roughly 50,000 script calls a second, so it saturates and more shards do not help. I count that key locally: each gateway leases tokens in batches of 100, so Redis sees 2,000 calls a second instead of 200,000 and the global bucket can never be overdrawn. The cost is up to 20,000 stranded tokens near the limit. Gateways detect hot keys with local counters and switch them to leasing automatically.

</Reveal>

<Reveal q="5 · How do you enforce one limit across three regions?">

Not with a cross-region call, which is tens to hundreds of milliseconds per check. Most customers are served from one region anyway, so I split each limit across regions by recent traffic share and rebalance every few seconds. If a contract needs one exact global number, each region counts locally and syncs counts asynchronously every second. The worst case is (regions - 1) x (burst + rate x lag) extra, which is 2,200 for an Enterprise key in this example, and I would state that bound.

</Reveal>

### Common mistakes

1. **"Limit to 100 per minute."** Per what identity, which window and burst, hard or soft, which endpoints?
2. **The fixed-window boundary, unmentioned.** Name it before the interviewer does: 2x in a second.
3. **"Redis is atomic."** Commands are. GET-then-SET is not. Use one script.
4. **"Add shards" for a hot key.** One key lives on one shard. Count it locally.
5. **"Fail open," full stop.** To what local limit, for which limits, and which alert fires?
6. **Trusting the client's IP header.** Use the address your own edge wrote.
7. **Using gateway clocks for the refill.** Skew becomes free tokens. Use Redis `TIME`.

**Look these up yourself**

- **Concurrency limiters vs rate limiters** — capping requests in flight rather than per second; why a slow dependency needs the former.
- **Adaptive concurrency limits** (e.g. Netflix's concurrency-limits library) — letting a service find its own limit from latency instead of a hand-set number.
- **Heavy-hitter detection** (count-min sketch, the space-saving algorithm) — finding hot keys in a stream with tiny memory, for the switch-to-leasing threshold.
- **redis-cell** — a Redis module that implements GCRA as a single command; compare it with a Lua script.
- **Cost-weighted limits** — charging an LLM call by tokens, or a search by its fan-out, from the same bucket.
- **Fair queuing (deficit round robin, weighted fair queuing)** — sharing a queue fairly between tenants when you must queue rather than reject.
- **CRDT counters (G-counter, PN-counter)** — the data structure behind conflict-free cross-region count merging.
- **SMS pumping fraud** — why OTP endpoints are a money limit, not just an abuse limit.
