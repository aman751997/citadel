<h2 id="prologue">Prologue · One query, fifty gigabytes</h2>

Imagine a marketplace with 50 million listings. Search ships on a Tuesday, implemented as `WHERE title ILIKE '%lamp%'` against Postgres. By evening the primary database sits at 100% CPU, and the slowest queries are all that one statement, each a sequential scan.

Support tickets arrive too: "I searched lamp and got a clamp." "I searched lamps and my own Brass Lamp is missing." "Why is the first result a bottle of lamp oil?" The query is both slow and wrong, for related reasons.

The fix is the same idea as the index at the back of a book. Nobody reads the whole book to find "lamp". You look "lamp" up and read the page numbers. A search engine does that for every word in every document.

Search appears in interviews in two ways. As a **box inside a bigger design** ("users can search posts / products / messages"), and as **the whole question** (Typeahead, Twitter search). Both reward one habit: knowing that search is a separate, derived system, and saying what that costs.

**Common slips.** Skipping the lag: the index trails the database by a second or two, and you should say so before the interviewer finds it. And conflating **search** with **typeahead**: they sound like one feature and are two different systems. This lesson keeps them apart.

**A search box in your design is five sentences:**

1. **Where the index lives.** A search engine fed from the database. Never `LIKE`, and never the source of truth.
2. **How text becomes terms, and how matches are ranked.** The analyzer, then BM25 plus whatever business signals the product wants.
3. **How the index stays in sync, and how stale it may be.** Change data capture, ordering, the refresh interval, a rebuild story.
4. **What one query costs.** Shards, replicas, the fan-out, and the slow tail it creates.
5. **Typeahead is its own system.** Precomputed suggestions per prefix, in memory, near the user.

<h2 id="like-scan">Chapter 1 · Why LIKE fails, and the search-vs-database call</h2>

**What is it?** A **B-tree index** keeps keys sorted by the whole string, starting from the first character. That makes two kinds of question cheap: an exact match, and a **prefix**. "Everything that starts with `lamp`" is one contiguous run of the sorted order, from `lamp` up to just before `lamq`. The database seeks to the start and reads until the run ends.

**Why does LIKE fail?** A **leading wildcard** destroys that. `'%lamp%'` can match at any position, so matches are scattered all over the sorted order and there is no place to start. The database reads every row.

<Figure caption="The same seven titles in B-tree order. Highlighted cells match '%lamp%': scattered, so the only plan is to read everything. 'lamp%' is one contiguous run the index can seek to.">
  <ArrayStrip name="sorted titles" indices={false} values={['brass lamp', 'clamp', 'desk', 'lamp', 'lamp oil', 'lampshade', 'oak table']} tones={{ 0: 'hot', 1: 'hot', 3: 'hot', 4: 'hot', 5: 'hot' }} regions={[{ from: 3, to: 5, label: 'lamp% — one seek', tone: 'green' }]} />
</Figure>

**The numbers.** Assumptions for this example: 50 million listings, about 1 KB of title and description each, 2,000 searches per second at peak.

- One scan reads 50M × 1 KB = **50 GB**. At an optimistic 2 GB/s that is **25 seconds** for one query.
- At peak the scan approach needs 50 GB × 2,000 = **100 TB per second**. No machine does that, and read replicas only divide an impossible number by a small one.

**The scan is also bad at its job.** The support complaints are quality failures, not speed failures:

| Failure | Why `LIKE` does it | What a search engine does instead |
|---|---|---|
| "lamp" finds "clamp" and "lampshade" | Substring match ignores word boundaries | Matches whole terms |
| "lamps" misses "Brass Lamp" | No stemming (and plain `LIKE` can be case-sensitive) | Lowercases and stems both to the term `lamp` |
| Lamp oil ranks first | `LIKE` is yes/no; there is no ranking | Scores each match (Chapter 3) |
| "brass desk lamp" needs three `LIKE`s | No notion of words or phrases | Multi-term and phrase queries over one index |

**The search-vs-database decision.** You do not always need a separate cluster. Both databases you already use have built-in text search:

```sql
-- MySQL 8 (InnoDB FULLTEXT): a real inverted index inside the table
ALTER TABLE listings ADD FULLTEXT INDEX ft_title (title, description);

SELECT id, title,
       MATCH(title, description) AGAINST ('brass lamp' IN NATURAL LANGUAGE MODE) AS score
FROM listings
WHERE MATCH(title, description) AGAINST ('brass lamp' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT 20;
```

```sql
-- Postgres: tsvector + GIN, ranked with ts_rank
SELECT id, title, ts_rank(tsv, q) AS rank
FROM listings, websearch_to_tsquery('english', 'brass lamp') q
WHERE tsv @@ q
ORDER BY rank DESC LIMIT 20;
```

Both are legitimate first answers: one system, transactionally consistent, no sync pipeline. Know their limits, since this is the question an interviewer asks next. For MySQL `FULLTEXT`: no leading wildcard (`*lamp` is not supported, `lamp*` is), no stemming, a minimum token length (`innodb_ft_min_token_size`, 3 by default), limited ranking control. For Postgres `pg_trgm`, trigram indexes can serve `LIKE '%lamp%'` and similarity, and `tsvector` gives stemming, but tuning relevance is clumsy.

| Question | Database text search is enough | Move to a search engine |
|---|---|---|
| Catalogue size and query rate | Up to a few million rows, modest QPS | Tens of millions of documents, or search load that should stay off the primary |
| Ranking | "Roughly relevant" is fine | You must tune it: field boosts, recency, popularity, learning to rank |
| Typo tolerance, synonyms, facets, highlighting | Not needed | Needed, over big result sets |
| Consistency | Search must see a commit instantly | A second or two of lag is acceptable |
| Operations | One system to run | You can run a cluster and a sync pipeline |

**A common slip.** "I'd add an index on the text column." Name which index. A B-tree cannot serve a leading wildcard. A MySQL FULLTEXT or Postgres GIN/trigram index can. A dedicated engine (Elasticsearch, OpenSearch, Solr, all built on Apache Lucene) is the answer at scale.

**Interview takeaway.** "A leading-wildcard LIKE cannot use a B-tree, so it scans every row: 50 GB per query here. For a small catalogue I would use Postgres full-text or MySQL FULLTEXT. At this scale, with relevance tuning and facets, I move to a search engine fed from the database."

<h2 id="inverted-index">Chapter 2 · The inverted index and analysis</h2>

**What is it?** A **forward index** maps document → words. That is what a table already is. An **inverted index** maps word → documents, like the index at the back of a book:

```text
term     → postings list (doc id : position)
brass    → d1:1, d2:1
lamp     → d1:2, d2:2, d3:2
```

To answer "brass lamp" you read no documents at all. You look up two short lists and combine them.

**Step one: analysis, deciding what a "word" is.** Before indexing, each text field goes through an **analyzer**:

1. **Character filters** clean the raw text (strip HTML, map `&` to `and`).
2. A **tokenizer** splits it into tokens and records each token's **position**.
3. **Token filters** normalise tokens: **lowercase**; drop **stop words** ("the", "for"); **stem** ("lamps" → "lamp", "running" → "run"); optionally add **synonyms** ("sofa" ↔ "couch").

<Figure caption="One listing through the analyzer. Positions survive the stop-word filter, which is why 'desk' is at position 5, not 3.">
  <Mermaid code={`flowchart LR
    R["Two brass lamps\nfor the desk"] --> T["tokenize\nTwo·brass·lamps·for·the·desk\n0 · 1 · 2 · 3 · 4 · 5"]
    T --> L["lowercase\ntwo·brass·lamps·for·the·desk"]
    L --> S["stop words\ntwo·brass·lamps·desk"]
    S --> ST["stem\ntwo@0 brass@1 lamp@2 desk@5"]`} />
</Figure>

You can watch this happen. In Elasticsearch 8.x/9.x with the Python client (`elasticsearch-py` 8.x):

```python
from elasticsearch import Elasticsearch
es = Elasticsearch("http://localhost:9200")

res = es.indices.analyze(analyzer="english", text="Two brass lamps for the desk")
print([(t["token"], t["position"]) for t in res["tokens"]])
# [('two', 0), ('brass', 1), ('lamp', 2), ('desk', 5)]
```

**The rule that makes it work: the same analyzer runs at index time and at query time.** The shopper's "Lamps" is lowercased and stemmed to `lamp` exactly like the listing, so they meet. Stems need not be real words: an aggressive stemmer such as Porter turns "vintage" into `vintag`, and nobody cares, because the query becomes `vintag` too. (The tables below use a light stemmer that only strips plurals.)

Stop words are a choice, not a law. Many modern setups keep them: BM25 (next chapter) already gives a word that appears everywhere almost no weight, and "to be or not to be" is nothing *but* stop words.

**Two field types you will meet at once.** The difference matters constantly:

| | `text` field | `keyword` field |
|---|---|---|
| Analysed? | Yes: tokenised, lowercased, stemmed | No: stored as one exact term |
| Query means | "Which documents are about this?" (scored) | "Is it exactly this value?" |
| Use for | title, description, free text | SKU, status, seller_id, category slug, anything you filter, sort or aggregate on |

A mapping that combines them (common: one `text` field plus an exact `keyword` sub-field):

```python
es.indices.create(index="listings_v1", mappings={"properties": {
    "title":      {"type": "text", "analyzer": "english",
                   "fields": {"raw": {"type": "keyword"}}},
    "description":{"type": "text", "analyzer": "english"},
    "listing_id": {"type": "keyword"},
    "sku":        {"type": "keyword"},
    "seller_id":  {"type": "keyword"},
    "price":      {"type": "scaled_float", "scaling_factor": 100},
    "in_stock":   {"type": "boolean"},
    "created_at": {"type": "date"},
}})
```

**Step two: the worked example.** Three listings, analysed as above:

| Doc | Text | Terms with positions |
|---|---|---|
| d1 | Vintage Brass Lamp | vintage@0, brass@1, lamp@2 |
| d2 | Two brass lamps for the desk | two@0, brass@1, lamp@2, desk@5 |
| d3 | Oak desk lamp, vintage | oak@0, desk@1, lamp@2, vintage@3 |

Inverting gives the index: terms sorted, each postings list sorted by document id.

| Term | Postings (doc:position) |
|---|---|
| brass | d1:1, d2:1 |
| desk | d2:5, d3:1 |
| lamp | d1:2, d2:2, d3:2 |
| oak | d3:0 |
| two | d2:0 |
| vintage | d1:0, d3:3 |

- **"brass lamp" (AND)**: intersect `{d1, d2}` with `{d1, d2, d3}` → **d1, d2**. Both lists are sorted by doc id, so intersection is one merge walk, the <a href={`${BASE}dsa/lessons/two-pointers/`}>two-pointer</a> pattern. Real engines add skip pointers to jump over long runs.
- **"desk lamp" (AND)** → **d2, d3**. **"desk lamp" as a phrase** → only **d3**, because it needs `lamp` at desk's position + 1. d2 has both words in the wrong order. Positions make phrase queries possible without opening a single document.

```python
# phrase query: terms adjacent and in order
es.search(index="listings", query={"match_phrase": {"title": "desk lamp"}})
```

<Trace title="Build and query the index" steps={analysis} takeaway="Analysis decides what a term is; the same analyzer runs on the query. AND is an intersection of sorted lists; a phrase also checks positions." />

**What else lives in the index.** In Lucene-based engines a **term dictionary** (with a compact in-memory term index, a finite-state transducer in Lucene) finds a term's postings fast. Postings are **delta-encoded and compressed**, because sorted doc ids have small gaps. A **column store** (*doc values*) holds per-document values for sorting, filtering and facets (Chapter 11). The original JSON is usually stored too, so results can be shown without a trip to the database.

**The price is paid on writes.** Indexing a document means analysing it and adding it to a postings list for every distinct term. That is far more work than inserting a row. Search buys read speed with index-write cost: the same trade as any database index, only bigger.

**How big is the index?** Assumptions: 50 million listings; about 150 indexed terms each after analysis; about 2 bytes per term occurrence in compressed postings; stored JSON compressing to about 1 KB each; about 80 bytes of doc values per listing.

| Piece | Arithmetic | Size |
|---|---|---|
| Postings | 50M × 150 × 2 B | 15 GB |
| Stored source | 50M × 1 KB | 50 GB |
| Doc values | 50M × 80 B | 4 GB |
| **One copy of the index** | | **≈ 70 GB** |

That number drives Part Two. In real life, **measure it**: index a sample of a million documents, look at the size on disk, and multiply. Positions, extra sub-fields and especially n-grams (Chapter 9) can each add a lot.

<Reveal q="Why keep positions at all, if they make the index bigger?">

Without positions you can answer "contains both words" but not "contains this phrase", and you cannot rank documents higher when the query words appear close together. Positions also feed highlighting. If a field never needs phrase queries or proximity (tags, category, SKU), index it without positions or as a single `keyword` and save the space.

</Reveal>

**Interview takeaway.** "The index maps each term to a sorted postings list with positions. The same analyzer runs at query time. AND intersects the lists; a phrase also checks positions."

<h2 id="relevance">Chapter 3 · Ranking: BM25, signals, freshness</h2>

**What is it?** Finding matches is half of search. **Ranking** them is the half users notice. Say the index works, "brass lamp" returns four thousand listings in 11 ms, and the first is a doorknob whose description says "lamp" forty-one times. Something must decide what makes one match better than another.

**Three intuitions build the standard answer:**

1. **Term frequency (TF).** A listing that mentions "lamp" several times is probably more about lamps than one that mentions it once, but with sharply diminishing returns.
2. **Inverse document frequency (IDF).** Rare words are more informative. Matching "brass" says more than matching "lamp", and matching "the" says almost nothing. Classic form: idf = ln(N / df), where N is the number of documents and df the number containing the term.
3. **Length normalisation.** One mention in a five-word title is stronger evidence than one in a two-thousand-word description.

**IDF with real numbers.** One million listings:

| Term | Listings containing it (df) | idf ≈ ln(N / df) |
|---|---|---|
| brass | 5,000 | ln(200) ≈ 5.30 |
| lamp | 20,000 | ln(50) ≈ 3.91 |
| the | 900,000 | ln(1.11) ≈ 0.11 |

**TF-IDF vs BM25.** **TF-IDF** multiplies the first two ideas, so a term repeated 100 times scores about 100 times higher: keyword stuffing wins. **BM25** (from the Okapi system) is the refinement and the **default similarity in Lucene-based engines** (check your version's docs). It makes TF **saturate** and adds length normalisation. For each query term it multiplies a smoothed idf by:

```text
tf part = tf × (k1 + 1) / (tf + k1 × (1 − b + b × docLength / avgDocLength))
defaults: k1 = 1.2 (how fast TF saturates), b = 0.75 (how much length matters)
```

You need the two behaviours, not the formula:

| Situation (k1 = 1.2, b = 0.75) | TF part |
|---|---|
| tf = 1, average length | 1.00 |
| tf = 2, average length | 1.38 |
| tf = 10, average length | 1.96 |
| tf = 100, average length | 2.17 (ceiling is k1 + 1 = 2.2) |
| tf = 1, half the average length | 1.26 |
| tf = 1, twice the average length | 0.71 |

Saturation means the doorknob's forty-one "lamp"s buy almost nothing over two or three. Length normalisation means its long, stuffed description counts against it. (Some implementations drop the constant `k1 + 1` numerator. Rankings are unchanged.)

**A tiny worked example.** Use the three listings from Chapter 2 and the query "brass lamp". Lengths after analysis: d1 = 3 terms, d2 = 4, d3 = 4, so the average is 3.67. N = 3, df(brass) = 2, df(lamp) = 3. With Lucene's smoothed idf, ln(1 + (N − df + 0.5) / (df + 0.5)):

- idf(brass) = ln(1 + 1.5/2.5) ≈ **0.47**. idf(lamp) = ln(1 + 0.5/3.5) ≈ **0.13**. "lamp" is in every document, so it barely separates anything.
- Both docs have tf = 1 for both terms. d1 is shorter: tf part ≈ **1.08**. d2 is longer: tf part ≈ **0.96**.
- d1 ≈ (0.47 + 0.13) × 1.08 ≈ **0.65**. d2 ≈ 0.60 × 0.96 ≈ **0.58**. d3 has no "brass", so it only gets the small "lamp" part and ranks last.

The numbers are illustrative; real engines compute these per shard and store lengths in a lossy one-byte form. The shape is the lesson.

**Field boosts.** A title match usually matters more than a description match. Query both and weight them:

```python
es.search(index="listings", size=20, query={"bool": {
    "must": {"multi_match": {"query": "brass lamp", "fields": ["title^3", "description"]}},
    "filter": [{"term": {"in_stock": True}}],
}})
```

Keep exact identifiers (SKUs, model codes) in a separate `keyword` field and boost exact hits there heavily.

**Business signals.** Text relevance answers "is this about lamps?". It does not know a listing is new, popular, or well reviewed. Products blend those in, typically by **multiplying** the text score by gentle, bounded factors:

```text
final score = BM25 × recency decay × (1 + log(1 + sales)) × seller-quality factor
```

```python
# function_score: BM25 x recency decay x damped popularity (Elasticsearch 8.x)
query = {"function_score": {
    "query": base_query,
    "functions": [
        {"gauss": {"created_at": {"origin": "now", "scale": "30d", "decay": 0.5}}},
        {"field_value_factor": {"field": "sales", "modifier": "log2p", "missing": 0}},
    ],
    "score_mode": "multiply", "boost_mode": "multiply",
}}
```

`gauss` with `scale: 30d, decay: 0.5` means a listing 30 days old gets half the recency factor. `log2p` is log10(2 + sales); it keeps the factor above zero for a listing with no sales (`log1p` of 0 would multiply the whole score by 0). Check current docs for modifiers.

**Two-stage ranking.** At larger scale, cheap BM25 retrieves the top few hundred candidates per shard, and a learned model (learning to rank) reorders the top 100 using many features. It is the same two-stage shape as <a href={`${BASE}sd/lessons/recsys/`}>recommendations</a>.

**Relevance vs freshness: two different meanings.** "Fresh" is used for two separate questions, and mixing them is a classic muddle:

| | Ranking freshness | Index freshness (staleness) |
|---|---|---|
| Question | Should newer content score higher? | How soon after a write can search see it? |
| Lives in | The scoring function (recency decay) | The pipeline and refresh interval (Chapters 4 and 5) |
| Knob | `scale`, `decay`, boost weight | Refresh interval, CDC lag, `wait_for` |
| Failure | New junk beats a great older match, or good old items sink | A price change or deleted item is still shown |
| Typical choice | A decay with a half-life, not a sort by date | "Searchable in one to two seconds"; read-your-own-writes from the database |

News and tweets weight ranking freshness heavily; a furniture catalogue barely does. Either way, a price or stock change is an index-freshness problem, and no scoring trick fixes a stale price.

    Q["query"] --> F["filters\nallowed or not"]
    F --> B["BM25\ntitle^3 + description"]
    B --> S["signals\nrecency x popularity"]
    S --> T["top 100\nper query"]
    T --> R["learned reranker\noptional"]
    R --> O["top 20 shown"]`} />

<h2 id="cluster">Chapter 4 · Shards, replicas, near-real-time</h2>

**What is it?** Say the first search cluster is three nodes and one big shard. It is fast at lunch and slow at nine in the evening, and adding six more nodes changes nothing: they sit idle while the one node holding the shard is at 100% CPU. A shard lives on one node. To use more machines you must split the index and copy the pieces.

**The vocabulary** (Elasticsearch and OpenSearch use these words; Solr says "collection" and "replica" for similar ideas):

- An **index** is a logical collection of documents (`listings`).
- It is split into **primary shards**. Each document lives on exactly one, chosen roughly by `hash(routing key) mod number_of_primaries`. The routing key is the document id unless you choose another. That formula is why **the primary count is fixed when the index is created**: change it and nearly every document maps somewhere else. You reindex, or use the split/shrink APIs.
- Each primary has **replicas**: full copies on other nodes. A write goes to the primary, which forwards it to the replicas. A search can be served by **any** copy.
- Each shard is a complete Lucene index made of immutable **segments**.

```python
es.indices.create(index="listings_v1",
    settings={"number_of_shards": 3, "number_of_replicas": 2})
```

| | Primary shards | Replicas |
|---|---|---|
| What they do | Split the data | Copy the data |
| Chosen for | Data size, indexing parallelism | Query rate, surviving node loss |
| Can change later? | No (reindex or split) | Yes, any time |
| Adding more | More fan-out per query | More read throughput |

<Figure caption="hash(routing key) mod primaries decides the shard. The same arithmetic is why you cannot change the primary count in place. Switch to 'ring' or 'slots' to see why some systems avoid mod-N.">
  <ShardingSim shards={3} keys={1000} mode="mod" />
</Figure>

**Why "near-real-time": the life of a write.**

<Figure caption="A write is durable when acknowledged (it is in the translog), but searchable only after the next refresh turns the buffer into a new segment.">
  <Mermaid code={`flowchart LR
    D["index a doc"] --> BUF["in-memory buffer"]
    D --> TL[("translog\non disk")]
    BUF -->|"refresh\n(default every 1 s)"| SEG["new small segment\nsearchable"]
    SEG -->|"background merge"| BIG["bigger segment\ndeleted docs dropped"]
    SEG -->|"flush: fsync segments,\ntrim translog"| DISK[("committed\nto disk")]`} />
</Figure>

1. The document lands in an in-memory buffer and is appended to the **translog** (a write-ahead log). By default the translog is fsynced before the write is acknowledged, so an acknowledged write survives a crash.
2. A **refresh** turns the buffer into a new, small segment that searches can see. Elasticsearch refreshes **every second by default**, on indices that received a search in the last 30 seconds (check current docs). That is where "searchable within about a second" comes from. A get-by-id can see the document sooner; a *search* cannot.
3. Segments never change. A **delete** marks the document as deleted; an **update** is a delete plus a new document. Background **merges** combine small segments and finally drop deleted documents.
4. A **flush** fsyncs segments to disk (a Lucene commit) and trims the translog.

| | Refresh | Flush | Merge |
|---|---|---|---|
| Makes docs searchable? | Yes | No (already searchable) | No |
| Makes docs durable? | No (the translog does) | Yes (segments on disk) | No |
| How often | Every 1 s by default | Automatic, by translog size | Continuous, background |
| Cost if too frequent | Many tiny segments, slow searches | Disk writes | CPU and I/O |

Bulk loads go faster with refresh off (`refresh_interval: -1`) and replicas at zero until the load ends. That is the standard tuning for an initial load or a rebuild; set both back afterwards.

**The life of a query: scatter-gather.** Elasticsearch's default is *query then fetch*:

<Figure caption="The coordinating node asks one copy of every shard for its local top results, merges them, then fetches only the winning documents.">
  <Mermaid code={`sequenceDiagram
    participant C as Coordinating node
    participant S0 as Shard 0 (a replica)
    participant S1 as Shard 1 (the primary)
    participant S2 as Shard 2 (a replica)
    C->>S0: query: top 20 for brass lamp
    C->>S1: query: top 20
    C->>S2: query: top 20
    S0-->>C: 20 (id, score)
    S1-->>C: 20 (id, score)
    S2-->>C: 20 (id, score)
    Note over C: merge 60 into global top 20
    C->>S1: fetch 9 documents
    C->>S0: fetch 7 documents
    C->>S2: fetch 4 documents`} />
</Figure>

One subtlety: each shard computes IDF from **its own** documents, so one listing can score slightly differently on different shards. With large, randomly routed shards the difference is negligible. For small indexes, `dfs_query_then_fetch` gathers global statistics first at the cost of an extra round trip.

**The tail.** A scatter-gather is as slow as its slowest shard. If each shard is slow 1% of the time, independently:

| Shards per query | Searches that hit at least one slow shard |
|---|---|
| 1 | 1% |
| 3 | 1 − 0.99³ ≈ 3% |
| 20 | 1 − 0.99²⁰ ≈ 18% |
| 100 | 1 − 0.99¹⁰⁰ ≈ 63% |

So: **keep shard counts modest** (each shard also costs memory and coordination). Let the engine pick the fastest copy (adaptive replica selection; check your version). Set **timeouts with partial results** where a slightly incomplete ranking is acceptable. Use **custom routing** when a query concerns one slice: "search my own listings" routed by `seller_id` hits one shard instead of all of them. The general slow-shard story is in <a href={`${BASE}sd/lessons/core-concepts/#tail-latency`}>Core concepts · The slowest of a hundred</a>.

```python
# index with routing, search with the same routing: one shard, not all three
es.index(index="listings", id="L123", routing="seller_42", document=doc)
es.search(index="listings", routing="seller_42", size=20,
          query={"bool": {"must": {"match": {"title": "lamp"}},
                          "filter": {"term": {"seller_id": "seller_42"}}}})
```

A very large seller can make one shard hot. Routing buys speed for small tenants and costs balance for big ones.

**Sizing a cluster, with numbers.** Assumptions: one copy ≈ 70 GB (Chapter 2); 2,000 searches/s at peak; about 10 ms of CPU per search per shard; nodes with 16 cores; Elastic's guidance of shards between roughly 10 GB and 50 GB (check current docs).

1. **Primaries:** 70 GB ÷ 3 ≈ **23 GB per shard**: inside the guideline, and only 3 shards to fan out to.
2. **CPU:** 2,000 searches/s × 3 shards = 6,000 shard-searches/s × 10 ms = **60 cores** busy. At about 60% utilisation → **100 cores**.
3. **Nodes and copies:** 100 ÷ 16 ≈ 6.25, so at least 7 nodes. Choose **2 replicas** → 3 × 3 = **9 shard copies on 9 nodes** (144 cores). Lose one node and 8 × 16 = 128 cores still cover 100.
4. **Memory:** 9 copies × 23 GB = 207 GB across 9 nodes ≈ **23 GB per node**. On 64 GB nodes that is small enough to sit in the operating system's page cache, where search is fastest.

The chain matches the caching lesson: **data size picks the primaries; query rate and failure tolerance pick the replicas.**

<Trace title="Size and shape the cluster" steps={cluster} takeaway="Primaries split data; replicas carry reads and survive failures. Fan-out multiplies tail latency, so keep shards few and route single-tenant queries to one shard." />

**Document or term partitioning?** A follow-up interviewers like, framed as Twitter search: billions of tweets, mostly searched within a day of posting.

<Reveal q="Term or document partitioning for tweet search: what do you say?">

**Document partitioning, and partition by time as well.** With **term partitioning** (a "global" index), a query touches only the shards owning its terms, which is attractive for reads. But a tweet with 20 distinct terms becomes writes to up to 20 shards. A two-word query has to ship one term's postings list to the other shard to intersect them. A trending term turns its owner into a hot shard exactly when everyone is searching it. **Document partitioning** (a "local" index per shard) keeps every write on one shard and spreads load evenly, at the price of scatter-gather on reads. Almost every production engine makes that trade. For tweets, add **time**: most queries want recent tweets, so the newest index is small, write-hot and in memory, while older slices are searched only when needed. Twitter described this shape in its Earlybird paper (ICDE 2012).

</Reveal>

**A common slip.** "Add more shards to handle more queries." More primaries means more fan-out per query and a worse tail. Throughput comes from replicas.

**Interview takeaway.** "Data size picks primaries, about 10 to 50 GB each. Query rate and fault tolerance pick replicas. Every query fans out to one copy of each shard, so p99 depends on shard count. Writes are searchable after the next refresh, about a second."

<h2 id="sync">Chapter 5 · Indexing pipeline and reindexing</h2>

**What is it?** The path that gets a change from your database into the search index, and keeps it correct. The one fact to hold: **the search index is never the source of truth.** It is a **derived, rebuildable** copy. Every design decision below follows from that.

**Why do we need a pipeline?** Say a seller lowers her armchair's price on Monday. On Thursday search still shows the old price and buyers are messaging her about it. The listing service wrote Postgres, then called Elasticsearch. Two edits a few milliseconds apart committed in order in the database, but the two index calls arrived in reverse, so the older version overwrote the newer one. A cache would heal at its TTL. A search index stays wrong until the document is edited again.

**Dual writes** (the app writes the database and then the engine) fail in three ways:

1. **Lost writes.** The database commits, the process dies (or the index call fails) before the second write. The listing never appears in search.
2. **Reordering.** Concurrent writers' index calls arrive in a different order from their commits, and the older version wins, permanently.
3. **Divergence over time.** Every bug, timeout and partial failure leaves a small permanent difference. Nobody notices until a seller does.

**The standard answer: change data capture (CDC) → queue → indexer.**

<Figure caption="One ordered change stream. Partitioning by listing_id keeps each listing's changes in order; external versions make duplicates and replays harmless.">
  <Mermaid code={`flowchart LR
    APP["listing service"] --> PG[("Postgres")]
    PG -->|"WAL"| CDC["CDC connector\ne.g. Debezium"]
    CDC --> K[["Kafka topic\nkey = listing_id"]]
    K --> IX["indexer\nbatches bulk requests"]
    IX -->|"version = row version / LSN"| AL{{"alias: listings"}}
    AL --> V1[("listings_v1")]`} />
</Figure>

| | Dual write | CDC → queue → indexer |
|---|---|---|
| Who tells search about a change | The application, after the commit | The database log: every committed change, from any writer |
| Crash between the two writes | Update is lost | The log still has it; the indexer catches up |
| Order | Whatever order the calls arrive | Per-listing order (key = listing_id) |
| Duplicates and replays | Overwrite blindly | No-ops, by external version |
| Cost | Simple | A connector, a topic, an indexer to run |

- **Capture from the log, not the application.** Every committed change, from any service, migration or admin script, flows through the write-ahead log. Nothing can forget to notify search. If you cannot tap the log, the <a href={`${BASE}sd/lessons/queues-streams/#outbox`}>outbox pattern</a> gives the same guarantee.
- **Order per document.** Key the topic by `listing_id` so all changes to one listing land in one partition and are consumed in order.
- **Versions, not hope.** Index with **external versioning**: the indexer passes the row's version (a version column, or the log position of the change) and the engine rejects anything not strictly newer than what it holds. Duplicates and replays become no-ops. Some teams instead make the indexer re-read the current row and index that, so a late event can only write the latest truth.
- **Denormalise on purpose.** A search document is flattened: the listing plus the seller's name, the category path, the review average. That makes queries fast and updates wide, because renaming a category touches every listing in it. Name which fields are copied and how they are refreshed.
- **Deletes are events too.** Soft and hard deletes must both produce a delete in the index.

```python
from elasticsearch import helpers

def to_action(event):
    row = event["after"]
    action = {
        "_op_type": "delete" if event["op"] == "d" else "index",
        "_index": "listings",                  # an alias, not a physical index
        "_id": row["id"],
        "_version": event["lsn"],              # external version: log position
        "_version_type": "external",
    }
    if event["op"] != "d":
        action["_source"] = to_doc(row)
    return action

ok, errors = helpers.bulk(es, (to_action(e) for e in batch),
                          raise_on_error=False, stats_only=False)
# version_conflict errors mean "a newer version is already here": safe to ignore
```

**What goes wrong in the pipeline, and what you do:**

| Failure | Effect | Response |
|---|---|---|
| Indexer or Kafka down | Lag grows; search serves older data; the database is unaffected | Alert on consumer lag; the log is the buffer; catch up when it is back |
| Elasticsearch rejects bulk (HTTP 429, overloaded) | Indexer is throttled | Back off with jitter, shrink batches |
| A poison document (mapping error) | One event fails forever | Send it to a dead-letter queue after N tries; do not block the partition |
| Source and index drift (a bug) | Silent wrong results | A periodic reconciliation job comparing counts and sampled checksums; reindex on mismatch |

**How stale is search?** Assume CDC capture about 100 ms, Kafka about 50 ms, the indexer batching for up to 500 ms, then up to 1 s until the next refresh. Worst case ≈ 0.1 + 0.05 + 0.5 + 1.0 = **1.65 s**. Say it as **"searchable within about one to two seconds"**, and say it before you are asked.

**Read-your-own-writes for the author.** The seller who just saved a listing must see it. Show "my listings" from the database, or, for that one write, ask the engine to wait for the next refresh before responding (`refresh="wait_for"`). Never force a refresh on every write: it creates tiny segments and hurts the whole cluster.

**Reindexing with zero downtime.** You will change analyzers, mappings and shard counts, and none of those can be applied to postings already built. Clients talk to an **alias**, never to a physical index:

1. Create `listings_v2` with the new mapping.
2. **Record the stream position**, then backfill v2 from a consistent snapshot of the database (or the engine's reindex API), indexing each row with the same external version the live stream uses.
3. Start a second consumer that replays the change stream into v2 **from the recorded position**. External versions make the overlap with the backfill harmless. (Kafka retention must outlast the backfill.)
4. Verify: document counts, sample queries, relevance checks.
5. **Atomically move the alias** `listings` from v1 to v2. Keep v1 for a while as the rollback.

```python
es.indices.update_aliases(actions=[
    {"remove": {"index": "listings_v1", "alias": "listings"}},
    {"add":    {"index": "listings_v2", "alias": "listings"}},
])   # both actions apply as one atomic step
```

<Figure caption="Zero-downtime reindex. The offset recorded before the backfill is what guarantees no change falls in the gap.">
  <Mermaid code={`sequenceDiagram
    participant Ops
    participant V2 as listings_v2
    participant K as Kafka
    participant A as alias listings
    Ops->>K: record offset X
    Ops->>V2: backfill from DB snapshot
    K->>V2: replay from X (versions dedupe)
    Ops->>V2: verify counts and queries
    Ops->>A: swap v1 to v2 (atomic)`} />
</Figure>

**If the cluster is destroyed**, the design pays off: reindex from the database. Assume 20,000 documents per second of bulk indexing (benchmark yours): 50 million ÷ 20,000 = 2,500 s ≈ **42 minutes**. Snapshots of the cluster make recovery faster; they do not change the story. Meanwhile search is **degraded, not lost**: show a "search is catching up" banner, fall back to category browsing. No data is gone, because none of it lived only in search.

<Trace title="Keep the copy honest" steps={sync} takeaway="One ordered change stream (CDC → Kafka keyed by id → indexer with external versions). Aliases make reindexing invisible. The database is the truth; the index is rebuildable." />

<Reveal q="Why not have the listing service publish its own 'listing changed' events instead of tapping the WAL?">

You can, if the service publishes them through a transactional outbox, so the event is committed in the same transaction as the row. Publishing to Kafka directly after the commit is just a dual write with a different second system: a crash between the two loses the event. Log-based CDC has a further advantage: it sees writes that bypass the service, such as migrations, backfills and other teams' jobs.

</Reveal>

**A common slip.** "We'll write to Elasticsearch when we write to the database." That is a dual write, and a search index has no TTL to heal the races. Say "CDC into a queue keyed by id, with versioned upserts", and say the one-to-two-second lag.

**Interview takeaway.** "The database is the truth. CDC reads its log into Kafka keyed by id, and an indexer upserts with external versions, so order and replays are safe. Search lags by one to two seconds. Mapping changes go to a new index behind an alias, and if the cluster dies I reindex in under an hour."

<h2 id="pagination">Chapter 6 · Deep pagination</h2>

**What is it?** Page 1 of results is cheap. Page 500 is not. Say a partner scrapes the catalogue one page at a time and every request from page 400 on is slower than the one before, until page 500 suddenly fails. Each page still returns only 20 results. Why does depth cost so much?

**Why does from/size get expensive?** The coordinator cannot know which listings are the 9,981st to 10,000th overall unless every shard sends its own top `from + size`. Every shard sorts that many; the coordinator merges them all and throws nearly everything away.

| Page (size 20, 3 shards) | from + size per shard | Entries the coordinator merges | Returned |
|---|---|---|---|
| 1 | 20 | 60 | 20 |
| 500 | 10,000 | 30,000 | 20 |
| 501 | 10,020 | refused | none |

Page 501 fails because Elasticsearch, by default, refuses `from + size` beyond **10,000** (`index.max_result_window`; check current docs). It is a safety limit, not a bug. Raising it only lets one bored scraper hurt everyone.

```python
# page 500 the expensive way: every shard sorts and returns 10,000
es.search(index="listings", query=q, from_=9980, size=20)
```

**How does a cursor fix it?** **search_after** replaces an offset with "the next 20 after this sort key". Sort by something with a **unique tiebreaker**, such as `(score, listing_id)` or `(created_at, listing_id)`. Each shard returns only 20, whatever the depth. Wrap the session in a **point-in-time (PIT)** so refreshes do not shift results between pages.

```python
pit = es.open_point_in_time(index="listings", keep_alive="2m")["id"]

body = dict(query=q, size=20, pit={"id": pit, "keep_alive": "2m"},
            sort=[{"_score": "desc"}, {"listing_id": "asc"}])
page = es.search(**body)

hits = page["hits"]["hits"]                      # page 1
last = hits[-1]["sort"]                          # e.g. [4.81, "L8841"]
page2 = es.search(**body, search_after=last)     # next 20, constant cost

es.close_point_in_time(id=pit)
```

Elastic now recommends `search_after` with a PIT over the older scroll API for deep paging (check current docs for your version). A PIT also adds an implicit tiebreaker if you omit one.

| | from/size | search_after (+ PIT) |
|---|---|---|
| Cost of page n | Grows with n: shards × (from + size) | Constant |
| Jump to page 37 | Yes | No: next/previous only |
| Stable across refreshes | No: results can shift | Yes, with a PIT |
| Use for | The first few pages of a results UI | Infinite scroll, exports, deep crawls |

<h2 id="typeahead">Chapter 7 · Typeahead is not search</h2>

**What is it?** Suggestions under the search box: type "l" and see "lamp", "ladder", "laptop stand". **How is it different from search?** The input is a **prefix**, the output a few **likely completions**, it fires on **every keystroke**, and it must feel instant: suggestions that arrive after the user has typed further are worse than none.

| | Search | Typeahead |
|---|---|---|
| Input | Complete words or a phrase | A prefix, often one or two letters |
| Output | Ranked documents | 5 to 10 completion strings |
| Triggered | Once per submit | Every keystroke (after debounce) |
| Latency target | Hundreds of milliseconds | About 100 ms, end to end |
| Data | The inverted index of documents | Precomputed suggestions from query logs |
| Freshness | Seconds | Hours, plus a small trending layer |
| Shared with search | | Only the query logs |

**The latency budget.** From keystroke to suggestions painted, about 100 ms. Each line is an assumption you would state out loud:

| Step | Budget |
|---|---|
| Client debounce (wait for a 30 ms pause in typing) | 30 ms |
| Network round trip to the user's region or edge | 30 ms |
| Load balancer + suggestion service (in-memory lookup) | 10 ms |
| Render | 10 ms |
| Headroom for jitter (p99, not average) | 20 ms |
| **Total** | **100 ms** |

Read it backwards and the architecture falls out:

- A round trip across an ocean is often 100 to 200 ms by itself, so suggestions are served **in every region**, hot prefixes **at the edge**.
- A database query (milliseconds to tens of milliseconds, with a tail) or a search-cluster scatter-gather would eat most of the server budget, so the answer must be **precomputed and in memory**: one lookup, no fan-out.
- The client is part of the system: debounce, cancel stale requests, cache what it already has.

<Figure caption="One keystroke, end to end. Most requests should end at the edge or the in-region service; none should reach the search cluster.">
  <Mermaid code={`flowchart LR
    K["keystroke"] --> D["debounce\n30 ms"]
    D --> C["client cache\nprefix to list"]
    C -->|"miss"| E["edge cache\nhot prefixes"]
    E -->|"miss"| S["suggestion service\nin region, in memory"]
    S --> R["top-K list\nless than 10 ms"]`} />
</Figure>

**Requests per second.** Assumptions: 20 million daily users, 5 searches each, about 8 keystrokes per search, peak = 3 × average.

- Keystrokes: 20M × 5 × 8 = **800 million per day** ≈ 9,259/s average ≈ **27,800/s at peak**.
- Assume debouncing and client-side reuse cut that to about 4 requests per search: 400 million per day ≈ 4,630/s average ≈ **13,900/s at peak**.
- If an edge cache answers about a third of those (the hot short prefixes), the origin sees about **9,300/s** at peak. An in-memory lookup costs microseconds, so a handful of nodes per region cover it. You run several per region for availability, not capacity.

**The client half** (interviewers like that you remember it exists):

- **Debounce**: send only after a short pause in typing, so bursts collapse into one request. A longer debounce means fewer requests but a laggier feel; it spends latency budget.
- **Ignore out-of-order responses**: tag each request with its prefix or a sequence number, paint only the response for what is in the box *now*, and abort superseded requests.
- **Client cache**: keep recent prefix → suggestions. Backspacing from "lamp" to "lam" costs nothing. If the server said "la" has only 3 completions (fewer than K), every "lam…" completion is among them, so filter locally.

**Cache the hot prefixes, with all four promises.** There are only 26 one-letter, 676 two-letter and 17,576 three-letter lowercase ASCII prefixes: 18,278 keys, carrying a large share of requests. Cache their responses at the edge, and say it the way the <a href={`${BASE}sd/lessons/caching/`}>caching lesson</a> taught:

- **Key**: `sugg:v{build}:{locale}:{normalised prefix}`, lowercased, trimmed, Unicode-normalised.
- **TTL and why**: until the next offline build (say an hour, jittered). Suggestions are popularity data, not facts.
- **Invalidation**: the build number is in the key, so a new build uses new keys and old ones age out.
- **Failure**: an edge miss falls through to the in-region service, which holds the whole dataset in memory. Nothing behind it can stampede. Personalised suggestions are **not** cached at the edge; the client merges the user's own history locally.

<Trace title="Spend the 100 ms" steps={typeahead} takeaway="Precomputed, in memory, in region, hot prefixes at the edge. The client debounces, caches, and paints only the response for the current prefix." />

**When would search-on-keystroke be acceptable?** For a small internal tool with a few users, querying Elasticsearch per keystroke works and saves building a second system. At consumer scale it spends the whole budget on a scatter-gather built for a different problem. Say why you separated the systems.

**Interview takeaway.** "Typeahead is a separate system: prefix in, a few completions out, under 100 ms per keystroke. So the suggestions are precomputed and held in memory in each region, hot prefixes sit at the edge, and the client debounces and drops stale responses."

<h2 id="trie">Chapter 8 · Trie with top-K</h2>

**What is it?** A **trie** (prefix tree) stores strings so every path from the root spells a prefix. To complete "ca", walk c → a; every query in the subtree below starts with "ca". The data-structure side of tries (insert, search, wildcard) is in the <a href={`${BASE}dsa/lessons/tries/`}>Tries lesson</a>.

**What is the problem?** For a short prefix the subtree is enormous. Finding its 10 most popular completions at query time means visiting every node below: hundreds of thousands or more for "c", on every keystroke.

**The trick: store the top-K at every node, precomputed.** Each node carries its K best completions (K = 5 or 10). A query walks to the node, one hop per character typed, and returns the list it finds. **Lookup cost: O(length of the prefix)**, microseconds, however big the subtree.

<Figure caption="Each node carries the top completions of its whole subtree, computed bottom-up. 'ca' merges its children's lists; the query never visits the subtree.">
  <Mermaid code={`flowchart TD
    R(("root")) --> C["c\ncar 900 · cat 700"]
    C --> CA["ca\ncar 900 · cat 700"]
    CA --> CAR["car ✓ 900\ncar 900 · card 400"]
    CA --> CAT["cat ✓ 700\ncat 700 · catalog 500"]
    CAR --> CARD["card ✓ 400\ncard 400"]
    CAR --> CARE["care ✓ 150\ncare 150"]
    CAT --> CATA["…catalog ✓ 500"]`} />
</Figure>

**Building it bottom-up.** A node's top-K is the best K of its own query (if it is one) plus its children's top-K lists. That merge is enough: any query in a node's top K must also be in the top K of whichever child's subtree contains it. One pass from the leaves up builds every list.

```python
import heapq

class Node:
    __slots__ = ("kids", "own", "top")
    def __init__(self):
        self.kids, self.own, self.top = {}, None, []

def build(counts, k=2):                      # counts: {"car": 900, "cat": 700, ...}
    root = Node()
    for query, n in counts.items():
        node = root
        for ch in query:
            node = node.kids.setdefault(ch, Node())
        node.own = (n, query)
    def fill(node):
        cands = [node.own] if node.own else []
        for child in node.kids.values():
            fill(child)
            cands += child.top
        node.top = heapq.nlargest(k, cands)  # best k by count
    fill(root)
    return root

def suggest(root, prefix):
    node = root
    for ch in prefix:
        node = node.kids.get(ch)
        if node is None:
            return []
    return [q for _, q in node.top]

trie = build({"car": 900, "card": 400, "care": 150, "cat": 700, "catalog": 500})
print(suggest(trie, "ca"))   # ['car', 'cat']
```

**The cost moved to writes, and then offline.** A search for "cardigan" should raise its rank in the lists of c, ca, car, card, and so on. Doing that on every search, on every serving replica, with locks on the hottest nodes, is the wrong trade. Instead:

<Figure caption="The offline loop. Serving nodes only ever read an immutable snapshot and swap to the next one.">
  <Mermaid code={`flowchart LR
    L[["search logs"]] --> A["aggregate\nhourly / daily batch"]
    A --> F["filter\nblocklist, min distinct users"]
    F --> B["build trie\ntop-K bottom-up"]
    B --> S[("snapshot\nversioned file")]
    S --> N1["serving node\nload, then swap"]
    S --> N2["serving node\nload, then swap"]
    TR["trending stream\nlast hour counts"] -.->|"merge at query time"| N1`} />
</Figure>

1. **Aggregate** query logs on a schedule (hourly or daily, batch or streaming), with **time decay** so this week beats last year: count each day's searches with a weight that halves every few days.
2. **Filter.** Remove offensive and unsafe suggestions with a blocklist, and only suggest queries searched by at least N **distinct** users, so one person's private search (a name, an address) can never appear in someone else's box.
3. **Build** the trie with top-K lists, serialise it into a compact, read-only format, and ship the snapshot.
4. **Swap.** Each serving node loads the new snapshot beside the old one and flips a pointer. Immutable data means no locks on the read path.

**Freshness is hours, not milliseconds, and that is the right trade.** For sudden trends, add a small real-time layer: a stream job counts recent queries over a short window (a count-min sketch plus a heap of current leaders; see <a href={`${BASE}sd/lessons/pattern-timeseries/`}>Time-series · top-K</a>), and the service merges those few fresh phrases into the trie's list at query time.

**This is a pattern, not a trie fact.** Pay at (offline) write time so reads are a lookup: the same trade as <a href={`${BASE}sd/lessons/pattern-fanout/`}>fan-out-on-write</a> and materialized views. Recognising the shape is the transferable skill.

**Does it fit in memory?** Assume the 1 million most popular queries, about 20 characters each.

- Raw suggestions: 1M × ~100 B (string, count, metadata) ≈ **100 MB**.
- Trie nodes: at most one per character of every query, so **≤ 20 million** (shared prefixes make it fewer).
- Top-10 lists as 4-byte query ids: 40 B per node plus ~20 B of node structure ≈ 60 B → 20M × 60 B = **1.2 GB** at most.

About a gigabyte, worst case: it fits in memory on every serving node in every region. A naive object-per-node trie in Java or Python can be many times larger, another reason to build a compact format offline. At much larger scale (many languages, hundreds of millions of queries), **shard by prefix**: by first characters with ranges balanced by traffic (far more queries start with "s" than with "x"), or by hash of the prefix if you store prefixes as keys (next chapter).

<Trace title="Build the top-K trie" steps={trie} takeaway="Top-K at each node, built bottom-up offline from logs, swapped in as a snapshot. A small trending layer handles freshness. Reads are O(prefix length)." />

<Reveal q="Why not rank suggestions by how often the completion appears in listings, instead of by what people search?">

Because typeahead predicts what *this user is about to type*, and the best evidence is what other users typed and then searched (better still, searched and clicked). Catalogue frequency suggests words sellers use, not words buyers want: "vintage" is everywhere in titles but rarely typed first. Many systems blend both: query logs for popular suggestions, catalogue terms to cover new or rare items, and the user's own history on the client.

</Reveal>

**A common slip.** "Walk the subtree and sort by count." Correct output, wrong cost: for one-letter prefixes it touches hundreds of thousands of nodes per keystroke. The answer is the precomputed top-K.

**Interview takeaway.** "Each trie node stores its subtree's top 10, built bottom-up offline from decayed, filtered query logs and swapped in as an immutable snapshot. A lookup is O(prefix length). A streaming top-K merged at query time handles trends."

<h2 id="prefix-stores">Chapter 9 · Three ways to answer a prefix</h2>

**What is it?** Two weeks later a new requirement arrives: sellers want suggestions when they search their own listings, from their own titles, filtered by category. The global trie cannot do it, since its suggestions are everyone's popular queries, not one seller's titles. The same question ("what completes this prefix?") has three different machines.

| Approach | How it works | Best for | Costs |
|---|---|---|---|
| **In-memory trie + top-K** | The tree from Chapter 8, built offline, held in every serving node | Global popular-query suggestions; the classic interview answer | A build pipeline; freshness in hours plus a trending layer |
| **Prefix table in a KV store** | One row per prefix: key = `prefix`, value = its top-K list. Typeahead becomes one `GET` | The same data as the trie when you would rather run Redis or a Dynamo-style store than custom servers | More storage (prefixes repeat the lists); sharding is trivial: hash the prefix |
| **Edge n-grams in the search index** | Index "lamp" as `l, la, lam, lamp`; a prefix is now an ordinary term | Completing over **documents** with filters: a seller's own titles, by category, by permission | Index grows several times for that field; it is a search query, with search latency |

<Figure caption="Pick by what you are completing: popular queries (precompute) or documents with filters (search index).">
  <Mermaid code={`flowchart TD
    Q["complete this prefix"] --> A{"what is being completed?"}
    A -->|"popular queries, same for everyone"| B{"run custom servers?"}
    B -->|"yes"| T["in-memory trie\nwith top-K"]
    B -->|"no"| K["prefix table\nin Redis or KV"]
    A -->|"documents, with filters or permissions"| N["edge n-grams\nin the search index"]`} />
</Figure>

**The prefix table, in Redis.** With 1 million queries of about 20 characters there are at most 20 million distinct prefixes. At serving time it is one lookup:

```redis
SET  sugg:v42:en:lam  "lamp|lamp oil|lampshade|lamps for desk"
GET  sugg:v42:en:lam
```

If each row stores its top 10 as strings (10 × ~20 B) plus a ~20 B key, that is about 220 B per row → **up to 4.4 GB**. Capping prefixes at 10 characters (longer ones fall back to search) halves it: at most 10 million rows ≈ **2.2 GB**. Comfortable for an in-memory KV cluster.

**Edge n-grams, done right.** Use the edge n-gram analyzer **only at index time**, and search with a plain analyzer. If the query is n-grammed too, "lam" becomes `l, la, lam`, and every title with a word starting with "l" matches.

```python
es.indices.create(index="listings_v1",
  settings={"analysis": {
      "tokenizer": {"edge": {"type": "edge_ngram", "min_gram": 1, "max_gram": 10,
                             "token_chars": ["letter", "digit"]}},
      "analyzer": {"title_prefix": {"tokenizer": "edge", "filter": ["lowercase"]}}}},
  mappings={"properties": {"title_prefix": {
      "type": "text", "analyzer": "title_prefix", "search_analyzer": "standard"}}})

es.search(index="listings", size=8, query={"bool": {
    "must":   {"match": {"title_prefix": "lam"}},
    "filter": [{"term": {"seller_id": "seller_42"}}, {"term": {"category": "lighting"}}]}})
```

The index cost is real: a 6-word title of 6-letter words becomes about 36 indexed grams instead of 6. For 50 million titles that is about 1.8 billion postings for that one field instead of 0.3 billion. Usually fine, but say it. (Engines also ship purpose-built suggesters, such as Elasticsearch's completion suggester with an in-memory FST. Check current docs for what yours offers.)

**So for the seller:** global suggestions from the trie (or prefix table); "search my listings" from an edge n-gram field, filtered by `seller_id` and routed to the seller's shard (Chapter 4). Two systems, each in the shape its data needs.

<h2 id="fuzzy">Chapter 10 · Typos and fuzzy matching</h2>

**What is it?** The report of queries that returned nothing last week shows "pizzza oven", "lmap", "armchiar", "vintge". Each has a perfect match in the catalogue, one slip of a finger away. The index is exact; people are not.

**Edit distance** counts the single-character edits that turn one string into another. **Levenshtein** distance counts insertions, deletions and substitutions. **Damerau–Levenshtein** also counts swapping two adjacent characters as one edit, one of the most common typos.

| Typed → meant | Levenshtein | With transpositions |
|---|---|---|
| pizzza → pizza | 1 (delete a z) | 1 |
| lmap → lamp | 2 (two substitutions) | 1 (one swap) |
| lamp → clamp | 1 (insert c) | 1 |
| lamp → damp | 1 (substitute) | 1 |

The last two rows are the warning: **fuzzy matching finds what the user meant and things they did not.** Rank exact matches above fuzzy ones and keep the allowed distance small.

```python
es.search(index="listings", size=20, query={"bool": {"should": [
    {"match": {"title": {"query": "lmap", "boost": 3}}},                       # exact first
    {"match": {"title": {"query": "lmap", "fuzziness": "AUTO", "prefix_length": 1}}},
]}})
```

**How engines avoid comparing against every word.** Lucene compiles the misspelt term into a **Levenshtein automaton**, a machine that accepts exactly the strings within distance n, and walks the sorted term dictionary with it, skipping whole regions that cannot match. Elasticsearch's `fuzziness: AUTO` allows exact match for terms of 1 to 2 characters, one edit for 3 to 5, two edits for longer; it counts transpositions by default (check current docs). Requiring an exact `prefix_length` cuts the work sharply and costs little, since people mistype the first letter less than the rest.

**N-grams: the other road.** Break words into overlapping character n-grams and compare the sets. With trigrams:

<Figure caption="'pizza' and 'pizzza' share 3 of 4 distinct trigrams: Jaccard similarity 3/4 = 0.75. Green = shared; red = only in the typo.">
  <ArrayStrip name="pizza" indices={false} values={['piz', 'izz', 'zza']} tones={{ 0: 'done', 1: 'done', 2: 'done' }} />
  <ArrayStrip name="pizzza" indices={false} values={['piz', 'izz', 'zzz', 'zza']} tones={{ 0: 'done', 1: 'done', 2: 'out', 3: 'done' }} />
</Figure>

A trigram index finds candidates that share many grams, then ranks them by overlap. This is how Postgres's `pg_trgm` does similarity search:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX listings_title_trgm ON listings USING gin (title gin_trgm_ops);
SELECT title, similarity(title, 'pizzza') AS sim
FROM listings WHERE title % 'pizzza' ORDER BY sim DESC LIMIT 5;
```

Query logs add the strongest signal of all: when many users search "armchiar" and immediately search "armchair", that rewrite can be learned and suggested.

**Typos in typeahead** are harder: the user has not finished the word, so you would need fuzzy *prefix* matching on every keystroke. Common answers: allow one edit only after the first few characters, or precompute popular misspellings from logs into the suggestion data.

<Trace title="Measure the typo" steps={fuzzy} takeaway="Edit distance with transpositions catches swaps as one edit; n-gram overlap finds candidates cheaply. Keep distance small, require a short exact prefix, rank exact matches first." />

**One related one-liner:** a **Bloom filter** answers "definitely not present" or "maybe present" in very little memory, with no false negatives. It shows up for crawler URL dedup and for cache-penetration defence (the caching lesson), so know the sentence even though search does not need it.

**A common slip.** "Make every query fuzzy with two edits." Short words then match many unrelated words ("lamp" → "damp", "camp", "lame", "limp"), and precision collapses. Fuzzy is a fallback and a ranking signal, not the default.

**Interview takeaway.** "I keep exact matches first and add a fuzzy clause with AUTO fuzziness, an exact first character, and transpositions counted. Trigrams give candidates for 'did you mean', and query logs teach corrections."

<h2 id="filters-facets">Chapter 11 · Filters and facets</h2>

**What is it?** A results page with a sidebar: price ranges, brands with counts beside them, "in stock", "ships to you". A tester files the first bug within an hour: she ticked "in stock" and a sold-out lamp appeared on page two. The cause: "in stock" had been implemented as a score boost.

**Filtering and ranking are different jobs,** and mixing them causes most of the bugs:

| | Filtering | Ranking (scoring) |
|---|---|---|
| Question | Is this result allowed? | How good is this result? |
| Output | Yes or no | A number |
| Examples | in stock, price ≤ 50, ships to the user's country, category, not hidden, visible to this user | text relevance, recency, popularity, distance |
| Cost | Cheap; results cacheable as bitsets and reused across queries | Per-document arithmetic |
| Elasticsearch | `filter` clauses (no score) | `must` / `should` clauses, function scores |

**Hard constraints are filters. Preferences are scores.** A boost lets a strong enough text match outrank the boost and leak through, which is the bug above. Permissions and visibility (hidden listings, blocked sellers, private items) are always filters, applied inside the engine, before ranking and paging. Filtering 20 results in the application after fetching them breaks page sizes and every page after.

**Facets** are the counts in the sidebar: how many matching listings per brand, per price range, per category. Engines compute them as **aggregations** over the matched set, reading the column-oriented doc values from Chapter 2.

```python
es.search(index="listings", size=20,
  query={"bool": {"must": {"match": {"title": "lamp"}},
                  "filter": [{"term": {"in_stock": True}}, {"range": {"price": {"lte": 50}}}]}},
  post_filter={"term": {"material": "brass"}},        # the ticked facet: hits only
  aggs={"materials": {"terms": {"field": "material", "size": 10, "shard_size": 50}},
        "price": {"histogram": {"field": "price", "interval": 25}}})
```

- **They cost real work** when the match set is large: counting brands over two million "furniture" matches touches two million values. High-cardinality fields cost more.
- **Distributed counts can be approximate.** A terms aggregation asks each shard for its top N buckets and merges them. A brand that is 11th on one shard and 1st on another can be undercounted. Ask shards for more buckets than you show (`shard_size`) and treat counts as estimates; the engine reports an error bound.
- **The selected facet should not hide its siblings.** When the shopper ticks "brass", the material list should still show the other materials' counts. `post_filter` applies the selection to the hits *after* aggregations are computed, for exactly this.

    F --> AG["aggregations\nbrand, price buckets"]

<h2 id="geo-vector">Chapter 12 · Geo, vectors and hybrid search</h2>

**What is it?** Two requests arrive on the same afternoon. Product wants "near me": local pickup only, closest first. And a shopper writes: "I searched 'something warm to read by in bed' and got nothing." She used no word that is in the listing, and the listing is exactly what she wants.

**Geo search.** Search engines index locations as points (Lucene uses tree structures built for multi-dimensional points) and support distance filters ("within 10 km"), bounding boxes and sorting by distance. In ranking, use a **distance decay** that multiplies the text score (closer is better, smoothly) rather than a hard sort that puts a barely relevant listing first because it is 200 metres away. The cell structures underneath (geohash, quadtrees, H3) and the "nearby drivers" variants are in <a href={`${BASE}sd/lessons/pattern-geospatial/`}>Geospatial indexing</a>.

**Semantic (vector) search.** An embedding model turns text into a vector so that texts with similar *meaning* land near each other: "something warm to read by in bed" lands near "bedside lamp, warm white". Finding the nearest vectors among millions needs an **approximate nearest-neighbour (ANN)** index such as HNSW. Elasticsearch and OpenSearch both offer one (check current docs), as do dedicated vector databases. The pipeline (chunking, embeddings, ANN, reranking) is in <a href={`${BASE}sd/lessons/rag/`}>RAG & vector search</a>.

**Lexical and semantic fail in opposite places:**

| Query | BM25 (lexical) | Vector (semantic) |
|---|---|---|
| "BL-4471" (a model code) | Excellent: a rare, exact token | Often poor: codes blur together |
| "something warm to read by in bed" | Poor: no shared words | Good: shared meaning |
| "brass desk lamp" | Good | Good |

So production systems run **hybrid search**: retrieve with both, then fuse. **Reciprocal rank fusion (RRF)** is the simple, robust default: each document scores Σ 1 / (k + rank) over the lists it appears in, with k = 60 in the original paper. It needs only ranks, so you never put BM25 scores and cosine similarities on one scale. A reranker can then reorder the fused top results.

<Figure caption="Hybrid retrieval: two retrievers, one fusion step by rank, an optional reranker.">
  <Mermaid code={`flowchart LR
    Q["query"] --> L["BM25 over text\ntop 50"]
    Q --> E["embed, then ANN\ntop 50"]
    L --> R["RRF\nsum 1/(60 + rank)"]
    E --> R
    R --> X["rerank\noptional"]
    X --> O["top 20"]`} />
</Figure>

```python
from collections import defaultdict

def rrf(*ranked_lists, k=60):
    scores = defaultdict(float)
    for ids in ranked_lists:                       # each list: doc ids, best first
        for rank, doc_id in enumerate(ids, start=1):
            scores[doc_id] += 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

bm25 = [h["_id"] for h in es.search(index="listings", size=50,
        query={"match": {"title": q}})["hits"]["hits"]]
vec  = [h["_id"] for h in es.search(index="listings", size=50,
        knn={"field": "embedding", "query_vector": embed(q), "k": 50, "num_candidates": 200,
             "filter": [{"term": {"in_stock": True}}]})["hits"]["hits"]]
final = rrf(bm25, vec)[:20]
```

The `embedding` field is a `dense_vector` mapping with a vector index (Elasticsearch 8.x). Some engines also offer RRF built in, sometimes on paid tiers, so check current docs; fusing in application code as above is always possible and easy to reason about.

**Filters meet vectors.** "Semantic search, but only in-stock items under 50" is harder than it sounds: an ANN index returns the nearest k overall, and filtering afterwards can leave three results instead of twenty. Engines offer filtered ANN search (the `filter` inside `knn` above applies during the search); know the problem exists and name it.

<Trace title="Words or meaning?" steps={hybrid} takeaway="Lexical wins exact tokens; vectors win paraphrase. Hybrid retrieval with RRF fuses ranks, not scores. Filtered ANN is a real problem: name it." />

**A common slip.** "Replace keyword search with embeddings." Exact names, codes and rare terms get worse. Say hybrid, and say why.

**Interview takeaway.** "BM25 for exact and rare terms, vectors for paraphrase. I retrieve with both and fuse by rank (RRF), with filters applied inside both retrievers. Geo is a filter plus a distance decay on the score."

<Fragment slot="short">

<Fragment slot="medium">

Search gets its own index; Postgres stays the source of truth. A `LIKE '%term%'` cannot use a B-tree and scans every row: at 50 million listings that is 50 GB per query. So **sync**: CDC reads the Postgres WAL into Kafka keyed by listing id, and an indexer bulk-writes Elasticsearch with external versions, so duplicates and replays are harmless. New listings are searchable in about **one to two seconds** (CDC lag plus the one-second refresh), and sellers see their own new listings from the database immediately.

**Text**: lowercase, tokenise, stem, the same analyzer at query time. **Ranking**: BM25 with title boosted over description, multiplied by a recency decay and a damped popularity factor. <Fragment slot="deep">

The 2-minute answer, plus the reasoning behind each choice. **Why not the database?** Postgres full-text or MySQL FULLTEXT is a fine first answer for a small catalogue; I move to an engine for tuned relevance, facets, typo tolerance and scale. **Sync.** Dual writes lose and reorder updates with no TTL to heal them; CDC plus a topic keyed by id plus versioned upserts gives per-document order and idempotent replay, and a crashed indexer means stale search, not an outage (alert on consumer lag, reconcile for drift). **Query cost.** A query waits for its slowest shard, so I keep shard counts modest and route per-seller queries. **Relevance.** BM25 plus bounded signals; ranking freshness is separate from index freshness. <AnswerModes id="search-typeahead" q="Design typeahead for the search box.">

<Fragment slot="short">

Typeahead is prefix completion under about 100 ms per keystroke, so it is separate from search: precomputed top-10 completions per prefix, in memory in every region, hot short prefixes cached at the edge, refreshed hourly from query logs. The client debounces and ignores stale responses.

</Fragment>

<Fragment slot="medium">

Typeahead is a separate system from search. I precompute it: an hourly job aggregates query logs with time decay, drops blocklisted terms and anything fewer than N distinct users searched, builds a trie with the **top 10 completions stored at every node**, and ships it as an immutable snapshot. A lookup is a walk of the prefix, in microseconds.

The top million queries is about 100 MB raw and about a gigabyte with the per-node lists, so every serving node in every region holds all of it in memory. Short prefixes (about 18,000 of up to three letters) are cached at the edge with the build number in the key. The client debounces about 30 ms, cancels stale requests and paints only the response for the current prefix.

At 20 million daily users that is about 28,000 keystrokes a second at peak, roughly half of which become requests. Fresh trends come from a small streaming top-K merged at query time. Freshness of hours is the right trade.

</Fragment>

**Five follow-ups you will get:**

<Reveal q="1 · Why not just use Postgres full-text search?">

For a modest catalogue with simple ranking, I might: a `tsvector` column with a GIN index (or `pg_trgm` for fuzzy matching) is one system and transactionally consistent. I would move to a dedicated engine when we need relevance tuning, facets over large result sets, typo tolerance and synonyms, horizontal scale for search traffic, or simply to keep search load off the primary. What I would never do is plain `LIKE '%term%'`.

</Reveal>

<Reveal q="2 · The search cluster is destroyed. What happens?">

Nothing is lost: the index is derived from Postgres. We rebuild: assuming about 20,000 documents per second (refresh off and replicas at zero during the load), 50 million listings take around 42 minutes, and restoring from snapshots is faster still. Meanwhile search is degraded, not down for the business: a banner, category browsing, cached popular result pages.

</Reveal>

<Reveal q="3 · Search p99 is three times p50. Where do you look?">

The fan-out. A query waits for its slowest shard, so tail latency compounds with shard count. I would check for one slow node or hot shard, keep the shard count modest, let the engine pick the fastest replica, add timeouts with partial results where an approximate ranking is fine, and route single-tenant queries ("my listings") to one shard. Deep pagination and expensive aggregations are the other usual suspects.

</Reveal>

<Reveal q="4 · You need to change the analyzer for titles. How, with no downtime?">

Postings are built by the analyzer, so existing documents must be reindexed. Clients use an alias. I create `listings_v2`, record the change-stream position, backfill v2 from a snapshot of the database, replay the stream into v2 from that position (external versions dedupe the overlap), verify counts and sample queries, then swap the alias atomically. v1 stays for rollback for a while.

</Reveal>

<Reveal q="5 · Your typeahead is stale for a breaking trend. And how would you shard it at ten times the size?">

The offline trie is refreshed hourly, so add a small streaming layer: count queries over the last few minutes (count-min sketch plus a heap of leaders) and merge those few fresh completions into the trie's list at query time. At ten times the size, shard by prefix, with ranges of first characters balanced by traffic, not by alphabet. Or store prefix → top-K in a key-value store and shard by hash of the prefix, which spreads load evenly because every lookup is an exact key.

</Reveal>

| When you see... | Say... |
|---|---|
| "Users can search X" | Separate search index fed by CDC; the DB stays the source of truth |
| `LIKE '%term%'` | Leading wildcard defeats a B-tree; full scan. Full-text/trigram index or a search engine |
| "How does search work?" | Analyzer → inverted index (term → sorted postings with positions); AND = intersection, phrase = positions |
| "Which result first?" | BM25 (rare terms weigh more, TF saturates, length normalised) × gentle business signals |
| More query traffic | More replicas, not more primaries |
| p99 much worse than p50 | Fan-out tail: fewer shards, replica selection, timeouts with partial results, routing |
| "Shard by term or document?" | Document (plus time for tweets); term partitioning makes writes wide and hot terms hot shards |
| "How fresh is search?" | CDC lag + 1 s refresh ≈ 1 to 2 s; say it; author reads own writes from the DB |
| Writes to DB and ES from the app | Dual-write races with no TTL to heal them → CDC + queue keyed by id + external versions |
| Search cluster lost | Reindex from the source of truth; degraded, not lost |
| Page 500, exports | search_after + point-in-time; cap browsable depth |
| Typeahead | Separate system: top-K per trie node, built offline, in memory per region, hot prefixes at the edge |
| Autocomplete over own documents with filters | Edge n-grams at index time only, plain analyzer at query time |
| Typos | Edit distance with transpositions (AUTO fuzziness), short exact prefix, or trigram candidates |
| In stock, permissions, price range | Filters (no score, cached), never boosts |
| Sidebar counts | Aggregations on doc values; approximate across shards; post_filter for the ticked facet |
| "Near me" | Geo filter + distance decay in the score |
| "Things like this", paraphrases | Vector ANN + BM25 hybrid, fused with RRF |

**Common mistakes**

1. **"We'll use LIKE" or "add an index on the text column."** Name the kind of index, or use a search engine.
2. **Treating the search index as the source of truth.** It is derived and rebuildable; the database is the truth.
3. **Dual writes to the database and the index.** Use one ordered change stream with versions, and say the one-to-two-second lag out loud.
4. **More primary shards for more traffic.** Replicas carry reads; primaries only add fan-out.
5. **Typeahead as "search on every keystroke".** It is precomputed top-K per prefix, in memory, near the user.

**Practice.** With a friend, run the 10-minute mini-design: **typeahead for an e-commerce search box**: trie + top-K, the offline aggregation loop, a memory estimate for 1 million products, and where the 100 ms budget goes (edge cache? a replica per region?). Then do it once more as Twitter search, out loud: term or document partitioning, and why.
