<h2 id="prologue">Overview · What behavioral patterns are for</h2>

A clinic system that has just gone live collects five kinds of bug. A bill split three ways sums to ₹99.99. A completed appointment is moved back to *confirmed* and billed again. A feedback SMS goes out for a visit whose save failed. An API request reads another clinic's patients. And the front desk wants undo. They map to five verbs: *split, move, react, check, undo*. Creational patterns build the objects and structural patterns connect them; neither is broken here. What is broken is what happens next. For each verb, ask: what changes next, and who needs to know?

**Behavioral patterns vary *what happens* — the algorithm, the reaction, the sequence, the history — at runtime, without `if/else` towers.** They are the lesson machine-coding rounds live in: nearly every classic problem (parking lot, Splitwise, vending machine, elevator, text editor, chess) is two or three of these wearing a costume.

Each one is named after the question it answers:

| Pattern | The question | The mess without it |
|---|---|---|
| **Strategy** | Which rule applies this time? | An `if` ladder over a type code that every new rule reopens |
| **Template Method** | Which steps differ in a fixed sequence? | Copy-pasted sequences that drift apart |
| **State** | What may happen next, given where we are? | Status checks scattered through every method; illegal moves that corrupt history |
| **Command** | Can this action be undone, queued, logged or replayed? | Method calls that evaporate the moment they return |
| **Memento** | Can we go back to how it was? | Undo that shares live state with the thing it is undoing |
| **Observer** | Who needs to know when this happens? | A core method that calls every side effect by name |
| **Chain of Responsibility** | Who may veto this, and in what order? | One method that authenticates, resolves, validates and rate-limits |
| **Mediator** | Who decides when many parties interact? | Every party holding references to every other party |
| **Iterator** | How do I walk this without seeing its insides? | Callers that index into your internal arrays |
| **Visitor** | How do I add operations to a stable tree? | A new method on every node class for every new report |

**How these are graded.** Nobody asks you to define Observer. The grader watches whether the follow-up ("now add a fourth split rule", "now notify the pharmacy too", "now add undo") lands as **a new class and one wiring line**. Each chapter below has the same shape: concept, problem, bad design, when to use it, better design in compilable Java, how it works, diagrams, trade-offs (when not to use it), practice, interview summary and revision cards.

**Composition or inheritance?** Most of these patterns use composition: a context holds an object and delegates to it (Strategy, State, Command, Observer, Chain, Mediator). Template Method is the deliberate exception and uses inheritance, in a base class designed for extension. Iterator and Visitor are interfaces that the structure and the operation implement. Chapter 3 compares the three look-alikes: Strategy, State and Template Method.

<h2 id="strategy">Chapter 1 · Splitting the bill</h2>

**Concept.** Strategy puts one interchangeable rule behind one interface. The caller picks the rule at runtime and never learns which one runs.

**Problem.** A clinic bill of ₹100.00 is split between three family members. The system returns three shares of ₹33.33, so the total is ₹99.99 and a paisa is missing. The `split` method is forty lines long and switches on the bill's split type: equal shares; insurance pays first and the family covers the rest; the account holder pays everything. Each branch does its own arithmetic, and two of them use `double`. Finance now wants a percentage split. Every new rule means reopening this method and risking the other branches. Ask how many rules this method will hold next month.

**Bad design.**** One verb — *split* — with every rule inlined:

```java fragment
List<Share> split(Bill bill) {
    switch (bill.splitType()) {
        case EQUAL:
            double each = bill.total() / bill.parties().size();      // 100.00 / 3 = 33.333...
            // ...round each share to 2 places: 33.33 x 3 = 99.99
        case INSURANCE_FIRST:
            // ...find the insurer, cap, then split the rest equally — a second copy of the equal logic
        case FIRST_PAYS_ALL:
            // ...
        default:
            throw new IllegalArgumentException("unknown split");
    }
}
```

**When to use it.** One operation, several interchangeable algorithms, and the choice arrives as **runtime data** (here, the bill's split type). In code you already have: a `switch` or `if` ladder over a type code, especially when each branch is more than a line and new branches keep arriving. In a round: the requirement lists the variants ("equal, percentage, and insurance-first splits").

**Better design.** Each branch becomes a class behind one interface. Money is a `long` count of paise — never a `double`:

```java group=split
record Party(String name, boolean isInsurer, long policyCap) {
    Party {
        if (policyCap < 0) throw new IllegalArgumentException("negative policy cap");
    }
    static Party person(String name) { return new Party(name, false, 0); }
    static Party insurer(String name, long policyCap) { return new Party(name, true, policyCap); }
}

record Share(Party party, long paise) {}

interface SplitStrategy {
    /** Shares sum exactly to total. No share is negative. */
    List<Share> split(long total, List<Party> parties);
}

class EqualSplit implements SplitStrategy {
    public List<Share> split(long total, List<Party> parties) {
        if (total < 0) throw new IllegalArgumentException("negative total");
        if (parties.isEmpty()) {
            if (total == 0) return List.of();
            throw new IllegalArgumentException("no one to split " + total + " paise between");
        }
        long each = total / parties.size();
        long extra = total % parties.size();              // paise that don't divide evenly
        List<Share> shares = new ArrayList<>();
        for (int i = 0; i < parties.size(); i++)
            shares.add(new Share(parties.get(i), each + (i < extra ? 1 : 0)));   // first `extra` parties pay 1 more
        return shares;                                    // shares sum EXACTLY to total
    }
}

class InsuranceFirstSplit implements SplitStrategy {
    private final SplitStrategy forTheRest;
    InsuranceFirstSplit(SplitStrategy forTheRest) { this.forTheRest = forTheRest; }

    public List<Share> split(long total, List<Party> parties) {
        if (total < 0) throw new IllegalArgumentException("negative total");
        Party insurer = parties.stream().filter(Party::isInsurer).findFirst()
            .orElseThrow(() -> new IllegalArgumentException("no insurer party"));
        long covered = Math.min(total, insurer.policyCap());       // insurer pays up to the cap
        List<Share> shares = new ArrayList<>();
        shares.add(new Share(insurer, covered));
        List<Party> family = parties.stream().filter(p -> !p.isInsurer()).toList();
        shares.addAll(forTheRest.split(total - covered, family));  // strategies compose
        return shares;
    }
}
```

That remainder line is a real grading moment: ₹100.00 across three people must sum to ₹100.00, not ₹99.99. In paise, 10 000 / 3 is 3 333 remainder 1, so `EqualSplit` returns **3 334 + 3 333 + 3 333**. Money conservation is the hidden invariant graders test with "does it sum back?". Giving the leftover paise to the first parties keeps every share within one paisa of every other; "the last party absorbs the remainder" is also deterministic and also fine — say which you chose.

Notice `InsuranceFirstSplit` doesn't re-implement equal splitting; it **holds another strategy** and hands it the rest. Strategies compose because they share one interface.

**Strategy + registry** is the standard pair — the same move as the creational lesson's payment registry, and as SOLID's fee map. The caller looks up a strategy by data; it never learns which rules exist:

```java group=split
enum SplitType { EQUAL, INSURANCE_FIRST, FIRST_PAYS_ALL }

record Bill(String id, long total, SplitType splitType, List<Party> parties) {
    Bill {
        if (parties.isEmpty()) throw new IllegalArgumentException("a bill needs at least one party");
        parties = List.copyOf(parties);
    }
}

class BillSplitter {
    private final Map<SplitType, SplitStrategy> strategies;
    BillSplitter(Map<SplitType, SplitStrategy> strategies) { this.strategies = Map.copyOf(strategies); }

    List<Share> split(Bill bill) {
        SplitStrategy strategy = strategies.get(bill.splitType());
        if (strategy == null) throw new IllegalArgumentException("no strategy for " + bill.splitType());
        return strategy.split(bill.total(), bill.parties());
    }
}

BillSplitter standardSplitter() {                     // composition root: the one place that wires types to rules
    SplitStrategy equal = new EqualSplit();
    return new BillSplitter(Map.of(
        SplitType.EQUAL, equal,
        SplitType.INSURANCE_FIRST, new InsuranceFirstSplit(equal),
        SplitType.FIRST_PAYS_ALL, (total, parties) -> List.of(new Share(parties.get(0), total))));   // a lambda is a strategy
}
```

**Lambdas are strategies.** `SplitStrategy` has one abstract method, so it is a functional interface, and `(total, parties) -> List.of(new Share(parties.get(0), total))` is a complete strategy. (It can call `parties.get(0)` safely because `Bill` refuses an empty party list.) Keep a rule as a lambda while it is one or two pure lines; promote it to a named class when it needs a name in stack traces, its own tests, injected dependencies, or real logic.

**The container-friendly registry.** In a Spring-style codebase you rarely write the map by hand: each strategy names its own key, the container injects a `List` of all of them, and the registry builds an immutable map once — failing at startup if two strategies claim the same key:

```java group=split
interface NamedSplit extends SplitStrategy { SplitType type(); }

Map<SplitType, SplitStrategy> registryOf(List<NamedSplit> all) {
    Map<SplitType, SplitStrategy> byType = new EnumMap<>(SplitType.class);
    for (NamedSplit s : all)
        if (byType.put(s.type(), s) != null) throw new IllegalStateException("two strategies claim " + s.type());
    return Map.copyOf(byType);                        // built once, immutable, fails at boot — never lazily
}
```

That last comment is earned: the War Room inventory has <a href={`${BASE}lld/war/inventory/#2-a-lazily-built-strategy-map--data-race`}>a lazily built strategy map that was a data race</a>. Build registries eagerly, in the constructor, and freeze them.

**How it works.** `BillSplitter` is the context. It reads the split type from the bill, asks the registry for the matching `SplitStrategy`, and calls it. The strategy returns shares. The splitter never contains arithmetic, and a strategy never knows who called it.

**The honest wrinkle from production.** Strategies rarely share a clean signature: a percentage split needs the percentages; an equal split doesn't. <a href={`${BASE}lld/war/build-drills/#drill-2--strategy--registry-with-a-real-signature-problem`}>Drill 2</a> makes you fight exactly that — the usual fix is a **context parameter object**, not fifteen overloads. Follow-up 1 does it. And the founding production example is <a href={`${BASE}lld/war/patterns-why/#1-strategy--five-payment-gateways`}>five payment gateways behind one Strategy seam</a>, whose verification algorithms share nothing but a signature.

**Trade-offs: when not to use it.**

- **Two variants that will never grow.** A single `if` is clearer than an interface, two classes and a map. Strategy pays off at the third variant, or when the interviewer signals the axis.
- **Variants that differ only in data.** Two "strategies" that both compute `hours × rate` with different rates are one class with a constructor argument (SOLID's `HourlyFee`).
- **An enum with an abstract method** is a fine Strategy for 2–3 small, fixed variants with no dependencies. It stops being fine when variants need injected keys, clients or SDKs — the War Room's Strategy follow-up.

**Practice.** The clinic's pharmacy gives discounts by patient category: general patients pay the full total; seniors get 10% off; staff get 25% off, capped at ₹500 (50 000 paise). Write the rules as lambdas in a registry.

<HintLadder hints={hints.discounts} labels={turn}>

```java group=split
enum PatientCategory { GENERAL, SENIOR, STAFF }

Map<PatientCategory, LongUnaryOperator> discounts() {
    return Map.of(
        PatientCategory.GENERAL, total -> total,
        PatientCategory.SENIOR,  total -> total - total / 10,                      // 10% off, discount rounded down
        PatientCategory.STAFF,   total -> total - Math.min(total / 4, 50_000));    // 25% off, at most ₹500
}
```

A senior's ₹1,000.00 (100 000 paise) becomes 90 000; staff pay 75 000 on the same bill; on a ₹5,000.00 bill (500 000 paise) the staff discount hits its cap and they pay 450 000. Each rule is one line, pure and stateless — exactly when lambdas beat classes. The day the staff rule needs to look up an employee's grade, it becomes a class with an injected directory.

</HintLadder>

<h2 id="template-method">Chapter 2 · Every report, same skeleton</h2>

**Concept.** Template Method fixes the order of steps in a base class and lets subclasses fill in only the steps that differ.

**Problem.** A clinic system produces three nightly reports: daily revenue, doctor utilisation and pharmacy stock. Each one fetches rows, tidies them, renders a page and delivers it, and delivery writes an audit line because a regulator once asked who received what. The three report classes were copy-pasted from each other. In March someone refactored the stock report's rendering and deleted a line that looked like noise. The stock report has not been audited since. Ask which steps are allowed to differ, and which one must be impossible to forget.

**Bad design** — compiled, so the checker can prove the missing audit:

```java id=reportMess
List<String> audit = new ArrayList<>();

String revenueReport(List<Long> invoices) {
    long total = 0;
    for (long paise : invoices) total += paise;                  // fetch + transform
    String out = "REVENUE " + total;                              // render
    audit.add("REPORT_DELIVERED revenue");                        // deliver
    return out;
}

String stockReport(Map<String, Integer> stock) {
    StringBuilder out = new StringBuilder("STOCK");
    stock.forEach((drug, units) -> out.append(' ').append(drug).append('=').append(units));
    return out.toString();                                        // copy-pasted... and the audit line is gone
}
```

**When to use it.** The **same sequence** of steps in several places, where only one to three steps differ per variant — and at least one step (the audit) that must never be skipped.

**Better design: Template Method.** The parent owns the sequence; children fill the holes:

```java group=reports
import java.time.*;

record Rendered(String name, String body) {}
record Report(String name, String body, long auditSeq) {}

abstract class ReportJob<T> {
    private final List<String> auditLog;                  // the skeleton's own state

    protected ReportJob(List<String> auditLog) { this.auditLog = auditLog; }

    final Report run(LocalDate day) {                     // final: the sequence is not negotiable
        List<T> raw = fetch(day);
        List<T> clean = transform(raw);
        Rendered out = render(day, clean);
        return deliver(out);                              // fixed step: no subclass can skip the audit
    }

    protected abstract List<T> fetch(LocalDate day);      // the holes subclasses must fill
    protected abstract Rendered render(LocalDate day, List<T> rows);
    protected List<T> transform(List<T> rows) { return rows; }   // optional hook: default no-op

    private Report deliver(Rendered r) {                  // private: not even visible to children
        auditLog.add("REPORT_DELIVERED " + r.name());
        return new Report(r.name(), r.body(), auditLog.size());
    }
}

class DailyRevenueReport extends ReportJob<Long> {
    private final Map<LocalDate, List<Long>> invoicesByDay;      // stands in for the billing module

    DailyRevenueReport(List<String> auditLog, Map<LocalDate, List<Long>> invoicesByDay) {
        super(auditLog);
        this.invoicesByDay = invoicesByDay;
    }
    protected List<Long> fetch(LocalDate day) { return invoicesByDay.getOrDefault(day, List.of()); }
    protected Rendered render(LocalDate day, List<Long> rows) {
        long total = 0;
        for (long paise : rows) total += paise;
        return new Rendered("revenue", "Revenue " + day + ": " + total + " paise from " + rows.size() + " invoices");
    }
}
```

Three keyword choices carry the pattern, and each one defends something:

<Reveal q="run() is final, deliver() is private, transform() has a default body. Each keyword choice defends something — what?">

**`final run()`** — the sequence is the asset; a subclass overriding it could skip the audit, which is the exact drift that motivated the pattern. **`private deliver()`** — not even *visible* to children: fixed steps that no variant should touch don't get `protected`. **Default-body `transform()`** — an *optional hook*: most reports don't transform, so forcing every subclass to write `return rows;` is noise. The pattern's precision is in the access modifiers — abstract = must fill, protected-with-default = may fill, private/final = hands off.

</Reveal>

This is the one classic pattern where **inheritance is the point**: the parent was *designed for extension* — exactly the case the SOLID lesson's composition chapter carves out. The JDK does it too: `AbstractList` asks you for `get` and `size` and builds the rest of `List` on top.

**Template Method vs Strategy.** They solve the same problem from opposite ends. Template Method varies steps by **inheritance**; Strategy varies them by **composition**. Here is the same skeleton with the holes passed in as functions:

```java group=reports
final class ReportRunner {                                // composition: the steps arrive as objects
    private final List<String> auditLog;
    ReportRunner(List<String> auditLog) { this.auditLog = auditLog; }

    <T> Report run(String name, LocalDate day,
                   Function<LocalDate, List<T>> fetch,
                   Function<List<T>, String> render) {
        String body = render.apply(fetch.apply(day));
        auditLog.add("REPORT_DELIVERED " + name);         // still impossible to skip
        return new Report(name, body, auditLog.size());
    }
}

Report revenueWithLambdas(ReportRunner runner, Map<LocalDate, List<Long>> invoices, LocalDate day) {
    return runner.run("revenue", day,
        d -> invoices.getOrDefault(d, List.of()),
        rows -> "Revenue " + day + ": " + rows.stream().mapToLong(Long::longValue).sum()
                + " paise from " + rows.size() + " invoices");
}
```

The checker runs both versions on the same invoices and gets the same report body.

| | Template Method | Strategy (runner + functions) |
|---|---|---|
| Varies steps by | Inheritance — subclass fills abstract methods | Composition — objects or lambdas passed in |
| Chosen | When the class is written (a `DailyRevenueReport` is always revenue) | At runtime, per call or per instance |
| Good when | Several hooks, optional hooks with defaults, shared protected state | One or two small steps, mixed and matched freely |
| Cost | A subclass per variant; coupled to the parent | Long parameter lists if the steps multiply |

**How it works.** The caller calls the final `run`. `run` calls the hooks in a fixed order, then calls the private `deliver`. Subclasses are called by the parent, never the other way round.

Production was pushed into Template Method by something sneakier than taste — <a href={`${BASE}lld/war/patterns-why/#7-template-method--forced-by-module-dependency-direction`}>module dependency direction</a>: the skeleton lived in a shared library that *could not see* the entity its persistence step needed, so that step had to be an abstract hook in each consuming service. The same class takes a `Supplier` for its data step — a Strategy passed into a Template Method, deliberately.

<Trace title="Recipe with blanks" steps={template} takeaway="Fixed sequence, a few holes: Template Method makes the sequence final and the holes abstract. If the holes are one-liners, a final runner that takes functions does the same job by composition." />

**Trade-offs: when not to use it.**

- **The holes are one-liners.** Use the runner with lambdas; a subclass per report is ceremony.
- **Variants need to mix and match** (revenue data rendered as CSV *or* PDF). Inheritance gives you one axis; two axes need composition (or the structural lesson's Bridge).
- **Hooks keep multiplying.** A base class with eleven protected hooks, half of them called in some subclasses' overrides, is a fragile base class waiting to happen.

**Practice.** The pharmacy wants a *low stock* report: only drugs with fewer than 10 units, lowest first, rendered as `Low stock 2026-03-13: insulin=2, gauze=7`. Write it as a `ReportJob` — and use the hook that was left open for you.

<h2 id="state">Chapter 3 · The visit that was billed twice</h2>

**Concept.** State makes an object's allowed operations depend on its lifecycle stage, and puts every legal transition in one place.

**Problem.** A clinic appointment moves `REQUESTED → CONFIRMED → CHECKED_IN → COMPLETED`, with `CANCELLED` reachable from the first two. Nobody wrote that down. A receptionist reopens a completed visit to fix a typo in the doctor's name. The edit screen saves the whole appointment, including a status field it loaded two hours earlier as `CONFIRMED`. The visit is completed again that afternoon and billed again. Four places set the status: the API, the bulk importer, the nightly scheduler and the edit screen. Three check whether the move is legal. One does not.

**Bad design.**** Status is a public field with a setter, and legality is re-checked — or not — by each caller:

```java fragment
appointment.setStatus(Status.COMPLETED);                  // the API checks first...
if (row.status() != null) appt.setStatus(row.status());  // ...the importer doesn't
```

**When to use it.** Not every status change is legal, and **an illegal one damages data** rather than erroring. Or: the same method does different things depending on a status field — a `switch (status)` at the top of several methods. Production's version of this scar is <a href={`${BASE}lld/war/patterns-why/#10-state--because-a-backwards-transition-corrupts-history`}>a backwards transition that corrupts history</a>: a `DONE` follow-up dragged back and completed again, overwriting `completedAt` and `completedBy`.

**Draw the diagram before the code. The diagram is the spec:** every arrow is a legal transition, every *missing* arrow is a guaranteed exception. No arrow leaves `COMPLETED` — the re-billing bug, made impossible.

    REQUESTED --> CANCELLED: cancel()

**Form 1 — enum + transition table.** The right size for most rounds, and for any lifecycle where only the *edges* vary:

```java group=appt
enum ApptStatus {
    REQUESTED, CONFIRMED, CHECKED_IN, COMPLETED, CANCELLED;

    private static final Map<ApptStatus, Set<ApptStatus>> LEGAL = Map.of(
        REQUESTED,  Set.of(CONFIRMED, CANCELLED),
        CONFIRMED,  Set.of(CHECKED_IN, CANCELLED),
        CHECKED_IN, Set.of(COMPLETED),
        COMPLETED,  Set.of(),                       // terminal: nothing leaves
        CANCELLED,  Set.of()
    );
    boolean canGoTo(ApptStatus next) { return LEGAL.get(this).contains(next); }
}

class Appointment {
    private ApptStatus status = ApptStatus.REQUESTED;

    private void transition(ApptStatus next) {       // ONE gate for every transition
        if (!status.canGoTo(next))
            throw new IllegalStateException(status + " -> " + next + " is not a legal transition");
        this.status = next;
    }
    public void confirm()  { transition(ApptStatus.CONFIRMED); }    // verbs, not setStatus
    public void checkIn()  { transition(ApptStatus.CHECKED_IN); }
    public void complete() { transition(ApptStatus.COMPLETED); }
    public void cancel()   { transition(ApptStatus.CANCELLED); }
    public ApptStatus status() { return status; }
}
```

Two details carry it. **There is no `setStatus`** — callers say what happened (`confirm()`), never what the field should become. And **`transition` checks before it assigns**, so a refused event changes nothing. The checker tries every (state, event) pair: the legal ones are exactly the five event arrows in the diagram, and every other one throws and leaves the status where it was. Terminal states returning an empty set also make "is this finished?" derivable instead of a second fact to maintain.

**A second example: a vending machine.** A vending machine's software has the same `switch (mode)` at the top of `insert`, `select`, `refund` and `restock`. Someone added a `SOLD_OUT` case to three of the four switches, so the machine took a customer's coins when it was empty.

```java fragment
void insert(int coin) {
    switch (mode) {
        case IDLE: case HAS_CREDIT: credit += coin; mode = Mode.HAS_CREDIT; break;
        // SOLD_OUT: nobody added this case here, so the coin is silently kept
    }
}
void select(String slot) {
    switch (mode) {
        case IDLE: throw new IllegalStateException("insert money first");
        case HAS_CREDIT: /* 15 lines: price, stock, change, next mode */ break;
        case SOLD_OUT: throw new IllegalStateException("sold out");
    }
}
// ...and the same switch again in refund(), restock(), and whatever the next requirement needs.
```

When each state **behaves** differently — not just allows different arrows — the enum's knowledge is smeared across every method. Adding a state means finding every switch. That is the moment for **Form 2 — one class per state.** Each state object answers every event; the defaults refuse:

```java group=vending
interface VendingState {
    default VendingState insert(VendingMachine m, int coin)    { throw illegal("insert"); }
    default VendingState select(VendingMachine m, String slot) { throw illegal("select"); }
    default VendingState refund(VendingMachine m)              { throw illegal("refund"); }
    default VendingState restock(VendingMachine m, String slot, int units) { throw illegal("restock"); }
    default IllegalStateException illegal(String event) {
        return new IllegalStateException(event + " not allowed while " + getClass().getSimpleName());
    }
}

class Idle implements VendingState {                   // no credit, something to sell
    public VendingState insert(VendingMachine m, int coin) { m.addCredit(coin); return new HasCredit(); }
    public VendingState restock(VendingMachine m, String slot, int units) { m.addStock(slot, units); return this; }
}

class HasCredit implements VendingState {              // money in, waiting for a choice
    public VendingState insert(VendingMachine m, int coin) { m.addCredit(coin); return this; }
    public VendingState select(VendingMachine m, String slot) {
        int price = m.priceOf(slot);                    // unknown slot: IllegalArgumentException, nothing changes
        if (m.stockOf(slot) == 0) { m.show(slot + " is sold out"); return this; }
        if (m.credit() < price)  { m.show("insert " + (price - m.credit()) + " more"); return this; }
        m.dispense(slot);                               // stock -1, change returned, credit back to 0
        return m.totalStock() == 0 ? new SoldOut() : new Idle();
    }
    public VendingState refund(VendingMachine m) { m.returnCredit(); return new Idle(); }
}

class SoldOut implements VendingState {                // nothing to sell: coins are refused
    public VendingState restock(VendingMachine m, String slot, int units) {
        m.addStock(slot, units);
        return new Idle();
    }
}
```

And the machine — the *context* — just delegates every event to its current state, and offers the operations the states use:

```java group=vending
class VendingMachine {
    private final Map<String, Integer> prices;
    private final Map<String, Integer> stock = new TreeMap<>();
    private VendingState state;
    private int credit;
    final List<String> dispensed = new ArrayList<>();
    final List<Integer> change = new ArrayList<>();     // every amount handed back: change or refund
    String display = "";

    VendingMachine(Map<String, Integer> prices, Map<String, Integer> initialStock) {
        this.prices = Map.copyOf(prices);
        for (String slot : prices.keySet()) stock.put(slot, initialStock.getOrDefault(slot, 0));
        state = totalStock() == 0 ? new SoldOut() : new Idle();
    }

    // Events: the machine only delegates. Each state decides what the event means.
    void insert(int coin) {
        if (coin <= 0) throw new IllegalArgumentException("not a coin: " + coin);
        state = state.insert(this, coin);
    }
    void select(String slot)             { state = state.select(this, slot); }
    void refund()                        { state = state.refund(this); }
    void restock(String slot, int units) { state = state.restock(this, slot, units); }
    String state()                       { return state.getClass().getSimpleName(); }

    // Operations the states use.
    int credit() { return credit; }
    int priceOf(String slot) {
        Integer price = prices.get(slot);
        if (price == null) throw new IllegalArgumentException("no slot " + slot);
        return price;
    }
    int stockOf(String slot) { priceOf(slot); return stock.get(slot); }
    int totalStock() {
        int sum = 0;
        for (int n : stock.values()) sum += n;
        return sum;
    }
    void addCredit(int coin) { credit += coin; display = "credit " + credit; }
    void addStock(String slot, int units) {
        priceOf(slot);
        if (units <= 0) throw new IllegalArgumentException("restock needs units > 0");
        stock.merge(slot, units, Integer::sum);
    }
    void show(String message) { display = message; }
    void dispense(String slot) {
        stock.merge(slot, -1, Integer::sum);
        dispensed.add(slot);
        int owed = credit - priceOf(slot);
        if (owed > 0) change.add(owed);
        credit = 0;
        display = "enjoy your " + slot;
    }
    void returnCredit() { change.add(credit); credit = 0; display = "refunded"; }
}
```

The sold-out coin bug is now structurally impossible: `SoldOut` doesn't override `insert`, so the default throws and the coin is never counted. Three invariants hold by construction, and the checker tests them on thousands of random event sequences against an independent `switch`-based simulator: **`Idle` always has stock** (you only reach it with stock, and only a sale reduces stock — which leaves `HasCredit` through a stock check); **`HasCredit` always holds credit**; and **money is conserved** — every coin inserted ends up as a sale, as change, or as credit still in the machine.

**How it works.** The machine (the context) holds the current state object and forwards every event to it. The state does the work and returns the next state. The machine stores that return value. Events a state does not override hit the interface default and throw.

**Enum table or state objects?** This exact trade-off is <a href={`${BASE}lld/war/build-drills/#drill-3--state-both-ways`}>Drill 3</a>:

| | Enum + transition table | One class per state |
|---|---|---|
| Right when | Only the **edges** vary; states are names | States **behave** differently (reserve a slot, start billing, refuse coins) |
| Adding a state | One constant, one table row | One class, plus an override in each state that gains an edge |
| Adding an event | One verb method | One default method in the interface, overridden where legal |
| Where the rules live | One table — easy to print as the spec | Spread across the state classes — easy to read per state |
| Middle ground | An enum whose constants override methods (constant-specific bodies): behaviour per state, no extra files, but no injected dependencies | |

Either form, the non-negotiable is the same: **transitions are validated in one place, and nothing else may write the state.** You derived that rule in the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson</a> ("no setter for state, ever"); the War Room's bed-management design doc forbids direct repository status writes by convention for the same reason.

**State is Strategy that swaps itself.** The class diagram is identical — a context holding an interface. The difference is who changes the object behind it: a strategy is chosen *from outside* by data; a state object returns *its own successor*.

<h3 id="compare">Strategy vs State vs Template Method</h3>

All three let one piece of code behave differently without an `if` ladder, which is why they get mixed up. The differences are who picks the variant, when, and how.

| | Strategy | State | Template Method |
|---|---|---|---|
| What varies | A whole algorithm | Behaviour by lifecycle stage | Some steps of a fixed sequence |
| Mechanism | Composition: the context holds an interface | Composition: the context holds a state interface | Inheritance: a subclass overrides hooks of a base class |
| Who picks the variant | The caller or configuration, from outside | The state objects themselves, from inside, as events arrive | The choice of subclass, made when the code is written |
| Changes during the object's life | Rarely | Yes, by design | No |
| Main job | Make rules swappable | Make illegal transitions impossible | Make the sequence unskippable |
| Example in this lesson | `EqualSplit` or `InsuranceFirstSplit` | `Idle`, `HasCredit`, `SoldOut` | `DailyRevenueReport` |
| Typical misuse | A class per constant | State classes where a table would do | A base class with eleven hooks |

**One requirement, three designs.** Take discounts. If the rule is chosen per call by customer type (senior, staff, general), use **Strategy**. If a coupon moves `UNUSED → APPLIED → EXPIRED` and each stage allows different actions, use **State**. If every discount runs the same validate, compute, record sequence and only the compute step differs, use **Template Method**. If you cannot say which of the three questions you are answering (which rule, what is allowed now, which step differs), you are not ready to pick one.

<Trace title="Traffic light" steps={state} takeaway="Draw the diagram first: every arrow legal, every missing arrow an exception. Enum table when only the edges vary, state classes when the behaviour does — either way, one gate." />

**Trade-offs: when not to use it.**

- **Two states and a boolean's worth of behaviour.** `isOpen` with one guard is not a state machine.
- **State classes for a lifecycle that only varies in its edges.** Five classes that differ only by which events they allow are a table pretending to be a design.
- **States that need to persist.** Store the *enum name* in the database, not the class; rebuild the state object on load. Workflow engines exist for lifecycles that are configured by the business rather than coded.

**Practice.** The clinic's appointments now *behave* differently per state: confirming reserves a slot; checking in assigns a room; completing releases the room; cancelling a confirmed appointment releases its slot. Promote the table to state classes — with the same legal arrows.

<h2 id="command">Chapter 4 · The front desk wants undo</h2>

**Concept.** Command turns an action into an object. Once an action is an object it can be undone, redone, queued, logged or replayed.

**Problem.** A clinic front desk handles forty walk-ins an hour: book, cancel, book again, cancel the wrong one. The staff want undo and redo. The controller looks like this:

```java fragment
class FrontDeskController {
    void book(BookingRequest r) { scheduler.book(r); }        // the call happens, then it is gone
    void cancel(String id)      { scheduler.cancel(id); }     // nothing remembers what was done, so nothing can be undone
}
```

A method call evaporates the moment it returns. To undo anything, something has to remember what was done.

**When to use it.** The words **undo, redo, history, queue, retry, replay, audit log of user actions, macro**. A method call can do none of those things. To undo, queue, log or replay an action, **the action itself must be an object** — with everything it needs to run, and everything it needs to take itself back.

First, the receiver: the part that knows scheduling and nothing about undo.

```java group=desk
import java.time.*;

record BookingRequest(String patient, String doctor, LocalDateTime slot) {}
record Appointment(String id, String patient, String doctor, LocalDateTime slot) {}

class Scheduler {                                          // the receiver
    private final Map<String, Appointment> byId = new TreeMap<>();
    private int nextId = 1;

    Appointment book(BookingRequest r) {
        Appointment a = new Appointment("A-" + nextId, r.patient(), r.doctor(), r.slot());
        ensureFree(a);
        nextId++;
        byId.put(a.id(), a);
        return a;
    }
    Appointment cancel(String id) {
        Appointment a = byId.remove(id);
        if (a == null) throw new IllegalArgumentException("no appointment " + id);
        return a;
    }
    void rebook(Appointment a) {                           // restore exactly this appointment, same id
        if (byId.containsKey(a.id())) throw new IllegalStateException(a.id() + " is already booked");
        ensureFree(a);
        byId.put(a.id(), a);
    }
    Appointment move(String id, LocalDateTime newSlot) {   // returns the appointment as it was
        Appointment before = byId.get(id);
        if (before == null) throw new IllegalArgumentException("no appointment " + id);
        Appointment after = new Appointment(id, before.patient(), before.doctor(), newSlot);
        ensureFree(after);
        byId.put(id, after);
        return before;
    }
    Map<String, Appointment> snapshot() { return Map.copyOf(byId); }

    private void ensureFree(Appointment a) {
        for (Appointment other : byId.values())
            if (!other.id().equals(a.id()) && other.doctor().equals(a.doctor()) && other.slot().equals(a.slot()))
                throw new IllegalStateException(a.doctor() + " is busy at " + a.slot());
    }
}
```

**Better design.** Each front-desk action becomes a command that knows how to `execute` itself and how to `undo` itself — and **remembers what its own execution did**:

```java group=desk
interface Command {
    void execute();
    void undo();
}

class BookAppointment implements Command {
    private final Scheduler scheduler;
    private final BookingRequest request;
    private Appointment booked;                            // the memory undo needs: what THIS execution created

    BookAppointment(Scheduler scheduler, BookingRequest request) {
        this.scheduler = scheduler;
        this.request = request;
    }
    public void execute() {
        if (booked == null) booked = scheduler.book(request);   // first run: a fresh booking
        else scheduler.rebook(booked);                          // redo: the same appointment, same id
    }
    public void undo() { scheduler.cancel(booked.id()); }
    Appointment booked() { return booked; }
}

class CancelAppointment implements Command {
    private final Scheduler scheduler;
    private final String apptId;
    private Appointment cancelled;                         // snapshot for the restore

    CancelAppointment(Scheduler scheduler, String apptId) {
        this.scheduler = scheduler;
        this.apptId = apptId;
    }
    public void execute() { cancelled = scheduler.cancel(apptId); }
    public void undo()    { scheduler.rebook(cancelled); }
}
```

The **invoker** knows nothing about scheduling. It runs commands and keeps two stacks:

```java group=desk
class FrontDesk {
    private final Deque<Command> undoStack = new ArrayDeque<>();
    private final Deque<Command> redoStack = new ArrayDeque<>();

    void run(Command c) {
        c.execute();                                       // if this throws, nothing is recorded
        undoStack.push(c);
        redoStack.clear();                                 // a new action forks history: the old future is gone
    }
    boolean undo() {
        Command c = undoStack.peek();
        if (c == null) return false;
        c.undo();                                          // if undo throws, both stacks are left as they were
        redoStack.push(undoStack.pop());
        return true;
    }
    boolean redo() {
        Command c = redoStack.peek();
        if (c == null) return false;
        c.execute();
        undoStack.push(redoStack.pop());
        return true;
    }
}
```

Four details are graded, and each one is a bug if you miss it:

1. **Undo uses execute-time memory, not the request.** `BookAppointment` keeps `booked` — the concrete appointment with its id. A request ("Asha with Dr Rao at 10:00") can't tell you *which* appointment to cancel.
2. **Redo reproduces the same effect.** The second `execute()` re-books the *same* appointment, same id, instead of creating a fresh `A-7`. Anything else that pointed at `A-3` (an SMS, an invoice) would dangle.
3. **A new command clears the redo stack.** Type after undoing, and redo is gone — in every editor you have used.
4. **Peek, act, then pop.** If `undo()` throws, the stacks are untouched and the history is still true.

The checker runs thousands of random sequences of book, cancel, reschedule, undo and redo through `FrontDesk`, and compares the schedule after every step with a **snapshot model** — an independent oracle that simply saves a copy of the whole schedule before every command and restores copies on undo and redo. Command-based undo and snapshot-based undo agree on every step.

**How it works.** The invoker (`FrontDesk`) calls `execute` on a command and pushes it on the undo stack. The command calls the receiver (`Scheduler`) and remembers what it did. On undo, the invoker pops the command, calls `undo`, and pushes it on the redo stack.

`rebook` finds the slot taken and throws `IllegalStateException`. Because `undo()` peeks before it pops, the cancel stays on the undo stack and nothing changes. **Between execute and undo the world moved** — that is why a command remembers its effect, and why undo must be allowed to fail honestly. In a single-user editor undo always works; in a shared system, undo is a new request that can be refused.

**Queued commands, and idempotency.** The same object can be put on a queue and executed later, by another worker — that is how job queues work. But queues deliver *at least once*: if the acknowledgement is lost, the command arrives again. A booking that runs twice is a double booking. Make the processing **idempotent** — give every command an id and skip ids already applied:

```java group=desk
record QueuedCommand(String commandId, Command command) {}

class CommandWorker {                                      // drains a queue; deliveries may repeat
    private final Deque<QueuedCommand> queue = new ArrayDeque<>();
    private final Set<String> applied = new HashSet<>();   // in production: a table with a unique key

    void submit(QueuedCommand q) { queue.add(q); }

    int drain() {
        int ran = 0;
        while (!queue.isEmpty()) {
            QueuedCommand q = queue.peek();
            if (!applied.contains(q.commandId())) {
                q.command().execute();                     // if this throws, q stays at the head for a retry
                applied.add(q.commandId());                // in production: same transaction as the effect
                ran++;
            }
            queue.poll();
        }
        return ran;
    }
}
```

The order matters: record the id only **after** the effect succeeds, or a failed command is marked done and never retried. In production the effect and the id must be committed **atomically** (one transaction), otherwise a crash between them leaves "done but not recorded". The other route to idempotency is making the effect itself idempotent — "set status to PAID" can run twice harmlessly; "add ₹500 to balance" cannot.

**Two production footnotes.** Real undo across a service boundary is a **compensating action**, not a rollback — the <a href={`${BASE}lld/war/patterns-why/#11-saga-compensation--transactional-cant-reach-outside-the-database`}>Saga compensation dossier</a>, where the method returns *what it created* so the caller can compensate it (<a href={`${BASE}lld/war/build-drills/#drill-6--compensating-action`}>Drill 6</a>). And beware naming: a class called `*Command` without an `execute()` <a href={`${BASE}lld/war/patterns-why/#18-the-one-that-lies--command-without-execute`}>may be lying to you</a> — it's a parameter object. Read the structure, not the label.

**Trade-offs: when not to use it.**

- **No undo, no queue, no log, no replay.** Wrapping every service call in a command object "for flexibility" is ceremony. The discriminator: *can this action be queued, retried or reversed?*
- **Undo that is really "restore how it was".** If reversing each action is hard but snapshotting state is easy, use Memento (next chapter) — or let commands store a memento for their own undo.

**Practice.** The front desk wants **reschedule**: move an appointment to a new slot, undoably. The scheduler already has `move(id, newSlot)`, which refuses a busy slot and returns the appointment as it was.

```java group=desk
class RescheduleAppointment implements Command {
    private final Scheduler scheduler;

    private final LocalDateTime newSlot;
    private Appointment before;                            // where it was, so undo can put it back

    RescheduleAppointment(Scheduler scheduler, String apptId, LocalDateTime newSlot) {
        this.scheduler = scheduler;

        this.newSlot = newSlot;
```

<h2 id="memento">Chapter 5 · The draft at 10:15</h2>

**Concept.** Memento takes a snapshot of an object's state, stored by someone who cannot read it, so the object can be restored later.

**Problem.** A doctor writes a prescription in a draft editor: add a line, remove a line, change the note to the pharmacist. At 10:40 she wants the 10:15 version back. An earlier attempt at "restore" deleted the entire prescription, because `save()` returned `lines`, not a copy of `lines`.

**Bad design** — compiled, so the checker can show the wipe:

```java id=draftMess
class LeakyDraft {
    final List<String> lines = new ArrayList<>();
    List<String> save() { return lines; }                       // the "snapshot" is the live list itself
    void restore(List<String> saved) {
        lines.clear();                                         // ...which also empties `saved`
        lines.addAll(saved);                                   // ...so this adds nothing
    }
}
```

Add `"A"`, save, add `"B"`, restore: the draft is **empty**. The snapshot was a view of the very state it was supposed to protect.

**When to use it.** "Restore it to how it was", "checkpoint", "revert to the saved version", "undo" where reversing each action is awkward but copying the state is easy. Plus one constraint: the thing being saved shouldn't have to expose its internals to whoever stores the saves.

**Better design: Memento.** Three roles. The **originator** (the draft) makes and restores snapshots of itself. The **memento** is an opaque, immutable snapshot. The **caretaker** (the history) stores mementos but never looks inside:

```java group=draft
class PrescriptionDraft {                                  // the originator
    private final List<String> lines = new ArrayList<>();
    private String note = "";

    void add(String line) { lines.add(line); }
    void remove(int index) { lines.remove(index); }
    void setNote(String note) { this.note = note; }
    List<String> lines() { return List.copyOf(lines); }
    String note() { return note; }

    Snapshot save() { return new Snapshot(List.copyOf(lines), note); }   // copy — never share live state
    void restore(Snapshot s) {
        lines.clear();
        lines.addAll(s.lines);
        note = s.note;
    }

    static final class Snapshot {                          // the memento: no getters, no setters
        private final List<String> lines;
        private final String note;
        private Snapshot(List<String> lines, String note) {
            this.lines = lines;
            this.note = note;
        }
    }
}

class DraftHistory {                                       // the caretaker: stores snapshots, never looks inside
    private final PrescriptionDraft draft;
    private final Deque<PrescriptionDraft.Snapshot> past = new ArrayDeque<>();

    DraftHistory(PrescriptionDraft draft) { this.draft = draft; }

    void checkpoint() { past.push(draft.save()); }
    boolean undo() {
        if (past.isEmpty()) return false;
        draft.restore(past.pop());
        return true;
    }
}
```

`Snapshot` has a private constructor and private fields with no accessors, so no code outside `PrescriptionDraft` can make one or read one — the caretaker can only hold it. (Nested classes of the *same* top-level class can read each other's private members in Java, so keep the snapshot nested inside its originator and the caretaker outside.) The copy is `List.copyOf` — immutable, and safe because `String` is immutable too. **A memento of mutable objects needs a deep copy**, or you are back to `LeakyDraft` one level down.

**How it works.** The caretaker (`DraftHistory`) asks the originator (`PrescriptionDraft`) to `save()`, and stacks the returned snapshot without looking inside. To undo, it pops a snapshot and hands it back to `restore()`.

**Memento vs Command** — both give you undo, from opposite ends:

| | Command | Memento |
|---|---|---|
| Remembers | The **action** and its effect | The **state** at a moment |
| Undo by | Running the inverse of that action | Restoring the snapshot |
| Good when | Actions are reversible, must be logged, queued or replayed | The inverse is hard to compute, or you want "how it was at 10:15" |
| Cost | An inverse per action | Memory per snapshot; deep copies |
| Reaches outside the process? | Yes — via compensation | No — a snapshot can't un-send an SMS |

They combine well: a command can store a memento of the receiver's state in `execute()` and restore it in `undo()`. That is often the simplest correct undo for complex in-memory edits.

<Trace title="The snapshot" steps={memento} takeaway="A memento is a copy, never a view. Use it to restore state; use Command to reverse actions — and remember a snapshot cannot reach outside your process." />

**Trade-offs: when not to use it.**

- **Large state, frequent checkpoints.** Snapshotting a 50 MB document on every keystroke is a memory leak with a nice name. Store diffs (that is Command again), or bound the history (your turn).
- **State that isn't yours.** Rows in a database or another service's records are restored by transactions or compensation, not by Java snapshots.

**Practice.** The draft history grows forever. Keep only the last `limit` snapshots, forgetting the oldest.

<HintLadder hints={hints.bounded} labels={turn}>

```java group=draft
class BoundedDraftHistory {
    private final PrescriptionDraft draft;
    private final int limit;
    private final Deque<PrescriptionDraft.Snapshot> past = new ArrayDeque<>();

    BoundedDraftHistory(PrescriptionDraft draft, int limit) {
        if (limit <= 0) throw new IllegalArgumentException("limit must be positive");
        this.draft = draft;
        this.limit = limit;
    }
    void checkpoint() {
        past.push(draft.save());
        if (past.size() > limit) past.removeLast();        // forget the oldest
    }
    boolean undo() {
        if (past.isEmpty()) return false;
        draft.restore(past.pop());
        return true;
    }
}
```

`push` adds at the front of the deque and `removeLast` drops from the back, so the newest snapshots survive. The checker compares it with an unbounded history on random edit sequences: they agree for the first `limit` undos, and then the bounded one honestly says `false`.

</HintLadder>

<h2 id="observer">Chapter 6 · The visit ends, the clinic reacts</h2>

**Concept.** Observer lets a subject announce events to listeners that register themselves. The subject does not know who listens.

**Problem.** When a clinic appointment completes, five things must happen: generate the invoice, send the feedback SMS, update the doctor's analytics, decrement consumables, schedule the follow-up. `complete()` calls all five by name:

```java fragment
void complete(String apptId) {
    repo.markCompleted(apptId);
    invoicing.generate(apptId);              // if anything below throws, the calls after it never run
    sms.sendFeedbackRequest(apptId);         // a slow vendor freezes the caller
    analytics.record(apptId);
    pharmacy.decrementConsumables(apptId);
    followUps.schedule(apptId);              // a sixth reaction means editing this method again
}
```

On Tuesday the SMS vendor was slow and every screen froze for eight seconds per completion. On Wednesday the analytics call threw, and the invoice, which came after it in the list, was never generated. On Thursday the pharmacy asked to be added as a sixth reaction. In one case a feedback SMS went out for a visit whose save had failed. The core method knows too much about its reactions.

**When to use it.** "When X happens, do these N things — and more later." N interested parties, **unknown to the producer**, needing to know *when* rather than *whether*. In code: a core method that calls a growing list of unrelated side effects by name.

**Better design: Observer (publish–subscribe).** The subject keeps a list of listeners and announces events; listeners register themselves. The core flow stops knowing who reacts:

```java group=events
record AppointmentCompleted(String apptId, String patientId, String doctorId) {}

interface AppointmentListener { void onCompleted(AppointmentCompleted event); }

class AppointmentEvents {                                  // the subject's listener list
    private final List<AppointmentListener> listeners = new CopyOnWriteArrayList<>();
    private final Executor delivery;                       // Runnable::run = synchronous; a pool = asynchronous
    final List<String> errors = new CopyOnWriteArrayList<>();   // stands in for log.error

    AppointmentEvents(Executor delivery) { this.delivery = delivery; }

    Runnable subscribe(AppointmentListener l) {            // returns the way out
        listeners.add(l);
        return () -> listeners.remove(l);
    }
    int listenerCount() { return listeners.size(); }

    void publish(AppointmentCompleted e) {
        for (AppointmentListener l : listeners)            // iterates a snapshot: (un)subscribing mid-loop is safe
            delivery.execute(() -> notifySafely(l, e));
    }

    private void notifySafely(AppointmentListener l, AppointmentCompleted e) {
        try {
            l.onCompleted(e);
        } catch (RuntimeException ex) {                    // one broken listener must not break the others —
            errors.add("listener failed: " + ex.getMessage());   // or the core flow
        }
    }
}

class AppointmentService {
    private final Map<String, String> repo = new ConcurrentHashMap<>();     // stands in for the database
    private final AppointmentEvents events;

    AppointmentService(AppointmentEvents events) { this.events = events; }

    String statusOf(String apptId) { return repo.get(apptId); }

    void complete(String apptId, String patientId, String doctorId) {
        repo.put(apptId, "COMPLETED");                     // 1. the state change (guarded, Chapter 3), persisted
        events.publish(new AppointmentCompleted(apptId, patientId, doctorId));   // 2. THEN tell the world
    }
}
```

Reactions are now plug-ins. The sixth one is a new line, not an edit to `complete()`:

```java group=events
void wireClinic(AppointmentEvents events, List<String> outbox) {
    events.subscribe(e -> outbox.add("invoice for " + e.apptId()));
    events.subscribe(e -> outbox.add("SMS to " + e.patientId() + ": How was your visit?"));
    events.subscribe(e -> outbox.add("analytics: visit for " + e.doctorId()));
}
```

**How it works.** The service saves its change, then calls `publish`. The event list copies on write, so `publish` loops over a snapshot of the listeners and hands each one the event through an executor. A listener that throws is caught and recorded; the others still run.

Six details make Observer work in production, and interviewers ask about every one:

**1. Notify after persisting** — and in real systems, **after the transaction commits.** Observers of an unsaved change observe a lie. The production timing subtlety is <a href={`${BASE}lld/war/patterns-why/#13-observer--the-existing-integration-only-fired-after-the-call-ended`}>the Observer dossier</a>: if the SMS fires inside the transaction and the transaction rolls back, the patient is asked about a visit that never completed. In Spring that's `@TransactionalEventListener(phase = AFTER_COMMIT)`; the durable version is a transactional outbox.

**2. The listener-throws problem.** With a plain loop, one listener's exception skips every listener after it *and* propagates into `complete()`. `notifySafely` catches per listener: a dropped SMS is an annoyance; a failed completion is an incident. (It catches `RuntimeException`, not `Throwable` — an `OutOfMemoryError` should still take the process down.)

**3. Unsubscribe — and the leak when nobody does.** The subject's list holds a **strong reference** to every listener, and every listener (a lambda) holds whatever it captured. A dashboard tab that subscribes on open and never unsubscribes stays in memory forever — the *lapsed listener* leak. `subscribe` returns the way out:

```java group=events
class DoctorScreen implements AutoCloseable {             // a dashboard tab that lives for minutes
    final List<String> shown = new CopyOnWriteArrayList<>();
    private final Runnable unsubscribe;

    DoctorScreen(AppointmentEvents events, String doctorId) {
        unsubscribe = events.subscribe(e -> { if (e.doctorId().equals(doctorId)) shown.add(e.apptId()); });
    }
    public void close() { unsubscribe.run(); }             // forget this and every closed tab stays subscribed
}
```

The checker opens and abandons 1 000 screens without closing them: the subject ends up holding **1 000** listeners. With try-with-resources it holds 0. The War Room's production subscriber deregisters on **all three exits** — completion, timeout and error — and gives every subscription a bounded lifetime. (Weak-reference listener lists exist, but they make lambda listeners vanish at random garbage collections; an explicit handle is the honest fix.)

**4. The thread-safe list.** The listener list is read on every event and changed rarely. That is exactly what `CopyOnWriteArrayList` is for:

| List | Iteration while (un)subscribing | Concurrent use | Fits a listener list? |
|---|---|---|---|
| `ArrayList` | `ConcurrentModificationException` (or a silently skipped listener) | Not thread-safe | No |
| `Collections.synchronizedList` | Iteration needs a manual `synchronized` block — and a listener that unsubscribes mid-loop still breaks the iterator | Safe per call | No |
| `CopyOnWriteArrayList` | Iterates a snapshot; changes appear on the next publish | Lock-free reads, each write copies the array | **Yes** — read-mostly |

Here is the `ArrayList` version, compiled so the checker can break it:

```java id=listenerMess
interface Listener { void on(String event); }

class NaiveEvents {
    private final List<Listener> listeners = new ArrayList<>();
    Runnable subscribe(Listener l) { listeners.add(l); return () -> listeners.remove(l); }
    void publish(String event) {
        for (Listener l : listeners) l.on(event);          // no try/catch, and iterating the live list
    }
}
```

With three listeners where the first unsubscribes itself, the next call to the iterator throws `ConcurrentModificationException` and the other two never run. With *two* listeners it's worse: the loop just stops, and the second listener is skipped **silently**. And a listener that throws takes `publish` — and the caller — down with it. The checker demonstrates all three.

**5. Synchronous or asynchronous delivery.** `AppointmentEvents` takes an `Executor`. With `Runnable::run`, delivery is **synchronous**: listeners run on the caller's thread, in order, and `complete()` waits for all of them — so a 2-second SMS listener makes every completion 2 seconds slower. With a thread pool, delivery is **asynchronous**: `complete()` returns at once; but listeners now run concurrently, in no guaranteed order, on other threads. So the event must be **immutable** (a record of strings is), listeners must be thread-safe, and errors surface on worker threads — which is why `notifySafely` records them instead of throwing. The checker publishes to a pool and proves the publisher returned before a deliberately blocked listener finished.

**6. The rungs.** The dossier's escalation ladder — in-process synchronous listeners, then after-commit listeners, then a broker fanning out across processes — is the same idea at three scales. Interviewers climb it; know which rung the question is on.

**Observer vs pub/sub.** The two are often used as synonyms, but they sit at different scales. In Observer the subject holds its listeners directly. In pub/sub, publisher and subscribers share only a topic or event type, and a bus or broker sits between them:

```java fragment
class EventBus {                                           // in-process pub/sub: subscribers know the event type, not the publisher
    private final Map<Class<?>, List<Consumer<Object>>> subscribers = new ConcurrentHashMap<>();

    <T> void subscribe(Class<T> type, Consumer<T> handler) {
        subscribers.computeIfAbsent(type, k -> new CopyOnWriteArrayList<>()).add(e -> handler.accept(type.cast(e)));
    }
    void publish(Object event) {
        subscribers.getOrDefault(event.getClass(), List.of()).forEach(h -> h.accept(event));
    }
}
```

| | Observer | Pub/sub (event bus or broker) |
|---|---|---|
| Who knows whom | The subject holds references to its listeners | Publisher and subscribers know only the topic or event type |
| Where it runs | One process | One process (event bus) or many (message broker) |
| Delivery | Usually synchronous, on the caller's thread | Usually asynchronous, queued; a broker can be durable and retry |
| A failing receiver | Reaches the subject unless you guard each call | Isolated by the bus; a broker gives retries and dead-letter queues |
| Ordering | Registration order when synchronous | Per topic or partition at best |
| Cost | A list and a loop | A bus or broker, serialisation, idempotent consumers |
| Use when | One component announces to a few local listeners | Many producers and consumers, or reactions that must survive a crash |

**Thread-safety caveats for Observer.** Collect them in one place:

- Keep the listener list in a `CopyOnWriteArrayList`, or copy it before iterating. A plain `ArrayList` breaks when a listener unsubscribes mid-delivery.
- Never call listeners while holding a lock. A listener that calls back into the subject can deadlock, and a slow listener holds the lock for everyone (Effective Java, Item 79).
- With asynchronous delivery, events must be immutable, listeners must be thread-safe, and nothing may rely on listener order.
- Subscribing and unsubscribing race with publishing: a listener can still receive one event just after it unsubscribes. Make listeners tolerate that.
- A listener that unsubscribes itself needs an `AtomicBoolean` or similar if it must fire at most once under concurrent delivery.

<Trace title="Newsletter" steps={observer} takeaway="Persist, then publish — after commit when the outside world is involved. Guard every listener, return an unsubscribe handle, use a copy-on-write list, and know whether delivery is on your thread or someone else’s." />

**Trade-offs: when not to use it.**

- **One known reaction that must succeed with the action.** If the invoice *must* exist whenever a visit completes, call the invoicing service directly (in the same transaction) — an observer's failure is deliberately swallowed.
- **Order matters between reactions.** Observers make no ordering promise you should rely on. If step 2 needs step 1's output, that's a sequence or a chain.
- **Debugging-by-grep matters more than decoupling.** Every listener is a "who calls this?" that your IDE can't answer. Five events with three listeners each is fine; a hundred event types is a distributed system living in one process.

**Practice.** The follow-up scheduler should react to the **first** completion only, then unsubscribe itself — from inside its own listener, while the subject is delivering to it.

<HintLadder hints={hints.oneShot} labels={turn}>

```java group=events
class FollowUpScheduler {                                  // reacts to the first completion only
    final List<String> scheduled = new CopyOnWriteArrayList<>();
    private final AtomicBoolean fired = new AtomicBoolean();
    private volatile Runnable unsubscribe = () -> {};

    void listenOnce(AppointmentEvents events) {
        unsubscribe = events.subscribe(e -> {
            if (!fired.compareAndSet(false, true)) return;   // at most once, even if two deliveries race
            scheduled.add("follow-up for " + e.patientId());
            unsubscribe.run();                               // leaving mid-delivery: safe on a CopyOnWriteArrayList
        });
    }
}
```

Leaving during delivery is safe because the subject iterates a snapshot. The `AtomicBoolean` matters only for asynchronous delivery, where two events could reach the listener at once; it guarantees "at most once" either way. (One honest corner: if an asynchronous event arrives before `subscribe` has even returned, `unsubscribe` is still the no-op — the listener stays registered but silent. Synchronous delivery can't hit this.)

</HintLadder>

<h2 id="chain">Chapter 7 · The gauntlet</h2>

**Concept.** Chain of Responsibility passes a request through an ordered list of handlers. Each handler either stops the request (a veto) or passes it on.

**Problem.** Every clinic API request passes the same checks: authenticate the token, work out which clinic the user belongs to, validate the body, rate-limit the client, then do the work. A month ago the startup code was tidied and the checks were built from a `Set`:

```java fragment
Set<Handler> handlers = Set.of(auth, tenant, validation, rateLimit, dispatch);
for (Handler h : handlers) { /* ... */ }      // Set iteration order is unspecified: tenant may run after the query
```

The order changed. Every test still passed, until a request for "today's appointments" ran its database query before the clinic had been resolved. The query, scoped to "no clinic", returned everyone's patients. One clinic could see another's. The tenant step makes something and a later step uses it, so the order is not a style choice.

**When to use it.** Sequential checks or transforms, **each with a veto**, where the list should be extensible and the order is meaningful. Web filters, middleware, interceptors, validation pipelines, approval chains ("over ₹10 000 needs a manager").

**Better design: Chain of Responsibility.** Each concern is a handler; a handler either **stops** the request (returns a response) or **passes it on**. The modern shape — the one servlet filters and OkHttp interceptors use — is a list plus a cursor:

```java group=pipeline
record User(String name) {}
record Clinic(String id) {}

record Response(int status, String body) {
    static Response ok(String body)          { return new Response(200, body); }
    static Response badRequest(String why)   { return new Response(400, why); }
    static Response unauthorized()           { return new Response(401, "unauthorized"); }
    static Response forbidden(String why)    { return new Response(403, why); }
    static Response tooManyRequests()        { return new Response(429, "slow down"); }
}

class Request {
    final String token, clientId, body;
    private final Map<String, Object> attached = new HashMap<>();
    Request(String token, String clientId, String body) {
        this.token = token;
        this.clientId = clientId;
        this.body = body;
    }
    void attach(String key, Object value) { attached.put(key, value); }
    <T> T attached(String key, Class<T> type) { return type.cast(attached.get(key)); }
}

interface Handler { Response handle(Request r, Chain chain); }

class Chain {                                             // the cursor over the ordered list
    private final List<Handler> handlers;
    private final int index;

    Chain(List<Handler> handlers) { this(List.copyOf(handlers), 0); }
    private Chain(List<Handler> handlers, int index) {
        this.handlers = handlers;
        this.index = index;
    }

    Response proceed(Request r) {
        if (index >= handlers.size()) throw new IllegalStateException("no terminal handler");
        return handlers.get(index).handle(r, new Chain(handlers, index + 1));
    }
}
```

The handlers. Notice which ones **produce** something later handlers **consume**:

```java group=pipeline
class AuthHandler implements Handler {
    private final Map<String, User> tokens;               // stands in for token verification
    AuthHandler(Map<String, User> tokens) { this.tokens = Map.copyOf(tokens); }

    public Response handle(Request r, Chain chain) {
        User u = r.token == null ? null : tokens.get(r.token);   // Map.copyOf maps throw on get(null)
        if (u == null) return Response.unauthorized();    // veto: the chain stops here
        r.attach("user", u);                              // PRODUCES the user
        return chain.proceed(r);                          // pass it on
    }
}

class TenantHandler implements Handler {
    static final ThreadLocal<Clinic> CURRENT = new ThreadLocal<>();   // ambient context the DB layer reads
    private final Map<User, Clinic> clinicOf;
    TenantHandler(Map<User, Clinic> clinicOf) { this.clinicOf = Map.copyOf(clinicOf); }

    public Response handle(Request r, Chain chain) {
        User u = r.attached("user", User.class);          // CONSUMES the user
        if (u == null) throw new IllegalStateException("TenantHandler needs AuthHandler before it");
        Clinic clinic = clinicOf.get(u);
        if (clinic == null) return Response.forbidden("no clinic for " + u.name());
        r.attach("clinic", clinic);                       // PRODUCES the clinic
        CURRENT.set(clinic);
        try {
            return chain.proceed(r);
        } finally {
            CURRENT.remove();                             // cleaned up even if a later handler throws
        }
    }
}

class ValidationHandler implements Handler {
    public Response handle(Request r, Chain chain) {
        if (r.body == null || r.body.isBlank()) return Response.badRequest("empty body");
        return chain.proceed(r);
    }
}

class RateLimitHandler implements Handler {
    private final int perClient;
    private final Map<String, Integer> used = new HashMap<>();   // a fixed budget; a real limiter refills over time
    RateLimitHandler(int perClient) { this.perClient = perClient; }

    public Response handle(Request r, Chain chain) {
        int n = used.merge(r.clientId, 1, Integer::sum);
        if (n > perClient) return Response.tooManyRequests();
        return chain.proceed(r);
    }
}

class DispatchHandler implements Handler {               // terminal: never calls proceed()
    public Response handle(Request r, Chain chain) {
        Clinic clinic = TenantHandler.CURRENT.get();      // the "database" is scoped by the ambient clinic
        return Response.ok(r.attached("user", User.class).name() + "@" + clinic.id() + ": " + r.body);
    }
}

Chain pipeline(Map<String, User> tokens, Map<User, Clinic> clinics, int perClient) {
    return new Chain(List.of(                             // ONE place, an ORDERED list, dependencies written down
        new AuthHandler(tokens),          // attaches user
        new TenantHandler(clinics),       // needs user; attaches clinic. MUST precede anything touching the DB
        new ValidationHandler(),
        new RateLimitHandler(perClient),
        new DispatchHandler()));          // terminal
}
```

**How it works.** The client calls the first handler with the request and a cursor. Each handler does its job, then either returns a response (stopping the chain) or calls `chain.proceed`, which runs the next one. Handlers attach what later handlers need to the request.

The red node is the scene's bug: everything after Tenant **depends on** the clinic it attaches. The graded sentence: **build the chain in one place, as an ordered list, with the dependencies commented** — because links depend on earlier links' side effects, and a `Set` or classpath scanning randomises that silently. Production writes it as arithmetic on constants so inserting a filter never renumbers the others: <a href={`${BASE}lld/war/patterns-why/#4-chain-of-responsibility--order-is-a-data-dependency`}>order is a data dependency</a>.

Three more details the checker pins down:

- **Short-circuit.** A vetoing handler returns without calling `proceed`, so nothing after it runs. With a budget of 2, a valid request, an empty one, and two more valid ones get **200, 400, 200, 429** — and the empty one never reaches `RateLimitHandler`, so it doesn't spend budget.
- **Fail loudly on wrong order.** `TenantHandler` throws if no user is attached. Assemble the chain backwards and you get an exception on the first request — not a cross-clinic leak in production.
- **Clean up in `finally`.** The ambient `ThreadLocal` is removed even when a later handler throws. Thread pools reuse threads; a leftover clinic would leak into the *next* request on that thread. (This is <a href={`${BASE}lld/war/build-drills/#drill-1--hand-rolled-chain-of-responsibility`}>Drill 1</a>'s "done when".)

The checker also fires thousands of random requests (valid, invalid and missing tokens, users with and without a clinic, empty bodies, several clients) and compares every response with a plain `if` oracle that applies the same checks in the same order.

<Reveal q="Rate limiting runs after validation here. Should it run first?">

It's a real trade-off, which is why you should say it out loud. **Rate-limit early** to shed load cheaply — a flood of junk requests shouldn't cost you validation work or database lookups. **Rate-limit late** so only well-formed requests spend a client's budget. Many systems do both: a coarse per-IP limit at the edge (before auth), and a per-user limit after auth. Whatever you choose, the order is a decision, and it lives in one list.

</Reveal>

**Two shapes of chain.** The list-plus-cursor above lets the *assembly* own the order. The classic GoF shape links handlers directly — each one holds `next` — and Drill 1 asks you to build that by hand. Both let a handler decide *whether* to continue; the linked form also makes it easy for a handler to pass on a *modified* request. You'll build the linked form below.

<Trace title="Airport security lanes" steps={chain} takeaway="Each concern is a handler that may veto; the chain is one ordered list assembled in one place, because later links consume what earlier links produce. Short-circuit stops everything after the veto." />

**Trade-offs: when not to use it.**

- **Every check must run and report.** A booking form that should show *all* its errors at once wants a list of validators whose results you collect — not a chain that stops at the first.
- **Exactly one handler applies and you can compute which.** That is a lookup (a Strategy registry), not a chain of "not me, try the next".
- **Nobody can veto.** Steps that always all run are a plain sequence, or decorators.

**Practice.** The clinic's booking form runs three rules, cheapest first: the patient must be known; the doctor must be on shift at that hour; the doctor's slot must be free. Report the **first** problem and evaluate nothing after it. Build it in the classic linked form.

```java group=rules
record BookingForm(String patient, String doctor, int hour) {}
record Shift(int fromHour, int toHour) {}                  // [fromHour, toHour)

abstract class BookingRule {                               // classic GoF shape: each link holds the next
    private BookingRule next;

    BookingRule then(BookingRule next) {                   // link, and return the new tail so calls chain
        this.next = next;
        return next;
    }

    final Optional<String> check(BookingForm form) {
        Optional<String> problem = problemWith(form);
        if (problem.isPresent() || next == null) return problem;   // short-circuit on the first problem
        return next.check(form);
    }

    protected abstract Optional<String> problemWith(BookingForm form);
}

class PatientKnown extends BookingRule {
    private final Set<String> patients;
    PatientKnown(Set<String> patients) { this.patients = Set.copyOf(patients); }
    protected Optional<String> problemWith(BookingForm f) {
        return patients.contains(f.patient()) ? Optional.empty() : Optional.of("unknown patient " + f.patient());
    }
}

class DoctorOnShift extends BookingRule {
    private final Map<String, Shift> shifts;
    DoctorOnShift(Map<String, Shift> shifts) { this.shifts = Map.copyOf(shifts); }
    protected Optional<String> problemWith(BookingForm f) {
        Shift s = shifts.get(f.doctor());
        if (s == null || f.hour() < s.fromHour() || f.hour() >= s.toHour())
            return Optional.of(f.doctor() + " is not on shift at " + f.hour() + ":00");
        return Optional.empty();
    }
}

class SlotFree extends BookingRule {
    private final Set<String> taken;                       // "doctor@hour"
    SlotFree(Set<String> taken) { this.taken = Set.copyOf(taken); }
    protected Optional<String> problemWith(BookingForm f) {
        return taken.contains(f.doctor() + "@" + f.hour())
            ? Optional.of(f.doctor() + " is booked at " + f.hour() + ":00")
            : Optional.empty();
    }
}

BookingRule bookingRules(Set<String> patients, Map<String, Shift> shifts, Set<String> taken) {
    BookingRule head = new PatientKnown(patients);
    head.then(new DoctorOnShift(shifts)).then(new SlotFree(taken));     // cheapest, most basic checks first
    return head;
}
```

Notice that `check` is `final` and `problemWith` is abstract: the chain's *traversal* is a Template Method, so no rule can forget to pass the form on. The checker plants counting rules after a failing one and confirms they are never evaluated.

<h2 id="mediator">Chapter 8 · One lane, two directions</h2>

**Concept.** Mediator makes participants talk to one coordinator that owns the rules of their interaction, instead of talking to each other.

**Problem.** A garage has a single-lane ramp between two levels. Cars may go up or down, never both at once; a convoy in one direction is fine. In the first version each car's controller asks every other car's controller: are you on the ramp, which way, are you waiting?

```java fragment
class CarController {
    List<CarController> others;                              // every car knows every other car
    boolean mayEnter(Direction d) {
        for (CarController o : others)
            if (o.onRamp() && o.direction() != d) return false;   // N-1 conversations per car, each from a stale view
        return true;
    }
}
```

With twelve cars that is 132 conversations. Two cars each decided the other was waiting, and both drove onto the ramp.

**When to use it.** Many objects that all react to each other, so each one references many others — **N² links**, and coordination rules smeared across every participant. Air-traffic control, a chat room, a form where changing one field enables three others, an operating theatre where surgeons, rooms and equipment all negotiate.

**Better design: Mediator.** Colleagues talk only to the mediator; **every coordination rule lives in the mediator**. Twelve cars, twelve links, one place to read the rules:

```java group=ramp
enum Direction { UP, DOWN }

interface RampControl {                                   // the mediator, as the cars see it
    void request(Car car, Direction d);
    void leave(Car car);
}

class Car {                                               // a colleague: knows the controller, never other cars
    final String plate;
    private final RampControl control;
    final List<String> heard = new ArrayList<>();

    Car(String plate, RampControl control) {
        this.plate = plate;
        this.control = control;
    }
    void wantRamp(Direction d) { control.request(this, d); }
    void offRamp()             { control.leave(this); }
    void hear(String message)  { heard.add(message); }
}

class RampController implements RampControl {            // every coordination rule lives here
    private final Set<Car> onRamp = new LinkedHashSet<>();
    private Direction flowing;                            // direction of the cars on the ramp, null when empty
    private final Deque<Car> waiting = new ArrayDeque<>();
    private final Map<Car, Direction> wants = new HashMap<>();

    public void request(Car car, Direction d) {
        if (onRamp.contains(car) || wants.containsKey(car)) throw new IllegalStateException(car.plate + " already asked");
        wants.put(car, d);
        if (waiting.isEmpty() && (onRamp.isEmpty() || flowing == d)) admit(car);   // join the flow only if nobody is queued
        else {
            waiting.add(car);
            car.hear("WAIT");
        }
    }

    public void leave(Car car) {
        if (!onRamp.remove(car)) throw new IllegalStateException(car.plate + " is not on the ramp");
        if (!onRamp.isEmpty()) return;
        flowing = null;
        while (!waiting.isEmpty() && (flowing == null || wants.get(waiting.peek()) == flowing))
            admit(waiting.poll());                        // the head of the queue, plus everyone behind it going the same way
    }

    private void admit(Car car) {
        flowing = wants.remove(car);
        onRamp.add(car);
        car.hear("GO " + flowing);
    }

    List<Car> onRamp()  { return List.copyOf(onRamp); }
    List<Car> waiting() { return List.copyOf(waiting); }
    Direction flowing() { return flowing; }
}
```

One rule deserves a sentence, because it is exactly the kind of rule that can only live in a mediator: **a car may join the flow only if nobody is queued.** Without it, a steady stream of UP cars would starve a DOWN car forever. No individual car can enforce that; only the party that sees everyone can.

The checker drives the controller with thousands of random requests and departures and asserts the invariants after every step: the cars on the ramp always share one direction; the ramp is never empty while someone waits; and **no car overtakes an earlier waiter**. A worked case: A goes UP; B asks DOWN and hears WAIT; C asks UP and *also* hears WAIT (B is queued); A leaves, B alone goes DOWN; B leaves, C goes UP.

**How it works.** A car calls `request` or `leave` on the controller and nothing else. The controller decides who may enter, queues the rest, and tells each car `GO` or `WAIT`.

**Mediator, Observer, Facade — three easily confused shapes:**

| | Mediator | Observer | Facade |
|---|---|---|---|
| Who talks to it | Colleagues, and it talks back to them | The subject announces; listeners receive | Clients only; subsystems never call it |
| Decides anything? | **Yes** — owns the interaction rules | No — announces and doesn't care who reacts | No — coordinates calls, never decides (structural lesson) |
| Direction | Two-way | One-way, subject to listeners | One-way, client to subsystems |

A mediator often *uses* Observer internally to talk back to its colleagues (`car.hear(...)`).

<Trace title="The control tower" steps={mediator} takeaway="When many parties react to each other, put the rules in one place they all talk to. The mediator decides; colleagues only ask and listen." />

**Trade-offs: when not to use it.**

- **Two or three colleagues with one simple interaction.** A direct reference is clearer.
- **The mediator becomes a God object.** If the controller grows billing, logging and display logic, it has absorbed its colleagues' responsibilities. A mediator owns *interaction rules*, nothing else.
- **Colleagues only broadcast and never need decisions.** That's Observer.

**Practice.** The clinic's ward staff want a chat room. A message goes to every member except the sender. A muted member can't post: they are told "(you are muted)" and nobody else hears anything. Members must never hold references to each other.

```java group=chat
class ChatRoom {                                          // the mediator
    private final Map<String, Member> members = new LinkedHashMap<>();
    private final Set<String> muted = new HashSet<>();

    Member join(String name) {
        if (members.containsKey(name)) throw new IllegalArgumentException(name + " is already here");
        Member m = new Member(name, this);
        members.put(name, m);
        return m;
    }
    void mute(String name)   { muted.add(name); }
    void unmute(String name) { muted.remove(name); }

    void send(Member from, String text) {                 // the only place that decides who hears what
        if (muted.contains(from.name)) {
            from.receive("(you are muted)");
            return;
        }
        for (Member m : members.values())
            if (m != from) m.receive(from.name + ": " + text);
    }
}

class Member {                                            // a colleague: knows the room, nobody else
    final String name;
    private final ChatRoom room;
    final List<String> inbox = new ArrayList<>();

    Member(String name, ChatRoom room) {
        this.name = name;
        this.room = room;
    }
    void say(String text)     { room.send(this, text); }
    void receive(String line) { inbox.add(line); }
}
```

Muting, private messages, "only nurses on night shift" — every new rule lands in `ChatRoom.send`, and `Member` never changes. That's the whole point.

<h2 id="iterator">Chapter 9 · The last three scans</h2>

**Concept.** Iterator lets callers walk a structure in a defined order without knowing how it is stored.

**Problem.** A garage entry gate keeps its most recent ticket scans in a ring buffer: a fixed array, a `start` index and a `size`. When it is full, the newest scan overwrites the oldest. The guard's screen reaches into it directly:

```java fragment
for (int i = 0; i < log.items.length; i++) screen.print(log.items[i]);   // raw array order, and it knows the ring layout
```

After the fourth scan, the screen shows the newest scan first, then the two older ones. A report job that iterates while the gate is still writing can print a mix of old and new scans: a list that never existed at any single moment.

**When to use it.** Callers indexing into your internal representation. A custom structure (a ring, a tree, a paged result, a generated sequence) that callers need to walk. Or a sequence too large — or infinite — to build as a list.

**Better design: Iterator.** You already use it on every `for (x : xs)`: the enhanced for loop works on anything `Iterable`. Hand-roll one only for your own structures — and when you do, decide what happens if the structure changes mid-walk. The JDK's answer for ordinary collections is **fail-fast**: the iterator remembers a modification count and throws `ConcurrentModificationException` rather than returning a mixture of old and new:

```java group=iter
import java.time.*;

class RecentScans<T> implements Iterable<T> {           // the last `capacity` scans, oldest first
    private final Object[] ring;
    private int start, size;
    private int modCount;                                // bumps on every change

    RecentScans(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
        ring = new Object[capacity];
    }

    void add(T item) {
        if (size < ring.length) {
            ring[(start + size) % ring.length] = item;
            size++;
        } else {
            ring[start] = item;                          // full: overwrite the oldest
            start = (start + 1) % ring.length;
        }
        modCount++;
    }

    int size() { return size; }

    @SuppressWarnings("unchecked")
    T get(int i) {
        if (i < 0 || i >= size) throw new IndexOutOfBoundsException(i);
        return (T) ring[(start + i) % ring.length];
    }

    public Iterator<T> iterator() {
        return new Iterator<T>() {
            private int next = 0;
            private final int expectedModCount = modCount;   // the version this iterator was born with

            public boolean hasNext() { return next < size; }

            public T next() {
                if (modCount != expectedModCount) throw new ConcurrentModificationException();
                if (next >= size) throw new NoSuchElementException();
                return get(next++);
            }
        };
    }
}
```

**How it works.** The caller asks the structure for an iterator and calls `hasNext` and `next`. The iterator remembers a position and the modification count it saw when it was created. If the structure changes underneath it, `next` throws.

**What fail-fast does and doesn't promise.** It catches the *same-thread* bug — modifying a collection inside a loop over it — reliably. Across threads it is only **best effort**: the JDK documentation says outright that fail-fast behaviour cannot be guaranteed under unsynchronised concurrent modification, and that you must not rely on it for correctness. (Here `modCount` isn't even volatile.) It is a bug *detector*, not a concurrency control. The alternatives are policies, not fixes:

| Iterator | On modification during iteration | Example |
|---|---|---|
| **Fail-fast** | Throws `ConcurrentModificationException` (best effort) | `ArrayList`, `HashMap`, `RecentScans` |
| **Snapshot** | Iterates a copy taken at creation; never throws, never sees changes | `CopyOnWriteArrayList` (Chapter 6's listener list) |
| **Weakly consistent** | Never throws; may or may not see changes made after it started | `ConcurrentHashMap`, `ConcurrentLinkedQueue` |

And the everyday fix for "remove while iterating" is not a new collection: use `Iterator.remove()` or `removeIf`, which change the collection *through* the iterator.

<Trace title="Walk without looking inside" steps={iterator} takeaway="An iterator hides the layout and fixes the order. Fail-fast catches same-thread modification by checking a version number — best effort across threads, so never your concurrency control." />

**Trade-offs: when not to use it.**

- **Your structure is already a `List` or `Collection`.** Return an unmodifiable view or a copy; don't hand-roll an iterator over an `ArrayList`.
- **You need parallelism, filtering and mapping.** Streams (built on `Spliterator`) give you that; a hand-rolled iterator gives you a loop.
- **Callers need random access or a size up front.** An iterator is deliberately forward-only.

**Lazy generation.** An iterator doesn't need a collection behind it at all. It can **compute** each element when asked — useful for sequences that are large, expensive, or unbounded. A clinic's booking screen needs the appointment slots between two times.

**Practice.** Write `slots(first, end, step)`: every slot from `first` (inclusive) to `end` (exclusive), generated lazily. Beware: `LocalTime` wraps at midnight.

<HintLadder hints={hints.slots} labels={turn}>

```java group=iter
Iterable<LocalTime> slots(LocalTime first, LocalTime end, Duration step) {
    if (step.isZero() || step.isNegative()) throw new IllegalArgumentException("step must be positive");
    return () -> new Iterator<LocalTime>() {             // a fresh iterator per loop; nothing stored up front
        private LocalTime next = first;
        private boolean done = !first.isBefore(end);

        public boolean hasNext() { return !done; }

        public LocalTime next() {
            if (done) throw new NoSuchElementException();
            LocalTime current = next;
            if (step.compareTo(Duration.between(current, end)) >= 0) done = true;   // the next slot would reach end
            else next = current.plus(step);                                          // safe: this addition can't wrap
            return current;
        }
    };
}
```

`slots(09:00, 10:00, 15 min)` yields 09:00, 09:15, 09:30, 09:45. `slots(23:00, 23:59, 30 min)` yields 23:00 and 23:30 — and the guard is why it stops. The naive loop *adds, then compares*: 23:30 + 30 minutes is 00:00, which **is** before 23:59, so `while (next.isBefore(end))` loops forever. (`Stream.iterate(first, t -> t.isBefore(end), t -> t.plus(step))` has exactly the same bug.) The fix is to **compare before you add**: if the step is at least the time left until `end`, this is the last slot. Then the addition only ever happens when it lands before `end`, so it can never wrap.

There is a tempting half-fix — "stop if the next time is not after the current one" — and it is worth knowing why it fails: a step of 24 hours and 22 minutes wraps to *22 minutes later*, which is after the current time. The checker caught exactly that case in an early draft of this iterator; it compares every output with brute-force minute arithmetic, including steps longer than a day.

<h2 id="visitor">Chapter 10 · The bill tree</h2>

**Concept.** Visitor puts each new operation in its own class, with one method per node type, so you can add operations without editing the nodes.

**Problem.** A clinic inpatient bill is a tree: room charges, a surgery package (surgeon's fee, theatre charges, an anaesthesia bundle with its own items), pharmacy. Packages sit inside packages and charges sit at the leaves, which is a Composite. Finance wants the total, then the tax, then a printed statement indented by level, and next a fraud audit, with more to come. Each was added as a method on every node class:

```java fragment
interface BillLine {
    long total();
    long tax(int percent);
    String print(int depth);
    // the fraud audit is a fourth method on Item, Bundle and every node type added later
}
```

The tree has not changed shape in a year. What keeps changing is the list of operations.

**When to use it.** A **stable** structure of a few node types, and a **growing** list of operations over it — compilers (syntax trees), document exporters, bill and invoice trees, file systems. Each new operation would otherwise be a new method on every node class.

**Better design: Visitor.** Each operation becomes one class with a method per node type. Each node has a single `accept` method:

```java group=bill
interface BillVisitor<R> {
    R visitItem(Item item);
    R visitBundle(Bundle bundle);
}

sealed interface BillLine permits Item, Bundle {
    <R> R accept(BillVisitor<R> visitor);
}

record Item(String name, long paise, boolean taxable) implements BillLine {
    public <R> R accept(BillVisitor<R> v) { return v.visitItem(this); }     // dispatch #2: on the visitor
}

record Bundle(String name, List<BillLine> lines) implements BillLine {     // "Package" is taken by java.lang
    Bundle { lines = List.copyOf(lines); }
    public <R> R accept(BillVisitor<R> v) { return v.visitBundle(this); }
}

class TotalVisitor implements BillVisitor<Long> {
    public Long visitItem(Item i) { return i.paise(); }
    public Long visitBundle(Bundle b) {
        long sum = 0;
        for (BillLine line : b.lines()) sum += line.accept(this);   // dispatch #1: on the line
        return sum;
    }
}

class TaxVisitor implements BillVisitor<Long> {
    private final long percent;
    TaxVisitor(long percent) { this.percent = percent; }
    public Long visitItem(Item i) { return i.taxable() ? i.paise() * percent / 100 : 0; }   // rounded down per line
    public Long visitBundle(Bundle b) {
        long sum = 0;
        for (BillLine line : b.lines()) sum += line.accept(this);
        return sum;
    }
}

class StatementVisitor implements BillVisitor<String> {
    private int depth = 0;
    public String visitItem(Item i) { return "  ".repeat(depth) + i.name() + " " + i.paise() + "\n"; }
    public String visitBundle(Bundle b) {
        StringBuilder out = new StringBuilder("  ".repeat(depth) + b.name() + "\n");
        depth++;
        for (BillLine line : b.lines()) out.append(line.accept(this));
        depth--;
        return out.toString();
    }
}
```

**Double dispatch** is the trick, and it is why `accept` exists. `line.accept(visitor)` is a virtual call, so it dispatches on the **line's** runtime type (first dispatch). Inside, `v.visitItem(this)` is a virtual call on the visitor, so it dispatches on the **visitor's** runtime type (second dispatch). Two runtime types, two virtual calls, one correct method.

Why not just overload `visit(Item)` and `visit(Bundle)` and call `visit(line)`? Because **Java picks overloads at compile time, from the static type.** Compiled, to prove it:

```java id=overloadMess
interface Line {}
record Fee(long paise) implements Line {}
record Pack(List<Line> lines) implements Line {}

String describe(Line l) { return "some line"; }
String describe(Fee f)  { return "fee " + f.paise(); }
String describe(Pack p) { return "pack of " + p.lines().size(); }

String describeAll(Pack p) {
    StringBuilder out = new StringBuilder();
    for (Line l : p.lines()) out.append(describe(l)).append('\n');   // static type is Line: describe(Line), every time
    return out.toString();
}
```

A pack holding a `Fee(100)` and an empty `Pack` prints "some line" twice. Overloading is single dispatch on the *receiver* plus a compile-time choice on the arguments; Visitor recovers the argument's runtime type with a second virtual call.

The sample bill used in the checker (all amounts in paise; a flat 18% tax on lines marked taxable — the rounding rule, per line and downwards, is a business decision you would ask about):

**How it works.** The caller hands a visitor to the root node. Each node calls the visitor method for its own type and, for bundles, passes the visitor on to its children. The visitor holds the operation and accumulates the result.

**The trade-off, said plainly.** Visitor makes **operations cheap** (one new class, no node edits) and **node types expensive** (a new `visitXxx` in the interface, so *every* visitor must change — and the compiler lists them all for you). Choose it when the structure is stable and the operations keep coming; avoid it when node types change often. <a href={`${BASE}lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree`}>Drill 4</a> builds exactly this tree, and its "done when" is that adding a node type breaks every visitor at compile time.

**Modern Java: sealed interfaces and pattern matching.** `BillLine` is `sealed`, so the compiler knows its subtypes are exactly `Item` and `Bundle`. That lets you write operations as plain functions, without `accept`. On **Java 17** you use `instanceof` patterns:

```java group=bill
long totalOf(BillLine line) {                              // Java 17: sealed types + instanceof patterns, no accept()
    if (line instanceof Item item) return item.paise();
    if (line instanceof Bundle bundle) {
        long sum = 0;
        for (BillLine child : bundle.lines()) sum += totalOf(child);
        return sum;
    }
    throw new IllegalStateException("unhandled BillLine: " + line);   // the compiler does not check if-chains
}
```

But an `if` chain is **never checked for exhaustiveness** — add a `Discount` record and this compiles happily, then throws at runtime. Pattern matching for `switch` became a final feature in **Java 21**, and a `switch` over a sealed type with no `default` *is* checked:

```java fragment
// Java 21+. Exhaustive over the sealed type, so no default: add a new permitted record
// and this stops compiling until you handle it. (Not compiled here: the checker runs Java 17.)
long totalOf(BillLine line) {
    return switch (line) {
        case Item item     -> item.paise();
        case Bundle bundle -> bundle.lines().stream().mapToLong(this::totalOf).sum();
    };
}
```

So on Java 21, **sealed types + switch patterns give you Visitor's compile-time safety without the `accept` boilerplate**, and many teams now prefer it for closed hierarchies. On Java 17, the visitor interface is still the way to get the compiler to list every operation you must update. Say which version you're on.

<Trace title="Two dispatches" steps={visitor} takeaway="Visitor = a new operation is a new class, a new node type touches every visitor. accept() exists because overloads are picked at compile time. On Java 21, sealed types + switch patterns give the same safety without accept()." />

**Trade-offs: when not to use it.**

- **Node types change often.** Each new one edits every visitor. Put operations on the nodes instead.
- **One or two operations.** Methods on the nodes (`total()` on a Composite) are simpler.
- **You're on Java 21 with a sealed hierarchy.** A pattern-matching `switch` does the job with less ceremony.
- **The operation needs node internals.** Visitors only see what nodes expose; forcing nodes to open up for visitors weakens encapsulation.

**Practice.** Finance's fraud audit wants the names of every line that is **not** taxable, in tree order. Add it without opening `Item`, `Bundle` or any other visitor.

<HintLadder hints={hints.exempt} labels={turn}>

```java group=bill
class ExemptItems implements BillVisitor<List<String>> {    // a fourth operation; no node class reopened
    public List<String> visitItem(Item i) { return i.taxable() ? List.of() : List.of(i.name()); }
    public List<String> visitBundle(Bundle b) {
        List<String> names = new ArrayList<>();
        for (BillLine line : b.lines()) names.addAll(line.accept(this));
        return names;
    }
}
```

On the sample bill it returns `[Surgeon fee, Anaesthetist fee]`. Nothing else in the file changed.

</HintLadder>

<h2 id="which-pattern">Chapter 11 · Which behavioral pattern?</h2>

**Concept.** Start from the forcing problem, never from the pattern you like. Name the pattern, say why, and say which pattern it looks like but is not.

**Problem.** In a round you are handed a requirement such as "when a payment succeeds, send a receipt, update loyalty points and notify the warehouse." You have about ten seconds to name the pattern, justify it, and name its look-alike.

**Key the decision on the forcing problem, never the other way round:**

| The forcing problem | Pattern | Not to be confused with | The tell |
|---|---|---|---|
| One operation, N interchangeable rules, chosen by runtime data | **Strategy** (+ registry) | State — the rule doesn't change over the object's life | A `switch` over a type code |
| A fixed sequence where 1–3 steps differ per variant | **Template Method** (or a runner taking lambdas) | Strategy — it's the *skeleton* that's shared | Copy-pasted sequences drifting apart |
| Not every status change is legal, and an illegal one corrupts data | **State** (enum table, or classes when behaviour varies) | Strategy — here the object picks its own successor | `switch (status)` at the top of several methods |
| An action that must be undone, redone, queued, retried, logged or replayed | **Command** | A parameter object named `*Command` | "undo", "history", "job queue", "macro" |
| Restore the state as it was at a moment | **Memento** | Command — this restores state, not reverses actions | "checkpoint", "revert to saved" |
| N parties, unknown to the producer, must know *when* something happens | **Observer** (after commit; unsubscribe) | Chain — observers can't veto and shouldn't depend on order | A core method calling side effects by name |
| Sequential checks, each with a veto, order meaningful | **Chain of Responsibility** | Decorator — adds behaviour, normally always passes on | Auth, tenant, validate, rate-limit |
| Many parties all reacting to each other | **Mediator** | Observer — the mediator *decides* | N² references, rules smeared across participants |
| Walk a custom structure without exposing it, or generate lazily | **Iterator** | Returning the internal array | Callers indexing into your fields |
| Many operations over a stable structure | **Visitor** (or sealed + switch on Java 21) | Composite — that's the tree, not the operations | A new method on every node class per report |

**The rest of the family — one line each, know the cue:**

| Pattern | Clinic cue | One-liner |
|---|---|---|
| **Interpreter** | Admins write eligibility rules like `age > 60 AND dept = CARDIO` | A tiny AST plus evaluate; <a href={`${BASE}lld/war/patterns-why/#14-interpreter--every-new-report-used-to-be-a-release`}>new reports stopped being releases</a>, <a href={`${BASE}lld/war/build-drills/#drill-5--a-tiny-interpreter`}>Drill 5</a> |
| **Null Object** | A clinic with no SMS vendor configured yet | A do-nothing sender instead of null checks — but decide fail-open vs fail-closed: <a href={`${BASE}lld/war/inventory/#3-a-null-object-that-fails-open`}>production's failed open</a> |

**How they combine in the classics.** A vending machine is State (+ Command if transactions are logged). A text editor is Command + Memento (+ Iterator over the document). Splitwise is Strategy (split rules) + Observer (balance notifications). A parking lot is Strategy (pricing) + State (spot, ticket) + Observer (the display board). An elevator is State (the car) + Mediator or Strategy (the dispatcher choosing which car). Naming the combination out loud, in the first ten minutes, is how you tell the grader you have a plan.

<Reveal q="The interviewer asks: “Isn’t State just Strategy with extra steps?”">

Structurally, yes — both are a context holding an interface, delegating to whichever object is behind it. The difference is **who changes the object and why**. A strategy is chosen *from outside*, by data, and usually stays put for the operation ("this bill splits equally"). A state object is replaced *from inside*, by the states themselves, as events arrive ("after a sale of the last item, I'm SoldOut"). The intent is different, so the invariants are different: State's job is to make illegal transitions impossible; Strategy's is to make rules swappable.

</Reveal>

<h2 id="sq-percent">Follow-up 1 · Split by percentages</h2>

**Requirement:** *"Families want to agree percentages. 50/30/20, say. Shares must still add up to the bill exactly."*

**Where it fits:** Strategy — but the new rule needs **extra input** that the others don't. `split(long total, List<Party> parties)` has nowhere to put percentages. The tempting fixes are an overload per rule, or a nullable `Map` parameter on every strategy. The honest fix is the one <a href={`${BASE}lld/war/build-drills/#drill-2--strategy--registry-with-a-real-signature-problem`}>Drill 2</a> teaches: a **context parameter object**. That changes the interface, so this is a genuine edit — a new group, with the unchanged types repeated.

<Reveal q="How do you round 10 001 paise at 33% / 33% / 34%?">

Exact shares are 3 300.33, 3 300.33 and 3 400.34 paise. Floor each: 3 300 + 3 300 + 3 400 = 10 000, one paisa short. Give the leftover to the share that lost the most to rounding — the **largest remainder** (34 hundredths beats 33): **3 300, 3 300, 3 401**. The sum of all remainders is always exactly 100 × the leftover, and each remainder is below 100, so the leftover paise always go to shares with a positive remainder — a 0% party can never receive one.

</Reveal>

```java group=splitCtx
record SplitRequest(long total, List<Party> parties, Map<String, Integer> percentByName) {   // the parameter object
    SplitRequest {
        if (total < 0) throw new IllegalArgumentException("negative total");
        parties = List.copyOf(parties);
        percentByName = Map.copyOf(percentByName);
    }
    SplitRequest(long total, List<Party> parties) { this(total, parties, Map.of()); }        // most rules need no extras
}

interface SplitStrategy { List<Share> split(SplitRequest request); }

class EqualSplit implements SplitStrategy {               // same arithmetic, new signature
    public List<Share> split(SplitRequest req) {
        List<Party> parties = req.parties();
        if (parties.isEmpty()) {
            if (req.total() == 0) return List.of();
            throw new IllegalArgumentException("no one to split " + req.total() + " paise between");
        }
        long each = req.total() / parties.size(), extra = req.total() % parties.size();
        List<Share> shares = new ArrayList<>();
        for (int i = 0; i < parties.size(); i++) shares.add(new Share(parties.get(i), each + (i < extra ? 1 : 0)));
        return shares;
    }
}

class PercentSplit implements SplitStrategy {             // NEW
    public List<Share> split(SplitRequest req) {
        List<Party> parties = req.parties();
        int sum = 0;
        for (Party p : parties) {
            Integer pct = req.percentByName().get(p.name());
            if (pct == null || pct < 0) throw new IllegalArgumentException("no valid percentage for " + p.name());
            sum += pct;
        }
        if (sum != 100) throw new IllegalArgumentException("percentages add up to " + sum + ", not 100");

        long[] amount = new long[parties.size()];
        long[] remainder = new long[parties.size()];      // in hundredths of a paisa
        long assigned = 0;
        for (int i = 0; i < parties.size(); i++) {
            long exact = req.total() * req.percentByName().get(parties.get(i).name());   // paise x 100
            amount[i] = exact / 100;
            remainder[i] = exact % 100;
            assigned += amount[i];
        }
        // Largest remainder: leftover paise go to the shares that lost most to rounding (ties: party order).
        List<Integer> order = new ArrayList<>();
        for (int i = 0; i < parties.size(); i++) order.add(i);
        order.sort((a, b) -> Long.compare(remainder[b], remainder[a]));    // List.sort is stable
        long left = req.total() - assigned;
        for (int k = 0; k < left; k++) amount[order.get(k)]++;

        List<Share> shares = new ArrayList<>();
        for (int i = 0; i < parties.size(); i++) shares.add(new Share(parties.get(i), amount[i]));
        return shares;
    }
}

enum SplitType { EQUAL, PERCENT }

class BillSplitter {
    private final Map<SplitType, SplitStrategy> strategies;
    BillSplitter(Map<SplitType, SplitStrategy> strategies) { this.strategies = Map.copyOf(strategies); }
    List<Share> split(SplitType type, SplitRequest request) {
        SplitStrategy s = strategies.get(type);
        if (s == null) throw new IllegalArgumentException("no strategy for " + type);
        return s.split(request);
    }
}

BillSplitter splitter() {
    return new BillSplitter(Map.of(SplitType.EQUAL, new EqualSplit(), SplitType.PERCENT, new PercentSplit()));
}
```

10 000 paise at 50/30/20 gives 5 000 / 3 000 / 2 000; 10 001 at 33/33/34 gives 3 300 / 3 300 / 3 401. The checker runs thousands of random totals and percentage vectors and confirms the shares always sum to the total, each share is the exact value rounded down or up by at most one paisa, and 0% parties pay nothing. (Party names are assumed unique — they key the map.)

</HintLadder>

<h2 id="sq-maintenance">Follow-up 2 · The technician's panel</h2>

```java group=vending2
    final List<String> dispensed = new ArrayList<>();
    final List<Integer> change = new ArrayList<>();
    String display = "";

    VendingMachine(Map<String, Integer> prices, Map<String, Integer> initialStock) {
        this.prices = Map.copyOf(prices);
        for (String slot : prices.keySet()) stock.put(slot, initialStock.getOrDefault(slot, 0));
        state = totalStock() == 0 ? new SoldOut() : new Idle();
    }

    void insert(int coin) {
        if (coin <= 0) throw new IllegalArgumentException("not a coin: " + coin);
        state = state.insert(this, coin);
    }
    void select(String slot)             { state = state.select(this, slot); }
    void refund()                        { state = state.refund(this); }
    void restock(String slot, int units) { state = state.restock(this, slot, units); }
    void openPanel()                     { state = state.openPanel(this); }        // NEW
    void closePanel()                    { state = state.closePanel(this); }       // NEW
    String state()                       { return state.getClass().getSimpleName(); }

    int credit() { return credit; }
    int priceOf(String slot) {
        Integer price = prices.get(slot);
        if (price == null) throw new IllegalArgumentException("no slot " + slot);
        return price;
    }
    int stockOf(String slot) { priceOf(slot); return stock.get(slot); }
    int totalStock() {
        int sum = 0;
        for (int n : stock.values()) sum += n;
        return sum;
    }
    void addCredit(int coin) { credit += coin; display = "credit " + credit; }
    void addStock(String slot, int units) {
        priceOf(slot);
        if (units <= 0) throw new IllegalArgumentException("restock needs units > 0");
        stock.merge(slot, units, Integer::sum);
    }
    void show(String message) { display = message; }
    void dispense(String slot) {
        stock.merge(slot, -1, Integer::sum);
        dispensed.add(slot);
        int owed = credit - priceOf(slot);
        if (owed > 0) change.add(owed);
        credit = 0;
        display = "enjoy your " + slot;
    }
    void returnCredit() { change.add(credit); credit = 0; display = "refunded"; }
}
```

The checker opens the panel from `Idle` and from `SoldOut`, confirms coins, selections and refunds are refused while it's open, confirms `openPanel` is refused in `HasCredit`, and checks that closing returns `Idle` or `SoldOut` depending on stock. It also re-runs Chapter 3's random sequences on this version: for the old events, nothing changed.

</HintLadder>

**Transfer test:** a new requirement adds an *out of order* state that only a technician's code can leave. With the enum-table form instead, what would this change have cost? Count the edits both ways.

<h2 id="sq-macro">Follow-up 3 · One click, one undo</h2>

**Requirement:** *"Moving a patient to another doctor is two clicks — cancel, then book. Make it one click, and one undo. And if the new booking fails, don't leave them cancelled."*

**Where it fits:** Command — a **macro command**: a command made of commands (Command + Composite). No existing class changes; `FrontDesk` sees one more `Command`.

<HintLadder hints={hints.macro} labels={turn}>

```java group=desk
class MacroCommand implements Command {                   // a Composite of commands: one undo step
    private final List<Command> steps;
    MacroCommand(List<Command> steps) { this.steps = List.copyOf(steps); }

    public void execute() {
        int done = 0;
        try {
            for (Command c : steps) {
                c.execute();
                done++;
            }
        } catch (RuntimeException e) {
            for (int i = done - 1; i >= 0; i--) steps.get(i).undo();   // all or nothing
            throw e;
        }
    }

    public void undo() {
        for (int i = steps.size() - 1; i >= 0; i--) steps.get(i).undo();   // reverse order
    }
}
```

`new MacroCommand(List.of(new CancelAppointment(s, "A-1"), new BookAppointment(s, toDrMehta)))` moves Asha in one click and back in one undo. If Dr Mehta is busy, the booking throws, the macro re-books A-1 with its original id, and `FrontDesk.run` records nothing. Undo runs in **reverse**: the booking is cancelled before the cancellation is undone — otherwise you'd briefly hold two appointments, or collide with yourself. The checker verifies all three cases, plus redo.

</HintLadder>

**Transfer test:** the booking also sends an SMS. Undo can't un-send it. What should the macro's undo do instead — and which War Room dossier is this?

<h2 id="sq-audit">Follow-up 4 · Audit every request</h2>

**Requirement:** *"The regulator wants a log: who called the API, and how each call ended — including the rejected ones."*

**Where it fits:** Chain — **one new handler and one line in the assembly**. The design question is *where in the list*. Before `AuthHandler` there's no user. At the end, rejected requests never arrive. Right after `AuthHandler`, calling `proceed` first and logging what comes back, it sees the user *and* every later veto.

<HintLadder hints={hints.audit} labels={turn}>

```java group=pipeline
class AuditHandler implements Handler {                  // NEW: sees everything after it, including vetoes
    private final List<String> log;
    AuditHandler(List<String> log) { this.log = log; }

    public Response handle(Request r, Chain chain) {
        Response response = chain.proceed(r);            // let the rest of the chain run...
        log.add(r.attached("user", User.class).name() + " " + response.status());   // ...then record who and how it ended
        return response;
    }
}

Chain auditedPipeline(Map<String, User> tokens, Map<User, Clinic> clinics, int perClient, List<String> auditLog) {
    return new Chain(List.of(
        new AuthHandler(tokens),          // attaches user
        new AuditHandler(auditLog),       // needs user; wraps everything after it, so it sees 400, 403, 429 and 200
        new TenantHandler(clinics),
        new ValidationHandler(),
        new RateLimitHandler(perClient),
        new DispatchHandler()));
}
```

With a budget of 2, the sequence from Chapter 7 — valid, empty body, valid, valid — plus one request with a bad token, logs `asha 200`, `asha 400`, `asha 200`, `asha 429`. The bad-token request gets its 401 from `AuthHandler` and **never reaches the auditor** — say that out loud, and log authentication failures at the edge if the regulator wants them. A handler that throws would also skip the log line; wrap `proceed` in `try/finally` if exceptions must be audited too.

</HintLadder>

**Transfer test:** the regulator now wants unauthenticated attempts too, by client id. Do you move `AuditHandler` before `AuthHandler`, or add a second, smaller handler there? What does each choice log for a valid request?

<h2 id="sq-discount">Follow-up 5 · A discount line</h2>

**Requirement:** *"Bills can now carry discount lines — a staff discount, a package deal. They reduce the total; tax is still charged on the taxable lines as before."*

**Where it fits:** Visitor — and this is the **expensive** direction. A new node type means a new `visitDiscount` in the interface and an implementation in **every** visitor. That's the trade you accepted; the good news is that the compiler finds every visitor for you. The `instanceof` version, meanwhile, compiles without complaint and throws at runtime.

<HintLadder hints={hints.discount} labels={turn}>

```java group=bill2
interface BillVisitor<R> {
    R visitItem(Item item);
    R visitBundle(Bundle bundle);
    R visitDiscount(Discount discount);                    // NEW: every visitor must now implement this
}

sealed interface BillLine permits Item, Bundle, Discount {
    <R> R accept(BillVisitor<R> visitor);
}

record Item(String name, long paise, boolean taxable) implements BillLine {
    public <R> R accept(BillVisitor<R> v) { return v.visitItem(this); }
}

record Bundle(String name, List<BillLine> lines) implements BillLine {
    Bundle { lines = List.copyOf(lines); }
    public <R> R accept(BillVisitor<R> v) { return v.visitBundle(this); }
}

record Discount(String name, long paise) implements BillLine {   // NEW node type
    Discount {
        if (paise < 0) throw new IllegalArgumentException("a discount is a positive amount taken off");
    }
    public <R> R accept(BillVisitor<R> v) { return v.visitDiscount(this); }
}

class TotalVisitor implements BillVisitor<Long> {
    public Long visitItem(Item i) { return i.paise(); }
    public Long visitBundle(Bundle b) {
        long sum = 0;
        for (BillLine line : b.lines()) sum += line.accept(this);
        return sum;
    }
    public Long visitDiscount(Discount d) { return -d.paise(); }        // NEW
}

class TaxVisitor implements BillVisitor<Long> {
    private final long percent;
    TaxVisitor(long percent) { this.percent = percent; }
    public Long visitItem(Item i) { return i.taxable() ? i.paise() * percent / 100 : 0; }
    public Long visitBundle(Bundle b) {
        long sum = 0;
        for (BillLine line : b.lines()) sum += line.accept(this);
        return sum;
    }
    public Long visitDiscount(Discount d) { return 0L; }                // NEW: the card says tax is unchanged
}

long totalOf(BillLine line) {                                   // the Java 17 instanceof version
    if (line instanceof Item item) return item.paise();
    if (line instanceof Bundle bundle) {
        long sum = 0;
        for (BillLine child : bundle.lines()) sum += totalOf(child);
        return sum;
    }
    throw new IllegalStateException("unhandled BillLine: " + line);    // a Discount lands here, at runtime
}
```

The checker adds a ₹500 (50 000 paise) staff discount to the sample bill: the total drops from 7 965 725 to 7 915 725 paise and the tax stays 569 830. And it confirms the unchanged `totalOf` throws on the discount line — the bug that a Java 21 exhaustive `switch` would have refused to compile.

</HintLadder>

**Transfer test:** finance now says tax should be charged *after* discounts, proportionally across taxable lines. Is that still a visitor change, or has the rule outgrown "one number per node"?

<h2 id="interview-script">Say it in the room</h2>

**The question:** "Walk me through the behavioral patterns in this design. And tell me where you chose not to use one." The follow-up "now add a technician mode" should land as one new class and a few one-line overrides.

**The 90-second answer** (adapt the nouns):

> "I started from what changes. The machine's behaviour depends on its lifecycle — idle, has credit, sold out — and the bug class I care about is illegal moves, like accepting coins when it's empty. So the machine delegates every event to a state object, the interface's defaults refuse, and each state overrides only what it allows; the technician mode was one new state. Pricing per slot is data, so it's a map, not a strategy — there's only one pricing rule. Sales are announced to listeners for the stock dashboard and the refill alert: they're isolated, they unsubscribe, and they'd fire after commit in a real system. Customer actions are not commands because nothing needs undo or a queue — if you asked for a transaction log or a remote 'cancel last purchase', I'd make each action a command with an id so replays are idempotent. And where nothing varies, I kept it concrete: slots and coins are plain values."

**Five follow-ups you will get:**

<Reveal q="1 · Isn’t State just Strategy?">

Same shape — a context holding an interface — different intent. A strategy is chosen from outside by data and stays put; a state replaces itself from inside as events arrive. State's job is to make illegal transitions impossible; Strategy's is to make rules swappable. I'd use an enum transition table if the states only differed in their edges.

</Reveal>

<Reveal q="2 · How would you implement undo and redo?">

Each action is a command with `execute` and `undo`, and it stores what its own execution did — the appointment it created, the slot it moved from. The invoker keeps an undo stack and a redo stack: undo pops to redo, redo pops back, and any new command clears redo. Redo replays the *same* effect, not a fresh one. If reversing actions is hard, a command can store a memento instead. Across services, undo becomes a compensating action.

</Reveal>

<Reveal q="3 · What can go wrong with Observer in production?">

Five things: notifying before the change is committed (fire after commit); one listener's exception breaking the rest (isolate each); listeners never unsubscribing, so the list leaks memory (return a handle, unsubscribe on every exit); `ConcurrentModificationException` when a listener leaves mid-delivery (use `CopyOnWriteArrayList`); and slow listeners blocking the publisher under synchronous delivery (hand delivery to an executor — and accept losing ordering).

</Reveal>

<Reveal q="4 · Your middleware chain: what decides the order?">

Data dependencies. Auth produces the user; tenant resolution consumes it and produces the clinic; everything that touches the database needs the clinic. So the order is an explicit list in one assembly method, with the dependencies commented, and a handler fails loudly if its input is missing. Ambient context like a ThreadLocal is cleared in a `finally`. I'd never build the chain from a Set or classpath scanning.

</Reveal>

<Reveal q="5 · When would you not use Visitor?">

When node types change more often than operations — every new node edits every visitor. When there are only one or two operations — methods on the nodes are simpler. And on Java 21 with a sealed hierarchy, a pattern-matching `switch` gives the same exhaustiveness check with no `accept` boilerplate. On Java 17 the visitor interface is still how I get the compiler to list every operation to update.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Pattern | Do… | The promise to keep |
|---|---|---|---|
| A `switch` over a type code choosing an algorithm | **Strategy** | Interface + class or lambda per rule; registry built eagerly | Every rule keeps the interface's contract (shares sum to the total) |
| Rules needing different inputs | Strategy + parameter object | One request object, not overloads | Extra inputs don't leak into other rules |
| The same sequence copy-pasted with 1–3 steps different | **Template Method** | `final` skeleton, abstract holes, optional hooks; or a runner with lambdas | Fixed steps are unskippable |
| Status changes that can be illegal | **State** | One guarded gate; enum table (edges vary) or state classes (behaviour varies) | Every missing arrow throws and changes nothing |
| Undo, redo, queue, retry, log, replay | **Command** | `execute` + `undo`, store the effect; two stacks; clear redo on new action | Redo replays the same effect; retries are idempotent |
| "Restore to how it was" | **Memento** | Originator makes copies; caretaker stores, never reads | A snapshot is a copy, never a view |
| "When X happens, do these N things" | **Observer** | Subscribe returns a handle; isolate listeners; copy-on-write list | Persist first; after commit; no leaks |
| Checks in order, each can veto | **Chain of Responsibility** | One ordered assembly; handlers return or proceed | Order follows data dependencies; cleanup in `finally` |
| Many parties reacting to each other | **Mediator** | Colleagues know only the mediator | Rules live in one place — and only rules |
| Callers indexing into your structure | **Iterator** | `Iterable`; fail-fast via a mod count; lazy where large | Fail-fast is best effort, never thread safety |
| New report over a stable tree, again | **Visitor** | `accept` + one visitor per operation; sealed + switch on Java 21 | New node types break every visitor at compile time — on purpose |
| Two variants, no growth signalled | — | An `if` | Don't build a seam nobody asked for |

## Five mistakes to leave behind

1. **Pattern first, problem second.** Name the forcing problem out loud, then the pattern. "I'll use Strategy here" with no reason is a red flag; "pricing varies by type and you hinted at more" is a design.
2. **Undo from inputs.** Undo reverses *this command's effect*. Capture it at execute time, and make redo replay it.
3. **Observers that can hurt the subject.** Unguarded exceptions, never-unsubscribed listeners, notifications before commit, `ArrayList` listener lists.
4. **Chains built from sets.** Order is a data dependency. One list, in one place, with the dependencies written down.
5. **Snapshots that are views.** A memento shares nothing mutable with the live object.

**Where this leaves you.** The five verbs, *split, move, react, check, undo*, each map to a pattern, and a sixth, *decide*, is the Mediator. In every case, name what varies before you name the pattern.

**Practice routine:** run the "name it in ten seconds" drill. Read a requirement, then name the forcing problem, the pattern, and the pattern it only resembles. Then build one classic (vending machine, text editor with undo, or elevator) in 45 minutes and ask yourself two follow-ups. For each, say where it lands before you type.

**Further study**

- Gamma, Helm, Johnson and Vlissides, *Design Patterns: Elements of Reusable Object-Oriented Software* (1994) — the original catalogue; read the "Applicability" and "Consequences" sections of each behavioral pattern, not just the diagrams.
- Eric Freeman and Elisabeth Robson, *Head First Design Patterns* (2nd edition) — Strategy, Observer, Command, Template Method, Iterator and State with gentler examples.
- Joshua Bloch, *Effective Java* (3rd edition) — Item 42 "Prefer lambdas to anonymous classes" (strategies as lambdas), Item 79 "Avoid excessive synchronization" (calling alien listener methods while holding a lock), Item 34 on enums with constant-specific methods.
- [JEP 409: Sealed Classes](https://openjdk.org/jeps/409) (final in Java 17) and [JEP 441: Pattern Matching for switch](https://openjdk.org/jeps/441) (final in Java 21) — the language features that replace many visitors.
- [CopyOnWriteArrayList](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/CopyOnWriteArrayList.html) and [ArrayList](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/ArrayList.html) Javadoc — snapshot iterators, and the exact wording of the fail-fast "best effort" warning.
- Martin Fowler, [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) — Command and Memento's ideas applied to a whole system's history.
- [Refactoring.Guru: Behavioral patterns](https://refactoring.guru/design-patterns/behavioral-patterns) — clear diagrams for each pattern, useful for a quick second explanation.

**Look these up yourself**

- **Transactional outbox** — the durable way to "publish after commit": write the event in the same transaction as the change, and relay it afterwards.
- **Double dispatch vs multiple dispatch** — languages like Common Lisp (CLOS) and Julia dispatch on every argument's runtime type, which makes Visitor unnecessary.
- **Hierarchical state machines (statecharts)** — David Harel's extension with nested states and history, for lifecycles too big for a flat table.
- **Reactive Streams / `java.util.concurrent.Flow`** — Observer with backpressure, for when the publisher is faster than its subscribers.
- **CQRS** — separating commands that change state from queries that read it, at architecture scale.
- **Weak listener lists** — `WeakReference`-based subscriptions, why they avoid the lapsed-listener leak, and why they make lambda listeners disappear unexpectedly.
- **Largest remainder method** — the apportionment rule behind Follow-up 1, also used to allocate parliamentary seats.
