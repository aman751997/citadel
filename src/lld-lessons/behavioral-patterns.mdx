## MediCore starts running

Creational made the objects, structural wired the clinic to the world. Now patients arrive and the *day-to-day* begins: bills get split between insurance and family, appointments move through their lifecycle, a completed visit triggers five downstream reactions, every API request runs a gauntlet of checks, and the front desk demands an undo button. Behavioral patterns vary **what happens** — the algorithm, the reaction, the sequence — at runtime, without if-else towers.

This is the lesson machine-coding rounds live in: nearly every classic problem (parking lot, splitwise, vending machine, chess) is two or three of these patterns wearing a costume.

## Strategy — splitting the bill

**Story beat.** A family checks out. The bill can be split **equally** among family members, by **percentages** they agree on, or **insurance-first** (insurer pays up to the policy cap, family covers the rest). Same verb — *split* — three interchangeable algorithms, chosen at runtime by data.

```java
interface SplitStrategy { List<Share> split(Money total, List<Party> parties); }

class EqualSplit implements SplitStrategy {
    public List<Share> split(Money total, List<Party> parties) {
        Money each = total.dividedBy(parties.size());        // careful: remainder paise!
        List<Share> shares = new ArrayList<>();
        Money assigned = Money.ZERO;
        for (int i = 0; i < parties.size() - 1; i++) {
            shares.add(new Share(parties.get(i), each));
            assigned = assigned.plus(each);
        }
        shares.add(new Share(parties.getLast(), total.minus(assigned)));  // last absorbs remainder
        return shares;                                        // shares sum EXACTLY to total
    }
}

class InsuranceFirstSplit implements SplitStrategy {
    public List<Share> split(Money total, List<Party> parties) {
        Party insurer = parties.stream().filter(Party::isInsurer).findFirst()
            .orElseThrow(() -> new IllegalArgumentException("no insurer party"));
        Money covered = Money.min(total, insurer.policyCap());   // insurer pays up to the cap
        Money remainder = total.minus(covered);
        List<Share> shares = new ArrayList<>();
        shares.add(new Share(insurer, covered));
        List<Party> family = parties.stream().filter(p -> !p.isInsurer()).toList();
        shares.addAll(new EqualSplit().split(remainder, family));  // strategies can compose!
        return shares;
    }
}
```

(That remainder line is a real grading moment: ₹100 across 3 people must sum to ₹100, not ₹99.99. Money conservation is the hidden invariant graders test with "does it sum back?")

**Strategy + registry** is the standard pair — the same move as the creational lesson's payment registry:

```java
class BillSplitter {
    private final Map<SplitType, SplitStrategy> strategies;   // injected; or self-registered via key()
    List<Share> split(Bill bill) {
        return strategies.get(bill.splitType()).split(bill.total(), bill.parties());
    }
}
```

The honest wrinkle from production: strategies rarely share a clean signature (percentage split needs the percentages; equal split doesn't). [Drill 2](/citadel/lld/war/build-drills/#drill-2--strategy--registry-with-a-real-signature-problem) makes you fight that — the usual fix is a context parameter object, not fifteen overloads. And the founding production example is [five payment gateways behind one Strategy seam](/citadel/lld/war/patterns-why/#1-strategy--five-payment-gateways).

> 🧠 **Memory hook.** *Choose your weapon:* same fight, swappable weapon, picked at fight time. The fighter (service) never knows which blade it holds — only that it cuts.
> **Cheat code:** one verb × N interchangeable algorithms, chosen by data → strategy (+ registry to kill the if-ladder).
> **Interview line:** *"Splitting varies by rule, not by caller — so each rule is a strategy behind one interface, a registry picks by type, and my equal-split conserves every paisa."*

## State — the appointment lifecycle

**Story beat.** An appointment flows `REQUESTED → CONFIRMED → CHECKED_IN → COMPLETED`, with `CANCELLED` reachable from the first two. The naive version — status checks scattered through every method — let a bug move a `COMPLETED` appointment back to `CONFIRMED`. It was re-billed. Production's version of this scar: [a backwards transition corrupts history](/citadel/lld/war/patterns-why/#10-state--because-a-backwards-transition-corrupts-history).

**Form 1 — enum + transition table** (right size for most rounds):

```java
enum ApptStatus {
    REQUESTED, CONFIRMED, CHECKED_IN, COMPLETED, CANCELLED;

    private static final Map<ApptStatus, Set<ApptStatus>> LEGAL = Map.of(
        REQUESTED,  Set.of(CONFIRMED, CANCELLED),
        CONFIRMED,  Set.of(CHECKED_IN, CANCELLED),
        CHECKED_IN, Set.of(COMPLETED),
        COMPLETED,  Set.of(),                       // terminal — nothing leaves
        CANCELLED,  Set.of()
    );
    boolean canGoTo(ApptStatus next) { return LEGAL.get(this).contains(next); }
}

class Appointment {
    private ApptStatus status = ApptStatus.REQUESTED;

    private void transition(ApptStatus next) {       // ONE gate for every transition
        if (!status.canGoTo(next))
            throw new IllegalStateException(status + " → " + next + " is not a legal transition");
        this.status = next;
    }
    public void confirm()  { transition(ApptStatus.CONFIRMED); }    // verbs, not setStatus
    public void checkIn()  { transition(ApptStatus.CHECKED_IN); }
    public void complete() { transition(ApptStatus.COMPLETED); }
    public void cancel()   { transition(ApptStatus.CANCELLED); }
}
```

**Form 2 — state-per-class** (when states carry real behavior, not just names):

```java
interface ApptState {
    default ApptState confirm(Appointment a)  { throw illegal("confirm"); }
    default ApptState checkIn(Appointment a)  { throw illegal("checkIn"); }
    default IllegalStateException illegal(String event) {
        return new IllegalStateException(event + " not allowed in " + getClass().getSimpleName());
    }
}
class Requested implements ApptState {
    public ApptState confirm(Appointment a) {
        a.reserveSlot();                              // state-specific BEHAVIOR — why classes earn keep
        return new Confirmed();
    }
}
class Confirmed implements ApptState {
    public ApptState checkIn(Appointment a) {
        a.assignRoom();
        return new CheckedIn();
    }
}
```

**The interview calibration** (this exact trade-off is [Drill 3](/citadel/lld/war/build-drills/#drill-3--state-both-ways)): few states, no per-state behavior → the enum table is less code and equally safe. States doing real different work → classes. Either form, the non-negotiable is **transitions validated in one place** — you already derived this rule in the object-modeling lesson ("no setter for state, ever").

> 🧠 **Memory hook.** *Traffic light:* what "go" means depends on which light is on, and lights change in a fixed legal order — red never jumps to green via yellow-backwards.
> **Cheat code:** behavior depends on lifecycle stage + illegal transitions must be impossible → state. Few dumb states → enum table; rich states → classes.
> **Interview line:** *"I'll centralize transitions in one guarded method over an explicit legal-moves table — and I'd only upgrade to state-per-class when states carry distinct behavior."*

## Observer — the visit ends, the clinic reacts

**Story beat.** When an appointment completes, five things must happen: generate the invoice, send the feedback SMS, update the doctor's analytics, decrement consumables, schedule the follow-up. Hard-coding five calls into `complete()` couples the core flow to every side effect; each new reaction edits the method.

```java
interface AppointmentListener { void onCompleted(AppointmentCompleted event); }

record AppointmentCompleted(String apptId, String patientId, String doctorId, Instant at) {}

class AppointmentService {
    private final List<AppointmentListener> listeners = new CopyOnWriteArrayList<>();
    private final AppointmentRepo repo;

    AppointmentService(AppointmentRepo repo) { this.repo = repo; }

    void register(AppointmentListener l) { listeners.add(l); }

    void complete(Appointment a) {
        a.complete();                                   // 1. the state transition (guarded, above)
        repo.save(a);                                   // 2. persist it
        AppointmentCompleted evt = new AppointmentCompleted(   // 3. THEN tell the world
            a.id(), a.patientId(), a.doctorId(), Instant.now());
        for (AppointmentListener l : listeners) notifySafely(l, evt);
    }

    private void notifySafely(AppointmentListener l, AppointmentCompleted e) {
        try { l.onCompleted(e); }
        catch (Exception ex) { log.error("listener failed: " + l.getClass(), ex); }
        // one broken listener must not break the others — or the core flow
    }
}

// Reactions are now plug-ins:
service.register(evt -> invoicing.generateFor(evt.apptId()));
service.register(evt -> sms.send(phoneOf(evt.patientId()), "How was your visit?"));
service.register(evt -> analytics.recordVisit(evt.doctorId()));
```

Three graded details in those lines: **notify after persisting** (observers of an unsaved change observe a lie), **isolate listener failures**, and `CopyOnWriteArrayList` so a listener can (un)subscribe during iteration without `ConcurrentModificationException`. The production timing subtlety — fire *after the transaction commits*, or the SMS announces a rollback — is [the Observer dossier](/citadel/lld/war/patterns-why/#13-observer--the-existing-integration-only-fired-after-the-call-ended); in Spring that's `@TransactionalEventListener(AFTER_COMMIT)`.

> 🧠 **Memory hook.** *Newsletter subscription:* the clinic publishes "visit completed"; subscribers signed up themselves; the publisher doesn't know or care who reads. One reader's spam filter breaking doesn't stop the others' delivery.
> **Cheat code:** "when X happens, do these N things — more later" → observer. Save first, notify after; guard each listener.
> **Interview line:** *"complete() publishes an event after persisting; reactions subscribe. New reaction = new listener, zero edits — and in real systems I'd fire after commit."*

## Chain of Responsibility — every request runs the gauntlet

**Story beat.** Every MediCore API request passes: authentication → clinic (tenant) resolution → validation → rate limiting → the actual handler. Each check can veto. The team assembled these from an unordered set once — and tenant resolution ran *after* a handler that touched the database. Cross-clinic data leak. Production wrote it down: [order is a data dependency](/citadel/lld/war/patterns-why/#4-chain-of-responsibility--order-is-a-data-dependency).

```java
interface Handler { Response handle(Request r, Chain chain); }

class Chain {                                        // the cursor over the ordered list
    private final List<Handler> handlers;
    private final int index;
    Chain(List<Handler> handlers) { this(handlers, 0); }
    private Chain(List<Handler> handlers, int index) { this.handlers = handlers; this.index = index; }

    Response proceed(Request r) {
        if (index >= handlers.size()) throw new IllegalStateException("no terminal handler");
        return handlers.get(index).handle(r, new Chain(handlers, index + 1));
    }
}

class AuthHandler implements Handler {
    public Response handle(Request r, Chain chain) {
        User u = tokens.verify(r.bearerToken());
        if (u == null) return Response.unauthorized();      // veto — chain stops here
        r.attach("user", u);
        return chain.proceed(r);                            // pass on
    }
}
class TenantHandler implements Handler {
    public Response handle(Request r, Chain chain) {
        Clinic clinic = clinics.forUser(r.attached("user", User.class));
        r.attach("clinic", clinic);                         // later handlers DEPEND on this
        return chain.proceed(r);
    }
}
class RateLimitHandler implements Handler {
    public Response handle(Request r, Chain chain) {
        if (!limiter.tryAcquire(r.clientId())) return Response.tooManyRequests();
        return chain.proceed(r);
    }
}

// Assembly: ONE place, an ORDERED list, dependencies written down.
Chain pipeline = new Chain(List.of(
    new AuthHandler(),        // attaches user
    new TenantHandler(),      // needs user; attaches clinic — MUST precede anything touching the DB
    new ValidationHandler(),
    new RateLimitHandler(),
    new DispatchHandler()     // terminal — never calls proceed()
));
```

Same shape as servlet filters and OkHttp interceptors — cite them. The graded sentence: **build the chain in one place, as an ordered list, with the dependencies commented** — because links depend on earlier links' side effects, and a `Set` or classpath scanning randomizes that silently.

> 🧠 **Memory hook.** *Airport security lanes:* passport check, then security, then boarding — each station can reject you, and swapping their order is not a style choice (security before passport control = chaos).
> **Cheat code:** sequential checks/transforms, each with a veto, order meaningful → chain. Assemble once, ordered, documented.
> **Interview line:** *"Each concern is a handler; the pipeline is an explicit ordered list assembled in one place — order is a data dependency here, so I keep it visible."*

## Command — the front desk wants undo

**Story beat.** Front-desk staff juggle walk-ins: book, cancel, reschedule — and misclick constantly. They want Ctrl+Z. A method call evaporates the moment it returns; to undo, queue, log, or replay an action, **the action itself must be an object**.

```java
interface Command { void execute(); void undo(); }

class BookAppointment implements Command {
    private final Scheduler scheduler;
    private final BookingRequest request;
    private Appointment booked;                          // memory the undo needs

    BookAppointment(Scheduler scheduler, BookingRequest request) {
        this.scheduler = scheduler; this.request = request;
    }
    public void execute() { booked = scheduler.book(request); }
    public void undo()    { scheduler.cancel(booked.id()); }
}

class CancelAppointment implements Command {
    private final Scheduler scheduler;
    private final String apptId;
    private Appointment cancelled;                       // snapshot for restore

    CancelAppointment(Scheduler scheduler, String apptId) {
        this.scheduler = scheduler; this.apptId = apptId;
    }
    public void execute() { cancelled = scheduler.cancel(apptId); }
    public void undo()    { scheduler.rebook(cancelled); }
}

// The invoker knows nothing about scheduling — it runs commands and stacks them:
class FrontDesk {
    private final Deque<Command> history = new ArrayDeque<>();
    void run(Command c) { c.execute(); history.push(c); }
    void undoLast() {
        if (history.isEmpty()) return;
        history.pop().undo();
    }
}
```

Recognition cues: **undo/redo** (text-editor round), **job queues**, **audit logs of user actions**, macro recording. Two production footnotes: real undo across a service boundary is a *compensating action*, not a rollback — the [Saga compensation dossier](/citadel/lld/war/patterns-why/#11-saga-compensation--transactional-cant-reach-outside-the-database) — and beware naming: a class called `*Command` without an `execute()` [may be lying to you](/citadel/lld/war/patterns-why/#18-the-one-that-lies--command-without-execute).

> 🧠 **Memory hook.** *Restaurant order slip:* the waiter writes your order on a slip — now it can be queued to the kitchen, re-fired, or crumpled (undone). A shouted order can't.
> **Cheat code:** "undo / queue / log / replay actions" → command. Each command carries the memory its own undo needs.
> **Interview line:** *"Every front-desk action is a command with execute and undo; the invoker just stacks them — and I'd note that cross-service undo becomes compensation, not rollback."*

## Template Method — every report, same skeleton

**Story beat.** MediCore ships reports: daily revenue, doctor utilization, pharmacy stock. Every one does fetch → transform → render → deliver; only fetch and render differ. Five copy-pasted sequences drifted — one report skipped delivery audit.

```java
abstract class ReportJob {
    final Report run(ReportRequest req) {        // final: the skeleton is not negotiable
        Data raw = fetch(req);
        Data clean = transform(raw);
        Rendered out = render(clean);
        return deliver(out);                     // fixed step — subclasses can't skip the audit
    }
    protected abstract Data fetch(ReportRequest req);      // the holes subclasses fill
    protected abstract Rendered render(Data d);
    protected Data transform(Data d) { return d; }         // optional hook: default no-op
    private Report deliver(Rendered r) {                   // private: not even visible to children
        storage.save(r);
        audit.record("REPORT_DELIVERED", r.id());
        return new Report(r);
    }
}

class DailyRevenueReport extends ReportJob {
    protected Data fetch(ReportRequest req) { return billing.revenueRows(req.date()); }
    protected Rendered render(Data d)       { return pdf.renderRevenueTable(d); }
}
```

This is the one pattern where inheritance is the *point* — the parent owns the algorithm and state, children own the holes (the interface-vs-abstract-class rule from Module 1, applied). Modern alternative worth naming: pass the varying steps as lambdas and keep the skeleton a plain final class; choose Template Method when hooks are several or need shared protected state. Production was pushed into it by something sneakier — [module dependency direction](/citadel/lld/war/patterns-why/#7-template-method--forced-by-module-dependency-direction): the skeleton lived in a core module that *couldn't see* its implementors.

> 🧠 **Memory hook.** *Recipe with blanks:* "prepare ___, cook at 180° for 20 min, garnish with ___" — the steps and order are printed and fixed; you only fill the blanks.
> **Cheat code:** same sequence, 1–3 steps differ per variant → template method (skeleton `final`). Steps trivially small → lambdas instead.
> **Interview line:** *"The sequence is the asset, so it's final in the parent; variants override only fetch and render — delivery and audit are physically unskippable."*

## The rest of the family — one line each, know the cue

| Pattern | MediCore cue | One-liner |
|---|---|---|
| **Iterator** | walk the bill tree without exposing lists | you use it every `for (x : xs)`; hand-roll only for custom structures |
| **Mediator** | OT scheduling: surgeons, rooms, equipment all negotiating | replace N² chatter with one coordinator |
| **Memento** | "restore this prescription draft" | opaque state snapshot; undo for *state* where Command is undo for *actions* |
| **Visitor** | itemized statement + GST over the bill tree | N operations over a stable tree; pairs with Composite ([Drill 4](/citadel/lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree)) |
| **Interpreter** | admins write eligibility rules like `age > 60 AND dept = CARDIO` | tiny AST + evaluate; [new reports stopped being releases](/citadel/lld/war/patterns-why/#14-interpreter--every-new-report-used-to-be-a-release), [Drill 5](/citadel/lld/war/build-drills/#drill-5--a-tiny-interpreter) |
