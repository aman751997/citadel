Machine-coding rounds draw from a surprisingly small pool. Interviewers reskin them — "parking lot" becomes "warehouse slotting", "Splitwise" becomes "team lunch settle-up", "BookMyShow" becomes "meeting-room booking" — but **the skeleton repeats: a resource allocator, a money splitter, a state machine, a cache, a seat inventory, a scheduler, a pipeline, a quota.** Learn eight skeletons properly and the reskins stop being new problems.

"Properly" has a precise meaning here. For each problem this lesson gives you:

1. **The client's brief** (a Scene) and the **cut**: must, should, won't — said out loud in the first ten minutes.
2. **The entities**, as a class diagram, with the invariant each one owns.
3. **The key decisions**, including which pattern absorbs the follow-up you will certainly be asked.
4. **The core, in compilable Java** — compact, but it runs, and the checker for this page tests it: fees, balances, state transitions, eviction order, seat holds under forty threads, lift routes, log filtering, token counts under a fake clock.
5. **Where the threads collide**, named and handled, because "what if two users do this at once?" is the most common probe in the room.
6. **The follow-up**, built as a "your turn" exercise, and **the trap** that loses the round.

You have done the theory: <a href={`${BASE}lld/lessons/solid/`}>SOLID</a>, the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral</a> and <a href={`${BASE}lld/lessons/structural-patterns/`}>structural</a> patterns, <a href={`${BASE}lld/lessons/concurrency-for-lld/`}>concurrency for LLD</a> and <a href={`${BASE}lld/lessons/machine-coding-protocol/`}>the 90-minute protocol</a>. <h2 id="skeleton">Chapter 0 · The skeleton under every costume</h2>

<Scene chapter="Chapter 0" title="Five words" mood="dawn">

On Friday you turn the cards over. Wren's five words are the same on every one:

*Cut. Owner. Seam. Claim. Clock.*

"Cut is scope," you say. "Seam is the strategy interface. Clock is the injected `Clock`." You hesitate. "Owner and claim?"

Oona, who has wandered over with a coffee, taps the parking card. "Who refuses a second car in the same spot?"

"The spot."

"And when two cars want it at the same millisecond?"

You think about the parking lot's code. Then the cinema's. Then the rate limiter's. They have the same shape.

*"Name the claim,"* says Wren, *"in all eight."*

</Scene>

Every problem in the canon is the same five moves. Learn the moves once; each chapter just finds them in a new costume.

| Move | What you do | What the grader sees |
|---|---|---|
| **Cut** | Must / should / won't, and *which axis will change* | You scoped deliberately instead of building everything |
| **Owner** | Each invariant lives inside one entity's methods (`Ticket.close` runs once; a `Ledger` always sums to zero) | No invariant that depends on every caller remembering it |
| **Seam** | One interface on the axis that changes — usually a **Strategy**; lifecycles as **State** | The follow-up lands as a new class |
| **Claim** | The contended step is *one* atomic operation: check-and-take, never check-then-take | You found the race before they asked |
| **Clock** | Time comes in through a `java.time.Clock` (or a tick counter); tests move it by hand | Expiry, fees and refills are tested without `sleep` |

Here is the **claim** in all eight, so you can see it is one idea:

| Problem | The contended step | The atomic claim on this page |
|---|---|---|
| Parking lot | Two cars, one last spot | `Spot.tryAssign` (synchronized check-and-assign) |
| Parking lot (exit) | Two exits, one ticket | `openTickets.remove(id, ticket)` — only one caller removes it |
| Splitwise | Two expenses at once | `synchronized` `Ledger.add` (the sum-to-zero invariant spans many balances) |
| Vending machine | One machine, one customer | `synchronized` entry points; the state field changes only inside them |
| LRU cache | Every `get` reorders the list | One lock around get *and* put — a read is a write |
| BookMyShow | Two users, seat F7 | `synchronized` `Show.hold`: all seats or none, under the show's lock |
| Elevator | Calls arrive while the car moves | `synchronized` `request` / `step` on the car |
| Logger | Many threads, one slow disk | A bounded queue between callers and one writer thread |
| Rate limiter | Refill then take | `synchronized` `tryAcquire`; `computeIfAbsent` for the per-key bucket |

And here is the **clock**, which every testable design in the canon needs. `java.time.Clock` is abstract; a test clock that only moves when told is eight lines:

```java id=manualClock
import java.time.*;

static class ManualClock extends Clock {              // time moves only when a test says so; nothing sleeps
    private Instant now;
    private final ZoneId zone;

    ManualClock(Instant start) { this(start, ZoneOffset.UTC); }
    private ManualClock(Instant start, ZoneId zone) { this.now = start; this.zone = zone; }

    synchronized void advance(Duration d) { now = now.plus(d); }
    @Override public synchronized Instant instant() { return now; }
    @Override public ZoneId getZone() { return zone; }
    @Override public Clock withZone(ZoneId z) { return new ManualClock(now, z); }
}
```

`Clock.millis()` is implemented in terms of `instant()`, so every design that asks for millis gets the hand-moved time too. The checker for this page uses this exact class to test parking fees, seat-hold expiry, log timestamps and token refills.

**Problem: Parking lot · resource allocator.** This is the worked example: one problem taken end to end through the six phases of <a href={`${BASE}lld/lessons/machine-coding-protocol/`}>the 90-minute protocol</a>. Every later chapter is the same walk, told faster.

<h3 id="parking-phase-1">Phase 1 — Requirements and the cut</h3>

Actors: driver, operator. Operations that must demo: **park, unpark, fee**. What varies: vehicle types, spot sizes, pricing, allocation policy. Invariants: one vehicle per spot; a ticket unparks exactly once; the fee covers the full stay; a vehicle is parked at most once.

| Must | Should | Won't (say so) |
|---|---|---|
| Park a bike, car or truck in a spot that fits; ticket out | Pluggable fee and allocation policies | Payments integration (a port, not built) |
| Unpark by ticket; fee by started hour | Free-spot count for the entrance display | Reservations, multiple entry gates |
| "Lot full" for that vehicle type; double unpark rejected | Safe under concurrent arrivals | Persistence — in-memory only |

Concurrency: design for it from the start, coarse-to-fine if asked. The <a href={`${BASE}lld/lessons/concurrency-for-lld/`}>concurrency lesson's</a> parking example is stage two of this exact problem.

Calls made out loud: `Ticket` is an **entity** (its identity survives change; it goes from open to closed exactly once). Money is a `long` of whole rupees — never a `double`. Spot occupancy is guarded *inside* `Spot` (`tryAssign`, not `isFree` + `assign` — that gap is the race from the concurrency lesson). Vehicle types are an **enum with a size**, not a class tree — the electric-SUV follow-up cuts across any tree you'd guess (the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson's</a> exact warning).

<h3 id="parking-phase-3">Phase 3 — The seams</h3>

Two interfaces carry all the flex: `SpotAllocator` (smallest-fit / nearest / spread across floors) and `FeeStrategy` (hourly / slab / weekend surge). Both are Strategy from the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral lesson</a>. Everything else is concrete, and you say so: *"Spots, floors and tickets are plain classes; I don't expect them to vary."*

<h3 id="parking-phase-4">Phase 4 — The core flow</h3>

The vocabulary first. Sizes are data on the enums, so "does it fit?" is one comparison, not a ladder:

```java group=parking
import java.time.*;

enum VehicleType {
    BIKE(1), CAR(2), TRUCK(3);
    final int size;
    VehicleType(int size) { this.size = size; }
}

enum SpotType {
    SMALL(1), MEDIUM(2), LARGE(3);
    final int size;
    SpotType(int size) { this.size = size; }
    boolean fits(VehicleType v) { return v.size <= size; }
}

record Vehicle(String plate, VehicleType type) {}

record Floor(int number, List<Spot> spots) {}

record Receipt(String ticketId, String spotId, long fee) {}

class LotFullException extends RuntimeException {
    LotFullException(VehicleType type) { super("no free spot for a " + type); }
}
```

The two entities that own invariants. `Spot` refuses a second occupant; `Ticket` refuses to close twice or before it opened:

```java group=parking
class Spot {
    private final String id;
    private final SpotType type;
    private Vehicle occupant;                          // guarded by this; null when free

    Spot(String id, SpotType type) { this.id = id; this.type = type; }

    synchronized boolean tryAssign(Vehicle v) {        // check AND claim in one atomic step
        if (occupant != null || !type.fits(v.type())) return false;
        occupant = v;
        return true;
    }
    synchronized void release() {
        if (occupant == null) throw new IllegalStateException("spot " + id + " is already free");
        occupant = null;
    }
    synchronized boolean isFree() { return occupant == null; }   // a hint for searching, never a promise
    String id() { return id; }
    SpotType type() { return type; }
}

class Ticket {
    private final String id;
    private final Vehicle vehicle;
    private final String spotId;
    private final Instant entry;
    private Instant exit;                              // null while the vehicle is inside

    Ticket(String id, Vehicle vehicle, String spotId, Instant entry) {
        this.id = id;
        this.vehicle = vehicle;
        this.spotId = spotId;
        this.entry = entry;
    }

    synchronized void close(Instant at) {              // exactly once, never before entry
        if (exit != null) throw new IllegalStateException("ticket " + id + " is already closed");
        if (at.isBefore(entry)) throw new IllegalArgumentException("exit before entry");
        exit = at;
    }
    synchronized boolean isOpen() { return exit == null; }
    String id() { return id; }
    Vehicle vehicle() { return vehicle; }
    String spotId() { return spotId; }
    Instant entry() { return entry; }
}
```

The two seams, each with the one implementation the brief needs:

```java group=parking
interface FeeStrategy {
    long fee(Ticket ticket, Instant exit);             // whole rupees; never negative
}

class HourlyFee implements FeeStrategy {
    private final Map<VehicleType, Long> perHour;
    HourlyFee(Map<VehicleType, Long> perHour) { this.perHour = Map.copyOf(perHour); }

    public long fee(Ticket t, Instant exit) {
        long minutes = Duration.between(t.entry(), exit).toMinutes();
        long startedHours = Math.max(1, (minutes + 59) / 60);    // every started hour; the first is charged on entry
        Long rate = perHour.get(t.vehicle().type());
        if (rate == null) throw new IllegalArgumentException("no tariff for " + t.vehicle().type());
        return startedHours * rate;
    }
}

interface SpotAllocator {
    Optional<Spot> pick(List<Floor> floors, VehicleType type);
}

class SmallestFitLowestFloor implements SpotAllocator {   // waste the least space, then walk the least
    public Optional<Spot> pick(List<Floor> floors, VehicleType type) {
        for (SpotType size : SpotType.values()) {          // SMALL, MEDIUM, LARGE
            if (!size.fits(type)) continue;
            for (Floor floor : floors)
                for (Spot spot : floor.spots())
                    if (spot.type() == size && spot.isFree()) return Optional.of(spot);
        }
        return Optional.empty();
    }
}
```

And the lot itself, which only coordinates:

```java group=parking
class ParkingLot {
    private final List<Floor> floors;
    private final Map<String, Spot> spotsById = new HashMap<>();
    private final SpotAllocator allocator;
    private final FeeStrategy fees;
    private final Clock clock;
    private final Map<String, Ticket> openTickets = new ConcurrentHashMap<>();
    private final Set<String> parkedPlates = ConcurrentHashMap.newKeySet();
    private final AtomicLong nextId = new AtomicLong();

    ParkingLot(List<Floor> floors, SpotAllocator allocator, FeeStrategy fees, Clock clock) {
        this.floors = List.copyOf(floors);
        for (Floor f : floors) for (Spot s : f.spots()) spotsById.put(s.id(), s);
        this.allocator = allocator;
        this.fees = fees;
        this.clock = clock;
    }

    Ticket park(Vehicle v) {
        if (!parkedPlates.add(v.plate())) throw new IllegalStateException(v.plate() + " is already parked");
        while (true) {
            Optional<Spot> candidate = allocator.pick(floors, v.type());
            if (candidate.isEmpty()) {
                parkedPlates.remove(v.plate());
                throw new LotFullException(v.type());
            }
            if (candidate.get().tryAssign(v)) {            // lost the race? someone took it since pick(): pick again
                Ticket t = new Ticket("T-" + nextId.incrementAndGet(), v, candidate.get().id(), clock.instant());
                openTickets.put(t.id(), t);
                return t;
            }
        }
    }

    Receipt unpark(String ticketId) {
        Ticket t = openTickets.get(ticketId);
        if (t == null) throw new IllegalArgumentException("unknown or already used ticket " + ticketId);
        Instant exit = clock.instant();
        long fee = fees.fee(t, exit);                      // may throw; nothing has changed yet
        if (!openTickets.remove(ticketId, t))              // the exit claim: exactly one caller wins
            throw new IllegalArgumentException("ticket " + ticketId + " was used by another exit");
        t.close(exit);
        spotsById.get(t.spotId()).release();
        parkedPlates.remove(t.vehicle().plate());
        return new Receipt(t.id(), t.spotId(), fee);
    }

    long freeSpots() { return spotsById.values().stream().filter(Spot::isFree).count(); }
}

ParkingLot copperline(Clock clock) {                   // the composition root: the only place that knows the wiring
    List<Floor> floors = List.of(
        new Floor(0, List.of(new Spot("S-0-1", SpotType.SMALL), new Spot("M-0-1", SpotType.MEDIUM),
                             new Spot("M-0-2", SpotType.MEDIUM), new Spot("L-0-1", SpotType.LARGE))),
        new Floor(1, List.of(new Spot("S-1-1", SpotType.SMALL), new Spot("M-1-1", SpotType.MEDIUM),
                             new Spot("L-1-1", SpotType.LARGE))));
    FeeStrategy tariff = new HourlyFee(Map.of(VehicleType.BIKE, 10L, VehicleType.CAR, 20L, VehicleType.TRUCK, 40L));
    return new ParkingLot(floors, new SmallestFitLowestFloor(), tariff, clock);
}
```

Details graders notice: **`clock` is injected** (`java.time.Clock`) so fee tests don't sleep; `Ticket.close` owns the exactly-once invariant (State, enum-sized: open or closed); the fee is computed **before** anything is mutated, so a missing tariff can't strand a car in a spot whose ticket is gone; and the race retry is a narrated loop, not a hidden recursion.

**Worked numbers** on Copperline's seven bays. A car parks at 09:00 and leaves at 11:10: 130 minutes, `(130 + 59) / 60` = 3 started hours × 20 = **60**. A car that leaves the same minute it arrived pays one hour, **20**. With M-0-1 and M-0-2 taken, the next car goes to **M-1-1** — a medium on floor 1 beats the large on floor 0, because smallest-fit is checked before floor. With both large bays taken, a truck gets `LotFullException` even though small and medium bays are free.

<h3 id="parking-concurrency">Where the threads collide: the last spot</h3>

`pick` reads `isFree()` without holding anything, so two threads can both be handed M-1-1. That is fine **because `pick` is only a hint**: the decision is `tryAssign`, which checks and claims under the spot's lock. One thread wins; the other gets `false`, loops, and either finds another spot or reports the lot full. The exit has the same shape: `openTickets.remove(ticketId, t)` succeeds for exactly one caller, so two barrier controllers handed the same ticket can't both release the spot.

The checker for this page runs it for real: 200 car threads start at once against the five bays a car fits (two medium and one large on floor 0, one medium and one large on floor 1) — exactly 5 tickets, 5 distinct bays, 195 `LotFullException`s, no bay with two cars, twenty rounds in a row. Then 8 threads race to unpark the same ticket: exactly one receipt. With 200 bikes, all 7 bays fill and no more. Remove `synchronized` from `tryAssign` and the same test hands out a sixth ticket for a bay that already has a car in it.

<h3 id="parking-follow-up">Phase 5 — The follow-up</h3>

The two follow-ups for this problem are **weekend surge pricing** and **a different allocation policy**. Surge is a decorator around `FeeStrategy`, built step by step in the <a href={`${BASE}lld/lessons/solid/#sq-surge`}>SOLID lesson's first side quest</a>. So here is the other one.

<Reveal q="Bram: “Floor 0 fills first and the ramp to floor 1 sits empty until noon. Spread cars evenly across floors.” What changes?">

One new `SpotAllocator` and one wiring line. `ParkingLot`, `Spot`, `Ticket` and the fee code are not opened — the allocation policy was the axis you closed in Phase 3. And the new allocator inherits the concurrency story for free: it is still only a hint, and `tryAssign` is still the claim.

</Reveal>

**Your turn.** Write `EvenSpread`: choose the floor with the most free spots that fit this vehicle, then the smallest fitting spot on that floor.

<HintLadder hints={hints.parking} labels={turn}>

```java group=parking
class EvenSpread implements SpotAllocator {            // the emptiest floor first, then the smallest fit there
    public Optional<Spot> pick(List<Floor> floors, VehicleType type) {
        Floor best = null;
        long bestFree = 0;
        for (Floor f : floors) {
            long free = f.spots().stream().filter(s -> s.isFree() && s.type().fits(type)).count();
            if (free > bestFree) { best = f; bestFree = free; }   // ties keep the lower floor
        }
        if (best == null) return Optional.empty();
        return best.spots().stream()
            .filter(s -> s.isFree() && s.type().fits(type))
            .min(Comparator.comparingInt((Spot s) -> s.type().size));
    }
}
```

On three floors of four medium bays, seven cars land 3, 2, 2: after every arrival the busiest and emptiest floors differ by at most one. The checker parks one car at a time and asserts exactly that.

</HintLadder>

<h3 id="parking-phase-6">Phase 6 — Tests and demo</h3>

Demo `main`: park two vehicles, unpark one, show the fee, show `LotFullException` for a truck, show double-unpark rejected. Six tests: fee math (a manual clock), full lot, double unpark, allocation choice, race on the last spot (many threads, one wins), money in whole units with no remainder.

**Catch the trap:** `if (spot.isFree()) spot.assign(v)` — check-then-act across two calls. It passes every single-threaded test and fails the first time two cars arrive together. The fix isn't "add synchronized to `park`" (that serialises the whole garage); it is **one atomic check-and-claim on the thing being claimed**.

**Say it aloud:** *"Pricing and allocation are the two axes I expect to change, so they're strategies; spots and tickets are concrete. The spot claims itself atomically with tryAssign — the allocator's search is only a hint, so losing a race just means picking again."*

**Three decisions decide this problem.**

1. **Money is a `long` of paise.** ₹100.00 split three ways is 3334 + 3333 + 3333 paise — and *who* gets the extra paisa must be deterministic. `double` can't represent 0.1 exactly; it is never the answer for money.
2. **Store net balances, not IOUs.** One number per person: positive means the group owes them, negative means they owe the group. Every expense adds `amount` to the payer and subtracts each share from its person. Because the shares sum to the amount, **the balances always sum to zero** — an invariant the `Ledger` owns and the checker verifies after every random expense.
3. **Simplify from the balances.** Who-owes-whom history is irrelevant to settling up; only net positions matter.

```java group=splitwise
interface Split {                                      // how one expense divides; the shares must sum to the amount
    Map<String, Long> shares(long amount);
}

record EqualSplit(List<String> people) implements Split {
    EqualSplit {
        if (people.isEmpty()) throw new IllegalArgumentException("nobody to split with");
        people = List.copyOf(people);
    }
    public Map<String, Long> shares(long amount) {
        Map<String, Long> out = new LinkedHashMap<>();
        long each = amount / people.size(), extra = amount % people.size();
        for (int i = 0; i < people.size(); i++)                       // the first `extra` people pay one paisa more
            out.merge(people.get(i), each + (i < extra ? 1 : 0), Long::sum);
        return out;
    }
}

record ExactSplit(Map<String, Long> amounts) implements Split {
    ExactSplit { amounts = Map.copyOf(amounts); }
    public Map<String, Long> shares(long amount) { return new LinkedHashMap<>(amounts); }   // the ledger checks the sum
}

record PercentSplit(Map<String, Integer> percents) implements Split {
    PercentSplit {
        if (percents.values().stream().anyMatch(p -> p < 0)) throw new IllegalArgumentException("negative percent");
        if (percents.values().stream().mapToInt(Integer::intValue).sum() != 100)
            throw new IllegalArgumentException("percents must sum to 100");
        percents = Collections.unmodifiableMap(new TreeMap<>(percents));   // fixed order: leftover paise go by name
    }
    public Map<String, Long> shares(long amount) {
        Map<String, Long> out = new LinkedHashMap<>();
        long given = 0;
        for (var e : percents.entrySet()) {
            long share = amount * e.getValue() / 100;                  // rounded down
            out.put(e.getKey(), share);
            given += share;
        }
        for (var e : percents.entrySet())                              // hand out what rounding kept back
            if (given < amount && e.getValue() > 0) { out.merge(e.getKey(), 1L, Long::sum); given++; }
        return out;
    }
}
```

Why one pass of leftovers is enough: each positive-percent share loses less than one paisa to rounding, so the leftover is smaller than the number of people with a positive percent.

```java group=splitwise
record Expense(String paidBy, long amount, Split split) {}
record Transfer(String from, String to, long amount) {}

class Ledger {
    private final Map<String, Long> balances = new TreeMap<>();   // + the group owes them; - they owe the group

    synchronized void add(Expense e) {                 // one lock: the invariant spans several balances
        if (e.amount() <= 0) throw new IllegalArgumentException("amount must be positive");
        Map<String, Long> shares = e.split().shares(e.amount());
        long sum = 0;
        for (long s : shares.values()) {
            if (s < 0) throw new IllegalArgumentException("negative share");
            sum += s;
        }
        if (sum != e.amount()) throw new IllegalArgumentException("shares sum to " + sum + ", expense is " + e.amount());
        balances.merge(e.paidBy(), e.amount(), Long::sum);
        shares.forEach((person, share) -> balances.merge(person, -share, Long::sum));
    }

    synchronized Map<String, Long> balances() { return new TreeMap<>(balances); }

    /** Biggest debtor pays biggest creditor, repeatedly. At most (people with a nonzero balance) - 1 transfers. */
    synchronized List<Transfer> simplify() {
        Comparator<long[]> biggestFirst = (a, b) -> a[0] != b[0] ? Long.compare(b[0], a[0]) : Long.compare(a[1], b[1]);
        List<String> names = new ArrayList<>(balances.keySet());       // sorted: ties break by name
        PriorityQueue<long[]> creditors = new PriorityQueue<>(biggestFirst), debtors = new PriorityQueue<>(biggestFirst);
        for (int i = 0; i < names.size(); i++) {
            long b = balances.get(names.get(i));
            if (b > 0) creditors.add(new long[] { b, i });
            else if (b < 0) debtors.add(new long[] { -b, i });
        }
        List<Transfer> plan = new ArrayList<>();
        while (!creditors.isEmpty()) {
            long[] c = creditors.poll(), d = debtors.poll();
            long x = Math.min(c[0], d[0]);
            plan.add(new Transfer(names.get((int) d[1]), names.get((int) c[1]), x));
            if (c[0] > x) creditors.add(new long[] { c[0] - x, c[1] });
            if (d[0] > x) debtors.add(new long[] { d[0] - x, d[1] });
        }
        return plan;
    }
}
```

**Worked numbers.** Friday lunch: Oona pays ₹900.00 split equally among Oona, Wren and Bram (₹300.00 each). Wren pays ₹600.00 exactly — ₹100.00 for her, ₹500.00 for Bram's steak. Balances: Oona +600, Wren +200, Bram −800 (in rupees; the code holds paise). `simplify()` pairs the biggest debtor with the biggest creditor: **Bram → Oona ₹600**, then **Bram → Wren ₹200**. Two transfers, and the balances still sum to zero at every step.

The old quiz example — A owes B ₹30, B owes C ₹30 — nets to A −30, B 0, C +30: **one transfer, A → C**. Cancelling IOUs pair by pair can't see through B; net balances can.

**Why simplify terminates in at most n − 1 transfers:** every transfer moves `min(debt, credit)`, which zeroes at least one of the two people, and the last transfer zeroes both. So with n people holding a nonzero balance, there are at most n − 1 transfers. The checker applies every plan to the balances and asserts everyone ends at exactly zero.

<Reveal q="Is greedy the minimum number of transfers?">

No — and saying so is worth points. Balances Oona +500, Wren +400, Ines +300, Bram −700, Kofi −500: greedy gives **4** transfers (Bram → Oona 500, Kofi → Wren 400, Bram → Ines 200, Kofi → Ines 100). The optimum is **3**: Kofi → Oona 500, then Bram → Wren 400 and Bram → Ines 300 — because the people split into zero-sum groups. Finding the minimum means finding the most zero-sum groups, which is NP-hard in general (it contains subset sum). Greedy's n − 1 bound is the accepted interview answer; name the optimum, say why you're not computing it. The checker brute-forces the optimum on small random ledgers and confirms greedy is never better than optimal and never worse than n − 1.

</Reveal>

<h3 id="splitwise-concurrency">Where the threads collide</h3>

`Ledger.add` updates several balances that must stay consistent as a group — exactly the "compound invariant" rung of the concurrency ladder. A `ConcurrentHashMap` with `merge` would make each balance safe and the **sum** wrong for an instant in between; a reader calling `balances()` mid-expense could see money that exists nowhere. One lock around the whole expense is correct and plenty fast for a ledger. The checker runs 8 threads × 500 random expenses and asserts the balances sum to zero and match a sequential replay.

**Problem: Vending machine · state machine.**

<h3 id="vending-cut">The cut</h3>

| Must | Should | Won't |
|---|---|---|
| Insert coins (1, 2, 5, 10, 20); reject others | Change made from coins actually in the box | Cards, UPI, notes |
| Select a slot: vend + change, or refuse with a reason and keep the credit | Out-of-service mode for restocking | Telemetry, remote price changes |
| Cancel: refund the credit | One customer at a time, enforced | Multiple selections per payment |
| Illegal actions fail loudly and change nothing | | |

The axis here isn't pricing — it is **what each button means depending on what the machine is doing**. That is the State pattern's exact job.

<Figure caption="Three states. Every arrow not drawn is an illegal action that throws and changes nothing.">
  <Mermaid code={`stateDiagram-v2
    [*] --> OutOfService
    OutOfService --> OutOfService : restock / load coins
    OutOfService --> Idle : back in service
    Idle --> Collecting : insert coin
    Idle --> OutOfService : out of service
    Collecting --> Collecting : insert coin, or a refused select
    Collecting --> Idle : select (vend + change)
    Collecting --> Idle : cancel (refund)`} />
</Figure>

**Decisions.**

1. **One class per state, each a tiny subclass of a base whose every action throws.** A state overrides only what is legal in it. Illegal actions are not forgotten `if`s; they are the default.
2. **Two kinds of "no".** An *illegal* action (select while idle, insert while out of service) throws `IllegalStateException` and nothing changes. A *legal request that can't be served* (sold out, not enough credit, can't make change) throws `Refused`, keeps the credit, and stays in `Collecting`. The customer can insert more, pick something else, or cancel.
3. **Change-making uses the coins in the box, not an infinite supply.** That is where greedy breaks.
4. **States are inner classes of the machine**, so they read the machine's fields directly; the machine's public methods forward to the current state, under one lock.

```java group=vending
record Product(String name, int price) {}
record Vend(String product, List<Integer> change) {}

class Refused extends RuntimeException {               // a legal request the machine can't serve right now
    Refused(String why) { super(why); }
}

class VendingMachine {
    private final Map<String, Product> products;                    // slot -> product
    private final Map<String, Integer> stock = new HashMap<>();
    private final TreeMap<Integer, Integer> coinBox = new TreeMap<>(Comparator.reverseOrder());
    private final Set<Integer> accepted = Set.of(1, 2, 5, 10, 20);
    private int credit = 0;
    private State state = new OutOfService();                       // a new machine waits to be loaded

    VendingMachine(Map<String, Product> products) {
        this.products = Map.copyOf(products);
        for (String slot : products.keySet()) stock.put(slot, 0);
    }

    // The public face: one customer at a time, every button forwarded to the current state.
    synchronized void insert(int coin)             { state.insert(coin); }
    synchronized Vend select(String slot)          { return state.select(slot); }
    synchronized List<Integer> cancel()            { return state.cancel(); }
    synchronized void outOfService()               { state.outOfService(); }
    synchronized void backInService()              { state.backInService(); }
    synchronized void restock(String slot, int n)  { state.restock(slot, n); }
    synchronized void loadCoins(int coin, int n)   { state.loadCoins(coin, n); }

    synchronized String stateName()                { return state.getClass().getSimpleName(); }
    synchronized int credit()                      { return credit; }
    synchronized int stock(String slot)            { return stock.getOrDefault(slot, 0); }
    synchronized Map<Integer, Integer> coinBox()   { return new TreeMap<>(coinBox); }

    abstract class State {                                          // default: every action is illegal here
        void insert(int coin)            { throw illegal("accept coins"); }
        Vend select(String slot)         { throw illegal("vend"); }
        List<Integer> cancel()           { throw illegal("refund"); }
        void outOfService()              { throw illegal("go out of service"); }
        void backInService()             { throw illegal("return to service"); }
        void restock(String slot, int n) { throw illegal("restock"); }
        void loadCoins(int coin, int n)  { throw illegal("load coins"); }
        private IllegalStateException illegal(String what) {
            return new IllegalStateException("cannot " + what + " while " + getClass().getSimpleName());
        }
    }

    class Idle extends State {
        @Override void insert(int coin) { accept(coin); state = new Collecting(); }
        @Override void outOfService()   { state = new OutOfService(); }
    }

    class Collecting extends State {
        @Override void insert(int coin) { accept(coin); }

        @Override Vend select(String slot) {
            Product p = products.get(slot);
            if (p == null) throw new IllegalArgumentException("no slot " + slot);
            if (stock.get(slot) == 0) throw new Refused(p.name() + " is sold out");
            if (credit < p.price()) throw new Refused("insert " + (p.price() - credit) + " more");
            List<Integer> change = makeChange(credit - p.price()).orElseThrow(() -> new Refused("exact change only"));
            stock.merge(slot, -1, Integer::sum);
            payOut(change);
            credit = 0;
            state = new Idle();
            return new Vend(p.name(), change);
        }

        @Override List<Integer> cancel() {
            List<Integer> refund = makeChange(credit).orElseThrow();   // the customer's own coins are in the box
            payOut(refund);
            credit = 0;
            state = new Idle();
            return refund;
        }
    }

    class OutOfService extends State {
        @Override void backInService() { state = new Idle(); }
        @Override void restock(String slot, int n) {
            if (!products.containsKey(slot) || n < 0) throw new IllegalArgumentException("bad restock of " + slot);
            stock.merge(slot, n, Integer::sum);
        }
        @Override void loadCoins(int coin, int n) {
            if (!accepted.contains(coin) || n < 0) throw new IllegalArgumentException("bad coins: " + coin);
            coinBox.merge(coin, n, Integer::sum);
        }
    }

    private void accept(int coin) {
        if (!accepted.contains(coin)) throw new IllegalArgumentException("rejected coin " + coin);   // drops to the tray
        coinBox.merge(coin, 1, Integer::sum);
        credit += coin;
    }

    private void payOut(List<Integer> coins) { for (int c : coins) coinBox.merge(c, -1, Integer::sum); }

    /** Fewest coins summing to amount, using only coins in the box (each at most once). Empty if impossible. */
    private Optional<List<Integer>> makeChange(int amount) {
        List<Integer> pieces = new ArrayList<>();                     // every physical coin, largest first
        coinBox.forEach((coin, count) -> { for (int i = 0; i < count; i++) pieces.add(coin); });
        int none = Integer.MAX_VALUE / 2;
        int[] fewest = new int[amount + 1];
        Arrays.fill(fewest, none);
        fewest[0] = 0;
        boolean[][] used = new boolean[pieces.size()][amount + 1];
        for (int i = 0; i < pieces.size(); i++) {                    // 0/1 knapsack, minimising the coin count
            int c = pieces.get(i);
            for (int a = amount; a >= c; a--)
                if (fewest[a - c] + 1 < fewest[a]) { fewest[a] = fewest[a - c] + 1; used[i][a] = true; }
        }
        if (fewest[amount] == none) return Optional.empty();
        List<Integer> change = new ArrayList<>();
        for (int i = pieces.size() - 1, a = amount; a > 0; i--)       // walk back through the choices
            if (used[i][a]) { change.add(pieces.get(i)); a -= pieces.get(i); }
        change.sort(Comparator.reverseOrder());
        return Optional.of(change);
    }
}
```

**Fennick's three bugs, gone by construction.** *Select with no money:* `Idle` doesn't override `select`, so it throws. *Cancel twice:* the first cancel moves to `Idle`, which doesn't override `cancel`. *Exact change only with three ₹2 coins:* that was greedy change-making. Here it is, compiled so the checker can show it failing:

```java id=greedyChange
// Largest coin first, as many as fit. Right for an infinite supply of 1-2-5-10-20; wrong for a real coin box.
List<Integer> greedyChange(int amount, TreeMap<Integer, Integer> box) {      // box ordered largest first
    List<Integer> change = new ArrayList<>();
    for (var e : box.entrySet()) {
        int coin = e.getKey(), left = e.getValue();
        while (left > 0 && coin <= amount) { change.add(coin); amount -= coin; left--; }
    }
    return amount == 0 ? change : null;                                     // null: "exact change only"
}
```

The box holds one ₹5 and three ₹2. The customer pays ₹20 for a ₹14 peanut bar, so the machine owes ₹6. Greedy takes the ₹5, needs ₹1, has none: *exact change only*. The knapsack finds **2 + 2 + 2**. Greedy is optimal for coin systems like 1-2-5-10-20 *only with unlimited coins*; a finite box breaks that guarantee. The checker compares `makeChange` against a brute-force search over every combination of coins in random boxes.

**Complexity:** change-making is O(coins in the box × amount) — a few thousand steps for a lobby machine. Say it; don't apologise for it.

<h3 id="vending-concurrency">Where the threads collide</h3>

A vending machine has one physical customer, but its software has at least two callers: the keypad and the operator's service port. Every public method is `synchronized`, and **the `state` field only changes inside a state's method, which only runs under that lock** — so a transition can never interleave with another button. If an interviewer asks for a remote "out of service" command, that is the second caller, and the lock already covers it.

<h3 id="lru-cut">The cut</h3>

| Must | Should | Won't |
|---|---|---|
| `get(key)` and `put(key, value)` in O(1) | Thread-safe on request | TTL, size-in-bytes capacity |
| Fixed capacity; evict the least recently used | Eviction policy as a seam (LFU later) | Distributed cache, write-through |
| A `get` counts as a use | | `null` values |

**The decision is two structures that each do half the job.** A `HashMap` finds a key in O(1) but knows nothing about order. A doubly linked list keeps recency order — most recent at the head, least recent at the tail — and can unlink any node in O(1) *if you already hold the node*. So the map stores **key → node**, and the list stores the order. Sentinel head and tail nodes remove every null check.

```java group=lru
class LruCache<K, V> {
    private final class Node {
        final K key;
        V value;
        Node prev, next;
        Node(K key, V value) { this.key = key; this.value = value; }
    }

    private final int capacity;
    private final Map<K, Node> index = new HashMap<>();
    private final Node head = new Node(null, null), tail = new Node(null, null);   // sentinels: no null checks

    LruCache(int capacity) {
        if (capacity < 1) throw new IllegalArgumentException("capacity must be at least 1");
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    V get(K key) {
        Node n = index.get(key);
        if (n == null) return null;
        moveToFront(n);                                // a read is a write: it changes the order
        return n.value;
    }

    void put(K key, V value) {
        Objects.requireNonNull(value, "null values would make get() ambiguous");
        Node n = index.get(key);
        if (n != null) { n.value = value; moveToFront(n); return; }
        if (index.size() == capacity) {                // evict the least recently used: the node before tail
            Node lru = tail.prev;
            unlink(lru);
            index.remove(lru.key);                     // this is why the node stores its key
        }
        n = new Node(key, value);
        index.put(key, n);
        linkFront(n);
    }

    int size() { return index.size(); }

    List<K> keysMostRecentFirst() {
        List<K> out = new ArrayList<>();
        for (Node n = head.next; n != tail; n = n.next) out.add(n.key);
        return out;
    }

    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void linkFront(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
    private void moveToFront(Node n) { unlink(n); linkFront(n); }
}
```

**Worked trace,** capacity 3: `put a`, `put b`, `put c` → order c, b, a. `get a` → a, c, b. `put d` → the cache is full, the tail end is **b**, so b is evicted → d, a, c. The checker runs 20,000 random operations at capacities 1 to 5 against `LinkedHashMap` in access order with `removeEldestEntry` — the JDK's own LRU — and the two agree on every `get` and on the full order after every step.

**Why the node stores its key:** eviction starts from the list (the tail) and must delete from the map. Without the key in the node, you'd have no way to find the map entry in O(1).

<Reveal q="Isn't LinkedHashMap with accessOrder = true just this, already written?">

Yes: `new LinkedHashMap<>(16, 0.75f, true)` plus an overridden `removeEldestEntry` is a correct single-threaded LRU in five lines, and in production you'd use it (or a library cache). Say that first — it shows you know the JDK. Interviewers then usually ask you to build it by hand, because the map-plus-list design is the actual question. Offer both, build the one they want.

</Reveal>

<h3 id="lru-concurrency">Where the threads collide</h3>

The reflex is a `ReadWriteLock`: many readers, one writer. **It is wrong here, because `get` writes** — it moves a node. Two "readers" moving nodes at the same time corrupt the links. So the honest thread-safe LRU is one lock around both operations (or a segmented design that gives up exact global LRU order, which is what production caches do). The <a href={`${BASE}lld/lessons/concurrency-for-lld/`}>concurrency lesson's</a> build #2 is this exact cache.

**Decisions.**

1. **The show is the unit of locking.** One show has a few hundred seats; two users fighting over F7 are, by definition, on the same show. A `synchronized` show makes "check every wanted seat, then mark them all" a single atomic step — and all-or-nothing for free. Locking per seat would allow more parallelism within one show, but a multi-seat hold must then take several locks in a fixed order to avoid deadlock. Say both; build the simple one.
2. **Holds expire lazily.** Every operation first frees holds whose time is up. No timer thread, nothing to shut down, and correctness never depends on a background job running on time. (A production system adds a sweeper so the seat map is accurate for browsing.)
3. **Never hold the lock while paying.** Payment takes seconds and can hang. The hold *is* the reservation; the lock only protects the moments of changing it.
4. **Time comes from an injected `Clock`.** Expiry is tested by moving a `ManualClock`, not by sleeping for ten minutes.

```java group=booking
import java.time.*;

enum SeatStatus { AVAILABLE, HELD, BOOKED }

record Hold(String id, String user, Set<String> seats, Instant expiresAt) {}
record Booking(String id, String user, Set<String> seats) {}

class HoldExpiredException extends RuntimeException {
    HoldExpiredException(String holdId) { super("hold " + holdId + " has expired or does not exist"); }
}

class Show {
    private final String id;
    private final Map<String, SeatStatus> seats = new LinkedHashMap<>();
    private final Map<String, Hold> holds = new HashMap<>();
    private final Clock clock;
    private final Duration holdFor;
    private int sequence = 0;

    Show(String id, List<String> seatIds, Clock clock, Duration holdFor) {
        this.id = id;
        this.clock = clock;
        this.holdFor = holdFor;
        for (String s : seatIds) seats.put(s, SeatStatus.AVAILABLE);
    }

    /** All the wanted seats, or none. Empty when any of them is held or booked. */
    synchronized Optional<Hold> hold(String user, Set<String> wanted) {
        if (wanted.isEmpty()) throw new IllegalArgumentException("pick at least one seat");
        expireHolds();
        for (String s : wanted) {
            SeatStatus status = seats.get(s);
            if (status == null) throw new IllegalArgumentException("no seat " + s);
            if (status != SeatStatus.AVAILABLE) return Optional.empty();
        }
        Hold h = new Hold(id + "-H" + (++sequence), user, Set.copyOf(wanted), clock.instant().plus(holdFor));
        for (String s : wanted) seats.put(s, SeatStatus.HELD);
        holds.put(h.id(), h);
        return Optional.of(h);
    }

    /** Call after payment succeeds. Throws if the hold ran out first: refund, don't book. */
    synchronized Booking confirm(String holdId) {
        expireHolds();
        Hold h = holds.remove(holdId);
        if (h == null) throw new HoldExpiredException(holdId);
        for (String s : h.seats()) seats.put(s, SeatStatus.BOOKED);
        return new Booking(id + "-B" + (++sequence), h.user(), h.seats());
    }

    synchronized void release(String holdId) {         // back button, or payment declined
        Hold h = holds.remove(holdId);
        if (h != null) free(h);
    }

    synchronized SeatStatus status(String seat) {
        expireHolds();
        return seats.get(seat);
    }

    private void expireHolds() {                       // lazy expiry: a hold is valid while now < expiresAt
        Instant now = clock.instant();
        for (Iterator<Hold> it = holds.values().iterator(); it.hasNext(); ) {
            Hold h = it.next();
            if (!now.isBefore(h.expiresAt())) { free(h); it.remove(); }
        }
    }

    private void free(Hold h) { for (String s : h.seats()) seats.put(s, SeatStatus.AVAILABLE); }
}
```

**Worked timeline,** holds last 10 minutes. At 19:00 Asha holds A5 and A6; her hold expires at 19:10:00. At 19:04 Ravi asks for A6 and A7: A6 is held, so he gets **nothing** — not A7 alone. At 19:10:00 exactly, Ravi asks again and gets both: at the expiry instant, `now.isBefore(expiresAt)` is false, so Asha's hold is gone. At 19:10:30 Asha's payment comes back approved; `confirm` throws `HoldExpiredException`, and the right response is a refund, not a booking. The checker runs this timeline with a `ManualClock`, second by second.

<h3 id="booking-concurrency">Where the threads collide</h3>

This is the chapter's whole point, and Oona's test is the proof: 40 threads, each repeatedly trying to hold a random pair of adjacent seats in a 30-seat show and immediately confirming. Afterwards the checker asserts that **no seat appears in two bookings**, every `BOOKED` seat belongs to exactly one booking, and every booking's seats are `BOOKED`. Then it repeats the race with a single hot seat: 64 threads, one booking.

<Reveal q="The cinema runs four app servers. Your synchronized Show lives in one JVM. What now?">

Move the atomic claim to the place all four servers share — the database. A conditional update does the same job as the lock: `UPDATE seats SET status = 'HELD', hold_id = ?, expires_at = ? WHERE show_id = ? AND seat_id IN (...) AND (status = 'AVAILABLE' OR (status = 'HELD' AND expires_at <= now))`, inside a transaction that checks the row count equals the number of seats wanted (or rolls back). A unique constraint on (show, seat) in the bookings table is the last line of defence. A Redis `SET key value NX PX 600000` per seat is the cache-shaped version of the same hold-with-TTL. Same skeleton — atomic claim plus expiry — at a different layer. This is the <a href={`${BASE}sd/lessons/pattern-contention/`}>SD contention pattern</a> in miniature; saying that cross-link out loud is exactly the range interviewers reward.

</Reveal>

<h3 id="elevator-cut">The cut</h3>

| Must | Should | Won't |
|---|---|---|
| One car, floors 0–9; requests from any floor | Scheduling policy as a strategy (FCFS, LOOK, SCAN) | Hall-call direction buttons (every call is a stop) |
| Keep direction while there is work ahead; reverse at the last request (LOOK) | A dispatcher for several cars | Weight limits, door sensors, emergency mode |
| Every request is served; none starves | Requests arrive while the car moves | Real-time timing — the simulation is tick-based |

**The decisions.** Model time as **ticks**: each `step()` either opens the doors at the current floor or moves one floor. That makes the scheduler deterministic and testable without threads or sleeps. The car keeps a sorted set of pending stops; the **scheduler** is a strategy that, given the floor, the direction and the stops, names the next target. Direction is a tiny enum-sized state (UP, DOWN, IDLE).

- **FCFS** drives to requests in arrival order: fair in theory, a saw blade in practice.
- **SCAN** (the "elevator algorithm" from disk scheduling) sweeps all the way to the end of the building before reversing.
- **LOOK** sweeps only as far as the last request in the current direction, then reverses. That's what we build.

```java group=elevator
enum Direction { UP, DOWN, IDLE }

interface Scheduler {
    /** The floor to head for next, or empty when there is nothing to do. */
    OptionalInt next(int floor, Direction dir, NavigableSet<Integer> stops);
}

class LookScheduler implements Scheduler {
    public OptionalInt next(int floor, Direction dir, NavigableSet<Integer> stops) {
        if (stops.isEmpty()) return OptionalInt.empty();
        Integer above = stops.ceiling(floor), below = stops.floor(floor);   // either may be this floor
        if (dir == Direction.UP)   return OptionalInt.of(above != null ? above : below);   // keep going, else reverse
        if (dir == Direction.DOWN) return OptionalInt.of(below != null ? below : above);
        if (above == null) return OptionalInt.of(below);                     // idle: nearest first, ties go up
        if (below == null) return OptionalInt.of(above);
        return OptionalInt.of(above - floor <= floor - below ? above : below);
    }
}

class Elevator {
    private final int lowest, highest;
    private final Scheduler scheduler;
    private final TreeSet<Integer> stops = new TreeSet<>();
    private final List<Integer> served = new ArrayList<>();
    private int floor;
    private Direction dir = Direction.IDLE;
    private int moves = 0;

    Elevator(int lowest, int highest, int start, Scheduler scheduler) {
        this.lowest = lowest;
        this.highest = highest;
        this.floor = start;
        this.scheduler = scheduler;
    }

    synchronized void request(int f) {                 // hall call or car button: both become a stop
        if (f < lowest || f > highest) throw new IllegalArgumentException("no floor " + f);
        stops.add(f);
    }

    synchronized void step() {                         // one tick: open the doors here, or move one floor
        OptionalInt target = scheduler.next(floor, dir, stops);
        if (target.isEmpty()) { dir = Direction.IDLE; return; }
        int t = target.getAsInt();
        if (t == floor) { stops.remove(floor); served.add(floor); return; }
        dir = t > floor ? Direction.UP : Direction.DOWN;
        floor += dir == Direction.UP ? 1 : -1;
        moves++;
    }

    synchronized int floor() { return floor; }
    synchronized Direction direction() { return dir; }
    synchronized NavigableSet<Integer> pendingStops() { return new TreeSet<>(stops); }
    synchronized List<Integer> served() { return List.copyOf(served); }
    synchronized int moves() { return moves; }
    synchronized boolean idle() { return stops.isEmpty(); }
}
```

And the contractor's controller, compiled so the checker can count its moves:

```java id=fcfs
// First come, first served: drive to each request in the order it arrived.
int fcfsMoves(int start, List<Integer> requests) {
    int moves = 0, at = start;
    for (int floor : requests) { moves += Math.abs(floor - at); at = floor; }
    return moves;
}
```

**Worked numbers,** Monday 08:58. The car is at 0; requests 9, 1, 8, 2. FCFS: 9 + 8 + 7 + 6 = **30 floors**. LOOK from idle picks the nearest stop (1), and the car is now going up, so it serves 1, 2, 8, 9 in one sweep: **9 floors**. A second case: the car is at 5 going up with stops at 7 and 2, and someone presses 6. LOOK serves **6, 7, 2** — 1 + 1 + 5 = 7 floors — because 6 is on the way. The checker simulates both.

**Why no request starves under LOOK:** a pending stop is either ahead of the car (it will be reached in this sweep) or behind it (the car reaches the last stop ahead, at most at the end of the building, then reverses). So the car travels at most **2 × (top − bottom)** floors between a request arriving and being served. The checker throws random requests at random ticks into a 10-floor building and asserts every request is served within 18 moves of arriving, and after it arrived.

<h3 id="elevator-concurrency">Where the threads collide</h3>

Buttons are pressed on many threads while the controller loop calls `step()`. Both `request` and `step` are `synchronized` on the car, so a stop added mid-tick is seen whole on the next tick, and `stops` (a plain `TreeSet`) is never iterated while it changes. The accessors return copies for the same reason. The dispatcher in the follow-up reads a snapshot of each car and then calls `request` — a stale snapshot only makes a choice slightly less optimal, never incorrect.

<HintLadder hints={hints.elevator} labels={turn}>

```java group=elevator
class NearestCarDispatcher {
    private final List<Elevator> cars;
    NearestCarDispatcher(List<Elevator> cars) { this.cars = List.copyOf(cars); }

    Elevator assign(int floor) {                       // ties go to the earlier car in the list
        Elevator best = null;
        int bestCost = Integer.MAX_VALUE;
        for (Elevator car : cars) {
            int cost = cost(car, floor);
            if (cost < bestCost) { best = car; bestCost = cost; }
        }
        best.request(floor);
        return best;
    }

    int cost(Elevator car, int f) {
        int at = car.floor();
        Direction d = car.direction();
        if (d == Direction.IDLE || (d == Direction.UP && f >= at) || (d == Direction.DOWN && f <= at))
            return Math.abs(f - at);                   // on the way
        NavigableSet<Integer> stops = car.pendingStops();
        int turn = stops.isEmpty() ? at : d == Direction.UP ? Math.max(at, stops.last()) : Math.min(at, stops.first());
        return Math.abs(turn - at) + Math.abs(turn - f);   // finish this sweep, then come back
    }
}
```

Car A is idle at 0; car B is at 6 going up to 9. A call from floor 4: A costs 4, B costs (9 − 6) + (9 − 4) = 8, so **A** goes. A call from floor 8: A costs 8, B costs 2, so **B**. The checker builds both situations.

</HintLadder>

**Catch the trap:** one `move()` method that decides direction, picks the next floor, handles doors and dispatches between cars. It works for one car and the interviewer's first example, and every follow-up (a second car, an express lift, a maintenance mode) edits it. **Car state, per-car scheduling and cross-car dispatch are three different reasons to change.**

**Say it aloud:** *"Each car has a sorted set of stops and a direction; a Scheduler strategy picks the next floor — LOOK by default, FCFS for comparison. Ticks keep it deterministic. A dispatcher strategy above the cars chooses which car takes a hall call, so adding cars doesn't touch the car."*

**Problem: Logger framework · pipeline + sinks.**

<h3 id="logger-cut">The cut</h3>

| Must | Should | Won't |
|---|---|---|
| Levels DEBUG < INFO < WARN < ERROR; a logger prints its level and above | An async appender so callers never wait for the disk | Config files, MDC, markers |
| Named loggers in a dotted hierarchy; a level set on `gearhouse.lift` applies to `gearhouse.lift.door` | Appender thresholds, rolling files | Structured JSON, log shipping |
| Several appenders (console, memory, file) with a pluggable layout | | |

**The decisions** — the same ones logback and log4j made, which is worth saying:

1. **Hierarchy is a chain.** Each logger has a parent (`gearhouse.lift.door` → `gearhouse.lift` → `gearhouse` → root). The **effective level** is the nearest level set on the way up. When an event passes, it is handed to this logger's appenders, then its parent's, and so on up — unless a logger is marked non-additive, which stops the chain. That is Chain of Responsibility, with the twist that every link handles the event instead of only one.
2. **Filter once, at the source.** The level check happens at the logger the call was made on, before an event is even built. Ancestors' levels do not re-filter it.
3. **Appenders are strategies (or observers).** The logger doesn't know where text goes; a `Layout` strategy decides how it looks.
4. **The registry builds parents first.** And it builds them *outside* `computeIfAbsent`, for a reason the trap section explains.

```java group=logger
import java.time.*;

enum Level { DEBUG, INFO, WARN, ERROR }                // ordered: a threshold passes itself and everything after it

record LogEvent(Instant at, Level level, String logger, String message) {}

interface Appender { void append(LogEvent e); }
interface Layout { String format(LogEvent e); }

class PatternLayout implements Layout {
    public String format(LogEvent e) { return e.at() + " " + e.level() + " [" + e.logger() + "] " + e.message(); }
}

class ConsoleAppender implements Appender {
    private final Layout layout;
    ConsoleAppender(Layout layout) { this.layout = layout; }
    public void append(LogEvent e) { System.out.println(layout.format(e)); }
}

class MemoryAppender implements Appender {             // tests, and the "last 100 lines" debug page
    final List<String> lines = Collections.synchronizedList(new ArrayList<>());
    private final Layout layout;
    MemoryAppender(Layout layout) { this.layout = layout; }
    public void append(LogEvent e) { lines.add(layout.format(e)); }
}

class Logger {
    private final String name;
    private final Logger parent;                       // null only for the root
    private final Clock clock;
    private volatile Level level;                      // null: inherit from the nearest ancestor that has one
    private volatile boolean additive = true;          // false: the chain stops here
    private final List<Appender> appenders = new CopyOnWriteArrayList<>();

    Logger(String name, Logger parent, Clock clock) {
        this.name = name;
        this.parent = parent;
        this.clock = clock;
    }

    void setLevel(Level level) { this.level = level; }
    void setAdditive(boolean additive) { this.additive = additive; }
    void addAppender(Appender a) { appenders.add(a); }
    String name() { return name; }

    Level effectiveLevel() {
        for (Logger l = this; l != null; l = l.parent) if (l.level != null) return l.level;
        return Level.DEBUG;                            // unreachable when the root has a level
    }

    void log(Level at, String message) {
        if (at.compareTo(effectiveLevel()) < 0) return;               // filtered once, at the source
        LogEvent e = new LogEvent(clock.instant(), at, name, message);
        for (Logger l = this; l != null; l = l.parent) {              // this logger's appenders, then each ancestor's
            for (Appender a : l.appenders) a.append(e);
            if (!l.additive) break;
        }
    }

    void debug(String m) { log(Level.DEBUG, m); }
    void info(String m)  { log(Level.INFO, m); }
    void warn(String m)  { log(Level.WARN, m); }
    void error(String m) { log(Level.ERROR, m); }
}

class LogManager {
    private final Clock clock;
    private final Logger root;
    private final Map<String, Logger> loggers = new ConcurrentHashMap<>();

    LogManager(Clock clock) {
        this.clock = clock;
        this.root = new Logger("", null, clock);
        root.setLevel(Level.INFO);
    }

    Logger root() { return root; }

    Logger get(String name) {                          // "gearhouse.lift.door" -> "gearhouse.lift" -> "gearhouse" -> root
        if (name.isEmpty()) return root;
        Logger existing = loggers.get(name);
        if (existing != null) return existing;
        int dot = name.lastIndexOf('.');
        Logger parent = get(dot < 0 ? "" : name.substring(0, dot));   // parents first, OUTSIDE computeIfAbsent
        return loggers.computeIfAbsent(name, n -> new Logger(n, parent, clock));
    }
}
```

**Worked example.** The root is at INFO with a memory appender R. `gearhouse.lift` is set to DEBUG with its own appender L. Then:

- `gearhouse.lift.door` logs DEBUG "still closed": its effective level is DEBUG (inherited from `gearhouse.lift`), so it passes, and lands in **L and R** (additive chain).
- `gearhouse.cinema` logs DEBUG "seat map": effective level INFO (from root) — **dropped**, nothing built.
- `gearhouse.cinema` logs WARN "hold expired": lands in **R only**.
- Set `gearhouse.lift` non-additive: the door's DEBUG lands in **L only** — the lift's noise stops reaching the main log, which is exactly what the on-call engineer needed at 2 a.m.

The checker builds random hierarchies with random levels and additivity, logs at every level from every logger, and compares each appender's contents against an independent oracle.

<h3 id="logger-concurrency">Where the threads collide</h3>

Two hotspots. **The registry:** many threads call `get("gearhouse.lift")` at startup and must receive the *same* logger, or a level set on one copy won't affect code holding the other. `computeIfAbsent` on a `ConcurrentHashMap` guarantees one value per key; the checker has 16 threads race for the same names and asserts identical instances. **The appenders:** the console and files are slow, and callers write from every thread. Levels and the appender list are `volatile` / copy-on-write so reconfiguration at runtime is visible without locking the hot path. And the disk — that's the follow-up.

<h3 id="logger-follow-up">The follow-up</h3>

Oona's sticky note: the app froze waiting to write. **Your turn.** Write `AsyncAppender`, a decorator that puts events on a bounded queue and lets one worker thread write them, with an explicit policy for a full queue.

<HintLadder hints={hints.logger} labels={turn}>

```java group=logger
class AsyncAppender implements Appender, AutoCloseable {
    private static final LogEvent STOP = new LogEvent(Instant.EPOCH, Level.ERROR, "", "stop");   // compared by reference
    private final Appender target;
    private final BlockingQueue<LogEvent> queue;
    private final AtomicLong dropped = new AtomicLong();
    private final Thread worker;
    private volatile boolean closed;

    AsyncAppender(Appender target, int capacity) {
        this.target = target;
        this.queue = new ArrayBlockingQueue<>(capacity);
        this.worker = new Thread(this::drain, "async-appender");
        worker.setDaemon(true);
        worker.start();                                // every field is assigned before the thread starts
    }

    public void append(LogEvent e) {                   // never blocks the caller
        if (closed || !queue.offer(e)) dropped.incrementAndGet();     // full: drop the newest and count it
    }

    private void drain() {
        try {
            for (LogEvent e = queue.take(); e != STOP; e = queue.take()) target.append(e);
        } catch (InterruptedException ie) {
            Thread.currentThread().interrupt();
        }
    }

    public void close() throws InterruptedException {  // flush what's queued, then stop
        closed = true;
        queue.put(STOP);
        worker.join();
    }

    long dropped() { return dropped.get(); }
}
```

The policy is the graded part: a bounded queue *will* fill, and "what then?" is the next question. The three honest answers are **block** the caller (no loss, but the app freezes again), **drop and count** (what this does; the count is itself logged), or **drop the low levels first** — logback's `AsyncAppender` by default starts discarding TRACE, DEBUG and INFO events when the queue is 80% full (check the current docs for the exact knobs). The checker pushes 5,000 events from 4 threads through a deliberately slow target with a capacity of 64 and asserts delivered + dropped = 5,000, with each thread's delivered events still in order; with a large queue, nothing is dropped.

</HintLadder>

**Catch the trap:** `loggers.computeIfAbsent(name, n -> new Logger(n, get(parentOf(n)), clock))` — creating the parent *inside* the mapping function. The `ConcurrentHashMap` documentation forbids a mapping function that updates other mappings of the same map; on modern JDKs it can fail with `IllegalStateException: Recursive update`, and older ones could loop forever. Build the parents first, then call `computeIfAbsent` with a function that does nothing but construct. You've seen its cousin in the War Room: <a href={`${BASE}lld/war/inventory/#2-a-lazily-built-strategy-map--data-race`}>a lazily built map, published unsafely</a>.

**Say it aloud:** *"Loggers form a tree by dotted name; the effective level is inherited and checked once at the source, then the event walks up the additive chain of appenders. Appenders and layouts are strategies. For the slow disk, an async decorator with a bounded queue and one worker — and when the queue fills, I drop and count rather than block."*

**Problem: Rate limiter · token bucket per key.** The SD lesson on <a href={`${BASE}sd/lessons/rate-limiter/`}>rate limiting</a> covers the distributed version; this is the in-process class you write in a machine-coding round.

<h3 id="limiter-cut">The cut</h3>

| Must | Should | Won't |
|---|---|---|
| `allow(key)`: true or false, immediately | Algorithm as a strategy (token bucket, sliding log, fixed window) | Distributed limits across servers (Redis — a port) |
| Each key has its own bucket: capacity 10, refilling 5 per second | Per-tier limits | Queuing or delaying requests |
| Exact under concurrency: never more than the bucket allows | Evict idle keys | Retry-After headers |

**Decisions.**

1. **Token bucket** — a bucket of `capacity` tokens refills continuously at a fixed rate; each request takes one or is rejected. It allows bursts up to the capacity and an average rate of the refill. Refill is **lazy**: computed from elapsed time when a request arrives, so no timer thread exists.
2. **Integer arithmetic, exactly.** Tokens are stored as `tokens × periodMillis`, so refilling `tokensPerPeriod` per period is `elapsedMillis × tokensPerPeriod` — no `double` drift, and tests can predict every count.
3. **Refill and take are one atomic step.** Two threads reading "1 token left" and both taking it is the bug.
4. **One bucket per key, created exactly once**, with `computeIfAbsent`.
5. **A clock that steps backwards mints nothing.** NTP corrections happen; the refill ignores negative elapsed time.

```java group=limiter
import java.time.*;

class TokenBucket {
    private final long capacity, tokensPerPeriod, periodMillis;
    private final Clock clock;
    private long scaled;                               // tokens x periodMillis: refill is exact integer arithmetic
    private long lastRefill;

    TokenBucket(long capacity, long tokensPerPeriod, Duration period, Clock clock) {
        if (capacity < 1 || tokensPerPeriod < 1 || period.toMillis() < 1) throw new IllegalArgumentException("bad bucket");
        this.capacity = capacity;
        this.tokensPerPeriod = tokensPerPeriod;
        this.periodMillis = period.toMillis();
        this.clock = clock;
        this.scaled = capacity * periodMillis;         // starts full
        this.lastRefill = clock.millis();
    }

    synchronized boolean tryAcquire() {                // refill and take: ONE atomic step
        refill();
        if (scaled < periodMillis) return false;
        scaled -= periodMillis;
        return true;
    }

    synchronized long available() { refill(); return scaled / periodMillis; }

    private void refill() {
        long now = clock.millis();
        if (now <= lastRefill) return;                 // the clock stood still or stepped back: mint nothing
        long full = capacity * periodMillis, elapsed = now - lastRefill;
        scaled = elapsed >= full ? full : Math.min(full, scaled + elapsed * tokensPerPeriod);
        lastRefill = now;
    }
}

interface RateLimiter { boolean allow(String key); }

class TokenBucketLimiter implements RateLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final Function<String, TokenBucket> newBucket;

    TokenBucketLimiter(long capacity, long tokensPerPeriod, Duration period, Clock clock) {
        this.newBucket = key -> new TokenBucket(capacity, tokensPerPeriod, period, clock);
    }

    public boolean allow(String key) {
        return buckets.computeIfAbsent(key, newBucket).tryAcquire();   // one bucket per key, created once
    }
}
```

**Worked numbers,** capacity 10, 5 tokens per second. At t = 0 the student's script sends 12 requests: **10 allowed, 2 rejected**. At t = 200 ms, 200 × 5 / 1000 = 1 token has refilled: one request allowed. At t = 300 ms only half a token has refilled: rejected. Silence until t = 1.2 s: another 0.9 s × 5 = 4.5 tokens on top of the half — **5** tokens. A different key at t = 0 still has its own full 10. The checker replays random request times against an independent oracle that simulates the bucket one millisecond at a time.

<h3 id="limiter-concurrency">Where the threads collide</h3>

The mess you'll be shown — or write, under time pressure — has two races:

```java fragment
class RacyLimiter {
    private final Map<String, TokenBucket> buckets = new HashMap<>();       // not thread-safe
    boolean allow(String key) {
        if (!buckets.containsKey(key)) buckets.put(key, newBucket());       // check-then-act: two buckets for one key
        TokenBucket b = buckets.get(key);
        if (b.tokens() >= 1) { b.take(); return true; }                     // check-then-act: two threads, one token
        return false;
    }
}
```

Fix both with the tools already on this page: `computeIfAbsent` for creation, and a `synchronized` `tryAcquire` that refills, checks and takes under one lock. Oona's test: 16 threads × 1,000 calls on one key with a frozen clock — exactly **10** succeed. Then 16 threads on 50 fresh keys at once — exactly 10 per key, so no key ever got two buckets.

<h3 id="limiter-follow-up">The follow-up</h3>

Bram: *"Partners have a contract: exactly 100 calls in any 60 seconds. Not 'on average'. Any 60 seconds."* A token bucket allows a burst of `capacity` plus refill in any window, so it can't promise that. A **fixed window** counter (reset every minute on the minute) is worse: it allows 100 at 00:59 and 100 more at 01:00 — 200 in two seconds. The exact answer is a **sliding window log**.

**Your turn.** Write `SlidingWindowLog implements RateLimiter`: at most `limit` allowed requests in any window of `windowMillis`.

<HintLadder hints={hints.limiter} labels={turn}>

```java group=limiter
class SlidingWindowLog implements RateLimiter {
    private final int limit;
    private final long windowMillis;
    private final Clock clock;
    private final Map<String, ArrayDeque<Long>> logs = new ConcurrentHashMap<>();

    SlidingWindowLog(int limit, Duration window, Clock clock) {
        this.limit = limit;
        this.windowMillis = window.toMillis();
        this.clock = clock;
    }

    public boolean allow(String key) {
        ArrayDeque<Long> log = logs.computeIfAbsent(key, k -> new ArrayDeque<>());
        synchronized (log) {                           // per-key lock: keys don't contend with each other
            long now = clock.millis();
            while (!log.isEmpty() && log.peekFirst() <= now - windowMillis) log.pollFirst();   // window is (now - W, now]
            if (log.size() >= limit) return false;
            log.addLast(now);
            return true;
        }
    }
}
```

The cost of exactness is memory: up to `limit` timestamps per key, against the token bucket's two numbers. With a limit of 3 per second, requests at 0, 100, 200 ms pass and 300 ms is rejected; at exactly 1,000 ms the request from 0 has left the window, so it passes. The checker compares random traffic against a brute-force count of allowed requests in every window. Same interface, so switching a partner's key to the exact limiter is a wiring change.

</HintLadder>

**Catch the trap:** a refill timer thread per bucket (ten thousand keys, ten thousand timers), or `double` tokens with `System.currentTimeMillis()` inside the bucket (untestable, and drifting). Lazy refill from an injected clock is simpler, exact and testable.

**Say it aloud:** *"A token bucket per key in a ConcurrentHashMap, created with computeIfAbsent. Refill is lazy from elapsed time on an injected clock, in integer units, and refill-check-take is one synchronized step. RateLimiter is an interface, so a partner who needs an exact window gets a sliding-log limiter behind the same seam."*

<h2 id="interview-script">Say it in the room</h2>

<Scene title="The interview room" mood="night">

The Interviewer slides a card across the table. It says *Design a movie ticket booking system* — but it could have said any of the eight, and you know it.

You don't start typing. You don't say "Strategy pattern". You pick up the marker.

</Scene>

**The first 90 seconds, for any problem in the canon** (adapt the nouns):

> "Let me pin down scope first. Must-haves: list shows and seats, hold seats, confirm a booking after payment. I'll treat payment as a port and leave search, cities and refunds out — tell me if any of those matter. The invariant that decides this problem is that no seat is ever booked twice, and the follow-up I'd expect is pricing tiers or running on several servers. So the entities are Show, which owns its seats and holds; Hold, with an expiry; and Booking. Pricing goes behind a PriceRule interface; everything else stays concrete. The contended step is the hold: I'll make it one atomic all-or-nothing claim under the show's lock, with expiry checked lazily against an injected Clock so I can test it without sleeping. The customer pays outside the lock, and confirm re-checks the hold. I'll build hold and confirm first, demo two users racing for one seat, then add pricing."

**Five follow-ups you will get:**

<Reveal q="1 · Why not just put synchronized on every public method of the top-level service?">

It is correct and it serialises everything — every car in the garage waits for every other car, every show's bookings queue behind every other show's. The skill being tested is choosing the **smallest unit that contains the invariant**: the spot for parking, the show for seats, the bucket for a rate-limit key, the ledger for balances. Locks at that level are still simple, and unrelated work runs in parallel. (For a ledger, the whole ledger *is* the smallest unit, and that's fine to say.)

</Reveal>

<Reveal q="2 · Your design holds state in memory. How does it change on three servers?">

The domain model doesn't change; the **claim moves** to the shared store. A seat hold becomes a conditional `UPDATE … WHERE status = 'AVAILABLE'` (or `SET NX PX` in Redis), a parking spot the same, a rate-limit bucket a Redis script that refills and decrements atomically, a ledger a database transaction. Name the atomic primitive, and keep the expiry (TTL) on the claim so a crashed server can't leave inventory locked forever.

</Reveal>

<Reveal q="3 · How do you test expiry, refills and fees without sleeping?">

Every design takes a `java.time.Clock`. Production passes `Clock.systemUTC()`; tests pass a manual clock they advance by hand — hold at 19:00, advance ten minutes, assert the seat is free. Same for refills (advance 200 ms, expect one token) and fees (advance 130 minutes, expect three started hours). A test that sleeps is slow and flaky; a test that sets the time is instant and exact.

</Reveal>

<Reveal q="4 · Where would you use State instead of Strategy, and what's the difference?">

Strategy is a choice made from outside — the client or the configuration picks a pricing rule, and it doesn't change itself. State is a choice the object makes about itself as things happen — the vending machine moves from `Idle` to `Collecting` because a coin arrived, and the meaning of the buttons changes with it. If the variation is "which algorithm", Strategy; if it is "which mode am I in, given my history", State. The elevator uses both: a scheduler strategy, and a direction state.

</Reveal>

<Reveal q="5 · You have seven interfaces and fifteen minutes left. What do you cut?">

Keep the interfaces with a second implementation, a test fake, or a follow-up already signalled — the fee strategy, the clock, the payment port. Inline the rest out loud: *"SeatRepository has one implementation and no fake; I'd make it a field."* Then spend the time on what is graded: a running demo, the race test, and the follow-up landing as a class.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Start with… | The promise to keep |
|---|---|---|
| Limited resources, many claimants (spots, seats, rooms, slots) | An entity with an atomic `tryAssign` / `hold`; search is only a hint | One claimant per resource, under any concurrency |
| Money split among people | Integer minor units; a `Split` strategy; net balances | Shares sum to the amount; balances sum to zero |
| "Settle up with fewest payments" | Greedy max debtor → max creditor over net balances | At most n − 1 transfers; optimum is NP-hard |
| Buttons that mean different things in different modes | One class per state; the base throws for illegal actions | Illegal actions change nothing |
| Change from a real coin box | Bounded knapsack over coins present | Never "exact change only" when change exists |
| O(1) get/put with recency eviction | HashMap key → node + doubly linked list with sentinels | Node carries its key; get is a write |
| A reservation the customer may abandon | Hold with expiry, lazy cleanup, injected clock | Valid while now is before expiry; confirm re-checks |
| Serving requests along a line (floors, disk tracks) | LOOK scheduler as a strategy; ticks | No request waits more than two sweeps |
| Named components with inherited settings | A parent chain; effective value = nearest set ancestor | Filter once at the source; additivity decides the chain |
| Slow sink, many producers | Bounded queue + one worker, explicit overflow policy | Callers never block on I/O |
| N per period per key | Token bucket per key, lazy integer refill, `computeIfAbsent` | Refill-check-take is one atomic step |
| "Exactly N in any window" | Sliding window log | Memory grows with N per key |

## Five mistakes to leave behind

1. **Check-then-act at the hotspot.** `if (free) take()` in two calls is the bug in four of the eight problems. Make the claim one atomic step on the thing being claimed.
2. **`double` for money and `now()` inside the domain.** Paise in a `long`; time from an injected `Clock`. Both make tests exact.
3. **One method that does everything.** `move()`, `fee()`, `isLegal()` with a switch inside. Find the reasons to change and give each one a class.
4. **Locking too much, or too little.** A lock on the whole service, or a read-write lock on a structure whose reads write. Lock the smallest unit that contains the invariant — and know what "read" really does.
5. **Patterns before axes.** Naming Strategy, Observer and Factory in minute two. Name what varies first; the pattern is the answer, not the opening line.
