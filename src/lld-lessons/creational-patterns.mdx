<h2 id="prologue">What creational patterns solve</h2>

### Concept

`new` is the most innocent word in Java and the most committed one. `new UpiProcessor()` hard-codes **a concrete class, a construction recipe, and a lifetime** into the line that says it. When that line is in `main()`, fine: somebody has to decide. When it sits inside the billing counter, the patient portal and the refund desk at once, all three classes must change when the decision changes.

**Creational patterns answer one question: when should the code that uses an object not be the code that decides how it is made?** Each pattern moves one kind of decision somewhere better.

### Problem

The example system for this whole lesson is a clinic platform: billing (UPI, card, wallet), appointments, lab orders, invoices, a database that allows 100 connections. A first draft written without any pattern has `new` scattered everywhere. Typical symptoms: a new payment type means editing three files; a test cannot replace the database; two services each open their own connection pool.

### The decisions and their patterns

| The decision | Move it out when... | Pattern | Chapter |
|---|---|---|---|
| **Which class?** | the choice depends on runtime data and is repeated at several call sites | Simple factory, then registry of instances or of suppliers | 1 |
| **Which class, inside a fixed algorithm?** | the algorithm is the same and only the object it creates differs | Factory Method | 2 |
| **Which family?** | several objects must always come from the same variant | Abstract Factory | 3 |
| **Assembled how?** | many optional parts, and rules between the parts | Builder | 4 |
| **From what?** | the cheapest correct start is a copy of a configured exemplar | Prototype | 5 |
| **How many?** | exactly one must exist, or a bounded few must be reused | Singleton (as a scope), Object Pool | 6, 7 |
| **Decided by whom?** | those decisions are scattered across the codebase | Dependency injection, composition root | 8 |

This is the first of three lessons on patterns. This one covers *creating* objects; the <a href={`${BASE}lld/lessons/structural-patterns/`}>structural patterns lesson</a> covers *connecting* them; the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> covers how they *behave at runtime*. The War Room <a href={`${BASE}lld/war/patterns-why/`}>dossiers</a> come from a real production hospital platform, so most patterns here have a "this actually happened" link.

### Trade-offs

Creational patterns are the **most over-applied patterns in machine-coding rounds**: a `ParkingLotFactory` for an object constructed once, a Singleton for something that only needed to be passed in, a builder for a record with two fields. Graders mark ceremony down as surely as a God class. Every chapter below ends with "When not to use it". Those sections are half the lesson.

### Interview summary

> "Creational patterns separate using an object from deciding how it is made. I reach for a factory when the class depends on data, an abstract factory when several objects must match, a builder when rules span many fields, a copy constructor for templates, and I let one composition root own every long-lived object. I name a pattern only when a requirement forces it."

<h2 id="three-ladders">Chapter 1: Simple factory and registry</h2>

### Concept

A **simple factory** is one place that decides which concrete class to build and returns the interface. A **registry** is the same idea where each implementation announces its own key, so adding a variant does not edit the chooser.

### Problem

The billing counter takes UPI, card and wallet. Finance adds EMI (monthly instalments for expensive scans) and someone adds `EMI` to the payment-mode enum. Everything compiles. A patient chooses EMI for a knee MRI and the system sends it to the wallet processor, which rejects it.

The cause: the counter decides which processor to build with an `if` ladder whose last branch is a plain `else`, so "everything that is not UPI or card is a wallet". The patient portal and the refund desk have copies of the same ladder. Nobody remembered all three.

### Bad design

The choice of concrete class, made at every call site, with a catch-all `else`:

```java id=ladderMess
enum PaymentMode { UPI, CARD, WALLET, EMI }           // EMI was added later

interface PaymentProcessor { String process(long paise); }
class UpiProcessor implements PaymentProcessor { public String process(long paise) { return "upi-" + paise; } }
class CardProcessor implements PaymentProcessor { public String process(long paise) { return "card-" + paise; } }
class WalletProcessor implements PaymentProcessor { public String process(long paise) { return "wallet-" + paise; } }

class CounterDesk {                                  // PortalCheckout and RefundDesk carry the same ladder, copied
    String charge(PaymentMode mode, long paise) {
        PaymentProcessor p;
        if (mode == PaymentMode.UPI) p = new UpiProcessor();
        else if (mode == PaymentMode.CARD) p = new CardProcessor();
        else p = new WalletProcessor();              // "everything else is a wallet": true until EMI was added
        return p.process(paise);
    }
}
```

Running it: `charge(EMI, 500000)` returns `wallet-500000`. No exception, no warning. The new mode silently lands in the wrong branch.

<Reveal q="Before reading on: EMI arrives again, later. In this design, how many files do you edit, and what happens if you miss one?">

Three files (counter, portal, refunds), plus the enum. Miss one and EMI silently becomes a wallet payment in that screen only. That is the bug above. The structure makes the mistake easy; the fix must make one place the only place.

</Reveal>

**Detection cues:**

1. **`new` on a concrete class, chosen by an `if` or `switch` on a type code.** The caller knows every implementation by name.
2. **The same ladder in several places.** Each new variant is a scavenger hunt; the one you miss is the bug.
3. **A catch-all `else` or `default`.** It turns "I forgot this case" from a compile error into a wrong answer.

### Better design

**Step 1: the simple factory.** Move the decision to one place that returns the *interface*. Callers now depend only on `PaymentProcessor`.

```java group=billing
enum PaymentMode { UPI, CARD, WALLET }

record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("money cannot be negative");
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }   // a static factory method
}

record PaymentRequest(PaymentMode mode, Money amount) {}

record PaymentResult(boolean ok, String reference) {
    static PaymentResult success(String reference) { return new PaymentResult(true, reference); }
}

interface PaymentProcessor { PaymentResult process(PaymentRequest r); }

class UpiProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("upi-" + r.amount().paise());
    }
}
class CardProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("card-" + r.amount().paise());
    }
}
class WalletProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("wallet-" + r.amount().paise());
    }
}

class ProcessorFactory {
    PaymentProcessor forMode(PaymentMode mode) {
        return switch (mode) {
            case UPI    -> new UpiProcessor();
            case CARD   -> new CardProcessor();
            case WALLET -> new WalletProcessor();
        };  // exhaustive switch over an enum, no default: add a mode and this stops compiling. That's a feature.
    }
}

// The counter, the portal, and refunds all just say:
PaymentResult charge(ProcessorFactory factory, PaymentRequest request) {
    PaymentProcessor p = factory.forMode(request.mode());
    return p.process(request);
}
```

A ten-rupee UPI payment, `charge(factory, new PaymentRequest(UPI, Money.rupees(10)))`, returns reference `upi-1000`. Money travels as paise in a `long`, never as a `double`. Add `EMI` to this enum and the switch **refuses to compile** until someone decides what EMI means. The `else` became a compiler error, which is where you want "I forgot a case" to surface.

This is usually called a **simple factory**. It is not one of the 23 Gang of Four patterns. The GoF **Factory Method** is the next chapter, and the difference is a favourite interview follow-up.

**Step 2: the registry.** "Isn't that switch an OCP violation?" Technically yes. Honestly graded, no: the variation is contained in one class whose single job is choosing, and an exhaustive enum switch gets compiler help. The upgrade, when the switch outgrows a screen or implementations live in different modules, is a registry. Each implementation announces its own key, and the switch disappears. The interface gains a method, so this is a real edit and starts a fresh design:

```java group=registry
// Unchanged from the simple factory, repeated so this design compiles on its own.
enum PaymentMode { UPI, CARD, WALLET }
record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("money cannot be negative");
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }
}
record PaymentRequest(PaymentMode mode, Money amount) {}
record PaymentResult(boolean ok, String reference) {
    static PaymentResult success(String reference) { return new PaymentResult(true, reference); }
}
```

```java group=registry
interface PaymentProcessor {
    PaymentMode mode();                              // each impl declares its OWN key
    PaymentResult process(PaymentRequest r);
}

class UpiProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.UPI; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("upi-" + r.amount().paise()); }
}
class CardProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.CARD; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("card-" + r.amount().paise()); }
}
class WalletProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.WALLET; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("wallet-" + r.amount().paise()); }
}

class UnsupportedModeException extends RuntimeException {
    UnsupportedModeException(PaymentMode mode) { super("no processor for " + mode); }
}

class ProcessorRegistry {
    private final Map<PaymentMode, PaymentProcessor> byMode;

    ProcessorRegistry(List<PaymentProcessor> processors) {
        this.byMode = processors.stream()
            .collect(Collectors.toUnmodifiableMap(PaymentProcessor::mode, p -> p));
        // toUnmodifiableMap throws on duplicate keys — two impls claiming UPI fails at STARTUP, not mid-payment
    }

    PaymentProcessor forMode(PaymentMode mode) {
        PaymentProcessor p = byMode.get(mode);
        if (p == null) throw new UnsupportedModeException(mode);  // the map is not exhaustive — name the miss policy
        return p;
    }
}

// Wiring — the ONLY place that lists implementations (Spring injects this list automatically):
ProcessorRegistry wiring() {
    return new ProcessorRegistry(List.of(
        new UpiProcessor(), new CardProcessor(), new WalletProcessor()));
}
```

The knowledge "UPI means UpiProcessor" moved *into UpiProcessor itself*. A new mode is a new class plus one wiring entry, with zero edits to the registry. You traded compile-time exhaustiveness for runtime flexibility; say that trade out loud. Two startup guarantees, confirmed by the checker: two processors claiming `UPI` make the constructor throw `IllegalStateException`, and a mode nobody wired throws `UnsupportedModeException` naming the mode. Production's version: <a href={`${BASE}lld/war/patterns-why/#2-registry--the-inbound-webhook-routing-problem`}>the Registry dossier</a>, webhook handlers announcing their provider key, built once in the constructor, immutable, failing at boot rather than at 2 a.m.

**Step 3: a registry of suppliers.** The registry above hands every caller *the same instance*. That is right for stateless processors and wrong when an object holds state that belongs to one use, such as a checklist for one patient or a retry counter for one payment. Then the registry stores **how to make one**, a `Supplier<T>`, instead of the thing itself:

```java group=registry
class ProcessorSuppliers {
    private final Map<PaymentMode, Supplier<PaymentProcessor>> makers;

    ProcessorSuppliers(Map<PaymentMode, Supplier<PaymentProcessor>> makers) {
        makers.forEach((mode, maker) -> {            // the key is written BESIDE the supplier, so check it at startup
            PaymentMode made = maker.get().mode();
            if (made != mode) throw new IllegalArgumentException(mode + " is wired to a " + made + " processor");
        });
        this.makers = Map.copyOf(makers);
    }

    PaymentProcessor fresh(PaymentMode mode) {
        Supplier<PaymentProcessor> maker = makers.get(mode);
        if (maker == null) throw new UnsupportedModeException(mode);
        return maker.get();                          // a new object on every call
    }
}

ProcessorSuppliers supplierWiring() {
    return new ProcessorSuppliers(Map.of(
        PaymentMode.UPI,    UpiProcessor::new,
        PaymentMode.CARD,   CardProcessor::new,
        PaymentMode.WALLET, WalletProcessor::new));
}
```

`UpiProcessor::new` is a factory you can store in a map: a constructor reference is a `Supplier`. One cost to say out loud: in the instance registry the key comes *from* the object (`mode()`), so it cannot drift. Here the key sits *beside* the supplier, so a typo such as `CARD, WalletProcessor::new` would route card payments to the wallet. The constructor builds one throwaway instance per key at startup and refuses a mismatch. The checker wires exactly that typo and watches it fail at construction.

### How it works

- **Callers** hold a `PaymentProcessor` and call `process`. They never name a concrete class.
- **The factory or registry** is the only code that knows which concrete class belongs to which key.
- **Wiring** (in `main()`) is the only place that lists implementations.

| | Simple factory (`switch`) | Registry of instances | Registry of suppliers |
|---|---|---|---|
| Who knows the mapping | the factory | each implementation (`mode()`) | the wiring |
| New variant costs | a `case` plus a class (compiler finds the switch) | a class plus one wiring entry | a class plus one wiring entry |
| Forgetting it fails | at compile time | at the first lookup | at the first lookup |
| Objects returned | new each call | one shared instance per key | new each call |
| Right when | a handful of variants, one module | stateless handlers that grow, maybe across modules | each use needs its own state |

**Static factory methods** are the small sibling: `Money.rupees(10)`, `PaymentResult.success(ref)`, `Duration.ofMinutes(5)`, `List.of(...)`. They are named constructors that validate, cache, or return subtypes (*Effective Java* Item 1). `Money.rupees` also uses `Math.multiplyExact`, so an absurd amount throws instead of silently overflowing.

### When to use

- A `switch` or `if` ladder on a type code builds a class, and the same choice appears in more than one place.
- Variants keep arriving (payment modes, export formats, notification channels).
- Each use needs its own stateful object (use the supplier registry).

### Trade-offs

A class constructed in exactly one place, with one implementation, needs no factory: `new` in `main()` *is* the factory. Do not build a registry for two variants that will never grow; the switch is shorter and the compiler checks it. Never discover implementations by **reflection or classpath scanning** in a 90-minute round. An explicit list in the wiring is readable, debuggable and fast.

<Reveal q="EMI arrives again. What exactly changes in the ladder, the switch factory, and the registry?">

**The ladder:** a new enum constant, then three edits in three files. Miss one and EMI silently becomes a wallet payment. **The switch factory:** a constant, an `EmiProcessor`, and one `case`; the compiler points at the switch, so you cannot miss it. **The registry:** a constant, an `EmiProcessor` that returns `EMI` from `mode()`, and one entry in the wiring list; no lookup code is touched. Forget the wiring entry and the first EMI payment throws `UnsupportedModeException`, loud and named, but at runtime. That is the trade: compile-time exhaustiveness versus not editing the chooser.

</Reveal>

**Your turn.** The lab desk prints a fresh order form for each test: blood panel, X-ray, MRI. Each form carries a **checklist the technician ticks off for that patient** ("fasting confirmed", "metal removed"). Today one shared form object per test type is handed out, and a tick for one patient has appeared on the next patient's MRI form. Write `LabOrders`: fresh forms per call, a loud failure for an unknown test, and a startup check that every test is wired to the right form.

<HintLadder hints={hints.labOrders} labels={turn}>

```java group=labs
enum LabTest { BLOOD_PANEL, XRAY, MRI }

interface LabOrder {
    LabTest test();
    List<String> checklist();                      // mutable: ticked off per patient
}

class BloodPanelOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("fasting confirmed", "two tubes labelled"));
    public LabTest test() { return LabTest.BLOOD_PANEL; }
    public List<String> checklist() { return checklist; }
}
class XrayOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("pregnancy screen", "metal removed"));
    public LabTest test() { return LabTest.XRAY; }
    public List<String> checklist() { return checklist; }
}
class MriOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("implant screen", "metal removed", "ear protection"));
    public LabTest test() { return LabTest.MRI; }
    public List<String> checklist() { return checklist; }
}

class LabOrders {
    private final Map<LabTest, Supplier<LabOrder>> makers;

    LabOrders(Map<LabTest, Supplier<LabOrder>> makers) {
        makers.forEach((test, maker) -> {
            if (maker.get().test() != test) throw new IllegalArgumentException(test + " is wired to the wrong form");
        });
        this.makers = Map.copyOf(makers);
    }

    LabOrder newOrder(LabTest test) {
        Supplier<LabOrder> maker = makers.get(test);
        if (maker == null) throw new IllegalArgumentException("no order form for " + test);
        return maker.get();
    }
}

LabOrders labOrders() {
    return new LabOrders(Map.of(
        LabTest.BLOOD_PANEL, BloodPanelOrder::new,
        LabTest.XRAY,        XrayOrder::new,
        LabTest.MRI,         MriOrder::new));
}
```

Two MRI orders are two objects: ticking "metal removed" off one leaves the other's three items intact (the checker does exactly that). A registry of *instances* would have shared one MRI form between every patient, which is the bug.

</HintLadder>

**A common slip:** *"A factory means I can never get a compile error for a missing case."* Only if you choose a map. An exhaustive `switch` expression over an enum, with no `default`, is the one creational shape where the compiler finds the call site for you. Pick the registry when you want the chooser closed, and accept that misses move to runtime.

### Interview summary

> "I centralize creation behind a factory returning the interface. If implementations multiply, I flip it to a registry where each one announces its key, built once at startup so duplicates fail at boot. If each use needs its own state, the registry holds suppliers instead of instances."

<h2 id="the-hook">Chapter 2: Factory Method</h2>

### Concept

**Factory Method** defines a skeleton algorithm in a *creator* class, with one step that creates an object left abstract. Subclasses (or an injected `Supplier`) decide which class that step creates. The Gang of Four wording: "Define an interface for creating an object, but let subclasses decide which class to instantiate."

### Problem

The clinic wants a doctor-utilisation report every evening, showing visits per doctor. Finance wants it as CSV. Reception wants it on the old dot-matrix printer in fixed-width columns. The easy solution is copy and paste: `CsvUtilisationReport` and `PrinterUtilisationReport`, forty lines each, identical except the lines that format output. Then a bug fix lands in one of them (doctors sorted by name in the CSV) and the printer version still prints in hash-map order. Thirty-seven of the forty lines are the same.

### Bad design

Two copies of one algorithm, differing in a single decision (which formatter to use) and already drifting:

```java fragment
class CsvUtilisationReport {
    String render(Map<String, Integer> visitsByDoctor) {
        StringBuilder sb = new StringBuilder("doctor,visits");
        new TreeMap<>(visitsByDoctor).forEach((d, v) -> sb.append('\n').append(d).append(',').append(v));   // fixed: sorted
        return sb.toString();
    }
}
class PrinterUtilisationReport {
    String render(Map<String, Integer> visitsByDoctor) {
        StringBuilder sb = new StringBuilder("DOCTOR      VISITS");
        visitsByDoctor.forEach((d, v) -> sb.append('\n').append(String.format("%-12s%d", d, v)));          // never got the fix
        return sb.toString();
    }
}
```

**Detection cue:** two or more classes whose methods are the same skeleton with **one `new` (or one formatting call) different**, and a bug fix that landed in only one of them.

### Better design

The skeleton lives once, in a **creator** class. The one line that differs becomes an abstract method that *creates* the object, and each subclass answers it:

```java group=reports
interface Exporter {
    String header();
    String row(String doctor, int visits);
}

class CsvExporter implements Exporter {
    public String header() { return "doctor,visits"; }
    public String row(String doctor, int visits) { return doctor + "," + visits; }
}

class PrinterExporter implements Exporter {                     // fixed-width for the dot-matrix printer
    public String header() { return "DOCTOR      VISITS"; }
    public String row(String doctor, int visits) { return String.format("%-12s%d", doctor, visits); }
}

abstract class UtilisationReport {                              // the creator
    final String render(Map<String, Integer> visitsByDoctor) {  // the algorithm, written once: final
        Exporter out = createExporter();                        // the factory method
        StringBuilder sb = new StringBuilder(out.header());
        new TreeMap<>(visitsByDoctor).forEach((doctor, visits) -> sb.append('\n').append(out.row(doctor, visits)));
        return sb.toString();
    }

    protected abstract Exporter createExporter();               // subclasses decide WHICH class
}

class CsvUtilisationReport extends UtilisationReport {
    protected Exporter createExporter() { return new CsvExporter(); }
}

class PrinterUtilisationReport extends UtilisationReport {
    protected Exporter createExporter() { return new PrinterExporter(); }
}
```

For Dr Rao with 14 visits and Dr Iyer with 9, the CSV report is `doctor,visits`, `Dr Iyer,9`, `Dr Rao,14`. The printer report now gets the same sorted order for free, because the sorting lives in the one `render` both share. `render` is `final` so no subclass can fork the algorithm again.

This is **a Template Method whose varying step is a creation.** That is how the GoF present it: the factory method is usually called from inside the creator's own algorithm. The JDK's canonical example is `Collection.iterator()`: every collection runs the same "give me something to walk you with" request, and each subclass decides which iterator class to build.

**Composition instead of inheritance: pass the factory in.** A subclass whose only job is to override `createExporter` is a lot of ceremony for one line. In Java 8+, one creator that *takes* a `Supplier` replaces the whole family of subclasses:

```java group=reports
class SuppliedReport extends UtilisationReport {                // Factory Method by composition
    private final Supplier<Exporter> exporters;
    SuppliedReport(Supplier<Exporter> exporters) { this.exporters = exporters; }
    protected Exporter createExporter() { return exporters.get(); }
}

String eveningReports(Map<String, Integer> visits) {
    String csv = new SuppliedReport(CsvExporter::new).render(visits);
    String printer = new SuppliedReport(PrinterExporter::new).render(visits);
    return csv + "\n\n" + printer;
}
```

The checker confirms `new SuppliedReport(CsvExporter::new)` renders exactly what `CsvUtilisationReport` renders, character for character. A `Supplier` handed in from outside is Chapter 1's registry of suppliers with one entry.

| | Inheritance form | Composition form |
|---|---|---|
| Who decides the class | a subclass overrides `createExporter` | a `Supplier` passed to the constructor |
| New variant costs | a new subclass | a new lambda or constructor reference |
| Fits when | the subclass also overrides other steps | the only difference is the created object |

### How it works

1. A caller invokes `render(visits)` on a concrete report.
2. `render` (final, in the creator) calls `createExporter()`.
3. The subclass (or supplier) returns a `CsvExporter` or `PrinterExporter`.
4. `render` uses the returned `Exporter` through the interface and never learns its class.

### When to use

- A fixed algorithm (report, import, campaign loop) where exactly one created object varies.
- A framework base class that cannot know which concrete helper the application wants.

### Trade-offs

One product, forever: just call `new` inside the algorithm. A creator hierarchy where each subclass overrides only the factory method: prefer the injected `Supplier`. And if the creator has no algorithm of its own, it only creates, so it is not Factory Method at all; it is a simple factory wearing inheritance.

<h2 id="sandbox-money">Chapter 3: Abstract Factory</h2>

### Concept

**Abstract Factory** makes a *family* of related objects the unit of construction. One factory interface has a method per product; one implementation exists per variant (sandbox, live). A consumer takes the factory, so it can never mix products from different variants.

### Problem

The system has a test mode. The payment gateway, the refund client and the webhook signature verifier each come in a **sandbox** version and a **live** version. After a release, every card payment shows *unpaid*: the gateway's confirmations are rejected. Worse, a test webhook signed with the sandbox's test secret, which is printed in the gateway's public documentation, was accepted in production. The release wired the live gateway with the sandbox verifier. Each object, on its own, was correct. The combination was the bug.

### Bad design

Members of two families, wired one object at a time:

```java fragment
// Wiring assembled one object at a time:
PaymentGateway gateway   = new PennyPayGateway(live.apiKey());           // live money
WebhookVerifier verifier = new SandboxVerifier(sandbox.testSecret());    // copied from the test setup
BillingService billing   = new BillingService(gateway, verifier);
```

The bug is not one wrong object; it is a **mixed family**. The checker reproduces both symptoms with the classes in the next block: a genuine live-signed webhook fails the sandbox verifier, and a forgery signed with the public test secret passes it, while the live verifier rejects the forgery.

**Detection cue:** the word **"family"**, or a sentence like "these three must always match". Several products, each with variants, and an invariant *across* the products: never a live gateway with a sandbox verifier; never a GST invoice with a gateway for another country.

### Better design

Make the *family* the unit of construction: one factory interface with a method per product, one implementation per variant. First the products:

```java group=suites
interface PaymentGateway  { String charge(String patientId, long paise); }
interface RefundClient    { String refund(String chargeRef); }
interface WebhookVerifier { boolean verify(String payload, String signature); }

record SandboxConfig(String baseUrl, String testSecret) {}
record LiveConfig(String apiKey, String webhookSecret) {}

static String sign(String secret, String payload) {               // stand-in for HMAC-SHA256: secret-dependent, deterministic
    return Integer.toHexString((secret + "|" + payload).hashCode());
}

class SandboxGateway implements PaymentGateway {
    private final String baseUrl;
    SandboxGateway(String baseUrl) { this.baseUrl = baseUrl; }
    public String charge(String patientId, long paise) { return "sandbox:" + patientId + ":" + paise; }   // no money moves
}
class SandboxRefundClient implements RefundClient {
    private final String baseUrl;
    SandboxRefundClient(String baseUrl) { this.baseUrl = baseUrl; }
    public String refund(String chargeRef) { return "sandbox-refund:" + chargeRef; }
}
class SandboxVerifier implements WebhookVerifier {
    private final String testSecret;
    SandboxVerifier(String testSecret) { this.testSecret = testSecret; }
    public boolean verify(String payload, String signature) { return sign(testSecret, payload).equals(signature); }
}

class PennyPayGateway implements PaymentGateway {
    private final String apiKey;
    PennyPayGateway(String apiKey) { this.apiKey = apiKey; }
    public String charge(String patientId, long paise) { return "pennypay:" + patientId + ":" + paise; }  // real money
}
class PennyPayRefundClient implements RefundClient {
    private final String apiKey;
    PennyPayRefundClient(String apiKey) { this.apiKey = apiKey; }
    public String refund(String chargeRef) { return "pennypay-refund:" + chargeRef; }
}
class PennyPayVerifier implements WebhookVerifier {
    private final String webhookSecret;
    PennyPayVerifier(String webhookSecret) { this.webhookSecret = webhookSecret; }
    public boolean verify(String payload, String signature) { return sign(webhookSecret, payload).equals(signature); }
}
```

Then the family contract, the two suites, and a consumer that takes the suite:

```java group=suites
interface GatewaySuite {           // the family contract
    PaymentGateway gateway();
    RefundClient refunds();
    WebhookVerifier verifier();
}

class SandboxSuite implements GatewaySuite {
    private final SandboxConfig cfg;
    SandboxSuite(SandboxConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new SandboxGateway(cfg.baseUrl()); }
    public RefundClient refunds()     { return new SandboxRefundClient(cfg.baseUrl()); }
    public WebhookVerifier verifier() { return new SandboxVerifier(cfg.testSecret()); }
}

class LiveSuite implements GatewaySuite {
    private final LiveConfig cfg;
    LiveSuite(LiveConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new PennyPayGateway(cfg.apiKey()); }
    public RefundClient refunds()     { return new PennyPayRefundClient(cfg.apiKey()); }
    public WebhookVerifier verifier() { return new PennyPayVerifier(cfg.webhookSecret()); }
}

class BillingService {
    private final PaymentGateway gateway;
    private final WebhookVerifier verifier;

    BillingService(GatewaySuite suite) {            // takes the FAMILY, never its members one by one
        this.gateway = suite.gateway();
        this.verifier = suite.verifier();
    }
    String charge(String patientId, long paise) { return gateway.charge(patientId, paise); }
    boolean confirm(String payload, String signature) { return verifier.verify(payload, signature); }
}

// Wiring picks ONE suite:
GatewaySuite suiteFor(boolean prod, LiveConfig liveCfg, SandboxConfig sandboxCfg) {
    return prod ? new LiveSuite(liveCfg) : new SandboxSuite(sandboxCfg);
}
```

**Where the guarantee actually comes from.** A suite on its own only makes the right thing *easy*: a caller could still write `new BillingService(live.gateway(), sandbox.verifier())` if `BillingService` accepted members. The constructor that accepts **the suite itself** makes the wrong thing *impossible*: there is no parameter list into which you could put a live gateway and a sandbox verifier. The environment is chosen once, in `suiteFor`, and everything billing touches comes from that choice. In a real codebase, make the product constructors package-private next to their suite, so the only way to get a `PennyPayVerifier` is through `LiveSuite`.

### How it works

1. Wiring picks one suite (`suiteFor(prod, ...)`).
2. `BillingService` receives the suite and asks it for the gateway and the verifier.
3. Both come from the same variant, by construction.

**Abstract Factory vs Factory Method.** Factory Method is one creation step varied by *inheritance* inside an algorithm. Abstract Factory is an *object* with several creation methods, chosen once, whose job is to keep products consistent. An abstract factory is often implemented with factory methods, but the intent differs: "vary one object in an algorithm" versus "keep N objects matching".

**Its known weakness.** Adding a new *family* (a staging environment, a second country) is one new class (Side quest 2 does it). Adding a new *product* to every family (say, a `PayoutClient`) edits the `GatewaySuite` interface **and every suite that implements it**. The GoF list this among the pattern's consequences: supporting new kinds of products is difficult. Before you reach for it, ask which axis grows: variants (cheap) or products (expensive).

### When to use

- The phrase "these N objects must always match" (live with live, one country's gateway with its tax format, one UI theme's widgets).
- A test double that must replace a whole group of collaborators together (the `RecordingSuite` below).

### Trade-offs

One product with variants is a factory, not a family. Two environments that differ only in **data** (a URL, a key) are one class configured twice: `new PennyPayGateway(sandboxKey)` against the sandbox endpoint needs no suite at all. If you cannot name the cross-product invariant ("never mix X with Y"), there is no family to protect.

<h2 id="eight-parameters">Chapter 4: Builder</h2>

### Concept

A **Builder** assembles one complex object step by step in a mutable staging object, then produces an immutable result through a single `build()` call. `build()` is where the rules that span several fields are checked.

### Problem

A booking record has eight constructor arguments: patient, doctor, slot, room, referral note, two booleans, an insurance id. A follow-up booking for room R-3 was meant to be *follow-up: true, teleconsult: false*. The call read `new Booking("P-1042", "D-07", slot, "R-3", null, true, false, null)`, and the constructor wanted the booleans the other way round. The system booked a video call in a physical room. Nothing could object, because no single place sees all the fields at once.

### Bad design

Telescoping constructors (each overload adds a parameter and delegates to the longest) and a call site nobody can read:

```java id=bookingMess
import java.time.*;

record Slot(LocalDateTime start, int minutes) {}

class Booking {
    final String patientId, doctorId, roomId, referralNote, insuranceId;
    final Slot slot;
    final boolean teleconsult, followUp;

    Booking(String patientId, String doctorId, Slot slot) {
        this(patientId, doctorId, slot, null, null, false, false, null);
    }
    Booking(String patientId, String doctorId, Slot slot, String roomId) {
        this(patientId, doctorId, slot, roomId, null, false, false, null);
    }
    Booking(String patientId, String doctorId, Slot slot, String roomId, String referralNote,
            boolean teleconsult, boolean followUp, String insuranceId) {
        this.patientId = patientId;
        this.doctorId = doctorId;
        this.slot = slot;
        this.roomId = roomId;
        this.referralNote = referralNote;
        this.teleconsult = teleconsult;
        this.followUp = followUp;
        this.insuranceId = insuranceId;
    }
}
```

The checker builds the booking with exactly that call: it succeeds, and the result is a teleconsult *with a room* that is *not* a follow-up.

**Detection cues:**

1. **More than about four parameters, several of the same type side by side.** Two `boolean`s or three `String`s in a row can be transposed and still compile.
2. **`null` passed to mean "I do not care".** Every `null` is a question the reader cannot answer.
3. **Overloads multiplying.** Each new optional field is another constructor. The War Room inventory found <a href={`${BASE}lld/war/inventory/#bonus-smell-six-overloads`}>six overloads of one method, telescoping through boolean flags</a>, the same pain one level up.
4. **Rules between fields with no home.** "Teleconsult means no room" belongs to the *whole* booking; no setter and no single parameter can enforce it.

### Better design

The full hand-rolled shape (rounds ask you to *write* this, not just call it). Blocks on this page are compiled as nested classes, which is why a few classes carry `static`; in your own files they are top-level and the keyword disappears.

```java group=booking
import java.time.*;

record Slot(LocalDateTime start, int minutes) {
    Slot {
        Objects.requireNonNull(start, "start");
        if (minutes <= 0) throw new IllegalArgumentException("a slot lasts at least one minute");
    }
}

static final class Booking {
    // all final — a built Booking is immutable
    private final String patientId;      // required
    private final String doctorId;       // required
    private final Slot slot;             // required
    private final boolean teleconsult;   // optional, default false
    private final String roomId;         // optional (but required in person — a cross-field rule)
    private final boolean followUp;      // optional, default false
    private final String referralNote;   // optional
    private final List<String> symptoms; // optional, possibly empty

    private Booking(Builder b) {         // private: the ONLY way in is build()
        this.patientId    = b.patientId;
        this.doctorId     = b.doctorId;
        this.slot         = b.slot;
        this.teleconsult  = b.teleconsult;
        this.roomId       = b.roomId;
        this.followUp     = b.followUp;
        this.referralNote = b.referralNote;
        this.symptoms     = List.copyOf(b.symptoms);   // a snapshot: later builder calls can't reach in
    }

    static Builder builder() { return new Builder(); }

    String patientId()          { return patientId; }
    String doctorId()           { return doctorId; }
    Slot slot()                 { return slot; }
    boolean teleconsult()       { return teleconsult; }
    Optional<String> roomId()   { return Optional.ofNullable(roomId); }
    boolean followUp()          { return followUp; }
    Optional<String> referral() { return Optional.ofNullable(referralNote); }
    List<String> symptoms()     { return symptoms; }    // List.copyOf is already unmodifiable

    static final class Builder {
        private String patientId;
        private String doctorId;
        private Slot slot;
        private boolean teleconsult = false;   // defaults live here
        private String roomId;
        private boolean followUp = false;
        private String referralNote;
        private final List<String> symptoms = new ArrayList<>();

        private Builder() {}

        Builder patient(String id)      { this.patientId = id; return this; }   // return this = chaining
        Builder doctor(String id)       { this.doctorId = id; return this; }
        Builder slot(Slot s)            { this.slot = s; return this; }
        Builder teleconsult(boolean t)  { this.teleconsult = t; return this; }
        Builder room(String roomId)     { this.roomId = roomId; return this; }
        Builder followUp(boolean f)     { this.followUp = f; return this; }
        Builder referral(String note)   { this.referralNote = note; return this; }
        Builder symptom(String s)       { symptoms.add(Objects.requireNonNull(s, "symptom")); return this; }  // one field: fail fast

        Booking build() {
            // 1. required fields present
            if (patientId == null || doctorId == null || slot == null)
                throw new IllegalStateException("patient, doctor, slot are required");
            // 2. CROSS-FIELD invariants — the whole point of build()
            if (teleconsult && roomId != null)
                throw new IllegalStateException("teleconsult bookings cannot have a room");
            if (!teleconsult && roomId == null)
                throw new IllegalStateException("in-person bookings need a room");
            return new Booking(this);
        }
    }
}

// Usage reads like the requirements doc:
Booking teleconsultFor(Slot slot) {
    return Booking.builder()
        .patient("P-1042")
        .doctor("D-07")
        .slot(slot)
        .teleconsult(true)
        .build();
}

Booking orThursdaysMistakeFixed(Slot slot) {          // the transposed booking, now impossible to write
    return Booking.builder()
        .patient("P-1042").doctor("D-07").slot(slot)
        .room("R-3")
        .followUp(true)
        .build();
}
```

Changes, and why:

- **Builder fields are mutable, the product's are final.** Mutation is quarantined inside the builder and ends at `build()`.
- **The product's constructor is private.** A half-configured `Booking` has no way to exist.
- **Setters `return this`** for chaining; **defaults live in the builder's field initializers.**
- **`build()` holds the cross-field rules** (teleconsult excludes room; in-person needs a room). A builder that just sets fields is syntax; a builder whose `build()` can refuse is an invariant gate. It restores the "constructed means valid" guarantee from the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson</a>. Lombok's `@Builder` writes the setters for you, but the rules in `build()` are yours either way, which is why rounds ask for the hand-rolled version.
- **`List.copyOf` in the constructor** snapshots the symptoms list.

**Three tiers of validation**, each in its own place:

| Rule | Example | Where it lives | When it fails |
|---|---|---|---|
| About one value | a symptom cannot be null; a slot lasts at least 1 minute | the setter, or the value's own type (`Slot`'s compact constructor) | immediately, at the bad call |
| Required presence | patient, doctor, slot | `build()`, or the builder's own signature (Your turn) | at `build()`, or at compile time |
| Between fields | teleconsult implies no room | `build()` | at `build()` |

**Final is not immutable.** `final List<String> symptoms` only stops the *field* from being reassigned. If the constructor stored the builder's list directly, a second `symptom(...)` call on the same builder, or any caller holding the list, would change a "built, immutable" booking. `List.copyOf` takes a snapshot that is also unmodifiable. The checker reuses one builder for two bookings and confirms the first booking's symptoms did not move, that `symptoms().add(...)` throws, and that every field of `Booking` is declared `final`.

<Reveal q="The cross-field rule is a fork: teleconsult XOR room. Is there a design where the invalid combination cannot even be written?">

Yes: **two named static factories** instead of a boolean, `Booking.teleconsult(patient, doctor, slot)` and `Booking.inPerson(patient, doctor, slot, room)`. Neither signature has a slot for the forbidden combination, so the rule moves from a runtime check to the type system. That beats the builder *for this rule*. The builder still earns its place when there are many independent optional fields (follow-up, referral, symptoms, insurance); the two compose, since `inPerson(...)` can return a builder pre-loaded with the fork already decided.

</Reveal>

### When to use

- A constructor past about four parameters, half of them optional.
- Rules that span fields and must hold for every instance that exists.
- An object that must be immutable once built.

### Trade-offs

Few fields, all required: a **record with a compact constructor** is the whole pattern in three lines (`record Slot(LocalDateTime start, int minutes)` validates itself above, no builder needed). A cluster of parameters that always travel together: a **parameter object**. A builder whose `build()` checks nothing and whose product has setters anyway is ceremony with extra steps.

<h2 id="the-photocopier">Chapter 5: Prototype</h2>

### Concept

**Prototype** creates a new object by copying a configured exemplar instead of building from scratch. In Java the honest tool is a **copy constructor** (or a static `copyOf`), not `clone()`.

### Problem

Every invoice starts from its clinic's standard template: letterhead, tax fields, the registration fee as a default line. Building the template costs three configuration lookups, so the old code built it once and copied it per patient. At 9:40 one clinic adds a chest X-ray to one patient's invoice. By noon every new invoice at that clinic has a chest X-ray on it. Seventeen patients were billed for a scan they did not have. The `clone()` method had one line inside it.

### Bad design

`Cloneable` and `super.clone()`: a field-by-field copy, so both "copies" hold **the same list**:

```java id=cloneMess
record LineItem(String code, String description, long paise) {}

class InvoiceTemplate implements Cloneable {
    String header;
    List<LineItem> items = new ArrayList<>();

    @Override public InvoiceTemplate clone() {
        try {
            return (InvoiceTemplate) super.clone();      // copies the REFERENCE to items, not the list
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);                 // can't happen: we implement Cloneable
        }
    }
}
```

The checker builds a template with one registration line, clones it, adds an X-ray to the clone, and the *template* now has two lines.

**Detection cue:** "start from a configured exemplar" (templates, default settings, a pre-filled form) where building from scratch is expensive or the configuration lives elsewhere. The moment you hear "copy", ask the graded question: **which fields are mutable, and does the copy get its own?**

### Better design

A copy constructor decides, field by field, what is shared and what is duplicated:

```java group=invoices
record LineItem(String code, String description, long paise) {}

class InvoiceTemplate {
    private final String header;
    private final List<LineItem> items;
    private final Map<String, String> taxFields;      // GSTIN, place of supply, ...

    InvoiceTemplate(String header, List<LineItem> items, Map<String, String> taxFields) {
        this.header = header;
        this.items = new ArrayList<>(items);
        this.taxFields = new LinkedHashMap<>(taxFields);
    }

    InvoiceTemplate(InvoiceTemplate other) {                       // copy constructor = Prototype in Java
        this.header = other.header;                                // String is immutable: sharing is safe
        this.items = new ArrayList<>(other.items);                 // a fresh list; the LineItem records inside are immutable, so they can be shared
        this.taxFields = new LinkedHashMap<>(other.taxFields);     // a fresh map — a shared map would let edits bleed between "copies"
    }

    void addItem(LineItem item)                  { items.add(item); }
    void setTaxField(String name, String value)  { taxFields.put(name, value); }
    String header()                              { return header; }
    List<LineItem> items()                       { return Collections.unmodifiableList(items); }
    Map<String, String> taxFields()              { return Collections.unmodifiableMap(taxFields); }

    long totalPaise() {
        long sum = 0;
        for (LineItem item : items) sum += item.paise();
        return sum;
    }
}

InvoiceTemplate patientInvoice(InvoiceTemplate standardTemplate) {
    InvoiceTemplate invoice = new InvoiceTemplate(standardTemplate);    // clone, then customize
    invoice.addItem(new LineItem("XR-01", "Chest X-ray", 85000));
    return invoice;
}
```

With a template holding one registration line of 200 rupees (20,000 paise), `patientInvoice` returns an invoice totalling 105,000 paise, and the template still totals 20,000 with one line. The checker also edits a tax field on the copy and confirms the template's map did not change.

**How deep is deep?** The rule: **copy every mutable thing reachable from the object; share every immutable thing**. Here the list and the map are mutable, so each copy gets its own; the `String` and the `LineItem` records are immutable, so sharing them is correct. "Deep copy" does not mean "copy everything recursively"; it means *no mutable state is shared*. Side quest 3 makes `LineItem` mutable and shows that `new ArrayList<>(...)` stops being enough.

**Why not `clone()`?** Prefer **copy constructors or `toBuilder()`** over `Cloneable`, which is broken by design (*Effective Java*, Item 13):

- `Cloneable` has **no `clone` method**. It is a marker that changes how the protected `Object.clone()` behaves; the interface itself promises nothing.
- `Object.clone()` is **shallow** and creates the copy **without running a constructor**, so any validation or setup in your constructors is skipped.
- It throws the **checked** `CloneNotSupportedException`, so every override wraps a `try` around something that cannot happen.
- It **fights `final` fields**: to deep-copy a `final List` inside `clone()`, you would have to reassign a final field, which does not compile.
- The one place `clone()` is the right tool: **arrays**. `int[] copy = original.clone();` is the idiomatic array copy (for arrays of mutable objects it is still shallow).

### How it works

1. A template object exists, fully configured (the exemplar).
2. A caller copies it with `new InvoiceTemplate(template)`: immutable fields shared, mutable containers duplicated.
3. The caller customises its own copy. The exemplar is never touched.

      +totalPaise() long

    class LineItem {

Both "copies" now share **one** `List` object. Customize the patient's invoice by adding a line item and the standard template silently grows that line too; every future invoice inherits it. Nothing crashes, no exception: the corruption just accumulates. That is why the rule is **deep-copy every mutable field**; immutable fields (`String header`) are safe to share, which is also the argument for making fields immutable in the first place.

</Reveal>

### When to use

- Templates, default configurations, pre-filled forms.
- Objects whose setup is expensive or lives outside the class, so copy-then-tweak is simpler than rebuild.
- A catalog of named exemplars (a prototype registry).

### Trade-offs

If construction is cheap and needs no outside configuration, just construct. If the object is **immutable, do not copy it at all**: share it. For variations of an immutable object, use "withers": `template.withHeader("Riverside")` returns a new object. And do not build a prototype registry for one template.

<h2 id="two-pools">Chapter 6: Singleton</h2>

### Concept

A **Singleton** guarantees that exactly one instance of a class exists in the process and gives everyone a way to reach it. The pattern bundles two separate ideas: **"there is one"** (a lifetime) and **"anyone can reach it from anywhere"** (a global access point). The first is often a real requirement. The second is where most of the damage comes from.

This chapter covers three things in order: why a naive lazy singleton is broken, the three thread-safe Java forms (enum, holder idiom, double-checked locking with `volatile`) and exactly why each is safe, and why in a real application a DI container usually makes the pattern unnecessary.

### Problem

At 6:02 p.m. the clinic database refuses new connections and all eleven clinics stop booking. The database allows a hundred connections; the application's pool opens twenty. An evening report job, needing "just one quick query", constructed its own `new ClinicDbPool()`, twenty more, and then a retry loop did it again. Two things went wrong at once: **anyone could call the constructor**, and the lazy `get()` that was meant to guard it was not thread-safe.

### Bad design

A public constructor (so anyone can make another) and a lazy `get()` with an unguarded check-then-act:

```java id=lazyMess
static final class LazyPool {
    private static LazyPool instance;                   // not volatile, no lock
    static final AtomicInteger opened = new AtomicInteger();

    LazyPool() {                                        // not private: anyone can open another pool
        opened.incrementAndGet();
        pause(50);                                      // opening 20 connections takes a while
    }

    static LazyPool get() {
        if (instance == null) instance = new LazyPool(); // check-then-act: two threads can both see null
        return instance;
    }
}

static void pause(long millis) {
    try { Thread.sleep(millis); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}
```

Watch the race first. Two threads both read `instance`, both see `null`, and both construct. Each step is safe alone; the pair is not atomic:

<ThreadTimelineSim scenario="check-then-act" title="Two threads, one lazy get(): both see null" />

The checker releases sixty-four threads at `LazyPool.get()` together: several of them see `null` during the slow constructor and each opens a pool. It also constructs a second `LazyPool` directly, because the constructor is not private.

**Detection cues:** a `static` field assigned inside an `if (x == null)`; a `getInstance()` with no lock and no `volatile`; a constructor that is not `private`.

### Better design

**The Java answers, in the order you should prefer them:**

```java group=singletons
// 1. Enum — serialization-safe, reflection-safe, thread-safe by class initialization. Effective Java's answer.
enum MetricsRegistry {
    INSTANCE;
    private final Map<String, LongAdder> counters = new ConcurrentHashMap<>();
    void record(String key, long value) { counters.computeIfAbsent(key, k -> new LongAdder()).add(value); }
    long total(String key) {
        LongAdder sum = counters.get(key);
        return sum == null ? 0 : sum.sum();
    }
}

// 2. Holder idiom — lazy without locks: class initialization is thread-safe by JLS guarantee.
static final class Config {
    static final AtomicInteger created = new AtomicInteger();   // demo-only: counts constructions
    private final Map<String, String> values;
    private Config() {
        created.incrementAndGet();
        values = Map.of("clinic.timezone", "Asia/Kolkata", "pool.size", "20");
    }
    private static class Holder { static final Config I = new Config(); }
    static Config get() { return Holder.I; }
    String value(String key) { return values.get(key); }
}

// 3. Double-checked locking — the classic exam answer. volatile is NOT optional:
static final class ClinicDbPool {
    private static volatile ClinicDbPool instance;
    static final AtomicInteger opened = new AtomicInteger();    // demo-only: counts pools opened
    private final int connections;

    private ClinicDbPool() {
        connections = 20;
        opened.incrementAndGet();
        pause(50);                                              // slow, like a real pool — widens every race
    }

    static ClinicDbPool get() {
        if (instance == null) {                                 // check 1: no lock on the fast path
            synchronized (ClinicDbPool.class) {
                if (instance == null) instance = new ClinicDbPool();   // check 2: under the lock
            }
        }
        return instance;
    }

    int connections() { return connections; }
}

static void pause(long millis) {
    try { Thread.sleep(millis); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}
```

| Form | Lazy? | Safe because | Reflection and serialization | Use when |
|---|---|---|---|---|
| **Enum** | on first use of the enum class | the JVM runs class initialization once, under a lock | safe: reflection cannot create enum instances, deserialization returns the same constant | default choice for a hand-rolled singleton; cannot extend a class |
| **Holder idiom** | yes, on the first `get()` | `Holder` is initialized once, on first touch, by the same JVM guarantee | not safe by default (needs a guard and `readResolve`) | must be lazy and must be a normal class |
| **Double-checked locking + `volatile`** | yes | a lock for creation plus `volatile` for safe publication | not safe by default | to show you know the memory model; rarely needed in practice |
| Eager `static final` field | no | class initialization | not safe by default | cheap to build and always needed |

The checker runs the three tested forms under the same sixty-four-thread cold start: one `MetricsRegistry`, one `Config`, one `ClinicDbPool`, and the constructors' counters read exactly 1. It also proves the holder is **lazy**: reading `Config.created` initializes `Config` but not `Holder`, and the counter is still 0 until the first `get()`.

**Why each form is safe.**

- **Enum:** the JVM creates `INSTANCE` during class initialization, which the Java Language Specification (§12.4.2) runs exactly once under a lock. Enums also defeat the two classic attacks. `Constructor.newInstance` refuses to create enum objects (the checker tries and gets `IllegalArgumentException`), and serialization writes enums by name and reads back the *same* constant (the checker round-trips `INSTANCE` through `ObjectOutputStream` and gets the identical object). A class-based singleton needs extra code for both, and the checker shows a reflective `setAccessible(true)` call happily making a second `Config`.
- **Holder:** `Holder` is not initialized until `get()` first touches `Holder.I`, and that initialization is the same JVM-guaranteed, once-only step. Lazy, and lock-free on every later call.
- **Double-checked locking (DCL):** check 1 keeps the common path lock-free; check 2 is the real decision, made under the lock; `volatile` makes the published reference safe to read without the lock.

**Common slips with DCL**, worth saying aloud because each is a classic interview probe:

1. *"volatile: always read the latest state of the object."* Close. The sharper version: `volatile` makes the write of `instance` a **safe publication**. Everything the constructor wrote *happens-before* any thread that reads the non-null reference. Without it, the reference can be visible before the fields it points to.
2. *"Private constructor required, otherwise any class in the same package can call it."* Exactly right, and it is what the 6:02 incident was: a report job calling `new` around all the ceremony. No private constructor, no singleton.
3. *"Two threads can pass check 1 before either locks; they enter the synchronized block one at a time; without the re-check, the second thread constructs a second pool."* Exactly right, and you can watch it happen:

```java id=noRecheckMess
static final class ClinicDbPool {
    private static volatile ClinicDbPool instance;
    static final AtomicInteger opened = new AtomicInteger();
    private ClinicDbPool() { opened.incrementAndGet(); pause(50); }

    static ClinicDbPool get() {
        if (instance == null) {
            synchronized (ClinicDbPool.class) {
                instance = new ClinicDbPool();          // no second check: every thread that passed check 1 builds one
            }
        }
        return instance;
    }
}

static void pause(long millis) {
    try { Thread.sleep(millis); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}
```

Under the checker's sixty-four threads, every thread that passed check 1 during the first 50 ms queues on the lock and builds its own pool, one after another.

### How it works: why volatile matters

`instance = new ClinicDbPool()` is three steps: allocate memory, run the constructor, write the reference. The Java Memory Model may reorder it to allocate, **write the reference**, then construct. A second thread then sees non-null at check 1, skips the lock, and returns a pool whose constructor has not finished. `volatile` forbids that reordering and creates a happens-before edge between the constructor's writes and any later read of the reference. DCL has been correct with `volatile` since Java 5's memory model (JSR-133).

Visibility is a separate problem from the race above. Without `volatile`, a reader thread has **no guarantee** of ever seeing another thread's write:

A non-null reference to a **partially constructed** object, because the reference write can be reordered before the constructor's field writes. The second thread skips the synchronized block (the reference is non-null) and reads default field values. `volatile` on `instance` forbids that reordering. Without a private constructor there is no singleton at all.

One honest caveat about tests: **no test on this page can show the missing-`volatile` bug.** It needs a specific reordering on a specific JIT and CPU, and typical x86 hardware rarely exhibits it. A passing test proves nothing here; the memory model does. That is the strongest reason to prefer the enum or the holder: there is no cliff to fall off.

**Other ways a "singleton" ends up with two instances:**

| Cause | Why | Fix |
|---|---|---|
| Public or package-private constructor | anyone can call `new` | private constructor |
| Reflection (`setAccessible(true)`) | bypasses `private` | enum, or throw from the constructor if one already exists |
| Serialization | deserializing creates a new object | enum, or `readResolve` returning the instance |
| Several classloaders | one class per classloader means one "singleton" per classloader (common in app servers and plugin systems) | one owner for the object, injected |
| Several processes or servers | a singleton is one per JVM, never one per cluster | an external coordinator (database, lock service), not a Java pattern |

**Why a Singleton is usually a smell.** "There is one" is a lifetime. "Anyone can reach it" is a hidden dependency:

```java group=singletons

        MetricsRegistry.INSTANCE.record("bookings", 1);   // a hidden, global dependency

}
```

`BookingDesk`'s constructor says it needs nothing. It is lying. Its test cannot substitute the metrics, and because the registry outlives every test, the checker shows the bleed: test A books once and sees `bookings = 1`; test B, run next in the same JVM, books once and sees **2**. Order-dependent tests, invisible dependencies, and no seam for a fake: that is the real charge sheet, not "singletons are slow". ### When a DI container makes a Singleton unnecessary

In real systems, **a singleton is a scope, not a pattern**. A DI container (or your `main()`) constructs one instance and injects it everywhere. You keep the one-ness and lose the global access point:

| Concern | Hand-rolled Singleton | One instance owned by a container or `main()` |
|---|---|---|
| Exactly one instance | private constructor plus a thread-safe form | the wiring creates it once |
| Who can reach it | everyone, through `get()` or `INSTANCE` | only classes that declare it in their constructor |
| Replace it in a test | hard; global state bleeds across tests | pass a fake into the constructor |
| Thread safety of construction | you must get DCL, holder or enum right | the container handles it |
| Thread safety of use | still yours | **still yours** (see below) |

A container's "singleton scope" is exactly this. Here is the idea in a few lines of compilable Java: bindings with either a shared (singleton) or per-use scope, built on demand, safe under concurrent callers.

```java group=container
record Pool(int id) {}
record ReportJob(Pool pool) {}

static final AtomicInteger poolsOpened = new AtomicInteger();

static final class MiniContainer {
    private record Binding(Supplier<?> recipe, boolean shared) {}

    private final Map<Class<?>, Binding> bindings = new HashMap<>();
    private final Map<Class<?>, Object> instances = new HashMap<>();

    <T> void singleton(Class<T> type, Supplier<T> recipe) { bindings.put(type, new Binding(recipe, true)); }
    <T> void perUse(Class<T> type, Supplier<T> recipe)    { bindings.put(type, new Binding(recipe, false)); }

    synchronized <T> T get(Class<T> type) {                 // one lock: construction is serialized, so a singleton is built once
        Binding binding = bindings.get(type);
        if (binding == null) throw new IllegalArgumentException("nothing bound to " + type.getSimpleName());
        if (!binding.shared()) return type.cast(binding.recipe().get());
        Object existing = instances.get(type);
        if (existing == null) {
            existing = binding.recipe().get();
            instances.put(type, existing);
        }
        return type.cast(existing);
    }
}

MiniContainer wiring() {                                    // the composition root, in miniature
    MiniContainer c = new MiniContainer();
    c.singleton(Pool.class, () -> new Pool(poolsOpened.incrementAndGet()));
    c.perUse(ReportJob.class, () -> new ReportJob(c.get(Pool.class)));
    return c;
}
```

```java fragment
// Spring says the same thing with annotations. Singleton scope is the default.
@Configuration
class AppConfig {
    @Bean ClinicDbPool pool() { return new ClinicDbPool(20); }          // built once per application context
}

@Service
class AppointmentService {
    AppointmentService(ClinicDbPool pool) { this.pool = pool; }        // visible, replaceable in tests
    private final ClinicDbPool pool;
}
```

Things to say precisely in an interview:

- A container singleton is **one per container**, not one per JVM. Two application contexts in one process create two instances.
- It is **shared by every request thread**, so a singleton bean must be stateless or thread-safe. The container removes the construction race, not the usage race.
- Hand-rolling a Singleton class in a codebase that already has a container is a smell. The container supplies the scope for free.
- Instance per use is the other scope (`@Scope("prototype")` in Spring, `perUse` above). For fresh objects inside a singleton, inject a factory (`Supplier` or `ObjectProvider`) rather than the object.

**When a Singleton class is still reasonable:** no container and a tiny tool or library; a genuinely process-wide, near-stateless piece of infrastructure (a metrics registry, `Runtime.getRuntime()` in the JDK); or a stateless strategy where an enum constant reads well. In every one of those, use the **enum**.

Related production variants: the <a href={`${BASE}lld/war/patterns-why/#15-copy-on-write-registry--two-maps-that-must-swap-together`}>copy-on-write registry</a> is a singleton whose *contents* must swap atomically (rebuild into new maps, swap references in one assignment). The inventory's <a href={`${BASE}lld/war/inventory/#2-a-lazily-built-strategy-map--data-race`}>lazily-built strategy map</a> is a non-volatile, unsynchronized lazy field: the same publication hazard as DCL without `volatile`, with the same best fix, *stop being lazy*: build it in the constructor and make it `final`. The <a href={`${BASE}lld/war/inventory/`}>War Room inventory</a> grades Singleton and Object Pool as framework-supplied for this reason.

<h2 id="twenty-connections">Chapter 7: Object Pool</h2>

### Concept

An **Object Pool** keeps a bounded set of expensive, reusable objects and lends them out. The caller borrows one, uses it, and returns it.

### Problem

A database connection is expensive to make: a network handshake, encryption, a login. Queries are mostly tiny ("is this slot free?"), so opening a fresh connection for each would cost more than the query. The database also allows only a hundred at a time, shared by everything. So the pool keeps twenty open and lends them out. The second half of the promise lives in the caller: a lab-results page threw an exception halfway through a query and never gave its connection back. After three of those, the page hangs forever.

**When an Object Pool is justified.** Three conditions, all at once: the object is **expensive to create** (connections, threads, large native buffers), it is **reusable** after a reset, and its number must be **bounded** (the database's connection limit, CPU cores). *Effective Java* (Item 6) is blunt about the rest: maintaining your own pool for lightweight objects is a bad idea, because modern garbage collectors make short-lived objects cheap and a pool adds contention and leaks. The database connection is Bloch's own example of an object that *does* justify one.

### Bad design

The caller is responsible for returning the connection, and an exception skips the return:

```java fragment
DbConnection c = pool.borrow(Duration.ofMillis(200));
String rows = c.query("SELECT * FROM lab_results WHERE patient = ?");   // throws halfway through...
pool.giveBack(c);                                                      // ...so this line never runs
```

Each exception leaks one connection. The checker borrows three without returning them: the fourth borrower times out, forever. That is the hang on the lab-results page.

### Better design

**A bounded pool on a `BlockingQueue`.** The queue does the hard concurrency: `poll` with a timeout blocks while every item is lent out and wakes when one comes back.

```java group=pool
class PoolExhaustedException extends RuntimeException {
    PoolExhaustedException(Duration waited) { super("nothing free after " + waited.toMillis() + " ms"); }
}

class BoundedPool<T> {
    private final BlockingQueue<T> idle;
    private final Set<T> lent = ConcurrentHashMap.newKeySet();

    BoundedPool(int size, Supplier<T> factory) {
        if (size <= 0) throw new IllegalArgumentException("size must be positive");
        this.idle = new ArrayBlockingQueue<>(size);
        for (int i = 0; i < size; i++) idle.add(factory.get());       // eager: pay the expensive part at startup
    }

    T borrow(Duration timeout) throws InterruptedException {
        T item = idle.poll(timeout.toNanos(), TimeUnit.NANOSECONDS);  // blocks while all are lent out
        if (item == null) throw new PoolExhaustedException(timeout); // bounded wait, loud failure
        lent.add(item);
        return item;
    }

    void giveBack(T item) {
        if (!lent.remove(item)) throw new IllegalArgumentException("not borrowed from this pool, or already returned");
        idle.add(item);                                               // can't overflow: only lent items come back
    }

    int idleCount() { return idle.size(); }
}

class DbConnection {                                  // stands in for a real JDBC connection
    final int id;
    DbConnection(int id) { this.id = id; }
    String query(String sql) { return "conn-" + id + ": " + sql; }
}
```

Design decisions to say out loud:

- **Bounded:** at most `size` objects ever exist, so the pool cannot become the thing that overwhelms the database.
- **A timeout, not a forever-wait:** when everything is lent out, a borrower waits a bounded time and then fails loudly with `PoolExhaustedException`, instead of hanging a request thread.
- **Returns are checked:** giving back something that is not currently lent (a double return, or an object from another pool) throws, instead of silently letting the pool hold more items than it lent. The `lent` set compares with `equals`; pooled objects like connections use identity equality, which is what you want.

The checker hammers it: a pool of 3 connections, 24 threads, 200 borrow-use-return cycles each, 4,800 loans. It tracks how many connections are in use at every moment (never more than 3), that no connection is ever lent to two threads at once, and that all 3 are idle at the end. With all 3 lent out, a fourth `borrow` with a 50 ms timeout throws `PoolExhaustedException`; a borrower blocked for up to 2 seconds wakes up and gets the connection the moment another thread returns one.

**Make the leak impossible to write by accident.** A `Lease` borrows in its constructor and gives back in `close()`, so `try`-with-resources returns the connection on every path, including exceptions. Closing twice is harmless. This is the "Your turn" below.

### How it works

1. The pool is filled eagerly at startup; every object sits in the `idle` queue.
2. `borrow` polls the queue (waiting up to the timeout), records the item in `lent`, and returns it.
3. `giveBack` removes the item from `lent` and puts it back in `idle`.
4. A `Lease` wraps the pair so `close()` always runs `giveBack`.

### When to use

- Expensive, reusable, limited resources: database connections, worker threads, large native buffers.

### Trade-offs

Cheap objects (`StringBuilder`s, DTOs, small arrays): allocation is cheaper than a pool's synchronization, and a stale pooled object is a bug factory. Anything your platform already pools: use an **`ExecutorService`** for threads and a production connection pool for connections (HikariCP is Spring Boot's default). They handle validation, idle eviction, leak detection and metrics you do not want to rewrite. In an interview, write the `BlockingQueue` version to show the mechanics, then say you would use the library.

**Your turn.** Make the leak impossible to write by accident: a `Lease` that borrows in its constructor and gives back in `close()`, so `try`-with-resources returns the connection on every path, including exceptions. Closing twice must be harmless. Do not edit `BoundedPool`.

<HintLadder hints={hints.lease} labels={turn}>

```java group=pool
class Lease<T> implements AutoCloseable {
    private final BoundedPool<T> pool;
    private final T item;
    private final AtomicBoolean returned = new AtomicBoolean(false);

    Lease(BoundedPool<T> pool, Duration timeout) throws InterruptedException {
        this.pool = pool;
        this.item = pool.borrow(timeout);
    }

    T get() {
        if (returned.get()) throw new IllegalStateException("lease already returned");
        return item;
    }

    @Override public void close() {
        if (returned.compareAndSet(false, true)) pool.giveBack(item);   // exactly once, however often close() is called
    }
}

String labResults(BoundedPool<DbConnection> pool, String patientId) throws InterruptedException {
    try (Lease<DbConnection> lease = new Lease<>(pool, Duration.ofMillis(200))) {
        return lease.get().query("SELECT * FROM lab_results WHERE patient = '" + patientId + "'");
    }                                                                     // returned here, on every path
}
```

The checker throws from inside the `try` a hundred times on a pool of 3 and every connection still comes back. (The string-built SQL is a stand-in; real code uses a `PreparedStatement` parameter. Never concatenate patient input into SQL.)

</HintLadder>

**A common slip:** *"A pool makes object creation faster."* It makes *expensive* creation rarer, at the price of contention, reset bugs and leaks. For ordinary objects it is slower and riskier than `new`. The justification is never "allocation is slow"; it is "this resource is expensive **and** limited".

### Interview summary

> "Connections are expensive and the database caps them, so I pool them: a bounded BlockingQueue, a borrow timeout that fails loudly, checked returns, and try-with-resources over a Lease so every loan comes back. In production I would use HikariCP rather than this."

<h2 id="who-calls-new">Chapter 8: Dependency injection and the composition root</h2>

### Concept

With **dependency injection**, each class *receives* its collaborators through its constructor instead of creating them. One place at the entry point of the application, the **composition root**, constructs the whole object graph once and decides every lifetime.

### Problem

Seven `new` calls remain, scattered across nine files: services that build their own collaborators. `AppointmentService` opens its own database pool. `DischargeService` opens another. Both read the clock straight from the wall and look up the SMS client through a static `getInstance()`. The result is the 6 p.m. incident again (two pools), code that cannot be tested without a real database, and times that cannot be controlled.

### Bad design

Every service decides its own collaborators, and their lifetimes, for itself:

```java fragment
class AppointmentService {
    private final Database db = new PooledDatabase(20);              // pool #1
    String book(String patientId, String doctorId) {
        LocalDateTime at = LocalDateTime.now();                      // the wall clock, welded in
        db.execute("INSERT ...");
        SmsClient.getInstance().send(patientId, "Booked for " + at); // a hidden singleton
        return patientId + "@" + at;
    }
}
class DischargeService {
    private final Database db = new PooledDatabase(20);              // pool #2: 40 connections, and the 6 p.m. incident again
}
```

**Detection cues:** `new` on anything long-lived or I/O-bound inside a class that makes business decisions; `getInstance()` and `now()` inside business logic; a constructor whose parameter list does not tell you what the class actually needs.

### Better design

Each class receives its collaborators through its constructor; `production()` is the composition root:

```java group=clinic
import java.time.*;

interface Database { void execute(String sql); }               // the port; in production it borrows from the pool
interface Notifier { void notify(String patientId, String text); }

class AppointmentService {
    private final Database db;
    private final Notifier notifier;
    private final Clock clock;

    AppointmentService(Database db, Notifier notifier, Clock clock) {      // constructor injection: final fields,
        this.db = Objects.requireNonNull(db, "db");                         // complete on construction,
        this.notifier = Objects.requireNonNull(notifier, "notifier");       // dependencies visible in one signature
        this.clock = Objects.requireNonNull(clock, "clock");
    }

    String book(String patientId, String doctorId) {
        LocalDateTime at = LocalDateTime.now(clock);
        db.execute("INSERT appointment " + patientId + " " + doctorId + " " + at);
        notifier.notify(patientId, "Booked with " + doctorId + " at " + at);
        return patientId + "@" + at;
    }
}

class DischargeService {
    private final Database db;
    DischargeService(Database db) { this.db = Objects.requireNonNull(db, "db"); }
    void discharge(String patientId) { db.execute("UPDATE admission SET discharged " + patientId); }
}

class RecordingDatabase implements Database {                  // stands in for the pooled JDBC database
    final List<String> statements = Collections.synchronizedList(new ArrayList<>());
    public void execute(String sql) { statements.add(sql); }
}

record MediCoreApp(Database db, AppointmentService appointments, DischargeService discharges) {}

MediCoreApp production() {                                     // the composition root: long-lived objects are built HERE
    Database db = new RecordingDatabase();                     // ONE instance: a singleton by scope, not by pattern
    Notifier sms = (patientId, text) -> { /* the SMS adapter, also built once, would go here */ };
    return new MediCoreApp(db,
        new AppointmentService(db, sms, Clock.systemDefaultZone()),
        new DischargeService(db));
}
```

Both services share the one database the root built (the checker books and discharges through `production()` and finds both statements in that single instance), and neither service can make another. "Exactly one" is now a fact about **one line in one method**, not about a class's static machinery.

**Ways to inject, ranked:**

| Style | How | Verdict |
|---|---|---|
| **Constructor injection** | collaborators are constructor parameters, stored in `final` fields | **Default.** Complete at construction, dependencies visible, trivially testable. |
| Setter injection | `setNotifier(...)` after construction | Only for genuinely optional dependencies; the object can exist half-wired. |
| Field injection | a container writes private fields (`@Autowired` on a field) | Hides dependencies, prevents `final`, needs the container even in unit tests. |
| Service locator | `Services.get(Notifier.class)` from inside the class | The Singleton problem with a map: dependencies hidden again. |

**Lifetimes are a wiring decision.** Once construction lives in one place, "how many" stops being a pattern and becomes a word: **singleton** (one per application; what Spring beans are by default), **prototype** or transient (a new instance per injection; Spring's name for it, borrowed loosely from the Prototype pattern), **scoped** (one per request or session). When a class needs *fresh objects repeatedly* (Chapter 1's lab forms), inject a **factory**: a `Supplier<LabOrder>` or the `LabOrders` registry itself. The creational patterns do not disappear under DI; they become the things the root wires together.

**DI is a `main()` method before it is a container.** Mark Seemann's name for the one place is the **composition root**: as close to the application's entry point as possible, the only place that knows the concrete classes. Spring or Guice automate that method; they do not change the design. In a 90-minute round, a hand-written root that wires six objects beats configuring a framework. It is also the answer to the <a href={`${BASE}lld/lessons/solid/`}>SOLID lesson</a>'s dependency-inversion chapter, from the creation side.

### When to use

Always for long-lived, I/O-bound, or nondeterministic collaborators: databases, clients, clocks, random sources, queues.

### Trade-offs

Values and pure helpers (a `Money`, a `StringBuilder`, an `ArrayList`, `Duration.between`) are created with `new` right where they are used; injecting them is ceremony. Do not put an interface over a stable class just "for DI" if nothing ever stands in for it. And do not reach for a container in an interview; the root is a method.

<h2 id="compare-patterns">Chapter 9: The five patterns side by side</h2>

### Concept

Factory Method, Abstract Factory, Builder, Prototype and Singleton are the five Gang of Four creational patterns. Each answers a different question. Most interview confusion comes from comparing their *shape* (they all "create objects") instead of their *question*.

### Problem

Asked "what is the difference between Factory Method and Abstract Factory?" a rusty answer lists vocabulary. A strong answer states the situation each one is for, what it costs, and what you would use instead.

### The comparison

| | Factory Method | Abstract Factory | Builder | Prototype | Singleton |
|---|---|---|---|---|---|
| **Question it answers** | which class does this one step create? | which family of objects goes together? | how do I assemble one complex object validly? | how do I start from a configured exemplar? | how many instances exist, and who can reach them? |
| **Structure** | creator with an abstract creation step, subclasses or a supplier fill it | factory interface with a method per product, one implementation per variant | mutable builder plus an immutable product with a private constructor | copy constructor (or `clone`) on the exemplar | private constructor plus a controlled access point |
| **Inheritance or composition** | inheritance (subclass) or composition (injected `Supplier`) | composition: the consumer holds a factory object | composition: a separate builder object | neither: the object copies itself | neither: static access |
| **Who decides** | a subclass, or the supplier you pass in | the wiring picks one factory | the caller, step by step | the caller picks the exemplar | the class itself, or the container |
| **Example in this lesson** | `UtilisationReport.createExporter()` | `GatewaySuite` (sandbox, live) | `Booking.builder()...build()` | `new InvoiceTemplate(template)` | `MetricsRegistry.INSTANCE` |
| **Seen in the JDK** | `Collection.iterator()` | rare; mostly frameworks | `HttpRequest.newBuilder()`, `Stream.builder()` | `ArrayList(Collection)` copy constructor, array `clone()` | `Runtime.getRuntime()` |
| **Main cost** | a subclass per variant, unless you pass a supplier | adding a product edits every factory | a second class to write and keep in sync with the product | shared mutable state if the copy is shallow | hidden global dependency, hard to test |
| **Do not use when** | one product, no algorithm around it | no rule spans the products | few fields, all required (use a record) | the object is immutable (share it) | a container or `main()` can own the instance |

### Factory Method vs Abstract Factory vs Builder, with one example each

| Requirement | Pattern | Why this one |
|---|---|---|
| "Daily report is the same loop; only the output format object differs." | Factory Method | One varying creation inside a fixed algorithm. |
| "Gateway, refund client and verifier must always be live together or sandbox together." | Abstract Factory | A cross-product invariant; the family is the unit. |
| "A booking has eight fields, half optional, and teleconsult excludes a room." | Builder | Many parts plus a rule between them, checked in `build()`. |
| "Every invoice starts from the clinic's standard template." | Prototype | Copy a configured exemplar; copy mutable parts, share immutable ones. |
| "Exactly one metrics registry." | Singleton scope | Better: build once in `main()` and inject. |

The same three questions sort most real cases:

1. **Is one object chosen inside an algorithm?** Factory Method.
2. **Must several objects match each other?** Abstract Factory.
3. **Is one object assembled from many parts under rules?** Builder.

**Two pairs that are confused often:**

| | Builder | Prototype |
|---|---|---|
| Starting point | an empty staging object | a fully configured exemplar |
| Strength | validates rules across fields | skips repeating expensive setup |
| Danger | forgetting defensive copies | shallow copies that share mutable state |
| They combine | `toBuilder()` copies an object into a builder | a prototype can hand out builders |

| | Factory Method | Simple factory | Static factory method |
|---|---|---|---|
| Is a GoF pattern | yes | no | no |
| Decided by | a subclass or supplier inside an algorithm | a `switch` on data | the product class itself |

<h2 id="which-pattern">Chapter 10: Choosing under a clock</h2>

### Concept

In a machine-coding round you are graded on the reason you give for a pattern, at the moment a requirement forces it. This chapter is a lookup table and a timeline.

### Problem

Given "Clinic appointment system. Patients, doctors, slots; pay by UPI, card or wallet; send reminders. Ninety minutes. The code must run.", at minute twelve the interviewer asks: "Which design patterns will you use?" Listing seven loses points.

### Better design

The honest answer is *"the ones the requirements force, and I will tell you when each one arrives."* Here is how to tell, quickly:

| You hear / you see | Pattern | The one-line reason | Do not, when... |
|---|---|---|---|
| A `switch` on a type picks a class, at one place | **Simple factory** | One place decides; the compiler checks the cases | one implementation; `new` in `main()` is enough |
| The same choice at several call sites, implementations growing | **Registry of instances** (`Map<K, T>`, key from the object) | The chooser never reopens | two fixed variants |
| Each use needs its own object (state per patient, per payment) | **Registry of suppliers** (`Map<K, Supplier<T>>`) | Fresh object per call, chosen by key | objects are stateless: share them |
| A fixed algorithm, one created object differs | **Factory Method** (or an injected `Supplier`) | The algorithm exists once | the creator has no algorithm of its own |
| "These N must always match" across variants | **Abstract Factory** | The family is the unit; mixing has no code path | no cross-product invariant; one product |
| Many optional fields, rules between them | **Builder** | `build()` is the invariant gate; product immutable | few fields, all required: use a record |
| Start from a configured exemplar | **Prototype** (copy constructor) | Copy is cheaper or simpler than rebuilding | object is immutable: share it instead |
| "Exactly one, shared everywhere" | **Singleton as a DI scope**; hand-rolled: enum | One instance without a global access point | "we only need one today" |
| Expensive, reusable, limited resource | **Object Pool** (bounded, timed, leases) | Bound the resource, reuse the expensive part | cheap objects; the platform already pools |
| `new`, `now()`, `getInstance()` inside business logic | **Dependency injection and a composition root** | Every lifetime decided in one place | values and pure helpers |

<h2 id="sq-card-retries">Side quest 1: Card retries</h2>

**Requirement:** *"Card payments: the bank allows three attempts per payment, then declines. We added an attempt counter to the card processor."*

**Where it lands:** Chapter 1's choice between a registry of **instances** and a registry of **suppliers**. The new `RetryingCardProcessor` holds state that belongs to *one payment*. Register a single shared instance, and its counter counts *every patient's* attempts: the fourth card payment of the morning is declined though it is that patient's first try.

<Reveal q="Before the code: with the instance registry, which payment is the first to be declined, and why?">

The fourth card payment of the day, whoever makes it. The shared processor's `attempts` field reaches 4 on the fourth call to `process`, regardless of which patient made the first three. The counter's lifetime is the application's; its meaning is one payment's. The fix is to make the lifetimes match (a fresh processor per payment) or to move the counter out of the processor into a per-payment object.

</Reveal>

<HintLadder hints={hints.cardRetries} labels={turn}>

```java group=registry
class RetryingCardProcessor implements PaymentProcessor {     // holds per-payment state: one instance per payment
    private int attempts = 0;
    public PaymentMode mode() { return PaymentMode.CARD; }
    public PaymentResult process(PaymentRequest r) {
        attempts++;
        if (attempts > 3) return new PaymentResult(false, "card-declined-after-3-attempts");
        return PaymentResult.success("card-" + r.amount().paise() + "-attempt-" + attempts);
    }
}

ProcessorSuppliers retryingWiring() {                         // one wiring change: a supplier, not an instance
    return new ProcessorSuppliers(Map.of(
        PaymentMode.UPI,    UpiProcessor::new,
        PaymentMode.CARD,   RetryingCardProcessor::new,
        PaymentMode.WALLET, WalletProcessor::new));
}
```

With the supplier wiring, a hundred patients each pay 10 rupees by card and each gets `card-1000-attempt-1`. The checker wires the same class into the *instance* registry for contrast: payments one to three succeed, and the fourth patient gets `card-declined-after-3-attempts`. Retrying one payment through the *same* fresh processor still stops after three, as the bank requires.

</HintLadder>

**Transfer test:** the attempt count must survive a server restart. Does it still belong in the processor at all, or in a `PaymentAttempt` record that the processor reads and returns?

<h2 id="sq-staging">Side quest 2: A staging environment</h2>

**Requirement:** *"Before go-live, the hospital's auditors want a staging environment: payments through the gateway's sandbox endpoint, but webhook signatures checked with the real algorithm and a staging secret."*

**Where it lands:** Chapter 3's abstract factory. A **new family** is one new class. Notice that this family *reuses product classes from both of the others*. That is allowed: the guarantee was never "sandbox classes stay with sandbox classes"; it is that **the combination is decided once, in one reviewed class**, and billing can only take a whole suite.

<Reveal q="And if the auditors also want a fourth product, a PayoutClient for refunds to doctors, in every environment?">

That is the expensive axis. `GatewaySuite` gains `payouts()`, and **every** suite (sandbox, live, staging, the test `RecordingSuite`) must implement it before anything compiles. Abstract Factory makes new families cheap and new products costly. If products are what keep growing, consider splitting the suite, or giving the interface a default method only where a safe default truly exists (a payout default that silently does nothing would be a fail-open bug).

</Reveal>

<HintLadder hints={hints.staging} labels={turn}>

```java group=suites
record StagingConfig(String sandboxUrl, String stagingSecret) {}

class StagingSuite implements GatewaySuite {
    private final StagingConfig cfg;
    StagingSuite(StagingConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new SandboxGateway(cfg.sandboxUrl()); }        // no real money
    public RefundClient refunds()     { return new SandboxRefundClient(cfg.sandboxUrl()); }
    public WebhookVerifier verifier() { return new PennyPayVerifier(cfg.stagingSecret()); }   // the real algorithm

```

`new BillingService(new StagingSuite(...))` charges through the sandbox and accepts only webhooks signed with the staging secret; one signed with the public sandbox test secret is rejected. No existing class was edited.

</HintLadder>

**Transfer test:** the product expands to a second country, with its own gateway, SMS provider and tax format. Is "country" a new family of the same suite, or a second, independent abstract factory? What goes wrong if you multiply environments by countries into one interface?

<h2 id="sq-discounts">Side quest 3: Per-line discounts</h2>

**Requirement:** *"Billing staff need to apply a discount to individual invoice lines, say 10% off the X-ray for a staff member's family."*

**Where it lands:** Chapter 5's prototype, and the depth of the copy. To support a discount, `LineItem` stops being an immutable record and gains a mutable `discountPercent`. The old copy constructor's `new ArrayList<>(other.items)` now produces a fresh list **of the same, shared, mutable line objects**. Discount the X-ray on one patient's invoice and it is discounted on the template, and on every invoice copied since.

<Reveal q="Which single line of the old copy constructor became wrong, without anyone editing it?">

`this.items = new ArrayList<>(other.items);` It was correct when `LineItem` was immutable (sharing immutable elements is fine) and became a shallow copy the moment `LineItem` gained a setter. **Deep-copy correctness depends on the mutability of everything you share**, so changing a type from immutable to mutable can silently break copy code in another class. That is one more reason to keep value types immutable.

</Reveal>

<HintLadder hints={hints.discounts} labels={turn}>

```java group=discounts
class LineItem {                                     // now MUTABLE: a discount can be set per line
    private final String code;
    private final long paise;
    private int discountPercent;

    LineItem(String code, long paise) {
        this.code = code;
        this.paise = paise;
    }
    LineItem(LineItem other) {                       // the element gets a copy constructor too
        this(other.code, other.paise);
        this.discountPercent = other.discountPercent;
    }

    void discount(int percent) {
        if (percent < 0 || percent > 100) throw new IllegalArgumentException("discount must be 0..100");
        this.discountPercent = percent;
    }
    int discountPercent() { return discountPercent; }
    long netPaise()       { return paise * (100 - discountPercent) / 100; }
}

class InvoiceTemplate {
    private final String header;
    private final List<LineItem> items = new ArrayList<>();

    InvoiceTemplate(String header, List<LineItem> items) {
        this.header = header;
        for (LineItem item : items) this.items.add(new LineItem(item));
    }
    InvoiceTemplate(InvoiceTemplate other) {
        this.header = other.header;
        for (LineItem item : other.items) this.items.add(new LineItem(item));   // copy the list AND every mutable element
    }

    LineItem item(int index) { return items.get(index); }
    long totalPaise() {
        long sum = 0;
        for (LineItem item : items) sum += item.netPaise();
        return sum;
    }
}
```

An invoice copied from a template with a 200-rupee registration line and an 850-rupee X-ray (20,000 + 85,000 paise) gets 10% off the X-ray: its total is 20,000 + 76,500 = 96,500 paise, and the template still totals 105,000. The checker also copies just the *list* of these mutable lines, discounts through the copy, and shows the original line changing: the bug, reproduced.

</HintLadder>

**Transfer test:** a third option avoids per-element copying entirely: keep `LineItem` immutable and make `discount` *return a new* `LineItem`. What does the template's copy constructor look like then, and which side of "share immutable, copy mutable" does it land on?

<h2 id="sq-stale">Side quest 4: Stale connections</h2>

**Requirement:** *"Every night at 2 a.m. the database restarts for backups. At 8 a.m., the first queries of the day fail on dead connections."*

**Where it lands:** Chapter 7's pool, which currently trusts every idle connection forever. A production pool **validates on borrow** (or in the background) and replaces what is broken, while keeping the bound and never losing a slot.

<Reveal q="If reconnecting fails during borrow (the database is still down), what must the pool NOT do?">

It must not **lose the slot**. If the stale connection is simply dropped and the replacement throws, the pool now owns one fewer object than its size, and after enough failures it owns none: a permanent outage from a temporary one. Put the stale object back (the next borrower will try again) and let the exception reach the caller.

</Reveal>

<HintLadder hints={hints.stale} labels={turn}>

```java group=healthyPool
class PoolExhaustedException extends RuntimeException {
    PoolExhaustedException(Duration waited) { super("nothing free after " + waited.toMillis() + " ms"); }
}

class ValidatingPool<T> {
    private final BlockingQueue<T> idle;
    private final Set<T> lent = ConcurrentHashMap.newKeySet();
    private final Supplier<T> factory;
    private final Predicate<T> healthy;
    final AtomicInteger replaced = new AtomicInteger();

    ValidatingPool(int size, Supplier<T> factory, Predicate<T> healthy) {
        if (size <= 0) throw new IllegalArgumentException("size must be positive");
        this.idle = new ArrayBlockingQueue<>(size);
        this.factory = factory;
        this.healthy = healthy;
        for (int i = 0; i < size; i++) idle.add(factory.get());
    }

    T borrow(Duration timeout) throws InterruptedException {
        T item = idle.poll(timeout.toNanos(), TimeUnit.NANOSECONDS);
        if (item == null) throw new PoolExhaustedException(timeout);
        if (!healthy.test(item)) {                       // stale: replace it, keeping the pool at full size
            T fresh;
            try {
                fresh = factory.get();
            } catch (RuntimeException e) {
                idle.add(item);                          // keep the slot; the next borrower retries
                throw e;
            }
            replaced.incrementAndGet();
            item = fresh;
        }
        lent.add(item);
        return item;
    }

    void giveBack(T item) {
        if (!lent.remove(item)) throw new IllegalArgumentException("not borrowed from this pool, or already returned");
        idle.add(item);
    }

    int idleCount() { return idle.size(); }
}
```

The checker marks two of three connections dead overnight: the next borrows replace them, `replaced` reads 2, and the pool still holds exactly 3. With the factory failing (database still down), the borrow throws, and the pool *still* has all 3 slots. Under 16 threads with random breakage, at most 3 connections are ever in use and every loan comes back. A production pool would also close the stale connection it discards; HikariCP additionally retires connections by age and tests idle ones in the background.

</HintLadder>

**Transfer test:** validating on every borrow costs a round trip per query. What would you trade it for (validating only connections idle longer than 30 seconds, or a background thread), and what failure does each allow?

<h2 id="interview-script">Say it in the room</h2>

**The 90-second answer** (adapt the nouns):

> "Everything long-lived is built once, in `main()`, and passed in through constructors: the repositories, the payment registry, the notifier, the clock. That is why there are no Singleton classes: 'exactly one database pool' is one line in the composition root, and my tests have their own root with a fixed clock and fakes. Payment mode varies per transaction, so processors sit behind a registry: each processor declares its mode, the registry is built from a list in the constructor, fails at startup on duplicates, and throws a named exception for an unknown mode. That is how EMI lands as one class. Booking has a rule between fields (teleconsult means no room), so it has a hand-rolled builder: required fields and the cross-field rule checked in `build()`, a private constructor, final fields, and a defensive copy of the symptoms list, so any Booking that exists is valid. Where a fixed algorithm creates one varying object, like the report exporter, I pass a `Supplier` instead of subclassing. And where I did not need a pattern (Slot, Money) they are records."

**Five follow-ups you will get:**

<Reveal q="1. Write me a thread-safe Singleton. Now tell me which form you would actually use.">

Write DCL with `volatile` and both checks, and narrate: check 1 for the fast path, check 2 under the lock because two threads can pass check 1, `volatile` for safe publication of a fully constructed object, private constructor or it is not a singleton. Then: *"In practice I would use an enum: the JVM's class initialization does the locking, and it is safe against reflection and serialization. Or the holder idiom if it must be lazy and a class. In application code I would rather not have a Singleton class at all: I would create one instance in the composition root, or let the DI container's singleton scope do it, and inject it."*

</Reveal>

<Reveal q="2. What is the difference between Factory Method and a simple factory?">

A simple factory is one method with a `switch` on runtime data that returns the interface; it is not a GoF pattern. Factory Method is GoF's: a creator class has an algorithm that calls an abstract creation method, and subclasses decide which class to instantiate, a Template Method whose varying step is a creation, like `Collection.iterator()`. And static factory methods like `List.of` are a third thing; *Effective Java* says outright that they are not the Factory Method pattern.

</Reveal>

<Reveal q="3. Your builder validates in build(). Why not validate in each setter?">

Single-value rules *do* go in setters (or in the value's own type), so they fail at the bad call. But required-presence and cross-field rules cannot be checked in a setter: when `room("R-3")` is called, `teleconsult(true)` may not have been called yet, because setter order is the caller's choice. `build()` is the first moment the whole object is visible, so it is the only place those rules can live. For required fields there is a stronger option: put them in the builder's own signature and make omission a compile error.

</Reveal>

<Reveal q="4. How would you implement a connection pool?">

A bounded `BlockingQueue` filled eagerly by a factory; `borrow` polls with a timeout and throws a named exception when exhausted; `giveBack` checks the object was actually lent (no double returns); a `Lease` implementing `AutoCloseable` so try-with-resources returns the connection on every path. Then the production concerns: validate on borrow and replace broken connections without losing the slot, evict idle ones, cap age, detect leaks. And then: *"In a real system, HikariCP. I would only write this to show the mechanics."*

</Reveal>

<Reveal q="5. Deep copy or shallow copy for your invoice template?">

Neither label is precise enough; the rule is **share immutable, copy mutable**. The header string and the immutable line-item records are shared; the list and the tax-field map are fresh, so editing a patient's invoice never touches the template. If line items became mutable (a per-line discount), each element would need copying too. I would use a copy constructor, not `Cloneable`: `clone()` is shallow, skips constructors, and fights final fields.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Pattern | Do... | The promise to keep |
|---|---|---|---|
| `if`/`switch` picking a class, copied across call sites | Simple factory | One method returning the interface; exhaustive `switch`, no `default` | One place decides |
| Implementations growing, maybe across modules | Registry of instances | `Map<K, T>` built in the constructor from a list, key from `mode()` | Fails at startup on duplicates; named exception on a miss |
| Per-use state in the created object | Registry of suppliers | `Map<K, Supplier<T>>`; verify keys at startup | A fresh object every call |
| Same algorithm, one created object differs | Factory Method | Abstract creation step in a `final` algorithm, or inject a `Supplier` | The algorithm exists once |
| "These N must always match" | Abstract Factory | One suite per variant; consumers take the suite | No parameter list can mix families |
| Many optional fields, cross-field rules | Builder | Private product constructor, final fields, `List.copyOf`, rules in `build()` | Constructed implies valid |
| Required fields easy to forget | Builder with required args | `builder(patientId, doctorId)` | Omission is a compile error |
| "Copy this configured template" | Prototype | Copy constructor; fresh mutable containers and elements | No mutable state shared |
| "Exactly one" | Singleton as a scope | Build once in the root (or container scope); hand-rolled: enum, then holder, then DCL plus `volatile` | One instance, no hidden access |
| Expensive, reusable, limited | Object Pool | Bounded `BlockingQueue`, borrow timeout, checked returns, `Lease` | Every loan comes back |
| `new` / `now()` / `getInstance()` in business logic | Dependency injection | Constructor injection, one composition root, a second root for tests | Dependencies visible in one signature |

The chapters at a glance:

## Five mistakes to leave behind

1. **Patterns before problems.** A factory for one class, a builder for two fields, a Singleton for something `main()` could build once. Name each pattern when its forcing requirement arrives.
2. **The catch-all `else`.** A ladder or `default` that swallows new variants turns a compile error into a wrong answer. Use exhaustive switches, or registries with a named miss policy.
3. **"Final means immutable."** A final field holding a mutable list is a window into your object. Copy defensively in, and expose unmodifiable views or copies out.
4. **DCL without `volatile`**, and the Singleton class itself. Prefer the enum or holder; in application code prefer one injected instance.
5. **A pool without a guaranteed return.** Borrow in a `Lease`, give back in `close()`, bound every wait. And do not pool what is cheap.

**Revision drill.** Take any 30-minute LLD core you have built (vending machine, parking lot, library), list every `new` outside `main()`, and for each say aloud which pattern, or no pattern, it should become. Then write the thread-safe Singleton from memory in under three minutes, narrating the `volatile`, and the `BlockingQueue` pool in under ten.

**Look these up yourself**

- **Staged (step) builders** — builders whose types force required fields in order, turning every "required" check into a compile error, at the cost of one interface per step.
- **`toBuilder()` / "withers"** — copying an immutable object with one field changed; how records and builders make Prototype unnecessary.
- **Safe publication idioms** — final fields, `volatile`, static initializers, concurrent collections: the four ways an object can be shared without a data race (JCIP §3.5).
