<h2 id="prologue">Prologue · Fourteen circles</h2>

<Scene chapter="Prologue" title="Fourteen circles" mood="dawn">

For the first time in months, Tuesday's change request isn't from Bram.

It's a forty-page spec from MediCore, a chain of eleven clinics: billing counters, appointments, lab orders, invoices, and a database that, the spec admits in a footnote, "struggles a little around 6 p.m." The Gearhouse has built ticket machines and vending machines. This is its first client whose machines are people.

Wren reads the spec in one sitting. Then she prints the prototype code the clinic's last vendor left behind, and goes through it with her green pen. When she hands it back, there is only one kind of mark on it: a circle, around the word `new`.

*"Every one of those is a decision,"* she says. *"Which class. How many. Assembled how. And who is allowed to know."*

You count the circles. Fourteen.

*"Find out which of them are in the wrong place."*

</Scene>

`new` is the most innocent word in Java and the most committed one. `new UpiProcessor()` hard-codes **a concrete class, a construction recipe, and a lifetime** into the line that says it. When the line is in `main()`, that's fine — somebody has to decide. When it is inside the billing counter, the patient portal and the refund desk at once, every one of those classes now has to change when the decision does.

**Creational patterns answer one question: when should the code that *uses* an object not be the code that *decides* how it is made?** Each pattern moves one kind of decision somewhere better:

| The decision | Move it out when… | Pattern | Chapter |
|---|---|---|---|
| **Which class?** | the choice depends on runtime data and is repeated at several call sites | Simple factory → registry of instances or of suppliers | 1 |
| **Which class, inside a fixed algorithm?** | the algorithm is the same and only the object it creates differs | Factory Method | 2 |
| **Which family?** | several objects must always come from the same variant | Abstract Factory | 3 |
| **Assembled how?** | many optional parts, and rules *between* the parts | Builder | 4 |
| **From what?** | the cheapest correct start is a copy of a configured exemplar | Prototype | 5 |
| **How many?** | exactly one must exist, or a bounded few must be reused | Singleton (as a scope), Object Pool | 6, 7 |
| **Decided by whom?** | those decisions are scattered across the codebase | Dependency injection, composition root | 8 |

This lesson is the first of three set at MediCore. This one *creates* MediCore's objects; the <a href={`${BASE}lld/lessons/structural-patterns/`}>structural patterns lesson</a> *connects* MediCore to the outside world; the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> *runs* the clinic day to day. Every pattern arrives when the story forces it — never before. The War Room mirrors the real thing: its <a href={`${BASE}lld/war/patterns-why/`}>dossiers</a> come from an actual production hospital platform, so most patterns here have a "this actually happened" link.

One warning before we start, because creational patterns are the **most over-applied patterns in machine-coding rounds**: a `ParkingLotFactory` for an object constructed once, a Singleton for something that only needed to be passed in, a builder for a record with two fields. Graders mark ceremony down as surely as a God class. Every chapter below ends with *when not to use it*. Those sections are half the lesson.

<h2 id="three-ladders">Chapter 1 · Three ladders</h2>

<Scene chapter="Chapter 1" title="Three ladders">

MediCore's billing counter takes UPI, card and wallet. On Friday, finance adds EMI — monthly instalments for expensive scans — and someone adds `EMI` to the payment-mode enum. Everything compiles.

On Monday, Oona's sticky note: *"Patient in Riverside clinic, ₹5,000 knee MRI, chose EMI. The system sent it to the wallet processor. The wallet said no. The patient said a lot more."*

You find the code. The counter decides which processor to build with an `if` ladder whose last branch is a plain `else`: everything that isn't UPI or card is a wallet. The patient portal has the same ladder. So does the refund desk. Nobody remembered all three.

Wren doesn't look at the ladder. She counts the files that contain it.

*"Three places decide which class to build,"* she says. *"How many should?"*

</Scene>

**The mess.** The choice of concrete class, made at every call site, with a catch-all `else`:

```java id=ladderMess
enum PaymentMode { UPI, CARD, WALLET, EMI }           // EMI was added on Friday

interface PaymentProcessor { String process(long paise); }
class UpiProcessor implements PaymentProcessor { public String process(long paise) { return "upi-" + paise; } }
class CardProcessor implements PaymentProcessor { public String process(long paise) { return "card-" + paise; } }
class WalletProcessor implements PaymentProcessor { public String process(long paise) { return "wallet-" + paise; } }

class CounterDesk {                                  // PortalCheckout and RefundDesk carry the same ladder, copied
    String charge(PaymentMode mode, long paise) {
        PaymentProcessor p;
        if (mode == PaymentMode.UPI) p = new UpiProcessor();
        else if (mode == PaymentMode.CARD) p = new CardProcessor();
        else p = new WalletProcessor();              // "everything else is a wallet" — true until Friday
        return p.process(paise);
    }
}
```

The checker runs it: `charge(EMI, 500000)` returns `wallet-500000`. No exception, no warning — the new mode silently lands in the wrong branch.

**The detection cues.**

1. **`new` on a concrete class, chosen by an `if` or `switch` on a type code.** The caller knows every implementation by name.
2. **The same ladder in several places.** Each new variant is a scavenger hunt; the one you miss is the bug.
3. **A catch-all `else` or `default`.** It turns "I forgot this case" from a compile error into a wrong answer.

**Refactor 1 — the simple factory.** Move the decision to one place that returns the *interface*:

  <Mermaid code={`flowchart LR
    C[Counter] --> F{{ProcessorFactory}}
    P[Portal] --> F
    R[Refunds] --> F
    F -->|returns interface| I[PaymentProcessor]

```java group=billing
enum PaymentMode { UPI, CARD, WALLET }

record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("money cannot be negative");
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }   // a static factory method
}

record PaymentRequest(PaymentMode mode, Money amount) {}

record PaymentResult(boolean ok, String reference) {
    static PaymentResult success(String reference) { return new PaymentResult(true, reference); }
}

interface PaymentProcessor { PaymentResult process(PaymentRequest r); }

class UpiProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("upi-" + r.amount().paise());
    }
}
class CardProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("card-" + r.amount().paise());
    }
}
class WalletProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("wallet-" + r.amount().paise());
    }
}

class ProcessorFactory {
    PaymentProcessor forMode(PaymentMode mode) {
        return switch (mode) {
            case UPI    -> new UpiProcessor();
            case CARD   -> new CardProcessor();
            case WALLET -> new WalletProcessor();
        };  // exhaustive switch over an enum, no default: add a mode and this stops compiling. That's a feature.
    }
}

// The counter, the portal, and refunds all just say:
PaymentResult charge(ProcessorFactory factory, PaymentRequest request) {
    PaymentProcessor p = factory.forMode(request.mode());
    return p.process(request);
}
```

A ₹10 UPI payment — `charge(factory, new PaymentRequest(UPI, Money.rupees(10)))` — returns reference `upi-1000`: money travels as paise in a `long`, never as a `double`. Add `EMI` to this enum and the switch **refuses to compile** until someone decides what EMI means. The ladder's catch-all `else` became a compiler error, which is exactly where you want "I forgot a case" to surface.

A naming note you'll need in the room: this is usually called a **simple factory**. It is not one of the 23 Gang of Four patterns; their **Factory Method** is the next chapter, and the difference is a favourite follow-up.

**"Isn't that switch an OCP violation?"** — the follow-up you should invite. Technically yes; honestly graded, no: the variation is *contained in one class whose single job is choosing*, and an exhaustive enum switch even gets compiler help. The upgrade, when the switch outgrows a screen or implementations live in different modules, is the **registry** — implementations announce their own key, the switch disappears. Because the interface gains a method, this is a genuine edit, so it starts a fresh design:

```java group=registry
// Unchanged from the simple factory, repeated so this design compiles on its own.
enum PaymentMode { UPI, CARD, WALLET }
record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("money cannot be negative");
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }
}
record PaymentRequest(PaymentMode mode, Money amount) {}
record PaymentResult(boolean ok, String reference) {
    static PaymentResult success(String reference) { return new PaymentResult(true, reference); }
}
```

```java group=registry
interface PaymentProcessor {
    PaymentMode mode();                              // each impl declares its OWN key
    PaymentResult process(PaymentRequest r);
}

class UpiProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.UPI; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("upi-" + r.amount().paise()); }
}
class CardProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.CARD; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("card-" + r.amount().paise()); }
}
class WalletProcessor implements PaymentProcessor {
    public PaymentMode mode() { return PaymentMode.WALLET; }
    public PaymentResult process(PaymentRequest r) { return PaymentResult.success("wallet-" + r.amount().paise()); }
}

class UnsupportedModeException extends RuntimeException {
    UnsupportedModeException(PaymentMode mode) { super("no processor for " + mode); }
}

class ProcessorRegistry {
    private final Map<PaymentMode, PaymentProcessor> byMode;

    ProcessorRegistry(List<PaymentProcessor> processors) {
        this.byMode = processors.stream()
            .collect(Collectors.toUnmodifiableMap(PaymentProcessor::mode, p -> p));
        // toUnmodifiableMap throws on duplicate keys — two impls claiming UPI fails at STARTUP, not mid-payment
    }

    PaymentProcessor forMode(PaymentMode mode) {
        PaymentProcessor p = byMode.get(mode);
        if (p == null) throw new UnsupportedModeException(mode);  // the map is not exhaustive — name the miss policy
        return p;
    }
}

// Wiring — the ONLY place that lists implementations (Spring injects this list automatically):
ProcessorRegistry wiring() {
    return new ProcessorRegistry(List.of(
        new UpiProcessor(), new CardProcessor(), new WalletProcessor()));
}
```

The knowledge "UPI → UpiProcessor" moved *into UpiProcessor itself*. New mode = new class + one wiring entry, zero edits to the registry. You traded compile-time exhaustiveness for runtime flexibility — say that trade out loud. The checker confirms both halves of the startup guarantee: two processors claiming `UPI` make the constructor throw `IllegalStateException`, and a mode nobody wired throws `UnsupportedModeException` naming the mode. Production's version: <a href={`${BASE}lld/war/patterns-why/#2-registry--the-inbound-webhook-routing-problem`}>the Registry dossier</a>, webhook handlers announcing their provider key — built once in the constructor, immutable, failing at boot rather than at 2 a.m.

**Refactor 3 — a registry of suppliers.** The registry above hands every caller *the same instance*. That is right for stateless processors and wrong the moment an object holds state that belongs to one use — a checklist for one patient, a retry counter for one payment. Then the registry stores **how to make one**, a `Supplier<T>`, instead of the thing itself:

```java group=registry
class ProcessorSuppliers {
    private final Map<PaymentMode, Supplier<PaymentProcessor>> makers;

    ProcessorSuppliers(Map<PaymentMode, Supplier<PaymentProcessor>> makers) {
        makers.forEach((mode, maker) -> {            // the key is written BESIDE the supplier, so check it at startup
            PaymentMode made = maker.get().mode();
            if (made != mode) throw new IllegalArgumentException(mode + " is wired to a " + made + " processor");
        });
        this.makers = Map.copyOf(makers);
    }

    PaymentProcessor fresh(PaymentMode mode) {
        Supplier<PaymentProcessor> maker = makers.get(mode);
        if (maker == null) throw new UnsupportedModeException(mode);
        return maker.get();                          // a new object on every call
    }
}

ProcessorSuppliers supplierWiring() {
    return new ProcessorSuppliers(Map.of(
        PaymentMode.UPI,    UpiProcessor::new,
        PaymentMode.CARD,   CardProcessor::new,
        PaymentMode.WALLET, WalletProcessor::new));
}
```

`UpiProcessor::new` is a factory you can store in a map: a constructor reference is a `Supplier`. One cost to say out loud: in the instance registry the key comes *from* the object (`mode()`), so it can't drift; here it sits *beside* the supplier, so a typo — `CARD, WalletProcessor::new` — would route card payments to the wallet. The constructor builds one throwaway instance per key at startup and refuses a mismatch. The checker wires exactly that typo and watches it fail at construction.

| | Simple factory (`switch`) | Registry of instances | Registry of suppliers |
|---|---|---|---|
| Who knows the mapping | the factory | each implementation (`mode()`) | the wiring |
| New variant costs | a `case` + a class (compiler finds the switch) | a class + one wiring entry | a class + one wiring entry |
| Forgetting it fails | at compile time | at the first lookup | at the first lookup |
| Objects returned | new each call | one shared instance per key | new each call |
| Right when | a handful of variants, one module | stateless handlers that grow, maybe across modules | each use needs its own state |

**Static factory methods** (the small sibling, worth dropping in passing): `Money.rupees(10)`, `PaymentResult.success(ref)`, `Duration.ofMinutes(5)`, `List.of(...)` — named constructors that validate, cache, or return subtypes. *Effective Java* Item 1; free polish. `Money.rupees` also uses `Math.multiplyExact`, so an absurd amount throws instead of silently overflowing.

<Reveal q="EMI arrives again. What exactly changes in the ladder, the switch factory, and the registry?">

**The ladder:** a new enum constant, then three edits in three files — and if you miss one, EMI silently becomes a wallet payment (the bug that started this chapter). **The switch factory:** a constant, an `EmiProcessor`, and one `case` — the compiler points at the switch, so you can't miss it. **The registry:** a constant, an `EmiProcessor` that returns `EMI` from `mode()`, and one entry in the wiring list; no lookup code is touched. Forget the wiring entry and the first EMI payment throws `UnsupportedModeException` — loud, named, but at runtime. That is the trade: compile-time exhaustiveness versus not editing the chooser.

</Reveal>

**When not to use it.** A class constructed in exactly one place, with one implementation, needs no factory: `new` in `main()` *is* the factory. Don't build a registry for two variants that will never grow — the switch is shorter and the compiler checks it. And never discover implementations by **reflection or classpath scanning** in a 90-minute round; an explicit list in the wiring is readable, debuggable and fast.

**Your turn.** MediCore's lab desk prints a fresh order form for each test: blood panel, X-ray, MRI. Each form carries a **checklist the technician ticks off for that patient** — "fasting confirmed", "metal removed". Today one shared form object per test type is handed out, and Oona has just watched a tick for one patient appear on the next patient's MRI form. Write `LabOrders`: fresh forms per call, a loud failure for an unknown test, and a startup check that every test is wired to the right form.

<HintLadder hints={hints.labOrders} labels={turn}>

```java group=labs
enum LabTest { BLOOD_PANEL, XRAY, MRI }

interface LabOrder {
    LabTest test();
    List<String> checklist();                      // mutable: ticked off per patient
}

class BloodPanelOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("fasting confirmed", "two tubes labelled"));
    public LabTest test() { return LabTest.BLOOD_PANEL; }
    public List<String> checklist() { return checklist; }
}
class XrayOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("pregnancy screen", "metal removed"));
    public LabTest test() { return LabTest.XRAY; }
    public List<String> checklist() { return checklist; }
}
class MriOrder implements LabOrder {
    private final List<String> checklist = new ArrayList<>(List.of("implant screen", "metal removed", "ear protection"));
    public LabTest test() { return LabTest.MRI; }
    public List<String> checklist() { return checklist; }
}

class LabOrders {
    private final Map<LabTest, Supplier<LabOrder>> makers;

    LabOrders(Map<LabTest, Supplier<LabOrder>> makers) {
        makers.forEach((test, maker) -> {
            if (maker.get().test() != test) throw new IllegalArgumentException(test + " is wired to the wrong form");
        });
        this.makers = Map.copyOf(makers);
    }

    LabOrder newOrder(LabTest test) {
        Supplier<LabOrder> maker = makers.get(test);
        if (maker == null) throw new IllegalArgumentException("no order form for " + test);
        return maker.get();
    }
}

LabOrders labOrders() {
    return new LabOrders(Map.of(
        LabTest.BLOOD_PANEL, BloodPanelOrder::new,
        LabTest.XRAY,        XrayOrder::new,
        LabTest.MRI,         MriOrder::new));
}
```

Two MRI orders are two objects: ticking "metal removed" off one leaves the other's three items intact (the checker does exactly that). A registry of *instances* would have shared one MRI form between every patient — the bug Oona found.

</HintLadder>

**Catch the trap:** *"A factory means I can never get a compile error for a missing case."* Only if you choose a map. An exhaustive `switch` expression over an enum, with no `default`, is the one creational shape where the compiler finds the call site for you. Pick the registry when you want the chooser closed, and accept that misses move to runtime.

**Say it aloud:** *"I'll centralize creation behind a factory returning the interface; if implementations multiply, I'll flip it to a registry where each one announces its key."*

<h2 id="the-hook">Chapter 2 · One line differs</h2>

<Scene chapter="Chapter 2" title="One line differs" mood="dusk">

MediCore wants a doctor-utilisation report every evening: how many visits each doctor saw. Finance wants it as CSV. Reception wants it on the old dot-matrix printer behind the front desk, in fixed-width columns, "like the old system did".

The last vendor solved this with copy and paste: `CsvUtilisationReport` and `PrinterUtilisationReport`, forty lines each, identical except for the lines that format the output. Last month someone fixed a bug in the CSV one — doctors now come out sorted by name. The printer version still prints them in whatever order the hash map felt like.

Wren highlights the two classes side by side. Thirty-seven lines are the same in both.

*"The algorithm is one thing,"* she says. *"The object it writes with is another. Which of them is allowed to vary?"*

</Scene>

**The mess.** Two copies of one algorithm, differing in a single decision — which formatter to create — and already drifting:

```java fragment
class CsvUtilisationReport {
    String render(Map<String, Integer> visitsByDoctor) {
        StringBuilder sb = new StringBuilder("doctor,visits");
        new TreeMap<>(visitsByDoctor).forEach((d, v) -> sb.append('\n').append(d).append(',').append(v));   // fixed: sorted
        return sb.toString();
    }
}
class PrinterUtilisationReport {
    String render(Map<String, Integer> visitsByDoctor) {
        StringBuilder sb = new StringBuilder("DOCTOR      VISITS");
        visitsByDoctor.forEach((d, v) -> sb.append('\n').append(String.format("%-12s%d", d, v)));          // never got the fix
        return sb.toString();
    }
}
```

**The detection cue.** Two or more classes whose methods are the same skeleton with **one `new` (or one formatting call) different** — and a bug fix that landed in only one of them.

**The pattern — Factory Method.** The Gang of Four's intent, word for word: *"Define an interface for creating an object, but let subclasses decide which class to instantiate."* The skeleton lives once, in a **creator** class; the one line that differs becomes an abstract method that *creates* the object; each subclass answers it:

```java group=reports
interface Exporter {
    String header();
    String row(String doctor, int visits);
}

class CsvExporter implements Exporter {
    public String header() { return "doctor,visits"; }
    public String row(String doctor, int visits) { return doctor + "," + visits; }
}

class PrinterExporter implements Exporter {                     // fixed-width for the dot-matrix printer
    public String header() { return "DOCTOR      VISITS"; }
    public String row(String doctor, int visits) { return String.format("%-12s%d", doctor, visits); }
}

abstract class UtilisationReport {                              // the creator
    final String render(Map<String, Integer> visitsByDoctor) {  // the algorithm, written once: final
        Exporter out = createExporter();                        // the factory method
        StringBuilder sb = new StringBuilder(out.header());
        new TreeMap<>(visitsByDoctor).forEach((doctor, visits) -> sb.append('\n').append(out.row(doctor, visits)));
        return sb.toString();
    }

    protected abstract Exporter createExporter();               // subclasses decide WHICH class
}

class CsvUtilisationReport extends UtilisationReport {
    protected Exporter createExporter() { return new CsvExporter(); }
}

class PrinterUtilisationReport extends UtilisationReport {
    protected Exporter createExporter() { return new PrinterExporter(); }
}
```

For Dr Rao with 14 visits and Dr Iyer with 9, the CSV report is `doctor,visits`, `Dr Iyer,9`, `Dr Rao,14` — and the printer report now gets the same sorted order for free, because the sorting lives in the one `render` both share. `render` is `final` so no subclass can fork the algorithm again.

Look at what kind of pattern this is: **a Template Method whose varying step is a creation.** That is how GoF present it — the factory method is usually called from inside the creator's own algorithm. The JDK's canonical example is `Collection.iterator()`: every collection runs the same "give me something to walk you with" request, and each subclass decides which iterator class to build (GoF's Iterator chapter calls it out as a factory method).

**The modern alternative: pass the factory in.** A subclass whose only job is to override `createExporter` is a lot of ceremony for one line. In Java 8+, one creator that *takes* a `Supplier` replaces the whole family of subclasses:

```java group=reports
class SuppliedReport extends UtilisationReport {                // Factory Method by composition
    private final Supplier<Exporter> exporters;
    SuppliedReport(Supplier<Exporter> exporters) { this.exporters = exporters; }
    protected Exporter createExporter() { return exporters.get(); }
}

String eveningReports(Map<String, Integer> visits) {
    String csv = new SuppliedReport(CsvExporter::new).render(visits);
    String printer = new SuppliedReport(PrinterExporter::new).render(visits);
    return csv + "\n\n" + printer;
}
```

The checker confirms `new SuppliedReport(CsvExporter::new)` renders exactly what `CsvUtilisationReport` renders, character for character. Notice where you've arrived: a `Supplier` handed in from outside is Chapter 1's registry of suppliers with one entry.

**When not to use it.** One product, forever: just call `new` inside the algorithm. A creator hierarchy where each subclass overrides only the factory method: prefer the injected `Supplier`. And if the creator has no algorithm of its own — it only creates — it isn't Factory Method at all; it's a simple factory wearing inheritance.

<Scene chapter="Chapter 3" title="Sandbox money" mood="night">

**The mess.** Members of two families, wired one object at a time:

```java fragment
// Thursday's wiring, assembled piece by piece:
PaymentGateway gateway   = new PennyPayGateway(live.apiKey());           // live money
WebhookVerifier verifier = new SandboxVerifier(sandbox.testSecret());    // copied from the test setup

```

The bug wasn't one wrong object; it was a **mixed family**. The checker reproduces both symptoms with the classes below: a genuine live-signed webhook fails the sandbox verifier, and a forgery signed with the public test secret passes it — while the live verifier rejects the forgery.

**The detection cue.** The word **"family"**, or a sentence like "these three must always match". Several products, each with variants, and an invariant *across* the products: never a live gateway with a sandbox verifier; never a GST invoice with a gateway for another country.

**The pattern — Abstract Factory.** Make the *family* the unit of construction: one factory interface with a method per product, one implementation per variant:

```java group=suites
interface PaymentGateway  { String charge(String patientId, long paise); }

interface WebhookVerifier { boolean verify(String payload, String signature); }

record SandboxConfig(String baseUrl, String testSecret) {}
record LiveConfig(String apiKey, String webhookSecret) {}

static String sign(String secret, String payload) {               // stand-in for HMAC-SHA256: secret-dependent, deterministic
    return Integer.toHexString((secret + "|" + payload).hashCode());
}

class SandboxGateway implements PaymentGateway {
    private final String baseUrl;
    SandboxGateway(String baseUrl) { this.baseUrl = baseUrl; }

}

}

    private final String testSecret;
    SandboxVerifier(String testSecret) { this.testSecret = testSecret; }

}

}

}
```

```java group=suites
interface GatewaySuite {           // the family contract
    PaymentGateway gateway();
    RefundClient refunds();
    WebhookVerifier verifier();
}

class SandboxSuite implements GatewaySuite {
    private final SandboxConfig cfg;
    SandboxSuite(SandboxConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new SandboxGateway(cfg.baseUrl()); }
    public RefundClient refunds()     { return new SandboxRefundClient(cfg.baseUrl()); }
    public WebhookVerifier verifier() { return new SandboxVerifier(cfg.testSecret()); }
}

class LiveSuite implements GatewaySuite {
    private final LiveConfig cfg;
    LiveSuite(LiveConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new PennyPayGateway(cfg.apiKey()); }
    public RefundClient refunds()     { return new PennyPayRefundClient(cfg.apiKey()); }
    public WebhookVerifier verifier() { return new PennyPayVerifier(cfg.webhookSecret()); }
}

class BillingService {
    private final PaymentGateway gateway;
    private final WebhookVerifier verifier;

    BillingService(GatewaySuite suite) {            // takes the FAMILY, never its members one by one
        this.gateway = suite.gateway();
        this.verifier = suite.verifier();
    }
    String charge(String patientId, long paise) { return gateway.charge(patientId, paise); }
    boolean confirm(String payload, String signature) { return verifier.verify(payload, signature); }
}

// Wiring picks ONE suite:
GatewaySuite suiteFor(boolean prod, LiveConfig liveCfg, SandboxConfig sandboxCfg) {
    return prod ? new LiveSuite(liveCfg) : new SandboxSuite(sandboxCfg);
}
```

**Where the guarantee actually comes from.** A suite on its own only makes the right thing *easy*: a caller could still write `new BillingService(live.gateway(), sandbox.verifier())` if `BillingService` accepted members. The constructor that accepts **the suite itself** is what makes the wrong thing *impossible* — there is no parameter list into which you could put a live gateway and a sandbox verifier. The choice of environment happens once, in `suiteFor`, and everything billing touches comes from that choice. (In a real codebase, make the product constructors package-private next to their suite, and the only way to get a `PennyPayVerifier` is through `LiveSuite`.)

**Its known weakness.** Adding a new *family* (a staging environment, a second country) is one new class — Side quest 2 does it. > **Cheat code:** "these N objects must never mix across variants" → abstract factory.

<Scene chapter="Chapter 4" title="Eight parameters">

**The mess.** Telescoping constructors — each overload adds a parameter and delegates to the longest — and a call site nobody can read:

```java id=bookingMess

    final Slot slot;
```

The checker builds Oona's booking with exactly that call: it succeeds, and the result is a teleconsult *with a room* that is *not* a follow-up. Nothing checks that a video call can't have a room, because no single place sees all the fields at once.

**The detection cues.**

1. **More than about four parameters, several of the same type side by side.** Two `boolean`s or three `String`s in a row can be transposed and still compile.
2. **`null` passed to mean "I don't care".** Every `null` is a question the reader can't answer.
3. **Overloads multiplying.** Each new optional field is another constructor. The War Room's inventory found <a href={`${BASE}lld/war/inventory/#bonus-smell-six-overloads`}>six overloads of one method, telescoping through boolean flags</a> — the same pain, one level up.
4. **Rules between fields with no home.** "Teleconsult means no room" belongs to the *whole* booking; no setter and no single parameter can enforce it.

**The pattern — Builder.** The full hand-rolled shape (rounds ask you to *write* this, not just call it). Blocks on this page are compiled as nested classes, which is why a few classes carry `static`; in your own files they're top-level and the keyword disappears.

```java group=booking
import java.time.*;

record Slot(LocalDateTime start, int minutes) {
    Slot {
        Objects.requireNonNull(start, "start");
        if (minutes <= 0) throw new IllegalArgumentException("a slot lasts at least one minute");
    }
}

static final class Booking {
    // all final — a built Booking is immutable
    private final String patientId;      // required
    private final String doctorId;       // required
    private final Slot slot;             // required
    private final boolean teleconsult;   // optional, default false
    private final String roomId;         // optional (but required in person — a cross-field rule)
    private final boolean followUp;      // optional, default false
    private final String referralNote;   // optional
    private final List<String> symptoms; // optional, possibly empty

    private Booking(Builder b) {         // private: the ONLY way in is build()
        this.patientId    = b.patientId;
        this.doctorId     = b.doctorId;
        this.slot         = b.slot;
        this.teleconsult  = b.teleconsult;
        this.roomId       = b.roomId;
        this.followUp     = b.followUp;
        this.referralNote = b.referralNote;
        this.symptoms     = List.copyOf(b.symptoms);   // a snapshot: later builder calls can't reach in
    }

    static Builder builder() { return new Builder(); }

    String patientId()          { return patientId; }
    String doctorId()           { return doctorId; }
    Slot slot()                 { return slot; }
    boolean teleconsult()       { return teleconsult; }
    Optional<String> roomId()   { return Optional.ofNullable(roomId); }
    boolean followUp()          { return followUp; }
    Optional<String> referral() { return Optional.ofNullable(referralNote); }
    List<String> symptoms()     { return symptoms; }    // List.copyOf is already unmodifiable

    static final class Builder {
        private String patientId;
        private String doctorId;
        private Slot slot;
        private boolean teleconsult = false;   // defaults live here
        private String roomId;
        private boolean followUp = false;
        private String referralNote;
        private final List<String> symptoms = new ArrayList<>();

        private Builder() {}

        Builder patient(String id)      { this.patientId = id; return this; }   // return this = chaining
        Builder doctor(String id)       { this.doctorId = id; return this; }
        Builder slot(Slot s)            { this.slot = s; return this; }
        Builder teleconsult(boolean t)  { this.teleconsult = t; return this; }
        Builder room(String roomId)     { this.roomId = roomId; return this; }
        Builder followUp(boolean f)     { this.followUp = f; return this; }
        Builder referral(String note)   { this.referralNote = note; return this; }
        Builder symptom(String s)       { symptoms.add(Objects.requireNonNull(s, "symptom")); return this; }  // one field: fail fast

        Booking build() {
            // 1. required fields present
            if (patientId == null || doctorId == null || slot == null)
                throw new IllegalStateException("patient, doctor, slot are required");
            // 2. CROSS-FIELD invariants — the whole point of build()
            if (teleconsult && roomId != null)
                throw new IllegalStateException("teleconsult bookings cannot have a room");
            if (!teleconsult && roomId == null)
                throw new IllegalStateException("in-person bookings need a room");
            return new Booking(this);
        }
    }
}

// Usage reads like the requirements doc:
Booking teleconsultFor(Slot slot) {
    return Booking.builder()
        .patient("P-1042")
        .doctor("D-07")
        .slot(slot)
        .teleconsult(true)
        .build();
}

Booking orThursdaysMistakeFixed(Slot slot) {          // Oona's booking, now impossible to transpose
    return Booking.builder()
        .patient("P-1042").doctor("D-07").slot(slot)
        .room("R-3")
        .followUp(true)
        .build();
}
```

The mechanics to narrate while writing it: **builder fields are mutable, the product's are final** — mutation is quarantined inside the builder and ends at `build()`; the product's constructor is **private** so a half-configured Booking has no way to exist; setters `return this` for chaining; defaults live in the builder's field initializers.

The part that separates a gold answer from a Lombok reflex: **`build()` is where cross-field invariants live** (teleconsult excludes room; slot within doctor's schedule). A builder that just sets fields is syntax; a builder whose `build()` can refuse is an invariant gate — it restores the "constructed ⇒ valid" guarantee from the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson</a>. (Lombok's `@Builder` would write the setters for you; the rules in `build()` are yours to write either way, which is why rounds ask for the hand-rolled version.)

**Three tiers of validation**, each in its own place:

| Rule | Example | Where it lives | When it fails |
|---|---|---|---|
| About one value | a symptom can't be null; a slot lasts ≥ 1 minute | the setter, or the value's own type (`Slot`'s compact constructor) | immediately, at the bad call |
| Required presence | patient, doctor, slot | `build()` — or the builder's own signature (Your turn) | at `build()` — or at compile time |
| Between fields | teleconsult ⇔ no room | `build()` | at `build()` |

**Final is not immutable.** `final List<String> symptoms` only stops the *field* from being reassigned. If the constructor stored the builder's list directly, a second `symptom(...)` call on the same builder — or any caller holding the list — would change a "built, immutable" booking. `List.copyOf` takes a snapshot that's also unmodifiable. The checker reuses one builder for two bookings and confirms the first booking's symptoms didn't move, that `symptoms().add(…)` throws, and that every field of `Booking` is declared `final`.

When asked "when builder over factory?": factory chooses **which class**, builder assembles **one complex object step-by-step**. Different questions; they compose (a factory can return builders).

**When not to use it.** Few fields, all required: a **record with a compact constructor** is the whole pattern in three lines — `record Slot(LocalDateTime start, int minutes)` validates itself above, no builder needed. **Your turn.** Prescriptions: patient and doctor are always required; at least one medicine; refills from 0 to 5; optional notes. Controlled medicines (sleeping pills, strong painkillers) can never be refilled. Make "forgot the doctor" a *compile* error, keep the rest of the rules where they belong, and make the result immutable.

```java group=prescription
record Medicine(String name, String dose, boolean controlled) {
    Medicine {
        Objects.requireNonNull(name, "name");
        Objects.requireNonNull(dose, "dose");
    }
}

static final class Prescription {
    private final String patientId;
    private final String doctorId;
    private final List<Medicine> medicines;
    private final int refills;
    private final String notes;

    private Prescription(Builder b) {
        this.patientId = b.patientId;
        this.doctorId  = b.doctorId;
        this.medicines = List.copyOf(b.medicines);
        this.refills   = b.refills;
        this.notes     = b.notes;
    }

    static Builder builder(String patientId, String doctorId) {   // required fields: the compiler enforces them
        return new Builder(patientId, doctorId);
    }

    String patientId()        { return patientId; }
    String doctorId()         { return doctorId; }
    List<Medicine> medicines() { return medicines; }
    int refills()             { return refills; }
    String notes()            { return notes; }

    static final class Builder {
        private final String patientId;
        private final String doctorId;
        private final List<Medicine> medicines = new ArrayList<>();
        private int refills = 0;
        private String notes = "";

        private Builder(String patientId, String doctorId) {
            this.patientId = Objects.requireNonNull(patientId, "patientId");
            this.doctorId  = Objects.requireNonNull(doctorId, "doctorId");
        }

        Builder medicine(String name, String dose)   { medicines.add(new Medicine(name, dose, false)); return this; }
        Builder controlled(String name, String dose) { medicines.add(new Medicine(name, dose, true)); return this; }
        Builder notes(String text)                   { this.notes = Objects.requireNonNull(text, "notes"); return this; }
        Builder refills(int n) {
            if (n < 0 || n > 5) throw new IllegalArgumentException("refills must be 0..5, got " + n);   // one value: fail fast
            this.refills = n;
            return this;
        }

        Prescription build() {
            if (medicines.isEmpty())
                throw new IllegalStateException("a prescription needs at least one medicine");
            if (refills > 0 && medicines.stream().anyMatch(Medicine::controlled))
                throw new IllegalStateException("controlled medicines cannot be refilled");   // a rule between fields
            return new Prescription(this);
        }
    }
}
```

Required fields in the builder's signature are Effective Java's own form (Item 2): you can't call `builder` without them.

</HintLadder>

**Catch the trap:** *"A builder makes the object immutable."* It doesn't, by itself. Immutability comes from final fields, no setters on the product, a private constructor, and **defensive copies of anything mutable** that passes through. Forget `List.copyOf` and your "immutable" booking changes when the builder does.

**Say it aloud:** *"Required fields checked in build(), cross-field invariants too — so a Booking that exists is valid by construction."*

**The mess.** `Cloneable` and `super.clone()` — a field-by-field copy, so both "copies" hold **the same list**:

```java id=cloneMess
record LineItem(String code, String description, long paise) {}

class InvoiceTemplate implements Cloneable {
    String header;
    List<LineItem> items = new ArrayList<>();

    @Override public InvoiceTemplate clone() {
        try {
            return (InvoiceTemplate) super.clone();      // copies the REFERENCE to items, not the list
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);                 // can't happen: we implement Cloneable
        }
    }
}
```

The checker builds the Riverside template with one registration line, clones it, adds an X-ray to the clone — and the *template* now has two lines.

**The detection cue.** "Start from a configured exemplar" — templates, default settings, a pre-filled form — where building from scratch is expensive or the configuration lives elsewhere. And the moment you hear "copy", ask the graded question: **which fields are mutable, and does the copy get its own?**

**The pattern — Prototype.** In GoF's terms, create new objects by copying a prototypical instance. In Java, the honest tool is a **copy constructor** (or a static `copyOf` factory), not `clone()`:

```java group=invoices
record LineItem(String code, String description, long paise) {}

class InvoiceTemplate {
    private final String header;
    private final List<LineItem> items;
    private final Map<String, String> taxFields;      // GSTIN, place of supply, ...

    InvoiceTemplate(String header, List<LineItem> items, Map<String, String> taxFields) {
        this.header = header;
        this.items = new ArrayList<>(items);
        this.taxFields = new LinkedHashMap<>(taxFields);
    }

    InvoiceTemplate(InvoiceTemplate other) {                       // copy constructor = Prototype in Java
        this.header = other.header;                                // String is immutable: sharing is safe
        this.items = new ArrayList<>(other.items);                 // a fresh list; the LineItem records inside are immutable, so they can be shared
        this.taxFields = new LinkedHashMap<>(other.taxFields);     // a fresh map — a shared map would let edits bleed between "copies"
    }

    void addItem(LineItem item)                  { items.add(item); }
    void setTaxField(String name, String value)  { taxFields.put(name, value); }
    String header()                              { return header; }
    List<LineItem> items()                       { return Collections.unmodifiableList(items); }
    Map<String, String> taxFields()              { return Collections.unmodifiableMap(taxFields); }

    long totalPaise() {
        long sum = 0;
        for (LineItem item : items) sum += item.paise();
        return sum;
    }
}

InvoiceTemplate patientInvoice(InvoiceTemplate standardTemplate) {
    InvoiceTemplate invoice = new InvoiceTemplate(standardTemplate);    // clone, then customize
    invoice.addItem(new LineItem("XR-01", "Chest X-ray", 85000));
    return invoice;
}
```

With a template holding one registration line of ₹200 (20,000 paise), `patientInvoice` returns an invoice totalling 105,000 paise, and the template still totals 20,000 with one line. The checker also edits a tax field on the copy and confirms the template's map didn't change.

**How deep is deep?** The graded phrase is **copy every mutable thing reachable from the object; share every immutable thing**. Here the list and the map are mutable, so each copy gets its own; the `String` and the `LineItem` records are immutable, so sharing them is not just safe but correct. "Deep copy" doesn't mean "copy everything recursively" — it means *no mutable state is shared*. Side quest 3 makes `LineItem` mutable and shows that `new ArrayList<>(...)` stops being enough.

**Why not `clone()`?** Prefer **copy constructors or `toBuilder()`** over `Cloneable`, which is broken by design (*Effective Java*, Item 13):

- `Cloneable` has **no `clone` method**. It's a marker that changes how the protected `Object.clone()` behaves; the interface itself promises nothing.
- `Object.clone()` is **shallow** and creates the copy **without running a constructor** — any validation or setup in your constructors is skipped.
- It throws the **checked** `CloneNotSupportedException`, so every override wraps a `try` around something that can't happen.
- It **fights `final` fields**: to deep-copy a `final List` inside `clone()`, you'd have to reassign a final field, which won't compile. You're pushed to make fields non-final just to copy them.
- The one place `clone()` is the right tool: **arrays**. `int[] copy = original.clone();` is the idiomatic array copy (for arrays of mutable objects it's still shallow).

<Reveal q="Delete the 'new ArrayList<>(...)' wrapper and copy the list reference directly. What bug ships?">

**When not to use it.** If construction is cheap and needs no outside configuration, just construct. If the object is **immutable, don't copy it at all** — share it; there's nothing a copy could protect. (For variations of an immutable object, use "withers": `template.withHeader("Riverside")` returns a new object.) And don't build a prototype registry for one template.

**Your turn.** MediCore has three templates — outpatient, pharmacy, inpatient — and every clinic should get *copies* out of a catalog without ever being able to corrupt the catalog's exemplars, even if the code that registered an exemplar keeps editing its own object afterwards. Write the catalog.

<HintLadder hints={hints.catalog} labels={turn}>

```java group=invoices
class TemplateCatalog {                                  // a prototype registry: named exemplars, copies out
    private final Map<String, InvoiceTemplate> prototypes = new HashMap<>();

    void register(String kind, InvoiceTemplate exemplar) {
        prototypes.put(kind, new InvoiceTemplate(exemplar));        // copy IN: the caller keeps its own object
    }

    InvoiceTemplate newInvoice(String kind) {
        InvoiceTemplate prototype = prototypes.get(kind);
        if (prototype == null) throw new IllegalArgumentException("no template " + kind);
        return new InvoiceTemplate(prototype);                      // copy OUT: callers never touch the exemplar
    }
}
```

Two copies of "outpatient" are independent; editing the object you registered, after registering it, changes nothing in the catalog. Copying on the way in matters as much as on the way out — that's GoF's *prototype manager* with Java's defensive-copy habit.

</HintLadder>

**Catch the trap:** *"I implemented `Cloneable`, so my class has a deep copy."* `Cloneable` gives you `Object.clone()`'s shallow, constructor-skipping copy and nothing else. Depth is something you write, field by field, and a copy constructor is the clearest place to write it.

**Say it aloud:** *"I'll copy the configured template with a copy constructor — fresh collections for the mutable fields, the immutable values shared — rather than Cloneable, which is shallow and skips constructors."*

**The mess.** A public constructor (so anyone can make another) and a lazy `get()` with an unguarded check-then-act:

**The Java answers, in interview-ranking order:**

```java group=singletons
// 1. Enum — serialization-safe, reflection-safe, thread-safe by class initialization. Effective Java's answer.
enum MetricsRegistry {
    INSTANCE;
    private final Map<String, LongAdder> counters = new ConcurrentHashMap<>();
    void record(String key, long value) { counters.computeIfAbsent(key, k -> new LongAdder()).add(value); }
    long total(String key) {
        LongAdder sum = counters.get(key);
        return sum == null ? 0 : sum.sum();
    }
}

// 2. Holder idiom — lazy without locks: class initialization is thread-safe by JLS guarantee.
static final class Config {
    static final AtomicInteger created = new AtomicInteger();   // demo-only: counts constructions
    private final Map<String, String> values;
    private Config() {
        created.incrementAndGet();
        values = Map.of("clinic.timezone", "Asia/Kolkata", "pool.size", "20");
    }
    private static class Holder { static final Config I = new Config(); }
    static Config get() { return Holder.I; }
    String value(String key) { return values.get(key); }
}

// 3. Double-checked locking — the classic exam answer. volatile is NOT optional:
static final class ClinicDbPool {
    private static volatile ClinicDbPool instance;
    static final AtomicInteger opened = new AtomicInteger();    // demo-only: counts pools opened
    private final int connections;

    private ClinicDbPool() {
        connections = 20;
        opened.incrementAndGet();
        pause(50);                                              // slow, like a real pool — widens every race
    }

    static ClinicDbPool get() {
        if (instance == null) {                                 // check 1: no lock on the fast path
            synchronized (ClinicDbPool.class) {
                if (instance == null) instance = new ClinicDbPool();   // check 2: under the lock
            }
        }
        return instance;
    }

    int connections() { return connections; }
}

static void pause(long millis) {
    try { Thread.sleep(millis); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}
```

The checker runs all three under the same sixty-four-thread cold start: one `MetricsRegistry`, one `Config`, one `ClinicDbPool`, and the constructors' counters read exactly 1. It also proves the holder is **lazy**: reading `Config.created` initializes `Config` but not `Holder`, and the counter is still 0 until the first `get()`.

**Why each form is safe.**

- **Enum:** the JVM creates `INSTANCE` during class initialization, which the JLS (§12.4.2) runs exactly once under a lock. Enums also defeat the two classic attacks: `Constructor.newInstance` refuses to create enum objects (the checker tries and gets `IllegalArgumentException`), and serialization writes enums by name and reads back the *same* constant (the checker round-trips `INSTANCE` through `ObjectOutputStream` and gets the identical object). A class-based singleton needs extra code for both — and the checker shows a reflective `setAccessible(true)` call happily making a second `Config`.
- **Holder:** `Holder` isn't initialized until `get()` first touches `Holder.I`, and that initialization is the same JVM-guaranteed, once-only step. Lazy and lock-free on every later call.
- **Double-checked locking:** check 1 keeps the common path lock-free; check 2 is the real decision, made under the lock; `volatile` makes the published reference safe to read without the lock.

You wrote three notes to yourself the first time you met this code. They're worth keeping, sharpened:

1. *"volatile: always read the latest state of the object."* Close. The sharper version: `volatile` makes the write of `instance` a **safe publication** — everything the constructor wrote *happens-before* any thread that reads the non-null reference. Without it, the reference can be visible before the fields it points to.
2. *"Private constructor required — without it any class in the same package can call it."* Exactly right, and it's what the 6:02 incident was: a report job calling `new` around all the ceremony. No private constructor, no singleton.
3. *"Double check: two threads can pass check 1 before either locks; they enter the synchronized block one at a time; without the re-check, the second thread constructs a second pool."* Exactly right — and you can watch it happen:

```java id=noRecheckMess
static final class ClinicDbPool {
    private static volatile ClinicDbPool instance;
    static final AtomicInteger opened = new AtomicInteger();
    private ClinicDbPool() { opened.incrementAndGet(); pause(50); }

    static ClinicDbPool get() {
        if (instance == null) {
            synchronized (ClinicDbPool.class) {
                instance = new ClinicDbPool();          // no second check: every thread that passed check 1 builds one
            }
        }
        return instance;
    }
}

static void pause(long millis) {
    try { Thread.sleep(millis); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}
```

Under the checker's sixty-four threads, every thread that passed check 1 during the first 50 ms queues on the lock and builds its own pool, one after another.

<Reveal q="Cover the explanation above. Why exactly is volatile load-bearing — what can a second thread observe without it?">

`instance = new ClinicDbPool()` is three steps — allocate, run constructor, write reference — and the JMM may reorder to allocate → **write reference** → construct. A second thread sees non-null at check 1, skips the lock, and returns a pool whose constructor **hasn't finished** — it reads garbage fields. `volatile` forbids that reordering. (Formally: without `volatile` there is no happens-before edge between the constructor's writes and the unsynchronized read, so the reader may see the reference with default field values. DCL has been correct with `volatile` since Java 5's memory model, JSR-133.) And without the private constructor there is no singleton at all — anything in the package can `new ClinicDbPool()` around the ceremony.

One honest caveat about tests: **no test on this page can show the missing-`volatile` bug.** It needs a specific reordering on a specific JIT and CPU, and typical x86 hardware rarely exhibits it. A passing test proves nothing here; the memory model does. That is the strongest reason to prefer the enum or the holder: there is no cliff to fall off.

</Reveal>

**Why a Singleton is usually a smell.** The pattern bundles two things: **"there is one"** (a lifetime) and **"anyone can reach it from anywhere"** (a global access point). The first is often a real requirement. The second is the damage:

```java group=singletons

```

`BookingDesk`'s constructor says it needs nothing. It's lying. Its test can't substitute the metrics, and because the registry outlives every test, the checker shows the bleed: test A books once and sees `bookings = 1`; test B, run next in the same JVM, books once and sees **2**. Order-dependent tests, invisible dependencies, and no seam for a fake — that's the real charge sheet, not "singletons are slow". (The War Room's <a href={`${BASE}lld/war/patterns-why/#3-ambient-context--why-the-tenant-id-isnt-a-parameter`}>ambient-context dossier</a> gives the production version of the answer: an invisible value has an invisible lifecycle, and every boundary it crosses is a place it can go missing.)

Then the sentence that shows senior judgment: **in real systems, singletons are a scope, not a pattern** — the DI container (or your `main()`) constructs one instance and injects it everywhere. Same one-ness, none of the global-state damage: tests can substitute it, hidden dependencies disappear. The <a href={`${BASE}lld/war/inventory/`}>War Room inventory</a> grades it exactly this way — Spring supplies singleton scope for free, so hand-rolling one in a Spring codebase is a smell, not a skill. **The detection cue — when an Object Pool is justified.** Three conditions, all at once: the object is **expensive to create** (connections, threads, large native buffers), it is **reusable** after a reset, and its number must be **bounded** (the database's connection limit, CPU cores). The classic justified case is exactly this one. *Effective Java* (Item 6) is blunt about the rest: maintaining your own pool for lightweight objects is a bad idea — modern garbage collectors make short-lived objects cheap, and a pool adds contention and leaks. The database connection is Bloch's own example of an object that *does* justify one.

**The pattern — a bounded pool on a `BlockingQueue`.** The queue does the hard concurrency: `poll` with a timeout blocks while every item is lent out and wakes when one comes back.

```java group=pool
class PoolExhaustedException extends RuntimeException {
    PoolExhaustedException(Duration waited) { super("nothing free after " + waited.toMillis() + " ms"); }
}

class BoundedPool<T> {
    private final BlockingQueue<T> idle;
    private final Set<T> lent = ConcurrentHashMap.newKeySet();

    BoundedPool(int size, Supplier<T> factory) {
        if (size <= 0) throw new IllegalArgumentException("size must be positive");
        this.idle = new ArrayBlockingQueue<>(size);
        for (int i = 0; i < size; i++) idle.add(factory.get());       // eager: pay the expensive part at startup
    }

    T borrow(Duration timeout) throws InterruptedException {
        T item = idle.poll(timeout.toNanos(), TimeUnit.NANOSECONDS);  // blocks while all are lent out
        if (item == null) throw new PoolExhaustedException(timeout); // bounded wait, loud failure
        lent.add(item);
        return item;
    }

    void giveBack(T item) {
        if (!lent.remove(item)) throw new IllegalArgumentException("not borrowed from this pool, or already returned");
        idle.add(item);                                               // can't overflow: only lent items come back
    }

    int idleCount() { return idle.size(); }
}

class DbConnection {                                  // stands in for a real JDBC connection
    final int id;
    DbConnection(int id) { this.id = id; }
    String query(String sql) { return "conn-" + id + ": " + sql; }
}
```

Three design decisions to say out loud. **Bounded:** at most `size` objects ever exist, so the pool can't become the thing that overwhelms the database. **A timeout, not a forever-wait:** when everything is lent out, a borrower waits a bounded time and then fails loudly with `PoolExhaustedException`, instead of hanging a request thread forever. **Returns are checked:** giving back something that isn't currently lent — a double return, or an object from another pool — throws, instead of silently letting the pool hold more items than it lent out. (The `lent` set compares with `equals`; pooled objects like connections use identity equality, which is what you want.)

The checker hammers it: a pool of 3 connections, 24 threads, 200 borrow-use-return cycles each — 4,800 loans. It tracks how many connections are in use at every moment (never more than 3), that no connection is ever lent to two threads at once, and that all 3 are idle at the end. With all 3 lent out, a fourth `borrow` with a 50 ms timeout throws `PoolExhaustedException`; a borrower blocked for up to 2 seconds wakes up and gets the connection the moment another thread returns one.

**The mess — Oona's leak.** The second half of the promise lives in the caller:

```java fragment
DbConnection c = pool.borrow(Duration.ofMillis(200));
String rows = c.query("SELECT * FROM lab_results WHERE patient = ?");   // throws halfway through...
pool.giveBack(c);                                                      // ...so this line never runs
```

Each exception leaks one connection. The checker borrows three without returning them: the fourth borrower times out, forever. That's the hang on the lab-results page.

**When not to use it.** Cheap objects — `StringBuilder`s, DTOs, small arrays: allocation is cheaper than a pool's synchronization, and a stale pooled object is a bug factory. Anything your platform already pools: use an **`ExecutorService`** for threads and a production connection pool for connections (HikariCP is Spring Boot's default) — they handle validation, idle eviction, leak detection and metrics you don't want to rewrite. In an interview, write the `BlockingQueue` version to show the mechanics, then say you'd use the library.

**Your turn.** Make the leak impossible to write by accident: a `Lease` that borrows in its constructor and gives back in `close()`, so `try`-with-resources returns the connection on every path — including exceptions. Closing twice must be harmless. Don't edit `BoundedPool`.

<HintLadder hints={hints.lease} labels={turn}>

```java group=pool
class Lease<T> implements AutoCloseable {
    private final BoundedPool<T> pool;
    private final T item;
    private final AtomicBoolean returned = new AtomicBoolean(false);

    Lease(BoundedPool<T> pool, Duration timeout) throws InterruptedException {
        this.pool = pool;
        this.item = pool.borrow(timeout);
    }

    T get() {
        if (returned.get()) throw new IllegalStateException("lease already returned");
        return item;
    }

    @Override public void close() {
        if (returned.compareAndSet(false, true)) pool.giveBack(item);   // exactly once, however often close() is called
    }
}

String labResults(BoundedPool<DbConnection> pool, String patientId) throws InterruptedException {
    try (Lease<DbConnection> lease = new Lease<>(pool, Duration.ofMillis(200))) {
        return lease.get().query("SELECT * FROM lab_results WHERE patient = '" + patientId + "'");
    }                                                                     // returned here, on every path
}
```

The checker throws from inside the `try` a hundred times on a pool of 3 and every connection still comes back. (The string-built SQL is a stand-in; real code uses a `PreparedStatement` parameter — never concatenate patient input into SQL.)

</HintLadder>

**Catch the trap:** *"A pool makes object creation faster."* It makes *expensive* creation rarer, at the price of contention, reset bugs and leaks. For ordinary objects it's slower and riskier than `new`. The justification is never "allocation is slow"; it's "this resource is expensive **and** limited".

**Say it aloud:** *"Connections are expensive and the database caps them, so I'll pool them: a bounded BlockingQueue, a borrow timeout that fails loudly, and try-with-resources so every loan comes back. In production I'd use HikariCP rather than this."*

**The detection cues.** `new` on anything long-lived or I/O-bound inside a class that makes business decisions; `getInstance()` and `now()` inside business logic; a constructor whose parameter list doesn't tell you what the class actually needs.

**The pattern — dependency injection with one composition root.** Each class *receives* its collaborators through its constructor; one place at the entry point of the application constructs the whole object graph, once:

```java group=clinic
import java.time.*;

interface Database { void execute(String sql); }               // the port; in production it borrows from the pool
interface Notifier { void notify(String patientId, String text); }

class AppointmentService {
    private final Database db;
    private final Notifier notifier;
    private final Clock clock;

    AppointmentService(Database db, Notifier notifier, Clock clock) {      // constructor injection: final fields,
        this.db = Objects.requireNonNull(db, "db");                         // complete on construction,
        this.notifier = Objects.requireNonNull(notifier, "notifier");       // dependencies visible in one signature
        this.clock = Objects.requireNonNull(clock, "clock");
    }

    String book(String patientId, String doctorId) {
        LocalDateTime at = LocalDateTime.now(clock);
        db.execute("INSERT appointment " + patientId + " " + doctorId + " " + at);
        notifier.notify(patientId, "Booked with " + doctorId + " at " + at);
        return patientId + "@" + at;
    }
}

class DischargeService {
    private final Database db;
    DischargeService(Database db) { this.db = Objects.requireNonNull(db, "db"); }
    void discharge(String patientId) { db.execute("UPDATE admission SET discharged " + patientId); }
}

class RecordingDatabase implements Database {                  // stands in for the pooled JDBC database
    final List<String> statements = Collections.synchronizedList(new ArrayList<>());
    public void execute(String sql) { statements.add(sql); }
}

record MediCoreApp(Database db, AppointmentService appointments, DischargeService discharges) {}

MediCoreApp production() {                                     // the composition root: long-lived objects are built HERE
    Database db = new RecordingDatabase();                     // ONE instance: a singleton by scope, not by pattern
    Notifier sms = (patientId, text) -> { /* the SMS adapter, also built once, would go here */ };
    return new MediCoreApp(db,
        new AppointmentService(db, sms, Clock.systemDefaultZone()),
        new DischargeService(db));
}
```

Both services share the one database the root built — the checker books and discharges through `production()` and finds both statements in that single instance — and neither service can make another. "Exactly one" is now a fact about **one line in one method**, not about a class's static machinery.

**Ways to inject, ranked:**

| Style | How | Verdict |
|---|---|---|
| **Constructor injection** | collaborators are constructor parameters, stored in `final` fields | **Default.** Complete at construction, dependencies visible, trivially testable. |
| Setter injection | `setNotifier(...)` after construction | Only for genuinely optional dependencies; the object can exist half-wired. |
| Field injection | a container writes private fields (`@Autowired` on a field) | Hides dependencies, prevents `final`, needs the container even in unit tests. |
| Service locator | `Services.get(Notifier.class)` from inside the class | The Singleton problem with a map: dependencies hidden again. |

**Lifetimes are a wiring decision.** Once construction lives in one place, "how many" stops being a pattern and becomes a word: **singleton** (one per application — what Spring beans are by default), **prototype**/transient (a new instance per injection — Spring's name for it, borrowed loosely from the Prototype pattern), **scoped** (one per request or session). When a class needs *fresh objects repeatedly* — Chapter 1's lab forms — inject a **factory**: a `Supplier<LabOrder>` or the `LabOrders` registry itself. The creational patterns don't disappear under DI; they become the things the root wires together.

**DI is a `main()` method before it's a container.** Mark Seemann's name for the one place is the **composition root**: as close to the application's entry point as possible, the only place that knows the concrete classes. Spring or Guice automate that method; they don't change the design. In a 90-minute round, a hand-written root that wires six objects beats configuring a framework — and it's the answer to the <a href={`${BASE}lld/lessons/solid/`}>SOLID lesson</a>'s dependency-inversion chapter, from the creation side.

<Trace title="Who calls new?" steps={injection} takeaway="Business classes receive collaborators; one composition root creates them. Lifetimes — one, per-use, per-request — become wiring decisions, and fresh objects arrive through injected factories." />

**When not to use it.** Values and pure helpers — a `Money`, a `StringBuilder`, an `ArrayList`, `Duration.between` — are created with `new` right where they're used; injecting them is ceremony. Don't put an interface over a stable class just "for DI" if nothing ever stands in for it. And don't reach for a container in an interview; the root is a method.

| You hear / you see | Pattern | The one-line reason | Don't, when… |
|---|---|---|---|
| A `switch` on a type picks a class, at one place | **Simple factory** | One place decides; the compiler checks the cases | one implementation; `new` in `main()` is enough |
| The same choice at several call sites, implementations growing | **Registry of instances** (`Map<K, T>`, key from the object) | The chooser never reopens | two fixed variants |

| "These N must always match" across variants | **Abstract Factory** | The family is the unit; mixing has no code path | no cross-product invariant; one product |
| Many optional fields, rules between them | **Builder** | `build()` is the invariant gate; product immutable | few fields, all required → record |
| Start from a configured exemplar | **Prototype** (copy constructor) | Copy is cheaper/simpler than rebuilding | object is immutable — share it instead |
| "Exactly one, shared everywhere" | **Singleton as a DI scope**; hand-rolled → enum | One instance without a global access point | "we only need one today" |
| Expensive, reusable, limited resource | **Object Pool** (bounded, timed, leases) | Bound the resource, reuse the expensive part | cheap objects; the platform already pools |
| `new`/`now()`/`getInstance()` inside business logic | **Dependency injection + composition root** | Every lifetime decided in one place | values and pure helpers |

<h2 id="sq-card-retries">Side quest 1 · The card that said no</h2>

**The note says:** *"Card payments: the bank allows three attempts per payment, then declines. We added an attempt counter to the card processor."*

**Where it lands:** Chapter 1's choice between a registry of **instances** and a registry of **suppliers**. The new `RetryingCardProcessor` holds state that belongs to *one payment*. Register a single shared instance, and its counter counts *every patient's* attempts: the fourth card payment of the morning is declined though it's that patient's first try.

<Reveal q="Before the code: with the instance registry, which payment is the first to be declined, and why?">

The fourth card payment of the day, whoever makes it. The shared processor's `attempts` field reaches 4 on the fourth call to `process`, regardless of which patient made the first three. The counter's lifetime is the application's; its meaning is one payment's. The fix is to make the lifetimes match — a fresh processor per payment — or to move the counter out of the processor into a per-payment object.

</Reveal>

<HintLadder hints={hints.cardRetries} labels={turn}>

```java group=registry
class RetryingCardProcessor implements PaymentProcessor {     // holds per-payment state: one instance per payment
    private int attempts = 0;
    public PaymentMode mode() { return PaymentMode.CARD; }
    public PaymentResult process(PaymentRequest r) {
        attempts++;
        if (attempts > 3) return new PaymentResult(false, "card-declined-after-3-attempts");
        return PaymentResult.success("card-" + r.amount().paise() + "-attempt-" + attempts);
    }
}

ProcessorSuppliers retryingWiring() {                         // one wiring change: a supplier, not an instance
    return new ProcessorSuppliers(Map.of(
        PaymentMode.UPI,    UpiProcessor::new,
        PaymentMode.CARD,   RetryingCardProcessor::new,
        PaymentMode.WALLET, WalletProcessor::new));
}
```

With the supplier wiring, a hundred patients each pay ₹10 by card and each gets `card-1000-attempt-1`. The checker wires the same class into the *instance* registry for contrast: payments one to three succeed, and the fourth patient gets `card-declined-after-3-attempts`. Retrying one payment through the *same* fresh processor still stops after three, as the bank requires.

</HintLadder>

**Transfer test:** MediCore later wants the attempt count to survive a server restart. Does it still belong in the processor at all — or in a `PaymentAttempt` record that the processor reads and returns?

<h2 id="sq-staging">Side quest 2 · A staging environment</h2>

<h2 id="sq-discounts">Side quest 3 · Per-line discounts</h2>

**The note says:** *"Billing staff need to apply a discount to individual invoice lines — say, 10% off the X-ray for a staff member's family."*

**Where it lands:** Chapter 5's prototype — and the depth of the copy. To support a discount, `LineItem` stops being an immutable record and gains a mutable `discountPercent`. The old copy constructor's `new ArrayList<>(other.items)` now produces a fresh list **of the same, shared, mutable line objects**. Discount the X-ray on one patient's invoice and it's discounted on the template — and on every invoice copied since.

<Reveal q="Which single line of the old copy constructor became wrong, without anyone editing it?">

`this.items = new ArrayList<>(other.items);` It was correct when `LineItem` was immutable — sharing immutable elements is fine — and became a shallow copy the moment `LineItem` gained a setter. **Deep-copy correctness depends on the mutability of everything you share**, so changing a type from immutable to mutable can silently break copy code in another class. That's one more reason to keep value types immutable.

</Reveal>

<HintLadder hints={hints.discounts} labels={turn}>

```java group=discounts
class LineItem {                                     // now MUTABLE: a discount can be set per line
    private final String code;
    private final long paise;
    private int discountPercent;

    LineItem(String code, long paise) {
        this.code = code;
        this.paise = paise;
    }
    LineItem(LineItem other) {                       // the element gets a copy constructor too
        this(other.code, other.paise);
        this.discountPercent = other.discountPercent;
    }

    void discount(int percent) {
        if (percent < 0 || percent > 100) throw new IllegalArgumentException("discount must be 0..100");
        this.discountPercent = percent;
    }
    int discountPercent() { return discountPercent; }
    long netPaise()       { return paise * (100 - discountPercent) / 100; }
}

class InvoiceTemplate {
    private final String header;
    private final List<LineItem> items = new ArrayList<>();

    InvoiceTemplate(String header, List<LineItem> items) {
        this.header = header;
        for (LineItem item : items) this.items.add(new LineItem(item));
    }
    InvoiceTemplate(InvoiceTemplate other) {
        this.header = other.header;
        for (LineItem item : other.items) this.items.add(new LineItem(item));   // copy the list AND every mutable element
    }

    LineItem item(int index) { return items.get(index); }
    long totalPaise() {
        long sum = 0;
        for (LineItem item : items) sum += item.netPaise();
        return sum;
    }
}
```

The checker also copies just the *list* of these mutable lines, discounts through the copy, and shows the original line changing — the bug, reproduced.

</HintLadder>

**Transfer test:** a third option avoids per-element copying entirely: keep `LineItem` immutable and make `discount` *return a new* `LineItem`. What does the template's copy constructor look like then, and which side of "share immutable, copy mutable" does it land on?

<h2 id="sq-stale">Side quest 4 · Stale connections</h2>

**The note says:** *"Every night at 2 a.m. the database restarts for backups. At 8 a.m., the first queries of the day fail on dead connections."*

**Where it lands:** Chapter 7's pool, which currently trusts every idle connection forever. A production pool **validates on borrow** (or in the background) and replaces what's broken — while keeping the bound and never losing a slot.

<Reveal q="If reconnecting fails during borrow — the database is still down — what must the pool NOT do?">

It must not **lose the slot**. If the stale connection is simply dropped and the replacement throws, the pool now owns one fewer object than its size, and after enough failures it owns none — a permanent outage from a temporary one. Put the stale object back (the next borrower will try again) and let the exception reach the caller.

</Reveal>

<HintLadder hints={hints.stale} labels={turn}>

```java group=healthyPool
class PoolExhaustedException extends RuntimeException {
    PoolExhaustedException(Duration waited) { super("nothing free after " + waited.toMillis() + " ms"); }
}

class ValidatingPool<T> {
    private final BlockingQueue<T> idle;
    private final Set<T> lent = ConcurrentHashMap.newKeySet();
    private final Supplier<T> factory;
    private final Predicate<T> healthy;
    final AtomicInteger replaced = new AtomicInteger();

    ValidatingPool(int size, Supplier<T> factory, Predicate<T> healthy) {
        if (size <= 0) throw new IllegalArgumentException("size must be positive");
        this.idle = new ArrayBlockingQueue<>(size);
        this.factory = factory;
        this.healthy = healthy;
        for (int i = 0; i < size; i++) idle.add(factory.get());
    }

    T borrow(Duration timeout) throws InterruptedException {
        T item = idle.poll(timeout.toNanos(), TimeUnit.NANOSECONDS);
        if (item == null) throw new PoolExhaustedException(timeout);
        if (!healthy.test(item)) {                       // stale: replace it, keeping the pool at full size
            T fresh;
            try {
                fresh = factory.get();
            } catch (RuntimeException e) {
                idle.add(item);                          // keep the slot; the next borrower retries
                throw e;
            }
            replaced.incrementAndGet();
            item = fresh;
        }
        lent.add(item);
        return item;
    }

    void giveBack(T item) {
        if (!lent.remove(item)) throw new IllegalArgumentException("not borrowed from this pool, or already returned");
        idle.add(item);
    }

    int idleCount() { return idle.size(); }
}
```

The checker marks two of three connections dead overnight: the next borrows replace them, `replaced` reads 2, and the pool still holds exactly 3. With the factory failing (database still down), the borrow throws, and the pool *still* has all 3 slots. Under 16 threads with random breakage, at most 3 connections are ever in use and every loan comes back. A production pool would also close the stale connection it discards; HikariCP additionally retires connections by age and tests idle ones in the background.

</HintLadder>

**Transfer test:** validating on every borrow costs a round trip per query. What would you trade it for — validating only connections idle longer than 30 seconds, or a background thread — and what failure does each allow?

<Reveal q="1 · Write me a thread-safe Singleton. Now tell me which form you'd actually use.">

Write DCL with `volatile` and both checks, and narrate: check 1 for the fast path, check 2 under the lock because two threads can pass check 1, `volatile` for safe publication of a fully constructed object, private constructor or it's not a singleton. Then: *"In practice I'd use an enum — the JVM's class initialization does the locking, and it's safe against reflection and serialization — or the holder idiom if it must be lazy and a class. In application code I'd rather not have a Singleton class at all: I'd create one instance in the composition root and inject it."*

</Reveal>

<Reveal q="2 · What's the difference between Factory Method and a simple factory?">

A simple factory is one method with a `switch` on runtime data that returns the interface — not a GoF pattern. Factory Method is GoF's: a creator class has an algorithm that calls an abstract creation method, and subclasses decide which class to instantiate — a Template Method whose varying step is a creation, like `Collection.iterator()`. And static factory methods like `List.of` are a third thing; *Effective Java* says outright that they're not the Factory Method pattern.

</Reveal>

<Reveal q="3 · Your builder validates in build(). Why not validate in each setter?">

Single-value rules *do* go in setters (or in the value's own type), so they fail at the bad call. But required-presence and cross-field rules can't be checked in a setter: when `room("R-3")` is called, `teleconsult(true)` may not have been called yet — setter order is the caller's choice. `build()` is the first moment the whole object is visible, so it's the only place those rules can live. For required fields there's a stronger option: put them in the builder's own signature and make omission a compile error.

</Reveal>

<Reveal q="4 · How would you implement a connection pool?">

A bounded `BlockingQueue` filled eagerly by a factory; `borrow` polls with a timeout and throws a named exception when exhausted; `giveBack` checks the object was actually lent (no double returns); a `Lease` implementing `AutoCloseable` so try-with-resources returns the connection on every path. Then the production concerns: validate on borrow and replace broken connections without losing the slot, evict idle ones, cap age, detect leaks. And then: *"In a real system, HikariCP — I'd only write this to show the mechanics."*

</Reveal>

<Reveal q="5 · Deep copy or shallow copy for your invoice template?">

Neither label is precise enough; the rule is **share immutable, copy mutable**. The header string and the immutable line-item records are shared; the list and the tax-field map are fresh, so editing a patient's invoice never touches the template. If line items became mutable (a per-line discount), each element would need copying too. I'd use a copy constructor, not `Cloneable` — `clone()` is shallow, skips constructors, and fights final fields.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Pattern | Do… | The promise to keep |
|---|---|---|---|
| `if`/`switch` picking a class, copied across call sites | Simple factory | One method returning the interface; exhaustive `switch`, no `default` | One place decides |
| Implementations growing, maybe across modules | Registry of instances | `Map<K, T>` built in the constructor from a list, key from `mode()` | Fails at startup on duplicates; named exception on a miss |
| Per-use state in the created object | Registry of suppliers | `Map<K, Supplier<T>>`; verify keys at startup | A fresh object every call |
| Same algorithm, one created object differs | Factory Method | Abstract creation step in a `final` algorithm — or inject a `Supplier` | The algorithm exists once |
| "These N must always match" | Abstract Factory | One suite per variant; consumers take the suite | No parameter list can mix families |
| Many optional fields, cross-field rules | Builder | Private product constructor, final fields, `List.copyOf`, rules in `build()` | Constructed ⇒ valid |
| Required fields easy to forget | Builder with required args | `builder(patientId, doctorId)` | Omission is a compile error |
| "Copy this configured template" | Prototype | Copy constructor; fresh mutable containers and elements | No mutable state shared |
| "Exactly one" | Singleton as a scope | Build once in the root; hand-rolled → enum, then holder, then DCL + `volatile` | One instance, no hidden access |
| Expensive, reusable, limited | Object Pool | Bounded `BlockingQueue`, borrow timeout, checked returns, `Lease` | Every loan comes back |
| `new` / `now()` / `getInstance()` in business logic | Dependency injection | Constructor injection, one composition root, a second root for tests | Dependencies visible in one signature |

The story at a glance:

| Story beat | You hear | Pattern | One-word cue |
|---|---|---|---|
| billing counter | "callers shouldn't know which implementation" | Factory → registry | *reception* |
| doctor-utilisation report | "same algorithm, one object differs" | Factory Method | *hook* |
| sandbox vs live | "these N must never mix across variants" | Abstract factory | *furniture set* |
| appointment form | "6 params, half optional, cross-field rules" | Builder | *stamped form* |
| invoice template | "copy the configured exemplar" | Prototype | *photocopy* |
| 6 p.m. connection pool | "exactly one, shared everywhere" | Singleton (as DI scope) | *one key* |
| lab-results leak | "expensive, limited, reused" | Object Pool | *library loan* |
| fourteen circles | "who calls new?" | DI + composition root | *one room* |

## Five mistakes to leave behind

1. **Patterns before problems.** A factory for one class, a builder for two fields, a Singleton for something `main()` could build once. Name each pattern when its forcing requirement arrives — not at minute twelve.
2. **The catch-all `else`.** A ladder or `default` that swallows new variants turns a compile error into a wrong answer. Exhaustive switches, or registries with a named miss policy.
3. **"Final means immutable."** A final field holding a mutable list is a window into your object. Copy defensively in, and expose unmodifiable views or copies out.
4. **DCL without `volatile`** — and the Singleton class itself. Prefer the enum or holder; in application code prefer one injected instance.
5. **A pool without a guaranteed return.** Borrow in a `Lease`, give back in `close()`, bound every wait. And don't pool what's cheap.

**Further study**

- Gamma, Helm, Johnson and Vlissides, *Design Patterns* (1994) — the creational chapter: Abstract Factory, Builder, Factory Method, Prototype, Singleton, including each pattern's "consequences" (Abstract Factory's cost of new products is listed there).
- Joshua Bloch, *Effective Java* (3rd edition) — Item 1 (static factory methods), Item 2 (builders, with required parameters in the builder's constructor), Item 3 (enforce the singleton property with a private constructor or an enum type), Item 5 (prefer dependency injection to hardwiring resources), Item 6 (avoid unnecessary objects — and when a pool is justified), Item 13 (override `clone` judiciously), Item 83 (lazy initialization, including the double-check idiom).
- Brian Goetz et al., *Java Concurrency in Practice* — Chapter 3 on safe publication and Chapter 16 on the Java Memory Model, where double-checked locking is dissected.
- [The "Double-Checked Locking is Broken" Declaration](https://www.cs.umd.edu/~pugh/java/memoryModel/DoubleCheckedLocking.html) (Bacon, Pugh et al.) — the classic explanation of why DCL failed before Java 5 and how `volatile` fixes it.
- [JLS §12.4.2, Detailed Initialization Procedure](https://docs.oracle.com/javase/specs/jls/se17/html/jls-12.html#jls-12.4.2) — the class-initialization lock that makes the enum and holder idioms thread-safe.
- Martin Fowler, [Inversion of Control Containers and the Dependency Injection pattern](https://martinfowler.com/articles/injection.html) — constructor vs setter injection, and DI vs service locator.
- Mark Seemann, [Composition Root](https://blog.ploeh.dk/2011/07/28/CompositionRoot/) — the one place where the object graph is composed.
- [`BlockingQueue` (Java 17 API)](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/BlockingQueue.html) — `poll` with timeout, `offer`, and the capacity guarantees the pool relies on.
- [HikariCP](https://github.com/brettwooldridge/HikariCP) — a production JDBC pool; its configuration docs explain validation, `maxLifetime` and leak detection.

**Look these up yourself**

- **Staged (step) builders** — builders whose types force required fields in order, turning every "required" check into a compile error, at the cost of one interface per step.
- **`toBuilder()` / "withers"** — copying an immutable object with one field changed; how records and builders make Prototype unnecessary.
- **Safe publication idioms** — final fields, `volatile`, static initializers, concurrent collections: the four ways an object can be shared without a data race (JCIP §3.5).
- **jcstress** — OpenJDK's harness for concurrency tests that *can* show reorderings like DCL-without-volatile, which ordinary unit tests can't.
- **Service Locator vs Dependency Injection** — why a global registry of services reintroduces the Singleton's hidden dependencies.
- **Spring bean scopes** (`singleton`, `prototype`, `request`, `session`) and **`ObjectProvider`** — lifetimes as configuration, and injecting a factory for fresh instances.
- **Serialization proxies and `readResolve`** — how class-based singletons defend against deserialization creating a second instance (the enum gets this for free).
- **Little's Law for pool sizing** — connections needed ≈ request rate × time each request holds a connection.
