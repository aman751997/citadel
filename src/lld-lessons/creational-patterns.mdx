## The story that carries this module

You're building **MediCore** — a clinic management platform. One story runs through all three pattern lessons: this one *creates* MediCore's objects, the structural lesson *connects* MediCore to the outside world, the behavioral lesson *runs* the clinic day to day. Every pattern arrives when the story forces it — never before. (This mirrors the real thing: the [War Room dossiers](/citadel/lld/war/patterns-why/) come from an actual production hospital platform, so every pattern here has a "this actually happened" link.)

Creational patterns all answer one question: **`new` hard-codes a concrete class at the call site — what do you do when the call site shouldn't know it?** Shouldn't know *which* class (factory), shouldn't wrestle with *how* to assemble it (builder), shouldn't create it *at all* because exactly one must exist (singleton).

## Factory Method — the billing counter

**Story beat.** MediCore's billing counter takes UPI, card, and wallet. Your first version: every place that charges a patient does `new UpiProcessor()` or `new CardProcessor()` based on an `if`. The same if-ladder now lives in the counter code, the online-portal code, and the refund code. Adding EMI means hunting all three down.

**Fix.** Move the decision to one place that returns the *interface*:

<Mermaid code={`flowchart LR
    C[Counter] --> F{{ProcessorFactory}}
    P[Portal] --> F
    R[Refunds] --> F
    F -->|returns interface| I[PaymentProcessor]
    I -.-> U[UpiProcessor]
    I -.-> CA[CardProcessor]
    I -.-> W[WalletProcessor]
    style F stroke:#e3b341,stroke-width:2px`} />

```java
enum PaymentMode { UPI, CARD, WALLET }

interface PaymentProcessor { PaymentResult process(PaymentRequest r); }

class UpiProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("upi-" + r.amount().paise());
    }
}
class CardProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("card-" + r.amount().paise());
    }
}
class WalletProcessor implements PaymentProcessor {
    public PaymentResult process(PaymentRequest r) {
        return PaymentResult.success("wallet-" + r.amount().paise());
    }
}

class ProcessorFactory {
    PaymentProcessor forMode(PaymentMode mode) {
        return switch (mode) {
            case UPI    -> new UpiProcessor();
            case CARD   -> new CardProcessor();
            case WALLET -> new WalletProcessor();
        };  // exhaustive switch over enum: compiler yells when a new mode is added. That's a feature.
    }
}

// The counter, the portal, and refunds all just say:
PaymentProcessor p = factory.forMode(request.mode());
PaymentResult result = p.process(request);
```

**"Isn't that switch an OCP violation?"** — the follow-up you should invite. Technically yes; honestly graded, no: the variation is *contained in one class whose single job is choosing*, and an exhaustive enum switch even gets compiler help. The upgrade, when the switch outgrows a screen or implementations live in different modules, is the **registry** — implementations announce their own key, the switch disappears:

```java
interface PaymentProcessor {
    PaymentMode mode();                              // each impl declares its OWN key
    PaymentResult process(PaymentRequest r);
}

class ProcessorRegistry {
    private final Map<PaymentMode, PaymentProcessor> byMode;

    ProcessorRegistry(List<PaymentProcessor> processors) {
        this.byMode = processors.stream()
            .collect(Collectors.toUnmodifiableMap(PaymentProcessor::mode, p -> p));
        // toUnmodifiableMap throws on duplicate keys — two impls claiming UPI fails at STARTUP, not mid-payment
    }

    PaymentProcessor forMode(PaymentMode mode) {
        PaymentProcessor p = byMode.get(mode);
        if (p == null) throw new UnsupportedModeException(mode);  // the map is not exhaustive — name the miss policy
        return p;
    }
}

// Wiring — the ONLY place that lists implementations (Spring injects this list automatically):
ProcessorRegistry registry = new ProcessorRegistry(List.of(
    new UpiProcessor(), new CardProcessor(), new WalletProcessor()));
```

The knowledge "UPI → UpiProcessor" moved *into UpiProcessor itself*. New mode = new class + one wiring entry, zero edits to the registry. You traded compile-time exhaustiveness for runtime flexibility — say that trade out loud. Production's version: [the Registry dossier](/citadel/lld/war/patterns-why/#2-registry--the-inbound-webhook-routing-problem), webhook handlers announcing their provider key.

**Static factory methods** (the small sibling, worth dropping in passing): `Money.rupees(10)`, `Duration.ofMinutes(5)` — named constructors that validate, cache, or return subtypes. *Effective Java* item 1; free polish.

> 🧠 **Memory hook.** *The hospital reception desk:* you say what you need, reception decides which department — you never walk the corridors yourself.
> **Cheat code:** callers naming concrete classes → factory. Choice logic duplicating → registry.
> **Interview line:** *"I'll centralize creation behind a factory returning the interface; if implementations multiply, I'll flip it to a registry where each one announces its key."*

## Abstract Factory — sandbox vs live money

**Story beat.** MediCore has a test mode. The payment gateway, the refund client, and the webhook signature verifier each have a **sandbox** and a **live** version. One evening someone wires the live gateway with the sandbox verifier — real charges, signatures never verified. The bug wasn't one wrong object; it was a **mixed family**.

**Fix.** Make the *family* the unit of construction — one factory interface, one implementation per environment:

<Mermaid code={`flowchart TB
    W[Wiring picks ONE suite] --> S
    W --> L
    subgraph S [SandboxSuite]
      SG[SandboxGateway] ~~~ SR[SandboxRefunds] ~~~ SV[SandboxVerifier]
    end
    subgraph L [LiveSuite]
      LG[RazorpayGateway] ~~~ LR[RazorpayRefunds] ~~~ LV[RazorpayVerifier]
    end
    S -. members can never mix .-> L
    style S stroke:#3fb950
    style L stroke:#f85149`} />

```java
interface GatewaySuite {           // the family contract
    PaymentGateway gateway();
    RefundClient refunds();
    WebhookVerifier verifier();
}

class SandboxSuite implements GatewaySuite {
    private final SandboxConfig cfg;
    SandboxSuite(SandboxConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new SandboxGateway(cfg.baseUrl()); }
    public RefundClient refunds()     { return new SandboxRefundClient(cfg.baseUrl()); }
    public WebhookVerifier verifier() { return new SandboxVerifier(cfg.testSecret()); }
}

class LiveSuite implements GatewaySuite {
    private final LiveConfig cfg;
    LiveSuite(LiveConfig cfg) { this.cfg = cfg; }
    public PaymentGateway gateway()   { return new RazorpayGateway(cfg.apiKey()); }
    public RefundClient refunds()     { return new RazorpayRefundClient(cfg.apiKey()); }
    public WebhookVerifier verifier() { return new RazorpayVerifier(cfg.webhookSecret()); }
}

// Wiring picks ONE suite; mixing members across environments now has no code path:
GatewaySuite suite = env.isProd() ? new LiveSuite(liveCfg) : new SandboxSuite(sandboxCfg);
BillingService billing = new BillingService(suite.gateway(), suite.verifier());
```

Recognition cue: the word **"family"**, or "these three must always match". No family — just one product? Plain factory method; don't upgrade for ceremony.

> 🧠 **Memory hook.** *A furniture set:* buy the sofa, table, and chairs as one matching set — you can't accidentally pair a Victorian sofa with a modern table because you never pick pieces, you pick the set.
> **Cheat code:** "these N objects must never mix across variants" → abstract factory.
> **Interview line:** *"The consistency rule spans several objects, so I'll make the family the unit of construction — you hold one suite, cross-environment mixing becomes unrepresentable."*

## Builder — the appointment form

**Story beat.** Booking an appointment at MediCore needs patient, doctor, and slot — plus maybe teleconsult flag, maybe room, maybe referral note, maybe insurance id. The constructor grows to eight parameters: `new Booking(patientId, doctorId, slot, null, null, true, false, null)`. Nobody can read which `null` means what; two booleans transpose silently; every new optional field breaks all callers.

**Fix — the full hand-rolled shape** (rounds ask you to *write* this, not just call it):

```java
class Booking {
    // all final — a built Booking is immutable
    private final String patientId;      // required
    private final String doctorId;       // required
    private final Slot slot;             // required
    private final boolean teleconsult;   // optional, default false
    private final String roomId;         // optional

    private Booking(Builder b) {         // private: the ONLY way in is build()
        this.patientId  = b.patientId;
        this.doctorId   = b.doctorId;
        this.slot       = b.slot;
        this.teleconsult = b.teleconsult;
        this.roomId     = b.roomId;
    }

    static Builder builder() { return new Builder(); }

    static class Builder {
        private String patientId;
        private String doctorId;
        private Slot slot;
        private boolean teleconsult = false;   // defaults live here
        private String roomId;

        Builder patient(String id)      { this.patientId = id; return this; }   // return this = chaining
        Builder doctor(String id)       { this.doctorId = id; return this; }
        Builder slot(Slot s)            { this.slot = s; return this; }
        Builder teleconsult(boolean t)  { this.teleconsult = t; return this; }
        Builder room(String roomId)     { this.roomId = roomId; return this; }

        Booking build() {
            // 1. required fields present
            if (patientId == null || doctorId == null || slot == null)
                throw new IllegalStateException("patient, doctor, slot are required");
            // 2. CROSS-FIELD invariants — the whole point of build()
            if (teleconsult && roomId != null)
                throw new IllegalStateException("teleconsult bookings cannot have a room");
            if (!teleconsult && roomId == null)
                throw new IllegalStateException("in-person bookings need a room");
            return new Booking(this);
        }
    }
}

// Usage reads like the requirements doc:
Booking booking = Booking.builder()
    .patient("P-1042")
    .doctor("D-07")
    .slot(slot)
    .teleconsult(true)
    .build();
```

The mechanics to narrate while writing it: **builder fields are mutable, the product's are final** — mutation is quarantined inside the builder and ends at `build()`; the product's constructor is **private** so a half-configured Booking has no way to exist; setters `return this` for chaining; defaults live in the builder's field initializers.

The part that separates a gold answer from a Lombok reflex: **`build()` is where cross-field invariants live** (teleconsult excludes room; slot within doctor's schedule). A builder that just sets fields is syntax; a builder whose `build()` can refuse is an invariant gate — it restores the "constructed ⇒ valid" guarantee from the object-modeling lesson.

When asked "when builder over factory?": factory chooses **which class**, builder assembles **one complex object step-by-step**. Different questions; they compose (a factory can return builders).

> 🧠 **Memory hook.** *The clinic's paper intake form:* fill fields in any order, skip the optional ones — but the receptionist checks the form is complete and consistent **before** stamping it. `build()` is the stamp.
> **Cheat code:** constructor past ~4 params, half optional → builder. Cross-field rules → they live in `build()`.
> **Interview line:** *"Required fields checked in build(), cross-field invariants too — so a Booking that exists is valid by construction."*

## Singleton — one connection pool for the whole clinic

**Story beat.** MediCore opens one database connection pool. Someone constructs a second one inside a report job; connections double, the DB hits its limit at 6 pm. You need **exactly one instance, enforced** — not requested politely.

**The Java answers, in interview-ranking order:**

```java
// 1. Enum — serialization-safe, reflection-safe, lazy, one line. Effective Java's answer.
enum MetricsRegistry { INSTANCE; void record(String k, long v) { ... } }

// 2. Holder idiom — lazy without locks: class-loading is thread-safe by JLS guarantee.
class Config {
    private Config() {}
    private static class Holder { static final Config I = new Config(); }
    static Config get() { return Holder.I; }
}

// 3. Double-checked locking — the classic exam answer. volatile is NOT optional:
class Pool {
    private static volatile Pool instance;
    private Pool() {}
    static Pool get() {
        if (instance == null) {
            synchronized (Pool.class) {
                if (instance == null) instance = new Pool();
            }
        }
        return instance;
    }
}
/**
1. volatile: always read latest state of object
2. private constructor required, w/o it any class in same package can call the constructor
3. double check: two threads can pass check 1 before either locks, they enter synchronized block one at a time,
without re-check second thread constructs a second Pool object.
*/
```

<Reveal q="Cover the comment block above. Why exactly is volatile load-bearing — what can a second thread observe without it?">

`instance = new Pool()` is three steps — allocate, run constructor, write reference — and the JMM may reorder to allocate → **write reference** → construct. A second thread sees non-null at check 1, skips the lock, and returns a Pool whose constructor **hasn't finished** — it reads garbage fields. `volatile` forbids that reordering. And without the private constructor there is no singleton at all — anything in the package can `new Pool()` around the ceremony.

</Reveal>

Then the sentence that shows senior judgment: **in real systems, singletons are a scope, not a pattern** — the DI container (or your `main()`) constructs one instance and injects it everywhere. Same one-ness, none of the global-state damage: tests can substitute it, hidden dependencies disappear. The [War Room inventory](/citadel/lld/war/inventory/) grades it exactly this way — Spring supplies singleton scope for free, so hand-rolling one in a Spring codebase is a smell, not a skill.

Related production variant worth knowing: the [copy-on-write registry](/citadel/lld/war/patterns-why/#15-copy-on-write-registry--two-maps-that-must-swap-together) — a singleton whose *contents* must swap atomically: rebuild into new maps, swap references in one assignment.

> 🧠 **Memory hook.** *One head pharmacist holds the narcotics-cabinet key.* Not "we agreed to share nicely" — there is physically one key (private constructor), and one official way to ask for it (`get()`).
> **Cheat code:** "exactly one, shared everywhere" → DI scope first, enum if hand-rolled, DCL only to prove you know the JMM.
> **Interview line:** *"I'd let the composition root own the single instance and inject it; if you want the classic, here's DCL — and here's why volatile is load-bearing."*

## Prototype — the invoice template

**Story beat.** Every MediCore invoice starts from the clinic's standard template — header, GST fields, default line items — then gets customized per patient. Rebuilding the template from scratch each time re-runs config lookups; you want to **copy the exemplar**.

```java
class InvoiceTemplate {
    private final String header;
    private final List<LineItem> defaultItems;

    InvoiceTemplate(InvoiceTemplate other) {              // copy constructor = Prototype in Java
        this.header = other.header;
        this.defaultItems = new ArrayList<>(other.defaultItems);  // DEEP-copy mutable fields —
    }                                                             // shallow copy shares the list,
}                                                                 // and edits bleed between "copies"

InvoiceTemplate patientInvoice = new InvoiceTemplate(standardTemplate);  // clone, then customize
```

Prefer **copy constructors or `toBuilder()`** over `Cloneable` (broken by design: no constructor call, shallow by default, checked exception). The one graded detail: **deep vs shallow** — copy mutable fields into fresh collections, or both objects silently share state.

> 🧠 **Memory hook.** *Photocopying a pre-filled form* instead of writing the letterhead again — but staple your own attachments (deep copy), don't share the original's.
> **Cheat code:** "copy this configured template" → copy constructor. Mutable field → fresh collection.

<Reveal q="Delete the 'new ArrayList<>(...)' wrapper and copy the list reference directly. What bug ships?">

Both "copies" now share **one** `List` object. Customize the patient's invoice — add a line item — and the standard template silently grows that line too; every future invoice inherits it. Nothing crashes, no exception: the corruption just accumulates. That's why the graded phrase is **deep-copy every mutable field**; immutable fields (`String header`) are safe to share, which is also the argument for making fields immutable in the first place.

</Reveal>
