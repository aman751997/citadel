<h2 id="prologue">Prologue · What changes next?</h2>

<Scene chapter="Prologue" title="The first review" mood="dawn">

On your first Monday at the Gearhouse, Wren prints your pull request. Nobody prints code any more. She does it anyway, and reads it with a green pen.

Your code works. You know it works: on the test bench, the Copperline Garage's ticket machine has issued four hundred tickets this morning without a single complaint. You wait for praise.

Wren writes one line at the top of page one and hands it back.

*What changes next?*

"Nothing," you say. "It's done."

From across the room, Oona laughs without looking up. On the whiteboard behind her, someone has written *Bram — Tuesday* and drawn a small, ominous clock.

</Scene>

Code that works today is the easy half. **Machine-coding rounds, and real jobs, grade the second half: what happens to your design when the requirement changes.** SOLID is five answers to that one question, each named after the mess you get without it:

| Letter | The question Wren asks | The mess without it |
|---|---|---|
| **S** — single responsibility | Who will ask this class to change? | Four teams editing one file; every change risks three others |
| **O** — open/closed | When the next variant arrives, do you add a class or edit one? | An `if/else` ladder that every new feature reopens |
| **L** — Liskov substitution | Can every implementation keep every promise the type makes? | Subclasses that throw, return nonsense, or need `instanceof` |
| **I** — interface segregation | Does each client see only what it calls? | Fourteen-method interfaces and fakes bigger than the test |
| **D** — dependency inversion | Do your business rules point at seams, or at vendors? | Tests that need a network, a credit card, or a particular time of day |

A little history keeps you honest in follow-ups: the principles were collected by Robert C. Martin around 2000, the open/closed principle goes back to Bertrand Meyer (1988), Liskov's to Barbara Liskov's 1987 keynote, and the acronym came later (Michael Feathers is usually credited).

**How to use SOLID in an interview: never recite it. Violate, notice, fix — out loud.** When your first-draft class collects a second reason to change, say *"this is drifting toward two responsibilities, let me split it"* and do it live. Interviewers grade the detection reflex far above the definition. That is how every chapter below is built: **the mess → the detection cue → the refactor → the pattern that industrialises it → when not to bother**.

One warning before we start, because it is the failure mode of people who *have* learned SOLID: **over-engineering loses machine-coding rounds too.** Seven interfaces with one implementation each, a factory for a class constructed once, a hierarchy "for the future" — graders mark those down as surely as a God class. Every chapter ends with *when not to apply it*. Read those sections twice.

<h2 id="one-reason">Chapter 1 · Four teams, one file</h2>

<Scene chapter="Chapter 1" title="Four teams, one file">

Three tickets land against `ShiftReport.java` in the same week.

Finance wants refunded tickets left out of the revenue total. Bram wants the total printed at the *top* of the email, "where I can see it without my glasses". And the Gearhouse's IT lead is moving the garage to a new mail server.

Three engineers open the same file. Two merge conflicts later, the report emails Bram a total that includes refunds, in the old layout, through the new server. Oona's test file for the class is 900 lines long and starts an in-memory database and a fake mail server just to check an addition.

Wren draws three stick figures on the whiteboard and an arrow from each to the same box.

*"Count the people who can ask this class to change,"* she says. *"Then tell me how many classes you need."*

</Scene>

**The mess.** One class loads the shift's tickets, adds up revenue, lays out the text and sends the email:

```java fragment
class ShiftReport {
    private final DataSource db;          // used only by load()
    private final String smtpHost;        // used only by send()
    private final int smtpPort;           // used only by send()

    void run(LocalDate day) {
        List<Ticket> tickets = load(day);                                  // the database owner's schema
        long total = 0;
        for (Ticket t : tickets) total += t.fee();                         // finance's arithmetic
        String body = "Shift report " + day + "\n" + /* ...layout... */;   // Bram's taste
        send("bram@copperline.example", body);                             // IT's mail server
    }
    private List<Ticket> load(LocalDate day) { /* JDBC */ }
    private void send(String to, String body) { /* SMTP */ }
}
```

**The detection cues.**

1. **Describe the class in one sentence.** If the sentence needs "and" — *loads AND totals AND formats AND sends* — it has several reasons to change.
2. **Fields cluster.** `db` is used only by `load`; `smtpHost` and `smtpPort` only by `send`. Two groups of fields used by two groups of methods are two classes sharing a body.
3. **Name the people.** Robert Martin's sharper wording of the principle is that a module should be responsible to **one actor** — one person or group who asks for its changes. Finance, Bram, IT and whoever owns the database schema are four actors.
4. **The test is hard to write.** To check one addition you must stand up a database and a mail server. A test that needs the whole world is testing a class that touches the whole world.

**The refactor.** Split along the *reasons to change* — not along "big class, so make smaller classes":

```java group=report
import java.time.*;

record Ticket(String id, long fee) {}

interface TicketLog {                       // changes when storage changes (the database owner)
    List<Ticket> closedOn(LocalDate day);
}

interface Mailer {                          // changes when delivery changes (IT)
    void send(String to, String subject, String body);
}

class RevenueTotals {                       // changes when finance changes the arithmetic
    long total(List<Ticket> tickets) {
        long sum = 0;
        for (Ticket t : tickets) sum += t.fee();
        return sum;
    }
}

class ReportFormatter {                     // changes when Bram changes his mind about layout
    String format(LocalDate day, List<Ticket> tickets, long total) {
        StringBuilder out = new StringBuilder("Shift report " + day + "\n");
        for (Ticket t : tickets) out.append(t.id()).append("  ").append(t.fee()).append('\n');
        return out.append("Tickets: ").append(tickets.size()).append("  Revenue: ").append(total).toString();
    }
}

class ShiftReportFlow {                     // changes only when the sequence of steps changes
    private final TicketLog log;
    private final RevenueTotals totals;
    private final ReportFormatter formatter;
    private final Mailer mailer;

    ShiftReportFlow(TicketLog log, RevenueTotals totals, ReportFormatter formatter, Mailer mailer) {
        this.log = log;
        this.totals = totals;
        this.formatter = formatter;
        this.mailer = mailer;
    }

    void send(LocalDate day, String to) {
        List<Ticket> tickets = log.closedOn(day);
        String body = formatter.format(day, tickets, totals.total(tickets));
        mailer.send(to, "Shift report " + day, body);
    }
}
```

Now finance's change touches `RevenueTotals` and nothing else; Bram's touches `ReportFormatter`; IT's touches whatever implements `Mailer`; a schema change touches whatever implements `TicketLog`. The three tickets can no longer collide, and the arithmetic test is three lines with no database.

**The orchestrator is allowed to exist.** `ShiftReportFlow` calls four collaborators, and that is fine: its one responsibility *is* the sequence. SRP doesn't ban coordinators; it bans classes that both coordinate *and* decide everything themselves. The tell for a coordinator gone bad is business logic creeping into it — an `if (ticket.refunded())` inside `send` would mean finance can ask `ShiftReportFlow` to change again.

**Why do `TicketLog` and `Mailer` get interfaces when `RevenueTotals` and `ReportFormatter` don't?** The first two touch the outside world (a database, a mail server), so tests need to replace them — that is Chapter 6's reason. The other two are pure computation with one implementation each. **Give a class an interface when something needs to stand in for it, not by reflex.**

<Trace title="Count the actors" steps={srp} takeaway="One actor per class. A coordinator's one job is the sequence; the moment it starts deciding, it has a second reason to change." />

**The pattern that industrialises it.** Extracted services, each owned by one actor, with a thin **Facade**-style coordinator in front (the <a href={`${BASE}lld/lessons/structural-patterns/`}>structural patterns lesson</a> makes this exact point: a facade *coordinates, never decides*). At architecture scale, the same idea becomes layers and bounded contexts.

**When not to apply it.** A forty-line class that one actor owns does not need splitting, even if its description has an "and" in it. Watch for these over-corrections:

- **Class confetti.** `TicketLoader`, `TicketLoaderImpl`, `TicketLoaderFactory` for one SQL query. SRP is about *reasons to change*, not about counting methods.
- **Stripping entities bare.** A `ParkingTicket` that opens, closes and validates its own times has one actor — the garage's ticket rules. Moving that logic into a `TicketService` leaves an anemic data bag and scatters the rules (the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson</a> grades that as a failure).
- **Splitting things that always change together.** If two classes are always edited in the same commit, you have created coupling, not cohesion (Chapter 7).

<Reveal q="Bram also wants the report sent by SMS on Sundays. Which classes change?">

Only the composition — the place that builds `ShiftReportFlow` — gets a second `Mailer`-like delivery (or the flow takes a list of deliveries). `RevenueTotals` and `ReportFormatter` are untouched because neither knows how the text leaves the building. If delivery choice becomes real logic ("SMS on Sundays, email otherwise"), that rule deserves its own small class; it is a new reason to change.

</Reveal>

**Your turn.** Oona hands you `ParkingTicket.java`. It records entry, closes on exit (refusing to close twice or before it opened), renders itself as a receipt string, and saves itself to the database with JDBC. Split it — and decide what *stays*.

<HintLadder hints={hints.srp} labels={turn}>

```java group=ticket
import java.time.*;

class ParkingTicket {                            // one actor: the garage's ticket rules
    private final String id;
    private final LocalDateTime entry;
    private LocalDateTime exit;                  // null while the car is inside

    ParkingTicket(String id, LocalDateTime entry) {
        this.id = id;
        this.entry = entry;
    }

    void close(LocalDateTime at) {
        if (exit != null) throw new IllegalStateException("ticket " + id + " is already closed");
        if (at.isBefore(entry)) throw new IllegalArgumentException("exit before entry");
        exit = at;
    }

    boolean isOpen() { return exit == null; }
    String id() { return id; }
    LocalDateTime entry() { return entry; }
    Optional<LocalDateTime> exit() { return Optional.ofNullable(exit); }
}

class ReceiptRenderer {                          // one actor: whoever designs receipts
    String render(ParkingTicket t, long fee) {
        String out = t.exit().map(LocalDateTime::toString).orElse("still parked");
        return "Copperline Garage\nTicket " + t.id() + "\nIn  " + t.entry() + "\nOut " + out + "\nFee " + fee;
    }
}

interface TicketRepository {                     // one actor: whoever runs storage
    void save(ParkingTicket t);
    Optional<ParkingTicket> find(String id);
}

class InMemoryTickets implements TicketRepository {
    private final Map<String, ParkingTicket> byId = new HashMap<>();
    public void save(ParkingTicket t) { byId.put(t.id(), t); }
    public Optional<ParkingTicket> find(String id) { return Optional.ofNullable(byId.get(id)); }
}
```

The ticket **keeps** `close` and its two guards: those are its invariants, and they change only when the garage's rules change. Rendering and storage leave. The in-memory repository is what you'd write in a 90-minute round; the JDBC one would be a second implementation of the same interface.

</HintLadder>

**Catch the trap:** *"SRP means a class should do one thing."* That reading produces confetti. The principle is **one reason to change** — one actor. `ParkingTicket` does several things (open, close, validate, report its state) for one actor, and that is exactly right.

**Say it aloud:** *"This class is starting to change for two reasons — the fee rules and the receipt layout. I'll pull the layout out now; it's two minutes and it keeps the fee tests free of string formatting."*

<h2 id="extend-dont-edit">Chapter 2 · Bram's Tuesday</h2>

<Scene chapter="Chapter 2" title="Bram's Tuesday" mood="dusk">

Bram arrives on Tuesday at ten past nine, as he always does, with a paper cup of coffee and a small change.

"Electric cars," he says. "They pay the hourly rate like everyone else, plus fifty for the charging. Easy, yes?"

It is easy. You add an `else if` to `fee()`. The next Tuesday it's trucks. The Tuesday after, it's a discount for the night shift at the hospital next door. By the fourth Tuesday, `fee()` is sixty lines long, and Oona's sticky note says: *bikes are being charged as cars since Thursday*. Someone had added a branch above the bike check.

Wren reads the method twice. *"You've edited this four times. Every edit re-opened code that already worked."* She taps the screen. *"What changes next — and can it arrive without touching this method at all?"*

</Scene>

**The mess.** A ladder over the vehicle type. It compiles, it works, and every new variant edits it:

```java id=feeMess
enum VehicleType { BIKE, CAR, EV }

long fee(VehicleType type, long minutes) {
    long startedHours = (minutes + 59) / 60;          // every started hour is billed
    if (type == VehicleType.BIKE) return startedHours * 10;
    else if (type == VehicleType.CAR) return startedHours * 20;
    else if (type == VehicleType.EV) return startedHours * 20 + 50;
    throw new IllegalArgumentException("no tariff for " + type);
}
```

**The detection cue is the follow-up question.** Machine-coding rounds are *designed* around one: "now add surge pricing", "now add trucks". If the follow-up lands as **a new class**, the design passed its only exam. If it lands as new branches in five methods, it failed. In code you already have, the cue is a `switch` or `if` ladder on a type code — especially the *same* ladder repeated in several places (fee, receipt label, allowed spot size…), each of which every new type must find and edit.

**The refactor.** Each branch becomes a class behind one interface; a map picks the class. We'll keep building on this code for the rest of the lesson, so it also gets a proper `ParkingSession` that refuses to exist with its times backwards:

```java group=garage
import java.time.*;

enum VehicleType { BIKE, CAR, EV }

record ParkingSession(VehicleType type, LocalDateTime entry, LocalDateTime exit) {
    ParkingSession {                                   // invariant: no time travel
        if (exit.isBefore(entry)) throw new IllegalArgumentException("exit before entry");
    }
    long minutes() { return Duration.between(entry, exit).toMinutes(); }
    long startedHours() { return (minutes() + 59) / 60; }
}

interface FeeStrategy {
    /** Accepts every valid session. Never negative. Staying longer never costs less. */
    long fee(ParkingSession s);
}

class HourlyFee implements FeeStrategy {
    private final long perHour;
    HourlyFee(long perHour) { this.perHour = perHour; }
    public long fee(ParkingSession s) { return s.startedHours() * perHour; }
}

class HourlyPlusChargingFee implements FeeStrategy {
    private final long perHour, chargingFlat;
    HourlyPlusChargingFee(long perHour, long chargingFlat) {
        this.perHour = perHour;
        this.chargingFlat = chargingFlat;
    }
    public long fee(ParkingSession s) { return s.startedHours() * perHour + chargingFlat; }
}

class FeeCalculator {
    private final Map<VehicleType, FeeStrategy> strategies;
    FeeCalculator(Map<VehicleType, FeeStrategy> strategies) { this.strategies = Map.copyOf(strategies); }

    long fee(ParkingSession s) {
        FeeStrategy strategy = strategies.get(s.type());
        if (strategy == null) throw new IllegalArgumentException("no tariff for " + s.type());
        return strategy.fee(s);
    }
}

// The composition root (it lives in Main): the one place that knows which class serves which type.
FeeCalculator standardTariff() {
    return new FeeCalculator(Map.of(
        VehicleType.BIKE, new HourlyFee(10),
        VehicleType.CAR,  new HourlyFee(20),
        VehicleType.EV,   new HourlyPlusChargingFee(20, 50)));
}
```

Three details are worth saying out loud. **Bike and car share one class** — they differ in data (the rate), not behaviour, so a `BikeFee` and a `CarFee` class would be ceremony. **`Map.copyOf`** makes the calculator's table immutable once built. **A missing tariff fails loudly** instead of silently charging zero. Money is a `long` of whole rupees — never a `double`, which cannot represent most decimal fractions exactly.

A refactor must not change behaviour. The checker for this page runs the ladder and the strategy map side by side for every vehicle type and every stay from 0 minutes to 3 days, and they agree on every fee.

**What OCP actually promises.** *Open for extension, closed for modification* does not mean no line anywhere ever changes. Adding a variant still edits the **composition root** — one wiring line — and maybe adds an enum constant. What stays closed is **behaviour that already works and is already tested**: `FeeCalculator`, `HourlyFee`, every other strategy. Those don't reopen, so they can't regress.

<Reveal q="Bram wants trucks at 40 an hour. With the strategy map, exactly what changes?">

One enum constant (`TRUCK`) and one wiring line: `VehicleType.TRUCK, new HourlyFee(40)`. **No new class at all** — trucks differ from cars only in data. Nothing in `FeeCalculator` or any strategy is edited. Compare the ladder: a new branch inside a method that already works, plus every other ladder on the type code that you have to remember to find.

</Reveal>

<Trace title="The follow-up question" steps={ocp} takeaway="Close the axis the interviewer signalled. A new variant should cost a new class (or just a new wiring line) — and nothing that already works should reopen." />

**The pattern that industrialises it.** **Strategy**, usually with a small registry (the map), which the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> builds properly. **Decorator** extends behaviour by wrapping (Side quest 1 adds weekend surge that way). **Chain of Responsibility** extends a pipeline by inserting a link. The War Room has the production version: <a href={`${BASE}lld/war/patterns-why/#1-strategy--five-payment-gateways`}>five payment gateways behind one Strategy seam</a>, everything else concrete — and <a href={`${BASE}lld/war/build-drills/#drill-2--strategy--registry-with-a-real-signature-problem`}>Drill 2</a> makes you build it.

**When not to apply it — the honesty clause.** OCP applies to the axis of change you **expect**. Making everything pluggable is *speculative generality*, a worse disease than the ladder. Martin himself wrote that no significant program can be closed against every change; closure has to be **strategic**. So: close the axis the interviewer signalled (pricing, in a parking lot), hard-code the rest, and say so. Two more honest calls:

- **An enum with an abstract method** is a fine Strategy for two or three small, fixed variants with no dependencies. It stops being fine when variants need injected configuration or clients (the War Room Strategy dossier's follow-up makes exactly this point).
- **One `switch` is not a crime.** A single switch in a factory or composition root that builds the right object is the normal place for the type code to live. The smell is the *repeated* ladder in behaviour code.

**Your turn.** Bram's Tuesday card: *"Bikes are free if they leave within 30 minutes. Otherwise, the normal hourly rate from the start."* Land it without editing any existing class.

<HintLadder hints={hints.ocp} labels={turn}>

```java group=garage
class GraceThenHourlyFee implements FeeStrategy {
    private final long graceMinutes, perHour;
    GraceThenHourlyFee(long graceMinutes, long perHour) {
        this.graceMinutes = graceMinutes;
        this.perHour = perHour;
    }
    public long fee(ParkingSession s) {
        return s.minutes() <= graceMinutes ? 0 : s.startedHours() * perHour;
    }
}

FeeCalculator tariffWithBikeGrace() {        // the only other change: one wiring line
    return new FeeCalculator(Map.of(
        VehicleType.BIKE, new GraceThenHourlyFee(30, 10),
        VehicleType.CAR,  new HourlyFee(20),
        VehicleType.EV,   new HourlyPlusChargingFee(20, 50)));
}
```

A 30-minute bike stay costs 0; 31 minutes costs 10 (one started hour); 61 minutes costs 20. `FeeCalculator`, `HourlyFee` and the EV strategy were not opened.

</HintLadder>

**Catch the trap:** *"OCP means you never edit existing code."* Bug fixes edit code. Wiring edits code. A requirement that changes what an existing rule *means* edits that rule. OCP is narrower and more useful: **adding a variant on the expected axis should not require modifying working behaviour.**

**Say it aloud:** *"Pricing is clearly going to vary, so I'll put it behind a FeeStrategy interface now — bike and car share one class with different rates. Spot allocation I'll keep concrete until you tell me it varies."*

<h2 id="substitutable">Chapter 3 · The square that lied</h2>

<Scene chapter="Chapter 3" title="The square that lied" mood="night">

The Gearhouse is building a floor-plan editor for Copperline's new level. Car bays are rectangles. Motorbike bays are square, so someone wrote `Square extends Rectangle` — a square *is* a rectangle; everyone learned that in school.

Oona's sticky note arrives at 6 p.m.: *"Stretch-all-bays to 5 × 4 m. Car bays: 20 m². Bike bays: 16 m². The paint crew used the printout."*

You open the code. Nothing throws. Nothing is null. Every method does exactly what its name says.

Wren pulls up a chair. *"Is a square a rectangle?"*

"Mathematically, yes."

*"I didn't ask about mathematics. I asked about this code."*

</Scene>

**The mess.** It compiles, it runs, and it is wrong:

```java id=rectMess
class Rectangle {
    protected int width, height;
    void setWidth(int w)  { width = w; }
    void setHeight(int h) { height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {               // "a square is a rectangle"
    @Override void setWidth(int w)  { width = w; height = w; }
    @Override void setHeight(int h) { width = h; height = h; }
}

int stretch(Rectangle r) {                     // a perfectly reasonable caller
    r.setWidth(5);
    r.setHeight(4);
    return r.area();                           // the caller expects 20
}
```

`stretch(new Rectangle())` returns 20. `stretch(new Square())` returns **16**: `setHeight(4)` quietly changed the width too. The checker for this page runs both and confirms the numbers.

**Liskov's rule.** If `S` is a subtype of `T`, then any code written against `T` must keep working when handed an `S`. "Working" means **behaviour**, not compilation. Barbara Liskov and Jeannette Wing made it precise in 1994 as *behavioural subtyping*, and it reduces to four rules about the promises a type makes:

| Promise | What a subtype may do | Square vs Rectangle |
|---|---|---|
| **Preconditions** — what callers must supply | Keep them or **weaken** them (accept more). Never demand more. | — |
| **Postconditions** — what the method guarantees afterwards | Keep them or **strengthen** them (promise more). Never deliver less. | `setWidth(w)` promised *width = w and height unchanged*. Square breaks the second half. |
| **Invariants** — what is always true of the object | Keep every one of the parent's, add its own | Square adds *width = height*, which cannot coexist with the parent's postcondition |
| **History** — how state may change over time | Never allow changes the parent forbids | An immutable parent must not get a mutable subtype |

The Java compiler checks only a sliver of this: an override may return a more specific type (covariant returns) and may not throw broader *checked* exceptions. Everything else — unchecked exceptions, nulls, ranges, ordering, side effects — **only tests can check**. That is why LSP bugs ship.

**The fix: model the real variation.** The problem was never "square" — it was mutable setters that promise independence. Make shapes immutable values and the conflict disappears:

```java group=shapes
interface Shape { int area(); }

record Rect(int width, int height) implements Shape {
    public int area() { return width * height; }
}

record Square(int side) implements Shape {
    public int area() { return side * side; }
}
```

<Reveal q="If Rectangle were immutable — final fields, no setters — would Square extends Rectangle be safe?">

Yes. With no setters there is no postcondition like "height unchanged" for a square to break; a square is then simply a rectangle whose two sides happen to be equal, and every promise the immutable rectangle makes still holds. **LSP is about behaviour, so changing the behaviour (removing mutation) changes the answer.** This is also why value objects and records almost never cause LSP trouble.

</Reveal>

**The cues in everyday code** are less geometric. A subclass is lying when it:

1. **throws where the parent succeeded** (`UnsupportedOperationException` from an inherited method),
2. **weakens a guarantee** (the parent's `find` never returns null; the child's does),
3. **needs callers to check its concrete type** — every `instanceof` added to protect callers from one subtype is the symptom. Refactoring calls this smell *Refused Bequest*: a subclass that doesn't want what it inherited.

<h3 id="contract">A contract you can test</h3>

Back to the garage. Read `FeeStrategy`'s doc comment again — it is a contract, and every implementation inherits it:

- **Precondition:** it accepts every valid `ParkingSession` (the session's own invariant already rules out exit-before-entry).
- **Postcondition 1:** the fee is never negative.
- **Postcondition 2:** staying longer never costs less.

That last one isn't decoration. Copperline's pay-on-foot machine lets drivers prepay, then charges *the difference* at the exit barrier: `fee(at exit) − fee(when prepaid)`. If a strategy can make that negative, the barrier would owe the driver money.

Three classes that compile against the interface and break the contract:

```java group=garage
class ChargingCapFee implements FeeStrategy {      // "chargers time out at 8 hours"
    public long fee(ParkingSession s) {
        if (s.minutes() > 480) throw new IllegalArgumentException("EV sessions are limited to 8 hours");
        return s.startedHours() * 20 + 50;
    }
}

class LoyaltyFee implements FeeStrategy {          // "members get 30 off"
    public long fee(ParkingSession s) { return s.startedHours() * 20 - 30; }
}

class AllDayDealFee implements FeeStrategy {       // "over 3 hours? flat 50 for the day"
    public long fee(ParkingSession s) {
        return s.minutes() > 180 ? 50 : s.startedHours() * 20;
    }
}
```

`ChargingCapFee` **strengthens a precondition**: a 9-hour session is valid, and it throws. `LoyaltyFee` **weakens a postcondition**: a 20-minute stay costs 20 − 30 = −10. `AllDayDealFee` weakens the other one: 3 hours cost 60, but 3 hours and 5 minutes cost 50.

You can't prove a contract with a test, but you can **sample it hard**, and run the same sample against every implementation — a *contract test*:

```java group=garage
class FeeContract {
    /** null when the strategy kept every promise on the sampled sessions; otherwise the first broken one. */
    static String firstViolation(FeeStrategy strategy, VehicleType type) {
        LocalDateTime[] entries = { LocalDateTime.of(2026, 3, 13, 9, 0), LocalDateTime.of(2026, 3, 14, 23, 50) };
        for (LocalDateTime entry : entries) {
            long previous = 0;
            for (long m = 0; m <= 3 * 24 * 60; m += 5) {
                long fee;
                try {
                    fee = strategy.fee(new ParkingSession(type, entry, entry.plusMinutes(m)));
                } catch (RuntimeException e) {
                    return "threw on a valid " + m + "-minute stay";
                }
                if (fee < 0) return "negative fee " + fee + " for " + m + " minutes";
                if (fee < previous) return "fee fell from " + previous + " to " + fee + " at " + m + " minutes";
                previous = fee;
            }
        }
        return null;
    }
}
```

The checker runs `firstViolation` against every strategy on this page. The honest ones return null; the three above fail exactly as described — `ChargingCapFee` at 485 minutes, `LoyaltyFee` at 0 minutes (0 started hours − 30 = −30), `AllDayDealFee` at 185. The repairs keep the business intent *inside* the contract:

```java group=garage
class MemberFee implements FeeStrategy {           // the discount, but never below zero
    public long fee(ParkingSession s) { return Math.max(0, s.startedHours() * 20 - 30); }
}

class DayCapFee implements FeeStrategy {           // the deal as a cap: never more than 50
    public long fee(ParkingSession s) { return Math.min(s.startedHours() * 20, 50); }
}
```

Both pass. A cap and a floor are monotone; a flat price that kicks in *after* a threshold is not. (The EV limit gets its own honest fix in Side quest 4.)

**The pattern that industrialises it.** **Composition over inheritance** (next chapter), **split hierarchies** so each type only claims what it can deliver, and **contract tests** — one abstract test suite run against every implementation. LSP is also the test for every inheritance decision you make: substitutable under *all* operations, or compose instead.

**When not to apply it.** LSP is a correctness rule, not an optional pattern, so the over-engineering risk is elsewhere: **don't build a hierarchy in the first place when the variation is only data.** `BikeFee extends HourlyFee` with a different constant is a subclass doing a constructor argument's job. And don't over-promise in contracts: every guarantee you write into an interface is one every future implementation must keep forever. Promise what callers actually rely on.

<h2 id="composition">Chapter 4 · The counter that counted twice</h2>

<Scene chapter="Chapter 4" title="The counter that counted twice">

Every night, the kiosk at Copperline's side entrance uploads the tickets it issued while the network was down. Every morning, Bram checks the dashboard number: *tickets issued*.

On Wednesday the kiosk uploads three tickets. The dashboard says six.

Oona has already narrowed it down by the time you arrive. She has a single test, three ticket ids, one call to `addAll` — and a counter that reads 6. Her sticky note just says: *who called add the other three times?*

Wren looks at the class declaration, sighs, and circles two words: `extends HashSet`.

</Scene>

**The mess.** A subclass that counts how many tickets were ever offered to the set:

```java id=countingMess
class CountingTicketSet extends HashSet<String> {
    int offered = 0;

    @Override public boolean add(String ticket) {
        offered++;
        return super.add(ticket);
    }

    @Override public boolean addAll(Collection<? extends String> tickets) {
        offered += tickets.size();
        return super.addAll(tickets);
    }
}
```

Add three tickets with `addAll` and `offered` is **6**. In the JDK (checked on Java 17), `HashSet` doesn't define its own `addAll`; it inherits the one from `AbstractCollection`, whose documentation says it iterates over the collection and adds each element in turn — by calling `add`. Which you overrode. Each ticket is counted once by your `addAll` and again by your `add`.

This is the **fragile base class problem**: a subclass depends on how its parent calls *itself* — an implementation detail the parent is free to change. Joshua Bloch uses this exact example (an `InstrumentedHashSet`) in *Effective Java*, Item 18, "Favor composition over inheritance".

**The refactor: hold the set instead of being one.**

```java group=counting
class CountingTicketSet {
    private final Set<String> tickets = new HashSet<>();
    private int offered = 0;

    boolean add(String ticket) {
        offered++;
        return tickets.add(ticket);
    }

    boolean addAll(Collection<String> batch) {
        offered += batch.size();
        return tickets.addAll(batch);           // HashSet's internal add() calls never reach us
    }

    int offered() { return offered; }
    int size() { return tickets.size(); }
}
```

Now `addAll` of three tickets counts 3, whatever `HashSet` does internally. The class exposes only the operations Copperline needs; if it must be usable as a `Set`, Bloch's version implements `Set` by forwarding every method to the wrapped instance (a *forwarding class*), which is exactly the Decorator pattern.

<Reveal q="Wouldn't simply deleting the addAll override fix the double count?">

Today, yes — the inherited `addAll` would call your `add` three times and count 3. But now your correctness depends on the parent's self-use: if a future `HashSet` overrode `addAll` to insert directly without calling `add`, your counter would silently read 0 for batch imports. Composition removes the dependency on that detail entirely, which is the point.

</Reveal>

      +add(e) boolean
      +addAll(c) boolean
    }

      -Set tickets
      -int offered

      +addAll(Collection batch) boolean

**The decision rule** from the <a href={`${BASE}lld/lessons/object-modeling/`}>object-modeling lesson</a>, now with its full justification: **inherit only when the subclass is substitutable for the parent under every operation (Liskov) *and* the parent was designed for extension.** Otherwise compose.

| | Inheritance | Composition |
|---|---|---|
| Relationship | is-a, fixed at compile time | has-a, chosen (and swappable) at runtime |
| Coupled to | the parent's internals, including self-calls | the collaborator's public contract |
| Variation along | one axis (one parent) | many axes (many collaborators) |
| Typical failure | fragile base class; hierarchies guessed wrong | a little forwarding boilerplate |

Machine-coding version: `ElectricSUV extends SUV extends Car extends Vehicle` dies the moment Bram asks for an electric *bike*. A `VehicleType` plus composed capabilities (`needsCharging`, a size) — or the strategy map from Chapter 2 — defers the guess. The JDK has its own museum of the other choice: `Stack extends Vector` (so a stack lets you insert into its middle) and `Properties extends Hashtable` (so you can `put` non-string values into it) are both cited by Bloch as inheritance that should have been composition.

<Trace title="Who called add?" steps={composition} takeaway="Inheriting a concrete class couples you to how it calls itself. Hold one and forward instead — unless the parent was designed and documented for extension." />

**When not to apply it — when inheritance is right.** When the parent is **designed and documented for extension**: an abstract class whose skeleton calls well-defined hooks (Template Method — the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral lesson</a> covers it). When the hierarchy is a **closed set of data shapes**: a `sealed interface` with record implementations. And don't wrap a class in a forwarding layer when you only *use* it — holding a `HashSet` as a private field is composition already; it needs no ceremony. Bloch's own advice for the other side: design and document for inheritance, or prohibit it (`final`).

**Catch the trap:** *"Composition over inheritance means never use `extends`."* Template Method, sealed data hierarchies and framework base classes built for extension are all fine. The rule is about extending **concrete classes you don't control**.

**Say it aloud:** *"I'll hold a HashSet rather than extend it — I don't want my counter to depend on how HashSet calls itself."*

Methods that one client uses together belong together. And a class with exactly one caller and no need for a test double doesn't need an interface at all yet.

**The mess.**

**The detection cue.** The word `new` applied to anything that does I/O, inside a class that makes business decisions. Its cousins: `now()`, `Random`, `UUID.randomUUID()` — anything nondeterministic — inside business logic. And domain packages importing framework or vendor packages.

**The refactor: invert the arrow.** The domain *defines* the port it needs, in its own words; the edge implements it; the composition root wires them together:

```java group=garage
interface PaymentGateway {                           // the port: owned by the domain, in the domain's words
    PaymentResult charge(String ticketId, long amount);
}
record PaymentResult(boolean approved, String reference) {}
record Receipt(String ticketId, long fee, String reference) {}

class CheckoutService {
    private final FeeCalculator fees;
    private final PaymentGateway gateway;
    private final Clock clock;

    CheckoutService(FeeCalculator fees, PaymentGateway gateway, Clock clock) {
        this.fees = fees;
        this.gateway = gateway;
        this.clock = clock;
    }

    Receipt checkout(String ticketId, VehicleType type, LocalDateTime entry) {
        LocalDateTime exit = LocalDateTime.now(clock);
        long fee = fees.fee(new ParkingSession(type, entry, exit));
        if (fee == 0) return new Receipt(ticketId, 0, "FREE");
        PaymentResult paid = gateway.charge(ticketId, fee);
        if (!paid.approved()) throw new IllegalStateException("payment declined for " + ticketId);
        return new Receipt(ticketId, fee, paid.reference());
    }
}
```

The vendor lives at the edge, behind an **adapter** that speaks both languages — including the vendor's units:

    FakeGateway gateway = new FakeGateway();
    CheckoutService checkout = new CheckoutService(standardTariff(), gateway, sixPm);

}

**DIP, DI and IoC are three different things** — a favourite follow-up:

- **Dependency inversion** is about the *direction of source-code dependencies*: high-level policy and low-level detail both depend on an abstraction, and the abstraction belongs to the policy side.
- **Dependency injection** is a *technique*: an object receives its collaborators (best through its constructor) instead of constructing them.
- **An IoC container** (Spring, Guice) is a *tool* that performs injection for you. **DI is a `main()` method before it's a container** — `liveCheckout` above is a complete, framework-free composition root.

Prefer **constructor injection with final fields**: the object is complete the moment it exists, its dependencies are visible in one signature, and a test can construct it with fakes in one line. Field injection (`@Autowired` on a private field) hides the dependencies and makes final fields impossible.

<Trace title="Which way the arrow points" steps={dip} takeaway="Business rules own the ports they need; vendors, clocks and devices plug in at the edge; main() wires it. Inject what does I/O or is nondeterministic — not values and pure helpers." />

**The pattern that industrialises it.** **Adapter behind a port** — the *ports and adapters* (hexagonal) architecture — with wiring at a composition root. The War Room shows the payoff from both ends: <a href={`${BASE}lld/war/patterns-why/#8-adapter--so-a-swap-is-config-not-a-release`}>an adapter seam</a> turned moving heavy report queries to a read replica into a config change rather than a release, and <a href={`${BASE}lld/war/patterns-why/#16-null-object--shipping-the-consumer-before-the-producer-exists`}>a Null Object behind the real seam</a> let one team ship and test its API before the component it depended on existed (with a trap worth reading: a stub that silently served canned data when a property was missing).

**When not to apply it.** **Inject what does I/O, what is nondeterministic, or what genuinely varies** — the gateway, the clock, an id generator. Don't inject a `StringBuilder`, an `ArrayList`, `Duration.between` or a `Money` value; constructing those with `new` is fine. Don't put an interface over your own stable domain class "for DI" when nothing will ever stand in for it. And in a 90-minute round, a hand-written `main()` that wires five objects beats configuring a container.

**Your turn.** The entry gate prints a ticket with `"T-" + UUID.randomUUID()` and `LocalDateTime.now()`. Oona can't write a test that predicts the ticket. Make `EntryGate` testable.

<h2 id="cohesion-coupling">Chapter 7 · Two dials</h2>

<Scene chapter="Chapter 7" title="Two dials" mood="dawn">

A month of Tuesdays later, on a quiet Friday afternoon, Wren draws two dials on the whiteboard and labels them **cohesion** and **coupling**.

*"Every principle you've learned this month,"* she says, *"turns one of these two. Tell me which."*

You start to answer, and realise you have to think about each one.

</Scene>

**Cohesion** is how strongly the things *inside* a module belong together — whether they use the same data and change for the same reason. **Coupling** is how much a module depends on, and knows about, *other* modules. Good design turns cohesion **up** and coupling **down** — and when coupling is unavoidable (collaborating objects must know *something* about each other), it points at stable things: interfaces and values, not internals and vendors.

You can *see* low cohesion. Here is which method of the original `ShiftReport` (Chapter 1) touches which field:

| Method | `db` | `smtpHost` | `smtpPort` | tickets & totals |
|---|---|---|---|---|
| `load` | ✓ | | | |
| `run` (totals and layout) | | | | ✓ |
| `send` | | ✓ | ✓ | |

Three islands that share nothing. When a class's methods split into groups that never touch each other's fields, it is several classes wearing one name — the field-clustering cue from Chapter 1.

| Principle | Dial it turns | How |
|---|---|---|
| **S** | Cohesion ↑ (within a class) | Everything in the class changes for one actor |
| **O** | Coupling ↓ to variants | Callers depend on `FeeStrategy`, never on `HourlyFee` |
| **L** | Keeps coupling to abstractions *honest* | Callers can depend on the interface alone because every implementation keeps its promises |
| **I** | Cohesion ↑ (within an interface), coupling ↓ for clients | Each client is coupled to exactly the methods it calls |
| **D** | Coupling direction | Volatile details depend on stable policy, never the reverse |
| **Composition** | Coupling ↓ | Coupled to a collaborator's public contract, not its internals |

Two smells from Martin Fowler's *Refactoring* name the failure on each side, and they are mirror images:

- **Divergent change** — one class changed for many different reasons. Too little cohesion: split it (S).
- **Shotgun surgery** — one change forces edits in many classes. The responsibility is scattered: gather it into one place. This is the over-split from Chapter 1's "when not" — and the repeated `switch` from Chapter 2.

<Figure caption="The target quadrant (positions are illustrative). Most SOLID refactors move a design up (more cohesive) or left (less coupled); over-splitting drops it into the bottom left.">
  <Mermaid code={`quadrantChart
    title Cohesion vs coupling
    x-axis Low coupling --> High coupling
    y-axis Low cohesion --> High cohesion
    quadrant-1 Wrong boundaries
    quadrant-2 The target
    quadrant-3 Destructive decoupling
    quadrant-4 God class
    ShiftReport before: [0.8, 0.2]
    ShiftReport after: [0.3, 0.8]`} />
</Figure>

<Trace title="Read the dials" steps={dials} takeaway="Divergent change: one class, many reasons — split it. Shotgun surgery: one reason, many classes — gather it. Couple to contracts, not internals." />

**Catch the trap:** *"Low coupling means fewer classes talking to each other."* A coordinator that talks to four small interfaces is less coupled than a God class that talks to no one because it has swallowed the database, the arithmetic and the mail server. Coupling is about **what you know** about your collaborators — their internals, their vendors, their timing — not how many you have.

Nobody in a machine-coding round asks *"define the open/closed principle"*. The grading rubric (the full version is in the <a href={`${BASE}lld/lessons/machine-coding-protocol/`}>90-minute protocol lesson</a>) scores **design** — seams on the variation axes, invariants owned by entities — and the **extensibility question**, where the follow-up should land as a new class. SOLID is how you earn both, and the grader can only credit what they can see or hear.

**Where each principle shows up on the clock:**

| Minutes | Phase | The SOLID move | Say it aloud |
|---|---|---|---|
| 0–10 | Requirements | Find the axis of change | *"Pricing sounds like it will vary — is that right? I'll make it pluggable and keep the rest concrete."* |
| 10–30 | Entities & interfaces | Seams only at variation and I/O (O, D, I) | *"FeeStrategy and PaymentGateway are interfaces; Spot and Ticket are plain classes."* |
| 30–65 | Core flow | Split as soon as a second reason appears (S) | *"This is drifting into two responsibilities; pulling receipt formatting out."* |
| 65–80 | The follow-up | The change lands as a class (O, L) | *"Surge is a decorator around the existing strategies — one new class, one wiring line, nothing reopened."* |
| 80–90 | Tests & demo | Injected fakes and a fixed clock (D) | *"The test injects a fixed clock, so the fee is deterministic."* |

**What loses points,** in roughly the order graders see it:

1. **Reciting definitions** instead of showing the move. The acronym earns nothing; the split earns everything.
2. **More interfaces than implementations.** Each interface should have a second implementation, a test double, or an announced reason to exist. Otherwise it is speculative generality.
3. **Deep vehicle hierarchies.** `Car extends Vehicle` with overridden `fee()` couples pricing to the vehicle tree. Pricing varies on more than vehicle type (time, day, membership).
4. **A God class with a good name.** `ParkingLotManager` that allocates, prices, charges and prints.
5. **`new` and `now()` in business logic**, discovered when you try to write the first test with five minutes left.

**The 30-second audit before you demo.** Run your eye down the class list and ask, for each class: one actor? For each interface: who stands in for it? For the follow-up axis: is it a new class? For checkout: can the test control the clock? Fixing one thing you find, out loud, is worth more than fixing it silently.

<h2 id="sq-surge">Side quest 1 · Weekend surge</h2>

**The card says:** *"Weekends cost one and a half times. All vehicles. Based on the day you drive in."*

**Where it lands:** open/closed, through a **Decorator**. Surge doesn't replace any pricing rule — it modifies whatever rule is already there. So it wraps a `FeeStrategy` and *is* a `FeeStrategy`, and existing strategies don't change.

<Reveal q="Why a decorator instead of adding a 'weekend' flag to HourlyFee and HourlyPlusChargingFee?">

A flag edits every existing strategy (and every future one must remember it): that is the ladder again, spread across classes — shotgun surgery. The decorator writes the surge rule once and applies it to any strategy, including ones that don't exist yet. It also composes: surge around a grace period, a cap around a surge.

</Reveal>

<HintLadder hints={hints.surge} labels={turn}>

```java group=garage
class WeekendSurge implements FeeStrategy {           // a decorator: wraps any strategy, is a strategy
    private final FeeStrategy base;
    private final long percent;
    WeekendSurge(FeeStrategy base, long percent) {
        if (percent < 0) throw new IllegalArgumentException("percent must be >= 0");
        this.base = base;
        this.percent = percent;
    }
    public long fee(ParkingSession s) {
        DayOfWeek day = s.entry().getDayOfWeek();
        boolean weekend = day == DayOfWeek.SATURDAY || day == DayOfWeek.SUNDAY;
        long fee = base.fee(s);
        return weekend ? fee * percent / 100 : fee;     // integer rupees, rounded down
    }
}

FeeCalculator weekendTariff() {
    return new FeeCalculator(Map.of(
        VehicleType.BIKE, new WeekendSurge(new HourlyFee(10), 150),
        VehicleType.CAR,  new WeekendSurge(new HourlyFee(20), 150),
        VehicleType.EV,   new WeekendSurge(new HourlyPlusChargingFee(20, 50), 150)));
}
```

On Saturday 14 March 2026, a car parked 15:30–18:00 pays 60 × 150 / 100 = **90**; the same stay on Friday the 13th pays 60. An EV for one hour on Saturday pays (20 + 50) × 1.5 = **105**. The surge keeps `FeeStrategy`'s contract: scaling a never-negative, never-decreasing fee by a non-negative percentage (and rounding down) keeps it never-negative and never-decreasing — the contract test agrees.

</HintLadder>

**Transfer test:** Bram then asks for surge *only between 17:00 and 20:00 on weekdays*. Which class changes, and which stays closed? The surge's *condition* is new behaviour — is it a new decorator, or a condition you pass into this one? Either can be right; say which and why before you write it.

<h2 id="sq-csv">Side quest 2 · The report, as CSV</h2>

**The card says:** *"My accountant wants the shift report as CSV. I still want mine as text."*

**Where it lands:** single responsibility already did the hard part — formatting lives in exactly one class, so only one class is affected. But now there are **two formats**, and that is the moment to **extract the interface**: the seam you correctly didn't build in Chapter 1 is now earned.

<Reveal q="Isn't extracting the interface an edit to existing code — an OCP violation?">

It is an edit, and it's the right one. OCP applies to the axis you *expect*; in Chapter 1 nobody expected a second format, so a concrete `ReportFormatter` was correct. When the second variant arrives, you pay a small, one-time refactor (rename the class, change one constructor parameter type) to open the axis. From then on, the third format is a pure addition. Building the seam on the second variant, not speculatively on the first, is the honest version of OCP.

</Reveal>

<HintLadder hints={hints.csv} labels={turn}>

```java group=reportCsv
import java.time.*;

// Unchanged from Chapter 1, repeated so this design compiles on its own.
record Ticket(String id, long fee) {}
interface TicketLog { List<Ticket> closedOn(LocalDate day); }
interface Mailer { void send(String to, String subject, String body); }
class RevenueTotals {
    long total(List<Ticket> tickets) {
        long sum = 0;
        for (Ticket t : tickets) sum += t.fee();
        return sum;
    }
}
```

```java group=reportCsv
interface ReportFormat {                              // extracted when the second format arrived
    String render(LocalDate day, List<Ticket> tickets, long total);
}

class PlainTextFormat implements ReportFormat {       // the old ReportFormatter, renamed
    public String render(LocalDate day, List<Ticket> tickets, long total) {
        StringBuilder out = new StringBuilder("Shift report " + day + "\n");
        for (Ticket t : tickets) out.append(t.id()).append("  ").append(t.fee()).append('\n');
        return out.append("Tickets: ").append(tickets.size()).append("  Revenue: ").append(total).toString();
    }
}

class CsvFormat implements ReportFormat {
    public String render(LocalDate day, List<Ticket> tickets, long total) {
        StringBuilder out = new StringBuilder("ticket,fee\n");
        for (Ticket t : tickets) out.append(t.id()).append(',').append(t.fee()).append('\n');
        return out.append("TOTAL,").append(total).toString();
    }
}

class ShiftReportFlow {                               // one parameter type changed: ReportFormat
    private final TicketLog log;
    private final RevenueTotals totals;
    private final ReportFormat format;
    private final Mailer mailer;

    ShiftReportFlow(TicketLog log, RevenueTotals totals, ReportFormat format, Mailer mailer) {
        this.log = log;
        this.totals = totals;
        this.format = format;
        this.mailer = mailer;
    }

    void send(LocalDate day, String to) {
        List<Ticket> tickets = log.closedOn(day);
        mailer.send(to, "Shift report " + day, format.render(day, tickets, totals.total(tickets)));
    }
}
```

Bram's flow is wired with `PlainTextFormat`, the accountant's with `CsvFormat`; `TicketLog`, `RevenueTotals` and `Mailer` never moved. One honest caveat: real CSV must quote any field containing a comma, quote or newline (RFC 4180). Ticket ids here never do; a free-text field would.

</HintLadder>

**Transfer test:** the accountant now wants the CSV *attached* rather than in the body. Which actor's class changes — format, delivery, or the flow?

<h2 id="sq-vendor">Side quest 3 · A new payment vendor</h2>

**The card says:** *"PennyPay's fees went up. From Monday we use CoinVault. Their system takes the amount as a string with two decimals and answers with a status code."*

**Where it lands:** dependency inversion. `CheckoutService` depends on `PaymentGateway`, which the domain owns, so the new vendor is **one new adapter plus one wiring line**. The domain doesn't change, and neither do its tests.

<Reveal q="CoinVault returns 503 when it's down. Where does that number get translated, and why there?">

In the adapter, and only there. The domain's port speaks in `PaymentResult(approved, reference)`; vendor status codes, string amounts and SDK exceptions are the adapter's job to translate. If `503` leaked into `CheckoutService`, the next vendor switch would edit the domain again — the arrow would be pointing the wrong way.

</Reveal>

<HintLadder hints={hints.vendor} labels={turn}>

```java group=garage
class CoinVaultApi {                                   // stand-in for the new vendor's SDK
    private final boolean online;
    final List<String> payments = new ArrayList<>();
    CoinVaultApi(boolean online) { this.online = online; }
    int pay(String amount, String reference) {
        if (!online) return 503;
        payments.add(reference + " " + amount);
        return 200;
    }
}

class CoinVaultAdapter implements PaymentGateway {
    private final CoinVaultApi api;
    CoinVaultAdapter(CoinVaultApi api) { this.api = api; }

    public PaymentResult charge(String ticketId, long amount) {
        int status = api.pay(amount + ".00", ticketId);             // whole rupees -> "60.00"
        return status == 200 ? new PaymentResult(true, "CV-" + ticketId) : new PaymentResult(false, null);
    }
}

CheckoutService coinVaultCheckout(CoinVaultApi api, Clock clock) {   // the one wiring change
    return new CheckoutService(standardTariff(), new CoinVaultAdapter(api), clock);
}
```

With CoinVault online, a 60-rupee checkout records `"T-17 60.00"` and returns reference `CV-T-17`. Offline, the adapter reports a decline and `CheckoutService` refuses to open the barrier — the same domain rule as before, untouched.

</HintLadder>

**Transfer test:** Bram wants to *try* CoinVault for 10% of checkouts first. Where does that choice live — inside an adapter, inside `CheckoutService`, or in a new `PaymentGateway` implementation that holds both?

<h2 id="sq-overstay">Side quest 4 · The eight-hour charger</h2>

**The card says:** *"EV chargers are reserved for 8 hours. Anyone who stays longer is blocking a charger — make them pay 200 extra."*

**Where it lands:** Liskov. The tempting implementation is Chapter 3's `ChargingCapFee`: throw for sessions over 8 hours. But a 9-hour stay is a *valid* session, and a strategy that throws on it **strengthens the precondition** — the exit barrier, which only knows `FeeStrategy`, would crash with a car waiting at it. The honest version prices the overstay: the fee jumps up, which the contract allows.

<Reveal q="Bram insists: 'no EV may stay more than 8 hours, full stop.' Now where does the rule go?">

Not in the fee. A rule about *whether a session may continue* belongs where sessions are managed — an alert to staff at the 8-hour mark, a booking limit at the charger, a penalty policy. The fee strategy's job is to price any valid session; forcing it to also enforce occupancy gives it a second reason to change *and* breaks its contract. Two principles, one answer.

</Reveal>

<HintLadder hints={hints.overstay} labels={turn}>

```java group=garage
class OverstayPenalty implements FeeStrategy {         // a decorator that keeps the contract
    private final FeeStrategy base;
    private final long limitMinutes, penalty;
    OverstayPenalty(FeeStrategy base, long limitMinutes, long penalty) {
        this.base = base;
        this.limitMinutes = limitMinutes;
        this.penalty = penalty;
    }
    public long fee(ParkingSession s) {
        return base.fee(s) + (s.minutes() > limitMinutes ? penalty : 0);
    }
}
```

Wiring: `VehicleType.EV, new OverstayPenalty(new HourlyPlusChargingFee(20, 50), 480, 200)`. Exactly 8 hours costs 8 × 20 + 50 = **210**; 9 hours costs 9 × 20 + 50 + 200 = **430**. The fee only ever jumps *up* at the limit, so the contract test passes where `ChargingCapFee` failed at 485 minutes.

</HintLadder>

**Transfer test:** Bram adds *"…but members are exempt."* Do you add a constructor flag to `OverstayPenalty`, or compose something around it? Which choice keeps `MemberFee`'s floor at zero?

<h2 id="interview-script">Say it in the room</h2>

<Scene title="The interview room" mood="night">

The demo runs. Surge pricing landed with eight minutes to spare. The Interviewer scrolls through your class list without saying anything, then looks up.

*"Walk me through how SOLID shows up in this design."*

A year ago you would have recited five definitions. Today you point at the code.

**The 90-second answer** (adapt the nouns):

> "I started from what's likely to change rather than from the acronym. Pricing was the axis you hinted at, so fees sit behind a `FeeStrategy` interface — bike and car share one hourly class with different rates, EV has its own — and when you asked for weekend surge it landed as one decorator class and one wiring line, nothing reopened. That's open/closed. Each class has one reason to change: `ParkingLot` allocates spots, `FeeCalculator` prices, `CheckoutService` only coordinates exit, and receipt formatting is separate because it changes for different people than the rules. Every fee strategy keeps one written contract — never negative, never cheaper for staying longer — and one contract test runs against all of them; that's Liskov in practice, and it's why there's no vehicle inheritance tree. The payment gateway and the clock come in through constructors as interfaces the domain owns, so my tests use a fake gateway and a fixed clock, and switching vendors is a new adapter. Clients see small role interfaces — the gate alert only sees `SmsSender`. And where nothing varies, I kept it concrete: spots and tickets are plain classes."

**Five follow-ups you will get:**

<Reveal q="1 · Isn't this over-engineered for a 90-minute problem?">

Where nothing varies, I didn't abstract: spots and tickets are concrete, there's no factory, no container. Interfaces exist in three places, each for a stated reason — pricing (three implementations, and your follow-up), the payment gateway (a vendor plus a test fake), and the clock (determinism in tests). If one of them didn't have a second implementation or a fake, I'd inline it.

</Reveal>

<Reveal q="2 · What's the difference between dependency inversion, dependency injection and an IoC container?">

Inversion is the direction of source dependencies: business rules own the abstraction, details implement it. Injection is the technique of handing an object its collaborators — here, through constructors. A container like Spring automates injection. I satisfied inversion with a constructor and a `main()`; a container would change nothing about the design.

</Reveal>

<Reveal q="3 · Give me a Liskov violation from the JDK.">

`java.sql.Date extends java.util.Date`, but `toInstant()` throws `UnsupportedOperationException` and the time getters such as `getHours()` throw `IllegalArgumentException`, because an SQL date has no time component — code written against `java.util.Date` breaks when handed one. `java.sql.Timestamp`'s own documentation admits its `equals` isn't symmetric with `Date`'s and calls the relationship implementation inheritance, not type inheritance. A subtler case: `List.add` is documented as an *optional operation*, so `List.of(...).add(x)` throwing is technically within the contract — but that contract pushes the check onto every caller, which is the fat-interface problem ISP describes.

</Reveal>

<Reveal q="4 · How would you test CheckoutService?">

Construct it with a fake `PaymentGateway` that records charges and a `Clock.fixed` instant. Park at 15:30, fix the clock at 18:00, expect 3 started hours × 20 = 60 and exactly one charge of 60. Then a declining fake to check the barrier stays shut, and a zero-minute stay to check the gateway is never called. No network, no card, same result at any time of day.

</Reveal>

<Reveal q="5 · Why not an abstract Vehicle with an overridden fee() in each subclass?">

Because price depends on more than the vehicle — time, day of week, membership, overstay — and those rules change for the business, not for the vehicle. Putting `fee()` on `Vehicle` gives every vehicle class a second reason to change and forces a new subclass for every pricing idea. Vehicles describe what's parked; strategies describe what it costs; a map connects them.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Principle | Do… | Pattern it grows into |
|---|---|---|---|
| A class description with "and"; fields used by separate method groups | **S** | Split by actor; keep a thin coordinator | Extracted services, Facade |
| A coordinator computing business rules | **S** | Move the rule into its own class | — |
| An `if`/`switch` ladder on a type, repeated | **O** | One class per branch behind an interface, a map to choose | Strategy + registry |
| "Now add X on top of whatever applies" | **O** | Wrap, don't edit | Decorator |
| A follow-up that edits five methods | **O** | Find the axis; open it once | Strategy, Chain |
| A subclass that throws, returns null, or demands more | **L** | Split the contract or compose | Role interfaces, contract tests |
| `Square extends Rectangle` with setters | **L** | Immutable values behind a shared interface | Records + interface |
| `extends` on a concrete class you don't control | Composition | Hold it and forward | Decorator / forwarding class |
| Fakes with many throwing methods | **I** | One role interface per client need | Role interface, Adapter |
| `new VendorClient()` / `now()` / `UUID` in business logic | **D** | Port owned by the domain, constructor injection, wire in `main()` | Adapter, ports and adapters |
| Interfaces with one implementation and no fake | Over-engineering | Inline them | — |
| A change touching many classes | Coupling | Gather the scattered responsibility | Move method / class |

## Five mistakes to leave behind

1. **Reciting the acronym.** Show the move instead: notice the second reason to change, say it, split it.
2. **Interfaces for everything.** More interfaces than implementations is speculative generality. Every seam needs a second implementation, a fake, or a stated reason.
3. **Subclassing for data.** `BikeFee extends HourlyFee` to change a rate is a constructor argument wearing a hierarchy.
4. **`new`, `now()` and `random` inside business rules.** They make the code untestable and pin it to a vendor. Inject them.
5. **"OCP means never edit."** Close the axis you expect, edit honestly everywhere else, and open a new axis when its second variant arrives.

**Further study**

- Robert C. Martin, *Agile Software Development: Principles, Patterns, and Practices* (2002) — the original chapters on all five principles, with the Square/Rectangle discussion; his later *Clean Architecture* (2017) restates SRP in terms of actors.
- [The Single Responsibility Principle](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html) (Robert C. Martin, 2014) — the "reasons to change are people" argument in his own words.
- Barbara Liskov and Jeannette Wing, [A Behavioral Notion of Subtyping](https://doi.org/10.1145/197320.197383) (ACM TOPLAS, 1994) — preconditions, postconditions, invariants and the history constraint, formally.
- Joshua Bloch, *Effective Java* (3rd edition) — Item 18 "Favor composition over inheritance" (the `InstrumentedHashSet`) and Item 19 "Design and document for inheritance or else prohibit it".
- Martin Fowler, [Inversion of Control Containers and the Dependency Injection pattern](https://martinfowler.com/articles/injection.html) — where the term *dependency injection* was named, and constructor vs setter injection.
- Martin Fowler, [RoleInterface](https://martinfowler.com/bliki/RoleInterface.html) — role interfaces versus header interfaces, the practical form of ISP.
- Martin Fowler, *Refactoring* (2nd edition) — the smells this lesson leans on: Divergent Change, Shotgun Surgery, Refused Bequest, Speculative Generality, Repeated Switches.
- [java.time.Clock](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/Clock.html) — the JDK's built-in seam for time, with `fixed` and `offset` for tests.
- [SOLID (Wikipedia)](https://en.wikipedia.org/wiki/SOLID) and [Liskov substitution principle (Wikipedia)](https://en.wikipedia.org/wiki/Liskov_substitution_principle) — short summaries with the history and original sources.

**Look these up yourself**

- **Design by Contract** (Bertrand Meyer, Eiffel) — the origin of preconditions/postconditions/invariants as language features; Java has no built-in equivalent, which is why contract tests exist.
- **Hexagonal architecture / ports and adapters** (Alistair Cockburn) — Chapter 6's port-and-adapter idea applied to a whole application.
- **GRASP** (Craig Larman) — Information Expert, Low Coupling, High Cohesion, Protected Variations; Protected Variations is OCP from a different angle.
- **Law of Demeter and "Tell, don't ask"** — two more coupling rules interviewers like, about how far one object should reach into another.
- **Sealed interfaces and exhaustive `switch`** (Java 17+) — when a closed set of types is the honest model, and the compiler checks every case for you.
- **Variance in overriding** — why Java allows covariant return types but not contravariant parameters, and how that maps to LSP's pre/postcondition rules.
- **Package principles** (Martin): REP, CCP, CRP, ADP, SDP, SAP — SOLID's ideas applied to modules instead of classes.
- **Connascence** — a finer-grained vocabulary for coupling (of name, type, meaning, position, timing…) than "high" and "low".
