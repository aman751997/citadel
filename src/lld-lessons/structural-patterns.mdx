<h2 id="prologue">Prologue · A clinic walks into a workshop</h2>

<Scene chapter="Prologue" title="Five contracts on the table" mood="dawn">

MediCore runs eleven clinics, and as of Monday it is the Gearhouse's newest client. The Gearhouse will write the software for their check-in kiosks, the discharge desk, the pharmacy counters and the operations dashboard.

Wren spreads MediCore's paperwork across the meeting table. An SMS vendor contract. A payment vendor contract. A thick binder titled *Patient Records — DO NOT MODIFY*. A sample bill that runs to four pages because surgery packages contain other packages.

"Last month," she says, "you learned to write code that changes well." She taps the vendor contracts one by one. "None of this is ours. We can't edit the SDKs. We shouldn't edit the records service — it's tested and certified. And procurement changes vendors every year."

You look at the pile. "So what do we write?"

*"Mostly,"* says Wren, *"wrappers. The question is which kind."*

</Scene>

The creational patterns lesson built MediCore's objects. This one connects them — to vendors with alien SDKs, to records that need a guard, to a discharge process that touches five systems. **Structural patterns are about how classes and objects are composed into bigger structures**, and nearly all of them work by wrapping one object in another:

| Pattern | The problem that forces it | The move |
|---|---|---|
| **Adapter** | A vendor's interface has the wrong shape, and you can't edit it | Translate their shape into the port your domain owns |
| **Decorator** | Behaviour must be added in combinations that vary per caller | Wrap with the same interface; stack at wiring time |
| **Proxy** | Every call must be guarded, deferred, cached or sent elsewhere — and callers mustn't opt out | Stand in front with the same interface; control the call |
| **Facade** | Many callers repeat one multi-system sequence | One new, smaller entry point that coordinates, never decides |
| **Composite** | Parts and wholes form a tree, and callers want to treat them alike | One interface; containers answer by asking their children |
| **Bridge** | Two independent dimensions multiply your subclasses | Split the hierarchies; hold one inside the other |
| **Flyweight** | Millions of objects repeat the same immutable data | Share the repeated part; pass the rest in |

**The trap that makes this family hard: on a class diagram, four of them look identical.** Adapter, Decorator, Proxy and Facade all "hold an object and forward calls to it". Interviewers know this, which is why the most common structural-pattern question isn't "define Decorator" — it's *"isn't that just a proxy?"*. The difference is **intent**: what the wrapper is *for*. Every chapter below ends with the detection cue and a memory hook aimed at telling the pattern apart from its neighbours, and <a href="#tell-them-apart">Part Four</a> puts them side by side.

<h2 id="adapter">Chapter 1 · The SDK that speaks alien</h2>

<Scene chapter="Chapter 1" title="The SDK that speaks alien">

MediCore sends appointment reminders by SMS through a vendor called TextWave. Their SDK arrived as a JAR and a PDF.

You read the PDF. TextWave does not have a `send` method. It has `submitMessage`, which takes a `TextWavePayload`, which wants the phone number as bare digits with no plus sign, the body as a `char[]`, and a sender code. It answers with an acknowledgement whose failures are reason codes like `E101_BAD_MSISDN`.

Oona has already grepped the old prototype. Four classes import `com.textwave`: reminders, lab results, discharge, one-time passwords. Each builds its own payload. Two of them forget to strip the plus sign.

Wren puts the procurement calendar on your desk. TextWave's contract ends in eleven months.

*"What changes next?"*

"The vendor."

*"Then how many classes should know its name?"*

</Scene>

**The mess.** Vendor vocabulary everywhere the domain needs a text sent:

```java fragment
class ReminderService {
    private final TextWaveClient textWave = new TextWaveClient(Config.textWaveKey());   // the vendor, welded in

    void remind(Appointment a) {
        TextWavePayload p = new TextWavePayload();
        p.setMsisdn(a.patientPhone());                     // forgot to strip the '+': E101 in production
        p.setBody(("Reminder: Dr " + a.doctor() + " at " + a.time()).toCharArray());
        p.setSender("MEDICORE");
        TextWaveAck ack = textWave.submitMessage(p);
        if (!ack.accepted()) log.warn("TextWave said " + ack.reasonCode());           // vendor errors, in the domain
    }
}
// ...and the same dozen lines in LabResultsService, DischargeService and OtpService.
```

**The detection cues.**

1. **Vendor names in domain imports.** If `com.textwave` appears in a class that also knows what an appointment is, the next vendor switch edits business code.
2. **Vendor types in domain signatures or logs.** `TextWaveAck`, `E101` and `char[]` bodies are someone else's vocabulary leaking in.
3. **The same translation repeated** — and, as Oona found, repeated slightly differently. Duplicated translation is where the bugs live.
4. **A swap you already know is coming.** The War Room's version: a dependency you will replace on a schedule you don't control.

**The pattern: Adapter.** First, the domain says what it *wishes* existed, in its own words. This interface — the **port** — belongs to MediCore:

```java group=clinic
import java.time.*;

record PhoneNumber(String e164) {                          // "+919812345678": plus, country code, 7-15 digits
    PhoneNumber {
        if (!e164.matches("\\+[1-9][0-9]{6,14}")) throw new IllegalArgumentException("not an E.164 number: " + e164);
    }
}

class SmsDeliveryException extends RuntimeException {
    SmsDeliveryException(PhoneNumber to, String reason) { super("SMS to " + to.e164() + " failed: " + reason); }
}

interface SmsGateway {                                     // the port: owned by MediCore's domain
    void send(PhoneNumber to, String text);
}

class ReminderService {                                    // domain code: knows the port, never the vendor
    private final SmsGateway sms;
    ReminderService(SmsGateway sms) { this.sms = sms; }

    void remind(PhoneNumber patient, String doctor, LocalDateTime at) {
        sms.send(patient, "Reminder: Dr " + doctor + ", " + at.toLocalDate() + " at " + at.toLocalTime());
    }
}
```

Here is TextWave's SDK, as it ships (a stand-in with the real thing's shape — you can't edit it):

```java group=clinic
class TextWavePayload {
    private String msisdn;                                 // digits only, country code first, no '+'
    private char[] body;
    private String sender;
    void setMsisdn(String msisdn) { this.msisdn = msisdn; }
    void setBody(char[] body) { this.body = body; }
    void setSender(String sender) { this.sender = sender; }
    String msisdn() { return msisdn; }
    char[] body() { return body; }
    String sender() { return sender; }
}

record TextWaveAck(boolean accepted, String reasonCode) {}

class TextWaveClient {
    private final String apiKey;
    final List<String> delivered = new ArrayList<>();       // stands in for TextWave's servers
    TextWaveClient(String apiKey) { this.apiKey = apiKey; }

    TextWaveAck submitMessage(TextWavePayload p) {
        if (p.msisdn() == null || !p.msisdn().matches("[0-9]{7,15}")) return new TextWaveAck(false, "E101_BAD_MSISDN");
        if (p.body() == null || p.body().length == 0) return new TextWaveAck(false, "E102_EMPTY_BODY");
        delivered.add(p.sender() + "->" + p.msisdn() + ": " + new String(p.body()));
        return new TextWaveAck(true, "OK");
    }
}
```

And the adapter: one class that speaks both languages, so nothing else has to:

```java group=clinic
class TextWaveAdapter implements SmsGateway {
    private final TextWaveClient client;                   // the adaptee: the vendor's SDK
    private final String senderCode;

    TextWaveAdapter(TextWaveClient client, String senderCode) {
        this.client = client;
        this.senderCode = senderCode;
    }

    public void send(PhoneNumber to, String text) {
        TextWavePayload payload = new TextWavePayload();    // translate OUR call into THEIR shape
        payload.setMsisdn(to.e164().substring(1));          // "+919812345678" -> "919812345678"
        payload.setBody(text.toCharArray());
        payload.setSender(senderCode);
        TextWaveAck ack = client.submitMessage(payload);
        if (!ack.accepted())                                // and THEIR failure into OUR exception
            throw new SmsDeliveryException(to, ack.reasonCode());
    }
}

SmsGateway liveSms(TextWaveClient client) {                // composition root: the vendor swap is this one line
    return new TextWaveAdapter(client, "MEDICORE");
}
```

Three directions of translation happen in that one method, and each is an adapter's whole job: **the request** (our `PhoneNumber` and `String` into their payload, including the plus sign they don't want), **the units and types** (`String` to `char[]`), and **the failure** (their reason code into our exception, so no domain class ever reads `E101`). The checker sends a thousand random valid numbers through it and confirms TextWave receives exactly the digits after the plus.

Two grading points. First, **the port belongs to the consumer**: your domain defines `SmsGateway`, and the adapter conforms to *it* — never the other way round. That is dependency inversion from the <a href={`${BASE}lld/lessons/solid/`}>SOLID lesson</a>: arrows point from volatile (vendor) to stable (domain). Second, **adapters are where a swap becomes configuration** — the <a href={`${BASE}lld/war/patterns-why/#8-adapter--so-a-swap-is-config-not-a-release`}>production dossier</a> exists because moving heavy report queries to a read replica had to be a config change, not a release. The same seam is why next year's SMS vendor is one new class and one wiring line.

**Object adapter or class adapter?** GoF describes two forms. A *class adapter* inherits from the adaptee and implements the target (`class TextWaveAdapter extends TextWaveClient implements SmsGateway`); an *object adapter* holds the adaptee. In Java, prefer the object adapter: it works when the SDK class is `final`, it can adapt any subclass of the adaptee, it hides every vendor method you didn't choose to expose, and a test can hand it a fake client. The class adapter exposes the whole vendor API through your adapter — the leak you were trying to plug.

> **Memory hook.** *A travel plug adapter:* your laptop's plug (the domain port) never changes — the adapter reshapes the wall socket (the vendor) to fit it.
> **Cheat code:** wrong *interface shape* → adapter. The port is defined by YOUR side.
> **Interview line:** *"I'll define the gateway interface in my domain and adapt each vendor to it — a vendor swap becomes a new adapter plus a config change."*

<Trace title="Whose shape wins?" steps={adapter} takeaway="The domain owns the port. Every vendor quirk — formats, units, integer widths, error codes — is translated inside the adapter and nowhere else." />

**When not to use it.**

- **Don't adapt what you would never swap.** Wrapping `java.time`, `java.util.List` or a mature JSON library behind your own interface buys nothing but a second API to learn. Adapters earn their place at **vendor, network and replaceable-infrastructure boundaries**.
- **Don't adapt your own code — change it.** If both sides are yours, make them agree. An adapter between two classes you own is a disagreement you postponed.
- **Don't let the adapter grow decisions.** Retry policy, vendor selection and business rules don't belong in it; it translates. (The next chapter puts retry where it belongs.)

**Your turn.** MediCore's payment vendor, PayLoom, has an SDK too. Your domain already owns the port, in its own words — money is a `long` of whole paise, never a `double`:

```java group=clinic
record Money(long paise) {                                 // whole paise; never a double
    static final Money ZERO = new Money(0);
    Money {
        if (paise < 0) throw new IllegalArgumentException("negative money: " + paise);
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }
    Money plus(Money other) { return new Money(Math.addExact(paise, other.paise)); }
    Money minus(Money other) { return new Money(paise - other.paise); }   // refuses to go negative
    @Override public String toString() {
        return "INR " + paise / 100 + "." + (paise % 100 < 10 ? "0" : "") + paise % 100;
    }
}

record PaymentResult(boolean approved, String reference) {}

interface PaymentProcessor {                               // the port, in MediCore's words
    PaymentResult process(String admissionId, Money amount);
}
```

PayLoom's SDK, as it ships. It counts money in an `int` number of paise ("minor units"), wants a currency code, refuses zero, and answers with HTTP-style status codes:

```java group=clinic
record PayLoomResponse(int status, String txnId, int capturedMinor) {}

class PayLoomSdk {
    final List<String> captures = new ArrayList<>();        // stands in for PayLoom's servers
    PayLoomResponse capture(String orderRef, String currency, int amountMinor) {
        if (amountMinor <= 0) return new PayLoomResponse(422, null, 0);
        captures.add(orderRef + " " + currency + " " + amountMinor);
        return new PayLoomResponse(201, "PL-" + captures.size(), amountMinor);
    }
}
```

Write `PayLoomAdapter`. Oona's sticky note has two weird inputs on it: *a patient who prepaid everything*, and *the corporate account's ₹2.5 crore quarterly settlement*.

<HintLadder hints={hints.payloom} labels={turn}>

```java group=clinic
class PayLoomAdapter implements PaymentProcessor {
    private final PayLoomSdk sdk;
    PayLoomAdapter(PayLoomSdk sdk) { this.sdk = sdk; }

    public PaymentResult process(String admissionId, Money amount) {
        if (amount.paise() == 0) return new PaymentResult(true, "NOTHING-DUE");   // PayLoom refuses zero; our domain doesn't
        int minor;
        try {
            minor = Math.toIntExact(amount.paise());        // long paise -> PayLoom's int minor units, or throw
        } catch (ArithmeticException overLimit) {
            return new PaymentResult(false, null);          // above 2,147,483,647 paise PayLoom can't take it at all
        }
        PayLoomResponse r = sdk.capture("MC-" + admissionId, "INR", minor);
        boolean ok = r.status() == 201 && r.capturedMinor() == minor;              // a partial capture is not a success
        return new PaymentResult(ok, ok ? r.txnId() : null);
    }
}
```

₹9,000 reaches PayLoom as `MC-ADM-2201 INR 900000`. A prepaid patient never reaches PayLoom at all. And ₹2.5 crore is 2,500,000,000 paise — more than an `int` holds (2,147,483,647, about ₹2.15 crore). A plain `(int)` cast would silently send **−1,794,967,296**; `Math.toIntExact` throws instead, and the adapter turns that into a clean decline. The checker runs all three, plus two thousand random amounts on both sides of the limit, plus a vendor that captures only part of the amount.

</HintLadder>

**Catch the trap:** *"The adapter's interface should mirror the vendor's, so nothing gets lost."* Then your "port" is `submitMessage(payload)` with a new name, every vendor quirk is still in the domain, and the next vendor — whose SDK looks nothing like TextWave's — edits every caller. **The port is shaped by what the domain needs, usually far smaller than the vendor's API.** The War Room's rule: an adapter *sized to the one call you actually make*.

**Say it aloud:** *"SmsGateway and PaymentProcessor are ports my domain owns. Each vendor gets an adapter that translates formats, units and error codes — including the int overflow on PayLoom's amounts. Switching vendors is a new adapter and one line in main."*

<h2 id="decorator">Chapter 2 · Sixteen classes for one SMS</h2>

<Scene chapter="Chapter 2" title="Sixteen classes for one SMS" mood="dusk">

The adapter goes live on Monday. By Wednesday, MediCore's operations desk has three tickets.

TextWave drops about two percent of calls, so reminders need **retry**. Bulk campaign blasts need a **rate limit**, or TextWave will throttle the account. And compliance wants every send **logged**. But one-time passwords must never be rate-limited — they're urgent — and the in-app channel needs none of it.

A colleague has started on it. You open the branch. `RetryingTextWaveAdapter`. `RateLimitedTextWaveAdapter`. `RetryingRateLimitedTextWaveAdapter`. A whiteboard photo in the pull request counts the classes still to write: sixteen, once the in-app channel is included.

Wren reads the class list aloud, slowly, the way you'd read a ransom note.

*"Every one of these is an SmsGateway,"* she says. *"So what if each behaviour simply held one?"*

</Scene>

**The mess.** Behaviour added by inheritance, one subclass per combination:

```java fragment
class RetryingTextWaveAdapter extends TextWaveAdapter { /* retry loop around super.send */ }
class RateLimitedTextWaveAdapter extends TextWaveAdapter { /* permit check, then super.send */ }
class RetryingRateLimitedTextWaveAdapter extends RetryingTextWaveAdapter { /* limiter copy-pasted in */ }
class LoggingRetryingRateLimitedTextWaveAdapter extends RetryingRateLimitedTextWaveAdapter { /* ... */ }
// ...one class for each subset of {logging, retry, rate limit}: 2 x 2 x 2 = 8 per vendor.
// Two senders (TextWave, in-app) make 16. A fourth behaviour makes 32. Changing vendor rewrites all of them.
```

**The detection cues.** Class names that are **lists of adjectives** (`LoggingRetryingRateLimited…`). The same behaviour **copy-pasted** into several subclasses because Java has one parent. Requirements phrased as *"also X, and some need Y, and these combinations vary"*. And behaviour bolted to one vendor that should apply to any.

**The pattern: Decorator.** A wrapper that implements the **same interface** it holds. Because it *is* an `SmsGateway` and *has* an `SmsGateway`, wrappers stack in any order, around any implementation, chosen at wiring time:

```java group=clinic
class RateLimitExceededException extends RuntimeException {
    RateLimitExceededException() { super("rate limit exceeded"); }
}

interface RateLimiter { boolean tryAcquire(); }            // the concurrency lesson builds a real token bucket
interface Sleeper { void pause(long millis); }             // injected, so tests never really sleep

class RetryingGateway implements SmsGateway {
    private final SmsGateway inner;                        // same type as itself: THAT is the pattern
    private final int maxAttempts;
    private final Sleeper sleeper;

    RetryingGateway(SmsGateway inner, int maxAttempts, Sleeper sleeper) {
        if (maxAttempts < 1) throw new IllegalArgumentException("maxAttempts must be at least 1");
        this.inner = inner;
        this.maxAttempts = maxAttempts;
        this.sleeper = sleeper;
    }

    public void send(PhoneNumber to, String text) {
        for (int attempt = 1; ; attempt++) {
            try {
                inner.send(to, text);
                return;
            } catch (SmsDeliveryException e) {             // only delivery failures are worth retrying
                if (attempt == maxAttempts) throw e;
                sleeper.pause(100L << (attempt - 1));      // 100 ms, 200 ms, 400 ms, ...
            }
        }
    }
}

class RateLimitedGateway implements SmsGateway {
    private final SmsGateway inner;
    private final RateLimiter limiter;

    RateLimitedGateway(SmsGateway inner, RateLimiter limiter) {
        this.inner = inner;
        this.limiter = limiter;
    }

    public void send(PhoneNumber to, String text) {
        if (!limiter.tryAcquire()) throw new RateLimitExceededException();
        inner.send(to, text);
    }
}

// Wiring: every combination, no new classes.
SmsGateway campaignSms(SmsGateway vendor, RateLimiter limiter, Sleeper sleeper) {
    return new RetryingGateway(new RateLimitedGateway(vendor, limiter), 3, sleeper);
}
SmsGateway otpSms(SmsGateway vendor, Sleeper sleeper) {
    return new RetryingGateway(vendor, 5, sleeper);        // urgent: retry hard, never rate-limit
}
SmsGateway plainSms(SmsGateway vendor) {
    return vendor;                                         // no wrapping is also a choice
}
```

Sixteen planned classes became **two adapters and three wrappers** (the third, logging, is your turn below), and a fourth behaviour would be one more class instead of sixteen more. Notice two design choices the checker pins down: the retry catches **only** `SmsDeliveryException`, so a full rate limiter fails fast instead of being hammered; and the sleeper is **injected**, so tests verify the 100 ms / 200 ms backoff without waiting for it.

<h3 id="order-matters">Order is semantics</h3>

**Interviewers probe this, and it is where decorators stop being a diagram and start being a design decision.** In `campaignSms`, retry sits *outside* the limiter, so every retry attempt re-enters the limiter and spends a permit. Flip the nesting and one logical send costs one permit, however many retries happen inside:

| Wiring | Send fails twice, then succeeds | Permits spent | Vendor calls |
|---|---|---|---|
| `Retrying(RateLimited(vendor))` | each attempt passes the limiter | **3** | 3 |
| `RateLimited(Retrying(vendor))` | one permit, then retries inside | **1** | 3 |

Neither is "correct". Outside-retry protects the *vendor's* rate (TextWave counts calls, not intentions); inside-retry protects *your* quota of logical messages. **Say which you want and why.** The checker runs both wirings on two thousand random combinations of failures, attempts and permits against a hand-simulated oracle — including the edge where the limiter runs dry mid-retry and the `RateLimitExceededException` escapes on attempt three.

This is also how `java.io` works: `new BufferedInputStream(new FileInputStream(f))` — `BufferedInputStream` is an `InputStream` that holds an `InputStream` and adds buffering. `Collections.unmodifiableList(list)` and `Collections.synchronizedList(list)` are decorators too. Cite them; interviewers like hearing that you've used the pattern without knowing it.

**Production scar:** decorators that hop threads lose `ThreadLocal` context — <a href={`${BASE}lld/war/patterns-why/#5-decorator--the-bug-threadlocals-cause-at-thread-boundaries`}>the dossier on exactly that bug</a>, where async writes were silently saved under a default tenant. A decorator that submits work to a pool must capture context *before* submit, restore it inside, and clear it in a `finally` because pool threads are reused.

> **Memory hook.** *Gift wrapping:* every layer wraps a gift and IS a gift — so you can keep wrapping. The order is visible from outside: last wrap = outermost layer = runs first.
> **Cheat code:** same interface + "ALSO needs X, some need Y, combinations vary" → decorator. Combination decided at wiring, not by class explosion.
> **Interview line:** *"Retry and rate-limit become decorators over the gateway; I compose per channel at wiring time — and the nesting order is a semantic decision: outside-retry burns a permit per attempt."*

<Trace title="Wrap it, then count" steps={decorator} takeaway="Decorators add behaviour the caller chose, with the same interface, stacked at wiring time. The nesting order is part of the design: say what each position means." />

**When not to use it.**

- **One caller, one behaviour, forever.** If only OTPs retry and nothing else ever will, a loop in `OtpService` is honest. Decorators pay off when behaviours combine or are shared.
- **Fat interfaces.** A decorator must forward *every* method of the interface. Around a fourteen-method interface, each decorator is fourteen methods of boilerplate — fix the interface first (interface segregation).
- **When identity matters.** A decorated object is a different object: `==`, `equals` and `instanceof TextWaveAdapter` checks no longer see the original. Code that inspects concrete types breaks.
- **Stacks nobody can read.** Seven wrappers deep, a stack trace is a maze. Name the stacks in one wiring method per channel, as above, so the order is written down once.
- **Commands are not cacheable.** "Add a caching decorator to `send()`" silently drops real messages. Caching wraps *queries* — that's next chapter.

**Your turn.** Compliance wants every send logged. Write `LoggingGateway` — then decide, with two wiring methods, whether the log tells one story per *logical send* or one per *vendor call*. Oona's note: *the log must never contain a full phone number.*

<HintLadder hints={hints.logging} labels={turn}>

```java group=clinic
class LoggingGateway implements SmsGateway {
    private final SmsGateway inner;
    private final List<String> log;                        // stands in for a real logger

    LoggingGateway(SmsGateway inner, List<String> log) {
        this.inner = inner;
        this.log = log;
    }

    public void send(PhoneNumber to, String text) {
        String who = mask(to);
        log.add("send " + who);
        try {
            inner.send(to, text);
            log.add("sent " + who);
        } catch (RuntimeException e) {                     // the exception's message holds the full number
            log.add("failed " + who + " " + e.getClass().getSimpleName());
            throw e;
        }
    }

    static String mask(PhoneNumber p) {                    // "+919812345678" -> "+91981234****"
        String n = p.e164();
        return n.substring(0, n.length() - 4) + "****";
    }
}

SmsGateway loggedPerSend(SmsGateway vendor, List<String> log, Sleeper sleeper) {
    return new LoggingGateway(new RetryingGateway(vendor, 3, sleeper), log);     // one story per logical send
}
SmsGateway loggedPerAttempt(SmsGateway vendor, List<String> log, Sleeper sleeper) {
    return new RetryingGateway(new LoggingGateway(vendor, log), 3, sleeper);     // one story per vendor call
}
```

For a send that fails twice and then succeeds, `loggedPerSend` writes **2** lines (`send`, `sent`) and `loggedPerAttempt` writes **6** (`send`/`failed` twice, then `send`/`sent`). Compliance probably wants the first; the on-call engineer debugging TextWave wants the second — and you can have both by wrapping twice. The checker asserts both logs line by line and that no full number appears in any of them.

</HintLadder>

**Catch the trap:** *"Decorator is just inheritance with extra steps."* Inheritance fixes the combination at compile time, couples you to the parent's internals (the <a href={`${BASE}lld/lessons/solid/#composition`}>counter that counted twice</a>), and multiplies classes. A decorator is composition: it knows only the interface, combinations are chosen at runtime, and the class count grows by one per behaviour.

**Say it aloud:** *"Retry, rate-limit and logging are decorators over SmsGateway. Each channel's stack is one wiring method. I put the limiter inside the retry because TextWave counts calls — if you'd rather count logical messages, I flip those two lines."*

If the rule is enforced by "remember to", it will be forgotten; the War Room's <a href={`${BASE}lld/war/patterns-why/#6-proxy--aop--the-leak-on-the-path-nobody-guarded`}>leak on the path nobody guarded</a> is one forgotten getter that read across hospitals.

**The pattern: Proxy.** Same shape as a decorator — implements the interface, holds the real thing — but the intent is **control**: whether, when, where or how the real call happens. Callers are handed the proxy and never know:

```java group=clinic
record User(String id, String role) {}
record History(String patientId, List<String> entries) {}

interface PatientRecords { History fullHistory(String patientId); }
interface AccessPolicy { boolean canReadHistory(User caller, String patientId); }
interface AuditLog { void record(String action, String subject, String detail); }
interface CallerContext { User current(); }                // who is asking: the session, injected

class AccessDeniedException extends RuntimeException {
    AccessDeniedException(String userId, String patientId) { super(userId + " may not read " + patientId); }
}

class RecordsAuthProxy implements PatientRecords {
    private final PatientRecords real;
    private final AccessPolicy policy;
    private final AuditLog audit;
    private final CallerContext caller;

    RecordsAuthProxy(PatientRecords real, AccessPolicy policy, AuditLog audit, CallerContext caller) {
        this.real = real;
        this.policy = policy;
        this.audit = audit;
        this.caller = caller;
    }

    public History fullHistory(String patientId) {
        User who = caller.current();
        if (!policy.canReadHistory(who, patientId)) {          // gate BEFORE the real call
            audit.record("DENIED_HISTORY", who.id(), patientId);
            throw new AccessDeniedException(who.id(), patientId);
        }
        audit.record("READ_HISTORY", who.id(), patientId);     // regulators want reads logged too
        return real.fullHistory(patientId);
    }
}

class TreatingTeamPolicy implements AccessPolicy {         // doctors read their own patients; nobody else does
    private final Map<String, Set<String>> patientsByDoctor;
    TreatingTeamPolicy(Map<String, Set<String>> patientsByDoctor) { this.patientsByDoctor = Map.copyOf(patientsByDoctor); }

    public boolean canReadHistory(User caller, String patientId) {
        return caller.role().equals("DOCTOR")
            && patientsByDoctor.getOrDefault(caller.id(), Set.of()).contains(patientId);
    }
}

// Wiring: the ONLY PatientRecords anyone is handed is the proxy.
PatientRecords guardedRecords(PatientRecords certified, AccessPolicy policy, AuditLog audit, CallerContext caller) {
    return new RecordsAuthProxy(certified, policy, audit, caller);
}
```

The certified service is untouched; the policy is its own class (it will change for different reasons than the audit format); and **the guarantee comes from wiring, not discipline** — if the composition root never hands out the raw service, there is no unguarded path. The checker runs two thousand random (user, patient, assignment) requests and confirms the real service was called exactly as often as the policy allowed, with one audit line per request either way.

<h3 id="proxy-kinds">Four reasons to stand in front</h3>

GoF names proxies by what they control. The structure never changes; the reason does.

| Kind | Controls | MediCore example | JDK / framework example |
|---|---|---|---|
| **Protection** | *whether* the call happens | `RecordsAuthProxy` | Spring Security's `@PreAuthorize` |
| **Virtual** | *when* the expensive object is created | `LazyScan` below | Hibernate's lazy-loaded associations |
| **Caching** | *whether the real object is needed at all* | `CachingEligibility` (your turn) | Spring's `@Cacheable` |
| **Remote** | *where* the real object lives | the insurer's eligibility API, called as if local | Java RMI stubs; declarative HTTP clients (Spring's `@HttpExchange` interfaces, Feign) |

A **virtual proxy** answers cheap questions itself and creates the real object only on first real use. MediCore's MRI scans live in cold storage; the scan list shows twenty of them, and a doctor opens one:

```java group=clinic
interface Scan {
    String id();
    byte[] pixels();
}

class LazyScan implements Scan {                           // a virtual proxy: stands in until you really look
    private final String id;
    private final Function<String, Scan> archive;          // the expensive load from cold storage
    private Scan real;                                     // null until the first pixels() call

    LazyScan(String id, Function<String, Scan> archive) {
        this.id = id;
        this.archive = archive;
    }

    public String id() { return id; }                      // answered without loading anything

    public byte[] pixels() {
        if (real == null) real = archive.apply(id);        // load once, on first real use
        return real.pixels();
    }
}
```

Listing twenty scans loads nothing; opening one loads it once, however often it's redrawn. (This version is for one viewer thread. Shared across threads, the null check is a race — two threads can both load; you'd synchronize it or use a thread-safe memoizer.)

A **remote proxy** makes a network call look like a method call. That is its power and its danger: the caller sees `check(policyId)` and cannot tell it may take seconds, time out, or fail halfway. The War Room's <a href={`${BASE}lld/war/inventory/`}>inventory</a> counts eighteen declarative HTTP clients in the production codebase — all generated remote proxies. When you write one, put timeouts in it and let failures surface as your domain's exceptions.

<h3 id="dynamic-proxy">The proxy nobody writes by hand</h3>

The industrial form is the **dynamic proxy**: a class generated at runtime that implements an interface and sends every call to one handler. The JDK has had it since Java 1.3 in `java.lang.reflect.Proxy`, and frameworks build AOP on it (or on bytecode-generated subclasses, for classes without interfaces). Here is the whole mechanism, compiled and tested:

```java group=clinic
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;

@SuppressWarnings("unchecked")
<T> T traced(Class<T> port, T target, List<String> calls) {
    InvocationHandler handler = (proxy, method, args) -> {
        calls.add(method.getName());                       // runs before EVERY call made on the proxy
        try {
            return method.invoke(target, args);
        } catch (InvocationTargetException e) {
            throw e.getCause();                            // rethrow the target's own exception, unwrapped
        }
    };
    return (T) Proxy.newProxyInstance(port.getClassLoader(), new Class<?>[] { port }, handler);
}

interface Ward {
    void admit(String patientId);
    void admitAll(List<String> patientIds);
}

class GeneralWard implements Ward {
    final List<String> beds = new ArrayList<>();

    public void admit(String patientId) {
        if (beds.contains(patientId)) throw new IllegalStateException(patientId + " is already admitted");
        beds.add(patientId);
    }

    public void admitAll(List<String> patientIds) {
        for (String id : patientIds) admit(id);            // this.admit(): a plain call on the target
    }
}
```

`traced(Ward.class, new GeneralWard(), calls)` returns an object that is a `Ward`, records every method name, and forwards. One handler can trace, time, authorize or transact *any* interface — that is how Spring applies `@Transactional` and `@PreAuthorize` without you writing a proxy class.

Now the follow-up every Java interviewer eventually asks. Call `proxy.admitAll(List.of("P-1", "P-2"))`. Both patients are admitted — but `calls` contains only **`["admitAll"]`**. Inside `GeneralWard`, `admit(id)` means `this.admit(id)`, and `this` is the real object, not the proxy. **Self-invocation bypasses the proxy.** In Spring, that is why a `@Transactional` method called from another method of the same bean runs without its own transaction advice. The checker runs exactly this, and also confirms the handler rethrows the target's `IllegalStateException` itself rather than a reflective wrapper. Fixes: move the inner method to another bean, or call it through the proxy.

**Proxy vs decorator in one breath** (they compile identically): a decorator *adds a feature the caller wants* (retry); a proxy *controls access the caller doesn't get a say in* (auth, lazy-load, cache). Intent, not structure.

> **Memory hook.** *The bouncer:* same door, same club behind it — but the bouncer decides whether you get in, and writes your name in the log either way. A gift-wrapper (decorator) makes the gift better; a bouncer (proxy) decides if you reach it.
> **Cheat code:** "check / defer / cache / log BEFORE the real call, caller unaware" → proxy.
> **Interview line:** *"Access control wraps as a proxy so the record service stays pure — and in Spring this is exactly what @PreAuthorize generates, with the self-invocation caveat."*

<Trace title="Who gets through the door?" steps={proxy} takeaway="Same shape as a decorator; different job. A proxy decides whether, when, where or how the real call happens — and it only sees calls made on the proxy." />

**When not to use it.**

- **Don't hide the network.** A remote proxy that makes a 2-second call look like a getter invites callers to put it in a loop. Name it so the cost is visible, and give it timeouts.
- **Don't cache without an owner for staleness.** A caching proxy serves old answers by design. Someone must decide how old is acceptable — the TTL is a business decision.
- **Don't rely on a proxy you can route around.** If code can reach the real object directly (a second bean, a static accessor, `this`), the guarantee is a suggestion. The production <a href={`${BASE}lld/war/inventory/#flagged-findings`}>flagged findings</a> include an AOP pointcut bound by a string that no compiler checks.
- **Don't proxy for one caller.** If exactly one screen reads the records and always will, a check in that screen is simpler. The proxy earns its place when callers multiply.

**Your turn.** MediCore's insurer exposes a slow remote eligibility check. Answers change rarely — a policy's cover holds for at least ten minutes. Write a caching proxy that counts hits and misses, expires entries after a TTL, and takes its clock as a dependency so a test can control time:

```java group=clinic
record Eligibility(boolean covered, Money cap) {}

interface EligibilityService { Eligibility check(String policyId); }   // a slow call to the insurer
```

<HintLadder hints={hints.cache} labels={turn}>

```java group=clinic
class CachingEligibility implements EligibilityService {
    private record Entry(Eligibility value, long storedAt) {}

    private final EligibilityService real;
    private final long ttlMillis;
    private final LongSupplier clockMillis;
    private final Map<String, Entry> cache = new HashMap<>();
    int hits, misses;

    CachingEligibility(EligibilityService real, long ttlMillis, LongSupplier clockMillis) {
        this.real = real;
        this.ttlMillis = ttlMillis;
        this.clockMillis = clockMillis;
    }

    public Eligibility check(String policyId) {
        long now = clockMillis.getAsLong();
        Entry e = cache.get(policyId);
        if (e != null && now - e.storedAt() < ttlMillis) {
            hits++;
            return e.value();
        }
        misses++;
        Eligibility fresh = real.check(policyId);          // if this throws, nothing is cached
        cache.put(policyId, new Entry(fresh, now));
        return fresh;
    }
}
```

With a long TTL, lookups `P1, P2, P1, P1, P3, P2` give **3 misses and 3 hits**, and the insurer is called 3 times. With a 10-minute TTL, a repeat at 9:59.999 is a hit and at exactly 10:00 a miss. The checker replays hundreds of random lookup sequences (twelve thousand lookups) with random clock jumps against an independent simulation, and confirms a failing insurer call is never cached. For production: this map is unbounded and single-threaded — use `ConcurrentHashMap` with an eviction policy, or a library cache such as Caffeine.

</HintLadder>

**Catch the trap:** *"A proxy and a decorator are different because proxies are generated."* Hand-written proxies (`RecordsAuthProxy`) are proxies; generated wrappers can be decorators. The full-marks answer is: **structure identical, intent differs** — a decorator *adds* what the caller chose; a proxy *controls* what the caller can't bypass.

**Say it aloud:** *"I won't touch the certified records service. The composition root hands out only a RecordsAuthProxy, which checks the treating-team policy and audits every read before delegating. If this were Spring, that's @PreAuthorize — and I'd watch for self-invocation, because calls on this never cross the proxy."*

**The pattern: Facade.** One class exposing the *use case*, hiding the choreography:

```java group=clinic
record Bill(String admissionId, PhoneNumber patientPhone, Money total, Money paidSoFar) {
    Money pendingDue() { return total.minus(paidSoFar); }
}

interface BillingService { Bill finalizeBill(String admissionId); }
interface PharmacyService { void dispenseTakeHome(String admissionId); }
record DischargeSummary(Bill bill, PaymentResult paid) {}

class DischargeFacade {
    private final BillingService billing;
    private final PaymentProcessor payments;               // Chapter 1's port, PayLoom behind it
    private final PharmacyService pharmacy;
    private final SmsGateway sms;                          // Chapter 2's decorated gateway
    private final AuditLog audit;                          // Chapter 3's audit log

    DischargeFacade(BillingService billing, PaymentProcessor payments,
                    PharmacyService pharmacy, SmsGateway sms, AuditLog audit) {
        this.billing = billing;
        this.payments = payments;
        this.pharmacy = pharmacy;
        this.sms = sms;
        this.audit = audit;
    }

    DischargeSummary discharge(String admissionId) {
        Bill bill = billing.finalizeBill(admissionId);                          // 1. freeze the bill
        PaymentResult paid = payments.process(admissionId, bill.pendingDue());  // 2. settle dues
        pharmacy.dispenseTakeHome(admissionId);                                 // 3. meds out
        audit.record("DISCHARGE", admissionId, paid.reference());               // 4. compliance FIRST
        sms.send(bill.patientPhone(), "Discharge complete. Bill: " + bill.total());  // 5. then notify
        return new DischargeSummary(bill, paid);
    }
}
```

GoF adds a point people forget: **a facade doesn't have to lock the subsystems away.** Callers with unusual needs may still use `BillingService` directly; the facade is the easy, safe path for the common use case, not a wall.

> **Memory hook.** *Hotel front desk:* you say "check me out" — the desk calls housekeeping, billing and the valet. You never phone the valet yourself.
> **Cheat code:** every caller re-implementing the same multi-subsystem sequence → facade. It sequences, it never decides.
> **Interview line:** *"I'll expose the use case as a facade so the five-step choreography exists exactly once — callers can't forget the audit step, because they never see the steps."*

The discriminator is **coordinates vs decides**. A God class *decides*: bill math, discount rules, stock logic all inline. The facade holds **zero business rules** — bill math lives in `BillingService`, stock logic in `PharmacyService`; the facade knows only the *sequence*. Sequencing one use case IS a single responsibility (SRP applied to entry points). The tell in code review: if the facade grows an `if` about money or medicine, logic is leaking in — push it down.

</Reveal>

**When not to use it.**

- **One caller, one subsystem.** A facade over a single service with a single caller is a pass-through class. Wait for the second caller or the second system.
- **Facades of facades.** If you need a facade to simplify your facade, the use cases have blurred together. Split by use case: `DischargeFacade`, `AdmissionFacade` — not `HospitalFacade`.
- **When it starts deciding.** The day `discharge()` computes a senior-citizen discount, it has become the God class it was protecting you from.

```java group=clinic
class DischargeBlockedException extends RuntimeException {
    DischargeBlockedException(String admissionId, String reason) { super(admissionId + ": " + reason); }

class GuardedDischargeFacade {
    private final BillingService billing;
    private final PaymentProcessor payments;
    private final PharmacyService pharmacy;
    private final SmsGateway sms;
    private final AuditLog audit;

    GuardedDischargeFacade(BillingService billing, PaymentProcessor payments,
                           PharmacyService pharmacy, SmsGateway sms, AuditLog audit) {
        this.billing = billing;
        this.payments = payments;
        this.pharmacy = pharmacy;
        this.sms = sms;
        this.audit = audit;
    }

    DischargeSummary discharge(String admissionId) {
        Bill bill = billing.finalizeBill(admissionId);
        PaymentResult paid = payments.process(admissionId, bill.pendingDue());
        if (!paid.approved()) {                            // stop BEFORE anything leaves the building
            audit.record("DISCHARGE_BLOCKED", admissionId, "payment declined");
            throw new DischargeBlockedException(admissionId, "payment declined");
        }
        pharmacy.dispenseTakeHome(admissionId);
        audit.record("DISCHARGE", admissionId, paid.reference());
        try {
            sms.send(bill.patientPhone(), "Discharge complete. Bill: " + bill.total());
        } catch (RuntimeException smsDown) {               // a failed text never undoes a discharge
            audit.record("DISCHARGE_SMS_FAILED", admissionId, smsDown.getClass().getSimpleName());
        }
        return new DischargeSummary(bill, paid);
    }
}
```

Is `if (!paid.approved())` an "if about money" leaking in? No — and the difference is worth saying: the facade doesn't decide *what is owed* or *whether a card is good*; it decides **whether to continue the sequence** given a result. That is failure policy, and the War Room's facade dossier puts it exactly here. The checker asserts the exact call list for both of Oona's inputs: after a decline, billing, payment and a `DISCHARGE_BLOCKED` audit, then an exception; with SMS down, a returned summary and a `DISCHARGE_SMS_FAILED` audit line.

</HintLadder>

**Catch the trap:** *"A facade is just a class that calls other classes."* So is every class. A facade is a **new, smaller interface over a subsystem, for one use case**, and it is graded on two things: callers can no longer get the sequence wrong, and no business rule lives inside it.

**Say it aloud:** *"Discharge touches five services and three callers were each doing the sequence, so I'll put it behind a DischargeFacade. It owns the order and the failure policy — a declined payment stops before pharmacy, a failed SMS is audited but doesn't undo the discharge. Bill math stays in billing."*

<h2 id="composite">Chapter 5 · The bill is a tree</h2>

<Scene chapter="Chapter 5" title="The bill is a tree">

MediCore's sample bill is four pages long because inpatient bills nest. Room charges sit at the top. Beside them, a *surgery package* contains the surgeon's fee and operating-theatre charges — and an *anesthesia* group inside the package, with its own items.

The prototype's `BillCalculator` has a method for charges, a method for packages, and a method for "packages that contain packages", which stops at two levels because that was the deepest anyone had seen.

On Friday, the cardiac ward sends a bill three levels deep. The total is ₹8,000 short.

Wren turns the printout sideways so the indentation becomes branches. *"Does the person reading the total care whether a line is a charge or a package of packages?"*

</Scene>

**The mess.** Code that asks every node what it is:

```java fragment
long total(Object node) {
    if (node instanceof Charge c) return c.amount();
    if (node instanceof Package p) {
        long sum = 0;
        for (Object child : p.items()) {
            if (child instanceof Charge c) sum += c.amount();
            else if (child instanceof Package inner)                  // two levels, because that's all we'd seen
                for (Charge c : inner.charges()) sum += c.amount();   // a third level is silently skipped
        }
        return sum;
    }
    throw new IllegalArgumentException("unknown bill node");
}
```

**The detection cue.** **A part–whole hierarchy where callers want to treat one and many the same way.** File systems (a folder's size is its contents' size), org charts, UI component trees, nested bills, a garage of levels of zones of spots. In code: `instanceof` ladders over "single" and "group" types, and recursion depth limits that match the deepest example someone happened to see.

**The pattern: Composite.** One interface; leaves implement it directly, containers implement it by asking their children:

```java group=clinic
interface BillNode { Money total(); }

record Charge(String description, Money amount) implements BillNode {
    public Money total() { return amount; }                // leaf: my own amount
}

class ChargeGroup implements BillNode {
    private final String name;
    private final List<BillNode> children = new ArrayList<>();   // leaves OR groups: same type

    ChargeGroup(String name) { this.name = name; }

    ChargeGroup add(BillNode child) {
        children.add(child);
        return this;
    }

    String name() { return name; }

    public Money total() {                                 // container: sum of children, at any depth
        return children.stream().map(BillNode::total).reduce(Money.ZERO, Money::plus);
    }
}

BillNode admissionBill() {                                 // building the bill reads like the bill itself
    return new ChargeGroup("Admission ADM-2201")
        .add(new Charge("Room, 3 nights", Money.rupees(9000)))
        .add(new ChargeGroup("Surgery package")
            .add(new Charge("Surgeon fee", Money.rupees(40000)))
            .add(new Charge("OT charges", Money.rupees(15000)))
            .add(new ChargeGroup("Anesthesia")
                .add(new Charge("Anesthetist", Money.rupees(8000)))
                .add(new Charge("Drugs", Money.rupees(2500)))));
}
```

`admissionBill().total()` is **₹74,500**: the room's ₹9,000 plus a ₹65,500 surgery package, which includes the ₹10,500 anesthesia group. One call at the root; the tree recurses itself, to any depth. The checker builds a thousand random trees up to seven levels deep and compares every root total with a flat sum of the leaves.

**Where does `add` live?** GoF describes two versions. The *transparent* composite puts `add`/`remove` on the shared interface, so leaves and groups look identical — and then `Charge.add` can only throw, which is a Liskov violation built into the interface. The *safe* composite, used here, puts `add` only on `ChargeGroup`: code that *builds* the tree knows which nodes are groups; code that *uses* it (`total`) never needs to. Prefer the safe version and say why.

Recognition cue: **part–whole hierarchy + "treat one and many uniformly"**. Follow-up to expect: *"now print an itemized statement AND compute GST per category"* — two-plus operations over one stable tree is Visitor's cue (<a href={`${BASE}lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree`}>Drill 4</a> builds exactly this pair).

> **Memory hook.** *Folders in folders:* a folder's size = the sum of its contents, and you never care if an item is a file or another folder. Bill groups are folders; charges are files.
> **Cheat code:** tree + "one and many treated alike" → composite. Second operation over the tree → visitor incoming.
> **Interview line:** *"Charges and packages share one BillNode interface, so totals are a single recursive call — and if you add more operations over the tree, I'd bring in Visitor rather than bloat the node interface."*

<Reveal q="Follow-up lands: “now print an itemized statement AND compute GST per category.” Why not just add print() and gst() to BillNode?">

Two operations today, five next quarter (insurance claim format, discount audit, export…) — every new operation edits **every node class**. The tree *structure* is stable; the *operations* over it multiply. That's Visitor's exact cue: one `accept(Visitor)` on the nodes, then each new operation is one new visitor class, zero node edits. Trade-off to say aloud: Visitor makes adding operations cheap but adding node *types* expensive — you're betting the structure is done growing. <a href={`${BASE}lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree`}>Drill 4</a> builds this pair; the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> covers Visitor itself.

</Reveal>

<Trace title="Walk the tree" steps={composite} takeaway="Leaves answer for themselves; containers answer by asking their children. Keep add() on the container, keep the structure a tree, and reach for Visitor when operations multiply." />

**When not to use it.**

- **Fixed depth, different types.** Hospital → Ward → Bed, where each level has different operations (wards have nurses, beds have patients), is better as three plain classes. Composite pays off when every level answers the *same* questions.
- **Few shared operations.** If leaves and containers have one method in common and ten that differ, forcing a shared interface creates the transparent-composite lie.
- **Cycles.** A composite must be a tree. Oona's weird input — `group.add(group)` — makes `total()` recurse forever (the checker shows the `StackOverflowError`). Build trees bottom-up from finished children, or reject adding an ancestor.

**Your turn.** Bram's Tuesday card, from the Copperline Garage: *"The display board at the entrance should show free spots for the whole garage, for each level, and — next month — for each zone."* Model it so the board asks a level exactly what it would ask a single spot.

```java group=garage
interface ParkingArea {
    int capacity();
    int free();
}

class Spot implements ParkingArea {                        // the leaf
    private final String id;
    private boolean occupied;

    Spot(String id) { this.id = id; }

    void park() {
        if (occupied) throw new IllegalStateException(id + " is taken");
        occupied = true;
    }
    void leave() { occupied = false; }

    public int capacity() { return 1; }
    public int free() { return occupied ? 0 : 1; }
}

class Section implements ParkingArea {                     // a level, a zone, a row: any grouping
    private final String name;
    private final List<ParkingArea> parts = new ArrayList<>();

    Section(String name) { this.name = name; }

    Section add(ParkingArea part) {
        parts.add(part);
        return this;
    }

    String name() { return name; }
    public int capacity() { return parts.stream().mapToInt(ParkingArea::capacity).sum(); }
    public int free() { return parts.stream().mapToInt(ParkingArea::free).sum(); }
}
```

One `Section` class serves levels, zones and rows, so "per zone next month" is a change to how the tree is *built*, not to any class. The board calls `free()` on the garage, then on each level. The checker builds a thousand random garages, parks cars at random, and compares every `free()` and `capacity()` with a flat count over the spots.

</HintLadder>

**Catch the trap:** *"Composite is for trees, so any tree is a composite."* A tree whose nodes answer different questions is just a tree. **Composite is the decision that one and many answer the same interface**, so callers stop asking what they are holding.

**Say it aloud:** *"The bill is a part–whole tree, so charges and groups share BillNode and total() recurses. I keep add() on the group only — a charge can't honour it. If you want statements and tax over the same tree, that's Visitor."*

<Scene chapter="Chapter 6" title="Nine invoice classes" mood="dawn">

**The mess.** One subclass per (kind × format) pair:

**The detection cue.** **Class names that are two words from two lists** (`PharmacyHtml…`, `LabEmail…`), and a new item on either list costs one class *per item on the other list*. Duplicated code along one axis (the HTML markup) is the second symptom.

**The pattern: Bridge.** Split the two dimensions into two hierarchies and connect them with a reference — the "bridge". The **abstraction** (what is billed) holds an **implementor** (how it's drawn):

```java group=invoices
record LineItem(String label, long paise) {}

interface Renderer {                                       // implementation side: HOW it is drawn
    String header(String title);
    String line(LineItem item);
    String footer(long totalPaise);

    static String rupees(long paise) {
        return paise / 100 + "." + (paise % 100 < 10 ? "0" : "") + paise % 100;
    }
}

abstract class Invoice {                                   // abstraction side: WHAT is billed
    private final Renderer renderer;                       // the bridge

    Invoice(Renderer renderer) { this.renderer = renderer; }

    abstract String title();
    abstract List<LineItem> items();

    final String render() {
        StringBuilder out = new StringBuilder(renderer.header(title()));
        long total = 0;
        for (LineItem item : items()) {
            out.append(renderer.line(item));
            total += item.paise();
        }
        return out.append(renderer.footer(total)).toString();
    }
}
```

The two sides grow independently. Invoice kinds know their lines and nothing about markup:

**Bridge, Strategy, Adapter — honest distinctions.** In Java, a bridge's abstraction holding its implementor looks exactly like an object holding a strategy, and some textbooks treat them as close cousins. The name signals intent: **Strategy** swaps one algorithm inside one class; **Bridge** says *both sides are hierarchies that will keep growing independently*, and you designed the split up front. **Adapter** is the opposite timing: a retrofit to make an existing class fit. > **Memory hook.** *A universal remote and any TV:* the remotes (basic, voice, kids') vary on one side, the TVs (brands) on the other, and one agreed protocol between them means any remote drives any TV. Nobody builds a "kids' remote for brand X".
> **Cheat code:** class names built from two lists → bridge. m × n becomes m + n.
> **Interview line:** *"Invoice type and output format vary independently, so I'll bridge them: Invoice holds a Renderer. Three types and three formats are six classes, not nine, and a new printer is one class."*

**When not to use it.**

- **Only one dimension varies.** Three invoice kinds that only ever render as HTML need no bridge; an HTML method on each, or one shared formatter, is enough.
- **Speculative second dimension.** "We might print them someday" is not a second axis. Extract the renderer when the second format arrives — the same honest-OCP rule as the SOLID lesson's CSV side quest.
- **The dimensions aren't independent.** If thermal receipts must show different *content* (no table, a QR code instead of line items), the axes are coupled, and forcing them through one `Renderer` interface produces special cases on both sides.

<h2 id="flyweight">Chapter 7 · Two hundred thousand paracetamols</h2>

<Scene chapter="Chapter 7" title="Two hundred thousand paracetamols" mood="storm">

The pharmacy dashboard loads a day of dispensing across all eleven clinics: about two hundred thousand lines. Each line says what was dispensed, to whom, how many.

On the first Monday of the month, it runs out of memory.

You take a heap histogram. The top entries are strings — "Paracetamol", "500 mg", the same manufacturer's name — and `DrugInfo` objects, two hundred thousand of them, for twelve hundred distinct drugs. Every line was loaded with its own copy of the drug's description.

Wren looks at the histogram for a long time. *"How many paracetamols are there?"*

"Thousands of lines."

*"I asked how many paracetamols."*

</Scene>

**The mess.** Each row from the database builds its own description of the drug, even the four-thousandth paracetamol:

```java id=pharmacyMess
record DrugInfo(String code, String name, String strength, String manufacturer) {}
record DispenseLine(DrugInfo drug, String patientId, int quantity) {}
record Row(String code, String name, String strength, String manufacturer, String patientId, int quantity) {}

List<DispenseLine> load(List<Row> rows) {
    List<DispenseLine> lines = new ArrayList<>(rows.size());
    for (Row r : rows)                                     // a fresh DrugInfo for every row
        lines.add(new DispenseLine(new DrugInfo(r.code(), r.name(), r.strength(), r.manufacturer()), r.patientId(), r.quantity()));
    return lines;
}
```

**The detection cue is a measurement, not a hunch:** a heap histogram (`jmap -histo`, or a JFR recording) dominated by **many objects that are equal to each other**, holding **immutable** data, where the number of *distinct* values is far smaller than the number of objects.

**The pattern: Flyweight.** Split the state in two. **Intrinsic** state is the same wherever the object appears and never changes — the drug's name, strength, manufacturer — so one shared, immutable object can serve every line. **Extrinsic** state differs per use — the patient, the quantity — so it stays outside the shared object. A small factory hands out the shared instances:

```java group=pharmacy
record DrugInfo(String code, String name, String strength, String manufacturer) {}   // intrinsic: shared, immutable
record DispenseLine(DrugInfo drug, String patientId, int quantity) {}              // extrinsic: this line only
record Row(String code, String name, String strength, String manufacturer, String patientId, int quantity) {}

class DrugCatalog {                                        // the flyweight factory
    private final Map<String, DrugInfo> byCode = new ConcurrentHashMap<>();

    DrugInfo intern(Row r) {                               // first sighting creates; every repeat shares
        return byCode.computeIfAbsent(r.code(), code -> new DrugInfo(code, r.name(), r.strength(), r.manufacturer()));
    }

    int size() { return byCode.size(); }
}

List<DispenseLine> load(List<Row> rows, DrugCatalog catalog) {
    List<DispenseLine> lines = new ArrayList<>(rows.size());
    for (Row r : rows) lines.add(new DispenseLine(catalog.intern(r), r.patientId(), r.quantity()));
    return lines;
}
```

Two hundred thousand lines across twelve hundred drugs now hold **1,200** `DrugInfo` objects instead of **200,000**, and every line for the same drug points at the *same* object. The checker loads exactly that day with fresh strings per row (as a database driver would produce) and counts distinct objects by identity in both versions. `ConcurrentHashMap.computeIfAbsent` is atomic, so two loader threads can't create two paracetamols. Records make the intrinsic part immutable — **which is not optional**: if one line could change its drug's strength, it would change it for every patient.

  <Mermaid code={`classDiagram

    }

      <<shared>>
      +String code
      +String name

    }

You've used flyweights all along. **`Integer.valueOf`** always caches −128 to 127, so `Integer.valueOf(127) == Integer.valueOf(127)` is guaranteed `true`; outside that range it may or may not be (the cache can be enlarged), which is why boxed numbers are compared with `equals`. **String literals** are interned and shared. **Enum constants** are the purest flyweight in Java: a closed set of shared, immutable instances the JVM manages for you. And G1's string deduplication (<a href="https://openjdk.org/jeps/192">JEP 192</a>) is a flyweight the garbage collector applies to duplicate strings on its own.

> **Memory hook.** *A font:* a document with ten thousand letter e's stores one shape for "e" and ten thousand positions. The shape is intrinsic; where it's drawn is extrinsic.
> **Cheat code:** measured memory pressure + many equal immutable objects → flyweight. Split intrinsic from extrinsic; share the first, pass the second.
> **Interview line:** *"The drug description is identical across thousands of lines, so it's a shared immutable flyweight from a catalog keyed by code; quantity and patient stay on the line. 200,000 copies become 1,200."*

<Trace title="How many paracetamols?" steps={flyweight} takeaway="Share what is identical and immutable; keep what differs per use outside the shared object. And measure first: flyweight is a memory optimisation, so it needs a memory problem." />

**When not to use it.**

- **No measured memory problem.** Two thousand objects is nothing. Flyweight adds a factory, an identity-sensitive design and a split state model; it needs a heap histogram to justify it.
- **The "shared" part is mutable.** Then sharing is a bug factory: one caller's change is every caller's change.
- **Few duplicates.** If most values are distinct, the factory's map costs memory and saves none.

**Your turn.** Back at Copperline, Bram's new display board draws all 2,000 spots as small glyphs — bike, car or EV, free or taken. The prototype makes a glyph object per spot that stores its own position. Make the glyphs flyweights in the purest GoF form: the glyph stores only intrinsic state, and **the position is passed in when drawing**.

<HintLadder hints={hints.glyphs} labels={turn}>

```java group=glyphs
enum SpotKind { BIKE, CAR, EV }

class SpotGlyph {                                          // intrinsic only: what it looks like
    private final SpotKind kind;
    private final boolean occupied;
    SpotGlyph(SpotKind kind, boolean occupied) {
        this.kind = kind;
        this.occupied = occupied;
    }
    String draw(int x, int y) {                            // extrinsic state arrives as arguments
        return kind + (occupied ? "#" : ".") + "@" + x + "," + y;
    }
}

class GlyphFactory {
    private record Key(SpotKind kind, boolean occupied) {}
    private final Map<Key, SpotGlyph> glyphs = new HashMap<>();

    SpotGlyph glyph(SpotKind kind, boolean occupied) {
        return glyphs.computeIfAbsent(new Key(kind, occupied), k -> new SpotGlyph(k.kind(), k.occupied()));
    }

    int created() { return glyphs.size(); }
}
```

Two thousand spots, at most **6** glyph objects (3 kinds × free/taken). `glyph(EV, false).draw(3, 4)` gives `EV.@3,4`. With a set this small and closed, a six-constant enum would be the same flyweight with the JVM as the factory — a fine answer to say aloud.

</HintLadder>

**Catch the trap:** *"Flyweight is an object pool."* A pool lends out **interchangeable mutable** objects (connections, threads) to one user at a time, who gives them back. A flyweight is **shared immutable** state used by many at once, never returned. Confusing them in a round is a common, avoidable mark-down.

**Say it aloud:** *"Before optimising I'd look at a heap histogram. If it shows two hundred thousand copies of twelve hundred drug descriptions, I'd make DrugInfo an immutable flyweight from a catalog keyed by code and keep quantity and patient on each line."*

<h2 id="tell-them-apart">Chapter 8 · They all wrap something</h2>

<Scene chapter="Chapter 8" title="They all wrap something" mood="night">

The Interviewer has let you draw for forty minutes. Your notification design has an adapter for the SMS vendor, a retry wrapper around it, and a guard in front of the user-preferences service.

They point at the retry wrapper with their pen. *"Is that a decorator or a proxy?"*

Then at the guard. *"And that one?"*

Then at the adapter. *"Couldn't that be a facade?"*

Three boxes. Identical arrows. You realise the diagram can't answer for you.

</Scene>

**Structure is not the answer; intent is.** Adapter, Decorator, Proxy and Facade all hold an object and forward to it. What separates them is the shape of the interface they offer *relative to what they wrap*, and *why* they exist:

| Pattern | Interface vs wrapped object | How many wrapped | Who chose the wrapper | Intent in one word | Story beat | Hook |
|---|---|---|---|---|---|---|
| **Adapter** | **different** — theirs → yours | one | you, to fit a misfit | translate | TextWave SDK | travel plug |
| **Decorator** | **same** — stacks | one (which may itself be wrapped) | the caller's wiring, per need | add | retry + rate limit | gift wrap |
| **Proxy** | **same** — usually single | one | the system; caller unaware | control | records auth | bouncer |
| **Facade** | **new, smaller** — over many | many | you, to simplify a use case | simplify | discharge button | front desk |
| **Composite** | same, over a **tree** | many children | the structure | unify | bill tree | folders |
| **Bridge** | abstraction holds implementor | one, by design | the design, up front | decouple | invoice × renderer | universal remote |
| **Flyweight** | shared object + passed-in state | shared by many | a factory | share | drug catalog | a font |

Three one-line discriminators for the round:

- **Adapter vs Facade:** an adapter makes **one** existing interface fit another that *already exists* (your port). A facade **invents** a new, simpler interface over **many** objects.
- **Decorator vs Proxy:** same structure. Decorator **adds** behaviour the caller chose and can stack; proxy **controls** access the caller doesn't know about. If removing it changes *what the feature does*, it's a decorator; if removing it changes *whether, when or where the call happens*, it's a proxy.
- **Adapter vs Decorator:** an adapter changes the **interface** and keeps the behaviour; a decorator keeps the **interface** and changes the behaviour.

    I -->|"yes, many objects,\none use case"| FA["Facade\nsimplify"]
    I -->|"no, same interface"| C{"Who wants\nthe extra behaviour?"}

    S -->|"two dimensions\nmultiplying classes"| BR["Bridge"]

</Figure>

<Trace title="Which wrapper is it?" steps={tellApart} takeaway="Ask two questions: does the caller see a different interface, and who wanted the wrapper? Different + one object = adapter; different + many = facade; same + caller's choice = decorator; same + system's control = proxy." />

**Patterns compose — and the order tells a story.** By now MediCore's SMS path reads, from the outside in: *logging (decorator) → retry (decorator) → rate limit (decorator) → TextWaveAdapter (adapter) → TextWave SDK*, and the discharge facade holds that whole stack as "the SMS gateway". Being able to narrate a stack like that — what each layer is, why it sits where it does — is what an interviewer means by "explain your design".

**Catch the trap:** *"It holds a reference and forwards calls, so it's a proxy."* Every one of the four does that. Name the pattern by **what the caller sees** and **why the wrapper exists**, and say the alternative you rejected: *"same interface and the caller doesn't choose it, so proxy rather than decorator."*

<h2 id="sq-footer">Side quest 1 · The opt-out footer</h2>

**The ticket says:** *"Legal: every marketing SMS must end with 'Reply STOP to opt out.' One-time passwords and appointment reminders must not."*

**Where it lands:** a **Decorator** around the campaign stack only. The behaviour applies to whatever gateway the campaign uses — today TextWave, next year someone else — and to no other channel.

<Reveal q="Why not add the footer inside TextWaveAdapter?">

Because the rule is about *marketing messages*, not about TextWave. Inside the adapter it would also land on OTPs and reminders (wrong), and it would vanish the day MediCore switches vendors (also wrong). The adapter translates; it doesn't decide what a message says. The decorator sits exactly where the rule applies: on the campaign channel's wiring.

</Reveal>

<HintLadder hints={hints.footer} labels={turn}>

```java group=clinic
class OptOutFooterGateway implements SmsGateway {
    static final String FOOTER = " Reply STOP to opt out.";
    private final SmsGateway inner;

    OptOutFooterGateway(SmsGateway inner) { this.inner = inner; }

    public void send(PhoneNumber to, String text) {
        inner.send(to, text.endsWith(FOOTER) ? text : text + FOOTER);   // wrapping twice still adds it once
    }
}

SmsGateway marketingSms(SmsGateway vendor, RateLimiter limiter, Sleeper sleeper) {
    return new OptOutFooterGateway(campaignSms(vendor, limiter, sleeper));   // OTP and reminder wiring untouched
}
```

"Flu shots this week." goes out as "Flu shots this week. Reply STOP to opt out." — and the footer sits outside the retry, so it is appended once per logical message, not once per attempt. `otpSms` and `plainSms` are not touched.

</HintLadder>

**Transfer test:** the footer pushes some messages past 160 characters, so they split into two billed SMS segments. Should segment counting live in this decorator, in a new one, or in the adapter? (Hint: who defines what a segment is?)

<h2 id="sq-kit">Side quest 2 · The discounted kit</h2>

**The ticket says:** *"Pharmacy: sell a post-op kit — dressing ₹450, antibiotics ₹1,200, painkillers ₹280 — at 10% off its contents. Kits appear on inpatient bills like any other charge."*

**Where it lands:** **Composite**, by adding a **new node type**. A kit is priced from its children, like a group, but with its own rule. `BillNode` doesn't change, `ChargeGroup` doesn't change, and every existing bill keeps working.

<Reveal q="Why not add a percentOff field to ChargeGroup?">

Every group would carry a field that almost all of them leave at zero, and the next pricing idea (buy-two-get-one, a cap) would add another. A new node type keeps each rule in its own class and leaves the tree's existing node types closed — the open/closed principle, applied to a composite. It also composes: a discounted kit can sit inside a surgery package, which sits inside an admission.

</Reveal>

<HintLadder hints={hints.kit} labels={turn}>

```java group=clinic
class DiscountedGroup implements BillNode {                // a new node type; no existing node edited
    private final ChargeGroup contents;
    private final int percentOff;

    DiscountedGroup(ChargeGroup contents, int percentOff) {
        if (percentOff < 0 || percentOff > 100) throw new IllegalArgumentException("percentOff must be 0..100");
        this.contents = contents;
        this.percentOff = percentOff;
    }

    public Money total() {
        long full = contents.total().paise();
        return new Money(full - full * percentOff / 100);  // the discount rounds down to whole paise
    }
}
```

The kit's contents total ₹1,930; at 10% off it costs **₹1,737**. Placed inside an admission bill next to a ₹9,000 room charge, the bill's total is ₹10,737 — the root never learned that kits exist. The checker tests 0%, 100%, out-of-range percentages, and a thousand random kits against an independent calculation.

</HintLadder>

**Transfer test:** finance now wants the statement to show the discount as its own negative line. Is that a change to `DiscountedGroup`, or the itemized-statement operation from the Visitor reveal? What would Visitor need to know about kits?

<h2 id="sq-thermal">Side quest 3 · The pharmacy printer</h2>

**The ticket says:** *"Pharmacy counters: print every invoice type on the new 58 mm thermal printers. 32 characters a line, amounts right-aligned."*

**Where it lands:** **Bridge**, on the implementation side: one new `Renderer`. No invoice class changes — consultation, pharmacy, lab and room-stay invoices all print on day one.

<Reveal q="How many classes would this ticket have cost with one subclass per (kind × format)?">

Four: `ConsultationThermalInvoice`, `PharmacyThermalInvoice`, `LabThermalInvoice` and `RoomStayThermalInvoice` — each a copy of the 32-column layout logic. With the bridge it is one class, and the layout logic exists once.

</Reveal>

<HintLadder hints={hints.thermal} labels={turn}>

```java group=invoices
class ThermalRenderer implements Renderer {                // 58 mm paper: 32 characters a line
    static final int WIDTH = 32;

    public String header(String title) {
        String t = title.length() > WIDTH ? title.substring(0, WIDTH) : title;
        return " ".repeat((WIDTH - t.length()) / 2) + t + "\n" + "-".repeat(WIDTH) + "\n";
    }
    public String line(LineItem item) { return row(item.label(), Renderer.rupees(item.paise())); }
    public String footer(long totalPaise) { return "-".repeat(WIDTH) + "\n" + row("TOTAL", Renderer.rupees(totalPaise)); }

    private static String row(String label, String amount) {
        int room = WIDTH - amount.length() - 1;            // keep at least one space before the amount
        String l = label.length() > room ? label.substring(0, room) : label;
        return l + " ".repeat(WIDTH - l.length() - amount.length()) + amount + "\n";
    }
}
```

Every body line is exactly 32 characters, the amount flush right, and a long medicine name is cut rather than wrapped into the amount column. The checker prints random invoices with labels up to 60 characters and amounts up to ₹1 crore through it and asserts every line's width and alignment.

</HintLadder>

**Transfer test:** MediCore's pharmacy now wants a QR code at the bottom of thermal receipts only. Does that fit inside `ThermalRenderer.footer`, or does it mean the two axes aren't independent after all?

<h2 id="sq-legacy">Side quest 4 · The acquired chain</h2>

**The ticket says:** *"MediCore has acquired Saltmarsh Clinics. Their patient charts live in a legacy store: `fetchChart(int mrn)` returns one semicolon-separated string. Doctors must see Saltmarsh histories in the same screens — under the same access rules."*

**Where it lands:** an **Adapter** *and* a **Proxy**, composed. The adapter makes the legacy store speak `PatientRecords`; the existing `RecordsAuthProxy` then wraps it, so the access rule applies with zero new auth code.

<Reveal q="Could the proxy go inside the adapter instead?">

Not without writing a second proxy. `RecordsAuthProxy` implements and holds a `PatientRecords`; the legacy store isn't one until the adapter makes it one. So the adapter goes inside, the proxy outside — and that order has a bonus: a denied caller is stopped before the legacy store is touched at all. The checker counts the legacy store's reads to prove it.

</Reveal>

Saltmarsh's store, as it ships:

```java group=clinic
class LegacyChartStore {
    private final Map<Integer, String> charts;             // medical record number -> "DX:...;RX:...;LAB:..."
    int reads = 0;
    LegacyChartStore(Map<Integer, String> charts) { this.charts = Map.copyOf(charts); }
    String fetchChart(int mrn) {
        reads++;
        return charts.getOrDefault(mrn, "");
    }
}
```

<HintLadder hints={hints.legacy} labels={turn}>

```java group=clinic
class LegacyRecordsAdapter implements PatientRecords {
    private final LegacyChartStore store;
    LegacyRecordsAdapter(LegacyChartStore store) { this.store = store; }

    public History fullHistory(String patientId) {
        if (!patientId.startsWith("P-")) throw new IllegalArgumentException("not a MediCore patient id: " + patientId);
        int mrn = Integer.parseInt(patientId.substring(2));          // "P-1042" -> record number 1042
        String chart = store.fetchChart(mrn);
        List<String> entries = chart.isEmpty() ? List.of() : List.of(chart.split(";"));
        return new History(patientId, entries);
    }
}

PatientRecords saltmarshRecords(LegacyChartStore store, AccessPolicy policy, AuditLog audit, CallerContext caller) {
    return new RecordsAuthProxy(new LegacyRecordsAdapter(store), policy, audit, caller);   // adapter inside, proxy outside
}
```

Dr Rao, treating `P-1042`, sees `[DX:asthma, RX:salbutamol]`. A receptionist asking for the same patient is denied and audited, and `store.reads` stays at zero.

</HintLadder>

**Transfer test:** Saltmarsh's store is slow. Where would a caching proxy go in this stack — outside the auth proxy, between the auth proxy and the adapter, or inside the adapter? Which position could leak one doctor's cached answer to a receptionist?

<h2 id="interview-script">Say it in the room</h2>

<Scene title="The interview room" mood="night">

The Interviewer has your notification design on the whiteboard: an adapter per vendor, a stack of wrappers, a guard, a facade for "notify patient of discharge".

*"Walk me through the structural decisions,"* they say. *"And tell me what each of those boxes is called — and why."*

A month ago you would have named them by their shape. Today you name them by their reasons.

</Scene>

**The 90-second answer** (adapt the nouns):

> "The edges of this system are vendors I can't change, so I started from ports my domain owns: an `SmsGateway` and a `PaymentProcessor`, each in my own words. Each vendor gets an **adapter** — it translates formats, units and error codes, including the int overflow on the payment vendor's amounts — so switching vendors is one class and one wiring line. Cross-cutting behaviour like retry, rate limiting and logging are **decorators** over the gateway, composed per channel in one wiring method; the nesting order is a decision I'll state — with retry outside the limiter, every attempt spends a permit. Access to patient records goes through a **proxy** that checks the policy and audits before delegating; it's the only object the composition root hands out, so there's no unguarded path — in Spring that's `@PreAuthorize`, with the self-invocation caveat. Discharge touched five services from three callers, so it's a **facade** that owns the sequence and the failure policy but no business rules. And the bill is a **composite** — charges and packages share one interface, so the total is one recursive call."

**Five follow-ups you will get:**

<Reveal q="1 · Decorator and proxy have the same structure. How do you tell them apart?">

By intent. A decorator adds behaviour the caller chose and can stack — retry, logging. A proxy controls access the caller doesn't get a say in — authorization, lazy loading, caching, remoting. A quick test: if removing it changes what the feature does, it's a decorator; if removing it changes whether, when or where the real call happens, it's a proxy.

</Reveal>

<Reveal q="2 · Why not just subclass the vendor adapter to add retry?">

Because behaviours combine. Retry, rate limit and logging as subclasses need one class per combination — sixteen across two senders — and each is coupled to its parent's internals. As decorators they're three classes that work around any `SmsGateway`, combined at wiring time, and a fourth behaviour is one class.

</Reveal>

<Reveal q="3 · Your caching proxy returns stale data. Is that a bug?">

It's a trade I made on purpose, and the TTL is the business decision behind it: an insurer's cover doesn't change minute to minute, so ten minutes of staleness saves most of the remote calls. For data where staleness is unacceptable — a bed's occupancy, a payment status — I wouldn't cache, or I'd invalidate on write. I'd also never cache failures, and I'd bound the cache's size in production.

</Reveal>

<Reveal q="4 · In Spring, why does @Transactional sometimes do nothing?">

The annotation is advice applied by a proxy around the bean. A call from one method of the bean to another is `this.method()` — a plain call on the target that never crosses the proxy — so the inner method's advice never runs. Fixes: move the method to another bean, or call it through the proxy. Same for private methods, which the proxy can't intercept.

</Reveal>

<Reveal q="5 · Isn't your facade a God class?">

It coordinates; it doesn't decide. Bill math lives in billing, stock in pharmacy; the facade knows the order of five calls and what to do when one fails. If it ever grew an `if` about money or medicine, that logic would move down into the service that owns it.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see… | Pattern | Do… | Watch out for |
|---|---|---|---|
| Vendor names and types inside domain code; a swap is coming | **Adapter** | Domain-owned port; one adapter per vendor translating requests, units and errors | Ports shaped like the vendor; decisions inside adapters; narrowing casts |
| Class names that list behaviours; "also X, some need Y" | **Decorator** | Same interface in and out; compose per channel at wiring | Nesting order changes semantics; fat interfaces; caching a command |
| A rule that must hold on every call, caller unaware | **Proxy** (protection) | Hand out only the proxy | Paths that bypass it — including `this` |
| An expensive object rarely used in full | **Proxy** (virtual) | Answer cheap calls; load on first real use | Thread-safety of the lazy load |
| A slow query that answers the same thing for a while | **Proxy** (caching) | Hit/miss with a TTL someone owns | Staleness, unbounded growth, caching failures |
| Several callers repeating one multi-system sequence | **Facade** | One use-case method; owns order and failure policy | Business rules creeping in |
| Part–whole tree; "treat one and many alike" | **Composite** | Shared interface; containers ask children; `add` on containers only | Cycles; second and third operations (→ Visitor) |
| Class names built from two lists | **Bridge** | Abstraction holds implementor; m × n → m + n | A speculative second axis; axes that aren't independent |
| Heap full of equal immutable objects | **Flyweight** | Factory shares intrinsic state; extrinsic stays outside | Mutable "shared" state; optimising without measuring |

## Five mistakes to leave behind

1. **Naming wrappers by their shape.** Four patterns share one diagram. Name each by what the caller sees and why it exists, and say the alternative you rejected.
2. **Letting vendor vocabulary into the domain.** The port is yours, in your words. Every format, unit, width and error code is translated in the adapter — and a narrowing cast in an adapter is a bug waiting for a big number.
3. **Ignoring decorator order.** Retry outside a limiter spends a permit per attempt; logging outside a retry logs per logical send. The order is a design decision — state it.
4. **Trusting a proxy you can walk around.** If any path reaches the real object — a second bean, a static accessor, a self-call — the guarantee is a suggestion.
5. **Reaching for Bridge and Flyweight to look clever.** Bridge needs two axes that really vary; Flyweight needs a measured memory problem. Without them, both are ceremony.

**Look these up yourself**

- **Anti-corruption layer** (Domain-Driven Design) — Adapter grown into a whole translation layer between your model and a legacy or partner system's model.
- **Visitor** — the follow-up to Composite whenever operations over a tree multiply; know its trade-off (cheap operations, expensive node types).
- **Resilience4j decorators** — retry, rate limiting, circuit breaking and bulkheads as composable wrappers around a function; the production version of Chapter 2, where order matters just as much.
- **Circuit breaker** — the wrapper that stops calling a failing dependency for a while; ask whether it's a decorator or a proxy, and defend your answer.
- **CGLIB / ByteBuddy class-based proxies** — how frameworks proxy classes without interfaces, and why `final` methods can't be intercepted that way.
- **Sidecar and service-mesh proxies** (Envoy) — the remote proxy moved out of the process: retries, mTLS and metrics added without touching the service.
- **Object pool vs flyweight** — both reuse objects; know why a connection pool is not a flyweight.
- **Private Class Data and Extension Object** — two lesser-known structural patterns that show up in older codebases and pattern catalogues beyond GoF.
