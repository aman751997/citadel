<h2 id="prologue">Overview · Seven ways to wrap an object</h2>

**Concept.** Structural patterns are about how classes and objects are composed into bigger structures. Nearly all of them work by wrapping one object in another.

**Problem.** The running example is a clinic chain called MediCore. Its software depends on things the team cannot edit: an SMS vendor SDK, a payment vendor SDK, a certified patient-records service. Bills nest inside bills. Without a plan, vendor types leak into business code and every change touches many classes.

| Pattern | The problem that needs it | The move |
|---|---|---|
| **Adapter** | A vendor's interface has the wrong shape and you can't edit it | Translate their shape into the port your domain owns |
| **Decorator** | Behaviour must be added in combinations that vary per caller | Wrap with the same interface; stack at wiring time |
| **Proxy** | Every call must be guarded, deferred, cached or sent elsewhere, and callers mustn't opt out | Stand in front with the same interface; control the call |
| **Facade** | Many callers repeat one multi-system sequence | One new, smaller entry point that coordinates and never decides |
| **Composite** | Parts and wholes form a tree and callers want to treat them alike | One interface; containers answer by asking their children |
| **Bridge** | Two independent dimensions multiply your subclasses | Split the hierarchies; hold one inside the other |
| **Flyweight** | Millions of objects repeat the same immutable data | Share the repeated part; pass the rest in |

**The trap that makes this family hard:** on a class diagram, four of them look identical. Adapter, Decorator, Proxy and Facade all hold an object and forward calls to it. So the common interview question is not "define Decorator". It is "isn't that just a proxy?". The difference is intent: what the wrapper is for. Each chapter ends with a detection cue aimed at telling the pattern from its neighbours, and <a href="#tell-them-apart">the comparison chapter</a> puts them side by side.

**Visual.** Where each pattern lands in the MediCore code by the end of this lesson. Everything on the right is a vendor or certified system the team cannot edit.

<h2 id="composition-over-inheritance">Composition over inheritance</h2>

**Concept.** Inheritance reuses code by extending a class. Composition reuses code by holding another object and calling it. All seven structural patterns are composition: the wrapper holds a reference and forwards calls. None of them needs the class it wraps to be a parent.

**Problem.** Inheritance fixes the combination at compile time, allows one parent, and couples the child to the parent's internals. Add three optional behaviours to an SMS sender by subclassing and you need a class for every subset.

**Bad design.** One subclass per combination:

```java fragment
class RetryingTextWaveAdapter extends TextWaveAdapter { /* retry loop around super.send */ }
class RateLimitedTextWaveAdapter extends TextWaveAdapter { /* permit check, then super.send */ }
class RetryingRateLimitedTextWaveAdapter extends RetryingTextWaveAdapter { /* limiter copy-pasted in */ }
class LoggingRetryingRateLimitedTextWaveAdapter extends RetryingRateLimitedTextWaveAdapter { /* ... */ }
// ...one class for each subset of {logging, retry, rate limit}: 2 x 2 x 2 = 8 per vendor.
// Two senders (TextWave, in-app) make 16. A fourth behaviour makes 32. Changing vendor rewrites all of them.
```

**Better design.** Each behaviour holds a gateway and implements the same interface, so combinations are chosen at wiring time:

```java fragment
SmsGateway campaign = new RetryingGateway(new RateLimitedGateway(vendor, limiter), 3, sleeper);
SmsGateway otp      = new RetryingGateway(vendor, 5, sleeper);
```

The Decorator chapter below builds exactly these classes with tests.

**How it works.** The caller depends on the interface only. Which behaviours run, and in what order, is decided where objects are created (the composition root), not inside the classes.

| Pattern | It holds | The inheritance version it replaces |
|---|---|---|
| Adapter | the vendor class (object adapter) | `extends VendorClient implements Port` (class adapter) |
| Decorator | another object of the same interface | one subclass per behaviour combination |
| Proxy | the real object | a subclass overriding every method with a guard |
| Facade | many subsystem objects | a base class that all callers extend to inherit the sequence |
| Composite | children of the same interface | none; the tree is the point |
| Bridge | an implementor | one subclass per (abstraction x implementation) pair |
| Flyweight | a shared intrinsic object | subclasses holding their own copy of the data |

**When to use composition.** Almost always. Use inheritance for a real "is a" relationship where the parent was designed for it, or to share code through an abstract base class you own.

**Trade-offs.** Composition costs forwarding boilerplate and more objects to wire. Around a fat interface (many methods) every wrapper must forward them all. Inheritance is fine when the hierarchy is shallow, you own both sides, and no combinations multiply. The <a href={`${BASE}lld/lessons/solid/#composition`}>SOLID lesson</a> has the counter that counted twice: a subclass broke because the parent called its own overridable method.

<h2 id="adapter">Chapter 1 · Adapter: translate a vendor SDK</h2>

**Concept.** An adapter makes one existing interface fit another that your code already expects. Your domain defines the interface it wants (the port). The adapter implements that port and calls the vendor SDK inside.

**Problem.** MediCore sends appointment reminders by SMS through a vendor called TextWave. TextWave has no `send` method. It has `submitMessage`, which takes a `TextWavePayload` wanting the phone number as bare digits with no plus sign, the body as a `char[]`, and a sender code. Failures come back as reason codes like `E101_BAD_MSISDN`. Four classes import `com.textwave`, each builds its own payload, and two forget to strip the plus sign. The contract ends in eleven months. How many classes should know the vendor's name? One.

**Bad design.** Vendor vocabulary everywhere a text is sent:

```java fragment
class ReminderService {
    private final TextWaveClient textWave = new TextWaveClient(Config.textWaveKey());   // the vendor, welded in

    void remind(Appointment a) {
        TextWavePayload p = new TextWavePayload();
        p.setMsisdn(a.patientPhone());                     // forgot to strip the '+': E101 in production
        p.setBody(("Reminder: Dr " + a.doctor() + " at " + a.time()).toCharArray());
        p.setSender("MEDICORE");
        TextWaveAck ack = textWave.submitMessage(p);
        if (!ack.accepted()) log.warn("TextWave said " + ack.reasonCode());           // vendor errors, in the domain
    }
}
// ...and the same dozen lines in LabResultsService, DischargeService and OtpService.
```

**Detection cues.**

1. **Vendor names in domain imports.** If `com.textwave` appears in a class that also knows what an appointment is, the next vendor switch edits business code.
2. **Vendor types in domain signatures or logs.** `TextWaveAck`, `E101` and `char[]` bodies are someone else's vocabulary leaking in.
3. **The same translation repeated**, and repeated slightly differently. Duplicated translation is where the bugs live.
4. **A swap you already know is coming.** A dependency you will replace on a schedule you don't control.

**Better design.** Three steps. First, the domain says what it wishes existed, in its own words. This interface belongs to MediCore, and the reminder service depends only on it:

```java group=clinic
import java.time.*;

record PhoneNumber(String e164) {                          // "+919812345678": plus, country code, 7-15 digits
    PhoneNumber {
        if (!e164.matches("\\+[1-9][0-9]{6,14}")) throw new IllegalArgumentException("not an E.164 number: " + e164);
    }
}

class SmsDeliveryException extends RuntimeException {
    SmsDeliveryException(PhoneNumber to, String reason) { super("SMS to " + to.e164() + " failed: " + reason); }
}

interface SmsGateway {                                     // the port: owned by MediCore's domain
    void send(PhoneNumber to, String text);
}

class ReminderService {                                    // domain code: knows the port, never the vendor
    private final SmsGateway sms;
    ReminderService(SmsGateway sms) { this.sms = sms; }

    void remind(PhoneNumber patient, String doctor, LocalDateTime at) {
        sms.send(patient, "Reminder: Dr " + doctor + ", " + at.toLocalDate() + " at " + at.toLocalTime());
    }
}
```

Second, here is TextWave's SDK as it ships (a stand-in with the real thing's shape; you can't edit it):

```java group=clinic
class TextWavePayload {
    private String msisdn;                                 // digits only, country code first, no '+'
    private char[] body;
    private String sender;
    void setMsisdn(String msisdn) { this.msisdn = msisdn; }
    void setBody(char[] body) { this.body = body; }
    void setSender(String sender) { this.sender = sender; }
    String msisdn() { return msisdn; }
    char[] body() { return body; }
    String sender() { return sender; }
}

record TextWaveAck(boolean accepted, String reasonCode) {}

class TextWaveClient {
    private final String apiKey;
    final List<String> delivered = new ArrayList<>();       // stands in for TextWave's servers
    TextWaveClient(String apiKey) { this.apiKey = apiKey; }

    TextWaveAck submitMessage(TextWavePayload p) {
        if (p.msisdn() == null || !p.msisdn().matches("[0-9]{7,15}")) return new TextWaveAck(false, "E101_BAD_MSISDN");
        if (p.body() == null || p.body().length == 0) return new TextWaveAck(false, "E102_EMPTY_BODY");
        delivered.add(p.sender() + "->" + p.msisdn() + ": " + new String(p.body()));
        return new TextWaveAck(true, "OK");
    }
}
```

Third, one class that speaks both languages, so nothing else has to:

```java group=clinic
class TextWaveAdapter implements SmsGateway {
    private final TextWaveClient client;                   // the adaptee: the vendor's SDK
    private final String senderCode;

    TextWaveAdapter(TextWaveClient client, String senderCode) {
        this.client = client;
        this.senderCode = senderCode;
    }

    public void send(PhoneNumber to, String text) {
        TextWavePayload payload = new TextWavePayload();    // translate OUR call into THEIR shape
        payload.setMsisdn(to.e164().substring(1));          // "+919812345678" -> "919812345678"
        payload.setBody(text.toCharArray());
        payload.setSender(senderCode);
        TextWaveAck ack = client.submitMessage(payload);
        if (!ack.accepted())                                // and THEIR failure into OUR exception
            throw new SmsDeliveryException(to, ack.reasonCode());
    }
}

SmsGateway liveSms(TextWaveClient client) {                // composition root: the vendor swap is this one line
    return new TextWaveAdapter(client, "MEDICORE");
}
```

**How it works.** `ReminderService` calls `SmsGateway.send`. The adapter builds the vendor payload, calls the client, and turns a rejected acknowledgement into a domain exception. Three translations happen in that one method, and they are the adapter's whole job: the request (our `PhoneNumber` and `String` into their payload, including the plus sign they don't want), the types (`String` to `char[]`), and the failure (their reason code into our exception, so no domain class ever reads `E101`). The checker sends a thousand random valid numbers through it and confirms TextWave receives exactly the digits after the plus.

Two grading points. First, **the port belongs to the consumer**: your domain defines `SmsGateway` and the adapter conforms to it, never the other way round. That is dependency inversion from the <a href={`${BASE}lld/lessons/solid/`}>SOLID lesson</a>: arrows point from volatile (vendor) to stable (domain). Second, **adapters turn a swap into configuration**. The <a href={`${BASE}lld/war/patterns-why/#8-adapter--so-a-swap-is-config-not-a-release`}>production dossier</a> exists because moving heavy report queries to a read replica had to be a config change, not a release. The same seam makes next year's SMS vendor one new class and one wiring line.

**Object adapter or class adapter?** GoF describes two forms. A class adapter inherits from the adaptee and implements the target (`class TextWaveAdapter extends TextWaveClient implements SmsGateway`). An object adapter holds the adaptee. In Java, prefer the object adapter: it works when the SDK class is `final`, it can adapt any subclass of the adaptee, it hides every vendor method you didn't choose to expose, and a test can hand it a fake client. The class adapter exposes the whole vendor API through your adapter, which is the leak you were trying to plug.

> **Memory hook.** A travel plug adapter: your laptop's plug (the domain port) never changes, and the adapter reshapes the wall socket (the vendor) to fit it.
> **Cheat code:** wrong interface shape, and the port is defined by YOUR side, so adapter.

**When to use.** At vendor, network and replaceable-infrastructure boundaries: payment, SMS, email, storage, legacy systems after an acquisition.

**Trade-offs and when NOT to use it.**

- **Don't adapt what you would never swap.** Wrapping `java.time`, `java.util.List` or a mature JSON library behind your own interface buys nothing but a second API to learn.
- **Don't adapt your own code. Change it.** If both sides are yours, make them agree. An adapter between two classes you own is a disagreement you postponed.
- **Don't let the adapter grow decisions.** Retry policy, vendor selection and business rules don't belong in it. It translates. (The next chapter puts retry where it belongs.)

**Practice.** Try the decision drill first, then the exercise.

**Your turn.** MediCore's payment vendor, PayLoom, has an SDK too. Your domain already owns the port, in its own words. Money is a `long` of whole paise, never a `double`:

```java group=clinic
record Money(long paise) {                                 // whole paise; never a double
    static final Money ZERO = new Money(0);
    Money {
        if (paise < 0) throw new IllegalArgumentException("negative money: " + paise);
    }
    static Money rupees(long rupees) { return new Money(Math.multiplyExact(rupees, 100)); }
    Money plus(Money other) { return new Money(Math.addExact(paise, other.paise)); }
    Money minus(Money other) { return new Money(paise - other.paise); }   // refuses to go negative
    @Override public String toString() {
        return "INR " + paise / 100 + "." + (paise % 100 < 10 ? "0" : "") + paise % 100;
    }
}

record PaymentResult(boolean approved, String reference) {}

interface PaymentProcessor {                               // the port, in MediCore's words
    PaymentResult process(String admissionId, Money amount);
}
```

PayLoom's SDK, as it ships. It counts money in an `int` number of paise ("minor units"), wants a currency code, refuses zero, and answers with HTTP-style status codes:

```java group=clinic
record PayLoomResponse(int status, String txnId, int capturedMinor) {}

class PayLoomSdk {
    final List<String> captures = new ArrayList<>();        // stands in for PayLoom's servers
    PayLoomResponse capture(String orderRef, String currency, int amountMinor) {
        if (amountMinor <= 0) return new PayLoomResponse(422, null, 0);
        captures.add(orderRef + " " + currency + " " + amountMinor);
        return new PayLoomResponse(201, "PL-" + captures.size(), amountMinor);
    }
}
```

Write `PayLoomAdapter`. Two edge cases to handle: a patient who prepaid everything, and a corporate account's ₹2.5 crore quarterly settlement.

<HintLadder hints={hints.payloom} labels={turn}>

```java group=clinic
class PayLoomAdapter implements PaymentProcessor {
    private final PayLoomSdk sdk;
    PayLoomAdapter(PayLoomSdk sdk) { this.sdk = sdk; }

    public PaymentResult process(String admissionId, Money amount) {
        if (amount.paise() == 0) return new PaymentResult(true, "NOTHING-DUE");   // PayLoom refuses zero; our domain doesn't
        int minor;
        try {
            minor = Math.toIntExact(amount.paise());        // long paise -> PayLoom's int minor units, or throw
        } catch (ArithmeticException overLimit) {
            return new PaymentResult(false, null);          // above 2,147,483,647 paise PayLoom can't take it at all
        }
        PayLoomResponse r = sdk.capture("MC-" + admissionId, "INR", minor);
        boolean ok = r.status() == 201 && r.capturedMinor() == minor;              // a partial capture is not a success
        return new PaymentResult(ok, ok ? r.txnId() : null);
    }
}
```

₹9,000 reaches PayLoom as `MC-ADM-2201 INR 900000`. A prepaid patient never reaches PayLoom at all. And ₹2.5 crore is 2,500,000,000 paise, more than an `int` holds (2,147,483,647, about ₹2.15 crore). A plain `(int)` cast would silently send **−1,794,967,296**; `Math.toIntExact` throws instead, and the adapter turns that into a clean decline. The checker runs all three, plus two thousand random amounts on both sides of the limit, plus a vendor that captures only part of the amount.

</HintLadder>

<h2 id="decorator">Chapter 2 · Decorator: add behaviour without subclasses</h2>

**Concept.** A decorator implements the same interface it holds. Because it is a gateway and has a gateway, wrappers stack in any order around any implementation, chosen where objects are wired.

**Problem.** The adapter is live. TextWave drops about two percent of calls, so reminders need retry. Bulk campaign blasts need a rate limit or TextWave will throttle the account. Compliance wants every send logged. One-time passwords must never be rate-limited, and the in-app channel needs none of it. A teammate's branch has `RetryingTextWaveAdapter`, `RateLimitedTextWaveAdapter`, `RetryingRateLimitedTextWaveAdapter` and more, with sixteen classes planned once the in-app channel is included.

**Bad design.** Behaviour added by inheritance, one subclass per combination:

```java fragment
class RetryingTextWaveAdapter extends TextWaveAdapter { /* retry loop around super.send */ }
class RateLimitedTextWaveAdapter extends TextWaveAdapter { /* permit check, then super.send */ }
class RetryingRateLimitedTextWaveAdapter extends RetryingTextWaveAdapter { /* limiter copy-pasted in */ }
class LoggingRetryingRateLimitedTextWaveAdapter extends RetryingRateLimitedTextWaveAdapter { /* ... */ }
// ...one class for each subset of {logging, retry, rate limit}: 2 x 2 x 2 = 8 per vendor.
// Two senders (TextWave, in-app) make 16. A fourth behaviour makes 32. Changing vendor rewrites all of them.
```

**Detection cues.** Class names that are lists of adjectives (`LoggingRetryingRateLimited...`). The same behaviour copy-pasted into several subclasses because Java has one parent. Requirements phrased as "also X, and some need Y, and these combinations vary". Behaviour bolted to one vendor that should apply to any.

**Better design.** Retry and rate limiting become wrappers over the gateway interface, and each channel is one wiring method:

```java group=clinic
class RateLimitExceededException extends RuntimeException {
    RateLimitExceededException() { super("rate limit exceeded"); }
}

interface RateLimiter { boolean tryAcquire(); }            // the concurrency lesson builds a real token bucket
interface Sleeper { void pause(long millis); }             // injected, so tests never really sleep

class RetryingGateway implements SmsGateway {
    private final SmsGateway inner;                        // same type as itself: THAT is the pattern
    private final int maxAttempts;
    private final Sleeper sleeper;

    RetryingGateway(SmsGateway inner, int maxAttempts, Sleeper sleeper) {
        if (maxAttempts < 1) throw new IllegalArgumentException("maxAttempts must be at least 1");
        this.inner = inner;
        this.maxAttempts = maxAttempts;
        this.sleeper = sleeper;
    }

    public void send(PhoneNumber to, String text) {
        for (int attempt = 1; ; attempt++) {
            try {
                inner.send(to, text);
                return;
            } catch (SmsDeliveryException e) {             // only delivery failures are worth retrying
                if (attempt == maxAttempts) throw e;
                sleeper.pause(100L << (attempt - 1));      // 100 ms, 200 ms, 400 ms, ...
            }
        }
    }
}

class RateLimitedGateway implements SmsGateway {
    private final SmsGateway inner;
    private final RateLimiter limiter;

    RateLimitedGateway(SmsGateway inner, RateLimiter limiter) {
        this.inner = inner;
        this.limiter = limiter;
    }

    public void send(PhoneNumber to, String text) {
        if (!limiter.tryAcquire()) throw new RateLimitExceededException();
        inner.send(to, text);
    }
}

// Wiring: every combination, no new classes.
SmsGateway campaignSms(SmsGateway vendor, RateLimiter limiter, Sleeper sleeper) {
    return new RetryingGateway(new RateLimitedGateway(vendor, limiter), 3, sleeper);
}
SmsGateway otpSms(SmsGateway vendor, Sleeper sleeper) {
    return new RetryingGateway(vendor, 5, sleeper);        // urgent: retry hard, never rate-limit
}
SmsGateway plainSms(SmsGateway vendor) {
    return vendor;                                         // no wrapping is also a choice
}
```

**Why this works.** Sixteen planned classes became two adapters and three wrappers (the third, logging, is your turn below), and a fourth behaviour would be one more class instead of sixteen more. Two design choices the checker pins down: the retry catches only `SmsDeliveryException`, so a full rate limiter fails fast instead of being hammered; and the sleeper is injected, so tests verify the 100 ms / 200 ms backoff without waiting for it.

**How it works.** A call enters the outermost layer and passes inward. Each layer does its bit and calls `inner.send(...)`. The vendor adapter is the core.

<h3 id="order-matters">Order is semantics</h3>

Interviewers probe this, and it is where decorators stop being a diagram and become a design decision. In `campaignSms`, retry sits outside the limiter, so every retry attempt re-enters the limiter and spends a permit. Flip the nesting and one logical send costs one permit, however many retries happen inside:

| Wiring | Send fails twice, then succeeds | Permits spent | Vendor calls |
|---|---|---|---|
| `Retrying(RateLimited(vendor))` | each attempt passes the limiter | **3** | 3 |
| `RateLimited(Retrying(vendor))` | one permit, then retries inside | **1** | 3 |

Neither is "correct". Outside-retry protects the vendor's rate (TextWave counts calls, not intentions). Inside-retry protects your quota of logical messages. Say which you want and why. The checker runs both wirings on two thousand random combinations of failures, attempts and permits against a hand-simulated oracle, including the edge where the limiter runs dry mid-retry and the `RateLimitExceededException` escapes on attempt three.

This is also how `java.io` works: `new BufferedInputStream(new FileInputStream(f))`. `BufferedInputStream` is an `InputStream` that holds an `InputStream` and adds buffering. `Collections.unmodifiableList(list)` and `Collections.synchronizedList(list)` are decorators too. Cite them in an interview.

**Production scar.** Decorators that hop threads lose `ThreadLocal` context. The <a href={`${BASE}lld/war/patterns-why/#5-decorator--the-bug-threadlocals-cause-at-thread-boundaries`}>dossier on exactly that bug</a> covers async writes silently saved under a default tenant. A decorator that submits work to a pool must capture context before submit, restore it inside, and clear it in a `finally` because pool threads are reused.

> **Memory hook.** Gift wrapping: every layer wraps a gift and IS a gift, so you can keep wrapping. The last wrap is the outermost layer and runs first.
> **Cheat code:** same interface plus "also needs X, some need Y, combinations vary" means decorator. The combination is decided at wiring, not by class explosion.

**When to use.** Cross-cutting behaviour that combines per caller or channel: retry, rate limit, logging, metrics, encryption, compression, authorisation checks the caller chose.

**Trade-offs and when NOT to use it.**

- **One caller, one behaviour, forever.** If only OTPs retry and nothing else ever will, a loop in `OtpService` is honest. Decorators pay off when behaviours combine or are shared.
- **Fat interfaces.** A decorator must forward every method. Around a fourteen-method interface, each decorator is fourteen methods of boilerplate. Fix the interface first (interface segregation).
- **When identity matters.** A decorated object is a different object: `==`, `equals` and `instanceof TextWaveAdapter` checks no longer see the original.
- **Stacks nobody can read.** Seven wrappers deep, a stack trace is a maze. Name the stacks in one wiring method per channel, as above, so the order is written down once.
- **Commands are not cacheable.** "Add a caching decorator to `send()`" silently drops real messages. Caching wraps queries, which is the next chapter.

**Practice.**

```java group=clinic
class LoggingGateway implements SmsGateway {
    private final SmsGateway inner;
    private final List<String> log;                        // stands in for a real logger

    LoggingGateway(SmsGateway inner, List<String> log) {
        this.inner = inner;
        this.log = log;
    }

    public void send(PhoneNumber to, String text) {
        String who = mask(to);
        log.add("send " + who);
        try {
            inner.send(to, text);
            log.add("sent " + who);
        } catch (RuntimeException e) {                     // the exception's message holds the full number
            log.add("failed " + who + " " + e.getClass().getSimpleName());
            throw e;
        }
    }

    static String mask(PhoneNumber p) {                    // "+919812345678" -> "+91981234****"
        String n = p.e164();
        return n.substring(0, n.length() - 4) + "****";
    }
}

SmsGateway loggedPerSend(SmsGateway vendor, List<String> log, Sleeper sleeper) {
    return new LoggingGateway(new RetryingGateway(vendor, 3, sleeper), log);     // one story per logical send
}
SmsGateway loggedPerAttempt(SmsGateway vendor, List<String> log, Sleeper sleeper) {
    return new RetryingGateway(new LoggingGateway(vendor, log), 3, sleeper);     // one story per vendor call
}
```

For a send that fails twice and then succeeds, `loggedPerSend` writes **2** lines (`send`, `sent`) and `loggedPerAttempt` writes **6** (`send`/`failed` twice, then `send`/`sent`). Compliance probably wants the first; the on-call engineer debugging TextWave wants the second, and you can have both by wrapping twice. The checker asserts both logs line by line and that no full number appears in any of them.

<h2 id="proxy">Chapter 3 · Proxy: guard, defer, cache</h2>

**Concept.** A proxy has the same shape as a decorator: it implements the interface and holds the real object. The intent is control. It decides whether, when, where or how the real call happens, and callers are handed the proxy without knowing.

**Problem.** The patient-records service is certified, audited and correct: `fullHistory(patientId)` returns everything. Nothing in it checks who is asking. The old desktop app checked roles in its own UI, and a kiosk built later didn't, so a receptionist's screen showed a full psychiatric history. Editing the certified service is not allowed. Every caller must be checked, including callers nobody has written yet.

**Bad design.** The check lives in callers, so each new caller is a new chance to forget it:

```java fragment
class FrontDeskKiosk {
    History showHistory(String patientId) {
        return records.fullHistory(patientId);             // no role check: the kiosk forgot
    }
}
class DoctorScreen {
    History showHistory(String patientId) {
        if (!session.user().role().equals("DOCTOR")) throw new AccessDeniedException("doctors only");   // remembered here
        return records.fullHistory(patientId);             // ...but no audit trail of the read
    }
}
```

**Detection cue.** A rule that must hold on every call to an object, including calls nobody has written yet (check permission, log access, load lazily, serve from cache, call across the network), where the caller should neither know nor be able to skip it. If the rule is enforced by "remember to", it will be forgotten. The <a href={`${BASE}lld/war/patterns-why/#6-proxy--aop--the-leak-on-the-path-nobody-guarded`}>leak on the path nobody guarded</a> in the War Room is one forgotten getter that read across hospitals.

**Better design.** Put the guard in a class that is a `PatientRecords` and holds one. Callers are handed the proxy and never know:

```java group=clinic
record User(String id, String role) {}
record History(String patientId, List<String> entries) {}

interface PatientRecords { History fullHistory(String patientId); }
interface AccessPolicy { boolean canReadHistory(User caller, String patientId); }
interface AuditLog { void record(String action, String subject, String detail); }
interface CallerContext { User current(); }                // who is asking: the session, injected

class AccessDeniedException extends RuntimeException {
    AccessDeniedException(String userId, String patientId) { super(userId + " may not read " + patientId); }
}

class RecordsAuthProxy implements PatientRecords {
    private final PatientRecords real;
    private final AccessPolicy policy;
    private final AuditLog audit;
    private final CallerContext caller;

    RecordsAuthProxy(PatientRecords real, AccessPolicy policy, AuditLog audit, CallerContext caller) {
        this.real = real;
        this.policy = policy;
        this.audit = audit;
        this.caller = caller;
    }

    public History fullHistory(String patientId) {
        User who = caller.current();
        if (!policy.canReadHistory(who, patientId)) {          // gate BEFORE the real call
            audit.record("DENIED_HISTORY", who.id(), patientId);
            throw new AccessDeniedException(who.id(), patientId);
        }
        audit.record("READ_HISTORY", who.id(), patientId);     // regulators want reads logged too
        return real.fullHistory(patientId);
    }
}

class TreatingTeamPolicy implements AccessPolicy {         // doctors read their own patients; nobody else does
    private final Map<String, Set<String>> patientsByDoctor;
    TreatingTeamPolicy(Map<String, Set<String>> patientsByDoctor) { this.patientsByDoctor = Map.copyOf(patientsByDoctor); }

    public boolean canReadHistory(User caller, String patientId) {
        return caller.role().equals("DOCTOR")
            && patientsByDoctor.getOrDefault(caller.id(), Set.of()).contains(patientId);
    }
}

// Wiring: the ONLY PatientRecords anyone is handed is the proxy.
PatientRecords guardedRecords(PatientRecords certified, AccessPolicy policy, AuditLog audit, CallerContext caller) {
    return new RecordsAuthProxy(certified, policy, audit, caller);
}
```

The certified service is untouched. The policy is its own class, because it changes for different reasons than the audit format. And the guarantee comes from wiring, not discipline: if the composition root never hands out the raw service, there is no unguarded path. The checker runs two thousand random (user, patient, assignment) requests and confirms the real service was called exactly as often as the policy allowed, with one audit line per request either way.

**How it works.** The caller calls `fullHistory`. The proxy asks the policy, audits, and only then calls the real service. A denied call never reaches it.

<h3 id="proxy-kinds">Four reasons to stand in front</h3>

GoF names proxies by what they control. The structure never changes; the reason does.

| Kind | Controls | MediCore example | JDK / framework example |
|---|---|---|---|
| **Protection** | whether the call happens | `RecordsAuthProxy` | Spring Security's `@PreAuthorize` |
| **Virtual** | when the expensive object is created | `LazyScan` below | Hibernate's lazy-loaded associations |
| **Caching** | whether the real object is needed at all | `CachingEligibility` (your turn) | Spring's `@Cacheable` |
| **Remote** | where the real object lives | the insurer's eligibility API, called as if local | Java RMI stubs; declarative HTTP clients (Spring's `@HttpExchange` interfaces, Feign) |

A virtual proxy answers cheap questions itself and creates the real object only on first real use. MediCore's MRI scans live in cold storage; the scan list shows twenty of them, and a doctor opens one:

```java group=clinic
interface Scan {
    String id();
    byte[] pixels();
}

class LazyScan implements Scan {                           // a virtual proxy: stands in until you really look
    private final String id;
    private final Function<String, Scan> archive;          // the expensive load from cold storage
    private Scan real;                                     // null until the first pixels() call

    LazyScan(String id, Function<String, Scan> archive) {
        this.id = id;
        this.archive = archive;
    }

    public String id() { return id; }                      // answered without loading anything

    public byte[] pixels() {
        if (real == null) real = archive.apply(id);        // load once, on first real use
        return real.pixels();
    }
}
```

Listing twenty scans loads nothing; opening one loads it once, however often it is redrawn. (This version is for one viewer thread. Shared across threads, the null check is a race: two threads can both load. You would synchronize it or use a thread-safe memoizer.)

A remote proxy makes a network call look like a method call. That is its power and its danger: the caller sees `check(policyId)` and cannot tell it may take seconds, time out, or fail halfway. The War Room's <a href={`${BASE}lld/war/inventory/`}>inventory</a> counts eighteen declarative HTTP clients in the production codebase, all generated remote proxies. When you write one, put timeouts in it and let failures surface as your domain's exceptions.

<h3 id="dynamic-proxy">The proxy nobody writes by hand</h3>

The industrial form is the dynamic proxy: a class generated at runtime that implements an interface and sends every call to one handler. The JDK has had it since Java 1.3 in `java.lang.reflect.Proxy`, and frameworks build AOP on it (or on bytecode-generated subclasses, for classes without interfaces). Here is the whole mechanism, compiled and tested:

```java group=clinic
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;

@SuppressWarnings("unchecked")
<T> T traced(Class<T> port, T target, List<String> calls) {
    InvocationHandler handler = (proxy, method, args) -> {
        calls.add(method.getName());                       // runs before EVERY call made on the proxy
        try {
            return method.invoke(target, args);
        } catch (InvocationTargetException e) {
            throw e.getCause();                            // rethrow the target's own exception, unwrapped
        }
    };
    return (T) Proxy.newProxyInstance(port.getClassLoader(), new Class<?>[] { port }, handler);
}

interface Ward {
    void admit(String patientId);
    void admitAll(List<String> patientIds);
}

class GeneralWard implements Ward {
    final List<String> beds = new ArrayList<>();

    public void admit(String patientId) {
        if (beds.contains(patientId)) throw new IllegalStateException(patientId + " is already admitted");
        beds.add(patientId);
    }

    public void admitAll(List<String> patientIds) {
        for (String id : patientIds) admit(id);            // this.admit(): a plain call on the target
    }
}
```

`traced(Ward.class, new GeneralWard(), calls)` returns an object that is a `Ward`, records every method name, and forwards. One handler can trace, time, authorize or wrap in a transaction any interface. That is how Spring applies `@Transactional` and `@PreAuthorize` without you writing a proxy class.

Now the follow-up every Java interviewer eventually asks. Call `proxy.admitAll(List.of("P-1", "P-2"))`. Both patients are admitted, but `calls` contains only **`["admitAll"]`**. Inside `GeneralWard`, `admit(id)` means `this.admit(id)`, and `this` is the real object, not the proxy. **Self-invocation bypasses the proxy.** In Spring, that is why a `@Transactional` method called from another method of the same bean runs without its own transaction advice. The checker runs exactly this, and also confirms the handler rethrows the target's `IllegalStateException` itself rather than a reflective wrapper. Fixes: move the inner method to another bean, or call it through the proxy.

> **Memory hook.** The bouncer: same door, same club behind it, but the bouncer decides whether you get in and writes your name in the log either way. A gift-wrapper (decorator) improves the gift; a bouncer (proxy) decides if you reach it.
> **Cheat code:** check, defer, cache or log BEFORE the real call, caller unaware, so proxy.

**When to use.** Access control, audit, lazy loading of expensive objects, caching of slow read-only lookups, remote calls behind a local interface, and framework cross-cutting concerns (transactions, security).

**Trade-offs and when NOT to use it.**

- **Don't hide the network.** A remote proxy that makes a 2-second call look like a getter invites callers to put it in a loop. Name it so the cost is visible, and give it timeouts.
- **Don't cache without an owner for staleness.** A caching proxy serves old answers by design. Someone must decide how old is acceptable. The TTL is a business decision.
- **Don't rely on a proxy you can route around.** If code can reach the real object directly (a second bean, a static accessor, `this`), the guarantee is a suggestion. The production <a href={`${BASE}lld/war/inventory/#flagged-findings`}>flagged findings</a> include an AOP pointcut bound by a string that no compiler checks.
- **Don't proxy for one caller.** If exactly one screen reads the records and always will, a check in that screen is simpler. The proxy earns its place when callers multiply.

**Practice.**

<Trace title="Who gets through the door?" steps={proxy} takeaway="Same shape as a decorator; different job. A proxy decides whether, when, where or how the real call happens, and it only sees calls made on the proxy." />

**Your turn.** MediCore's insurer exposes a slow remote eligibility check. Answers change rarely: a policy's cover holds for at least ten minutes. Write a caching proxy that counts hits and misses, expires entries after a TTL, and takes its clock as a dependency so a test can control time:

```java group=clinic
record Eligibility(boolean covered, Money cap) {}

interface EligibilityService { Eligibility check(String policyId); }   // a slow call to the insurer
```

<HintLadder hints={hints.cache} labels={turn}>

```java group=clinic
class CachingEligibility implements EligibilityService {
    private record Entry(Eligibility value, long storedAt) {}

    private final EligibilityService real;
    private final long ttlMillis;
    private final LongSupplier clockMillis;
    private final Map<String, Entry> cache = new HashMap<>();
    int hits, misses;

    CachingEligibility(EligibilityService real, long ttlMillis, LongSupplier clockMillis) {
        this.real = real;
        this.ttlMillis = ttlMillis;
        this.clockMillis = clockMillis;
    }

    public Eligibility check(String policyId) {
        long now = clockMillis.getAsLong();
        Entry e = cache.get(policyId);
        if (e != null && now - e.storedAt() < ttlMillis) {
            hits++;
            return e.value();
        }
        misses++;
        Eligibility fresh = real.check(policyId);          // if this throws, nothing is cached
        cache.put(policyId, new Entry(fresh, now));
        return fresh;
    }
}
```

With a long TTL, lookups `P1, P2, P1, P1, P3, P2` give **3 misses and 3 hits**, and the insurer is called 3 times. With a 10-minute TTL, a repeat at 9:59.999 is a hit and at exactly 10:00 a miss. The checker replays hundreds of random lookup sequences (twelve thousand lookups) with random clock jumps against an independent simulation, and confirms a failing insurer call is never cached. For production: this map is unbounded and single-threaded. Use `ConcurrentHashMap` with an eviction policy, or a library cache such as Caffeine.

<h2 id="facade">Chapter 4 · Facade: one door over many systems</h2>

**Concept.** A facade is a new, smaller interface over several subsystems, for one use case. It owns the order of the calls and the failure policy. It holds no business rules.

**Problem.** Discharging a patient touches five systems: freeze the final bill, charge what is owed, release take-home medicines, write the audit trail, and text the patient a summary. The front-desk screen does all five, so does the mobile app, and so does the night batch that discharges day-care patients after midnight. Compliance finds forty-one discharges with no audit record, all after midnight: the batch job's copy of the sequence had the audit step commented out during debugging.

**Bad design.** Every caller owns the choreography:

```java fragment
class NightDischargeBatch {
    void run(List<String> admissions) {
        for (String id : admissions) {
            Bill bill = billing.finalizeBill(id);
            PaymentResult paid = payments.process(id, bill.pendingDue());
            pharmacy.dispenseTakeHome(id);
            // audit.record("DISCHARGE", id, paid.reference());   // commented out in March, never restored
            sms.send(bill.patientPhone(), "Discharge complete. Bill: " + bill.total());
        }
    }
}
// FrontDeskScreen and MobileDischarge each hold their own copy of the same five steps.
```

**Detection cue.** Several callers repeat the same multi-system sequence, and the copies have started to drift. Its cousins: a caller that injects five services only to call them in a fixed order; a cross-cutting rule (audit, error mapping, timeouts) that must be identical for every caller and is implemented in each.

**Better design.** One class exposes the use case and hides the choreography:

```java group=clinic
record Bill(String admissionId, PhoneNumber patientPhone, Money total, Money paidSoFar) {
    Money pendingDue() { return total.minus(paidSoFar); }
}

interface BillingService { Bill finalizeBill(String admissionId); }
interface PharmacyService { void dispenseTakeHome(String admissionId); }
record DischargeSummary(Bill bill, PaymentResult paid) {}

class DischargeFacade {
    private final BillingService billing;
    private final PaymentProcessor payments;               // Chapter 1's port, PayLoom behind it
    private final PharmacyService pharmacy;
    private final SmsGateway sms;                          // Chapter 2's decorated gateway
    private final AuditLog audit;                          // Chapter 3's audit log

    DischargeFacade(BillingService billing, PaymentProcessor payments,
                    PharmacyService pharmacy, SmsGateway sms, AuditLog audit) {
        this.billing = billing;
        this.payments = payments;
        this.pharmacy = pharmacy;
        this.sms = sms;
        this.audit = audit;
    }

    DischargeSummary discharge(String admissionId) {
        Bill bill = billing.finalizeBill(admissionId);                          // 1. freeze the bill
        PaymentResult paid = payments.process(admissionId, bill.pendingDue());  // 2. settle dues
        pharmacy.dispenseTakeHome(admissionId);                                 // 3. meds out
        audit.record("DISCHARGE", admissionId, paid.reference());               // 4. compliance FIRST
        sms.send(bill.patientPhone(), "Discharge complete. Bill: " + bill.total());  // 5. then notify
        return new DischargeSummary(bill, paid);
    }
}

// Every caller (desk, app, night batch) now writes one line:
//     DischargeSummary s = discharge.discharge("ADM-2201");
```

The batch job can no longer forget the audit, because it never sees the steps. The checker runs a discharge of a ₹74,500 bill with ₹20,000 prepaid through the real PayLoom adapter and asserts the exact order of the five calls: billing, a ₹54,500 capture, pharmacy, `DISCHARGE` audited with PayLoom's reference, then the SMS.

**How it works.** Callers call `discharge(id)`. The facade calls each subsystem in order. Each subsystem keeps its own rules.

**A facade is not a God class:** it coordinates and never decides. No business rules inside, just the sequence and a uniform failure story. Bill math lives in `BillingService`; the facade only knows the order. That coordination is its single responsibility (SRP applied to entry points, the same reason the SOLID lesson's `ShiftReportFlow` was allowed to exist). The product was not fewer imports. It was one failure policy instead of forty.

GoF adds a point people forget: a facade doesn't have to lock the subsystems away. Callers with unusual needs may still use `BillingService` directly. The facade is the easy, safe path for the common use case, not a wall.

> **Memory hook.** Hotel front desk: you say "check me out" and the desk calls housekeeping, billing and the valet. You never phone the valet yourself.
> **Cheat code:** every caller re-implementing the same multi-subsystem sequence means facade. It sequences and never decides.

<Reveal q="Interviewer pushes: “Your DischargeFacade calls five services. Isn’t that a God class?” Defend it.">

The discriminator is **coordinates vs decides**. A God class decides: bill math, discount rules, stock logic all inline. The facade holds zero business rules. Bill math lives in `BillingService`, stock logic in `PharmacyService`; the facade knows only the sequence. Sequencing one use case is a single responsibility (SRP applied to entry points). The tell in code review: if the facade grows an `if` about money or medicine, logic is leaking in, so push it down.

</Reveal>

**When to use.** Several callers repeat one sequence across subsystems; a failure or timeout policy must be identical for every caller; you want a small stable API in front of a messy subsystem.

**Trade-offs and when NOT to use it.**

- **One caller, one subsystem.** A facade over a single service with a single caller is a pass-through class. Wait for the second caller or the second system.
- **Facades of facades.** If you need a facade to simplify your facade, the use cases have blurred together. Split by use case: `DischargeFacade`, `AdmissionFacade`, not `HospitalFacade`.
- **When it starts deciding.** The day `discharge()` computes a senior-citizen discount, it has become the God class it was protecting you from.

**Practice.**

```java group=clinic
class DischargeBlockedException extends RuntimeException {
    DischargeBlockedException(String admissionId, String reason) { super(admissionId + ": " + reason); }
}

class GuardedDischargeFacade {
    private final BillingService billing;
    private final PaymentProcessor payments;
    private final PharmacyService pharmacy;
    private final SmsGateway sms;
    private final AuditLog audit;

    GuardedDischargeFacade(BillingService billing, PaymentProcessor payments,
                           PharmacyService pharmacy, SmsGateway sms, AuditLog audit) {
        this.billing = billing;
        this.payments = payments;
        this.pharmacy = pharmacy;
        this.sms = sms;
        this.audit = audit;
    }

    DischargeSummary discharge(String admissionId) {
        Bill bill = billing.finalizeBill(admissionId);
        PaymentResult paid = payments.process(admissionId, bill.pendingDue());
        if (!paid.approved()) {                            // stop BEFORE anything leaves the building
            audit.record("DISCHARGE_BLOCKED", admissionId, "payment declined");
            throw new DischargeBlockedException(admissionId, "payment declined");
        }
        pharmacy.dispenseTakeHome(admissionId);
        audit.record("DISCHARGE", admissionId, paid.reference());
        try {
            sms.send(bill.patientPhone(), "Discharge complete. Bill: " + bill.total());
        } catch (RuntimeException smsDown) {               // a failed text never undoes a discharge
            audit.record("DISCHARGE_SMS_FAILED", admissionId, smsDown.getClass().getSimpleName());
        }
        return new DischargeSummary(bill, paid);
    }
}
```

Is `if (!paid.approved())` an "if about money" leaking in? No, and the difference is worth saying: the facade doesn't decide what is owed or whether a card is good. It decides whether to continue the sequence given a result. That is failure policy, and the War Room's facade dossier puts it exactly here. The checker asserts the exact call list for both inputs: after a decline, billing, payment and a `DISCHARGE_BLOCKED` audit, then an exception; with SMS down, a returned summary and a `DISCHARGE_SMS_FAILED` audit line.

<h2 id="composite">Chapter 5 · Composite: part-whole trees</h2>

**Concept.** A composite gives leaves and containers one interface. A leaf answers for itself. A container answers by asking its children. Callers never need to know which one they hold.

**Problem.** Inpatient bills nest. Room charges sit at the top. Beside them, a surgery package contains the surgeon's fee and theatre charges, and an anesthesia group inside the package has its own items. The prototype's `BillCalculator` has a method for charges, one for packages, and one for "packages that contain packages", which stops at two levels because that was the deepest anyone had seen. A cardiac-ward bill three levels deep comes out ₹8,000 short.

**Bad design.** Code that asks every node what it is:

```java fragment
long total(Object node) {
    if (node instanceof Charge c) return c.amount();
    if (node instanceof ChargeGroup p) {
        long sum = 0;
        for (Object child : p.items()) {
            if (child instanceof Charge c) sum += c.amount();
            else if (child instanceof ChargeGroup inner)                  // two levels, because that's all we'd seen
                for (Charge c : inner.charges()) sum += c.amount();   // a third level is silently skipped
        }
        return sum;
    }
    throw new IllegalArgumentException("unknown bill node");
}
```

**Detection cue.** A part-whole hierarchy where callers want to treat one and many the same way: file systems (a folder's size is its contents' size), org charts, UI component trees, nested bills, a garage of levels of zones of spots. In code: `instanceof` ladders over "single" and "group" types, and recursion depth limits that match the deepest example someone happened to see.

**Better design.** One interface. Leaves implement it directly; containers implement it by asking their children:

```java group=clinic
interface BillNode { Money total(); }

record Charge(String description, Money amount) implements BillNode {
    public Money total() { return amount; }                // leaf: my own amount
}

class ChargeGroup implements BillNode {
    private final String name;
    private final List<BillNode> children = new ArrayList<>();   // leaves OR groups: same type

    ChargeGroup(String name) { this.name = name; }

    ChargeGroup add(BillNode child) {
        children.add(child);
        return this;
    }

    String name() { return name; }

    public Money total() {                                 // container: sum of children, at any depth
        return children.stream().map(BillNode::total).reduce(Money.ZERO, Money::plus);
    }
}

BillNode admissionBill() {                                 // building the bill reads like the bill itself
    return new ChargeGroup("Admission ADM-2201")
        .add(new Charge("Room, 3 nights", Money.rupees(9000)))
        .add(new ChargeGroup("Surgery package")
            .add(new Charge("Surgeon fee", Money.rupees(40000)))
            .add(new Charge("OT charges", Money.rupees(15000)))
            .add(new ChargeGroup("Anesthesia")
                .add(new Charge("Anesthetist", Money.rupees(8000)))
                .add(new Charge("Drugs", Money.rupees(2500)))));
}
```

`admissionBill().total()` is **₹74,500**: the room's ₹9,000 plus a ₹65,500 surgery package, which includes the ₹10,500 anesthesia group. One call at the root; the tree recurses itself, to any depth. The checker builds a thousand random trees up to seven levels deep and compares every root total with a flat sum of the leaves.

**How it works.** `total()` on a group calls `total()` on each child. A child that is a group does the same. The recursion ends at leaves. Building the bill reads like the bill itself.

**Where does `add` live?** GoF describes two versions. The transparent composite puts `add`/`remove` on the shared interface, so leaves and groups look identical, and then `Charge.add` can only throw, which is a Liskov violation built into the interface. The safe composite, used here, puts `add` only on `ChargeGroup`: code that builds the tree knows which nodes are groups; code that uses it (`total`) never needs to. Prefer the safe version and say why.

Recognition cue: part-whole hierarchy plus "treat one and many uniformly". A follow-up to expect: "now print an itemized statement AND compute GST per category". Two or more operations over one stable tree is Visitor's cue (<a href={`${BASE}lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree`}>Drill 4</a> builds exactly this pair).

> **Memory hook.** Folders in folders: a folder's size is the sum of its contents, and you never care whether an item is a file or another folder. Bill groups are folders; charges are files.
> **Cheat code:** tree plus "one and many treated alike" means composite. A second operation over the tree means visitor is coming.

<Reveal q="Follow-up lands: “now print an itemized statement AND compute GST per category.” Why not just add print() and gst() to BillNode?">

Two operations today, five next quarter (insurance claim format, discount audit, export...). Every new operation edits every node class. The tree structure is stable; the operations over it multiply. That is Visitor's exact cue: one `accept(Visitor)` on the nodes, then each new operation is one new visitor class and zero node edits. The trade-off to say aloud: Visitor makes adding operations cheap but adding node types expensive, so you are betting the structure is done growing. <a href={`${BASE}lld/war/build-drills/#drill-4--composite--visitor-on-a-bill-tree`}>Drill 4</a> builds this pair; the <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> covers Visitor itself.

</Reveal>

**When to use.** Any tree where one and many answer the same questions: totals, sizes, counts, rendering, permissions over nested groups.

**Trade-offs and when NOT to use it.**

- **Fixed depth, different types.** Hospital, Ward, Bed, where each level has different operations (wards have nurses, beds have patients), is better as three plain classes. Composite pays off when every level answers the same questions.
- **Few shared operations.** If leaves and containers share one method and differ on ten, forcing a shared interface creates the transparent-composite lie.
- **Cycles.** A composite must be a tree. `group.add(group)` makes `total()` recurse forever (the checker shows the `StackOverflowError`). Build trees bottom-up from finished children, or reject adding an ancestor.

**Practice.**

**A common slip:** "Composite is for trees, so any tree is a composite." A tree whose nodes answer different questions is just a tree. Composite is the decision that one and many answer the same interface, so callers stop asking what they are holding.

**Interview summary.** "The bill is a part-whole tree, so charges and groups share BillNode and total() recurses. I keep add() on the group only, because a charge can't honour it. If you want statements and tax over the same tree, that is Visitor."

<h2 id="bridge">Chapter 6 · Bridge: two axes of change</h2>

**Concept.** Bridge splits two dimensions that vary independently into two hierarchies and connects them with a reference. The abstraction (what) holds an implementor (how).

**Problem.** MediCore issues three kinds of invoice (consultation, pharmacy, lab) and shows them two ways: HTML in the patient portal and plain text in an email. The prototype has a class for each pair, six in all. The HTML table markup is pasted three times and the lab copy still has last year's typo. Then pharmacy counters order 58 mm thermal receipt printers, and a ticket says "add ThermalInvoice x3". Two things change independently, but every class pays for both.

**Bad design.** One subclass per (kind x format) pair:

```java fragment
abstract class Invoice { abstract String render(); }
class ConsultationHtmlInvoice extends Invoice { /* consultation lines + HTML table markup */ }
class ConsultationEmailInvoice extends Invoice { /* consultation lines + plain text layout */ }
class PharmacyHtmlInvoice extends Invoice { /* pharmacy lines + the same HTML markup, pasted */ }
class PharmacyEmailInvoice extends Invoice { /* ... */ }
class LabHtmlInvoice extends Invoice { /* ... */ }
class LabEmailInvoice extends Invoice { /* ... */ }
// Thermal printers: three more. A fourth kind of invoice: one per format. m kinds x n formats = m * n classes.
```

**Detection cue.** Class names that are two words from two lists (`PharmacyHtml...`, `LabEmail...`), where a new item on either list costs one class per item on the other. Duplicated code along one axis (the HTML markup) is the second symptom.

**Better design.** The abstraction (what is billed) holds an implementor (how it is drawn):

```java group=invoices
record LineItem(String label, long paise) {}

interface Renderer {                                       // implementation side: HOW it is drawn
    String header(String title);
    String line(LineItem item);
    String footer(long totalPaise);

    static String rupees(long paise) {
        return paise / 100 + "." + (paise % 100 < 10 ? "0" : "") + paise % 100;
    }
}

abstract class Invoice {                                   // abstraction side: WHAT is billed
    private final Renderer renderer;                       // the bridge

    Invoice(Renderer renderer) { this.renderer = renderer; }

    abstract String title();
    abstract List<LineItem> items();

    final String render() {
        StringBuilder out = new StringBuilder(renderer.header(title()));
        long total = 0;
        for (LineItem item : items()) {
            out.append(renderer.line(item));
            total += item.paise();
        }
        return out.append(renderer.footer(total)).toString();
    }
}
```

The two sides grow independently. Invoice kinds know their lines and nothing about markup:

```java group=invoices
class ConsultationInvoice extends Invoice {
    private final String doctor;
    private final long feePaise;
    ConsultationInvoice(Renderer renderer, String doctor, long feePaise) {
        super(renderer);
        this.doctor = doctor;
        this.feePaise = feePaise;
    }
    String title() { return "Consultation"; }
    List<LineItem> items() { return List.of(new LineItem("Dr " + doctor, feePaise)); }
}

record Dispensed(String medicine, int quantity, long unitPaise) {}

class PharmacyInvoice extends Invoice {
    private final List<Dispensed> dispensed;
    PharmacyInvoice(Renderer renderer, List<Dispensed> dispensed) {
        super(renderer);
        this.dispensed = List.copyOf(dispensed);
    }
    String title() { return "Pharmacy"; }
    List<LineItem> items() {
        List<LineItem> lines = new ArrayList<>();
        for (Dispensed d : dispensed)
            lines.add(new LineItem(d.medicine() + " x" + d.quantity(), d.quantity() * d.unitPaise()));
        return lines;
    }
}

class LabInvoice extends Invoice {
    private final List<LineItem> tests;
    private final long collectionPaise;
    LabInvoice(Renderer renderer, List<LineItem> tests, long collectionPaise) {
        super(renderer);
        this.tests = List.copyOf(tests);
        this.collectionPaise = collectionPaise;
    }
    String title() { return "Lab"; }
    List<LineItem> items() {
        List<LineItem> lines = new ArrayList<>(tests);
        lines.add(new LineItem("Sample collection", collectionPaise));
        return lines;
    }
}
```

And renderers know markup and nothing about medicine:

```java group=invoices
class HtmlRenderer implements Renderer {
    public String header(String title) { return "<h1>" + esc(title) + "</h1><table>"; }
    public String line(LineItem item) {
        return "<tr><td>" + esc(item.label()) + "</td><td>" + Renderer.rupees(item.paise()) + "</td></tr>";
    }
    public String footer(long totalPaise) { return "</table><p>Total " + Renderer.rupees(totalPaise) + "</p>"; }

    private static String esc(String s) {                  // a doctor's name is data, not markup
        return s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;");
    }
}

class EmailTextRenderer implements Renderer {
    public String header(String title) { return title.toUpperCase() + "\n"; }
    public String line(LineItem item) { return item.label() + ": " + Renderer.rupees(item.paise()) + "\n"; }
    public String footer(long totalPaise) { return "Total: " + Renderer.rupees(totalPaise) + "\n"; }
}
```

`new ConsultationInvoice(new HtmlRenderer(), "Rao", 80000).render()` produces `<h1>Consultation</h1><table><tr><td>Dr Rao</td><td>800.00</td></tr></table><p>Total 800.00</p>`. Three kinds and two formats are five classes instead of six today, and the thermal printer will be one new class instead of three (Side quest 3). In general, m x n subclasses become m + n. For three kinds and three formats that is 9 versus 6; a fourth format makes it 12 versus 7. The checker renders every kind through every renderer and asserts the exact output, including a doctor named `<script>`.

**How it works.** The caller creates an invoice with a renderer and calls `render()`. `render()` is final: it asks the renderer for a header, a line per item and a footer, and sums the total. Kinds supply `title()` and `items()`.

**Bridge, Strategy, Adapter.** In Java, a bridge's abstraction holding its implementor looks exactly like an object holding a strategy, and some textbooks treat them as close cousins. The name signals intent. Strategy swaps one algorithm inside one class. Bridge says both sides are hierarchies that will keep growing independently, and you designed the split up front. Adapter is the opposite timing: a retrofit to make an existing class fit. (`render()` being `final` with abstract hooks is also a small Template Method. Patterns combine; naming the main one is enough.) The <a href="#bridge-vs-strategy">comparison chapter</a> puts Bridge and Strategy side by side. The production version is in the War Room's <a href={`${BASE}lld/war/inventory/#the-eight-that-arent-here`}>list of missing patterns</a>: the same invoice x renderer grid, "6 classes instead of 9".

> **Memory hook.** A universal remote and any TV: remotes (basic, voice, kids') vary on one side, TVs (brands) on the other, and one agreed protocol means any remote drives any TV. Nobody builds a "kids' remote for brand X".
> **Cheat code:** class names built from two lists means bridge. m x n becomes m + n.

**When to use.** Two dimensions that are both expected to grow: report type and output format, shape and renderer, device and remote, notification type and channel.

**Trade-offs and when NOT to use it.**

- **Only one dimension varies.** Three invoice kinds that only ever render as HTML need no bridge; an HTML method on each, or one shared formatter, is enough.
- **Speculative second dimension.** "We might print them someday" is not a second axis. Extract the renderer when the second format arrives (the same honest-OCP rule as the SOLID lesson's CSV side quest).
- **The dimensions aren't independent.** If thermal receipts must show different content (no table, a QR code instead of line items), the axes are coupled, and forcing them through one `Renderer` interface produces special cases on both sides.

<h2 id="flyweight">Chapter 7 · Flyweight: share repeated state</h2>

**Concept.** A flyweight splits an object's state in two. Intrinsic state is identical wherever the object appears and never changes, so one shared immutable object serves every use. Extrinsic state differs per use and stays outside the shared object. A small factory hands out the shared instances.

**Problem.** The pharmacy dashboard loads a day of dispensing across eleven clinics: about two hundred thousand lines. On the first Monday of the month it runs out of memory. A heap histogram shows `DrugInfo` objects, two hundred thousand of them, for twelve hundred distinct drugs. Every line was loaded with its own copy of the drug's description.

**Bad design.** Each row builds its own description of the drug, even the four-thousandth paracetamol:

```java id=pharmacyMess
record DrugInfo(String code, String name, String strength, String manufacturer) {}
record DispenseLine(DrugInfo drug, String patientId, int quantity) {}
record Row(String code, String name, String strength, String manufacturer, String patientId, int quantity) {}

List<DispenseLine> load(List<Row> rows) {
    List<DispenseLine> lines = new ArrayList<>(rows.size());
    for (Row r : rows)                                     // a fresh DrugInfo for every row
        lines.add(new DispenseLine(new DrugInfo(r.code(), r.name(), r.strength(), r.manufacturer()), r.patientId(), r.quantity()));
    return lines;
}
```

**Detection cue.** A measurement, not a hunch: a heap histogram (`jmap -histo`, or a JFR recording) dominated by many objects that are equal to each other, holding immutable data, where the number of distinct values is far smaller than the number of objects.

**Better design.** A catalog hands out one shared `DrugInfo` per drug code. The line keeps only what differs:

```java group=pharmacy
record DrugInfo(String code, String name, String strength, String manufacturer) {}   // intrinsic: shared, immutable
record DispenseLine(DrugInfo drug, String patientId, int quantity) {}              // extrinsic: this line only
record Row(String code, String name, String strength, String manufacturer, String patientId, int quantity) {}

class DrugCatalog {                                        // the flyweight factory
    private final Map<String, DrugInfo> byCode = new ConcurrentHashMap<>();

    DrugInfo intern(Row r) {                               // first sighting creates; every repeat shares
        return byCode.computeIfAbsent(r.code(), code -> new DrugInfo(code, r.name(), r.strength(), r.manufacturer()));
    }

    int size() { return byCode.size(); }
}

List<DispenseLine> load(List<Row> rows, DrugCatalog catalog) {
    List<DispenseLine> lines = new ArrayList<>(rows.size());
    for (Row r : rows) lines.add(new DispenseLine(catalog.intern(r), r.patientId(), r.quantity()));
    return lines;
}
```

Two hundred thousand lines across twelve hundred drugs now hold **1,200** `DrugInfo` objects instead of **200,000**, and every line for the same drug points at the same object. The checker loads exactly that day with fresh strings per row (as a database driver would produce) and counts distinct objects by identity in both versions. `ConcurrentHashMap.computeIfAbsent` is atomic, so two loader threads can't create two paracetamols. Records make the intrinsic part immutable, and that is not optional: if one line could change its drug's strength, it would change it for every patient.

**How it works.** The loader asks the catalog for the drug of each row. The catalog creates it on first sight and returns the same instance afterwards. The line object holds the shared reference plus its own patient and quantity.

You have used flyweights all along. `Integer.valueOf` always caches −128 to 127, so `Integer.valueOf(127) == Integer.valueOf(127)` is guaranteed `true`; outside that range it may or may not be (the cache can be enlarged), which is why boxed numbers are compared with `equals`. String literals are interned and shared. Enum constants are the purest flyweight in Java: a closed set of shared, immutable instances the JVM manages for you. And G1's string deduplication (<a href="https://openjdk.org/jeps/192">JEP 192</a>) is a flyweight the garbage collector applies to duplicate strings on its own.

> **Memory hook.** A font: a document with ten thousand letter e's stores one shape for "e" and ten thousand positions. The shape is intrinsic; where it is drawn is extrinsic.
> **Cheat code:** measured memory pressure plus many equal immutable objects means flyweight. Split intrinsic from extrinsic; share the first, pass the second.

**When to use.** A measured memory problem caused by a very large number of equal, immutable objects: game tiles, text glyphs, catalog entries, repeated reference data on rows.

**Trade-offs and when NOT to use it.**

- **No measured memory problem.** Two thousand objects is nothing. Flyweight adds a factory, an identity-sensitive design and a split state model; it needs a heap histogram to justify it.
- **The "shared" part is mutable.** Then sharing is a bug factory: one caller's change is every caller's change.
- **Few duplicates.** If most values are distinct, the factory's map costs memory and saves none.

**Practice.**

<h2 id="tell-them-apart">Chapter 8 · Compare all seven</h2>

**Concept.** Structure is not the answer; intent is. Adapter, Decorator, Proxy and Facade all hold an object and forward to it. What separates them is the shape of the interface they offer relative to what they wrap, and why they exist.

**Problem.** In a design round you draw an adapter for the SMS vendor, a retry wrapper around it, and a guard in front of the user-preferences service. The interviewer points at the retry wrapper: "Is that a decorator or a proxy?" Then at the guard. Then at the adapter: "Couldn't that be a facade?" Three boxes with identical arrows. The diagram can't answer for you. Your reasoning has to.

| Pattern | Interface vs wrapped object | How many wrapped | Who chose the wrapper | Intent | Example here | When NOT to use |
|---|---|---|---|---|---|---|
| **Adapter** | **different**: theirs to yours | one | you, to fit a misfit | translate | TextWave SDK | stable library; code you own |
| **Decorator** | **same**, stacks | one (which may itself be wrapped) | the caller's wiring, per need | add | retry + rate limit | one caller, fat interface |
| **Proxy** | **same**, usually single | one | the system; caller unaware | control | records auth | one caller; hidden network cost |
| **Facade** | **new, smaller**, over many | many | you, to simplify a use case | simplify | discharge | one caller, one subsystem |
| **Composite** | same, over a **tree** | many children | the structure | unify | bill tree | fixed depth, different ops |
| **Bridge** | abstraction holds implementor | one, by design | the design, up front | decouple | invoice x renderer | only one axis varies |
| **Flyweight** | shared object plus passed-in state | shared by many | a factory | share | drug catalog | no measured memory problem |

Three one-line discriminators for the round:

- **Adapter vs Facade:** an adapter makes one existing interface fit another that already exists (your port). A facade invents a new, simpler interface over many objects.
- **Decorator vs Proxy:** same structure. A decorator adds behaviour the caller chose and can stack. A proxy controls access the caller doesn't know about. If removing it changes what the feature does, it is a decorator; if removing it changes whether, when or where the call happens, it is a proxy.
- **Adapter vs Decorator:** an adapter changes the interface and keeps the behaviour. A decorator keeps the interface and changes the behaviour.

<h3 id="decorator-vs-proxy">Decorator vs Proxy</h3>

The code shapes are identical. The wiring shows the difference:

```java fragment
// Decorator: the caller's wiring chose the behaviour, and it stacks.
SmsGateway campaign = new RetryingGateway(new RateLimitedGateway(vendor, limiter), 3, sleeper);

// Proxy: the system decided; callers are handed only this and cannot skip the guard.
PatientRecords records = new RecordsAuthProxy(certified, policy, audit, caller);
```

| Question | Decorator | Proxy |
|---|---|---|
| Who decides it is there? | The caller or channel wiring | The system, so callers can't opt out |
| What does it change? | What the feature does (retry, log, compress) | Whether, when or where the call happens (guard, lazy, cache, remote) |
| Stackable in any order? | Yes, and order is semantics | Usually one, standing exactly where the real object would be |
| May it create the real object itself? | No, it receives a ready one | Yes (virtual proxy loads on first use) |
| Remove it and... | the feature does less | access, latency or location changes |
| Examples | `BufferedInputStream`, retry, logging | `@PreAuthorize`, lazy ORM associations, HTTP client stubs |

<h3 id="adapter-vs-facade">Adapter vs Facade</h3>

An adapter makes `TextWaveClient` fit the `SmsGateway` interface that already exists in your domain. A facade, `DischargeFacade`, did not fit anything that existed; it is a new interface built for one use case over five collaborators.

| Question | Adapter | Facade |
|---|---|---|
| Does the target interface already exist? | Yes, your port | No, you design it |
| How many objects behind it? | One | Many |
| Main job | Translate formats, units, errors | Fix a sequence and a failure policy |
| Should it contain decisions? | No | Only about continuing the sequence, never business rules |
| Swap story | A new vendor means a new adapter | A new subsystem means editing the facade |

<h3 id="bridge-vs-strategy">Bridge vs Strategy</h3>

Both hold an interface and delegate to it, so the diagrams match. The question is whether the holder is one class with a swappable algorithm, or the top of a hierarchy that grows on its own.

```java fragment
// Strategy: ONE class, one swappable algorithm. No hierarchy above it.
class Checkout {
    private final FeePolicy policy;                 // swap flat fee, percentage fee, ...
    Money total(Cart cart) { return cart.subtotal().plus(policy.feeFor(cart)); }
}

// Bridge: a HIERARCHY of abstractions, each holding one of a HIERARCHY of implementors.
abstract class Invoice { private final Renderer renderer; /* title(), items() hooks */ }
class LabInvoice extends Invoice { /* ... */ }      // grows on its own
class ThermalRenderer implements Renderer { /* ... */ }   // grows on its own
```

| Question | Strategy | Bridge |
|---|---|---|
| Holder | one context class | an abstraction hierarchy (abstract class plus subclasses) |
| What varies | one algorithm | two dimensions, each growing |
| Decided | usually when a rule changes | up front, at design time |
| Class count | 1 context + n strategies | m abstractions + n implementors, instead of m x n |
| Example | fee policy inside checkout | invoice kind x renderer |

Rule of thumb: if you can name two lists whose items multiply, it is a bridge. If there is one list of interchangeable behaviours, it is a strategy. The <a href={`${BASE}lld/lessons/behavioral-patterns/`}>behavioral patterns lesson</a> covers Strategy in full.

The discharge facade holds that whole stack as "the SMS gateway". Being able to narrate a stack like that, saying what each layer is and why it sits where it does, is what an interviewer means by "explain your design".

<h2 id="sq-footer">Side quest 1 · The opt-out footer</h2>

**Requirement:** "Legal: every marketing SMS must end with 'Reply STOP to opt out.' One-time passwords and appointment reminders must not."

**Where it lands:** a **Decorator** around the campaign stack only. The behaviour applies to whatever gateway the campaign uses (today TextWave, next year someone else) and to no other channel.

<Reveal q="Why not add the footer inside TextWaveAdapter?">

Because the rule is about marketing messages, not about TextWave. Inside the adapter it would also land on OTPs and reminders (wrong), and it would vanish the day MediCore switches vendors (also wrong). The adapter translates; it doesn't decide what a message says. The decorator sits exactly where the rule applies: on the campaign channel's wiring.

</Reveal>

<HintLadder hints={hints.footer} labels={turn}>

```java group=clinic
class OptOutFooterGateway implements SmsGateway {
    static final String FOOTER = " Reply STOP to opt out.";
    private final SmsGateway inner;

    OptOutFooterGateway(SmsGateway inner) { this.inner = inner; }

    public void send(PhoneNumber to, String text) {
        inner.send(to, text.endsWith(FOOTER) ? text : text + FOOTER);   // wrapping twice still adds it once
    }
}

SmsGateway marketingSms(SmsGateway vendor, RateLimiter limiter, Sleeper sleeper) {
    return new OptOutFooterGateway(campaignSms(vendor, limiter, sleeper));   // OTP and reminder wiring untouched
}
```

"Flu shots this week." goes out as "Flu shots this week. Reply STOP to opt out." The footer sits outside the retry, so it is appended once per logical message, not once per attempt. `otpSms` and `plainSms` are not touched.

</HintLadder>

**Transfer test:** the footer pushes some messages past 160 characters, so they split into two billed SMS segments. Should segment counting live in this decorator, in a new one, or in the adapter? (Hint: who defines what a segment is?)

<h2 id="sq-kit">Side quest 2 · The discounted kit</h2>

**Requirement:** "Pharmacy: sell a post-op kit (dressing ₹450, antibiotics ₹1,200, painkillers ₹280) at 10% off its contents. Kits appear on inpatient bills like any other charge."

**Where it lands:** **Composite**, by adding a new node type. A kit is priced from its children, like a group, but with its own rule. `BillNode` doesn't change, `ChargeGroup` doesn't change, and every existing bill keeps working.

<Reveal q="Why not add a percentOff field to ChargeGroup?">

Every group would carry a field that almost all of them leave at zero, and the next pricing idea (buy-two-get-one, a cap) would add another. A new node type keeps each rule in its own class and leaves the tree's existing node types closed: the open/closed principle, applied to a composite. It also composes: a discounted kit can sit inside a surgery package, which sits inside an admission.

</Reveal>

<HintLadder hints={hints.kit} labels={turn}>

```java group=clinic
class DiscountedGroup implements BillNode {                // a new node type; no existing node edited
    private final ChargeGroup contents;
    private final int percentOff;

    DiscountedGroup(ChargeGroup contents, int percentOff) {
        if (percentOff < 0 || percentOff > 100) throw new IllegalArgumentException("percentOff must be 0..100");
        this.contents = contents;
        this.percentOff = percentOff;
    }

    public Money total() {
        long full = contents.total().paise();
        return new Money(full - full * percentOff / 100);  // the discount rounds down to whole paise
    }
}
```

The kit's contents total ₹1,930; at 10% off it costs **₹1,737**. Placed inside an admission bill next to a ₹9,000 room charge, the bill's total is ₹10,737. The root never learned that kits exist. The checker tests 0%, 100%, out-of-range percentages, and a thousand random kits against an independent calculation.

</HintLadder>

**Transfer test:** finance now wants the statement to show the discount as its own negative line. Is that a change to `DiscountedGroup`, or the itemized-statement operation from the Visitor reveal? What would Visitor need to know about kits?

<h2 id="sq-thermal">Side quest 3 · The pharmacy printer</h2>

**Requirement:** "Pharmacy counters: print every invoice type on the new 58 mm thermal printers. 32 characters a line, amounts right-aligned."

**Where it lands:** **Bridge**, on the implementation side: one new `Renderer`. No invoice class changes. Consultation, pharmacy, lab and room-stay invoices all print on day one.

<Reveal q="How many classes would this ticket have cost with one subclass per (kind x format)?">

Four: `ConsultationThermalInvoice`, `PharmacyThermalInvoice`, `LabThermalInvoice` and `RoomStayThermalInvoice`, each a copy of the 32-column layout logic. With the bridge it is one class, and the layout logic exists once.

</Reveal>

<HintLadder hints={hints.thermal} labels={turn}>

```java group=invoices
class ThermalRenderer implements Renderer {                // 58 mm paper: 32 characters a line
    static final int WIDTH = 32;

    public String header(String title) {
        String t = title.length() > WIDTH ? title.substring(0, WIDTH) : title;
        return " ".repeat((WIDTH - t.length()) / 2) + t + "\n" + "-".repeat(WIDTH) + "\n";
    }
    public String line(LineItem item) { return row(item.label(), Renderer.rupees(item.paise())); }
    public String footer(long totalPaise) { return "-".repeat(WIDTH) + "\n" + row("TOTAL", Renderer.rupees(totalPaise)); }

    private static String row(String label, String amount) {
        int room = WIDTH - amount.length() - 1;            // keep at least one space before the amount
        String l = label.length() > room ? label.substring(0, room) : label;
        return l + " ".repeat(WIDTH - l.length() - amount.length()) + amount + "\n";
    }
}
```

Every body line is exactly 32 characters, the amount flush right, and a long medicine name is cut rather than wrapped into the amount column. The checker prints random invoices with labels up to 60 characters and amounts up to ₹1 crore through it and asserts every line's width and alignment.

</HintLadder>

**Transfer test:** the pharmacy now wants a QR code at the bottom of thermal receipts only. Does that fit inside `ThermalRenderer.footer`, or does it mean the two axes aren't independent after all?

<h2 id="sq-legacy">Side quest 4 · The acquired chain</h2>

**Requirement:** "MediCore has acquired Saltmarsh Clinics. Their patient charts live in a legacy store: `fetchChart(int mrn)` returns one semicolon-separated string. Doctors must see Saltmarsh histories in the same screens, under the same access rules."

**Where it lands:** an **Adapter** and a **Proxy**, composed. The adapter makes the legacy store speak `PatientRecords`; the existing `RecordsAuthProxy` then wraps it, so the access rule applies with zero new auth code.

<Reveal q="Could the proxy go inside the adapter instead?">

Not without writing a second proxy. `RecordsAuthProxy` implements and holds a `PatientRecords`; the legacy store isn't one until the adapter makes it one. So the adapter goes inside and the proxy outside, and that order has a bonus: a denied caller is stopped before the legacy store is touched at all. The checker counts the legacy store's reads to prove it.

</Reveal>

Saltmarsh's store, as it ships:

```java group=clinic
class LegacyChartStore {
    private final Map<Integer, String> charts;             // medical record number -> "DX:...;RX:...;LAB:..."
    int reads = 0;
    LegacyChartStore(Map<Integer, String> charts) { this.charts = Map.copyOf(charts); }
    String fetchChart(int mrn) {
        reads++;
        return charts.getOrDefault(mrn, "");
    }
}
```

<HintLadder hints={hints.legacy} labels={turn}>

```java group=clinic
class LegacyRecordsAdapter implements PatientRecords {
    private final LegacyChartStore store;
    LegacyRecordsAdapter(LegacyChartStore store) { this.store = store; }

    public History fullHistory(String patientId) {
        if (!patientId.startsWith("P-")) throw new IllegalArgumentException("not a MediCore patient id: " + patientId);
        int mrn = Integer.parseInt(patientId.substring(2));          // "P-1042" -> record number 1042
        String chart = store.fetchChart(mrn);
        List<String> entries = chart.isEmpty() ? List.of() : List.of(chart.split(";"));
        return new History(patientId, entries);
    }
}

PatientRecords saltmarshRecords(LegacyChartStore store, AccessPolicy policy, AuditLog audit, CallerContext caller) {
    return new RecordsAuthProxy(new LegacyRecordsAdapter(store), policy, audit, caller);   // adapter inside, proxy outside
}
```

Dr Rao, treating `P-1042`, sees `[DX:asthma, RX:salbutamol]`. A receptionist asking for the same patient is denied and audited, and `store.reads` stays at zero.

</HintLadder>

**Transfer test:** Saltmarsh's store is slow. Where would a caching proxy go in this stack: outside the auth proxy, between the auth proxy and the adapter, or inside the adapter? Which position could leak one doctor's cached answer to a receptionist?

<h2 id="interview-script">Say it in the room</h2>

**The 90-second answer** (adapt the nouns):

> "The edges of this system are vendors I can't change, so I started from ports my domain owns: an `SmsGateway` and a `PaymentProcessor`, each in my own words. Each vendor gets an **adapter**. It translates formats, units and error codes, including the int overflow on the payment vendor's amounts, so switching vendors is one class and one wiring line. Cross-cutting behaviour like retry, rate limiting and logging are **decorators** over the gateway, composed per channel in one wiring method; the nesting order is a decision I'll state. With retry outside the limiter, every attempt spends a permit. Access to patient records goes through a **proxy** that checks the policy and audits before delegating. It's the only object the composition root hands out, so there's no unguarded path. In Spring that's `@PreAuthorize`, with the self-invocation caveat. Discharge touched five services from three callers, so it's a **facade** that owns the sequence and the failure policy but no business rules. And the bill is a **composite**: charges and packages share one interface, so the total is one recursive call."

**Five follow-ups you will get:**

<Reveal q="1 · Decorator and proxy have the same structure. How do you tell them apart?">

By intent. A decorator adds behaviour the caller chose and can stack (retry, logging). A proxy controls access the caller doesn't get a say in (authorization, lazy loading, caching, remoting). A quick test: if removing it changes what the feature does, it's a decorator; if removing it changes whether, when or where the real call happens, it's a proxy.

</Reveal>

<Reveal q="2 · Why not just subclass the vendor adapter to add retry?">

Because behaviours combine. Retry, rate limit and logging as subclasses need one class per combination (sixteen across two senders), and each is coupled to its parent's internals. As decorators they're three classes that work around any `SmsGateway`, combined at wiring time, and a fourth behaviour is one class.

</Reveal>

<Reveal q="3 · Your caching proxy returns stale data. Is that a bug?">

It's a trade I made on purpose, and the TTL is the business decision behind it: an insurer's cover doesn't change minute to minute, so ten minutes of staleness saves most of the remote calls. For data where staleness is unacceptable (a bed's occupancy, a payment status) I wouldn't cache, or I'd invalidate on write. I'd also never cache failures, and I'd bound the cache's size in production.

</Reveal>

<Reveal q="4 · In Spring, why does @Transactional sometimes do nothing?">

The annotation is advice applied by a proxy around the bean. A call from one method of the bean to another is `this.method()`, a plain call on the target that never crosses the proxy, so the inner method's advice never runs. Fixes: move the method to another bean, or call it through the proxy. The same goes for private methods, which the proxy can't intercept.

</Reveal>

<Reveal q="5 · Isn't your facade a God class?">

It coordinates; it doesn't decide. Bill math lives in billing, stock in pharmacy; the facade knows the order of five calls and what to do when one fails. If it ever grew an `if` about money or medicine, that logic would move down into the service that owns it.

</Reveal>

<h2 id="cheat-sheet">Cheat sheet</h2>

| When you see... | Pattern | Do... | Watch out for |
|---|---|---|---|
| Vendor names and types inside domain code; a swap is coming | **Adapter** | Domain-owned port; one adapter per vendor translating requests, units and errors | Ports shaped like the vendor; decisions inside adapters; narrowing casts |
| Class names that list behaviours; "also X, some need Y" | **Decorator** | Same interface in and out; compose per channel at wiring | Nesting order changes semantics; fat interfaces; caching a command |
| A rule that must hold on every call, caller unaware | **Proxy** (protection) | Hand out only the proxy | Paths that bypass it, including `this` |
| An expensive object rarely used in full | **Proxy** (virtual) | Answer cheap calls; load on first real use | Thread-safety of the lazy load |
| A slow query that answers the same thing for a while | **Proxy** (caching) | Hit/miss with a TTL someone owns | Staleness, unbounded growth, caching failures |
| Several callers repeating one multi-system sequence | **Facade** | One use-case method; owns order and failure policy | Business rules creeping in |
| Part-whole tree; "treat one and many alike" | **Composite** | Shared interface; containers ask children; `add` on containers only | Cycles; second and third operations (use Visitor) |
| Class names built from two lists | **Bridge** | Abstraction holds implementor; m x n becomes m + n | A speculative second axis; axes that aren't independent |
| Heap full of equal immutable objects | **Flyweight** | Factory shares intrinsic state; extrinsic stays outside | Mutable "shared" state; optimising without measuring |

## Five mistakes to leave behind

1. **Naming wrappers by their shape.** Four patterns share one diagram. Name each by what the caller sees and why it exists, and say the alternative you rejected.
2. **Letting vendor vocabulary into the domain.** The port is yours, in your words. Every format, unit, width and error code is translated in the adapter, and a narrowing cast in an adapter is a bug waiting for a big number.
3. **Ignoring decorator order.** Retry outside a limiter spends a permit per attempt; logging outside a retry logs per logical send. The order is a design decision. State it.
4. **Trusting a proxy you can walk around.** If any path reaches the real object (a second bean, a static accessor, a self-call), the guarantee is a suggestion.
5. **Reaching for Bridge and Flyweight to look clever.** Bridge needs two axes that really vary; Flyweight needs a measured memory problem. Without them, both are ceremony.
