**One-line answer.** "It is past a POC and not yet production: the full chain is proven end to end with real uploads, the contracts between three services are authenticated and idempotent, and it has metrics, dead-lettering and tests. What it lacks is what a first production incident would expose — retries, a drained dead-letter queue, a gold-set quality measure, and a BAA-covered model path. I can name every gap and the order I would fix them."

## 1. How to answer "was it production or a POC?"

Interviewers ask this to see whether you inflate. The winning answer has three parts: (1) what is genuinely production-grade, with evidence; (2) what is not, named plainly; (3) the ordered plan. Never say "production" without qualification; never say "POC" for something with 361 tests and a dead-letter queue. Say "pre-production on the dev server, with these specific gaps".

## 3. The traps, grouped by what they would do in production

### Would lose or corrupt data

1. **Entity write total-loss window.** Old rows deleted unconditionally, then only successfully uploaded entities re-inserted. If every S3 upload fails mid-run, the document ends with nothing. Fix: write new, swap pointers, delete old (the same order the write path already uses for chunks).
2. **Erasure can leave unreachable PHI.** S3 batch delete logs failures after pointer rows are gone. Fix: delete objects first or keep a tombstone table until S3 confirms.
3. **Half-failed document acked as success.** Fix: per-track outcome recorded; any track failure dead-letters; DLQ drained by a redrive job.

### Would page someone at 3 a.m.

4. **No retries**; a transient Gemini 503 sends the document straight to a DLQ nobody drains. Fix: quorum queues (so `x-delivery-count` exists) or explicit republish-with-delay, plus a DLQ alert.
5. **Truncated model output → empty list**, silently. Fix: treat `MAX_TOKENS` as failure; metric.
6. **Shutdown does not stop the consumer**; the pool closes under in-flight handlers. Fix: cancel consumers, await in-flight, then close.
7. **DLQ gauge task reference dropped** — can be garbage-collected and stop updating. One line: keep the task handle.

### Would embarrass you in a clinical review

8. **Allergies not extracted.**
9. **Alert rules match on display name** — fixed by LOINC grouping, but the rule file still names analytes by string.
10. **LLM concerns have no stable identity**; a dismissal does not survive re-analysis (J13).
11. **Lab unit normalisation once computed then discarded** — fixed; the regression test is the point.

### Would fail a security or compliance review

12. Default internal token shipped in config; a committed JWT literal in Java; `patient_id` still a metric label on one counter; prompts exposed by a catalogue endpoint; local-dev `CREATE TABLE IF NOT EXISTS` runs on every boot in every environment.

## 4. What I would do first, in order (and why that order)

1. **J14 — persist the four sections** after every merge. Turns a 5–20 s read into 30 ms and removes the S3 fan-out from the read path entirely. Unblocks the Java switch.
2. **J3 — Java reads sections from the pipeline** and stops generating its own from Gemini summaries. Today the cards a clinician sees are Gemini prose, not the extracted entities; two Gemini bills per document. This is the single biggest correctness-and-cost item.
3. **Gold set + P/R** for the five demo notes and 50 real de-identified notes. Every model/prompt decision after this is measured.
4. **Reliability trio**: quorum queues + retries, DLQ redrive + alert, per-track failure handling.
5. **Data-safety pair**: entity write ordering, erasure tombstones.
6. **BAA path**: Vertex AI or MedGemma 4B on-prem — a business decision with the numbers already gathered.

## 5. The corrections I made to my own earlier docs — say these, they prove rigour

* "Section reads take 5–7 s" → measured 5–30 s; then found the cause (unbounded S3 fan-out) and fixed it.
* "Three retries" → there were none; the header the code checked never exists on classic queues.
* "Dashboards show pipeline health" → several panels read metrics nothing incremented; one implied the consumer was down. Replaced four dashboards with one honest one.
* "Cost panel" → priced at a two-generations-old rate, \~4× under.
* "The webhook 401 has three causes" → found a fourth by running it: the rate limiter after the security chain. Also revealed a production endpoint broken the same way.

## 6. Likely follow-ups

* _"How would you know it's healthy in production?"_ — Documents processed vs dead-lettered per hour; p95 stage durations; webhook 2xx ratio; span-located ratio; Gemini error and 429 rates; DLQ depth alert; a synthetic upload every 15 minutes with an expected entity count.
* _"Rollback plan for J3?"_ — One config row per section key (`source = GEMINI | PIPELINE`). Flip back, no deploy.
* _"SLA?"_ — None defined; I would propose "sections updated within 3 minutes of upload for 95% of documents" and instrument it from the progress events, which already carry the timestamps.
* _"What would you cut to ship sooner?"_ — The RAG read path (no consumer yet) and the MedGemma path (measured too slow). Both are already sequenced last.
