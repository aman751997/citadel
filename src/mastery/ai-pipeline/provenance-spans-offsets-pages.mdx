**One-line answer.** "Every entity carries the verbatim sentence it came from, its character offsets in the source text, and the PDF page. The model's quote is treated as a claim, not a fact: a resolver has to find it in the real text before it becomes an offset, and if it cannot, the entity says `unlocated` instead of guessing. That is what turns a model output into something a doctor will click on."

## 1. Why a doctor needs this

A clinician will not act on "Metformin–renal risk, confidence 0.87". They will act on _"eGFR: 48 mL/min/1.73m2" — page 1, labs panel, 20 Jan 2025_, because they can open the document and check in three seconds. Provenance is the difference between a decision-support tool and a rumour. It is also the hallucination defence: a fabricated entity has no sentence to point at, so it fails resolution and is flagged.

## 2. What was broken before (J10) — say this, it shows judgement

* `raw_text` was documented as "exact span from clinical text" but actually held the model's _canonical name_. It and `normalized_name` were the same string. So "Type 2 Diabetes Mellitus" was recorded as the "raw text" of a sentence that said "T2DM".
* Character offsets were computed nowhere. The legacy zero-shot stage produced them and the client threw them away.
* Nothing in either service knew about pages — PDF extraction flattened the document to one string.

Three fixes, two repos: Java preserves page boundaries when it extracts text (a page map alongside the text in S3); the prompts ask every model for the verbatim `span` next to the canonical name; and a resolver turns quotes into offsets.

## 3. How the resolver works

<Mermaid code={`flowchart TD
    Q[entity.source_span<br>model's quote] --> E{exact substring<br>in source text?}
    E -->|yes| O[char_start / char_end<br>span_match = exact]
    E -->|no| N{whitespace / case<br>normalised match?}
    N -->|yes| O2[offsets from the<br>original string<br>span_match = normalized]
    N -->|no| U[span_match = unlocated<br>offsets null — no guessing]
    O --> P["page = page_map.lookup(char_start)"]
    O2 --> P
    G[GLiNER entity<br>already has offsets] -->|shift only, never re-match| P`} />

Three details interviewers pick on:

1. **Model quotes are not guaranteed substrings.** LLMs "fix" typos, drop double spaces, change case. So the match is tiered and strict: exact, then normalised, then a guarded fuzzy tier (see the repo note below). A loose match would let a quote land on the wrong sentence and produce a confident wrong page. Wrong provenance is worse than none.
2. **GLiNER offsets are trusted, never re-matched.** GLiNER returns character spans natively. In the cascade it ran on masked text, but the mask is space-for-character, so offsets are identical to the original. They are only _shifted_ if the text was windowed.
3. **Masking preserves coordinates.** This is the trick that ties pages 3 and 5 together: replacing covered spans with spaces (not deleting them) means every later stage's offsets are already in document coordinates. No offset arithmetic, no off-by-one class of bugs.

Real run: `Span resolution complete … total_entities=49 located=49 pages_assigned=49 match_counts={"exact": 49}`.

<StatusBadge kind="implemented" /> **Repo check, original text disagrees.** The resolver in `app/services/span_resolver.py` has a third, `fuzzy` tier between `normalized` and `unlocated`, which this page originally listed as a next experiment. It only runs for quotes of at least 12 normalised characters, scores candidate regions with `difflib.SequenceMatcher.ratio()` at a 0.85 minimum, and has a numeric guard: every number in the quote must appear in the candidate, because in a clinical record the numbers are the finding (a "152/94" sentence must never be shown as the source of a "118/72" finding). The reasoning in point 1 below still holds: a loose match produces confident wrong provenance, so the guard is strict. The `normalized` tier also strips PDFBox line-break hyphenation. Rehearse the four tiers as exact, normalized, fuzzy (guarded), unlocated, and note that the measured run above resolved everything at `exact`.

## 4. Pages

Java's PDFBox extraction writes the text with page boundaries preserved (form-feed separators / a page map of character ranges) into S3 next to the text. The pipeline fetches the page map, and `page = the page whose range contains char_start`, 1-based. Scanned PDFs go through Gemini OCR in Java and produce the same map. When there is no map (older documents), `page` is null and the UI shows a document link instead of a page reference — degrade, do not fabricate.

## 6. Provenance vs PHI isolation — how they coexist

Offsets and page numbers are _not_ PHI: they are integers. The verbatim quote _is_ PHI, so it lives in the S3 entity JSON (encrypted at rest, one object per entity, under the patient prefix) and Postgres carries only the pointer plus the numbers needed to sort and group. A section read fetches the JSONs it needs (see the S3 fan-out story on page 10 for how that went wrong and was fixed).

## 7. Hallucination — the answer they want

"The LLM never creates a fact without a quote; the quote must be found in the source text; unfound quotes are flagged, counted (`span_match` distribution on the dashboard) and shown as unlocated rather than hidden. Codes come from a vocabulary lookup, not the model, wherever MedCAT covered the span. And the sections are computed from entities by deterministic code — the only place free-text reasoning enters is the critical-alerts pass, which returns `related_entities` so each concern points back at the facts it used."

## 8. What is still missing

* No _relation_ provenance — a drug and its dose are two entities linked by proximity, not an explicit edge. A dosage change on page 3 and a drug name on page 1 will not be linked.
* `normalized` matches (case/whitespace) are honest but coarse. The repo has since added a guarded fuzzy tier (similarity ratio with a strict threshold and a numeric guard); how good it is still needs measuring against a gold set, not eyeballing.
* The AlertDetail screen that shows the quotes is not built yet (frontend U4 in the plan). The data is there; the UI is not.

<Reveal q="Intermediate: why does masking use spaces instead of deleting the covered text?">

<Reveal q="Advanced: the LLM quotes a sentence that differs slightly from the source. What could go wrong with a loose match?">

A fuzzy match can land on the wrong sentence and show a confident wrong page. In a clinical note near-identical sentences differ only in numbers, so the repo's fuzzy tier requires the quote's numbers to appear in the candidate, and a quote that fails the guard or the 0.85 score stays `unlocated`.
