<Reveal q="Q1. Walk me through the system.">

The 60-second pitch on page 1. Upload → Java → RabbitMQ event with an S3 pointer → Python: three-stage NER + chunking in parallel → merge → four webhooks → Java section jobs → STOMP push → cards. 55 s per document.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q2. Why is it event-driven?">

Latency mismatch (analysis takes a minute; the upload must return now), decoupled failure (either side can be down), and the broker as the throttle and fan-out point. Trade-off: harder debugging, no ordering — paid for with progress events and idempotency keys.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q4. Why Python for the pipeline in a Java shop?">

The models are Python-native. Java owns the record, Python owns the reading, and the boundary is a queue and two authenticated HTTP contracts.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q5. Where does the LLM sit?">

Three places: enrichment and discovery inside NER (thinking off), the reasoning pass inside critical alerts (thinking on), and — being retired — Java's own section generator.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q6. How does the browser get updates?">

Java publishes to `/topic/patients.{id}.ai-sections` via a STOMP relay to RabbitMQ; the portal's single multiplexed STOMP client subscribes with a Bearer JWT; CONNECT is authenticated and each SUBSCRIBE authorised against a verified user–patient link. <StatusBadge kind="unverified" label="WebSocket auth" /> I could not find this auth code in the local Java checkout (it is on a different branch than the one checked out), so confirm it before you state it.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q7. Multi-tenancy?">

Enforced in Java (JWT `tenantId`, Hibernate filter, tenant-scoped uniqueness). The event carries `tenantId`; entities and chunks store it. Gap: chunk tenancy still falls back to a DB lookup.

*Topic: A. Architecture and design.*

</Reveal>

<Reveal q="Q15. What is the claim-check pattern and where do you use it?">

The message carries a pointer (S3 key), not the payload. The broker never holds clinical text; the consumer fetches it.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q19. Why three stages instead of one LLM?">

Cost, latency, PHI surface, and codes/provenance. MedCAT is free and gives UMLS codes; GLiNER reads context MedCAT misses; the LLM handles the long tail. Each stage narrows the next one's input.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q20. What is MedCAT?">

A UMLS concept linker on spaCy with context-vector disambiguation and MetaCAT meta-annotations (Status, Subject). Fast, deterministic, code-linked. Needs a UMLS licence.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q21. What is GLiNER?">

A small bi-encoder transformer for zero-shot span NER: give it label names, get spans. No codes, so we use it only on text MedCAT left uncovered.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q22. How do you avoid the stages double-tagging?">

Space-mask MedCAT's covered spans so every remaining character keeps its offset; GLiNER and the LLM see only leftovers.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q26. Provenance — how does a doctor trust an extraction?">

Verbatim span, character offsets, page. The model's quote is a claim; a resolver finds it in the source or marks it unlocated. 49/49 exact on the measured runs.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q30. Entity types?">

DIAGNOSIS, CONDITIONS, MEDICATIONS, LAB_VALUE, VITAL_SIGN, PROCEDURES, ANATOMY. Codes: UMLS CUI (with ICD-10/SNOMED lists), RxNorm, LOINC.

*Topic: C. Clinical NLP.*

</Reveal>

<Reveal q="Q35. Why is CRITICAL_ALERTS fast and the others slow?">

It is persisted after every merge and served from a row (30 ms); the others compute on read and fetch entity JSONs from S3 (5–20 s cold). Persisting all four is J14.

<Reveal q="Q47. Chunking?">

512 tokens (the encoder's limit) with 50 overlap, split on clinical section headers first. Tokens, not characters.

<Reveal q="Q48. Embedding model?">

MedCPT article encoder, 768-d, biomedical, self-hosted. Caveat: trained on articles, not notes.

<Reveal q="Q49. Is retrieval built?">

Indexing yes; querying no. Plan: hybrid (vector + tsvector), reciprocal rank fusion, cross-encoder rerank, cited answers, RAGAS-style evaluation.

<Reveal q="Q50. Where does PHI live?">

S3 only (entity JSON, extracted text). Postgres holds pointers, codes, numbers, offsets — and chunk vectors plus a full-text (`tsvector`) index of the chunk words, because you cannot vector-search S3. The raw chunk text stays in S3.

## Intermediate: defend your decisions

<AnswerModes id="rabbit-vs-kafka" q="Why RabbitMQ and not Kafka?">
<Fragment slot="short">

Work-queue semantics: per-message ack, dead-letter and retry, plus the STOMP plugin for the browser relay. Kafka wins when you need replay or many independent consumer groups reading history, and we do not need that yet.

</Fragment>
<Fragment slot="medium">

RabbitMQ gives per-message ack and nack, dead-lettering and the STOMP relay the browser uses. Kafka gives a replayable log, ordering per partition, multiple consumer groups and very high throughput, but costs you native dead-lettering, delayed retry and the STOMP relay, and has heavier operations. The one Kafka feature I would want, replay, I could get by re-publishing the extraction-completed events from the documents table, because the text is still in S3. <StatusBadge kind="hypothetical" label="No replay script exists" />

</Fragment>
<Fragment slot="deep">

Add when I would change my answer: if many downstream consumers of the same events appear (analytics, de-identification, billing), the log model pays off. Add the honest weaknesses of what we chose: today there are no retries because the code checks `x-delivery-count`, which only quorum queues set and ours are classic; the fix is quorum queues or republish-with-delay, a DLQ alert and a redrive job.

</Fragment>
</AnswerModes>

<AnswerModes id="thinking-budget" q="How did you cut an LLM call from 40 seconds to 10?">
<Fragment slot="short">

I read `usage_metadata` instead of blaming the model. Each call carried 7,004 hidden thought tokens. Structured extraction is not a reasoning task, so I set `thinking_budget=0` on the extraction calls: 40.3 s to 10.2 s on the same prompt and schema.

</Fragment>
<Fragment slot="medium">

Everyone assumed LLMs are slow. The usage metadata showed 7,004 thought tokens per call, the model's hidden reasoning, billed as output and never returned. I turned thinking off for extraction only and kept it on for the clinical-reasoning pass, as a setting. Same prompt and schema, comparable output, 40.3 s down to 10.2 s. Then I measured 3.8-flash against 2.5-flash on five notes: 9.6 s against 25.4 s median, with counts that matched the notes.

</Fragment>
<Fragment slot="deep">

Add the cost angle: thought tokens are billed as output, so they also dominated cost, and the cost counter under-reported about 4x until the price table was fixed (2.5 Flash is $0.30 input and $2.50 output per million tokens). Add the trade-off: with thinking on, the reasoning pass took 23 s and produced 9 concerns; off, 6-8 s and 7-9 concerns, so thinking is kept on there. Lesson: defaults are tuned for chat, not for pipelines.

</Fragment>
</AnswerModes>

<Reveal q="Q9. Exactly-once?">

Doesn't exist across a broker, two databases and an HTTP call. At-least-once delivery plus idempotent side effects gives effectively-once outcomes.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q12. Prefetch vs concurrency?">

Prefetch is how many unacked messages the broker hands us (a buffer, 5); the semaphore is how many we run (1 locally). Prefetch above concurrency keeps the next message warm without over-committing.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q14. How do you make the webhook idempotent?">

Key `patient:section:document:pipeline_run_id`; Java `INSERT … ON CONFLICT DO NOTHING`; a no-op insert is a replay. Run id is per handler invocation, so redelivery = fresh key, notifier retry = same key.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q17. Ordering between two documents of one patient?">

Not guaranteed and not needed: sections recompute from all entities on every merge, so the final state is the same whichever finishes last.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q8. What would you change if you started over?">

<Reveal q="Q10. What happens if the consumer crashes mid-document?">

The message is unacked; RabbitMQ redelivers to the next consumer; every write is a replace (delete-by-document, re-insert) and the webhook carries a fresh idempotency key because the work really was redone.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q11. How do you stop a poison message looping?">

`message.process(requeue=False)`: an exception rejects without requeue, the dead-letter exchange routes it to `ai-pipeline.dlq`.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q13. Retries?">

Honestly: none today. The code checks `x-delivery-count`, which only quorum queues set; ours are classic. Fix is quorum queues or explicit republish-with-delay, plus a DLQ alert and redrive.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q16. Outbox pattern?">

Dual-write problem: row + publish. Java writes the row first, marks it `*_PENDING_MQ` if publish fails, and a scheduler republishes. Outbox-lite: the job row is the outbox. Gap: a crash between commit and publish leaves a row at QUEUED nothing revisits.

*Topic: B. Messaging and reliability.*

</Reveal>

<Reveal q="Q18. Back-pressure?">

The queue absorbs bursts; the semaphore is the knob; webhooks run outside it so a dead Java cannot hold a pipeline slot.

*Topic: B. Messaging and reliability.*

</Reveal>
