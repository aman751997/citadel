## The 60-second pitch (memorise this)

"Hospitals accumulate paper — discharge summaries, lab reports, consultation notes. A doctor opening a patient's record has ninety seconds to answer three questions: what medicines is this person on, what are the labs doing, and is anything dangerous going on. I built the service that reads every uploaded document and keeps four live sections of the record up to date: active medications, recent labs, a patient timeline, and critical alerts. It is a Python service driven by RabbitMQ events from our Java patient-service. Each document goes through a three-stage clinical NER pipeline — MedCAT for UMLS concepts, GLiNER for spans MedCAT missed, and an LLM for normalisation and discovery — then the entities are stored with verbatim span provenance, embedded into pgvector for retrieval, and the four sections are recomputed. Java is told over an authenticated webhook, and the browser gets a STOMP push so the cards update live. End to end a document takes about 55 seconds on a laptop, 49–75 entities per note, every span located back to its page."

That paragraph contains the six things every follow-up question hangs off: **event-driven**, **three-stage NER**, **provenance**, **sections**, **RAG index**, **numbers**. Each has its own page.

### Each box in plain English

| Component | What it does for the user |
| --- | --- |
| Java patient-service | Accepts the upload, stores the PDF, turns it into text, announces "text is ready" |
| RabbitMQ | Holds the announcement until the pipeline can pick it up |
| Python consumer | Takes one announcement at a time and runs the whole analysis |
| NER stage | Finds medicines, labs and diagnoses in the text and records where each came from |
| Chunk and embed stage | Cuts the text into pieces and indexes them for search (pgvector) |
| Profile merge and alerts | Combines everything known about the patient and checks for danger |
| Section-ready webhooks | Tell Java that each of the four sections can be refreshed |
| STOMP push | Makes the card on the doctor's screen update without a reload |

## Why event-driven and not a REST call?

Interviewers ask this first. Three reasons, in order of weight:

1. **Latency mismatch.** Reading a document takes tens of seconds to minutes (a 27B model reading a page is slow; even Gemini takes 10 s per call). No HTTP client should hold a connection that long, and the uploader should get a 201 immediately. The upload returns in about a second; the analysis finishes when it finishes.
2. **Decoupled failure.** If the AI service is down, uploads still work. Events queue in RabbitMQ and are processed when it comes back. If Java is down when analysis finishes, the webhook retries and the sections stay readable through the pipeline's own API. Neither side can take the other down.
3. **Back-pressure and fan-out.** The broker holds the load. Concurrency is a single knob on the consumer (`MAX_CONCURRENT_EVENTS`). A second consumer (say, a de-identification job) subscribes to the same exchange without touching Java.

The honest trade-off: _debugging is harder_ (a request has no single stack trace) and _ordering is not guaranteed_. We paid for that with per-stage progress events (J11) and idempotency keys (page 2).

## The two services and who owns what

| Concern | Owner | Why there |
| --- | --- | --- |
| Documents, patients, users, auth, tenants | Java patient-service | Existing system of record; JWT, tenancy, RBAC already live |
| PDF → text (PDFBox, Gemini OCR for scans) | Java | It already had the file and the S3 client; text extraction is not "AI" |
| Clinical NER, provenance, entity store | Python pipeline | Python ML ecosystem: MedCAT, GLiNER, transformers, aioboto3 |
| Chunking, embeddings, vector index | Python | Same |
| Section computation (meds, labs, timeline, alerts) | Python computes; Java caches, serves, pushes | Java already had the result table, the job queue with retries, S3 persistence, the WebSocket relay — a whole "AI section subsystem". The integration is a source swap behind that machine, not a rebuild |
| Database schema | Java (Flyway) owns it; Python writes three tables directly | One shared Postgres. A known trap: two repos, one schema (page 9) |

## The stack, one line each

* **Python 3.12, FastAPI, aio-pika, asyncpg, aioboto3, pydantic, structlog, prometheus_client** — the service is \~8,100 lines under `app/`, 361 unit tests.
* **RabbitMQ** — topic exchange for events, dead-lettering, STOMP plugin on 61613 for the browser relay.
* **Postgres 18 + pgvector 0.8** — shared with Java; entities, chunks, health profile.
* **S3 (ap-south-1)** — every entity is its own JSON object under `patients/{id}/entities/{uuid}.json`; Postgres holds only pointers and non-PHI columns. That is the PHI isolation rule.
* **MedCAT 1.16 + UMLS Small pack** (573k concepts), **GLiNER medium v2.1**, **MedCPT** article encoder (768-d), **Gemini 2.5/3.8 Flash** via AI Studio, **MedGemma 27B** self-hosted (parked, page 7).
* **Prometheus + Grafana** — one dashboard, one row per stage; Pushgateway for one-shot benchmarks.
* **Docker Compose** locally; the model services (medcat, gliner, embedding) are separate containers with memory limits.

## Likely follow-ups and one-line answers

* _"Why Python for the pipeline when the company is Java?"_ — The models are Python-native (MedCAT, GLiNER, transformers). Java owns the record; Python owns the reading. The boundary is a queue and two authenticated HTTP contracts.
* _"Why RabbitMQ and not Kafka?"_ — It was already the platform broker, we need work-queue semantics (ack per message, dead-letter, retry) rather than a replayable log, and the STOMP plugin gives the browser relay for free. Kafka would be the answer if we needed replay or multiple independent consumer groups reading history.
* _"Why not one LLM call per document and be done?"_ — Cost, latency, PHI, and provenance. Page 3.
* _"Multi-tenant?"_ — Java enforces tenancy (JWT `tenantId`, Hibernate filter, per-tenant uniqueness). The pipeline receives `tenantId` on the event and forwards it on progress events; entity rows carry it. Honest gap: chunk tenancy depends on a DB lookup, page 9.

<Reveal q="Intermediate: why does the event carry pointers instead of the extracted text?">

The broker is not a PHI store, messages get logged and inspected, and a queue full of 100 KB notes is a different capacity problem. The consumer fetches the text from S3 itself. The pattern is called claim check.

</Reveal>

<Reveal q="Advanced: Java is down when analysis finishes, and a second hospital joins. What happens, and what breaks first?">

Java down: the webhook retries (two attempts with backoff), then is logged and the message is acked; sections stay queryable through the pipeline's API. Second hospital: Java enforces tenancy (JWT `tenantId`, Hibernate filter, per-tenant uniqueness), the pipeline forwards `tenantId` and entity rows carry it. The honest gap the text names is chunk tenancy, which depends on a DB lookup (page 9). Design drill 3 works the rest.
