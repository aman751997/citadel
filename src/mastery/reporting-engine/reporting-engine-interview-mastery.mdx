## What it does, who it is for, and what was built

**Business problem.** Hospital staff need reports (revenue by branch, no-shows by doctor, top medicines) and product keeps changing what those reports must say. Writing SQL, a controller and a release for each one does not keep up.

**Who uses it.** Tenant admins and branch admins of the hospital platform. The access policy in the code maps `SUPER_ADMIN` and `ADMIN` to the whole tenant and `BRANCH_ADMIN` to one branch. <StatusBadge kind="implemented" /> How many tenants or users run it is not in the source. <StatusBadge kind="unverified" /> Confirm this yourself.

**My responsibilities.** The original text says "I designed and led `reporting-service`". <StatusBadge kind="unverified" /> Confirm this yourself. A read-only look at the git history (2026-10-18) shows 164 commits touching the folder from 18 author names. The first commit, the bulkhead PR #1706 and the GST migrations V33 and V36 were written by other contributors; about 50 commits are under two author names that look like yours. ### Corrections found when I checked the code (2026-10-18)

The chapters now carry these fixes inline. Learn them, because an interviewer who reads the code will find them:

1. **Branch header.** The shared `BranchContextFilter` prefers the `X-Branch-Id` header over the token's branch claim. The tenant filter prefers the token. So "headers are ignored" is true for tenant (when the token has a tenant claim) but not for branch. Details on page 6.
2. **`excludePatientIdentifiers`** is stored in the DSL but nothing in the validator or compiler reads it. The PII protection is the catalog allow-list and the name-pattern block.
3. **k-anonymity** uses the `minimumGroupSize` the DSL carries. The compiler adds `HAVING` only when the query is grouped and the value is above zero. There is no server-side minimum.
4. **Audit row** has a `report_definition_id` column, but the adapter never fills it. It records user, SQL hash, datasource, row count, truncated flag, elapsed time and tenant.
5. A datasource with no tenant column throws `IllegalStateException`, which the global handler turns into a 500, not a 400.
6. **Refund netting** was done by rewriting computed catalog columns (correlated subqueries with the `{f}.` placeholder in V30, V31, V35, V38), not by repointing datasources at views named `v_*_net_of_approved_refunds`. Those view names are not in the repository. `v_invoice_revenue_line` is a real billing view.
7. **Counts.** Six `*E2EIT` classes (not seven). 40 migrations by end of 2026-09-11. V19 was added 2026-07-09, not August.
8. **Platform roles.** The real role prefix in the code differs from the neutral `PLATFORM_*` wording used here.

## 1. Why this project is worth 10 minutes of an interviewer's time

Most teams build reports the slow way: a product manager asks for "revenue by branch for last month", a developer writes SQL, wraps it in a controller, tests it, ships a release. Three weeks later the next report request arrives. We built the other way: **one engine, zero code per report**. A report is a small JSON recipe saved in a table. The engine turns the recipe into safe SQL at run time. Adding a new dashboard is a data change, not a deploy.

The analogy that lands with every interviewer: **this is Grafana + Prometheus for business data.**

| Grafana / Prometheus concept | Reporting engine equivalent | Concrete artefact |
| --- | --- | --- |
| A **data source** Grafana can query (a Prometheus instance) | `catalog_datasource` row: one fact table or view, with its tenant / branch / date / soft-delete columns and which DB pool to use | `'patient.appointments'` → table `patient.appointments`, pool `patient` |
| A **metric name and its labels** (`http_requests_total{status}`) | `catalog_field` row: field key, physical column, roles (DIMENSION / MEASURE / TIME / FILTER), type, allowed aggregations and operators | `status` → DIMENSION+FILTER, STRING, operators EQUALS/IN |
| A **panel** with a PromQL query | `report_definition` row: the JSON DSL (datasource, dimensions, measures, filters, sort, limit, privacy) + chart type | "Appointment Status" PIE, COUNT by `status` |
| A **dashboard** (JSON of panels in a grid) | `report_dashboard` row: `items` JSONB list of `{definitionId, layoutHint}`, default date range, default branch scope | 4 tiles, `layoutHint: "half"|"full"` |
| **PromQL engine** that evaluates the query | `QueryCompiler` (489 lines): DSL → parameterised SQL, injecting tenant / branch / k-anonymity / LIMIT / timezone | Page 2 shows the exact SQL |
| **Time range picker** at the top of the dashboard | `ExportDateRangeResolver`: TODAY / THIS_WEEK / THIS_MONTH computed in the tenant's timezone, appended as a BETWEEN filter | one definition serves all three ranges |
| **Provisioning** dashboards from files in Git | Flyway migrations seed catalog rows and starter definitions; a PR review is the approval gate | V3, V4, V9 and most of V16–V40 are data-only (my count: 28 of the 40 files at 2026-09-11 contain no CREATE or ALTER) |
| **Alerting / scheduled reports** | `report_schedule` + ShedLock poller: cron delivery of a definition as CSV by email, with the creator's stored scope | polls every 60 s, lock 30 s–9 min |
| What Grafana does **not** give you | Tenant + branch isolation from the security context, PII allow-list, k-anonymity, per-tenant timezone, a per-run audit row. This is why we built instead of embedding. | Pages 1, 3, 6 |

One sentence to memorise: **"Catalog is the type system, the DSL is the program, the compiler is the interpreter, and the guardrails are compiled in so nobody can forget them."**

## 3. The 60-second pitch (say it out loud)

"I designed and led `reporting-service`, a metadata-driven reporting engine for our multi-tenant hospital platform. Instead of hand-writing SQL per report, a tenant admin composes a report in the UI; we persist it as an eight-field JSON DSL, and at run time a compiler turns it into parameterised SQL against a server-controlled catalog. The catalog is an allow-list: which tables, which columns, which aggregations and operators. The compiler injects the tenant predicate from the token and the branch predicate from the branch context, k-anonymity via HAVING when the report sets a minimum group size, a hard row cap after a deterministic sort, and timezone-correct bucketing. Execution goes through a read-only pool per source database with a 3-second statement timeout and a bulkhead. There is a synchronous audit row per run (a cache hit skips it), a short-TTL result cache, and a ShedLock-based scheduler that emails CSVs with the creator's stored scope. Thirty-eight migrations later, roughly two-thirds of them are pure data: new dashboards ship as INSERTs. It is live and iterating weekly with product."

## 4. The 3-minute version (when they say "tell me more")

1. **Problem.** Five service teams, each hand-rolling report endpoints. Every product tweak ("GST-inclusive or exclusive?") was a code change and a release. No shared tenancy or PII rules across them.
2. **Insight.** Every report is the same shape: _from one table, group by some columns, aggregate some columns, filter, sort, limit_. That shape is small enough to be a DSL and safe enough to compile if identifiers come from a catalog and values are bound.
3. **Guardrails compiled in.** Tenant predicate always. Branch predicate for branch admins. HAVING COUNT(\*) >= k for privacy, using the k the report carries. LIMIT with a forced ORDER BY so truncation is meaningful. `AT TIME ZONE :tz` so a 2 a.m. IST appointment lands in the right month.
4. **Protecting the OLTP databases.** Read-only Hikari pools, `SET LOCAL statement_timeout`, resilience4j bulkhead with fail-fast 429, Redis result cache. The adapter is a seam: moving to the read replica was a URL change.
5. **Operations.** Catalog snapshot reloaded every 5 minutes. ShedLock scheduler. Synchronous audit row. Two-tenant integration test. Real-engine E2E tests per business domain (appointments, billing, pharmacy, telecaller, refunds).
6. **Proof it works.** Product reversed a GST decision in one week (V33 exclusive → V36 inclusive). Both were data migrations. No Java changed. That is the whole argument for metadata-driven.

<AnswerModes id="re-why-metadata-driven" q="Why did you build a metadata-driven reporting engine instead of writing endpoints per report?">
<Fragment slot="short">

Every report has the same shape: one table, group by, aggregate, filter, sort, limit. That shape fits a small JSON DSL, so we store reports as rows and compile them to safe SQL in one place. A new report is an INSERT, not a release, and the tenancy and privacy rules live in the compiler where nobody can forget them.

</Fragment>
<Fragment slot="medium">

The problem was that each report was a ticket: SQL, controller, test, release, and no shared tenancy or PII rules. The insight was that all reports are the same shape. So the DSL has eight fields, a catalog says which tables and columns are allowed, and a compiler builds the SQL. Identifiers come from the catalog, values are bound, and group and order use ordinals. The guardrails (tenant predicate, branch predicate, row cap, timeout, bulkhead) are compiled in. The best proof was the GST decision: product reversed it within a week and both directions were data migrations, with no Java change.

</Fragment>
<Fragment slot="deep">

Layers: catalog (type system), DSL (program), validator (type checker), compiler (interpreter), adapter (sandboxed runtime). Safety comes from the layering: PII is handled at field level, tenancy at datasource level, layout at dashboard level. A flat "report equals SQL string" table would need a SQL parser to enforce any of it. Trade-offs: the compiler is single-table plus same-database lookup joins, so anything else needs a view or a computed catalog column; and catalog changes are PR-reviewed rather than self-service. Not yet built: per-tenant bulkheads, a compile dry-run at save, async exports. <StatusBadge kind="planned" />

</Fragment>
