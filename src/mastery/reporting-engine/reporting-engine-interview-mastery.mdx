## 1. Why this project is worth 10 minutes of an interviewer's time

Most teams build reports the slow way: a product manager asks for "revenue by branch for last month", a developer writes SQL, wraps it in a controller, tests it, ships a release. Three weeks later the next report request arrives. We built the other way: **one engine, zero code per report**. A report is a small JSON recipe saved in a table. The engine turns the recipe into safe SQL at run time. Adding a new dashboard is a data change, not a deploy.

The analogy that lands with every interviewer: **this is Grafana + Prometheus for business data.**

| Grafana / Prometheus concept | Reporting engine equivalent | Concrete artefact |
| --- | --- | --- |
| A **data source** Grafana can query (a Prometheus instance) | `catalog_datasource` row: one fact table or view, with its tenant / branch / date / soft-delete columns and which DB pool to use | `'patient.appointments'` → table `patient.appointments`, pool `patient` |
| A **metric name and its labels** (`http_requests_total{status}`) | `catalog_field` row: field key, physical column, roles (DIMENSION / MEASURE / TIME / FILTER), type, allowed aggregations and operators | `status` → DIMENSION+FILTER, STRING, operators EQUALS/IN |
| A **panel** with a PromQL query | `report_definition` row: the JSON DSL (datasource, dimensions, measures, filters, sort, limit, privacy) + chart type | "Appointment Status" PIE, COUNT by `status` |
| A **dashboard** (JSON of panels in a grid) | `report_dashboard` row: `items` JSONB list of `{definitionId, layoutHint}`, default date range, default branch scope | 4 tiles, `layoutHint: "half"|"full"` |
| **PromQL engine** that evaluates the query | `QueryCompiler` (489 lines): DSL → parameterised SQL, injecting tenant / branch / k-anonymity / LIMIT / timezone | Page 2 shows the exact SQL |
| **Time range picker** at the top of the dashboard | `ExportDateRangeResolver`: TODAY / THIS_WEEK / THIS_MONTH computed in the tenant's timezone, appended as a BETWEEN filter | one definition serves all three ranges |
| **Provisioning** dashboards from files in Git | Flyway migrations seed catalog rows and starter definitions; a PR review is the approval gate | V3, V4, V9, V16–V38 are pure data |
| **Alerting / scheduled reports** | `report_schedule` + ShedLock poller: cron delivery of a definition as CSV by email, with the creator's stored scope | polls every 60 s, lock 30 s–9 min |
| What Grafana does **not** give you | Tenant + branch isolation from the JWT, PII allow-list, k-anonymity, per-tenant timezone, regulator-grade audit row. This is why we built instead of embedding. | Pages 1, 3, 6 |

One sentence to memorise: **"Catalog is the type system, the DSL is the program, the compiler is the interpreter, and the guardrails are compiled in so nobody can forget them."**

## 3. The 60-second pitch (say it out loud)

"I designed and led `reporting-service`, a metadata-driven reporting engine for our multi-tenant hospital platform. Instead of hand-writing SQL per report, a tenant admin composes a report in the UI; we persist it as an eight-field JSON DSL, and at run time a compiler turns it into parameterised SQL against a server-controlled catalog. The catalog is an allow-list: which tables, which columns, which aggregations and operators. The compiler injects tenant and branch predicates from the JWT, k-anonymity via HAVING, a hard row cap after a deterministic sort, and timezone-correct bucketing. Execution goes through a read-only pool per source database with a 3-second statement timeout and a bulkhead. There is a synchronous audit row per run, a short-TTL result cache, and a ShedLock-based scheduler that emails CSVs with the creator's stored scope. Thirty-eight migrations later, roughly two-thirds of them are pure data: new dashboards ship as INSERTs. It is live and iterating weekly with product."

## 4. The 3-minute version (when they say "tell me more")

1. **Problem.** Five service teams, each hand-rolling report endpoints. Every product tweak ("GST-inclusive or exclusive?") was a code change and a release. No shared tenancy or PII rules across them.
2. **Insight.** Every report is the same shape: _from one table, group by some columns, aggregate some columns, filter, sort, limit_. That shape is small enough to be a DSL and safe enough to compile if identifiers come from a catalog and values are bound.
3. **Guardrails compiled in.** Tenant predicate always. Branch predicate for branch admins. HAVING COUNT(\*) >= k for privacy. LIMIT with a forced ORDER BY so truncation is meaningful. `AT TIME ZONE :tz` so a 2 a.m. IST appointment lands in the right month.
4. **Protecting the OLTP databases.** Read-only Hikari pools, `SET LOCAL statement_timeout`, resilience4j bulkhead with fail-fast 429, Redis result cache. The adapter is a seam: moving to the read replica was a URL change.
5. **Operations.** Catalog snapshot reloaded every 5 minutes. ShedLock scheduler. Synchronous audit row. Two-tenant integration test. Real-engine E2E tests per business domain (appointments, billing, pharmacy, telecaller, refunds).
6. **Proof it works.** Product reversed a GST decision in one week (V33 exclusive → V36 inclusive). Both were data migrations. No Java changed. That is the whole argument for metadata-driven.

## 7. The analogy table (memorise the columns)

| Programming languages | Reporting engine | What it guarantees |
| --- | --- | --- |
| Type system | Catalog (datasources + fields + allowed aggs/operators) | You cannot reference something that does not exist or is not allowed |

| Type checker | `CatalogValidator` | Field-level 400s before any SQL exists |
| Compiler | `QueryCompiler` | Identifiers looked up, values bound, structure by ordinals, guardrails injected |
