Security interviewers do not want the list of features. They want to hear you _attack your own system_ and name the exact line that stops each attack. This page is written that way: an attacker's move, what the engine does, and why it is enough.

<StatusBadge kind="implemented" /> Each claim below was re-read against the code on 2026-10-18 (state of `develop` at 2026-09-11 for `reporting-service`, plus the shared `healthcare-common` filters). Where the code does not support an earlier claim, this page now says so. Three attacks (4, 6 and 7) changed materially after that check, so read those carefully. Do not repeat the old versions in an interview.

## The one rule everything hangs on

> **Values are bound. Identifiers are looked up. Structure is ordinals.** Users can only ever choose from a menu the server wrote; the only thing that travels as free text is a _value_, and values go through JDBC bind parameters.

## Attack 1 — classic SQL injection through a filter value

```json
{ "field": "status", "operator": "IN", "values": ["COMPLETED') OR 1=1 --"] }
```

**What happens.** The compiler emits `status::text IN (:flt_0)` and binds the list. Postgres receives the literal string `COMPLETED') OR 1=1 --` as a value and compares it to the status column. Zero rows match. Nothing else changes.

**Line that stops it.** `QueryCompiler.appendFilter`, which never concatenates values. [OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html): defence 1, prepared statements.

## Attack 2 — injection through an identifier

```json
{ "field": "status; DROP TABLE patient.appointments; --", "alias": "x" }
```

**What happens.** `CatalogValidator` looks the field key up in the catalog snapshot. Not found → HTTP 400 with a field-level error message. The compiler never runs. Even if the validator were bypassed, the compiler _also_ resolves fields through the catalog and throws on an unknown key.

**Why this matters.** Identifiers cannot be bind parameters in SQL, so the only safe identifier is one the server already knows. That is the whole reason the catalog exists. Interviewers love this line: _"You cannot bind a column name, so we made column names a lookup."_

## Attack 3 — injection through an alias

```json
{ "agg": "COUNT", "field": "count", "alias": "x\" FROM patient.patients; --" }
```

**What happens.** Aliases are the one place a user string reaches the SQL text. The compiler strips everything outside `[A-Za-z0-9_ ]`, de-duplicates against other aliases, and wraps in double quotes: `AS "x FROM patientpatients"` (the compiler also trims the result). Harmless. GROUP BY and ORDER BY never use the alias; they use ordinals, so a mangled alias cannot change the statement's shape.

## Attack 4 — spoofing tenant or branch via headers

```http
POST /api/v1/reporting/reports/{id}/run
X-Tenant-Id: some-other-hospital
X-Branch-Id: BR-XYZ
Authorization: Bearer <my real JWT for tenant acme, branch BR-DIL>
```

**Tenant: the attack fails.** `TenantContextFilter` takes the tenant from the token's tenant claim first. The `X-Tenant-Id` header is only a fallback when the token has no tenant claim (it exists for unauthenticated flows such as registration). With a normal token the spoofed tenant header is ignored. The compiler then injects `tenant_id = :tenant_id` unconditionally. <StatusBadge kind="implemented" />

**Branch: the code does not stop it.** `BranchContextFilter` reads `X-Branch-Id` _first_ and falls back to the token's branch claim only when the header is absent. `ReportAccessPolicy.resolve` then takes the branch for a `BRANCH_ADMIN` from that branch context, so a branch admin who sends a different `X-Branch-Id` is compiled as `(acme, RESTRICTED, [BR-XYZ])`. Tenant isolation still holds; branch isolation inside the tenant depends on something else, and I found no check in the filter, the policy or the compiler that compares the header with the branches in the token. <StatusBadge kind="implemented" label="Confirmed in code" /> The filter's own comment says the header "allows multi-branch switching", so this may be deliberate. <StatusBadge kind="unverified" /> I could not see whether a gateway strips or overwrites the header before it reaches the service; confirm this yourself before you describe it as exploitable or as safe.

**What the old text said, and why not to repeat it.** "Headers are ignored; everything derives from the token" is true for tenant and false for branch. If an interviewer reads the shared filter, that sentence fails.

**What I would do about it.** Make the policy intersect the header with the branches in the token, and add a test that sends a spoofed `X-Branch-Id`. <StatusBadge kind="hypothetical" /> Not built, and I found no existing test for it.

**Soundbite (accurate version).** "Tenant scope comes from the token. Branch scope comes from the branch context, which currently prefers the header, and that is the first thing I would tighten."

## Attack 5 — a datasource someone forgot to scope

Suppose a future migration adds a datasource with `tenant_column = NULL`. **The compiler refuses to compile it** and throws `IllegalStateException`. A missing tenant column is not "no filter", it is "no report". Fail closed. The caller sees a 5xx rather than a 400, because only validation exceptions map to 400. The same refusal applies to a branch-restricted caller on a datasource with no branch column.

## Attack 6 — pulling PII columns

```json
{ "field": "phone_hash" }   or   { "field": "aadhaar_vault_id" }
```

**What happens.** Two layers. First, the catalog simply does not list raw identifiers; the catalog is an allow-list and anything unlisted "does not exist". Second, the validator applies a regex block `.*_(vault_id|token|hash)$` (case-insensitive) to both the field key _and_ the physical column, so even a mistaken catalog row cannot expose a tokenised identifier. <StatusBadge kind="unverified" /> The old text also said the `privacy.excludePatientIdentifiers` flag is enforced server-side. In the code, that flag is stored in the DSL but nothing in the validator or compiler reads it. Do not claim it protects anything; the protection is the catalog allow-list and the name-pattern block. The regex only catches names ending in `_vault_id`, `_token` or `_hash`, so a raw identifier column with a different name would be blocked only by never being in the catalog.

## Attack 7 — re-identifying a patient from a tiny group

"Patients seen by Dr X with consultation type PANCHAKARMA on 2026-09-03" might return a group of 1. With a date filter and a branch, that one row is a person.

**What happens.** `privacy.minimumGroupSize` compiles to `HAVING COUNT(*) >= :min_group_size`. Groups smaller than k are removed _inside the database_, before rows leave, so a client cannot post-process its way around it. This is [k-anonymity](https://en.wikipedia.org/wiki/K-anonymity) applied at the aggregate level; we do not claim the stronger l-diversity or differential privacy, and saying so out loud earns credibility.

**The limits you must know.** <StatusBadge kind="implemented" /> k is not chosen by the server. It is the value in the report's own `privacy` block. The compiler adds `HAVING` only when the query has both dimensions and measures and `minimumGroupSize` is above 0, and I found no server-side minimum or default. `preview` accepts a DSL from the request, and report authors can save their own definitions, so anyone who can submit a DSL also chooses k. The real V19 migration even seeds a revenue report with `minimumGroupSize` 1, on purpose, with the comment "pure revenue aggregate, no patient-level data to protect". The accurate claim is: "k-anonymity is enforced in SQL for whatever k the report carries, and system templates set it deliberately." A server-side floor per datasource (for example in the catalog) would close the gap. <StatusBadge kind="hypothetical" />

## Attack 8 — a background job with no user

Scheduled reports run from a cron poller. There is no JWT. The first implementation resolved scope as ALL, so a branch admin's scheduled CSV could have contained every branch. **Fix (V10):** persist `branch_scope_type` and `branch_ids` on the schedule row at creation time; compile at fire time with that stored scope. **Lesson:** every background path needs an explicit identity; "no user" must never default to "all access". Full story on page 4.

## Attack 9 — denial of service via an expensive report

A user (or a buggy UI loop) submits a 5-dimension, 90-day, hour-bucketed report against a large table, 50 times a second.

| Knob | Bounds | What the user sees |
| --- | --- | --- |
| Validator bounds (≤5 dims, ≤10 filters, ≤100 values, limit ≤5000) | query _shape_ | 400 before SQL exists |
| `SET LOCAL statement_timeout = '3000ms'` | time per statement | report error after 3 s; connection freed |
| `LIMIT :row_limit` (hard cap 5000) after a forced ORDER BY | rows into JVM memory | `meta.truncated=true`, biggest groups kept |
| Read-only Hikari pool per source DB | connections reporting can open to OLTP | waits on the pool |
| resilience4j bulkhead, 10 concurrent, `maxWaitDuration=0` | threads in the reporting JVM | immediate 429 "try again" |
| Redis result cache 60 s / 30 s, key includes tenant + branches + DSL + params | repeated identical runs | `meta.cached=true`, no DB hit |

Soundbite: **"Four knobs, four failure modes: timeout bounds time, LIMIT bounds memory, pool size bounds the database, bulkhead bounds the JVM."** Read more: [statement_timeout](https://www.postgresql.org/docs/current/runtime-config-client.html#GUC-STATEMENT-TIMEOUT), [resilience4j Bulkhead](https://resilience4j.readme.io/docs/bulkhead), [HikariCP readOnly](https://github.com/brettwooldridge/HikariCP#gear-configuration-knobs-baby).

## Attack 10 — poisoning the cache across tenants

Two tenants run byte-identical report definitions. Could tenant B get tenant A's cached rows?

**What happens.** Cache key = `rpt:run:{definitionId}:sha256(tenant | branches | canonical DSL | sorted params)`. Different tenant → different hash → different key. Editing a definition evicts `rpt:run:{definitionId}:*`. Honest gap: eviction uses the Redis `KEYS` scan, which is O(N) and would be replaced with `SCAN` or key tagging at scale ([Redis docs on why KEYS is dangerous](https://redis.io/docs/latest/commands/keys/)).

## Defence in depth — which layer is load-bearing?

<Mermaid code={`flowchart TD
    L1["@PreAuthorize REPORT_VIEW / admin roles<br>(coarse gate)"] --> L2["ReportAccessPolicy<br>PLATFORM_* → 403 · ADMIN → ALL · BRANCH_ADMIN → RESTRICTED"]
    L2 --> L3["CatalogValidator<br>unknown field, PII regex, bounds"]
    L3 --> L4["QueryCompiler<br>refuses DENY scope · refuses unscoped datasource · injects predicates"]
    L4 --> L5["PostgresJdbcAdapter<br>read-only tx · timeout · bulkhead"]
    L5 --> L6["Postgres role: SELECT only on source schemas (unverified)"]
    style L2 fill:#ffe0b2,stroke:#e65100`} />

The highlighted layer is the load-bearing one for **platform staff** (PLATFORM\_\* roles). The controller's `@PreAuthorize` lets those roles in, so the policy is what stops them; if it did not, the compiler would have nothing to inject. (The shared Hibernate tenant filter also has a platform bypass for specific cross-tenant roles on our own database; it is separate from source-database reads.) That is why the policy throws `AccessDeniedException` for any PLATFORM\_\* role before anything else runs. Knowing _which_ layer matters most is what separates "we have defence in depth" from understanding it.

## Read-only, enforced three times

1. Hikari pool `readOnly=true` (connection-level default).
2. `DataSourceTransactionManager.enforceReadOnly=true` (issues `SET TRANSACTION READ ONLY`).
3. `TransactionTemplate.readOnly=true` around the adapter call.

A compiler bug that emitted `UPDATE` would still be refused by Postgres, because the transaction is read-only. <StatusBadge kind="unverified" /> A database role that only has SELECT would be a fourth layer; I could not see the grants, so confirm whether it exists before you claim it.

## Audit trail (DPDP / regulator conversation)

Every executed run writes one row to `report_run_audit`: user id, sha256 of the compiled SQL, datasource key, row count, truncated flag, elapsed ms, tenant and the created timestamp. The table has a `report_definition_id` column, but the adapter never sets it, so it is empty. A result served from the Redis cache returns before the adapter and writes no audit row. It is written **synchronously** after the query, inside try/catch, and a failure to audit is logged but never fails the report. Why synchronous: `@Async` loses the thread-local tenant context and can drop rows on a crash; we had a real incident pattern with after-commit writes not committing. India's [DPDP Act](https://www.meity.gov.in/data-protection-framework) framing: "who accessed what, when" must be demonstrable.

<Reveal q="Basic: in one sentence, why is this not a SQL injection machine?">

Values are bound parameters, identifiers are looked up in the catalog, operators and aggregations are enums, aliases are sanitised and quoted, and GROUP BY and ORDER BY use ordinals, so no user string shapes the statement.

</Reveal>

<Reveal q="Intermediate: the catalog's column names go straight into SQL text. Why is that acceptable?">

Because the catalog is seeded by Flyway and reviewed in a pull request, not editable by users. The trust boundary is the migration review. If the catalog were editable through a UI, those physical column and table names would become an injection surface, which is exactly why catalog changes are treated as security changes.

</Reveal>

<Reveal q="Advanced: attack your own system. What are the weakest points?">

Branch scope can be set by a request header (tenant cannot); k-anonymity depends on the k the report carries and has no server floor; `excludePatientIdentifiers` is not enforced; the PII regex only matches three name suffixes; a datasource with no tenant column fails as a 5xx rather than being caught at startup. Each of these is a real, code-confirmed gap, and each has a small fix. <StatusBadge kind="hypothetical" /> Naming them before the interviewer does is the strongest answer.

</Reveal>
