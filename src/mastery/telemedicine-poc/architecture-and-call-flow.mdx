## In plain words first

A video call needs three things: a way for two browsers to find each other (signalling), a server that forwards audio and video packets between them (an SFU, "selective forwarding unit"), and permission tokens so random people cannot join a consultation. LiveKit gives us the SFU and the token format; we wrote the small server that mints tokens, starts recordings, and turns finished recordings into notes. Everything runs on one Mac; the patient joins from a phone on the same Wi-Fi.

<StatusBadge kind="tested" label="Prototyped on one Mac" /> Everything on this page ran in the August 2026 demo. None of it is a production deployment.

## Processes and ports

| Process | Port | Role | Started by |
| --- | --- | --- | --- |
| Redis (Homebrew, native on the host) | 6379 | Coordination between LiveKit server and the egress worker | `brew services start redis` |
| `livekit-server` (binary) | 7880 ws/http · 7881 tcp fallback · 50000–50200 udp | The SFU: signalling websocket, media forwarding, room state, webhooks | `start-all.sh` |
| `livekit/egress` (Docker) | — | Joins rooms as a hidden participant and writes track audio to `/out` (bind-mounted `./recordings`) | `docker compose up` |
| Token/API server (Express 5, ESM) | 3001 | Mint JWTs, start/stop egress, finalise, transcribe, summarise, sign, serve sessions | `start-all.sh` |
| Vite dev server (HTTPS, self-signed) | 5173 | Serves the React app and proxies `/api` and `/lk` | `start-all.sh` |

In plain English, each component does one job:

* **Redis:** the shared notebook LiveKit and the egress worker use to find each other.
* **livekit-server:** the SFU. Forwards audio and video, holds room state, fires webhooks.
* **egress (Docker):** a hidden participant that writes one microphone track to a file.
* **Token/API server:** the server we wrote ourselves. Tokens, recording control, finalise, transcription trigger, summary, sign-off.
* **Vite dev server:** serves the React app and hides two backends behind one HTTPS address.

## The single-origin trick (the networking decision worth explaining)

Browsers grant microphone and camera access only on secure origins. A phone on the LAN must therefore load the app over HTTPS. But if the page is HTTPS and the signalling websocket is plain `ws://host:7880`, the browser blocks it as mixed content. And if the API is on a different port, the phone must accept a second self-signed certificate. So the Vite dev server serves HTTPS with one self-signed cert and **proxies both** the REST API (`/api` → `http://localhost:3001`) and the LiveKit signalling websocket (`/lk` → `ws://localhost:7880`, with `ws: true`). One origin, one certificate, no mixed content. WebRTC media itself still flows directly over UDP and is encrypted by DTLS-SRTP regardless.

## Three paths into one finalise

A call can end in three ways, and every one of them must produce exactly one manifest and stop exactly the right egresses:

1. **Doctor presses Stop recording** → `POST /recording/stop`.
2. **Doctor presses End** → `POST /consult/{room}/end`: finalise _first_, then `deleteRoom`, so egress stops cleanly before the room disappears.
3. **Nobody presses anything** (browser crash, tab closed) → LiveKit fires the `room_finished` webhook, signature-verified with the raw body, which calls the same finalise.

`finalizeRecording` is idempotent: it removes the room from the in-memory `activeRecordings` map _before_ any await, closing the re-entrancy window, and it swallows "egress already ended" errors because an unpublished track or a closed room may have stopped it already.

<Mermaid code={`stateDiagram-v2
    [*] --> Idle
    Idle --> Recording: POST /recording/start (409 if already)

## On-disk layout (the filesystem is the database)

```plaintext
recordings/
  consult-1/
    2026-08-17T13-28-44-880Z/          ← one folder per recording session
      doctor_Asha-TR_AMnvJi9WBm6A5J.ogg   (deleted after successful transcription)
      patient_Ravi-TR_Qh8k2…ogg           (deleted)
      EG_abc123.json                      ← egress result, source of startedAt
      manifest.json                       ← {room, session, stoppedAt, tracks[]}
      transcribe.log
      transcript.json                     ← {room, segments:[{speaker, role, start, end, text}]}
      transcript.md                       ← **[MM:SS] Doctor (Asha)**: …
      summary.json / summary.md           ← MedGemma draft
      signed-note.json                    ← write-once
```

Session folder name is `toISOString()` with `:` and `.` replaced by `-`, so a room can be recorded many times without overwriting. The UI parses it back and shows local time.

## Webhook handling done right

LiveKit signs webhooks. Verification needs the _unparsed_ body, so the route uses `express.raw({ type: "application/webhook+json" })` and hands the raw buffer plus the `Authorization` header to `WebhookReceiver.receive`. A bad signature is a 400. Only `room_finished` is acted on. Interview line: "If you JSON-parse before verifying, you cannot verify."

<AnswerModes id="idempotent-finalise" q="A browser can die mid-call. How do you make sure the recording is still finalised exactly once?">
<Fragment slot="short">

Three paths call the same finalise: Stop, doctor End, and the signature-verified room_finished webhook. Finalise removes the room from the in-memory activeRecordings map before any await, so a second caller finds nothing and returns, and it ignores errors from egresses that already ended.

</Fragment>
<Fragment slot="medium">

The webhook covers the nobody-pressed-anything case. Verification needs the raw body, so that route uses express.raw and hands the buffer plus the Authorization header to WebhookReceiver; a bad signature is a 400. End finalises before deleteRoom so egress stops cleanly before the room disappears, and the later room_finished finds an empty map. Trade-off: the map is in memory, so a server restart loses active recordings. <StatusBadge kind="planned" label="Fix: persist sessions" />

</Fragment>
<Fragment slot="deep">

Also cover the poll: stopping an egress is asynchronous and startedAt appears later, so finalise polls listEgress up to 20 x 500 ms. If the poll gives up, startedAtNs is 0 and alignment silently falls back to relative time. The better design is the egress_ended webhook and failing loudly. <StatusBadge kind="hypothetical" label="Improvement" />

</Fragment>
</AnswerModes>

<Reveal q="Why does End call finalise first and deleteRoom second?">

If the room were deleted first, egress could be cut off mid-flush and the start timestamps might never be written (this is the design reasoning; I did not find a test or log that reproduces it). Finalising first stops the recorders cleanly. The room_finished webhook that follows finds the room already removed from the map and does nothing.

</Reveal>
